# issue から始める

入口: [ccnavi 承認ボードの要件](../requirements.md)

| ID | 区分 | 要件 |
|---|---|---|
| REQ-CHR-06 | 事象 | 承認者がボードの「Issue一覧を取得」で開いた issue で「始める」を押したとき、Chrome 拡張は `ccnavi-start.sh` と同じ手順で進むこと。(1) issue を閉じる開いた MR（題・本文の閉じる語（`Closes`・`Fixes`・`Resolves` など）に続く `#<番号>`・`<owner/repo>#<番号>`・`issues/<番号>`。参照しているだけの MR と、元ブランチの名前の番号だけの MR は含めない）を探し、1 本あればその元ブランチを親として採用し、ブランチも MR も作らない（`ccnavi-start.sh` は `--issue` だけで来てこの PC にそのブランチのワークツリーが無いと聞いて止まるが、Chrome は承認者が「始める」を押した操作を同意とみなし、聞かずに採用する。ADR-0161）。採用の確認は、MR が open・フォークでない・マージ先が統合先・ブランチ名が保護された名前でない・ブランチ名の `/` を `-` に置き換えた識別子が使える（64 文字以内、末尾が `-<2 桁>` でない）・同じ識別子になる別のブランチが無い（全ブランチで見る）・統合先の `done/` でクローズ済みでない・互換の版が合う・同じブランチ名のマージ済み MR が無い（ホストに聞く）で、引っかかれば何も作らない。(2) 2 本以上あれば何も作らずに一覧を出して止める。(3) 無ければ、同梱の ccnavi の `ticket_ids.issue_identifier` が issue の番号とタイトルから決めた識別子（`feature-<番号>-<slug>`・`feature-<番号>-<プロジェクト名>-<slug>`）の親のブランチを統合先の今の先頭から作り、初期コミットを積み（GitHub は差分のないブランチから PR を作れない）、本文を `Closes #<番号>` とする Draft の MR を作る。その識別子が統合先の `done/` にある・同じ名前のブランチがある・開いた親子のチケットに同じ識別子がある・予約の名前に当たる・互換の版が違う、のどれかなら作らない。ブランチを作った後に MR を作れなかったときは、作ったことと続きの手（`ccnavi-start.sh --issue <番号>`）を言って止まる（REQ-APV-19） |
