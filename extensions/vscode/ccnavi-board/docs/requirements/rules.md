# ルール管理画面

同じ拡張に「ルール管理画面」がある。ルールファイル（`rules.yml`）を画面で直し、保存する前に「この操作はどう判定されるか」を試し、hook の一覧を見る。判定は実行ファイルの `--test --json` / `--test-expectations --json` で行い、拡張は glob も regex も自分では当てない。

編集する対象は 3 種（ccnavi の docs/guide/rules.md「ルールは 3 つのレイヤーの和で当たる」）。共通の設定のルール（`.ccnavi/config/common/rules.yml`）、ワークスペースの設定（既定 `.ccnavi/config/project/rules.yml`）、プロジェクト 1 つの設定（既定 `projects/<名前>/.ccnavi/config/project/rules.yml`）。サイドパネルからは共通の設定を開く。編集する 1 本は、画面上部の「設定」の欄（共通の設定・ワークスペース・設定のあるプロジェクトの一覧）で切り替える。欄は対象が 2 つ以上あるときだけ出る。タブは 1 枚で、別の対象を選ぶと中身が入れ替わる。未保存の変更があれば、破棄してよいかを聞く。

編集する 1 本とは別に、読み取りの統合結果の表示を持つ。効いているルールは共通の設定との和なので、ワークスペースの統合結果は「共通の設定 + ワークスペースの設定」、プロジェクトの統合結果は「共通の設定 + そのプロジェクトの設定」を出す。パスを持たないツール（Bash など）が当てる、全プロジェクトの設定を足した和ではない（その旨を画面に注記する）。統合結果は実行ファイルが出し（`--explain --json` が持つ合成結果を使う）、拡張は自分では判定も合成もしない。統合結果の表示は読み取り専用で、直すときは編集する 1 本に切り替える。

ワークスペースとプロジェクトの設定ファイルの場所は `--explain --json` の `layers[]` から取るので、実行ファイルが見つからないとその画面はエラーの表示になる。編集中の内容は、共通の設定なら `--rules`、ワークスペースとプロジェクトの設定なら `--project-rules-file <名前>=<パス>`（ワークスペースの設定は `self=<パス>`）で実行ファイルに渡す。

プロジェクトの設定は、親チケットの着手（`ticket start`）で上書きされない。着手が配るのは、共通の設定のミラー（そのプロジェクトの `.ccnavi/config/common/`）だけで、プロジェクトの `.ccnavi/config/project/` には触れない（設計 11.12）。この画面でプロジェクトの `rules.yml` を直して保存した内容は、そのまま残る。ミラーは誰も編集しないファイルで、この画面は開かない。ミラーはワークスペースの中では読まれず、そのプロジェクトを単体で clone したときにだけ共通の設定として読まれる。ミラーの配布は実行ファイルが行い、この画面は何もしない。

保存を止めるのは、共通の設定とワークスペースの設定ならどのツリーに `doing` があっても（どちらも全ツリーの Bash に当たるため）、プロジェクトの設定ならそのプロジェクトに `doing` があるときだけ。

共通の設定とプロジェクトの設定のファイルが無いのは「設定が無い」正常な状態で、画面は空として出し、不備の注意は出さない（ファイルを作って保存すれば置ける）。

実行ファイルがこの設定のファイルを読めず（不正で）空として扱っている（ここのルールは 1 件も有効になっていない）ときは、上部に注意が出る。

見出しの「取り込み待ちを開く」から取り込み待ち画面へ進める（プロジェクトの設定を見ているときは、そのプロジェクトのツリー。それ以外はワークスペースのツリー）。実行ファイルが `handoff` の機能を持たなければ押せず、理由が横に出る。案内の間は押せない。

タブは 3 つ。

| タブ | 何ができるか |
|---|---|
| ルール | `rules.yml` をタイプ（deny / ask / allow）ごとに一覧し、id・match・glob か regex・message・additionalContext（当たるたびにモデルへ渡す文）・additionalContextOnce（文脈で最初に当たったときだけ渡す文）・additionalContextFile / additionalContextOnceFile を直す。match は手でも書けるし、欄を押すと判定が対象を取り出せるツールの選択肢が出て選べる。欄に書いてある知らない名前も選択肢として並ぶ。message は deny だけで、止められたモデルに届く文。additionalContextFile / additionalContextOnceFile は文に続けて本文を渡すファイルで、ルートからの相対パス。「選択…」で VS Code のダイアログから選べ、外のファイルは入らない。一覧は 1 ルール 1 行（id、match、pattern とメッセージの先頭、コンテキストの有無の ●）で、既定は全部畳んである。行を押すとその下に欄が開き、欄名は欄の左に出る。additionalContext 系の 4 欄は「コンテキストの追加」の 1 行に畳んであり、値があるルールだけ最初から開く。開いた行は id で覚えておき、更新のあとも開いたまま。上の絞り込み欄に打つと、id・match・pattern・message・additionalContext に含む行だけが残る（開いている行は隠れない）。見出しの件数は「一致した数 / 全体」になり、一致しないが開いたままの行があればその数も添える。ask と allow に message の欄は無く、残っていれば消すボタンだけが出る。足す（足した行は開いて出る）・消す・上下に動かす・タイプを移す。タイプの見出しの畳むボタンでそのタイプごと畳める。判定に当たったルールは畳んであっても開く。保存の前に一時ファイルへ書いて `--lint` を通し、error があれば保存しない |
| 判定を試す | ツールと対象（`--test` の subject）を入れて `--test --json` に掛ける。判定・根拠コード・当たったルール（翻訳後の正規表現まで）・返る文面と、そのツールで走る hook を出す。「期待する判定を一括で確認する」は `--test-expectations --json` で期待する判定をすべて回し、期待と食い違ったものを赤く出す。どちらも**編集中の内容**で試す（保存は要らない）。「記録から候補を出す」は `--suggest --json` で、判定の記録から `deny` / `ask` の下書き（`rules:` と `expectations:` の組）を並べる。こちらは**保存済みのルール**で確かめた候補で、ルールには足さない（置くのはユーザ） |
| hook | `.claude/settings.json` と `.claude/settings.local.json` の hooks を読むだけの一覧。書き換えない。ユーザごとの設定（`~/.claude/settings.json`）は載らない |

`rules.yml` のキー名は、欄名にマウスを重ねると title として出る。「コンテキストの追加」の中の欄は、キー名をそのまま欄名にしている。対応は次のとおり。

| 欄名 | キー |
|---|---|
| id | `id` |
| ツール | `match` |
| タイプ | `deny` / `ask` / `allow` のどのリストに入れるか |
| パターン | `glob` / `regex`（左の選択が形式、右が値）。組み合わせ条件のルールでは出さない |
| 組み合わせ条件 | `when`（下の「組み合わせ条件」。在るルールではパターンの欄の代わりに図を出す） |
| 除外 | `except`（見せるだけで編集しない。畳んだ行には「除外 N」、開いた行には各パターンを出す。書き戻しは元のまま残し、欄を変えてもタイプを移しても消えない。直すのはルールファイルで。「組み合わせ条件に変換」を押したときだけ、組み合わせ条件の中へ移して消える） |
| メッセージ | `message` |
| every | `every`（空なら当たるたびに渡す。`5` なら 5 回に 1 度で、`additionalContextOnce` はその最初の 1 回＝ 5 回目に届く） |
| additionalContext | `additionalContext` |
| additionalContextFile | `additionalContextFile` |
| additionalContextOnce | `additionalContextOnce` |
| additionalContextOnceFile | `additionalContextOnceFile` |

## 組み合わせ条件（`when`）

ルールは `glob` / `regex` / `when` のどれか 1 つで当てる（`except:` はどれとも併用できる）。`when:` は
ノードを入れ子にした式で、各ノードはキーをちょうど 1 つ持つ。個別条件は `glob: '…'` / `regex: '…'`、演算子は
`all: [ノード, …]`（すべてに当たる）/ `any: [ノード, …]`（どれかに当たる）で 1 個以上、否定は `not: ノード`。
上限は深さ 8（最上位のノードが 1）、ノード数 64（個別条件も数える）。当たる・当たらないは実行ファイルが決め、画面は組み合わせ条件の形だけを扱う。

| 何 | ふるまい |
|---|---|
| 畳んだ行 | 組み合わせ条件を 1 行に縮めて出す。最上位の演算子は中身を並べ、その下の演算子は子の数だけ言う（`all(regex ^{root}[\/], not(any(2)))`）。`not` は段に数えない。書式の誤りがあれば「組み合わせ条件に誤り N」を添える |
| 開いた行 | パターンの欄の代わりに、組み合わせ条件の図（React Flow）を出す。最上位のノードを左に置き、段ごとに右へ伸ばす。個別条件は上から 1 行ずつ、演算子は子の真ん中の高さ。置き場所は組み合わせ条件の形だけで決め、ドラッグでは動かさない（直すたびに置き直す）。図は開いた行にだけ置く |
| 選ぶ | 点を押すと選ばれ（縁が太くなる）、図の下の操作の欄がその点に効く。最初は最上位のノード。選んだ点が消えたら最上位のノードに戻る |
| 子を足す | all / any と、中が空の not に、glob / regex / all / any / not を足す。足した子が選ばれる |
| 消す | 選んだ点を消す。演算子の子なら並びから外し、not の中なら中を空にする（穴の点「空」が出て、押すと中に入れるものを選べる）。最上位のノードは消せない（ボタンの説明に、包んでから直す道を出す）。消したら親が選ばれる |
| 種別を替える | all ⇄ any、glob ⇄ regex だけ。子と文字は持ち越す |
| 個別条件の文字 | 選んだ個別条件の文字を欄で直す |
| all / any で包む | 選んだ点を all / any で包む。最上位のノードが個別条件や not の組み合わせ条件を、組み合わせへ広げる入口（包んだ演算子が選ばれ、子を足せる） |
| not で包む / not を外す | 選んだ点を not で包む。not を選べば外せる（中が空の not は外せない） |
| 読めないノード | 書式が違うノード（キーが 0 個か 2 個以上、知らないキー、値の型が違う、引用符の無い個別条件の値を実行ファイルが文字列以外に読む `yes` `on` `0755` など）は「読み込めない」点として残し、理由と値を見せる。画面では直せないので、消すか「glob に置き換える」。触らなければ読んだ値のまま書き戻す |
| 誤りの一覧 | 図の下に、空の演算子・中が空の not・空の個別条件・読めないノード・深さとノード数の上限超えを並べる。押すとその点が選ばれる。保存を止めるのは保存前の `--lint` で、画面は見せるだけ |
| 組み合わせ条件に変換 | glob / regex 1 つのルールの「パターン」の横のボタン。同じ意味の組み合わせ条件 `all: [本体, not: {any: 除外}]`（除外が無ければ `all: [本体]`）に替え、`except:` は組み合わせ条件の中へ移したので書き戻しで消す。組み合わせ条件から glob / regex 1 つへは戻さない。`except:` がリストでない・要素が glob / regex 1 つのマップでない・空のルールと、`glob` と `regex` を両方書いたルール（変換すると片方が黙って消える）では押せず、理由をボタンの説明に出す |
| 両方書いてある | `when` と `glob` / `regex`、または `glob` と `regex` を両方書いたルールは、上部の注意に出す。画面は組み合わせ条件のほうを見せ、組み合わせ条件を直さなければ両方そのまま書き戻す（止めるのは lint） |

書き戻しの決まり。

- **変えていない組み合わせ条件には触らない。** 読み込んだときと同じ組み合わせ条件なら、`when:` のコメントも引用符もそのまま
- **変えた組み合わせ条件は元のノードを使い回す。** all ⇄ any や個別条件の文字の変更はキーと値だけを書き換える。子は同じ中身のノードを
  先に当てるので、子を消したり並べ替えたりしても、残った子のコメントは自分に付いたまま。残りは、前後で当たった子に挟まれた
  元のノード（消されていない子は元の相対順のまま）に、数が同じなら順に当て、違えば似たもの（個別条件なら文字が前か後ろで重なるもの）
  どうしだけを当てる。消した子のコメントを別の子に付けない。先頭の子の前のコメントも、その子を消せば一緒に消える。
  包む（not・all / any）・not を外すときは、元のノードを中に使い回し、そのノードと中の子のコメントを残す（外した not の
  前置きのコメントは中身へ移す）。新しい個別条件は単引用符で囲む。引用符の無い個別条件の値が実行ファイルの読みで文字列以外になるなら囲む
- **変換してもコメントを残す。** 元の `glob` / `regex` と `except:` の各要素に付いていたコメント（前置き・行末）は、
  対応する個別条件に付けたまま移す。`except:` のキーの前のコメントは `not` の前へ移す
- **組み合わせ条件を書いたら `glob` / `regex` を消す。** 変換や編集で組み合わせ条件になったルールに、元のパターンを残さない。`when:` は `match` の直後に置く
- **`except:` を消すのは変換のときだけ。** 組み合わせ条件を直しただけでは消さない（組み合わせ条件と併用できる）
- 判定を試す・サンプルを一括で判定・保存は、どれも組み合わせ条件を書き戻した内容を実行ファイルに渡す（試すのに保存は要らない）

「判定を試す」の「対象」は `--test` の subject。

次のことを守っている。

- **判定は実行ファイルが出す。** 拡張は `--test` の答えを並べるだけで、glob も regex も自分で当てない。
  hook の「走る／走らない」だけは matcher を拡張で当てる（Claude Code の hook の登録であって ccnavi の判定ではない）
- **作業中のチケットがある間は保存できない。** 着手済みのチケット（`.ccnavi/approved/doing/` にあり `started_at` を持つ）が 1 件でもあれば（どのワークツリーでも）、
  編集はできるが保存ボタンが押せない。hook はツール呼び出しのたびにルールを読み直すので、セッションの途中で
  判定が変わるのを避ける。ボードの JSON が読めないときも保存しない（確かめられないときは止めるほうを選ぶ）
- **外で変わったら上書きしない。** 読み込んだときの更新時刻と保存時のそれが違えば止める。編集中に
  `rules.yml` や `settings.json` が変わると上部に「ファイルの変更を検知しました。更新してください。」と出るので、更新してから直し直す
- **コメントを残す。** `rules.yml` のコメントと折り返しは、変えていない場所ではそのまま。変えた欄も
  引用符や折り返しの書き方は元のまま。新しく足すルールは glob / regex を単引用符で囲む
- **記録を汚さない。** 試し打ちは `--ticket-control disable --state "" --log ""` で走らせ、`decisions.jsonl` に残さない
- 上部に、実行ファイルが答えた動作モード（`--explain --json` の `settings.mode`）が `dry-run` か `disable` のときの注意が出る。`dry-run` は判定と記録をして、一般の保護は止めず、チケットの関門と補助の保護は止めること、`disable` は判定しないことを言う。読めない値は実行ファイルが `enable` と答えるので注意は出ない。試す判定は enable のときの答え
