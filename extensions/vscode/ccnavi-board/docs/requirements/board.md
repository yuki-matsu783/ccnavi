# チケット管理画面（ボード）

列は 未着手 / 作業中（承認済み・レビュー待ちを含む）/ 完了 / 取り消し。保存先のフォルダとの対応は、未着手 = `wip/proposals/todo/`、作業中 = `.ccnavi/approved/doing/` と `wip/proposals/review/`（レビュー待ちはカードの札「レビュー待ち」で分かる）、完了 = `.ccnavi/approved/done/`、取り消し = 同じ `done/` で `cancelled_at` を持つもの。

カードは上から、見出し（ID・題・状態の札）、位置、ユーザ待ち、注意、フェーズ行（親だけ）、補助の操作、詳細（畳む）の順に並ぶ。表示する量は絞り、ひと目で「状況」と「ユーザ待ちか」が分かることを優先する。詳しい値は詳細に畳み、開きたいときだけ見る。

**状態の札は「状況」、操作欄（ユーザ待ち）は「ユーザができること」。** 別の規則で決め、同時に出てよい（例: 札「要確認」と［承認］）。札は見出しの右端に 1 つで、言葉を必ず出す（色だけに頼らない）。札の規則は上から順に適用し、最初にヒットしたものを採る。判定は実行ファイルの JSON が持ち、ボードは判定済みの欄（`blocked`・`scattered`・`pending_approval`・`gate_closed`・`review_waiting`・`cancelled_at`・`close_early`・マーカー）を表示の言葉に置き換えるだけで、レビューの要否・ゲートの条件・リスクは判定し直さない。

- 子: 1. `blocked` か `scattered` がある → 要確認（理由はツールチップ）／2. 承認待ち → 承認待ち／3. 取り消し（アーカイブも同じ）→ 取り消し／4. 完了の列、または取り消しでないアーカイブ → 完了／5. 置き場がレビュー待ち（`wip/proposals/review/`）→ 自分のフェーズの一言（レビュー待ち／レビュー準備中／レビュー予定。ほかは要確認）／6. 置き場が作業中 → フェーズがレビューで止まっていれば要確認、`started_at` が空なら開始前、あれば作業中／7. どれにもヒットしない → 要確認（読めた欄をツールチップに出す）
- 親（レビューの状態はフェーズ一覧から見る。親カードの `gate_closed` は使わない）: 1. 要確認（同上）／2. 承認待ち（承認済みの親に改版が出ていれば「承認待ち（改版）」）／3. 取り消し／4. 完了（早めに閉じていれば「完了（早めに終了）」。アーカイブも）／5. どれかのフェーズがレビュー待ち → レビュー待ち／6. どれかのフェーズがレビュー準備中 → レビュー準備中／7. 作業中の置き場 → 開始前／作業中／8. 要確認

フェーズ行の一言は、`gate_closed` かつ `review_waiting` → レビュー待ち、`gate_closed` → レビュー準備中、`marks.reviewed` → レビュー済み、`marks.skipped.deferred_to` があり引き受け先のフェーズに `marks.reviewed` → レビュー済み、`deferred_to` がある → レビュー予定、`marks.skipped` → レビュー省略、`state` が ended／active／planned → 終了／進行中／これから、ほか → 要確認（上から順）。`marks` の中身は JSON に載っているので、ボードはそれを読むだけ。

「ユーザ待ち」は、ユーザができることがあるカードにだけ出す。主ボタンは 1 つ。親: 承認待ちなら「内容を確認して承認してください」と［承認］。レビューの操作は各フェーズ行に置く。子: 承認待ちなら［承認］、札が「レビュー待ち」なら「マージリクエストでレビューしてください」と［MR を開く］（リンク）と［レビュー完了］。どちらでもなければ出さない（札が「要確認」の子にレビューの操作は出さない。取り消した子にも出さない）。承認は `pending_approval` だけを条件に出す。操作してよいかの最終判断は実行ファイルが持つ。

注意の行は、例外のときだけ短い言葉で出す: 不備・書き込み停止中・先行待ち・リスク HIGH 以上・複数の場所にある・ワークツリーなし（閉じていないものだけ）・未送信（親の `ahead` が 1 以上）。理由の全文は詳細に畳む。

札の「開始前」と「作業中」は、承認済みで `started_at` が空か、あるかで分ける。承認の直後は作業中の列に入るが、`start` するまでは範囲の確かめが行われない。そこで列は変えず、札で区別する。`start` するのはエージェントで、ユーザの対応を求める状態ではないので、注意の行には出さず、要対応の判定（`attention`）にも含めない。`started_at` はボードが実行ファイルの答え（`copy` と同じ行）から読むだけ。「承認済み」「着手済み」の常時表示は画面から消した（チケットのファイルにだけ残る）。

「先行待ち（<識別子>）」は、子が挙げる先行（`predecessors`）のどれかが `done/` に無いか取り消し済みのため、承認と着手（`start`）が止まっていることを表す。tooltip では、承認待ちのカードなら承認も着手も止まり、承認済みで未着手なら着手が止まる、と書き分ける。着手済み・レビュー待ちのカードでは「先行チケットの条件が未達成（<識別子>）」になり、作業と `finish` は止まらないことを示す。書き込みはどちらでも止まらない。どの先行が何の状態かは注意の行の tooltip と詳細に出る。数えるのは実行ファイル（`predecessors_unmet`）で、ボードはその結果を表示するだけ。

「複数の場所にある」は、同じ ID のチケットが別々の保存先のフォルダ（`doing/` と `done/` など）に残っていて、どれを正とするか決まらないときに付く。こうなるのは、移動が途中で止まったときか、先に進んだワークツリーがまだ合流していないとき。子のワークツリーに承認済みチケットがあるだけなら、正とする側が決まるので付かない。正とするのは親のツリー（親自身なら自分のツリー）にある側で、そこに無ければ元ツリー（ワークスペースルート。プロジェクトのチケットならそのプロジェクト）にある側。ただし親のツリーが無く、元ツリーより先のフォルダに合流していない承認済みチケットがあるときは、どれを正とするか決めずに付く。別のリポジトリにある同じ ID は同じチケットと見なさず、1 件にまとめずに数える。`todo/` が並んでいれば、ほかのフォルダが違っていても付かない（同じフォルダの重複があるときだけ付く）。

レビューが済むまで止まっている間は、札とフェーズ行の一言に段の名前を出す。依頼を出すまでが「レビュー準備中」で、次に動くのはエージェント。出してからレビュー済みまでが「レビュー待ち」で、次に動くのはユーザ（判定はこれを JSON の `review_waiting` で示す）。レビューが済んだカードには出ない。依頼のマーカー自体は残り、経緯として `ccnavi --explain` の文には出る。マーカーの名前は画面には出さない。

詳細（初期状態は畳む）には、MR・issue・ブランチ・ワークツリー名・プロジェクト・取り消しの理由、不備・書き込み停止・複数の場所の理由の全文、カードのリスク（`riskLevel`・`riskPoints`）とフェーズのリスク（`risk_line`。JSON の文言のまま）、人間レビューの要否と理由、フェーズごとのレビューの要否、リモートとの差（未送信・遅れ）が入る。ここのリンクは普通のリンクのままで、ボタンの寸法にしない。base / 合流の sha、マーカー名は画面に出さない。詳細の開閉はカードごと（プロジェクトと ID の組）に Webview の状態として覚え、更新や列の移動でも閉じない。案内の見本では、開閉を実際の状態として扱わない。

親カードにはフェーズの一覧が 1 フェーズ 1 行で付く。左の丸がフェーズ（終了は緑の塗り、進行中は青の輪）、右が状態の一言。手で動かした子の確認待ち・移動が未共有など、ユーザが対応する注意（`manual`）は行の下に 1 行で出す。レビュー待ちの行には、行の中に［MR を開く］と［レビュー完了］（主ボタン）を置く。複数のフェーズが同時にレビュー待ちなら、それぞれの行に置く。フェーズ一覧の幅が 300px 以下では、名前と状態を縦 2 段にする。止まっているフェーズは名前も状態も赤になる。

上部の見出しには、承認待ちと不備の件数を 1 件以上のときだけ出し、残りと全体は薄く添える。

上部の「要対応のみ」を入れると、ユーザが対応する必要があるカードだけが残る。要対応かどうかは実行ファイルが決め（JSON の `attention`）、ボードはそれで絞るだけ。カードのバッジと不備の行は、その理由の表示にあたる。

その隣の「アーカイブ済みチケットを表示」を入れると、5 つめの列「アーカイブ」が出て、Draft を外したとき（`ccnavi-review.sh ready`）に手元の `logs/archive/` へ退避した閉じたチケットが並ぶ。既定は外してあり、列ごと出ない。アーカイブのカードは表示だけで、操作もバッジも持たず、上部の件数（残り・全・不備）にも数えない。押すと退避したファイルを開く。

このPCに親のワークツリー（`.claude/worktrees/<親>`）が無い親は、ほかのツリーのコピーでは代用しない。チケットはボードに出ない。

依頼のマーカーが持つマージリクエストは、レビュー待ちの子のカードとフェーズ行の［MR を開く］（ボタンと同じ寸法のリンク）と、詳細の普通のリンクで出て、既定のブラウザで開く。リンクはマージリクエスト自体を指す（依頼の投稿の `#` から後ろは除く）。http(s) 以外の URL はリンクにしない。ボードのレビュー待ちの表示はリモートを見に行かず、マージ状況は「マージ状況を確認」を押したときだけ聞く。

列は画面の幅に合わせて伸び縮みし、1 列が 220px より狭くなるとき（エディタを分割したときや、サイドパネルが広いとき）だけ横スクロールになる。列の見出しを押すと、その列を見出し 1 行ぶんの幅に畳める。列の右端をドラッグすると幅を固定でき、ダブルクリックで元の伸び縮みに戻る。幅を固定した列も、畳めば見出し 1 行ぶんに縮み、広げると固定した幅に戻る。畳んだ列・列の幅・絞り込みは更新しても残る。

ユーザの承認はボードのオーバーレイで行う。「承認」を押すと、拡張が `ccnavi --agree --preview --json` を子プロセスで打ち、承認先行の一覧（いま承認待ちのもの全部）の本文・対象外の提案・読めない提案をボードの上に出す。「この N 件を承認する」を押すと `ccnavi --agree --yes <識別子,…> --json` を打つ。実行ファイルは「見せた提案（識別子の一覧と各提案ファイルのバイト列全体）が今も同じ」ことを確かめてから承認済みチケットを置き、違えば何も置かない。そのときボードは「内容が更新されました」と伝えて一覧を読み直して出し直し、もう一度押してもらう。この経路ではターミナルからの起動（stdin が tty）を求めない。エージェントが Bash で同じ形のコマンドを打っても、実行ファイルの組み込みの deny が止める。

一覧に計画（`plan:`。改版や立案で `feedback:` も）を持つ親があれば、オーバーレイは本文の上にその計画の図を、計画ごとに 1 枚、読むだけで出す。中身は `--agree --preview --json` の `plans` で、承認する提案そのものの順序（ステップの番号・直接の先行）。点は番号・定義の題・見る場所（本文と同じ言葉の短い形。「レビュー不要」「レビュー必須（MR）」）と、子が承認された番号の印。延期したステップは見る場所の代わりに引き受け手を本文と同じ言い方で出す（「レビューは 5 と一緒に」）。先行の無いステップへ「開始」から、後続の無いステップから「終了」へ、図だけの仮の線を引く（保存しない。フィードバック計画では「全体計画のレビュー後」「親をクローズする」）。最後のステップの先行になっていないステップ（`loose`）は、点の縁とそのステップから終了への線を注意の色で描く。図の下に、すぐ始まるステップ（`ready`）、延期の引き受け手、最後のステップの先行になっていないステップ（「最後のステップの先行になっていない: …。最後のステップへ線を引くか、合流のステップを置く」）、順序の検査の理由（`problems`）を出す。どれも実行ファイルの答えをそのまま描くだけで、画面は判定しない。開いたときは全体を枠に収めるが、倍率 0.7 より縮めず（文字が読めなくなるため）、収まらなければ開始の側から見せ、残りはパンで見る。図は拡大・縮小・全体表示ができるが、点は動かせず、線は引けず、点も線も選べない。`plans` が無い・空なら図は出ない。

図は親ごとにまとめ（全体計画とフィードバック計画は同じ親の 2 枚）、その前に「計画を編集」を置く。押すとオーバーレイを閉じてから、その親の計画編集タブ（docs/requirements/workflow.md）を開く。開いたままにしないのは、タブで保存すると提案が書き換わり、オーバーレイが見せていた一覧はダイジェストが変わってもう承認できないため。承認はタブで保存したあとに開き直す。承認している最中は出さない。計画を持たない親（図の無い親）には出ない。

親の計画編集タブに未保存の変更があれば、その一覧は承認できない。その親の図の上に「計画編集タブに保存していない変更があります。保存するか破棄するまで、この一覧は承認できません。」を出し、「この N 件を承認する」を押せなくして、その上に「親 <親> の計画編集タブに未保存の変更があります。保存するか破棄してから承認してください」を出す。未保存の順序のまま承認して、直したつもりの順序と違うものが通らないように。タブで線を変えて ccnavi の答えを待っている間（「確認しています…」）も、未保存と同じに扱う（答えを待つ間に承認が通らないように）。拡張は押されたときと、承認を打つ直前にも同じことを確かめ、ヒットすれば打たない。タブを閉じた・案に戻した（破棄した）・保存したら、その場で押せるようになる。

タブで保存したあとに提案が変わっていれば、図の上に「計画編集タブで保存したあとに、提案が変わっています（エージェントが変更した可能性があります）。図を確認してから承認してください。」を出す。拡張は保存で返った `source_sha`（親と子の提案をまとめたハッシュ）を覚えておき、オーバーレイの一覧が返ったときに `plans` の `source_sha` と比べる。図は今の提案をそのまま描くので、エージェントが `after` を書き戻して保存した順序を黙って戻しても、ユーザが気づける。承認は止めない（今の提案の中身はダイジェストで縛られていて、図はそれを見せている）。保存を押してすぐタブを閉じても、書けていればハッシュは覚える。覚えたハッシュは、ボードを読み直したときに承認待ちの提案が無くなった親（ボード・ターミナル・Chrome 拡張のどこで承認しても、取り下げても）のぶんを忘れ、VS Code を閉じれば消える。

承認できたら、同じオーバーレイが「N 件を承認しました」に替わる。Claude Code に渡すプロンプト（承認された識別子と後工程の進め方）は、「コピー」「新しいセッションで開く」「ターミナルで実行」の 3 ボタンで渡す。「コピー」ならプロンプトをコピーし、「新しいセッションで開く」なら `vscode://anthropic.claude-code/open?prompt=…` で新しいセッションの入力欄に入れる。送信はユーザが Enter で行う。「ターミナルで実行」は、Claude Code の CLI（`claude`）が PATH にあるときの経路で、プロンプトをファイルに書き、専用の新しいターミナル「ccnavi claude」で `claude -p --permission-mode auto < <ファイル>` を実行する（許可は auto モードの自動承認）。確認のダイアログは挟まず、押すとすぐ、確認なしで無人実行される（ファイルの変更や git の操作が起きうる）。専用の新しいターミナル「ccnavi claude」で実行するので、承認の push の sh が走っている「ccnavi」ターミナルとは入力を取り合わない。結果は拡張が受け取らず、ターミナルに流れるだけ。止めるには、ターミナルで Ctrl+C を押す。追加の送信もできない（続けるときは、ターミナルで `claude --continue` を打つか、拡張のセッションで開く）。hook は承認をモデルに知らせない。進行中のセッションで続けるときは、このプロンプトを貼るか、エージェントに `ccnavi-ticket.sh status` で承認済みチケットの状態を確かめさせる。プロンプトには、承認はユーザが済ませたこと、承認を頼み直さないこと、前の会話が無くても `ccnavi-ticket.sh status` で状況を確かめられることも入る。

レビューを終えるには、フェーズ行（または札が「レビュー待ち」の子のカード）の［レビュー完了］を押す。「レビューの対応」のメニューと「レビュー済み連絡」は廃止した。拡張は `ccnavi-review.sh decide <N> --preview` で未解決の指摘と digest（指摘一覧の照合用の値）を読み、**厳しく検証する**。次のどれかなら件数を出さず「指摘を読み取れませんでした（理由）」とし、確定のボタンも出さない: 子プロセスが失敗した・出力が JSON でない・最上位がマップでない／`version` が想定外／`parent` が文字列でない、または頼んだものと違う／`phase` が整数でない、または頼んだものと違う／`mr.number` が整数でない、またはフェーズ行の依頼が持つ MR の番号（分かるとき）と違う／`digest` が無い・文字列でない・`v2.` で始まらない／`threads` が無い・配列でない／スレッドの要素がマップでない・`key` が空か文字列でない・`key` が重複する・`body`・`url`・`path` が文字列でない・`line` が整数でない（不正な要素は破棄せず、全体をエラーにする）。URL が http(s) でないことはエラーにしない（リンクにしないだけ）。

正しく読めて未解決が 0 件なら「フェーズ N に未解決の指摘はありません」と主ボタン「レビュー済みにする」。1 件以上なら、承認と同じオーバーレイに指摘が 1 件ずつ並び、それぞれに対応方針（対応しない・このフェーズで直す・issue に回す）を選ぶ。選択肢は同じ寸法の切り替え（ラジオの意味とキーボード操作は保つ）。本文は 1 行目を出し、「全文」で開ける。URL は http(s) のときだけリンク。ボタンが押されたら `ccnavi-user-decide.sh decide <N> --choices … --digest …` を子プロセスで打つ（ホストを読むのは sh）。全部の指摘に選ぶまで主ボタン「この対応方針を確定」は押せず、置いている最中はオーバーレイを閉じない（連打しても 1 回）。置けたら、結果は実行ファイルの答えに従って出す。`reviewed` が真ならレビュー済み。偽で `pending_extra` があれば「表示した後に指摘が追加されたため、レビュー済みにしていません」と言い、続きの子が起きていなければ［指摘を読み直して決め直す］で戻れる。決めた結果のプロンプトは、承認と同じ 3 ボタンで渡す。文の末尾には、前の会話が無くても `ccnavi-ticket.sh status <親>` で状況を確かめる案内が付く。親を早めに閉じる `close-early` はボードに出さないので、ターミナルで `ccnavi-user-close-early.sh` を打つ。

副ボタン「エージェントに相談するプロンプトをコピー」は、指摘が 1 件以上のときだけ出る。オーバーレイは閉じず、選びかけの対応方針も変えない。確定中は押せない。コピーできたら短く知らせ、できなければ失敗と言う。プロンプトは `commands.ts` の `consultPrompt` が組み、親・フェーズ・MR の URL・親のワークツリーを書く。許すのは親のワークツリーで読み取り専用の `decide <N> --preview` を単体の Bash で実行することだけ（cwd が違えば先に `cd` だけを別の Bash で）。未解決の指摘を 1 件ずつ要約し、対応方針の案と理由を返させる。対応方針を確定する `ccnavi-user-decide.sh`・`ccnavi-review.sh confirm`・その他の状態を変える操作は実行させず、決めるのはユーザで、ボードの「レビュー完了」から行うと書く。末尾に `ccnavi-ticket.sh status <親>` で状況を確かめる 1 文が付く。

「マージ状況を確認」（ツールバー。通常の色）は、片付けの記録（`retire/<親>.json`）を持つ親のマージリクエストが、マージ済みかを確かめる。押している間は「確認中…」で押せず、二重に走らせない。一覧は実行ファイルの `sync retired` から取る。頭の行が `retired 1` でない・コマンドが失敗した・未知の行がある・`retired` の行の項目が足りないときは「一覧を取れない（形式の異常）」とエラーを出し、「ありません」とは言わず、行を知らないうちに破棄しない。`incomplete` の行は「確認できない（記録が不完全: 理由）」として出す。正しく取れて両方とも 0 件のときだけ「マージ待ちの親はありません」と言う。対象ごとに、そのリポジトリを cwd にして `ccnavi-review.sh mr-state <番号>` を聞く（1 回ごとに 45 秒の期限を付け、失敗はその親だけに留めてほかを続ける）。答えは次をすべて満たすときだけ正常とみなす: 1 行目が `mr-state 1`・2 行目の最初の語が既知の状態（`open`・`merged`・`closed`・`unknown`）・項目の数が状態ごとの数・番号が頼んだ MR と同じ・Draft が `yes` / `no`・終了コードが状態と合う。ほかは「出力の形が想定外」。sh が想定外の終了コードで終わったときは「実行できない」。期限切れは拡張の側だけの種類 `timeout` で、sh の `unknown` の種類（`no-tool`・`auth`・`network`・`api`・`not-found`）には入れない。結果はボードが開いている間だけ拡張ホストが持つ（タブを隠して画面が作り直されても残り、閉じて開き直すと消える）。閉じたボードや前の確認から遅れて返った結果は破棄する。

帯の行の題は、アーカイブの同じ親（プロジェクトと ID が一致するもの）から取り、無ければ ID だけを出す: マージ待ち（Draft なら付記）と［MR を開く］／マージ済みと［片付ける］／マージせず閉じた（自動では片付けず、破棄した親ならユーザがターミナルで `ccnavi-launcher.sh worktree retire --abandon <親>` を実行して記録を消す。コマンドはコピーのボタンだけで、ボードからは送らない）／確認できない（種類と理由）。確認した時刻も出す。［片付ける］は、確認のダイアログ（`ccnavi-sync.sh <親>` を実行する。sync はリモートの取り込みも行い、MR がマージ済みかを確かめ直したうえで、条件を満たすものだけを片付ける。結果はターミナルで確認する）で「実行する」と答えたあと、ボードのターミナルに `cd <ルート> && sh <ルート>/.ccnavi/scripts/ccnavi-sync.sh <親>` を送る（ルート・パス・親は単引用符で引用する）。ダイアログを開いている間と送信中は、同じ親の［片付ける］を押せないようにする。送れたら行を「片付けのコマンドを送信しました。結果はターミナルで確認してください」にして、次に「マージ状況を確認」を押すまで押せなくする。送れなかったら「送信できませんでした」と理由を出して押し直せる。送信の成功は実行の成功ではない。完了は検出しないので、再確認のあとにもう一度送れる。sync の側の安全策（MR の再確認・削除の条件）は変えない。

| 「詳細」 | カードの詳細を開閉する。開閉はカードごとに覚え、更新や列の移動でも閉じない。押してもカードのファイルは開かない |
| ツールバーの「マージ状況を確認」 | 片付けの記録を持つ親のマージリクエストの状況を聞き、上の帯に出す。確認中は押せない |
| 帯の［片付ける］ | 確認のダイアログのあと、`cd <ルート> && sh <ルート>/.ccnavi/scripts/ccnavi-sync.sh <親>` をボードのターミナルに送る。ダイアログ中・送信中は再入させず、送ったら次の確認まで押せない |
| 帯の「コマンドをコピー」 | マージせず閉じた親の、記録を消すコマンドをコピーする（ボードからは送らない） |
| ［MR を開く］（レビュー待ちの行・子のカード） | 依頼のマーカー（`marks.requested` の `mr` / `url`）の URL から `#` 以降を除いたマージリクエスト自体を開く。http(s) 以外の URL はリンクにしない。リンクの上ではカードを開かない |
| 「要対応のみ」 | ユーザが対応する必要があるカードだけを出す。要対応かどうかは実行ファイルが JSON の `attention` で返し、ボードは組み直さずにそれで絞る（条件は ccnavi の docs/requirements/json-shapes.md「ボードの JSON」）。不備の行も実行ファイルの `issues` をそのまま出す。プロジェクト・親の絞り込みと重ねて適用され、列の件数と「承認待ち N 件を承認」もその分になる。選択は Webview の状態として覚える |
| 「アーカイブ済みチケットを表示」 | 手元の退避（`logs/archive/`。実行ファイルの JSON の `archived[]`）にある閉じたチケットを「アーカイブ」の列に出す。既定は外していて、外している間は列もカードも出ない。入れると、右端に足されたアーカイブの列まで横へスクロールする。プロジェクト・親・要対応の絞り込みと重ねて適用される（アーカイブのカードは要対応に入らない）。`logs/archive/` の変化も監視するので、`ready` の後に自動で読み直る。選択は Webview の状態として覚える |
| プロジェクトの絞り込み | `projects/` があるときだけ出る。選択は Webview の状態として覚える |
| 親の絞り込み | 親チケットが 1 つでもあれば出る。選んだ親とその子だけを出す。プロジェクトの絞り込みと重ねて利用できる。選択は Webview の状態として覚える |
| 絞り込みと件数 | 列の見出しの件数と「承認待ち N 件を承認」の N は、絞り込みで見えている分の数になる。上部の「残り／全／不備／承認待ち」はボード全体の数のまま |
| 動いた表示 | 前の読み直しから列が変わったカード（承認された、レビュー不要で閉じた、レビューが済んだ、取り消された）と、新しく現れたカードに緑の輪と帯が出る。帯は「未着手 → 作業中」「新規起票」のように書く。新しく現れたカードの帯には行き先を書かない。置かれた列を見れば分かる。着手（`ticket start`）は列を動かさないので動いた表示は出ない。時間では消さず、次に何かが動くまで残す。開いた直後は出ない。列が動いていないボードが渡し直されても（オーバーレイの出し入れ、何も変わらなかった「更新」）作り直さない。読み直せなかった画面を挟んでも、最後に読めたボードと比べる。色だけに頼らず帯の文で伝え、`prefers-reduced-motion` では光らない。覚えるのは拡張ホストで、画面が作り直されても表示は残る。パネルを閉じると消える（`core/board-moved.ts`） |
| 「更新」 | ボードを読み直す。押すとすぐに非活性になり、回り記号と「更新中…」に替わる。読み直しが終わると HTML が作り直され、新しい画面のボタンは活性で出る。失敗したときは更新ボタンごとエラー画面に差し替わるので、やり直しはコマンドパレットの「チケット管理を更新」から。実行ファイルが 60 秒で返らないときは打ち切って失敗として見せる。監視による自動の読み直しと、コマンドパレットの「チケット管理を更新」では、ボタンの見た目は変わらない |

- 提案（`wip/**/proposals/`、全ワークツリーの同じ場所）・承認済みチケットとマーカー（`.ccnavi/approved/`）・
  ワークツリーの登録（`.git/worktrees/`、`projects/*/.git/worktrees/`）を監視し、変化が 120 ミリ秒
  止まったら自動で読み直す。オーバーレイの状態は拡張側が持つので、読み直しで HTML が作り直されても消えない
- 承認の後も、承認済みチケットが `.ccnavi/approved/doing/` に置かれたことで読み直す
- それとは別に、承認の側からも読み直す（`approval-machine.ts` の `refresh`）。承認済みチケットの置き場は
  固定で、`core/watch.ts` の監視するパスとずれない。この読み直しは `files.watcherExclude` で置き場を外したときも動く。
  重なった読み直しは 1 回にまとめられる（`board-panel.ts` の `again`）
- 対象はワークスペースの最初のフォルダだけ。`projects/` 配下のプロジェクト向けチケットも
  同じボードに出る（詳細の「プロジェクト」）
- レビューのスレッドの現状は、［レビュー完了］を押したとき（`decide <N> --preview`）と、「マージ状況を確認」を押したとき（`mr-state`）だけ sh が取りに行く。監視による自動の読み直しでは取りに行かない
- 実行ファイルが無い、JSON が読めない、版が違うときはボードを開かず通知で伝える。
  開いている間に読めなくなったら、前の表示を消して理由を出す

カードの中の操作ボタン（［承認］・［レビュー完了］・フロー・計画編集・テンプレートの下書き）と、操作として置いた［MR を開く］リンクは、共通の `button.action` を使わず、`card-button`（主ボタンは `card-button primary`）を付ける。`Card.css` で文字サイズ・高さ・余白を明示し、親（カード・フェーズ一覧・列）の文字サイズを引き継がない。幅に収まらない言葉はボタンの中で折り返す。主ボタンは「ユーザの番の操作」だけで、操作のまとまり（「あなたの番」と各フェーズ行）ごとに 1 つまで。補助の操作（フロー・計画編集・テンプレートの下書き）は通常の色。カードの中で縦に広がるメニューは使わない。詳細の中のリンクは普通のリンクのままで、`card-button` を付けない。決まりは [docs/design/screens.md](../design/screens.md) にも書く。

## 案内

ヘッダ右上の「?」から、基本の案内と使い方ごとの案内を選べます。案内の間は、見本（`tours/board.yml` の `sample:`）を描きます。実際のチケットにも拡張ホストにも触れません。基本の案内のすぐ次に、「作業を頼んでからマージするまでの流れ」の案内が並びます。この案内は、次の順にたどります。issueを用意する（人がGitLabで作る場合と、エージェントに頼む場合の2通り）、Claude Codeに頼む、MRを用意する（エージェントが作る場合と人が作る場合）、承認、作業、MRでのレビュー（指摘が残ったときの対応の子チケットと再レビューを含む）、MRの画面でのマージ、片付け。ボードの外の画面（GitLabのissueの作成、Claude Codeの入力欄、GitLabのMRの作成とマージ、差分の吹き出しと「Start thread」）は、画面を保存した画像で見せます。画像は、吹き出しを画面の中ほどに広く出し、本文の下に置きます。
