# 計画編集タブ

同じ拡張に「計画編集タブ」がある。承認待ちの親の提案（`todo/` にある、計画を持つ親。新規の親と改版の提案の両方）の作業・レビュー計画（全体計画 `plan:` とフィードバック計画 `feedback:`。旧称ワークフロー）のステップどうしの先行（`after`。どのステップにどのステップが先行するか）を図で引き直す。エージェントが計画に書いた先行（案）を、ユーザが承認の前に直すための画面。

フロー編集画面と同じ形の専用のタブで、違いは 3 つ。

| | フロー編集（子のフロー） | 計画編集（親の計画の順序） |
|---|---|---|
| 編集の元 | 承認済みの領域のフロー。エージェントの下書きは「提案あり」から取り込む | `todo/` の提案の `plan:` / `feedback:`。開いたときの中身がそのまま初期値で、取り込む段は無い |
| 書くのは | 拡張 | 実行ファイル（`ccnavi --plan-order <親> --order <JSON> --expect <ハッシュ> --write`）。拡張はファイルを書かない |
| 保存先 | 承認済みの領域（エージェントは書けない） | 親の提案と、番号の変わるステップを指す子の提案（どちらもエージェントも書ける）。開いたときのハッシュと違えば書かない |

**画面は判定しない。番号も振り直さない。** 線を変えるたびに、元の番号（いま提案に書いてある番号）での直接の先行を `ccnavi --plan-order <親> --json --order <JSON>` に渡し、実行ファイルが振り直した番号・順序の検査の理由（`problems`）・最後のステップの先行になっていないステップ（`loose`）・書けるか（`writable`）・付け替える子の提案（`children`）を答える。画面はその答えを描く。番号の振り直しの決まり（先行が全部前に並んだステップのうち、元の番号がいちばん小さいものから順に番号を振る。子が承認された番号は動かさない）は実行ファイルの 1 か所にある。

`--plan-order` は `user agree` の外の独立したフラグ。書き換えたあとの承認はダイジェストに縛られるので、保存したら、承認はボードから開き直す。

| 何 | どう出るか、何が起きるか |
|---|---|
| 開き方 | ボードの親の提案のカードの「計画編集」（全体計画を持つ承認待ちの親の提案だけ。実行ファイルがボードの JSON の提案の `has_plan` で言う）、承認のオーバーレイの「計画を編集」（計画の図のある親ごと。オーバーレイを閉じてから開く）か、親の識別子を渡すコマンド（`ccnaviBoard.openWorkflow`）で開く。コマンドパレットには出さない（開く親を選ぶ段が無い）。タブは親ごとに 1 枚で、同じ親をもう 1 度開けば前面に出す。開くと `ccnavi --plan-order <親> --json` を打ち、何も書かない。開けない（親の提案が承認待ちに無い・計画が無い・実行ファイルが無い・古い・非 0 終了・JSON でない）ときは、タブの中に理由と「再読み込み」を出す。古い実行ファイルは `--version --json` の `flags` に `--plan-order` `--order` `--expect` `--write` が無いことで見分け、使わない |
| 図 | 全体計画とフィードバック計画は別の図。点は計画のステップで、番号・定義の題・見る場所（延期なら引き受けるステップ）を出す。言葉は承認のオーバーレイの図と同じ（同じ部品）。start と end の仮の点（フィードバック計画は「全体計画のレビュー後」「親をクローズする」）を描き、先行の無いステップへ start から、後続の無いステップから end へ線を引く。どちらも図だけのもので保存しない。最後のステップの先行になっていないステップ（実行ファイルの `loose`）は縁と end への線を注意の色にし、図の下に理由を出す。子が承認された番号は薄くし「子が承認済み」を付ける |
| 線を引く | ステップの右の点から別のステップの左の点へドラッグすると、元のステップが線の先のステップの先行になる。並びの逆向き（大きい番号から小さい番号へ）も引ける。自分へ・start と end に触れる線・循環になる線・子が承認された番号へ入る線は、引いている最中に断る（放しても線はできない） |
| 線を消す | ステップどうしの線の真ん中の × で消す（先行でなくなる）。start と end の仮の線と、子が承認された番号へ入る線には × が無い |
| 振り直し | 線を変えるたびに実行ファイルに聞き直し、答えが届くまで「確認しています…」と出して線を変えさせない。答えの番号で名札を付け直す。点の置き場所は動かさない（振り直す前の番号で覚える）。「並べ直す」で今の線から置き場所を組み直す。実行ファイルが線を断った（循環・子が承認された番号へ入る線・空いた番号に詰められない）ときと、聞けなかったときは、線を引く前の形のまま理由を出す |
| 案に戻す | 提案に書いてある先行と番号に戻す（往復しない） |
| 保存（「この順序に決める」） | 押せるのは、線を変えていて、実行ファイルの答えが書ける（`writable`）ときだけ。押せない理由はボタンに出す（順序の検査の error・改版の錠・子の提案を付け替えられない・確かめている途中・外で変わった・提案が無くなった）。押すと、番号の変わるステップと、付け替える子の提案（旧識別子 → 新識別子、`phase:` の旧 → 新、`predecessors` の直し）と、計画の値の中のコメントが消えることを一覧で見せ、「保存する」で `--write` を打つ。書けたら書き換えた提案を読み直し、通知で知らせる。書かなかったら実行ファイルの理由を出す。書き換えた提案はコミットされない |
| 計画と食い違う子 | `phase:` が親の計画の番号に無い子の提案（実行ファイルの `mismatched`）は、一覧に出すだけで保存は止めない |
| 外で変わったとき | 提案の置き場を見張り、動いたら `--plan-order <親> --json` を打ち直してハッシュを比べる。違えば「提案が外で変わりました」の帯と、番号ごとに「開いたとき／いま」の定義と先行の差分を出し、「取り込む（編集を破棄する）」か「編集を続ける（保存はできない）」を選ばせる。線の答えのハッシュが開いたときと違うときと、保存の `--expect` が合わなかったとき（何も書かない）も同じ帯を出す |
| 承認待ちから無くなった | 親の提案が `todo/` から無くなったら（ボードの答えで見分ける）、図を読むだけにし、新規の親の提案で承認済みなら「順序を変えるには改版を出す」、承認済みチケットが無ければ取り下げ・削除と出す。改版の提案（開いたときの答えが改版）は、承認されても取り下げられても承認済みチケットが残って見分けられないので、「承認されたか、取り下げ・削除されました」と言い切らずに出す |
| 未保存 | 線を変えて提案と違えば未保存。タブの題の頭に「●」、ツールバーに「未保存」を出す。VS Code の Webview には閉じるのを止める仕組みが無いので、閉じた後に未保存だったら「開き直して戻す」「破棄する」を聞く。戻すのは、提案のハッシュが閉じた時点から変わっていないときだけで、変わっていれば戻せないと言う。同じ親のタブが既に開いていれば戻さない |
| 再読み込み | 未保存なら確かめてから、提案を読み直す |
| ボードの承認との結び付き | 未保存の間と、線を変えて答えを待っている間は、ボードの承認のオーバーレイでこの親を含む一覧を承認できない（理由が出て、承認のボタンを押せない。拡張は承認を打つ直前にも確かめる）。題の「●」と「未保存」は答えが届いてから出す。タブを閉じた・案に戻した・読み直した・保存したら外れる。保存すると、書いたあとの `source_sha` を拡張が覚え（保存を押してすぐ閉じても覚え、そのときは戻すかを聞かない）、承認のオーバーレイの一覧の `source_sha` がそれと違えば「保存したあとに提案が変わっています」の注意が図の上に出る（承認は止めない）。どちらも拡張の中だけで持ち、VS Code を閉じれば消える（docs/11_requirements/board.md） |
| 初回の案内 | 初めて開いたときだけ吹き出しの案内を出す（図・直す手段・この順序に決める・承認との関係・ヘッダ右上の ?）。? からいつでも出せる。図を出せない答え（計画が空）では、案内の間だけ見本の計画（実行ファイルの答えの実例をコピーしたもの）を読むだけで出し、「案内のための見本」の帯を付ける。閉じたら消え、見本は線の頼みにも保存にも使わない |
| 読み直しの見え方 | フロー編集と同じ `retainedHost`。中身が届くのは「再読み込み」「取り込む」と保存が通ったときだけで、外で変わっただけのときは帯が出る |
