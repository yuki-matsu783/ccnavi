# ccnavi ボード（VS Code 拡張）

ccnavi のチケットが、どのワークツリーでどこまで進んでいるかをカンバンで見る。

この拡張が何をするか（画面ごとのふるまい）は [docs/requirements.md](docs/requirements.md)、作り（構成・画面の段取り・テストの ID）は [docs/design.md](docs/design.md) に書いてある。この README には、必要なもの・組み立てと導入・動かし方・手動確認の手順だけを書く。

## 必要なもの

| もの | 版 |
|---|---|
| VS Code | 1.90 以上 |
| ccnavi の実行ファイル | 探す順は、設定 `ccnaviBoard.binPath` → `.claude/settings.json`（`settings.local.json` が優先）の `CCNAVI_BIN_PATH` → `dist/ccnavi/ccnavi[.exe]` → `.ccnavi/scripts/ccnavi-launcher.sh` → ソースがあれば `uv run python -m ccnavi`。振り分けの sh（名前が `ccnavi-launcher.sh`）を指していれば、sh を通さず `../bin/<os>-<arch>/` にあるこの OS と CPU 向けの実行ファイルを使い、無ければ次の候補へ進む（Windows では sh を直接起動できないため、sh そのものは使わない）。それ以外のパスは、そのまま実行ファイルとして使う |
| 実行ファイルの版 | 起動のときに 1 度 `--version --json` を聞き、互換の版（`compat`）が拡張の `EXTENSION_COMPAT` と違うか、`--version` を知らない古い実行ファイルなら通知を出す。通知では、どちらが古いかと直し方（ccnavi のリポジトリなら `build.py` で組み立て直し、配布先なら `scripts/ccnavi-setup.sh --force` で配り直し、拡張が古ければ入れ直し）を示す。画面は止めない（ccnavi の README「版の JSON」） |
| bash | clone / fetch / pull を送るターミナル。承認と未解決の指摘の対応方針はこのターミナルを通らない（子プロセスで打つ。sh はこのシェルで走らせる）。Windows は Git Bash（`C:\Program Files\Git\bin\bash.exe`、無ければ PATH の `bash`） |
| git | PATH にあること。プロジェクト管理画面が origin を読み、ターミナルで clone を打つ |
| Node.js / pnpm | 22 以上 / 10。組み立てとテストにだけ要る |

## 組み立てと導入

次のコマンドは `extensions/vscode/ccnavi-board/` で打つ。

```sh
pnpm install --frozen-lockfile
pnpm run compile   # tsc -p .（拡張ホスト）と tsc -p tsconfig.webview.json（画面）で型を見て、esbuild で out/webview/<名前>.js と out/extension.js にバンドルする
pnpm test          # 全部（203 本。9.5〜11.5 秒）
pnpm test:rules    # 領域だけ。board / rules / risk / phases / projects / shared
pnpm test:dom      # happy-dom で画面のスクリプトを動かすものだけ（*.dom.test.ts）
pnpm test:for src/core/rules-doc.ts   # 触ったファイルが関わる領域だけ
pnpm test:plan src/core/rules-doc.ts  # 何を回すかだけ出す（走らせない）
pnpm run package   # scripts/package.sh: install → compile → vsce package（テストは回さない）
```

`pnpm run package` は `dist/ccnavi-board-<version>.vsix`（リポジトリの `dist/`、gitignore 済み）に出力する。`<version>` は `package.json` の `version` の値。出来上がったパスは package の最後にも表示される。Marketplace には出さない。入れるには次を打つ。

```sh
code --install-extension dist/ccnavi-board-<version>.vsix --force   # --force は入れ替えのとき
```

入れたあと、開いているウィンドウは再読み込み（`Developer: Reload Window`）すると新しい版になる。

入れたときの `[DEP0169] DeprecationWarning: url.parse() ...` は `code` コマンド自身の警告で、拡張とは関係ない。`successfully installed` が出ていれば入っている。

テストの入口は `scripts/test-groups.js` の 1 本で、`pnpm test` とその仲間はすべてここを通る。回すグループを決め、`clean-out` → `tsc -p tsconfig.test.json` →（要るときだけ画面の型の検査）→ 画面のバンドル → `node --test <出来上がったファイル>` の順に進む。グループをいくつ選んでもコンパイルは 1 回で、`src/` と `test/` を全部見るので、絞っても短くならない（3〜4 秒）。短くなるのは実行（全部で約 4.6 秒）と、画面の型検査を省けるぶん（1.5 秒）。

バンドルは、画面の型を見ないときでも必ず回す（`clean-out.js` が `out/webview` を消すため）。バンドルするのはスクリプト（`<名前>.js`）と CSS（`<名前>.css`）の 2 本で、CSS は小さくしない。小さくしても減るのは数 KB なので、開発者ツールで読めるほうを選ぶ。

どのグループがどのファイルを読むかは、テストの `import`（CSS は `@import`）を辿って決める。辿れないものだけはパスで決める。その決まりは `test-groups.js` の先頭にまとめてあり、固定データ `test/fixtures/` は全部のグループを回す。画面 `src/webview/` は、辿れたぶんとバンドルしたものを読むグループを回す。組み立てに使う `package.json`・`tsconfig*.json`・`scripts/`・`pnpm-lock.yaml` は全部を回し、文書 `*.md` と画像 `media/` は何も回さない。`out/`・`node_modules/` は数えない。テストが 1 つも読まないファイルは `tsc` だけ通す。`test/<グループ>/` を増やすときに直すのは、`package.json` の行 1 本だけ。

`test/shared/` は 5 画面を比べるので、バンドルした画面を読む。そのため `shared` を含む計画には必ず画面の型検査とバンドルが付き、`src/core/` の大半は `shared` を含む。絞って減らせるのは 1 ターンあたり 2.5〜4.5 秒。

ワークスペース側の hook（`.claude/hooks/mark-ext.sh` と `test-ext.sh`）は `pnpm test:for` と同じ仕組みで動く。拡張のファイルを触ったターンの終わりに、関わるグループだけが回る。

テストは画面の領域ごとのディレクトリに分けてあり、一部を直したときはその領域だけを流せる。組み立てと HTML の文字列を見る単体テスト（`*.test.ts`）と、画面を happy-dom で実際に動かすテスト（`*.dom.test.ts`）を同じディレクトリに置く。ボードの画面は React なので、何を描くかも動かして見る（`board/render.dom.test.ts`）。React は押した直後には描き直さないので、操作のあとは `await page.settle()` を挟んでから見る。

`pnpm test` と `pnpm run compile` は、tsc の出力（`out/src` と `out/test`）を先に消す。esbuild がバンドルした `out/extension.js` は消さないので、package の compile → test の順でも入口は残る。出荷物の型検査は `tsconfig.json`（`src/webview` を除く。lib は DOM 無し、拾う型は node と vscode だけ）と `tsconfig.webview.json`（`src/webview` だけ。lib に DOM、JSX は `react-jsx`、`noEmit`。JS を出すのは esbuild のほう）の 2 本に分かれている。テストは `tsconfig.test.json`（`skipLibCheck`。happy-dom の型定義が `@types/node` 22 と合わないため）。

実行時の依存は `yaml`（コメントを残して書き戻すため）の 1 つ。開発時の依存に happy-dom と react / react-dom を足してある（画面はバンドルして配るので、実行時の依存にはしない）。vsix には `node_modules/` を入れず、`scripts/bundle.js`（esbuild）が本体ごと `out/extension.js` にバンドルする。テストはバンドルする前の `out/src/` を使い、画面だけはバンドルした `out/webview/<名前>.js` を使う。`out/webview/` は vsix に入る。拡張が起動時に読んで `<script nonce>` に流し込むので、Webview の `localResourceRoots` は空のままでよく、CSP も nonce だけで済む。

生成物を消すときは `pnpm run clean`（`scripts/clean.js`）。消すのは `node_modules/` と `out/` の 2 つだけで、引数は取らない（`rm -rf` はルール `recursive-delete` が止める）。ワークツリー（`.claude/worktrees/<名前>`）でこの拡張を組み立てたら、`git worktree remove` の前にこれを走らせる。走らせないと、`node_modules/.pnpm/` が残って削除が途中で止まることがある。

## 拡張開発ホストで動かす

1. `pnpm install && pnpm run compile`
2. VS Code で `extensions/vscode/ccnavi-board/` を開く
3. `F5`（実行とデバッグ → 拡張機能）で拡張開発ホストを起動する
4. そのウィンドウで、ccnavi を入れたリポジトリ（`.ccnavi/common/` を持つフォルダ）を開く
5. コマンドパレットから `ccnavi ボード: チケット管理を開く` を実行する

## 手動確認の手順

`extension.ts` / `board-panel.ts` / `rules-panel.ts` / `risk-panel.ts` / `phases-panel.ts` / `flow-panel.ts` / `prompt-handover.ts` / `projects-panel.ts` / `sidebar.ts` / `terminal.ts` / `ccnavi.ts` / `git.ts` は、VS Code の API か子プロセスに触れるので単体テストの対象外。次の項目を拡張開発ホストで確かめる。チケットのある状態を作るには、`tests/ticket/test_board.py` の `scene()` と同じ手順（親を承認、子を着手・閉じる、次の子を提案）を実際のリポジトリでたどる。

| # | 確認すること | 手順 | 期待 |
|---|---|---|---|
| 1 | ボードが開く | `チケット管理を開く` | 4 列と、上部に残り・全件・不備・承認待ちの件数 |
| 2 | カードでファイルが開く | カードをクリック。ボードのタブに戻ってから Tab で別のカードへ移り Enter | どちらも提案の Markdown がプレビューで開く（素のテキストではない） |
| 2b | ファイルが無い | 提案のファイルを消した直後（ボードが読み直す前）にそのカードをクリック | 「チケットのファイルを開けませんでした」の通知が出て、カードが消える |
| 2c | プレビューが無い | 拡張の一覧で組み込みの「Markdown Language Features」を無効にしてからカードをクリック | 提案の Markdown がエディタ（素のテキスト）で開く |
| 3 | 自動更新 | ボードを開いたまま、別のターミナルで `sh .ccnavi/scripts/ccnavi-ticket.sh finish <子>` | コマンドを打たなくてもカードの属性が「レビュー待ち」になる（レビュー不要なら完了へ動く） |
| 3a | 動いた表示 | 3 の直後、動いたカードを見る | レビュー不要の子なら完了の列へ動き、そのカードにだけ緑の輪と「作業中 → 完了」の帯が出る。レビュー要で属性が「レビュー待ち」になっただけのとき（列は作業中のまま）は動いた表示が出ない。他のカードにも出ない。もう 1 度「更新」を押しても（何も動いていなければ）表示は消えない。次に別のカードが動くと、表示はそちらだけに移る |
| 3b | 更新の手応え | ボードの「更新」を押す | 押すとすぐにボタンが非活性になり、回り記号が回って「更新中…」になる。読み直しが終わると「更新」に戻って押せる。畳んだ列・絞り込みは残る |
| 3c | 更新できない | 返らない実行ファイルを設定 `ccnaviBoard.binPath` で指して「更新」を押す。用意するのはその OS が直接起動できる形（`#!/bin/sh` と `sleep 999` を書いて実行ビットを立てた sh）。シェルを介さず起動するので、実行ビットとシェバンが無いと 60 秒待たずに即エラーになる。**Windows ネイティブでは試せない**（シェルを介さないので `.sh` も `.cmd` も直接は起動できない。Windows で確かめるときは WSL 側の VS Code で行う）。**名前を `ccnavi-launcher.sh` にしない**（振り分けの sh として読み飛ばされ、本物の実行ファイルで成功してしまう） | 60 秒はボタンが「更新中…」のまま（待っている間に別のタブへ移って戻ると webview が作り直され、活性の「更新」に戻る）。そのあと「ccnavi --explain --json が失敗しました: 60 秒で返らないので打ち切りました」のエラー画面に替わる。更新ボタンごと消えるので、やり直しはコマンドパレットの「チケット管理を更新」 |
| 3d | 画面が作り直されない（React） | ボードを縦にスクロールし、列を 1 つ畳んでから、別のターミナルで提案を 1 枚足す（監視が読み直す） | カードは増えるが、スクロール位置も畳んだ列もそのまま。開発者ツール（`Developer: Toggle Developer Tools`）の Console に CSP の拒否（`Refused to execute inline script`）が出ていない |
| 3f | 裏にいる間の見た目の切り替え（保持しない画面の代表。プロジェクト管理も同じ流れ） | ボードのタブを裏に回し、コマンドパレットの「ccnavi ボード: 見た目を切り替える」で配色を変える。ボードを表に戻す | 戻したボードが新しい配色になる。組み上がる（`ready`）までの一瞬だけ古い配色が見えてよい（裏にいる間の切り替えは送らず、`ready` で送り直す） |
| 4 | 承認 | 未承認の提案を置き、「承認待ち 1 件を承認」を押す | ボードの上にオーバーレイが出て、ID とタイトルの表と承認画面の本文が並ぶ。「この 1 件を承認する」でオーバーレイが画面の中央のまま「1 件を承認しました」に替わり、カードが承認済みになる。「コピー」で承認の文がコピーされてオーバーレイが閉じる。「新しいセッションで開く」で Claude Code の新しいタブに文が入る。右下の通知は出ない |
| 4a | 承認したら動いて見える | 4 の承認の後、オーバーレイを閉じる | カードが未着手から作業中の列へ動いていて、緑の輪と「未着手 → 作業中」の帯が付いている。閉じた拍子に動いた表示が消えない。監視を切った状態（`files.watcherExclude` に `**/.ccnavi/**` と `**/wip/**` を足す）でも、承認の後は同じように動く |
| 4a2 | タブを移って戻る | 4a の後、承認の文を「新しいセッションで開く」で渡し、Claude Code のタブからボードのタブへ戻る | 画面は作り直されるが、輪と帯は付いたまま（動いた表示を持っているのは拡張ホスト）。作り直すので、輪がもう一度光る |
| 4b | 一覧が変わった | オーバーレイを出したまま、別のターミナルで `wip/proposals/todo/` に提案をもう 1 枚置き、「この 1 件を承認する」 | 承認済みチケットは置かれず、オーバーレイが「表示した一覧と今の一覧が違います」の注意付きで 2 件に読み直される |
| 4c | やめる | オーバーレイで「やめる」か Esc | 何も置かれず閉じる |
| 4d | 1 件だけ承認 | 同じ親の子を 2 枚承認待ちにして、片方のカードの「この 1 件を承認」を押す。もう一度同じ手順でオーバーレイを出し、別のターミナルでもう片方の提案に書き足してから「この 1 件を承認する」 | オーバーレイに出るのはその 1 件だけ。承認すると、もう片方は承認待ちのまま残る。書き足しても 1 件のまま承認される（絞った 1 件の中身は変わっていないため）。押した 1 件の提案を `wip/proposals/todo/` から消してから押すと、「表示した一覧と今の一覧が違います」の注意付きで承認待ち全部に戻る |
| 4e | 承認できない | 3c と同じ実行ファイルを指して「承認待ち N 件を承認」を押す | オーバーレイが 60 秒「承認待ちの内容を読み込み中…」のまま。そのあと「ccnavi --agree --preview --json を 60 秒で打ち切りました。何も承認していません」と出て、「閉じる」で閉じられる。この 60 秒の間に監視が読み直しを起こすと、そちらも打ち切られてエラー画面が画面ごと覆う。そのときは binPath を戻して「チケット管理を更新」すると、残っていたオーバーレイが出てくる |
| 4f | 承認が途中で切れる | `--yes` が引数にあるときだけ返らず、それ以外は本物の ccnavi に渡す実行ファイルを指して、オーバーレイの「この N 件を承認する」を押す | オーバーレイのボタンが 60 秒「承認中…」のまま。そのあと「ccnavi --agree --yes を 60 秒で打ち切りました。…」と出る。binPath を戻して「チケット管理を更新」すると、打ち切られるまでに置かれたぶんが承認済みで出る（コミットと push は送られていない） |
| 4g | 承認が途中で書けない | 子の承認済みチケットのフォルダ（`.ccnavi/approved/doing/`）に、その子と同じ名前のディレクトリ（例 `i0001-01-01.md`）を作ってから、親と子をまとめて承認する | 「ccnavi --agree --yes が i0001-01-01 で止まりました: 書けない（…）。i0001 の 1 件は承認済みチケットに入っています。コミットと push はターミナルに送っていません…」と出る。ボードを更新すると、親だけが承認済みで出る。止まるまでに出た行（マーカーを消した、など）があれば、文面の末尾に改行区切りで続く。書けたあとの後始末（マーカーを置く）で落ちたときは「…の後始末で止まりました」に変わる |
| 5 | 未解決の指摘を決める | レビュー待ち（依頼済みで止まったまま）で未解決の指摘が付いたフェーズの「対応方針を決める」を押し、指摘ごとに対応方針を選んで「この方針で決める」 | 全部に選ぶまで押せない。押すと「反映中…」で閉じられず、反映できたら決めた文とコピー・新しいセッションで開くが出る。「このフェーズで直す」を選んだ分は続きの子チケットがボードに現れ、issue に回した分はマージリクエストのコメントに issue への参照が残る |
| 5b | レビュー済み連絡 | 同じフェーズの「レビュー済み連絡」を押す。「コピー」で貼る。もう一度押して「新しいセッションで開く」 | オーバーレイに「フェーズ N のレビュー済み連絡」と、親のワークツリーで `confirm --phase N` を打つ文（マージリクエストの URL 付き）。マーカーもターミナルも動かない。貼った文でエージェントが `confirm` を打ち、止まっていたのが解ける。「新しいセッションで開く」で Claude Code の新しいタブに同じ文が入る |
| 5c | マージリクエストのリンク | 依頼済みのフェーズ行と親カードの「MR #N」を押す | 既定のブラウザで、フェーズ行は依頼の投稿、親カードはマージリクエストが開く。提案のプレビューは開かない |
