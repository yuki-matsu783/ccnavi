# ccnavi

ccnavi は、Claude Code を使った開発を、ルール・チケット・必要時の情報参照・振り返りで支えるツールです。
Claude Code の hook でツール呼び出しを止め、止めた理由と代わりに取る手段を返す、というガードが出発点です。
いまは、止めるだけでなく、作業を合意からレビューまで進め、必要な資料を必要なときに引き、記録から次の作業の決まりを良くするところまでを受け持ちます。

## コア機能

| # | コア機能 | 何をするか | 主な入口 |
|---|---|---|---|
| 1 | ルールによる作業のガードとガイド | ツール実行とファイル操作をルールに照らして判定し、止める・人間に確認する・注意点や進め方を伝える。拒否には理由と代わりの手段を添える。ルールが関係する場面で、理由・注意点・手順を届ける | [ルール](docs/guide/rules.md)、[ツール実行後チェック](docs/guide/hooks.md) |
| 2 | チケットによる作業・レビュー管理 | 作業の目的・範囲・計画をチケットで管理し、人間の承認、フェーズの進行、先行との依存、子への分担、レビュー、指摘への対応を経て、合意した作業をレビューまで進める。ワークツリーとサブエージェントの連携、実績の差分に基づくリスク評価、計画テンプレートの利用を含む | [チケット](docs/guide/tickets.md)、[レビュー](docs/guide/review.md) |
| 3 | ドキュメント・スキルの検索と必要時の参照 | 文書とスキルの本文を最初から全部は渡さず、目録と索引で読む対象を絞り、本文はエージェントが必要になったときに読む。ccnavi 自身のヘルプに限らず、ワークスペースとプロジェクトの文書・作業手順を引く | [ドキュメントの索引](docs/guide/docs-search.md)、[プロジェクトのスキル](docs/guide/tickets.md) |
| 4 | 記録と振り返りによるルール・作業手順の改善 | 判定の記録、作業・レビューの気づき、振り返りから、ルール・作業手順・スキル・文書・計画テンプレートの改善候補を見つけて提案し、人間が採ったものを次の作業に活かす | [記録と振り返り](docs/guide/records.md)、[設定の確かめ方](docs/guide/check.md) |

### 1 つ目と 3 つ目の違い

どちらも「必要な情報をモデルへ届ける」仕組みだが、届くきっかけが違う。

- ガードとガイド（1）: 操作や作業の状況がきっかけになる。判定は ccnavi の hook 処理が、モデルのコンテキストの外で行う。
  モデルがルールを読んで自発的に守ることには依存しない。関係する場面（拒否・確認・通すとき・ターンの終わりなど）で、
  その場に要る理由・注意点・手順が届く。「ルールを全部コンテキストに入れてから判定する」仕組みではない
- 検索と必要時の参照（3）: エージェントが情報を必要としたときに、自分で資料や手順を探して読む。
  ccnavi は何を読めばよいかを絞る目録と索引を用意する。

どちらも、不要な情報を最初から入れず、同じ説明を重ねて渡さないための設計である。
ただし、渡す量が減ることやルールが守られることは保証しない。

### 設計原則

4 つのコア機能に共通する原則が 3 つある。

- **必要な情報を、必要なタイミングで届ける。** 作業の前提と情報への入口は開始時に示す（セッション開始時に作業の決まりの要点、文書の引き方、
  プロジェクトのスキル目録を渡す）。具体的な理由・注意点・ガイドは、関係する操作や作業の段階で届ける。詳しい文書やスキルは、必要なときに検索して読む。
  開始時に何も渡さない、という意味ではない
- **人間の判断を残し、その経路を守る。** 作業の合意（承認）、必要なレビュー、改善の採否は人間が決める。承認やガード自身の変更を、
  エージェントが無断で代行できる形は作らない（承認の入口は組み込みの deny が止め、ガード自身は自己防衛が守る）
- **作業とレビューを、単一 PC・単一セッションに閉じ込めない。** 作業の分担・引き継ぎ・レビューを、親のブランチに載るチケットとマーカー、
  成果物、マージリクエスト上のレビューでつなぐ。承認者やレビュアーは、作業者のセッションの外から操作できる。
  同期は fetch と push が前提で、リアルタイムではない。前提と制約は[複数人・別 PC・別セッションで進める](docs/guide/multi-pc.md)に書く

### コア機能を支える仕組み

次のものは 5 つ目・6 つ目のコア機能ではなく、コアのどれかを支える仕組み、操作の入口、利用範囲である。

| 仕組み | 支えるコア | 役割 |
|---|---|---|
| ツール実行前・実行後のチェック | 1 | 実行前は引数を判定する。引数に現れない書き込みは、実行後に git の差分で拾う |
| 保護領域の変更検知・復元 | 1 | 実行後チェックで、`deny` と宣言された場所の変更を見つけ、ユーザへ報告し、`CCNAVI_RESTORE_IF_DENY` が `enable`（既定）なら元に戻す |
| ガード自身の保護（自己防衛） | 1 | hook の登録・設定ファイル・実行ファイルを書き換えから守る |
| 判定ログ、dry-run、診断・設定検証・判定テスト（`--lint` `--test` `--explain`） | 1、4 | ルールを入れる前後に判定を確かめる。判定ログは 4 の入力にもなる |
| ワークツリー | 2 | チケットごとの作業場所。ほかの作業と影響し合わない |
| リモート経由の共有・同期（`ccnavi-fetch.sh` `ccnavi-sync.sh`） | 2 | 親のブランチを運び手に、別 PC・別の人へ作業をつなぐ |
| 実績に基づくリスク評価 | 2 | 子の差分から点を付け、高いものを人間のレビューに引き上げる |
| フェーズ・フロー・計画テンプレート | 2（使う）、4（完了した作業から作る） | 使うのは作業の進め方の再利用。完了した作業の計画・フローからテンプレートの下書きを起こすのは改善 |
| VS Code の拡張（ボード）と Chrome の拡張（承認ボード） | 2 | チケットの状態を見て、承認・レビュー済みなどの人間の操作を受ける入口 |
| 複数リポジトリ（ワークスペースとプロジェクト） | 1、2、3 | ルール・チケット・文書の索引を、ワークスペースと下のプロジェクトにまたがって扱う |

用語は [CONTEXT.md](docs/CONTEXT.md)、要求は [requirements.md](docs/requirements.md)、設計は
[docs/design.md](docs/design.md)、判断の理由と経緯は [docs/adr/](docs/adr/README.md) にある。
「承認済みチケット」「マーカー」「ワークツリー」「直接作業」のような呼び名は用語集で定義している。

## 導入

どんなコマンドが打たれ、ルールが何に当たるかは、動かしてみるまで分からない。`dry-run` で導入し、記録を読みながら
ルールを直し、記録が落ち着いてから `enable` に切り替える。

1. `dry-run` で立てる。実行ファイルを組み立て、hook を登録し、`CCNAVI_MODE` を `dry-run` にする
2. 普段どおり開発する。ccnavi は判定だけを記録し、呼び出しには手を出さない
3. 記録（`logs/decisions.jsonl`）を読む。止めた回、どこにも当たらなかった回、通した回を数える
4. ルールを直す。直したら `ccnavi --lint` と `ccnavi --test` で確かめる
5. 記録が落ち着いたら `CCNAVI_MODE` を `enable` にして、セッションを開き直す

手順の詳細と記録を読む `jq` の例は [docs/guide/install.md](docs/guide/install.md) にある。

## 設定とルールの最小例

設定は環境変数で、`.claude/settings.json` の `env` ブロックに書く。hook には実行ファイルだけを登録すればよい。
`sh scripts/ccnavi-setup.sh <ワークスペースルート>` が、何度打っても同じ形になるよう書く。

```json
"env": {
  "CCNAVI_MODE": "dry-run"
}
```

ルールファイルは YAML で、`deny` `ask` `allow` の 3 つのタイプに分かれる。

```yaml
version: 1

deny:
  - id: force-push
    match: Bash
    glob: "*git push*--force*"
    message: リモートの履歴を書き換えます。送り直したい理由をユーザに伝えてください。

ask:
  - id: migrations
    match: Write|Edit
    glob: "*/migrations/*"
    additionalContext: 移行ファイルは実行前にユーザが中身を見る。何が変わるかを先に言うこと。
```

環境変数の全表と hook の登録は [docs/guide/settings.md](docs/guide/settings.md)、ルールの書き方は [docs/guide/rules.md](docs/guide/rules.md) にある。
