# learn

人が頼んだ気づきを、気づきの記録に 1 件足す。足すだけで、wiki・スキル・ルール・配点・フェーズ定義は直さない（直すのは提案と承認の流れ。`docs/design/tickets/learning-wiki.md`）。

## 手順

1. 頼まれた内容を、次の作業でも使える 1 件の文にまとめる。会話の引用・日付・チケット番号・エラー文・絶対パス・コマンドの全文・秘密の値は書かない
2. 種類を決める。決められなければ省く（省けば「未定」になる）

   | 種類 | 直す対象 |
   |---|---|
   | `rule` | ルール（rules.yml） |
   | `risk` | リスクの配点（risks.yml） |
   | `phase` | フェーズ定義（phases.yml） |
   | `template` | 作業・レビュー計画のテンプレート |
   | `skill` | スキル・スキルの references |
   | `docs` | 文書 |

3. 信号を決める。省けば `訂正`。`訂正`（ユーザの訂正・苛立ち）、`落とし穴`、`失敗と回避`、`誤り`（読んだ手順や文書の誤り）のどれか
4. 次を打つ。`--note` の本文は 1 つの引数として、引用符で囲む。

   ```sh
   sh .ccnavi/scripts/ccnavi-ticket.sh learn --note "<まとめた文>" [--target <種類>] [--signal <信号>]
   ```

   ワークツリーの中ではワークスペースルートの絶対パスで打つ（`sh <ワークスペースルートの絶対パス>/.ccnavi/scripts/ccnavi-ticket.sh learn ...`）。
5. 出力のパスをユーザに伝える。チケットに結び付いたワークツリーなら `wip/handoff/learnings/` の記録。チケットに結び付かない直接作業のワークツリーなら、そのワークツリーの `docs/wiki/inbox/` の受信箱のファイル。ワークスペースルート（とプロジェクトのルート）では書かずに断られるので、ワークツリーを切って打ち直す。コミットは、通常の作業のコミットに含める

## 注意

- 1 回の依頼で複数の気づきがあるときは、1 件ずつ打つ
- 本文が空、または内容が決まらないときは打たずに、ユーザに何を覚えるのか聞く
- 「ccnavi が learn を通さない」と出たら迂回せず、ユーザに `.ccnavi/scripts/ccnavi-ticket.sh` の更新を頼む（保護対象のファイルで、ユーザが置いて効く）
- 識別子を付けるときは、オプションの前に置く（`ticket learn <識別子> --note ...`）。ふつうは付けなくてよい（作業ディレクトリのワークツリーの名前が使われる）
