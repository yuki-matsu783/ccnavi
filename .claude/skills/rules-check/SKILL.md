# rules-check

ルールは書いた瞬間から、当たるつもりのものに当たっているかどうかが分からない。
`glob` は正規表現に翻訳され、Bash のコマンドは実行される部分まで絞られてから
当たる。書いた人の頭の中の当たり方と実際の当たり方がずれても、ずれたことに
気づく手立てが無い。気づかないルールは、足したつもりで何も止めていない 1 行になる。

このスキルはその差を埋める。見本を判定に掛けて、食い違いを名指しする。

## 絶対ルール

- **`.claude/ccnavi/rules.yml` を書き換えない。** ガード自身の設定で、ルールが
  deny している。直す必要が出たら、何をどう直すべきかを言って利用者に依頼する
- **判定を自分で真似しない。** 必ず `ccnavi --test` を通す。正規表現を目で読んで
  「当たるはず」と判断すると、判定と別のことを言うことになる
- **見本を期待に合わせて書き換えない。** 食い違いが出たとき、直すべきは
  ルールか見本のどちらかで、それを決めるのは利用者
- **TodoWrite と Agent ツールを使わない**

## 手順

### 1. 設定が壊れていないことを確かめる

```sh
uv run python -m ccnavi --lint
```

error が 1 件でもあれば、そこで止めて報告する。壊れた設定の上で見本を回しても、
出てくるのはルールの話ではなく壊れ方の話になる。

### 2. 見本を回す

```sh
uv run python testdata/check_rules.py
```

`testdata/rule-samples.yml` の見本をすべて判定に掛ける（中身は `ccnavi --test-samples` で、
`--test` と同じ判定を通る）。区画の名前が期待する判定になる。`deny` なら止まるはず、`allow` なら通るはず、
`ask` なら人に確認が出るはず。

出力は 3 つに分かれる。

| 見出し | 意味 | やること |
|---|---|---|
| 食い違い | 期待と違う判定になった | 手順 3 へ |
| 判定に入らずに通った | 呼び出しは通るが allow に当たったわけではない | 報告する。ルールを書いても当たらない場所 |
| 件数 | 区画ごとの一致数 | 報告する |

### 3. 食い違いを 1 件ずつ調べる

食い違った見本について、判定の中身を見る。

```sh
uv run python -m ccnavi --test Bash "git push origin main"
```

出るのは、判定・根拠コード・当たったルール・`glob` が翻訳された正規表現・
返る文面。どこでずれたかはここで分かる。よくある形は 3 つ。

- **`glob` が文字列全体に当たる書き方になっていない。** `glob` は fnmatch の意味で
  文字列全体に当たる。部分一致が欲しければ前後に `*` を書く。`git push *` は
  `cd /repo && git push` に当たらない。`*git push*` なら当たる
- **語の切れ目が無い。** `*sed*` は `sedate` にも当たる。右側だけなら空白を書いて
  `*sed *` とする。左側は glob では書けないので `regex` を使う
- **`allow` が広すぎて deny より先に見えている、ように見える。** 実際は区画の順で
  deny が先に見られるので、この形なら原因は別のところにある

### 4. 怪しい当たり方を利用者に確認する

食い違っていなくても、次に当たるものは黙って通さずに聞く。

- **権限モードへの委譲（`UNDECLARED`）が多い。** どのルールも言及していない呼び出し。
  同じ場所が繰り返し出るなら `allow` に 1 行足す先が決まっているということで、
  毎回違う場所が出るなら `allow` の粒度が細かすぎる。どちらなのかを添えて聞く
- **`allow` が広すぎるかもしれない書き方。** `*` 単独や、コマンド名を挟まない
  regex は、書いた人が思っているより広い範囲を「人が見なくてよい」に変える
- **`deny` の当たり方が広すぎるかもしれない書き方。** 語の切れ目が無いために
  無関係なコマンドに当たるもの。誤検知の多い拒否は、そのうち文面ごと読まれなくなる
- **`regex` に手を伸ばしているルール。** `glob` で書けるなら `glob` のほうがよい。
  書けない理由があるはずなので、その理由を確かめる

確認は AskUserQuestion で、1 件ずつではなくまとめて出す。聞くのは
「このルールをどうするか」であって「このコマンドを通してよいか」ではない。

### 5. 報告する

書くのは 4 つ。区画ごとの一致数、食い違いの中身と原因、判定に入らなかったもの、
利用者に確認した結果。ルールを直す必要があるなら、どのルールをどう直すかまで
書いて依頼する。直すのは利用者。

## 見本を足す

ルールを 1 件足したり直したりしたら、`testdata/rule-samples.yml` にも足す。
足さないと、あとから読んだ人に「そのルールが何のために在るのか」を伝える手立てが
ルールの文面しか無くなる。文面は止められた側に向けた言葉で、何に当たるかは
書いていない。

見本は `tool` と `subject` と `why` の 3 つ。`subject` は Bash / PowerShell / Monitor なら
コマンド、Read / Write / Edit / MultiEdit / NotebookEdit なら絶対パス、Skill ならスキル名、
Agent なら見出し、WebFetch なら URL。パスの `/repo` は走らせたワークスペースルートに
読み替えられる。

止めたいものだけでなく、**止めたくないものを必ず一緒に足す**。片側だけの見本は、
ルールを広げすぎたことに気づけない。
