# 確かめる

設定は書いた瞬間から、書いたつもりのことをしているかが分からない。glob は正規表現に
翻訳され、Bash はシェルとして読まれ、フェーズの種類は親の計画と噛み合って初めて意味を
持ち、配点は差分に当たって初めて数字になる。ここでやるのは、そのずれを機械に名指し
させ、機械が言えないところを人に聞くこと。

手順は 5 つ。1 で止まったら先へ進まない。壊れた設定の上で見本を回しても、出てくるのは
壊れ方の話になる。

## 1. lint

```sh
ccnavi --lint --log "" --state ""
```

3 本まとめて読む。error が 1 件でもあればそこで止めて報告する。warn は読んで
「意図した防御が効いていない」箇所として拾う。

| 出どころ | error（防御が消える・全部止まる） | warn（判定は動くが意図とずれる） |
|---|---|---|
| `(rules)` / ルール id | 読めない、版が違う、`deny` が空、文面・match・glob を欠く、glob と regex の両方、`ask` `allow` に `message`、組めない正規表現、`additionalContextFile` が上に出る | `allow` が空、id 無し・重複、当てる対象の無いツール、広い allow に文、指すファイルが無い・長い |
| `(phases)` | 読めない、版が違う、`phases` が無い、kind / review の値、feedback が mr でない、id / title の重複、overlap / requires の先が無い、scope が外に出る | 自分を overlap / requires に挙げている |
| `(risk)` | 読めない、版が違う、levels の順、id の重複・形、points が負、当て方が 0 か 2 つ、script の置き場が外、glob が組めない | 知らない段階名 |
| `(ticket)` `(project)` `(mode)` | 承認済みの写しの置き場が守られていない、計画を持つ親があるのに phases が読めない | dry-run、登録の欠け、作業ツリーとチケットの食い違い |

下書きを見るときは `--rules` `--phases` `--risk` で差し替える。3 本は互いに読み合うので
（写しの置き場を rules が守っているか、親の計画が phases を指せるか）、1 本だけ差し替えて
lint しても、本物と組み合わせたときの答えになる。それでよい。

## 2. rules: 見本を回す

```sh
uv run python testdata/check_rules.py            # このリポジトリ。写しと記録を外して回す
ccnavi --test-samples testdata/rule-samples.yml --log "" --state "" --approved ""
```

出力は 3 つに分かれる。

| 見出し | 意味 | やること |
|---|---|---|
| 食い違い | 置いたタイプと違う判定になった | 1 件ずつ原因を読む（下） |
| 判定に入らずに通った | 呼び出しは通るが allow に当たったわけではない（`known` が偽） | 報告する。ルールを書いても当たらない場所 |
| 件数 | タイプごとの一致数 | 報告する |

食い違いには「当たったルール」が出る。よくある形は 3 つ。

- **glob が全体に当たる書き方になっていない。** `git push *` は `cd /repo && git push` に
  当たらない。`*git push*` なら当たる
- **語の切れ目が無い。** `*sed*` が `sedate` に当たる。右は `*sed *`、左は regex
- **タイプの順で強い側が先に当たっている。** allow に置いた見本が deny の `raw-git` に当たる、
  など。この形なら見本の置き場かルールの広さのどちらかが間違っている

単発で試したい形があれば、見本ファイルを scratchpad に書いて `--test-samples` で回す
（`--test` に直接書くと、禁止語を含む Bash 自体が当たる）。`--json` を付ければ翻訳後の
正規表現（`pattern`）と返る文面（`response`）まで出る。

**守られているかも見本で見る。** rules.yml と phases.yml と risk.yml、承認済みの写しの
置き場、settings.json への Write / Edit を deny の見本に置いて回す。ワークスペースルート
直下と、**実在する作業ツリーの名前**での写しの両方。作業ツリーの写しは、ブランチを
統合すればそのまま main の設定になる道を持つ。出るのはルールの判定だけで、組み込みの
守り（settings.json と rules.yml を実行後に戻す働き）は `--test` には出ない。allow に
見えたものは「ルールでは止めていない」ということなので、そのまま報告する。戻す働きに
頼れるのは settings.json と rules.yml だけで、phases.yml と risk.yml にはそれも無い。

## 3. phases: 計画と噛み合うか

lint が通っても、種類が計画と噛み合っているかは lint の外。

```sh
ccnavi --explain --log "" --state ""
```

承認済みの親とその計画が出る。見るのは 4 つ。

- 開いている親の `plan:` / `feedback:` が指す種類が、全部 phases.yml に在るか。無ければ
  その親は次のフェーズを承認できない
- `review: none` の種類が、本当に人が見なくてよい成果か。`when` に「飛ばしてよい条件」まで
  書いてあるか
- `scope` の広さ。子 ⊆ 種類 ⊆ 親なので、種類の scope が親より広くても効かない。逆に狭すぎると
  子の提案が承認で落ちる。rules.yml の deny と重なる場所は deny が勝つ
- `deliverables` に挙げた名前が、その種類の子が必ず作れる名前か。閉じるときに無いと、
  最後の子を閉じられない

## 4. risk: 配点が実績に合うか

配点を差分に当てる道具は `ticket done` しか無い。ここで見るのは、当てたときの数字が
意図に合うかどうかの見積もり。**見積もりであって判定ではない**と報告に書く。

```sh
sh .claude/scripts/ccnavi-git.sh log --shortstat -20
```

- 最近の子 1 本ぶんの差分（行数・ファイル数）を閾値と並べる。普通の子が毎回 HIGH に届く
  配点は宣言の意味を消し、どの子も MEDIUM に届かない配点は入っていないのと同じ
- `glob` の項目は、当たるごとに加点で `max` が無ければ青天井。当たりそうな場所の
  ファイル数を数えて、1 回で CRITICAL に跳ねないか見る
- `script` の項目は、その sh を子の作業ツリーで実際に打つ。`CCNAVI_BASE_SHA` と
  `CCNAVI_HEAD` を環境変数で渡し、標準出力が整数か `{"points": N}` か、失敗したときに
  何も出さないか（重い側に倒れて丸ごと加点される）を見る
- `judge` の問いは、差分だけを読んで yes / no で答えられるか。答えられない問いは、判定が
  揃わずに子が閉じられなくなる

## 5. 利用者に確認する

食い違っていなくても、次に当たるものは黙って通さずに聞く。まとめて 1 回で、
AskUserQuestion。聞くのは「この設定をどうするか」で、「この呼び出しを通してよいか」ではない。

- **権限モードへの委譲（`UNDECLARED`）が多い。** `.claude/ccnavi/log.jsonl` の
  `decision == "handover"` を数える。同じ場所が繰り返し出るなら allow に 1 行足す先が決まって
  いるということで、毎回違う場所なら allow の粒度が細かすぎる。どちらかを添えて聞く
- **広すぎる allow、広すぎる deny。** `*` 単独、語の切れ目の無い glob、コマンド名を挟まない
  regex。誤検知の多い拒否は、そのうち文面ごと読まれなくなる
- **regex に手を伸ばしているルール。** glob で書けないか。書けない理由を確かめる
- **人が見なくてよい種類（`review: none`）と、閾値に届かない配点。** 守っていないことが
  外からは守っているように見える組み合わせ
- **承認済みの親の計画が指す種類を変える提案。** 変えると親の計画が読めなくなる

## 報告

書くのは 5 つ。lint の error / warn の中身、見本の件数と食い違いの原因、phases の噛み合わせ、
risk の見積もり、利用者に確認した結果。直す必要があるなら、どのファイルのどこをどう直すかまで
書いて、[add.md](add.md) の「利用者に渡す形」で依頼する。直すのは利用者。
