# ルールとチケットの判定を合わせ、厳しい側を採る

利用者との相談で B（範囲の外も含めて厳しい側を採る）に決めた。

2026-09-13 18:23 に一度承認されたが、着手の直後に OS が予期せず停止し、提案と承認済みチケットが
中身の無いファイル（全部 NUL）になった。利用者が 2 つを消し、同じ内容で出し直している。
変えたのは、`main` の取り込みで移ったルールの置き場（`.ccnavi/common/rules.yml`）と行番号だけ。

## 何をなぜ変えるか

### 今の判定

ルールを `deny` → `ask` → `allow` の順に見て、どれかに当たればそこで決まる。チケットを見るのは
どれにも当たらなかったときだけ（`ccnavi/judge.py:259-264`）。実行後の監視も同じ順で、ルールの
`allow` に当たる場所はチケットの範囲を見ない（`ccnavi/post.py:420`、`_allowed`）。

### 起きていること

- `.ccnavi/common/rules.yml` の `allow` の `worktrees`（`*/.claude/worktrees/*`）が作業ツリーへの
  書き込みを全部通す。チケットの範囲の外も、範囲の `ask` も、実行前の判定と実行後の監視に出ない
- サブエージェント終了時の検査（`ccnavi/phase.py:656` `scope_findings`）はルールを見ずに範囲を当てる。
  実行前は通したものを、終わるときに差し戻す
- チケットに `deny` を書いても、ルールの `allow` に当たる場所では効かない

### 変えたあとの判定

ルールの判定とチケットの判定を両方出し、厳しい側を採る。強さは `deny` > `ask` > `allow`。
チケットの範囲の外は `deny`。

| ルール | チケット | 結果 |
|---|---|---|
| deny | どれでも | deny（ルールの文面） |
| ask | deny / 範囲の外 | deny（チケットの文面） |
| ask | ask / allow | ask（ルールの文面） |
| allow | deny / 範囲の外 | deny（チケットの文面） |
| allow | ask | ask（チケットの文面） |
| allow | allow | allow |
| 何も言わない | どれでも | 今と同じ（チケットの判定） |
| どれでも | チケットが無い | 今と同じ（ルールの判定。何も言わなければ権限モード） |

チケットが効く条件（`Write` / `Edit` / `NotebookEdit`、行き先が承認済みチケットと同じ名前の作業ツリーの中、
未承認は効かない、親子は厳しい側）は変えない。

## どう変えるか

1. **実行前の判定**（`judge.py`）。ルールが当たっても、チケットの判定を出して強さを比べる。
   同じ強さならルールの文面を使う。人が書いた宣言の文面を先に見せるため
2. **実行後の監視**（`post.py`）。`_allowed` の近道を外し、ルールの `allow` に当たる場所でも
   チケットの範囲を当てる。ルールの `deny` / `ask` に当たる変更をルールの側で報告する順は変えない
3. **チケットの置き場を範囲の外でも咎めない。** 実行前の判定と実行後の監視は、今はチケット自身の
   提案ファイルしか外していない（`judge.py:512`、`post.py:306`）。サブエージェント終了時の検査は
   提案の置き場と承認済みチケットの置き場を丸ごと外している（`phase.py:686`）。B にすると、親が
   自分の作業ツリーに子の提案を書く手が止まるので、3 か所を同じ外し方にそろえる
4. **理由コードと文面。** チケットがルールの `allow` / `ask` を狭めたことを文面で言う。
   「ルールは通しているが、このチケットの範囲では止める / 聞く」と読めるようにする。
   範囲の外とチケットの `deny` を別のコードに分けるかは設計で決める
5. **承認画面。** 親の画面は「このチケットで書き込みが許される領域（これ以外はすべて止まる）」と
   すでに言っている。ルールの `allow` もこの外では止まることが読めるかを確かめ、足りなければ直す。
   VS Code 拡張のオーバーレイも同じ文面を見せているかを確かめる
6. **文書。** `ccnavi.md` §6.1 の流れ、§9.5 の表、原則 P2、`README.md` のチケットの節、
   ADR-0022 を置き換える新しい ADR（ADR-0008 の「失ったもの」の記述も直す）、要求表、`HANDOVER.md`

## 得るもの

- チケットの範囲が、書いたとおり実行前にも実行後にも効く。今このワークスペースでは効いていない
- 実行前の判定・実行後の監視・サブエージェント終了時の検査が同じ範囲を言う
- チケットの `deny` と `ask` で、ルールが開けている場所を作業 1 本のあいだだけ狭められる
- 緩む向きは無い。ルールの `deny` はどう書いても最も強く、チケットは今と同じく広げる手段を持たない

## 失うもの

- **ADR-0022 の「ルールのほうが強い」を覆す。** エージェントが下書きし人が承認したチケットが、
  人の書いたルールの `allow` を閉じられるようになる。閉じる向きだけで承認も通るが、承認画面が
  それを読ませないと、人は「ルールで開けてあるから大丈夫」と読み違える
- **チケットのある作業ツリーでは、範囲の外への書き込みがすべて止まる。** ついでの文書の直しなども
  止まる。親の `allow` は改版で変えられないので、範囲を見誤ると次のチケットを起こすことになる
- **配ったルールの振る舞いが変わる。** 作業ツリーを `allow` で開けている他のプロジェクトは、
  更新した時点でチケットの範囲が効き始める。移り方を README に書く
- **判定の代金が増える。** 今はルールが当たるとチケットを読まない。変えたあとは作業ツリーへの
  `Write` / `Edit` のたびに承認済みチケットを走査する。記録の `ms` で前後を比べる
- **Bash との非対称が目立つ。** `Write` で止まった場所に、シェルからは実行前の判定を通って書ける
  （実行後の監視が言う）。今と同じ限界だが、止まる場所が増えるぶん踏む回数が増える
- **このチケットの途中で振る舞いが変わりうる。** 実装が統合先に入り、ワークスペースの実行ファイルを
  組み直した時点から、このチケット自身の残りのフェーズにも新しい判定が効く

## やらない場合どうなるか

このワークスペースでは、チケットの範囲は実行前の判定にも実行後の監視にも効かず、サブエージェント
終了時の差し戻しにしか出ない。承認画面が言う「これ以外はすべて止まる」が事実と違ったまま残る。

## 代案

- **A. チケットに書いた `deny` / `ask` だけルールより強くする。** 範囲の外はルールの `allow` に従う。
  今の作業を止める範囲は小さいが、範囲の外が止まらないことは今と同じで、1 枚のチケットの中で
  範囲の外の扱いが場所によって変わる。利用者との相談で採らなかった
- **C. コードを変えず、rules.yml の `worktrees` の `allow` を外す。** チケットのある作業ツリーでは
  範囲が効くが、チケットの無い作業ツリーは権限モード任せになり確認が増える。チケットの `ask` で
  ルールの `allow` を狭めることはできない。配ったプロジェクトごとにルールを直すことになる
- **D. ルールの項に「チケットより弱い」印を足す。** 項ごとに選べるが、ルール書式の版が上がり
  （ADR-0010）、どの `allow` が弱いかを人が覚えることになる

## 順序と分割

1. **設計**（`wip/design/`、`docs/`）。上の 3〜5 の未決を決める。とくに、チケットの置き場の外し方、
   理由コードの分け方、組み込みの守りとチケットの強さ、`--explain` と `--lint` への影響、
   `ms` の見込み。ADR の下書きもここで書く
2. **受入テスト作成**（`tests/`）。上の表の全組み合わせ、実行前と実行後が同じ答えを返すこと、
   チケットの置き場の外し方、親子の合成、未承認とチケットの無い作業ツリーで今と変わらないこと。
   実装と並行してよい
3. **実装とテスト**（`ccnavi/`、`tests/`、必要なら `vscode-extension/`）
4. **文書**（`ccnavi.md`、`README.md`、`requirements.md`、`docs/`、`HANDOVER.md`、`CONTEXT.md`）

保護済みファイル（`.ccnavi/scripts/`、`.claude/hooks/`、`.ccnavi/common/rules.yml`）は触らない見込み。
触る必要が出たら `staging` の種類で写す版を作る。

## 確かめ方

- 既存の unittest が全部通ること
- 受入テストの表の全行が通ること
- 実行前に止まる書き込みを、シェルで書いたときに実行後の監視が同じ範囲で言うこと
- dry-run で数日回し、記録の `DENY_TICKET_SCOPE` と `TICKET_ASK` の件数と `ms` を前と比べる
