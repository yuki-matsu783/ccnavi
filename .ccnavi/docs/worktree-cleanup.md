# ワークツリーの片付け

## ccnaviが片付けるもの

- ワークツリーはccnaviが片付ける。マージを待たない
  - 方針は、閉じた子のワークツリーは完了でも取り消しでも消すこと。閉じた子の続きを進めるときは、新しいチケットで
    新しいワークツリーを切る。残るのは、作業中（`doing/`）の子と、レビュー待ち（`review/`）の子（見返す場所）の
    ワークツリー。`decide`・Chromeのレビュー済みで`done/`へ動いた子のワークツリーは、その場では消えず、
    次にその親子で`finish`か`cancel`が打たれるまで残る
  - 子のワークツリーは、`confirm`が子を`done/`へ動かしたあと（そのフェーズの子）と、`finish`・`cancel`のあと
    （親でも子でも、その親子の閉じた子を全部。親の`finish`では取りこぼしを拾う安全網）に消える。
    レビュー待ち（`review/`）の子のものは残す。そこで積んだコミットは親へ合流しないので、指摘は同じフェーズに子を足して直す
  - 親のワークツリーは、`ready`がDraftを外したあとの最後に消す。Draftを外す前と、外せなかったときは消さない
  - `ready`がDraftを外したあとは、子のワークツリーを全部（レビュー待ちだったものも）消し、子の手元のブランチと親のワークツリーも
    片付ける。子のブランチを消す条件は次の2つ。条件の確認も削除もccnaviが行い、
    エージェントは`git branch -D`を使えない
    - 合流した子: ブランチの先頭が`merged_sha`（合流した先頭）と同じで、その先頭がpush済みの親の先頭（`origin/<親のブランチ>`）の祖先であること。
      どちらかが違えば消さず、理由と手で消すコマンドを出す
    - 取り消した子: 一覧（親に入っていないコミットがあればそう添える）を出すだけで消さない。一覧をユーザに見せる。消すのはユーザで、消してよければ
      ユーザが先頭に`!`を付けて`! sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-user-clean-branch.sh <子の識別子> --confirmed`を打つ。
      エージェントからは打てない（hook が止める。メインもサブエージェントも）。`--confirmed`を単なる語として添えて、確認を飛ばせないようにするため。
      エージェントは一覧と、出てきたコマンドをそのままユーザに見せて頼む。`--confirmed`なしでは消えない
  - 消し方は生成物の掃除（`ccnavi-clean.sh`と同じもの）のあと`worktree remove`（`--force`なし）。ワークツリーを消してもブランチは消えない
    （ブランチは上の条件か、下の「MRがマージされたあと」で片付ける）
  - cwdが消す対象の中にあると消さず、「cwdが中にあるので消さなかった」と、外に出てから打つ1本
    （`sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-clean.sh --worktree <名前>`）が出る。`worktree drop`や`worktree retire`を親のワークツリーの中から
    直接打ったときはこの形になる。`ready`は外から`--parent`を付けて打つので、この形にはならない。ExitWorktreeか`cd`でワークスペースルートに出てから、出た1本をそのまま打つ
  - 未コミットの変更があるワークツリーは、何も消さずに止まる（中身は`git -C <パス> status`で見る）。別のセッションの作業かもしれないので、ユーザに確かめる
  - gitが無視しているファイル（`.env`など）があるワークツリーも、何も消さずに名指しされる。`worktree remove`はそれごと消し、
    履歴から戻せないため。残したいならワークツリーの外へ退避し、要らないならユーザに確かめて消してから打ち直す。
    数えないのは、生成物（`ccnavi-clean.sh`が消すもの）だけ。下書きの置き場は`wip/handoff/`（追跡される。
    [scratchpad.md](scratchpad.md)）で、gitが無視するファイルではない。未コミットの下書きは「未コミットの変更」として止まる
  - `git worktree remove`が断る（ロック・submoduleなど）ワークツリーは残り、gitの拒否文が出る。生成物は先に消えているが、作り直せる

## MRがマージされたあと

- 閉じたかはMRがマージ済みかで決める。`ccnavi-sync.sh`（ボードの同期・`ccnavi-start.sh`の最後・エージェントの`sync`）が、
  親子のチケットごとにホストへ聞く。親のブランチがリモートに残っていても聞く（ホストはマージの後もブランチを残すことがある）。
  親のワークツリーを片付けたあとは、`ready`が書いた片付けの記録を一覧の元にして聞く。
  MRの番号が分からない親は、推定せず「閉じたか判断できない」と1行出す。ホストに聞けなければ推定せず止まる
- 片付けの記録が読めない親は、一覧の案内だけを出し、自動では片付けない
- MRをマージせずに閉じた（放棄した）親の記録は、ユーザが`ccnavi worktree retire --abandon <親の識別子>`で消す（エージェントは打てない）。
  放棄した親のワークツリーを片付ければ、`ccnavi-sync.sh`の対象から外れる
- 片付けの実行はshが中で行う。エージェントが実行ファイルを直に打つと止められる。
- マージ済みと分かったら、手元の親を片付ける。消すのは、親のワークツリー（未コミットの変更や、gitが無視している
  ファイルがあれば残す）、親の手元のブランチ（親の識別子のブランチで、手元の先頭がpush済みの先頭（手元の`origin/<ブランチ>`）と
  マージされたMRの先頭の両方に含まれるときだけ。`origin/<ブランチ>`が手元に無ければ消さない）、
  その親の片付けの記録。残った子のブランチも、MRの先頭を基準に上と同じ条件で消す
- 片付けた内容は1行ずつ出る。消さなかったものは、理由と手で消すコマンド（`git -C <リポジトリ> branch -D <ブランチ>`）が出る。
  ユーザが確かめて打つ。何かが残ると片付けの記録も残り、直してから`ccnavi-sync.sh`を打ち直せば片付く
- `logs/archive/`は消さない。閉じたチケットのバックアップで、判定には使わない

## 自分で片付けるとき

- 自分で`worktree remove`を打つとき（`<統合先>`に直接取り込んだワークツリーなど）は、その前に`ccnavi-clean.sh <名前>`で
  node_modules・.venvなどの生成物を消す。Windowsで削除が途中で止まるのを防ぐためである。未コミットの変更があるワークツリーでは、
  `ccnavi-clean.sh`は何も消さずに止まる。node が無いときも何も消さず、ユーザが打つ削除の1本を出して止まる（エージェントは打たず、ユーザに頼む）。`ccnavi-clean.sh --worktree <名前>`は掃除と`worktree remove`を1本で行う
- 片付けの1本（`ccnavi-clean.sh --worktree`）や`ccnavi-git.sh rm -r wip`がClaude Codeの自動モードの分類器に止められたら、迂回しない。
  ユーザに許可を頼む。続けて許すなら、ユーザがホームの`~/.claude/settings.json`の`permissions.allow`に、操作ごとに絞った許可
  （例 `Bash(sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-clean.sh --worktree *)`）を足す。分類器はプロジェクトの
  `.claude/settings.json`を読まないので、そこに足しても効かない。`ccnavi-git.sh *`のような広い許可はpushまで分類器を通さなくなるので勧めない
