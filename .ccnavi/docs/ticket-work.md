# 作業の進め方（直接作業とチケット作業）

チケット制御を使っているワークスペースでは、進め方は 2 つある。

- 直接作業（調査・小さな修正）: チケットを起こさずそのまま進める。判定は全体のルールだけに従う。
- チケット作業（設計に触れる・複数のフェーズに分かれる・ユーザのレビューが要る）: `wip/proposals/todo/` に提案を書き、`ccnavi-ticket.sh propose <識別子>` で親のブランチへ送って承認を受ける。承認されると提案は承認済みの置き場の `doing/` へ動く（置き場は設定で変わる。既定は `wip/proposals/` と `.ccnavi/approved/`。[projects.md](projects.md)）。以後の操作は `ccnavi-ticket.sh` を通す（使い方は `--help`）。

チケット作業は必ず issue と MR のセットで進める。issue が無ければ `ccnavi-start.sh --new-issue <題>` で作ってから進める（題の似た open の issue・MR があれば作らずに止まり、ユーザに聞く。似たものが無くても、haiku のサブエージェントに `ccnavi-start.sh --list-open` を読ませ、意味が近いものがないかを確かめる段を挟む。詳細は worktree-start.md）。作れなければユーザに作ってもらう。入口で `ccnavi-start.sh --check` を打ち、ホストの API と git のリモートが使えるかを確かめる。子の作業から始めるセッションでは、`ccnavi-ticket.sh` の `start`・`finish`・`propose`・`consolidate` が自動で確かめる。直接作業では確かめない。

どちらで進めるか迷ったら、ユーザに聞く。ただし issue・MR を指定された実装は、直接作業にせずチケット作業で進める（ホストで作られたものを途中から頼まれた場合も同じ）。詰まったら直接実装に切り替えず、ユーザに報告して止まる。

## 正本と親のワークツリー

作業の正本は、親のブランチを checkout した親のワークツリー（名前はブランチ名の `/` を `-` に置き換えたもの）。親のワークツリーには書かず、子のワークツリーで作業する。ワークツリーが無い PC や HEAD が違う PC では操作が止まるので、案内の `ccnavi-start.sh` で準備する。親の提案には `issue:` と `mr:` を必ず書く。詳細は [worktree.md](worktree.md)。

## レビュー準備中・レビュー待ちの間

別の親・別の目的の新しい依頼をこのセッションで受けず、ワークスペースルートで起動した別のセッションで受けるようユーザに伝える。同じ親のレビュー対応・相談・中止の指示・取り消し・次のフェーズの計画・進行中の子の完了処理は続けてよい（案内だけで、機械的には止めない）。

## 非対話セッションで子が詰まったとき

ユーザがその場でやり取りできない非対話セッション（`claude -p`、コンテナでの自動実行など）では、終わるとコンテナごと閉じ、子のワークツリーとブランチ（手元だけにある）も失われる。
ccnavi は、環境変数`CLAUDE_CODE_SESSION_ATTENDED`が`0`のセッションだけを非対話と見て、作業の決まりにこの案内を足す。示されない環境では足さないので、非対話だと分かっているときは、この節に従う。
子が途中まで進めて詰まったり、ユーザの確認が要ったりしたときは、報告して止まる前に、メインが次のどちらかを決め、リモートへ反映してからターンを終える。

サブエージェントは背景にせず、前景で起動して完了を待つ。非対話では、メインがターンを終えるとプロセスが終わり、背景のサブエージェントは作業の途中で打ち切られる。背景のコマンドをサブエージェントが残したままにしない（長いコマンドは timeout を明示する）。対話セッションでは、メインがユーザとのやり取りを続けられるよう、背景で任せる。

1. 子（サブエージェント）は作業を止め、詰まった点・ユーザに聞きたいこと・ここまでの状態をメインに返す。子は push も状態の操作もしない
   ユーザが停止・待機・相談を指示したとき、ガードや範囲に止められたとき、範囲・計画の改版が要るときは、次の 2 を使わず、報告して止まる。止められた操作の迂回に `cancel` や `finish` を使わない。範囲・計画の改版は、`propose` で改版を送って承認を待つ
2. メインは、使える成果があるかで決める
   - 残す: 子に途中の状態をコミットさせ（未コミットの変更があると `finish` が止まる）、`finish` が求めるもの（フェーズ定義の成果物、`ccnavi-ticket.sh learn` による気づきの記録のコミット〔学びの蓄積が有効なとき〕、`record-risk` による定性のリスク判定）を済ませてから、`ccnavi-ticket.sh finish <子>` で親へ合流して push する。`finish` はコードが動くかを見ないので、合流した途中の状態は、承認前から親のブランチと MR に載る。落ちているテストがあれば、その名前を続きの子の本文に書く。続けて、同じフェーズの新しい連番の子として残りの提案を書き、`ccnavi-ticket.sh propose <続きの子>` で送る。本文に、元の子の残り・詰まった点・ユーザの判断が要る点を書く。壊れた状態で合流したときも、その旨を書く
   - 捨てる: 成果が使えない・やり方が違うときは、`ccnavi-ticket.sh cancel <子> --reason <詰まった点と聞きたいこと>` で取り消し、新しい連番の子の提案を `propose` で送る。手元の子のブランチは、コンテナとともに消える
3. `finish`・`cancel`・`propose` は push まで行う。`ccnavi-ticket.sh status` で届いたかを確かめる。どれも通らなければ、通らなかった操作と出力を最終報告に書く（作業は失われる）
4. ターンの最後の報告に、どちらを選んだか・理由・ユーザに頼むこと（続きの子の承認、判断）を書いて終える。続きの子は承認待ちの提案で、承認を待たずに先へ進まない

続きの子の承認は、別の PC・別のセッションからでもできる。
