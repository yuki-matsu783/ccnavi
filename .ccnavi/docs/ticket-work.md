# 作業の進め方（直接作業とチケット作業）

チケット制御を使っているワークスペースでは、進め方は 2 つある。

- 直接作業（調査・小さな修正）: チケットを起こさずそのまま進める。判定は全体のルールだけに従う。成果は `integrate` で取り込む。ただし、issue がある依頼をユーザが直接作業と明示したときは、成果を MR で受ける（「作業のパターン」の表の 4）。
- チケット作業（設計に触れる・複数のフェーズに分かれる・ユーザのレビューが要る）: `wip/proposals/todo/` に提案を書き、`ccnavi-ticket.sh propose <識別子>` で親のブランチへ送って承認を受ける。承認されると提案は承認済みの置き場の `doing/` へ動く（置き場は設定で変わる。既定は `wip/proposals/` と `.ccnavi/approved/`。[projects.md](projects.md)）。以後の操作は `ccnavi-ticket.sh` を通す（使い方は `--help`）。

チケット作業は必ず issue と MR のセットで進める。issue が無ければ `ccnavi-start.sh --new-issue <タイトル>` で作ってから進める（タイトルの似ている open の issue・MR があれば、作らずに止まり、ユーザに聞く。似たものが無くても、haiku のサブエージェントに `ccnavi-start.sh --list-open` を読ませ、意味が近いものがないか確かめる段を挟む。詳細は worktree-start.md）。作れなければユーザに作ってもらう。入口で `ccnavi-start.sh --check` を打ち、ホストの API と git のリモートが使えるかを確かめる。子の作業から始めるセッションでは、`ccnavi-ticket.sh` の `start`・`finish`・`propose`・`consolidate` が自動で確かめる。直接作業では確かめない。

どちらで進めるか迷ったら、ユーザに聞く。ただし issue・MR を指定された実装は、直接作業にせずチケット作業で進める（ホストで作られたものを途中から頼まれた場合も同じ）。詰まったら直接実装に切り替えず、ユーザに報告して止まる。
例外はユーザが直接作業を明示したときだけで、その指示に従う（次の節）。ただし、親のワークツリーからは、親の提案が承認前のときだけ切り替えられる（「拒否される条件と、切り替える前の取り下げ」）。

## 作業のパターン

依頼を受けたら、次の 2 つを見て、表のどの行に当たるかを決める。迷ったらユーザに聞く。

- issue・MR の指定があるか（`#152`・`!5`・URL。ホストで作られたものを途中から頼まれた場合も含む）
- ユーザが自分の言葉で直接作業を求めたか（「直接作業で」「チケットを切らずに」「承認は要らない」）

| # | issue・MR | 直接作業の明示 | 進め方 | 取り込み |
|---|---|---|---|---|
| 1 | なし | なし。調査・小さな修正 | 直接作業。統合先ではなく、ユーザのチェックアウトが開いているブランチから切る（[direct-flow.md](direct-flow.md)） | `integrate` でユーザが差分を見て確定 |
| 2 | なし | なし。設計に触れる・複数のフェーズ・ユーザのレビューが要る | チケット作業。`ccnavi-start.sh --new-issue <タイトル>` で issue を作ってから進める | MR のマージ |
| 3 | あり | なし | チケット作業。`ccnavi-start.sh --issue <番号>`（MR なら `--mr <番号>`）。「小さいから」と判断して直接作業にはしない | MR のマージ |
| 4 | あり | あり | 直接作業を MR で受ける形（下の「issue がある依頼を直接作業で進めるとき」） | MR のマージ |
| 5 | なし | あり | 1 と同じ。MR は作らない | `integrate` |
| 6 | 問わず | 問わず。詰まった・承認が通らないとき | 直接実装に切り替えず、報告して止まる | |

## ユーザが直接作業を明示したとき

ユーザが自分の言葉で「直接作業で」「チケットを切らずに」「承認は要らない」のように直接作業を求めたときは、「issue・MR を指定された実装は直接作業にしない」の規則より、その指示を優先する。ただし、親のワークツリーの中から `ccnavi-worktree.sh` を打って切り替えられるのは、親の提案が `wip/proposals/todo/` にあり承認前のときだけ。親が承認済み・レビュー待ち、または着手済みの子がある間は、親のワークツリーからは切り替えられない。

どの場合にどう進めるかは、上の「作業のパターン」の表で決める。issue・MR を指定しただけで直接作業の明示が無いとき（表の 3）は、エージェントが「小さいから」と判断して直接作業にはしない。詰まった・承認が通らないとき（表の 6）に報告して止まるのは、ユーザの指示による切り替えとは別である。

- 直接作業はチケット制御の関門（承認・範囲・親のワークツリー）を通らない。ただし、承認済みの置き場や保護対象は直接作業でも書けない。保護対象は `ccnavi-stage.sh` で下書きに写して直す
- 直接作業は新しいワークツリーとブランチ（`<先頭の語>-<番号>-<slug>`）に書く。issue に紐づく既存の MR のブランチには書かない。名前が既存のブランチと同じ識別子になるときは、切らずに止まる（[worktree.md](worktree.md)）。名前が違えば並行したブランチになる。始めるときに知らせるかは、別に判断する。

### issue がある依頼を直接作業で進めるとき

issue（または MR）を指定され、かつユーザが直接作業を明示したとき（上の表の 4）。提案・承認・親子は使わないが、成果は MR で受ける。MR だけが指定されて issue の番号が分からないときは、ユーザに聞く。

1. `ccnavi-start.sh` は打たない（親のワークツリーと Draft MR を作る入口で、チケット作業用のため）。代わりに `ccnavi-worktree.sh <先頭の語>-<issue の番号>-<slug>` で切る。同じ識別子のブランチがあって止まったときは、案内される `ccnavi-start.sh` へは進まず、ユーザに聞く。
   - 起点は、ユーザのチェックアウトが開いているブランチ（取り込み先）の HEAD である。`origin` からは切らない。`origin` より遅れていれば、確認に従って先に合わせる。
   - MR は統合先に出すため、ユーザのチェックアウトが統合先であることを確かめる。統合先でなければ、そのブランチから切ると MR に余計な変更が載るので、ユーザに統合先へ切り替えてもらう。MR の宛先をそのブランチにしてよいと言われたときだけ、そのまま進める。
2. 実装・検証してコミットし、そのブランチを `ccnavi-git.sh push -u origin <名前>` で送る。MR で受けるときは `integrate` を打たないので、使い終えた `wip/handoff/` の下書きは自動では外れない。push の前に消す。
3. MR を作る（origin が GitHub なら `gh pr create`、GitLab なら `glab mr create`）。本文は、issue を完全に閉じるなら `Closes #<番号>`、一部だけなら `Refs #<番号>` とする。範囲、未実施の部分、確かめたことと確かめていないことを書く。
4. 取り込みは、ユーザの確認のあとに MR をマージして行う。MR の URL を示し、レビューとマージを頼んで、ターンを終える。
5. `integrate` は打たない。取り込みは MR のマージで行うため、Stop hook が「integrate を打っていない」と促しても、理由（MR で取り込む）を書いて終える。マージされたら、`ccnavi-clean.sh --worktree <名前>` で片付ける（ブランチは残る）。

- 既存の MR のブランチには書かない（上の決まり）。既存の MR の続きを頼まれたときは、別のブランチと新しい MR になるため、既存の MR との関係（閉じるか、残すか）をユーザに聞く。
- 残りの作業は、MR を分ける。残りがあるときは `Refs`、全部終えたときだけ `Closes` を使う。

### 拒否される条件と、切り替える前の取り下げ

親のワークツリーの中から `ccnavi-worktree.sh` で直接作業へ切り替えられるのは、親の提案が `wip/proposals/todo/` にあるだけの（承認前の）ときだけ。切り替えると、承認待ちの提案と MR は取り下げられずに残る。残っているものは、切り替えたあとの出力の `案内:` が伝える。MR を閉じる操作は無く、閉じるか Draft のまま残すかはユーザがホストで決める。

次のときは、ワークツリー・記録・ref を作る前に断る（終了コード 1）。親の状態は `ccnavi tree leftover` の `stage`（`doing` > `review` > `todo`）で決める。

| 状態 | 切り替え | 切り替える前の取り下げ |
|---|---|---|
| 承認前の提案だけ（`stage` が `todo`、`doing/` の子なし） | 通す | 提案のファイルは削除できる（`cancel` は `doing/` のチケット用で、提案には使えない）。削除できない・`propose` で送った分が親のブランチに残るときは、状態を報告してユーザの判断を仰ぐ |
| 親が承認済み（`stage` が `doing`） | 断る | ユーザが親のワークツリーで `sh .ccnavi/scripts/ccnavi-user-close-early.sh --reason <理由>` を打つ。エージェントは打てず、判断もしない。残りは issue に書き出す。`--no-issue` を付けると書き出さない。作業中の子がいる間は打てない。未着手の子は自動で `cancel` される。そのあと親で `ccnavi-ticket.sh finish` して push し、`ccnavi-review.sh ready` を実行する。マージリクエストが無い・変更要求が残るときは、ここでも通らない |
| 着手済みの子がある（`doing/` の子が 1 件以上） | 断る | メインが `ccnavi-ticket.sh cancel <子の識別子> --reason <理由>` を打つ。`--reason` が要り、サブエージェントは打てない |
| 親が完了済みでレビュー待ち（`stage` が `review`） | 断る | 早めに閉じる操作の対象ではない。レビューの結果を待つ |

- 断られたら、状況をユーザに報告し、親を早めに閉じるか子を取り下げるかの判断を頼んで返事を待つ。直接実装には切り替えない
- 断るのは、cwd が親のワークツリーのときだけ。`--dry-run` でも断る。ワークツリーが既にあるときの冪等の終了（終了コード 0）は、断るより前に通る。実行ファイルに聞けないときは、断らずに通す。古くて `stage` が答えに無くても、`doing/` の子が 1 件以上なら断る。`--adopt` は対象外（親のワークツリーの引き取りは `adopt-ticket` が断る）。閉じた親（`done/`）は、`doing/` に子が残っていなければ断らない
- `ccnavi-user-close-early.sh` が MR について行うのは、親が片付いたあとに `ccnavi-review.sh ready` が Draft を外すところまで。MR を閉じる操作ではない
- ccnavi には MR を閉じる操作が無い。Draft のまま残すか閉じるかは、ユーザがホストで決める。エージェントは MR を閉じない
- 既存の MR のブランチは、直接作業へ切り替えても変わらない。直接作業の変更は別のブランチ（`ccnavi-worktree.sh` の名前）に入る


## 正本と親のワークツリー

作業の正本は、親のブランチをチェックアウトした親のワークツリー（名前はブランチ名の `/` を `-` に置き換えたもの）。親のワークツリーには書かず、子のワークツリーで作業する。ワークツリーが無い PC や HEAD が違う PC では操作が止まるので、案内の `ccnavi-start.sh` で準備する。親の提案には `issue:` と `mr:` を必ず書く。詳細は [worktree.md](worktree.md)。

承認の前は、親のワークツリーへの書き込みが判定の対象外として通る（承認済みの索引にまだ無いため）。ユーザが「先に実装して」と頼んだ場合など、承認の前に親のワークツリーへ入った変更は、承認の後に書き込みを断られ（`DENY_TICKET_PARENT`）、子の `finish` も止める。承認の時点で、提案とチケットの置き場以外の未コミットの変更があれば、承認の結果（ターミナルは標準エラー、拡張は承認の通知の `案内:` の行）で知らせる。承認は止めない。親のワークツリーに残った変更は、次のどちらかで片付ける。

- 要らない変更: 親のワークツリーで `ccnavi-git.sh restore --staged --worktree -- <パス>` を、パスを 1 つずつ名指しして打つ（ツリー全体を指すと止まる）。自分が書いた変更でなければ、戻す前にユーザへ確かめる
- 残す変更: 子のワークツリーへ移してコミットする

拒否されたら、Bash のリダイレクトなど別の手で親のワークツリーへ書き込んで迂回しない。

## レビュー準備中・レビュー待ちの間

自分が準備・依頼したレビューの待ち中は、別の親・別の目的の新しい依頼をこのセッションで受けず、ワークスペースルートで起動した別のセッションで受けるようユーザに伝える。他の会話が待っている親は対象外。同じ親のレビュー対応・相談・中止の指示・取り消し・次のフェーズの計画・進行中の子の完了処理は続けてよい（案内だけで、機械的には止めない）。

## 非対話セッションで子が詰まったとき

ユーザがその場でやり取りできない非対話セッション（`claude -p`、コンテナでの自動実行など）では、終わるとコンテナごと閉じ、子のワークツリーとブランチ（手元だけにある）も失われる。
ccnavi は、環境変数`CLAUDE_CODE_SESSION_ATTENDED`が`0`のセッションだけを非対話と見て、作業の決まりにこの案内を足す。示されない環境では足されないので、非対話だと分かっているときは、この節に従う。
子が途中まで進めて詰まったり、ユーザの確認が要ったりしたときは、報告して止まる前に、メインが次のどちらかを決め、リモートへ反映してからターンを終える。

サブエージェントはバックグラウンドにせず、フォアグラウンドで起動して完了を待つ。非対話では、メインがターンを終えたあと、バックグラウンドのサブエージェントは待ち上限まで待たれるが、環境の設定によっては作業の途中で消える。バックグラウンドのコマンドをサブエージェントが残したままにしない（長いコマンドは timeout を明示する）。対話セッションでは、メインがユーザとのやり取りを続けられるよう、バックグラウンドで任せる。

1. 子（サブエージェント）は作業を止め、詰まった点・ユーザに聞きたいこと・ここまでの状態をメインに返す。子は push も状態の操作もしない
   ユーザが停止・待機・相談を指示したとき、ガードや範囲に止められたとき、範囲・計画の改版が要るときは、次の 2 を使わず、報告して止まる。止められた操作の迂回に `cancel` や `finish` を使わない。範囲・計画の改版は、`propose` で改版を送って承認を待つ
2. メインは、使える成果があるかで決める
   - 残す: 子に途中の状態をコミットさせ（未コミットの変更があると `finish` が止まる）、`finish` が求めるもの（フェーズ定義の成果物、`ccnavi-ticket.sh learn` による気づきの記録のコミット〔学びの蓄積が有効なとき〕、`record-risk` による定性のリスク判定）を済ませてから、`ccnavi-ticket.sh finish <子>` で親へ合流して push する。`finish` はコードが動くかを見ないので、合流した途中の状態は、承認前から親のブランチと MR に載る。落ちているテストがあれば、その名前を続きの子の本文に書く。続けて、同じフェーズの新しい連番の子として残りの提案を書き、`ccnavi-ticket.sh propose <続きの子>` で送る。本文に、元の子の残り・詰まった点・ユーザの判断が要る点を書く。壊れた状態で合流したときは、その旨も書く
   - 破棄する: 成果が使えない・やり方が違うときは、`ccnavi-ticket.sh cancel <子> --reason <詰まった点と聞きたいこと>` で取り消し、新しい連番の子の提案を `propose` で送る。手元の子のブランチは、コンテナとともに消える
3. `finish`・`cancel`・`propose` は push まで行う。`ccnavi-ticket.sh status` で届いたかを確かめる。どれも通らなければ、通らなかった操作と出力を最終報告に書く（作業は失われる）
4. ターンの最後の報告に、どちらを選んだか・理由・ユーザに頼むこと（続きの子の承認、判断）を書いて終える。続きの子は承認待ちの提案で、承認を待たずに先へ進まない

続きの子の承認は、別の PC・別のセッションからでもできる。
