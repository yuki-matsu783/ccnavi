# ワークツリーの作業を統合先に取り込む

作業が完了したら`<統合先>`に取り込む。コンフリクトの解消で判断に困る場合はユーザに確認する。
取り込んだあとの片付けは[worktree-cleanup.md](worktree-cleanup.md)。

## 直接作業のワークツリーを取り込む（`integrate`）

取り込み先は、ワークツリーを切った時点でユーザのチェックアウトが開いていたブランチで、統合先（`origin/HEAD`）とは限らない。手順の全体は[direct-flow.md](direct-flow.md)。

- 直接作業では、作業を終えたらコミットをまとめて打ち、その直後に`integrate`を打つ。ユーザの確認を待つ間はコミットしない。
- ターンの終わりに、直接作業のワークツリーに取り込み先に入っていないコミットがあって、取り込みの途中でなければ、hookが1回だけ止めて`integrate`を促す。未コミットの変更だけなら促さない。促しの文のコマンドは1行で完結し、別のツリーで打つものは`cd <パス> && …`で始まる。そのまま打つ
- セッションの開始で、終わっていない取り込みの跡（途中の記録、一時ワークツリーなど）があれば知らせる。別のセッションの取り込みの場合もあるので、操作する前に担当と今の状態をユーザに確かめる。知らせは、ユーザのチェックアウトの変更を操作してよい根拠ではない。壊れた記録は自動では再開しない
- 直接作業は、マージコミットを作らず、1コミットで取り込み先へ載せる。確認の間、ユーザのチェックアウトのindex・ワークツリー・HEADには書かない。`integrate`と`integrate-done`は、取り込み先をチェックアウトしているユーザのチェックアウトで打つ。ほかのツリーで打つと拒否され、正しい場所が出る。ブランチが替わっていたら、ユーザに戻してもらう（エージェントはcheckoutしない）。次の3段になる
  1. `ccnavi-git.sh integrate <名前>`: 取り込み結果を一時ワークツリー（`logs/direct-tmp/`の下）に作って止まる。
     ブランチが持ち込んだ`wip/handoff/`の下書きは取り込まない。コミットした下書きのうち、起点に元が無いもの（新規のメモ・報告）は
     取り込みを止めず、`案内: 取り込まない下書き:`の一覧に出す。一覧の下書きは取り込まれず、作業ブランチを片付けると消える。内容をユーザに伝え、
     必要なら先に別の場所へ写してもらう。作業ワークツリーに未コミットの変更があるとき、または取り込まれていない下書き（元があって中身が違う写し、許可リストに当たる下書き）が残っているときは拒否される。コミットした分しか取り込まれないため。
     ユーザのチェックアウトに未コミットの変更があっても拒否しない。ユーザが横で作業しているものとして、最後に載せるときにgitが持ち越す。
     衝突したときは、衝突したパスを挙げて断る。ユーザのチェックアウトでは解かず、作業ワークツリーの中で`ccnavi-git.sh merge <取り込み先>`を打って解いてコミットしてから、`integrate`を打ち直す
  2. ユーザが差分と変わるファイルの一覧を確かめる。エージェントは結果を報告する（報告の指示は、`integrate <名前>`を打ったときに追加の文脈として渡される）。対話のセッションでは、`integrate-done`を打つとユーザの確認が出る。
     非対話のセッションでは、`integrate`のあとにユーザの発言が1回あるまで、`integrate-done`は拒否される。
     バックグラウンド作業の完了通知と、`Stop`の促しで続けたターンは、ユーザの発言に数えない。同じ発言の中で「取り込んで」と頼まれていても、確定は次の発言のあとになる。同じコマンドに`integrate`と`integrate-done`を連結した形は、どちらでも拒否される。変わるファイルをエディタで開いて保存していない編集があれば、`integrate-done`の前に保存してもらう。
     取り込み結果は一時ワークツリーで検証できる（そこは編集しない）。
     取り込みで増えるパスがユーザのチェックアウトのignoredのファイルと重なっていれば、`integrate`が挙げる。ユーザに退避を頼む
  3. `ccnavi-git.sh integrate-done <名前> -m <メッセージ>`: 一時ワークツリーで1コミットにし（フックは通る）、ユーザのチェックアウトに載せる。そのあと作業ワークツリー、一時ワークツリー、ブランチ、取り込みの記録を片付ける。
     ユーザの未コミットの変更（別のファイル）・staged・新規ファイルは持ち越される。同じファイルが未コミットなら、何も変えずにファイル名が出る（そのファイルだけコミットかstashしてもらう）。
     ignoredのファイルと重なるときも、上書きせずに止まる。HEADや作業ブランチの先頭が確認したあとに動いたときは、`integrate`を打ち直す。
     ccnaviの設定ファイルなどの自己防衛の対象を含む取り込みは、ユーザがターミナルで、エージェントのターンが終わってから打つ（ターミナル以外では断る）。
     片付けが途中で止まったら、残したものが出る。原因を片付けて同じコマンドを打ち直すと、済んだところを飛ばして続きから進む。
     一時ワークツリーに知らないファイルやignoredのファイルが残っているときは、削除せずにパスと中身を通知する
- 取り込みをやめるときは、`ccnavi-git.sh integrate --abort <名前>`で一時ワークツリーと途中の記録を消す。
  作業ワークツリーとユーザのチェックアウトには触らず、作業を続けてもう一度`integrate`を打てる。
  取り込みが済んでいるときは断る。ユーザが`git revert`する
- `integrate`が「版を知りません」と言って止まったら、取り込みの途中の記録が古い形か壊れている。エージェントは操作せず、ユーザに確かめる。ユーザは`git status`で統合先のstagedを確かめ、不要なら`git reset --merge`で戻してから、出力に示された記録のディレクトリを手で消す。Stopの促しも同じ文面で止まる
- `integrate`の対象は直接作業のワークツリーだけで、チケットに結び付く名前（承認済みチケットや提案に同じ名前がある、など）は拒否される。取り込み先のブランチがチケットに結び付くときは、ワークツリーを切る前に断られる。チケットの作業は、下のマージリクエストの手順で出す
- 記録の無い直接作業のワークツリーは、`integrate`が断って`ccnavi-worktree.sh <名前> --adopt --base <ブランチ>`での引き取りを案内する。名前がチケットに結び付くときは`--adopt`を案内せず、マージリクエストで出すと言う
- 取り込んだコミットをリモートへ送るかどうかはユーザが決める。`origin/<取り込み先>`が手元より進んでいれば、`integrate`が警告し、
  `integrate-done`が`git push origin <取り込み先>`をユーザに頼む案内を出す（`ccnavi-git.sh push`は統合先へも取り込み先へも送らない）

## 取り込み先・統合先が進んでいるとき・保護されているとき

取り込み方は作業の種類で決まる。「手元の`<統合先>`への取り込み」と「リモートへの push の保護」は別の話で、混ぜない。

| 作業 | 取り込み方 |
|---|---|
| 直接作業 | `integrate` → ユーザ確認 → `integrate-done`（上の節）。載せ先は取り込み先のブランチ。`<統合先>`がリモートで保護されていても手元への取り込みは変わらない |
| 直接作業のうち、issue がある依頼をユーザが明示したもの | ブランチを push して MR を作り、ユーザのレビューとマージで取り込む（[ticket-work.md](ticket-work.md)の表の 4）。`integrate` は打たない |
| チケット作業 | マージリクエストに出す（下の節）。手元の`<統合先>`へは取り込まない |

- ワークツリーのブランチを切ったあとに取り込み先が進んでいたら、ワークツリーの中で`ccnavi-git.sh merge <取り込み先>`を打ってコンフリクトを解消し、それから`integrate`を打つ
- 統合先のユーザのチェックアウトで`ccnavi-git.sh merge <ブランチ>`は打てない（`--abort` `--continue` `--quit`以外は、どの形でも止まる）。`pull <リモート> <別のブランチ>`と、`fetch`のあとの`merge FETCH_HEAD`も同じく止まる。統合先の更新（引数なしの`pull`、`pull [--ff-only] <リモート> <統合先>`）は打てる。取り込みは`integrate-done`が行い、衝突は作業ワークツリーで解く
- 保護の種類は2つある。手元の取り込み先を保護対象のツリーとして書き込めないときは、`integrate-done`をユーザがターミナルで打つ（上の節）。リモートの`<統合先>`が保護されていてpushできないのは、ユーザがどう出すかを決める話（`ccnavi-git.sh push`は統合先へは送らない）
- 上の2つに該当しない作業（例: 統合先にそのままfast-forwardで取り込む）は、ユーザが明示的に頼んだときだけの例外。ユーザがターミナルで行い、エージェントの`ccnavi-git.sh merge`は統合先のユーザのチェックアウトで止まる。`ccnavi-git.sh worktree remove <パス>`と`ccnavi-git.sh branch -d <名前>`で片付けるのは、取り込みが済んでから

## 子の成果を親のブランチへ合流する（子の`finish`）

チケット作業の子は、メインが`ccnavi-ticket.sh finish <子>`を打つと、親のブランチへ合流してから push する。
サブエージェントは子のワークツリーで実装して手元でコミットするだけで、合流・状態の記録・push はしない。

- `finish`は1操作（write-and-push）で次を順に行う。途中で止まったときは、何も変えていない
  1. 親のワークツリーが merge / rebase の途中でないことを確かめる
  2. 取り込み（sync）。親のワークツリーに、状態の置き場以外の未コミットの変更があれば止める
  3. 子のワークツリーに未コミットの変更があれば止める（「サブエージェントの作業がコミットされていません」。コミットさせてからやり直す）
  4. 取り込み直後の親の先頭と子のブランチの共通の祖先から、子の先頭までの変更を検査する。置き場
     （`.ccnavi/approved/`・`wip/proposals/`。フェーズのマーカーと記録を含む）の変更が1つでもあるか、子・親・フェーズ定義の範囲の外のパスがあれば合流しない
  5. `merge --no-ff --no-commit`で子を入れ、完了の記録（`review/`か`done/`へ移す）と子の承認済みチケットの`merged_sha:`（合流した子の先頭）を足して、
     合流と状態を1つのマージコミットにする。衝突したら merge を取りやめて何も変えずに止まる
  6. push。通らなければ、合流したコードも含めて元に戻す。応答が失われても、リモートに届いていれば成功
  7. 完了（`done/`）した子のワークツリーを片付ける。レビュー待ち（`review/`）の子のワークツリーは残す。片付けに失敗しても`finish`は成功
- 合流は`finish`の1回だけ。レビュー待ち（`review/`）の子のワークツリーで後から積んだコミットは親へ入らない。指摘を直すときは、同じフェーズに子を足してユーザの承認を受け、その子で直す（差し戻し）。手元の子のブランチに合流されていないコミットが残っていると、レビューの依頼が止まる
- 衝突したときは、子のワークツリーで`ccnavi-git.sh merge <親のブランチ>`を打って衝突を解き、コミットしてから`finish`をやり直す。
  並行していた子とぶつかったときも、解くのは後から`finish`した子のワークツリーで行う
- `cancel`は子を親へ合流させずに閉じる。子のブランチは手元に残り、親を閉じる`ready`のあとに、一覧をユーザに見せて確認を取ってから消す（[worktree-cleanup.md](worktree-cleanup.md)）
- レビューの依頼（`review-request`）の前提は、すべての子が合流済みであること。`finish`のあとに子のブランチへ積んだ未合流の修正があっても満たさない
- 衝突を解くために子へ親を取り込んでも、ほかの子の変更はサブエージェントの範囲の検査やリスクの計測に混ざらない
- 子のワークツリーで統合先（`origin/<統合先>`）を merge して衝突を解いたあとも、`finish`の範囲の検査とリスクは、その merge が持ち込んだだけのパス（統合先に既にある内容）を数えない。衝突の解決で書き換えたパスと、取り込んだあとに子が直したパスは、子の変更として検査する
- originの無いリポジトリでは、`finish`は合流も push もしない

## マージリクエストに出すとき

- マージリクエストに出した場合は、すべての子が合流済みと確かめ（合流は子の`finish`が済ませている）、親を`finish`で閉じてpushし、親のワークツリーの外（ワークスペースルートなど）から
  `ready --parent <親>`を打つ。ここ（`finish` → push → `ready`）までは、ユーザがレビュー済みにした時点で合意の範囲に入る。
  pushとDraftを外す前に、ユーザへ確認を取り直さずに進める（分類器に止められたときだけ許可を頼む）。`ready`はDraftを外す前に、閉じたチケットとその記録
  （`.ccnavi/approved/`の`done/`・`phases/<親>/`・`flows/`。マーカー`ready.json`も含む）をワークスペースの
  `logs/archive/`（バックアップ。閉じたかの判定には使わない）へ移し、`wip/`の追跡済みのファイルを消して、その削除をコミットしてpushする。`wip/`を自分で消す手順（`rm -r wip`）は要らない。
  消したファイルと、戻せる版（消す前のHEAD）が出力に出る。`wip/`に未追跡のファイルがあると、履歴から戻せないので消さずに名指しして止まる。
  要るものは別の場所へ移し、要らないものはユーザに確かめてから消して打ち直す。
  `ready`が「置き場かwip/に未コミットの変更がある」と言って止まったときは、その削除をコミットしてpushしてから`ready`を打ち直す
- マージリクエストの差分をレビューするときは、`wip/handoff/`の下を対象に数えない（作業中の下書き）。レビューの依頼の本文とマージリクエストの下書きにも、その旨の一文が入る
- `ready`がDraftを外したあと、子のワークツリーと合流済みの子の手元のブランチ、親のワークツリーを片付ける。取り消した子のブランチは確認を取ってから消す。親の手元のブランチは、ユーザがMRをマージしたことを
  `ccnavi-sync.sh`が確かめたあとに、未pushのコミットが無いときだけ消す。
  squashで取り込まれると`branch -d`が通らないので、条件の確認と削除はccnaviが行う。
  ブランチを消す条件は[worktree-cleanup.md](worktree-cleanup.md)にある
