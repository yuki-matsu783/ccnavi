# ワークツリーの作業を統合先に取り込む

作業が完了したら`<統合先>`に取り込む。コンフリクトの解消で判断に困る場合はユーザに確認する。
取り込んだあとの片付けは[worktree-cleanup.md](worktree-cleanup.md)。

## 直接作業のワークツリーを取り込む（`integrate`）

- ターンの終わりに、直接作業のワークツリーに未コミットの変更か`<統合先>`に入っていないコミットがあって`integrate <名前>`の記録が無ければ、hook が1回だけ止めて`integrate`を促す。
  促しの文のコマンドは1行で完結し、別のツリーで打つものは`cd <パス> && …`で始まる。そのまま打つ
- セッションの開始で、終わっていない`integrate`の記録（`.git/ccnavi-integrate/<名前>/marker`）があれば知らせる。別のセッションの取り込みの場合もあるので、
  操作する前に担当と今の状態をユーザに確かめる。知らせは、統合先のツリーの変更を操作してよい根拠ではない
- チケットを起こさない直接作業のワークツリーは、マージコミットを作らず、staged（add済み・未コミット）の状態で`<統合先>`へ取り込める。
  ユーザが中身を確かめてからコミットするための形で、手順は次の3段になる。どれも`<統合先>`をチェックアウトしているツリー
  （ワークスペースルートなど）で打つ。ほかのツリーで打つと拒否され、正しいツリーの場所が出る
  1. `ccnavi-git.sh integrate <名前>`: `.claude/worktrees/<名前>`のブランチを`merge --squash`で取り込み、staged にして止まる。
     ブランチが持ち込んだ`wip/handoff/`の下書きは取り込まずに外す（indexと作業ツリーから消す）。
     `wip/`のそれ以外（`wip/proposals/`など）は外さない。
     `<統合先>`のツリーに未コミットの変更（staged・未ステージ・未追跡。gitが無視するものは数えない）があると、
     別のセッションやユーザの書きかけを巻き込むので拒否される。持ち主に確かめてから打ち直す。
     取り込む側のワークツリーに未コミットの変更があるときも拒否される（コミットした分しか取り込まれないため）
  2. ユーザが`ccnavi-git.sh status`と`ccnavi-git.sh diff --staged`で中身を確かめる。エージェントは結果を見せて返事を待つ
  3. `ccnavi-git.sh integrate-done <名前> -m <メッセージ>`: staged をコミットし（フックは通る）、ワークツリー・ブランチ・取り込みの記録を片付ける。
     ユーザが自分でコミットした後なら、`-m`なしで片付けだけ行う。staged が取り込んだときと違う、ブランチの先頭が動いた、
     ブランチの中身が`<統合先>`に入りきっていない（gitが2.38未満で確かめられないときも。`wip/handoff/`の差は数えない）のどれかなら、何も消さずに理由が出る。
     片付けが途中で止まったら（gitが無視するファイルが残っている、など）、残したものが出るので、原因を片付けて同じコマンドを打ち直す。
     済んだところは飛ばして続きから進む
- `integrate-done`がコミットした squash も、ターンの終わりの報告（コミット済みの差分）から外れる。`integrate-done`は片付けの直前に
  記録を`ccnavi-integrate-done/<名前>`（git ディレクトリの中）へ写して残し、実行後チェックはそれを手がかりに git で確かめる。
  外すのは、コミットの親が記録の`base`でツリーが記録の`tree`、記録のブランチの先頭が HEAD の祖先でもローカルのブランチと stash の中でもなく、
  `merge-tree --write-tree <base> <先頭>`の結果がそのツリーと`wip/handoff/`の下を除いて同じで、名前がチケットに結び付かないときだけ。
  同じターンの別のコミットも触ったパスは外さない。片付けの後なので、ワークツリーがその先頭を開いていたことはもう確かめられない。
  この除外の限界として、`.git`の中を書けるエージェントは、記録とオブジェクトを作って取り込みに見せかけた直接のコミットを外せる
  （レビューで確認済み）。`.git`を書く操作は実行後チェックの報告に残らない場合があるため、この除外は「誤って直接のコミットを取り込みとして扱う」ことを防ぐ
  ものであり、意図的な偽装を防ぐものではない。偽装を防ぐには、記録をスクリプトだけが書ける場所へ移す必要があり、それは別途の判断になる
- 取り込みをやめるとき、または`integrate`が衝突で止まったときは、`ccnavi-git.sh integrate --abort <名前>`で取り込む前に戻す。
  squash の衝突は`merge --abort`では戻せず、`reset`は通らない。衝突は`<統合先>`のツリーでは解かず、
  ワークツリーの中で`ccnavi-git.sh merge <統合先>`を打って解いてコミットしてから、`integrate`を打ち直す
- `integrate`の対象は直接作業のワークツリーだけで、チケットに結び付く名前は拒否される。結び付くかは実行ファイルの`tree bound`に聞いて決める
  （承認済みチケット・提案に同じ名前がある、手元の退避に同じ名前の親がある、origin に同名のブランチが在る親のワークツリー）。チケットの作業は今までどおり、下のマージリクエストの手順で出す
- `integrate`の staged は、統合先のツリーが保護領域でも、実行後チェックの報告から外れる（外さないと戻す設定で自動的に
  戻され、取り込みが効かない）。外すのは、取り込みの記録・ブランチの先頭・HEAD・index が合い、index が
  `merge-tree --write-tree`の結果（HEAD にそのブランチを squash したもの）と、`wip/handoff/`の下を除いて同じで、`.claude/worktrees/<名前>`が
  そのブランチを同じ先頭で開いていて、チケットに結び付かないときだけ。記録は`.git`の中にありエージェントも書けるので、
  内容は信用せず git の状態で確かめている。残るリスクは、ワークツリーの中での書き込みを、そのツリーの実行後チェックが
  見逃した場合に、`integrate`がそのまま統合先へ運べること。記録をスクリプトだけが書ける場所へ移す案は、この変更の範囲外
- 「`<統合先>`が保護されている」はリモートへの push に効く話で、手元の`<統合先>`のツリーへの`integrate`には影響しない。
  取り込んだコミットをリモートへ送るかどうかはユーザが決める（`ccnavi-git.sh push`は統合先へは送らない）

## 統合先が進んでいるとき・保護されているとき

取り込み方は作業の種類で決まる。「手元の`<統合先>`への取り込み」と「リモートへの push の保護」は別の話で、混ぜない。

| 作業 | 取り込み方 |
|---|---|
| 直接作業 | `integrate` → ユーザ確認 → `integrate-done`（上の節）。`<統合先>`がリモートで保護されていても手元への取り込みは変わらない |
| チケット作業 | マージリクエストに出す（下の節）。手元の`<統合先>`へは取り込まない |

- ワークツリーのブランチを切ったあとに`<統合先>`が進んでいたら、ワークツリーの中で`ccnavi-git.sh merge <統合先>`を打ってコンフリクトを解消し、それから`integrate`を打つ
- 保護の種類は2つある。手元の`<統合先>`を保護対象のツリーとして書き込めない（実行後チェックの扱いは上の節）のは`integrate`の話。リモートの`<統合先>`が保護されていて push できないのは、ユーザがどう出すかを決める話（`ccnavi-git.sh push`は統合先へは送らない）
- 上の2つに当てはまらない作業（例: 統合先にそのままfast-forwardで取り込む）は、ユーザが明示的に頼んだときだけの例外。`ccnavi-git.sh worktree remove <パス>`と`ccnavi-git.sh branch -d <名前>`で片付けるのは、取り込みが済んでから

## 子の成果を親のブランチへ合流する（子の`finish`）

チケット作業の子は、メインが`ccnavi-ticket.sh finish <子>`を打つと、親のブランチへ合流してから push する。
サブエージェントは子のワークツリーで実装して手元でコミットするだけで、合流・状態の記録・push はしない。

- `finish`は1操作（write-and-push）で次を順に行う。途中で止まったときは、何も変えていない
  1. ロックを取り、親のワークツリーが merge / rebase の途中でないことを確かめる
  2. 取り込み（sync）。親のワークツリーに、状態の置き場以外の未コミットの変更があれば止める
  3. 子のワークツリーに未コミットの変更があれば止める（「サブエージェントの作業がコミットされていません」。コミットさせてからやり直す）
  4. 取り込み直後の親の先頭と子のブランチの共通の祖先から、子の先頭までの変更を検査する。置き場
     （`.ccnavi/approved/`・`wip/proposals/`。フェーズのマーカーと記録を含む）の変更が1つでもあるか、子・親・フェーズ定義の範囲の外のパスがあれば合流しない
  5. `merge --no-ff --no-commit`で子を入れ、完了の記録（`review/`か`done/`へ移す）と子の承認済みチケットの`merged_sha:`（合流した子の先頭）を足して、
     合流と状態を1つのマージコミットにする。衝突したら merge を取りやめて何も変えずに止まる
  6. push。通らなければ、元の先頭から最終の先頭までを戻す（合流したコードも）。シグナルで中断されたときも同じ。応答が失われても、リモートに届いていれば成功
  7. 完了（`done/`）した子のワークツリーを片付ける。レビュー待ち（`review/`）の子のワークツリーは残す。片付けに失敗しても`finish`は成功
- 合流は`finish`の1回だけ。レビュー待ち（`review/`）の子のワークツリーで後から積んだコミットは親へ入らない。指摘を直すときは、同じフェーズに子を足してユーザの承認を受け、その子で直す（差し戻し）。手元の子のブランチに合流されていないコミットが残っていると、レビューの依頼が止まる
- 衝突したときは、子のワークツリーで`ccnavi-git.sh merge <親のブランチ>`を打って衝突を解き、コミットしてから`finish`をやり直す。
  並行していた子とぶつかったときは、先に合流した子の名前が出る。解くのは後から`finish`した子のワークツリー
- `cancel`は子を親へ合流させずに閉じる。子のブランチは手元に残り、親を閉じる`ready`のあとに、一覧をユーザに見せて確認を取ってから消す（.ccnavi/docs/worktree-cleanup.md）
- レビューの依頼（`request`）の前提は、すべての子が合流済みであること。合流済みは、子の`merged_sha`が親のブランチの先頭の祖先かで確かめ、さらに子の手元のブランチに`finish`のあとに積んだ未合流の修正があれば満たさないとする（子のワークツリーが無い PC では、この修正の確認は行わない）
- サブエージェントの範囲の検査とリスクの計測は、上の4と同じ取り方（共通の祖先から）で数える。衝突を解くために子へ親を取り込んでも、ほかの子の変更が混ざらない
- origin の無いリポジトリの親は write-and-push の対象外で、`finish`は合流しない（`merged_sha`は、子の先頭がすでに親に入っているときだけ書く）

## マージリクエストに出すとき

- マージリクエストに出した場合は、すべての子が合流済みと確かめ（合流は子の`finish`が済ませている）、親を`finish`で閉じてpushし、親のワークツリーの外（ワークスペースルートなど）から
  `ready --parent <親>`を打つ。ここ（`finish` → push → `ready`）までは、ユーザがレビュー済みにした時点で合意の範囲に入る。
  pushとDraftを外す前に、ユーザへ確認を取り直さずに進める（分類器に止められたときだけ許可を頼む）。`ready`はDraftを外す前に、閉じたチケットとその記録
  （`.ccnavi/approved/`の`done/`・`phases/<親>/`・`flows/`。マーカー`ready.json`も含む）をワークスペースの
  `logs/archive/`（バックアップ。閉じたかの判定には使わない）へ移し、`wip/`の追跡済みのファイルを消して、その削除をコミットしてpushする。`wip/`を自分で消す手順（`rm -r wip`）は要らない。
  消したファイルと、戻せる版（消す前のHEAD）が出力に出る。`wip/`に未追跡のファイルがあると、履歴から戻せないので消さずに名指しして止まる。
  要るものは別の場所へ移し、要らないものはユーザに確かめてから消して打ち直す。
  `ready`が「置き場かwip/に未コミットの変更がある」と言って止まったときは、その削除をコミットしてpushしてから`ready`を打ち直す
- マージリクエストの差分をレビューするときは、`wip/handoff/`の下を対象に数えない（作業中の下書き）。レビューの依頼の本文とマージリクエストの下書きにも、その旨の一文が入る
- `ready`がDraftを外したあと、子のワークツリーと、合流済みの子の手元のブランチ（先頭が`merged_sha`と同じで、push済みの親に含まれるもの）、
  親のワークツリーを片付ける。取り消した子のブランチは確認を取ってから消す。親の手元のブランチは、ユーザがMRをマージしたことを
  `ccnavi-sync.sh`が確かめたあとに、手元の先頭がMRの先頭に含まれ未pushのコミットが無いときだけ消す（同時に親の片付けの記録も消える）。
  squashで取り込まれると`branch -d`が通らず、ラッパースクリプトは`-D`を通さないので、条件の確認と削除はccnaviの実行ファイルが行う。
  詳しくは.ccnavi/docs/worktree-cleanup.md
