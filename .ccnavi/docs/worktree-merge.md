# ワークツリーの作業を統合先に取り込む

作業が完了したら`<統合先>`に取り込む。コンフリクトの解消で判断に困る場合はユーザに確認する。
取り込んだあとの片付けは[worktree-cleanup.md](worktree-cleanup.md)。

## 直接作業のワークツリーを取り込む（`integrate`）

取り込み先は、ワークツリーを切った時点でメインのチェックアウトが開いていたブランチで、直接作業の記録（`ccnavi-direct/<名前>`）に残っている。統合先（`origin/HEAD`）とは限らない。手順の全体は[direct-flow.md](direct-flow.md)。

- ターンの終わりに、直接作業のワークツリーに未コミットの変更か取り込み先に入っていないコミットがあって、取り込み中のmarkerが無ければ、hookが1回だけ止めて`integrate`を促す。
  促しの文のコマンドは1行で完結し、別のツリーで打つものは`cd <パス> && …`で始まる。そのまま打つ
- セッションの開始で、終わっていない`integrate`の記録（`.git/ccnavi-integrate/<名前>/marker`）、残った取り込み済みの記録、一時ワークツリー、専用のrefがあれば知らせる。
  別のセッションの取り込みの場合もあるので、操作する前に担当と今の状態をユーザに確かめる。知らせは、メインのチェックアウトの変更を操作してよい根拠ではない。
  壊れた記録は自動では再開しない
- チケットを起こさない直接作業のワークツリーは、マージコミットを作らず、1コミットで取り込み先へ載せる。
  確認の間、メインのチェックアウトのindex・作業ツリー・HEADには書かない。手順は次の3段になる。`integrate`と`integrate-done`は、
  取り込み先をチェックアウトしているメインのチェックアウトで打つ。ほかのツリーで打つと拒否され、正しい場所が出る。取り込み先を開いていなければ断る
  （ブランチが替わっていたら、ユーザに戻してもらう。エージェントはcheckoutしない）
  1. `ccnavi-git.sh integrate <名前>`: 取り込み結果（C）を`merge-tree --write-tree --merge-base=S HEAD T`で計算し、一時ワークツリー（`logs/direct-tmp/<repo>/<名前>`）に展開して止まる。
     ブランチが持ち込んだ`wip/handoff/`の下書きは取り込まない。作業ワークツリーに未コミットの変更があるとき、
     取り込み待ちの下書きが残っているときは拒否される（コミットした分しか取り込まれないため）。
     メインのチェックアウトに未コミットの変更があっても拒否しない。ユーザが横で作業しているものとして、最後のfast-forwardでgitが持ち越す
  2. ユーザが差分と変わるファイルの一覧を確かめる。エージェントは結果を見せて返事を待つ。変わるファイルをエディタで開いて保存していない編集があれば、`integrate-done`の前に保存してもらう。
     取り込み結果は一時ワークツリーで検証できる（そこは編集しない。プロジェクトのレイヤーのルールが通常どおり当たる場所ではない）。
     取り込みで増えるパスがメインのチェックアウトのignoredのファイルと重なっていれば、`integrate`が挙げる。ユーザに退避を頼む
  3. `ccnavi-git.sh integrate-done <名前> -m <メッセージ>`: 一時ワークツリーで1コミット（K）にし（フックは通る）、Kの親と木を確かめてから、
     メインのチェックアウトで`git merge`の`--ff-only --no-overwrite-ignore`でKを載せる。そのあと作業ワークツリー、一時ワークツリー、ブランチ、専用のrefと記録、markerを片付ける。
     ユーザの未コミットの変更（別のファイル）・staged・新規ファイルは持ち越される。同じファイルが未コミットなら、何も変えずにファイル名が出る。
     ignoredのファイルと重なるときも、上書きせずに止まる。HEADや作業ブランチの先頭が確認したあとに動いたときは、`integrate`を打ち直す。
     自己防衛の対象（ccnaviの設定ファイルなど）を含む取り込みは、ユーザが端末で、エージェントのターンが終わってから打つ（端末以外では断る。
     fast-forwardで設定ファイルが書き換わると、エージェントのツール呼び出しのあとの照合が元に戻してしまうため）。
     片付けが途中で止まったら、取り込みの成功とは分けて残したものが出る。原因を片付けて同じコマンドを打ち直すと、済んだところを飛ばして続きから進む。
     一時ワークツリーに知らないファイルやignoredのファイルが残っているときは、削除せずにパスと中身を通知する
- `integrate-done`が載せたKは、ターンの終わりの報告（コミット済みの差分）から外れる。`integrate-done`は片付けの直前に取り込み済みの記録を
  `ccnavi-integrate-done/<名前>`（gitディレクトリの中）へ写して残し、実行後チェックはそれを手がかりにgitで確かめる。
  外すのは、コミットの親が記録の`head`でツリーが記録の`c_tree`で、名前がチケットに結び付かないときだけ。記録に`k`があれば、それがK自身であること。
  専用のrefは求めない。gcでオブジェクトが消えたあとは照合できず、報告に出る。
  この除外の限界として、`.git`の中を書けるエージェントは、記録とオブジェクトを作って取り込みに見せかけた直接のコミットを外せる。
  この除外は「誤って直接のコミットを取り込みとして扱う」ことを防ぐものであり、意図的な偽装を防ぐものではない。
- 取り込みをやめるときは、`ccnavi-git.sh integrate --abort <名前>`で一時ワークツリーと専用のref（`t`・`c`・`k`）とmarkerを消す。
  作業ワークツリーとメインのチェックアウトには触らず、直接作業の記録は残るので、作業を続けてもう一度`integrate`を打てる。
  Kがすでに取り込み先に載っているときは断る。ユーザが`git revert`する。
  `integrate`が衝突で止まったときは、衝突したパスを挙げて断る。メインのチェックアウトでは解かず、
  作業ワークツリーの中で`ccnavi-git.sh merge <取り込み先>`を打って解いてコミットしてから、`integrate`を打ち直す
- `integrate`の対象は直接作業のワークツリーだけで、チケットに結び付く名前は拒否される。結び付くかは実行ファイルの`tree bound`に聞いて決める。
  取り込み先のブランチがチケットに結び付くかは、別の判定として`tree base-bound`に聞き、ワークツリーを切る前に断る
  （承認済みチケット・提案に同じ名前がある、手元の退避に同じ名前の親がある、取り込み先のリポジトリの承認済みチケットの`branch:`が一致する、など）。
  チケットの作業は今までどおり、下のマージリクエストの手順で出す
- 記録の無い直接作業のワークツリーは、`integrate`が断って`ccnavi-worktree.sh <名前> --adopt --base <ブランチ>`での引き取りを案内する
- 版の無い古い形式のmarker（旧来のsquashでstagedにした取り込み）は、`integrate`が断る。`integrate-done`か`integrate --abort`で終わらせる。
  更新の前に、途中の`integrate`を終わらせておく
- 取り込んだコミットをリモートへ送るかどうかはユーザが決める。`origin/<取り込み先>`が手元より進んでいれば、`integrate`が警告し、
  `integrate-done`が`git push origin <取り込み先>`をユーザに頼む案内を出す（`ccnavi-git.sh push`は統合先へも取り込み先へも送らない）

## 取り込み先・統合先が進んでいるとき・保護されているとき

取り込み方は作業の種類で決まる。「手元の`<統合先>`への取り込み」と「リモートへの push の保護」は別の話で、混ぜない。

| 作業 | 取り込み方 |
|---|---|
| 直接作業 | `integrate` → ユーザ確認 → `integrate-done`（上の節）。載せ先は取り込み先のブランチ。`<統合先>`がリモートで保護されていても手元への取り込みは変わらない |
| チケット作業 | マージリクエストに出す（下の節）。手元の`<統合先>`へは取り込まない |

- ワークツリーのブランチを切ったあとに取り込み先が進んでいたら、ワークツリーの中で`ccnavi-git.sh merge <取り込み先>`を打ってコンフリクトを解消し、それから`integrate`を打つ
- 保護の種類は2つある。手元の取り込み先を保護対象のツリーとして書き込めないときは、`integrate-done`をユーザが端末で打つ（上の節）。リモートの`<統合先>`が保護されていてpushできないのは、ユーザがどう出すかを決める話（`ccnavi-git.sh push`は統合先へは送らない）
- 上の2つに当てはまらない作業（例: 統合先にそのままfast-forwardで取り込む）は、ユーザが明示的に頼んだときだけの例外。`ccnavi-git.sh worktree remove <パス>`と`ccnavi-git.sh branch -d <名前>`で片付けるのは、取り込みが済んでから

## 子の成果を親のブランチへ合流する（子の`finish`）

チケット作業の子は、メインが`ccnavi-ticket.sh finish <子>`を打つと、親のブランチへ合流してから push する。
サブエージェントは子のワークツリーで実装して手元でコミットするだけで、合流・状態の記録・push はしない。

- `finish`は1操作（write-and-push）で次を順に行う。途中で止まったときは、何も変えていない
  1. ロックを取り、親のワークツリーが merge / rebase の途中でないことを確かめる
  2. 取り込み（sync）。親のワークツリーに、状態の置き場以外の未コミットの変更があれば止める
  3. 子のワークツリーに未コミットの変更があれば止める（「サブエージェントの作業がコミットされていません」。コミットさせてからやり直す）
  4. 取り込み直後の親の先頭と子のブランチの共通の祖先から、子の先頭までの変更を検査する。置き場
     （`.ccnavi/approved/`・`wip/proposals/`。フェーズのマーカーと記録を含む）の変更が1つでもあるか、子・親・フェーズ定義の範囲の外のパスがあれば合流しない
  5. `merge --no-ff --no-commit`で子を入れ、完了の記録（`review/`か`done/`へ移す）と子の承認済みチケットの`merged_sha:`（合流した子の先頭）を足して、
     合流と状態を1つのマージコミットにする。衝突したら merge を取りやめて何も変えずに止まる
  6. push。通らなければ、元の先頭から最終の先頭までを戻す（合流したコードも）。シグナルで中断されたときも同じ。応答が失われても、リモートに届いていれば成功
  7. 完了（`done/`）した子のワークツリーを片付ける。レビュー待ち（`review/`）の子のワークツリーは残す。片付けに失敗しても`finish`は成功
- 合流は`finish`の1回だけ。レビュー待ち（`review/`）の子のワークツリーで後から積んだコミットは親へ入らない。指摘を直すときは、同じフェーズに子を足してユーザの承認を受け、その子で直す（差し戻し）。手元の子のブランチに合流されていないコミットが残っていると、レビューの依頼が止まる
- 衝突したときは、子のワークツリーで`ccnavi-git.sh merge <親のブランチ>`を打って衝突を解き、コミットしてから`finish`をやり直す。
  並行していた子とぶつかったときは、先に合流した子の名前が出る。解くのは後から`finish`した子のワークツリー
- `cancel`は子を親へ合流させずに閉じる。子のブランチは手元に残り、親を閉じる`ready`のあとに、一覧をユーザに見せて確認を取ってから消す（.ccnavi/docs/worktree-cleanup.md）
- レビューの依頼（`request`）の前提は、すべての子が合流済みであること。合流済みは、子の`merged_sha`が親のブランチの先頭の祖先かで確かめ、さらに子の手元のブランチに`finish`のあとに積んだ未合流の修正があれば満たさないとする（子のワークツリーが無い PC では、この修正の確認は行わない）
- サブエージェントの範囲の検査とリスクの計測は、上の4と同じ取り方（共通の祖先から）で数える。衝突を解くために子へ親を取り込んでも、ほかの子の変更が混ざらない
- origin の無いリポジトリの親は write-and-push の対象外で、`finish`は合流しない（`merged_sha`は、子の先頭がすでに親に入っているときだけ書く）

## マージリクエストに出すとき

- マージリクエストに出した場合は、すべての子が合流済みと確かめ（合流は子の`finish`が済ませている）、親を`finish`で閉じてpushし、親のワークツリーの外（ワークスペースルートなど）から
  `ready --parent <親>`を打つ。ここ（`finish` → push → `ready`）までは、ユーザがレビュー済みにした時点で合意の範囲に入る。
  pushとDraftを外す前に、ユーザへ確認を取り直さずに進める（分類器に止められたときだけ許可を頼む）。`ready`はDraftを外す前に、閉じたチケットとその記録
  （`.ccnavi/approved/`の`done/`・`phases/<親>/`・`flows/`。マーカー`ready.json`も含む）をワークスペースの
  `logs/archive/`（バックアップ。閉じたかの判定には使わない）へ移し、`wip/`の追跡済みのファイルを消して、その削除をコミットしてpushする。`wip/`を自分で消す手順（`rm -r wip`）は要らない。
  消したファイルと、戻せる版（消す前のHEAD）が出力に出る。`wip/`に未追跡のファイルがあると、履歴から戻せないので消さずに名指しして止まる。
  要るものは別の場所へ移し、要らないものはユーザに確かめてから消して打ち直す。
  `ready`が「置き場かwip/に未コミットの変更がある」と言って止まったときは、その削除をコミットしてpushしてから`ready`を打ち直す
- マージリクエストの差分をレビューするときは、`wip/handoff/`の下を対象に数えない（作業中の下書き）。レビューの依頼の本文とマージリクエストの下書きにも、その旨の一文が入る
- `ready`がDraftを外したあと、子のワークツリーと、合流済みの子の手元のブランチ（先頭が`merged_sha`と同じで、push済みの親に含まれるもの）、
  親のワークツリーを片付ける。取り消した子のブランチは確認を取ってから消す。親の手元のブランチは、ユーザがMRをマージしたことを
  `ccnavi-sync.sh`が確かめたあとに、手元の先頭がMRの先頭に含まれ未pushのコミットが無いときだけ消す（同時に親の片付けの記録も消える）。
  squashで取り込まれると`branch -d`が通らず、ラッパースクリプトは`-D`を通さないので、条件の確認と削除はccnaviの実行ファイルが行う。
  詳しくは.ccnavi/docs/worktree-cleanup.md
