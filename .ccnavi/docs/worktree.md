# ワークツリーで作業する

ワークツリーを切る前後の決まり。issue・MRを指定されたときは[worktree-start.md](worktree-start.md)、`<統合先>`への取り込みは[worktree-merge.md](worktree-merge.md)、片付けは[worktree-cleanup.md](worktree-cleanup.md)を読む。チケット作業（親と子）の手順は[ticket-flow.md](ticket-flow.md)、直接作業の手順は[direct-flow.md](direct-flow.md)にあり、どちらもステップごとの一覧と図で示す。

## 基本

- gitは直接呼ばず、`ccnavi-git.sh`経由で使う。使えるサブコマンドとオプションは、このスクリプトの`--help`で確かめられる
- `.ccnavi/scripts/`はワークスペースルートにしか無いため、shを呼び出すときのパスはcwdによって変わる

  | cwd | 呼び出し方 |
  |---|---|
  | ワークスペースルート | `sh .ccnavi/scripts/ccnavi-git.sh ...` |
  | ワークツリーや`projects/<名前>`の中 | `sh <ワークスペースルートの絶対パス>/.ccnavi/scripts/ccnavi-git.sh ...` |

  ワークツリーや`projects/<名前>`の中では、相対パス（`../../../`・`../../`）を使わない。cwdがその最上段のときしか届かず、サブディレクトリへ`cd`した後や別のツリーから打つと外れるため。
  `ccnavi-git.sh`は cwd のリポジトリに対して動くため、ワークツリーで操作するときは、そのツリーへ`cd`してから打つ。
  コマンド名やパスを変数に入れない（止められる）。
  gitを直接呼んで拒否されたときの案内も、実際の絶対パスに展開した同じ形で出るので、そのまま使える

## 他セッションの作業を踏まないために

- 自分のワークツリーの外、つまりワークスペースルートや他のワークツリーにある未コミットの変更は、他セッションのものとして扱う
- 他セッションの書きかけの変更は、コミットも、ブランチの移動も、`reset`もしない。ビルドが失敗していても直さず、
  何が失敗しているかを報告して判断を仰ぐ
- 変更の退避が必要なときは`ccnavi-git.sh stash push -u`を使う。ユーザがその変更を捨てるよう明示して頼んだときも、捨てずに`stash push -u -- <頼まれたパス>`で退避する（`restore`は退避を作らず失うので使わない）。退避で変更を消す前に、[scratchpad.md](scratchpad.md)の置き場へコピーも取っておく。コピーは他セッションのツリーの中には置かない

## ワークツリーを切る

### スクリプトで切る

- 直接作業のワークツリーは`sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-worktree.sh <名前>`で切る。取り込み先の確認・リモートとのずれの確認・書きかけの扱いをまとめて行う。
  取り込み先は、切った時点でユーザのチェックアウト（`git worktree list`の先頭）が開いているブランチ。起点は、取り込み先のHEADか、`--copy-wip`でコピーした書きかけを含むスナップショット。`origin`からは切らず、手元の取り込み先は進めない。ルートのindexとワークツリーには書かない。
  次のどれかに当たると、切らずに終了コード3で止まり、状態・勧め・リスク・選択肢・確認コードを出す。報告をユーザに伝え、了承を得てから`--base`・`--accept`などを付けて打ち直す。
  - cwdのブランチが取り込み先と違う（`--base <取り込み先>`が要る）
  - 取り込み先が統合先（`origin/HEAD`）でない
  - `origin/<取り込み先>`より遅れている・進んでいる・分岐している・`origin`に無い・リモート未確認（`fetch`が届かない場合を含む）
  - ユーザのチェックアウトに書きかけ（追跡済みの変更・新規ファイル。ワークツリーの置き場 `.claude/worktrees/` は数えない）がある（`--copy-wip`か`--no-wip`が要る）
  後ろの3つは`--accept <確認コード>`も要る。確認コードは今の状態から決まるので、状態が動けば報告からやり直す。何もずれが無ければ確認なしで切る。
  `--side-by-side`を付けると、このワークツリーが残っている間は、ユーザのチェックアウトで見つかった変更を自動で戻さず報告にする（ccnaviの設定ファイルは戻す）。付けるとユーザの確認ダイアログが出る。
  取り込み先の断り: ユーザのチェックアウトがdetached HEAD、取り込み先がチケットに結び付く、結び付くかを確かめられない、gitが2.40未満。
  行き先は`<ワークスペースルート>/.claude/worktrees/<名前>`で、cwdが`projects/<名前>`の中でも変わらない。ワークツリーが既にあれば、パスを出すだけです。`--dry-run`は予定だけ出す（fetchしない）。
  `origin`か手元に同じ識別子になるブランチ（同じ名前、`feature/7-x`に対する`feature-7-x`、英字の大文字小文字だけ違う名前）があるときは、切らずに終了コード1で止まり、`ccnavi-start.sh`を案内する（既にあるブランチは、MRを採用してよいか確かめてから出す）。名前に使える字と長さは、`ccnavi-worktree.sh`が確かめる。
  `worktree add`が拒否されたときは、`ccnavi-git.sh`の出力の案内に従う。以下の手動の手順は、このスクリプトを使えないときに使います。名前と同じブランチが既にあってワークツリーが無いときは2段に分かれます。まず`ccnavi-git.sh worktree add .claude/worktrees/<名前> <名前>`でワークツリーを出し、次に`ccnavi-worktree.sh <名前> --adopt --base <統合先>`で引き取ります（ユーザの確認が要ります。引き取らないと、`integrate`は記録が無いため止まります。`--adopt`は既存のワークツリーが前提です）
- `ccnavi-worktree.sh`は直接作業のワークツリー用で、名前と同じブランチを新しく切る。親子のチケットの親のワークツリーには使わない。
  親のワークツリーの中から切り替えられるのは、親の提案が承認前（`todo/` にあるだけ）のときだけ。承認済み・レビュー待ち・着手済みの子があるときは、切る前に終了コード 1 で断る（[ticket-work.md](ticket-work.md)の「拒否される条件と、切り替える前の取り下げ」）。
  親は識別子の名前のブランチを作らず、親のブランチ（MRの元ブランチ）を直接チェックアウトする。作るのは`ccnavi-start.sh --mr <番号>`か
  `--issue <番号>`。子のワークツリーは`ccnavi-ticket.sh start <子>`が親のブランチから作る

### 置き場と名前

- 置き場はワークスペースの`.claude/worktrees/<ブランチ名>`にする（チケットのワークツリーは`.claude/worktrees/<識別子>`）。プロジェクトから切る場合も同じ場所に置く。
  階層は1段だけにして、その下にさらに階層を作らない
- 行き先の名前とブランチ名は揃える（`-b <行き先の名前>`）。名前に`/`を含むブランチだけは、行き先をブランチ名の`/`を`-`に置き換えた名前にする
  （`feature/123-login`は`.claude/worktrees/feature-123-login`。識別子のブランチは作らず、ブランチを直接チェックアウトする）。`-B`・`--detach`・`--force`は拒否される。
  `-b`を付けずに2つ目の語を渡す場合、渡せるのは行き先と同じ名前の手元のブランチか`origin/<名前>`だけで、タグやshaは拒否される。

### 手で切るとき

- 直接作業のワークツリーは手で切らず、`ccnavi-worktree.sh`で切る。起点は取り込み先のHEADで、`origin/<統合先>`から切らない。以下はチケット作業の親と子、または`ccnavi-worktree.sh`を使えないときの手順
- `ccnavi-git.sh worktree add <行き先> -b <名前> --no-track origin/<統合先>`で作る。起点は`origin/<統合先>`にして、
  手元の`<統合先>`は進めない（追跡の設定も付けない）。末尾の起点を省くと今いるブランチが起点になるため、省かずに書く
- 切る前に`ccnavi-git.sh fetch origin <統合先>`し、`ccnavi-git.sh log --oneline <統合先>..origin/<統合先>`で遅れを確かめる。
  遅れていなければ、基点を`<統合先>`にして切ってもよい。遅れていれば、上のとおり`origin/<統合先>`から切る
  基点が`<統合先>`か`origin/<統合先>`のとき、fetchが古い、または手元の統合先がoriginより遅れていると`worktree add`は拒否する。オフラインでfetchできないときは、警告だけで通す
- `<行き先>`はcwdからの相対パスとして解釈される。ワークスペースルートからなら`.claude/worktrees/<名前>`、
  `projects/<名前>`の中からなら`../../.claude/worktrees/<名前>`と書く。間違えるとコマンドは拒否され、cwdに合わせた正しいパスが表示される
- `worktree add`に渡せるオプションは決まっている（`-b` `--reason` `--track`など）。
  一覧に無いオプションは拒否される。必要なオプションが出てきたら、ユーザに一覧へ足してもらう
- `branch` `checkout` `switch` `fetch` `pull` `merge` `commit` `rm` `restore`のオプションは、許可リストと照らし合わせて通すかどうかが決まる。`merge`は、統合先のユーザのチェックアウトでは`--abort` `--continue` `--quit`以外は止める（ワークツリーの中と、統合先でないブランチでは通る）。`pull`は、統合先のユーザのチェックアウトでは、引数なしと`pull <リモート> <統合先>`だけが通る。
  長いオプションは略さずに書く。`--force-c`のような略は拒否される
- プロジェクトのワークツリーは`cd projects/<名前>`してから切る。`<統合先>`はそのプロジェクトのブランチで、
  ワークスペースの`main`ではない
- `<統合先>`がリモートにしか無いときは、先にプロジェクトの中で`ccnavi-git.sh fetch <リモート> <統合先>`を実行する

### 起点にする統合先

- この節は、親のワークツリーと、手で切るワークツリーの起点の話。直接作業のワークツリーの起点は取り込み先のHEAD（`--copy-wip`のときは書きかけのスナップショット）で、`origin`からは切らない
- 起点はリモートにある最新の統合先にする。統合先の名前は、そのリポジトリの手元の`origin/HEAD`が指すブランチで、無ければ`origin/main`、`origin/master`の順に使う。
  環境変数や`.claude/settings.local.json`で上書きする手段は無く、`projects/`の下のプロジェクトも、それぞれ自分の`origin/HEAD`で決まる。
  originの無いリポジトリでは統合先が決まらない。決まらないと案内が出たら、ユーザに`git fetch origin`のあと`git remote set-head origin -a`を頼む。`ccnavi-git.sh push`は統合先へも
  （`main`・`master`・`develop`・`release`・`release/*`と同じく）直接は送らない
- 手元の統合先が古いと、そこから切ったブランチも古いコミットから始まり、`<統合先>`に取り込むときにfast-forwardできなくなる。
  そのため、セッションの開始時に`ccnavi-fetch.sh`が手元の統合先をfast-forwardで進める。進められないとき（統合先をチェックアウトしているツリーに未コミットの変更がある、
  リモートと分岐している、など）は進めず、結果をセッションの冒頭の「[ccnavi]」で始まる行に出す。「進めた」か「から作った」で終わる行以外が1行でもあれば、統合先が古いままのことがある。
  そのときは、ワークツリーを切る前に`ccnavi-git.sh fetch origin <統合先>`と`ccnavi-git.sh log --oneline <統合先>..origin/<統合先>`で確かめる。
  logに何も出なければ、手元の統合先は最新である。fetchが失敗するならネットワークや認証を解消し、
  logにコミットが出るなら次の項目の手順で`origin/<統合先>`から切る。分岐しているならユーザに合流させてもらい、未コミットの変更があるならそのツリーの持ち主に聞く
- 手元の統合先を進めるのは、セッションの開始時の`ccnavi-fetch.sh`だけである。`ccnavi-git.sh fetch origin <統合先>`も`ccnavi-sync.sh`も、手元の`<統合先>`は進めない。
  セッション中にリモートが進んだときは、`ccnavi-git.sh fetch origin <統合先>`のあとに
  `ccnavi-git.sh worktree add <行き先> -b <名前> --no-track origin/<統合先>`で`origin/<統合先>`から切る。
  `--no-track`を省くと、新しいブランチが`origin/<統合先>`を追跡し、次のセッションの開始時にそのブランチが`origin/<統合先>`に合わされてしまう

## 親チケットのワークツリー

- 親チケットのワークツリーでは、別のブランチへ`checkout` / `switch`できない。ccnaviは親のワークツリーを
  「名前が親の識別子で、HEADのブランチ名の`/`を`-`に置き換えたものがその名前になるもの」として探す。
  別のブランチに移ると親のワークツリーが決まらず、リモートでの承認の取り込み（`ccnavi-sync.sh`、セッション開始時の取り込み）が飛ばされ、
  親と子のチケットの承認・状態の操作・実行前の判定も止まる
- 子の成果は、メインが打つ子の`finish`が親のブランチへ合流してpushする（[worktree-merge.md](worktree-merge.md)）。
  サブエージェントは子のワークツリーで実装して手元でコミットするだけで、親のワークツリーにはmerge・commit・書き込みをしない（止められる）
- 親のワークツリーへのWrite / Edit / NotebookEditは、メインセッションも置き場（`wip/proposals/`・`wip/handoff/`・`wip/eli5/`・承認済みの置き場）の外では止まる。
  親の範囲の中でも同じで、範囲を広げても通らない。親自身の作業（`plan: [quick-work]` など）も、子チケットを起こして子のワークツリーで行う。
  子のワークツリーでのコミットと、衝突を解くために子のワークツリーで親のブランチをmergeすることはできる
- 承認の前に親のワークツリーへ入った変更は、承認の後に戻すのも子の`finish`も止まる。片付け方は[ticket-work.md](ticket-work.md)の「正本と親のワークツリー」

## 直接作業のワークツリーの名前

- 新しく切る直接作業のワークツリーとブランチも、`<先頭の語>-<番号>-<slug>` の形にそろえる。親チケットと同じ形なので、後で取り込みを追うときや、チケットに移すときに名前を付け直さずに済む
  - 先頭の語は `CCNAVI_BRANCH_PREFIXES` の既定（`feature` `hotfix` `fix` `bugfix` `chore` `refactor` `docs`）から選ぶ
  - 番号は issue があればその番号、無ければ `sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-ticket.sh next-id` の通し番号（通し番号は直接作業の名前だけに使う。親チケットは必ず issue と MR のセットで、番号は issue の番号）
  - 例: `feature-341-direct-branch-name`（issue #341 の作業）、`chore-12-cleanup`（通し番号 12）
- 形に合わない名前は、切る前に（`--dry-run` でも）`ccnavi-worktree.sh` が warn を 1 行出す。`--lint` も同じ warn を名指しする
- 既にある直接作業のワークツリーとブランチの名前は変えない。この形は新しく切るものから適用する

## 親チケットの正本（親のワークツリーだけを読む）

- 親チケットの正本は親のブランチで、各PCでは`.claude/worktrees/<親の識別子>`にチェックアウトしたもの。承認済みチケット・マーカーは、その中のものだけを読む。ワークスペースルート・プロジェクトの元ツリー・子のワークツリーに残ったコピーで代用しない（`--lint`の診断にだけ使う）
- 親のワークツリーが無い、または`HEAD`のブランチ名の`/`を`-`に置き換えたものがフォルダ名と合わないPCでは、その親子の承認・状態の操作が止まる。`ccnavi-start.sh --mr <番号>`でそのブランチを`.claude/worktrees/<識別子>`にチェックアウトしてから続ける
- 親子ごとの取り込み状態は手元に持たない。判定は、親のワークツリーと、親のブランチ上のチケット・マーカーだけで決まるので、別のPCでも同じ結果になる。`ticket start`・`finish`は取り込み・コミット・pushまで行う
- 親のブランチがリモートから消えたときは、親のブランチへのpushが止まる。ブランチを改名したか消し間違えたのなら、ユーザが元の名前で戻す（ターミナルで`git push origin <ブランチ>`を一度）。破棄した親子のチケットなら、親のワークツリーを片付ければ止まらなくなる。診断は`ccnavi-sync.sh <親の識別子>`が出す
- 親チケットの作成と承認には、親のワークツリーがあること、`issue:`と`mr:`（`ccnavi-start.sh`が「必須」の行で出す値）が書いてあることが要る。`ccnavi ticket new --issue <値> --mr <番号>`が書く。`ticket new`の雛形に残る空欄の目印（`（ここに〜を書く）`）を書き換えていない提案も、承認と`--lint`が止める
- 提案は書いただけでは手元にしかない。承認を頼む前に`sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-ticket.sh propose <識別子>`で、親のブランチへ送る。別のPCでは、セッション開始時の取り込みで承認の画面にその提案が出る。サブエージェントは打てない
- ユーザに承認を頼んだあとは、承認待ちの提案ファイルを書き換えない。承認は、ユーザが見た提案が承認の直前も同じときだけ通る。違えば何も承認せず、「内容が更新されました」と最新を表示し直して、もう一度押してもらう
- `ticket start`で子のワークツリーが無ければ、親ブランチの先頭から`.claude/worktrees/<子の識別子>`を作る。同名のブランチが手元に残っていて、親の先頭に無いコミットがあれば作らずに止まる
- レビューの依頼（`ccnavi-review.sh request`）は、親ブランチのopenのMRが無ければMRを作らずに止まる。MRの元ブランチが`HEAD`のブランチと同じで、マージ先が統合先であることも確かめる
- 親を閉じたかはMRがマージ済みかで決める。`ccnavi-sync.sh`がホストに聞き、聞けなければ推定せず止まる。マージ済みと分かったら、親の手元のブランチ・ワークツリーを片付ける（条件は[worktree-cleanup.md](worktree-cleanup.md)）
- 同じ識別子のチケットが親のワークツリーの中で複数の置き場（`doing/`と`done/`など）にあれば、どれが正か決まらないので、状態の操作は止まる
