# ワークツリーで作業する

ワークツリーを切る前後の決まり。issue・MRを指定されたときは[worktree-start.md](worktree-start.md)、`<統合先>`への取り込みは[worktree-merge.md](worktree-merge.md)、片付けは[worktree-cleanup.md](worktree-cleanup.md)を読む。チケット作業（親と子）の手順は[ticket-flow.md](ticket-flow.md)、直接作業の手順は[direct-flow.md](direct-flow.md)にあり、どちらもステップごとの一覧と図で示す。

## 基本

- gitは直接呼ばず、`ccnavi-git.sh`経由で使う。使えるサブコマンドとオプションは、このスクリプトの`--help`で確かめられる
- `.ccnavi/scripts/`はワークスペースルートにしか無いため、shを呼び出すときのパスはcwdによって変わる

  | cwd | 呼び出し方 |
  |---|---|
  | ワークスペースルート | `sh .ccnavi/scripts/ccnavi-git.sh ...` |
  | ワークツリーや`projects/<名前>`の中 | `sh <ワークスペースルートの絶対パス>/.ccnavi/scripts/ccnavi-git.sh ...` |

  ワークツリーや`projects/<名前>`の中では、相対パス（`../../../`・`../../`）を使わない。cwdがその最上段のときしか届かず、サブディレクトリへ`cd`した後や別のツリーから打つと外れるため。
  コマンド名やパスを変数に入れない（`DENY_COMMAND_NAME_EXPANSION`で止まる）。
  gitを直接呼んで拒否されたときの案内も、実際の絶対パスに展開した同じ形で出るので、そのまま使える

## 他セッションの作業を踏まないために

- 自分のワークツリーの外、つまりワークスペースルートや他のワークツリーにある未コミットの変更は、他セッションのものとして扱う
- 他セッションの書きかけの変更は、コミットも、ブランチの移動も、`reset`もしない。ビルドが失敗していても直さず、
  何が失敗しているかを報告して判断を仰ぐ
- 変更の退避が必要なときは`ccnavi-git.sh stash push -u`を使う。退避で変更を消す前に、下書きの置き場（.ccnavi/docs/scratchpad.md）へ
  コピーも取っておく。コピーは他セッションのツリーの中には置かない

## ワークツリーを切る

### スクリプトで切る

- 直接作業のワークツリーは`sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-worktree.sh <名前>`で切る。取り込み先の確認・リモートとのずれの確認・書きかけの扱いをまとめて行う。
  取り込み先は、切った時点でメインのチェックアウト（`git worktree list`の先頭）が開いているブランチ。起点（S）は、取り込み先のHEADか、`--copy-wip`でコピーした書きかけを含むスナップショット。`origin`からは切らず、手元の取り込み先は進めない。ルートのindexとワークツリーには書かない。
  次のどれかにヒットすると、切らずに終了コード3で止まり、状態・勧め・リスク・選択肢・確認コードを出す。報告をユーザに伝え、了承を得てから`--base`・`--accept`などを付けて打ち直す。
  - cwdのブランチが取り込み先と違う（`--base <取り込み先>`が要る）
  - 取り込み先が統合先（`origin/HEAD`）でない
  - `origin/<取り込み先>`より遅れている・進んでいる・分岐している・`origin`に無い・リモート未確認（`fetch`が届かない場合を含む）
  - メインのチェックアウトに書きかけ（追跡済みの変更・新規ファイル）がある（`--copy-wip`か`--no-wip`が要る）
  後ろの3つは`--accept <確認コード>`も要る。確認コードは今の状態から決まるので、状態が動けば報告からやり直す。何もずれが無ければ確認なしで切る。
  `--side-by-side`を付けると、このワークツリーが残っている間は、メインのチェックアウトで見つかった変更を自動で戻さず報告にする（ccnaviの設定ファイルは戻す）。付けるとユーザの確認ダイアログが出る。
  取り込み先の断り: メインのチェックアウトがdetached HEAD、取り込み先がチケットに結び付く（実行ファイルの`tree base-bound`）、結び付くかを確かめられない、gitが2.40未満。
  行き先は`<ワークスペースルート>/.claude/worktrees/<名前>`で、cwdが`projects/<名前>`の中でも変わらない。ワークツリーが既にあればパスを出すだけ。`--dry-run`は予定だけ出す（fetchしない）。
  `origin`か手元に同じ識別子になるブランチ（同じ名前、`feature/7-x`に対する`feature-7-x`、英字の大文字小文字だけ違う名前）があるときは、切らずに終了コード1で止まり、`ccnavi-start.sh`を案内する（既にあるブランチは、MRを採用してよいか確かめてから出す）。名前の字と長さ（64文字まで）は実行ファイルが確かめる。
  記録（version 4）は共通のgitディレクトリの`ccnavi-direct/<名前>`、Sは`refs/ccnavi/direct/<名前>/s`に置く。
  `worktree add`が拒否されたときは、`ccnavi-git.sh`の出力の案内に従う。以下の手動の手順は、このスクリプトを使えないとき（既存のブランチを出すときなど）に使う
- `ccnavi-worktree.sh`は直接作業のワークツリー用で、名前と同じブランチを新しく切る。親子のチケットの親のワークツリーには使わない。
  親は識別子の名前のブランチを作らず、親のブランチ（MRの元ブランチ）を直接チェックアウトする。作るのは`ccnavi-start.sh --mr <番号>`か
  `--issue <番号>`。子のワークツリーは`ccnavi-ticket.sh start <子>`が親のブランチから作る

### 置き場と名前

- 置き場はワークスペースの`.claude/worktrees/<ブランチ名>`にする（チケットのワークツリーは`.claude/worktrees/<識別子>`）。プロジェクトから切る場合も同じ場所に置く。
  階層は1段だけにして、その下にさらに階層を作らない
- 行き先の名前とブランチ名は揃える（`-b <行き先の名前>`）。名前に`/`を含むブランチだけは、行き先をブランチ名の`/`を`-`に置き換えた名前にする
  （`feature/123-login`は`.claude/worktrees/feature-123-login`。識別子のブランチは作らず、ブランチを直接チェックアウトする）。`-B`・`--detach`・`--force`は拒否される。
  `-b`を付けずに2つ目の語を渡す場合、渡せるのは行き先と同じ名前の手元のブランチか`origin/<名前>`だけで、タグやshaは拒否される。

### 手で切るとき

- 直接作業のワークツリーは手で切らず、`ccnavi-worktree.sh`で切る。起点は取り込み先のHEADで、`origin/<統合先>`から切らない。以下はチケット作業の親と子、または`ccnavi-worktree.sh`を使えないときの手順
- `ccnavi-git.sh worktree add <行き先> -b <名前> --no-track origin/<統合先>`で作る。起点は`origin/<統合先>`にして、
  手元の`<統合先>`は進めない（追跡の設定も付けない）。末尾の起点を省くと今いるブランチが起点になるため、省かずに書く
- 切る前に`ccnavi-git.sh fetch origin <統合先>`し、`ccnavi-git.sh log --oneline <統合先>..origin/<統合先>`で遅れを確かめる。
  遅れていなければ、基点を`<統合先>`にして切ってもよい。遅れていれば、上のとおり`origin/<統合先>`から切る
  基点が`<統合先>`か`origin/<統合先>`のとき、`worktree add`は最後のfetchが10分より前、または手元の統合先がoriginより遅れていると拒否する。
  fetchを試して失敗した記録が10分以内にあるとき（オフライン）は、警告だけで通す
- `<行き先>`はcwdからの相対パスとして解釈される。ワークスペースルートからなら`.claude/worktrees/<名前>`、
  `projects/<名前>`の中からなら`../../.claude/worktrees/<名前>`と書く。間違えるとコマンドは拒否され、cwdに合わせた正しいパスが表示される
- `worktree add`に渡せるオプションは決まっている（`-b` `--reason` `--track`など）。
  一覧に無いオプションは拒否される。必要なオプションが出てきたら、ユーザに一覧へ足してもらう
- `branch` `checkout` `switch` `fetch` `pull` `merge` `commit` `rm` `restore`のオプションは、許可リストと照らし合わせて通すかどうかが決まる。
  長いオプションは略さずに書く。`--force-c`のような略は拒否される
- プロジェクトのワークツリーは`cd projects/<名前>`してから切る。`<統合先>`はそのプロジェクトのブランチで、
  ワークスペースの`main`ではない
- `<統合先>`がリモートにしか無いときは、先にプロジェクトの中で`ccnavi-git.sh fetch <リモート> <統合先>`を実行する

### 起点にする統合先

- この節は、親のワークツリーと、手で切るワークツリーの起点の話。直接作業のワークツリーの起点は取り込み先のHEAD（`--copy-wip`のときは書きかけのスナップショット）で、`origin`からは切らない
- 起点はリモートにある最新の統合先にする。統合先の名前は、そのリポジトリの手元の`origin/HEAD`が指すブランチで、無ければ`origin/main`、`origin/master`の順に使う。
  環境変数や`.claude/settings.local.json`で上書きする手段は無く、`projects/`の下のプロジェクトも、それぞれ自分の`origin/HEAD`で決まる。
  origin の無いリポジトリでは統合先が決まらない。`origin/HEAD`は、セッションの開始時に`ccnavi-fetch.sh`がホストの既定ブランチへ向け直す。
  決まらないと案内が出たら、ユーザに`git fetch origin`のあと`git remote set-head origin -a`を頼む。`ccnavi-git.sh push`は決まった統合先へも
  （`main`・`master`・`develop`・`release`・`release/*`と同じく）直接は送らず、`ccnavi-review.sh`は依頼のとき、既存のマージリクエストのマージ先がこの統合先と一致するかを確かめる（マージリクエストを作るのは`ccnavi-start.sh`）
- 手元の統合先が古いと、そこから切ったブランチも古いコミットから始まり、`<統合先>`に取り込むときにfast-forwardできなくなる。
  そのため、セッションの開始時に`ccnavi-fetch.sh`が手元の統合先をfast-forwardで進める。ワークスペースルートが別のブランチを
  チェックアウトしていても進める。統合先をチェックアウトしているツリーに未コミットの変更があるときと、
  リモートと分岐しているとき、または進める先に ignored のファイルと同じパスがあるときは進めない。結果はセッションの冒頭に、「[ccnavi]」で始まる見出しの行に続けて1件1行で出る。
  何も動かなかったときは何も出ない。進めたという知らせは「進めた」か「から作った」で終わる行だけで、
  それ以外の行が1行でもあれば、統合先が古いままのことがある。統合先の名前を含まない行でも同じである。
  同じリモートで先に取ってくるのに失敗すると統合先は取りに行かず、統合先をチェックアウトしているツリーの結果は
  そのツリーの名前で出るためである。
  そのときは、ワークツリーを切る前に`ccnavi-git.sh fetch origin <統合先>`と`ccnavi-git.sh log --oneline <統合先>..origin/<統合先>`で確かめる。
  fetchが通ってlogに何も出なければ、手元の統合先は最新である。fetchが失敗するならネットワークや認証といった原因を解消し、
  logにコミットが出るなら次の項目の手順で`origin/<統合先>`から切る。
  分岐しているならユーザに合流させてもらい、未コミットの変更があるならそのツリーの持ち主に聞く
- 手元の統合先を進めるのは、セッションの開始時の`ccnavi-fetch.sh`だけである。`ccnavi-git.sh fetch origin <統合先>`が更新するのは
  `origin/<統合先>`だけで、手元の`<統合先>`は古いままになる。`ccnavi-sync.sh`が更新するのは、親のブランチと、取得した`origin/<統合先>`・`origin/HEAD`だけで、手元の`<統合先>`は進めない。
  セッション中にリモートが進んだときは、`ccnavi-git.sh fetch origin <統合先>`のあとに
  `ccnavi-git.sh worktree add <行き先> -b <名前> --no-track origin/<統合先>`で`origin/<統合先>`から切る。
  `--no-track`を省くと、新しいブランチが`origin/<統合先>`を追跡する。すると次のセッションの開始時に、
  `ccnavi-fetch.sh`がそのブランチを`origin/<統合先>`に合わせようとする

## 親チケットのワークツリー

- 親チケットのワークツリーでは、別のブランチへ`checkout` / `switch`できない。ccnaviは親のワークツリーを
  「名前が親の識別子で、HEADのブランチ名の`/`を`-`に置き換えたものがその名前になるもの」
  として探すためである。
  別のブランチに移ると、リモートでの承認を取り込む処理がそのワークツリーを飛ばす。この処理には、`ccnavi-sync.sh`と、
  セッション開始時に`ccnavi-fetch.sh`がfast-forwardで進める処理がある。親のワークツリーが決まらないので、
  親と子のチケットの承認・状態の操作（`start`・`finish`・取り消し・記録・レビューのマーカー）・実行前の判定も止まる
- 子の成果は、メインが打つ子の`finish`が親のブランチへ合流してpushする（手順は[worktree-merge.md](worktree-merge.md)）。
  サブエージェントは子のワークツリーで実装して手元でコミットするだけで、親のワークツリーにはmerge・commit・書き込みをしない
  （hookが止める）。
- 親のワークツリーへのWrite / Edit / NotebookEditは、メインセッションも置き場（`wip/proposals/`・`wip/handoff/`・`wip/eli5/`・承認済みの置き場）の外では止まる（`DENY_TICKET_PARENT`）。
  親の範囲の中でも同じで、範囲を広げても通らない。親自身の作業（`plan: [quick-work]` など）も、子チケットを起こして子のワークツリーで行う。
  親かどうかは、承認済みの索引とそのワークツリー自身のチケット（`parent:` が無い）のどちらかが言えば親とする。子のワークツリーでのコミットと、衝突を解くために子のワークツリーで親のブランチをmergeすることはできる

## 直接作業のワークツリーの名前

- 新しく切る直接作業のワークツリーとブランチも、`<先頭の語>-<番号>-<slug>` の形にそろえる。親チケットと同じ形なので、後で取り込みを追うときや、チケットに移すときに名前を付け直さずに済む
  - 先頭の語は `CCNAVI_BRANCH_PREFIXES` の既定（`feature` `hotfix` `fix` `bugfix` `chore` `refactor` `docs`）から選ぶ
  - 番号は issue があればその番号、無ければ `sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-ticket.sh next-id` の通し番号（通し番号は直接作業の名前だけに使う。親チケットは必ず issue と MR のセットで、番号は issue の番号）
  - 例: `feature-341-direct-branch-name`（issue #341 の作業）、`chore-12-cleanup`（通し番号 12）
- 形に合わない名前は、切ったあとに `ccnavi-worktree.sh` が `--lint` と同じ文面の warn を 1 行出す（判定は `ccnavi worktree name <名前>` が持つ）。`--lint` も同じ warn を名指しする
- 既にある直接作業のワークツリーとブランチの名前は変えない。この形は新しく切るものから適用する

## 直接作業からチケット作業に移るとき

直接作業のワークツリーで調べて提案を書き始め、そのままチケット作業になることがある。チケット作業は必ず issue と MR のセットなので、issue が無ければ `ccnavi-start.sh --new-issue <題>` で作り（作れなければユーザに作ってもらい）、`ccnavi-start.sh --issue <番号>` で親のワークツリーと MR を作って、書いた提案をそこへ移す。親のワークツリーは識別子と同名でなければならないので、提案を書いたツリーが識別子と違う名前なら、承認の前に移す。

- 識別子の番号は issue の番号にする（`ccnavi-start.sh --issue <番号>` が決める。通し番号の `next-id` は直接作業のワークツリー名だけに使い、親チケットには使わない）。同じリポジトリの別の親と番号が重なると`--lint`が警告する
- 提案を書いたツリーが識別子と違う名前なら、承認の前に`ccnavi-start.sh --issue <番号>`で識別子と同名のワークツリーと MR を作る。提案をそこへ移し（`wip/proposals/todo/`の同じ相対位置）、元のツリーの提案は消す。提案の`issue:`と`mr:`は、`ccnavi-start.sh`の「必須」の行の値にする
- 承認の後に切り直さない。ccnaviは親のワークツリーを「名前が識別子のもの」として探し、そこにあるチケットだけを正とするので、別名のツリーで承認すると親が決まらず、承認済みチケットの自動コミットも動かず、`--lint`が「親 X が承認されていない」を出し続ける
- 先に書いた提案は、識別子と同名のワークツリーに移してから承認の依頼に進む。ユーザの承認が別名のツリーの提案に対するものだったら、移した後の中身が同じことを見せて、承認を取り直す
- `--lint`は、識別子と違う名前のツリーにある親の提案と、親と同名でないツリーにある子の提案を警告する（ワークスペースルートの提案は言わない）
- 承認の画面（`ccnavi-user-agree.sh`）は、識別子と違う名前のツリーにある親の提案と、親と同名でないツリーにある子の提案を承認の対象にしない（error を出す。ワークスペースルートとプロジェクトの元ツリーの提案は名指ししない）
- 別名のツリーで承認されたチケットは、`ticket start`と`ticket finish`が止める。直すには、親のワークツリーを切り、提案を移して承認を取り直す。`ccnavi-user-push-approved.sh`と`ccnavi-sync.sh`は各ツリーの置き場を送る・取り込むだけで、ツリーの間でチケットを動かさない

## 親チケットの正本（親のワークツリーだけを読む）

- 親チケットの正本は親のブランチで、各PCでは`.claude/worktrees/<親の識別子>`にチェックアウトしたもの。承認済みチケット・マーカーは、その中のものだけを読む。ワークスペースルート・プロジェクトの元ツリー・子のワークツリーに残ったコピーで代用しない（`--lint`の診断にだけ使う）
- 親のワークツリーが無い、または`HEAD`のブランチ名の`/`を`-`に置き換えたものがフォルダ名と合わないPCでは、その親子の承認・状態の操作が止まる。ボードにはその親子のチケットが出ない。`ccnavi-start.sh --mr <番号>`でそのブランチを`.claude/worktrees/<識別子>`にチェックアウトしてから続ける
- 親子ごとの取り込み状態は手元に持たない。判定は、親のワークツリーと、親のブランチ上のチケット・マーカーだけで決まるので、別のPCでも同じ結果になる。`ticket start`・`finish`は取り込み・コミット・pushまで行う
- 親のブランチがリモートから消えたときは、親のブランチへのpush（`ccnavi-git.sh push`・write-and-push・`ccnavi-user-push-approved.sh`）が共通の関門で止まる。ブランチを改名したか消し間違えたのなら、ユーザが元の名前で戻す（ターミナルで`git push origin <ブランチ>`を一度）。破棄した親子のチケットなら、親のワークツリーを片付ければ関門の対象から外れる。診断は`ccnavi-sync.sh <親の識別子>`が出す
- 親チケットの作成と承認には、親のワークツリーがあること、`HEAD`の確認に通ること、`issue:`と`mr:`（`ccnavi-start.sh`が「必須」の行で出す値）が書いてあることが要る。`ccnavi ticket new --issue <値> --mr <番号>`が書く。`ticket new`の雛形に残る空欄の目印（`（ここに〜を書く）`）を書き換えていない新規の提案も、承認と`--lint`が止める
- 提案は書いただけでは手元にしかない。承認を頼む前に`sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-ticket.sh propose <識別子>`で、親のワークツリーの`wip/proposals/todo/`（親子の提案）と`wip/proposals/flows/`（子のフローの下書き）を親のブランチへコミットして送る。別のPCでは、セッション開始時の取り込みが親のワークツリーを進めるので、承認の画面にその提案が出る。送るのは親のワークツリーの中の、その親子の提案だけ（サブエージェントは打てない）
- ユーザに承認を頼んだあとは、承認待ちの提案ファイルを書き換えない。承認は、ユーザが見た提案（識別子の一覧と各提案ファイルのバイト列）が承認の直前も同じときだけ通る。違えば何も承認せず、「内容が更新されました」と最新を表示し直して、もう一度押してもらう（ターミナル・ボード・Chromeで同じ）
- `ticket start`で子のワークツリーが無ければ、取り込み直後の親ブランチの先頭から`.claude/worktrees/<子の識別子>`を作る（別のPCで承認された子でも、どのPCでも同じ）。同名のブランチが手元に残っていて、親の先頭に無いコミットがあれば作らずに止まる
- レビューの依頼（`ccnavi-review.sh request`）は、親ブランチのopenのMRが無ければMRを作らずに止まる。MRの元ブランチが`HEAD`のブランチと同じで、マージ先が統合先であることも確かめる
- 親を閉じたかはMRがマージ済みかで決める（手元の退避`logs/archive/`は判定に使わず、バックアップとして残す）。`ccnavi-sync.sh`がホストに聞き、聞けなければ推定せず止まる。マージ済みと分かったら、親の手元のブランチ・ワークツリー・片付けの記録（`ready`が書く`retire/<親>.json`）を片付ける（片付けの条件は.ccnavi/docs/worktree-cleanup.md）
- 同じ識別子のチケットが親のワークツリーの中で複数の置き場（`doing/`と`done/`など）にあれば、どれが正か決まらないので、状態の操作は止まる
