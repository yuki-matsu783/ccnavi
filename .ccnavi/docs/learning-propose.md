# 学びの提案を出す

SessionStart でユーザに「提案の候補がある」と知らされ、ユーザが提案を頼んだときの手順。専用のスキルやコマンドは無い。
気づきを溜めるのは親を閉じる前の統合の子（`ccnavi-ticket.sh consolidate <親>`）で、ここではパターンを手順（スキル・ルールなど）にする提案を扱う。

## 読む順

1. `ccnavi --learnings` の一覧。「候補」のパターン、`target` ごとの内訳、観測元の数、`承認待ち` の提案を見る
2. 関係する採否の記録（`docs/wiki/impact/`）。却下されたものを、理由を覆す根拠なしに出し直さない
3. 動機のパターン（`docs/wiki/patterns/`）。観測元の数が多いものを優先する
4. 反映先の現物

## 提案の作り方

- 提案は反映先 1 つに絞る。複数に及ぶときは分ける
- 差分と、`docs/wiki/impact/<提案>.md`（`status: 承認待ち`）を同じチケットに入れる
- 反映先のパスで、直し方を分ける
  - 保護対象でないもの（`.claude/skills/*` の多く、`docs/*`）: 提案チケットの中で直接直す
  - 保護対象のもの（ルール・配点・フェーズ定義・テンプレート・`.ccnavi/docs/*` など）: 下書きを置き、ユーザの取り込み（`ccnavi user handoff`）で直す

`impact/<提案>.md` の frontmatter:

| 欄 | 中身 |
|---|---|
| `proposal` | 提案の名前（ファイル名と同じ） |
| `target` | `rule` `risk` `phase` `template` `skill` `docs` のどれか 1 つ |
| `files` | 反映先のパス |
| `patterns` | 動機のパターン名 → 観測元の数 |
| `status` | `承認待ち` `承認` `却下` `延期` |
| `reason` | 却下・延期の理由 |
| `decided_at` | タイムゾーン付きの日時。`承認待ち` では空 |

本文に差分を書く。

## 決着

採否はマージで決まる。MR の中で `status`・`decided_at`・`patterns` を書き換えてからマージする。
`patterns` の各値は、その時点でマージ先のパターンから数えた観測元の数に書き直す（提案を作ったときの値のままにしない。直さないと、延期した提案がマージ直後に候補へ戻る）。

| 決着 | すること |
|---|---|
| 承認 | 反映先の実際の差分を確かめる（保護対象は取り込みを済ませる。下書きが無いことは、取り込んだ証拠にならない）。`status: 承認`、`decided_at`、`patterns` の今の数を書いてマージ |
| 却下 | 差分を戻し、`status: 却下`、`reason`、`decided_at`、`patterns` の今の数を書いてマージ |
| 延期（取り下げを含む） | 差分を戻し、`status: 延期`、`decided_at`、`patterns` の今の数を書いてマージ。その後に観測元が増えたパターンだけが候補に戻る |

MR を閉じただけでは、採否の記録は統合先に入らない。パターンは候補のままで、次に通知の変化が起きたときに一覧へ含まれる。

## パターンの状態

1. そのパターンを `patterns` に含む採否の記録に `承認待ち` が 1 つでもあれば「提案中」
2. それ以外は、`decided_at` が最も新しい採否の記録で決める（同じ日時なら `proposal` の名前順で後のもの）。`承認`・`却下` なら「決着」。`延期` は、今の観測元の数がその記録の `patterns` の数より多ければ「候補」、多くなければ「決着」
3. 採否の記録が 1 つも無ければ「候補」
