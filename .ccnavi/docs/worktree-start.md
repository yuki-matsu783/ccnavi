# issue・MRを指定して着手する

ワークツリーの一般的な切り方は[worktree.md](worktree.md)。

## issue・MRの指定を受けたとき

- チケット作業は必ずissueとMRのセットで進める。issueが無ければユーザに作ってもらう（エージェントが作るのは頼まれたときだけ）。
  最初に`sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-start.sh --check`を打ち、ホストのAPIとgitのリモートが使える状態かを確かめる（下の「事前確認」）。
- issueやMRを指定して作業を頼まれたら（`#152`・`!5`・URLなど）、ワークツリーを切る前に
  `sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-start.sh --issue <番号>`（MRなら`--mr <番号>`。`--issue`と`--mr`は一緒に渡せる）を打つ。
  紐づくブランチを`ccnavi-branches.sh`で探し、結果に応じて進める。プロジェクトのissue・MRは`projects/<名前>`に`cd`してから打つ。依頼にURLがあるときは`--repo <owner/repo>`を付ける。実行した場所のoriginと違えば、ホストに問い合わせる前に止まり、移動先を案内する。
  `--slug <語>`・`--prefix <語>`・`--title <題>`で名前と題を指定でき、`--dry-run`なら何も作らず予定だけ出す（リモートは読むだけ）

  | 結果 | 終了コード | エージェントの動き |
  |---|---|---|
  | 候補が1件で、開いたMRがある | 0 | 出力の「次:」の行に従う（下の「issue・MRを指定された作業は」）。既存のMRを採用してよいか確かめ（下の「既存のMRを採用するときの確認」）、毎回originから取って早送りし、`ccnavi-sync.sh <識別子>`を打つ。ワークツリーのパスが出る（無ければ`.claude/worktrees/<識別子>`に、ブランチを直接チェックアウトして作る）。続きの作業はそこで行う |
  | 候補が0件（`--issue`） | 0 | 統合先から`<先頭の語>-<番号>-<slug>`を切る。slugはChrome拡張の「始める」と同じ作り方で題から作る。作る前に、下の採用の確認のうち識別子・同じ識別子の別ブランチ・同名のマージ済みMRを確かめ、引っかかれば何も作らずに止まる。確かめたら、ワークツリー・空の初期コミット・push・Draft MR（本文に`Closes #<番号>`）まで作り、`ccnavi-sync.sh <識別子>`を打つ。パス・ブランチ名・識別子・MRのURLを1項目1行で出し、出力の「次:」の行に従う |
  | 候補が複数、MRの無い候補（作りかけの再開を除く）、統合先より進んでおらずMRも無い古いブランチ、MRが閉じるissueが複数 | 3 | 何も作られていない。出た一覧をユーザに見せ、MRの無い候補なら「ユーザにMR（説明欄に`Closes #<番号>`）を作ってもらって`--mr`で打ち直す・新しく切る・やめる」を、複数の候補なら既存のブランチで続けるか（下の「既にある`/`を含むブランチで親チケットの作業をするとき」）・新しく切るか・やめるかを、閉じるissueが複数なら`--issue <値>`を付けて打ち直すのを聞いて、返事を待つ |
  | ホストを見られない | 4 | 既存のMRも閉じるissueも確かめられないので、新規作成にも、手元の候補で続けることにも進まず止まる。下の「ホストに届かないとき」に従う |
  | MRを採用できない、前提の未充足 | 1 | 理由が出る（MRの無い候補にも、同じ識別子になる別のブランチの確認は掛かる。MRがopenでない・フォーク・マージ先が統合先でない・保護されたブランチ・識別子が使えない・同じ識別子になる別のブランチがある・同じブランチ名のマージ済みMRがある、など）。ユーザに伝えて判断を仰ぐ |
  | 依頼のリポジトリ（`--repo`）が、実行した場所のoriginと違う | 1 | ホストには問い合わせずに止まる。出た移動先（`projects/<名前>/`）に`cd`して同じコマンドを打ち直す。`projects/`に無いときはcloneが要るとユーザに伝えて止まる |
  | 引数の誤り（`--slug`が要る、`--branch`を`--mcp-checked`なしで渡した、など）、issueが無い・権限が無い・PRの番号だった | 2 | 理由が出る。引数の誤りは文面に従って打ち直し、issueの問題は番号を確かめてユーザに伝える |

  出力の先頭は`対象リポジトリ: <owner/repo>（<プロジェクト名>）`。意図したリポジトリかをここで確かめる。`--title`を付けても、ホストが読めるかぎりissueの存在は確かめる（存在しない番号では何も作らず、issueをユーザに作ってもらって番号を打ち直す。APIが一時的に失敗して読めなかったときは、`--slug`があれば仮の題で進む。MCPで代行するときは、案内の手順でissueの実在も確かめる）。

  成功の条件: 開始の操作（`--check`・`--help`・`--dry-run`を除く）が終了コード0で終わったら、採用したMRと、そのMRが閉じるissue（リポジトリと番号）と、元ブランチが確定している。`--dry-run`は予定を示すだけで、開始の完了ではない。出力には「必須」の行（`issue: <値>`と`mr: <番号>`を提案のfrontmatterに書く）が必ず出る。issueの値は、MRと同じリポジトリなら`<番号>`、違えば`<owner/repo>#<番号>`で、大文字小文字は区別しない。
  - `--issue M`で新しくMRを作るときは、本文に`Closes #M`を入れるので、組は作った時点で確定する
  - 既存のMRを採用するとき（`--issue M`でも`--mr N`でも）は、MRの採用の確認のあとで、そのMRが**閉じる**issueを読む（GitHubはGraphQLの`closingIssuesReferences`、GitLabは`closes_issues`）。`--issue`があれば、それが含まれること（参照しているだけでは足りない。説明欄に`Closes #M`を書くようユーザに頼む）。無ければ、ちょうど1件に決まること（0件は終了コード1、2件以上は一覧を出して3）。読めなければ（GraphQLの`errors`・`pullRequest: null`・件数の上限を含む）終了コード4で、MCPなどで確かめて打ち直す
  - 作りかけ（初期コミットだけで、MRが無い）の再開は、MRを作って続ける。それ以外の、MRの無い候補は成功させない

  事前確認（`ccnavi-start.sh --check`。単独で使う）: 先頭の行は`対象リポジトリ: …`、続けて1項目1行で`確認: <項目>: OK|NG|未確認|省略|注意 (<理由>)`、最後に結論の1行と、必要なら`次:`を1本出す。項目はtools（git・jq）・origin（ホストのURLで読める）・integration（統合先が決まる）・api（認証とリポジトリの有無）・access（書き込みの権限）・git（`ls-remote`が通る）。
  結果は4種類で、`ng`（確定した不備。直すにはユーザの対応が要る）・`unverified`（通信できない・時間切れ・応答が読めない）・`skipped`（前提の項目がokでないので確かめなかった）・`ok`。全体は、ngが1つでもあればng、無くてunverifiedかskippedがあればunverified、それ以外はok。
  終了コード: 0 使える / 1 不備がある（ng） / 2 引数の誤り / 4 確かめられなかった項目がある。
  「権限が足りる」は、リポジトリのロール上は書き込める、の意味に限る（トークンのscope・ブランチの保護・APIとgitが別の資格情報で動いていることは確かめていない）。`--issue`・`--mr`も、何かを作る前に同じ確認の一部（認証・リポジトリの有無・権限）を行い、足りなければ終了コード1で止まる。1回の問い合わせは15秒、全体は60秒まで。キャッシュはしない

  途中で失敗して打ち直しても、完了済みの処理（ブランチ・ワークツリー・push・MR）をスキップし、未完了の処理から再開する。
  依頼文にissue・MRの指定があると、ccnaviがUserPromptSubmitで同じ指示を足す
- 識別子はブランチ名の`/`を`-`に置き換えたもの（`feature/123-login`は`feature-123-login`）。ワークツリーは`.claude/worktrees/<識別子>`に、
  `worktree add .claude/worktrees/<識別子> <ブランチ>`でそのブランチを直接チェックアウトする。識別子の名前のブランチは作らない。
  変換は`ccnavi_branch_to_id`（sh）・`ticket_ids.branch_to_id`（Python）・拡張の`branchToId`（TS）に同じものがあり、
  `tests/fixtures/branch-to-id.json`の同じ表で一致を確かめている
- 既存のMRを採用するときの確認（引っかかったら何も作らずに止まる）
  - MRがopenである。閉じた・マージ済みのMRのブランチでは続けない
  - フォークのMRでない（元ブランチがこのリポジトリに無い）
  - マージ先が統合先である
  - ブランチ名が保護されたブランチ（統合先・`main`・`master`・`develop`・`release`など）でない
  - 変換した識別子がIDとして使える。58文字以内（子の識別子は親の識別子に6文字足すので、64文字に収める）で、末尾が`-<2桁>`でない（子の識別子の途中と紛れる）
  - 同じ識別子になる別のブランチが無い。`ls-remote`でoriginの全ブランチを見て、手元のブランチも合わせて比べる（MRの有無によらない。英字の大文字小文字は区別しない。どの機械でも同じ識別子として扱い、両立させない）
  - 識別子が使えるかは実行ファイルに聞く。答えが無ければ「確かめられない」と止まる（実行ファイルをビルドするか配置してから打ち直す）
  - 同じブランチ名のマージ済みMRが無い。ホストに聞く（手元の退避には頼らない）。ホストに届かないか、断られたときは終了コード4で止まり、
    MCPで確かめたあとに`--mcp-checked`を付けて打ち直す
- 続けるブランチは、手元にあっても毎回`origin`から取って早送りする（分かれていれば動かさず言う。取り込みは`ccnavi-sync.sh`）。
  取れなかったときは手元のまま続け、「リモート未確認」と言う。最後に`ccnavi-sync.sh <識別子>`を打つ（親チケットも提案もまだ無いと取り込まれない。止めずに言う）
- MRの番号とissueは手元に保存しない。出力の「必須」の行にある`issue: <値>`と`mr: <番号>`を、親の提案のfrontmatterに必ず書く（`ccnavi ticket new ... --issue <値> --mr <番号>`が書く。どちらかが無いと`ticket new`・承認・`--lint`が止める）。雛形の空欄の目印（`（ここに〜を書く）`）が残っていると止まるので、書き換える。
  `ccnavi-sync.sh`などが閉じたかを聞くときは、この`mr:`の番号を使う
- issue・MRを指定された作業は、直接作業にせずチケット作業で進める（ユーザがホストで作ったものを途中から頼まれた場合も同じ）。
  親チケットも提案も無いワークツリーでは、出力に「次:」の行が出る。識別子・題・`--issue`・`--mr`を埋めた`ccnavi ticket new`なので、
  `--scope`の`<触るファイルの glob>`だけを実際のパスに直して、ワークツリーの中で打つ。設計判断が要らない作業は、範囲が複数のディレクトリや文書・設定にまたがっても`--plan quick-work`で足りる。
  大きい作業は`--plan`を`design,implement`のように変える（型と範囲は`.ccnavi/config/common/phases.yml`）。
  提案は手で書かない。承認が通らないなど詰まったら、直接実装に切り替えず、ユーザに報告して止まる。
  チケットが既にあるワークツリーでは、「次:」の行が`ccnavi-ticket.sh status <識別子>`を勧める。行頭の語は[terms.md](terms.md)
- ホストに届かないか、断られたとき（Claude remoteのコンテナでは、GitHubのAPIに届かないことがある）、`ccnavi-start.sh`は終了コード4で止まり、
  どの段で届かなかったか・その段までに出来たこと・MCPで行う手順を標準出力に出す。エージェントはその手順どおりに`mcp__github__`のツールで代行し、
  同じコマンドを打ち直す。段は3つある
  - 既存のMRを確かめる段: `mcp__github__search_pull_requests`で探す。見つかれば候補としてユーザに聞く。無いと確かめたら`--mcp-checked`を付けて打ち直す
  - issueの題を読む段（slugが決められないとき）: `mcp__github__issue_read`で題を読み、`--slug <語> --title '<題>'`を付けて打ち直す
  - MRを作る段（ブランチ・ワークツリー・pushは済んでいる）: `mcp__github__create_pull_request`を、案内の値（`head`はブランチ名、`base`は統合先、
    `title`、`body`は`Closes #<番号>`、`draft: true`）で呼ぶ。作れたら、案内のコマンド`--issue M --mr <作ったMRの番号> --branch <ブランチ> --mcp-checked`（`<作った番号>`を実際の番号に直す）を打ち直すと、ホストを見ずに続きからワークツリーのパスが出る
  - 閉じるissueを確かめる段（`issue-link`）: `mcp__github__pull_request_read`で元ブランチと本文の`Closes`を読み、`mcp__github__issue_read`でissueの実在を確かめて、`--mr N --issue <値> --branch <元ブランチ> --mcp-checked`で打ち直す

  `--branch <元ブランチ>`は`--mcp-checked`と一緒のときだけ使える（それ以外は終了コード2）。ホストに届かないとき、候補の探索の代わりにこのブランチを使う。`--issue`・`--mr`・`--branch`の3つがそろえばホストを見ずに成功してよく、出力に「ホストは見ていない（MCPなどで確認済みとして扱った）」と出る。3つがそろわないときは終了コード4。ブランチは、ブランチ名として使える・手元かoriginにある・識別子が使える・同じ識別子の別ブランチが無い・保護されたブランチでない、を確かめる。ホストに届くときは`--mcp-checked`を使わず普通に確かめ、MRの元ブランチが`--branch`と違えば終了コード1。`--mcp-checked`は「ホストに届かず、エージェントが別の手段で確かめた」ことを示すだけで、ホストにしか無い情報は補わない
  GitLabにはMCPの案内が無い。理由と手で行う手順が出る。理由にホストの返事（`HTTP <番号>: <本文>`）があるときは、その番号と本文から原因を絞る（401・403は認証、404は番号かアクセス権で、非公開は404で返ることがある。それ以外は要求の中身かccnaviの不具合を疑う）。
  ホストに届かず返事が無いときは、glabの認証か`GITLAB_TOKEN`をユーザに頼んで打ち直す。
  gitのpushが通らないときは、従来どおり`ccnavi-git.sh`の拒否の出力に従う

## 既にある`/`を含むブランチで親チケットの作業をするとき

- 既にある`feature/123-login`のような`/`を含むブランチで親チケットの作業をするときも、`ccnavi-start.sh`が
  `.claude/worktrees/feature-123-login`に`feature/123-login`を直接チェックアウトして作る
  （手で切るときは`worktree add .claude/worktrees/feature-123-login feature/123-login`）。親の識別子はブランチ名の
  `/`を`-`に置き換えたもの（`feature-123-login`）で、提案の`ticket:`にそれを書き、`issue: <値>`と`mr: <番号>`も書く。
  提案にブランチ名を書く欄は無い（`branch:`の欄があればエラー）。ccnaviは親のブランチ名を、
  親のワークツリーのHEADから読む。HEADのブランチ名を変換した識別子がフォルダ名と合わないと、取り込み・早送りの対象にならない。
  子のブランチは子の識別子で、起点は親のブランチ
  （`-b <子> feature/123-login`）。`ccnavi-sync.sh`の引数は識別子
  - 子のワークツリーは、VS Code拡張で承認したときに親のブランチから自動で切る（親のワークツリーが在り、子のものがまだ無いとき）。
    拡張は承認のJSONの`worktrees`の`create`だけを`ccnavi-git.sh worktree add <行き先> -b <子> <base>`で作る。作れなかった子は、
    警告の通知に、ワークツリー名と手で打つコマンド（同名のブランチが既にあるときの形も）を出す。承認の文面（Claude Codeに渡す文）には
    作成の失敗は入らない。親のワークツリーが無い子とプロジェクトの子は自動で切らない。
    ターミナルの承認（`user agree`）では自動で切らない
