# `{!root}` の書き方をスキルの説明に足す

## なぜ別チケットなのか

i0061 のフェーズ 4（docs）で一緒にやるつもりだったが、**できなかった**。

`docs` フェーズの `scope` には `.claude/skills/*` を足してある。しかし子が宣言できる
範囲は「フェーズの種類 ∩ **親の範囲**」で、親 i0061 の `allow` に `.claude/skills/*` が無い。

親の範囲を広げようとして改版（同じ識別子の提案を `todo/` に書く）を試したが、
**改版として拾われる条件は `plan` か `feedback` が変わることだけ**だった
（`approval._plan_differs`）。範囲だけを変える改版は承認の一覧に現れない。

承認済みの親の範囲は、いまの仕組みでは広げられない。だから別のチケットにする。

## 書くもの

`.claude/skills/ccnavi-config/references/add.md` の「当て方」の節に `{!root}` を足す。

| 書くこと | |
|---|---|
| 何か | 「ワークスペースルートの外」。先読みが使えないので実行ファイルが入れ子の式に展開する |
| 書ける場所 | `regex` だけ。`glob` に書くと error |
| 置ける位置 | `^` の直後に 1 回だけ |
| 直後の量化子 | error。`^{!root}?` は展開結果ごと省略でき、どの対象にも当たる式になる |
| 後ろに続く式 | 書ける。`.*` のように任意の位置まで進む形で受けていなければ warn |
| 対象がルートそのもの | 「中」。`Glob` を `path` 省略で呼ぶと対象が cwd（＝ルート）になる |
| ルートが 256 字以上 | 組み立てられず、そのルールが見るツールが全部止まる。回復は利用者が `rules.yml` から外すことだけ |

**素朴に `deny: ^{!root}` と置く危険も書く。** セッションのスクラッチパッド、
他リポジトリの参照、他ツールの出力先が一度に塞がる。`match` を絞って `Read` を残す、
例外が要るなら名指しのルールにする、を先に考えさせる。

詳細は ADR-0058 と `ccnavi.md` §5.3 にあるので、スキルは「書くときに踏む穴」に絞る。

## 先に済んでいる必要があること

**i0061（MR #69）がマージされてから入れる。** `{!root}` が main に無い状態でスキルだけ
先に更新すると、説明どおりに書いたルールが error になる。

このワークツリーは main から切ってあるので、着手の前に i0061 の合流を確かめること。

## 得るもの

- 実行ファイルの語彙とスキルの説明が揃う。次のセッションが古い書き方を試して止まらない
- 「素朴に置くと何が塞がるか」が、ルールを書く手前で読める

## 失うもの

- **範囲に `.claude/skills/*` が入る。** ここはエージェント向けの指示の置き場で、
  書けるということは**次のセッションが読む指示を書き換えられる**ということ。
  hook 本体（`.claude/hooks/`）と `settings.json` は deny が先に当たるので含まれないが、
  スキルの本文は判定を通る
- 同じ内容が ADR-0058・`ccnavi.md` §5.3・スキルの 3 か所に散る。スキルは「踏む穴」に
  絞って重複を減らすが、ゼロにはならない

## やらない場合

スキルが古い説明を配り続ける。`{!root}` を知らないまま `(?!...)` を書こうとして
error になるか、`{!root}` を見つけても `^{!root}[\\/]foo` のような書き方をして
意図どおりに動かない。どちらも i0061 で塞いだはずの穴に落ちる。

## 代案

**`ccnavi.md` §5.3 を読ませる 1 行だけをスキルに足す。** 重複は減るが、
スキルは「書いた人が踏みやすい穴」を書く場所で、設計書への参照だけでは役目を果たさない。
`{!root}` は `{root}` と性質が違う（`glob` に書けない、前に置けない、直後に量化子を
置けない）ので、その差分こそスキルに書く価値がある。
