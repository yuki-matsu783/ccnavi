# 置き場の env を読まない sh の写す版を wip/design/scripts/ に置く

親 i0064 のフェーズ 4（staging）。設計書 `wip/design/i0064-fixed-places.md` §3 に従う。
`ccnavi/`・`scripts/`・`vscode-extension/`・文書（フェーズ 5）には触らない。

## 前提: 親のブランチに `main` を取り込んでから切る

設計書 §3 は「写す版は `main` の `.ccnavi/scripts/` の現行から作り直す」と決めている。
今の親のブランチ（i0064）は `main` より 68 コミット遅れていて、`.ccnavi/scripts/` の 8 本が
`main` と違う（`main` 側に `ccnavi_compat_skew`・`tell_skew`・`skip_temp` などが入っている）。

写す版は親のブランチの `.ccnavi/scripts/` に写されて、そのまま統合先へ入る。`main` の現行を
土台にした写す版を、`main` を取り込んでいないブランチへ写すと、ブランチの実行ファイルが
知らない `--version` を sh が呼ぶことになり、ブランチの中のテストと sh がずれる。

そこで、**この子を切る前に、親が自分のワークツリーで `ccnavi-git.sh merge main` を済ませる。**
そうすると「`main` の現行」と「親のブランチの現行」が同じになり、写す版の土台が 1 つに決まる。
取り込みで衝突したら親が解く（`docs/claude/worktree.md`「`<統合先>` へ戻す」）。子は取り込まない。

子は着手の最初に、土台が揃っていることを確かめる:
`ccnavi-git.sh diff --stat main -- .ccnavi/scripts/` が空。空でなければ手を止めて報告する。

### 言い方を揃えるもの

フェーズ 3 で実行ファイルと導入スクリプトに入った言い方に、sh の説明を揃える。

- 直に書いた綴りの横の説明は「固定（ADR-0084）」で揃える（`settings.py`・`ticket.py`・`wrapguard.py`・
  `ccnavi-setup.sh` と同じ言い方）。env で動いた頃の話は書かない
- `ccnavi-git.sh` の「既定は settings.py の DEFAULT_APPROVED と揃える」は、揃える相手を
  `DEFAULT_PROJECTS`・`DEFAULT_TICKETS`・`DEFAULT_APPROVED` の 3 つに広げて残す。
  hook の同じ検査（`wrapguard.py` の子の push。`settings.approved_dir`・`conf.tickets`・`conf.projects`）と
  同じ場所を見ていることを 1 行で書く（ADR-0077 の 2 重目）
- `ccnavi-review.sh` の控えの置き場 `logs/state` は、導入スクリプトが env を外したときの文面
  （「置き場は既定の logs/state に固定されています」）と同じ綴り。変えない
- 導入スクリプトの `DEPLOY_SCRIPTS` は、写す版に新しいファイルが無いので直さない

### 写す手順（`wip/design/scripts/README.md`）

以前の写す版（`approve-carry`）の README と同じ形で書く。中身は次のとおり。

- **写すのは人。** エージェントは `.ccnavi/scripts/` に書けず、`cp` や生の `git` を打たない
- 写す先は**親のワークツリー**（`.claude/worktrees/i0064/.ccnavi/scripts/`）。ワークスペースルートの
  `.ccnavi/scripts/`（`main`）には写さない。統合先へは親のブランチごと入る
- 写す前に、土台が動いていないことを確かめる。README に 6 本それぞれの土台の
  `git hash-object`（写す版を作ったときの `.ccnavi/scripts/<名前>`）を表で載せ、人は
  `git hash-object .ccnavi/scripts/<名前>` が一致することを見る。違えば写さず、写す版を作り直してもらう
  （写すと、その間に入った変更を黙って消す）
- **6 本を 1 つのコミットで写す。** どれか 1 本だけ写すと、sh の間で置き場の決まり方が食い違う
  （例: `ccnavi-git.sh` だけ写すと、子の push の検査は既定だけを見るのに、`ccnavi-push-approved.sh` は env を読む）
- 打つもの（親のワークツリーで）:

  ```sh
  cp wip/design/scripts/ccnavi-common.sh wip/design/scripts/ccnavi-fetch.sh \
     wip/design/scripts/ccnavi-git.sh wip/design/scripts/ccnavi-push-approved.sh \
     wip/design/scripts/ccnavi-review.sh wip/design/scripts/ccnavi-approve.sh .ccnavi/scripts/
  git add .ccnavi/scripts/
  git diff --cached --summary   # mode change が出ないこと（cp は写す先のモードを残す）
  git commit -m "feat: 置き場の env を読まない sh を写す（i0064-04）"
  ```

  6 本とも既にあるファイルなので、実行ビットの付け直しは要らない（`ccnavi-approve.sh`・`ccnavi-fetch.sh`・
  `ccnavi-push-approved.sh` は 100755 のまま残る）
- 写したあとに回すもの（下の「終わりの条件」の後半）
- 元に戻す: コミット前は `git restore --staged --worktree .ccnavi/scripts/`、コミット後は `git revert`。
  戻すときも 6 本を一緒に戻す

## 失うもの

- **人が 6 本を写す手間が要る。** 写し忘れると A9 が落ちたまま統合の直前まで残る。写すまでは、
  sh だけが env を読み、実行ファイルとずれる（親のブランチの中だけの話）
- **前提として、親が `main` を取り込む必要がある。** 68 コミット分で、フェーズ 3 の差分
  （`settings.py`・`lint.py`・`ccnavi-setup.sh`・拡張）と衝突しうる。解くのは親で、この子の前に時間を取る
- **写す版と写す先の間に変更が入ると、写すことでその変更を消す。** 土台の `hash-object` を README に載せて
  写す前に照らすが、照らし忘れれば防げない
- **子の push の検査（2 重目）は、env で置き場を動かしていた人には既定しか見なくなる。** hook（1 重目）は
  フェーズ 3 で既に既定だけを見ているので、守りの範囲は hook と揃うだけで狭まらない
- テスト 3 本の頭に `CCNAVI_SH_DIR` の数行が増える

## やらない場合

実行ファイル・導入スクリプト・拡張は既定に固定されたのに、sh だけが env を読み続ける。env に値が
残っている配布先では、`ccnavi-push-approved.sh` が別の置き場を運び、`ccnavi-review.sh` が別の控えを見て、
実行ファイルと食い違う。A9 の 3 本は落ちたままで、親を統合先へ戻せない。

## 代案

1. **`main` を取り込まず、`git show main:.ccnavi/scripts/<名前>` を土台に写す版を作る。**
   親の取り込みを待たずに始められる。代わりに、写した時点で親のブランチの sh だけが `main` に
   追いつき、実行ファイルとテストは古いまま（`--version` を知らない実行ファイルに sh が互換を聞き、
   標準エラーに「古い版」が出る）。ブランチの中で sh とそれ以外がずれるので採らない
2. **親のブランチの今の `.ccnavi/scripts/` を土台にする（`main` を見ない）。** 取り込みが要らない。
   代わりに、写した版を統合先へ戻すときに `main` 側の sh の変更と衝突し、設計書 §3 の決め
   （`main` の現行から作り直す）にも反する
3. **テストに `CCNAVI_SH_DIR` を足さず、写す版を一時的な複製のワークスペースに重ねて全件を回す。**
   テストを直さずに済む。代わりに、複製の作り方が毎回の手作業になり、次の写す版で同じことをもう一度組む
