# 置き場を既定に固定する受入テストを書き、env で置き場を指していたテストを直す

親 i0064 のフェーズ 2（acceptance）。実装（`ccnavi/`・`scripts/`・拡張）には触らない。

## 書くもの

設計書 §6 のうち、`tests/` の下に置けるもの。

| # | 確かめること | 置き場 | 実装前 |
|---|---|---|---|
| A1 | 6 つの env を既定と違う値で入れても、`--explain --json` の `settings` が既定の置き場を返す | `tests/config/` | 赤 |
| A2 | 上書き設定ファイル（`ccnavi.settings.local.json`）に 6 つのキーを書いても、同じく既定を返す | `tests/config/` | 赤 |
| A3 | `CCNAVI_PROJECTS=""` を入れても `projects/` の下のプロジェクトが数えられる | `tests/guard/test_projects.py` | 赤 |
| A4 | `CCNAVI_LOG=""` を入れても記録が `logs/log.jsonl` に書かれる | `tests/guard/` か `tests/core/` | 赤 |
| A5 | ワークスペースが `projects/foo.txt` を追跡しているとき、`--lint` が `(projects)` の warn を先頭の句つきで 1 件出し、「無視されていない」を出さない。プロジェクトが 0 件でも出る | `tests/ticket/` | 赤 |
| A6 | 追跡が無く、プロジェクトがあり、無視されていないときは、今どおり「無視されていない」が出る | 同上 | 緑（回帰の見張り） |
| A7 | 導入スクリプトが、既存の `env` の 6 つを外し、既定と違う値だけを名指しする。既定と同じ値は黙って外す | `tests/sh/test_setup.py` | 赤 |
| A8 | 導入スクリプトが `projects/` の追跡を見つけたとき、`--lint` と同じ先頭の句を出し、終了コードを変えない | `tests/sh/test_setup.py` | 赤 |
| A9 | sh が env の値を読まない: `CCNAVI_PROJECTS=/x` を入れても `ccnavi_project` が `projects/<名前>` を返す。`CCNAVI_STATE=/x` を入れても `ccnavi-review.sh` が `logs/state` を見る | `tests/sh/` | 赤 |

A9 は今の `.ccnavi/scripts/` を相手にするので、**実装前は赤のまま**になる。sh の写す版が
人の手で写されるまで（フェーズ 4 の後）、A9 は緑にならない。赤のまま残る間は、テストに
`skip` を付けずに「フェーズ 4 で写すと通る」旨をコメントで残す。統合先へ戻す前に人が写す。

## 直すもの

設計書 §6「直すテスト」の表に従う。

| テスト | 直し方 |
|---|---|
| `test_projects.py`・`test_config_union.py` の「数えない」（`CCNAVI_PROJECTS=""`） | `projects/` を作らないワークスペースで確かめる |
| `CCNAVI_PROJECT_HOME` を入れていた 7 本 | 名前を変える意味のあるテストは消す。層の読み方を見ているだけなら既定の `.ccnavi` にする |
| `CCNAVI_TICKETS_APPROVED`・`CCNAVI_TICKETS_PROPOSAL` を入れていた 5 本 | 同上 |
| `CCNAVI_LOG`・`CCNAVI_STATE` を入れていた 3 本 | `--root` の下の `logs/` を見るか、診断のフラグ `--log` / `--state` に寄せる |
| `test_push_approved_sh.py` の正規化の 2 本 | 消す。A9 と同じ形で「値を読まない」を 1 本置く |
| `test_wrapguard.py` の `CCNAVI_PROJECTS=/x` | **残す**（ADR-0077。置く形を止める見本） |

直す前に、対象を `grep -rn "CCNAVI_\(PROJECTS\|PROJECT_HOME\|TICKETS_PROPOSAL\|TICKETS_APPROVED\|LOG\|STATE\)" tests/` で
全部拾い、設計書の本数と合わなければ、合わない分を報告に書く。

## 終わりの条件

- 直したテストは、今のコードで緑
- A6 は緑、A9 を含む新しい受入テストは赤で、赤の理由が「まだ実装が無い」ことだと報告に書く
- `ruff format --check` と `ruff check` が通る
- `ccnavi/`・`scripts/`・`.ccnavi/scripts/`・`vscode-extension/` に差分が無い

## 得るもの

- 実装の子（フェーズ 3）が、赤を緑にする形で進められる
- env に頼っていたテストが先に片付くので、フェーズ 3 の差分にテストの直しが混ざらない

## 失うもの

- **フェーズの間、`tests/` に赤が残る。** 統合先へ戻すのは全フェーズが済んでからなので、
  親のブランチの中だけの話。ただし Stop hook のテストが赤を報告し続ける
- **A9 は人が sh を写すまで緑にならない。** 写し忘れると、統合の直前まで赤が残る
- 診断のフラグに寄せたテストは、フラグを廃止する次のチケットでもう一度直すことになる

## やらない場合

実装とテストの直しが 1 つの子に混ざり、何が合格線で何が既存の直しかが差分から読めなくなる。
env を入れたままのテストは、フェーズ 3 で落ちてから原因を辿ることになる。
