# 実装側に残った文面とテストの説明を直す（`{!root}`）

親 i0061 のフェーズ 6（implement-feedback）。**振る舞いは変えない。**
コメントと docstring だけを直す。

## 直すもの

### 1. `ccnavi/rules.py:690` の不自然な日本語

```
ここだけ特別なのは、開く穴の大きさが「ワークスペースの外の全部」だから。
```

「開く穴の大きさ」が不自然だという指摘を受けた。同じ表現は `requirements.md` と
設計文書でも直してあり、ここだけ残っている。

```
ここだけ特別なのは、守られなくなる範囲が「ワークスペースの外の全部」に広がるから。
```

私は当初「指摘の側が誤り」と判断したが、利用者の指摘を受けて撤回した。

### 2. `tests/core/test_not_root_placeholder.py` の docstring が実態と違う

`test_a_very_long_root_does_not_raise` の docstring はこう書いてある。

```
`re` の組み立ては `RecursionError` を投げうる。捕まえていない例外は、
hook のプロセスごと落として呼び出しを素通りさせる入口になる。
```

**しかし、このテストは例外処理に到達しない。** `_expand_not_root` が
`len(real) >= MAX_ROOT_LEN`（256）で `re.compile` を呼ぶ前に必ず弾くので、
`except RecursionError` の側は一度も実行されない。組み立てが落ちるのは 493 字で、
256〜493 の範囲は事前の検査で全部止まる。

変異テスト（`rules.py` を壊してテストが落ちるか）で、**`except RecursionError` を
丸ごと消してもこのテストは落ちない**ことが確かめられている。

docstring を実態に合わせる。

- このテストが実際に縛っているのは「長すぎるルートで未処理例外にならないこと」であって、
  「例外処理そのものが動くこと」ではない
- `except RecursionError` を残す理由（閾値や展開の形を変えれば到達しうる）は
  `rules.py` の側に既に書いてある。テストからはそちらを指す

**テストの名前と assert は変えない。** 縛っている内容は正しく、説明だけが過剰だった。

## 得るもの

- 「不自然な日本語を直す」という指示が全部片付く
- 「保証している体裁だけのテスト」が無くなる。次に読む人が
  「`RecursionError` の捕捉はテストで守られている」と誤解しない

## 失うもの

- 1 行の文面のためにフェーズを 1 つ使う。提案・承認・着手・レビューの往復が 1 周増える
- テストの docstring が「何を縛っていないか」まで書くので、少し長くなる

## やらない場合

`rules.py` にだけ不自然な表現が残り、テストは実態と違う説明を持ち続ける。
どちらも動作には影響しないが、次に読む人が同じことを調べ直すことになる。

## 代案

**直接作業で直す。** `ccnavi/*` はチケットの範囲でしか書けないので、
チケット無しでは書けない。採れない。

## フェーズの範囲について

`implement-feedback` の `scope` は `inherit`（親の範囲そのまま）なので、
`ccnavi/*` と `tests/*` を宣言できる。ただし**この子が触るのは 2 ファイルだけ**で、
どちらも振る舞いを変えない。
