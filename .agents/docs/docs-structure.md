# 文書の置き場・読み手・リンクの向き

ccnavi の文書を足す・直す・動かすときの決まり。要件書・設計書・ADR それぞれに何を書くかは[要件書・設計書・ADRの書き分け](docs-writing.md)、思想は[思想の書き方](idea-writing.md)にある。ここでは、文書全体を読み手と階層で整理する。

## 読み手と置き場

文書は、読み手ごとに置き場を分ける。

| 読み手 | 置き場 | 書くこと | 入口 |
|---|---|---|---|
| 利用者（人） | `README.md`、`docs/50_guide/` | 使い方の手引き。症状や操作から引ける。内部実装・設計書の節番号・ADR の番号に依存しない | `README.md` → `docs/50_guide/index.md` |
| 利用者のエージェント | `.ccnavi/CCNAVI.md`、`.ccnavi/docs/` | 作業の決まりと手順。配布先にも配るので、配布先で成り立つ書き方にする | `.ccnavi/CCNAVI.md` の「詳細」の表 |
| 開発者（人） | `docs/40_development.md`、`docs/00_idea.md`・`docs/10_requirements.md`・`docs/20_design.md`・`docs/30_adr.md` とその配下 | 開発の入口、思想、要件、設計、判断の記録 | `docs/40_development.md` |
| 開発者のエージェント | `AGENTS.md`、`.agents/docs/` | ccnavi の開発で常に守る決まり。配布しない | `AGENTS.md` の「詳細」の表 |
| 実行時にコードが読む | `docs/wiki/` | 学びの蓄積。コードが固定のパスと書式で読む | `docs/40_development.md` |
| 用語集 | `docs/CONTEXT.md` | ccnavi の概念の定義。コードは読まない | `docs/40_development.md` |

- 開発の決まり（`.agents/docs/`）の一覧は `AGENTS.md` の「詳細」の表にある。開発環境、開発用 hook、組み立てと配布物は `docs/40_development.md` の案内表から辿れる。
- 利用者向けの文書（`docs/50_guide/`、`.ccnavi/docs/`）に、開発者向けの置き場（`docs/10〜30`、`.agents/docs/`、`src/`、`tests/`）のパスや節番号を書かない。配布先には無い。
- `.ccnavi/docs/` は配布先のエージェントが引く。配布先に無いパス（`src/`、`tests/`、`docs/`、`.agents/`、`scripts/`）を、読む手がかりとして書かない。
- `docs/50_guide/` は人が通して読む。同じ話題を `.ccnavi/docs/` が手順として持つなら、手引きは「何ができるか・なぜか」、使い方の文書は「どう打つか」と分け、同じ文を二重に書かない。
- 実行時にコードが読むもの（`docs/wiki/` の `patterns/`・`impact/` の欄など）は、書式をコードと揃える。書式を変えるときはコードと要件書・設計書を同じ変更の中で直す。

## 階層とリンクの向き

開発者向けの文書には上下がある。上から、思想（`00_idea.md`）、要件書（`10_requirements.md`・`11_requirements/`）、設計書（`20_design.md`・`21_design/`）、ADR・コードの順。

| 向き | 可否 |
|---|---|
| 下位から上位へのリンク | 書いてよい。根拠や前提を上位に求める形 |
| 上位から下位へのリンク | 一覧の参照先として書くときだけ可（入口の案内表、目次、「詳細」の表） |
| 上位の本文の説明文から、下位の特定の文書・節・ADR を指す | 書かない |

- 上位が下位を必要とするなら、その内容を上位に書く。要件を手引きに預けない。
- 設計書から ADR を指したいときは、設計書に判断の中身を書かない。判断の理由は ADR にあり、ADR が設計書を指す。
- 設計書から利用者向けの手引きを指さない。手引きの置き場や節は動く。
- 利用者向けの手引きから設計書の節番号を指さない。どうしても必要なら、設計書の文書名と見出しの言葉で、一覧の末尾にまとめる。
- 一覧の参照先でも、行数・節番号・表の何行目では指さず、文書名と見出しの言葉で指す（[書き分け](docs-writing.md)）。
- 入口・目次（`README.md`、`docs/40_development.md`、`docs/50_guide/index.md`、`docs/10_requirements.md`、`docs/20_design.md`、`docs/30_adr.md`、`AGENTS.md`、`.ccnavi/CCNAVI.md`）は、下位を並べるのが役目なので、案内表に限り上位から下位を指してよい。

## 1つの事実は1か所

- 同じ話を複数の文書に書かない。正を決めて、ほかは意味で指す。
- 用語の定義は `docs/CONTEXT.md`（ccnavi の概念）と `.ccnavi/docs/terms.md`（使い方で出る呼び名）に分かれる。同じ語を両方で定義しない。どちらかに寄せ、もう一方は指す。
- 値・閾値・一覧は、コードや設定に正があるなら、文書にコピーしない。
- コア機能の表のように入口に置く要約は、元の文書の言い回しと揃える。

## 作業メモ・進捗・経緯

- 設計書・決まりの文書に、調査の記録、未実施の予定、進捗の表、「以前は」の経緯を置かない。経緯は ADR に、日付は git の履歴にある。
- 進捗を書く文書は、陳腐化する前提で、「済み」「残り」の2つの表だけにする。計画や決めたことは ADR に置く。
- 作業中の下書きは作業ブランチの `wip/` に置く。git 管理外ではないが、main に入れる前に消す。

## 呼び名

| 呼び名 | 指すもの |
|---|---|
| 手引き | `docs/50_guide/`（利用者の人向け） |
| 使い方の文書 | `.ccnavi/docs/`（利用者のエージェント向け。配布する） |
| 開発の決まり | `.agents/docs/`（開発者のエージェント向け） |
| 要件書・設計書・ADR | `docs/10_requirements.md`・`docs/20_design.md`・`docs/30_adr.md` とその配下 |
| 利用形態 | ワークスペースだけで使う形と、プロジェクトを持つ形（かつて「使い方 A/B」と呼んだもの） |

「ガイド」は frontmatter の `type: guide` の値と、コア機能「ガードとガイド」にだけ使う。ほかの意味で使わない。

## 番号

`docs/` の番号は、入口の文書と、配下の詳細の置き場を対にする。

| 番号 | 入口 | 詳細 |
|---|---|---|
| 00・01 | `00_idea.md` | `01_idea/`（スライド） |
| 10・11 | `10_requirements.md` | `11_requirements/` |
| 20・21 | `20_design.md` | `21_design/` |
| 30 | `30_adr.md` | `30_adr/` |
| 40 | `40_development.md` | （配下を持たない） |
| 50 | `50_guide/index.md` | `50_guide/` |

`CONTEXT.md` と `wiki/` は、入口と詳細の対に当たらないので番号を付けない。`wiki/` はコードが固定のパスで読む。

## 文書を足す・動かすとき

1. 読み手を決め、上の表の置き場に置く。迷ったら、読み手が引く入口から辿れる側に置く。
2. 入口の案内表に1行足す。どの入口からも辿れない文書（孤児）を作らない。`.ccnavi/CCNAVI.md` の表は長さの上限があるので、足せないときは、親にあたる文書から辿れるようにする。
3. frontmatter を付ける（[値の決まり](frontmatter.md)）。
4. 動かす・改名するときは、旧い名前を文字列で検索して、参照を同じ変更の中で直す。見る場所は次のとおり。
   - 文書内のリンク
   - コードとスクリプトのコメント・文面（`src/`、`scripts/`、`.ccnavi/scripts/`、`.ccnavi/messages/`）
   - テストの期待値（`tests/`）
   - 設定（`.ccnavi/config/`）
   - 拡張の文書（`extensions/`）
5. ADR を別の主題へ動かすときは、番号を変えず、そのファイルへのパスのリンクだけを直す。
6. 手引き・使い方の文書・設計書を直したら、同じ話を書いたほかの文書を検索して、同じ変更の中で直す（[書き分け](docs-writing.md)）。

## 確かめ方

文書だけの変更でも、次を回す。

```sh
uv run python -m tests tests/core
```

リンクの先が実在することは、文書を直したあとに確かめる。
