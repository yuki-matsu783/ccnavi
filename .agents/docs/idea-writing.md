# 思想（00_idea.md とスライド）の書き方

ccnavi の根底にある考え方を書く文書の決まり。要件書・設計書・ADR の書き分けは[要件書・設計書・ADRの書き分け](docs-writing.md)にある。

## 置き場と扱い

| もの | 置き場 | 読み手 |
|---|---|---|
| 思想（正） | `docs/00_idea.md`（`type: idea`） | 開発者、エージェント |
| スライド | `docs/01_idea/index.html`（1 ファイルで動く HTML） | 人間。Claude Code を知らない人も読む |

- 思想は要件書より上段にある。ユーザが依頼しない限り直さない。機能の追加や仕様の変更では動かさず、要件書・設計書・ADR を直す
- 思想を直すときは、同じ変更の中で、スライドと、設計書の「コア機能と設計原則」にあるテーマと P の対応を揃える
- 要件書・設計書・ADR に、思想の中身を写さない。`00_idea.md` を指す
- 思想に書かないこと: 外から観測できる約束（要件書）、いまの実装（設計書）、個々の決定の経緯（ADR）、個別の関数・ファイル・オプションの仕様

## 構成

`00_idea.md` は次の順に書く。

1. 一文で言うと
2. 全体像: 解決するテーマの表（要点と、4 つのコア機能への対応を 1 つの表に）。続けて、前提（コンテキストロット・費用・スキルの budget）、Claude Code とモデルの進歩を見込むこと、想定する環境（手元の PC・別の PC・コンテナの実行）
3. テーマごとの Why・What・How・具体例
4. 作らないもの・限界
5. 下位の文書との関係

## テーマの切り方

- テーマは、ccnavi が解決する内容で切る。機能名やモジュールの単位では切らない
- 数は 5 前後にする。同じ解決策で片づくもの、同じ原因から出るものは 1 つにまとめる。1 つのテーマが、関係の薄い 2 つを抱えていたら分ける
- 4 つのコア機能とは別の軸で切るので、対応は全体像の表に 1 列で書く。章の中で 2 つの分類を並べない
- 共通の原則を別の節に立てない。どれかのテーマの What か How に入れる
- 新しい問題意識を足すときは、既存のテーマに入るかを先に問う。入らないときだけテーマを足す

## Why・What・How・具体例の書き分け

| 見出し | 書くこと |
|---|---|
| Why | 何が困るか。なぜ既存のやり方では足りないか。読み手が自分の問題として分かる場面 |
| What | ccnavi が何を実現するか。どうやるかは書かない |
| How | なぜその実装にしたか（理由）と、どうやって実現しているか（仕組みの考え方）。実装の細部ではなく、設計書の原則に落ちる粒度 |
| 具体例 | 1 つの場面を、順を追って書く |

- How は、実装の事実を並べない。各項目に、理由を添える（「〜するのは〜だから」「〜のために〜する」）。仕組みの名前（hook、ワークツリー、レイヤーなど）は、理由を説明するために使い、名前だけの列挙にしない
- 仕組みが「前提にしないこと」も、理由とともに書く（例: 同期していなくても動く。同期できない環境でも使えるようにするため）
- 具体例は、特定のコマンドや設定の仕様に寄せすぎない。たとえば、止める例は「一括削除を止めて、ファイル名の指定へ案内する」のように、場面が分かるものにする
- 具体例の固有名（ファイル名、件数など）は、分かりやすさのための想定でよい。ただし、実際の挙動と食い違うことは書かない
- 確率や数式は、前提を添える（例: 「ルールで検知できる外れについて、検知が漏れず、やり直しが互いに独立なら」）
- 実装の一部だけを言い切らない。書く前に、用語集（`docs/CONTEXT.md`）と要件書で、次のような条件を確かめる
  - テンプレートは、人間が取り込んだものだけが効く（AI が書くのは下書きまで）
  - 共通設定の写しは、プロジェクトを対象にした作業の時点で配られる。写しが無いと共通のルールは効かない
  - 組み込みの配点は行数・ファイル数・削除数など。マイグレーションを高リスクにするには、配点の設定が要る
  - issue・マージリクエスト・ブランチの 1 対 1 対 1 は、親子のチケットの単位
- テーマをまたいで、同じ題材の具体例を使わない。同じ題材だと、別のテーマの話と食い違って見える（例: 範囲外を止める例と、範囲に含めて承認した例）

## 言葉の揃え方

- 解決する内容のまとまりは「テーマ」と呼ぶ。「課題」と呼ばない
- 止めるのは ccnavi で、主語を ccnavi にした能動で書く（「ccnavi が止める」「機械的に止める」）。「止まる」「止められる」は使わない
- 止めるときは、理由と代わりの手段を一緒に返す、と書く。止めるだけだと別の書き方で打ち直される
- 人間の判断は、エージェントが代行できない形にする、と書く
- 共通のレイヤーの設定は「共通設定」と呼ぶ。「共通ルール」は使わない（用語集の「全体ルール」は deny / ask / allow を指す）。共通とプロジェクトの区別は「レイヤー」で書く（「2 層」と書かない）
- 「マージリクエスト」と書く。略称「MR」は用語集で使ってよい言い方なので、図の箱で略してもよい（画面の画像の中の表示は直せないので、そのまま）
- 「ワークフロー」「タスク」と書かない。「一連の作業・レビューの流れ」「作業」と書く
- 「設定ファイル」は、ccnavi のルール・フェーズ定義・配点を指す。Claude Code の hook の登録は「hook の登録」と書き分ける
- 親チケットを受け持つのはエージェント、レビューの単位はフェーズ。「親が」「子だけレビュー」と書かない
- 判定の結果は、通す・止める・人間に確認・Claude Code に任せる（ルールに当たらない）の 4 つ。「通す」と「任せる」を混ぜない
- スライドは、最初に「AI エージェントを AI と書く」と決め、「AI」で通す。文書は「エージェント」で通す
- 利用者がつけた言い換え（例: 「少なくなっていく仕組みです」）は、査読の指摘より優先して、そのまま使う

## スライドの作り方

読み手は、Claude Code を知らない人も含む。問題が分かり、それをどう解決しようとしているかが分かるようにする。

- 構成は、表紙、拡張の画面（見出しは「CCNAVI / IDEA」）、この資料の読み方、前提（Claude Code とは、ツール呼び出し、hook、文章の指示と hook の違い、コンテキストロット、費用、スキルの budget、ccnavi とは、チケットとは、想定する環境、Claude Code とモデルの進歩を見込むこと）、5 つのテーマ、作らないもの・限界、まとめ、文書の地図の順
- テーマごとに、問題、解決、具体例の順に、3 枚以上に分ける。1 枚に Why・What・How を詰め込まない
- 1 枚に 1 つの図を置き、短い文を添える。図で具体例を説明する
- 1 つの HTML ファイルで動くようにする。外部の読み込みを使わず、図はインライン SVG にする。明暗の両方で読めるようにし、キー・ボタンで送れる
- 色は、ccnavi が通す・人間が操作するものを青、止めるものを赤で揃える
- 拡張の画面を見せるときは、拡張の見本のデータ（`extensions/vscode/ccnavi-board/src/webview/tours/*.yml` の `sample:`）で画面を描いて撮り、WebP にして HTML へ埋め込む。実際のチケットや絶対パスが写る画面は使わない。見本の画面だと、スライドに書く
- 画面の画像には、日付と絶対パスを写さない。撮る範囲を狭めて外す。見本のデータが、説明と食い違うとき（例: deny のルールの文面が確認を求める）は、見本の文面を直して撮る
- 画面の画像は、スライドの本体と別に、ダークで撮る
- 同じ種類のものを、色で交互に塗り分けない。青い箱だけが特別（実装済みなど）に見える
- 枚数など、数える値は、数えて入れる。手で書かない
- スライドにだけある内容を作らない。スライドで前提・定義・画面・具体例を足すときは、先に `00_idea.md` に書く（スライドは文書に従う）。足したあと、スライドのタイトルと説明文を一覧にして、文書に無い主張が残っていないか見る
- eli10 で図を試作してから、スライドに移してよい。試作は正本ではない。`00_idea.md` が正で、スライドはそれに従う

## 確かめ方

- 画面の大きさを 4 つ（1280×720、1920×1080、1024×576、1366×768）にして、全スライドが画面に収まるか（スクロールが要らないか、下のボタンに被らないか）をブラウザで測る
- 図の中の文字と線、文字どうし、文字と箱が重ならないか、ブラウザで測る。見た目の確認と両方やる

- スライドは、全枚を描画して、文字のはみ出しと線の重なりを見る。図の中の文字は、箱に収まる長さにする
- `00_idea.md` に「課題」「止まる」「止められる」が残っていないか、文字列で検索する
- 思想を直したら、スライドの該当箇所と、設計書のテーマと P の対応を見直す

## 査読と横展開

思想とスライドは、直した場所の外にも同じ言い回しが残りやすい。次の順で確かめる。

1. 直したあと、別のモデルのサブエージェント（Opus）に、敵対的な査読をさせる。観点は、言葉の統一、文書とスライドの矛盾、実装との食い違い、スライドの流れ、図の問題、初見の読み手への分かりやすさ
2. 指摘は、そのまま取り込まず、1 件ずつ、用語集・要件書・設計書で確かめて、採るか決める。利用者が決めた言い方と食い違う指摘、意図して決めた配置（利用者が指定した順序など）に反する指摘は、採らず、理由を書く
3. 言い回しを直したら、別のモデルのサブエージェント（Haiku）に、残りの同じ言い回しを探させる（横展開）。対象は、`00_idea.md`、スライド、この文書、設計書の対応表。探す語は、直した前後の言い回し
4. 見つかったものは、直す。直さないものは、理由を残す
