# 操作を止める条件（関門）の置き方と、シンプルな実装・後方互換を考えない決まり

ccnavi の開発で、操作を止める条件を足す・直すとき、実装の方法を選ぶとき、名前や形式を変えるときの決まり。短い版は [AGENTS.md](../../AGENTS.md)。

## 関門の条件は 1 か所に置く

操作を止める条件（親のワークツリーに未コミットの変更がある、親のブランチが未 push、など）は、条件ごとに 1 つの関数に置く。複数の操作が同じ条件を見るときは、全部がその関数を呼ぶ。同じ意味の条件を、操作ごとに別の関数や sh で書き直さない。

- 置き場は実行ファイル（`src/ccnavi/`）。sh は実行ファイルに聞く（[exe-boundary.md](exe-boundary.md)）
- 「どの操作がどの条件を見るか」は、条件の側で宣言する。操作の側に条件を書き並べない。条件を足したら、見る操作を宣言に足す
- 条件が返すのは、理由と次の一手を持つ共通の形（Problem）。表示（ターミナルの文・ボードの JSON・案内）は、その結果を言い換えるだけにする。表示の入口が複数あっても、判定の実装は 1 つ

`start`・`finish`・`cancel`・`consolidate` の書く前の検査は、`lifecycle/commands.py` の `start_gate`・`finish_gate`・`cancel_gate` と `consolidate.py` の `gate` に置き、本体と `--check`（sh が取り込みの前に呼ぶ）が同じ関数を通る。合流のあとでないと分からない検査だけが本体に残る。

`review-request` の前提は `tickets/review/request.py` の `request_gate`、`decide` の依頼の記録・動きの検査は `tickets/review/decide.py` の `decide_gate` に置く。本体と `--check`（`ccnavi --check review prepare`・`ccnavi --entry sh --check user reviewed N --accept-unresolved`。sh がロック・取り込みの前に呼ぶ）が同じ関数を通る。`approval-request`・`review confirm`・`ready` も同じ型で、sh がロック・取り込みの前に `--check` を呼び、本体と同じ関数で断る。マージリクエストの有無など、ホストの API が要る条件は事前には判断しない。

親のワークツリーの未コミットの変更と親ブランチの未 push は、`lifecycle/treegate.py`（`check`）に寄せた。操作が見る条件は `WATCHES` に宣言する。git の呼び出しが重複していないことは `tests/core/test_gate_single_source.py`、操作ごとの拒否は `tests/core/test_treegate.py` が守る。置き場の判定は `ticket_places.is_ticket_place` に一本化した。

## ユーザに頼む操作は、後の関門で止まる条件を先に拒否する

承認を頼む操作（`approval-request`）とレビューを頼む操作（`review-request`）は、ユーザが次の一手を打てる状態でなければ、何も送らずに拒否する。

- 頼んだあとに、ユーザが拒否を見る、または承認・レビューのあとで作業が止まる、という往復を作らない
- 承認やレビューのあとに操作（`start`・`finish`・`ready` など）を止める条件のうち、頼む時点で分かるもの（環境だけで決まるもの）は、頼む操作も同じ関数で調べる。後の関門に条件を足したら、頼む操作にも足す。足し忘れは、関数を共有していれば起きない
- `--check` は、頼む操作と同じ拒否条件を通すだけの読み取り専用の入口。条件を別に持たない

## 開始前に分かる条件は、何も変えずに最初に断る

操作を止める条件のうち、操作を始める前に分かるもの（cwd・ファイルの有無・git の状態・引数の形・ローカルの記録）は、処理に入る前に断る。副作用（ファイルの書き込み・移動・git の変更・ホストへの投稿）のあとで気づいて案内を出すと、直す側は「どこまで進んだか」を読み取る手間を負う。

- 断るときは、何も変えず、`次:` で直し方を示す。エージェントが案内どおり直して打ち直せば済む形にする
- 判定は、最初に断る側と、あとの処理が使う側で同じ関数を共用する（同じ条件を 2 か所に書かない）
- 実行して結果を見ないと分からない条件（git の結果・ホストの API・入出力の失敗）は、途中で止めてよい。ホストの API のように事前確認の口が無いものは、最初には判断できない
- 理由と実例は ADR-0217

## 条件を足す・直すときの手順

1. 同じ意味の条件が既にないかを探す（`git status` を呼んでいる箇所、`origin/` との差を数えている箇所など）。あれば、その関数を直すか、共通の関数に寄せる
2. 条件の関数に足す。見る操作を宣言する
3. 試験を足す。条件ごとに、宣言した操作の全部で拒否されることを確かめる試験にする（操作をまたいで揃うことを試験が守る）
4. 文書に書く場所は、`.ccnavi/docs/ticket-flow.md`（拒否条件の一覧）と、設計書（`docs/21_design/tickets/`）

## シンプルな実装を選ぶ

実装は、読み手にとって一番シンプルになる方法を選ぶ。既存の作りに合わせて継ぎ足すより、共通の関数・型・置き場にまとめて単純にできるなら、そちらを選ぶ。

- 修正範囲が広がることは理由にしない。同じ処理が複数の場所にあるなら、1 か所に寄せる変更は、触るファイルが増えても進める
- 複製を残したまま、コメントで「あちらと同じ条件」と書いて済ませない。関数を共有する
- ただし、判定が緩む・やり取りの形が変わる・元に戻せない・影響範囲を読み切れない変更は、`.ccnavi/docs/decisions.md` のとおり、実装の前にユーザと合意する。シンプルにする理由で、合意を省かない

## 責務と依存関係を考える

共通化や関数の移動で、置き場と import の向きを崩さない。

- 1 つのモジュールは 1 つの責務を持つ。条件の関数は「何を調べるか」だけを持ち、表示（文・JSON）、操作の流れ、書き込みを持たない
- import は、同じ段か下の段へだけ向ける（`tests/core/test_module_layers.py`。サブパッケージの層は `docs/21_design/modules.md`）。共通の条件の関数は、それを呼ぶ操作の全部より下の段に置く。操作の側から共通の条件へ向け、逆は作らない
- 共通化のために上の段のモジュールを呼ぶ必要が出たら、呼び方を直さず、置き場を下へ動かす。関数の中の import や引数での注入は、循環を隠すだけなので避ける（循環は `test_module_layers` が全部拾う）
- 新しいモジュールを足したら、段と役割（docstring）を決めて `test_module_layers` の表に足す
- 環境を読む処理（git・ホスト）と、状態（チケット・マーカー）を読む処理は分ける。環境だけで決まる条件は、状態を知らない関数にして、承認の前後どちらの操作からも呼べるようにする

## 後方互換を考えない

コマンド名・オプション・出力の形・設定の書き方・ファイルの置き場を変えるときは、旧名や旧形式を残さず、新しいものに置き換える。

- 別名（エイリアス）、旧形式を読む処理、移行用の分岐、非推奨の警告を作らない
- 変えたら、リポジトリ内の旧名を全部置き換える（コード・sh・メッセージ・文書・試験・拡張・受入シナリオ）。置き換え漏れは全文検索で探す
- 旧名のまま残してよいのは、過去の経緯を残す ADR だけ。ADR は書き換えず、新しい ADR か改訂の一文で変更を書く
- 配布先への影響は、変更を提案するときにメリット・デメリットとして書く。互換のための仕組みで受け止めない
