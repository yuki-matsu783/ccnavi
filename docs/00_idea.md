# ccnavi の思想

ccnavi の根底にある考え方を書く。要件書・設計書・ADR は、ここに書いた考え方を実装と約束に落とした下位の文書である。
人間がスライドで通して読むための版は [01_idea/index.html](01_idea/index.html) にある（中身はこの文書と同じ）。

この文書はアプリの土台なので、ユーザが依頼しない限り直さない。機能の追加や仕様の変更では動かさず、要件書・設計書・ADR を直す。
考え方そのものが変わるときだけ、ユーザの依頼を受けてここから直し、下位の文書を追従させる。

## 一文で言うと

エージェントに任せる範囲を広げながら、人間の判断と目が届く道を失わせない。そのために、ccnavi がモデルの外で機械的に止め、誘導し、記録する。

## 全体像

ccnavi は、Claude Code を使った開発を、ルール・チケット・必要時の情報参照・振り返りで支えるツールである。
ccnavi が Claude Code の hook でツール呼び出しを止め、止めた理由と代わりの手段を返すガードが出発点で、いまは作業を合意からレビューまで進め、記録から決まりを良くするところまでを受け持つ。

ccnavi が解決するテーマは 5 つある。テーマごとに、Why・What・How を次の節に書く。4 つのコア機能との対応は表のとおり。

| # | テーマ | What（要点） | コア機能 |
|---|---|---|---|
| 1 | エージェントに、指示と制約を守らせる | 外れを hook で検知し、ガイドを添えてやり直させる。守る対象はプロジェクトが決め、逸れたら人間の目に触れさせる | ルールによる作業のガードとガイド |
| 2 | 計画で決めて、そのとおりに進める | 分類は事前に定義し、計画で選ぶ。承認された計画のとおりに進め、流れはテンプレートとして再利用する | チケットによる作業・レビュー管理 |
| 3 | レビューを厳密に管理する | issue・マージリクエスト・ブランチを 1 対 1 対 1 で紐づける。リスクの高い作業は人間のレビューを必須にし、状態は VS Code の拡張で見せる | チケットによる作業・レビュー管理 |
| 4 | 設定ファイルを共通とプロジェクトで共存させる | 設定ファイル（ルール・フェーズ定義・リスクの配点など）を git で管理し、共通の設定をプロジェクト側へ同期する | ルールによる作業のガードとガイド |
| 5 | 必要な情報を必要な時に届け、記録から育てる | 開始時は入口だけ渡し、理由は場面で、詳しい資料は必要なときに引く。記録と振り返りから改善候補を出し、人間が採ったものを次に活かす | 記録と振り返りによる改善、ドキュメント・スキルの検索と必要時の参照 |

判定の記録、dry-run、診断、ワークツリー、リモート経由の共有、拡張などは、コア機能を支える仕組みと入口である。5 つ目以降のコア機能ではない。

## テーマごとの Why・What・How

### テーマ 1: エージェントに、指示と制約を守らせる

**Why**

- たとえば「hello と尋ねられたら、必ず answer.md に『こんにちは』と書く」スキルを作っても、エージェントが必ず従うとは限らない。LLM の答えは確率的で、100% に近づけることはできても、絶対にはならない。スキルそのものが使われないこともある
- 作業に必要だと判断すると、禁止された操作を突破しようとする。悪意はなく、「hook が邪魔なので外す」「deny が厳しいので緩める」を、目的を達成しようとして普通に選ぶだけである
- 任せる範囲を広げるほど、人間が一手ずつ見ることはできなくなる
- 既存の防ぎ方には 4 つの穴がある
  - 設定のパターン一致はコマンドの構造（連鎖・サブシェル・リダイレクト）を見ないので、複合コマンドの後段が素通りする
  - プロンプトに書いた禁止は、守られる確率を上げるだけで 0 にはならない
  - 権限を静的に固定すると、広く開けるか毎回確認するかの二択になる。広く開ければ守れず、毎回確認すれば承認が形骸化する
  - 拒否の根拠がエージェントの書き換えられる作業ツリーの中にある

**What**

- 想定外の挙動を検知し、ガイドを添えて、やり直させる
- 外れる確率が 1% の LLM でも、外れるたびに検知してやり直させれば、3 回続けて外れる確率は 1% × 1% × 1% = 0.0001% になる。回数を重ねるほど、失敗し続ける確率はほぼ 0% に近づく（やり直しが互いに独立なら）
- 守る対象はプロジェクトが決め、それ以外は作業ごとの合意（チケット）に委ねる。委ねた先で逸れたときは、人間の目に触れさせる。これで、広く開けるか毎回確認するかの二択を崩す
- hook を作る手間が重いと、誰も作らない。作る手間を軽くする仕組みも作る

**How**

- 判定と案内は、モデルのコンテキストの外で動く ccnavi の hook の処理が行い、止めるときは機械的に止める。エージェントが自発的に守ることには頼らない
- 検知と案内は、ルールとして宣言する。hook そのものを自作しなくてよい。案内は、起きた時点の危険と失敗に対して、その場で返す
- 拒否は、止めた理由と代わりの手段を一緒に返す。止めるだけだと、別の書き方で打ち直される
- 失敗の向きは非対称である。誤検知で止めても、エージェントが一手遅れるだけだが、素通りは気づけない。迷ったら ccnavi が止める。ただし、設定 1 つの破損で回復手段まで奪う形は作らない
- 宣言された制約は緩められない。チケットは、絞る向きにだけ働く
- ガード自身（hook の登録・ルール・実行ファイル）を守る。委ねた回も、既定に落ちた回も、見られなかった回も、記録に残す

**具体例**

エージェントが rm -rf build/ で一括削除しようとする。ccnavi が止め、「一括削除は取り返しがつかない」と理由を返し、消すファイルを名前で指定して消すよう案内する。エージェントは案内どおり、名前を指定して消す。hook を外そうと設定ファイルを書き換えても、ccnavi がその書き換え自体を止める。

### テーマ 2: 計画で決めて、そのとおりに進める

**Why**

- どう作業を分割するか、どの範囲を直すか、どこでレビューするかは、作業を始める前に決めたい
- 計画のたびに分類を考え直すと、ぶれる
- 一連の作業の流れ（ワークフロー）は、似た形で何度も現れる。毎回ゼロから計画すると、手間もぶれも増える

**What**

- 計画のときに、分割・範囲・レビューの場所を決め、人間が承認した計画のとおりに作業する
- 作業の分類は事前に定義しておき、計画では、その中から選んで提案する
- 流れをテンプレートとして蓄積し、次のタスクでも再利用できるようにする

**How**

- 計画は、親と子のチケット（目的・範囲・フェーズ・レビューの位置）として書き、人間が承認する
- ccnavi は、承認された範囲の外を止め、中は聞かない。計画の変更は、改版の提案に限る
- 作業の分類は、フェーズの定義として持つ
- 完了した計画をテンプレートとして貯め、新しい計画を提案するときに使い回す

**具体例**

「ログイン画面のバグを直して」と頼む。親が、調査（読むだけ）→ 実装（src/auth/ と tests/ だけ）の 2 つの子に分け、実装が終わった時点をレビューの位置に決める。人間が承認すると、子が範囲外の migrations/ を触ろうとした時点で、ccnavi が止める。終わった計画は「バグ修正」のテンプレートとして貯まり、次の依頼で使い回される。

### テーマ 3: レビューを厳密に管理する

**Why**

- チケット作業では、レビューを厳密に管理したい
- 作業は複数台の PC や複数のセッションで進み、手元の対話セッションも、終われば消える自動実行もある
- すべての作業を同じ重さでレビューすると、人間が追いつかない。重く見るべきものを勘で選ぶと、ぶれる
- チケットの状態や承認待ちは、文字だけでは追いにくい

**What**

- チケットをマージリクエストに載せて管理し、チケットの動きを制御する
- issue・マージリクエスト・ブランチは 1 対 1 対 1 で紐づけて進める。どれか 1 つを見れば、残りの 2 つと作業の状態へたどれる
- リスクの高い作業を事前に定義し、一定以上リスクの高い作業は、人間のレビューを必須にする
- レビューのタイミングは hook で厳密に管理し、エージェントが乗り越えられないようにする
- VS Code の拡張で、状態を見える形にする

**How**

- チケットとマーカーは、親のブランチに載せる。レビューはホスト上で受ける。同期は操作の時点で行う
- 承認・レビュー済みの合図は、人間が直接操作する場所（端末・ボード・Chrome 拡張）で受ける。エージェントが代行できる形は作らない
- 作業は子のワークツリーで行い、親は計画・判断・報告に徹する。作業とレビューを、単一の PC・セッションに閉じ込めない
- レビューの前後で進められる操作は、ccnavi が hook で決める。レビュー待ちの間に先へ進む操作や、エージェント自身による「レビュー済み」の合図は、ccnavi が機械的に止める
- リスクは、実績の差分（実際に変えたもの）に配点して測る。高いものは、レビューが済むまで ccnavi が先へ進ませない
- 拡張のボードで、チケットの状態・承認・レビューを見せ、人間が判断する場所にもする

**具体例**

issue 「ログインのバグ」に、ブランチ fix-login と MR が 1 つずつ付く。別の PC でも、MR を開けば同じチケットの状態が見える。DB のマイグレーションを変える子は高リスクと測られ、人間のレビューが済むまで、ccnavi が先へ進ませない。承認待ちは VS Code のボードに並ぶ。レビュー待ちの子を、エージェントが自分で「レビュー済み」にして先へ進めようとしても、ccnavi が止める。

### テーマ 4: 設定ファイルを共通とプロジェクトで共存させる

**Why**

- Claude Code 専用のワークスペースの下にプロジェクトを clone し、共通の設定（ルール・フェーズ定義・リスクの配点など）をまとめて管理する使い方がある
- 各プロジェクトのディレクトリで Claude Code を起動する使い方もある
- 2 つの使い方は、同じチームに共存する

**What**

- どちらの使い方でも、誰もが同じ設定で、同じルールで作業できるようにする

**How**

- 設定ファイルは共通とプロジェクトの 2 層に分け、判定は両者の和で決める
- 設定ファイルも git で管理する。ワークスペースの共通の設定を、プロジェクト側にも常に同期する。写しが無くても、ccnavi は動く

**具体例**

共通ルール「rm -rf は禁止。ファイル名を指定して消す」を、ワークスペースで 1 回だけ書く。projects/web を開いた人も、projects/api を単独で開いた人も、同じルールで判定される。プロジェクト固有の「migrations/ は確認する」は、そのプロジェクトのルールに書く。

### テーマ 5: 必要な情報を必要な時に届け、記録から育てる

**Why**

- 決まりや手順は、最初に作って終わりにならない。使いながら、同じ失敗を繰り返さないよう直したい
- 決まりや文書を最初から全部渡すと、コンテキストが膨らみ、肝心なものが読まれない。必要になった時に、必要なものだけ届けたい

**What**

- 判定の記録、作業やレビューの気づき、振り返りから、ルール・作業手順・スキル・文書・計画テンプレートの改善候補を見つけて提案する
- 人間が採ったものを、次の作業に活かす
- 開始時は、作業の前提と入口だけを渡す。理由と手順は、関係する場面で届ける。詳しい資料は、エージェントが必要になったときに引く（テーマ 1 の案内もこの考えに沿う）

**How**

- 改善候補を出すのはエージェントまで。採るかどうかは人間が決める
- 改善するのはルール・手順・文書・計画の側で、モデルの学習ではない
- 場面に応じた案内は、テーマ 1 の判定と一緒に返す。文書の本文は最初から渡さず、frontmatter の索引と目録で読む対象を絞り、エージェントが自分で引く

**具体例**

セッションの開始では、作業の入口と文書の目録だけを渡す。マイグレーションを触る場面になって初めて、その手順書を引かせる。記録に「同じ拒否が 5 回出ている」と見つかれば、ルールの文面を直す案が提案され、人間が採ると、次の作業から効く。

## 作らないもの

- OS・DB・実行環境の権限分離の代わり。同じ権限で任意のシェルを実行できる相手に対しては境界にならない。ccnavi は、逸れていくエージェントと事故に対する柵である
- 人間の判断の代行。承認・レビュー済み・改善の採否を、エージェントが出せる形は作らない
- AI モデル自体の学習。改善するのはルール・作業手順・文書・計画の側である
- ルールが守られる、渡す情報が減る、という保証。そうなるよう設計するが、保証はしない
