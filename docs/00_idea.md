# ccnavi の思想

ccnavi の根底にある考え方を書く。要件書・設計書・ADR は、ここに書いた考え方を実装と約束に落とした下位の文書である。
人間がスライドで通して読むための版は [01_idea/index.html](01_idea/index.html) にある（この文書に従う）。

この文書はアプリの土台なので、ユーザが依頼しない限り直さない。機能の追加や仕様の変更では動かさず、要件書・設計書・ADR を直す。
考え方そのものが変わるときだけ、ユーザの依頼を受けてここから直し、下位の文書を追従させる。

## 一文で言うと

エージェントに任せる範囲を広げながら、人間の判断と目が届く道を失わせない。そのために、ccnavi が AI の判断の外で機械的に止め、誘導し、記録する。

## 全体像

ccnavi は、Claude Code を使った開発を、ルール・チケット・必要時の情報参照・振り返りで支えるツールである。
ccnavi が Claude Code の hook でツール呼び出しを止め、止めた理由と代わりの手段を返すガードが出発点で、いまは作業を合意からレビューまで進め、記録から決まりを良くするところまでを受け持つ。

ccnavi が解決するテーマは 5 つある。テーマごとに、Why・What・How を次の節に書く。4 つのコア機能との対応は表のとおり。

| # | テーマ | What（要点） | コア機能 |
|---|---|---|---|
| 1 | エージェントに、指示と制約を守らせる | 外れを hook で検知し、ガイドを添えてやり直させる。守る対象はプロジェクトが決め、逸れたら人間の目に触れさせる | ルールによる作業のガードとガイド |
| 2 | 計画で決めて、そのとおりに進める | 分類は事前に定義し、計画で選ぶ。承認された計画のとおりに進め、流れはテンプレートとして再利用する | チケットによる作業・レビュー管理 |
| 3 | レビューを厳密に管理する | issue・マージリクエスト・ブランチを 1 対 1 対 1 で紐づける。リスクの高い作業は人間のレビューを必須にし、状態は VS Code の拡張で見せる | チケットによる作業・レビュー管理 |
| 4 | 設定ファイルを共通とプロジェクトで共存させる | 設定ファイル（ルール・フェーズ定義・リスクの配点など）を git で管理し、共通設定をプロジェクト側へ同期する。画面でも編集できる | ルールによる作業のガードとガイド、チケットによる作業・レビュー管理 |
| 5 | 必要な情報を必要な時に届け、記録から育てる | 開始時は入口だけ渡し、理由は場面で、詳しい資料は必要なときに引く。連続する作業の指示は、前の作業が完了した時に次の案内を出す。スキルは工程ごとの入口に絞り、reference を育てる。記録と振り返りから改善候補を出し、人間が採ったものを次に活かす | 記録と振り返りによるルール・作業手順の改善、ドキュメント・スキルの検索と必要時の参照 |

判定の記録、dry-run（判定だけ記録して止めない試運転）、診断、ワークツリー、リモート経由の共有、拡張などは、コア機能を支える仕組みと入口である。5 つ目以降のコア機能ではない。

### 前提: Claude Code・hook・チケット

この文書とスライドは、Claude Code を知らない人にも読めるようにする。次の 4 つを前提にする。

- **ツール呼び出し**: Claude Code のエージェントは、ファイルの読み書き、コマンドの実行、git の操作などを、自分で選んで進める。作業は、ツール呼び出しという 1 回ずつの操作でできている。1 回ずつの操作なので、その手前で止められる
- **hook**: ツール呼び出しの直前と直後に、外部のプログラムを呼べる仕組み。ccnavi は、この hook に登録された見張り役で、操作を判定して、通す・止める・人間に確認する・Claude Code に任せる（ルールに当たらないとき）のどれかを返す。止めるときは、理由と代わりの手段を一緒に返す
- **文章の指示と hook**: CLAUDE.md・スキル・プロンプトのような文章の指示は、エージェントが読んで従うかを決める（確率）。hook は、プログラムが機械的に判定するので、確率に左右されない
- **チケット**: 作業の目的・範囲・計画を書いた、人間との合意。計画を書く親チケットと、フェーズごとの作業を受け持つ子チケットがある。人間が承認してから、作業を始める

### 前提: コンテキストと費用

テーマ 5 を理解するには、エージェントが一度に見ている情報（コンテキスト）の性質を知っておく必要がある。コンテキストには、指示、会話、読んだファイル、ツールの結果が入る。

- **コンテキストロット**: コンテキストが長く雑多になるほど、重要な指示が埋もれ、エージェントの精度が落ちる。指示を足せば足すほど守られる、とは限らない。モデルが一度に受け取れるトークン量（入力の上限）が増えても、これは解決しない。入れられる量が増えることと、入れた量を同じ精度で使えることは別である
- **費用**: エージェントは、やり取りのたびにコンテキストを読み込む。指示や文書を作りすぎると、そのぶん、毎回の費用と時間が増える
- **スキルの budget**: スキルの名前と説明は、常にコンテキストに載る。載せられる量には上限（budget）がある。ユーザが自由にスキルを作って増えすぎると、上限を使い切り、一部のスキルは載らず、使われなくなる

最初に全部を渡さず、必要な時に必要なものだけを届ける考え方は、この性質から来ている。

### Claude Code とモデルの進歩を見込む

ccnavi は、Claude Code やモデルが育ち続けることを見込む。いまの ccnavi の案内や hook は、いまの限界を補うためにある。

- 進歩して、そのまま使っても意図どおりに動くようになるほど、ccnavi が注入するコンテキストは少なくなっていく仕組みにする。補う必要がなくなった案内や決まりは、減らす
- 進歩を待たずに足し続けない。足すときは、いまの限界を補うものか、将来は不要になるかを意識する
- 進歩しても残るものは、人間の判断を残すことと、複数の環境をつなぐことである

### 想定する環境

ccnavi は、いろいろな環境で使われることを前提にする。同じプロジェクトを、異なる環境の人やセッションが共有する。

| 環境 | 特徴 | ccnavi の考え方 |
|---|---|---|
| 手元の PC の対話セッション | ユーザが付き添う。Windows（Git Bash・WSL）・Linux・macOS のどれでも動く | 承認・レビューは、ユーザが直接操作する場所で受ける |
| 別の PC・別のセッション | 同じプロジェクトを、別の機械や別のセッションで進める | チケットとマーカーをブランチに載せ、レビューはホスト上で受ける。同期は操作の時点で行う |
| Claude Code 実行用のコンテナ | ユーザが付き添わず、非対話で動く。終わるとコンテナごと消え、コンテナの中だけにある作業は失われる | 残したい作業はリモートへ反映し、ユーザの判断（承認・レビュー）は、あとから別の場所で受ける |

どの環境でも、同じ設定とルールで同じ判定になることを目指す（テーマ 3、テーマ 4）。

## テーマごとの Why・What・How

### テーマ 1: エージェントに、指示と制約を守らせる

**Why**

- たとえば「hello と尋ねられたら、必ず answer.md に『こんにちは』と書く」スキルを作っても、エージェントが必ず従うとは限らない。LLM の答えは確率的で、100% に近づけることはできても、絶対にはならない。スキルそのものが使われないこともある
- 作業に必要だと判断すると、禁止された操作を突破しようとする。悪意はなく、「hook が邪魔なので外す」「deny が厳しいので緩める」を、目的を達成しようとして普通に選ぶだけである
- 任せる範囲を広げるほど、人間が一手ずつ見ることはできなくなる
- Claude Code デフォルトの防ぎ方には 4 つの穴がある
  - 設定のパターン一致はコマンドの構造（連鎖・サブシェル・リダイレクト）を読み切れず、複合コマンドの後段が素通りすることがある
  - プロンプトに書いた禁止は、守られる確率を上げるだけで 0 にはならない
  - 権限を静的に固定すると、広く開けるか毎回確認するかの二択になる。広く開ければ守れず、毎回確認すれば承認が形骸化する
  - 拒否の根拠（プロジェクトの設定）が、エージェントの書き換えられるワークツリーの中にある

**What**

- 想定外の挙動を検知し、ガイドを添えて、やり直させる
- 外れる確率が 1% の LLM でも、外れるたびに検知してやり直させれば、3 回続けて外れる確率は 1% × 1% × 1% = 0.0001% になる。回数を重ねるほど、失敗し続ける確率は 0% に近づく（ルールで検知できる外れについて、検知が漏れず、やり直しが互いに独立なら）
- 守る対象はプロジェクトが決め、それ以外は作業ごとの合意（チケット）に委ねる。委ねた先で逸れたときは、人間の目に触れさせる。これで、広く開けるか毎回確認するかの二択を崩す
- hook を作る手間が重いと、誰も作らない。作る手間を軽くする仕組みも作る

**How**

- 判定と案内は、AI の判断の外で動く ccnavi が行う。AI が守る気になるかに頼ると、確率で外れるから。hook はツールを使う直前に外部のプログラムを呼べるので、その手前で機械的に判定できる
- 検知と案内は、hook を自作せず、ルールとして宣言できるようにする。hook を作る手間が重いと、誰も作らないから。案内は、起きた時点の危険と失敗に対して、その場で返す。最初に決まりを詰め込むと、コンテキストロットになるから
- 止めるときは、理由と代わりの手段を一緒に返す。止めるだけだと、別の書き方で打ち直されるから
- 迷ったら ccnavi が止める。誤検知で止めても、エージェントが一手遅れるだけだが、素通りは気づけないから。ただし、設定 1 つの破損で回復手段まで奪わない。直す道を残さないと、止めたまま動けなくなるから
- 宣言された制約は、チケットでも緩められない。緩められると、突破の入口になるから。チケットは、絞る向きにだけ働く
- ガード自身（hook の登録・ルール・実行ファイル）も守る。AI が外せると、ほかの防ぎ方がすべて無意味になるから。ルールに当たらず Claude Code に委ねた回も、読めずに既定のルールで判定した回も、実行後に確かめられなかった回も記録に残し、あとから見直せるようにする

**具体例**

エージェントが rm -rf build/ で一括削除しようとする。ccnavi が止め、「一括削除は取り返しがつかない」と理由を返し、消すファイルを名前で指定して消すよう案内する。エージェントは案内どおり、名前を指定して消す。hook の登録を書き換えて外そうとしても、ccnavi がその書き換え自体を止める。

### テーマ 2: 計画で決めて、そのとおりに進める

**Why**

- どう作業を分割するか、どの範囲を直すか、どこでレビューするかは、作業を始める前に決めたい。範囲を決めずに任せると、気づかないうちに想定外のファイルが変わる
- 計画のたびに分類を考え直すと、ぶれる
- 一連の作業・レビューの流れは、似た形で何度も現れる。毎回ゼロから計画すると、手間もぶれも増える

**What**

- 計画のときに、分割・範囲・レビューの場所を決め、人間が承認した計画のとおりに作業する
- 作業の分類は事前に定義しておき、計画では、その中から選んで提案する
- 完了した計画からテンプレートの下書きを作り、人間が取り込んだものを、次の作業でも再利用できるようにする

**How**

- 計画は、親と子のチケット（目的・範囲・フェーズ・レビューの位置）としてエージェントが提案し、人間が承認する。作業を始める前に、分け方・範囲・レビューの場所を合意しておくため。作業はフェーズごとに進み、計画でレビューが要ると決めたフェーズだけを、人間がレビューする
- ccnavi は、承認された範囲の外を止め、中は聞かない。範囲の外は人間が見ていないが、中を毎回聞くと承認が形骸化するから。計画を変えたいときは、改版の提案を経る
- 作業の分類は、フェーズの定義として事前に持つ。計画のたびに分類を考え直すと、ぶれるから
- 完了した計画から、テンプレートの下書きを作る。人間が取り込んだものだけが、新しい計画を提案するときに使い回される。エージェントが勝手に貯めて効かせると、人間の目を通らない決まりが増えるから

**具体例**

「ログイン画面のバグを直して」と頼む。エージェントが、調査（読むだけ）と実装（src/auth/ と tests/ だけ）の 2 つのフェーズに分け、実装のフェーズが終わった時点をレビューの位置にする計画を提案する。人間が承認すると、作業する子が範囲外の migrations/ を触ろうとした時点で、ccnavi が止める。終わった計画から「バグ修正」のテンプレートの下書きを作り、人間が取り込めば、次の依頼で使い回せる。

### テーマ 3: レビューを厳密に管理する

**Why**

- 状態が散ると、どこまで進んだか、誰がレビュー済みにしたかが分からず、レビューを飛ばして取り込む事故が起きうる。レビューは厳密に管理したい
- 作業は複数台の PC や複数のセッションで進み、手元の対話セッションも、終われば消える自動実行もある
- すべての作業を同じ重さでレビューすると、人間が追いつかない。重く見るべきものを勘で選ぶと、ぶれる
- 計画の時点では、どの作業にレビューが要るかを、完全には判断できない。作ってみて初めて、大きな変更だと分かることがある
- チケットの状態や承認待ちは、文字だけでは追いにくい

**What**

- チケットをマージリクエストに載せて管理し、チケットの動きを制御する
- 親チケット 1 つにつき、issue・マージリクエスト・ブランチを 1 つずつ（1 対 1 対 1）紐づけて進める。どれか 1 つを見れば、残りの 2 つと作業の状態へたどれる
- リスクの配点を事前に定義する。計画でレビュー不要としていた作業でも、実績が一定以上のリスクになったら、レビュー要にして、人間のレビューを必須にする
- レビューのタイミングは hook で厳密に管理し、エージェントが乗り越えられないようにする
- VS Code の拡張で、状態を見える形にする

**How**

- チケットとマーカーは、親のブランチに載せ、レビューはホスト上で受ける。ブランチとホストは、どの PC・コンテナからも同じ状態に見える共通の置き場だから。同期は操作の時点で行う
- 承認・レビュー済みの合図は、人間が直接操作する場所（端末・ボード・Chrome 拡張）で受ける。エージェントが出せる形にすると、人間の判断の代行になるから
- 作業は子のワークツリーで行い、親は計画・判断・報告に徹する。親のコンテキストを清潔に保つため。作業とレビューを、単一の PC・セッションに閉じ込めない
- レビューの前後で進められる操作は、ccnavi が hook で決める。レビュー待ちの間に先へ進む操作や、エージェント自身による「レビュー済み」の合図を機械的に止めるのは、レビューのタイミングを AI が乗り越えられないようにするため
- リスクは、計画ではなく、実績の差分（実際に変えたもの）に配点して測る。計画の時点では、完全には分からないから。一定以上になったら、計画でレビュー不要としていたものも、レビュー要に切り替え、レビューが済むまで ccnavi が先へ進ませない
- 拡張のボードで、チケットの状態・承認・レビューを見せる。承認の画面では、計画の流れと、レビューが要るフェーズも見せる。文字だけでは追いにくく、内容を確かめてから人間が判断できるようにするため

**具体例**

issue「決済の金額が合わない」に、ブランチ fix-payment とマージリクエストが 1 つずつ付く。別の PC でも、マージリクエストを開けば同じ状態が見える。計画では DB のマイグレーションも範囲に含めて承認してある。マイグレーションに配点したプロジェクトでは、その子は高リスクと測られ、人間のレビューが済むまで、ccnavi が先へ進ませない。計画の承認待ちは VS Code のボードに並ぶ。レビュー待ちの子を、エージェントが自分で「レビュー済み」にして先へ進めようとしても、ccnavi が止める。

### テーマ 4: 設定ファイルを共通とプロジェクトで共存させる

**Why**

- Claude Code 専用のワークスペースの下にプロジェクトを clone し、共通設定（ルール・フェーズ定義・リスクの配点など）をまとめて管理する利用形態がある
- 各プロジェクトのディレクトリで Claude Code を起動する利用形態もある
- 2 つの利用形態は、同じチームに共存する

**What**

- どちらの利用形態でも、誰もが同じ設定で、同じルールで作業できるようにする
- 設定ファイルは、ファイルを直接書かなくても、VS Code の拡張の画面で足したり直したりできるようにする

**How**

- 設定ファイルは共通とプロジェクトの 2 つのレイヤーに分け、判定は両者の和で決める。共通の決まりは 1 回書けば全員に効き、プロジェクト固有の決まりは、そのプロジェクトにだけ効かせるため
- 設定ファイルも git で管理する。履歴と差分が残り、複数人で共有できるから
- 設定ファイルは、VS Code の拡張の画面でも編集できる。書式を知らなくても、足したり直したりできるようにするため
- 共通設定は、作業の時点で、プロジェクトへ同期する。プロジェクトだけを開く人にも、共通設定が届くようにするため。同期していなくても、ccnavi は動く（その場合は、共通設定が使われないだけ）。同期を前提にすると、同期を前提にしないのは、同期できない環境でも使えるようにするため

**具体例**

共通設定に、ルール「rm -rf は禁止。ファイル名を指定して消す」を、ワークスペースで 1 回だけ書く。projects/web を開いた人も、projects/api を単独で開いた人も、同じルールで判定される。プロジェクト固有の「migrations/ は確認する」は、そのプロジェクトのルールに書く。

### テーマ 5: 必要な情報を必要な時に届け、記録から育てる

**Why**

- 決まりや手順は、最初に作って終わりにならない。使いながら、同じ失敗を繰り返さないよう直したい
- 決まりや文書を最初から全部渡すと、コンテキストが膨らんで、重要な指示が希薄化し（コンテキストロット）、肝心なものが読まれず、費用も増える。必要になった時に、必要なものだけ届けたい
- スキルを自由に作って増やすと、スキルの budget を使い切り、スキルが使われなくなる
- 作業 A、作業 B、作業 C の順に連続して進めるとき、その手順を CLAUDE.md などに最初から全部書くと、まだ先の指示までコンテキストを占める。途中で要るのは、次の作業の案内だけである

**What**

- 判定の記録、作業やレビューの気づき、振り返りから、ルール・作業手順・スキル・文書・計画テンプレートの改善候補を見つけて提案する
- 人間が採ったものを、次の作業に活かす
- スキルは、標準の工程ごとの薄い入口（工程スキル）に絞る。細かい手順は reference として溜めて育て、必要なときに引く
- 注入は、いまの限界を補うものに限る（前提の「Claude Code とモデルの進歩を見込む」節）
- 開始時は、作業の前提と入口だけを渡す。理由と手順は、関係する場面で届ける。詳しい資料は、エージェントが必要になったときに引く（テーマ 1 の案内もこの考えに沿う）
- 連続する作業の指示は、全体を最初に渡さない。作業 A が完了したときに初めて次の作業 B を案内し、作業 C の案内は作業 B が完了したときに渡す

**How**

- 改善候補を出すのはエージェントまで。採るかどうかは人間が決める。ルールや手順は、人間の判断を経て育てるものだから
- 改善するのはルール・手順・文書・計画の側で、モデル自体の学習ではない
- スキルは、名前と説明だけがコンテキストに載る薄い入口（工程スキル）に絞る。スキルが増えると、budget を使い切って使われなくなるから。細かい手順は、reference として `references/` に置き、必要なときに引く。共通のものとプロジェクト固有のものに分けるのは、ほかのプロジェクトでも使える手順を共有するため。振り返りの結果は、reference の追加や追記として入れ、育てる
- 場面に応じた案内は、テーマ 1 の判定と一緒に返す。文書の本文は最初から渡さず、索引と目録で読む対象を絞り、エージェントが自分で引く。コンテキストロットと費用を抑えるため
- 連続する作業の指示は、前の作業が完了した時に、次の作業の案内を出す。案内は、前の作業の出力に「このあとは作業 B」と書いて渡す。前の作業の出力を変えられないとき（Claude Code の組み込みのツール呼び出しなど）は、その完了後に、hook が追加の文脈として足す。全体を最初に渡すと、まだ先の指示まで常に読み込まれ、いま要る一手が埋もれるから。前の作業が完了した時点で渡せば、その結果に応じた次の作業を案内できる。危険や失敗への案内に限らず、普段の作業の続きも、同じ仕組みで渡す

**具体例**

セッションの開始では、作業の入口と文書の目録だけを渡す。マイグレーションを触る場面になって初めて、その手順書を引かせる。記録に「同じ拒否が 5 回出ている」と見つかれば、ルールの文面を直す案が提案され、人間が採ると、次の作業から効く。

ツール A、ツール B、ツール C の順に使う作業なら、最初には A だけを案内する。A の出力に「このあとはツール B」と書き、B の出力に「このあとはツール C」と書く。出力を変えられないツールなら、その呼び出しが完了した後に、hook が同じ案内を足す。

ccnavi の例では、子チケットの作業が完了した時に、出力が「親の状態を確かめる」と案内する。親を閉じてマージに進む手順は、親の作業が完了した時の出力で初めて出る。

## 作らないもの・限界

- OS・DB・実行環境の権限分離の代わり。同じ権限で任意のシェルを実行できる相手に対しては境界にならない。ccnavi は、逸れていくエージェントと事故に対する柵である
- 人間の判断の代行。承認・レビュー済み・改善の採否を、エージェントが出せる形は作らない
- AI モデル自体の学習。改善するのはルール・作業手順・文書・計画の側である
- 完全な防止。複雑すぎる回避は、防ぎきれない。ccnavi は、できる限りは防ぐ（コマンドの構造を読んで判定する、書き換えを検知して戻す、など）が、守られること、渡す情報が減ることの保証はしない
