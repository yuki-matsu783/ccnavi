# ccnavi の思想

ccnavi の根底にある考え方を書く。要件書・設計書・ADR は、ここに書いた考え方を実装と約束に落とした下位の文書である。
人間がスライドで通して読むための版は [01_idea/index.html](01_idea/index.html) にある（中身はこの文書と同じ）。

この文書はアプリの土台なので、ユーザが依頼しない限り直さない。機能の追加や仕様の変更では動かさず、要件書・設計書・ADR を直す。
考え方そのものが変わるときだけ、ユーザの依頼を受けてここから直し、下位の文書を追従させる。

## 一文で言うと

エージェントに任せる範囲を広げながら、人間の判断と目が届く道を失わせない。そのために、モデルの外にある仕組みで止め、誘導し、記録する。

## Why: なぜ作るか

### 課題

課題は 7 つある。

#### 1. 指示を緻密に書いても、エージェントは希望どおりに動かない

たとえば「hello と尋ねられたら、必ず answer.md に『こんにちは』と書く」スキルを作っても、エージェントが必ず従うとは限らない。

- LLM の答えは確率的で、100% に近づけることはできても、絶対にはならない
- スキルそのものが使われないこともある

対策は、想定外の挙動を hook で検知し、ガイドを添えてやり直させることである。外れる確率が 1% の LLM でも、外れを検知してやり直させれば、ほぼ希望どおりに動かせる。
ただし hook を作るのは大変で、作る負担が重いと誰も作らない。hook を作る手間を軽くする仕組みも要る。

#### 2. エージェントは、目的のために制約を突破しようとする

作業に必要だと判断すると、禁止された操作を突破しようとする。悪意はなく、「hook が邪魔なので外す」「deny が厳しいので緩める」を、目的を達成しようとするエージェントが普通に選ぶだけである。
任せる範囲を広げるほど、人間が一手ずつ見ることはできなくなる。既存の防ぎ方には 4 つの穴がある。

- 設定のパターン一致はコマンドの構造（連鎖・サブシェル・リダイレクト）を見ないので、複合コマンドの後段が素通りする
- プロンプトに書いた禁止は、守られる確率を上げるだけで 0 にはならない
- 権限を静的に固定すると、広く開けるか毎回確認するかの二択になる。広く開ければ守れず、毎回確認すれば承認が形骸化する
- 拒否の根拠がエージェントの書き換えられる作業ツリーの中にある

#### 3. 厳密なレビュー管理が要るが、作業は複数の PC・セッションに散る

チケット作業では、レビューを厳密に管理したい。しかし作業は複数台の PC や複数のセッションで進む。
そこで、チケットをマージリクエストに載せて管理し、チケットの動きを制御する仕組みが要る。
issue・マージリクエスト・ブランチは 1 対 1 対 1 で紐づけて作業を進める。どれか 1 つを見れば、残りの 2 つと作業の状態へたどれる。

#### 4. 複数のプロジェクトを、共通のルールとプロジェクトのルールで分けて管理したい

Claude Code 専用のワークスペースの下にプロジェクトを clone し、共通のルールをまとめて管理する使い方と、各プロジェクトのディレクトリで Claude Code を起動する使い方は、同じチームに共存する。
どちらの使い方でも、誰もが同じルールで作業できなければならない。ルールも git で管理し、ワークスペースの共通ルールを、いつもプロジェクト側へ同期する。

#### 5. 作業の分け方・範囲・レビューの場所を、計画で決めて、そのとおりに進めたい

どう作業を分割するか、どの範囲を直すか、どこでレビューするかは、計画のときに決める。人間が承認した計画のとおりに作業を進める。
計画のたびに分類を考え直すと、ぶれる。そこで、作業の分類は事前に定義しておき、計画では、その中から選んで提案する。

#### 6. リスクの高い作業は、人間が必ず見る

すべての作業を同じ重さでレビューすると、人間が追いつかない。リスクの高い作業を事前に定義しておき、一定以上リスクの高い作業は、人間のレビューを必須にする。

#### 7. 同じ流れを毎回作り直し、いまの状況も見えにくい

一連の作業の流れ（ワークフロー）は、似た形で何度も現れる。毎回ゼロから計画すると、手間もぶれも増える。流れをテンプレートとして蓄積し、次のタスクで再利用できるようにする。
また、チケットの状態や承認待ちは文字だけでは追いにくい。VS Code の拡張で、見て分かる形にする。

### 解きたいこと

- 守る対象はプロジェクトが決め、それ以外は作業ごとの合意（チケット）に委ねる。委ねた先で逸れたときは、人間の目に触れさせる。これで、広く開けるか毎回確認するかの二択を崩す（課題 2）
- 指示が外れたことを hook で検知し、ガイドを添えてやり直させる。その hook を作って育てる手間を軽くする（課題 1）
- チケットをマージリクエストに載せ、issue・マージリクエスト・ブランチを 1 対 1 対 1 で紐づけ、動きを制御して、複数の PC・セッションにまたがる作業とレビューを厳密に管理する（課題 3、5）
- ルールを共通とプロジェクトに分けて git で管理し、共通ルールをプロジェクト側へ同期して、どの使い方でも同じルールで作業できるようにする（課題 4）
- 分割・範囲・レビューの場所を計画で決め、承認された計画のとおりに進める。作業の分類は事前に定義し、計画ではその中から選ぶ（課題 5）
- リスクの高い作業を事前に定義し、一定以上は人間のレビューを必須にする（課題 6）
- 作業の流れをテンプレートとして蓄積して再利用し、状態を VS Code の拡張で見えるようにする（課題 7）

### 目指す姿

- エージェントは、止められても、代わりに何をすればよいかが分かり、自力で作業を進められる
- 人間は、承認・レビュー・改善の採否という判断に集中でき、その判断はエージェントが代行できない
- 作業の記録が残り、同じ失敗を繰り返さないよう、決まりと手順が育つ

## What: 何を作るか

ccnavi は、Claude Code を使った開発を、ルール・チケット・必要時の情報参照・振り返りで支えるツールである。
Claude Code の hook でツール呼び出しを止め、止めた理由と代わりの手段を返すガードが出発点で、いまは作業を合意からレビューまで進め、記録から決まりを良くするところまでを受け持つ。

| コア機能 | 何をするか |
|---|---|
| ルールによる作業のガードとガイド | ツール実行とファイル操作をルールに照らして判定し、止める・確認する・注意点を伝える。拒否には代わりの手段を添える |
| チケットによる作業・レビュー管理 | 作業の目的・範囲・計画を合意し、承認、フェーズ、レビュー、指摘への対応を経て、合意した作業をレビューまで進める |
| ドキュメント・スキルの検索と必要時の参照 | 文書と作業手順を最初から全部は渡さず、目録と索引で絞り、本文は必要になったときに読ませる |
| 記録と振り返りによるルール・作業手順の改善 | 判定の記録と気づきから改善候補を見つけて提案し、人間が採ったものを次の作業に活かす |

判定の記録、dry-run、診断、ワークツリー、リモート経由の共有、拡張などは、この 4 つを支える仕組みと入口である。5 つ目以降のコア機能ではない。

### 作らないもの

- OS・DB・実行環境の権限分離の代わり。同じ権限で任意のシェルを実行できる相手に対しては境界にならない。ccnavi は、逸れていくエージェントと事故に対する柵である
- 人間の判断の代行。承認・レビュー済み・改善の採否を、エージェントが出せる形は作らない
- AI モデル自体の学習。改善するのはルール・作業手順・文書・計画の側である
- ルールが守られる、渡す情報が減る、という保証。そうなるよう設計するが、保証はしない

## How: どう実現するか

### 3 つの原則

製品として共通する原則は 3 つで、設計書の P1〜P14 はこれを実装に落とした決まりである。

1. **必要な情報を、必要なタイミングで届ける**。開始時は作業の前提と入口だけを渡す。理由と手順は関係する場面で、詳しい資料は必要なときに引く。先に詰め込まない
2. **人間の判断を残し、その経路を守る**。承認・レビュー・改善の採否と、ガード自身の変更を、エージェントが代行できる形を作らない。ユーザの判断は、ユーザが直接操作する場所で受ける
3. **作業とレビューを単一 PC・単一セッションに閉じ込めない**。チケットとマーカーはブランチに載せ、レビューはホスト上で受ける。手元の対話セッションも、終われば消える自動実行も同じ道で扱う

### 考え方

| 考え方 | 中身 |
|---|---|
| 判定はモデルの外で行う | ルールを読んでエージェントが自発的に守ることには頼らない。hook の処理がコンテキストの外で判定する |
| 拒否は誘導と一緒に返す | 止めるだけだと、エージェントは別の表記で打ち直す。止めた理由と代わりの手段を名指しで返す |
| 失敗の向きは非対称 | 誤検知はエージェントが一手止まるだけで、理由が返れば直せる。素通りは強制そのものを無意味にし、気づけない。迷ったら止める。ただし、設定 1 つの破損で回復手段まで奪う形は作らない |
| 宣言された制約は緩められない | チケットは絞る向きにだけ働く。承認された範囲の外は止め、中は聞かない |
| 逸脱は必ず見せる | 委ねた回も、既定に落ちた回も、見られなかった回も記録に残す |
| 親のコンテキストは清潔に保つ | 親は計画・判断・報告を受け持ち、作業は子に切り出す |
| 分類と危険度は事前に定義する | 作業の種類と、リスクの高い作業は先に決めておく。計画では選ぶだけにし、一定以上のリスクは人間のレビューを必須にする |
| 流れはテンプレートとして貯める | 一連の作業の流れを蓄積し、次のタスクで再利用する |
| 状態は見える形にする | チケットの状態や承認待ちを、VS Code の拡張で視覚化する |
| 育てる | 記録と振り返りから改善候補を出し、採るかどうかは人間が決める |
