# ccnavi の思想

ccnavi の根底にある考え方を書く。要件書・設計書・ADR は、ここに書いた考え方を実装と約束に落とした下位の文書である。
人間がスライドで通して読むための版は [01_idea/index.html](01_idea/index.html) にある（中身はこの文書と同じ）。

この文書はアプリの土台なので、ユーザが依頼しない限り直さない。機能の追加や仕様の変更では動かさず、要件書・設計書・ADR を直す。
考え方そのものが変わるときだけ、ユーザの依頼を受けてここから直し、下位の文書を追従させる。

## 一文で言うと

エージェントに任せる範囲を広げながら、人間の判断と目が届く道を失わせない。そのために、モデルの外にある仕組みで止め、誘導し、記録する。

## 全体像

ccnavi は、Claude Code を使った開発を、ルール・チケット・必要時の情報参照・振り返りで支えるツールである。
Claude Code の hook でツール呼び出しを止め、止めた理由と代わりの手段を返すガードが出発点で、いまは作業を合意からレビューまで進め、記録から決まりを良くするところまでを受け持つ。

課題は 7 つある。課題ごとに、Why・What・How を次の節に書く。

| # | 課題 | What（要点） |
|---|---|---|
| 1 | 指示を緻密に書いても、エージェントは希望どおりに動かない | 外れを hook で検知し、ガイドを添えてやり直させる。hook を作る手間を軽くする |
| 2 | エージェントは、目的のために制約を突破しようとする | 守る対象はプロジェクトが決め、あとは合意に委ねる。逸れたら人間の目に触れさせる |
| 3 | 厳密なレビュー管理が要るが、作業は複数の PC・セッションに散る | issue・マージリクエスト・ブランチを 1 対 1 対 1 で紐づけ、チケットの動きを制御する |
| 4 | 複数のプロジェクトを、共通ルールとプロジェクトのルールで管理したい | ルールを git で管理し、共通ルールをプロジェクト側へ同期する |
| 5 | 作業の分け方・範囲・レビューの場所を、計画で決めて進めたい | 分類は事前に定義し、計画で選ぶ。承認された計画のとおりに進める |
| 6 | リスクの高い作業は、人間が必ず見る | リスクの高い作業を事前に定義し、一定以上は人間のレビューを必須にする |
| 7 | 同じ流れを毎回作り直し、いまの状況も見えにくい | 流れをテンプレートとして蓄積して再利用し、状態を VS Code の拡張で見せる |

これらをまとめた、4 つのコア機能がある。

| コア機能 | 何をするか | 主な課題 |
|---|---|---|
| ルールによる作業のガードとガイド | ツール実行とファイル操作をルールに照らして判定し、止める・確認する・注意点を伝える。拒否には代わりの手段を添える | 1、2 |
| チケットによる作業・レビュー管理 | 作業の目的・範囲・計画を合意し、承認、フェーズ、レビュー、指摘への対応を経て、合意した作業をレビューまで進める | 3、5、6、7 |
| ドキュメント・スキルの検索と必要時の参照 | 文書と作業手順を最初から全部は渡さず、目録と索引で絞り、本文は必要になったときに読ませる | 1、4 |
| 記録と振り返りによるルール・作業手順の改善 | 判定の記録と気づきから改善候補を見つけて提案し、人間が採ったものを次の作業に活かす | 1、7 |

判定の記録、dry-run、診断、ワークツリー、リモート経由の共有、拡張などは、この 4 つを支える仕組みと入口である。5 つ目以降のコア機能ではない。

## 課題ごとの Why・What・How

### 課題 1: 指示を緻密に書いても、エージェントは希望どおりに動かない

**Why**

- たとえば「hello と尋ねられたら、必ず answer.md に『こんにちは』と書く」スキルを作っても、エージェントが必ず従うとは限らない
- LLM の答えは確率的で、100% に近づけることはできても、絶対にはならない
- スキルそのものが使われないこともある

**What**

- 想定外の挙動を検知し、ガイドを添えて、やり直させる
- 外れる確率が 1% の LLM でも、外れを検知してやり直させれば、ほぼ希望どおりに動かせる
- hook を作る手間が重いと、誰も作らない。作る手間を軽くする仕組みも作る

**How**

- 判定と案内は、モデルのコンテキストの外で動く hook の処理が行う。エージェントが自発的に守ることには頼らない
- 検知と案内は、ルールとして宣言する。hook そのものを自作しなくてよい
- 案内は、起きた時点の危険と失敗に対して、その場で返す。最初に決まりを詰め込まない

### 課題 2: エージェントは、目的のために制約を突破しようとする

**Why**

- 作業に必要だと判断すると、禁止された操作を突破しようとする。悪意はなく、「hook が邪魔なので外す」「deny が厳しいので緩める」を、目的を達成しようとして普通に選ぶだけである
- 任せる範囲を広げるほど、人間が一手ずつ見ることはできなくなる
- 既存の防ぎ方には 4 つの穴がある
  - 設定のパターン一致はコマンドの構造（連鎖・サブシェル・リダイレクト）を見ないので、複合コマンドの後段が素通りする
  - プロンプトに書いた禁止は、守られる確率を上げるだけで 0 にはならない
  - 権限を静的に固定すると、広く開けるか毎回確認するかの二択になる。広く開ければ守れず、毎回確認すれば承認が形骸化する
  - 拒否の根拠がエージェントの書き換えられる作業ツリーの中にある

**What**

- 守る対象はプロジェクトが決め、それ以外は作業ごとの合意（チケット）に委ねる。委ねた先で逸れたときは、人間の目に触れさせる
- これで、広く開けるか毎回確認するかの二択を崩す

**How**

- 拒否は、止めた理由と代わりの手段を一緒に返す。止めるだけだと、別の書き方で打ち直される
- 失敗の向きは非対称である。誤検知は一手止まるだけだが、素通りは気づけない。迷ったら止める。ただし、設定 1 つの破損で回復手段まで奪う形は作らない
- 宣言された制約は緩められない。チケットは、絞る向きにだけ働く
- ガード自身（hook の登録・ルール・実行ファイル）を守る
- 委ねた回も、既定に落ちた回も、見られなかった回も、記録に残す

### 課題 3: 厳密なレビュー管理が要るが、作業は複数の PC・セッションに散る

**Why**

- チケット作業では、レビューを厳密に管理したい
- 作業は複数台の PC や複数のセッションで進み、手元の対話セッションも、終われば消える自動実行もある

**What**

- チケットをマージリクエストに載せて管理し、チケットの動きを制御する
- issue・マージリクエスト・ブランチは 1 対 1 対 1 で紐づけて進める。どれか 1 つを見れば、残りの 2 つと作業の状態へたどれる

**How**

- チケットとマーカーは、親のブランチに載せる。レビューはホスト上で受ける。同期は操作の時点で行う
- 承認・レビュー済みの合図は、人間が直接操作する場所（端末・ボード・Chrome 拡張）で受ける。エージェントが代行できる形は作らない
- 作業は子のワークツリーで行い、親は計画・判断・報告に徹する

### 課題 4: 複数のプロジェクトを、共通ルールとプロジェクトのルールで管理したい

**Why**

- Claude Code 専用のワークスペースの下にプロジェクトを clone し、共通ルールをまとめて管理する使い方がある
- 各プロジェクトのディレクトリで Claude Code を起動する使い方もある
- 2 つの使い方は、同じチームに共存する

**What**

- どちらの使い方でも、誰もが同じルールで作業できるようにする

**How**

- ルールは共通とプロジェクトの 2 層に分け、判定は両者の和で決める
- ルールも git で管理する。ワークスペースの共通ルールを、プロジェクト側にも常に同期する。写しが無くても、ccnavi は動く

### 課題 5: 作業の分け方・範囲・レビューの場所を、計画で決めて進めたい

**Why**

- どう作業を分割するか、どの範囲を直すか、どこでレビューするかは、作業を始める前に決めたい
- 計画のたびに分類を考え直すと、ぶれる

**What**

- 計画のときに、分割・範囲・レビューの場所を決め、人間が承認した計画のとおりに作業する
- 作業の分類は事前に定義しておき、計画では、その中から選んで提案する

**How**

- 計画は、親と子のチケット（目的・範囲・フェーズ・レビューの位置）として書き、人間が承認する
- 承認された範囲の外は止め、中は聞かない。計画の変更は、改版の提案に限る
- 作業の分類は、フェーズの定義として持つ

### 課題 6: リスクの高い作業は、人間が必ず見る

**Why**

- すべての作業を同じ重さでレビューすると、人間が追いつかない
- 重く見るべきものを、人間の勘だけに頼って選ぶとぶれる

**What**

- リスクの高い作業を事前に定義する
- 一定以上リスクの高い作業は、人間のレビューを必須にする

**How**

- リスクは、実績の差分（実際に変えたもの）に配点して測る
- 高いものは、レビューが済むまで先へ進めない

### 課題 7: 同じ流れを毎回作り直し、いまの状況も見えにくい

**Why**

- 一連の作業の流れ（ワークフロー）は、似た形で何度も現れる。毎回ゼロから計画すると、手間もぶれも増える
- チケットの状態や承認待ちは、文字だけでは追いにくい

**What**

- 流れをテンプレートとして蓄積し、次のタスクでも再利用できるようにする
- VS Code の拡張で、状態を見える形にする

**How**

- 完了した計画をテンプレートとして貯め、新しい計画を提案するときに使い回す
- 記録と振り返りから改善候補を出す。採るかどうかは人間が決める
- 拡張のボードで、チケットの状態・承認・レビューを見せ、人間が判断する場所にもする

## 共通の原則

課題ごとの How に共通する原則は 3 つで、設計書の P1〜P14 はこれを実装に落とした決まりである。

1. **必要な情報を、必要なタイミングで届ける**。開始時は作業の前提と入口だけを渡す。理由と手順は関係する場面で、詳しい資料は必要なときに引く。先に詰め込まない
2. **人間の判断を残し、その経路を守る**。承認・レビュー・改善の採否と、ガード自身の変更を、エージェントが代行できる形を作らない。ユーザの判断は、ユーザが直接操作する場所で受ける
3. **作業とレビューを単一 PC・単一セッションに閉じ込めない**。チケットとマーカーはブランチに載せ、レビューはホスト上で受ける

## 作らないもの

- OS・DB・実行環境の権限分離の代わり。同じ権限で任意のシェルを実行できる相手に対しては境界にならない。ccnavi は、逸れていくエージェントと事故に対する柵である
- 人間の判断の代行。承認・レビュー済み・改善の採否を、エージェントが出せる形は作らない
- AI モデル自体の学習。改善するのはルール・作業手順・文書・計画の側である
- ルールが守られる、渡す情報が減る、という保証。そうなるよう設計するが、保証はしない
