# 拡張の使い方

ccnavi には、チケットの状態を見て人の操作を受ける拡張が 2 つある。どちらも判定は実行ファイルが行い、拡張は見せて、ユーザが押した操作を実行ファイルに渡すだけである。
作業中のエージェントのセッションへプロンプトを送り込む手段は持たない。

| 拡張 | 使う場面 | README |
|---|---|---|
| VS Code の「ccnavi ボード」 | 手元の VS Code で、チケットの進み具合を見る。承認、レビューで残った指摘への対応、ルール・リスク・フェーズ定義を画面で直す。不具合の再現を録画・スクリーンショット・ログで zip にまとめる | [extensions/vscode/ccnavi-board/README.md](../../extensions/vscode/ccnavi-board/README.md) |
| Chrome の「ccnavi 承認ボード」 | 作業者の環境の外で、ブラウザと PAT だけで、承認とレビュー済みをリモートの親のブランチへ書く。issue から親のブランチを始める | [extensions/chrome/ccnavi-approval/README.md](../../extensions/chrome/ccnavi-approval/README.md) |

組み立て方・入れ方・試験の手順は、各拡張の README にある。このページは、入れたあとに何ができるかを書く。
VS Code からワークツリーを見えるようにする設定は[導入と配布](install.md)にある。

## VS Code の ccnavi ボード

必要なもの（VS Code の版、ccnavi の実行ファイルを探す順、設定のキー）は[拡張の README](../../extensions/vscode/ccnavi-board/README.md)の「必要なもの」にある。
入れ方は同じ README の「組み立てと導入」にある。

チケットがどのワークツリーでどこまで進んでいるかは、この拡張で見られる。

### 案内

拡張の版が変わって最初に起動したとき、左パネルの案内（VS Code のウォークスルー）が開く。左パネルのタイトルバーの「?」でも開ける。案内からは、プロジェクト管理とチケット管理の基本の案内を続けて見られる。チケット制御が無効のワークスペースでは、プロジェクト管理の基本の案内だけである。
各画面は、初めて開いたときに吹き出しの案内が出る。見直すときは、画面の右上の「?」を押す。

### 承認

承認はボードに承認待ちの一覧を見せ、ユーザが押すと、承認したものがコミットされて push される。
一覧を見せたあとに提案の中身が変わっていたら、承認は通らず、最新の一覧を表示し直す。

### 残った指摘

レビューで残った指摘は、フェーズ行の［レビュー完了］で指摘ごとに対応方針を選ぶ（ターミナルでは `ccnavi-user-decide.sh`）。レビューの流れは[レビュー](review.md)にある。

`close-early` はボードに置かない。ターミナルで `ccnavi-user-close-early.sh` を打つ。

### バグ報告

拡張の不具合を報告するときは、サイドパネルのタイトルバーの虫のアイコン（配色のアイコンの横）を押し、不具合を再現してからステータスバーの「再現中: 終了」を押す。
途中の画面は、ステータスバーの「スクリーンショット」のボタンか、ボードのタイトルのカメラのボタンで何枚でも撮れる（再現を促す通知は時間が経つと隠れるが、この 2 つは報告の間ずっと出ている）。終えると `logs/bug-report/bug-report-<時刻>.zip` に、録画の gif・スクリーンショット・その間の診断ログ（`logs/diag/`）がまとまる。
録画には ffmpeg が要る（Windows・macOS・WSL）。ffmpeg が無ければ録画だけを省く。画面に映ったものはそのまま入るので、渡す前に中身を確かめる。詳しくは[入口とコマンド](../../extensions/vscode/ccnavi-board/docs/requirements/commands.md#バグ報告)にある。

### ルール管理画面

ルールファイルを画面で直し、保存する前に判定を試せる。

- 編集する 1 本（共通・ワークスペース・プロジェクト）は切り替えられる。共通+ワークスペース、共通+プロジェクトの統合結果は読み取りで見られる
- 判定は ccnavi の試験（[設定の確かめ方](check.md)）と同じ実行ファイルが行う
- hook の一覧は `.claude/settings.json` と `settings.local.json` を読むだけで書き換えない
- 作業中のチケット（承認済みチケットが `doing`）がある間は保存できない（セッションの途中で判定が変わるのを避けるため）

ルールの書き方は[ルールの書き方](rules.md)、判定の試し方は[設定の確かめ方](check.md)にある。

### リスク管理画面

実績で測るリスクの配点（`.ccnavi/config/common/risks.yml`、ワークスペースとプロジェクトの `.ccnavi/config/project/risks.yml`）の境目の点と項目を画面で直せる。

- 編集する 1 本は切り替えられ、共通+ワークスペース、共通+プロジェクトの統合結果は読み取りで見られる
- 保存の前に、共通の設定と合わせて検証する
- 点を数えるのは実行ファイルで、拡張は差分を数えない
- ファイルが無ければ組み込みと同じ値で作れる
- `CCNAVI_TICKET_CONTROL` が `disable` なら入口ごと出ない

### フェーズ管理画面

フェーズ定義を画面で直せる。対象は共通レイヤー（`.ccnavi/config/common/phases.yml`）、自身のレイヤー（`.ccnavi/config/project/phases.yml`）、プロジェクトのレイヤーの 3 種。
共通レイヤーを開いたときは、その定義をそのまま編集する。プロジェクトのレイヤーは、プロジェクト管理画面から開く。

- 保存の前に検証し、提案がワークツリーに在る親の計画が指すフェーズ定義を消すとそこで止まる（承認済みチケットの計画は照合しない。チケット制御が disable なら照合は走らない）
- 子の範囲が上限に収まるかを判定するのは実行ファイルで、拡張はフェーズ定義を書く場所だけ
- 共通レイヤーの `phases.yml` が読めなければ画面の上部に error を出す。組み込みの既定も雛形も無い。フェーズ定義は共通レイヤー・自身のレイヤー・プロジェクトのレイヤーのどれかに置く
- `CCNAVI_TICKET_CONTROL` が `disable` なら入口ごと出ない

フェーズ定義は[チケット](tickets.md)の「フェーズ」にある。

## Chrome の ccnavi 承認ボード

承認者がブラウザと PAT だけで、リモートのブランチの承認待ちを見て、承認・レビュー済みを親のブランチへ書き、issue から親のブランチを始める。
GitHub と GitLab の、ワークスペースとプロジェクトのリポジトリを扱う。

承認者の操作を、作業者の開発環境やセッションの外に置くための入口である。同期はリアルタイムではなく、
書いた結果は作業側の次の fetch / sync で届く（[複数人・別 PC・別セッション](multi-pc.md)）。
組み立て方と試験の手順は[拡張の README](../../extensions/chrome/ccnavi-approval/README.md)にある。
