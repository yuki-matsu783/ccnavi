# レビューの依頼と確認

見る場所が `mr` のフェーズでは、エージェントがマージリクエストにレビューを依頼し、ユーザが指摘を付け、指摘が片付いたらレビュー済みにする。
この文書は、その間にユーザが何を見て何を打つかをまとめる。チケット全体の流れは [チケットによる作業範囲の使い方](tickets.md)。

## 依頼から確認までの流れ

エージェントが `ccnavi-review.sh` の `request`・`confirm`・`comment` を打つ。

- `request` は、フェーズが終わっていて、すべての子が親に合流済みで、未コミットが無く、push 済みであることを確かめる。1 つでも欠けたら全件を列挙して何もしない。通れば、親のブランチの open の MR に依頼コメントを投稿する。MR は作らない（作るのは `ccnavi-start.sh`）
- 依頼後に親の HEAD が動いたら、レビュー済みになる前なら `request` を打ち直せる
- `confirm` は、依頼したときから変わっていなくて push 済みであることを求め、今残っている未解決のスレッドを数える。未解決も変更要求も無ければレビュー済みになり、そのフェーズの `review/` の子が `done/` へ動く。残るなら一覧を返す
- `comment` は、このセッションで受けた承認や判断を MR のコメントにコピーする

## ELI5 を見て、crit で指摘を付ける

`request` には ELI5 の HTML が付く。変更の目的・何が変わるか・リスクを専門用語なしで書いた 1 枚の HTML で、マージリクエストの差分に載る。
依頼の投稿が済むと、エージェントは次の形の案内を出す。

```
ELI5 を見る: ユーザがターミナルで cd <ルート> してから crit review <相対パス> を打ち、… crit push <番号> で …
```

ユーザはその手順を手元のターミナルで打つ。

1. `crit review <相対パス>` で HTML のソースの行に指摘を付ける
2. `crit push <番号>` でマージリクエストの行のスレッドとして送る

- GitHub は `gh`、GitLab は `glab` が要る。crit・gh・glab が無い環境でも、依頼そのものは通る
- GitLab での `crit push` は未確認である
- `crit <相対パス>` だけだと描画のプレビューになり、そこで付けたピンは送られない
- 手元のチェックアウトがマージリクエストの先頭より古いと行の番号がずれるので、先に合わせる。差分の外の行がホストに拒まれるかは未確認である
- 送った指摘はユーザのスレッドなので、`confirm` が未解決として数えて止め、`decide` で 1 件ずつ行き先を選べる

依頼の後に ELI5 の HTML だけを直したときは、打ち直しが要らない。push すれば `confirm` は止まらない。
直す前の行に付けたスレッドは残るので、ユーザが resolve する。ほかのファイルと一緒に直したときは、`request` の打ち直しが要る。
`wip/` は `ready` の前に丸ごと消すので、squash した成果物に HTML は残らない。

## レビュー済みにする場所

レビュー済みにする場所は 4 つある。

- ターミナルの `ccnavi-review.sh confirm --phase <N>`
- VS Code のボードの［レビュー完了］。残った指摘を読み、0 件なら［レビュー済みにする］で `decide` と同じ内容を記録する
- Chrome 拡張のボードの「レビュー済み」。親のブランチへマーカーと `done/` への移動を 1 コミットで書く。`confirm` と同じ判定を通る
- 下の `decide`。指摘が 0 件、またはどれも直さないときにレビュー済みにする

ユーザが子を手で `done/` に動かして commit・push した場合は、`confirm` が移動の前に付いた未解決の指摘を受け入れ台帳に足して確定する。
移動の後に付いた指摘が残れば確定せず、変更要求があれば保留する。

## 残った指摘への対応方針（decide）

残った指摘の対応方針はユーザが決める。ボードの［レビュー完了］か、ターミナルで `ccnavi-user-decide.sh <N>` を打つ。

- **対応しない（受け入れて進む）。** スレッドに受け入れて進む旨の返信を残して解決済みにする。返信か解決に失敗したら何も書かずに止まる。受け入れは親全体に該当し、他の人が開き直せば未解決として数える
- **このフェーズで直す。** 直す指摘をコピーした続きの子を、同じフェーズの番号で `.ccnavi/approved/doing/` に直接置く。フェーズは開き直り、マーカーは消える
- **issue に回す。** 受け入れたうえで、その指摘を載せた issue を作る。いつでも選べる

直す指摘が無く、見せたあとに増えた指摘（追加分）も無ければレビュー済みにする。1 件でも直すなら見た子を `done/` へ動かし、マーカーは付けない。
追加分は止めずに未対応のまま残し、次の `decide` で扱う。決めた内容は sh がコメントにコピーする。
途中で失敗した送信は `ccnavi-user-decide.sh --resume <操作ID>` で続きを送れる。

ボードの［レビュー完了］では、何も選ばなければ全件が「このフェーズで直す」になる。指摘が 2 件以上なら、一覧の上の「すべて」の行で全件を同じ対応方針にまとめて切り替えられる。個別の選び直しもできる。
Chrome 拡張のボードにも、同じ内容を決める「残った指摘の行き先を決める」画面がある。拡張は、先にホストへ issue・返信・解決を書く。そのあと、親のブランチへ記録を 1 コミットで送る。
ボードの経路はターミナルを求めない代わりに、見せた指摘の内容が変わっていないことを確かめてから記録する。エージェントが同じ形を打つ経路は止まる。
「このフェーズで直す」を選んだスレッドは、続きの子で直したあと、ユーザがホスト上で確かめて resolve する。エージェントは fix を理由に resolve しない。

### 変更要求が出ているとき

変更要求のレビューが出ている間は、どの経路でもレビュー済みにできない（判定はホストを問わず同じ）。案内はホストごとに出し分ける。
表示される文面は次のとおり。

| ホスト | 案内 |
|---|---|
| GitLab | 変更を依頼（Request changes）が出ています。解除はレビュアーの承認（Approve）で行います。作成者によるレビューの再依頼（Re-request review）で状態が戻るかは未検証です。再依頼した場合も、ccnavi で状態を取り直して確かめます |
| GitHub | 変更要求（Changes requested）が出ています。解除はレビュアーの Approve か、レビューの dismiss で行います |

## 必要な道具と認証

リモートを読み書きするのは `ccnavi-review.sh` で、ccnavi の実行ファイルはネットワークに出ない。

- 道具は `gh` / `glab` があればそれ、無ければ `curl` と `GITHUB_TOKEN` / `GITLAB_TOKEN`。どちらも無ければ止まる。`jq` が要る
- GitHub と GitLab は origin の URL で見分ける（`github.com`・`ghe.com`・`*.ghe.com` が GitHub、それ以外は GitLab）
- origin の表記はポートと scheme をそのまま使う（`http://localhost:8929/g/p.git` なら `http://localhost:8929/api/v4`）。URL に埋めた資格情報は読み飛ばし、出力では伏せる
- push の認証は、gh / glab でログイン済みならそのまま通る。それ以外は git の設定側（Git Credential Manager か `credential.helper`）に置く。git のラッパースクリプトは環境変数での差し替えも認証画面も使えない
- origin の読み方が合わないときは `sh .ccnavi/scripts/ccnavi-review.sh origin` で、ホスト・scheme・API の URL・使う道具を確かめる

## 親を閉じるとき

最後のレビューが済んだら、親を `finish` で閉じて push し、`ready` で Draft を外す。マージはユーザが行う。この順、片付け、早めに閉じる方法は
[チケットによる作業範囲の使い方](tickets.md) の「親を閉じる」にある。
