# hook の挙動

ccnaviが止めたとき、報告したとき、止めなかったときに、画面で何が起きているかを読むための文書である。
環境変数とhookの登録は [settings.md](settings.md)。実行前に何が止まるかは [rules.md](rules.md)。

## 動作モード

| 値 | 挙動 |
|---|---|
| `enable` | 判定し、`deny`なら止め、`ask`ならユーザに確認を出す。指定が無いときはこれ |
| `dry-run` | 同じ判定を行い、一般の保護は呼び出しに手を出さず「`enable`なら何をしていたか」を伝える。チケットの関門（状態の操作・範囲・レビュー待ち・承認済みの置き場と操作記録への書き込み・サブエージェントの状態操作）と、それを外す抜け道をふさぐ補助の保護（生のgit・環境変数の指定など）は、`dry-run`でも止める |
| `disable` | 判定しない |

`disable`は`.claude/settings.json`に書いても有効にならない（その指定を無視し、理由を出す。`ccnavi --lint`も指摘する）。エージェントが書き換えられるファイルなので、
監視される側が監視を止められないようにしている。`disable`にするときはセッションを起動する側の環境から渡す。
読めない値は報告して`enable`として扱う。

## ツール実行後チェック

実行前チェックは引数しか見ないので、引数に現れない書き込み（ビルドの出力、スクリプトの内部、読み切れないシェル構文）は
止められずに通る。実行後チェックは、走ったあとのワークツリーを`git status`で読んでそれを拾う。

保護領域は別に宣言しない。`match`に`Write` `Edit` `NotebookEdit`のどれかを含むルールが、そのまま保護領域の宣言になる。
記録とstateの置き場は最初から保護領域に入らない。チケットの置き場では、ccnaviのサブコマンドが書いたと内容から見分けられる変更だけが外れる。
作業範囲・親・フェーズが変わっていれば報告する。

```
[ccnavi] POST_VIOLATION (rule: guard-config)
path: .ccnavi/config/common/probe.json (?? / new)
after: Bash(npm run build)
undo: rm -- ".ccnavi/config/common/probe.json"
ガード自身のルールです。エージェントの判断で書き換えず、変更が要る理由を伝えてユーザに依頼してください。
```

呼び出しは取り消せないので、`enable`ではexit 2 と標準エラーで差し戻し、`dry-run`では`additionalContext`で報告だけする。
戻す手順は対象ごとに 1 つ。

| 変更の種類 | 戻し方 |
|---|---|
| 中身が変わった・消えた | `<git> restore --staged --worktree -- <path>` |
| 追跡されていないものが現れた | `rm -- <path>` |
| 索引に足された状態で現れた | `<git> restore --staged -- <path> && rm -- <path>` |
| 横で作業する記録が有効なユーザのチェックアウトで見つかった変更 | 戻す手順を出さない。「出所不明の変更（ユーザか別のセッションの可能性）」として報告し、戻すかはユーザが決める |

`<git>`は、ワークスペースルートにgitのラッパー（`.ccnavi/scripts/ccnavi-git.sh`）があればその実パス（`sh <ルート>/.ccnavi/scripts/ccnavi-git.sh`）になる。
無ければ、gitの操作はユーザに頼む文になる（生のgitは組み込みでいつも止まるため。[git.md](git.md)）。

### 前から在った変更は原因にしない

セッション前からある変更（他のセッションやユーザの書きかけ）は、初めて見たときに記録する。以降は新しく現れたものだけを差し戻す。
前からある変更は`POST_PREEXISTING`として 1 度だけ伝える。戻すなと明示し、自動復元の対象にもしない。
同じ場所でも「変わった」の次に「消えた」が来れば、もう一度伝える。

### ターンの終わりにユーザへ報告する

`Stop`に登録すると、そのターンで変わった保護領域を戻す手順付きでユーザに報告する。
比べる相手は`UserPromptSubmit`で記録した状態なので、`UserPromptSubmit`を登録していないと`Stop`は何も報告しない（記録には`no-turn-baseline`が残る）。
ここでは戻さず、`CCNAVI_MODE`も見ない。見えたことを伝えるだけなので、`dry-run`でも報告する。

同じ`Stop`で、ccnaviが次の一手を促してターンを止めることがある。モデルには理由と次のコマンドが渡り、ユーザには保護領域の報告が同じ応答で届く。

- チケット作業で`finish`を打たずに終えようとしたとき（`NUDGE_TICKET_FINISH`）。まだ続けるなら、理由を書いてから終える
- レビューの依頼までの道の途中で、ユーザの許可を待って終えようとしたとき（`NUDGE_TICKET_REQUEST`）。この道にユーザの許可は要らない
- 全体計画のレビューが済み、フィードバック計画が決まらないまま終えようとしたとき（`NUDGE_TICKET_FEEDBACK`）。改版（`feedback: []` か対応のフェーズ）を書いて `propose` で送り、ユーザに承認を頼む
- 終わったサブエージェントが、範囲外の変更を残したか範囲を確かめられないまま終わったとき（`NUDGE_SUBAGENT_OUTCOME`）
- チケットに結び付かない直接作業のワークツリーに、取り込み先に入っていないコミットがあるのに`integrate`を打っていないとき（`NUDGE_INTEGRATE`）。差分を確かめてもらい、了承を得てから取り込む。直接作業のコミットは`integrate`の直前にまとめて打つので、未コミットの変更だけのときと、`integrate`のあとで確定を待っているときは促さない
- `match: Stop`のルールが渡す回（`NUDGE_STOP_RULE`。[rules.md](rules.md)）

1 回の`Stop`で止める理由は 1 つで、どの促しも、同じ状態では 1 回だけである。`dry-run`でも止める（止めないと文がモデルに届かないため）。

- サブエージェントの結果で促すのは、範囲外の変更を残したまま終わったときと、範囲を確かめられなかったときだけ。正常に終わったとき、差し戻して直ったときは促さない
- 実行中のサブエージェントが居る間は、委任して待つ回なので促さない
- ユーザが`review/`の子を`done/`へ手で動かして共有（commit・push）済みのフェーズでは、依頼までの道の促しが次の一手を`confirm`にして 1 回だけ促す。未共有の移動は促さない
- 続きのターン（Stopの促しを受けて続けているターン）、サブエージェント自身の`Stop`、記録を置けないときは促さない。チケット制御が`disable`のときは、チケットに係る促し（`finish`・依頼までの道・サブエージェントの結果）を出さない

止められたときは、促された内容に従うか、続けるなら理由をユーザに書いてから終える。

同じ`Stop`で、同じ理由で繰り返し止められた呼び出しも並べる（[rules.md](rules.md)の「同じ呼び出しを繰り返し止めたとき」）。

### 自動復元

`CCNAVI_RESTORE_IF_DENY=enable`（既定）のとき、ccnavi自身が戻す。`dry-run`では戻さず、報告に`would-restore`の行を足す。
`disable`では戻さず、その行も出さない。`CCNAVI_MODE=dry-run`のときは、こちらが`enable`でも`dry-run`として振る舞う。

戻す先はコミット済みの内容なので、保護領域に置いた未コミットの変更は失われる。守りたいなら`disable`にするか、宣言を狭める。
現れたファイルは消さずに`logs/state/aside/<日時>/`へ退避し、退避先を報告に載せる。
例外として、直接作業の記録（`ccnavi-direct/<名前>`）が`side_by_side yes`で有効なユーザのチェックアウトは、ユーザが横で編集している前提なので戻さない。
ターンの終わりに「出所不明の変更（ユーザか別のセッションの可能性）」として報告し、判定の記録にも残す。ccnaviの設定ファイルの自己防衛は、この例外の外で戻す。

## コアファイルを守る

実行後チェックはルールファイルから保護領域を決めるので、ルールファイル自身はそこでは守れない。そこで次のものは組み込みで持つ。
`CCNAVI_GUARD_CORE_FILES`が切り替える。

| 対象 | 何が懸かっているか |
|---|---|
| `.claude/settings.json`・`.claude/settings.local.json` | hookの登録そのもの |
| `.ccnavi/config/common/`と`.ccnavi/config/project/`の`rules.yml`・`phases.yml`・`risks.yml`（ワークスペースと各プロジェクトの分も） | 判定の中身そのもの |
| `CCNAVI_ENTRY_PATH`が指すファイルと、この機械のccnaviの実行ファイル | 判定器の実体 |

- 設定ファイルは、ツール実行前と、ユーザの発言時にバックアップを取る。実行後に変わっていればバックアップから戻す（未コミットの編集は残る）
- ユーザの発言（`UserPromptSubmit`）では、その時点の状態を基準に取り直す。ターンの間にユーザが直した・消したものは戻さない。`UserPromptSubmit`に登録しないと、この受け入れが働かず、消したものが次の呼び出しで戻る
- 実行ファイルはセッション開始でバックアップする。`SessionStart`に登録しないと守られない。`CCNAVI_ENTRY_PATH`を指定しなければ対象に入らない。`CCNAVI_ENTRY_PATH`が振り分けのshのときは、PATHにある`ccnavi`の実体も同じように守る
- gitが追跡しているものは、ワークツリーが持つ同じファイルも対象に入る（統合すればそのまま反映されるため）。実行ファイルは除く
- 無いファイルは対象から外れる。無かったところに現れた場合は報告するが、消さない
- `.ccnavi/scripts/`のスクリプトはこの一式に入れない。組み込みの`deny`（`*/.ccnavi/*`）と`CCNAVI_RESTORE_IF_DENY`が受け持つ

戻す前に止める側も組み込みで持つ。この機能が有効な間、これらのファイルと`.ccnavi`の下、記録とstateの置き場へシェルから書き込む形は、ルールに書いていなくても拒否される。
ルールファイルが不正で組み込みの既定を使っている間も同じである。`rm -rf .ccnavi`や`mv .ccnavi .ccnavi.bak`も止まる。
`ccnavi-git.sh`を通しても同じ場所は消せない。名指しのツール（`Write` / `Edit` / `NotebookEdit`）からも守られる。期待する判定のファイル`.ccnavi/config/common/rule-expectations.yml`も同じである。

止めるのは書き込みの形と場所の組で、場所の名前が出ただけでは止めない（`cat .ccnavi/config/common/rules.yml`や`git add <パス>`は通る）。
`builtin:guard-`で始まるidはどのレイヤーのルールファイルにも書けない（書けばerror。`--lint`も指摘する）。外したいならenvでこの機能ごと切る。

止まったときは、エージェントに回避させない。ユーザがターミナルで自分で打つ。承認済みチケットの置き場（`.ccnavi/approved/`）やレビュー待ちの置き場（`wip/proposals/review/`）を
エージェントがラッパーで消す形も止まるので、レビュー済みのマーカーを消す`rm`や、レビュー待ちの提案を外す操作は、ユーザがターミナルで打つ。
守る場所を直したいときは、エージェントが下書きを`wip/handoff/`に置き、ユーザが`ccnavi-user-handoff.sh`で取り込む（[配布するスクリプト](scripts.md)）。

`PreToolUse`の登録ごと消された場合はccnaviが一切動かない。hookの登録をhook自身で守ることはできない。

## 見えないもの

実行後チェックが何も言わなかったときの原因は、次のとおりである。

| 見えない | なぜ |
|---|---|
| `.gitignore`に入っているファイル | `git status`に出ない |
| gitのワークツリーの外 | 実行後チェックはリポジトリの中だけを見る |
| この呼び出しが触っていないツリー | 呼び出しごとに見るのはワークスペースルートと、この呼び出しの行き先（Bashはcwd）が属するツリーだけ。ターンの区切り（`UserPromptSubmit`と`Stop`）では全部のツリーを見る。子のワークツリーは、サブエージェントの終了時にも見る |
| `PostToolUseFailure`を登録していないときの、失敗したツール呼び出しの副作用 | `PostToolUse`は成功した呼び出しの後にしか走らない。失敗した呼び出しは`PostToolUseFailure`が同じ照合で見る（失敗する前に変えていることがあるため。登録は [settings.md](settings.md)） |
| `Read` `Grep` `Glob` `WebFetch` `WebSearch`の直後 | 次の書きうるツールの直後に確かめる（遅れであって見落としではない） |
