# ワークツリーで作業する

CLAUDE.md「ソースコード編集方法」の詳細。ワークツリーを切るとき、`<統合先>` へ戻すとき、片付けるときに読む。

## 基本

- 他セッションでも並行して作業が進められるよう、ワークツリーを切ってから手を付けること
- git は直接呼ばず `ccnavi-git.sh` を通す。通る形はそのスクリプトの `--help` に出る
- **sh の綴りは、どこから打つかで変わる。** `.ccnavi/scripts/` はワークスペースにしか無い

  | cwd | 綴り |
  |---|---|
  | ワークスペースルート | `sh .ccnavi/scripts/ccnavi-git.sh ...` |
  | ワークツリーの中 | `sh ../../../.ccnavi/scripts/ccnavi-git.sh ...` |
  | `projects/<名前>` の中 | `sh ../../.ccnavi/scripts/ccnavi-git.sh ...` |

  拒否の文面が案内する綴りは `{root}` から始まる絶対パスで出る。そのまま打てばどこからでも通る

## 他セッションの作業を踏まないために

- 自分のワークツリーの外（ワークスペースルートや他のワークツリー）に未コミットの変更があったら、
  それは他セッションのものとして扱う。
- 他セッションの書きかけを、コミットも、ブランチの移動も、`reset` もしない。
  ビルドが壊れていても直さない。何が壊れているかを報告して判断を仰ぐ。
- 退避が要るときは `ccnavi-git.sh stash push -u` を使う。消す前に下書きの置き場へコピーも取る
  （自分のワークツリーの中なら `scratchpad/`、無ければワークスペースの外にあるセッションの
  スクラッチパッド）。他セッションのツリーの中には置かない。

## ワークツリーの作り方

- 置き場は**ワークスペースの** `.claude/worktrees/<ブランチ名>`。プロジェクトから切る場合も同じ。
  1 段だけで、その下に階層を作らない
- `ccnavi-git.sh worktree add <行き先> -b <名前> <統合先>` で作る。起点は `<統合先>` の HEAD。
  末尾を省くと今いるブランチが起点になるので、`<統合先>` が `main` のときも省かずに書く
- `<行き先>` は cwd から解かれる。ワークスペースルートからなら `.claude/worktrees/<名前>`、
  `projects/<名前>` の中からなら `../../.claude/worktrees/<名前>`。**間違えると止まり、
  文面が正しい綴りを出す**ので、出たとおりに打ち直せばよい
- `worktree add` に渡せるオプションは決まっている（`-b` `-B` `--reason` `--detach` `--force` など）。
  一覧に無いものは通らない。行き先を取り違えないためで、要るものが出たら利用者に足してもらう
- **プロジェクトのワークツリーは、そのプロジェクトから切る。** `cd projects/<名前>` してから打つ。
  `<統合先>` はそのプロジェクトのブランチであって、ワークスペースの `main` ではない
- `<統合先>` がリモートにしか無いときは、先に `ccnavi-git.sh fetch <リモート> <統合先>` をする。
  これもプロジェクトの中で打つ
- **起点はリモートの最新のデフォルトブランチ**（`origin/HEAD` が指すもの。多くは `main`）。
  セッションの頭の `ccnavi-fetch.sh` が、チェックアウトされていなくても ff で進めるので、
  ワークスペースルートが `main` 以外に居ても揃う（ADR-0060）。進められなかったときは
  「ワークツリーの起点になる ... 」で始まる行が頭に出ている。その行が出ていたら、切る前に
  理由を片付ける（分岐なら人に合流させてもらう、未コミットならそのツリーの持ち主に聞く）。
  セッションが長引いてリモートが進んだときは、`ccnavi-git.sh fetch origin <統合先>` を打ち直す
- 作業が完了したら `<統合先>` へ戻す。コンフリクトして判断に困る場合はユーザに確認する

## `<統合先>` へ戻す

- ワークツリーのブランチが `<統合先>` の HEAD の直上なら fast-forward で入る
- `<統合先>` が先に進んでいたら、ワークツリーの中で `ccnavi-git.sh merge <統合先>` して取り込み、
  衝突を解いてから戻す
- `<統合先>` が保護されていて直接は入れられないなら、マージまでやらない。
- 直接 `<統合先>` に戻した場合は、統合が済んでから `ccnavi-git.sh worktree remove <パス>` と
  `ccnavi-git.sh branch -d <名前>` で片付ける
- マージリクエストに出した場合は、マージを待たず、`ready` で Draft を外した直後にワークツリーを片付ける。
  順は「`ready` → マーカー `.ccnavi/approved/phases/<親>/ready.json` をコミットして push →
  `ccnavi-clean.sh` → `worktree remove`」。`ready` が置くマーカーは push の後に書かれるので、
  コミットせずにワークツリーを消すとマーカーが消える。親に取り込んで閉じた子のワークツリーも、
  このときに外す（前提の検査は子のブランチを引くので、ワークツリーが無くても外れない）
- マージリクエストに出したブランチは消さない。リモートはホストがマージのときに消す（GitHub の
  「マージ後にブランチを自動削除」）。ローカルは squash で入るので `branch -d` が通らず、
  ラッパースクリプトは `-D` を通さない。残ったローカルのブランチは利用者が消す
- `worktree remove` の前に `ccnavi-clean.sh <名前>` で生成物（node_modules・.venv など）を消す。
  Windows では、これが残っていると削除が途中で止まり、消しきれなかったディレクトリが残る。未コミットの変更がある
  ワークツリーでは何も消さずに止まる
