# 要件書・設計書・ADRの書き分け

`docs/`の`requirements`・`design`・`adr`に書くときの決まり。

## 何をどこに書くか

| 文書 | 書くこと | 書かないこと |
|---|---|---|
| 要件書（`docs/requirements.md`・`docs/requirements/**`） | 外から観測できる振る舞い。入力に対して何が出る・起きるか、終了コード、出力、ファイルに残るもの | 内部の作り、関数名、採った理由 |
| 設計書（`docs/design.md`・`docs/design/**`） | 外から観測できない側の設計の振る舞い。モジュールの責務、データの流れ、状態、判定の手順。いまの実装の説明だけ | 経緯（以前はどうだったか）、採らなかった案、なぜそう決めたか |
| ADR（`docs/adr/`） | 設計・実装の経緯。状況、決めたこと、理由、得たもの・失ったもの、採らなかった案 | いまの実装の全体説明（設計書に書く） |

迷ったら、観測できる側かを問う。ユーザやほかのプログラムが入出力だけで確かめられるなら要件書、実装を読まないと分からないなら設計書。
要件書と設計書が食い違っていたら要件書を優先して直す。

## 1つのモジュールで閉じる話はコードに書く

| 書く場所 | 書くこと |
|---|---|
| コードのコメント・docstring | そのモジュールの役割、入出力の契約、内部の処理の理由や注意点。1つのモジュールで閉じる話 |
| 設計書 | 複数のモジュールにまたがる振る舞い（流れ・状態・境界・横断の流儀）と、サブパッケージ間の約束 |
| 要件書 | 外から観測できる約束 |

- ファイル1本ごとの役割は、そのファイル先頭の説明に書く。設計書にファイル単位の表を作らない（サブパッケージや役割のまとまりまで）
- モジュールごとの契約を設計書に書き写さない。コードと二重になる
- モジュールを足したら、先頭の説明を書く。設計書の側は、役割のまとまりが変わるときだけ直す

## コメントの粒度

粒度は3段で決める。周りのコードのコメントの密度に合わせる。

| 場所 | 書くこと |
|---|---|
| モジュール先頭の docstring | 役割を1文。入出力の契約、触る状態と置き場、失敗したときの振る舞い、呼ぶ側との境界（何をしない・何を呼び側に任せるか） |
| 公開する関数・クラスの docstring | 名前と型から読み取れないものだけ。前提条件、戻り値の意味、例外や終了コード、副作用 |
| 手順が複数ある関数の docstring | 処理の流れを番号つきで並べる（呼ぶ先の名前を添える）。コードを開かなくても、入口から出口までの流れが追える |
| 関数の中のコメント | 処理のまとまりごとに、何をするかの概要を1行（長い関数の段落の見出しとして、上から読めば流れが分かる）。理由（なぜそうするか）、落とし穴、順序に依存するところは、そこに足す |

- 概要は段落ごとに1行にする。1行ごとの実況（`i を 1 足す`など、コードを読めば分かること）は書かない
- 経緯（以前は〜だった）、ADRの番号、日付は書かない。経緯はADRに、日付は git の履歴にある
- 設計書や要件書の内容を写さない。ほかの文書に正があるなら、その文書を指す
- 変更したら、同じ変更の中でコメントも直す。コードと食い違ったコメントは、無いより悪い

## 書く前に置き場を決める

書き残したいことが出たら、先に行き先を決める。次の問いを上から順にかけ、最初に当たった行き先に送る。

| 問い | 当たったときの行き先 |
|---|---|
| 決定か（採らなかった案やトレードオフがある） | ADR。1つの決定を1枚にする |
| コード・型・テストを読めば再生成できる事実か（関数の形、項目の一覧、値の上限など） | 書かない。コードが正で、文書には読む場所だけを書く |
| コードが変わるたびに変わるか（処理の細かい順序、内部の変数名など） | 書かない。書くならコードから生成する |
| 安定していて、コードの1か所を読んでも見えないか（全体の構成、責務の分担、横断の流儀、運用の手順、用語） | 設計書 |

ADRと設計書の分かれ目は、決定を1つ切り取るか、全体の整合を1枚にまとめるか。
「この方式を選んだ理由」はADR、「全体がどう噛み合っているか」は設計書。決定が増えたとき、ADRは1枚増え、設計書は中身が追従する。

要件書の側は、外から観測できる約束かだけを問う。観測できないなら要件書には置かない。

迷ったら書かない側に倒す。コードと二重になった記述は、いつか食い違う。

## 写さず、出典を指す

- 値・閾値・一覧は、ほかの文書やコードに正があるなら書き写さず、その場所を意味で指す。写すと、正を直したときに追従しない
- 用語・値・コマンド・手順を変えたら、同じものを書いたほかの文書（要件書・設計書・ADR・`CLAUDE.md`・`docs/claude/`・`.ccnavi/docs/`）を文字列で検索し、同じ変更の中で直す
- 守らせたいことが型・lint・テストで機械的に止められるなら、止める側に持たせ、文書には書かない
- ADRの決定と実装が食い違ったら、新しい1枚で解釈を残す（置き換えの手順は[ADRの README](../adr/README.md)）

## 既存のADRは明示的に指示されたときだけ書き換える

ADRは決めた時点の記録なので、本文を書き換えない。覆すときは新しい1枚を足し、古い側の状態を「置き換え」にする。消さない。
書き換えてよいのは、ユーザが明示的に指示したときだけ。誤字や参照の直しなど小さなものも、指示が無ければ直さず、直したい旨を伝える。
状態の行を「置き換え」にする、一覧に載せる、番号の重複を直す、といったADRの README が定める管理の操作は、この例外に当たる。

## 文書ごとの保ち方

- 設計書に「以前は」「〜に変えた」のような経緯が混ざったら、ADRに移し、設計書にはいまの形だけを残す
- 要件書は、外から見える約束ごとに安定した識別子（`REQ-PRE`のようなID）を持つ。ほかの文書から指すときはIDと項の言葉で指す
- 要件書に関数名・ファイル名・内部の型の名前を入れない。観測できるのは入出力、終了コード、残るファイルまで
- ファイルやスクリプトを1つずつ並べる表は、足すたびに直すことになる。サブパッケージや役割の単位まで粗くし、細かい中身は各ファイルの先頭の説明に任せる。表を残すなら、表と実体の対応をテストで見る
- 作業中の下書き（`wip/`）や計画は、陳腐化する前提で置く。最新に保とうとせず、残す価値があるものは要件書・設計書・ADRに移す

## 日付を書かない

3種類のどれにも日付を書かない。いつ決めたか・変えたかは git の履歴が持つ。
「2026-10-11に決めた」「追記（日付）」のように書くと、文書の側が履歴の写しになり、食い違う。
追記は日付ではなく、何についての追記かを見出しで示す。

書式の細かい決まりは[ADRの README](../adr/README.md)にある。既存のADRに入っている日付は、消すよう明示的に指示されたときだけ消す。

## ADRから要件書・設計書を指すときは意味で書く

要件書と設計書は直されて動く。行数・節番号・表の何行目で指すと、直されたとき対象が分からなくなる。
対象は、読めば何を指すか分かる言葉で書く。

- 文書の名前と、見出しの文言、または項目の名前で指す。例：「設計書の自己防衛の節にある『守る対象』の表」「要件書の`REQ-PRE`の拒否の文言の項」
- 何についての記述かを添える。見出しが変わっても、記述の中身で探し直せる
- 行数、`L123`、`4.6`のような節番号、表の上から何番目、は書かない
- 実装の関数名・ファイル名は、そのADRが決めた対象そのものであるときだけ書く

ADRの番号を要件書・設計書・コメントに書かない決まりは[実行環境とADRの扱い](environment.md)にある。向きが逆で、ADRから設計書を指すのは意味で書く。
