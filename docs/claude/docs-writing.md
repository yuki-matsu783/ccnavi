# 要件書・設計書・ADRの書き分け

`docs/`の`requirements`・`design`・`adr`に書くときの決まり。

## 何をどこに書くか

| 文書 | 書くこと | 書かないこと |
|---|---|---|
| 要件書（`docs/requirements.md`・`docs/requirements/**`） | 外から観測できる振る舞い。入力に対して何が出る・起きるか、終了コード、出力、ファイルに残るもの | 内部の作り、関数名、採った理由 |
| 設計書（`docs/design.md`・`docs/design/**`） | 外から観測できない側の設計の振る舞い。モジュールの責務、データの流れ、状態、判定の手順。いまの実装の説明だけ | 経緯（以前はどうだったか）、採らなかった案、なぜそう決めたか |
| ADR（`docs/adr/`） | 設計・実装の経緯。状況、決めたこと、理由、得たもの・失ったもの、採らなかった案 | いまの実装の全体説明（設計書に書く） |

迷ったら、観測できる側かを問う。ユーザやほかのプログラムが入出力だけで確かめられるなら要件書、実装を読まないと分からないなら設計書。
要件書と設計書が食い違っていたら要件書を優先して直す。

## 日付を書かない

3種類のどれにも日付を書かない。いつ決めたか・変えたかは git の履歴が持つ。
「2026-10-11に決めた」「追記（日付）」のように書くと、文書の側が履歴の写しになり、食い違う。
追記は日付ではなく、何についての追記かを見出しで示す。

書式の細かい決まりは[ADRの README](../adr/README.md)にある。既存のADRに入っている日付は、触るついでに消す。まとめて書き換えない。

## ADRから要件書・設計書を指すときは意味で書く

要件書と設計書は直されて動く。行数・節番号・表の何行目で指すと、直されたとき対象が分からなくなる。
対象は、読めば何を指すか分かる言葉で書く。

- 文書の名前と、見出しの文言、または項目の名前で指す。例：「設計書の自己防衛の節にある『守る対象』の表」「要件書の`REQ-PRE`の拒否の文言の項」
- 何についての記述かを添える。見出しが変わっても、記述の中身で探し直せる
- 行数、`L123`、`4.6`のような節番号、表の上から何番目、は書かない
- 実装の関数名・ファイル名は、そのADRが決めた対象そのものであるときだけ書く

ADRの番号を要件書・設計書・コメントに書かない決まりは[実行環境とADRの扱い](environment.md)にある。向きが逆で、ADRから設計書を指すのは意味で書く。
