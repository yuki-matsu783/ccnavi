# スキルの振り返り

この文が届いたら（ターンの終わりにccnaviが止めたときや、提案を書くとき）、ここまでの作業を1度だけ振り返る。
ほとんどの回は、振り返っても出すものが無い。ccnaviが止めた回に守ること（タスクを続けない、問いで終わっていたら問いを最後に書き直す、
出すものが無ければ「振り返り: 無し」と書く）は、ccnaviが止めたときの文の頭に書いてある。

## スキルを直接書き換えない

振り返りでは、`.claude/skills/`もプロジェクトの`docs/skills/`も書き換えない。出すのは候補か提案だけにする。
スキルを直すのは、ユーザが承認したフェーズかチケットの中で行う。

## 拾うもの

- ユーザの訂正や苛立ち（「そうじゃない」「毎回〜しないで」「覚えておいて」）。いちばん強い信号になる
- 手順の順番や進め方の訂正
- 時間をかけた末に分かった、次の作業でも役立つ手順や注意点
- 読んだスキルの誤り・手順の抜け・古くなった記述
- サブエージェントの報告にある「スキル候補」の節（サブエージェントには振り返りが届かないので、報告で受け取る）

## 拾わないもの

- 環境が原因の失敗（コマンドが無い、認証が無い、入れ忘れ）。直し方が分かったなら、その手順だけを拾う
- 道具や機能を否定する主張（「Xは使えない」）
- 途中で解消した一時的なエラー、1回きりの作業の経緯
- 解決しないまま終わった試行錯誤
- CLAUDE.md・docs/claude/・ADRにすでに書いてあること

## どこに足すか（上ほど優先）

1. このセッションで読んだスキルを直す
2. 同じ種類の作業を扱う既存のスキルを直す（節・注意点・使う場面を足す）
3. 既存のスキルに`references/<話題>.md`を足すか広げ、SKILL.mdに1行の案内を足す
4. 作業の種類を単位にして新しいスキルを作る。今日の作業名・チケット番号・エラー文を名前にしない

- 直す前に、対象のSKILL.mdと触るreferences/を読み直す。会話中の引用で済ませない
- 1つの事実は1か所に書く。同じ規則が既にあるなら、新しく足さずに、その文を強めるか言い直す
- 手順の順に書く。注意点は、該当する手順に「規則 + なぜ（1句）」の形で添える。日付・番号・ユーザの言葉の引用を中身にしない
- yomiyasuスキルは、ユーザが明示的に頼んだときだけ使う。`docs/claude/`・`CLAUDE.md`・`.claude/skills/`・プロジェクトの`docs/skills/`・`rules.yml`の`message`には使わない（表・箇条書き・「規則 + なぜ」の形を地の文に崩してしまうため）
- 誤りは、間違った文そのものを直す

## 対象のスキル

| 振り返る作業 | 対象 |
|---|---|
| ワークスペース自身 | `.claude/skills/<名前>/` |
| `projects/<名前>/`の作業 | `projects/<名前>/docs/skills/<名前>/`（Claude Codeのスキルと同じ形。ccnaviが目録を渡す） |

どちらに書くかは、学んだことを使う作業の側で決める。両方にまたがるなら、手順を使う側に1本だけ書く。

## 候補の渡し方

| 今の作業 | すること |
|---|---|
| 計画のある親チケットの下で、フィードバック計画をまだ出していない | 親のワークツリーの`scratchpad/skill-candidates.md`に候補を足す（対象・作るか直すか・中身の下書き・根拠）。フィードバック計画を書くときに、候補があり、種類に`skill-improve`があり、親の範囲に対象の置き場が入っていれば、`feedback:`に`skill-improve`を入れる。承認されたら、そのフェーズの子でスキルを直し、MRでレビューしてもらう |
| それ以外（計画の無いチケット、フィードバック計画が承認済み、親の範囲に置き場が無い、チケットの外） | 提案チケットを書く（下） |
| サブエージェント | 自分では書かない。最後の報告に「スキル候補」の節を足して、メインセッションに返す |

## 提案チケット

置き場は1つに決める。作業中のMRに提案のファイルを混ぜない。

| 対象 | 書くツリー |
|---|---|
| ワークスペースのスキル | `.claude/worktrees/skill-proposals`。無ければワークスペースルートで`<統合先>`から切る |
| プロジェクトのスキル | `.claude/worktrees/<プロジェクト>-skill-proposals`。無ければ`cd projects/<プロジェクト>`して、そのプロジェクトのブランチから切る |

そのツリーの`wip/proposals/todo/<識別子>.md`に書いてコミットし、パスをユーザに伝えて承認を頼む。
識別子は`skill-<スキル名>-<要点>`のように1語で書く。

```yaml
---
version: 1
ticket: skill-commit-push-retry
human_review:
  required: true
  reason: エージェントの手順を変えるため
title: commit スキルに push の打ち直しを足す
rationale: |
  直す（新しく作るなら「作る」）。拾った信号と、次のセッションで何が変わるか。
allow:
  - match: Write|Edit
    glob: ".claude/skills/commit/*"
---
対象の SKILL.md（と references/）の差分か、新しく作るなら全文の下書き。
```

プロジェクトのスキルの提案は、そのプロジェクトの提案として書き、`allow`に`docs/skills/<スキル>/*`を書く
（パスはプロジェクトのルートからの相対で書く）。
