# 提案と判断・セッションの役割分担

## 提案と判断

- 提案にはメリットとデメリットを両方書く。デメリットが本当に無いなら「無い」と書く
- 次のどれかに当たる対応は自分で決めない。手を動かす前に「何をなぜ変えるか・得るもの・失うもの・
  やらない場合どうなるか・代案」を示し、返事を待つ
  - 止まっていたものが通るようになる（判定が緩む、例外が増える、確認が減る）
  - 判定の結果を無視する、条件を狭める、報告を消す
  - 元に戻せなくなる（消す、履歴を書き換える、他セッションの作業に触る）
  - 影響範囲を読み切れない（共有の設定、hook、スクリプト、配布物、他のプロジェクトへ配るもの）
- 調べる作業（再現する、読む、隔離した場所で試す）は、相談せずに進める。相談が要るのは、結果をこのリポジトリに入れるとき

## セッションの役割分担

- メインは利用者とのやり取り（相談・判断・報告）を受け持つ。実装・調査・テストは、サブエージェントを
  バックグラウンドで起動して任せる
- 1ファイルで済む小さな確認や修正と、レビュー準備中以降の合流・push・依頼は、サブエージェントに任せない
- サブエージェントを並行して動かすときは、それぞれに別のワークツリーを割り当てる
- サブエージェントは利用者に直接は聞けない。相談が要る条件に当たったら、作業を止め、聞きたいことを書いてメインに返す。
  メインが利用者に聞き、その答えを渡して同じサブエージェントを再開させる
- メインはサブエージェントの報告を差分とテスト結果で確かめてから、利用者に伝える
- 入れ子で起動するときは、プロンプトに担当の子チケット・ワークツリー・範囲と、他の子のワークツリーに
  触れないことを必ず書く。孫のhookの`cwd`はメインの`cwd`になるので、ccnaviは孫の担当を見分けられない
- 入れ子の上限（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`）に達したサブエージェントには、Agentツールが無い。
  入れ子での起動が必要なのにAgentツールが無いときは、起動してほしいエージェントの種類・プロンプト・担当を書いて
  メインに返す。メインがそのとおりに起動し、結果を渡して同じサブエージェントを再開させる。上限の値と実測の結果は
  ccnavi.md付録C「入れ子のサブエージェント」にある

## サブエージェントのモデル選び

Agentツールの`model`に、任せる作業に合わせてhaiku・sonnet・opusのどれかを指定する。省くとエージェント定義の
モデルで動き、定義にモデルが無ければメインと同じモデルで動く。

- haiku: 手順が決まっていて判断の要らない作業（用意したファイルへの置き換え、決まった語の検索、ログの抜き出し）。
  速くて安いが、手順書を読み違えたり、拒否の理由を誤解したりしやすい
- sonnet: 調査、ふつうの実装、テストの実行と修正。判断力と費用のバランスがよい。ただし、設計について深い判断が
  要る作業では、opusより見落としが出やすい
- opus: 設計に関わる変更、影響範囲の広い修正、文章の推敲のように細かい判断が要る作業。質が最も安定するが、
  遅くて高い
- `ccnavi-git.sh`を通すgit操作のように、拒否の文面を読んで進める場面がある作業は、手順が決まっていてもsonnet以上を使う
