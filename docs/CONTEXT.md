# ccnavi

ccnavi は、Claude Code を使った開発を、ルール・チケット・必要時の情報参照・振り返りで支えるツールで、出発点は、hook で危ないツール呼び出しを止めて代わりのやり方を返すガードである。
コア機能は 4 つ（ルールによる作業のガードとガイド、チケットによる作業・レビュー管理、ドキュメント・スキルの検索と必要時の参照、記録と振り返りによるルール・作業手順の改善）。
このファイルは ccnavi の設計の概念の用語集である。ワークスペースルート、git プロジェクトルート、作業・レビュー計画、フロー、先行関係、ユーザ待ち、タイトル、統合先、取り込み先など、使い方で出る呼び名は [.ccnavi/docs/terms.md](../.ccnavi/docs/terms.md) が定義するので、ここでは定義しない。実装は docs/20_design.md、要求は docs/10_requirements.md、判断の理由は docs/30_adr/ に書いてある。置き場のパスと環境変数は docs/20_design.md の置き場と環境変数の節にある。
このファイルは番号を付けず、`ccnavi --docs` の索引が frontmatter を読む。

## 用語

### 判定のレイヤー

**全体ルール**:
ルールファイルで宣言し、hook がすべてのツール呼び出しに適用する deny / ask / allow のこと。
チケット制御と対になる語で、どのレイヤーに書いたかは問わない。
使わない言い方: 共通ルール、グローバルルール

**レイヤー**:
設定 3 本（ルール、フェーズ定義、リスクの配点）を 1 組にして置く場所。
共通レイヤー・自身のレイヤー・プロジェクトのレイヤーの 3 種がある。ファイルはそれぞれ無くてもよく、置かれていないものは空として扱う（正常で、不備ではない）。フェーズ定義も 3 種のどれにも置ける。
使わない言い方: 層（共通層・自身の層・プロジェクトの層・層の和も同じ）、設定セット（状態を持つ場所の「2 層」は別の話）

**共通レイヤー**:
ワークスペースルートにある ccnavi の設定の置き場に置くレイヤーで、どのツリーにも適用される。名前は `common` で、識別子に接頭辞は付かない。
各プロジェクトへ配る定義でもある。プロジェクトを対象とする着手済みの親チケットがあれば、ユーザの発言のたびに、ワークスペースルートの `.ccnavi/config/common/` の中身を、そのプロジェクトの `.ccnavi/config/common/`（ミラー）へ配る。プロジェクトの `.ccnavi/config/project/` には触れない。
ミラーは、ワークスペースの中では読まず、そのプロジェクトを単体で clone したときにだけ共通レイヤーとして読まれる。ルール・リスク・フェーズ定義は共通レイヤーと config の和で判定する。
使わない言い方: 全体レイヤー、グローバルレイヤー、ワークスペースのレイヤー（自身のレイヤーと紛れる）

**自身のレイヤー**:
ワークスペースルートに、プロジェクトのレイヤーと同じ形で置くレイヤー。
ワークスペース自身のツリー（ワークスペースルートと、そこから切ったワークツリー）にだけ適用される。名前は `self` を使う。
使わない言い方: ワークスペースのレイヤー、self レイヤー

**プロジェクトのレイヤー**:
各プロジェクトの git プロジェクトルートに置くレイヤーで、そのプロジェクトのツリー（プロジェクト本体と、そこから切ったワークツリー）にだけ適用される。
名前にはプロジェクトの名前を使う。`common` と `self` は予約してあるので、その名前のプロジェクトは予約名として扱い、レイヤーにしない。
使わない言い方: リポジトリのレイヤー、プロジェクトのルール（ルール以外の 2 本も持つ）

**レイヤーの和**:
共通レイヤーに、そのツリーのレイヤーを足したもの。判定はレイヤーの和で行う。足すだけで、上書きや取り消しはしない。
パスを持つツール（Read / Grep / Glob / Write / Edit / NotebookEdit）では共通レイヤーと行き先の 1 レイヤーを足し、パスを持たないツール（Bash / PowerShell / WebFetch / Skill / Agent）では共通レイヤーと全部のレイヤーを足す。
フェーズ定義と配点は、共通レイヤーに、親の承認済みチケットの `project:` のレイヤー（空なら自身のレイヤー）を足して使う。フェーズ定義は、共通レイヤーと同じ `id` で中身が違う定義や `title` が重なる定義があれば、レイヤーの側のその定義だけを使わない（同じ `id` なら共通の定義を使う）。
例外が 2 つある。`match: Stop` のルールは共通レイヤーと自身のレイヤーだけから引く。
Chrome での承認は、ワークスペースの統合先の共通レイヤーと、プロジェクトの統合先のレイヤーを使う。手元の判定はワークツリーのレイヤーを読み、食い違いは lint の warn で知らせる。
使わない言い方: マージ、上書き、継承

**チケット制御**:
提案を承認して承認済みチケットを作り、その範囲、フェーズの HITL ポイント、サブエージェントの制限を判定に使う仕組みの全体。
使うかどうかはワークスペースごとに決め、プロジェクトごとには切り替えない。
使わない言い方: チケットによる範囲の制御、チケットの範囲、チケット管理（拡張の入口と、そこから開く画面の名前としてだけ使う）

**保護領域**:
「ここに書かせない」と宣言された場所。書き込み系ツールを `match` に含む deny / ask のルールがそのまま宣言を兼ねる。
実行後チェックはこの場所を見る。
使わない言い方: 保護対象ディレクトリ、監視対象

**コアファイル**:
ルールとは別に、組み込みの保護が守るファイル。hook の登録、各レイヤーの設定 3 本、実行ファイルがこれにあたる。
ルールを空にされても、コアファイルの保護は消えない。
使わない言い方: 中核ファイル、重要ファイル、システムファイル

**組み込みの保護**:
ルールファイルに書かなくても ccnavi が持っている保護。コアファイルを書き換える呼び出しを止め、実行前にバックアップを取って
実行後にバックアップから戻す（`selfguard`）。保護をルールとして判定に足したものは、ルール id で指すとき「組み込みルール」と呼ぶ（`builtin`）。

**縮退**:
Bash のコマンドを、実際に実行される部分まで読み切れなかったときに、生の文字列との一致で判定すること。
縮退した呼び出しには allow を適用しない。
使わない言い方: フォールバック、劣化

**ヒットする**:
ルールや glob が、対象の操作やパスに一致すること。一致しないときは「ヒットしない」と書く。
使わない言い方: マッチする、当たる

### 届け方

**ガイド**:
ルールにヒットした操作や、作業の段階がきっかけになって、モデルに届く理由・注意点・手順。判定は hook の処理がモデルのコンテキストの外で行い、文面（`message` と `additionalContext`）だけが届く。
エージェントが自分で資料を探して読む「検索と必要時の参照」（`ccnavi --docs`）とは、届くきっかけが違う。
使わない言い方: ルールをコンテキストに入れる（判定にモデルのコンテキストは使わない）

**別 PC・別セッションの作業**:
チケット（親と子）ごとの作業を、別の PC・別の Claude Code セッション・別の人が進めること。親のブランチ上のチケットとマーカー、ホスト上のレビューでつなぐ。サブエージェントによる分担（同じ PC・同じセッション）とは別のもの。
同期は操作の時点で行い、リアルタイムではない。

**分類に使うホスト**は、origin の URL から取り出したホストを小文字にし、ポートを除いたもの。`.` の区切りで照合して GitHub（`github.com`・`ghe.com`・`*.ghe.com`）か GitLab（それ以外の全部）かを決める。接続先のうち GitLab のものは、ポートを除かず origin の scheme・ホスト・ポートを保つ。
使わない言い方: ドメインの後方一致

**代表の note**は、GitLab のスレッド（discussion）が持つ note のうち、system の note を除いた集合から、本文が ccnavi の目印（`<!-- ccnavi:`）で始まらない最初のものを選んだもの（無ければ先頭）。指摘の本文・URL・位置・書き手はここから取る。ccnavi の依頼コメントにユーザが返信したスレッドでは、返信が代表になる。

### 作業の進め方

**直接作業**:
チケットを起こさず、全体ルールだけで判定して進める作業。調査と小さな修正がこれにあたる。
ワークスペースルート直下での作業と、承認済みチケットの無いワークツリーでの作業も、直接作業として扱う。
使わない言い方: チケット無しの作業、軽い作業

**チケット作業**:
提案を書いて承認を受け、フェーズとリスクの配点に従って issue とマージリクエストを作りながら進める作業。
使わない言い方: 重い作業、正式な作業

### チケットの持ち物

**提案**:
これから適用したい範囲の宣言。エージェントが各ワークツリーの提案の置き場（`todo/`）に書き、`ccnavi-ticket.sh propose` で親のブランチへ送り、ユーザが読んで承認する。
承認されると、提案の置き場から承認済みチケットの置き場へ動く。提案の置き場にコピーは残らない。
使わない言い方: チケットファイル、下書き

**承認済みチケット**:
ユーザが承認して承認済みチケットの置き場（`doing/`）へ動かした提案そのもの。判定はこれだけを読む。
作業が終わると提案の置き場の `review/` へ動き、ユーザが見たあとに承認済みチケットの置き場の `done/` へ動く。
承認済みチケットの置き場へ動かすのはユーザで、提案の置き場へ動かすのはエージェントである。
使わない言い方: 提案のコピー、複製、台帳

**レビュー待ちのチケット**:
エージェントが `finish` で閉じて、提案の置き場の `review/` に置かれているチケット。次に動くのはユーザである。
判定の範囲としては適用されない。
使わない言い方: 完了チケット、done

**マーカー**:
フェーズの進み具合（依頼済み・レビュー済み・省略）と、親の閉じ方（閉じた・下書きを外した・ユーザが早めに閉じた）を表すファイル。
承認済みチケットの置き場の下に置く。
使わない言い方: 印、マーク、フラグ

**先行**:
子チケットが `predecessors` に挙げる子チケットで、先に閉じている必要があるもの。
承認と着手（`start`）には、先行が全部 `.ccnavi/approved/done/` にあり、どれも取り消しでないことが求められる。
レビュー待ちの先行は、この条件を満たさない。書き込みは止めない。ボードでは「先行待ち」と表示する。
使わない言い方: 依存チケット、前提チケット、ブロッカー

**承認の push**:
承認済みチケットの置き場（とマーカー）だけをコミットし、保護ブランチでなければ push すること。
`ccnavi-user-push-approved.sh` と、`ccnavi-ticket.sh`・`ccnavi-review.sh` の最後に呼ぶ共通の関数が行う。

**ダイジェスト**:
承認画面でユーザに見せた提案の識別子の一覧と、各提案ファイルのバイト列から計算するハッシュ（`--digest`）。承認のときに提案が変わっていないことを確かめる。レビューの残った指摘（`decide`）にも同じ名前があり、そちらは見せた指摘から計算する。

**早めに閉じる**:
残りの子やフェーズがあるのを承知で、ユーザが親チケットを閉じること（`close-early`）。ターミナルで打ち、y/N で確かめてから閉じる。
親の閉じ方は、閉じた（`closed`）・下書きを外した（`ready`）・早めに閉じた（`close-early`）の 3 つ。

**ワークツリー**:
次の 2 つの意味がある。文脈で分かるときは「ワークツリー」だけで足りる。区別が要る場面は、前者を「チケット用のワークツリー」、後者を「working tree」と書き分ける。
- チケット 1 本のために切る git worktree。名前はチケットの識別子と同じにする。判定では、ファイルの行き先がどのワークツリーかが決め手になる。ツリー 3 種のうちの 1 つになる。
- git の working tree。索引と対になる側で、ツリー 3 種のどれにもなりうる。実行後チェックが `git status` で読むのは、こちらである。
使わない言い方: ブランチ、worktree（英語の表記は git のコマンド名としてだけ使う）

**レビュー準備中**:
ユーザのレビューが要るフェーズが終わってから、レビューの依頼を出すまでの間。
この間はサブエージェントの起動とシェルの実行が止まる。次に動くのはエージェントで、合流済みの確認・push・依頼を行う（合流は子の finish が済ませている）。
使わない言い方: ゲート閉、足止め、ロック、ブロック

**レビュー待ち**:
レビューの依頼を出してから、レビュー済みのマーカーが置かれるまでの間。次に動くのはユーザである。
使わない言い方: ゲート閉、依頼済み待ち

**HITL ポイント**:
ユーザの手が入るところ（Human In The Loop）。範囲の承認、レビュー、未解決の受け入れの 3 か所がある。
フェーズの終わりのレビューは、レビュー準備中、レビュー待ち、レビュー済みの順に進む。
判定とボードでの表記は `gate_closed` である。
使わない言い方: ゲート、足止め、ロック、ブロック

**マージリクエスト**:
レビューを行う場所の 1 つ。GitHub の pull request もこの語で呼ぶ。ホストの違いは origin の URL で見分ける。
略称「MR」は、GitLab の呼び名で、`mr:` や `--mr` などの識別子にもなっているので、文書でも使ってよい。GitHub の pull request も「マージリクエスト」「MR」で呼ぶ。
使わない言い方: PR、プルリクエスト

**見る場所**:
フェーズの終わりに、ユーザがどこでレビューするか。見ない・マージリクエストの 2 つがある。
フェーズ定義で宣言し、厳しい側を採る。
使わない言い方: レビュー先、レビュー方式

### フェーズ

**フェーズ定義**:
設定ファイルに定義された名前付きの型で、親の計画に並べて使う。
使わない言い方: 段、ステージ、フェーズの種類

**フェーズ**:
親の計画に並んだ番号付きの実体。同じ親の、同じ番号の子チケットをまとめたもの。
計画では、親の計画に並んだ 1 つ 1 つを「ステップ」と呼ぶ。ステップは計画の側の呼び名で、フェーズは同じ番号の子チケットの側の呼び名。
使わない言い方: 段階

**テンプレート**:
完了した親の作業・レビュー計画（`plan:` と `feedback:` のステップと `after`）と、子のフローの本文を 1 ファイルにまとめた雛形。共通とプロジェクトの 2 層に置き、ユーザが取り込んだものだけが効く。エージェントが書くのは効力の無い下書きまで。
使わない言い方: ひな形、フローテンプレート

**有効／無効**:
テンプレートや定義の状態のバッジ。ユーザが取り込んだものが有効で、そうでないものは無効。
使わない言い方: 使える／使えない

**バッジ**:
状態などを示す小さな表示。画面のカードや見出しに付く（コードの `Badge`、`status.label`）。
使わない言い方: 札、ラベル（`status.label` などコードの識別子は除く）

**気づき**:
子チケットのセッションが拾った、次の作業でも使える知識の 1 件。子ごとに 1 ファイルの記録（`wip/handoff/learnings/<子の識別子>.md`）に書く。
使わない言い方: 学び（記録の中身を指すときは気づき。蓄積の仕組みを指すときの「学びの蓄積」は可）

**learning-wiki**:
気づきを統合した知識の置き場（`docs/wiki/`）。パターンと採否の記録を持つ。作業のセッションには渡さず、手順書（スキル・ルール・テンプレートなど）を作る側が読む。
使わない言い方: skill-wiki（概念の呼び名として。スキルの振り返りで wiki を使う手順の文書名 `skill-wiki.md` はそのまま使う）

**パターン**:
learning-wiki の 1 ページ。気づきを統合した、失敗や有効だった進め方 1 つ。反映先の種類（`target`）と、観測元の ID の一覧（`sources`）を持ち、その数を観測元の数と呼ぶ。

**反映先**:
学びの提案が直すもの。ルール・配点・フェーズ定義・テンプレート・スキル・文書の 6 種。

**反映の提案**:
反映先 1 つへの変更の案。差分と動機のパターンを持つ。チケットの提案（`wip/proposals/`）と紛れるときは「反映の提案」と書く。
使わない言い方: 学びの提案（チケットの提案と紛れる）

**局面**:
親チケットが計画のどこにいるかを表す語。作業中・レビュー準備中・レビュー待ち・フィードバック計画待ち・フィードバック対応中・クローズ可、がある（ユーザが早めに閉じたときは「閉じられる（ユーザが早めに閉じた）」）。計画が無い親は局面を持たない。
使わない言い方: 段階、ステータス

**リスクレベル**:
実績で測ったリスクの高さで、LOW / MEDIUM / HIGH / CRITICAL の 4 つがある。「レベル」とだけ書かない。
使わない言い方: 等級、段階、ランク

**境目の点**:
リスクの点がこの値以上になると、リスクレベルが 1 段上がる、という値。
`levels` の medium / high / critical の 3 つで、既定は 20 / 40 / 70。判定は「以上」で行う。
使わない言い方: 閾値、しきい値、基準

**基準**:
配点の項目で、この数を超えたら加点する、という数。`lines_over` / `files_over` / `deleted_over` の値で、判定は「超え」で行う。
使わない言い方: 閾値、しきい値、境目

### 親のブランチと取り込み

**親のブランチ**:
親チケットの作業ブランチ（`P`）。子チケットにとっては親のもの、親チケット自身にとっては自分のもの。

**親子のチケット**:
親チケットとその子チケットのまとまり。親のブランチ 1 本と 1 対 1 で対応し、取り込みと承認はこの単位で扱う。
識別子・保存先の名前では `family` / `families` と書く。

**取り込み状態**（廃止）:
ADR-0142 で廃止した。使わない。親子のチケットの状態は親のブランチだけで判定する。

**state の置き場**:
手元だけに置き、リポジトリには入れない置き場（`logs/state/`）。実行後チェックの記録、セッションの記録、
コアファイルのバックアップ、親を閉じた後の片付けの記録（`retire/<親>.json`）をここに置く。

**write-and-push**:
親のワークツリーがあり、origin があり、HEAD の確認に通る親子のチケットで、状態を書く操作（`start`・`finish`・マーカーを置くサブコマンドなど）を、
ロック → 置き場の未コミットの変更を見分けてコミット → 取り込み → 書く → 書いたパスだけをコミット → push、の 1 操作にする仕組み。
push が通るまで操作を完了にしない。Chrome 拡張は親のブランチを読むので、手元にだけある未送信の状態を溜めないため。
origin が無い親のワークツリーは push せず、手元に書くだけで終わる。親のブランチがリモートから消えていれば、push の前に共通の push の関門
（`ccnavi_push_gate`）が止める。対象かどうかと断る理由は `ccnavi write-and-push family <親>` で引ける（`target`）。
サブコマンド名・モジュール名・環境変数（`write-and-push`、`CCNAVI_WRITE_AND_PUSH_*`）もこの語を使う。sh の関数と変数の接頭辞は `ccnavi_wap_`（write-and-push の頭文字）。

**正とする側**:
どのツリー・ブランチ上の承認済みチケットを判定が読むか（`_authoritative`）。どの親子のチケットでも、
親のワークツリー（親のブランチ上）のチケットだけを正とする。

**元に戻すコミット**:
GitLab へ書き込んだあとに競合が見つかったとき、その書き込みを元に戻すために積む revert のコミット。
チケットの取り消し（cancel）とは別のもの。

### 場所

**プロジェクト**:
プロジェクト置き場（`projects/`）の直下に clone した、ワークスペースとは別のリポジトリ。
ツリー 3 種のうちの 1 つで、記録とレイヤーではこの名前で呼ぶ。
使わない言い方: サブリポジトリ、子リポジトリ、git プロジェクトルート（あれは 3 種の総称）

**ツリー**:
判定の単位になる場所で、ワークスペースルート・プロジェクト・ワークツリー（チケット用）の 3 種がある。
どのツリーに属するかは、実パスの最長一致で決まる。
使わない言い方: リポジトリ、チェックアウト

**元リポジトリ**:
そのワークツリーが属するリポジトリ。ワークスペースルートかプロジェクトのどちらかで、`.git` ファイルの `gitdir:` が指す先で確かめる。
レイヤーの選択、`project:` の照合、ワークツリー側の設定を探す先は、元リポジトリで決まる。
使わない言い方: 切り元、親リポジトリ（親チケットと紛れる）、ベース、
元ブランチ（元リポジトリはブランチでない）

**元のプロジェクトが無いワークツリー**:
プロジェクト（`projects/<名前>/` の別リポジトリ）を消したあとも残った、または元のプロジェクトへ戻る参照が切れた、元のプロジェクトを失ったワークツリー。
元リポジトリをたどれないのでツリーとして数えず、中のパスはワークスペースルートとして判定され、そのプロジェクトの `deny` が効かない。
`--lint` が warn し、`--explain` が節「■ 元のプロジェクトが無いワークツリー」で名指しする。
対処は、ワークツリーを消すか、プロジェクトを戻すこと。
