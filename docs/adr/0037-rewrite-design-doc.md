# ADR-0037: 設計書を実装に合わせて書き直す

状態: 採用

## 状況

設計書 ccnavi.md は「到達点であって、現在の実装ではない」と冒頭で断り、4 層の設定
（settings.json / 組み込み不変 deny / `config.yaml` / `.current-ticket.md` / 環境変数
`TICKET_GUARD_*`）、最も厳しい値を選ぶ合成関数、`config_hash`、承認キャッシュ、ask の二分類、
DB 破壊操作の共起検知、二段階承認などを書いていた。実装はそのほとんどを別の形で作るか、作らずに
済ませた。食い違いの一覧は引き継ぎ文書の「判断の経緯」に散らばり、設計書の冒頭にも表があった。
読む人は 3 つの文書を突き合わせないと今の形が分からなかった。

## 決定

設計書は「いまの実装がどう作られているか」だけを書く文書にし、全部書き直す。「なぜ」と
「以前の形」と「採らなかった案」は、判断 1 つにつき 1 枚の ADR（`docs/adr/`）へ移す。
引き継ぎ文書は現状と次の一手だけを持つ。

## 理由

設計書が到達点のままだと、実装と違う箇所を「まだ作っていないだけ」と「判断が変わった」に
分けて読む必要があり、その分け方が引き継ぎ文書にしか無かった。判断の理由を設計書に混ぜると、
今の形を知りたいだけの人が経緯を読まされる。

## 得たもの・失ったもの

- 得たもの: 設計書を読めば今の形が分かる。「なぜ」は ADR の 1 枚で読める
- 失ったもの: 到達点として書いてあった未実装の構想（承認キャッシュ、セッション開始時の提示）は、
  要件書と引き継ぎ文書の「未実装」に残るだけになる。作るときは要件書から起こす
- 失ったもの: コードのコメントとテストにある旧節番号の参照は、この表で引く
