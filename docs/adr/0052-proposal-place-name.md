# ADR-0052: 提案の置き場の既定を `wip/proposals` にする

状態: 採用

## 状況

チケットの置き場は 2 つある。エージェントが書く提案（既定 `wip/tickets/`）と、判定が読む
承認済みチケット（既定 `.ccnavi/tickets/`）で、要求は正反対になっている。提案はエージェントが
書けないと起草できず、承認済みチケットはエージェントが書けると自分で範囲を広げられる
（ADR-0023）。

その 2 つが、どちらも `tickets` という同じ名前だった。文書でも会話でも「チケット」がどちらを
指すのか毎回言い添えることになり、「承認は何をしているのか」「提案を手で動かす意味はあるのか」と
いった問いが、置き場の読み違いから始まっていた。

## 決定

提案の置き場の既定を `wip/tickets` から `wip/proposals` に変える。承認済みチケットの置き場
（`.ccnavi/tickets`）は変えない。

綴りはどちらも今までどおり env で決められる（`CCNAVI_TICKETS_PROPOSAL` /
`CCNAVI_TICKETS_APPROVED`）。既定を変えるだけで、判定の当て方は変わらない。

既定のまま使っているツリーの旧の置き場（`wip/tickets/`）に提案が残っていたら、`--lint` が識別子を
添えて warn で名指しする（`lint._legacy_tickets`）。文面は、移す道と、env に旧の綴りを書く道の
両方を出す。

見るのは**置き場の有無ではなく、中に残っている提案**。置き場の有無で決めると、新しい置き場を
1 つ作った時点で旧の残りが永久に見えなくなる。移し忘れがいちばん起きるのはその形（部分移行）。
逆に、同じ綴りが新しい置き場にもあるもの（写し終えた分）と、`done/` `cancelled/` に在って承認済み
チケットが閉じているものは数えない。後者は記録として残っているだけで、閉じたことの権威も
フェーズの状態も承認済みチケットの側から読む（`phase.phases_of`）。数えると、履歴を残した人に
毎回同じ 1 行が出て、他の報告ごと読まれなくなる。

状態を置き場で表すこと（ADR-0024）は変えない。`todo` / `doing` / `done` / `cancelled` の 4 つは
そのままで、名前が変わるのは 1 つ上の段だけ。

## 理由

- 2 つの置き場は役割が反対で、しかも片方は deny 領域。**名前が同じだと、その境界が名前から
  読めない。** `proposals` と `tickets` に分ければ、「提案は書ける、チケットは書けない」が
  綴りのうえで言える
- 既定を据え置いて呼び分けだけを文書で徹底する道もあったが、実際に目に入るのはディレクトリの
  名前のほうで、文書は読まれたときにしか効かない
- 移行を黙って進めると、旧の置き場が残ったツリーで提案が 1 つも走査されないまま「承認待ちは
  無い」で通る。**気づけない向きの失敗**なので、検証が名指しする側に倒す。判定で止めないのは、
  置き場の綴りは人が決める設定で、既定と違うこと自体は不備ではないから

## 得たもの・失ったもの

- 得たもの: 提案（エージェントが書ける）と承認済みチケット（書けない）が名前で分かれる
- 得たもの: 旧の置き場が残ったツリーを `--lint` が名指しする。黙って「承認待ちは無い」にならない
- 失ったもの: **既定のまま使っていたツリーは、ディレクトリを改名するか env を 1 行足すまで提案が
  走査されない。** 検証が言うだけで、自動では移さない
- 失ったもの: この ADR より前の記録（ADR-0023、0024、0038 など）は `wip/tickets` の綴りで書かれた
  まま残る。過去の記録は消さない決まりなので、旧の綴りを見たら本 ADR に当たることになる
- 失ったもの: **env で旧の綴りに戻した人は、VS Code 拡張の自動更新が効かない。** 拡張が提案の
  変化を見る場所は既定の綴りで固定してあり、env を読まない（改名前からの制約で、既定が
  両方 `wip/tickets` で一致していたため表面化していなかった）。開いた時点の中身は正しく、手で
  「更新」を押せば追いつく。README の env の表に書いた

## 採らなかった案

- **既定は据え置き、呼び分けだけ文書で徹底する。** 目に入るのはディレクトリの名前のほう
- **承認済みチケットの側を改名する。** そちらは `.ccnavi/` の下にあって場所で役割が言えており、
  組み込みの守り（`builtin-guard-project-home`）と設計文書の参照も多い。動かす対象として重い
- **旧の綴りも既定として走査する（2 つ見る）。** 置き場が 2 つある状態を実装が正常として扱うことに
  なり、同じ識別子が両方に在るときの権威を決める話が増える。移行のための一時的な仕組みが、
  移行が終わっても残る
- **置き場が在るかどうかだけで警告する。** 実装は短いが、新しい置き場を 1 つ作った時点で旧の
  残りが永久に見えなくなる。移行の途中がいちばん危ないのに、そこで黙る（敵対的レビューで指摘）
- **起動時に自動で改名する。** ファイルを動かすのは人の判断（消える向きではないが、git の履歴に
  出る）。実行ファイルが黙って作業ツリーを書き換える形は採らない
