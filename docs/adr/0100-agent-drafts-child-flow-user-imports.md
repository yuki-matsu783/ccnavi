# ADR-0100: エージェントは子のフローの下書きを提案の置き場に書き、ユーザがフロー編集画面で取り込む

状態: 採用（実装済み。チケットのワークフローを使わず、ユーザの判断で直接作業で実装した。ADR-0085 の「フローはユーザが書く。エージェントには書かせない」と、その「失ったもの」の「エージェントが段取りを書き起こしてユーザに渡すことはできない」を一部置き換える。ほかは 0085 のまま。2026-10-03 にユーザが相談事項を決めた）

## 状況

2026-10-03。子チケットのフローは `.ccnavi/approved/flows/<子>.yml` に置き、ユーザがボードのフロー編集画面で書く
（ADR-0085）。エージェントの書き込みは組み込みの保護 `builtin-guard-project-home`（`Write` / `Edit` / `NotebookEdit`）と
`builtin-guard-setting-files`（シェル）が止め、着手中はロック `DENY_TICKET_FLOW_LOCKED` も止める。フローは承認の対象ではない
（ADR-0030 に合わせ、判断の点を増やさない）。

この形では、段取りの書き起こしを全部ユーザが手で行う。エージェントは調べた結果から段取りの案を作れるのに、それを
ユーザへ渡す置き場が無い。チャットに貼った案をユーザがエディタで写すことになる。

調べて分かったこと。

- 提案の置き場 `wip/proposals/` は、丸ごとチケットの範囲の外として扱われる（`ticket_places.is_ticket_place`）。実行前・実行後・
  サブエージェント終了時のどのチェックでも報告しない。組み込みが止めるのは `review/` への直接の作成と移動だけ
  （`ticket_guard.guard_rules`、`GUARDED_STATES`）。提案として走査するのは `todo/` と `review/` だけ（`ticket_model.STATES`）
- 依頼の後に `wip/proposals/` だけを変えたコミットは、「ユーザが見るものが動いた」に数えない（`review._moved_since_request`）
- `wip/` は `ready` の前に丸ごと消してコミットする。ここに置いたものは squash した成果物に残らない
- フローは `SubagentStart` の hook（`flow.briefing`）が案内として渡すだけで、強制はしない。読むのは本物とするツリーの
  `.ccnavi/approved/flows/<子>.yml` だけ
- ボードの保存の前の差分（`flow-diff.ts` の `diffFlows`、`SaveReview.tsx`）は、変わった欄の名前だけを見せ、文の中身は見せない
- 拡張が Claude Code に文を渡す経路は、承認の文と「レビュー済み連絡」で使う「コピー / 新しいセッションで開く」の 2 つ
  （ADR-0040、`vscode://anthropic.claude-code/open?prompt=…`）。走っているセッションへ文を送り込む公開の手段は無い。
  統合ターミナル「ccnavi」（`terminal.ts` の `runInTerminal`）はシェルで、送れるのは sh のコマンドだけ（ADR-0093 で
  保存の後に `ccnavi-push-approved.sh` を送る仕組みもこれ。押したときだけ送る）
- `ccnavi-push-approved.sh` がコミットに入れるのは、承認済みの置き場・`review/`・承認で消えた `todo/` の提案（`ls-files --deleted`）だけ。フローの保存の一時ファイル `flows/.*.tmp` は除く。`wip/proposals/flows/` の変更は入らない。C1 の分け（`ccnavi c1 sort`）が見るのも承認済みの置き場と `review/` だけで、消えた `todo/` の提案は sh が別に拾う

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| エージェントは子のフローの**下書き**を `wip/proposals/flows/<子>.yml` に書ける。プロジェクトの子なら `projects/<名前>/wip/proposals/flows/<子>.yml`。置くツリーは、フロー編集画面がその子のフローを保存するツリー（承認の前は提案のツリー、後は本物とするツリー）と同じ | 承認済みの領域で `flows/` が `doing/` `done/` と並ぶのに揃え、提案の置き場でも `todo/` `review/` と並べる。`wip/proposals/` は既に範囲の外で、`flows/` は守る状態の置き場でも走査の対象でもないので、**判定を変えずに**書ける。チケットと同じ git に入り、親のブランチで他の機械へ届く。`ready` の前に `wip/` ごと消える | `wip/proposals/todo/<子>.flow.yml`（承認待ちの提案と同じ置き場に、チケットでないファイルが混ざる。`todo/` への書き込みには提案の案内が出る）。`wip/flows/`（範囲の外にならず、親の範囲に足すことになる）。承認済みの領域に別名で置く（組み込みの保護に例外を作ることになる） |
| 下書きには**効力が無い**。`SubagentStart` も着手のときのハッシュも下書きを読まない。承認のダイジェスト（`--agree` の digest）にも入れない | 効くのはユーザが取り込んで `approved/flows/` に保存したものだけ。下書きの書き込みを止めなくても、勝手に書かれた害は余計な提案が 1 つ画面に出る程度に収まる | 下書きを案内に載せる。ユーザが読んでいない手順が子に渡る |
| 「依頼されたときだけ書く」は**運用で守り、判定では強制しない** | 上の理由で害が小さい。強制には依頼のマーカーと、そのマーカーをエージェントが作れない置き場が要り、判定と保護が増える | 依頼のマーカーが無ければ止める（下の「採らなかった案」の B） |
| フロー編集画面は、下書きが在って中身がいまのフローと違うとき（`sameFlow` が偽）に「提案あり」を出す。ユーザが開くと、下書きを `ccnavi --lint --json --flow <下書き>` に掛け、error なら取り込めないと言う。通れば、いまのフローとの差分を、**変わった欄の名前だけでなく文の前後まで**見せる | フローの文はサブエージェントへの案内文になり、プロンプトインジェクションの経路になる。歯止めは取り込みのときにユーザが差分を読むことなので、欄の名前だけでは足りない。正しいかの答えは実行ファイルが持つ（ADR-0035、ADR-0085 の lint） | 欄の名前だけの差分（いまの `SaveReview`）。下書きを開いた画面で直接見せる（いまのフローとの違いが読めない） |
| 「取り込む」は、下書きの中身を編集中の内容として画面に入れるだけにする。保存はいつもどおり（保存の前の差分・lint・押した時点のロックの聞き直し）で `approved/flows/<子>.yml` に書く。編集中で未保存の変更があるときは、取り込む前に確かめる | 書き込みの経路を 1 本のまま保ち、ロック・リンク・ハードリンク・大きさの保護を新しく書かない。取り込んでから直してもよい | 取り込むボタンでそのまま保存する。保存の経路が 2 本になる |
| **取り込んだ下書きは消す**。消すのは、取り込んだ内容の保存が成功した時点（`approved/flows/<子>.yml` を書けたあと）。取り込んで編集中に入れた時点では消さず、取り消し・保存の失敗・ロックで止まったときも消さない。消すのは、下書きの中身が取り込んだときの中身（ハッシュ）と同じときだけ。違えば（取り込んだあとにエージェントが書き直した）消さずにそう言う。リンク・ハードリンク・ふつうのファイルでないものは消さない（読むときと同じ保護） | 古い下書きが残ると「提案あり」と紛らわしい。保存の成功を待つのは、取り込んでも保存しなかったときに案が失われないようにするため。中身を比べるのは、ユーザが読んでいない新しい案を消さないため | 消さない（`ready` の前の `wip/` の片付けに任せる）。古い下書きが残り、エージェントが少し直すと取り込み済みの案がまた「提案あり」になる。取り込んで編集中に入れた時点で消す。保存しなかったときに案が消える |
| 消したことは、フローの保存と同じ経路でコミットに入れる。`ccnavi-push-approved.sh` は、`todo/` の提案と同じく `wip/proposals/flows/` の追跡されていて消えたファイル（`ls-files --deleted`）をコミットして push する対象に足す（C1 の親子のチケットの `carry_paths` と、そうでない親子のチケットのコミットの両方）。追跡されていない下書き（エージェントがコミットしていない）は消すだけで、コミットするものは残らない。消した下書きは保存のあとの知らせ（「ターミナルで送る」と、そうでない親子のチケットへの案内）にも名前を出す。`ccnavi c1 sort` の置き場は変えない | 消したことがコミットされないと、親のツリーにユーザのコミットしていない削除が残る。フローの保存と同じ 1 回の操作でコミットして push すれば、ユーザの手は増えない。`c1 sort` の置き場に `wip/proposals/flows/` を足すと、エージェントが書いた未コミットの下書きが C1 の分けに入り、着手や終わりの操作を止めうるので、消えた `todo/` と同じく sh が消えたものだけを拾う | ボードが自分でコミットする（拡張はコミットしない作り）。削除を未コミットのまま残し、ユーザに任せる |
| 着手後のロックは今のまま。着手中の子では「提案あり」は出しても、取り込みは保存と同じく止める | ロックの意味（読んだ手順と後で見る手順を食い違わせない）は変わらない | 着手中も取り込める |
| フロー編集画面に**「エージェントにフローの作成を頼む」ボタン**を置く。ボード本体（一覧）には置かない。押すと依頼文を組み、「コピー」と「新しいセッションで開く」の 2 つで渡す。依頼文には、子の識別子・書く置き場・いまのフローの置き場（在れば）・`--lint --flow` で確かめてから渡すこと・`approved/flows/` には書かないことを入れる | 依頼は書き込みの許可条件ではなく、依頼を出す便利な入口。文を渡す経路は承認の文と「レビュー済み連絡」で既にあり、実行ファイルも hook も変えずに乗れる。フロー編集画面に置くのは、どの子のフローかが画面で決まっていて、取り込みも同じ画面で行うため | 依頼のマーカーを置いて hook で知らせる。統合ターミナルに送る（下の「採らなかった案」） |
| ボタンを出す状態: 子が着手の前（承認待ち・承認済みで未着手）なら、フローが無いときは「作成を頼む」、在るときは「直しを頼む」（依頼文にいまのフローの置き場を入れる）。下書きが既に在れば文言を「頼み直す」にする。着手中（ロック）・閉じた子・ロックの確認中には出さない | 着手中は取り込めないので、頼んでも使えない下書きができる | どの状態でも出す |
| 実行ファイルは `--explain --json` の `tickets[].flow` に下書きの置き場と有無を載せる。拡張はパスを自分で組まない | フローの置き場と同じく、置き場の答えは実行ファイルが持つ（ADR-0035） | 拡張が置き場を組む。置き場のパスが 2 か所になる |
| 判定・組み込みの保護・ルール（`selfguard`・`rules.yml`）は変えない。受入テストで、下書きへの書き込みが通ること、`approved/flows/` への書き込みが今までどおり止まること、`briefing` が下書きを読まないこと、保存の成功で下書きが消えて `ccnavi-push-approved.sh` が削除をコミットして push することを確かめる。`ccnavi-push-approved.sh` は保護済み（`.ccnavi/scripts/`）だが、エージェントが直接直す（ユーザの判断: いまは dry-run で組み込みの保護が止めないため、エージェントが直接直した。dry-run を外したあとなら staging でユーザが写す形になる） | 書ける場所は既に書ける。変えるのは画面と、置き場を伝える JSON と、削除をコミットして push する sh と、文書だけ | 下書きの置き場に専用の allow を足す。要らない判定が増える |

## 相談が要る変更としての整理

docs/claude/decisions.md の「止まっていたものが通るようになる」と「ユーザとのやり取りの形が変わる」に当たる。

- 何をなぜ変えるか: エージェントが段取りの案を書き起こし、ユーザが差分を読んで取り込めるようにする。書き起こしの手間を
  ユーザから外し、決めるのはユーザのまま残す
- 得るもの: ユーザがエディタで写す手間が無くなる。案と現状の違いが差分で読める。判定・保護・承認の点は増えない
- 失うもの: エージェントの書いた文が、ユーザの取り込みを経て子への案内になる経路ができる（下の「気をつけること」）。
  依頼されていない下書きも書ける（運用で守る）。フロー編集画面のボタンと表示が増える。保護済みの `ccnavi-push-approved.sh` を
  エージェントが直す（いまは dry-run のため。dry-run を外したあとならユーザが写す）
- やらない場合: 今までどおり。案はチャットで渡り、ユーザがエディタで写す。写し間違いと手間が残る
- 代案: 下の「採らなかった案」の B と、`--agree` の digest に含める案

## 気をつけること

- **フローの中身はサブエージェントへの案内文になる。** 下書きにエージェントの文（外から読んだ文書のコピーを含む）が入り、
  ユーザが読まずに取り込めば、そのまま子への指示になる。案内に載せるときの囲み（ADR-0085 の M3・L-a）は ccnavi の接頭辞の
  真似を防ぐだけで、中身の良し悪しは見ない。歯止めは取り込みのときの差分で、そのために文の前後まで見せる
- フローの中身の危険（MCP や codex など外部の道具を使わせる指示、エージェント定義の指定など）を見る検査は今も無く、
  **この ADR では足さない**（ユーザの決定）。歯止めは取り込みのときに文の前後まで見せる差分で、検査は別のチケットで扱う
- 下書きは `ready` の前に消えるが、親のブランチの履歴には残る

## ADR-0085 との関係

ADR-0085 の決定の表の「（改めた）フローはユーザがボードのエディタで書く。エージェントには書かせない」の行のうち、
「エージェントが案を書く」部分を、この ADR が置き換える。**効力のあるフロー（`approved/flows/`）を書くのはユーザだけ**、
承認の対象にしない、着手中のロック、組み込みの保護は変えない。0085 には追記で関係を書き、実装と一緒に状態の行を
「採用（エージェントの下書きは置き換え（ADR-0100））」に改めた（0094 と 0095 の書き方に合わせる）。

`docs/claude/projects.md` の「子のフローは、エージェントが書かない（シェルからも書かない）」も、実装と一緒に
「効力のあるフローは書かない。下書きは `wip/proposals/flows/<子>.yml` に、頼まれたときだけ書く」に改めた。

## 得たもの・失ったもの

- 得たもの: エージェントが段取りの案をユーザへ渡せる。ユーザは差分を読んで取り込むだけでよい。取り込んだ下書きは保存と一緒に
  消え、その削除もコミットされて push されるので、古い案が「提案あり」として残らない。判定・保護・承認・ロックは変わらない
- 失ったもの: エージェントの文がユーザの取り込みを経て案内になる経路が増える。歯止めはユーザが差分を読むことだけで、
  読まずに取り込めば止まらない。「依頼されたときだけ書く」は判定で守られない。取り込んだ下書きの削除をコミットして push するために、保護済みの
  `ccnavi-push-approved.sh` を直す（いまは dry-run なのでエージェントが直接直す）。取り込んだあとにエージェントが書き直した下書きは消さないので残る

## 採らなかった案

- **B: 依頼のマーカーで強制する。** ボタンがマーカーを置き、マーカーの無い子への下書きの書き込みを止める。マーカーをエージェントが作れない置き場
  （承認済みの領域など）に置き、判定に新しい分岐を足すことになる。下書きは取り込まれるまで効かないので、止めて守るものが
  小さい。マーカーが書き込みの許可に見え、許可の経路が 1 つ増える
- **下書きを `--agree` の digest に含める。** 承認のたびに下書きの中身がダイジェストに入る。フローは承認の対象にしない
  （ADR-0085、ADR-0030）と決めており、下書きを直すたびに承認をやり直すことになる。ユーザが判断する点が増える
- **依頼の方式: マーカーを置いて hook で知らせる。** 承認の知らせ（ADR-0040）と同じく次の `UserPromptSubmit` でモデルに伝える形。
  実行ファイルと hook と state の置き場の変更が要り、どのセッションに伝えるかも決める必要がある。マーカーが許可に見える点は B と同じ
- **依頼の方式: 統合ターミナル「ccnavi」に送る。** あれはシェルで、依頼文を送るとコマンドとして実行される。`claude -p` を
  送る形は、ユーザの見ていない非対話のセッションを起こし、親のセッションの文脈も持たない
- **ボタンをボード本体（一覧）に置く。** どの子のフローかを選ぶ手間が増え、取り込む画面とも離れる
- **取り込んだ下書きを消さない。** 古い下書きが残り、「提案あり」と紛らわしい（ユーザの決定で、消す側に改めた）
- **取り込んで編集中に入れた時点で消す。** 取り消したり保存に失敗したりすると、案が消える
