# ADR-0073: 権威のツリーが無ければ元ツリーを採る

状態: 採用

## 状況

同じ識別子のチケットが複数のツリーに写るのは普通の形で（承認済みチケットは親のブランチに乗り、
そこから切ったワークツリーの数だけ写しができる。ADR-0024）、どれが本物かは**親のツリー**で決めていた。
親のツリーがその識別子を持っていなければ「決まらない」として全部を残し、状態の操作は
「複数の場所にある」で止まり、ボードは `scattered` のバッジを出していた。

権威を探す先が 1 つしか無いので、**親のワークツリーを畳んだ瞬間に権威が消える**。`docs/claude/worktree.md` の手順は
合流のあとにワークツリーを畳むので、片付けた家族はこの形に入る。2026-09-22 に手元で再現した。

```
--- 親のワークツリーがある間 ---
i0001-02 seen: [('i0001','doing'), ('i0001-02','doing')] scattered: []
--- 親のワークツリーを畳んだあと ---
i0001-02 seen: [('','doing'), ('i0001-02','doing')] scattered: [('','doing'), ('i0001-02','doing')]

$ ccnavi ticket done i0001-02
ccnavi: i0001-02 が複数の場所にある: (ワークスペースルート):doing, i0001-02:doing。1 つにしてから
```

ファイルは壊れていない。同じコミットの写しが 2 つ在るだけで、`--lint` は正しく黙っている
（`--lint` は 1 つのツリーの中で 2 つの置き場に在る形だけを咎める）。**騒いでいたのは
`ticket` の操作とボードのバッジだけ**で、しかも「1 つにしてから」と言われた人にできるのは
残ったワークツリーを畳むことだけ。文面はそれを案内しない。

同じ場面で、ボードは別の数え違いもしていた。`review/` は提案の置き場でもあり承認済みチケットでも
あるので、2 つの走査が同じファイルを拾い、`seen_in` に 2 つ、`scattered` に 2 つ出る。人の
レビューを待っているチケットは全部これに当たっていた。

## 決定

| 決めたこと | なぜ |
|---|---|
| 権威は「親のツリー → 元ツリー（ワークスペースルート。プロジェクトのチケットならそのプロジェクト）→ 決まらない」の順（`ticket.fold`、`approval._authoritative`） | ワークツリーは畳めば消えるが、元ツリーは消えない。元ツリーは合流先でもあるので、親のツリーが畳まれたあとに新しいのはそちら |
| **元ツリーより先の置き場（`todo` < `doing` < `review` < `done`）に在る写しが 1 つでもあれば、元ツリーを採らない**（`ticket.behind`） | 元ツリーを権威にしてよい根拠は「他の写しは合流の結果で、同じか手前の状態」。親のツリーで閉じ、子のツリーだけが取り込んだ形ではそれが成り立たず、採ると閉じた子をもう一度閉じ、リスクの記録を別の差分で書き直す |
| リポジトリをまたいだ衝突（同じ識別子が別のプロジェクトにある）は畳まない | 写しではなく別物。権威を決めるとどちらかが黙って消え、`--lint` の「複数のリポジトリにある」も出なくなる |
| `--lint` の「複数の場所にある」も `ticket.collisions` を通し、作業中の写しを `by_id` で畳まずに数える | 畳んで 2 つ以上残る形（＝操作が止まる形）を、`--lint` はそれまで黙って見逃していた。CI が言えない止まり方を残さない |
| 止める文面に次の一手を書く（`ops._undecided`） | 写しはどれも追跡されたファイルなので、「1 つにしてから」だけでは受け取った側にできることが読めない |
| ボードの `scattered` は `ticket.collisions` が決め、`--lint` と同じ関数（`ticket.collided_states`）を通る | README は前から「`--lint` が ERROR で言うのと同じ条件」と書いていたが、実際は違う条件だった。2 か所に同じ規則を書かない |
| `scattered` は「畳んでも 2 つ以上残る」と「1 つのツリーの中で 2 つの置き場に在る」の 2 つを見る | 前者は状態の操作が止まる形、後者は `--lint` が ERROR で言う形。板は「いま止まる理由」を出す画面なので、両方が要る |
| 写りの一覧は同じファイルを 2 度数えない（`diagnose._one_per_file`） | `review/` を 2 つの走査が拾う。同じ実体を 2 つと数えると、レビュー待ちが全部「複数の場所にある」になる |

咎める側は変えていない。同じツリーの中で `doing/` と `done/` に在る形（動かす途中で止まった跡）は
今までどおり `--lint` の ERROR で、状態の操作も止まる。

## 理由

**止まる形を減らしたのではなく、決まる形を増やした。** 「決まらないから止める」は、本当に
決まらないときだけ価値がある。元ツリーの写しは合流の結果そのもので、どれが本物かは決まっている。
決まっているものを止めると、人は毎回「1 つにしてから」を回避する手（ワークツリーを消す、
バッジを無視する）を覚え、**本物の食い違いのときも同じ手で通す**。

## 得たもの・失ったもの

- 得たもの: 合流して片付けた家族の `start` / `done` が通る。ボードのバッジが、いま止まる理由の
  ときだけ出る
- 得たもの: レビュー待ちのチケットに出ていた誤りのバッジが消える
- 失ったもの: 元ツリーを採る根拠は「合流先だから」であって保証ではない。置き場が先へ進んでいる
  写しは `behind` が見るが、**同じ置き場のまま中身だけが進んだ写し**（本文やリスクの記録の更新）は
  見分けられず、操作は元ツリーの側に当たる
- 失ったもの: **元ツリーが権威になると、状態の移動は元ツリーの作業ツリーに書かれる。** 親の
  ワークツリーを畳んだ後の `done` は、ワークスペースルート（プロジェクトなら元リポジトリ）の
  `.ccnavi/approved/` を書き換えて未コミットで残す。`ccnavi-push-approved.sh` はそこを push しないので、
  運ぶのは人の手になる。止まったままよりは進むが、「通れば運ばれる」ではない
- 失ったもの: 権威の順が 3 段になり（親のツリー → 元ツリー → 先の写しが無いこと）、「どれを
  読んでいるか」を追うのに段が増えた
- 失ったもの: 要件 REQ-MLT-30 を改めた。旧い文面（「親のツリーが持たないときにかぎり見つかった側」）で
  書かれた読み手は、新しく探す先を知らない

## 採らなかった案

- **バッジだけ消す。** いちばん安いが、`ticket` の操作が止まる形は残るので、人は操作が落ちて
  初めて知る。板がそれを予告するためにあることを考えると、いまより悪い
- **元ツリーを見ずに、ツリーをまたいだ食い違いを全部許す。** 閉じたチケットが、切った時点の
  写しを持つ古いワークツリーのせいで開いたものとして復活する（`approval.scan` が前から避けている形）
- **親のワークツリーを畳ませない。** 片付けの手順（`docs/claude/worktree.md`）と衝突し、ワークツリーが増え続ける
