# ADR-0073: 本物とするツリーが無ければ元ツリーを採る

状態: 採用

## 状況

同じ識別子のチケットが複数のツリー上にあるのは普通の形で（承認済みチケットは親のブランチに乗り、
そこから切ったワークツリーの数だけ同じチケットが並ぶ。ADR-0024）、どれが本物かは**親のツリー**で決めていた。
親のツリーがその識別子を持っていなければ「決まらない」として全部を残し、状態の操作は
「複数の場所にある」で止まり、ボードは `scattered` のバッジを出していた。

本物を探す先が 1 つしか無いので、**親のワークツリーを片付けた時点で本物とする側が消える**。`docs/claude/worktree.md` の手順は
合流のあとにワークツリーを片付けるので、片付けた親子はこの形に入る。2026-09-22 に手元で再現した。

```
--- 親のワークツリーがある間 ---
i0001-02 seen: [('i0001','doing'), ('i0001-02','doing')] scattered: []
--- 親のワークツリーを畳んだあと ---
i0001-02 seen: [('','doing'), ('i0001-02','doing')] scattered: [('','doing'), ('i0001-02','doing')]

$ ccnavi ticket done i0001-02
ccnavi: i0001-02 が複数の場所にある: (ワークスペースルート):doing, i0001-02:doing。1 つにしてから
```

ファイルは壊れていない。同じコミットのチケットが 2 つのツリー上に在るだけで、`--lint` は正しく何も言わない
（`--lint` は 1 つのツリーの中で 2 つの置き場に在る形だけを報告する）。**問題として出していたのは
`ticket` の操作とボードのバッジだけ**で、しかも「1 つにしてから」と言われたユーザにできるのは
残ったワークツリーを片付けることだけ。文面はそれを案内しない。

同じ場面で、ボードは別の数え違いもしていた。`review/` は提案の置き場でもあり承認済みチケットでも
あるので、2 つの走査が同じファイルを拾い、`seen_in` に 2 つ、`scattered` に 2 つ出る。ユーザの
レビューを待っているチケットは全部これに当たっていた。

## 決定

| 決めたこと | なぜ |
|---|---|
| 本物とする側は「親のツリー → 元ツリー（ワークスペースルート。プロジェクトのチケットならそのプロジェクト）→ 決まらない」の順（`ticket_fold.fold`、`approval._authoritative`） | ワークツリーは片付ければ消えるが、元ツリーは消えない。元ツリーは合流先でもあるので、親のツリーが片付けられたあとに新しいのはそちら |
| **元ツリーより先の置き場（`todo` < `doing` < `review` < `done`）に在るチケットが 1 つでもあれば、元ツリーを採らない**（`ticket_fold.behind`） | 元ツリーを本物としてよい根拠は「他のツリー上のチケットは合流の結果で、同じか手前の状態」。親のツリーで閉じ、子のツリーだけが取り込んだ形ではそれが成り立たず、採ると閉じた子をもう一度閉じ、リスクの記録を別の差分で書き直す |
| リポジトリをまたいだ衝突（同じ識別子が別のプロジェクトにある）は 1 つにまとめない | 同じチケットではなく別物。どちらを本物とするか決めると、どちらかが知らないうちに消え、`--lint` の「複数のリポジトリにある」も出なくなる |
| `--lint` の「複数の場所にある」も `ticket_fold.collisions` を通し、作業中のツリー上のチケットを `by_id` でまとめずに数える | まとめても 2 つ以上残る形（＝操作が止まる形）を、`--lint` はそれまで何も言わずに見逃していた。CI が言えない止まり方を残さない |
| 止める文面に次の一手を書く（`ops_close._undecided`） | どのツリー上のチケットも追跡されたファイルなので、「1 つにしてから」だけでは受け取った側にできることが読めない |
| ボードの `scattered` は `ticket_fold.collisions` が決め、`--lint` と同じ関数（`ticket_fold.collided_states`）を通る | README は前から「`--lint` が ERROR で言うのと同じ条件」と書いていたが、実際は違う条件だった。2 か所に同じ規則を書かない |
| `scattered` は「1 つにまとめても 2 つ以上残る」と「1 つのツリーの中で 2 つの置き場に在る」の 2 つを見る | 前者は状態の操作が止まる形、後者は `--lint` が ERROR で言う形。ボードは「いま止まる理由」を出す画面なので、両方が要る |
| 在る場所の一覧は同じファイルを 2 度数えない（`diagnose_board._one_per_file`） | `review/` を 2 つの走査が拾う。同じ実体を 2 つと数えると、レビュー待ちが全部「複数の場所にある」になる |

ERROR にする側は変えていない。同じツリーの中で `doing/` と `done/` に在る形（動かす途中で止まって残ったもの）は
今までどおり `--lint` の ERROR で、状態の操作も止まる。

## 理由

**止まる形を減らしたのではなく、決まる形を増やした。** 「決まらないから止める」は、本当に
決まらないときだけ価値がある。元ツリー上のチケットは合流の結果そのもので、どれが本物かは決まっている。
決まっているものを止めると、ユーザは毎回「1 つにしてから」を回避するやり方（ワークツリーを消す、
バッジを無視する）を覚え、**本物の食い違いのときも同じやり方で通す**。

## 得たもの・失ったもの

- 得たもの: 合流して片付けた親子の `start` / `done` が通る。ボードのバッジが、いま止まる理由の
  ときだけ出る
- 得たもの: レビュー待ちのチケットに出ていた誤りのバッジが消える
- 失ったもの: 元ツリーを採る根拠は「合流先だから」であって保証ではない。置き場が先へ進んでいる
  チケットは `behind` が見るが、**同じ置き場のまま中身だけが進んだチケット**（本文やリスクの記録の更新）は
  見分けられず、操作は元ツリーの側に当たる
- 失ったもの: **元ツリーを本物とすると、状態の移動は元ツリーの作業ツリーに書かれる。** 親の
  ワークツリーを片付けた後の `done` は、ワークスペースルート（プロジェクトなら元リポジトリ）の
  `.ccnavi/approved/` を書き換えて未コミットで残す。`ccnavi-push-approved.sh` はそこを push しないので、
  コミットと push はユーザの手になる。止まったままよりは進むが、「通ればコミットされて push される」ではない
- 失ったもの: 本物とする側を決める順が 3 段になり（親のツリー → 元ツリー → 先へ進んだチケットが無いこと）、「どれを
  読んでいるか」を追うのに段が増えた
- 失ったもの: 要件 REQ-MLT-30 を改めた。旧い文面（「親のツリーが持たないときにかぎり見つかった側」）で
  書かれた読み手は、新しく探す先を知らない

## 採らなかった案

- **バッジだけ消す。** いちばん安いが、`ticket` の操作が止まる形は残るので、ユーザは操作が落ちて
  初めて知る。ボードがそれを予告するためにあることを考えると、いまより悪い
- **元ツリーを見ずに、ツリーをまたいだ食い違いを全部許す。** 閉じたチケットが、切った時点の
  チケットを持つ古いワークツリーのせいで開いたものとして復活する（`approval.scan` が前から避けている形）
- **親のワークツリーを片付けさせない。** 片付けの手順（`docs/claude/worktree.md`）と衝突し、ワークツリーが増え続ける
