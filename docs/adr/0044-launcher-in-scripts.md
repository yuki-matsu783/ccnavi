# ADR-0044: 振り分けの sh は `.ccnavi/scripts/` に、実行ファイルは `.ccnavi/bin/<os>-<arch>/` に固定する

状態: 採用

## 状況

ADR-0041 で、実行ファイルを機械ごとの置き場に並べ、hook は振り分けの sh を起動する形にした。その時点の置き場は次のとおり。

| 何 | ccnavi のリポジトリ | 配布先 |
|---|---|---|
| 振り分けの sh | 原本 `scripts/ccnavi-launcher.sh` | `.ccnavi/bin/ccnavi`（導入スクリプトの `--bin` で動く） |
| 実行ファイル | `dist/ccnavi/`（組み立ての出力） | sh の隣の `<os>-<arch>/` |
| `CCNAVI_BIN_PATH` | `dist/ccnavi/ccnavi` | `.ccnavi/bin/ccnavi` |

これには 3 つの食い違いがあった（2026-09-13 に確かめた）。

- `.ccnavi/scripts/` は「原本と配布先が同じ綴りで、置いた場所でそのまま動く sh」の置き場で、ゲートの sh はそこにある。
  振り分けの sh は配布先の hook が必ず通るのに、原本と配布先で名前も場所も変わっていた
- `.ccnavi/bin/` に sh と実行ファイルが混ざっていた
- このリポジトリの hook は `dist/ccnavi/ccnavi` を直に起動していて、振り分けの sh を通らなかった。同じフォルダを
  Windows と WSL から開くと片方で起動しない。sh の不具合にも、配布先で起きるまで気づけない

## 決定

置き場を 2 つに分けて固定する。

| 何 | ccnavi のリポジトリ | 配布先 |
|---|---|---|
| 振り分けの sh | `.ccnavi/scripts/ccnavi-launcher.sh`（追跡。モード 100755） | 同じ綴り（導入スクリプトが配る） |
| 実行ファイル | `dist/ccnavi/`（組み立ての出力）と、`build.py` がそこから写す `.ccnavi/bin/<os>-<arch>/`（無視） | `.ccnavi/bin/<os>-<arch>/`（導入スクリプトが配る。無視） |
| `CCNAVI_BIN_PATH` | `.ccnavi/scripts/ccnavi-launcher.sh` | 同じ |

- **sh は自分の隣ではなく `../bin/` を探す。** 隣（`.ccnavi/scripts/<os>-<arch>/`）は配る場所ではないので探さない。
  見つからなければ 127 で終わり、文面にこの機械の `<os>-<arch>` と探した場所を出す。探す順（`uname -sm` を 1 回、
  arm64 の macOS と Windows は自分向けが無いときだけ x86_64）は ADR-0041 のまま
- **導入スクリプトの `--bin` を廃止する。** 渡されたら終了コード 2 で断り、何も書かない
- **sh を追跡し、実行ビットを git のモードで運ぶ。** 導入スクリプトは sh を配る回に `chmod +x` を付け直す。
  設定 lint は、`CCNAVI_BIN_PATH` の指す先が在るのに実行できなければ error（POSIX だけ）、前の既定の綴りなら warn を出す
- **自己防衛の `binary_clause` と `launched_executable` は、`CCNAVI_BIN_PATH` の名前が `ccnavi-launcher.sh` なら `../bin/` を、
  それ以外なら前の形（隣の `<os>-<arch>/`）を見る。** 切り替えの条件は名前だけで、2 つで揃える。前の形は、
  導入スクリプトを打ち直すまでの配布先のために残す

**移し替え。** 導入スクリプトは `CCNAVI_BIN_PATH` を次のように扱う。

| 今の値 | 動き |
|---|---|
| 無い | 新しい綴りを書く |
| `.ccnavi/scripts/ccnavi-launcher.sh` | 何もしない |
| 前の既定（`.ccnavi/bin/ccnavi`）で、新しい置き場で起動できる | 新しい綴りへ書き換える |
| 前の既定で、新しい置き場で起動できない | 書き換えず、理由を 1 行出す |
| それ以外（既定でない綴り） | 書き換えず、名指しで 1 行出す。導入は止めず、終了コードも変えない（`--check` では揃っていない側に数える）。前の sh にも触らない |

**前の `.ccnavi/bin/ccnavi` を消す条件。** 次のすべてが揃ったときだけ消す。`--check` では消さずに名前を挙げる。
同じ置き場の `<os>-<arch>/` は新しい置き場そのものなので触らない。

1. リンクでない、通常のファイルとして在る
2. この回に `CCNAVI_BIN_PATH` を前の既定から書き換えた、または既に新しい綴りを指している。
   env が無かった回と既定でない綴りの回は消さない
3. 書き終えたあとの `CCNAVI_BIN_PATH` がそこを指さない
4. 新しい置き場で hook が起動できる
5. 導入スクリプトを打ったセッションの env の `CCNAVI_BIN_PATH` がそこを指さない。指していれば消さず、
   開き直してから打ち直すよう 1 行出す（ADR-0041 と同じ扱い）

機械ごとに並べる、sh が起動のたびに選ぶ、語を `platformtag.py`・sh・導入スクリプト・拡張で揃える、は ADR-0041 から引き継ぐ。
置き換えるのは置き場と `--bin` の部分。

## 理由

振り分けの sh は「原本と配布先が同じ綴りで、置いた場所でそのまま動く sh」に当てはまる。`.ccnavi/scripts/` に置けば、
ゲートの sh と同じ手順で配り、同じ綴りで守れる。

置き場が固定なら、sh は自分の位置から実体を一意に決められる。`--bin` と「隣を探す」は、置き場が動くことの
帳尻を合わせるためのものだったので、要らなくなる。隣を探さないのは、探すと自己防衛の綴りが当たらない置き場から
実体を起動する道ができるため。

このリポジトリも配布先と同じ経路（env → sh → `.ccnavi/bin/<os>-<arch>/`）を通る。sh の不具合は、ここで先に踏む。

`--bin` を受けて無視せず断るのは、名指しを黙って無視すると、打った人は指した場所に置いたつもりで進むため。

移し替えを前の既定の綴りに限るのは、ADR-0041・ADR-0042 と同じく、人が決めた綴りの先で何が使われているかを
導入スクリプトが決められないため。既定でない綴りのときに前の sh まで残すのは、文面の
「前に置いた sh と実行ファイルは消していません」と揃えるため。

消す条件の 2 を「書き換えた回」だけにしないのは、打ったセッションの env が前の綴りだったために消さなかった回
（条件 5）の次に、開き直して打ち直した回で消すため。その回には env は既に新しい綴りで、書き換えは起きない。
env が無かった回に消さないのは、その sh を何が起動しているかを settings.json から読めないため。書いた次の回に消す。

## 得たもの・失ったもの

- 得たもの: 原本と配布先で sh の綴りが同じになり、`.ccnavi/bin/` は実行ファイルだけになる
- 得たもの: このリポジトリも、Windows と WSL で同じ hook が起動する。sh の不具合に自分で気づける
- 失ったもの: このリポジトリでも、ツール呼び出しのたびに sh の起動と `uname` 1 回ぶんが乗る
- 失ったもの: 組み立てたあと、`build.py` が `.ccnavi/bin/<os>-<arch>/` に写し終えるまで、hook は新しい実行ファイルを起動しない。
  `build.py` が ccnavi ディレクトリに書くようになる。入れ替え（rename 2 回）の間の数 ms に来た hook は 127 で終わり、
  その 1 回は判定が走らない（止まらない側になる）
- 失ったもの: `--bin` で置き場を動かしていた配布先は、手で戻す必要がある。`--bin` を書いた手順書や CI は 2 で止まる
- 失ったもの: 自己防衛の対象が `.ccnavi/scripts/` と `.ccnavi/bin/` の 2 か所に分かれ、`binary_clause` と
  `launched_executable` が sh の名前で 2 つの形を持つ。別の名前で置いた sh は前の形で扱われ、その `../bin/` は守りから外れる
- 失ったもの: 既定でない浅い綴り（`scripts/ccnavi-launcher.sh`、`ccnavi-launcher.sh`）では、相対のシェル書き込み
  （`rm -rf bin/linux-x86_64`）が実行ファイルの守りに当たらない。導入スクリプトはその綴りを作らない。実行後の控えと復元は効く。
  前の形にも同じ種類の限界があった
- 失ったもの: sh を追跡すると、実行ビットを git のモードで運ぶことになる。Windows（`core.filemode=false`）で最初に
  足すと 100644 で入り、別の機械で clone した直後は導入スクリプトを打つまで hook が 126 で起動しない
- 失ったもの: 前の `.ccnavi/bin/ccnavi` を消すのは戻せない。消すのは前の版の導入スクリプトが配った、無視されている
  生成物だけで、前の版で配り直せる
- 失ったもの: このリポジトリの切り替えは、エージェントの範囲の外の手順になった。人が sh を `.ccnavi/scripts/` に写し、
  `.gitignore` に `/.ccnavi/bin/` を足し、スキルの綴りと `CCNAVI_BIN_PATH` を直し、ワークスペースルートで組み立ててから
  開き直す。順を誤ると hook が 126 か 127 で起動しない

## 採らなかった案

- 自分のリポジトリに導入スクリプトを当てて配る。組み立てのたびに 1 手増える
- sh を `.ccnavi/bin/` に残して名前だけ揃える。sh と実行ファイルが混ざったまま残る
- hook の `command` を `sh "…"` にする。実行ビットは要らなくなるが、登録済みの hook の書き換えと見分けが要り、範囲が広がる
- 配布先では sh を無視し、機械ごとに配る。同じ置き場に追跡するものと無視するものが混ざる
- `--bin` を受けて無視し、1 行出す。打った人が指した場所に置いたつもりで進む
- 名前が `ccnavi-launcher.sh` でない `CCNAVI_BIN_PATH` の「隣を探す」形を消す。打ち直すまでの間、隣の実体の守りと控えが外れる
- `bin/<os>-<arch>` を位置を問わず守り、浅い綴りの相対の書き込みも塞ぐ。どのディレクトリの `bin/linux-x86_64` にも当たり、
  1 段の綴り（`../bin/`）はそれでも塞がらない
- 前の `.ccnavi/bin/ccnavi` を「この回に書き換えたとき」だけ消す。打ったセッションの env のために消さなかった前の sh が、
  開き直して打ち直しても残り続ける
