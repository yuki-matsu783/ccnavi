# ADR-0058: 承認できるかはエージェントが先に確かめ、その案内は組み込みの allow が渡す

状態: 採用

## 状況

提案を書いたエージェントには、それが承認できる形かどうかを知る手立てが無かった。承認の対象を
組むのは `approval.gather` で、それを通るのは人が打つ `--approve` と、VS Code のボードが打つ
`--approve --preview --json` の 2 本。前者は端末を求め、後者は一覧を見せるための枝で、
承認の対象にしない提案（親が承認されていない、計画に無いフェーズ、範囲の書き損じ）があっても
0 で返る。読む側のボードが 0 以外を失敗として扱うので、そこで 1 を返すと一覧が出せなくなるため。

その結果、落ちたことを最初に知るのは端末に座った人になっていた。往復が 1 回増えるだけでなく、
人の承認という門の前に「エージェントの書き損じ」を並べることになる。門は人の判断のためにあり、
形の検査のためではない。2026-09-17。

案内の届け方にも穴があった。確かめる手立てを文書に書いても、提案を書いている最中のエージェントに
届くとは限らない。ccnavi は「要る場所で言う」を採ってきた（`reasons.py` の冒頭）のに、
提案を書いた回に言うものが無かった。

## 決定

- **確かめる枝は `--approve --preview --check` として `--preview` に相乗りさせる。** 新しい免除の語を
  足さない。組み込みの deny（`builtin-guard-ticket-approval`）が免除するのは `--preview` の付いた
  `--approve` だけで、その綴りは 1 語のまま動かない
- **答えは終了コードで返す。** 0 = 指定したもの（指定が無ければ承認待ち全部）がそのまま承認の
  対象に入る、1 = 入らない。読む相手がエージェントなので、文だけでは判断がその場の読みに委ねられる
- **判定は `gather` の 1 か所に置く。** `--check` は読み替えるだけ。承認と確かめで答えが割れない
- **`--approve` が落とさないものでは落とさない。** 範囲の超過（判定が切り詰めるだけ）と、
  読めない提案（走査は絞る前の全ツリーを見る）。どちらも本文には出す
- **提案を書いた回に、この確認を 1 度だけ勧める。** `wip/proposals/todo/` への Write / Edit に
  当たる組み込みの allow（`builtin-ticket-propose`）が `additionalContextOnce` で渡す。止めない

## 理由

**免除を広げないために相乗りさせた。** ADR-0040 が「免除は許さない側から書く」と決めた場所で、
そこに新しい語を足すのは、免除の条件を 1 つ増やすこと。`--check` は `--preview` を要求し、
単独で打てば使い方の誤りとして 1 で返る。免除の正規表現は 1 文字も変わっていない。

**`--preview` の終了コードは変えなかった。** ボードのオーバーレイは `--preview --json` の
0 以外を失敗として扱う。そこに答えを載せると、承認の対象にしない提案が 1 件あるだけで
一覧が出せなくなる。見せる枝と確かめる枝は、読む相手が違う。

**読めない提案で落とさないのは、承認が落とさないから。** 走査は全ツリー（絞る前）を見るので、
他のセッションの書きかけ 1 本で「確かめでは 1、承認は 0」になる。確かめが嘘をつく形にすると、
確かめる習慣のほうが先に壊れる。黙らせもしない。自分が書いた 1 本かもしれないので、
件数と綴りは本文に出す。

**案内をルールファイルではなく組み込みに置いた。** `.ccnavi/common/rules.yml` は保護済みで、
人が写す手順（`staging` のフェーズ）が要る。確かめる枝と同じ版で届かないと、案内した綴りが
その配布先に無い、という食い違いが起きる。実行ファイルと一緒に動くものは実行ファイルが持つ。

## 代償

- **`todo/` への書き込みが「ccnavi が言及する場所」になる。** ルールファイルがそこに何も
  言っていないワークスペースでは、いままで「どのタイプも言及しない」に落ちていた。そこで
  外れる止まりが 2 つある。確認できる者が居ないモード（`dontAsk` / `bypassPermissions`）の deny と、
  知らない綴りのモードを ask に倒す既定。**`CCNAVI_GUARD_UNWATCHED=enable`（既定）でも外れる**
  （組み込みの allow は、その門に届く前の段で当たる）。提案を書けなければチケット制御そのものが
  始まらないので通す側へ倒したが、この 1 経路だけは、確認できない側の扱いをプロジェクトが
  選べる範囲（ADR-0049）から外れる。緩むのはその置き場の中だけで、同じツリーの他の場所は
  変わらない（`tests/ticket/test_approve_check.py` が杭を打つ）。人が書いた `deny` と `ask` も
  動かない（判定は強いタイプから見て最初に当たった段で決まる）
- **当てる正規表現は deny 用に書かれたものの転用。** `(^|[\\/])` のアンカーは「前に何が来ても
  よい」ので、ticket の機構と関わりなく `wip/proposals/todo/` という並びを持つディレクトリ
  （取り込んだ他所のコード、固定データ）にも当たる。deny 側では余分に止めるだけで安全側だが、
  allow 側では上の止まりが外れる側へ効く
- **`--check` を足したことで `--ch` が曖昧になった。** argparse の接頭辞省略で `--chat` と
  重なる。リポジトリの中に `--ch` と書いている場所は無いが、省略形に頼った外の呼び出しは
  無言で 1 で終わる
- **枝が 3 本になった。** `--approve` / `--preview` / `--preview --check` は同じ `gather` を通るが、
  読む側から見ると「置く・見せる・答える」の 3 つを覚えることになる
- **確かめは合意ではない。** 0 で返っても、承認そのものは人が通す。確かめが通ることを
  「承認されたも同然」と読む道ができる（文面は「利用者に承認を依頼してよい」で止めてある）

## 採らなかった案

- **`--approve --dry-run` を新設する。** 綴りが短く、利用者の言葉（dry-run）にも近い。採らなかった
  のは、組み込みの deny の免除に語を 1 つ足すことになるため（ADR-0040）。加えて ccnavi の
  `dry-run` は「判定するが止めない」の意味で使っており、同じ語が 2 つの意味を持つ
- **`ccnavi-ticket.sh` に `check` を足す。** エージェントの入口が 1 本に揃う。採らなかったのは、
  `.ccnavi/scripts/` が保護済みで人が写す手順が要り、判定の読み取り（JSON）が sh の側に乗るため
- **`--preview` 自身の終了コードを答えにする。** 枝が増えない。採らなかったのは、ボードが
  一覧を出せなくなるため（上の理由）
- **案内を `.ccnavi/common/rules.yml` に書く。** 実行ファイルを触らずに済み、配布先ごとに
  文面を変えられる。採らなかったのは、保護済みファイルなので人が写すまで届かず、確かめる枝と
  同じ版で配れないため
- **案内を `PostToolUse` で渡す。** 書けたあとに言うので「書いた回」に正確に当たり、判定にも
  触らない（上の代償が丸ごと消える）。採らなかったのは、`post.py` が見ているのが保護された
  場所の変更で、そこに「通った書き込みへの助言」を足すと、あの経路の役目が 2 つになるため。
  代償を嫌うならここが次の候補になる
- **セッション開始の案内（`reasons.py`）に 1 行足す。** 判定に触らない。採らなかったのは、
  あの文が「線引きと入口だけ」と決めてあり、要る場所で言うほうが届くため
