# ADR-0091: プロジェクトのスキルは `docs/skills/` に置き、ccnavi は目録だけを渡す

状態: 採用

## 状況

振り返り（ADR-0090、`docs/claude/skill-review.md`）で拾った手順を、プロジェクトの作業にも残したいという要望が出た
（2026-09-27）。スキルの置き場は Claude Code の決まりでは `.claude/skills/` だが、プロジェクトは `.claude/` を持たない
決まり（ADR-0033、REQ-MLT-16）。Claude Code がそこのスキルを読み、ワークスペースルートの決め方も最初の `.claude/` で
止まるので、cd 1 回で別のルートに見える。

最初は ccnavi ディレクトリの `.ccnavi/skills/` に置いた。そこは組み込みの守りが丸ごと止めるので、承認したチケットの
中でもエージェントが書けず、ユーザが写すしかなかった。ユーザと相談して `docs/skills/` に移した（同日）。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| 置き場は `projects/<名前>/docs/skills/<スキル>/SKILL.md`。形は Claude Code のスキルと同じ（frontmatter の `name` / `description`、任意の `references/`） | ADR-0033 を守ったまま、プロジェクトの git に入る。守りの外のふつうの場所なので、ほかのファイルと同じく、承認したチケットの範囲（`skill-improve` のフェーズの子や提案チケット）の中で書け、マージリクエストで見てもらえる。守りは 1 つも変えない | `.ccnavi/skills/`（最初の形）。書かせるには `builtin-guard-project-home` とシェルの `builtin-guard-setting-files` から穴を開ける必要があり、「`.ccnavi/` の下は丸ごとユーザのもの」に例外が増える。開けなければユーザが写すしかない |
| ccnavi は `SessionStart` と `SubagentStart` で、cwd がそのプロジェクトのツリーの中にあるときだけ目録（名前・説明・場所）を渡す。本文は渡さない | Claude Code のスキルと同じく、要るときに開く。本文まで渡すと、プロジェクトに入るたびに文脈が膨らむ | 本文を渡す。数が増えると文脈を圧迫する |
| cwd がそのプロジェクトの中にある最初の `PreToolUse` でも、同じ目録を 1 度だけ添える（`additionalContextOnce` と同じ状態ファイル、鍵はプロジェクトごと） | セッションはワークスペースルートで始まり、あとから `cd` で入るのがふつう。開始だけでは届かない（レビューで指摘） | 開始だけにして、限界として書く |
| 見出しは「参考に読む。CLAUDE.md・ccnavi の知らせ・ガードと食い違えばそちらに従う」 | 外のリポジトリの文なので、従うべき指示として渡さない | 「開いて従う」（最初の形） |
| スキルのディレクトリ名は `^[A-Za-z0-9._-]+$` のものだけを読み、パスも 1 行にまとめる。区切りの行の文は子のフローと同じ表（`flow._FENCE_PHRASES`）に並べて置き換える | ディレクトリ名はパスとしてそのまま文に出る。改行や区切りの文、`[ccnavi]` を名前に入れて偽の知らせを組めた（レビューで再現） | 名前を素のまま出す |
| 読むのは元リポジトリの版。ふつうのファイルで途中にリンクの無いものだけを読み（`flow.read_bytes`）、名前と説明は 1 行にまとめて切り、データとして囲む。30 本・4000 文字まで | プロジェクトのリポジトリの文は誰が書いたか ccnavi には分からない。子のフロー（ADR-0085）と同じ扱いにする | 素のまま渡す。偽の知らせを混ぜられる |
| フロー編集画面の候補（`flow.candidates`）には載せない | フローの `skill` に書けるのは Claude Code が起動できるスキルで、プロジェクトのスキルは当たらない | 候補に載せる。起動できない名前を選べてしまう |

## 得たもの・失ったもの

- 得たもの: `.claude/` を置かず、守りも変えずに、プロジェクト向けの手順をプロジェクトの git で育てられる。直すのはチケットの中のエージェントで、ユーザはマージリクエストで見る
- 失ったもの: **`docs/skills/` は ccnavi が持つ場所だと見た目で分からない。** プロジェクトの文書の一部に見え、ユーザが ccnavi と無関係に置いた `docs/skills/` も目録に載る。
  名前がぶつかるプロジェクトでは置き場を選べない（パスは固定）
- 失ったもの: **守りの外なので、チケットの無いワークツリー（直接作業）からは、ほかのファイルと同じく承認なしで書ける。** 振り返りでは書かない決まり（`skill-review.md`）に頼る。
  書いたものはそのブランチを統合するまで元リポジトリに入らず、目録は元リポジトリの版しか読まないので、統合の手前でユーザの目は入る
- 失ったもの: **Claude Code のスキルとしては起動されない。** `Skill` ツールで呼べず、説明に合う作業で自動で読まれることもない。
  目録を見たエージェントが自分で開く
- 失ったもの: cwd がワークスペースルートのまま絶対パスでプロジェクトを触るセッションには届かない（cd で入った場合は最初の呼び出しで届く）
- 失ったもの: 目録は文脈ごとにプロジェクトごと 1 度だけ。途中でスキルが増えても、次の開始（compact の後を含む）まで届かない
- 失ったもの: 名前に英数と `._-` 以外（日本語など）を使ったスキルは目録に載らない

## 採らなかった案

- **`projects/<名前>/.claude/skills/`。** Claude Code がそのまま読むが、ADR-0033 の理由がそのまま当たる
- **`projects/<名前>/.ccnavi/skills/`（最初の形）。** ccnavi が持つ場所だとはっきりするが、組み込みの守りを緩めないとエージェントが書けない（上の表）
- **ワークスペースの `.claude/skills/` にプロジェクトごとの節を置く。** プロジェクトだけを clone したユーザには届かず、プロジェクトの git で育たない
