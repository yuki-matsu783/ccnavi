# ADR-0061: 拡張のテストもターンの終わりに回し、回すのは触ったファイルが関わるグループだけ

状態: 採用

## 状況

拡張（`vscode-extension/ccnavi-board`）のテスト 203 本は、人が `pnpm test` を打ったときにしか
回らなかった。このリポジトリに CI は無く、`.claude/hooks/` の登録対象でもないので、ターンの
終わりに走る Python のテスト（ADR-0036）にも乗っていない（issue #89）。

`package.json` にはグループごとの行（`test:board`・`test:rules` など）が 8 行あり、どの行も
`clean-out` → `tsc -p tsconfig.test.json` → 束ね → `node --test` を自分で並べていた。`tsc` は
`src/` と `test/` を全部見るので、グループを絞ってもコンパイルは安くならない。

## 決定

| 決めたこと | なぜ |
|---|---|
| ターンの終わり（`Stop`）に `.claude/hooks/test-ext.sh` で回す。編集ごとには回さない | ADR-0036 と同じ。1 ファイル直すたびに全件を走らせると、複数ファイルにまたがる変更では途中の状態が必ず落ちる |
| 拡張のファイルを触っていないターンは何もしない | 文書だけのターンや Python だけのターンを待たせない。触ったかどうかは `PostToolUse` の `.claude/hooks/mark-ext.sh` が `logs/session/<セッション>.ext-files` に書き残す |
| 回すのは、触ったファイルが関わるグループだけ。決めるのは `vscode-extension/ccnavi-board/scripts/test-groups.js` | 関わらないテストを回しても何も確かめない。`src/core/risk-doc.ts` を直したターンで board の 63 本は何も言わない |
| どのグループがどのファイルを読むかは、テストの `import` を辿って数える。辿れないものだけ綴りで決める | 全部を表にすると、ファイルを増やしたときに黙って古くなる。辿れないぶんは残るので「表が無い」わけではない（下記） |
| コンパイルは、いくつグループを選んでも 1 回 | `tsc` は `src/` と `test/` を全部見るので、グループを絞っても安くならない。安くなるのは実行のほうだけ |
| `package.json` のテストの 8 行は全部この 1 本に寄せる | 8 か所に同じ工程が並んでいると、工程を直すときに 8 か所直すことになる |
| 画面の束ね（esbuild、0.1 秒）は、画面の型を見ないときでも必ず回す | `clean-out.js` が `out/webview` を消すので、作り直さないと、束ねたものを読む側（拡張の `webview-script.ts`、board のテスト）が「画面が束ねられていない」で落ちる |
| `node --test` は spec レポータで回す | 端末でないとき node は TAP を出し、`not ok` は落ちたファイルの位置に出る。hook がモデルへ渡せるのは末尾 40 行なので、TAP だと「落ちた」とだけ伝わって何が落ちたかが入らない |
| 差し戻しは 3 回まで。回数のファイルは `test-py.sh` と分ける | 上限の理由は ADR-0036 と同じ。別々に数えるのは、片方の失敗で他方の残り回数が減らないため |
| 環境が足りないとき（`node_modules` が無い）は終了コード 3 で、差し戻しに数えない | テストは落ちていないので、「落ちたテストを直してから終わってください」は嘘になる。人に `pnpm install` を頼む |
| このリポジトリの `.claude/settings.json` には登録しない（**利用者の判断を待っている**） | `test-py.sh` と揃えてある。ただし ADR-0036 が登録しなかった理由（数分かかるテストが文書だけのセッションまで待たせる）は、触っていないターンが 0 秒のこの hook には当たらない。登録すべきかは人が決める |

`import` では辿れないものは 6 つあり、それぞれ綴りで決める。**ここは表であり、古くなりうる。**

| 綴り | 何を回すか | なぜ辿れないか |
|---|---|---|
| `test/fixtures/` | 全グループ | 実行時に名前で開く |
| `src/webview/` | 辿れたぶん ∪ 束ねたものを読むグループ | esbuild が束ね、テストは束ねたものを読む |
| `package.json`・`pnpm-lock.yaml`・`tsconfig*.json`・`scripts/` | 全グループ | 組み立ての土台 |
| `*.md`・`media/` | 何も回さない（コンパイルもしない） | 読み物と絵 |
| `out/`・`node_modules/` | 何も回さない | 生成物と依存の置き場 |
| `test/helpers/`・`src/` のその他 | 辿って決まるぶん。どのテストも読まないなら `tsc` だけ | （辿れる） |

## 理由

`import` を辿るのは、対応を全部表に書くと「新しいテストがどのグループに要るか」を人が覚えて
いなければならなくなるため。辿るなら、ファイルを足した時点で正しい答えが出る。辿れない 6 つを
`test-groups.js` の先頭に集めてあるのは、古くなる場所をそこだけに閉じるため。

回すグループを 1 行で出す（`--plan`）のは、sh と JS の契約をその 1 行に閉じるため。sh は
`groups=... compile=... webview=...` を読むだけで、どのファイルがどのグループに属するかを
知らない。テストは sh の代わりにこの 1 行を読む。

**絞って浮く時間は、この機械で 1 ターンあたり 2.5〜4.5 秒。**（Linux 4 コア、Node 22 での実測）

| 触ったもの | 回るもの | 時間 |
|---|---|---|
| `*.md` | 何も | 0 秒 |
| `src/extension.ts` など、テストが読まないファイル | 型の検査だけ | 約 3 秒 |
| `src/core/*.ts` の大半 | そのグループ + `shared` + 画面の型検査 | 約 6 秒 |
| `src/webview/board/*.tsx` | board + shared + 画面の型検査 | 約 8 秒 |
| 全部（`pnpm test`、203 本） | 全部 | 9.5〜11.5 秒 |

**`shared` はほぼ必ず付いてくる。** `test/shared/style.test.ts` が「5 つの画面が同じ骨組みの CSS を
持つ」ことを見るために、束ねた画面を読む入口（`test/helpers/board.ts`）を辿るので、`shared` を
含む計画は必ず画面の型検査と束ねを伴う。テストが読む `src/` の 28 本のうち 27 本が `shared` を
含む。つまり実態は「そのグループ + shared」で、board の 63 本を飛ばす代わりに画面のコンパイルを
払う。`style.test.ts` を board へ移せば絞りは効くようになるが、あのテストの主題は 5 画面の
比較なので、置き場としては `shared` が正しい。絞りの値をこれ以上上げるなら、テストの分け方の
ほうを変えることになる。

## 得たもの・失ったもの

- 得たもの: 拡張を触ったターンで、`pnpm test` を打たなくても落ちたことが分かる（登録した人の手元で）
- 得たもの: 2 グループ以上を回すときコンパイルが 1 回で済む（`pnpm test:rules && pnpm test:risk`
  の 9.4 秒が `node scripts/test-groups.js rules risk` の 4.9 秒になる）
- 失ったもの: 拡張を触ったターンが 3〜8 秒伸びる
- **失ったもの（issue #89 の中心には届かない）: 混み具合で結果が変わる失敗は、この hook では
  拾えない。** issue が挙げたのは「React の描き直しを待ち切れないテストは、混んでいる機械では
  落ちることがあり、1 回打って通ったかどうかでは分からない」。この hook がするのは、同じ機械で
  1 回回すことで、検出力は人が 1 回打つのと同じ。そこに効くのは道 1（CI で別の機械・複数回）か、
  同じテストを繰り返す枝で、どちらも入れていない
- **失ったもの: 登録は任意なので、取り込んだだけでは誰の手元でも 1 本も回らない。**
  `settings.local.json` に足した人だけが気づける
- 失ったもの: Bash で変えたものには印が付かない（`sed -i`、`ccnavi-git.sh merge` で入ってきた
  変更、`pnpm install` による lockfile の変更）。印を書くのは `PostToolUse` の `Write|Edit` だけ。
  このリポジトリはヒアドキュメントを判定で止めていて Write/Edit に寄せてあるので大半は拾えるが、
  拾えない道は残る
- 失ったもの: 同じツリーで 2 つ同時に回すと、`clean-out.js` が相手の `out/` を消して偽の失敗に
  なりうる（`pnpm test` を 2 つ走らせたときと同じだが、ターンの終わりに自動で走るぶん当たりやすい）
- 失ったもの: hook が 2 本増えた（`mark-ext.sh`・`test-ext.sh`）。拡張には整形も静的検査も
  無いので、`lint-py.sh` のように「もう走っている hook に相乗り」ができなかった
- 失ったもの: 記録のファイルが 1 セッションに 2 つ増える（`.ext-files`・`.ext-retries`）。
  掃除は `test-py.sh` と同じ 1 時間。ただし自分のセッションのぶんは外す（1 つのターンが
  1 時間を超えることがあり、読む前に消すと黙って何も回らない）
- 失ったもの: 300 行の入口と 2 本の hook を足して浮くのが 1 ターン 2.5〜4.5 秒。絞りの値だけを
  見れば釣り合っていない。釣り合うのは「8 か所に並んだ工程が 1 か所になった」ぶんと合わせたとき

## 採らなかった案

- **GitHub Actions を足す**（issue #89 の道 1）。**issue の中心の懸念に効くのはこちら**（別の機械、
  複数回、必ず走る）。足さなかったのはこのリポジトリに CI という層が無く、持つかどうかが
  人の判断であるため。hook と両方持つこともできる
- **何もしない**（道 3）。統合先へ戻す前と MR に出す前に人が打つ、という運用を続ける
- **`Stop` で `pnpm test` を丸ごと回す。** 9.5〜11.5 秒。絞る仕掛けも 300 行も要らない。
  差は 1 ターン 2.5〜4.5 秒
- **同じテストを N 回回す枝を足す。** 混み具合で変わる失敗に唯一効く手元の道。入れていないのは、
  ターンの伸びが N 倍になり、どのテストを何回回すかを決める根拠が無いため。要るなら dom の
  テストだけを対象にするのが筋
- **触ったファイルを `git status` から数える。** hook を 1 本増やさずに済むが、前のターンで
  直してすでにテストした変更も、他セッションの書きかけも混ざる
- **`lint-py.sh` に「拡張なら印を書く」を足して相乗りする。** hook が 1 本増えない代わりに、
  名前（`lint-py`）と仕事が合わなくなる。どちらも人に登録を頼む点は同じ
- **グループの対応を全部表にする。** 辿るより速いが、ファイルを増やしたときに黙って古くなる
- **`tsc` もグループごとに絞る。** `tsconfig.test.json` は `src/` と `test/` を全部見るので、
  絞るには入口の一覧を組み立てることになる。型の検査が「テストが読むぶんだけ」に狭まり、
  拡張ホスト側の型の誤りが落ちなくなる
