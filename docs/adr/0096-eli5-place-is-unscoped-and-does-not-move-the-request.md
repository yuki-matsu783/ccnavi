# ADR-0096: `wip/eli5/` はチケットの範囲を当てず、そこだけを変えたコミットは依頼の後に動いたと数えない

状態: 採用（ADR-0095 の「失ったもの」のうち、範囲の書き足しと ELI5 だけの直しでの依頼し直しの 2 つを改める。ほかは 0095 のまま。除外の綴りの読み方（`\` を `/` に直さない）と `ready` の大文字小文字は置き換え（ADR-0097））

## 状況

ADR-0095 で、ELI5 の HTML は依頼を出すワークツリーの `wip/` の下（既定 `wip/eli5/phase-<N>.html`）にコミットし、
マージリクエストの差分に載せることにした。そのとき、2 つの手間が残った（2026-10-01）。

- 親チケットの範囲（`allow`）に `wip/eli5/*` か `wip/*` が無いと、親のワークツリーで HTML を書く Write が
  `DENY_TICKET_SCOPE` で止まる（テストで確かめた）。依頼のたびに必要な材料なのに、提案のたびに範囲へ書き足させる形になる
- 依頼の後に ELI5 だけを直したコミットも「ユーザが見るものが動いた」に数え、`confirm` が止まり `request` の打ち直しが要る。
  crit push の指摘を受けて説明を直すたびに依頼のコメントが増え、レビュー済みが遠のく

どちらを変えても判定が緩む。ユーザが両方とも変えると決めた（2026-10-01）。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| `wip/eli5/` の下（ツリーのルートからの相対。大文字小文字を区別）は、チケットの範囲を当てない（`ticket.is_eli5_place`）。実行前チェック（`ticket.is_unscoped`）、実行後チェック（`post.ScopeGuard.finding`）、サブエージェント終了時チェック（`phase.scope_findings`）のどれでも外す | `scratchpad/` と違って追跡される置き場なので、実行前だけで外すと、通した書き込みがコミットのあとで範囲外として咎められる。3 か所を揃える | 実行前だけで外す（`scratchpad/` と同じ）。コミットのたびに報告が出る |
| 親のツリーでも子のツリーでも外す | `is_unscoped` は親子を区別せず、ツリーに結び付いたチケットの範囲を外す作りで、それに揃えた。子が ELI5 を書いて親に合流する流れも自然に通る。`wip/` は `ready` の前に丸ごと消すので、子が書いても成果物には残らない | 親だけで外す。`is_unscoped` に親子の区別を持ち込むことになり、判定の鍵（ファイルの行き先）とずれる |
| 外すのは `wip/eli5/` の下だけ。`wip/` のほかの場所（`wip/design/` など）・`wip/eli5x/`・`docs/wip/eli5/`・同じ名前のファイル `wip/eli5` は外さない。名前は設定で動かさない | フェーズの種類は `wip/research/*` や `wip/design/*` を範囲の上限に使っており、`wip/` ごと外すとその上限が働かなくなる。名前を動かせると、ソースの置き場に向けるだけで範囲を迂回できる | `wip/` ごと外す |
| 綴りの大文字小文字は区別する | 依頼の検査（`ccnavi-review.sh`）と `ready` の前提（`git ls-files -- wip`）も区別して `wip/` を見る。区別しない側に広げると、`WIP/eli5/` が「範囲を外すのに ready で消えない場所」になりうる | 範囲の照合（`_fold`）と同じく区別しない |
| 依頼の後に `wip/eli5/` の下だけを変えたコミットは、REQ-TKT-16 の「親ブランチの HEAD が動いた」に数えない（`review._unseen_by_review`）。`confirm`（`moved_since`。Chrome のレビュー済みも同じ関数）と、出し直しの「依頼済み」の判定（`_already_requested`）の両方で。ELI5 とほかのファイルを一緒に変えたコミットは今までどおり数える | 提案と承認済みチケットの置き場と同じ扱い。ELI5 は依頼に添える説明で、成果物ではない | ELI5 だけの直しでも依頼し直させる（0095 の形） |
| push は今までどおり求める。未コミットの検査（`_dirty`）と push の検査（`_unpushed`）は ELI5 を外さない | 未 push の ELI5 はマージリクエストの差分に無く、crit push が届かない。未コミットの ELI5 は依頼のときに sh が止める | 置き場と同じく未 push も数えない。差分に無い ELI5 で依頼が通る |
| review 側の見分けは git の `-z` の綴りをそのまま見る（`\` を `/` に直さない） | `_outside_approved` と同じ理由。直すと `wip\eli5\x` という名前のファイル 1 個が置き場の中に見える | 範囲の判定と同じ `is_eli5_place` を使う |

## 得たもの・失ったもの

- 得たもの: 親の範囲に何も書き足さずに ELI5 を書ける。範囲の書き忘れで依頼の手前で止まらない
- 得たもの: crit push の指摘を受けて ELI5 を直しても、push するだけで済む。依頼のコメントが増えない
- 失ったもの: **直した ELI5 をユーザが見直す保証が無くなる。** 依頼の後に説明を書き換えても、`confirm` はそれを知らずにレビュー済みを置く。
  ユーザが見たのとは違う説明が差分に残りうる。ELI5 は `ready` の前に消えるので成果物には残らないが、レビューの材料としての確かさは下がる
- 失ったもの: 直す前の行に付いた crit push のスレッドは、直したあとも未解決のまま残る（GitHub では outdated の表示が付く）。
  `confirm` はそれを数え続けるので、ユーザが resolve するか `decide` で決める
- 失ったもの: `wip/eli5/` の下には、範囲の宣言に関わらず何でも書ける（HTML に限らない）。そこに置いたものは `ready` の前に消えるが、
  レビューの間はマージリクエストの差分に載る
- 失ったもの: `wip/eli5/` だけの変更は「動いた」に数えないので、そこにコードを置いて依頼後に差し替えても `confirm` は気づかない。
  ただし `wip/` は squash の前に消すので、既定のブランチには届かない

## 採らなかった案

- **`wip/` ごと外す。** 上の表のとおり、種類の範囲の上限が働かなくなる
- **ELI5 の直しは数えないが、直したことを依頼のコメントに追記する。** sh が依頼後のコミットを監視する仕組みが要り、今回の範囲を超える
- **HTML だけ（`*.html`）を外す。** 置き場で外すほうが既存の外し方（置き場ごと）に揃い、拡張子の綴りの揺れ（`.htm`、大文字）で結果が分かれない
