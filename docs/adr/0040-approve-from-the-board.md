# ADR-0040: 承認は端末ではなくボードのオーバーレイで受け、承認したことは hook が伝える

状態: 採用

## 状況

承認は `ccnavi --approve` を端末で打ち、束を見て `y` を押す形だった。VS Code の拡張（ボード）の
「承認」ボタンは、統合ターミナルにその 1 行を送るだけで、y/N は人がターミナルで押していた。
拡張の子プロセスで承認を実行しないのは、`--approve` が「標準入力が端末であること」を求めるから
（ADR-0026）。これはエージェントが人の合意を自分で出せないための壁で、子プロセスは端末を持たない。

この形には 2 つ不便がある。承認の内容がターミナルに出るので、ボードで見ているものと承認で見る
ものが別の画面になる。もう 1 つは、承認したことをモデルが知らないこと。人が「承認した」と
チャットで打つまで、エージェントは後工程に入れない。

## 決定

承認をボードの中で完結させる。オーバーレイが `--approve --preview --json [<絞り>...]` で束を読んで
見せ、人が押したら `--approve --yes <識別子,…> --json [<絞り>...]` を子プロセスで打つ。
`accept` は端末のまま（sh がレビューのスレッドを取ってきてから判断する経路で、拡張に移すには
その結果を JSON で返す契約が別に要る）。`wrapup` はボードに置かない。

`--yes` には端末を求めない。代わりに 2 つを求める。

- **見せた束と今の束が一致すること。** 人が見ていない提案が束に紛れ込んでいれば何も承認しない
- **エージェントが打てないこと。** 組み込みの deny（`builtin-guard-ticket-approval`）が
  Bash / PowerShell からの `--yes` を止める

承認されたことは hook が次の `UserPromptSubmit` / `PreToolUse` で 1 度だけモデルに伝える。控えは
`<state>/approved-<session>-<agent>.json` で、中身は「識別子 → 印（`approved_at` と `revised_at`）」。

## 理由

端末の壁を残したまま拡張から承認しようとすると、`CCNAVI_GUARD_TICKET_APPROVAL=disable` で壁ごと
切ることになり、`--reviewed` と `accept` の守りまで落ちる。壁を切るのではなく、承認だけを別の
守りに移した。守りの数は減っていない（tty 1 つが、束の一致と組み込み deny の 2 つになった）。

伝える仕組みが要るのは、承認とセッションが離れたから。端末で承認していたときは、同じ人が同じ
画面で次の指示を打っていたので、承認したことは人が伝えていた。

走っている Claude Code のセッションへ拡張から文を送り込む公開の口は無い（`vscode://anthropic.claude-code/open?prompt=…`
は新しいタブに文を埋めるだけで、送信は人が Enter）。だから「承認したら後工程が勝手に走り出す」
までは行かず、人の 1 手を残す。拡張は通知の 2 ボタン（コピー / 新しいセッションで開く）で文を渡す。

## 失うもの

- `CCNAVI_MODE=dry-run` の間は deny が止めないので、エージェントは `--yes` を打てる。dry-run は
  「判定を言うだけ」のモードで、承認の経路だけを例外にはしない。例外を作ると、dry-run で
  確かめている判定と本番の判定が別物になる
- 同じセッションの hook が同時に走ると、同じ承認を 2 度伝えることがある（控えの読み書きを
  直列化していない）。伝えすぎる側なので受け入れる。競合のために黙る形にはしない

## 実装で踏んだ穴

**免除は許さない側から書く。** 最初の deny は「`--preview` があれば免除」を `--approve` と `--yes` の
両方に掛けていた。同じコマンドに `--preview` を書き足すだけで承認が通り、PowerShell（shellread を
通らず生の文字列に当たる）では後ろのコマンドに書いた `--preview` が前の `--yes` まで免除した。
承認そのものを免除の対象から外し、免除の範囲をコマンド 1 本に区切って直した。

**絞りと「見せたもの」は別の引数にする。** 束の絞り込み（ADR-0039）を取り込んだとき、`--yes` の
識別子を絞りとしても使ったため、狭めた束と渡した識別子が必ず一致し、束の一致の検査が素通りした。
`--yes` は「人が見た識別子」、後ろの語は「そのとき掛けていた絞り」に分けた。比べるのは
「その絞りで今できる束」と「見た識別子」。

**識別子だけでは新しい合意を見分けられない。** 親の改版は承認済みチケットを書き換えるだけで識別子を増やさない。
控えを「識別子 → 印」にした。承認の直後に子が閉じる形もあるので、閉じた承認済みチケットも見る。

どれも敵対的レビュー（経緯を渡さない読み取り専用サブエージェント）と受入テストが見つけた。
