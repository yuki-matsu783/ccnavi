# ADR-0060: ワークツリーの起点になるデフォルトブランチは、セッションの頭で進める

状態: 採用

## 状況

親のワークツリーの起点は「リモートの最新のデフォルトブランチ」にはなっていなかった。
`ccnavi-git.sh worktree add <行き先> -b <名前> <統合先>` の起点は `<統合先>` の HEAD で、
それは**手元の** `main` の HEAD になる。手元の `main` が古ければ、そこから切る枝も古いところから
伸びる。

`CLAUDE.md` が書いていた手当ては「`<統合先>` がリモートにしか無いときは先に `fetch` する」だけで、
**ローカルにあるが古いとき**には何も書かれていなかった。止める側も見ていない
（`ccnavi-git.sh` の `worktree add` が検査するのは行き先の綴りとオプションの一覧だけ）。

セッションの頭に走る `ccnavi-fetch.sh` でも埋まらなかった。進めるのは **そのツリーが
チェックアウトしているブランチ**（`@{u}` まで ff）だけなので、**ワークスペースルートが `main`
以外に居ると `main` には届かない**。issue を書いた時点のワークスペースが実際にその形だった。

```
+ claude/busy-cray-tz98u6 6177e0b (...) [origin/claude/busy-cray-tz98u6]
  main                    11234e9 [origin/main]
```

困るのは 3 つ。**統合先へ戻すときに ff-only が通らない**（毎回 `merge` と衝突の解決が要る）。
**承認済みチケットとマーカーを古い版で判定する**（`ccnavi-fetch.sh` が防ごうとしているものが、
別の入口から起きる）。**別の機械で続きができない側に倒れる**（設計 §9.2 / REQ-MLT-14 は、承認と
フェーズの進みが親チケットのブランチに乗って届くことを前提にしている）。2026-09-16、issue #56。

## 決定

- **`ccnavi-fetch.sh` が、リポジトリごとにデフォルトブランチも ff で進める。** そのツリーが
  チェックアウトしているブランチを進める周（第 1 周）はそのまま、リポジトリを回る周（第 2 周）を足す
- **デフォルトブランチは `origin/HEAD` が指すもの。** 無ければ `origin/main`・`origin/master` の
  在る側に落とし、どちらも無ければ何もしない。当てずっぽうで別のブランチを進めない
- **チェックアウトされていなければ `update-ref`、されていればそのツリーで `merge --ff-only`。**
  チェックアウト中のブランチの ref を付け替えると索引と作業ツリーがずれる
- **見るのはワークスペース自身と `projects/<名前>` だけ。** ワークツリーは元リポジトリと ref を
  共有しているので、元で進めれば届く
- **第 2 周は `.ccnavi/approved/` の有無で絞らない。** 第 1 周が絞っているのは「承認済みチケットを
  持つツリー」で、ここで欲しいのは「これから切るワークツリーの起点」。いま何を持っているかとは別
- **デフォルトブランチが手元に無ければ、リモートの版で作る。** 無いままでは `worktree add` の
  起点に指せない
- 進めない条件は第 1 周と同じ。**未コミットの変更があるツリーは触らず、分岐していたら進めず、
  理由を 1 行で言う。** 何も動かなければ黙る
- `CLAUDE.md` は「起点はリモートの最新のデフォルトブランチ」を決まりとして書き、
  進まなかったときに何が出るかを添える

## 理由

**止める側（案 1）ではなく、揃える側にした。** `worktree add` が起点の遅れを見て断つ形は、
起点が古い状態が実際に止まる代わりに、**毎回ネットワークを待つ**ことになる。しかも `fetch` が
落ちたときに「遅れているかどうか」が分からず、分からないときに通すなら担保にならない場面が残る。
ccnavi のラッパースクリプトは判定の経路に居るので、そこにネットワーク待ちを入れると、
オフラインで枝を切る道ごと細くなる。

**セッションの頭は、待ちを置いてよい唯一の場所。** `ccnavi-fetch.sh` はもともとネットワークに
出る hook で、落ちても 0 で返る（オフラインでも作業は続く）。ここに足すぶんには、判定の経路は
動かない。

**第 1 周と同じ道具立てにした。** ff だけ・未コミットのツリーは触らない・進めなければ 1 行で言う。
セッションの頭に走るものが、人や別のセッションの書きかけを動かしてよい理由は無い
（`CLAUDE.md`「他セッションの作業を踏まないために」）。

**第 1 周が見るツリーがデフォルトブランチを持っているときは、第 2 周は黙って飛ばす。**
同じことを 2 度取ってこないためと、同じ事実を 2 行で報せないため。

## 得たもの

- **ワークスペースルートがどのブランチに居ても、`main` が揃う。** issue の形がそのまま消える
- **統合先へ戻すときの ff が通りやすくなる。** 起点が origin の HEAD なので、`<統合先>` が
  進んでいなければ直上に居る
- **承認済みチケットとマーカーが、`main` 経由でも新しくなる。** `main` を持つツリーが
  `.ccnavi/approved/` を持たなくても届く
- **プロジェクトも同じ形で揃う。** 見るのが「git プロジェクトルート」なので、`projects/<名前>` が
  そのまま乗る
- **テストが付いた。** `ccnavi-fetch.sh` はそれまでテストから一度も呼ばれていなかった
  （`tests/sh/test_fetch_sh.py`）

## 代償

- **セッションの頭の待ちが増える。** ルートがデフォルトブランチに居ないセッションでは、
  リポジトリ 1 つにつき `fetch` が 1 回増える。プロジェクトを n 個置いていれば n+1 回になりうる。
  hook の timeout は 60 秒のまま
- **担保ではない。** 揃えるのはセッションの頭の 1 回だけで、長いセッションの途中で origin が
  進めば、そこから切る枝はまた古い。`worktree add` は相変わらず起点の遅れを見ない
- **手元の `main` が黙って動く。** 進むのは ff だけ・分岐していれば触らないとはいえ、
  「セッションを始めたら `main` の位置が変わっていた」は起こる。`main` にコミットを積んで
  push 前に置いている人は、分岐として弾かれる（進まず 1 行出る）
- **手元に無いブランチを作ることがある。** `--single-branch` で clone した手元に
  デフォルトブランチができる。ref を 1 本足すだけだが、意図して持っていなかった人には増える
- **`origin/HEAD` が無い手元では、名前を推測している。** `main`・`master` の順で在る側を採る。
  どちらでもない名前のデフォルトブランチを `git init` + `remote add` で持っている手元では、
  第 2 周は何もしない（黙る）。`git remote set-head origin <名前>` で直せる
- **報せの行が 1 種類増えた。** セッションの頭に出る文が増える側の変更で、
  「何も動かなかったときは黙る」は守っているが、動いたときは 2 行出うる

## 採らなかった案

- **案 1: `ccnavi-git.sh worktree add` が起点の遅れを見て断る。** 起点が古い状態が実際に止まる
  唯一の案。採らなかったのは、判定の経路に毎回のネットワーク待ちが乗り、`fetch` が落ちたときに
  担保にならない場面が残るため（上の理由）。**この案とは排他ではない。** 起点の古さが
  それでも事故になるなら、`--reason` の要る警告として後から足せる
- **案 3: `CLAUDE.md` に手順として書くだけ**（`worktree add` の前に `fetch` を打つ）。すぐ入り、
  オフラインでも困らない。採らなかったのは担保が無いため。忘れても誰も言わない
- **案 4: 何もしない。** 代償は無いが、上の「困るのは 3 つ」がそのまま残る
- **第 2 周も `.ccnavi/approved/` のあるツリーだけに絞る。** 絞りが 1 つで済む。採らなかったのは、
  ルートが `main` 以外に居る形（まさにこの issue）で `main` を持つワークツリーが承認済みチケットを
  持たないことがあり、そこが抜けるため
- **`fetch origin <main>:<main>` で進める。** git が ff を保証し、チェックアウト中なら断る。
  採らなかったのは、第 2 周が先に `fetch origin <main>` を打っているので取り直しになるのと、
  断られたときの理由（チェックアウト中か、分岐か）が文面から読み分けにくいため。
  遅れと分岐は自分で数え、`update-ref` は古い sha を添えて付け替える
