# ADR-0058: 承認の権威は置き場。記録の欄は必須にしない

状態: 採用

## 状況

チケットの承認は端末を通る（ADR-0029）か、VS Code の拡張のボードから `--yes` で通る
（ADR-0040）。どちらも持たない人が居る。手元に ccnavi を置けず、GitHub の画面でファイルを
動かすことしかできない運用で、承認の意思を出す手段が無かった。

置き場は既に承認の権威として設計されている（ADR-0055、`approval.py` 冒頭）。`.ccnavi/approved/`
は ccnavi ディレクトリの下なので、組み込みの守りがエージェントの書き込みを止める。それでも
`load_copy` が `ccnavi_approved` の欄を必須にしていたので、置き場を動かしただけのチケットは
「承認を通っていない」で読まれず、判定からも `ticket start` からも消えていた。

欄を人が手で書けば通る。だがそれは 1 行の YAML を正確に書かせることで、承認の意思表示としては
筋が悪い。しかも欄を書いても、承認のときにしか走らない検査（親が承認されているか、`project:` が
置き場と合っているか）は誰も走らせないままになる。

## 決定

| 決めたこと | 採らなかった側 | なぜ |
|---|---|---|
| `.ccnavi/approved/` では `ccnavi_approved` を必須にしない。欄は承認の記録であって承認そのものではない | 欄を必須のまま残す | 権威は置き場だと設計が既に言っている。守りが 2 枚ある置き場で、欄を「人が手で書ける 1 行」として扱うのは、守りではなく手間 |
| `wip/proposals/review/` では必須のまま | ここも外す | そこはエージェントが書ける側で、守りは組み込みの deny 1 枚。欄を second layer として残す |
| 承認のときにしか当たらなかった構造の検査を、判定の側でも当てる（`blocking_problems`）。引っかかったチケットは範囲を当てずに全部止める | 検査を承認だけに残す | 置き場を動かすだけの運びは `--approve` を通らない。親が引けない子は、どの範囲で切り詰めるかが決まらないまま、自分の宣言だけが効く |
| 検査は `scan` が 1 回当てて `Ticket.blocked` に印を付け、`scope_verdict` が読む | 3 か所（実行前の判定・実行後の監視・サブエージェント終了時）が別々に呼ぶ | 別々に書くと、同じ書き込みが実行前は通って実行後に咎められる |
| 止めるのは「範囲をどこで切り詰めるかが決まらない」検査だけ。フェーズの順序と計画の形は `--lint` が言う | 承認の検査を全部 deny にする | 順序が狂っていても、その子の範囲をどの親で切り詰めるかは決まる。止めるとレビュー待ちの間その子が一切書けなくなり、`held_phase` が `Agent` とシェルだけを止めて Write を通す形（ADR-0024）とは結果が離れる |
| 承認済みチケットの `project` も、提案と同じく置き場が決める | frontmatter の欄だけを読む | ADR-0038 は提案についてそう決めた。承認済みチケットだけ欄を読むと、手で動かした分の層が空になる |
| 理由のコードは `DENY_TICKET_BLOCKED` として `DENY_TICKET_SCOPE` と分ける | 同じコードにする | 受け取った側の次の一手が違う。範囲外なら範囲の中で済ませる道があるが、こちらは人が直すまでどこにも書けない |
| 印を付けるときに親を引く池は、判定が引く索引と同じもの（`by_id(kept)`） | 閉じた親・レビュー待ちの親まで引ける池を別に組む | **最初はそちらで書いて穴を作った。** 印を付ける側は親を引けて印を付けず、判定の側は引けずに `parent=None` になり、子の宣言だけで範囲が決まった。範囲外への書き込みが無音で通る。池は 1 つにして、引けないなら止める側へ倒す |
| 止まっていることはボードの JSON（`blocked`）にも出す | 判定と `--lint` にだけ伝える | `copy.status` は `open` のままなので、ボードしか見ない人には書き込みが全部拒否されていることが見えない |

## 理由

承認とは「この範囲でよい」と人が言うことで、その意思をどう出すかは置き場・端末・ボードの
どれでもよい。守りは「エージェントがそこへ書けないこと」で成り立っていて、欄の有無では
成り立っていない。欄を必須にすることで実際に止まっていたのは、書き込みの手段を持たない
エージェントではなく、端末を持たない人だった。

検査を判定へ持ってきたのは、承認の経路が 1 つ増えたから。経路ごとに検査が違うと、通りやすい
経路が選ばれる。同じ検査がどの経路でも当たるなら、経路を増やしても緩まない。

## 得たもの・失ったもの

- 得たもの: 端末もボードも無い人が、ファイルを動かすだけで承認できる
- 得たもの: 親が引けない子が自分の宣言だけで書ける形が、承認を通った分についても塞がった
- 得たもの: 承認済みチケットの層が、手で動かした分でも置き場から決まる
- 失ったもの: 承認の画面（範囲の超過の警告、計画の差分、フィードバックの注記）を人が見ない
  経路ができた。まとめて見せてまとめて決める形が、そのぶん緩む
- 失ったもの: **フェーズの順序が実質未検査になる。** `--approve` なら error で弾いていた
  「前のフェーズが閉じてレビューが済むまで次のフェーズの子は承認しない」が、置き場を動かす
  経路では誰も当てない。判定では止めない（範囲の決まり方に効かないので）ので、残るのは
  `--lint` の warn だけで、それは人が打たなければ出ない
- 失ったもの: 親が閉じたのに子が開いている形が、道具の外から作れるようになった。そのとき
  子は `blocked` になって全部止まる。安全な側に倒してはいるが、人から見れば
  「動いていた子が突然どこにも書けなくなる」ので、閉じる順を間違えたときの戻し方が要る
- 失ったもの: 判定のたびに構造の検査が走る。走査は `scan` の中なので増えないが、
  `project_problems` の置き場の一覧でディレクトリを 1 回読む
- 失ったもの: 承認日時が空のチケットができる。「いつ承認したか」がコミットの日時にしか残らない

## 採らなかった案

- CI が移動を拾って `--approve --yes` を走らせる。承認の検査は全部残るが、CI に
  `.ccnavi/approved/` への push 権限が要り、プロジェクトごとにワークフローを配ることになる。
  ccnavi 本体だけで完結しない
- 移動を「承認の申し出」として第 5 の状態にする。状態が増えるぶん、置き場が状態を表すという
  ADR-0055 の一貫性が崩れる
- 欄を必須のまま残し、人に 1 行書かせる。書けるが、書き損じたときの落ち方が「チケットが
  存在しない」になり、原因に手が届かない
