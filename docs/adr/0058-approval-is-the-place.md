# ADR-0058: 承認は置き場を本物とする。記録のキーは必須にしない

状態: 採用

## 状況

チケットの承認は端末を通る（ADR-0029）か、VS Code の拡張のボードから `--yes` で通る
（ADR-0040）。どちらも持たないユーザが居る。手元に ccnavi を置けず、GitHub の画面でファイルを
動かすことしかできない運用で、承認の意思を出す手段が無かった。

置き場を承認の本物とする設計は既にある（ADR-0055、`approval.py` 冒頭）。`.ccnavi/approved/`
は ccnavi ディレクトリの下なので、組み込みの保護がエージェントの書き込みを止める。それでも
`load_copy` が `ccnavi_approved` のキーを必須にしていたので、置き場を動かしただけのチケットは
「承認を通っていない」として読まれず、判定からも `ticket start` からも消えていた。

キーをユーザが手で書けば通る。だがそれはユーザに 1 行の YAML を正確に書かせることになり、承認の意思表示の方法としては
筋が悪い。しかもキーを書いても、承認のときにしか実行されない検査（親が承認されているか、`project:` が
置き場と合っているか）は誰も実行しないままになる。

## 決定

| 決めたこと | 採らなかった側 | なぜ |
|---|---|---|
| `.ccnavi/approved/` では `ccnavi_approved` を必須にしない。キーは承認の記録であって承認そのものではない | キーを必須のまま残す | 置き場を本物とすることは設計で既に決めている。保護が 2 重にある置き場で、キーを「ユーザが手で書ける 1 行」として扱っても、保護にはならず手間になる |
| `wip/proposals/review/` では必須のまま | ここも外す | そこはエージェントが書ける側で、保護は組み込みの deny 1 つだけ。キーは 2 つ目の保護として残す |
| 承認のときにしか行わなかった構造の検査を、判定の側でも行う（`blocking_problems`）。引っかかったチケットは範囲を適用せずに全部止める | 検査を承認だけに残す | 置き場を動かすだけの承認の経路は `--approve` を通らない。親が引けない子は、どの範囲で切り詰めるかが決まらないまま、自分の宣言だけが適用される |
| 検査は `scan` が 1 回だけ行って `Ticket.blocked` を立て、`scope_verdict` が読む | 3 か所（実行前チェック・実行後チェック・サブエージェント終了時）が別々に呼ぶ | 別々に書くと、同じ書き込みが実行前は通って実行後に報告される |
| 止めるのは「範囲をどこで切り詰めるかが決まらない」検査だけ。フェーズの順序と計画の形は `--lint` が指摘する | 承認の検査を全部 deny にする | 順序が狂っていても、その子の範囲をどの親で切り詰めるかは決まる。止めるとレビュー待ちの間その子が一切書けなくなり、`held_phase` が `Agent` とシェルだけを止めて Write を通す形（ADR-0024）とは結果が食い違う |
| 承認済みチケットの `project` も、提案と同じく置き場が決める | frontmatter のキーだけを読む | ADR-0038 は提案についてそう決めた。承認済みチケットだけキーを読むと、手で動かした分の層が空になる |
| 理由のコードは `DENY_TICKET_BLOCKED` として `DENY_TICKET_SCOPE` と分ける | 同じコードにする | 受け取った側の次の一手が違う。範囲外なら範囲の中で済ませる方法があるが、こちらはユーザが直すまでどこにも書けない |
| `blocked` を立てるときに親を引く対応表は、判定が引く索引と同じもの（`by_id(kept)`） | 閉じた親・レビュー待ちの親まで引ける対応表を別に組む | **最初はそちらで書いて穴を作った。** `blocked` を立てる側は親を引けて立てず、判定の側は引けずに `parent=None` になり、子の宣言だけで範囲が決まった。範囲外への書き込みが気づかれないまま通る。対応表は 1 つにして、引けないなら止める側にする |
| 止まっていることはボードの JSON（`blocked`）にも出す | 判定と `--lint` にだけ伝える | `copy.status` は `open` のままなので、ボードしか見ないユーザには書き込みが全部拒否されていることが見えない |

## 理由

承認とは「この範囲でよい」とユーザが言うことで、その意思をどう出すかは置き場・端末・ボードの
どれでもよい。保護は「エージェントがそこへ書けないこと」で成り立っていて、キーの有無では
成り立っていない。キーを必須にすることで実際に止まっていたのは、書き込みの手段を持たない
エージェントではなく、端末を持たないユーザだった。

検査を判定へ持ってきたのは、承認の経路が 1 つ増えたから。経路ごとに検査が違うと、通りやすい
経路が選ばれる。どの経路でも同じ検査を行うなら、経路を増やしても検査は緩まない。

## 得たもの・失ったもの

- 得たもの: 端末もボードも無いユーザが、ファイルを動かすだけで承認できる
- 得たもの: 親が引けない子が自分の宣言だけで書ける形が、承認を通った分についても無くなった
- 得たもの: 承認済みチケットの層が、手で動かした分でも置き場から決まる
- 失ったもの: 承認の画面（範囲の超過の警告、計画の差分、フィードバックの注記）をユーザが見ない
  経路ができた。まとめて見せてまとめて決める形が、そのぶん弱まる
- 失ったもの: **フェーズの順序が実質未検査になる。** `--approve` なら error で弾いていた
  「前のフェーズが閉じてレビューが済むまで次のフェーズの子は承認しない」が、置き場を動かす
  経路では誰も検査しない。判定では止めない（範囲の決まり方に影響しないため）。そのため、残るのは
  `--lint` の warn だけで、それはユーザが `--lint` を打たなければ出ない
- 失ったもの: 親が閉じたのに子が開いている形が、道具の外から作れるようになった。そのとき
  子は `blocked` になって全部止まる。安全な側にしてはいるが、ユーザから見れば
  「動いていた子が突然どこにも書けなくなる」ので、閉じる順を間違えたときの戻し方が要る
- 失ったもの: 判定のたびに構造の検査が実行される。走査は `scan` の中なので増えないが、
  `project_problems` の置き場の一覧でディレクトリを 1 回読む
- 失ったもの: 承認日時が空のチケットができる。「いつ承認したか」がコミットの日時にしか残らない

## 採らなかった案

- CI がチケットの移動を検知して `--approve --yes` を実行する。承認の検査は全部残るが、CI に
  `.ccnavi/approved/` への push 権限が要り、プロジェクトごとにワークフローを配ることになる。
  ccnavi 本体だけで完結しない
- 移動を「承認の申し出」として第 5 の状態にする。状態が増えるぶん、置き場が状態を表すという
  ADR-0055 の一貫性が崩れる
- キーを必須のまま残し、ユーザに 1 行書かせる。書けるが、書き損じたときの失敗の仕方が「チケットが
  存在しない」になり、原因にたどり着けない
