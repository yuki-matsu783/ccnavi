# ADR-0024: 並行するチケットの骨子：行き先で結ぶ、子は親の部分集合、状態は置き場

状態: 採用

## 状況

メインエージェント（親）が作業を子チケットに分け、サブエージェントに 1 本ずつ実行させる。
子は別々の git worktree で同時に走る。1 本のチケットと 1 つの台帳だけでは、同時に有効な承認が複数ある
こと、呼び出しがどのチケットの仕事かを hook が 1 件ごとに決めること、親の承認と子の承認の
関係を決めること、の 3 つを実現できない。2026-09-09 にユーザと 1 問ずつ相談して決めた。

## 決定

| 決めたこと | 採らなかった側 | なぜ |
|---|---|---|
| 判定の鍵は Write の行き先が属するワークツリー | `cwd`、`session_id`、`agent_id` | サブエージェントは親と `cwd` を共有しうる。行き先なら誰が書いても同じ判定になる |
| ワークツリー名 = チケット識別子。親が git のラッパースクリプトで作る | チケットに `worktree:` を書く、`Agent` の `isolation: worktree` に任せる | `isolation` は名前を選べない。名前で結べば `--lint` で一致を確かめられる |
| 子は親の部分集合。書いていない場所は範囲外 | 親からの差分だけ書く | 子のファイルだけ読んで、子が書ける場所が分かる |
| 親と子では厳しい側を採る。深さ 2 段 | 無制限 | 承認画面で祖先を全部たどらずに済む。必要になったら上限を上げればよい |
| 親も自分のチケットに縛られ、ワークツリーを持てる | 親は main で 1 本だけ | 複数の親を同時に走らせたい。main はチケットを持たない |
| 承認済みの状態はチケットごとのファイルで表す（ADR-0023） | 識別子ごとに引ける台帳 | 有効な集合 = ディレクトリの中身 |
| 状態は提案の置き場（`todo` / `doing` / `done` / `cancelled`）で表し、保護済みスクリプトだけが動かす | frontmatter のキー | `ls` で見え、コミットに残り、「閉じたつもり」が起きない |
| 閉じるのは親だけ。承認は要らない | `ccnavi --close` を打たせる、ワークツリー削除で閉じる | 閉じる操作は範囲を消す向きにしか働かない。エージェントに ccnavi のコマンドを打たせない |
| 計画中の親はルールだけ。計画の終わりにまとめて承認 | 親を先に承認、未承認の親にも `wip/tickets/` への書き込みだけ許す | 「未承認は効かない」（ADR-0022）を崩さない |
| フェーズは子の `phase:` で表す。同じ番号に子を足せる | 必ず次の番号 | 足した時点でマーカーを消せば意味は保てる |
| レビュー準備中・レビュー待ちで止めるのは `Agent` と Bash（3 本の sh は例外）。Write は通す | Write も止める | 次のフェーズの計画はレビュー前に進めてよい |
| 止める判定を外す条件は、マージリクエストの未解決スレッドが 0 | ユーザがマーカーを置くだけ | レビューそのものと結び付ける。GitLab と GitHub をリモート URL で見分ける |
| 未解決を残して進めるのはユーザが端末で | チャットの OK をエージェントが伝える、UserPromptSubmit で文を拾う | 止められた側が自分で止める判定を外す形にしない。ユーザの手が入る場所を、承認と同じ 1 種類にまとめる |
| ブランチの親子と範囲の重なりは見ない | `--lint` で merge-base を見る、重なる承認を拒む | write の範囲だけを見る。重なりを止めると、エージェントはチケットの許可範囲を広げて止まらないようにする方向に動く。レビュー依頼の前提としてだけ合流を見る |

書いてみて決まったことも 4 つある。

| 決めたこと | なぜ |
|---|---|
| 子のワークツリーにある提案は読まない。同じ識別子が複数のツリーにあれば、親のツリーの側を採る | 子は親のブランチから切るので、親の `wip/tickets/` がそのまま写っている。全部を数えると「複数の場所にある」として状態を動かせなくなる。**この行は ADR-0073 が改めた。** 親のツリーが無ければ元ツリーの側を採る |
| 子が親の部分集合かは、子の項の字義どおりの前置部分に 1 文字足した文字列を、親の項に当てて決める（`src/b/*` → `src/b/x`） | 前置の末尾の `/` を落として当てると、親の `src/b/*` が `src/b` に当たらず、正当な子を「超えている」と判定してしまった |
| スクリプト 2 本は実行ファイルを探して渡すだけの薄い形。本体は `ccnavi ticket` と `ccnavi review` | 承認済みチケットの読み方を判定と共有し、1 か所に保つ。`.git` の `gitdir:` から元リポジトリを引くので、ワークツリーの中から呼んでも元リポジトリの側の承認済みチケットを読む。**この行は ADR-0028 が改めた。** `ccnavi-review.sh` はリモートを取ってくる本体を持ち、薄いのは `ccnavi-ticket.sh` だけ |
| 状態の移動はそのキーの行の値だけを書き換える。元のファイルを消せなければ、書き出した側を消して元に戻す | 読み直して書き出すとユーザの書いたコメントが消えた。両方に残ると以後の操作が全部止まった |

## 理由

参考にした運用（ADR-0025）は判定の材料を cwd のツリーの作業中チケットから採っていて、そのために
並列実施を「隔離はされるが統制が効かない」として発効を保留していた。「行き先で結ぶ」ことで、その問題を解消する。

## 得たもの・失ったもの

- 得たもの: サブエージェントの起動の仕方が判定に影響しない
- 失ったもの: 書き込みは行き先、起動とシェルは `cwd`、と鍵を使い分けることになる。`cwd` は `cd` 1 回で
  変わるので、レビュー準備中・レビュー待ちで止める判定が緩む向きに外れることがある。ただし、移った先で起動したサブエージェントの書き込みは
  行き先で止まるので致命的にはならない
- 失ったもの: Stop の exit 2 は処理を「続行させる」ための仕組みで、「ターンを終えてユーザに聞け」を強制する
  手段は hook に無い。先に文で伝え、それでも進んだら止める、という 2 段階になる
- 決めていないこと: `ticket start` / `done` は承認済みチケットの有無を見ず、未承認のまま `doing/` `done/` まで
  進める（`--lint` は指摘する）。`--approve` は `done/` にある未承認の提案も承認の対象に入れる。ユーザが子を
  再開しても、そのフェーズの `reviewed` は残る
