# ADR-0154: フィードバック計画の承認でレビューの状態を変えず、issue に回すをいつでも選べるようにする

状態: 採用（互換の版を 17 から 18 に上げる）

## 状況

フィードバック計画（`feedback:`）を初めて足す親の改版の承認は、次をまとめてしていた。

- 全体計画の最後のフェーズに `reviewed` のマーカー（`by: feedback-plan`）を置く
- `review/` にある全体計画の子を `done/` へ動かし、`settled_by: feedback-plan` を書く
- 「最後のレビューを済ませた扱いにした」と出す

つまり、ユーザが計画を承認した時点で、まだ決めていない指摘（未解決のスレッド）を含めて、レビューが済んだことにしていた。
承認画面が見せるのは計画であって指摘ではないので、指摘を見ないまま受け入れたことになる。さらに、`decide` の「issue に回す」は
フィードバック計画が承認されたあとだけ選べたため、最後のレビューで残った指摘を issue に回すには、先にこの承認を通す必要があり、
承認がレビューの合意を兼ねる形になっていた。

## 決定

| 決めたこと | なぜ |
|---|---|
| フィードバック計画を初めて足す改版の承認は、レビューの状態を変えない。`reviewed` を置かず、`review/` の子を動かさず、`settled_by` も書かない（`phase.settle_last_review` は消す） | 承認は計画への合意で、指摘の受け入れではない。受け入れは `confirm`・`decide`・手で動かした子の確定で、指摘ごとに版つきで残す |
| 承認できるのは、全体計画の最後のフェーズがレビュー済み（`reviewed` あり。レビュー不要・延期は今までどおり）のときだけ。`requested` だけでは偽（`phase.plan_finished`） | 差し戻しの結果を見てから計画を立てる、という元の意図は、レビューが済んでいれば満たせる。手で動かした子の確定（`via: manual`）も `reviewed` を置くので足りる |
| まとめて承認するとき、フィードバック計画の初回の改版と、同じ親の全体計画の番号（`len(plan)` 以下）の子が同じ承認に入っていたら、その親の改版と該当する子を両方拒む。無関係の親子は部分承認の規則のまま。フィードバック計画のフェーズの子との同時承認は許す | 全体計画に子を足すとそのフェーズが開き直り、レビュー済みという承認の前提が崩れる。片方だけ通すと順序の判断をユーザに任せることになる。絞り込みの有無・入口（CLI・VS Code・Chrome）で同じ結果になるよう、判定は `agree_candidates.candidates` の 1 か所に置く |
| 拒否の文面に順番を書く: 全体計画に足す子を先に承認し、その作業と再レビューを済ませてから、フィードバック計画の改版を承認する | 直し方が分かるようにする |
| `decide` の `can_issue` を常に真にする。JSON の欄は互換のために残す。前提（依頼の記録・HEAD が動いていない・変更要求が無い）は今までどおり | issue に回す条件がフィードバック計画の承認に結び付く理由がなくなった。最後のレビューで残った指摘もそのまま issue に回せる |
| 古い版が置いた `reviewed` の `by: feedback-plan` は読めるまま残し、`--lint` が info で一覧にする。`settled_by: feedback-plan` は許す値から外さない。新しくは書かない。移行のコードは書かない | 公開前なので、過去のデータを読むための分岐は新しく足さない決まり。消すかどうかはユーザが決める |

## 互換の版

17 から 18 に上げる。承認の意味（レビューの状態を動かす → 動かさない）、承認の通る条件、`decide` の選択肢が変わる。新旧が混ざると、
古い sh は「フィードバック計画が承認されるまで issue を選べない」前提で案内し、古い実行ファイルは承認でレビューを動かすため、
ユーザが見た結果が食い違う。ほかの項目（依頼コメントへの返信を指摘に数える・ホストの判定・取り下げの廃止など）の変更と同じ版で
上げる（`ticket-flow.md` の「更新したときの変更点」）。

## 採らなかった案

- 承認でレビューを済ませるのをやめ、条件も付けない。差し戻しの結果を見ないままフィードバック計画を立てられ、`feedback` の
  対応フェーズの `confirm` が前の指摘を全部数えて詰まる（元の `settle_last_review` が必要だった理由）
- 同じ承認に入った全体計画の子を、計画の側だけ通す。子を足すとレビュー済みが外れるので、承認した直後に改版の前提が崩れる
- 古い `by: feedback-plan` を読まない・自動で消す。過去のデータを読む処理は外す決まりだが、承認済みの置き場を動かすのはユーザの仕事
