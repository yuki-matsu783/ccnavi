用語:

- 「親のブランチ」（`P`）は親チケットの作業ブランチ。子チケットにとっては親のもの、親チケット自身にとっては自分のもの
- 「親のワークツリー」は `P` を checkout した `.claude/worktrees/<P>`
- 「開発者の手元」はエージェントが動く機械の clone。「承認者」は Chrome 拡張で承認するユーザ。同じ人のこともある
- 「親子のチケット」（古い呼び名: 家族）は親チケットと子チケットのまとまりで、`P` と 1 対 1。`P_X` は識別子 `X` が属する親子のチケットの親のブランチ
- 「統合先」は `done/` とレイヤーと置き場のパスを読むブランチ（D30）。統合先の設定はリポジトリには置かず、Chrome 拡張の設定と手元の環境変数で変えられる。未設定ならホストのデフォルトブランチになる。
  `P` はここから切り、マージリクエストはここへマージする（`docs/claude/environment.md` の「統合先ブランチ」と同じもの）
- 「state の置き場」は手元の `conf.state`。リポジトリには入らない（古い呼び名: 控え）
- 「親子のチケットの取り込み状態」は `sync/<リポジトリ>/families/<P>`、「統合先の取り込み結果」は `sync/<リポジトリ>/integration/`（3.6・4.2。古い呼び名: 家族の控え・統合先の控え）。
  `<リポジトリ>` はワークスペース自身なら `self`、プロジェクトならプロジェクト名。取り込み状態がある親子のチケットを「取り込み済みの親子のチケット」と呼ぶ
- 「手元の統合先」は最後に取り込んだ `origin/<統合先>`（D26）
- 「承認の push」はユーザの判断を `P` へコミットして送る処理。今の `ccnavi-push-approved.sh` を改修したもの（4.6）
- 「承認の取り下げ」は Chrome から承認を未承認（`todo/`）に戻す操作（8.8）。
  既存の「差し戻し」（`review.py:419` など。レビューの後に同じフェーズへ子を足してやり直すこと）とも、
  「取り消し」（`cancel`、`done/` へ `cancelled` で閉じる）とも違う

## 1. 背景と目的

- 今の承認は端末（`ccnavi-approve.sh`）か VS Code 拡張のボードで、どちらも手元に ccnavi 本体と作業ツリーが要る。
  ボードは `--approve --preview --json` → `--approve --yes <ids> --digest <d> --json` を子プロセスで呼び
  （`vscode-extension/ccnavi-board/src/ccnavi.ts:264-335`）、承認後に `ccnavi-push-approved.sh` を端末に送ってコミットと push をする
  （設計 9.4）
- 開発者と承認者（レビュアー）は別の人であることがよくある。承認者の機械には clone も ccnavi も無いことが多い。一人で開発・承認する場合もある
- 目的は 2 つ
  1. 承認者がブラウザと PAT だけで、リモートのブランチに対して承認できること。書き先は GitHub / GitLab の API
  2. 他の人がリモートで承認したものを、開発者の手元（エージェント）が取り込んで、その承認に従って動けること
- 障害は 3 つ
  1. 本物とするチケットをツリーから推定しているので、ブランチしか見えない API 側では同じ答えを出せない
  2. 判定の中核が I/O と絡んでいて、ブラウザで同じコードを動かすには切り出しが要る
  3. 状態（着手・終了・マーカー）を手元が書き、承認をリモートが書くので、両者の間に二重の状態ができる
- 制約: ccnavi の実行ファイルはネットワークに出ない（`docs/claude/exe-boundary.md`）。外とのやり取りは `.ccnavi/scripts/` の sh が受け持つ

## 3. 親のブランチと本物とする側

### 3.1 親のブランチ名の規則

#### 今の運用（読んだもの）

- ワークツリーの置き場は `.claude/worktrees/<ブランチ名>`（`.ccnavi/docs/worktree.md:34`）
- 着手はワークツリーの**ディレクトリ名**が識別子と大文字小文字まで一致することを求め、
  作り方として `worktree add ".claude/worktrees/<id>" -b <id>` を案内する（`ccnavi/ops.py:57-68`）。子も同じ（`ccnavi/review.py:524`）
- 「ワークツリーの名前は識別子と同じ」は既に明文（設計 9.3）。識別子の形の規則は 設計 9.3
- 識別子とブランチ・ワークツリーの結び付きは、着手・レビュー・push の保護・本物とする側の判定のほかに
  `ops.py:339,395,707`、`diagnose.py:645,992`、`flow.py:1360`、`lint.py:910` にもある
- 本物とする側の推定は `approval._authoritative` の `at_home`（`approval.py:275`）で、ツリー名と親の識別子を比べる
- `ccnavi-git.sh` は「ディレクトリ名 = ブランチ名 = 識別子」を強制していない（`worktree)` の節は行き先の置き場しか見ない）
- `ccnavi-git.sh branch` の拒否に入っていない形がある:
  - 短いオプションの検査 `*f* | *m* | *u*`（`ccnavi-git.sh:186-188`）は大文字小文字を区別するので、`-M`（強制の改名）は通る
  - 長いオプションは `--move` を拒否する（`:178`）が、使い方の文（`:82`）は「`-M` 不可」と書いていて、実装と食い違う
  - `-D` は `*D*` で拒否（`:183-185`）、`-m` は拒否
- `ccnavi-git.sh fetch` は `-f`・`--force` などを拒否するが、refspec（`+refs/...:refs/...`）は通す（`:493-501`）
- 今の復旧案内は `checkout -B <ブランチ> <リモート>/<ブランチ>` を勧めている（使い方 `:99`、reset の拒否文 `:607`）
- `issue:` は親だけのキーで、正の整数か `#12`（`ticket.py:186-197,596-607`）。マージリクエストの本文に `Closes #N` を書き出す（`review.py:284-285`）
- 識別子の形は `_ID = ^[A-Za-z0-9][A-Za-z0-9._-]*$`（`ticket_ids.py:27`）。子は `_CHILD = ^<親>-<2 桁>$`（`ticket_ids.py:28-30`）
  （追記 2026-10-04: ADR-0101 で子の形を `<親>-<2 桁のフェーズ番号>-<2 桁の連番>` に改めた）
- 既存の親は `i0055`・`i0060`・`i0061`・`i0062` で、どれも `issue:` を持たない

| N2 | `<番号>-<slug>`（ホストの既定） | ホストの既定どおり。一覧で読める | 題が変わると引けない。日本語の題は slug がほぼ空。`-12` で終わると子の識別子と紛れる |
| N3 | 識別子とは別に `branch:` キーを持つ | 名前を自由にできる | 値を書き換えれば本物とする置き場が動く |

（2026-10-04 追記）N3 は ADR-0102 の 5 章で任意のキーとして入れた。本物とするブランチは「そのブランチの上の親チケットが自分で名乗る」形で決め、名乗るブランチが 1 本でなければ止め、取り込み状態が親のブランチ名を持ち、改版で書き換えさせない。

#### 規則（N1）

（2026-10-03 追記）4・5・6・7 の識別子の形（`i<番号>`・`<プロジェクト名>-i<番号>`）は ADR-0102 で `<先頭の語>-<番号>-<slug>` に改めた。

1. **親のブランチ名 = 親の識別子**。子のブランチ名も子の識別子（今と同じ）
2. **ref として安全な形に限る**。新規の提案に次を足す: `..` を含まない、`.lock` で終わらない、`.` で終わらない。既存の識別子がこれに当たらないことを確かめてから入れる
3. **大文字小文字だけが違う識別子を許さない**。一意性の検査は大文字小文字を区別せずに行う
4. **王道（issue あり）**: 親の識別子は `i` + issue 番号の 4 桁 0 埋め（5 桁以上はそのまま）。frontmatter の `issue:` に番号を書く
5. **予約**: 新規の提案で `^i\d+$` の形は `issue:` があるときだけ許す。`main`・`master`・`develop`・`release`・`release/*`・`release-*`（大文字小文字は区別しない）と、
   その時点の統合先の名前は識別子に使わない（`P` が保護されたブランチや統合先と同じ名前になるのを防ぐ。`ccnavi-push-approved.sh:174-175` の一覧と揃える）。
   既存の `i0055`〜`i0062` は issue #55〜#62 と名前が衝突する（GitHub の番号は issue とマージリクエストで共有、既に #130 まで使用）。
   衝突は「始める」（8.6）と承認の同じ識別子の検査の両方で止める: 統合先の `done/` か開いた親子のチケットに同じ識別子があれば、その issue からは始められない
6. **フォールバック（issue なし）**: 識別子はユーザが付け、ブランチ名はその識別子。`^i\d+$` と `-\d{2}$` の形は使わない（`-\d{2}$` は `_CHILD` と紛れるため）
   （追記 2026-10-04: ADR-0101 で子の形が `-\d{2}-\d{2}$` になった。`-\d{2}$` を避ける規則はそのまま残し、`-\d{2}-\d{2}$` で終われば子そのもの、`-\d{2}$` だけなら子の識別子の途中と紛れるとして warn にする）
7. **プロジェクト（`projects/<名前>`）**: プロジェクトの issue からは `<プロジェクト名>-i<番号>`（例 `web-i0012`）。プロジェクト名は手元の `projects/` の下の名前で、Chrome 拡張には設定画面でリポジトリごとに登録する（10.3 の 1。段階 5 で決めた）
8. **リポジトリをまたぐ issue**: `issue:` に `owner/repo#N` を許す。識別子はフォールバックと同じくユーザが付け、マージリクエストの本文は `Closes owner/repo#N`
9. **一致の検査は新規の提案のときだけ**。承認後は識別子を優先し、`issue:` の書き換えは既に改版で許していない（`approval.py:2279`）
10. **ハードに拒否する場所（`ccnavi-git.sh`）**: 段階 0 の lint の warn（2・3・5・6）とは別に、次を `ccnavi-git.sh` で拒否する。
    - 段階 0: `branch` の拒否に入っていない形を直す。短いオプションの検査に `*M*` を足し（`-C` の強制コピーも同じ検査で見る）、`-M`・`-rM`・`--move` の回帰試験を足す。
      `fetch`・`pull` の引数で `:` か `+` を含むもの（refspec）を拒否する。文面は「取ってくるのはブランチ名だけ。手元の ref は `ccnavi-sync.sh` が進める」
    - 段階 2b（`ccnavi-sync.sh` と同時。D36）: `worktree add` で「行き先のディレクトリ名 = 新しいブランチ名（`-b`）」を求める。
      `--detach`・`-f`/`--force`・`-B`（今は `ccnavi-git.sh:247` で通している）、`checkout -B`/`switch -C`、親のワークツリーで別のブランチへ移る形を拒否する。
      同時に `:99` の使い方と `:607` の reset の拒否文を「リモートに合わせるなら `ccnavi-sync.sh <P>`。分かれていて進めないならユーザの対応に切り替える」に書き換える
    - 親のブランチに当たったときの文面は、何が止まるかをそのまま言う。手元は親のワークツリーを「名前が `P` で、HEAD がブランチ `P` を指すもの」として探す（3.3）。
      HEAD が別のブランチを指すと、取り込み（`ccnavi-sync.sh`・SessionStart の早送り。4.2）がそのワークツリーを飛ばし、
      取り込み済みの親子のチケットでは親を決められず、親と子の承認・状態の操作・実行前の判定が止まる。文面は「ccnavi は親チケットのワークツリーを、
      名前が親チケットの識別子で、同じ名前のブランチをチェックアウトしているものとして探します。別のブランチに移ると、リモートでの承認を取り込む処理
      （ccnavi-sync.sh と、セッション開始時に ccnavi-fetch.sh が fast-forward で進める処理）がこのワークツリーを飛ばします。
      親チケットのブランチを一度でも push したか ccnavi-sync.sh で取り込んだことがあると、親と子のチケットの承認・状態の操作（start・finish など）・
      実行前の判定も止まります」。
      `worktree add` で行き先の名前とブランチ名が違うときも、親のブランチを識別子と違う名前のワークツリーに出すと同じことが起きる（取り込みが親のワークツリーとして見つけられない）と言う
11. **同じ関数**: 「チケット → 親のブランチ名」は `t.parent or t.ticket`。「issue → 識別子」は `f(番号, プロジェクト名)` の 1 つだけを `ticket.py` に置き、Pyodide でも使う
12. **置き場のパスの設定が絶対パス**（`CCNAVI_TICKETS_APPROVED` などをリポジトリの外に向けた設定）のワークスペースは、write-and-push の対象外にする。
    置き場がブランチに入らないので `P` 上のチケットを本物とできない。lint がその旨を info で出す
    - Chrome 拡張は置き場の env を読まず、既定の置き場（`wip/proposals`・`.ccnavi/approved`・`.ccnavi`）を使う。env に絶対パスがあっても断らず、既定の置き場を読む
    - （追記 2026-10-05: 前は Chrome も対象外にしていた。その後、置き場を既定に固定した（ADR-0098）ので、Chrome 拡張は置き場を env からも統合先の設定からも読まなくなり、対象外にする理由が無くなった）

### 3.2 王道とフォールバックの流れ（開発者と承認者が別の人）

| 段 | 誰が | 王道（issue あり） | フォールバック（issue なし） |
|---|---|---|---|
| 1 | ユーザ | issue を作る（ホストの画面） | なし |
| 2 | ユーザ | 親のブランチ `i<番号>` を統合先の先頭から作る（Chrome 拡張の「始める」か、ホストの画面） | なし |
| 3 | エージェント | `ccnavi-git.sh fetch origin i<番号>` → `worktree add .claude/worktrees/i<番号> -b i<番号> origin/i<番号>` → `ccnavi-sync.sh i<番号>` で親子のチケットの取り込み状態ができ、write-and-push の対象になる | `worktree add .claude/worktrees/<id> -b <id> <統合先>`。最初の push までは今の手元の動き |
| 4 | エージェント | 親のワークツリーで提案を書き（`issue:` 付き）、`--approve --preview --verify <id>` で確かめ、コミットして push | 同じ（`issue:` なし）。push が通ると `ccnavi-git.sh` が親子のチケットの取り込み状態を `present` で作り、write-and-push の対象になる（4.3 の最初の push） |
| 5 | 承認者 | Chrome 拡張で承認。承認済みチケットと提案の削除が 1 つのコミットで `P` に入る。着手前なら取り下げられる（8.8。取り下げは ADR-0155 が廃止） | 同じ |
| 6 | 開発者の手元 | 取り込み: `start` の write-and-push の中で取り込まれる。先に見たければ `ccnavi-sync.sh`（4.2） | 同じ |
| 7 | エージェント | `start`・`finish`・マーカーは write-and-push で `P` へのコミットと push まで済ませる（4.3） | 同じ |
| 8 | エージェント | `ccnavi-review.sh request` がマージリクエストを探し、無ければ Draft を作って依頼を投稿 | 同じ |
| 9 | 承認者 | マージリクエストのスレッドを片付け、Chrome の「レビュー済み」でマーカーを付ける（8.9）。エージェントが `confirm` を打っても同じマーカーになる | 同じ |
| 10 | エージェント | 親を閉じ（`ticket finish <親>`）、`wip/` を消して push、`ccnavi-review.sh ready` で Draft を外す | 同じ |
| 11 | 承認者 | Draft が外れたマージリクエストに最後の Approve を付け、統合先へ squash でマージ。ホストが `P` を消す（3.6 の正常系） | 同じ |

要点は「**提案は親のブランチの上で書き、push してから承認を頼む**」です。
今は親のワークツリーが承認のあとに作られることがある（`approval.py:326-328` の docstring）ので、取り込み済みの親子のチケットでは運用が変わります（それ以外は今のまま。3.4）。
REQ-APV-14 の案内（`ticket.py:1163-1179`）に「push してから依頼する」を足します。

### 3.3 本物とする側の決め方

「`P` がある」「統合先」の定義を場所ごとに分けます。

- **統合先の名前**（D30。案 C）: リポジトリには置かず、使う側がそれぞれ持つ
  - Chrome 拡張: 設定画面でリポジトリごとに入れる（`chrome.storage.local`）。空なら `GET /repos/{o}/{r}` / `GET /projects/:id` のデフォルトブランチ
  - 手元: 環境変数 `CCNAVI_INTEGRATION_BRANCH`（`.claude/settings.local.json` の `env` か、シェルの環境）。空ならホストのデフォルトブランチ（`origin/HEAD`、無ければ `ccnavi-fetch.sh` の `ccnavi_fetch_default` と同じ探し方）。
    プロジェクトのリポジトリも同じ値を使う（プロジェクトごとに変える必要が出たら後で足す）
  - **デメリット**: ユーザごと・機械ごとに値がずれうる。承認者の Chrome と開発者の手元が別の統合先を読むと、閉じた親子のチケットの見え方とレイヤーが食い違い、手元の C3 が親子のチケットを止めることがある
  - **軽い緩和**: 設定したブランチがリモートに無ければ（`ls-remote` の一覧に無い / API が 404）、既定に切り替えずに止めて「統合先 `<名前>` がリモートに無い。設定を直す」と知らせる。
    `ccnavi-sync.sh` は使った統合先の名前と、それが設定か既定かを統合先の取り込み結果の `head`（`branch`・`source`）に書いて出力にも出す。Chrome はボードの見出しに使った統合先の名前を常に出す。
    値を揃える仕組み（リポジトリの設定との突き合わせなど）は持たない
- **リモート（Chrome 拡張）**: ホストにブランチ `P` がある。`origin/P` の中身を本物とする。統合先は上の名前のブランチの先頭
- **手元（hook・lint・ボード・コマンド）**: `.claude/worktrees/P` があり、その HEAD がブランチ `P` を指している。中身は「最後に取り込んだ `origin/P` + 手元の作業」
- **手元の統合先**（D26）: 最後に取り込んだ `origin/<統合先>` を優先する。`ccnavi-sync.sh` と write-and-push が取り込むたびに、
  その先頭から判定に要るもの（`.ccnavi/approved/done/` の一覧と中身、`.ccnavi/config/common/` のレイヤー、自身の `.ccnavi/config/project/` のレイヤー、置き場のパスの設定）を
  統合先の取り込み結果 `sync/<リポジトリ>/integration/`（と、その中の `head` に `remote`・`branch`・`sha`・`fetched_at`。D33 の形）へ書き出す。
  ワークスペースとプロジェクトのリポジトリで取り込み結果を分ける。判定は git を起こさず、この取り込み結果を読む
  - origin が無い・一度も取り込んでいないリポジトリでは、今どおり作業ツリーを読む

本物とする側の規則:

1. **`P` がある**: `P` の `.ccnavi/approved/` と `wip/proposals/review/` を本物とする
2. **`P` が無く、統合先の `done/` に親のチケットがある**（取り消し済みを含む）: 親子のチケットは閉じている。統合先を本物とする（3.6 の正常系）
3. **`P` が無く、統合先の `done/` にも親が無い**: **決まらない → その親子のチケットの承認も状態の操作も止める**（3.6）。
   「統合先で未承認なら新規扱い」にすると、改版の制約（`approval.py:2270-2285`）を新規の承認として迂回できるため
4. **開いた親子のチケットでも、統合先の `done/` は常に一緒に読む**。古い統合先から切った `P` で、識別子の再利用が新規として通らないようにするため
5. **参照先の親子のチケットは閉包で集める**（D2）: 先行（`approval_ops.predecessor_pool`、`approval_ops.py:373-380`）は `_loop_back`（`:725-745`）で多段を辿るので、
   1 段の `P_X` だけでは Chrome と手元で答えが変わる。
   - 親子のチケットの引き方: 識別子 `X` が `_CHILD`（`ticket_ids.py:28-30`）に当たれば、その `parent` の組が親。当たらなければ `X` 自身が親。
     親の識別子に `-\d{2}$` を使わせない（3.1 の 6）ので、この引き方は一意に決まる。既存の親に当たる形が無いことは段階 0 の lint で確かめる
     （追記 2026-10-04: ADR-0101 で子の形が `<親>-<2 桁>-<2 桁>` になり、引き方は右から 2 段を剥がす形に改めた。Python・hook・sh で同じ規則）
   - 提案が参照する識別子の `P_X` を読み、その上のチケットが参照する識別子の親子のチケットをさらに読む、を新しい親子のチケットが出なくなるまで繰り返す。
     統合先の `done/` にある（閉じた）親子のチケットはそこで止める（`_loop_back` も閉じたものの先を辿らない）
   - **上限は親子のチケット 16 組**。根拠: 読み取りは親子のチケット 1 組あたり tree 1 回と、blob をまとめて読む 1 回なので、承認 1 回の読み取りが GraphQL と REST を合わせて 40 回ほどに収まる。
     今の開いた親子のチケットは 4 組で、上限に届く形は想定していない。超えたら「決まらない」で止め、次を出す:
     「先行を辿ると 16 を超える親子のチケットに広がった（<親子のチケットの一覧>）。Chrome では判定できない。計画を分けて先行を減らすか、手元で `--approve --preview --verify` を打って確かめる」
   - `P_X` が無ければ 2・3 と同じ規則（`done/` にあれば閉じた親子のチケット、無ければ決まらない）
   - **手元でも揃える**: 取り込み済みの親子のチケットの判定では、先行を引く対応表を作る範囲を「その `P` のツリー + 閉包の親のワークツリー + 統合先の取り込み結果の `done/`」に限る。
     閉包の親のワークツリーが手元に無ければ「決まらない」で止め、切り直しを案内する。こうすると、他のワークツリー上の古いチケットで `PRED_SCATTERED`（`approval.py:626,719`）が
     出るかどうかが Chrome と食い違わない。取り込み済みでない親子のチケットは今の全ツリー走査のまま（Chrome はその親子のチケットを見ない）
6. **レイヤーと設定は `P` から読まない**。`P` の上で書き換えれば承認やレビューを不要にできてしまうため
   - 共通レイヤー（`.ccnavi/config/common/`）とワークスペース自身のレイヤー: ワークスペースの統合先から読む（手元は `sync/self/integration/`）
   - 置き場: 既定（提案は `wip/proposals`、承認済みは `.ccnavi/approved`）に固定する。統合先の `.claude/settings.json` からは読まない
   - プロジェクトのレイヤー（D28）: ADR-0084 の configsync（`configsync.py:1-20`）は着手のときに共通レイヤーを**親のワークツリー（`P` の上）のプロジェクトのレイヤー**へコピーする。
     判定はこれを読まず、「**プロジェクトの統合先の現在のレイヤー**（手元は `sync/<プロジェクト>/integration/`）に、共通レイヤーを `configsync.projected` で写したレイヤー」を計算して使う。
     - これは着手のときにコピーしたレイヤーではなく**統合先の現在値**です。着手の後に統合先の共通レイヤーやプロジェクトのレイヤーが変わると、
       開いている親子のチケットの判定の基準もそれに合わせて動きます（着手でコピーした結果とは違いうる）。`P` の上のレイヤーを書き換えても判定が変わらないことを優先しました
     - `P` の上のプロジェクトのレイヤーがこの計算と違えば、取り込み（4.2）と `--lint` が warn を出す
     - configsync 自体（プロジェクトだけを clone したユーザにレイヤーを配る役）は残す。写したレイヤーは `start` の write-and-push でコミットして push する（D34・4.3）
     - **ADR-0084 を改訂対象に入れる**（設計書と要件に反映済み）
   - **手元のレイヤー（段階 2c のレビューの後のユーザの決定 B1）**: 上の 2 つ（統合先から読む・D28 の計算）は **Chrome の側にだけ当てる**。
     手元（hook・lint・承認・状態の操作）は今どおりワークスペースルートとプロジェクトの作業ツリーのレイヤーを読む。
     作業ツリーのレイヤーと統合先の取り込み結果のレイヤーの違い、`P` の上のプロジェクトのレイヤーと D28 の計算の違いは `--lint`（と取り込みの後の検査）の warn で知らせる。
     手元の判定を統合先の取り込み結果のレイヤーに切り替えると、統合先のレイヤーが作業ツリーより緩いときに通るものが増えるため
   - 手元では、`settings.local.json` に承認の判定を変える値（置き場のパスなど）を置かせない lint を入れる。**例外は `CCNAVI_INTEGRATION_BRANCH` だけ**（D30 で置き場として決めたため）
7. **プロジェクト**: プロジェクトのチケットはそのプロジェクトのリポジトリの `P` と、そのリポジトリの統合先で同じ規則。
   Chrome 拡張にプロジェクトのリポジトリが登録されていなければ、プロジェクトが絡む提案は承認しない

### 3.6 `P` の削除・改名

#### 場合分け

| 場合 | 見え方 | 扱い |
|---|---|---|
| 正常系: マージリクエストがマージされ、ホストが `P` を消した | `P` が無い。統合先の `done/` に親のチケットがある | 親子のチケットは閉じている（3.3 の 2）。**戻す案内は出さない**。Chrome はこの親子のチケットに操作を出さない |
| マージ後もホストが `P` を残した | `P` も統合先の `done/` もある | `P` を本物とする。中身は同じなので答えは変わらない |
| マージせずに消した・改名した・掃除で消えた | `P` が無い。`done/` にも親が無い | **決まらない**（3.3 の 3）。その親子のチケットへの書き込みを止め、理由と戻し方を出す |

改名はホストでは止められないので追わず、3 行目の扱いにします。手元の `branch -M` は段階 0 で拒否します（3.1 の 10）。
リモートの消去（`push origin :P`・`push --delete`）は push の形の制限（`ccnavi-git.sh:584-603`）で通りません。

#### 正常系を必ず正常系にする（1）: `ready` の前提に「親が閉じている」を足す

今の `ready` は `ops_close.close_problems` だけを見るので、親を閉じる前に Draft を外せます（`review.py:1083-1098`）。
その形でマージされると `done/` に親が無いまま `P` が消えて 3 行目の場合になります。`ready` の前提に「親のチケットが `done/` にある」を足します（判定が厳しくなる変更）。

#### 正常系を必ず正常系にする（2）: 消えたと言う前に `done/` を確かめる（`ccnavi-sync.sh` と write-and-push だけ）

確かめは `ccnavi-sync.sh` と write-and-push の中の取り込み（同じ関数、`ccnavi-common.sh`）だけで行います。SessionStart はしません（D12）。

1. origin ごとに 1 回 `ls-remote --heads origin` を打ち、全ブランチの有無を得る（ブランチごとに打たない）。
   出力は `grep -F -x` で「`<sha><タブ>refs/heads/<P>`」の形の行と完全一致で比べる（前方一致で `i0131` と `i0131-x` を取り違えない）。
   `ls-remote` 自体が落ちたら「取ってこられなかった」（オフライン・認証）として止める
2. `P` が一覧に無ければ「消えた候補」とし、`P` の fetch は打たない
3. 消えた候補がある origin でも、`origin/<統合先>` は必ず fetch する
4. sh の中で `git cat-file -e origin/<統合先>:<done の置き場>/<親>.md` を見る（置き場のパスは Python が出す。判定の外なので `git` を起こしてよい）。
   あれば「閉じた」として取り込み状態に書き、戻す案内は出さない
5. 無ければ観測ずれを疑う（ホストはマージの後に `P` を消すが、読み取りの複製の遅れで `done/` が見えないことがある）。
   **3 回まで 5 秒おきに** 3〜4 を繰り返す。それでも無く、`ccnavi-review.sh` が使うもの（`gh`/`glab`/curl とトークン）が使えれば
   マージリクエストの状態を引き、マージ済みなら「マージ済みだが統合先への反映がまだ見えない。少し待って `ccnavi-sync.sh`」と言って止める（戻す案内は出さない）
6. どれにも当たらなければ「消えた」として取り込み状態にその旨を書き、その親子のチケットを止め、次を出す（モデルとユーザの両方が読む出力）:
   - 理由: 「親のブランチ `P` がリモートに無い。統合先にも閉じた記録が無いので、この親子のチケットの状態を決められない」
   - 戻し方 1（改名・消し間違い）: 元の名前 `P` でブランチを作り直す。案内文だけを出し、ccnavi は作らない:
     端末なら `git push origin <取り込み状態の sha>:refs/heads/P`、GitHub ならマージリクエストの画面の「Restore branch」、
     GitLab ならマージリクエストの `refs/merge-requests/<N>/head` から `P` を作る
   - 戻し方 2（親子のチケットを捨てた）: 親のワークツリーを片付け（`ccnavi-git.sh worktree remove`）、ユーザが `ccnavi-sync.sh --forget <P>` で親子のチケットの取り込み状態を消す
     （段階 2c のレビューの後の決定 A。エージェントは打たない）

`ccnavi-fetch.sh`（SessionStart）の側は 1 点だけ直します: fetch が「リモートにその ref が無い」（`couldn't find remote ref`）で落ちたときは、
その origin を `failed`（`ccnavi-fetch.sh:94-95`）に入れない。今は入れるので、同じ origin の統合先の fetch まで飛ばされる（`:76-78`）。
SessionStart は「`P` を取ってこられなかった。`ccnavi-sync.sh <P>` で確かめる」とだけ言い、消えたとは判断しません。

#### 親子のチケットの取り込み状態と push の拒否

- 親子のチケットの取り込み状態 `sync/<リポジトリ>/families/<P>` は 1 行 1 項目のテキスト（D33）: `remote`・`branch`・`sha`・`fetched_at`（`date +%s`）・`state`（`present` / `closed` / `gone` / `blocked`）・`reason`
- **「一度も push していない `P`」と「消えた `P`」は取り込み状態の有無で分ける**。取り込み状態が無ければ手元だけの親子のチケットなので、リモートに無くても止めず、今の手元の動きのまま（write-and-push の対象外）
- 取り込み状態を作る・書き直すのは `ccnavi-sync.sh`、write-and-push の取り込み、`ccnavi-git.sh push`（通ったとき。4.3 の最初の push）の 3 か所
- **取り込み状態は削除せずに残す**（段階 2c のレビューの後の決定 A）。親のワークツリーを片付けても消さない（消すと、「決まらない」で止めていた親子のチケットが
  取り込み状態の無い親子のチケットに戻り、止めが外れる）。消すのはユーザが打つ `ccnavi-sync.sh --forget <P>` だけで、親のワークツリーが残っていれば断る。
  エージェントが打った場合は組み込みの deny（`builtin-guard-ticket-approval`）が止める。閉じたかは親子のチケットの取り込み状態に頼らず統合先の取り込み結果の `done/` から引くので、
  片付けた後に削除せずに残した `present` の取り込み状態も、統合先を取り込み直せば閉じた親子のチケットとして扱われ、何も出さない
- `ccnavi-git.sh push` は、取り込み状態の `state` が `gone` の `P` への push だけを拒否する。毎回の `ls-remote` はしない（取り込み状態を `sed -n 's/^state //p'` で読むだけ）。
  ユーザが戻した後は、次の `ccnavi-sync.sh` が `present` に書き直して拒否が解ける
- Chrome 拡張は先頭を記録せず、ブランチを戻す機能も持たない。消えた親子のチケットには上の戻し方の案内文だけを出す

- メリット: マージ後の正常系で何も起きず、閉じた親子のチケットを誤って戻させない。SessionStart が待たない。push の保護が毎回ネットワークを使わない
- デメリット: 改名でも親子のチケットが止まり、ユーザが戻す手間がある。観測ずれの確認で最長 15 秒ほど待つことがある

## 4. 取り込みと二重状態

### 4.1 二重状態の問題

| 書き手 | 書くもの | 書く場所 |
|---|---|---|
| 承認者（Chrome 拡張） | 承認済みチケット、改版、提案の削除、マーカーの消去（`clear_marks`）、フローの移動、承認の取り下げ（8.8）、レビュー済みのマーカーと子の `done/` への移動（8.9） | リモートの `P` |
| 開発者の手元（ccnavi のコマンド） | 着手・終了・取り消し・続きの子・マーカー・レビュー済みのマーカー・リスクの記録・フローのハッシュ・configsync の写したレイヤー | 親のワークツリー |
| 開発者の手元（hook） | フェーズの終わりの告知が置く `N.pending`/`N.skipped` と状態の履歴（4.4） | 親のワークツリー |
| ユーザ（端末・ボード） | ユーザの判断（4.4 の (c)） | 親のワークツリー |

起きること（write-and-push を入れる前）:

- **手元 → リモートの遅れ**: 手元の状態が push されていないと、Chrome は古い状態で判定する（子のあるフェーズの計画を変える改版が通る、着手済みを取り下げられる）
- **リモート → 手元の遅れ**: Chrome の改版が `clear_marks` で reviewed マーカーを消しても、手元に届くまで古い reviewed マーカーで判定が続く
- **衝突**: 両方が `approved/` を書いて merge が衝突したとき、エージェントが解くとどちらを本物とするかをエージェントが決めることになる

### 4.2 取り込み（他の人の承認を手元へ）

取り込みは 2 つの強さに分けます（D12）。

| | SessionStart（`ccnavi-fetch.sh`） | `ccnavi-sync.sh [<P>...]`（手で打つ）と write-and-push の中 |
|---|---|---|
| いつ | セッションの頭 | ユーザが承認を知らせたとき（ボードのボタン、「承認した」と言われたエージェント）、write-and-push の最初 |
| ロック | 取れなければその親子のチケットを飛ばす（待たない） | 待つ（4.3 の 1） |
| fetch | 今どおり（15 秒のタイムアウト監視） | 今どおり |
| 進め方 | **早送りだけ** | 早送り、分かれていれば merge |
| 消えたかの確かめ | しない（3.6） | する（3.6 の 1〜6） |
| 取り込み状態 | 書かない | 親子のチケットの取り込み状態と統合先の取り込み結果を書く |
| lint と判定し直し | しない | する（下の 5） |

#### SessionStart の早送り

- 対象は次を全部満たすツリーだけ（他セッションのワークツリーを動かさないため）:
  - `.claude/worktrees/` の直下で、ディレクトリ名 = ブランチ名
  - その中に `ticket: <その名前>` の**親の承認済みチケットか提案**がある（`parent:` を持つ子のチケットがあるだけでは足りない）
  - 親子のチケットの取り込み状態がある
- ロック（4.3）を 1 回だけ試し、取れなければ「`<P>` は他の操作の最中なので進めなかった」と言って飛ばす
- 手元の `P` が `origin/P` の祖先なら `merge --ff-only` する。書きかけとの重なりは git に任せ、拒まれたら
  「書きかけの `<パス>` と重なるので進めない。コミットか退避をしてから `ccnavi-sync.sh`」と言う
- **時間の枠**: hook の上限は 60 秒（`.claude/settings.json` の SessionStart）。早送りは fetch が済んだ後に行い、
  sh の開始から 45 秒（`date +%s` の差）を過ぎたら残りの早送りは飛ばして名指しする。早送りは merge と違い途中の状態（`MERGE_HEAD`）を残さない
- 対象に当たらないツリーは今の検査（未コミットがあれば進めない。`ccnavi-fetch.sh:209-213`）のまま

#### `ccnavi-sync.sh` と write-and-push の取り込み（sh が行う。Python は置き場のパスと、判定・検査の結果を出すだけ）

1. `ls-remote` と消えたかの確かめ（3.6 の 1〜6）。`P` があれば `fetch origin P` と統合先の fetch を打つ。統合先の名前は環境変数 `CCNAVI_INTEGRATION_BRANCH`、空ならホストのデフォルトブランチ（D30）。
   設定した名前が `ls-remote` の一覧に無ければ止めて知らせる。使った名前は統合先の取り込み結果と出力に出す
2. 早送りできれば早送り
3. 分かれていれば `merge origin/P`（rebase はしない）。前提は索引が HEAD と同じこと（`git diff --cached --quiet`）。
   非 ff の merge は、重ならないステージ済みの変更があっても「would be overwritten」で拒む（git 2.43 で確かめた）ので、先に見て
   「ステージ済みの変更がある。コミットするか `ccnavi-git.sh restore --staged` で外してから」と言う。
   `.ccnavi/approved/` か `wip/proposals/review/` で衝突したら **`merge --abort` して止め、ユーザの対応に切り替える**。
   ただし `phases/<P>/seq`（GitLab だけ。8.4）だけの衝突は、`seq` は本物とするファイルではなく比べるためのファイルなので origin 側を採って解く。それ以外の衝突も `merge --abort` して止める
4. Python の `--lint` の該当分（本物とする側の検査、3.3 の 6 のレイヤーの食い違い）と、C3 の判定し直しを回し、error があれば親子のチケットを止める（取り込み状態の `state` を `blocked`、`reason` に理由）
5. 記録を書く（親子のチケットの取り込み状態、統合先の取り込み結果）

hook の判定中はネットワークも外部プロセスも使わない（`tree.py:95-96`）ので、hook は最後に取り込んだ中身で判定します。

- メリット: SessionStart が短く終わり、途中で切られても merge の書きかけを残さない。承認は次の状態の操作（write-and-push）の前に必ず手元へ届く。衝突の決着をユーザに残す
- デメリット: セッションの頭で分かれていた親子のチケットは、次の write-and-push か `ccnavi-sync.sh` まで古いまま hook が判定する

### 4.3 手元 → リモートの遅れの解消（write-and-push を絞って入れる）

（案 C1 は、のちに write-and-push と改名した。以降の本文の write-and-push は、もとの C1 を指す。C2・C3 は案の記号のまま）

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| **write-and-push（採用、絞る）** | 取り込み済みの親子のチケットに限り、状態を書く操作を 1 操作にし、push が通るまで完了にしない | Chrome が見る親子のチケットでは未 push の状態が溜まらない | 対象の親子のチケットでは状態の操作にネットワークが要る |
| write-and-push（すべての親子のチケット） | すべての親子のチケットで同じ | 規則が 1 つ | origin の無い・まだ push していない親子のチケットまで止まる |
| C2 | 未送信のマーカーを `P` に置き、Chrome はその親子のチケットを止める | オフラインでも操作できる | マーカーを置くのに push が要る |
| C3 | 取り込み時に判定し直すだけ | 変更が小さい | 緩い承認が一度は `P` に入る |

#### 対象

- **対象**: origin があり、親子のチケットの取り込み状態の `state` が `present` の親子のチケット
- **対象外（今の手元の動きのまま）**: origin が無い、一度も push していない `P`（取り込み状態が無い）、chat だけの親子のチケット（マージリクエストを持たずリモートで承認されない親子のチケット）、置き場のパスの設定が絶対パス（3.1 の 12）。
  Chrome はリモートにある `P` しか見ないので、対象外の親子のチケットに二重状態は起きない
- 取り込み状態の `state` が `gone` か `blocked` なら write-and-push の操作は止める。`closed` なら親子のチケットは閉じていて状態の操作は無い

#### 最初の push で write-and-push の対象に入る

取り込み状態を取り込みでしか作らないと、最初の push から次の取り込みまで、親子のチケットが write-and-push の外なのに Chrome から見えます。この間をなくします。

- `ccnavi-git.sh push` は、push が通ったとき、送った先が親のブランチ（ディレクトリ名 = ブランチ名で、親の承認済みチケットか提案がある）なら、親子のチケットの取り込み状態を `present` で作る
- ただし、その時点で置き場に未コミットの変更（今の手元の動きで書いた状態）があれば取り込み状態を作らず、
  「置き場に未コミットの状態がある（<パス>）。コミットして push し直すと、この親子のチケットは取り込み（sh <スクリプトの置き場>/ccnavi-sync.sh <P>）の対象になる」と言う。
  こうすると、対象に入った時点の置き場は必ず `origin/P` と同じになり、未送信の状態を持ち越さない
- 取り込み状態を作れない間は親子のチケットは対象外のままで、Chrome からは見えるが手元の状態は今の動き（エージェントが commit して push する）になる。
  この間の遅れは C3（取り込みでの判定し直し）で拾う

#### 1 操作の中身（sh が持つ。D17）

`ccnavi-ticket.sh`（start・finish・cancel）、`ccnavi-review.sh`（request のマーカー・confirm・decide・ready）、
続きの子を起こす操作（`approval_ops.followup` を呼ぶ経路）は、対象の親子のチケットなら次の順に進めます。

1. **ロック**（D32、下）を取る
2. **途中の操作を確かめる**: `git rev-parse --git-path <名前>` で引いた `MERGE_HEAD`・`CHERRY_PICK_HEAD`・`REVERT_HEAD`・`rebase-merge/`・`rebase-apply/`・`sequencer/`・`index.lock`
   のどれかがあれば始めない（ワークツリーでは git ディレクトリが別の所にあるので、パスを決め打ちしない）
3. **write-and-push の外の変更を見分けてコミットする**（4.4）: Python が置き場の未コミットの変更を (b)・(c)・(d) に分ける。
   (c) か (d) があれば何も書かずに止める。(b) があれば `commit --only -- <(b) のパス>` で先にコミットする（新しいファイルは先に `add -- <パス>`）。
   こうしておくと、次の取り込みの merge が hook の書きかけ（`events/<親>.jsonl` の追記など）とぶつからない
4. **取り込み**（4.2）。merge が「local changes would be overwritten」で落ちたら（3 と 4 の間に他のセッションの hook が書いた）、3 からもう 1 回だけやり直す。2 回目も落ちたら失敗にする
5. **未送信の置き場の変更を確かめる**: `git diff --name-only origin/P HEAD -- <置き場>` の各パスを 4.4 の見分けにかけ、(b) 以外（ユーザの判断の未送信、見分けられない変更）があれば止める。
   REQ-APV-11 の補足（下）の前提を守るため
6. 元の先頭 `H0` を記録する（`rev-parse HEAD`）
7. **書く**: Python のコマンドを `--record-writes <ファイル>` つきで起こす。Python は fsio の記録レイヤー（下）で、この実行で書いたパスの一覧を出す
8. **コミット**: 一覧のパスだけを `commit --only -- <パス>`（新しいファイルは先に `add -- <パス>`）。`--no-verify` でユーザの hook を飛ばし
   （状態のファイルだけなので。段階 2d のレビューの決定 C）、署名はユーザの設定に従うがタイムアウト監視の時間（`CCNAVI_WRITE_AND_PUSH_COMMIT_TIMEOUT`、既定 60 秒）で切る。
   落ちたら、この実行が `add` したパスを索引から外す。ほかのステージ済みの変更は索引に残ったまま入らない（D35。git 2.43 で確かめた）。
   GitLab のリポジトリなら `phases/<P>/seq` の更新を同じコミットに含める（8.4。段階 5 の 2 段目から）。コミットメッセージはユーザが読む説明だけ（D37）
9. **push**: `git push origin P`（`--force` なし）。通れば取り込み状態の `sha` を書き換えてロックを外す
10. **push が落ちたら、まず届いたかを確かめる**: `git ls-remote origin refs/heads/P` の行が「`<C の sha><タブ>refs/heads/P`」と `grep -F -x` で一致すれば、届いていた（応答だけが落ちた）として成功にする
11. 届いていなければ**戻す**（下）。自動の再試行は 1 回だけ（3 からやり直す）。2 回目も落ちたら失敗にして「`ccnavi-sync.sh` で取り込んでから打ち直す」と言う

オフラインでは 4 か 9 で落ちるので、対象の親子のチケットの操作は失敗になり、「接続を戻してから打つ」と案内します。

#### ロック（D32）

- 置き場: state の置き場の `locks/<リポジトリ>/<P>/`（ディレクトリ）。`mkdir` の原子性は Git Bash・Linux・macOS で同じ。`flock` は macOS に無いので使わない
- 取れたら中の `owner` に 1 行で `<ホスト名> <pid> <開始時刻（date +%s）> <持ち主の情報> <OS（uname -s）>` を書く。`<持ち主の情報>` は `<pid>-<開始時刻>`。
  書けない・読み返した中身が違うときは取れていないとして待ちに戻る（段階 2b のレビューで直した）
- **古いロックの判断**:
  - 同じホスト名で同じ OS、置き場が `/mnt/` の下でなければ pid で見る。`kill -0 <pid>` が失敗すればすぐ古い。
    **持ち主が生きていれば、10 分を過ぎても強制取得しない**（段階 2d のレビューの決定 B。長い操作のロックを強制取得して二重に書かせない）。
    待っても取れなければ「ロックが長い（10 分を超えて持たれている）。持ち主はまだ動いている」と言って失敗にする
  - ホスト名か OS が違う（WSL と Git Bash は同じホスト名になり pid が通じない）、置き場が `/mnt/` の下、`owner` が読めない、のどれかなら
    pid を確かめられないので時刻だけで判断する（**10 分**。`owner` が無ければ `find <ロック> -maxdepth 0 -mmin +10` で見る）
  - 数は先頭の 0 を落としてから比べる（`$(( ))` が 8 進に読まない）
  - pid の再利用で、落ちたセッションのロックが生きた別のプロセスの pid と重なると取れなくなる。受け入れて、ユーザがロックを確かめて消す
  - Git Bash の `$$` は MSYS の番号で、`kill -0` はロックを取る側も見る側も sh なので通る見込み（確度は中程度。段階 2d の試験で確かめ、駄目なら Git Bash では時刻だけにする）
- **強制取得の仕方**（段階 2b のレビューで直した）:
  1. 強制取得の操作を別のロック `<ロック>.steal`（`mkdir`）で 1 つにする。このロックが取れなければ強制取得せずに待ちに戻る。10 分を過ぎたこのロックは強制取得の途中で落ちたプロセスの残りとして外す
  2. `<ロック>.steal` を持ったまま、古いと判断したときに読んだ `owner` の行と今の行を比べる。違えば（持ち主が替わった）強制取得しない。行が空なら、ロックの年齢（`-mmin +10`）をもう一度確かめる
  3. 同じなら `mv <ロック> <ロック>.stale.<自分の pid>` で退け、退けた中の `owner` がまだ同じなら退けたものを消して `mkdir` から取り直す
  4. 違えば（`mv` までの間に替わった）、元の名前が空いているときだけ `mv` で戻して待ちに戻る。空いていなければ（別の持ち主が取った）戻さずに失敗にしてユーザの対応に切り替える
  5. `<ロック>.steal` を外す
- **待ち**: 既定 120 秒、1 秒おきに試す（`CCNAVI_LOCK_WAIT` で変えられる）。並列の子 3 つがそれぞれ fetch と push を往復すると 30 秒を超えるため、30 秒より長くした。
  SessionStart だけは待たない（4.2）
- **入れ子**: 取った sh は `CCNAVI_LOCK_HELD="<リポジトリ>/<P>:<持ち主の情報>"` を子に渡す。write-and-push の中から呼ばれた sh（承認の pushなど）は、自分の親子のチケットとこの値が一致し、その持ち主の情報がロックの `owner` のものと同じならロックを取ったものとして進み、外さない（持ち主の情報の合わない値は偽物として無視する）。
  この持ち主の情報は協調のためのもので、保護ではない。同じ OS ユーザーのプロセスは `owner` を読んで同じ値を作れるので、偽の値でロックを取らずに進める（段階 2d のレビュー。受け入れる）
- 外すのは取った sh だけ。`owner` の持ち主の情報が自分のものでなければ（強制取得された後）外さない。外すときに自分が渡した `CCNAVI_LOCK_HELD` も消す。
  `trap` は EXIT と INT・TERM・HUP の両方に置く（dash は EXIT の trap をシグナルで走らせない）

#### 戻しの定義

`reset` は使いません。

- **先頭が自分のコミット `C` のときだけ**戻す。`git update-ref refs/heads/P H0 C`（比較つき。先頭が `C` でなければ git が拒むので、
  その間に別の操作が積んだコミットを消さない）。先頭が `C` でなければ戻さず、失敗にしてユーザの対応に切り替える
- 戻した後、`C` に入れたパスの索引を `git restore --staged --source=H0 -- <パス>` で `H0` に合わせる
- **この実行で書いたパス**だけ、作業ツリーの中身も書く前に戻す: `H0` にあれば `git restore --worktree --source=H0 -- <パス>`、無ければ消す
- 3 で先にコミットした (b) と、4 の取り込みの merge は戻さない（手元に残り、次の write-and-push の push で送られる。5 の確かめは (b) を許すので止まらない）
- write-and-push の中の sh は `ccnavi-git.sh` を通らずに git を呼ぶ（`ccnavi-git.sh` はエージェントの入口の保護）。5.2 で `restore --source` を拒否するのは
  エージェントの入口だけで、ここの戻しには当たらない
- 限界: hook が同じ状態の履歴のファイル（`events/<識別子>.jsonl`）に 7〜11 の間に追記すると、戻しでその行が消えることがある。履歴は補助で、本物とするものではない（`history.py:3-7`）ので受け入れる

#### fsio の「この実行で書いたパス」の記録レイヤー

「書いたパス」の一覧をコアの `Changes`（6.2）だけから取ると足りなくなります。コアの外で書いている箇所があるためです:
`ops.start`・`finish`・`cancel`、`approval_ops.followup`（`approval_ops.py:286-372`）、`configsync.apply`（`configsync.py:159`）、
フローのハッシュ `flow.record_digest`（`flow.py:964-`）、リスクの記録 `phases/<親>/<子>.risk.json`（`approval.py:914`）。

- `fsio` の書き込みの関数（`write_text`・`write_text_atomic`・`write_bytes`・`write_json_atomic`・`remove`、`fsio.py:143-293`）に、
  記録が有効なあいだだけ「書いた・消したパス」を記録するレイヤーを入れる。有効にするのは CLI の入口で、sh から `--record-writes <ファイル>` を渡されたときだけ
- 記録のファイルは**state の置き場の側**（`conf.state` の下の `write-and-push/<リポジトリ>/<P>.<持ち主の情報>.writes`）に置く。ワークツリーに置くと記録のファイル自身が未コミットの変更になる
- 出すのはワークツリーからの相対パスの一覧。**置き場の外が入っていたら error**（write-and-push は状態だけをコミットして push する）。例外は 1 つだけ（D34）:
  `start` の中の `configsync.apply` がコピーしたプロジェクトのレイヤー（共通レイヤーにあるファイル名に限る）と、指す先を直した配点のスクリプト。
  コピーする役は ADR-0084 どおり残るので、`P` に入れて、プロジェクトだけを clone したユーザへ渡す
- fsio を通らない書き込みは記録レイヤーを通す形に揃える。今ある所:
  - `approval.py` の `os.remove`（`:382,492,859,1843`）・`os.rename`（`:461`）・`shutil.copy2`（`:486`）・`os.remove`（`:497`）。`clear_marks`（`:853-870`）を含む
  - `history.note` の追記（`history.py:197` の `os.open`）
  - `configsync._replace`（`configsync.py:541-553`。一時ファイル `.ccnavi-sync` に `open` で書いて `os.replace`）
  - 揃ったことは「記録を有効にして各コマンドを回し、`git status` の変化と一覧が一致する」試験で確かめる

#### そのほか

- **`record-risk`** は write-and-push にしない。書いた `<子>.judge.json` はその子の `finish` の write-and-push がコミットして push する（`finish` はこの判定を入力として読むので、記録レイヤーが読んだ入力として一覧に足す）。
  record-risk を別の write-and-push にする形は採らない
- **push する先は `P` だけ**。子のブランチは送らない（`ccnavi-git.sh:562` と同じ）
- **REQ-APV-11** が止めているのは「承認済みチケットをコミットして push する sh をエージェントが起こすこと」です。補足の文を事実に合わせて直します（設計書と要件に反映済み）。直した文は次のとおり。
  > write-and-push の push は `P` の未送信のコミットをすべて送る（git push の性質）。コードのコミットはエージェントが `ccnavi-git.sh push` で送れる範囲と同じ。
  > 置き場について送るのは、状態の操作がこの実行で書いたパスと、ccnavi が書いたと内容で分かるパス（4.4 の (b)）だけで、
  > それ以外の置き場の変更が未送信なら write-and-push は送らずに止める（4.3 の 5）
- **CI**: ccnavi のコミット（Chrome と write-and-push）が `P` に積まれるたびに、ホストの CI が走る。既定では `[skip ci]` を付けない。
  付ける設定を置く場合も、**`ready` のマーカーのコミットには付けない**（マージ時の先頭が skip だと必須チェックが走らない）
- C3 の「取り込み時の判定し直し」は安全網として入れる（ユーザが手で push した状態も拾える）

### 4.4 write-and-push の外の書き手が書いたものをどう push するか

write-and-push の 3（と 5）で、置き場（`.ccnavi/approved/`・`wip/proposals/review/`）の未コミットの変更を次のどれかに分けます。
見分けは Python が行い（ローカルの git と中身だけを見る）、sh は結果に従います。

- **(a) この実行が書いた**: fsio の記録レイヤーの一覧。8 でコミットする
- **(b) ccnavi が書いたと内容で分かる**: `configsync.is_synced_write`（`configsync.py:202-`）と同じ考え方で、パスの形と中身の形と
  変更前のコミット済みの中身が揃ったときだけ当てる。台帳は持たない。当たったものは 3 で**取り込みの前にコミット**する
- **(c) ユーザが push するもの**: write-and-push は push しない
- **(d) 見分けられない**: 何も書かずに止め、「置き場に ccnavi の知らない変更がある（<パス>）。ユーザに確かめる」と言う
- **数えないもの**: 書きかけの一時ファイル（fsio の `*.<一意>.part.*`、`fsio.py:189`、フローの保存の一時ファイル `flows/.*.tmp`、configsync の `*.ccnavi-sync`）。
  どれにも数えず、コミットもしない

**(c) の規則は 1 つです**: 置き場に (c) の未コミットの変更があれば、write-and-push は止めて「ユーザの判断が未送信（<パス>）。承認の push（`ccnavi-push-approved.sh <P>`）を打つ」と言う。
ユーザが打つコマンドは最後に承認の pushを自動で呼ぶ（D27・4.6）ので、止まるのは承認の pushが失敗したとき（オフライン・競合）と、ユーザが実行ファイルを直に打ったときだけです。

エージェントがシェルから偽の `skipped` を書いて (b) としてコミットして push されても、レビューで止める判定（`phase.gate_closed`、`phase.py:590`）は
`review_required` をマーカーとは関係なく、フェーズの種類などから計算し直し、`reviewed` のマーカーが無ければ止めたままにします。この前提（止める判定が `skipped` を見ない）が崩れる変更をしたら、(b) の範囲を見直します。
ただし `phase.plan_finished`（`phase.py:1086-1087`）は最後のフェーズで `requested`・`reviewed`・`skipped` のどれか（asked）があれば「計画を終えた」と数えるので、
偽の `skipped` が計画の終わりの判断を左右する余地は残ります。受け入れる危険に数えます（5.1）。

- メリット: hook の書き込みをコミットして push する仕組みを別に持たずに済む。ユーザの判断はエージェントが送らない。取り込みが hook の書きかけで止まり続けない
- デメリット: ユーザの判断を push できなかったあいだ、エージェントの状態の操作が止まる。hook が置いたマーカーは次の write-and-push まで Chrome から見えない

`docs/claude/exe-boundary.md` の「実行ファイルはネットワークに出ない」を守ります。

| 仕事 | 置き場 |
|---|---|
| `ls-remote`・fetch・早送り・merge・`git cat-file` での `done/` の確かめ・取り込み状態の書き出し | `ccnavi-sync.sh`（新規）と write-and-push。SessionStart の `ccnavi-fetch.sh` は fetch と早送りだけ |
| ロック・コミット・push・失敗したときに届いたかの確認・戻し | `ccnavi-ticket.sh`・`ccnavi-review.sh`・承認の push（共通の関数は `ccnavi-common.sh`） |
| マージリクエストのマージ済みの確認、`confirm` のマーカーに入れるアカウントの引き当て（GitHub `GET /user` の `login`、GitLab `GET /user` の `username`） | `ccnavi-review.sh`。結果は `--actor <名前>` と `--result` で Python に渡す |
| 置き場のパス、書いたパスの一覧、write-and-push の外の変更の見分け、判定、lint | Python（ローカルの git とファイルだけ） |

sh の書き方（Windows Git Bash・WSL・Linux・macOS の bash 3.2 と BSD のコマンド）:

- 日時は `date +%s` と `find -mmin` だけにする（`stat -c`・`date -d` は BSD に無い）
- `ls-remote` の出力は `grep -F -x` で完全一致にする
- **jq を使わない**（D33）: `ccnavi-fetch.sh` は jq を使わない方針で、`ccnavi-git.sh` と `ccnavi-sync.sh` も同じにする。取り込み状態は 1 行 1 項目の `<鍵> <値>` にして `sed -n 's/^<鍵> //p'` で読む。
  JSON（`.claude/settings.json` など）は Python が読んで、sh には 1 行で返す。`ccnavi-review.sh` は今どおり jq が要る（ホストの応答を組むため）
- `$( )` の中に `case` を書かない（bash 3.2。`ccnavi-fetch.sh:114-115` の注意と同じ）。`mktemp -d` は `-t` の書き方も試す（`ccnavi-fetch.sh:63`）
- `kill -0`・`mv`・`mkdir` のほかに、プロセスを扱うコマンドや原子的な操作のためのコマンドを使わない

- Python のコマンド `ccnavi sync` は置かず、`ccnavi-sync.sh` に置き換える
- メリット: 実行ファイルの境界と hook の前提（外部プロセスとネットワークを使わない）を崩さない
- デメリット: sh が増え、3 つの OS で動く書き方と試験が要る

### 4.6 承認の push（`ccnavi-push-approved.sh` の改修。D27）

今の `ccnavi-push-approved.sh` は、全ツリーを回って置き場を丸ごと `add` し、パスを限った `commit -- <パス>` をして push します（`:156-190`）。
取り込みをせず、ロックも取らず、push に失敗してもコミットを残します。これを次のように改めます。

- **引数で親子のチケットを受け取る**: `ccnavi-push-approved.sh [<P>...]`。省けば今どおり変更のある全ツリー。ユーザのコマンドから自動で呼ぶときは、その `P` を渡す
- **対象の親子のチケットなら write-and-push と同じ手順**: ロック（入れ子を許す）→ 途中の操作の確認 → 取り込み（4.2）→ 置き場の変更のコミット → push → 失敗したら届いたかの確認。
  取り込んでから送るので、Chrome の承認と重なっても push が拒まれにくい。衝突したら `merge --abort` して止め、ユーザの対応に切り替える
- **コミットは `commit --only -- <パス>`**（D35）。今の `commit -- <パス>` も git の既定で `--only` と同じ働きだが、明示する。置き場を丸ごと `add` するのは変えない（ユーザの判断のパスを 1 つずつ数えない）
- GitLab のリポジトリなら `seq` を同じコミットで更新する（8.4 の 2 段目から）
- push に失敗したら今どおりコミットは残す（ユーザが打ち直せる）。write-and-push は 4.3 の 5 でこの未送信のコミットを見つけて止まり、承認の pushを打ち直すよう案内する
- 対象外の親子のチケット（取り込み状態が無い）では今の動きのまま

**自動で呼ぶ場所**（ユーザが打つコマンドの最後）:

| ユーザの操作 | 呼び方 |
|---|---|
| 端末の承認 `ccnavi-approve.sh` | 今どおり最後に呼ぶ（`ccnavi-approve.sh:86-87`） |
| VS Code のボードの承認 | 今どおり端末に 1 行送る（設計 9.4） |
| `--reviewed --chat`・`--config-synced`・`--close-early` | ユーザが打つ入口を sh にする: `ccnavi-review.sh chat <N>`・`ccnavi-review.sh config-synced <親>`・`ccnavi-review.sh close-early`。中で実行ファイルを呼び出し、通ったら承認の pushを呼ぶ。エージェントが打った場合は今の deny（`phase.py:105-113`）と同じく止める |
| ボードのフローの保存 | 保存の後、承認と同じく端末に 1 行送る |

実行ファイルをユーザが直に打った場合（`ccnavi --reviewed --chat` など）はpush されません。次の write-and-push が (c) を見つけて止まり、承認の pushを案内します。

- メリット: ユーザの判断が溜まらず、write-and-push が止まるのはpush できなかったときだけになる。承認の pushも取り込みの後に送るので Chrome との競合で止まりにくい
- デメリット: ユーザの操作の最後にネットワークが要り、オフラインでは判断の後に打ち直しが要る。偽物が置き場に紛れていれば一緒に push される（5.1）

## 5. 受け入れる危険

リモートで承認する形では、今の「承認済みの置き場にエージェントが書けない」（要件 REQ-APV-07）が成り立ちません。
ユーザの判断で、エージェントの自己承認の対策は頑張りすぎず、手間をかけずに防げる抜けだけ防ぎ、残りは危険として受け入れます。

### 5.1 残る穴（エージェントによる自己承認）と REQ-APV-07 の改訂

エージェントは次の経路で、承認されたように見えるチケットを `P` に作れます。**どの経路にも、表示で気付ける仕組みはありません**（D29）。

- **ホストの API への直接の書き込み**: `gh api`、`GITHUB_TOKEN` と curl、GitHub MCP、GitLab の API
- **`ccnavi-git.sh` を通るチケットの巻き戻し**: `checkout <古い ref> <パス>`、`restore --source <ref>` で `approved/` を過去の中身に戻す（5.2 で防ぐ）
- **ブランチの付け替え**: `checkout -B`・`worktree add -B` で `P` を別のコミットに向け直す（段階 2b で防ぐ）
- **merge への混入**: `P` への通常の merge に、作ったチケットを混ぜる
- **(b) への偽装**: hook が置くマーカーの形を真似た `pending`・`skipped`。レビューで止める判定は解けない（4.4）が、最後のフェーズの偽の `skipped` は `plan_finished`（`phase.py:1086-1087`）を真にしうる
- **deny の表記の抜け**（段階 2d のレビュー）: 承認の push・`--forget`・ユーザの判断の入口の sh を止める組み込みの deny は、コマンドの位置の表記
  （`sh -x …` のようにシェルに選択肢を付けた形を含む）で見る。変数の展開（`$S/ccnavi-push-approved.sh`）や `cat … | sh -s` のように、
  表記が実行するまで現れない形は止めない。これらを止めると、読み切れない形を全部止めることになるので、受け入れる
  （2026-10-11 追記: 2 段目の無い入口（`--forget`、`decide --choices`、実行ファイルの `--yes`）は、引数を読み切れなければ止める側に移した。ADR-0122）
- **(c) への紛れ込み**: エージェントが置き場に作ったファイルが、ユーザが打った承認の pushの「置き場を丸ごと `add`」で一緒に送られる。台帳は作らない（D27）
- **手元の窓**: リモートから手元への反映の遅れが、hook の判定に残る（SessionStart で分かれていた親子のチケットは次の write-and-push まで古い）
- **一人開発**: 承認者と開発者が同じアカウントなら、上のどれもユーザの目で区別する材料が無い
- **統合先の変更で基準が動く**（D28。ユーザの決定で受け入れる）: Chrome の判定はプロジェクトのレイヤーと共通レイヤーを統合先の現在値から計算するので、
  着手の後に統合先のレイヤーが変わると、開いている親子のチケットの Chrome の判定の基準もそれに合わせて動く（厳しくなる場合も緩む場合もある）。統合先への変更はマージリクエストのレビューを経る前提で受け入れる。
  手元はワークスペースルートと作業ツリーのレイヤーを読む（決定 B1）ので、手元と Chrome でレイヤーが食い違いうる。違いは `--lint` の warn で知らせるだけ
- **統合先の名前のずれ**（D30）: Chrome と手元が別の統合先を読むと答えが食い違う。止める・名前を出す緩和だけで、揃える仕組みは持たない
- **削除せずに残した親子のチケットの取り込み状態をユーザが消せる**（段階 2b のレビューの後の「片付けで消せる」を、段階 2c のレビューの後の決定 A で改めた）:
  片付けと `ccnavi-sync.sh` では取り込み状態は消えない。消せるのはユーザが打つ `ccnavi-sync.sh --forget <P>` だけで、消した後は同じ名前でワークツリーを
  切り直して push し直せる（捨てた親子のチケットを同じ識別子で切り直すための手段）。エージェントの Bash は組み込みの deny が止め、state の置き場（`logs/state/`）は
  自己防衛が守る。残る危険は、ユーザが止まった理由を確かめずに消すことと、ホストの API への直接の書き込み（5.2 と同じく防がない）
- **止めの解除にネットワークが要る**: `gone`・`blocked` の親子のチケットを戻すのは、オンラインで打つ `ccnavi-sync.sh <P>`（取り込みと検査し直し）だけ。
  オフラインでは解けず、案内文にも「オンラインで」と書く
- **`expectedHeadOid` は `P` しか守らない**（段階 3 のレビューの後の決定 C）: Chrome が読んでから書くまでの間に、統合先の `done/`・レイヤーや
  閉包の `P_X` が動いても、書き込みは通る（先頭の一致を取るのは書く先の `P` だけ）。その間の変更で判定が変わる形は、手元の取り込みの後の
  判定し直し（C3。4.2 の 4）が後で見つけて親子のチケットを `blocked` にする前提で受け入れる。書き込みそのものは戻さない
- **ダイジェストが関係の無いワークツリーの動きで揺れる**（段階 2c のレビューの後の決定 B2）: 手元の read_set は、取り込み状態の無い親子のチケットでは全ツリー上のチケットを読むので、
  preview と `--yes` の間に関係の無いワークツリーを作る・片付けるとダイジェストが変わり、見せ直しになる。厳しくする変更（承認が通らないだけ）なので受け入れる

**REQ-APV-07 の改訂（決定。判定がさらに緩む変更）**: 次に書き換えます。

> 承認済みチケットの置き場に在ること自体を 3 つめの証拠として認める。手元の置き場へのファイル操作はエージェントに書かせない。
> リモートの置き場（親のブランチ）はホストの権限でのみ守る（書き手の表示は行わない）

「取り込むときに、置き場を変えたコミットの書き手を表示すること」を改訂文に入れなかったので、書き手を表示する案より判定がさらに緩む変更です。
改訂が適用され始めるのは Chrome で承認を書く段階 3 です。判定が緩む変更であることは、ADR と要件の変更履歴に明記します。

### 5.2 安く塞ぐ抜け（既存のガードで足りるもの）

| 抜け | 塞ぎ方 | 場所 | 段階 |

| `branch -M`（強制の改名）が通る | 短いオプションの検査に `*M*` を足す。回帰試験（3.1 の 10） | `ccnavi-git.sh` の `branch)` | 0 |

| `restore --ours/--theirs` で `approved/` の衝突を解く | 置き場に当たる形を拒否し、「ユーザの対応に切り替える」と案内 | `ccnavi-git.sh` の `restore)` | 0 |

ホストの API への直接の書き込み（`gh api`・`glab api`・curl・MCP）は**防ぎません**。`gh api` だけを ask にしても、
`GITHUB_TOKEN` と curl で同じことができ（`rules.yml:137-150` は curl に文脈を添えるだけ）、一貫しないためです。受け入れる危険に数えます。

### 5.3 書き手の表示をしない（D29）

検討の途中にあった案（取り込みで `approved/` を変えたコミットの作者・merge の中身を表示し、Chrome にも「拡張以外の変更」を出す）は、ユーザの判断でやめます。

- 手元: 取り込み（4.2）で書き手を表示しない。`history.note` にも残さない。merge コミットの分解もしない
- Chrome: 承認・取り下げ・レビュー済みの画面に書き手の一覧を出さない。そのための `GET /commits?path=` も引かない
- 署名の検証の状態も出さない（D10）
- コミットの目印も表示の材料だったので削る（D37）。write-and-push の見分けも取り下げも目印を読まない（4.4・8.8）

- メリット: 取り込みと Chrome の画面が軽くなり、表示のための API の読み取りと merge の分解の実装が要らない
- デメリット: 別の人が承認する普通の形でも、偽の承認を目で見付ける手掛かりが無くなる（ホストの履歴をユーザが見に行けば分かる）

### 5.4 将来の強化案: 承認者の署名（案 S。今回は入れない）

- 承認者ごとに Chrome 拡張の中で鍵を作り、承認の中身（承認済みチケットの本文、識別子、判定が読んだ中身のダイジェスト）に署名し、その署名を承認済みチケットのキーの値として承認済みチケットの欄に載せる
- 公開鍵は統合先の保護された場所（例 `.ccnavi/config/common/approvers.yml`）に登録し、取り込みで検証する。取り下げとレビュー済みも対象
- メリット: 一人開発でも、PAT が漏れても、承認は偽造できない
- デメリット: 鍵の置き場が同じ OS ユーザーから守れない問題が残り、鍵の運用と手元の署名検証の依存が増える

### 5.5 PAT の保管と XSS

#### 保管（D23）

**PAT は `chrome.storage.local` に平文で永続保存**します。暗号化（鍵もプロファイルに残る）、OS のキーチェーン（Native Messaging が要る）、
`storage.sync`（他の機械へ広がる）は採りません。

受け入れる危険: 同じ OS ユーザーのプロセス（エージェントを含む）はプロファイルの中の PAT を読めます。
承認者の機械が開発機と別ならそれらのプロセスは PAT を読めませんが、同じ機械で一人開発をしているなら読めます。マルウェア・バックアップ・拡張の乗っ取り・ログへの混入も受け入れます。

残す緩和:

- リポジトリを限った最小の権限のトークンにする（8.5）。ただし GitLab.com の無料版で project access token が使えない場合は、
  `api` スコープの個人の PAT になり、**リポジトリを限れない**。これも受け入れる危険に入れる（10.2 の確認事項 3）
- エージェント用のトークン（`ccnavi-review.sh:169-195` の `GITHUB_TOKEN`/`GITLAB_TOKEN`）とは別のトークンにする
- 設定画面からいつでも削除・差し替えでき、差し替えのときは古いトークンの失効を案内する

#### 期限（D25）

- 既定は 90 日。登録画面でホストの作成画面へのリンクと、選ぶ権限の一覧を出す
- 期限はホストの PAT の期限を優先する。GitHub は応答ヘッダ `github-authentication-token-expiration`、GitLab は `GET /personal_access_tokens/self` の `expires_at`
- GitHub のヘッダは、`host_permissions` を持つ拡張の fetch が CORS の制限を受けないので読めるはず（確度は中程度）。**段階 3 で確かめる**。
  読めなければ登録時にユーザが期限の日付を入れる（入れなければ「期限不明」と出し続ける）
- 期限が切れる 7 日前から、service worker が `chrome.alarms` で 1 日 1 回期限を確かめ、バッジとボードの帯で知らせる。401 が返ったら差し替えを促す

#### XSS への対策（入れる）

1. **入力の扱い**: チケット本文・コメント・issue の本文・ブランチ名・マージリクエストのスレッドなど、リポジトリやホスト由来の文字列は攻撃者が制御しうる入力として扱う
2. **描画**: Markdown は HTML に変換した後に DOMPurify（同梱）でサニタイズする。素の文字列は `textContent`。リンクは `http:`・`https:`・`mailto:` だけ
3. **CSP**: MV3 の既定を緩めない。足すのは Pyodide に要る `'wasm-unsafe-eval'` だけ。`'unsafe-eval'`・`'unsafe-inline'`・外部のスクリプトは入れない。
   Pyodide に `'unsafe-eval'` が要る場合は、その部分だけ sandbox ページに移す（7.2）
4. **PAT に触る場所を限る**: PAT を読むのは service worker だけ。画面と Pyodide の Worker には渡さず、ホストの API の呼び出しは、名前で限った操作として
   `chrome.runtime.sendMessage` で service worker に頼む。`sender` を確かめ、`externally_connectable` は宣言しない。
   限界: 同じ拡張オリジンなので、画面で XSS が起きれば storage を読める。主な対策は 2・3
5. **外へ送りにくくする**（D24。ADR-0128 が改める。設定画面で足すホストは `optional_host_permissions` で許可を取り、`connect-src` は https 全般）: `host_permissions` を、ビルドのときに埋め込んだ API のホストに限る。既定は `api.github.com` と `gitlab.com`
6. **試験**: 悪意のある Markdown の見本（`<script>`、`<img onerror>`、`javascript:` のリンク、`<svg onload>`、`data:` の URL、実体参照で崩したスキーム）を段階 1 と段階 4 で回す

## 6. 判定のコアと差し替え点の境目

### 6.1 今 I/O が混ざっている所（読んだもの）

- 読み: `gather` が提案・承認済みチケット・閉じたもの・レビュー待ちを走査（`approval.py:1170-1178`）。`phase.phases_of` が中で `approval.scan` を 2 回呼ぶ（`phase.py:703-704`）。

### 6.2 境目

```
Snapshot（入力）
  branches: { 名前 → { head_sha, files: { 相対パス → bytes | NOT_FETCHED } } }   # 統合先、P、参照の閉包の P_X だけ
  layers:   ワークスペースの統合先の共通レイヤーと自身のレイヤー、プロジェクトの統合先のレイヤー（3.3 の 6 で合成）
  settings: 置き場のパス（統合先から）
  compat:   統合先の CCNAVI_COMPAT（7.3）
  stamp:    時刻（オフセット付き文字列）
  actor:    { account: ホストのアカウント名 or 手元の git の user, via: chrome|cli|terminal|board }

judge(snapshot, only, shown_ids?, shown_digest?) -> Verdict
  batch, rejected, screen_text, digest, problems, read_set    # read_set = 判定が読んだ { ブランチ, パス → sha256 }

plan(snapshot, verdict) -> Changes
  per_branch: { 名前 → [ {op: create|update|delete, path, content?} ] }   # 状態の履歴の行を含む。seq は含まない（GitLab の Writer が足す）
  lines: ユーザに見せる行

withdraw(snapshot, ids, prior_proposals, reason) -> (problems, Changes)    # 8.8。prior_proposals = 承認コミットの親にあった todo/<id>.md
confirm(snapshot, phase_no, result, changed_since_request) -> (problems, Changes)  # 8.9
reviewed_mark(mr, accepted, actor, stamp) -> dict                                 # 8.9。confirm と decide の両方が使う
```

- **判定の入力は統合先・`P`・閉包の `P_X` に固定**する。直近 N 日のブランチとユーザが指定したブランチは、表示する提案を見つけるのに使うだけ
- **取っていないファイル**: 一覧（tree）にあるが中身を取っていないファイルは `NOT_FETCHED` にし、判定が読もうとしたら error にする（「無い」と読ませない）。
  コアに移る前の、MEMFS で動かす間（段階 1）は、判定が読みうるものを全部取る（8.2）
- **ダイジェスト**は画面の本文と `read_set` から作る。全ブランチの `head_sha` は入れない
- **先頭の一致は書き込みの条件として別に確かめる**（8.3・8.4）
- 差し替え点は 3 つ: **Reader**（手元のツリーと取り込み結果 / REST・GraphQL API から Snapshot を組む）、**Writer**（手元に書く / GitHub GraphQL / GitLab Commits API）、**Clock**
- 手元の `--approve` は「Reader(FS) → judge → plan → Writer(FS)」、hook・lint・explain は「Reader(FS) → judge の部分関数」。
  手元の Writer(FS) は fsio を通るので、write-and-push の記録レイヤーがそのまま使える
- `settle_review` の再走査は、plan の中で「このバッチで動かした後の Snapshot」を組み直して行う
- `history.note` の 1 行も `Changes` に入れる（`events/<識別子>.jsonl` の末尾に足した中身を `update` で書く）。
  Chrome は先頭の一致を条件にした 1 コミットで書き、先頭が動いていれば必ず新しい Snapshot から plan をやり直す（8.3）ので、相手の追記を消さない

同じ答えを出すことの確かめ方:

- 今の見本は新規の承認 1 件だけで、比較は差分のパスの一覧だけ（`pyodide-trial/run.mjs:161`）。中身のバイト比較に変える
- 見本を足す: 改版、マーカーの消去、フローの移動、`settle_review`、多段の先行（閉包で集めた対応表と、手元で閉包に揃えた対応表で答えが同じになること）、通らない提案（問題点の文面まで）、取り下げ、レビュー済み
- 手元と Pyodide の両方の Python の版で回す。MV3 の拡張のページの Worker での起動と一致は段階 1 で確かめる

- メリット: 実行場所に依存しない。書くファイルの一覧が値として出るので 1 コミットに組みやすい
- デメリット: `approval.py`（2616 行）・`phase.py`（1365 行）・`review.py`（1941 行）の広い範囲に手が入り、影響範囲が読み切れない（着手前に相談する）

## 7. 承認の実行場所（Pyodide で確定）

### 7.1 TS に寄せると二重になるもの

本物とする側の推定を片付けても、次の判定は残り、どれも hook・lint・explain と共有しています（`lint.py:535-541,705-710`、`diagnose.py:757-775`）。

| 部分 | 場所 | 二重になる理由 |
|---|---|---|
| チケットの読み | `ticket.py`（1436 行の大半） | 読み方の違いがそのまま判定の違いになる |
| フェーズの種類とレイヤーの合成 | `phasetypes.py`（561 行）、`phase.load_types` / `layer_types` | 種類で待ち方が変わる |
| 待ち方の計算 | `workflow.py`（187 行） | 違えば改版の判定（`approval.py:2142`）が食い違う |
| フェーズの一覧と順序 | `phase.phases_of`、`order_problems`（`:993-1062`） | 承認でしか止まらない「フェーズ順序」 |
| 承認の検査 | `validate` / `project_problems` / `revision_problems` / `plan_problems` / `predecessor_problems` / `candidates` / `waiting` | 計画の形・改版の制約・done の開き直し |
| レビュー済みの検査 | `review.confirm` / `_unresolved` / `effective` / `accepted_threads` | 変更要求・未解決スレッドの数え方 |
| 画面とダイジェスト | `screen` / `approval_digest`（`:1414`） | 同じ提案に 2 つのダイジェストができる |
| 書き出しの本文 | `ticket.insert_front` / `set_fields`、`admit`、`revise_copy` | ユーザの書いた行を保つ行単位の編集 |
| YAML の読み | PyYAML の SafeLoader（YAML 1.1）、`flow._Loader`（`flow.py:467-520`） | 型の差が判定の差になる |

TS への書き直しは 3,000 行を上回る見込みです。

### 7.2 比較（記録として残す）

| 観点 | **P: Pyodide（決定）** | T: TS に寄せる | H: 読み取りは TS、承認は Pyodide |
|---|---|---|---|
| 判定が 1 か所か | はい | いいえ（3,000 行超の二重） | 承認はい / 表示は二重 |
| 起動と応答 | 起動 + import 3.5〜4.5 秒（.pyc 同梱で import 0.43 秒）、承認処理 0.1 秒（Node で測った値） | 速い | 表示は速い |
| 配布の大きさ | 約 14MB（gzip 6.5MB）を同梱 | 小さい | 両方 |
| MV3 の制約 | CSP `'wasm-unsafe-eval'`。拡張のページの Web Worker で動かす | 無い | P と同じ |
| ADR-0035 | 「同じコードの答え」と読み替える改訂 | 原則を捨てる | 表示の分で反する |

**MV3 の CSP での確認（段階 1）**: Pyodide は Emscripten の `EM_ASM`/`EM_JS` を持ち、その一部が `eval`（`new Function`）を使うと
`'unsafe-eval'` の無い CSP では動かない恐れがあります（確信なし）。段階 1 で、C 拡張を使わない純 Python の PyYAML を入れた形で
起動・読み込み・見本の一致を確かめます。動かないなら、Pyodide を manifest の `sandbox` ページ（`'unsafe-eval'` を許せるが拡張の API と storage に触れない）に置き、
ボードとは `postMessage` でやり取りします（PAT は sandbox に渡さない）。

- メリット: 判定の二重化が起きない。承認・hook・lint が同じ答えを出す（ADR-0035・ADR-0058）
- デメリット: 14MB と初回数秒の待ち。Pyodide の版上げと同梱の手間。CSP に縛られ、sandbox に移すなら経路が 1 段増える

### 7.3 版ずれ（D31）

Chrome は ccnavi の .pyc を同梱するので、手元の ccnavi と版がずれます。ずれたまま承認すると、手元の C3（取り込みでの判定し直し）が別の答えを出して親子のチケットを止めます。

- 目印は既存の互換の版 `CCNAVI_COMPAT`（`ccnavi-common.sh:27`、`ccnavi_compat_skew` `:168-183` が実行ファイルと sh の食い違いに使っているもの）
- Chrome は統合先の `.ccnavi/scripts/ccnavi-common.sh` からこの行を読み、同梱の版の互換と比べる。**違えば承認・取り下げ・レビュー済みを出さず、表示だけにする**。
  画面には「拡張は互換 X、リポジトリは互換 Y。拡張を更新する（Y が新しい）か、リポジトリの ccnavi の更新を待つ（X が新しい）」と出す
- 止めた状態はどこにも書かない。ボードを開くたびに比べ直すので、版が揃えば自然に解ける
- 互換が同じでも手元の C3 と答えが違ったら、不具合として扱う: C3 は親子のチケットの取り込み状態を `blocked`（`reason` に「Chrome <拡張の版> と手元 <版> で判定が違う」）にして止める。
  解き方は、版を揃えてから `ccnavi-sync.sh <P>` を打ち直す（判定し直して通れば `present` に戻る）。拡張の版は状態の履歴の行（`via: chrome`）に入れて残す

- メリット: 互換の違う判定の結果がリモートに書かれない。既存の互換の仕組みを使うので新しいマーカーが要らない
- デメリット: リポジトリか拡張のどちらかが更新されるまで、Chrome で承認できない期間ができる

| D32 | ロックに持ち主を書き、`mv` で強制取得し、入れ子を許す。生きた持ち主のロックは強制取得しない | 落ちたセッションのロックで止まり続けず、承認の pushを write-and-push の中から呼べる。長い操作のロックを強制取得して二重に書き込ませることがない | ホストをまたぐと時刻だけの判断になり、最長 10 分待つことがある。同じ機械で持ち主が止まったまま生きていれば、ユーザが確かめるまで取れない |

| D34 | configsync の写したレイヤーは `start` の write-and-push でコミットして push する | プロジェクトの親子のチケットで `start` が止まらず、写したレイヤーが ADR-0084 どおり配られる | 記録レイヤーの「置き場の外は error」に例外ができる |
| D35 | `commit --only`、merge は索引が HEAD と同じとき | 他のステージ済みの変更が write-and-push のコミットに混ざらない | ステージ済みの変更があると取り込みの merge で止まる |
| D36 | `checkout -B` の拒否は `ccnavi-sync.sh` と同時、文面も同時に更新 | 復旧手順を途切れさせない | 段階 2b まで付け替えの穴が開いたまま |
| D37 | コミットの目印を削る | どの処理もメッセージに頼らず、目印の偽装を考えなくてよい | ホストの履歴で ccnavi のコミットを機械的に拾えない |

## 得たもの・失ったもの

決定ごとの得失は 10.1 の表に 1 行ずつ置いた。まとめると次のとおり。

- 得たもの: 承認者がブラウザと PAT だけで承認でき、手元とブラウザが同じコード・同じ入力で同じ答えを出す。本物とするのが「親のブランチ上のチケット + 統合先の `done/`」に決まり、ツリーからの推定が消える
- 失ったもの: **REQ-APV-07 が緩む**（リモートの置き場はホストの権限でのみ守り、書き手も表示しない。5.1）。一人開発や PAT の漏れでは偽の承認を区別できない
- 失ったもの: 取り込み済みの親子のチケットでは状態の操作にネットワークが要り、sh（`ccnavi-sync.sh`・write-and-push・ロック）が増える。`approval.py`・`phase.py`・`review.py` の広い範囲に手が入る
- 失ったもの: Chrome 拡張に Pyodide（約 14MB）を同梱し、初回に数秒待つ
- 段階 0 で失ったもの: 置き場に当たるパスを `checkout <ref>`・`restore --source`・`restore --ours / --theirs` で戻す手段と、`fetch`・`pull` の refspec と URL と、`branch -M`・`-C` がエージェントから使えなくなる。要るときはユーザが打つ
- 段階 2b で失ったもの: `checkout -B`・`switch --force-create`・`worktree add -B / --detach / -f`、行き先の名前とブランチ名の違う `worktree add`、親のワークツリーでの別のブランチへの移動がエージェントから使えなくなる。squash マージの後で早送りできないブランチはユーザの対応に切り替える
- 段階 4 で失ったもの: マージリクエストのスレッドとレビューを取ってくる処理が sh と TS の 2 か所になり、ホストの API が変わると見本・sh・TS を揃えて直す手間がかかる。
  ボードを開くたびに、依頼済みのフェーズごとにホストの API を 3〜4 回多く読む。Chrome は依頼時の先頭が祖先でないときも止めるので、手元の confirm が通る形でも止まることがある
- 段階 5 で失ったもの: GitLab には比較つきの書き込みが無いので、書いてから元に戻すまでの間、判定の変わった書き込みが親のブランチに残りうる（8.4 の 1 段目）。
  元に戻すコミットが収まらなければユーザが直すまで残る。手元の C3 が親子のチケットを止める。GitLab の読み書きが sh と TS の 2 か所に増え、
  blob を 1 件ずつ読むので初回のボードが GitHub より遅い。プロジェクト名を Chrome の設定と手元のディレクトリで揃える手間
- 段階 3 で失ったもの: **REQ-APV-07 が緩む**（上の 1 つめ）。ホストの API へ直接書いたチケットと、Chrome でユーザが承認したチケットを区別できない。判定の入力に読めない（バイナリの）ファイルがある親子のチケットは、Chrome では承認も表示も「決まらない」になる

## 採らなかった案

- **状態専用ブランチにチケットを集める**: 作業の履歴と別になり、提案の削除と承認済みチケットの追加を 1 コミットにできない。手元の hook から読めない
- **承認済みチケットを統合先に直接書く**: 保護設定に当たり、変更量が大きい
- **承認以外だけを Chrome に載せる / Native Messaging で手元の ccnavi を呼ぶ**: 承認者の機械に clone と ccnavi が無い前提に合わない
- **ブランチ名を `<番号>-<slug>` にする（N2）**: 題の変更と日本語の題で名前が引けなくなる
- **判定を TS で書き直す（T）・表示だけ TS（H）**: 3,000 行を超える二重化。H は ADR-0035 に反する
- **`P` が無いときに統合先で新規扱いにする**: 改版の制約を迂回できる
- **`P` の改名を追う仕組み / Chrome の「ブランチを戻す」**: 追う先を間違えると本物とする側が動く。戻しはユーザが行い、ccnavi は案内だけにする
- **判定の中で `git cat-file` から `P` を読む**: 判定の中で外部プロセスを起こさない前提に反する（sh の中でだけ使う）
- **Python の `ccnavi sync` にネットワークとコミットを持たせる**: 実行ファイルの境界に反する（4.5）
- **write-and-push をすべての親子のチケットに適用する**: origin の無い・まだ push していない親子のチケットまで止まる（4.3）
- **write-and-push の戻しに `reset` を使う**: 先頭が他の操作で動いていたときに、そのコミットを消しうる。比較つきの `update-ref` にした
- **write-and-push で「取り込み → 書く → コミット」の順**: hook の書きかけと merge がぶつかって止まり続ける。見分けとコミットを取り込みの前に置いた
- **SessionStart で merge・観測ずれの再試行・マージリクエストの確認をする**: hook の時間の枠で途中の merge が残り、ロックなしで他の操作とぶつかる
- **消えた `P` を fetch 失敗の一覧に入れる**: 統合先の取り込みまで飛ばされ、閉じた親子のチケットを「決まらない」にする
- **`ccnavi-git.sh push` の毎回の `ls-remote`**: push のたびにネットワークを往復する。取り込み状態で足りる（届いたかの確認は push が落ちたときだけ）
- **書き手を表示する・merge コミットを分解して見せる・署名の検証を表示する**: ユーザの判断でやめた（D29）
- **コミットの目印を残す**: 表示をやめた後は機械的に読む所が無く、読めば偽装の余地になる（D37）
- **(c) の偽物を防ぐ台帳**: ユーザの判断で作らない。受け入れる危険に数えた
- **record-risk を別の write-and-push にする**: `finish` が同じ判定を入力に読むので、`finish` の write-and-push にまとめた
- **両ホストで `seq` を書く**: GitHub は `expectedHeadOid` で足り、余計なファイルと衝突の種を増やす
- **GitLab で最初から `seq` に頼る**: `last_commit_id` の意味を確かめる前に前提にしない。事後確認から始める
- **取り込み状態を JSON にして sh で jq を使う**: SessionStart と `ccnavi-git.sh` に依存を足す
- **`checkout -B` を段階 0 で拒否する**: 今の復旧手順を、代わりなしに使えなくする
- **configsync の写したレイヤーを未コミットで残す**: write-and-push の記録レイヤーの検査で `start` が止まり、プロジェクトだけを clone したユーザにレイヤーが届かない
- **統合先をデフォルトブランチに固定する**: develop 運用で `done/` とレイヤーを間違ったブランチから読む
- **統合先の名前をホストのデフォルトブランチの `.claude/settings.json` に置く**（検討の途中で推した案）: ユーザの判断で採らない。リポジトリの設定を増やさず、使う側に持たせた
- **版を問わず Chrome で承認する**: 互換の違う判定がリモートに入り、手元の判定し直しで親子のチケットが止まる
- **ダイジェストに全ブランチの `head_sha` を入れる**: 無関係なコミットで承認が通らなくなる
- **Git Data API + `PATCH refs`（`force: false`）**: force push 後の巻き戻しを早送りとして通してしまう
- **承認中に `P` が動いたとき古い plan を新しい先頭に書く**: 状態の履歴の全文の `update` で相手の追記を消す
- **「始める」で Draft のマージリクエストも作る**: 差分 0 のブランチからマージリクエストは作れない（422）
- **GitLab の競合を一時ブランチ + ff マージで防ぐ**: マージリクエストが 1 本増える。前提が崩れたときの予備の案
- **二重状態を C2・C3 で解く**: マーカーを置くのに push が要る / 緩い承認が一度は入る
- **取り下げで `ccnavi_approved.added` を見てキーを外す（`unadmit`）**: 新しいキーとコアの関数が要り、古いチケットで組み直しが不確か。履歴のバイト列を戻す方が確実
- **着手後の承認や改版も Chrome から取り下げる**: 着手で始まった作業と、改版で動いた子・消えたマーカーを戻せない
- **`decide` を Chrome に載せる**: 指摘ごとに行き先を選ぶ画面と issue の下書きの投稿まで要り、今回の目的を超える
- **ホストの設定を変えて Approve が外れないようにさせる**: 設定の可否が未確認で、組織の保護設定に手を入れさせる
- **`gh api` / `glab api` の書き込みを ask にする**: `GITHUB_TOKEN` と curl で同じことができ一貫しない
- **署名を必須にする（案 S）**: ユーザの判断で今回は入れない
- **PAT を毎回入力する（`storage.session`）・WebCrypto で暗号化する**: ユーザの判断、または同じ OS ユーザーには難読化程度にしかならない
