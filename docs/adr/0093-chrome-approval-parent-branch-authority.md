# ADR-0093: 承認は Chrome 拡張から API で行い、写しの権威は親のブランチ 1 枚に固定する

状態: 提案（2026-09-28。段階 0 を採用して実装した。2026-09-29 に段階 1 を実装した（11.2）。同日、利用者が段階 2a〜2d に進むことを承認し（2b・2c は判定を変える段階として相談して承認を得た）、段階 2a を実装した（11.3）。同日、段階 2b を実装した（11.4）。段階 3 以降は 11 章のとおり、入れる前に利用者に相談する）

本文の `ファイル:行` は、この ADR を書いた時点（`6d0e53e`）の行番号です。段階 0 の変更で `ccnavi-git.sh` の行はずれています。

用語:

- 「親のブランチ」（`P`）は親チケットの作業ブランチ。子チケットにとっては親のもの、親チケット自身にとっては自分のもの
- 「親のワークツリー」は `P` を checkout した `.claude/worktrees/<P>`
- 「開発者の手元」はエージェントが動く機械の clone。「承認者」は Chrome 拡張で承認する人。同じ人のこともある
- 「家族」は親チケットと子チケットのまとまり。`P_X` は識別子 `X` の家族の親のブランチ
- 「統合先」は `done/` と層と置き場の綴りを読むブランチ（D30）。リポジトリには置かず、Chrome 拡張の設定と手元の環境変数で変えられ、未設定ならホストのデフォルトブランチ。
  `P` はここから切り、MR はここへマージする（`docs/claude/environment.md` の「統合先ブランチ」と同じもの）
- 「控え」は手元の控えの置き場（`conf.state`）。リポジトリには入らない
- 「家族の控え」は `sync/<リポジトリ>/families/<P>`、「統合先の控え」は `sync/<リポジトリ>/integration/`（3.6・4.2）。
  `<リポジトリ>` はワークスペース自身なら `self`、プロジェクトならプロジェクト名。家族の控えがある家族を「取り込み済みの家族」と呼ぶ
- 「手元の統合先」は最後に取り込んだ `origin/<統合先>`（D26）
- 「運ぶ処理」は人の判断を `P` へコミットして送る処理。今の `ccnavi-push-approved.sh` を改修したもの（4.6）
- 「承認の取り下げ」は Chrome から承認を未承認（`todo/`）に戻す操作（8.8）。
  既存の「差し戻し」（`review.py:419` など。レビューの後に同じフェーズへ子を足してやり直すこと）とも、
  「取り消し」（`cancel`、`done/` へ `cancelled` で閉じる）とも別物

## 1. 背景と目的

- 今の承認は端末（`ccnavi-approve.sh`）か VS Code 拡張のボードで、どちらも手元に ccnavi 本体と作業ツリーが要る。
  ボードは `--approve --preview --json` → `--approve --yes <ids> --digest <d> --json` を子プロセスで呼び
  （`vscode-extension/ccnavi-board/src/ccnavi.ts:264-335`）、承認後に `ccnavi-push-approved.sh` を端末に送って運ぶ
  （`ccnavi.md:1302-1310`）
- 開発者と承認者（レビュアー）は別の人であることがよくある。承認者の機械には clone も ccnavi も無いことが多い。一人で開発・承認する場合もある
- 目的は 2 つ
  1. 承認者がブラウザと PAT だけで、リモートのブランチに対して承認できること。書き先は GitHub / GitLab の API
  2. 他の人がリモートで承認したものを、開発者の手元（エージェント）が取り込んで、その承認に従って動けること
- 障害は 3 つ
  1. 写しの権威を「ツリー」から推定しているので、ブランチしか見えない API 側では同じ答えを出せない
  2. 判定の中核が I/O と絡んでいて、ブラウザで同じコードを動かすには切り出しが要る
  3. 状態（着手・終了・マーカー）を手元が書き、承認をリモートが書くので、両者の間に二重の状態ができる
- 制約: ccnavi の実行ファイルはネットワークに出ない（`docs/claude/exe-boundary.md`）。外とのやり取りは `.ccnavi/scripts/` の sh が持つ

## 3. 親のブランチと権威

### 3.1 親のブランチ名の規則

#### 今の運用（読んだもの）

- ワークツリーの置き場は `.claude/worktrees/<ブランチ名>`（`docs/claude/worktree.md:34`）
- 着手はワークツリーの**ディレクトリ名**が識別子と大文字小文字まで一致することを求め、
  作り方として `worktree add ".claude/worktrees/<id>" -b <id>` を案内する（`ccnavi/ops.py:57-68`）。子も同じ（`ccnavi/review.py:524`）
- 「ワークツリーの名前は識別子と同じ」は既に明文（`ccnavi.md:1059`）。識別子の形の規則は `ccnavi.md:1056-1057`
- 識別子とブランチ・ワークツリーの結び付きは、着手・レビュー・push の守り・権威のほかに
  `ops.py:339,395,707`、`diagnose.py:645,992`、`flow.py:1360`、`lint.py:910` にもある
- 権威の推定は `approval._authoritative` の `at_home`（`approval.py:275`）で、ツリー名と親の識別子を比べる
- `ccnavi-git.sh` は「ディレクトリ名 = ブランチ名 = 識別子」を強制していない（`worktree)` の節は行き先の置き場しか見ない）
- `ccnavi-git.sh branch` の拒否には漏れがある:
  - 短いオプションの検査 `*f* | *m* | *u*`（`ccnavi-git.sh:186-188`）は大文字小文字を区別するので、`-M`（強制の改名）は通る
  - 長いオプションは `--move` を拒否する（`:178`）が、使い方の文（`:82`）は「`-M` 不可」と書いていて、実装と食い違う
  - `-D` は `*D*` で拒否（`:183-185`）、`-m` は拒否
- `ccnavi-git.sh fetch` は `-f`・`--force` などを拒否するが、refspec（`+refs/...:refs/...`）は通す（`:493-501`）
- 今の復旧の案内は `checkout -B <ブランチ> <リモート>/<ブランチ>` を勧めている（使い方 `:99`、reset の拒否文 `:607`）
- `issue:` は親だけの欄で、正の整数か `#12`（`ticket.py:186-197,596-607`）。MR の本文に `Closes #N` を写す（`review.py:284-285`）
- 識別子の形は `_ID = ^[A-Za-z0-9][A-Za-z0-9._-]*$`（`ticket.py:113`）。子は `_CHILD = ^<親>-<2 桁>$`（`ticket.py:114`）
- 既存の親は `i0055`・`i0060`・`i0061`・`i0062` で、どれも `issue:` を持たない

#### 比べた案

| 案 | ブランチ名 | メリット | デメリット |
|---|---|---|---|
| **N1（採用）** | 親の識別子そのもの。識別子を issue 番号から決める（`i<番号 4 桁 0 埋め>`、例 `i0131`） | 既存の結び付きがそのまま合う。名前を求める関数が恒等写像なので、Python・sh・TS で食い違いようがない | ブランチ一覧に題が出ない。ホストの「issue からブランチを作る」既定名とは違う |
| N2 | `<番号>-<slug>`（ホストの既定） | ホストの既定どおり。一覧で読める | 題が変わると引けない。日本語の題は slug がほぼ空。`-12` で終わると子の識別子と紛れる |
| N3 | 識別子とは別に `branch:` 欄を持つ | 名前を自由にできる | 欄を書き換えれば権威の置き場が動く |

#### 規則（N1）

1. **親のブランチ名 = 親の識別子**。子のブランチ名も子の識別子（今と同じ）
2. **ref として安全な形に限る**。新規の提案に次を足す: `..` を含まない、`.lock` で終わらない、`.` で終わらない。既存の識別子は当たらないことを確かめてから入れる
3. **大文字小文字だけが違う識別子を許さない**。一意性の検査は大文字小文字を畳んで行う
4. **王道（issue あり）**: 親の識別子は `i` + issue 番号の 4 桁 0 埋め（5 桁以上はそのまま）。frontmatter の `issue:` に番号を書く
5. **予約**: 新規の提案で `^i\d+$` の形は `issue:` があるときだけ許す。`main`・`master`・`develop`・`release`・`release/*`・`release-*`（大文字小文字を畳む）と、
   その時点の統合先の名前は識別子に使わない（`P` が保護されたブランチや統合先と同じ名前になるのを防ぐ。`ccnavi-push-approved.sh:174-175` の一覧と揃える）。
   既存の `i0055`〜`i0062` は issue #55〜#62 と名前が衝突する（GitHub の番号は issue と PR で共有、既に #130 まで使用）。
   衝突は「始める」（8.6）と承認の同じ識別子の検査の両方で止める: 統合先の `done/` か開いた家族に同じ識別子があれば、その issue からは始められない
6. **フォールバック（issue なし）**: 識別子は人が付け、ブランチ名はその識別子。`^i\d+$` と `-\d{2}$` の形は使わない（`-\d{2}$` は `_CHILD` と紛れるため）
7. **プロジェクト（`projects/<名前>`）**: プロジェクトの issue からは `<プロジェクト名>-i<番号>`（例 `web-i0012`）。プロジェクト名の決め方は未決（10.3 の 1）
8. **リポジトリをまたぐ issue**: `issue:` に `owner/repo#N` を許す。識別子はフォールバックと同じく人が付け、MR の本文は `Closes owner/repo#N`
9. **一致の検査は新規の提案のときだけ**。承認後は識別子が正で、`issue:` の書き換えは既に改版で許していない（`approval.py:2279`）
10. **ハードに拒否する場所（`ccnavi-git.sh`）**: 段階 0 の lint の warn（2・3・5・6）とは別に、次を `ccnavi-git.sh` で拒否する。
    - 段階 0: `branch` の漏れを直す。短いオプションの検査に `*M*` を足し（`-C` の強制コピーも同じ並びで見る）、`-M`・`-rM`・`--move` の回帰試験を足す。
      `fetch`・`pull` の引数で `:` か `+` を含むもの（refspec）を拒否する。文面は「取ってくるのはブランチ名だけ。手元の ref は `ccnavi-sync.sh` が進める」
    - 段階 2b（`ccnavi-sync.sh` と同時。D36）: `worktree add` で「行き先のディレクトリ名 = 新しいブランチ名（`-b`）」を求める。
      `--detach`・`-f`/`--force`・`-B`（今は `ccnavi-git.sh:247` で通している）、`checkout -B`/`switch -C`、親のワークツリーで別のブランチへ移る形を拒否する。
      同時に `:99` の使い方と `:607` の reset の拒否文を「リモートに合わせるなら `ccnavi-sync.sh <P>`。分かれていて進めないなら人に回す」に書き換える
    - 親のブランチに当たったときの文面は「親のブランチの名前は識別子で、変えると家族が止まる（3.6）」
11. **同じ関数**: 「チケット → 親のブランチ名」は `t.parent or t.ticket`。「issue → 識別子」は `f(番号, プロジェクト名)` の 1 つだけを `ticket.py` に置き、Pyodide でも使う
12. **置き場の綴りが絶対パス**（`CCNAVI_TICKETS_APPROVED` などをリポジトリの外に向けた設定）のワークスペースは、C1 と Chrome の対象外にする。
    ブランチに乗らないので権威を `P` に置けない。lint がその旨を info で出す

### 3.3 権威の決め方

「`P` がある」「統合先」の定義を場所ごとに分けます。

- **統合先の名前**（D30。案 C）: リポジトリには置かず、使う側がそれぞれ持つ
  - Chrome 拡張: 設定画面でリポジトリごとに入れる（`chrome.storage.local`）。空なら `GET /repos/{o}/{r}` / `GET /projects/:id` のデフォルトブランチ
  - 手元: 環境変数 `CCNAVI_INTEGRATION_BRANCH`（`.claude/settings.local.json` の `env` か、シェルの環境）。空ならホストのデフォルトブランチ（`origin/HEAD`、無ければ `ccnavi-fetch.sh` の `ccnavi_fetch_default` と同じ探し方）。
    プロジェクトのリポジトリも同じ値を使う（プロジェクトごとに変える要が出たら後で足す）
  - **デメリット**: 人ごと・機械ごとに値がずれうる。承認者の Chrome と開発者の手元が別の統合先を読むと、閉じた家族の見え方と層が食い違い、手元の C3 が家族を止めることがある
  - **軽い緩和**: 設定したブランチがリモートに無ければ（`ls-remote` の一覧に無い / API が 404）、既定に落とさずに止めて「統合先 `<名前>` がリモートに無い。設定を直す」と知らせる。
    `ccnavi-sync.sh` は使った統合先の名前と、それが設定か既定かを統合先の控えの `head`（`branch`・`source`）に書いて出力にも出す。Chrome はボードの見出しに使った統合先の名前を常に出す。
    値を揃える仕組み（リポジトリの設定との突き合わせなど）は持たない
- **リモート（Chrome 拡張）**: ホストにブランチ `P` がある。権威は `origin/P` の中身。統合先は上の名前のブランチの先頭
- **手元（hook・lint・ボード・コマンド）**: `.claude/worktrees/P` があり、その HEAD がブランチ `P` を指している。中身は「最後に取り込んだ `origin/P` + 手元の作業」
- **手元の統合先**（D26）: 最後に取り込んだ `origin/<統合先>` を正とする。`ccnavi-sync.sh` と C1 が取り込むたびに、
  その先頭から判定に要るもの（`.ccnavi/approved/done/` の一覧と中身、`.ccnavi/common/` の層、自身の `.ccnavi/config/` の層、置き場の綴りの設定）を
  統合先の控え `sync/<リポジトリ>/integration/`（と、その中の `head` に `remote`・`branch`・`sha`・`fetched_at`。D33 の形）へ書き出す。
  ワークスペースとプロジェクトのリポジトリで控えを分ける。判定は git を起こさず、この控えを読む
  - origin が無い・一度も取り込んでいないリポジトリでは、今どおり作業ツリーを読む

権威の規則:

1. **`P` がある**: `P` の `.ccnavi/approved/` と `wip/proposals/review/` が、その家族の権威
2. **`P` が無く、統合先の `done/` に親の写しがある**（取り消し済みを含む）: 家族は閉じている。統合先が権威（3.6 の正常系）
3. **`P` が無く、統合先の `done/` にも親が無い**: **決まらない → その家族の承認も状態の操作も止める**（3.6）。
   「統合先で未承認なら新規扱い」にすると、改版の制約（`approval.py:2270-2285`）を新規の承認として迂回できるため
4. **開いた家族でも、統合先の `done/` は常に一緒に読む**。古い統合先から切った `P` で識別子の再利用が新規として通らないため
5. **参照先の家族は閉包で集める**（D2）: 先行（`predecessor_pool`、`approval.py:688-694`）は `_loop_back`（`:725-745`）で多段を辿るので、
   1 段の `P_X` だけでは Chrome と手元で答えが変わる。
   - 家族の引き方: 識別子 `X` が `_CHILD`（`ticket.py:114`）に当たれば、その `parent` の組が家族の親。当たらなければ `X` 自身が親。
     親の識別子に `-\d{2}$` を使わせない（3.1 の 6）ので、この引き方は一意に決まる。既存の親に当たる形が無いことは段階 0 の lint で確かめる
   - 提案が参照する識別子の家族の `P_X` を読み、その中の写しが参照する識別子の家族をさらに読む、を新しい家族が出なくなるまで繰り返す。
     統合先の `done/` にある（閉じた）家族はそこで止める（`_loop_back` も閉じたものの先を辿らない）
   - **上限は 16 家族**。根拠: 1 家族あたり tree 1 回と blob の束 1 回なので、承認 1 回の読み取りが GraphQL と REST を合わせて 40 回ほどに収まる。
     今の開いた家族は 4 つで、上限に届く形は想定していない。超えたら「決まらない」で止め、次を出す:
     「先行を辿ると 16 を超える家族に広がった（<家族の一覧>）。Chrome では判定できない。計画を分けて先行を減らすか、手元で `--approve --preview --verify` を打って確かめる」
   - `P_X` が無ければ 2・3 と同じ規則（`done/` にあれば閉じた家族、無ければ決まらない）
   - **手元でも揃える**: 取り込み済みの家族の判定では、池を「その家族の `P` のツリー + 閉包の家族の親のワークツリー + 統合先の控えの `done/`」に限る。
     閉包の家族の親のワークツリーが手元に無ければ「決まらない」で止め、切り直しを案内する。こうすると、他のワークツリーの古い写しで `PRED_SCATTERED`（`approval.py:626,719`）が
     出る・出ないが Chrome と食い違わない。取り込み済みでない家族は今の全ツリー走査のまま（Chrome はその家族を見ない）
6. **層と設定は `P` から読まない**。`P` の上で書き換えれば承認やレビューを不要にできてしまうため
   - 共通層（`.ccnavi/common/`）とワークスペース自身の層と置き場の綴りの設定: ワークスペースの統合先から読む（手元は `sync/self/integration/`）
   - プロジェクトの層（D28）: ADR-0084 の configsync（`configsync.py:1-20`）は着手のときに共通層を**親のワークツリー（`P` の上）のプロジェクトの層**へ写す。
     判定はこれを読まず、「**プロジェクトの統合先の現在の層**（手元は `sync/<プロジェクト>/integration/`）に、共通層を `configsync.projected` で写したもの」を計算して使う。
     - 正直に書くと、これは着手のときの写しではなく**統合先の現在値**です。着手の後に統合先の共通層やプロジェクトの層が変わると、
       開いている家族の判定の基準もそれに合わせて動きます（着手で写した結果とは違いうる）。`P` の上の層の書き換えが判定に効かないことを優先しました
     - `P` の上のプロジェクトの層がこの計算と違えば、取り込み（4.2）と `--lint` が warn を出す
     - configsync 自体（プロジェクトだけを clone した人に層を配る役）は残す。写した層は `start` の C1 で運ぶ（D34・4.3）
     - **ADR-0084 を改訂対象に入れる**（9 章）
   - 手元では、`settings.local.json` に承認に効く値（置き場の綴りなど）を置かせない lint を入れる。**例外は `CCNAVI_INTEGRATION_BRANCH` だけ**（D30 で置き場として決めたため）
7. **プロジェクト**: プロジェクトのチケットはそのプロジェクトのリポジトリの `P` と、そのリポジトリの統合先で同じ規則。
   Chrome 拡張にプロジェクトのリポジトリが登録されていなければ、プロジェクトが絡む提案は承認しない

手元での読み替え:

- 手元に親のワークツリーが無く、ブランチ `P` だけがある: 読みも書きも止め、「親のワークツリーを切り直す」と案内する。
  判定の中で `git cat-file` を読む形は、判定が外部プロセスを起こさない前提（`tree.py:95-96`）に反するので採らない（`git cat-file` を使うのは sh の中だけ。3.6）
- 元ツリー（ワークスペースルート）に未コミットで書く形（ADR-0073）は、取り込み済みの家族ではやめる

### 3.6 `P` の削除・改名

#### 場合分け

| 場合 | 見え方 | 扱い |
|---|---|---|
| 正常系: MR がマージされ、ホストが `P` を消した | `P` が無い。統合先の `done/` に親の写しがある | 家族は閉じている（3.3 の 2）。**戻す案内は出さない**。Chrome はこの家族に操作を出さない |
| マージ後もホストが `P` を残した | `P` も統合先の `done/` もある | `P` が権威。中身は同じなので答えは変わらない |
| マージせずに消した・改名した・掃除で消えた | `P` が無い。`done/` にも親が無い | **決まらない**（3.3 の 3）。家族の書き込みを止め、理由と戻し方を出す |

改名はホストでは止められないので追わず、3 行目に落とします。手元の `branch -M` は段階 0 で塞ぎます（3.1 の 10）。
リモートの消去（`push origin :P`・`push --delete`）は push の形の制限（`ccnavi-git.sh:584-603`）で通りません。

#### 正常系を必ず正常系にする（1）: `ready` の前提に「親が閉じている」を足す

今の `ready` は `ops.close_problems` だけを見るので、親を閉じる前に Draft を外せます（`review.py:1083-1098`）。
その形でマージされると `done/` に親が無いまま `P` が消えて 3 行目に落ちます。`ready` の前提に「親の写しが `done/` にある」を足します（締まる向き）。

#### 正常系を必ず正常系にする（2）: 消えたと言う前に `done/` を確かめる（`ccnavi-sync.sh` と C1 だけ）

確かめは `ccnavi-sync.sh` と C1 の中の取り込み（同じ関数、`ccnavi-common.sh`）だけで行います。SessionStart はしません（D12）。

1. origin ごとに 1 回 `ls-remote --heads origin` を打ち、全ブランチの有無を得る（ブランチごとに打たない）。
   出力は `grep -F -x` で「`<sha><タブ>refs/heads/<P>`」の形の行と完全一致で比べる（前方一致で `i0131` と `i0131-x` を取り違えない）。
   `ls-remote` 自体が落ちたら「取ってこられなかった」（オフライン・認証）で、止める
2. `P` が一覧に無ければ「消えた候補」とし、`P` の fetch は打たない
3. 消えた候補がある origin でも、`origin/<統合先>` は必ず fetch する
4. sh の中で `git cat-file -e origin/<統合先>:<done の置き場>/<親>.md` を見る（置き場の綴りは Python が出す。判定の外なので `git` を起こしてよい）。
   あれば「閉じた」として控えに書き、戻す案内は出さない
5. 無ければ観測ずれを疑う（ホストはマージの後に `P` を消すが、読み取りの複製の遅れで `done/` が見えないことがある）。
   **3 回まで 5 秒おきに** 3〜4 を繰り返す。それでも無く、`ccnavi-review.sh` の道具（`gh`/`glab`/curl とトークン）が使えれば
   MR の状態を引き、マージ済みなら「マージ済みだが統合先への反映がまだ見えない。少し待って `ccnavi-sync.sh`」と言って止める（戻す案内は出さない）
6. どれにも当たらなければ「消えた」として控えに印を書き、家族を止め、次を出す（モデルと利用者の両方に届く出力）:
   - 理由: 「親のブランチ `P` がリモートに無い。統合先にも閉じた記録が無いので、この家族の状態を決められない」
   - 戻し方 1（改名・消し間違い）: 元の名前 `P` でブランチを作り直す。案内文だけを出し、ccnavi は作らない:
     端末なら `git push origin <控えの sha>:refs/heads/P`、GitHub なら PR の画面の「Restore branch」、
     GitLab なら MR の `refs/merge-requests/<N>/head` から `P` を作る
   - 戻し方 2（家族を捨てた）: 親のワークツリーを片付ける（`ccnavi-git.sh worktree remove`）

`ccnavi-fetch.sh`（SessionStart）の側は 1 点だけ直します: fetch が「リモートにその ref が無い」（`couldn't find remote ref`）で落ちたときは、
その origin を `failed`（`ccnavi-fetch.sh:94-95`）に入れない。今は入れるので、同じ origin の統合先の fetch まで飛ばされる（`:76-78`）。
SessionStart は「`P` を取ってこられなかった。`ccnavi-sync.sh <P>` で確かめる」とだけ言い、消えたとは判断しません。

#### 家族の控えと push の拒否

- 家族の控え `sync/<リポジトリ>/families/<P>` は 1 行 1 項目のテキスト（D33）: `remote`・`branch`・`sha`・`fetched_at`（`date +%s`）・`state`（`present` / `closed` / `gone` / `blocked`）・`reason`
- **「一度も push していない `P`」と「消えた `P`」は控えの有無で分ける**。控えが無ければ手元だけの家族なので、リモートに無くても止めず、今の手元の動きのまま（C1 の対象外）
- 控えを作る・書き直すのは `ccnavi-sync.sh`、C1 の取り込み、`ccnavi-git.sh push`（通ったとき。4.3 の移り目）の 3 か所
- `ccnavi-git.sh push` は、控えの `state` が `gone` の `P` への push だけを拒否する。毎回の `ls-remote` はしない（控えを `sed -n 's/^state //p'` で読むだけ）。
  人が戻した後は、次の `ccnavi-sync.sh` が `present` に書き直して拒否が解ける
- Chrome 拡張は先頭を控えず、ブランチを戻す機能も持たない。消えた家族には上の戻し方の案内文だけを出す

- メリット: マージ後の正常系で何も起きず、閉じた家族を誤って戻させない。SessionStart が待たない。push の守りが毎回ネットワークを使わない
- デメリット: 改名でも家族が止まり、人が戻す手間がある。観測ずれの確認で最長 15 秒ほど待つことがある

## 4. 取り込みと二重状態

### 4.1 二重状態の問題

| 書き手 | 書くもの | 書く場所 |
|---|---|---|
| 承認者（Chrome 拡張） | 承認の写し、改版、提案の削除、マーカーの消去（`clear_marks`）、フローの運び、承認の取り下げ（8.8）、レビュー済みの印と子の `done/` への移動（8.9） | リモートの `P` |
| 開発者の手元（ccnavi のコマンド） | 着手・終了・取り消し・続きの子・マーカー・レビュー済みの印・リスクの記録・フローの指紋・configsync の写し | 親のワークツリー |
| 開発者の手元（hook） | フェーズの終わりの告知が置く `N.pending`/`N.skipped` と跡（4.4） | 親のワークツリー |
| 人（端末・ボード） | 人の判断（4.4 の (c)） | 親のワークツリー |

起きること（C1 を入れる前）:

- **手元 → リモートの遅れ**: 手元の状態が push されていないと、Chrome は古い状態で判定する（子のあるフェーズの計画を変える改版が通る、着手済みを取り下げられる）
- **リモート → 手元の遅れ**: Chrome の改版が `clear_marks` で reviewed マーカーを消しても、手元に届くまで古い reviewed が効く
- **衝突**: 両方が `approved/` を書いて merge が衝突したとき、エージェントが解くと権威をエージェントが決めることになる

### 4.2 取り込み（他の人の承認を手元へ）

取り込みは 2 つの強さに分けます（D12）。

| | SessionStart（`ccnavi-fetch.sh`） | `ccnavi-sync.sh [<P>...]`（手で打つ）と C1 の中 |
|---|---|---|
| いつ | セッションの頭 | 利用者が承認を知らせたとき（ボードのボタン、「承認した」と言われたエージェント）、C1 の最初 |
| ロック | 取れなければその家族を飛ばす（待たない） | 待つ（4.3 の 1） |
| fetch | 今どおり（15 秒の見張り） | 今どおり |
| 進め方 | **早送りだけ** | 早送り、分かれていれば merge |
| 消えたかの確かめ | しない（3.6） | する（3.6 の 1〜6） |
| 控え | 書かない | 家族の控えと統合先の控えを書く |
| lint と判定し直し | しない | する（下の 5） |

#### SessionStart の早送り

- 対象は次を全部満たすツリーだけ（他セッションのワークツリーを動かさないため）:
  - `.claude/worktrees/` の直下で、ディレクトリ名 = ブランチ名
  - その中に `ticket: <その名前>` の**親の写しか提案**がある（子の写しが無いだけでは足りない）
  - 家族の控えがある
- ロック（4.3）を 1 回だけ試し、取れなければ「`<P>` は他の操作の最中なので進めなかった」と言って飛ばす
- 手元の `P` が `origin/P` の祖先なら `merge --ff-only` する。書きかけとの重なりは git に任せ、拒まれたら
  「書きかけの `<パス>` と重なるので進めない。コミットか退避をしてから `ccnavi-sync.sh`」と言う
- **時間の枠**: hook の上限は 60 秒（`.claude/settings.json` の SessionStart）。早送りは fetch が済んだ後に行い、
  sh の開始から 45 秒（`date +%s` の差）を過ぎたら残りの早送りは飛ばして名指しする。早送りは merge と違い途中の状態（`MERGE_HEAD`）を残さない
- 対象に当たらないツリーは今の検査（未コミットがあれば進めない。`ccnavi-fetch.sh:209-213`）のまま

#### `ccnavi-sync.sh` と C1 の取り込み（sh が行う。Python は置き場の綴りと、判定・検査の結果を出すだけ）

1. `ls-remote` と消えたかの確かめ（3.6 の 1〜6）。あれば `fetch origin P` と統合先。統合先の名前は環境変数 `CCNAVI_INTEGRATION_BRANCH`、空ならホストのデフォルトブランチ（D30）。
   設定した名前が `ls-remote` の一覧に無ければ止めて知らせる。使った名前は控えと出力に出す
2. 早送りできれば早送り
3. 分かれていれば `merge origin/P`（rebase はしない）。前提は索引が HEAD と同じこと（`git diff --cached --quiet`）。
   非 ff の merge は、重ならないステージ済みの変更があっても「would be overwritten」で拒む（git 2.43 で確かめた）ので、先に見て
   「ステージ済みの変更がある。コミットするか `ccnavi-git.sh restore --staged` で外してから」と言う。
   `.ccnavi/approved/` か `wip/proposals/review/` で衝突したら **`merge --abort` して止め、人に回す**。
   ただし `phases/<P>/seq`（GitLab だけ。8.4）だけの衝突は、`seq` が権威でなく印なので origin 側を採って解く。それ以外の衝突も `merge --abort` して止める
4. Python の `--lint` の該当分（権威の検査、3.3 の 6 の層の食い違い）と、C3 の判定し直しを回し、error があれば家族を止める（控えの `state` を `blocked`、`reason` に理由）
5. 控えを書く（家族の控え、統合先の控え）

hook の判定中はネットワークも外部プロセスも使わない（`tree.py:95-96`）ので、hook は最後に取り込んだ中身で判定します。

- メリット: SessionStart が短く終わり、途中で切られても merge の書きかけを残さない。承認は次の状態の操作（C1）の前に必ず手元へ届く。衝突の決着を人に残す
- デメリット: セッションの頭で分かれていた家族は、次の C1 か `ccnavi-sync.sh` まで古いまま hook が判定する

### 4.3 手元 → リモートの遅れの解消（C1 を絞って入れる）

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| **C1（採用、絞る）** | 取り込み済みの家族に限り、状態を書く操作を 1 操作にし、push が通るまで完了にしない | Chrome が見る家族では未 push の状態が溜まらない | 対象の家族では状態の操作にネットワークが要る |
| C1（全家族） | すべての家族で同じ | 規則が 1 つ | origin の無い・まだ push していない家族まで止まる |
| C2 | 未送信の印を `P` に置き、Chrome はその家族を止める | オフラインでも操作できる | 印を置くのに push が要る |
| C3 | 取り込み時に判定し直すだけ | 変更が小さい | 緩い承認が一度は `P` に乗る |

#### 対象

- **対象**: origin があり、家族の控えの `state` が `present` の家族
- **対象外（今の手元の動きのまま）**: origin が無い、一度も push していない `P`（控えが無い）、chat だけの家族（MR を持たずリモートで承認されない家族）、置き場の綴りが絶対パス（3.1 の 12）。
  Chrome はリモートにある `P` しか見ないので、対象外の家族に二重状態は起きない
- 控えの `state` が `gone` か `blocked` なら C1 の操作は止める。`closed` なら家族は閉じていて状態の操作は無い

#### 移り目（最初の push で対象に入る）

控えを取り込みでしか作らないと、最初の push から次の取り込みまで、家族が C1 の外なのに Chrome から見えます。これを塞ぎます。

- `ccnavi-git.sh push` は、push が通ったとき、送った先が親のブランチ（ディレクトリ名 = ブランチ名で、親の写しか提案がある）なら、家族の控えを `present` で作る
- ただし、その時点で置き場に未コミットの変更（今の手元の動きで書いた状態）があれば控えを作らず、
  「置き場に未コミットの状態がある（<パス>）。コミットして push し直すと、この家族は C1 の対象になる」と言う。
  こうすると、対象に入った瞬間の置き場は必ず `origin/P` と同じになり、未送信の状態を持ち越さない
- 控えを作れない間は家族は対象外のままで、Chrome からは見えるが手元の状態は今の動き（エージェントが commit と push で運ぶ）になる。
  この間の遅れは C3（取り込みでの判定し直し）で拾う

#### 1 操作の中身（sh が持つ。D17）

`ccnavi-ticket.sh`（start・finish・cancel）、`ccnavi-review.sh`（request のマーカー・confirm・decide・ready）、
続きの子を起こす操作（`approval.followup` を呼ぶ経路）は、対象の家族なら次の順に進めます。

1. **ロック**（D32、下）を取る
2. **途中の操作を確かめる**: `git rev-parse --git-path <名前>` で引いた `MERGE_HEAD`・`CHERRY_PICK_HEAD`・`REVERT_HEAD`・`rebase-merge/`・`rebase-apply/`・`sequencer/`・`index.lock`
   のどれかがあれば始めない（ワークツリーでは git ディレクトリが別の所にあるので、綴りを決め打ちしない）
3. **C1 の外の変更を見分けてコミットする**（4.4）: Python が置き場の未コミットの変更を (b)・(c)・(d) に分ける。
   (c) か (d) があれば何も書かずに止める。(b) があれば `commit --only -- <(b) のパス>` で先にコミットする（新しいファイルは先に `add -- <パス>`）。
   こうしておくと、次の取り込みの merge が hook の書きかけ（`events/<親>.ndjson` の追記など）とぶつからない
4. **取り込み**（4.2）。merge が「local changes would be overwritten」で落ちたら（3 と 4 の間に他のセッションの hook が書いた）、3 からもう 1 回だけやり直す。2 回目も落ちたら失敗にする
5. **未送信の置き場の変更を確かめる**: `git diff --name-only origin/P HEAD -- <置き場>` の各パスを 4.4 の見分けにかけ、(b) 以外（人の判断の未送信、見分けられない変更）があれば止める。
   REQ-APV-11 の補足（下）の前提を守るため
6. 元の先頭 `H0` を控える（`rev-parse HEAD`）
7. **書く**: Python のコマンドを `--record-writes <ファイル>` つきで起こす。Python は fsio の記録層（下）で、この実行で書いたパスの一覧を出す
8. **コミット**: 一覧のパスだけを `commit --only -- <パス>`（新しいファイルは先に `add -- <パス>`）。ほかのステージ済みの変更は索引に残ったまま入らない（D35。git 2.43 で確かめた）。
   GitLab のリポジトリなら `phases/<P>/seq` の更新を同じコミットに含める（8.4。段階 5 の 2 段目から）。コミットメッセージは人が読む説明だけ（D37）
9. **push**: `git push origin P`（`--force` なし）。通れば控えの `sha` を書き換えてロックを外す
10. **push が落ちたら、まず届いたかを確かめる**: `git ls-remote origin refs/heads/P` の行が「`<C の sha><タブ>refs/heads/P`」と `grep -F -x` で一致すれば、届いていた（応答だけが落ちた）として成功にする
11. 届いていなければ**戻す**（下）。自動の再試行は 1 回だけ（3 からやり直す）。2 回目も落ちたら失敗にして「`ccnavi-sync.sh` で取り込んでから打ち直す」と言う

オフラインでは 4 か 9 で落ちるので、対象の家族の操作は失敗になり、「接続を戻してから打つ」と案内します。

#### ロック（D32）

- 置き場: 控えの `locks/<リポジトリ>/<P>/`（ディレクトリ）。`mkdir` の原子性は Git Bash・Linux・macOS で同じ。`flock` は macOS に無いので使わない
- 取れたら中の `owner` に 1 行で `<ホスト名> <pid> <開始時刻（date +%s）> <印>` を書く。`<印>` は `<pid>-<開始時刻>`
- **古いロックの判断**:
  - 同じホスト名で、`kill -0 <pid>` が失敗すれば、すぐ古い
  - ホスト名が違う（WSL と Windows で同じ置き場を見る場合など）か、`owner` が読めなければ、時刻だけで判断する（`owner` が無ければ `find <ロック> -maxdepth 0 -mmin +10` で見る）
  - 年齢の上限は **10 分**。pid が生きていても、10 分を過ぎれば古い（pid の再利用に備える。C1 は通常 1 分以内に終わる）
  - Git Bash の `$$` は MSYS の番号で、`kill -0` はロックを取る側も見る側も sh なので通る見込み（確信中。段階 2d の試験で確かめ、駄目なら Git Bash では時刻だけにする）
- **奪い方**: 古いと判断したら、見た `owner` の中身を控えてから `mv <ロック> <ロック>.stale.<自分の pid>` で退避し、退避した中の `owner` が控えたものと同じか確かめる。
  同じなら退避を消して `mkdir` から取り直す。違えば（その間に別の持ち主に替わった）退避を元の名前に `mv` で戻して待ちに戻る。戻せなければ失敗にして人に回す
- **待ち**: 既定 120 秒、1 秒おきに試す（`CCNAVI_LOCK_WAIT` で変えられる）。並列の子 3 つがそれぞれ fetch と push を往復すると 30 秒を超えるため、30 秒より長くした。
  SessionStart だけは待たない（4.2）
- **入れ子**: 取った sh は `CCNAVI_LOCK_HELD="<リポジトリ>/<P>:<印>"` を子に渡す。C1 の中から呼ばれた sh（運ぶ処理など）は、自分の家族とこの値が一致すればロックを取ったものとして進み、外さない
- 外すのは取った sh だけ（`trap` で EXIT のときにも外す）

#### 戻しの定義

`reset` は使いません。

- **先頭が自分のコミット `C` のときだけ**戻す。`git update-ref refs/heads/P H0 C`（比較つき。先頭が `C` でなければ git が拒むので、
  その間に別の操作が積んだコミットを消さない）。先頭が `C` でなければ戻さず、失敗にして人に回す
- 戻した後、`C` に入れたパスの索引を `git restore --staged --source=H0 -- <パス>` で `H0` に合わせる
- **この実行で書いたパス**だけ、作業ツリーの中身も書く前に戻す: `H0` にあれば `git restore --worktree --source=H0 -- <パス>`、無ければ消す
- 3 で先にコミットした (b) と、4 の取り込みの merge は戻さない（手元に残り、次の C1 の push で送られる。5 の確かめは (b) を許すので止まらない）
- C1 の中の sh は `ccnavi-git.sh` を通らずに git を呼ぶ（`ccnavi-git.sh` はエージェントの入口の守り）。5.2 で `restore --source` を拒否するのは
  エージェントの入口だけで、ここの戻しには当たらない
- 限界: hook が同じ跡のファイル（`events/<識別子>.ndjson`）に 7〜11 の間に追記すると、戻しでその行が消えることがある。跡は補助で権威ではない（`history.py:3-7`）ので受け入れる

#### fsio の「この実行で書いたパス」の記録層

「書いたパス」の一覧をコアの `Changes`（6.2）だけから取ると漏れます。コアの外で書いている箇所があるためです:
`ops.start`・`finish`・`cancel`、`approval.followup`（`approval.py:540-615`）、`configsync.apply`（`configsync.py:159`）、
フローの指紋 `flow.record_digest`（`flow.py:964-`）、リスクの記録 `phases/<親>/<子>.risk.json`（`approval.py:914`）。

- `fsio` の書き込みの関数（`write_text`・`write_text_atomic`・`write_bytes`・`write_json_atomic`・`remove`、`fsio.py:143-293`）に、
  記録が有効なあいだだけ「書いた・消したパス」を控える層を入れる。有効にするのは CLI の入口で、sh から `--record-writes <ファイル>` を渡されたときだけ
- 記録のファイルは**控えの側**（`conf.state` の下の `c1/<リポジトリ>/<P>.<印>.writes`）に置く。ワークツリーに置くと自分が未コミットの変更になる
- 出すのはワークツリーからの相対パスの一覧。**置き場の外が入っていたら error**（C1 は状態だけを運ぶ）。例外は 1 つだけ（D34）:
  `start` の中の `configsync.apply` が写したプロジェクトの層（共通層にあるファイル名に限る）と、指す先を直した配点のスクリプト。
  写す役は ADR-0084 どおり残るので、`P` に乗せてプロジェクトだけを clone した人へ届ける
- fsio を通らない書き込みは記録層を通す形に揃える。今ある所:
  - `approval.py` の `os.remove`（`:382,492,859,1843`）・`os.rename`（`:461`）・`shutil.copy2`（`:486`）・`os.remove`（`:497`）。`clear_marks`（`:853-870`）を含む
  - `history.note` の追記（`history.py:197` の `os.open`）
  - `configsync._replace`（`configsync.py:541-553`。一時ファイル `.ccnavi-sync` に `open` で書いて `os.replace`）
  - 揃ったことは「記録を有効にして各コマンドを回し、`git status` の変化と一覧が一致する」試験で確かめる

#### そのほか

- **`record-risk`** は C1 にしない。書いた `<子>.judge.json` はその子の `finish` の C1 が運ぶ（`finish` はこの判定を入力として読むので、記録層が読んだ入力として一覧に足す）。
  record-risk を別の C1 にする形は採らない
- **push する先は `P` だけ**。子のブランチは送らない（`ccnavi-git.sh:562` と同じ）
- **REQ-APV-11** が止めているのは「承認済みチケットを運ぶ sh をエージェントが起こすこと」です。補足の文を事実に合わせて直します（9 章）:
  > C1 の push は `P` の未送信のコミットをすべて送る（git push の性質）。コードのコミットはエージェントが `ccnavi-git.sh push` で送れる範囲と同じ。
  > 置き場について送るのは、状態の操作がこの実行で書いたパスと、ccnavi が書いたと内容で分かるパス（4.4 の (b)）だけで、
  > それ以外の置き場の変更が未送信なら C1 は送らずに止める（4.3 の 5）
- **CI**: ccnavi のコミット（Chrome と C1）が `P` に積まれるたびに、ホストの CI が走る。既定では `[skip ci]` を付けない。
  付ける設定を置く場合も、**`ready` のマーカーのコミットには付けない**（マージ時の先頭が skip だと必須チェックが走らない）
- C3 の「取り込み時の判定し直し」は安全網として入れる（人が手で push した状態にも効く）

### 4.4 C1 の外の書き手をどう運ぶか

C1 の 3（と 5）で、置き場（`.ccnavi/approved/`・`wip/proposals/review/`）の未コミットの変更を次のどれかに分けます。
見分けは Python が行い（ローカルの git と中身だけを見る）、sh は結果に従います。

- **(a) この実行が書いた**: fsio の記録層の一覧。8 でコミットする
- **(b) ccnavi が書いたと内容で分かる**: `configsync.is_synced_write`（`configsync.py:202-`）と同じ考え方で、パスの形と中身の形と
  変更前のコミット済みの中身が揃ったときだけ当てる。台帳は持たない。当たったものは 3 で**取り込みの前にコミット**する
- **(c) 人が運ぶもの**: C1 は運ばない
- **(d) 見分けられない**: 何も書かずに止め、「置き場に ccnavi の知らない変更がある（<パス>）。人に確かめる」と言う
- **数えないもの**: 書きかけの一時ファイル（fsio の `*.<一意>.part.*`、`fsio.py:189`、フローの保存の一時ファイル `flows/.*.tmp`、configsync の `*.ccnavi-sync`）。
  どれにも数えず、コミットもしない

**(c) の規則は 1 つです**: 置き場に (c) の未コミットの変更があれば、C1 は止めて「人の判断が未送信（<パス>）。運ぶ処理（`ccnavi-push-approved.sh <P>`）を打つ」と言う。
人が打つコマンドは最後に運ぶ処理を自動で呼ぶ（D27・4.6）ので、止まるのは運ぶのに落ちたとき（オフライン・競合）と、人が実行ファイルを直に打ったときだけです。

| 書き手 | 書くもの | 分け | 運び方 |
|---|---|---|---|
| hook のフェーズの終わりの告知（PostToolUse → `events.py:502` → `phase.announce` `phase.py:834-925`） | `phases/<P>/<N>.pending`・`<N>.skipped`（`approval.write_mark` `approval.py:840-850`）と跡の追記 | (b) | 次の C1 の 3 でコミット。見分けの条件: パスが `phases/<P>/<N>.(pending\|skipped)`、中身が `{at}` と既知の欄だけの JSON、変更前は無い。跡は「変更前の中身が前置きで、足した行がどれも跡の行として読める」。遅くとも親の `finish`（C1）で運ばれる |
| フローの保存（ボード、`flows/<子>.yml`、`flow.py:1-15`） | 人の書いた手順 | (c) | ボードが保存の最後に運ぶ処理を呼ぶ（4.6） |
| `--reviewed --chat`（端末、`review.py:1043`） | reviewed 印（`by: "chat"`）、子の `done/` への移動、跡 | (c) | 最後に運ぶ処理を呼ぶ（D27） |
| `--config-synced`（端末、`cli.py:651-658`） | `config-sync.json` の見た印 | (c) | 同上 |
| `close-early`（端末、`review.py:1366,1379`） | `skipped` 印・reviewed 印（`by: "close-early"`）、子の `done/` への移動 | (c) | 同上。8.7 と揃えた |
| 端末の承認（`ccnavi-approve.sh`、段階 6 まで）・VS Code の承認 | 写し・提案の削除・マーカーの消去 | (c) | 今どおり最後に運ぶ処理を呼ぶ（改修した運ぶ処理に置き換わる） |
| `decide`（`ccnavi-review.sh decide`、端末・ボード） | reviewed 印（`accepted`）、続きの子、跡 | (a) | sh の中で C1 を回す（人が打っても sh が送る） |
| `record-risk`（`ccnavi-ticket.sh record-risk`） | `<子>.judge.json` | (a) | その子の `finish` の C1 で運ぶ（4.3 のそのほか） |
| `prepare`（`ccnavi review prepare`） | 依頼の本文と下書き | ― | 控えの置き場にしか書かないので運ばない |
| `configsync.apply`（着手の中） | プロジェクトの層と `config-sync.json` | (a) | `start` の C1 に入る（D34） |

**(b) が安全な根拠**: (b) は hook が書く `pending`・`skipped` の 2 種と跡の追記だけです。`reviewed` の印は入れません。
エージェントがシェルから偽の `skipped` を書いて (b) として運ばれても、レビューの止め（`phase.gate_closed`、`phase.py:590`）は
`review_required` を種類から独立に計算し直し、`reviewed` の印が無ければ止めたままにします。この前提（止めが `skipped` を見ない）が崩れる変更をしたら、(b) の範囲を見直します。
ただし `phase.plan_finished`（`phase.py:1086-1087`）は最後のフェーズで `requested`・`reviewed`・`skipped` のどれか（asked）があれば「計画を終えた」と数えるので、
偽の `skipped` が計画の終わりの判断に効く余地は残ります。受け入れる危険に数えます（5.1）。

- メリット: hook の書き込みを運ぶ仕組みを別に持たずに済む。人の判断はエージェントが送らない。取り込みが hook の書きかけで止まり続けない
- デメリット: 人の判断を運べなかったあいだ、エージェントの状態の操作が止まる。hook の印は次の C1 まで Chrome から見えない

### 4.5 実行ファイルとネットワークの境界（D17）と sh の書き方

`docs/claude/exe-boundary.md` の「実行ファイルはネットワークに出ない」を守ります。

| 仕事 | 置き場 |
|---|---|
| `ls-remote`・fetch・早送り・merge・`git cat-file` での `done/` の確かめ・控えの書き出し | `ccnavi-sync.sh`（新規）と C1。SessionStart の `ccnavi-fetch.sh` は fetch と早送りだけ |
| ロック・コミット・push・届いたかの確かめ・戻し | `ccnavi-ticket.sh`・`ccnavi-review.sh`・運ぶ処理（共通の関数は `ccnavi-common.sh`） |
| MR のマージ済みの確認、`confirm` の印に入れるアカウントの引き当て（GitHub `GET /user` の `login`、GitLab `GET /user` の `username`） | `ccnavi-review.sh`。結果は `--actor <名前>` と `--result` で Python に渡す |
| 置き場の綴り、書いたパスの一覧、C1 の外の変更の見分け、判定、lint | Python（ローカルの git とファイルだけ） |

sh の書き方（Windows Git Bash・WSL・Linux・macOS の bash 3.2 と BSD の道具）:

- 日時は `date +%s` と `find -mmin` だけにする（`stat -c`・`date -d` は BSD に無い）
- `ls-remote` の出力は `grep -F -x` で完全一致にする
- **jq を使わない**（D33）: `ccnavi-fetch.sh` は jq を使わない方針で、`ccnavi-git.sh` と `ccnavi-sync.sh` も同じにする。控えは 1 行 1 項目の `<鍵> <値>` にして `sed -n 's/^<鍵> //p'` で読む。
  JSON（`.claude/settings.json` など）は Python が読んで、sh には 1 行で返す。`ccnavi-review.sh` は今どおり jq を要る（ホストの応答を組むため）
- `$( )` の中に `case` を書かない（bash 3.2。`ccnavi-fetch.sh:114-115` の注意と同じ）。`mktemp -d` は `-t` の書き方も試す（`ccnavi-fetch.sh:63`）
- `kill -0`・`mv`・`mkdir` のほかにプロセスや原子性の道具を使わない

- Python のコマンド `ccnavi sync` は置かず、`ccnavi-sync.sh` に置き換える
- メリット: 実行ファイルの境界と hook の前提（外部プロセスとネットワークを使わない）を崩さない
- デメリット: sh が増え、3 つの OS で動く書き方と試験が要る

### 4.6 運ぶ処理（`ccnavi-push-approved.sh` の改修。D27）

今の `ccnavi-push-approved.sh` は、全ツリーを回って置き場を丸ごと `add` し、パスを限った `commit -- <パス>` をして push します（`:156-190`）。
取り込みをせず、ロックも取らず、push が落ちてもコミットを残します。これを次のように改めます。

- **引数で家族を取る**: `ccnavi-push-approved.sh [<P>...]`。省けば今どおり変更のある全ツリー。人のコマンドから自動で呼ぶときは、その家族の `P` を渡す
- **対象の家族なら C1 と同じ手順**: ロック（入れ子を許す）→ 途中の操作の確認 → 取り込み（4.2）→ 置き場の変更のコミット → push → 届いたかの確かめ。
  取り込んでから送るので、Chrome の承認と重なっても push が拒まれにくい。衝突したら `merge --abort` して止め、人に回す
- **コミットは `commit --only -- <パス>`**（D35）。今の `commit -- <パス>` も git の既定で `--only` と同じ働きだが、明示する。置き場を丸ごと `add` するのは変えない（人の判断のパスを 1 つずつ数えない）
- GitLab のリポジトリなら `seq` を同じコミットで更新する（8.4 の 2 段目から）
- push が落ちたら今どおりコミットは残す（人が打ち直せる）。C1 は 4.3 の 5 でこの未送信を見つけて止まり、運ぶ処理を打ち直すよう案内する
- 対象外の家族（控えが無い）では今の動きのまま

**自動で呼ぶ場所**（人が打つコマンドの最後）:

| 人の操作 | 呼び方 |
|---|---|
| 端末の承認 `ccnavi-approve.sh` | 今どおり最後に呼ぶ（`ccnavi-approve.sh:86-87`） |
| VS Code のボードの承認 | 今どおり端末に 1 行送る（`ccnavi.md:1302-1310`） |
| `--reviewed --chat`・`--config-synced`・`--close-early` | 人が打つ入口を sh にする: `ccnavi-review.sh chat <N>`・`ccnavi-review.sh config-synced <親>`・`ccnavi-review.sh close-early`。中で実行ファイルを起こし、通ったら運ぶ処理を呼ぶ。エージェントからは今の deny（`phase.py:105-113`）と同じく止める |
| ボードのフローの保存 | 保存の後、承認と同じく端末に 1 行送る |

実行ファイルを人が直に打った場合（`ccnavi --reviewed --chat` など）は運ばれません。次の C1 が (c) を見つけて止まり、運ぶ処理を案内します。

- メリット: 人の判断が溜まらず、C1 が止まる場面が運べなかったときだけになる。運ぶ処理も取り込みの後に送るので Chrome との競合で止まりにくい
- デメリット: 人の操作の最後にネットワークが要り、オフラインでは判断の後に打ち直しが要る。偽物が置き場に紛れていれば一緒に運ばれる（5.1）

## 5. 受け入れる危険

リモートで承認する形では、今の「承認済みの置き場にエージェントが書けない」（REQ-APV-07、`requirements.md:313`）が成り立ちません。
利用者の判断で、エージェントの自己承認の対策は頑張りすぎず、安く塞げる抜けだけ塞ぎ、残りは危険として受け入れます。

### 5.1 残る穴（エージェントによる自己承認）と REQ-APV-07 の改訂

エージェントは次の経路で、承認されたように見える写しを `P` に作れます。**どれも表示で気付く仕組みを持ちません**（D29）。

- **ホストの API への直接の書き込み**: `gh api`、`GITHUB_TOKEN` と curl、GitHub MCP、GitLab の API
- **`ccnavi-git.sh` を通る写しの巻き戻し**: `checkout <古い ref> <パス>`、`restore --source <ref>` で `approved/` を過去の中身に戻す（5.2 で塞ぐ）
- **ブランチの付け替え**: `checkout -B`・`worktree add -B` で `P` を別のコミットに向け直す（段階 2b で塞ぐ）
- **merge への混入**: `P` への通常の merge に、作った写しを混ぜる
- **(b) への偽装**: hook の印の形を真似た `pending`・`skipped`。止めは開かない（4.4）が、最後のフェーズの偽の `skipped` は `plan_finished`（`phase.py:1086-1087`）を真にしうる
- **(c) への紛れ込み**: エージェントが置き場に作ったファイルが、人が打った運ぶ処理の「置き場を丸ごと `add`」で一緒に送られる。台帳は作らない（D27）
- **手元の窓**: リモート → 手元の遅れが hook の判定の間に残る（SessionStart で分かれていた家族は次の C1 まで古い）
- **一人開発**: 承認者と開発者が同じアカウントなら、上のどれも人の目で区別する材料が無い
- **統合先の変更で基準が動く**（D28。利用者の決定で受け入れる）: 判定はプロジェクトの層と共通層を統合先の現在値から計算するので、
  着手の後に統合先の層が変わると、開いている家族の判定の基準もそれに合わせて動く（締まる向きにも緩む向きにも）。統合先への変更は MR のレビューを経る前提で受け入れる
- **統合先の名前のずれ**（D30）: Chrome と手元が別の統合先を読むと答えが食い違う。止める・名前を出す緩和だけで、揃える仕組みは持たない

**REQ-APV-07 の改訂（決定。判定がさらに緩む変更）**: 次に書き換えます。

> 承認済みチケットの置き場に在ること自体を 3 つめの証拠として認める。手元の置き場へのファイル操作はエージェントに書かせない。
> リモートの置き場（親のブランチ）はホストの権限でのみ守る（書き手の表示は行わない）

「取り込むときに、置き場を変えたコミットの書き手を表示すること」を改訂文に入れなかったので、書き手を表示する案よりさらに緩む向きです。
改訂が効き始めるのは Chrome で承認を書く段階 3 です（11 章）。判定が緩む向きの変更であることは、ADR と要件の変更履歴に明記します。

### 5.2 安く塞ぐ抜け（既存のガードで足りるもの）

| 抜け | 塞ぎ方 | 場所 | 段階 |
|---|---|---|---|
| `branch -M`（強制の改名）が通る | 短いオプションの検査に `*M*` を足す。回帰試験（3.1 の 10） | `ccnavi-git.sh` の `branch)` | 0 |
| `fetch`・`pull` の refspec で手元の ref を書き換える | `:` か `+` を含む引数を拒否 | `ccnavi-git.sh` の `fetch \| pull)`（`:493-501`） | 0 |
| `checkout <ref> <パス>`・`restore --source <ref>` で `approved/` を戻す | 置き場に当たる形を拒否 | `ccnavi-git.sh` の `checkout)`・`restore)` | 0 |
| `restore --ours/--theirs` で `approved/` の衝突を解く | 置き場に当たる形を拒否し、「人に回す」と案内 | `ccnavi-git.sh` の `restore)` | 0 |
| `worktree add --detach/-f/-B`、`checkout -B`/`switch -C`、親のワークツリーで別のブランチへ移る | 拒否。同時に `:99`・`:607` の復旧の案内を `ccnavi-sync.sh` に書き換える（D36） | `ccnavi-git.sh` の `worktree)`・`checkout)` | 2b |
| リモートで消えた `P` を普通の push で作り直す | 家族の控えが `gone` なら拒否（3.6） | `ccnavi-git.sh` の `push)` | 2b |

`checkout -B` の拒否を段階 0 に置かないのは、今の復旧の道（squash マージの後に fast-forward できないときの `checkout -B <br> origin/<br>`）を代わりの道なしに塞ぐためです。

ホストの API への直接の書き込み（`gh api`・`glab api`・curl・MCP）は**塞ぎません**。`gh api` だけを ask にしても、
`GITHUB_TOKEN` と curl で同じことができ（`rules.yml:137-150` は curl に文脈を添えるだけ）、一貫しないためです。受け入れる危険に数えます。

### 5.3 書き手の表示をしない（D29）

検討の途中にあった案（取り込みで `approved/` を変えたコミットの作者・merge の中身を表示し、Chrome にも「拡張以外の変更」を出す）は、利用者の判断でやめます。

- 手元: 取り込み（4.2）で書き手を表示しない。`history.note` にも残さない。merge コミットの分解もしない
- Chrome: 承認・取り下げ・レビュー済みの画面に書き手の一覧を出さない。そのための `GET /commits?path=` も引かない
- 署名の検証の状態も出さない（D10）
- コミットの目印も表示の材料だったので削る（D37）。C1 の見分けも取り下げも目印を読まない（4.4・8.8）

- メリット: 取り込みと Chrome の画面が軽くなり、表示のための API の読み取りと merge の分解の実装が要らない
- デメリット: 別の人が承認する普通の形でも、偽の承認を目で見付ける手掛かりが無くなる（ホストの履歴を人が見に行けば分かる）

### 5.4 将来の強化案: 承認者の署名（案 S。今回は入れない）

- 承認者ごとに Chrome 拡張の中で鍵を作り、承認の中身（写しの本文、識別子、判定が読んだ中身の指紋）に署名して写しの欄に載せる
- 公開鍵は統合先の保護された場所（例 `.ccnavi/common/approvers.yml`）に登録し、取り込みで検証する。取り下げとレビュー済みも対象
- メリット: 一人開発でも、PAT が漏れても、承認は偽造できない
- デメリット: 鍵の置き場が同じ OS ユーザーから守れない問題が残り、鍵の運用と手元の署名検証の依存が増える

### 5.5 PAT の保管と XSS

#### 保管（D23）

**PAT は `chrome.storage.local` に平文で永続保存**します。暗号化（鍵もプロファイルに残る）、OS のキーチェーン（Native Messaging が要る）、
`storage.sync`（他の機械へ広がる）は採りません。

受け入れる危険: 同じ OS ユーザーのプロセス（エージェントを含む）はプロファイルの中の PAT を読めます。
承認者の機械が開発機と別なら届きませんが、同じ機械の一人開発では届きます。マルウェア・バックアップ・拡張の乗っ取り・ログへの混入も受け入れます。

残す緩和:

- リポジトリを限った最小の権限のトークンにする（8.5）。ただし GitLab.com の無料版で project access token が使えない場合は、
  `api` スコープの個人の PAT になり、**リポジトリを限れない**。これも受け入れる危険に入れる（10.2 の確認事項 3）
- エージェント用のトークン（`ccnavi-review.sh:169-195` の `GITHUB_TOKEN`/`GITLAB_TOKEN`）とは別のトークンにする
- 設定画面からいつでも削除・差し替えでき、差し替えのときは古いトークンの失効を案内する

#### 期限（D25）

- 既定は 90 日。登録画面でホストの作成画面へのリンクと、選ぶ権限の一覧を出す
- 期限の正はホストの PAT の期限。GitHub は応答ヘッダ `github-authentication-token-expiration`、GitLab は `GET /personal_access_tokens/self` の `expires_at`
- GitHub のヘッダは、`host_permissions` を持つ拡張の fetch が CORS の制限を受けないので読めるはず（確信中）。**段階 3 で確かめる**。
  読めなければ登録時に利用者が期限の日付を入れる（入れなければ「期限不明」と出し続ける）
- 切れる 7 日前から、service worker が `chrome.alarms` で 1 日 1 回比べ、バッジとボードの帯で出す。401 が返ったら差し替えを促す

#### XSS への対策（入れる）

1. **入力の扱い**: チケット本文・コメント・issue の本文・ブランチ名・MR のスレッドなど、リポジトリやホスト由来の文字列は攻撃者が制御しうる入力として扱う
2. **描画**: Markdown は HTML に変換した後に DOMPurify（同梱）でサニタイズする。素の文字列は `textContent`。リンクは `http:`・`https:`・`mailto:` だけ
3. **CSP**: MV3 の既定を緩めない。足すのは Pyodide に要る `'wasm-unsafe-eval'` だけ。`'unsafe-eval'`・`'unsafe-inline'`・外部のスクリプトは入れない。
   Pyodide が `'unsafe-eval'` を要る場合は、その部分だけ sandbox ページに移す（7.2）
4. **PAT に触る場所を限る**: PAT を読むのは service worker だけ。画面と Pyodide の Worker には渡さず、ホストの API は名前で限った操作を
   `chrome.runtime.sendMessage` で頼む。`sender` を確かめ、`externally_connectable` は宣言しない。
   限界: 同じ拡張オリジンなので、画面で XSS が起きれば storage を読める。本命は 2・3
5. **外へ送りにくくする**（D24）: `host_permissions` と CSP の `connect-src` を、ビルドのときに焼き込んだ API のホストに限る。既定は `api.github.com` と `gitlab.com`
6. **試験**: 悪意のある Markdown の見本（`<script>`、`<img onerror>`、`javascript:` のリンク、`<svg onload>`、`data:` の URL、実体参照で崩したスキーム）を段階 1 と段階 4 で回す

### 6.2 境目


- **先頭の一致は書き込みの条件として別に取る**（8.3・8.4）
- 差し口は 3 つ: **Reader**（手元のツリーと控え / REST・GraphQL API から Snapshot を組む）、**Writer**（手元に書く / GitHub GraphQL / GitLab Commits API）、**Clock**

  手元の Writer(FS) は fsio を通るので、C1 の記録層がそのまま効く

- デメリット: 14MB と初回数秒の待ち。Pyodide の版上げと同梱の手間。CSP に縛られ、sandbox に移すなら経路が 1 段増える

### 7.3 版ずれ（D31）

Chrome は ccnavi の .pyc を同梱するので、手元の ccnavi と版がずれます。ずれたまま承認すると、手元の C3（取り込みでの判定し直し）が別の答えを出して家族を止めます。

- 目印は既存の互換の版 `CCNAVI_COMPAT`（`ccnavi-common.sh:27`、`ccnavi_compat_skew` `:168-183` が実行ファイルと sh の食い違いに使っているもの）
- Chrome は統合先の `.ccnavi/scripts/ccnavi-common.sh` からこの行を読み、同梱の版の互換と比べる。**違えば承認・取り下げ・レビュー済みを出さず、表示だけにする**。
  画面には「拡張は互換 X、リポジトリは互換 Y。拡張を更新する（Y が新しい）か、リポジトリの ccnavi の更新を待つ（X が新しい）」と出す
- 止めた状態はどこにも書かない。ボードを開くたびに比べ直すので、版が揃えば自然に解ける
- 互換が同じでも手元の C3 と答えが違ったら、不具合として扱う: C3 は家族の控えを `blocked`（`reason` に「Chrome <拡張の版> と手元 <版> で判定が違う」）にして止める。
  解き方は、版を揃えてから `ccnavi-sync.sh <P>` を打ち直す（判定し直して通れば `present` に戻る）。拡張の版は跡の行（`via: chrome`）に入れて残す

- メリット: 互換の違う判定がリモートに乗らない。既存の互換の仕組みを使うので新しい印が要らない
- デメリット: リポジトリか拡張のどちらかが更新されるまで、Chrome で承認できない期間ができる

## 8. Chrome 拡張の構成

### 8.1 形

- MV3。ボードは拡張のページ（サイドパネルかタブ）。Pyodide はそのページが起こす Web Worker で動かす（落ちるなら sandbox ページ。7.2）
- CSP: `script-src 'self' 'wasm-unsafe-eval'; object-src 'self'; connect-src 'self' <API のホスト>`。Pyodide・PyYAML・ccnavi の .pyc・DOMPurify を同梱
- PAT とホストの API の呼び出しは service worker が持つ（5.5 の 4）
- ビルドのときに API のホストの一覧から `host_permissions` と `connect-src` を生成する（D24）
- コアの切り出しが済むまでは、MEMFS にブランチごとの仮のツリーを組んで今のコードを動かす（段階 1）

### 8.2 ブランチの読み方と読み取り量

- 統合先: 拡張の設定にあればその名前、空なら `GET /repos/{o}/{r}` / GitLab `GET /projects/:id` のデフォルトブランチ（3.3）。設定した名前のブランチが無ければ（404）止めて知らせ、使った名前をボードの見出しに出す
- 直近 N 日（表示用）: GitHub は GraphQL の `refs { target { committedDate } }`、GitLab は `GET /repository/branches`
- `P` と閉包の `P_X`: 提案の `parent or ticket` と、参照する識別子から求める（3.3 の 5）
- 読むのは置き場のサブツリーだけ。GitHub はパスで置き場の tree の sha を引き、`?recursive=1` で取る。`truncated: true` なら error で止める。
  GitLab は `repository/tree`（`path`・`recursive`）をページングで取り切り、取り切れなければ error

読み取りを減らす工夫:

- **blob は sha で引き、IndexedDB に控える**（sha が同じなら中身は同じなので、失効が要らない）。ボードを開くたびに読むのは tree だけになる
- **まとめて取る**: GitHub は GraphQL の別名（`f1: object(expression: "P:path") { ... on Blob { text } }` を並べる）で、控えに無い blob を 1 回に最大 50 件ほど取る。
  GitLab は GraphQL の `repository { blobs(paths: [...], ref:) }` を使う見込み（確信中。段階 5 で確かめる）
- **統合先の `done/`**: 今の `predecessor_pool` は `scan(closed=True)` で `done/` を全部読む（`approval.py:688-694`）。
  MEMFS で今のコードを動かす間（段階 1〜2a）は `done/` の blob を全部取る。コアに移ってからは、判定が要るもの（閉包の先行、同じ識別子の検査で当たったもの）だけを取り、
  取らなかったものは `NOT_FETCHED`（6.2）にする

見積もりの式（初回）: blob の数 ≒ Σ（判定に入る家族の置き場のファイル数）+ 統合先の `done/` の件数。GraphQL の呼び出し ≒ ⌈blob の数 / 50⌉ + 1（refs）。
2 回目以降は、変わった blob の分だけ。

例（GitHub、承認待ちのある家族 3 つ、各家族の置き場に 40 ファイル、`done/` に 200 件）:

| 場面 | REST | GraphQL | 備考 |
|---|---|---|---|
| ボードを開く（初回） | 約 11（リポジトリ 1、tree 各ブランチ 2 × 4、互換の印 1、統合先の有無 1） | 約 8（refs 1、blob の束 7） | blob 約 320 件（家族 120 + `done/` 200） |
| ボードを開く（2 回目以降、変更なし） | 約 11 | 1 | blob は控えから |
| 承認 1 回（読み直し + 書き込み） | 約 4 | 2 | 指紋の比較と `createCommitOnBranch` |

GitHub の上限（REST 5,000 回/時、GraphQL 5,000 点/時）に対して十分小さい。GitLab.com も認証済みの上限に対して小さい見込み。

### 8.3 承認の流れと競合

1. preview: Snapshot を組み、`judge` → 画面と指紋。書く先の `P` の先頭 `H` を控える
2. yes: Snapshot を組み直し、指紋が同じか確かめる（違えば preview からやり直し）
3. `plan` の変更を、`P` へ 1 コミットで書く。条件は「`P` の先頭が `H` のまま」
4. 先頭が動いていたら（D20）、**新しい先頭で Snapshot を組み直し、`judge` と `plan` を必ずやり直す**。
   指紋が同じなら新しい plan を新しい先頭に書く（人に見せ直さない）。違えば preview からやり直す。
   古い plan をそのまま書くことはしない（跡の全文の `update` で、相手が足した行を消すため）。3 周しても書けなければ人に回す

**1 回の承認は 1 つの `P` に限る**。取り下げ（8.8）とレビュー済み（8.9）も同じ流れで書きます。

### 8.4 1 コミットの作り方

- **GitHub**: GraphQL の `createCommitOnBranch`（`expectedHeadOid = H`）。先頭が `H` でなければ落ちるので、そのまま競合の検出になる。
  Git Data API + `PATCH refs` は force push 後の巻き戻しを早送りとして通すので採らない。**`seq` は書かない**（`expectedHeadOid` で足りる）
- **GitLab**: `POST projects/:id/repository/commits`（`branch: P`、`actions`）。既存ブランチに「先頭がこの sha のときだけ」の指定が無い見込み。2 段で入れます（D21）
  - **1 段目（段階 5 の最初）: 事後確認と打ち消しだけ**。書いた後にコミットの `parent_ids[0]` が `H` と同じか確かめ、違えば新しい先頭で判定をやり直し、
    結論が違えば打ち消しのコミットを積んで知らせる。打ち消しがさらに競合して 2 回で収まらなければ、止めて人に回す（ボードに家族を「要確認」で出す）。
    この段では、取り下げと子の承認が同時に通ったとき「親の無い子」が一時的に `P` に残りうる
  - **2 段目（確認事項 2 が取れたら）: 印ファイル `phases/<P>/seq` を足す**。ccnavi の全コミット（Chrome の承認・取り下げ・レビュー済み、C1、運ぶ処理）が
    GitLab のリポジトリでだけ必ず更新する家族ごとの小さなファイル（中身は通し番号と最後の操作）。
    Chrome は書く直前に `GET repository/commits?path=phases/<P>/seq&ref_name=P&per_page=1` で「`seq` を最後に変えたコミット」の sha を引き、
    `seq` の `update` の action に `last_commit_id = <その sha>` を付ける。`last_commit_id` は「そのファイルを最後に変えたコミット」と比べる見込み（確信中〜高）なので、
    ccnavi の書き込みどうしは後の方が落ち、疑似的な比較つき書き込みになる。コードだけのコミットは `seq` を変えないので落ちない（状態には関係しない）。
    引いてから書くまでの間の書き込み（TOCTOU）とコードのコミットは捕まえられないので、1 段目の事後確認は安全網として残す
  - 代案（一時ブランチ + MR の fast-forward マージ）は、確認で前提が崩れたときの控え
- 手元の merge で `seq` だけが衝突したら origin 側を採って解く（4.2 の 3）
- 提案の削除: 提案が `P` の上にあれば同じコミットで消す。`P` 以外のブランチにある提案は承認しない
- コミットメッセージは人が読む説明（「ccnavi: <識別子> を承認」など）と拡張の版だけ。どの処理も読まない（D37）。`[skip ci]` は付けない（4.3）

### 8.5 PAT の権限

| ホスト | 承認・取り下げ（段階 3） | レビュー済み（段階 4） | 「始める」（段階 5） |
|---|---|---|---|
| GitHub（fine-grained、リポジトリを限る） | Contents: Read and write、Metadata: Read、Pull requests: Read | 同じ | 同じ + Issues: Read |
| GitLab | `api`（Commits API は `write_repository` では書けない） | 同じ | 同じ |

GitLab のトークンの種類: project access token（リポジトリを限れる）を勧めるが、**GitLab.com の無料版では使えない見込み**（確信中。10.2 の確認事項 3）。
使えなければ `api` スコープの個人の PAT になり、リポジトリを限れない点を受け入れる危険に入れる（5.5）。

保護されたブランチ（`main` など）と統合先へは書かない（`ccnavi-push-approved.sh:174-175` と同じ一覧 + 統合先の名前）。

### 8.6 Chrome 拡張から issue・ブランチを作る操作（「始める」。D19）

| 案 | 内容 | メリット | デメリット |
|---|---|---|---|
| G0 | 載せない。人がホストの画面で作る | 権限が最小 | ホストの既定のブランチ名を人が毎回 `i<番号>` に直す |
| **G1（採用）** | issue の一覧に「始める」: `P = i<番号>` を統合先の先頭から作る。PR/MR は作らない | 名前を拡張が求めるので直し忘れが無い | PAT にブランチを作る権限が要る |
| G2 | issue の作成も載せる | 全部が拡張で済む | ホストの issue 画面の再実装に近づく |

- **拒否する場合**: 求めた識別子が統合先の `done/` にある（既存の `i0055`〜`i0062` と issue #55〜#62 の衝突など）、
  同じ名前のブランチが既にある、開いた家族に同じ識別子がある、予約の名前に当たる（3.1 の 5）。画面に「この issue からは始められない。識別子を人が付けて（フォールバック）始める」と出す
- 差分 0 のブランチからは GitHub が PR を作らせない（422）ので、PR/MR は最初の push の後に `ccnavi-review.sh request` が作る

### 8.8 承認の取り下げ

Chrome のボードに「承認を取り下げる」を置きます（D14）。既存の「差し戻し」（子を足してやり直す）とも `cancel`（取り消し。`done/` に `cancelled` で閉じる）とも別の操作です。

**条件**（すべて満たすときだけ出す。判定はコアの `withdraw`）:

- 写しが `P` の `doing/` にあり、**新規の承認**である（`ccnavi_approved` に `revised_at`・`feedback_at` が無い）。改版は `settle_review` などが走っていて戻せない
- **followup の写しではない**: `followup_of` を持つ写し、または `source_path` が空の写し（`approval.followup`、`approval.py:540-615` が起こしたもの）は対象外
- **未着手**: `started_at` が空。C1 で着手は `P` に必ず届いている前提（対象外の家族は Chrome に見えない）
- **子が無い**（親の写しのとき）: その親を `parent:` に持つ写しが `doing/`・`review/`・`done/` に無く、**`todo/` にも子の提案が無く**、`phases/<親>/` にマーカーが無い
- **`P` に `todo/<識別子>.md` が無い**（戻す先に別の提案がある間は出さない）
- **承認コミットが引ける**（下の 2）。引けなければ出さない

**操作**（`P` への 1 コミット）:

1. `doing/<識別子>.md` を消す
2. `wip/proposals/todo/<識別子>.md` に、**承認コミットの親にあったバイト列**をそのまま戻す。
   承認コミットは、`P` の履歴で `doing/<識別子>.md` を足したコミットのうち**最新の、親が 1 つのもの**（merge コミットは飛ばす）。
   GitHub は `GET /commits?sha=P&path=<doing の綴り>`、GitLab は `repository/commits?ref_name=P&path=` で引き、各コミットの変更で「足した」かを確かめる。
   その親のコミットの `todo/<識別子>.md` を読む。**目印は見ない**（D37）。親に提案が無い（端末で承認して別のブランチから運んだ場合など）ときは取り下げを出さない。
   取り下げの後に承認し直せば、次の取り下げは新しい方の承認コミットを選ぶ
3. `events/<識別子>.ndjson` に 1 行足す: `{"kind": "withdrawn", "from": "doing", "to": "todo", "actor": <アカウント>, "via": "chrome", "version": <拡張の版>, "at": <時刻>, "reason": <任意>}`
4. GitLab の 2 段目からは `seq` を更新する

子の承認で消えたフェーズのマーカーは戻しません（締まる向き）。

**着手後**は取り下げられません。画面には「着手済み。取りやめるなら `ccnavi-ticket.sh cancel <識別子> --reason <理由>` をエージェントに頼む（`done/` に取り消しの記録が残る）」と出します。

**Python 側**:

- `events/` は補助で、判定も状態の操作も読まない（`history.py:3-7`）。判定側の変更は要らない
- 足すもの: `history.KIND_WITHDRAWN = "withdrawn"`、経路 `history.VIA_CHROME = "chrome"`（経路の一覧は `history.py:55-64`）、跡の行の `actor`・`version` 欄
- VS Code のボードの呼び名の表（`vscode-extension/ccnavi-board/src/webview/board/text.ts:155-181`）に `withdrawn: "承認の取り下げ"` と `chrome: "Chrome 拡張"` を足す
- 取り下げ後に同じ識別子を承認し直すのは普通の新規の承認。`next_child_id` は todo の提案も数えるので、番号は再利用されない

- メリット: 押し間違いを、エージェントが動く前なら跡付きで元のバイト列に戻せる。条件が狭く、判定は緩まない
- デメリット: 着手後・改版・followup・子のある親・承認コミットの引けない承認は取り下げられない。取り下げのたびに履歴の API を数回引く

### 8.9 レビュー済みの印を Chrome から付ける

開発者と承認者が別の前提では、MR を見てスレッドを片付けるのは承認者側です。Chrome に「レビュー済み」を置きます（D15）。
`ccnavi-review.sh confirm` は手元用に残し、両方とも同じコアの `confirm` と `reviewed_mark` を使います。

**印の中身**（`phases/<親>/<N>.reviewed`）:

```json
{"mr": 42, "accepted": [], "actor": "<ホストのアカウント名>", "via": "chrome", "at": "<時刻>"}
```

- 既存の欄 `by` は**経路名**（`"feedback-plan"` `phase.py:1128`、`"chat"` `review.py:1043`、`"close-early"` `review.py:1366,1379`）なので、
  アカウントは新しい欄 **`actor`** に入れる。`confirm` の印は今どおり `by` を持たない
- Chrome の `actor` は PAT の持ち主。手元の `confirm` の `actor` は `ccnavi-review.sh` がトークンの持ち主を API で引いて `--actor` で渡す
  （引けなければ git の `user.name`）。`via` は `cli`。`decide` の印も同じ関数で書く（`via` は `terminal` か `board`）
- 読む側（`phase.py` の止める判定）は印が在るかと `mr`・`accepted` しか見ないので、欄を足しても判定は変わらない。`actor` は記録で、表示や警報には使わない（D29）

**`confirm` の検査を Chrome で同じにできるか**:

| 検査（`review.confirm`） | 手元での材料 | Chrome での材料 | 同じにできるか |
|---|---|---|---|
| 依頼のマーカーがある | `P` の `phases/<親>/<N>.requested` | 同じファイルを API で読む | できる |
| 依頼の後に人が見るものが動いていない（`_moved_since_request`） | 手元の git の差分 | compare API の変更パスをコアに渡す。打ち切られたら（GitHub は 300 件）動いたと数える | できる |
| push 済みか（`_unpushed`） | 手元と `origin/P` の差 | 不要 | 手元だけに残す |
| 同じ MR か（`_matching`） | `ccnavi-review.sh fetch` の写し | 印の `host`・`mr` で MR を直接引く | できる |
| 変更要求のレビューが無い（`effective`） | 写しの `reviews` | GitHub `GET /pulls/{n}/reviews`、GitLab は approvals と discussions | できる |
| 未解決スレッドが無い | 写しの `threads` と `accepted.json` | GitHub GraphQL の `reviewThreads.isResolved`、GitLab `discussions` の `resolved` | できる |
| レビュー待ちの子を `done/` へ | ファイルの移動 | 同じ移動を `Changes` にして同じコミットに入れる | できる |

ホストの写しは `ccnavi-review.sh` が組む JSON（`{host, mr, threads, reviews, fetched_at}`）と同じ形にして `Result.load` に渡します。
未解決が残るときは Chrome では通さず、「解決するか、`decide`（端末・VS Code のボード）で受け入れる」と出します。

**sh と TS の二重実装の見本と更新手順**（段階 4）:

- ホストの応答を録った見本を `tests/fixtures/host/<github|gitlab>/<場面>/` に置く（ページングの 2 ページ目、解決済みと未解決の混在、変更要求の後の承認など）
- 期待値は「その見本から sh が組んだ写しの JSON」1 つで、sh の試験と TS の試験の両方がそれと突き合わせる
- 更新の手順: (1) ホストの応答の形が変わったら、録り直しの sh で見本を取り直す、(2) sh の試験を回して期待値の JSON を作り直す、
  (3) TS の試験を回し、落ちたら TS を直す、(4) 見本・期待値・sh・TS の変更を**同じコミット**に入れる。片方だけの変更は CI で落ちる
- メリット: レビューした本人がその場で印を付けられ、印に誰が付けたかが残る
- デメリット: ホストのスレッドの取り方が sh と TS で二重になる（判定はコアで 1 か所）

### 8.10 ホストの「新しいコミットで既存の承認を外す」設定

GitHub の「Dismiss stale pull request approvals when new commits are pushed」、GitLab の「Remove all approvals when commits are added to the source branch」が
有効だと、ccnavi のコミットが `P` に積まれるたびに MR の Approve が外れます（D16）。

方針: ccnavi のコミットはチケットの置き場だけを変えるので、コードの最後の Approve の前に済ませる運用にします。
ccnavi 自身は MR の Approve を読まない（`review.py:396-433`）ので、途中の Approve が外れても ccnavi の流れは止まりません。

| 時点 | ccnavi のコミット（`P` へ） | MR | ホストの Approve |
|---|---|---|---|
| 親の計画の承認 | Chrome の承認 | まだ無い | 無い |
| 着手・子の承認・子の終了 | C1、Chrome の承認 | Draft | 付けない |
| フェーズのレビュー | 依頼のマーカー（C1）→ Chrome の「レビュー済み」か `confirm` | Draft | 付けない |
| 親を閉じる | `finish`（C1）→ `wip/` を消して push → `ready` のマーカー（C1） | Draft を外す | ― |
| マージ | 無い | Ready | ここで最後の Approve を付ける |

Chrome の画面では、MR に Approve が付いているときに「このコミットで MR の Approve が外れることがあります」と出します。止めはしません。
設定の側で避ける手（GitLab の Code Owners の対象から `.ccnavi/approved/` を外すなど）は未確認なので、確かめるまで案内しません（10.2 の確認事項 1）。

| 「ref が無い」で落ちた fetch（3.6） | `ccnavi-fetch.sh` | `couldn't find remote ref` で落ちたら、その origin を落ちたものに数えない（同じ origin の統合先の取り込みを飛ばさない）。家族なら「`ccnavi-sync.sh <P>` で確かめる」と言う |
| push の移り目と `gone` の拒否（4.3・3.6） | `ccnavi-git.sh` の `push)` | 送る前に、控えが `gone` の `P` への push を拒否する（控えを読むだけ。`ls-remote` はしない）。通った後、送った先が親のブランチ（ディレクトリ名 = ブランチ名、親の写しか提案がある）で送り先が origin なら、控えを `present` で作る。置き場（`approved/`・`proposals/review/`。未追跡を含む）に未コミットの変更があれば作らずに言う。`present` の控えは `sha` だけ書き直し、`closed` は触らない |
| 付け替えと移動の拒否（D36・5.2・3.1 の 10） | `ccnavi-git.sh` の `worktree)`・`checkout \| switch)` | `worktree add` の `-B`・`--detach`/`-d`・`-f`/`--force` を拒否し、`-b` の名前（`-b` が無ければ 2 つ目の語）が行き先の名前と違えば拒否。`checkout -B`（束ねた `-qB` も）・`switch --force-create` を拒否（`switch -C` は全引数の `-C` で前から止まる）。親のワークツリーでは、自分のブランチと `HEAD` 以外へ移る形（`checkout <別>`・`-b`・`--orphan`・`--detach`・`switch --create`・`-d`・`-`）を拒否し、「親のブランチの名前は識別子で、変えると家族が止まる」と言う |
| 案内文の書き換え（D36・3.1 の 10） | `ccnavi-git.sh` の使い方と `reset` の拒否文、`fetch`・`pull` の refspec の拒否文 | 「リモートに合わせるなら、親のブランチは `ccnavi-sync.sh <P>`。ほかのブランチは `fetch` のあと `merge <リモート>/<ブランチ>`。分かれていて進めないなら人に回す」。refspec の文は「手元の ref は `ccnavi-sync.sh <ブランチ>` が進める」 |
| 統合先の名前の予約（3.1 の 5） | `ticket.branch_name_problems`、`lint`、`cli` の `--integration-branch` | 渡された統合先の名前（大文字小文字を畳む）に当たる新規の親の識別子を `--lint` の warn で言う。環境変数は読まない |
| 配る sh | `scripts/ccnavi-setup.sh` | `ccnavi-sync.sh` を配る一覧に足した（拒否の文面が案内するため） |

後方互換（D11）: origin の無いリポジトリと、一度も push していない `P`（控えが無い）は前と同じ動き。
chat だけの家族（MR を持たない家族）も、送らなければ控えができず前と同じ。送れば控えができる（見分けは実行ファイルの種類の読みが要るので、C1 の対象を決める 2d で入れる）。
控えができた家族で段階 2b が変えるのは、SessionStart の早送りの規則、`ccnavi-sync.sh` の消えたかの確かめ、`gone` の `P` への push の拒否の 3 つ。
控えの無い親のワークツリーは、SessionStart でも前の規則（未コミットがあれば進めない）のまま。控えができるのは、段階 2b の後に `ccnavi-git.sh push` が通ったときか、`ccnavi-sync.sh` を打ったとき。
判定（hook・lint・承認）は控えを読まないので、答えは変わらない。

ADR に無かった判断:

- 置き場の綴りと settings.local.json の統合先の値は、実行ファイルの `ccnavi sync paths`（1 行 1 項目）で sh に渡す。実行ファイルが無ければ環境変数の綴りに落とす。統合先の名前は環境変数が settings.local.json より先
- `--integration-branch` を今渡す呼び手は無い（2c で sync の lint がこれを渡す）
- MR の確認は `ccnavi-review.sh merged`（新しい副命令。実行ファイルを起こさない）で行い、答えが `merged <番号>` のときだけ「反映待ち」にする
- 「3 回まで 5 秒おき」は最初の確かめの後の確かめ直しの回数と読んだ。試験のために `CCNAVI_SYNC_RETRIES`・`CCNAVI_SYNC_RETRY_WAIT`・`CCNAVI_FETCH_BUDGET` で変えられる（既定は ADR の値）
- `ccnavi-sync.sh` が扱うのは親のワークツリーだけ。ほかのブランチには `merge <リモート>/<ブランチ>` を案内する
- 早送りや merge が止まったときも、控えは `present`（リモートにあること）で書く
- 引数を省いた `ccnavi-sync.sh` は、家族が無くても origin のあるリポジトリ（ワークスペースとプロジェクト）の統合先の控えを書く

入れなかったもの:

- 判定が控えを読むこと（権威・閉じた家族・閉包の池・統合先の控えからの層）、取り込みの後の `--lint` と C3 の判定し直し、控えの `blocked`、`ready` の前提: 段階 2c
- 指紋を `read_set` にすること: 2c（Reader の差し替えと同時。利用者の決定）
- 書いたパスの一覧の基点を `P` のワークツリーに絞ることと、置き場の外を error にすること: 2d（利用者の決定）
- C1、運ぶ処理の改修、人の入口の sh: 2d。ロックの関数は入れたが、C1 からの入れ子の使い方と Git Bash の `kill -0`（10.2 の 6）は 2d で確かめる
- `phases/<P>/seq` だけの衝突を origin 側で解くこと: GitLab の段階 5
- `settings.local.json` に承認に効く値を置かせない lint と、`P` の上のプロジェクトの層の食い違いの warn: 2c
- `ccnavi-fetch.sh` の 2 周目（ワークツリーの起点）は今までどおりデフォルトブランチを進める。統合先の名前には合わせていない

#### 11.4.1 段階 2b で触った守りの対象

`.ccnavi/scripts/` の `ccnavi-git.sh`・`ccnavi-fetch.sh`・`ccnavi-common.sh`・`ccnavi-review.sh`（`merged` の副命令）と、新しい `ccnavi-sync.sh`。
利用者の承認を得て直接直した。

## 得たもの・失ったもの

決定ごとの得失は 10.1 の表に 1 行ずつ置いた。まとめると次のとおり。

- 得たもの: 承認者がブラウザと PAT だけで承認でき、手元とブラウザが同じコード・同じ入力で同じ答えを出す。権威が「親のブランチ 1 枚 + 統合先の `done/`」に決まり、ツリーからの推定が消える
- 失ったもの: **REQ-APV-07 が緩む**（リモートの置き場はホストの権限でのみ守り、書き手も表示しない。5.1）。一人開発や PAT の漏れでは偽の承認を区別できない
- 失ったもの: 取り込み済みの家族では状態の操作にネットワークが要り、sh（`ccnavi-sync.sh`・C1・ロック）が増える。`approval.py`・`phase.py`・`review.py` の広い範囲に手が入る
- 失ったもの: Chrome 拡張に Pyodide（約 14MB）を同梱し、初回に数秒待つ
- 段階 0 で失ったもの: 置き場に当たるパスを `checkout <ref>`・`restore --source`・`restore --ours / --theirs` で戻す道と、`fetch`・`pull` の refspec と URL と、`branch -M`・`-C` がエージェントから使えなくなる。要るときは利用者が打つ
- 段階 2b で失ったもの: `checkout -B`・`switch --force-create`・`worktree add -B / --detach / -f`、行き先の名前とブランチ名の違う `worktree add`、親のワークツリーでの別のブランチへの移動がエージェントから使えなくなる。squash マージの後で早送りできないブランチは人に回す

## 採らなかった案

- **状態専用ブランチに写しを集める**: 作業の履歴と別になり、提案の削除と写しの追加を 1 コミットにできない。手元の hook から読めない
- **写しを統合先に直接書く**: 保護設定に当たり、変更量が大きい
- **承認以外だけを Chrome に載せる / Native Messaging で手元の ccnavi を呼ぶ**: 承認者の機械に clone と ccnavi が無い前提に合わない
- **ブランチ名を `<番号>-<slug>` にする（N2）**: 題の変更と日本語の題で名前が引けなくなる
- **判定を TS で書き直す（T）・表示だけ TS（H）**: 3,000 行を超える二重化。H は ADR-0035 に反する
- **`P` が無いときに統合先で新規扱いにする**: 改版の制約を迂回できる
- **`P` の改名を追う仕組み / Chrome の「ブランチを戻す」**: 追う先を間違えると権威が動く。戻しは人が行い、ccnavi は案内だけにする
- **判定の中で `git cat-file` から `P` を読む**: 判定の中で外部プロセスを起こさない前提に反する（sh の中でだけ使う）
- **Python の `ccnavi sync` にネットワークとコミットを持たせる**: 実行ファイルの境界に反する（4.5）
- **C1 を全家族に掛ける**: origin の無い・まだ push していない家族まで止まる（4.3）
- **C1 の戻しに `reset` を使う**: 先頭が他の操作で動いていたときに、そのコミットを消しうる。比較つきの `update-ref` にした
- **C1 で「取り込み → 書く → コミット」の順**: hook の書きかけと merge がぶつかって止まり続ける。見分けとコミットを取り込みの前に置いた
- **SessionStart で merge・観測ずれの再試行・MR の確認をする**: hook の時間の枠で途中の merge が残り、ロックなしで他の操作とぶつかる
- **消えた `P` を fetch 失敗の一覧に入れる**: 統合先の取り込みまで飛ばされ、閉じた家族を「決まらない」にする
- **`ccnavi-git.sh push` の毎回の `ls-remote`**: push のたびにネットワークを往復する。控えの印で足りる（届いたかの確かめは落ちたときだけ）
- **書き手を表示する・merge コミットを分解して見せる・署名の検証を表示する**: 利用者の判断でやめた（D29）
- **コミットの目印を残す**: 表示をやめた後は機械的に読む所が無く、読めば偽装の余地になる（D37）
- **(c) の偽物を防ぐ台帳**: 利用者の判断で作らない。受け入れる危険に数えた
- **record-risk を別の C1 にする**: `finish` が同じ判定を入力に読むので、`finish` の C1 にまとめた
- **両ホストで `seq` を書く**: GitHub は `expectedHeadOid` で足り、余計なファイルと衝突の種を増やす
- **GitLab で最初から `seq` に頼る**: `last_commit_id` の意味を確かめる前に前提にしない。事後確認から始める
- **控えを JSON にして sh で jq を使う**: SessionStart と `ccnavi-git.sh` に依存を足す
- **`checkout -B` を段階 0 で拒否する**: 今の復旧の道を代わりなしに塞ぐ
- **configsync の写しを未コミットで残す**: C1 の記録層の検査で `start` が止まり、プロジェクトだけを clone した人に層が届かない
- **統合先をデフォルトブランチに固定する**: develop 運用で `done/` と層を間違ったブランチから読む
- **統合先の名前をホストのデフォルトブランチの `.claude/settings.json` に置く**（検討の途中で推した案）: 利用者の判断で採らない。リポジトリの設定を増やさず、使う側に持たせた
- **版を問わず Chrome で承認する**: 互換の違う判定がリモートに乗り、手元の判定し直しで家族が止まる
- **指紋に全ブランチの `head_sha` を入れる**: 無関係なコミットで承認が通らなくなる
- **Git Data API + `PATCH refs`（`force: false`）**: force push 後の巻き戻しを早送りとして通してしまう
- **承認中に `P` が動いたとき古い plan を新しい先頭に書く**: 跡の全文の `update` で相手の追記を消す
- **「始める」で Draft PR も作る**: 差分 0 のブランチから PR は作れない（422）
- **GitLab の競合を一時ブランチ + ff マージで防ぐ**: MR が 1 本増える。前提が崩れたときの控え
- **二重状態を C2・C3 で解く**: 印を置くのに push が要る / 緩い承認が一度は乗る
- **取り下げで `ccnavi_approved.added` を見て欄を外す（`unadmit`）**: 新しい欄とコアの関数が要り、古い写しで組み直しが不確か。履歴のバイト列を戻す方が確実
- **着手後の承認や改版も Chrome から取り下げる**: 着手で始まった作業と、改版で動いた子・消えたマーカーを戻せない
- **`decide` を Chrome に載せる**: 指摘ごとに行き先を選ぶ画面と issue の下書きの投稿まで要り、今回の目的を超える
- **ホストの設定を変えて Approve が外れないようにさせる**: 設定の可否が未確認で、組織の保護設定に手を入れさせる
- **`gh api` / `glab api` の書き込みを ask にする**: `GITHUB_TOKEN` と curl で同じことができ一貫しない
- **署名を必須にする（案 S）**: 利用者の判断で今回は入れない
- **PAT を毎回入力する（`storage.session`）・WebCrypto で暗号化する**: 利用者の判断、または同じ OS ユーザーには難読化程度にしかならない
