# ADR-0056: 控えは途中を見せない書き方で置き、取りこぼしはロックで塞がない

状態: 採用

## 状況

`logs/state/` の控えは、並んで走る hook が「読んで、足して、書き戻す」形で使う。
`ctxfile` の渡した回の数え、`post` の報告済みの控えとターンの基準、`approval` の
伝えた承認の控えが全部これにあたる。

書き込みは `open(path, "w")` だった。これは開いた時点で中身を捨てるので、書き終えるまでの
あいだファイルは空になる。そこを別の呼び出しに読まれると、読む側は「まだ何も無い」と読む。
途中で落ちたときも空のまま残り、次の起動が同じ読み違いをする。

実測（8 プロセス × 40 回を同じ控えにぶつけたもの）では、320 回のうち 59 回が読めず、
最後に残った数えは 7 だった。`every` を持つルールでは、数えが 0 に戻るたびに「5 回目」が
遠のくので、**勧告が 1 度も届かないことがあった**。

**この数値は 1 つの機械での 1 回の計測で、回すたびに大きくばらつく。** 別の環境で同じ実験を
回したときは、読めない回が 1〜26 のあいだで動いた。順序を決めているのは OS の都合なので、
再現するのは向き（読めない回が出る／取りこぼしが残る）であって、値ではない。

## 決定

- **控えは途中を見せない書き方で置く**（`fsio.write_text_atomic`）。同じディレクトリに
  一意な名前の一時ファイルを作り、書き切ってから `os.replace` で差し替える
- **読み側にも打ち直しを足す**（`fsio.read_json`）。差し替えは中身を壊さないが、Windows では
  その一瞬だけ共有違反で開けない。片方だけでは並列を捌けない
- **読めなかった回は書き戻さない**（`ctxfile._load_once` が「まだ無い」と「読めない」を分けて返す）。
  文は届ける側へ倒しつつ、控えには触らない
- **取りこぼし（2 つが両方読めて、両方が `+1` を書く）はロックで塞がない。** 残す

## 理由

3 つを揃えて初めて「数えが 0 に戻る」が消える。差し替えだけでは失敗の形が
「空を読む」から「開けない」に変わるだけで、読む側の結論（まだ何も無い）は同じだった。
打ち直しを足しても、尽きたときに書き戻せば同じ場所に落ちる。実測で読めない回が
0 になったのは 3 つ目を入れてからで、これは順に足して確かめた。

ロックを入れなかったのは、値段が釣り合わないため。

- Python の標準ライブラリに移植性のあるファイルロックが無い。`fcntl` と `msvcrt` の
  出し分けが要る。このリポジトリは Git Bash・WSL・Linux・macOS の 4 つで動く
- **ccnavi は全ツール呼び出しの経路にいる。** ロックを掴んだまま固まったプロセスが 1 つあると、
  以降の全操作が待たされる。勧告が届かないことより、セッションが止まるほうが重い
- タイムアウトで諦めればロック無しに戻るので、境目の挙動が読みにくくなる
- このリポジトリにロックの前例が無い

## 得たもの・失ったもの

**得たもの**

- 数えが 0 に戻らなくなった。実測で読めない回が 320 中 0
- 途中で落ちても、前の中身が残る。次の起動が空を掴まない
- 同じ形の控え 5 か所（`_save_once`・`_save_seen`・`_save_turn`・`_write_known`・
  `remember_accepted`）が同じ書き方に揃った

**失ったもの**

- **取りこぼしは残る。** 上の実測で、最後の数えは 320 中 74〜185（回すたびに動く）。
  **規模は小さくない。** 残るのは「遅れ」であって「後戻り」ではない（数えは 1 ずつしか
  進まないので `every` の倍数も `Once` の N 回目も飛び越さない）が、5 回目が何回目にずれるかは読めない
- **打ち直しを使い切った回は、刻みを外れて渡る。** 読めなかったときは「渡す側へ倒す」ので、
  倍数でも N 回目でもない回に文が渡り、`Once` も改めて渡りうる。これは上の「遅れ」とは
  別の種類のずれで、刻みの外に出る向き。控えを潰すよりは軽いと見て採った倒し方だが、
  **刻みの正確さを壊す経路がもう 1 つある**ことに変わりはない
  （`SessionStart` での 0 戻しと合わせて 2 つ。ADR-0057）
- **目に見える症状が消えた。** 以前は読めなかったときに stderr へ出ていた。取りこぼしは
  何も言わずに起きる。直した側が静かになったぶん、残った側も静かになった
- **電源断は守らない。** 差し替えの前に `fsync` をしていないので、ディスクへ届く順は
  ファイルシステム任せ。控えは失っても取り直せるものなので、そこまでの値段は払わない
- **一時ファイルの名前が元より 20 文字ほど長い。** Windows の 260 文字の上限ぎりぎりの
  行き先では、以前は書けたものが書けないことがある
- **残骸の種類が 1 つ増えた。** 落ちて残った `.part.json` は、`ctxfile.forget` が掃く
  `once-` と `approved-` の控えなら掃除されるが、`post` の `seen` / `turn` には掃除機構が無い
- **マーカーと承認済みチケットは素の書き方のまま。** read-modify-write ではないのでレースは
  無いが、途中で落ちれば壊れたものが残る。`ready.json` が中途半端に残ると
  「Draft をまだ外していない」に静かに戻る。ここは別に扱う

## 採らなかった案

- **ファイルロック。** 本当に取りこぼしまで直る。採らなかったのは上の 4 つの理由から。
  数えを正確に使いたい機能が出てきたら、そのときに値段を払う
- **差し替えだけ（読みの打ち直しを入れない）。** 変更が 1 か所で済む。採らなかったのは、
  Windows で失敗の形が変わるだけで症状が消えなかったため（実測）
- **読めなかったときも書き戻す（従来どおり）。** 分岐が増えない。採らなかったのは、
  打ち直しが尽きた回に、覚えていたぶんを空で潰すため（実測で 50 → 1）
- **`fsync` を入れる。** 電源断にも耐える。採らなかったのは、控えが失っても取り直せるもので、
  全ツール呼び出しの経路に同期の待ちを足す値段に見合わないため
- **一時ファイルの名前を固定にする**（`<行き先>.part`）。`selfguard` の前例と揃う。
  採らなかったのは、同時に書く 2 つが同じ一時ファイルを取り合い、書きかけを差し替えることに
  なるため。直そうとした事故が形を変えて戻る
