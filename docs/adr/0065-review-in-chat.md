# ADR-0065: レビューはマージリクエストのほかに、このセッションでも受ける

状態: 採用

旧番号: 0051（番号が 2 つの決定に付いていたので動かした。issue #98）

## 状況

フェーズの種類の `review` は `none` と `mr` の 2 値だった。ユーザが見る手段はマージリクエスト 1 本で、
そこにはホストの認証（`GITHUB_TOKEN` / `GITLAB_TOKEN` か gh / glab）が要る。

その結果、ワークスペースの中で完結する作業の進め方が 2 つに分かれていた。`review: none` で
チケットとフェーズの範囲は適用するがユーザが見る段で止めない（ユーザが見る場所が無い）か、`review: mr` で
ホストまで出るか。前者は止まらないので「ユーザが見る」を挟めず、後者は小さな作業に認証と
マージリクエストを要求する。2026-09-16。

## 決定

`review` を 3 値にする（`none` / `chat` / `mr`）。`chat` は「このセッションでユーザが差分を見る」。
ホストへは出ない。

| 決めたこと | なぜ |
|---|---|
| 止める段は `mr` と同じに置く | 「ユーザが見る」を挟むのがその段の仕事で、見る場所は関係ない |
| 開けるのは端末から打つ `ccnavi --reviewed <N> --chat` | ユーザの合意の経路を既存の 2 つの守り（標準入力が端末であること・`DENY_TICKET_APPROVAL_CLI`）にそのまま乗せる。`--reviewed` は既にその正規表現に入っているので、新しい表記を足さない |
| `--chat` は種類が `chat` と宣言したフェーズにしか当たらない | 当たると、`mr` と宣言したフェーズを安い経路で通せる。宣言を緩める手段は作らない |
| 見る場所は `none` < `chat` < `mr` の厳しい側が勝つ | 延期を引き受けたフェーズが、引き受けた分より緩い場所で見ることを防ぐ |
| 子の `human_review.required` と実績のリスクは、`none` を `chat` へ上げるだけ | どちらも「要る」としか言わず、場所を言わない。場所を言う宣言（種類と計画の項）を上書きしない |
| 実績のリスクが高いフェーズではマージリクエストを勧めるが、強制しない | 強制すると、ローカルで回している作業が大きくなった時点で認証が要るようになる。勧めたうえで、選ぶのは端末に座っているユーザ。選んだ結果はマーカーに残す |
| `kind: feedback` の種類は `chat` も許す（`none` は引き続き許さない） | フィードバック対応の結果をユーザが見ない手段は作らないが、見る場所までホストに縛る理由は無い |
| 親を閉じたとき `phases/<親>/closed.json` を置く | 提案（`wip/`）は統合先へ戻す前に消える。マージリクエストを作らない進め方では、締めた事実の残る先がここしか無い |

## 理由

ユーザの合意を確かめる材料は、もともとマージリクエストの中身ではなく、**打ったユーザが端末に居ること**
だった（`--reviewed --accept-unresolved` がそうなっている）。その材料はマージリクエストが無くても揃うので、
`chat` は既存の経路の引数違いで済む。sh は 1 行も変わらず、実行ファイルがネットワークに
出ないという境界（ADR-0028）にも触れない。

## 得たもの・失ったもの

- 得たもの: ホストの認証もマージリクエストも無しに、フェーズの停止とユーザの確認が働く。
  「チケットは起こすが外へは出さない」進め方が、止まる形で持てる
- 失ったもの: 「ユーザが見た」の証拠が薄くなる。`mr` なら未解決スレッドの数という外形が残り、
  マージリクエストと依頼の記録を照らし合わせる（ADR-0031）。`chat` に照らし合わせる相手は無く、残るのは
  「端末から打たれた」ことと、ユーザが y と答えたことだけ
- 失ったもの: レビューの中身が残らない。何を見て良しとしたかはマーカーの外に出ない
- 失ったもの: 変更要求（REQ-TKT-19 の「このままではマージしない」）に当たる状態が `chat` に無い。
  ユーザが「まだ駄目」と答えたことは、次の呼び出しには残らない
- 失ったもの: 実績のリスクが高いフェーズが、ホストに何も残さずに閉じられるようになった。
  ADR-0027 の「測る」は残るが、測った結果を反映させるのは勧めるところまでになる。緩めた事実は
  `reviewed.json` の `recommended` に残す

## 採らなかった案

- **リスクが高ければ `mr` へ強制的に上げる。** 安全側だが、ローカルで回している作業が
  途中で認証が要るようになる。止まる場所を作ることと、どこで見るかを決めることは別の問題で、
  後者はユーザが決められる
- **計画の項（`plan:` の `review:`）でも `chat` を書けるようにする。** 項は `mr` に強めるだけ、
  という不変条件を崩す。緩める手段は種類（ユーザが持つ設定）の側にだけ置く
- **`chat` 用の副命令（`ccnavi review chat <N>`）を足す。** `DENY_TICKET_APPROVAL_CLI` の
  一覧に足し忘れると、エージェントが自分で先へ進められる。既にある `--reviewed` に
  フラグを足すほうが穴を開けない
