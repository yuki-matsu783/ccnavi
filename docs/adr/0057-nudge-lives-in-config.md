# ADR-0057: 勧告の文面としきい値は設定が持ち、実行ファイルは数えるところだけを持つ

状態: 採用

## 状況

編集が積み重なっても、レビューを入れるきっかけが無かった。`PostToolUse` の hook は `lint-py.sh` だけで、
これは編集したファイル 1 本の整形と検査しかしない。複数ファイルにまたがった変更が、
このリポジトリに溜めてきた決まり（`CLAUDE.md`・`.ccnavi/common/rules.yml`・`docs/adr/` 53 枚・
`CONTEXT.md`）に沿っているかの確認は、人が「そろそろ見て」と言うまで入らなかった。

溜めた決まりは、書いた本人が次に読むとは限らない場所にある。ADR は 53 枚あり、全部を毎回の編集で
思い出せる量ではない。照らし合わせは、別の文脈を持った読み手に任せるのが向いている。

一方、モデルへ文を渡す頻度は 2 通りしかなかった。`additionalContext` は当たるたび、`additionalContextOnce` は
最初の 1 回だけ。「編集が 5 件たまったところで 1 度だけ言う」は、どちらでも書けなかった。

## 決定

- **しきい値と勧告の文面は設定（`rules.yml`）が持つ。** ルールに `every: N` を足し、
  文面は `additionalContext` に書く
- **実行ファイルが持つのは数えるところだけ。** `ctxfile.py` の控えを「当たったか」から
  「何回当たったか」へ広げる。勧告の文言も、何件で勧告を出すかも、実行ファイルには入れない
- **`every` で決まるのは「渡す回」。** `additionalContext` は渡す回のたび、
  `additionalContextOnce` は渡す回の最初の 1 回に文を渡す。キーごとの例外を覚えなくてよい形にする
- **数えるのは「そのルールが当たった回数」。** 変わったファイルの本数ではない

## 理由

観点は後から足したくなる種類のものだった。「ADR を挙げる」「決まりのほうが古い可能性も見る」は
どちらも、書いてみて足りないと分かって足した項目で、そのたびに実行ファイルを作り直すのは割に合わない。
`rules.yml` なら人が写すだけで変わる。

配布先ごとに変えられることも要る。ADR の置き場も `CLAUDE.md` の有無もリポジトリで違うので、
「`docs/adr/` を読め」と実行ファイルに組み込むと、そうでないリポジトリでは事実と合わなくなる。

新しい仕組みは要らなかった。控えも、モデルへ文を返す経路も、hook の登録も既にあった。
`once` の数え方を 1 から N へ広げるだけで済む。

## 得たもの・失ったもの

**得たもの**

- 頻度を 1 本の軸で表せるようになった。`every` が渡す回を決め、2 つのキーがそのうち「たびに」か「最初の 1 回」かを選ぶ
- 「たまったところで 1 度だけ言う」が書けるようになった（`every: 5` + `additionalContextOnce`）
- `every` は `additionalContext` を持つルールなら何にでも使える。今回の用途だけのキーにならない

**失ったもの**

- **数えた回数が `SessionStart` で 0 に戻る。** 回数は「1 度だけ渡す文」の控えに一緒に記録していて、
  その記憶は起動・再開・compact の後に捨てられる（`ctxfile.forget`）。文脈が変われば
  「この文脈で何回目か」も無くなるので筋は通っているが、回数はそのぶん正確でなくなる。
  既にある記憶を流用した（「新しい仕組みは要らなかった」）ことの直接の代償。compact が
  いつ起きるかは ccnavi から見えないので、ずれの大きさはここでは分からない
- **ずれる向きが、どちらのキーに書くかで逆になる。** 回数は 0 に戻ることはあっても先へ進むことはないので、
  `additionalContext` + `every` では届くのが遅れる（0 に戻ることが続けば一度も届かない）。
  一方、この決定の主眼である `additionalContextOnce` + `every`（たまったところで 1 度だけ言う）では
  0 に戻るたびに「渡す回の最初の 1 回」がまた来るので、セッション全体では 1 度より多く届く。
  どちらにしても、この決定のいちばん肝心な点は長いセッションでは守りきれない
- **数え方が不正確なことが、そのまま `every` の意味になってしまった。** 同じファイルを 5 回直しても 5 と数える。
  `post.py` が見ている git の実際の変更のほうが正確だが、そちらを使うには実行ファイルに組み込むことになる。
  あとから直すには `every` の意味を変えることになる
- **キー名だけでは「何が N 回ごとか」が分からない。** `every: 5` は「5 秒ごと」とも「5 ファイルごと」とも
  読める。「当たった回数」であることは文書を読んで覚える
- **`Once` の読み方が 2 通りになった。** `every` の無いルールでは「当たった最初の 1 回」、
  あるルールでは「渡す回の最初の 1 回」。同じキーでも、`every` があるかどうかで文が届く回が違うので、文書でどちらか一方の読み方にそろえられない
- **強制力が無い。** `exit 2` と違い hook エラー通知が出ないので、モデルが無視しても画面に何も出ない。
  勧告に従ったかどうかを ccnavi は知ることができない
- **ルールのスキーマが 1 つ増えた。** 配布先すべてに入る。使わなければ無害だが、覚えることと
  `--lint` の検査が増える
- **控えのファイル形式が変わった。** `once-*.json` が配列から辞書になる。古い形を読む処理は残すが、
  読めなかったときは「覚えていない」とみなし、毎回渡す
- **シェルやビルドが書いたぶんを数えない。** `match` がツール名なので、`Bash` を書かない限り当たらない

## 採らなかった案

- **`post.py` に組み込む。** git が返した実際の変更を数えるので「同じファイルへの 5 回」を正しく
  1 本と数えられる。採らなかったのは、しきい値と観点が実行ファイルに固定され、配布先ごとに
  変えられなくなるため。観点を足すたびにビルドが要る
- **専用の hook スクリプト（`.claude/hooks/review-nudge.sh`）。** ccnavi に触らずに済む。
  採らなかったのは、`.claude/hooks/` が保護済みで人が写す必要があり、しかも数えるのが
  `Write`/`Edit` の呼び出しだけになるため
- **折衷（ccnavi が変わったファイルの本数を数え、文面は `rules.yml` が持つ）。** `every` の
  数え方の不正確さを補える。採らなかったのは、`every:` の意味が「当たった回数」ではなくなり、
  `every:` の定義から決め直すことになるため
- **頻度をキー名で表す（`additionalContextEvery` / `additionalContextEveryNth`）。** N 回ごとの頻度がどの文に適用されるかが
  キー名で分かるので、決まりを覚えなくてよい。採らなかったのは、同じ系統のキー名がさらに長くなり、
  `additionalContextOnceFile` と並べたときの読みにくさが増すため
- **`Stop` で数える。** ターンの終わりに 1 回だけ数える。書きかけの途中には届かないので、見てもらう変更と今の状態がずれない。採らなかったのは、
  ルールの条件ではなく hook の話になり、`rules.yml` から外れるため
- **`exit 2` で差し戻す。** 勧告に留めた。止めるほどの確度が無く、`additionalContext` は
  hook エラーにならない
