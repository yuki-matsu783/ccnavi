# ADR-0057: 勧告の文面としきい値は設定が持ち、実行ファイルは数えるところだけを持つ

状態: 採用

## 状況

編集が積み上がってもレビューが入る契機が無かった。`PostToolUse` の hook は `lint-py.sh` だけで、
これは編集したファイル 1 本の整形と検査しか見ない。複数ファイルにまたがった変更が、
このリポジトリに溜めてきた決まり（`CLAUDE.md`・`.ccnavi/common/rules.yml`・`docs/adr/` 53 枚・
`CONTEXT.md`）に沿っているかを見る目は、人が「そろそろ見て」と言うまで入らなかった。

溜めた決まりは、書いた本人が次に読むとは限らない場所にある。ADR は 53 枚あり、全部を毎回の編集で
思い出せる量ではない。突き合わせは、別の文脈を持った読み手にやらせるのが向いている。

一方、渡す頻度は 2 つしかなかった。`additionalContext` は当たるたび、`additionalContextOnce` は
最初の 1 回だけ。「編集が 5 件たまったところで 1 度だけ言う」は、どちらでも書けなかった。

## 決定

- **しきい値と勧告の文面は設定（`rules.yml`）が持つ。** ルールに `every: N` を足し、
  文面は `additionalContext` に書く
- **実行ファイルが持つのは数えるところだけ。** `ctxfile.py` の控えを「当たったか」から
  「何回当たったか」へ広げる。勧告の文言も、何件で声を掛けるかも、実行ファイルには入れない
- **`every` が刻むのは「渡す回」。** `additionalContext` は渡す回のたび、
  `additionalContextOnce` は渡す回の最初の 1 回。掛かる先の例外を覚えなくてよい形にする
- **数えるのは「そのルールが当たった回数」。** 変わったファイルの本数ではない

## 理由

観点は後から足したくなる種類のものだった。「ADR を挙げる」「決まりのほうが古い可能性も見る」は
どちらも、書いてみて足りないと分かって足した項目で、そのたびに実行ファイルを作り直すのは割に合わない。
`rules.yml` なら人が写すだけで変わる。

配布先ごとに変えられることも要る。ADR の置き場も `CLAUDE.md` の有無もリポジトリで違うので、
「`docs/adr/` を読め」と実行ファイルに焼き込むと、そうでないリポジトリで嘘になる。

新しい仕組みは要らなかった。控えも、モデルへ文を返す経路も、hook の登録も既にあった。
`once` の数えを 1 から N へ広げるだけで済む。

## 得たもの・失ったもの

**得たもの**

- 頻度が 1 本の軸に並んだ。`every` が渡す回を刻み、2 つの文がその上で「たびに」と「最初の 1 回」を選ぶ
- 「たまったところで 1 度だけ言う」が書けるようになった（`every: 5` + `additionalContextOnce`）
- `every` は `additionalContext` を持つルールなら何にでも使える。今回の用途だけの欄にならない

**失ったもの**

- **刻みが `SessionStart` で 0 に戻る。** 数えは「1 度だけ渡す文」の控えに相乗りしていて、
  その記憶は起動・再開・compact の後に捨てられる（`ctxfile.forget`）。文脈が変われば
  「この文脈で何回目か」も無くなるので筋は通っているが、刻みはそのぶん正確でなくなる。
  既にある記憶を流用した（「新しい仕組みは要らなかった」）ことの直接の代償。compact が
  いつ起きるかは ccnavi から見えないので、ずれの大きさはここでは分からない
- **ずれる向きが書き方で逆になる。** 数えは進みを捨てるだけで先へは進まないので、
  `additionalContext` + `every` では届くのが遅れる（戻りが続けば一度も届かない）。
  一方、この決定の主眼である `additionalContextOnce` + `every`（たまったところで 1 度だけ言う）では
  「渡す回の最初の 1 回」が改めて成り立つので、セッション全体では 1 度より多く届く。
  どちらにしても、決定の核は長いセッションでは守りきれない
- **数えの不正確さが欄の定義になった。** 同じファイルを 5 回直しても 5 と数える。
  `post.py` が見ている git の実際の変更のほうが正確だが、そちらは実行ファイルに焼き込む形になる。
  あとから直すには欄の意味を変えることになる
- **欄名だけでは「何が N 回ごとか」が分からない。** `every: 5` は「5 秒ごと」とも「5 ファイルごと」とも
  読める。「当たった回数」であることは文書で覚える
- **`Once` の読み方が 2 通りになった。** `every` の無いルールでは「当たった最初の 1 回」、
  あるルールでは「渡す回の最初の 1 回」。同じ欄でも、置かれ方によって文が届く回が違うので、文書で一方に寄せられない
- **強制力が無い。** `exit 2` と違い hook エラー通知が出ないので、モデルが無視しても画面に何も出ない。
  走ったかどうかを ccnavi は知れない
- **ルールのスキーマが 1 つ増えた。** 配布先すべてに届く。使わなければ無害だが、覚えることと
  `--lint` の検査が増える
- **控えのファイル形式が変わった。** `once-*.json` が配列から辞書になる。古い形を読む道は残すが、
  読めなかったときは「覚えていない」＝毎回渡す側になる
- **シェルやビルドが書いたぶんを数えない。** `match` がツール名なので、`Bash` を書かない限り当たらない

## 採らなかった案

- **`post.py` に焼き込む。** git が返した実際の変更を数えるので「同じファイルへの 5 回」を正しく
  1 本と数えられる。採らなかったのは、しきい値と観点が実行ファイルに固定され、配布先ごとに
  変えられなくなるため。観点を足すたびにビルドが要る
- **専用の hook スクリプト（`.claude/hooks/review-nudge.sh`）。** ccnavi に触らずに済む。
  採らなかったのは、`.claude/hooks/` が保護済みで人が写す必要があり、しかも数えるのが
  `Write`/`Edit` の呼び出しだけになるため
- **折衷（ccnavi が変わったファイルの本数を数え、文面は `rules.yml` が持つ）。** `every` の
  不正確さを埋める。採らなかったのは、`every:` の意味が「当たった回数」ではなくなり、
  欄の定義から決め直しになるため
- **欄名で言い切る（`additionalContextEvery` / `additionalContextEveryNth`）。** 掛かる先が欄名で
  決まるので決まりを覚えなくてよい。採らなかったのは、家族の欄名がさらに伸び、
  `additionalContextOnceFile` と並べたときの読みにくさが増すため
- **`Stop` で数える。** ターンの終わりに 1 回だけ。対象と現状がズレない。採らなかったのは、
  ルールの条件ではなく hook の話になり、`rules.yml` から外れるため
- **`exit 2` で差し戻す。** 勧告に留めた。止めるほどの確度が無く、`additionalContext` は
  hook エラーにならない
