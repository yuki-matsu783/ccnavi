# ADR-0085: 子チケットにフローを持たせ、着手中は書き換えを止める

状態: 採用

追記（2026-09-25）: レビューを受けて、フローの置き場を `references/<子>/flow.json`（`flow:` で指せる）から
承認済みの領域の `.ccnavi/approved/flows/<子>.json`（固定）へ移した（利用者の決定）。決定の表のうち置き場・`flow:`・
書くのは人・ロックの行は、下の「レビューを受けて改めたこと」で置き換えた。元の行は経緯として残す。
2 回目のレビューで、読むファイルの種類・読む置き場・着手のあとの書き換えの知らせ・親のツリーからの案内・
承認での運び方・名乗りの真似の見分け方を改めた（「レビュー 2 回目で改めたこと」）。

## 状況

2026-09-25。フェーズの管理を細かくしたい。ただし HITL の流れ（承認・フェーズ・レビュー）は変えたくない。
人が見る点を増やさずに、子チケット 1 本の中の段取り（調べる → 利用者に聞く → 入れ子で深掘りする …）を
書き、担当のサブエージェントがそれに沿って進むようにしたい。

段取りの書き方には、CC Workflow Studio（breaking-brake/cc-wf-studio）の `workflow.json`
（`.vscode/workflows/*.json`）が既にあり、エディタで絵として書ける。ccnavi は MIT、あちらは AGPL。

サブエージェントには 3 つの制約がある（付録 C、2026-09-25 実測・文書）。AskUserQuestion は全部の
サブエージェントから外される。入れ子の起動は上限（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`、既定 3、
クラウドの環境は 1）に達すると Agent ツールが渡らない。自動 compact で `SubagentStart` の文が消えうる。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| （改めた）子の frontmatter に **`flow:`**。省けば既定の `references/<子>/flow.json` | 欄を書き忘れても置き場で見つかる。子ごとに置き場が分かれ、ロックの単位と一致する | 親に 1 本持たせて子の番号で引く。子ごとのロックが書けない |
| 置き場は**チケットと同じツリー**のルートからの相対。プロジェクトのチケットならプロジェクトの側（改めた後もツリーは同じ。その承認済みの領域の下） | チケットと同じ git に乗り、親のブランチで他の機械へ届く（設計 9.2 と同じ理屈）。子のワークツリーにも写る | ワークスペースルートに固定。プロジェクトのチケットだけが別の git に乗り、clone で続きができない |
| （改めた）`flow:` は `references/` の下だけ。外れた値（`..`・絶対パス・`~`・`$`・外）は **warn で捨てて既定を見る** | ロックの検査を `references/` の下の書き込みに限れ、他の書き込みで承認済みチケットを走査しない。error にすると、置き場を人が動かした承認済みチケットが読めなくなり、範囲ごと効かなくなる（緩む） | どこでも指せる。書き込みのたびに走査が要る |
| 形は `workflow.json` と**互換**にし、コードは使わない。**知らない種類も落とさない** | 絵で書ける道具をそのまま使える。ライセンスが混ざらない。あちらが種類を足しても壊れない | 自前の形。書く道具が無い |
| フローは**承認の対象にしない**（指紋にも入れない）。承認されるのは `flow:` の値まで（改めた後は `flow:` が無く、承認に関わるものは無い） | 段取りは作業の中身で、人の判断の点を増やさない（ADR-0030）。着手の前に直せる | 承認画面に出して指紋に入れる。直すたびに承認をやり直すことになる |

| `SubagentStart` がフローのファイルと `flow:` を名指しし、手順を 1 ノード 1 行で並べる（改めた後はファイルだけを名指しする。置き場が子の識別子で決まる） | JSON を読まずに追える。compact で消えても、ファイルと欄から辿り直せる。消えた文は次の起動（再開）で入れ直される（文書） | ファイルを指すだけ |
| `askUserQuestion` のノードでは**止まってメインに返す** | サブエージェントは利用者に聞けない。メインが聞いて同じサブエージェントを再開させる（docs/claude/decisions.md の役割分担と同じ） | 聞かずに自分で決める。利用者の判断が抜ける |
| `subAgent` のノードは、Agent ツールがあれば入れ子で起こし、プロンプトに**担当の子・ワークツリー・範囲**を必ず書かせる。**無ければ止まってメインに返し**、起動してほしい種類・プロンプト・担当を添える | 孫の hook の `cwd` はメインの `cwd` なので、hook からは孫の担当が決められない（下の「残る弱点」）。上限 1 の環境では Agent ツールが渡らず、ハングせず終わる（実測）ので、自分でこなさせると入れ子の段取りが黙って潰れる | Agent が無ければ自分でこなす（最初の案。実測を受けて改めた） |
| 入れ子のサブエージェントが差し戻しを無視して終わったら、その知らせを `systemMessage` にも載せる | 入れ子の起動では、知らせは起動した子の `additionalContext` にしか届かず、人にもメインにも見えない | 載せない |
| （改めた）**フローは人がボードのエディタで書く。エージェントには書かせない**（利用者の決定）。親の範囲に `references/` を入れない | 段取りは人が決めて渡すもの。範囲に入れなければ、エージェントの `Write` / `Edit` は範囲の外として止まるので、判定を足しも緩めもせずに運用が守られる | エージェントにも書かせ、親の範囲に `references/` を入れる。人が見ていない手順が作業の前に書き換わりうる |
| `PreCompact` / `PostCompact` でフローを入れ直す hook は足さない | 文書上、どちらも `additionalContext` を受けると書かれておらず、`systemMessage` は捨てられる。効くと書かれていない経路に頼らない | 登録を足す。共有の設定（`.claude/settings.json`）を変えることになり、効くかも分からない |

## レビューを受けて改めたこと（2026-09-25）

2 本の敵対的なレビューが、`references/` の置き場に 2 つの問題を見つけた（どちらも再現した）。

- **H1** 人がボードで保存したフロー（hook を通らない書き込み）が、次のエージェントの呼び出しの実行後の監視で、
  範囲の外の変更（`POST_TICKET_SCOPE`、戻し方に `git clean -f`）として咎められた。運用どおり親の範囲に
  `references/` を入れないほど、人の手順書をエージェントが消しにいく形になる
- **M1** 「エージェントには書かせない」は運用（親の範囲に `references/` を入れない）でしか守られていなかった。
  範囲に `references/` を入れた親や、範囲が `*` の親では、エージェントがフローを書けた

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| 置き場は**承認済みの領域**の `<承認済みチケットの置き場>/flows/<子>.json`（既定 `.ccnavi/approved/flows/<子>.json`）に**固定**。置き場を持つツリーは承認済みチケットが在るツリー | 承認済みの領域は、どのツリー（ワークスペースルート・親と子のワークツリー・`projects/<名前>/`）でも組み込みの守り `builtin-guard-project-home`（`*/<ccnavi ディレクトリ>/*` への `Write` / `Edit` / `NotebookEdit`）が止め、シェルからは `builtin-guard-setting-files` が止める。「フローは人が書く」が判定で守られる（M1）。承認済みチケットと同じ守りで、足しも緩めもしない。実行後の監視は承認済みの領域を範囲の外として咎めず、frontmatter の無いファイルは副命令の書き込みとして外すので、人の保存が咎められない（H1）。運び方も承認済みチケットと同じ `ccnavi-push-approved.sh` | `references/` のまま、範囲の外として外す場所に足す。判定が緩む向きで、エージェントが書けることも変わらない |
| **`flow:` の欄はやめる**。書いてあれば warn で名指しして読み飛ばす | 置き場が子の識別子で決まるので、欄が要らない。パスを書かせないので、行き先を外へ向ける綴り（`..`・リンク）を読む面が消える。error にすると承認済みチケットが読めなくなり、範囲ごと効かなくなる（緩む） | 欄を残して承認済みの領域の下だけを指させる。検査が残り、置き場が 2 通りになる |
| ロック（`DENY_TICKET_FLOW_LOCKED`）は残す。覆うのはその子の `flows/<子>.json`。綴りは解いた先・解く前・ディレクトリだけ解いたものの 3 通りに当て、着手中かは識別子で畳む前の写しの全部で見る | エージェントの書き込みは承認済みの領域の守りでも止まるが、その守りは `CCNAVI_GUARD_CORE_FILES=disable` で切れる。ロックはそれと独立に効き、止めた理由（着手中）を名指しする。3 通りの綴りは、置き場を指すリンクや、リンクに差し替えたフローを越えさせないため（H2）。畳む前の写しを見るのは、写しの 1 本だけが着手中でも止めるため（止める向きだけ） | ロックを外して守りの 1 本に畳む。守りを切った設定で手順書が作業中に変わる |
| **リンクは読まない・書かない**。フローのファイルか、ツリーのルートからそこまでの途中がシンボリックリンクなら、`SubagentStart` は読まずにそう言い、ボードは読まないし書かない。ボードの保存は同じディレクトリの一時ファイルを `wx` で書いて `rename` で入れ替える | リンクの先は承認済みの領域の外（エージェントが書ける場所）かもしれず、そこを人の手順書として渡すことになる（H2）。入れ替えは途中で落ちても半端なファイルを残さず、行き先のリンクを辿らない | リンクを解いて先を確かめる。解いた先の検査と読む瞬間の間に差し替えられる |
| **壊れたフローで落ちない**。読む・並べるのどこでも例外を外に出さず、`SubagentStart` はフローの案内を例外ごと 1 行に落として子の一覧と範囲を渡す。型を確かめ（`connections` などは並び、項目は辞書）、`fromPort` の番号は ASCII の数字だけ読む | 型の崩れた 1 本（`"connections": 5` など）で、`SubagentStart` の文が丸ごと消えていた（H3） | 形を承認で検査する。フローは承認の対象ではない |
| 分岐の出口の名前は、出口が項目の `id` と**ちょうど同じ**か `branch-<番号>` のときだけ当てる。出口は番号の順 | 部分一致（`b` が `branch-1` に当たる）で名前を取り違えていた（M2）。`branch-10` が `branch-2` の前に並んでいた（L5）。ボードの線の言葉も同じ読み方に揃えた（L7） | 末尾の数字だけで読む |
| 大きさの上限。ファイル 256KB、1 ノードの項目 10 件、子 1 本の手順の文 4000 文字、`SubagentStart` 全体でフローに 12000 文字。並べる順は線の数に比例する手間で決める | 大きなフローで文脈を埋め、並べるのに秒単位かかっていた（M3） | 上限なし |
| フローの文は**データとして囲って**渡す。1 行に畳み、改行と制御文字を落とし、`[ccnavi]` は全角の括弧に置き換える。パスや値を文脈に載せるときも改行と制御文字を落とす | フローの文が ccnavi の知らせに見える行を作れた（M3、L6） | そのまま渡す |
| 案内のロックの言葉を分ける。着手中は「終わるまで書き換えられない」、着手の前は「着手すると書き換えられなくなる」 | 着手の前にも「着手中は書き換えられない（ロック）」と言っていた（L2） | 1 通り |

ボードの保存は、押した時点で実行ファイルに聞き直してから書く。聞き直してから書くまでの間に子が着手されると、
着手の直後に書き込みが入りうる（L4。1 回の保存の中の短い間）。塞ぐには実行ファイルの側に錠の置き場が要るので、
狭めるだけにした。

## レビュー 2 回目で改めたこと（2026-09-25）

2 回目の敵対的なレビューが、読み方と運び方に次を見つけた（どれも再現した）。直し方は利用者が承認した。
判定を緩めたのは lint の警告 1 つだけで、それも利用者の決定（表の最後の行）。ほかは締める向きか、知らせを足す向き。

| 見つかったこと | 決めたこと | なぜ | 採らなかった側 |
|---|---|---|---|
| **H-1** 着手のあとにフローを名前付きパイプ（FIFO）に差し替えると、`SubagentStart` が開いたまま固まる | 読むのは**ふつうのファイルだけ**。`lstat` で `S_ISREG` を確かめ、`O_NONBLOCK \| O_NOFOLLOW` で開き（無い OS では 0）、開いたものを `fstat` でもう一度確かめる（ふつうのファイルで、`lstat` と同じ inode）。ボードも同じ | 開いてから待つ形を 1 つも残さない。確かめてから開くまでの差し替えも、開いたものを確かめ直せば読まない | 時間で打ち切る。hook の中で待ち時間を持つことになり、固まる形は残る |
| **M-1** 範囲の中（`wip/` など）にフローのハードリンクを作ると、別名への `Write` で手順書を書き換えられた。綴りに置き場が出ないのでロックも組み込みの守りも当たらない | **名前が 2 つ以上のフローは読まない**（シンボリックリンクと同じく 1 行で言う）。ボードも読まないし書かない。ロックは綴りの照合に加えて、書き込み先が在って名前が 2 つ以上のときだけ、着手中の子のフローと (デバイス, inode) を比べて止める | 読まなければ別名から書いた中身は手順書にならない。inode の比較は止める向きだけで、名前が 1 つのふつうのファイルには何も読まない（走査の代金を払わない） | ハードリンクを作る `ln` を止める。行き先を追えない形が残り、判定が増える |
| **M-2** 行き先を追えないシェルの書き込み（変数に入れた綴り・スクリプト）は止まらない（前から「塞げないもの」）。子のワークツリーの写しも読んでいたので、そこへ書けば手順書になった | (a) 読むのは**権威のツリー**（承認済みチケットが在るツリー）の版だけ。子のワークツリーの写しは読まない。(b) 着手（`ccnavi-ticket.sh start`）のときにフローの指紋（sha256。無ければ「無い」、読めなければその理由）を `phases/<親>/<子>.flow.json` に控え、`SubagentStart` と `SubagentStop` が**いまの指紋と違えば知らせる**（`NOTICE_TICKET_FLOW_CHANGED`「着手後にフローが書き換わった」。`additionalContext` と `systemMessage` の両方）。止めない。(c) 案内は「エージェントは書けない」と言わず、人が持つもので編集しないこと、書き換わったら知らせることを言う | 塞げないものは、起きたら人に見えるようにする。控えは子の記録（`.risk.json`）と同じ置き場で、承認済みの領域なのでエージェントは書けず、親のブランチに乗る。知らせるだけなので何も通らなくならない。「書けない」は事実と違い、書けた形を見つけたエージェントが迷う | 違えば止める。人が着手のあとに直したい場面（取り消してやり直す前）まで止まる。控えをセッションの `state/` に置く。機械をまたげず、別のセッションが着手した子を見られない |
| **M-4** 親のツリーからの起動（入れ子の孫も cwd は親のツリー）で、全部の子の手順を並べていた。どの子の担当かは hook から決められず、別の子の手順に従いうる | 手順を並べるのは、起動の cwd が**その子のワークツリー**で子が 1 本に決まるときだけ。親のツリーからは各子のフローのパスを 1 行ずつと、「自分の担当の子チケットのフローだけを読んで従う。他の子のフローには従わない」を言う | 担当を知っているのは起動した側（プロンプト）で、パスがあれば辿れる。並べた手順が別の子のものに化けない | 全部並べて見出しで分ける。長い文の中で取り違える |
| **M-3** 承認の前に、ボードが示す置き場（提案が在るツリー）へ保存したフローが、承認で子が親のワークツリーへ動くと元のツリーに残って読まれなくなった | 承認（人の操作）で、子の提案のツリーの `flows/<子>.json` を承認済みチケットのツリーの `flows/` へ**動かす**。行き先に違う中身が在れば上書きせず、そう言って元も残す。同じ中身なら元を消す。リンク・ふつうのファイルでないもの・ハードリンクは運ばない | ボードの示す置き場（承認の前は提案のツリー、後は承認済みチケットのツリー）と読む置き場が、承認の前後どちらでも一致する | ボードが承認の前から行き先のツリーを示す。行き先は承認のときに決まる（`home_dir`）ので、前もって決めると外れうる |

| **L-b** 承認済みの置き場の設定が `./.ccnavi/approved`・`.ccnavi//approved`・`x/../.ccnavi/approved` だと、畳んだ綴りに当てるロックが外れた | 置き場の綴りを畳んでから当てる（`posixpath.normpath`）。ツリーの外（`../`）を指す置き場は、どのプロジェクトの子でも止める。Windows で同じファイルに届く名前（末尾の `.` と空白、`:` から後ろの代替データストリーム）も畳む | 止める向きだけ。`ticket._under`（範囲を当てない場所の判定）は、畳むと外す場所が広がる向きなので変えない | ― |
| **L-c** パスの途中に全体の `lower()` で長さが変わる字（`İ`）があると、大文字小文字を畳まない綴りに落ち、`I0001-01.JSON` でロックが外れた | 1 字ずつ畳み、畳むと長さの変わる字だけを残す（長さを変えない）。名前の比べ合わせは `casefold` でも見る | 位置で切り出すので、長さが変わると読みがずれる | ― |
| **L-e** ボードは読み書きに大きさの上限が無く、保存が途中で落ちると一時ファイルが残りえ、それを `ccnavi-push-approved.sh` がコミットしえた。線の言葉が真偽値・数の値を実行ファイルと違う綴りで読んだ | ボードも 256KB まで（読むのも書くのも）。一時ファイルは落ちても消す（`finally`）。`ccnavi-push-approved.sh` は `flows/.*.tmp` を数えず運ばない（pathspec の `:(exclude)`）。線の言葉は真偽値を空、数は整数なら整数の綴り（`1.0` は `1`）で読む。実行ファイルの側も同じに揃えた | 半端な中身を人の手順書としてコミットしない | ― |
| lint が、ワークツリーの承認済みの領域のファイル（承認済みチケット・マーカー・フロー）を「ワークツリーにしかない。統合されるまで効かない」と warn で言っていた | **承認済みの領域の下は数えない**（利用者の決定。報告を減らす唯一の変更）。ほかの層のファイルは今までどおり言う | 承認済みの領域は親のワークツリーの版が読まれるので、「効かない」は誤った案内になる | そのまま言う。人が正しいものを消しにいく |

## 得たもの・失ったもの

- 得たもの: 人の判断の点を増やさずに、子の中の段取りを絵で書いて渡せる。作業中に手順が変わらない。
  入れ子の上限が 1 の環境でも、段取りが黙って潰れずメインへ戻る
- 失ったもの: 着手中は手順を直せない（直すなら終わってから、か次の子で）。フローは人がボードのエディタ
  （VS Code 拡張のフロー編集画面）で書き、エージェントには書かせない（利用者の決定）。承認済みの領域の守りが
  止めるので、エージェントが段取りを書き起こして人に渡すことはできない（書くなら人がエディタで写す）。
  置き場は子の識別子で決まり、別の場所を指せない。人は承認済みチケットと同じくフローもコミットする
  （`ccnavi-push-approved.sh`）。Bash から書く形は、承認済みの領域の綴りが出れば組み込みが止めるが、
  行き先を追えない形は止まらない（範囲と同じ）。止まらなかった書き換えは、着手のあとなら指紋の違いで知らせる
  （レビュー 2 回目）。着手の前の書き換えは知らせない（人が直す時期と見分けられない）
- 残る弱点: 孫の `cwd` はメインの `cwd` なので、`SubagentStart` は親の全部の子を並べ、`SubagentStop` は兄弟の
  子の変更でも差し戻す。手順を並べるのは cwd が子のワークツリーのときだけにしたので（M-4）、親のツリーからの
  起動（孫も）には各子のフローのパスと「自分の担当の子のフローだけに従う」しか渡らない。どの子の担当かは
  起動した側のプロンプトが決め、hook は決められない。孫は範囲の中なら兄弟のワークツリーに書ける。
  プロンプトに担当を書かせるのは緩和で、塞いではいない。exit 2 で差し戻す同じ呼び出しでは `systemMessage` が
  読まれない（着手のあとの書き換えの知らせも、差し戻しの文にだけ載る）。ハードリンクは、ロックは inode で
  当てるが、組み込みの守り（`builtin-guard-project-home`）は綴りで当てるので別名への書き込みを止めない。
  読む側（案内とボード）がハードリンクを読まないので、別名から書いた中身は手順書にならない。Windows の 8.3 形式の
  短い名前は畳めず、解いた綴りが長い名前に戻ることに任せる。着手の指紋の控えはこの変更より前に着手した子には無く、
  その子には何も言わない

## 採らなかった案

- `references/<子>/` をチケットの置き場と同じく範囲の外として外す。フローは人がボードのエディタで書き、
  エージェントには書かせないので、エージェントが `references/` に書けるようにする理由が無い。外す場所が
  増えるのは判定が緩む向きでもある。最初は親の範囲に `references/` を入れない運用で守ったが、レビューで
  H1・M1 が出て、承認済みの領域へ移した（上）
- フローを子の本文（Markdown）に書く。承認の指紋に入り、着手の前に直すたびに承認が要る
