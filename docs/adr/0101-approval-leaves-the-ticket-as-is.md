# ADR-0101: 承認はチケットの中身を変えない。状態は status で聞き、承認の知らせは外す

状態: 提案（実装はまだ。ADR-0058 の「欄は承認の記録」と承認済みチケットへの `project:` の書き足し、ADR-0086 の承認の時刻の出どころ、ADR-0088 の続きの子の目印の置き場、ADR-0040 の「承認したことは hook が伝える」、ADR-0093 の取り込みでの「閉じた」の照合と取り下げの条件、設計 9.4 の「承認されたことは hook が伝える」を改める。承認済みの置き場を運ぶのがユーザであること（設計 9.4、ADR-0043）は改めない）

## 状況

2026-10-04。ユーザが GitHub の画面しか触れない環境でも承認できるよう、提案を `.ccnavi/approved/doing/` へ
手で動かすことも承認として認めている（ADR-0058）。ところが ccnavi の承認（端末の `--agree`、ボード、Chrome 拡張）は、
承認済みチケットの frontmatter に次を書き足す。手で動かした承認には、どれも無い。

| 書き足すもの | 書く場所（この ADR を書いた時点） |
|---|---|
| `ccnavi_approved: {approved_at, source_tree, source_path}` | 新規の承認（`approval.admit`） |
| `ccnavi_approved.revised_at` / `feedback_at` | 親の改版（`agree.revise_copy`） |
| `ccnavi_approved: {approved_at, source_tree: "", source_path: "", followup_of}` | 続きの子（`approval.followup`。`doing/` に直に起こす） |
| `project:`（frontmatter に無ければ） | 新規の承認（`approval.admit`） |
| `workflow:`（全体計画の待ち方のコピー） | 親の新規の承認と改版（`approval.admit`、`agree.revised_front`） |

しかも `admit` は提案をテキストで読み（`fsio.load_text`。改行を LF に揃える）、欄を差し込んで書き直す
（`insert_front` と `write_text`）。欄を足さない場合でも、CRLF の提案は承認で 1 バイト以上変わる。

起きたこと。

- エージェントが、手で置かれた承認済みチケットに欄が無く未コミットなのを見て「`ccnavi-agree.sh` が途中で止まった」と
  読み違え、ユーザに聞いて止まった。欄の有無が「どの経路で承認したか」を表してしまい、手で置いた承認が
  壊れた承認に見える
- 承認の知らせ（`agree.news` / `agree.baseline`）を取りこぼした。知らせはセッションの最初の hook
  （`SessionStart` の `baseline`）で起点を取り、それより後に増えた承認済みチケットだけを伝える。セッション開始時の
  取り込み（`ccnavi-fetch.sh`）で届いた承認は起点に含まれ、伝わらない

欄が担っている働きを、コードで確かめた（書いた時点の行番号）。

| 働き | いまの読み方 |
|---|---|
| 承認の取り下げ（Chrome 拡張だけが打つ） | `hook/core.py` の `_withdraw_problems`（918 行付近）が「`revised_at` / `feedback_at` がある」「`followup_of` がある、または `source_path` が無い」で止める。**戻し先と戻す中身は欄を読まない。** 戻し先は承認済みチケットのツリーの `wip/proposals/todo/<識別子>.md`、中身は Chrome 拡張が引いた承認コミットの親の提案（`prior_proposals`）。手で動かした承認は `source_path` が無いので取り下げられない |
| 取り込み済みの親子で、統合先の `done/` の親が手元の親と同じものか | `tickets/syncstate.py` の `_closed_in_integration`（548 行付近）が `approved_at` を比べる。手元の親が無い、**または手元の親に `approved_at` が無い**と「閉じた」とする。sh の側（`.ccnavi/scripts/ccnavi-sync.sh` の `closed_in_integration`）は逆で、手元に `approved_at` が無ければ「閉じていない」とする。Python の注記は「sh の見方と同じ」と書くが、ここだけ食い違っている。sh の `approved_at_of` は本文を含むどの行の `approved_at:` も拾う |
| `wip/proposals/review/` の 2 枚目の保護 | `approval.review_all` が `require_record=True` で `ccnavi_approved` を必須にしている（ADR-0058）。欄を書かなくなると、新しいチケットが `finish` で `review/` へ動いたとき読まれなくなる |
| 承認の時刻を見せる | ボード（`--explain --json` の `copy.approved_at` → `approvedAt`）、`--diagnose`（`entry/diagnose.py` 636 行と 979 行）、判定の拒否文（`hook/judge.py` 902 行）。手で置いたものは空 |
| 承認の知らせの版 | `agree._mark` が `approved_at` と `revised_at` で版を作り、改版も新しい合意として伝える |
| 承認済みチケットのプロジェクト | 書いてはいるが、読む側は置き場で決める。`approval.scan_all` がツリーの `project` で入れ直し、`load_copy` は欄を照合に使うだけ（ADR-0058） |
| 全体計画の待ち方 | 下の「`workflow:` を調べた結果」 |

承認済みの置き場をコミットすることについての今の事実も書いておく。`ccnavi-git.sh` は承認済みの置き場への
`add`・`commit` を止めていない（止めているのは置き場を過去の中身に戻す `restore --source` などだけ）。
エージェントに止めているのは `ccnavi-push-approved.sh` などのスクリプトの文字列で（`tickets/phase.py` 362〜380 行付近の
`ticket_approval_rule`。組み込みの deny）、置き場をコミットした差分は、ターンの報告で違反に数えない（`hook/post.py` 294 行付近）。
**この ADR はそこを変えない。** 別の件として扱う。

## 決定

### 承認で中身を変えない

| 決めたこと | 採らなかった側 | なぜ |
|---|---|---|
| **承認はチケットの中身を変えない。** 新規の承認は提案のファイルを `todo/` から `doing/` へ rename するか、バイト単位でコピーして（`fsio.read_bytes` / `write_bytes`）元を消す。`ccnavi_approved`・`project:`・`workflow:` を書き足さず、改行も BOM も変えない。端末・ボード・Chrome 拡張・手で動かす、のどれで承認しても、承認済みチケットは提案とバイト単位で同じになる | 欄を承認で書き続け、手で動かした承認には欄が無いことを「正常」と案内する | 欄の有無が経路を表す限り、読む側（エージェントも人も）は欄の無いものを壊れたものと読む。案内で直すより、違いを無くすほうが確か。本物とするのは前から置き場で、欄は記録でしかない（ADR-0058）。バイト単位にするのは、取り下げを中身の一致で決めるため（下） |
| 承認の指紋（`digest`）に入る「書き出す中身」（`agree._carried`）を、`render()` した姿ではなく、動かすバイト列にする。`read_set` もバイト列で取る。提案の走査（`ticket.py` 1140 行付近）が `raw["project"]` に差し込む値は指紋に入らなくなる（書かないものを指紋に入れない） | 今の `render()` のまま | 書くものと見せたものの指紋が別の姿になると、照合が「書いたもの」を覆わない。承認が中身を変えないなら、動かすバイト列がそのまま書く中身 |
| 承認の検査（親子・計画・`project:` と置き場・先行）は今までどおり承認のときに当て、判定の側でも当てる | — | 変えない。やめるのは書き足しだけ |
| 提案（`todo/`）に、スクリプトだけが書く欄（`ticket.SCRIPT_FIELDS`: `started_at`・`completed_at`・`base_sha`・`cancelled_at`・`cancel_reason`）の空でない値があれば、`--agree` と `--lint` で error にする。判定では提案に当てない | 今のまま見ない。判定でも当てる | 承認が中身を変えないので、提案に書いた値がそのまま承認済みチケットの値になる。下の `review/` の必須欄と、閉じた親の照合は、これらの欄がスクリプトだけが書いたものであることを前提にする。今はどこも見ていない（`SCRIPT_FIELDS` の値を検査する経路は無い）。判定で承認済みチケットに同じ検査を当てると、着手済みの `doing/` が全部止まる |
| 承認済みチケットには、中身だけで分かる欄の組み合わせの矛盾を検査する。`started_at` が無いのに `base_sha` がある `doing/` は `blocked` にする（判定で止める）。`doing/` に `completed_at`・`cancelled_at`・`cancel_reason` の値があるものは、`--lint` と status で warn にとどめ、判定では止めない | `doing/` の `completed_at` などを `blocked` にする | `start` は `started_at` と `base_sha` を一緒に書くので、前者だけが無い形は道具を通らない。`finish` は `doing/` から `review/` か `done/` へ、`cancel` は `done/` へ動かすので、道具を通る限り `doing/` に `completed_at` や `cancelled_at` は残らない。ただしユーザが `done/` から `doing/` へ手で戻す再開（状態の履歴の注記と `--lint` の案内が認めている運び）では欄が残ったまま `doing/` に来る。止めると、ユーザの再開がどこにも書けなくなる |
| 手で動かした承認に仕込まれた `started_at` / `base_sha` は、中身だけでは道具が書いたものと見分けられない。`start`・status・`--lint` で「チケットのワークツリーがあり、`base_sha` がその HEAD の祖先か」と「状態の履歴に `started` の行があるか」を確かめ、前者が満たされなければ blocked と同じ扱いで進めず、後者だけが欠ければ warn にする。判定には入れない | 判定でも確かめる | 判定は履歴も git も読まない取り決め（ADR-0086、下の「判定の拒否文」の行）。履歴は ccnavi の外で動かした分を持たないので、無いことだけでは止められない |
| 承認で `project:` を書き足さない。承認済みチケットのプロジェクトは置き場（ツリー）から決まる | 書き足し続ける | 読む側は既に置き場で決めている（`scan_all`）。`ticket.py` の注記（1136 行付近）は「親が閉じたとき judge が子の `project` を見る」と書くので、実装の前に、その経路が欄ではなくツリーから決まることを確かめる |
| 改版の `revised_at` / `feedback_at` は書かない。改版の時刻は状態の履歴の `revised`（`feedback: true` を含む）に残る | `ccnavi_approved` に書き続ける | 改版は計画を書き換えるので中身が変わるのは避けられないが、時刻まで中身に書く理由は無い。読んでいたのは承認の知らせの版（外す）と取り下げの検査（中身の一致に代える）だけ |
| 続きの子の目印 `followup_of` は、`ccnavi_approved` の外のトップレベルの欄として、ccnavi が `doing/` に直に書くときに書く | 目印を持たせない | 続きの子は提案を経ずに ccnavi が新しく作るチケットで、作るときに書く欄は「承認で中身を変える」に当たらない。取り下げで理由を名指しするのに使う |
| 既存の承認済みチケットに残る `ccnavi_approved`・`project:`・`workflow:` は消さない。移行はしない | 移行で欄を消す | 読んでも害が無い。保存済みのデータの表記を変えると既存のワークスペースとの互換が崩れる（ADR-0099 の「変えなかったもの」、`approval.admit` の「前の形も読む」と同じ方針）。承認済みの置き場はエージェントが書けないので、消すにはユーザの手が要る |

### 欄が担っていた働きの代わり

| 決めたこと | 採らなかった側 | なぜ |
|---|---|---|
| `wip/proposals/review/` で必須にする欄を、`ccnavi_approved` から `completed_at`（**値が空でない**）に替える。`review_all` の docstring と `load_copy` の `require_record` の説明も改める。古い形は両方を満たすので読める | 必須をやめる。`finish` が別の目印を書く | `completed_at` は `finish` が書くスクリプトの欄で、`review/` に来るものは必ず持つ。提案に書けば error になる（上）ので、エージェントが `review/` に置いたファイルは読まれない。2 枚目の保護の働きはそのまま残る |
| 取り下げの戻し先は今までどおり承認済みチケットのツリーの `wip/proposals/todo/<識別子>.md`（プロジェクト向けは `projects/<名前>/` 配下）。欄は読まない | `source_path` を読んで戻す | 戻し先は置き場から決まる。いまのコードも `source_path` を戻し先には使っていない |
| 取り下げを書く側（`core.withdraw`）は、「`doing/` の中身が、承認コミットの親の提案（`prior_proposals`）とバイト単位で同じ」で通す。比べるのはバイト列で、`fsio.read_text`（改行を揃える）は使わない。親の取り下げでは、加えて、`phases/<親>/workflow.yml` の中身が、承認コミットの親の提案と今の `phases.yml` から `workflow.compute` で計算した待ち方と同じであることを求める。違えば止める。通れば `workflow.yml` を一緒に消す。続きの子（`followup_of`）は理由を名指しして止める | 状態の履歴（`revised` / `started`）を読んで決める。`workflow.yml` があれば止める | 一致すれば、改版も着手（`started_at` / `base_sha` を書く）もされていない。手で動かした承認も取り下げられる。履歴を読んで状態の操作を決めると、ADR-0086 の「正は置き場。判定も状態の操作も履歴を読まない」を崩す。待ち方だけの改版は `doing/` を変えない（待ち方は別のファイル）ので、待ち方の中身で見る。「あれば止める」にすると、`--agree` で承認した計画付きの親は必ず `workflow.yml` を持つので、必ず取り下げられなくなる。承認のあとに `phases.yml` が変わっていれば計算が変わって一致せず、止める側に倒れる（取り下げられないだけで、待ち方が勝手に変わることはない） |
| 取り下げの「`phases/<親>/` にマーカーがある」の検査（`hook/core.py` の `_withdraw_problems`、930〜942 行付近。今はディレクトリが空でなければ止める）から `workflow.yml` を外す | 今のまま | 外さないと、上と同じく計画付きの親が必ず止まる。待ち方は上の行で別に見る |
| 取り下げを出すかの一覧（`core.withdrawable`。`prior_proposals` に空のバイト列を渡して呼ぶ）は粗く見る。「`ccnavi_approved` が無い新しい形」か「古い形で今の条件を満たす」なら出す。一致は書く側だけが見る | 一覧でも中身の一致を見る | 一覧は承認コミットを引く前に組むので、比べる相手が無い。出しすぎても、押したときに書く側が止める（判定は緩めない） |
| `ccnavi_approved` を持つ古い承認済みチケットの取り下げは、今の条件（欄を読む）のまま | 古いものも中身の一致で決める | 古いものは承認で欄が足されているので、承認コミットの親の提案と一致しない。一致で決めると、取り下げられたものが取り下げられなくなる |
| 取り下げの一致は、BOM 付きの提案など、ホストの API が読んだ姿と手元のバイト列が違うものでは一致しない側に倒れると見込む（実装で確かめる）。承認コミットがマージ（親が 2 つ）のときは今と同じく引けず、取り下げは出ない | — | どちらも止める側で、取り下げられないだけ |
| 取り込み済みの親子で親が閉じたかは、統合先の `done/` の親と手元の親を `base_sha` → `started_at` → `cancelled_at` の順に比べ、最初に両方が値を持つ欄が同じなら「閉じた」とする。空どうしは一致とみなさない。`base_sha: ""` は無いとみなす。どの欄でも照合できない（未着手のまま閉じた親など）ときと、手元に親が無いときは「閉じていない」とし、止めて戻し方を出す。移行の間は、両方に 3 つとも無く両方に古い `approved_at` があるときに限り、今までどおり `approved_at` で比べる | 今までどおり `approved_at` で比べ、手元に無ければ「閉じた」とする | 承認で `approved_at` を書かなくなるので比べる欄が要る。3 つはどれもスクリプトだけが書き（提案に書けば error）、同じ識別子の別の親子では違う値になる。`cancelled_at` まで見るのは、未着手のまま取り消した親が永久に止まらないようにするため。照合できないときに「閉じた」とすると、閉じていない親の状態を閉じたものとして扱い、親のワークツリーの片付けまで案内してしまう。止めるのは厳しい側で、ユーザと合意した。Python と sh の食い違い（上の「状況」）も、厳しい側の sh に揃う形で消える |
| sh（`ccnavi-sync.sh`）で欄を拾う `sed` は、frontmatter の中の行頭（`^base_sha:` など）に限る | 今の `approved_at_of` と同じく、どの行でも拾う | 本文に同じ語を書いた行があると、別の値を拾う |
| 承認の時刻は、状態の履歴 `events/<識別子>.ndjson` の `approved`（続きの子は `raised`）の `at` → 無ければ `git log --no-renames --diff-filter=A` で `doing/<識別子>.md` が入ったコミットの時刻（いちばん新しいもの） → どちらも無ければ「未コミット（手で置いた）」と出す。ボード（`approvedAt`）と `--diagnose` と status がこの順で読む | `approved_at` の欄を読み続ける | 欄を書かなくなる。履歴は ccnavi が動かした分を持ち、手で動かした分はコミットに残る。`--no-renames` を付けるのは、GitHub の画面での移動が rename のコミットになり、付けないと `A` に当たらないため。表示だけなので、履歴を読んでも ADR-0086 の「判定は履歴を読まない」には触れない |
| `git log` は、履歴で時刻が取れないチケットがあるときだけ、ツリーごとに 1 回打って `doing/` 全体の分をまとめて引く。Chrome 拡張（Pyodide）には git が無いので、そこでは空を返す | チケットごとに毎回 `git log` を打つ | ボードの読み込みがチケットの数だけ遅くなる。実行ファイルが git を読むのは今もしている（拡張は git を読まない。ADR-0035） |
| 判定の拒否文（`hook/judge.py`）からは承認の時刻を外す。hook の中では履歴も git も読まない | 拒否文にも同じ順で時刻を出す | 判定は hook のたびに走る。時刻のために判定の経路で履歴と git を読むと遅くなるうえ、判定が履歴を読まない取り決めの境目が曖昧になる。時刻が要れば status で聞ける |

### 互換の版と取り込む順序

| 決めたこと | 採らなかった側 | なぜ |
|---|---|---|
| 互換の版（COMPAT）を上げる。`entry/version.py` の説明に「データの形（待ち方の置き場・取り下げの条件など）が変わるときも上げる」を足す | 上げない（フラグも JSON の欄も消していない） | 新しい sh は古い実行ファイルにない `ticket status` を呼ぶ（古い実行ファイルは argparse で落ちる）。待ち方の置き場と取り下げの条件が変わり、古い実行ファイル（古いコアを積んだ Chrome 拡張を含む）が新しい形の承認済みチケットを読むと、待ち方を一直線と読み、取り下げを「承認の記録が無い」で止める。今の説明は「呼ぶ側が頼っているフラグや出力の形」だけを挙げていて、データの形が変わるときに上げることが書かれていない |

取り込む順序と、その間に起きること。互換の版の食い違いで止めるのは Chrome 拡張だけで、sh と VS Code 拡張は知らせて進む。
sh で止める変更は、この ADR ではしない。

1. 統合先に、実行ファイルのソース・`.ccnavi/scripts/` の sh（`ccnavi-ticket.sh`・`ccnavi-sync.sh`・`ccnavi-common.sh` の
   `CCNAVI_COMPAT`）・VS Code 拡張の `EXTENSION_COMPAT` を同じ変更で入れる。`.ccnavi/scripts/` は保護された場所なので、
   sh の書き換えは人の手で入れる
2. 実行ファイルを `build.py` で組み直す。組み直すまでは、sh（`ccnavi-common.sh` の `ccnavi_compat_skew`、
   `ccnavi-ticket.sh` は 91 行付近で呼ぶ）が食い違いを標準エラーに 1 行出して、そのまま古い実行ファイルを呼ぶ。

   （古い実行ファイルは承認で欄を書き、待ち方を承認済みチケットに書く）
3. VS Code 拡張を入れ直す。入れ直すまでは、古い拡張が起動のときに食い違いを知らせるだけで、止めはしない
   （`vscode-extension/ccnavi-board/src/version-check.ts`）
4. Chrome 拡張を配り直す。配り直すまでは、同梱の互換の版が古い Chrome 拡張は、統合先の版が上がった時点で

- sh だけが古いワークスペース（統合先から sh を取り込んでいない手元）では、`ccnavi-sync.sh` の
  `closed_in_integration` が `approved_at` だけを読むので、新しい形の親を「閉じていない」と読み続ける（止まる側）

## `workflow:` を調べた結果

- 中身は親の全体計画の待ち方。`order`（`sequential` / `dag`）、`waits`（番号 → 待つ番号）、`review_at`
  （延期した番号 → 引き受ける番号）。`workflow.compute` が `phases.yml` の種類（`overlap`・祖先・`order: dag`）と
  計画から計算する（設計 9.7）
- 読む側: `workflow.effective` / `waits_of`（どのフェーズが前のどれを待つか。承認の順序の検査と判定の
  フェーズの順序）、`Ticket.review_at` / `covered_by`（延期したフェーズのレビューをどこで引き受けるか）、
  `phase.is_dag`、改版の比べ方（`agree._workflow_differs`、`revision_problems` の延期の引き受け手の変化）
- 承認済みの親に `workflow:` が無いと、`effective` は**いまの種類を使わず**一直線（`compute(parent, None)`）で読む。
  手で動かした `order: dag` の親は、今も一直線として扱われている。安全な側（前の番号を全部待つ）だが、
  ユーザが承認した待ち方とは違う
- 承認で固定しているのは、承認のあとに `phases.yml`（親の着手で共通層から配られる。ADR-0084）が変わっても、
  作業中の親の待ち方と延期の引き受け手がユーザの見ていないところで変わらないようにするため。固定は要る
- よってマーカーの置き場（`phases/<親>/workflow.yml`）へ移す。手で動かした承認にはそのファイルが無く、今と同じく
  一直線で読む。status は「待ち方の固定が無いので一直線で読んでいる。並行にしたければ改版で `--agree` を通す」と言う

## 既存の ADR と設計との関係

- ADR-0058: 「`ccnavi_approved` は承認の記録であって承認そのものではない」を進め、記録を承認では書かないことにする。
  「承認済みチケットの `project` は置き場が決める」は変えず、書き足しもやめる。`review/` の 2 枚目の保護は
  `ccnavi_approved` から `completed_at` に替える。「失ったもの」の「承認日時が空のチケットができる。いつ承認したかが
  コミットの日時にしか残らない」は、status とボードがコミットの日時を読むことで補う
- ADR-0086: 承認の時刻の第一の出どころが欄から履歴になる。履歴は補助のままで、判定も状態の操作も履歴を読まない
  （取り下げは中身の一致と待ち方の計算の一致で決める）。表示（ボード・`--diagnose`・status）だけが読む
- ADR-0088: 先行を承認と着手で求める判断は変えない。続きの子の目印 `followup_of` の置き場が `ccnavi_approved` の中から
  トップレベルへ移る。手で動かした承認には承認の検査が当たらないので、満たしていない先行は status が着手の前に名指しする
  （`ticket start` が止めるのは今と同じ）
- ADR-0040: 「承認したことは hook が伝える」を外す。ボードのオーバーレイで承認を受けることと、拡張が承認の文を
  渡すことは変えない
- ADR-0093: 取り込み済みの親子の「閉じた」の照合（Python と `ccnavi-sync.sh`）を `approved_at` から着手と取り消しの欄に
  変える。取り下げの条件（8.8）を中身の一致に変える。Chrome 拡張が書く承認も中身を変えない形になる
- 設計 9.4: 「承認されたことは hook が伝える」を消す。承認済みの置き場を運ぶのがユーザであることは変えない

## 得たもの・失ったもの

- 得たもの: 手で動かした承認と ccnavi の承認が、バイト単位で同じ中身になる。欄の有無から「承認が途中で止まった」と
  読み違える形が無くなる
- 得たもの: 手で動かした承認も取り下げられる。取り込み済みの親子の「閉じた」の照合で、Python と sh の食い違いが消える
- 得たもの: 承認済みチケットの状態を、ファイルを読んで推測せずに ccnavi に聞ける
- 得たもの: 開始時の取り込みで届いた承認を取りこぼす経路（知らせ）が無くなり、状態は聞けば常に今のものが返る
- 得たもの: 提案にスクリプトの欄を書いた形は `--agree` と `--lint` が、`workflow:` を書いた形は `--agree`・`--lint`・判定が
  error にする。承認済みチケットでは、`started_at` の無い `base_sha` を判定が止める
- 失ったもの: **作業の途中（`PreToolUse`）にエージェントが自分で承認に気づく経路が無くなる。** ユーザがセッションに何か送るか、
  エージェントが status を打つまで、承認に気づかない
- 失ったもの: 承認の時刻を引くのに履歴か git を読むことになる。未コミットのうえ履歴も無い承認は時刻が出ない
  （「未コミット（手で置いた）」と出る）。Chrome 拡張の画面では、履歴の無い承認の時刻は出ない
- 失ったもの: 着手も取り消しもしていない親子と、手元に親が無い親子は、取り込みで「閉じた」と言えず止まる。今の Python は
  手元に親が無いとき「閉じた」としているので、そこは止まる側に変わる。戻し方を出すが、ユーザの手が 1 回増える
- 失ったもの: 待ち方の固定が承認済みチケットの外のファイルになり、承認・改版・取り下げで書く・消すものが 1 つ増える。
  C1 が見分ける形も 1 つ増える。手で動かした `order: dag` の親は今と同じく一直線で読む
- 失ったもの（残る弱点）: **手で動かした承認に、提案の段階で `started_at` と `base_sha` を仕込まれると、中身だけでは見分けられない。**
  `--agree` を通らない経路なので提案の検査は当たらず、判定はその値を信じる。`base_sha` は、サブエージェント終了時と
  実行後の範囲外の検査（`phase.scope_findings` の `base_sha..HEAD`）、実績のリスクの基準点（`risk.measure`）、取り込み済みの
  親子の「閉じた」の照合に使われるので、基準点をずらされると、範囲外の書き込みとリスクの数え漏れ、別の親子を閉じたと読む
  取り違えが起きうる。`start`・status・`--lint` が祖先の関係と履歴で確かめるが、判定は確かめない。手で動かせるのは
  承認済みの置き場に書ける権限を持つユーザだけなので、仕込めるのもその人か、その人が置いたファイルを書いた者に限られる
- 失ったもの: 判定の拒否文から承認の時刻が消える
- 失ったもの: 手で置かれて未コミットの承認は、ユーザが `ccnavi-push-approved.sh` を打つまで子のワークツリーと
  他の機械に届かない（今と同じ）。status はそれを言うだけ
- 失ったもの: 互換の版を上げるので、Chrome 拡張を配り直すまで、Chrome からの承認・取り下げ・「始める」が止まる。実行ファイルを
  組み直すまでは、sh は警告を出して古い実行ファイルで進み、`status` だけが落ちる
- 失ったもの: 古い承認済みチケットには欄が残り、新しいものには無い。移行の間は両方の形が並び、取り下げと照合が
  古い形の分の分岐を持つ

## 採らなかった案

- `UserPromptSubmit` で、承認済みチケットがあるたびに機械的に「status を打って確かめて」と案内する。ターンごとに
  同じ文がコンテキストに積もる。承認の無いターンでも出るか、出す条件を決めるために結局「新しい承認か」を数えることになり、
  外す知らせと同じ起点の問題を抱える
- `SessionStart` で承認を知らせる。開始時の取り込みとの前後で取りこぼしが残るうえ、compact や再開のたびに同じ承認を
  言い直すか、言ったかを覚える記録が要る（外す記録と同じもの）
- 承認済みチケットを `Read` したときに状態を添える。読むのは推測の入口そのもので、添えた文と読んだ中身のどちらを
  信じるかがエージェントに残る。status の出力のほうが言い切れる
- `Stop` で「承認されたものがあるので status を打って」と背中を押す。ターンの終わりは承認に気づくには遅く、
  止めるとターンを続けさせる意味になる。何を伝えたかの記録も要る
- 承認の知らせを残し、起点を取り込みの後に取り直す。取り込みは sh（`ccnavi-fetch.sh`）で hook の外にあり、起点を
  取り直す時機を hook から知る手段が無い。直しても、効くのは ccnavi が置いた承認の検出だけで、欄の有無による
  読み違えは残る
- 欄を承認で書き続け、手で動かした承認には ccnavi が後から欄を書き足す（status や hook で）。承認済みの置き場は
  エージェントが書けない場所で、書けるようにすると保護が 1 枚減る。書き足した時刻は承認の時刻ではない
- 欄を承認で書き続け、手で動かした承認には「欄が無いのは正常」と文書で案内する。読み違えを読む側の注意で防ぐ形で、
  今回それが効かなかった
- 手で置かれて未コミットの承認を、エージェントが `ccnavi-git.sh` で親のブランチへコミットして送る。一度は採ったが撤回した。
  理由は「状態を聞く副命令」の表のとおり
