# ADR-0101: 承認はチケットの中身を変えない。状態は status で聞き、承認の知らせは外す

状態: 提案（実装はまだ。ADR-0058 の「欄は承認の記録」と承認済みチケットへの `project:` の書き足し、ADR-0086 の承認の時刻の出どころ、ADR-0088 の続きの子の目印の置き場、ADR-0040 の「承認したことは hook が伝える」、ADR-0043 の「承認済みチケットは sh が運ぶ」の一部、設計 9.4 の「承認されたことは hook が伝える」と「承認済みの置き場を運ぶのはユーザ」を改める）

## 状況

2026-10-04。ユーザが GitHub の画面しか触れない環境でも承認できるよう、提案を `.ccnavi/approved/doing/` へ
手で動かすことも承認として認めている（ADR-0058）。ところが ccnavi の承認（端末の `--agree`、ボード、Chrome 拡張）は、
承認済みチケットの frontmatter に次を書き足す。手で動かした承認には、どれも無い。

| 書き足すもの | 書く場所（この ADR を書いた時点） |
|---|---|
| `ccnavi_approved: {approved_at, source_tree, source_path}` | 新規の承認（`approval.admit`） |
| `ccnavi_approved.revised_at` / `feedback_at` | 親の改版（`agree.revise_copy`） |
| `ccnavi_approved: {approved_at, source_tree: "", source_path: "", followup_of}` | 続きの子（`approval.followup`。`doing/` に直に起こす） |
| `project:`（frontmatter に無ければ） | 新規の承認（`approval.admit`） |
| `workflow:`（全体計画の待ち方のコピー） | 親の新規の承認と改版（`approval.admit`、`agree.revised_front`） |

起きたこと。

- エージェントが、手で置かれた承認済みチケットに欄が無く未コミットなのを見て「`ccnavi-agree.sh` が途中で止まった」と
  読み違え、ユーザに聞いて止まった。欄の有無が「どの経路で承認したか」を表してしまい、手で置いた承認が
  壊れた承認に見える
- 承認の知らせ（`agree.news` / `agree.baseline`）を取りこぼした。知らせはセッションの最初の hook
  （`SessionStart` の `baseline`）で起点を取り、それより後に増えた承認済みチケットだけを伝える。セッション開始時の
  取り込み（`ccnavi-fetch.sh`）で届いた承認は起点に含まれ、伝わらない

欄が担っている働きを、コードで確かめた（書いた時点の行番号）。

| 働き | いまの読み方 |
|---|---|
| 承認の取り下げ（Chrome 拡張だけが打つ） | `hook/core.py` の `_withdraw_problems`（918 行付近）が「`revised_at` / `feedback_at` がある」「`followup_of` がある、または `source_path` が無い」で止める。**戻し先と戻す中身は欄を読まない。** 戻し先は承認済みチケットのツリーの `wip/proposals/todo/<識別子>.md`、中身は Chrome 拡張が引いた承認コミットの親の提案（`prior_proposals`）。欄は「取り下げてよいか」の検査にだけ使っている。手で動かした承認は `source_path` が無いので取り下げられない |
| 取り込み済みの親子で、統合先の `done/` の親が手元の親と同じものか | `tickets/syncstate.py` の `_closed_in_integration`（548 行付近）が `approved_at` を比べる。手元の親が無い、**または手元の親に `approved_at` が無い**と「閉じた」とする。sh の側（`.ccnavi/scripts/ccnavi-sync.sh` の `closed_in_integration`）は逆で、手元に `approved_at` が無ければ「閉じていない」とする。Python の注記は「sh の見方と同じ」と書くが、手元に欄が無いときだけ食い違っている |
| 承認の時刻を見せる | ボード（`--explain --json` の `copy.approved_at` → `approvedAt`）、`--diagnose`（`entry/diagnose.py` 636 行と 979 行）、判定の拒否文（`hook/judge.py` 902 行）。手で置いたものは空 |
| 承認の知らせの版 | `agree._mark` が `approved_at` と `revised_at` で版を作り、改版も新しい合意として伝える |
| 承認済みチケットのプロジェクト | 書いてはいるが、読む側は置き場で決める。`approval.scan_all` がツリーの `project` で入れ直し、`load_copy` は欄を照合に使うだけ（ADR-0058） |
| 全体計画の待ち方 | 下の「`workflow:` を調べた結果」 |

## 決定

| 決めたこと | 採らなかった側 | なぜ |
|---|---|---|
| **承認はチケットの中身を変えない。** 新規の承認は提案のファイルを `todo/` から `doing/` へそのまま動かす。`ccnavi_approved`・`project:`・`workflow:` を書き足さない。端末・ボード・Chrome 拡張・手で動かす、のどれで承認しても、承認済みチケットは同じ中身になる | 欄を承認で書き続け、手で動かした承認には欄が無いことを「正常」と案内する | 欄の有無が経路を表す限り、読む側（エージェントも人も）は欄の無いものを壊れたものと読む。案内で直すより、違いを無くすほうが確か。本物とするのは前から置き場で、欄は記録でしかない（ADR-0058） |
| 承認の検査（親子・計画・`project:` と置き場・先行）は今までどおり承認のときに当て、判定の側でも当てる | — | 変えない。中身を変えないのは書き足しをやめることだけで、検査は残す |
| 取り下げの戻し先は今までどおり承認済みチケットのツリーの `wip/proposals/todo/<識別子>.md`（プロジェクト向けは `projects/<名前>/` 配下）。欄は読まない | `source_path` を読んで戻す | 戻し先は置き場から決まる。いまのコードも `source_path` を戻し先には使っておらず、有無を検査に使っているだけ |
| 取り下げてよいかは「`doing/` の中身が、承認コミットの親の提案（`prior_proposals`）とバイト単位で同じ」で決める。同じなら、改版も着手（`started_at` / `base_sha` を書く）もされていない。手で動かした承認も取り下げられる | 状態の履歴（`revised` / `started`）を読んで決める | 履歴を読んで状態の操作を決めると、ADR-0086 の「正は置き場。判定も状態の操作も履歴を読まない」を崩す。中身が変わらない承認なら、中身の一致がそのまま「承認のあと何も起きていない」の証拠になる |
| `ccnavi_approved` を持つ古い承認済みチケットの取り下げは、今の条件（欄を読む）のまま | 古いものも中身の一致で決める | 古いものは承認で欄が足されているので、承認コミットの親の提案と一致しない。一致で決めると、取り下げられたものが取り下げられなくなる |
| 続きの子の目印 `followup_of` は、`ccnavi_approved` の外のトップレベルの欄として、ccnavi が `doing/` に直に書くときに書く。取り下げは `followup_of` を持つものを止める（今と同じ） | 目印を持たせない | 続きの子は提案を経ずに ccnavi が新しく作るチケットで、作るときに書く欄は「承認で中身を変える」に当たらない。承認コミットの親に提案が無いので中身の一致でも止まるが、理由を名指しできるよう目印は残す |
| 取り込み済みの親子で親が閉じたかは、統合先の `done/` の親と手元の親の `base_sha`（`ticket start` が親に書く基準点）が同じときだけ「閉じた」とする。どちらかに無い（未着手のまま閉じた親など）ときは照合できないので「閉じていない」とし、止めて戻し方を出す。移行の間は、両方に `base_sha` が無く両方に古い `approved_at` があるときに限り、今までどおり `approved_at` で比べる | 今までどおり `approved_at` で比べる。手元に無ければ「閉じた」とする | 承認で `approved_at` を書かなくなるので比べる欄が要る。`base_sha` は着手で書かれ、同じ識別子の別の親子では違う値になる。照合できないときに「閉じた」とすると、閉じていない親の状態を閉じたものとして扱い、親のワークツリーの片付けまで案内してしまう。止めるのは厳しい側で、ユーザと合意した。Python と sh の食い違い（上の「状況」）も、厳しい側の sh に揃う形で消える |
| 承認の時刻は、状態の履歴 `events/<識別子>.ndjson` の `approved`（続きの子は `raised`）の `at` → 無ければ `git log --no-renames --diff-filter=A` で `doing/<識別子>.md` が入ったコミットの時刻（いちばん新しいもの） → どちらも無ければ「未コミット（手で置いた）」と出す。ボード（`approvedAt`）と `--diagnose` と status がこの順で読む | `approved_at` の欄を読み続ける | 欄を書かなくなる。履歴は ccnavi が動かした分を持ち、手で動かした分はコミットに残る。`--no-renames` を付けるのは、GitHub の画面での移動が rename のコミットになり、付けないと `A` に当たらないため。表示だけなので、履歴を読んでも ADR-0086 の「判定は履歴を読まない」には触れない |
| ボードは承認の時刻を、ツリーごとに `git log` を 1 回だけ打って `doing/` 全体の分をまとめて引く | チケットごとに `git log` を打つ | ボードの読み込みはチケットの数だけ遅くなる。実行ファイルが git を読むのは今もしている（拡張は git を読まない。ADR-0035） |
| 判定の拒否文（`hook/judge.py`）からは承認の時刻を外す。hook の中では履歴も git も読まない | 拒否文にも同じ順で時刻を出す | 判定は hook のたびに走る。時刻のために判定の経路で履歴と git を読むと、遅くなるうえ、判定が履歴を読まない取り決めの境目が曖昧になる。時刻が要れば status で聞ける |
| 改版の `revised_at` / `feedback_at` は書かない。改版の時刻は状態の履歴の `revised`（`feedback: true` を含む）に残る | `ccnavi_approved` に書き続ける | 改版は計画を書き換えるので中身が変わるのは避けられないが、時刻まで中身に書く理由は無い。読んでいたのは承認の知らせの版（外す）と取り下げの検査（中身の一致に代える）だけ |
| 承認で `project:` を書き足さない。承認済みチケットのプロジェクトは置き場（ツリー）から決まる | 書き足し続ける | 読む側は既に置き場で決めている（`scan_all`）。`ticket.py` の注記（1136 行付近）は「親が閉じたとき judge が子の `project` を見る」と書くので、実装の前に、その経路が欄ではなくツリーから決まることを確かめる |
| 全体計画の待ち方（`workflow:`）は、承認のときに固定する必要がある（下の「`workflow:` を調べた結果」）。承認済みチケットの外の置き場 `<承認済みの置き場>/workflows/<親>.yml` に移し、`--agree` と改版が書く。判定・延期・改版の比べ方はそのファイルを読む | 承認済みチケットに書き続ける。固定をやめて毎回 `phases.yml` から計算する | 前者は中身を変える。後者は承認のあとに `phases.yml` が変わると、作業中の親の待ち方と延期の引き受け手が、ユーザの見ていないところで変わる。置き場の名前は `flows/`（子のフロー）と分ける |
| 既存の承認済みチケットに残る `ccnavi_approved`・`project:`・`workflow:` は消さない。読む側は今までどおり読む（`workflow:` は新しい置き場が無いときだけ読む）。移行はしない | 移行で欄を消す | 読んでも害が無い。保存済みのデータの表記を変えると既存のワークスペースとの互換が崩れる（ADR-0099 の「変えなかったもの」、`approval.admit` の「前の形も読む」と同じ方針）。承認済みの置き場はエージェントが書けないので、消すにはユーザの手が要る |
| `ccnavi-ticket.sh status [<親>]` を足す。親を渡せばその親子、渡さなければ全部の、各チケットについて次を ccnavi が判断して出す: 置き場とツリー、承認の時刻（上の順）、着手しているか、置き場のファイルが未コミットか・コミット済みで未 push か、止まっている理由（`blocked`・先行・親が未着手）、次の一手 | エージェントにファイルと `git status` を読ませて推測させる | 推測が今回の読み違えを生んだ。「欄が無い」「未コミット」の意味は ccnavi が知っていて、ccnavi が言えば読み違えない |
| 次の一手は、未コミットなら親のブランチのツリーで置き場（と `todo/` から消えた提案）を add・commit・push するコマンドを `ccnavi-git.sh` の形で出す。親のブランチがデフォルトブランチ（`main` / `master` / `develop` / `release` / `release/*`）なら、`ccnavi-git.sh` が送らないので、ユーザに送ってもらうよう言う | 今までどおり「ユーザが `ccnavi-push-approved.sh` を打つ」とだけ言う | 手で置かれて未コミットの承認は、ユーザがもう承認の意思を出したあとのもの。コミットと push はその記録を運ぶだけで、承認の範囲を広げない。置き場への書き込みの保護は変えない（エージェントは置き場のファイルを作れも書き換えもできない） |
| status は読むだけで、ネットワークに出ない（取り込みはしない）。push 済みかは手元のリモート追跡の ref で見る。打てるのは他の副命令と同じく親（メインエージェント）だけ | 打つたびに取ってくる | 実行ファイルはネットワークに出ない（設計 P11）。最新にしたければ `ccnavi-sync.sh` を先に打つよう、古いかもしれないことを出力に添える |
| CLAUDE.md の詳細の表と `docs/claude/projects.md` に「承認済みチケットの状態を確かめるとき（着手の前、引き継ぎを読んだあと、承認の有無に迷ったとき）は、ファイルを読んで推測せず status を打つ」と書く | hook で毎回案内する | 下の「採らなかった案」 |
| **承認の知らせを外す。** `agree.news` / `agree.baseline` と記録 `<state>/approved-<session>-<agent>.json`、`UserPromptSubmit`・`PreToolUse`・`SessionStart` からの呼び出しを消す。`ctxfile` の古い `approved-` ファイルの掃除は、残ったファイルを消すために残す | 知らせを残し、起点の取り方を直す | 知らせが確実に効くのはセッションの途中の承認だけで、開始時の取り込みで届いた承認は起点に含まれて取りこぼす。ボードの承認は拡張が同じ文（`--agree --yes` の `prompt`）をクリップボードか新しいセッションで渡す（`vscode-extension/ccnavi-board/src/prompt-handover.ts`）。端末・GitHub・Chrome の承認では、ユーザがそのあとセッションに一言送るので、status で足りる |
| 承認を伝える文 `agree.approved_text` は残す（`--agree --yes` の `prompt` が使う）。提案を書いた回に承認の前の確認を勧める文（`ticket.propose_notice`、REQ-APV-14）は、同じ `PreToolUse` の `additionalContext` の経路で今までどおり渡す | 一緒に外す | 確認の案内は承認の知らせと経路を共有しているだけで、役目は別 |

### `workflow:` を調べた結果

- 中身は親の全体計画の待ち方。`order`（`sequential` / `dag`）、`waits`（番号 → 待つ番号）、`review_at`
  （延期した番号 → 引き受ける番号）。`workflow.compute` が `phases.yml` の種類（`overlap`・祖先・`order: dag`）と
  計画から計算する（設計 9.7）
- 読む側: `workflow.effective` / `waits_of`（どのフェーズが前のどれを待つか。承認の順序の検査と判定の
  フェーズの順序）、`Ticket.review_at` / `covered_by`（延期したフェーズのレビューをどこで引き受けるか）、
  `phase.is_dag`、改版の比べ方（`agree._workflow_differs`、`revision_problems` の延期の引き受け手の変化）
- 承認済みの親に `workflow:` が無いと、`effective` は**いまの種類を使わず**一直線（`compute(parent, None)`）で読む。
  手で動かした `order: dag` の親は、今も一直線として扱われている。安全な側（前の番号を全部待つ）だが、
  ユーザが承認した待ち方とは違う
- 承認で固定しているのは、承認のあとに `phases.yml`（親の着手で共通層から配られる。ADR-0084）が変わっても、
  作業中の親の待ち方と延期の引き受け手がユーザの見ていないところで変わらないようにするため。固定は要る
- よって別の置き場へ移す。手で動かした承認にはそのファイルが無く、今と同じく一直線で読む。status は
  「待ち方の固定が無いので一直線で読んでいる。並行にしたければ改版で `--agree` を通す」と言う

## 既存の ADR と設計との関係

- ADR-0058: 「`ccnavi_approved` は承認の記録であって承認そのものではない」を進め、記録を承認では書かないことにする。
  「承認済みチケットの `project` は置き場が決める」は変えず、書き足しもやめる。「失ったもの」の「承認日時が空の
  チケットができる。いつ承認したかがコミットの日時にしか残らない」は、status とボードがコミットの日時を読むことで
  補う。`wip/proposals/review/` で欄を必須にしている（`review_all` の `require_record`）のは、別に決める（下の「実装の前に決めること」）
- ADR-0086: 承認の時刻の第一の出どころが欄から履歴になる。履歴は補助のままで、判定も状態の操作も履歴を読まない
  （取り下げは中身の一致で決め、履歴を読まない）。表示（ボード・`--diagnose`・status）だけが読む
- ADR-0088: 先行を承認と着手で求める判断は変えない。続きの子の目印 `followup_of` の置き場が `ccnavi_approved` の中から
  トップレベルへ移る。手で動かした承認には承認の検査が当たらないので、満たしていない先行は status が着手の前に名指しする
  （`ticket start` が止めるのは今と同じ）
- ADR-0093: 取り込み済みの親子の「閉じた」の照合（設計の取り込みの節と `ccnavi-sync.sh`）を `approved_at` から `base_sha` に
  変える。Chrome 拡張が書く承認も中身を変えない形になる
- ADR-0040: 「承認したことは hook が伝える」を外す。ボードのオーバーレイで承認を受けることと、拡張が承認の文を
  渡すことは変えない
- ADR-0043: 承認済みチケットを運ぶのは今までどおり sh（`ccnavi-push-approved.sh`）。手で置かれて未コミットの承認だけは、
  エージェントが `ccnavi-git.sh` で運んでよい
- 設計 9.4: 「承認されたことは hook が伝える」を消す。「承認済みチケットは運ぶまで届かない」の「運ぶのはユーザ
  （`ccnavi-push-approved.sh`）。エージェントからは組み込みの deny で止める」を、**手で置かれて未コミットの承認に限り**、
  エージェントが `ccnavi-git.sh` で親のブランチへコミットして送ってよい、と改める。`ccnavi-push-approved.sh` を
  エージェントに打たせないのは変えない

## 実装の前に決めること・気をつけること

- `.ccnavi/scripts/` は保護された場所で、`ccnavi-ticket.sh`（通す副命令の一覧に `status` を足す）と `ccnavi-sync.sh`
  （`closed_in_integration` を `base_sha` で比べる）の書き換えは人の手で入れる。sh だけ古いと、新しい親は `approved_at` を
  持たないので、sh は閉じた親を「閉じていない」と読み続ける（止まる側）
- 新しい sh が古い実行ファイルの `ticket status` を呼ぶと落ちる。互換の版（COMPAT）を上げるかは `entry/version.py` の
  上げ方で決める
- `wip/proposals/review/` は `ccnavi_approved` を必須にして 2 枚目の保護にしている（ADR-0058）。承認で欄を書かないと、
  新しい承認済みチケットが `finish` で `review/` へ動いたときに読まれなくなる。`finish` が `review/` へ動かすときに
  目印を書く（承認ではなく状態の操作の書き込み）か、`review/` の保護を別の形にするかを、実装の前にユーザと決める
- 承認の指紋（`digest`）に入る「承認のとき書き出す中身」は提案そのものになる。見せる側と照らす側が同じ実行ファイルなら
  食い違わない

## 得たもの・失ったもの

- 得たもの: 手で動かした承認と ccnavi の承認が同じ中身になる。欄の有無から「承認が途中で止まった」と読み違える形が無くなる
- 得たもの: 手で動かした承認も取り下げられる。取り込み済みの親子の「閉じた」の照合で、Python と sh の食い違いが消える
- 得たもの: 承認済みチケットの状態を、ファイルを読んで推測せずに ccnavi に聞ける。手で置かれて未コミットの承認を、
  ユーザの手を待たずにエージェントが運べる
- 得たもの: 開始時の取り込みで届いた承認を取りこぼす経路（知らせ）が無くなり、状態は聞けば常に今のものが返る
- 失ったもの: **作業の途中（`PreToolUse`）にエージェントが自分で承認に気づく経路が無くなる。** ユーザがセッションに何か送るか、
  エージェントが status を打つまで、承認に気づかない
- 失ったもの: 承認の時刻を引くのに履歴か git を読むことになる。ボードは読み込みのたびにツリーごとに `git log` を 1 回打つ。
  未コミットのうえ履歴も無い承認は時刻が出ない（「未コミット（手で置いた）」と出る）
- 失ったもの: 未着手のまま閉じた親など `base_sha` を持たない親子は、取り込みで「閉じた」と言えず止まる。戻し方を出すが、
  ユーザの手が 1 回増える
- 失ったもの: 待ち方の固定が承認済みチケットの外のファイルになり、承認済みの置き場のファイルが 1 種類増える。手で動かした
  `order: dag` の親は今と同じく一直線で読む
- 失ったもの: 判定の拒否文から承認の時刻が消える
- 失ったもの: エージェントが承認済みの置き場をコミットして送れる場面ができる。置き場への書き込みの保護は変えないので、
  送れるのはユーザが置いたものだけだが、push の時機をユーザが決める形（設計 9.4）はその場面に限って崩れる
- 失ったもの: 古い承認済みチケットには欄が残り、新しいものには無い。移行の間は両方の形が並ぶ

## 採らなかった案

- `UserPromptSubmit` で、承認済みチケットがあるたびに機械的に「status を打って確かめて」と案内する。ターンごとに
  同じ文がコンテキストに積もる。承認の無いターンでも出るか、出す条件を決めるために結局「新しい承認か」を数えることになり、
  外す知らせと同じ起点の問題を抱える
- `SessionStart` で承認を知らせる。開始時の取り込みとの前後で取りこぼしが残るうえ、compact や再開のたびに同じ承認を
  言い直すか、言ったかを覚える記録が要る（外す記録と同じもの）
- 承認済みチケットを `Read` したときに状態を添える。読むのは推測の入口そのもので、添えた文と読んだ中身のどちらを
  信じるかがエージェントに残る。status の出力のほうが言い切れる
- `Stop` で「承認されたものがあるので status を打って」と背中を押す。ターンの終わりは承認に気づくには遅く、
  止めるとターンを続けさせる意味になる。何を伝えたかの記録も要る
- 承認の知らせを残し、起点を取り込みの後に取り直す。取り込みは sh（`ccnavi-fetch.sh`）で hook の外にあり、起点を
  取り直す時機を hook から知る手段が無い。直しても、効くのは ccnavi が置いた承認の検出だけで、欄の有無による
  読み違えは残る
- 欄を承認で書き続け、手で動かした承認には ccnavi が後から欄を書き足す（status や hook で）。承認済みの置き場は
  エージェントが書けない場所で、書けるようにすると保護が 1 枚減る。書き足した時刻は承認の時刻ではない
- 欄を承認で書き続け、手で動かした承認には「欄が無いのは正常」と文書で案内する。読み違えを読む側の注意で防ぐ形で、
  今回それが効かなかった
