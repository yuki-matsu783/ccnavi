# ADR-0105: 承認済みチケットは一時ファイルに書き切って fsync してから差し替える

状態: 採用（2026-10-04 に実装。ADR-0056 が「マーカーと承認済みチケットは別に扱う」と残した件のうち、承認済みチケットの側を決める。マーカーはこの ADR の外）

## 状況

2026-10-04（issue #225）。承認は提案を `todo/` からバイト列のまま読み、同じバイト列を `doing/<識別子>.md` に
書いてから元を消す。書き込みは `fsio.write_bytes`（`open(path, "wb")`）だった。開いた時点で中身を捨てるので、
書き終える前に落ちる（プロセスが殺される、電源が落ちる、ディスクが一杯になる）と、空か書きかけの
承認済みチケットが残る。

承認済みチケットは判定が範囲を読む元で、承認は「提案とバイト単位で同じ」ことが条件（ADR-0104）。
壊れたものが残ると、

- 判定は読めないチケットとして扱い、そのチケットの範囲が効かない
- 提案は消える前なら `todo/` に残るが、`doing/` に壊れた同じ識別子が在るので「複数の場所にある」で止まる
- state の記録と違って、次の起動で取り直す手段が無い

同じ形の書き込みは、承認で一緒に書く親の待ち方（`phases/<親>/workflow.yml`）、落ちたときに待ち方を戻す処理、
Chrome 拡張の取り下げで提案を `todo/` へ戻す処理にもあった。承認済みチケットを書き直す処理（親の改版、
着手と終わりの欄、続きの子を `doing/` に起こす）は `open(path, "w")` で、同じく途中で落ちると空か書きかけが残る。

もう 1 つ見つかった。state の記録などを書く `write_text_atomic` の一時ファイルは `<名前>.<一意>.part<拡張子>` で、
先頭に `.` が無い。承認済みの置き場を運ぶ `ccnavi-push-approved.sh` と C1 のコミットが除くのは `.<名前>.part*` の形
なので、承認済みの置き場（`phases/<親>/` の記録）に落ちて残った一時ファイルはコミットされうる。

ADR-0056 は state の記録を `write_text_atomic`（差し替えるが `fsync` しない）にしたとき、
「マーカーと承認済みチケットは素の書き方のまま。ここは別に扱う」と残していた。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| `fsio.write_bytes_atomic` を足す。同じディレクトリに一時ファイルを作って書き切り、flush と `fsync` をしてから `os.replace` で差し替え、最後に親ディレクトリを `fsync` する | 途中で落ちても前の中身か新しい中身のどちらかが残る。`fsync` までするので、電源断の直後に「差し替わっているが中身が空」も残さない | `write_text_atomic` をそのまま使う（電源断を守らない。テキストとして書くので改行が変わりうる） |
| 使うのは承認済みチケット（新規の承認）、親の待ち方、待ち方を前の中身へ戻す処理（`put_back`）、取り下げで提案を `todo/` へ戻す処理 | ユーザの決定（範囲は承認）。どれも承認と組で、壊れると取り返しが付かない | レビュー・自己防衛の書き込みまで広げる（範囲の外。影響を読み切れない） |
| 承認した子のフローを承認済みのツリーへ移す処理は `fsio.write_new_durable` で書く。行き先に在るかを確かめ、無ければ一時ファイルに書いて `fsync` し `os.replace` で置く。在るときの扱い（同じ中身なら何もしない、違う中身なら上書きせずに言う）は前と同じ。フローの読み手がハードリンクを拒む検査は緩めない | 前の `write_new`（`O_EXCL`）は途中で落ちると書きかけのフローを残し、次の承認は「違う中身のフローが在る」で止まる。承認の経路にも、同じ行き先を書くボードの保存にもロックが無いので、ロックの下で確かめる形は取れない | hard link で置いてから一時ファイルを消す（落ちた直後にリンク数 2 のファイルが残り、フローの読み手が拒む）。OS ごとの置き換えない rename（OS ごとのコードと確認が要る）。ロックを新しく作る（Python・TS・sh にまたがる）。`write_new` のまま（書きかけが残る） |
| 取り下げの検査は、`phases/<親>/` の一時ファイル（`fsio.is_temp_name`。`.<名前>.<一意>.part` と `.<名前>.<一意>.part<拡張子>`）をマーカーと数えない。それ以外の、待ち方でない名前は今までどおりマーカーと数えて止める | 承認で待ち方を書く途中で落ちると、残った一時ファイルだけで取り下げが止まる。一時ファイルはコミットされず、状態を表さない | 一時ファイルも数えて止めたまま（ユーザが手で消すまで取り下げられない） |
| 承認済みチケットの書き直し（親の改版、着手と終わりの欄、続きの子）は `fsio.write_text_durable` で書く。中身は `write_bytes_atomic` と同じ書き方で、改行は `write_text` と同じに変える（`newline=None` なら機械の改行。Windows は CRLF） | 書き直しも承認済みチケットを壊しうる。改行の扱いを変えると、Windows の手元のファイルが 1 回の書き直しで別のバイト列になる | 書き直しもバイト列で書く（Windows で改行が変わる） |
| 溜める段では新しい種類 `OP_BYTES_ATOMIC`・`OP_TEXT_DURABLE`・`OP_NEW_DURABLE` として溜め、Writer(FS) がそれぞれの関数で書く。溜める中身（Changes）は前と同じ（改行は LF に固定） | `OP_BYTES`・`OP_TEXT`・`OP_NEW` を書き換えると、他の書き込みまで書き方が変わる。種類を分ければ影響は承認済みチケットの書き込みだけ。Chrome のコミットと手元の plan が同じバイト列になることは変えない | `OP_BYTES` の実行側を原子版に切り替える |
| `write_text_atomic` の一時ファイルの名前を `.<名前>.<一意>.part<拡張子>` にする（先頭に `.` を足す）。掃除する側（`ctxfile.forget` と `prune`）は、先頭の `.` を外した名前（`fsio.temp_origin`）に今までの条件を当てる。掃除される範囲は名前の形で違い、前（先頭に `.` が無かった頃）と同じ: `ctxfile.forget` は `.once-…` を消す。`prune` は `.once-…`・`.approved-…` を同じセッションの記録と一緒に（組が無ければそれ自身の日付で）、`.nudged-…`・`.denied-…`・`.stop-…` を別の組としてそれ自身の日付で消す。`post` の seen（`.<セッション>.<一意>.part.json`）と turn（`.<セッション>.turn.<一意>.part.json`）はどの形にも当たらず、消さずに残る | 運ぶ側の除外の形に当たり、承認済みの置き場の残骸がコミットされない。掃除の当たり方は名前の `.` を外せば前と同じになる。消す範囲は広げない（形を広げると、知らないファイルまで消しうる。消すのは元に戻せない） | 運ぶ側の sh と C1 の除外を広げる（保護された sh の書き換えが要り、除外の形が 2 つになる） |
| 一時ファイルの名前は `.<元の名前>.<一意>.part` | 先頭の `.` と末尾の `.part` は `ccnavi-push-approved.sh` と C1 のコミットが除外する形。`.md` で終わらないので、`doing/` を読む側（`.md` だけを読む）が残骸をチケットとして読まない | `write_text_atomic` と同じ `<名前>.<一意>.part<拡張子>`（`doing/` の残骸が識別子とファイル名の違うチケットとして読まれ、除外にも当たらない） |
| macOS では `F_FULLFSYNC` を先に試し、使えなければ `os.fsync` | macOS の `fsync` はディスクの書き込みキャッシュまでは届かない | `os.fsync` だけ |
| 親ディレクトリの `fsync` は開けない・できないときは黙って飛ばす（Windows では開けない）。ファイルの `fsync` で落ちたら差し替えず、書けなかったとして返す | 差し替えの後なので、ディレクトリの `fsync` の失敗で「書けなかった」にすると、書けたものを戻す処理が走る。ファイルの `fsync` の失敗は中身が届いたか分からないので本番にしない | ディレクトリの `fsync` の失敗も書けなかったことにする |
| 行き先が既に在って書き込み権が無い（0444、Windows の読み取り専用属性。`os.access(path, os.W_OK)` が偽）ときは、一時ファイルを作る前に書けなかったこと（EACCES）にする | 差し替えはディレクトリの書き込み権だけで通るので、そのままだとユーザが chmod で止めた承認済みチケットの書き換えを素通りさせる。前の素の書き方は同じファイルに EACCES で失敗していた | 差し替えで上書きする（読み取り専用が効かなくなる） |
| 権限は `write_text_atomic` と同じく、在ればその権限、無ければ素の `open` と同じにする。ただし最善努力で、chmod が失敗しても（vfat・一部の CIFS の EPERM）書き込みは続け、`mkstemp` が作った 0600 のまま置く。`fsync` の失敗は今までどおり書けなかったことにする | `mkstemp` は 0600 で作るので、そのままだと承認済みチケットの権限が狭まる。一方、chmod を受け付けないファイルシステムで書けなくなると、前の書き方（素の `open`）では書けた承認が全部止まる | chmod の失敗も書けなかったことにする |

## 得たもの・失ったもの

**得たもの**

- 承認・改版・着手・終わりの途中で落ちても、承認済みチケットと待ち方は前の中身か新しい中身のどちらか。
  空や書きかけは残らない
- 中身はバイト列のまま書くので、承認がバイト単位で提案と同じことは変わらない。書き直しの改行も前と同じ
- 途中を見せない書き方の一時ファイルが承認済みの置き場に残っても、`ccnavi-push-approved.sh` と C1 のコミットは
  運ばない（除外が見るのは承認済みの置き場だけ。下の「失ったもの」の `todo/` を参照）

**失ったもの**

- **承認 1 件ごと、着手・終わり 1 回ごとに `fsync` の待ちが増える。** どれもチケットの操作で、全ツール呼び出しの
  経路ではないので受け入れた。state の記録（ADR-0056）は今までどおり `fsync` しない
- **一時ファイルの名前が元より長い。** Windows の 260 文字の上限ぎりぎりの行き先では、以前は書けたものが
  書けないことがある
- **残骸の種類が 1 つ増えた。** 落ちて残った `.<名前>.<一意>.part` を掃除する仕組みは無い。承認済みの置き場に
  残ったものはコミットされず、チケットとしても読まれず、取り下げの検査もマーカーと数えないが、置き場に残る
- **取り下げで提案を戻す途中で落ちると、提案の置き場（`wip/proposals/todo/`）に `.<識別子>.md.<一意>.part` が残る。**
  これは承認済みの置き場の外なので、`ccnavi-push-approved.sh` と C1 の除外は効かない。代わりに、このリポジトリの
  `.gitignore` に `.*.part` と `.*.part.*` を足した（ユーザの決定）ので、`git add -A` にも入らない。
  チケットとしては読まれない（`.md` で終わらない）。`git status` にも出ないので、見つけるには
  `ls -a` か `git status --ignored` を使う。配布先の `.gitignore`（導入スクリプトが足す行）には、この 2 行を
  まだ足していない（別の判断）
- **ディレクトリに書き込み権が無いと書けない。** 一時ファイルを同じディレクトリに作るので、ファイルには書けても
  ディレクトリが書き込み不可（0555 など）なら `mkstemp` が EACCES で落ちる。前の素の書き方（ファイルを開いて
  上書き）はそこでも書けた（一般ユーザで確かめた）
- **新しい inode になる。** 差し替えたファイルの所有者とグループは書いたプロセスのものに変わり（別の利用者が
  持っていたファイルでも）、ハードリンクは切れる（もう片方の名前は前の中身のまま）。前の素の書き方は同じ inode を
  上書きしたので、どちらも変わらなかった（所有者 1000 のファイルを root で書き直して確かめた）
- **行き先がシンボリックリンクなら、リンクの先ではなくリンクそのものを差し替える。** 前の書き方はリンクを辿った
- **Windows では、差し替えを約 60ms で諦める。** 同じファイルを他のプロセス（エディタ・ウイルス対策・
  ボード）が開いていると、`os.replace` は共有違反で失敗する。打ち直しは 3 回、20ms 間隔なので、それより長く
  開かれていれば書けなかったことになる
- **前の中身への戻し（`put_back`）は、失敗しても何も言わない。** 承認の途中で落ちて待ち方を前の中身へ戻すとき、
  戻しの書き込み自体が（上の共有違反などで）失敗すると、待ち方は新しい中身のまま残る。承認が止まったことは
  言うが、戻せなかったことは言わない
- **権限を引き継げないことがある。** chmod を受け付けないファイルシステムでは、承認済みチケットは 0600 で置かれる
- **フローの移しの「在れば書かない」が弱まった。** 前の `write_new` は `O_EXCL` で、在れば必ず書かなかった。
  いまは在るかを確かめてから `os.replace` で置くので、確かめてから置くまでの短い間にボードの保存（や人）が
  同じ子のフローを置くと、それを上書きする。起きるのは、ユーザが承認と同時にその子のフローを承認済みのツリーへ
  保存したときだけ。承認の経路にもボードの保存にもロックが無いので塞げない

## 採らなかった案

- **全部の書き込みを原子的にする。** 一度で揃う。採らなかったのは、ユーザが範囲を承認に絞ったため。
  レビュー・自己防衛の書き込みはそれぞれ読み手と残骸の掃除が違い、影響を読み切れない
- **`fsync` をしない（`write_text_atomic` と同じ値段）。** 速い。採らなかったのは、承認済みチケットは
  取り直せないので、電源断の直後に空が残る余地を残す理由が無いため
