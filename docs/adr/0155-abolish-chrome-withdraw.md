# ADR-0155: Chrome 拡張の承認の取り下げを廃止し、子は取り消して出し直し、親は改版か取り消しにする

状態: 採用

## 状況

Chrome 拡張には、承認した直後のチケットを `doing/` から `todo/` に戻す「承認を取り下げる」があった。承認は提案を中身を変えずに動かすだけなので、
承認コミットの親にあった提案のバイト列をそのまま `todo/` に書き戻し、`doing/` を消す。戻せるのは次をすべて満たすときだけだった。

- `doing/` の中身が承認コミットの親の提案とバイト単位で同じ（改版も着手もされていない）
- 続きの子でなく、親なら子もフェーズのマーカーも無い
- 戻す先の `todo/` に同じ識別子の提案が無い
- 承認コミットを、親のブランチの first-parent の履歴から引ける

この操作には次の問題があった。

- 条件が多く、拒む理由のコードだけで 11 種類（付録 A の `CORE_WITHDRAW_*`）になる。戻せない場合の大半は、結局 `cancel` を案内して終わっていた
- 承認コミットを履歴から引くのはホストの API を読む拡張の側で、GitHub と GitLab で別々に書いていた。GitHub は承認コミットを `renamed` と返すことがあり、
  変更の一覧は 300 件で切れ、merge や別の枝のコミットも履歴に混ざる。引き方を誤ると、別のコミットの親の提案を戻してしまう
- 手元の端末や VS Code のボードには同じ操作が無く、Chrome だけにある操作だった。取り下げだけのために、コアの入口と判定、付録 A のコード、
  拡張の見本（ホストの応答）と試験を持ち続けていた
- 取り消して出し直す手順は、取り下げが通る場合も通らない場合も使える。取り消しは `done/` に理由つきの記録が残る

## 決定

| 決めたこと | なぜ |
|---|---|
| Chrome 拡張の「承認を取り下げる」ボタンと、入口（`py/ccnavi_chrome.py`）の `withdraw` / `withdrawable` の op、ボードの答えの `withdrawable` を消す | 承認を戻す操作を拡張に置かない |
| コアの `withdraw` / `withdrawable`（`core_withdraw.py`）と、付録 A の `CORE_WITHDRAW_*` を消す | 呼ぶ側が無くなる |
| 承認コミットを履歴から引く読み（ホストごとの `approvalCommit`・first-parent の鎖と、`findPrior`）を消す | 取り下げのためだけに使っていた。競合の検出や元に戻すコミット（revert）が使う書いた後の確かめ（コミットの親を引く関数など）は残す |
| 承認を戻す操作は持たない。承認した子を直すときは `cancel --reason` で取り消して新しい連番で出し直す。承認した親は、中身を直すなら改版し、やめるなら `cancel` する | 戻せる場合と戻せない場合で手順を分けず、どの場合も同じ手順にする。取り消しは理由が記録に残る |
| 状態の遷移の表から「`doing` → `todo`（取り下げ）」の行を消し、同じ方針を書く | 表に無い遷移を、拡張だけが行えないようにする |

## 互換の版

公開している入口（Chrome 拡張の入口の `withdraw` / `withdrawable` の op と、コアの `withdraw` / `withdrawable`）の削除なので、互換の版を上げる対象になる。
旧 Chrome 拡張と新しい実行ファイルが混ざると、旧 Chrome 拡張が送る `withdraw` の op を受けなくなる。上げる値は他の変更とまとめて別に揃える。

## 採らなかった案

- 取り下げを残し、戻せる条件を広げる（着手後や改版後も戻す）。戻す提案の中身は承認コミットの親から引くので、承認のあとに加えた変更を黙って捨てることになる
- 取り下げを残し、承認コミットを引く読みだけを簡単にする。履歴の読みは merge・rename・ページの上限で外れうる。判定を緩めると別のコミットの親の提案を戻す
- 取り下げを端末や VS Code のボードにも足す。入口が増えるだけで、取り消して出し直す手順と二重になる
