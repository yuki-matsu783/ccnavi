# ADR-0016: 判定を実行せずに試す道を、判定と同じ関数で作る

状態: 採用

## 状況

ルールは書いた瞬間から、当たるつもりのものに当たっているかが分からない。`glob` は正規表現に
翻訳され、Bash のコマンドは実行される部分まで絞られてから当たる。ずれても気づく手立てが無いと、
足したつもりで何も止めていない 1 行になる。

## 決定

`--test <ツール> <対象>` は判定・根拠コード・当たったルール・翻訳後の正規表現・返る文面を出す。
`--explain` はタイプごとのルールと承認済みの作業範囲を一覧する。`--test-samples` は見本
（`.claude/ccnavi/rule-samples.yml`）をまとめて判定に掛け、期待と食い違ったものを名指しする。
どれも hook の判定と同じ関数を呼ぶ。試験のモードは常に `enable`。

見本は `deny` / `ask` / `allow` のタイプに置き、タイプの名前が期待する判定になる。
ルールを 1 件足したら見本も 1 行足す。止めたいものだけでなく止めたくないものを一緒に置く。
`/ccnavi-config` スキルがこの流れを回す。

## 理由

判定を作り直すと、試験が通ったのに実運用で落ちる、という一番まずい形になる（REQ-DIA-03）。
片側だけの見本は、ルールを広げすぎたことに気づけない。

VS Code 拡張が読む `--test --json` / `--test-samples --json` も同じ関数を通す（ADR-0035）。
`--json` のときは終了コードを常に 0 にし、食い違いの数は本文で読む。「食い違った」と
「試験そのものが失敗した」を終了コードで見分けられるように。

## 得たもの・失ったもの

- 得たもの: ルールを足すたびに確かめられる。拡張が判定を持たずに済む
- 失ったもの: 端末からの試験には `permission_mode` が来ないので、言及の無い呼び出しは `ask` と
  出る（ADR-0009）。見たいなら payload を直接流す

## 採らなかった案

- 試験用に判定を別に書く。上のとおり
