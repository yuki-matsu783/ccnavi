# ADR-0026: フェーズに種類を与え、親が計画を持つ

状態: 採用

## 状況

それまでのフェーズは番号しか持たず、「2 番目の束」以上の意味が無かった。2026-09-10。

## 決定

`.claude/ccnavi/phases.yml` に種類（調査・設計・受入テスト作成・実装・フィードバック対応など）を
定義し、親が `plan:` に種類の並びを書く。それが全体計画で、`--approve` が通ることが合意。
各フェーズの計画は、その番号の子を提案して承認を受けること。用語は「フェーズの種類」（定義）と
「フェーズ」（計画に並ぶ番号付きの実体）で、「段」は使わない。

| 決めたこと | なぜ |
|---|---|
| 種類は人が持つ設定（ルールで守る）。組み込みの既定は無し | エージェントが種類を書けると、レビュー不要の種類を作ってから使える。既定を組み込むと意図せずレビューの要否が決まる |
| `kind: work` は全体計画に、`kind: feedback` はフィードバック計画にしか置けない | 対応の中で実装をやり直すなら `implement-feedback` のような対応の種類を定義する。線を種類の側に引く |
| 順序は承認で止める。N 番目の子は N-1 番目までが閉じてレビューが済むまで承認されない。`overlap` は例外 | 作業が終わるまで次の計画は立てない、をそのまま形にする。承認されたのに始められない子を作らない |
| 計画の項で `review: defer`（延期）が書ける。延期は省略ではなく、次にレビューがあるフェーズの依頼に含める。最後の項とレビュー不要の種類は延期できない | 対応が軽いとき「設計の対応は実装と一緒に見る」ができる。省略の道は作らない |
| フィードバック計画は全体計画の最後のレビューが済んでから 1 回だけ。指摘が無くても `feedback: []` を改版で出して承認を受ける | 作業をするまで対応は計画できない。空でも出すのは「見たうえで対応なし」の証跡を残すため。1 回だけなのは計画であって、承認済みのフィードバック作業フェーズの中で差し戻しを受けて子を足すのは何度でもできる |
| 改版は写しが動かない原則の唯一の例外。変えられるのは `plan` と `feedback` だけで、`plan` は子がまだ承認されていない番号の項に限る | 番号がずれると子の `phase` が指す先が変わる |
| フェーズの最後の子を閉じる前に、種類の `deliverables` が親か子の作業ツリーに在って追跡されているかを見る。中身は見ない | 空でも在ることは分かるので「調査したことにする」は塞げる |
| 残った指摘は `ccnavi-review.sh handoff` で別の issue に切り出す | 対応の連鎖を切る出口を機械が持つ |
| `--approve` は、読めない提案があって承認するものが無いとき 1 を返す | 壊れた提案を「何も無い」で通さない。テストで見つけた |
| 親はコンテキストを清潔に保ち、作業は必ず子に切り出す | 親の範囲は広いので親が手を動かすと範囲の絞りが効かず、フェーズの終わりも子の閉じで数えている。親のコンテキストに作業の出力が積もると、計画と合流の判断が薄まる |

## 得たもの・失ったもの

- 得たもの: 計画に人が合意する形ができ、フェーズが意味を持つ
- 失ったもの: `phases.yml` はワークスペースに 1 本で、プロジェクトごとに変えられない（ADR-0033）
- 計画の無い親は今までどおり番号だけで動く。`phases.yml` も要らない

## 採らなかった案

- 各フェーズの計画に別の文書を求める。子チケットの題・理由・範囲・本文が計画そのもので、
  承認画面がそれを見せる。計画に文書が要る種類は `deliverables` で実施の成果物として求める
