# ADR-0078: フェーズの種類に依存（`after`）を持たせ、ワークフローを DAG で書く

状態: 採用（ADR-0026 の「順序は承認で止める」と、ADR-0070 の「線に向きは付けない」の一部を改める。図の下に常に出す注記は ADR-0082 が改める）

## 状況

2026-09-23。全体計画は種類の一直線の並びで、N 番目の子は 1〜N-1 番目の全部が閉じてレビューが
済むまで承認されない（ADR-0026）。並行できるのは種類どうしの `overlap` の組だけだった。

欲しいのは 2 つ。

- **ワークフローを DAG で書く。** 受入テストと実装を並べ、合流してから文書へ進む、のような形を
  一直線の例外（`overlap`）の組み合わせでなく、依存そのものとして書く
- **HITL（人が見るところ）の位置を、そのワークフローの上ではっきり決める。** 合流点で 2 本をまとめて
  見る、のような置き方を、人が持つ設定の側で決めたい

置き場所は 2 つ考えられた。親の `plan:` の項ごとに依存を書く形と、`phases.yml` の種類に書く形。
利用者の意図は後者（「phases.yml の定義を変えればいい」）。

最初の案（4efd3e4）を Sonnet と Opus の敵対的レビューにかけ、下の「レビューで直したこと」を入れた。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| 種類に **`after:`**（先に閉じてレビューが済んでいるべき種類）を足す。`kind: work` だけが持て、指せるのも `kind: work` だけ | ワークフローと HITL の位置を、人が持つ設定（§8 のコアファイル）の 1 か所で決める。エージェントは書き換えられない | `plan:` の項ごとに `after: [番号]` を書く。計画ごとに形を変えられるが、依存を決めるのがエージェントの提案になる |
| ファイルの頭に **`order: sequential | dag`**。既定は `sequential`（今までどおり） | `after` を 1 本書いただけで他の全部の組が並行に変わる、という暗黙の切り替えを作らない | `after` が 1 つでもあれば DAG と読む |
| **`dag` は、合成に入る層で `phases.yml` を持つものが全部 `dag` と書いたときだけ。** 食い違えば `sequential`、`--lint` は warn。共通層に `phases.yml` が無ければプロジェクトの層 1 本で決まる | 共通層が `sequential` のとき、緩む側への切り替えを、プロジェクトの `phases.yml` 1 本（clone や merge で届く）でできないようにする。共通層が無いときは種類そのもの（`review` を含む）もその 1 本で決まるので、`order` だけを別に扱う理由が無い | 共通層だけが持つ。このワークスペースは種類を自身の層に置いており、共通層に `phases.yml` が無い |
| **フィードバック計画は常に一直線。** `order` は全体計画にだけ効く | フィードバックの種類は `after` を持てず、`dag` を当てると全部が根になって並行し、延期の引き受け手も無くなる | フィードバックの種類にも `after` を許す |
| N 番目が待つのは、N より前の項のうち、種類が N の種類の**祖先**（`after` を推移的に辿る）か、N と同じ種類のもの | 計画に置かなかった種類を飛ばしても、依存が先へ引き継がれる。同じ種類を 2 度置いたら順に進む | 直接の `after` だけを見る |
| **待ち方は承認のときに計算し、親の承認済みチケットの `workflow:` に写す。** 判定・延期・フィードバック計画の前提は写しだけを読む | 種類は判定のたびに読み直しているので、写さないと `phases.yml` を直した瞬間に進行中の親の待ちが変わる。人が承認した計画の意味を、承認後に変えない。変えたければ改版（承認画面が待ちの差分を見せる） | 写さず、進行中の親がいる状態で `after` / `order` が変わったら `--lint` で警告する。直した瞬間に判定が変わり、緩む変更もそのまま効く |
| 計画に読めない種類が 1 つでもあれば、写しは `sequential` | 祖先が分からないものを並行にしない。読めなくなる経路（層の衝突でその層が空になる）では `order` の食い違いが起きないので、別に塞ぐ | — |
| 承認で、循環が無いこと、**並びが DAG と噛み合うこと**（後ろの項が前の項の祖先なら error）、**終端が 1 つ**（最後の項に対して、他のどの項も祖先か同じ種類）を確かめる | 待つのは前の番号だけなので、逆に並べると依存が黙って消えて並行になる（止まるのではなく緩む）。終端を 1 つにするのは、フィードバック計画の前提を 1 つの番号で言うため | 終端を複数許し、終端すべての依頼を前提にする |
| 延期（`defer`）の引き受け手は、後ろで延期した番号を待つ（写しの `waits` に持つ）、**延期していない**最小の番号（延期した子孫は飛ばす）。計算は写しを作る 1 か所で行い、`review_at` を読む側はみな写しを読む | 枝分かれがあると「次の番号」が延期した作業を含むとは限らない。子孫なら、引き受け手は延期した側が閉じるまで始まらない。計算を 2 か所に持つと違う引き受け手を言う | 引き受け手を項に明示させる（`review: {defer: 5}`） |
| HITL の位置は今までどおり種類の `review`（と計画の項の `mr` / `defer`）で決める。欄は増やさない | 人の手は承認・レビュー・受け入れの 3 か所（ADR-0030）。DAG で変わるのは「どこがフェーズの終わりか」の並びだけ | フェーズの始まりにも人の関門を置く欄を足す。子の承認がすでに毎フェーズ人の手を通っている |
| 承認画面に、各番号の待ち（「3 と 4 は並行」）を出す | 辺の書き漏れは並行として通る。それを人が見つける場所を、承認の手前に置く | `--explain` だけに出す |
| レビュー準備中・レビュー待ちで止めるのは、今までどおり**親ごと**（`DENY_PHASE_REVIEW`） | 枝ごとに開けると、人が見ていない間に先へ進む道が増える（判定が緩む）。止まる側に倒す | 止める単位・スレッド・受け入れをフェーズごとにする。並行は本当に効くが、レビューの仕組みをほぼ作り直すうえ判定が緩む。使ってみてから考える |
| **受け入れは、受け入れたフェーズとその子孫（写しの上で）にだけ効く** | 親ごとに受け入れを持つと、A のために受け入れた B のスレッドで、B のレビューが指摘を直さずに通る。`sequential` では後ろの番号はみな前を待つので、後ろの全部に効く | 受け入れを親ごとのままにする |
| 局面・次の案内を DAG で読む。作業中・レビュー準備中・レビュー待ちを番号で並べ、次の案内は待ちが済んだフェーズだけを挙げる | 最初の 1 つしか言わないと、同時にレビュー準備中の枝が見えず、まだ始められない番号を案内する | — |
| `overlap` はそのまま残す。`dag` の写しを作るとき、祖先が `overlap` の組なら待ちに入れない | 既存の設定の意味を変えない。整理（廃止か警告か）は別のチケット | `dag` では `overlap` を読まない |
| 同じ組を `after` と `overlap` の両方に挙げれば error。終端の検査は実際の待ち（`overlap` で外れた組を除く）で見る | 両方あると待ち方の計算は `overlap` を採り、書いた依存が黙って消える。依存を見る検査だけが通ると、終端が 1 つという前提が崩れる | `after` を優先する |
| 改版では、子が承認された番号までの延期の引き受け手を変えさせない。提案に `workflow:` があれば拒む | 引き受け手が前へ動くと、済んだレビューが延期した作業を引き受けたことになる。写しを書くのは `--approve` だけ | — |
| 層どうしの重なりの比較（`PhaseType.key()`）に `after` を入れる | 入れないと、`after` だけが違う同じ id が「全欄同じ」として捨てられ、層の `after` が黙って消える | — |

### フェーズ管理画面（拡張機能）

ADR-0070 は「`phases.yml` に順序の情報は無い。矢印を描くと無い制約を描くことになる」として向きの無い
図にした。`after` は順序そのものなので、**`after` の線にだけ向きを付ける。** `requires` と `overlap` は
今までどおり向きの無い線のまま。

| 決めたこと | なぜ |
|---|---|
| `after` は矢印付きの線（待たれる側 → 待つ側）。`requires`（実線）・`overlap`（破線）とは色で分ける | 3 種類を 1 枚に出しても読み分けられるように |
| そのファイルが `order: dag` と書いていれば、**ドラッグで置いていない点**を `after` の深さ（根からの最長の段数）で列に分け、列の中は id 順に並べる。ドラッグで置いた点は動かさない | 深さで並べないと合流と分岐が交差した線に埋もれる |
| 深さは、辿っている途中で同じ点に戻ったら、その点から先の深さを 0 として打ち切る。**画面は循環を見つけたとは言わず、並べ方も切り替えない** | 格子へ戻すと、循環の有無で並べ方が飛び、それ自体が画面の判定になる（ADR-0035）。循環の error は `--lint` と承認が出す |
| 見る場所が `chat` / `mr` の**種類**は、点の縁を強調する。図の下に「種類の宣言。計画の延期・実績のリスクで変わる」と添える | 実際に見る場所は計画の項と実績でも変わる（§9.8）。図が言えるのは種類の宣言まで |
| 図の下に、このファイルだけを描くこと（他の層の種類への `after` は描かず、その種類は根に見える）と、判定が使う `order` は層を合わせたうえで承認時に決まることを常に出す | 画面が受け取るのは層 1 本（ADR-0070）。見えない範囲を、見えないと書く |
| 一覧の編集に `after` の欄と、ファイルの頭の `order` の選択を足す | 関係を直すのは一覧、図は読むだけ（ADR-0070）を保つ |
| ボードの親カードには待ちを出さない | 利用者の判断。カードの幅で DAG を読ませるのは後で考える |

## 得たもの・失ったもの

- 得たもの: ワークフローの形と HITL の位置を、人が `phases.yml` の 1 か所で決められる。
  計画の書き方（`plan:` に種類を並べる）は変わらない
- 得たもの: `order` を書かない `phases.yml` は一直線のまま動く
- 失ったもの: **辺の書き漏れは並行として通る。** 判定の側に止める道は無く、人が書くときと承認画面の待ちの一覧で確かめるしかない。
  `sequential` では起こりえなかった、緩む向きの漏れ
- 失ったもの: **並行して進むのは、レビューとレビューの間だけ。** どれかの枝がレビュー準備中・レビュー待ちに入ると、
  その親からは別の枝にも新しい子を起こせない
- 失ったもの: 依頼を出したあとに別の枝を親ブランチへ合流すると、`check` が依頼のやり直しを求め、やり直した依頼には
  その枝の作業も入る
- 失ったもの: `phases.yml` を直しても進行中の親には効かない。効かせるには改版が要る
- 失ったもの: 計画ごとにワークフローの形を変えられない。層は他の層の種類に `after` を足せない
- 失ったもの: 承認済みチケットに欄（`workflow:`）が 1 つ増え、承認の検査が増える（循環・並び・終端・延期の引き受け手）。
  `accepted.json` に受け入れた番号が加わる
- 失ったもの: `dag` の図は、`after` を足しても消しても、ドラッグしていない点が動く。ADR-0070 が避けた
  「線を触ると絵が飛ぶ」を、`after` についてだけ受け入れる。`requires` / `overlap` を触っても動かない

## レビューで直したこと

4efd3e4 への敵対的レビュー（Sonnet・Opus）の指摘と、どう直したか。

| 指摘 | 直したこと |
|---|---|
| `phases.yml` を判定のたびに読むので、承認後に `after` / `order` を直すと進行中の親の待ちと延期が変わり、レビューが消える（両方） | 承認時に写す `workflow:` |
| レビュー待ちで親ごと止めると並行はほぼ効かない。依頼中の合流で依頼が壊れ、受け入れが別の枝に漏れる（両方） | 止め方は変えず、失ったものに正直に書いた。受け入れをフェーズと子孫に結んだ |
| 終端の検査が、同じ種類を 2 度置いた計画を拒む（両方） | 「祖先か同じ種類」 |
| 種類が読めないと祖先が空になり、何も待たない | 写しを `sequential` で書く |
| フィードバック計画にも `dag` が効く書き方で、全部が並行し延期も書けない | フィードバック計画は常に一直線 |
| 「逆に並ぶと永久に始まらない」は誤りで、実際は依存が消えて緩む | 理由を直した |
| 層ごとの `order` の読み方が無い。プロジェクト 1 本で `dag` に切り替えられうる | 全員が `dag` と書いたときだけ |
| 延期の引き受け手に延期した子孫を含むかが曖昧。`review_at` を使う箇所が 4 つあり二重になる | 延期していない最小の子孫。計算は写しを作る 1 か所 |
| 局面と次の案内が最初の 1 つしか言わない | 番号で並べ、待ちの済んだものだけを案内する |
| 承認画面に待ちが出ない | 出す |
| 図の「人が見る」強調が実態とずれる。循環で格子に戻すのは画面の判定 | 種類の宣言と明記。循環でも並べ方を切り替えない |
| `PhaseType.key()` に `after` を入れ忘れると層の `after` が消える | 決定に入れた |
| `order` の食い違いを承認で扱うかが本文に無い | 食い違いは `sequential` に倒す、と 1 か所で書いた（写しがそれを使う） |

## やらなかった場合

並行できるのは `overlap` の組だけで、合流を書く手段が無い。合流点で人が見るには、一直線に並べて
前の項を `defer` にするしかなく、並行の分だけ待つ時間が増える。
