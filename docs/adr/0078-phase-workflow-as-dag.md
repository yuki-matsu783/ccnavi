# ADR-0078: フェーズの種類に依存（`after`）を持たせ、ワークフローを DAG で書く

状態: 採用（ADR-0026 の「順序は承認で止める」と、ADR-0070 の「線に向きは付けない」の一部を改める）

## 状況

2026-09-23。全体計画は種類の一直線の並びで、N 番目の子は 1〜N-1 番目の全部が閉じてレビューが
済むまで承認されない（ADR-0026）。並行できるのは種類どうしの `overlap` の組だけだった。

欲しいのは 2 つ。

- **ワークフローを DAG で書く。** 受入テストと実装を並べ、合流してから文書へ進む、のような形を
  一直線の例外（`overlap`）の組み合わせでなく、依存そのものとして書く
- **HITL（人が見るところ）の位置を、そのワークフローの上ではっきり決める。** 合流点で 2 本をまとめて
  見る、のような置き方を、人が持つ設定の側で決めたい

置き場所は 2 つ考えられた。親の `plan:` の項ごとに依存を書く形と、`phases.yml` の種類に書く形。
利用者の意図は後者（「phases.yml の定義を変えればいい」）。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| 種類に **`after:`**（先に閉じてレビューが済んでいるべき種類）を足す。`kind: work` だけが持て、指せるのも `kind: work` だけ | ワークフローと HITL の位置を、人が持つ設定（§8 のコアファイル）の 1 か所で決める。エージェントは書き換えられない | `plan:` の項ごとに `after: [番号]` を書く。計画ごとに形を変えられるが、依存を決めるのがエージェントの提案になり、人は承認画面で辺を読むことになる |
| ファイルの頭に **`order: sequential | dag`**。既定は `sequential`（今までどおり） | `after` を 1 本書いただけで他の全部の組が並行に変わる、という暗黙の切り替えを作らない。緩む向きの切り替えは明示させる | `after` が 1 つでもあれば DAG と読む。書き足した 1 行で判定が広く緩む |
| 層どうしで `order` が食い違う、または `after` に循環がある → `--lint` の error、判定は `sequential` に倒す | 読めないときは待つ側に倒す（§9.8 の「緩い側に倒すと行き先が消える」と同じ向き） | どちらかの層を採る |
| N 番目が待つのは、N より前のフェーズのうち、種類が N の種類の**祖先**（`after` を推移的に辿る）か、N と同じ種類のもの | 計画に置かなかった種類を飛ばしても、飛ばした種類が待っていたものが先へ引き継がれる。同じ種類を 2 度置いたら順に進む | 直接の `after` だけを見る。飛ばした種類のところで依存が切れる |
| 承認で、並びが DAG と噛み合うこと（後ろの項が前の項の祖先なら error）と、**最後の項が他の全部を祖先に持つこと**（終端は 1 つ）を確かめる | 番号の小さいほうから始まるので、逆に並ぶと永久に始まらない。フィードバック計画の前提「最後のフェーズまで閉じて依頼した」を、1 つの番号で言える形に保つ | 終端を複数許し、終端すべての依頼を前提にする。延期と前提の検査が番号 1 つで済まなくなる |
| 延期（`defer`）の引き受け手は、後ろにある子孫のうちレビューのある最小の番号。居なければ承認の error | 枝分かれがあると「次の番号」が延期した作業を含むとは限らない。子孫なら、引き受け手は延期した側が閉じるまで始まらないので、依頼に中身が必ず入る | 引き受け手を項に明示させる（`review: {defer: 5}`）。書く手間の割に、選べる候補がほぼ 1 つしかない |
| HITL の位置は今までどおり種類の `review`（と計画の項の `mr` / `defer`）で決める。欄は増やさない | 人の手は承認・レビュー・受け入れの 3 か所（ADR-0030）。DAG で変わるのは「どこがフェーズの終わりか」の並びだけで、見る場所の決め方は変えなくてよい | フェーズの始まりにも人の関門を置く欄を足す。子の承認がすでに毎フェーズ人の手を通っている |
| レビュー準備中・レビュー待ちで止めるのは、今までどおり**親ごと**（`DENY_PHASE_REVIEW`） | 枝ごとに開けると、人が見ていない間に先へ進む道が増える（判定が緩む）。並行の効き目は減るが、止まる側に倒す | 関係の無い枝は通す。別に相談して決める |
| `overlap` はそのまま残す。`order: dag` の中でも、待つはずの祖先が `overlap` の組なら待たない | 既存の設定の意味を変えない。整理（廃止か警告か）は別のチケット | `dag` では `overlap` を読まない |
| `--explain` は計画の各項に待つ番号を添える。作業中が 2 つ以上なら並べて言う | エージェントが「今どれを始められるか」を 1 回で読める | JSON の `phases[]` にも `after` を足してボードに出す。今回はボードのカードに出さない（利用者の判断）ので、契約は増やさない |

### フェーズ管理画面（拡張機能）

ADR-0070 は「`phases.yml` に順序の情報は無い。矢印を描くと無い制約を描くことになる」として向きの無い
図にした。`after` は順序そのものなので、**`after` の線にだけ向きを付ける。** `requires` と `overlap` は
今までどおり向きの無い線のまま。

| 決めたこと | なぜ |
|---|---|
| `after` は矢印付きの線（待たれる側 → 待つ側）。`requires`（実線）・`overlap`（破線）とは色で分ける | 3 種類を 1 枚に出しても読み分けられるように |
| `order: dag` のとき、**ドラッグで置いていない点**は `after` の深さ（根からの最長の段数）で列を分け、列の中は id 順に並べる。`sequential` のときと、循環があって深さが決まらないときは今までどおり id 順の格子 | 深さで並べないと合流と分岐が交差した線に埋もれる。ドラッグで置いた位置は控えのまま動かさない |
| 見る場所が `chat` / `mr` の種類は、点の縁を強調して「人が見る」を添える | HITL の位置を図の上で一目で読めるように |
| 一覧の編集に `after` の欄と、ファイルの頭の `order` の選択を足す | 関係を直すのは一覧、図は読むだけ（ADR-0070）を保つ |
| 循環は画面では言わない。深さが決まらなければ格子に戻すだけ | 判定は実行ファイル（ADR-0035）。循環の error は `--lint` が出す |
| ボードの親カードには待ちを出さない | 利用者の判断。カードの幅で DAG を読ませるのは後で考える |

## 得たもの・失ったもの

- 得たもの: ワークフローの形と HITL の位置を、人が `phases.yml` の 1 か所で決められる。
  計画の書き方（`plan:` に種類を並べる）は変わらない
- 得たもの: `order` を書かない `phases.yml` は今までと同じに動く
- 失ったもの: **辺の書き漏れは並行として通る。** 判定の側に止める道は無く、人が書くときと図で確かめるしかない。
  `sequential` では起こりえなかった、緩む向きの漏れ
- 失ったもの: 計画ごとにワークフローの形を変えられない。変えたければ種類を分けて定義する
- 失ったもの: 承認の検査が 3 つ増える（並び、終端、延期の引き受け手）。`order` の食い違いと循環の検査も増える
- 失ったもの: `order: dag` の図は、`after` を 1 本足すとドラッグしていない点が動く。ADR-0070 が避けた
  「線を足すと絵が飛ぶ」を、`after` についてだけ受け入れる。関係の無い `requires` / `overlap` を足しても動かない
- 失ったもの: 片方の枝のレビュー待ちで、もう片方も止まる

## やらなかった場合

並行できるのは `overlap` の組だけで、合流を書く手段が無い。合流点で人が見るには、一直線に並べて
前の項を `defer` にするしかなく、並行の分だけ待つ時間が増える。
