# ADR-0073: 実行後の監視は、自分の副命令の書き込みを姿で見分ける

状態: 採用

## 状況

実行後の監視は、保護領域をルールファイルの `deny` と `ask` から導く（ADR-0017）。そこから
外れるのは記録と控えの置き場（`CCNAVI_LOG`、`CCNAVI_STATE`）だけだった。

承認済みチケットの置き場（`.ccnavi/approved/`）は、このリポジトリの共通層が
`deny`（`guard-approved-tickets`）と宣言している。ワークスペースルートなら `main-tree` も
同じ場所に当たる。そこへ書くのは、人の承認だけではない。**`ccnavi-ticket.sh` の
`start` / `done` / `cancel` と、`ccnavi-review.sh` の `request` / `check` / `ready` が書く。**
着手の時刻と基準点、レビュー待ちへの移動、フェーズのマーカー。どれも手順を進めるための
書き込みで、置き場は `deny` の中にある。

結果、実行後の監視はこれを毎回「エージェントによる書き換え」として報告していた。文面は
`ccnavi did not touch this path` で、自分が書いたことを自分で否定していた。`CCNAVI_MODE` と
`CCNAVI_RESTORE_IF_DENY` の両方を `enable` にすると、**`start` が書いた着手の時刻は
コミット済みの内容へ戻り、`ready` が置いたマーカーは `state/aside/` へ退避される。**
手順はそこで止まる。再現して確かめた。2026-09-22。

実行前の判定はこの経路を通している（`tests/guard/test_repo_rules.py`）。スクリプトを叩くこと
自体は通り、書いた結果だけが咎められる、という食い違いになっていた。

`is_ticket_place` は既にあり、実行前の判定と、ターンの終わりの「コミットに入ったぶん」
（ADR-0072）はこれで置き場を外している。ただしその根拠は「外しても、承認済みチケットは
自己防衛の組み込みが `deny` で止めるから」で、**組み込みを足すのは `judge` だけ。実行後の
ルール集合には 1 本も入らない。** 置き場をそのまま外すと、後ろには何も残らない。

## 決定

- 実行後の監視は、チケットの置き場（提案と承認済みチケット）の変更を **内容で見分けて外す**
  （`post._script_writes`）。外れるのは 3 つ
  - どちらの版も範囲を宣言していないもの（マーカー、`.risk.json`、閉じの記録）
  - スクリプトだけが書く欄（`ticket.SCRIPT_FIELDS`）以外が 1 文字も変わっていないチケット
    （`ticket.script_shape` が同じ姿を返す）
  - `done` と `cancel` の移動。同じ姿のチケットが消えて、レビュー待ち
    （`wip/proposals/review/`）か閉じた置き場（`.ccnavi/approved/done/`）に現れた組。
    片側だけなら外さない
- **範囲・親・フェーズ・本文が変わったチケット、新しく現れた承認済みチケット、消えただけの
  チケットは今までどおり報告する。**
- **読めなかったものは外さない。** git を起こせない、期限に達した、HEAD が無い、ファイルを
  読めない。どれも「変わっていない」ではない
- 誰が書いたかの台帳は持たない

## 理由

**台帳を持たない理由。** 承認とマーカーは親のブランチに乗って別の機械へ届き、clone すれば
続きができる（設計 §9.2、REQ-MLT-14）。台帳はワークスペース側にあって git に入らないので、
届いた先には 1 件も無い。台帳で見ると、同じ操作がその機械でだけ報告される。内容で見れば、
どの機械でも同じ答えになる。

**置き場をまるごと外さない理由。** 承認済みチケットの frontmatter は、そのワークツリーの
作業範囲そのもの。まるごと外すと、引数に現れない書き込み（シェル、ビルドの出力、スクリプトが
内部で開くファイル）で自分の範囲を広げる道が、どの面からも報告されないまま 1 本できる。
実行後の監視は、まさにその経路のために置かれている。

**戻す側だけを止める道（`_restorable` でチケットの置き場を外す）も採らなかった。** 事故は
消えるが、報告は残る。`undo:` の手順が毎回モデルに届き、親切に実行されればやはり手順が戻る。

**移動の行き先を 2 つに絞った理由。** `doing/` から出したチケットを `todo/` に置き直す形は、
承認済みチケットを消すのと同じ効き目を持つ。承認済みチケットが 1 本も無いワークツリーは
範囲を持たず、範囲を持たないツリーはチケットの側から何も言われない。

## 得たもの

- **ccnavi 自身の手順が、自分の監視で止まらない。** `CCNAVI_RESTORE_IF_DENY=enable` に
  寄せられる
- 実行前と実行後の言うことが揃った。スクリプトを叩くことが通り、その結果も通る
- 承認済みチケットが宣言する範囲は、引数に現れない書き込みに対しても見張られたまま
- 別の機械へ clone した続きでも、同じ変更が同じように外れる

## 代償

- **マーカーの偽造と削除は、実行後の監視からは見えなくなった。** `<N>.reviewed` を置いて
  「レビュー済み」に見せる形も、置かれたものを消す形も、範囲を宣言しないので内容から
  見分けられない。実行前は組み込みが名指しのツールとシェルを止めるが、引数に現れない
  書き込みは通る。ここを塞ぐには台帳が要る
- **git を 1 回多く起こす。** チケットの置き場に変更があった回だけ、その 1 本につき
  `git show HEAD:<path>`（新しく現れたファイルなら `ls-tree` も）が増える
- **`ticket.SCRIPT_FIELDS` を増やすと、外れる範囲が広がる。** 欄を 1 つ足すことが、
  監視の穴を 1 つ足すことになる。足すときはここを思い出す必要がある
- 突き合わせは行単位なので、スクリプトが欄の書き方を変えた（1 行の値を複数行にした、など）
  回は姿が変わり、報告が出る。出たときに直すのは監視ではなくスクリプトの側
