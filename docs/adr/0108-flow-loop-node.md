# ADR-0108: 子のフローの反復は loop ノードで書き、loop を通らない巡回は warn で言う

状態: 採用（実装済み。2026-10-06 にユーザが決めた）

## 状況

子のフローは、順次（線）と分岐（`ifElse` / `switch` / 問い）は書けたが、反復を表す種類が無かった。
反復は、分岐の出口から前のノードへ線を戻すことでしか書けず、次の問題があった。

- 戻り線が反復なのか単なる飛び先なのかが、構造から分からない。変換の文にも図にも「繰り返し」と出ない
- 「最大 3 回まで」を書くなら線の `condition` の文字列で、検査も表示もできない
- 条件の書き間違いで終わらないフローが、保存の時点では見つからない（巡回は意図して書くことがあるので、検査は巡回を言わなかった）

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| `loop` ノードを足す。`data` は `condition`（続ける条件）・`maxIterations`（1 以上の整数）・`branches`（`body` = 繰り返す、`done` = 抜ける の 2 項目） | 反復が構造に出る。上限を欄にでき、検査と表示ができる | 戻り線の `condition` に「最大 N 回」を書く決まりだけで済ませる（回数が文字列のままで検査があいまい） |
| 出口は既存の分岐と同じ仕組み（`branches` の項目の `id` か `branch-<番号>`）で持ち、BRANCH_KEYS に `loop` を足す | 出口の読み・変換の分岐名・「出口に線が無い」の検査を作り直さずに済む。ボードの線の言葉も同じ読み方のまま | `loop` 専用の出口（`body` / `done` の固定ポート）を別に読む |
| 手順の行は `[loop] 名前: 条件: … / 最大 N 回 → 繰り返す側, 抜ける側`。`loop` があるフローには、数え方と「最大に達しても条件が成り立つなら最後の報告に書く」の段落を足す | 数えるのはサブエージェントで、ccnavi は強制しない（フローは案内で、判定の材料ではない）。上限に達して抜けたことが黙って消えないようにする | 段落を足さず、行だけを渡す |
| `--lint --flow` の warn に、`maxIterations` が 1 以上の整数でない・出口（`branches`）が 2 つでない・`loop` を通らない巡回、を足す。読むのも保存も止めない | 上限の無い反復と、`loop` を通らず終わらなくなりうる巡回に、保存の時点で気づける | 巡回は従来どおり言わない／error にして保存を止める（既存のフローを読めなくする） |
| 画面（ボード）は部品箱に「繰り返し」を足し、`condition` と `maxIterations` の欄を持つ。出口の 2 項目は固定で、増減や label の編集はできない | 2 項目が崩れると、変換と検査の前提が崩れる | `ifElse` と同じく項目を増減できる |

## 得たもの・失ったもの

- 得たもの: 反復が変換の文・図・検査に出る。上限の回数が欄になる。終わらない巡回に保存の時点で気づける
- 失ったもの: 「`loop` を通らない巡回は書かない」という新しい決まりが増え、従来は黙って通った巡回に warn が出る（止めはしない）。
  ノードの種類が 1 つ増え、ボード・実行ファイル・文書・テストを揃えて保つ手間が増える。
  `loop` は外のエディタが知らない独自の種類になりうる。知らない種類は落とさず名前だけで並ぶので、読めなくはならない
- 変わらないもの: 回数を数えて止まるのはサブエージェント。ccnavi は上限を強制しない

## 採らなかった案

- 戻り線の `condition` に「最大 N 回」と書く決まりと、`--lint` の巡回 warn だけにする: 安いが、回数が文字列のままで、検査があいまいになる
- 上限を強制する（hook で回数を数えて止める）: フローは判定の材料にしないという前提（設計 9.3.1）を崩す
