# ADR-0012: ルールが読めないときは組み込みの既定に落ちる

状態: 採用

## 状況

以前はルールファイルが読めないと、`enable` で全ツール呼び出しが終了コード 2 で止まっていた。
壊れたファイルを直すための呼び出しも止まるのでセッションが死ぬ。既定モードが `enable` なので、
ルールを置く前に hook を登録しただけで踏む。要件書に「設定が読めないは判断できないではなく
設定が壊れているであり、拒否側へ倒すと壊れた設定を直す操作まで止まって回復できなくなる」
（REQ-PRE-06）と書いてあったとおりのことをやっていた。

## 決定

ルールファイルが無い・壊れているときは、組み込みの既定で判定を続ける。既定に入れるのは
取り返しの付かない操作だけ：`rm -rf`、`git push`、`git reset --hard`、認証情報の置き場、
シェルからガード自身の設定への書き込み。`Read` は通す。既定に落ちたことは、止めた回だけでなく
通した回にも伝え、記録に `fallback` を残す。

`Write` / `Edit` によるルールファイルの編集は既定では通し、シェルからの書き込みは止める。
マージの衝突を `git add` / `git restore --ours` で解く形も通す。

## 理由

ガードが落ちている最中はルールの一覧が信用できないので、広く止めても「なぜ止まったのか」を
確かめる手立てが利用者に無い。止める数ではなく、止めそこねたときに戻せないものを見る。

`Write` / `Edit` を通し、シェルを止めるのは対になっている。通常のルールは前者を止めているが、
既定で止めると直す道が 1 本も残らない。一方でシェルを開けると、`echo x > rules.yml` でルールを
壊し、壊れた結果として緩んだ既定に落ちる、という順路ができる。壊す側と直す側で経路を
分けることでそれを閉じた。

止めるのは書き込む綴りだけで、場所の名前が出たかどうかでは止めない。衝突マーカーの入った
ルールファイルは YAML として読めないので、衝突を解いている最中は必ず既定に落ちている。
そこで名前が出たら止める形にすると、いちばんガードを直したいときにいちばん強く効く。

通した回にも伝えるのは、黙って落ちると、ガードが立っているように見えて実際はプロジェクトの
ルールを 1 件も見ていない状態が続くから。それはガードが止まっているより悪い。

## 得たもの・失ったもの

- 得たもの: 壊れた設定を直す道が残る
- 失ったもの: 既定にはプロジェクトの `allow` が無いので、読み取り以外はほぼ確認になる。
  本当に見てほしい 1 件がその中に埋もれる。REQ-PRE-06 の「修復を妨げない」は満たしている。
  妨げるのは `deny` だけで、`ask` は人が答えれば進む

## 採らなかった案

- 読めなければ全部止める。上のとおり
- 読めなければ全部通す。ガードが消えたことに気づけない
