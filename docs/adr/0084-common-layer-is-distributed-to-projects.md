# ADR-0084: 共通層は配る定義にし、親の着手でプロジェクトの層を上書きして最初のレビューで知らせる

状態: 採用

## 状況

2026-09-24、共通層を持つ意味を利用者と見直した。発端は配点の穴。

- 配点（`risks.yml`）の合成は、同じ `id` で中身の違う項目が共通層とプロジェクトの層にあると、error にして
  **その層を空として扱っていた**。項目も境目の点も落ち、点が下がる。プロジェクトが共通層と同じ名前（`big-diff` など）の
  項目を 1 本書くだけで起きる
- 根はもっと深かった。共通層はワークスペースの git にあり、プロジェクトだけを clone した人からは見えない。同じプロジェクトを
  別のワークスペースで扱う人は、どの共通層で判定され、どの配点で数えられたかを知る手段が無い

途中で 2 つの案を検討して落とした（下の表）。敵対的レビュー（2 本）で、フェーズの種類と配点を各ツリーの層だけにする案は
配点の下限が外れることが指摘された。利用者の判断は「2 重管理になっても、プロジェクトの側だけを見ている人が気づけない状況が
いちばんよくない」。

## 決定

**共通層は、共通の設定を各プロジェクトへ配るための定義。正本は各プロジェクトの `.ccnavi/config/`。**

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| プロジェクト向けの親の `ticket start` で、共通層にあるファイルごとに、親のワークツリーのプロジェクトの層と比べ、違えば共通層の中身で上書きする | 作業の直前で、ワークツリーがある。上書きした中身は親のブランチに乗って、プロジェクトの git で見られる | 承認のときに写す（承認は人がボードか端末で打つ場面で、ワークツリーに書く場面ではない）。子の着手でも写す（子は親のブランチに乗る） |
| 写す先は `.ccnavi/config/{rules,phases,risks}.yml` そのもの | 置き場を分けると、見る場所が増えて分かりにくい（利用者の判断） | `.ccnavi/config/common/` に別に置く |
| 共通層に無いファイルは消さない | このワークスペースの共通層に `phases.yml` は無い。消すとプロジェクトのフェーズの種類が消え、計画が承認で止まる | 共通層に無いファイルも消して揃える |
| 上書きで消える識別子を、着手の出力と印に名指しする | 黙って消えるのを避ける | 言わずに上書きする |
| 印 `phases/<親>/config-sync.json` を置き、最初のレビュー（依頼の本文か chat の確認）の頭に載せ、`notified` に残す | 上書きを人の目に通す。2 回目以降は繰り返さない | 着手を止めて人に写させる（止まる理由が「共通層が新しい」だけのことが多い） |
| 判定の仕組みは変えない | 共通層の守り（`deny`、配点の項目、境目の点の min）が下限として残る | フェーズの種類と配点を各ツリーの層だけにする（下限が外れる） |
| 配点が指す共通層のスクリプトも写し、`script:` の指す先をプロジェクトの層の綴りに直す | 層から共通層のスクリプトは指せない。直さずに写すと、プロジェクトの配点が層ごと壊れる（敵対的レビューの指摘。利用者の判断で「一緒に写す」） | `script:` を持つ配点は写さない |
| 写す前にプロジェクトの層として読めるかを確かめ、写す先に未コミットの変更があれば止める。印を先に置き、1 本でも書けなければ全部戻す | 壊れた設定を配らない。人の書きかけを踏まない。途中で止まっても知らせを失わない | 読めるかを見ずに写す |
| 知らせていない親は、利用者が端末で `ccnavi --config-synced <親>` を打つまで閉じず、Draft も外さない（`close_problems` に置き、finish と ready の両方が通る）。締めるときは締める前の確認に知らせを出す | 計画の無い親や `review: none` だけの親は、最初のレビューを通らず、知らせが人に届かない | 閉じるときに出力で知らせるだけにする（読むのはエージェントで、人に届く保証が無い） |
| 写した書き込みは、実行後の監視と控えと復元が、置き場（承認済みの親チケットのワークツリー）・リンクが無いこと・内容（共通層と同じ）・その親の印（その指紋を名指し）・変更前のコミット済みの中身（印の上書き前と同じ）の 5 つで見分けて外す。コミットに入った分はコミットされた中身をバイト列で見る | 外さないと、着手が写した中身が同じ呼び出しで戻され、報告される。台帳は持たない（ADR-0075 と同じ理由）。印をその親に限らないと、1 度どこかで写したあとは、どのワークツリーでも共通層の中身へ戻す書き込みが外れる（敵対的レビューで再現） | 中身だけで見る（シェルで写した分も外れ、知らせが残らない）。どこかのツリーの印で見る（上のとおり外れる）。ディスクの中身で見る（コミットしてからディスクだけ戻す形が外れる） |
| 配点の同じ `id` で中身が違う項目は、層を空にせず両方を数え、後ろの層の側を `<層>:<id>` と名乗らせる（warn） | 空にすると点が下がる。配点は足すだけの仕組みなので、両方を数えれば加点を増やす側にしか働かない。ルールの同じ `id` と同じ扱い | 空にしたまま lint の error で目に付かせる |

## 得たもの・失ったもの

- 得たもの: プロジェクトだけを clone した人が、どの共通層のもとで作業されたかをプロジェクトの git で見られる
- 得たもの: 共通層が変わると、次の親の最初のレビューで人の目を通る
- 得たもの: 配点の同じ `id` で点が下がる穴が塞がった
- 失ったもの: 2 重管理になる。共通層とプロジェクトの層は、次の親の着手まで食い違いうる
- 失ったもの: プロジェクトの層に、共通層にあるファイルと同じ名前でプロジェクトだけの設定を持てない。次の着手で上書きされる
- 失ったもの: 違う共通層を持つワークスペースどうしが同じプロジェクトを扱うと、着手のたびに上書きが入れ替わり、知らせが出る
- 失ったもの: 並行する 2 本の親が別々に上書きすると、統合先へ戻すときに衝突しうる
- 失ったもの: 共通層のルールの中身がプロジェクトの git に入る。public のリポジトリなら外に出る
- 失ったもの: 「見える」ようにはなるが「揃う」わけではない。プロジェクトだけを clone した人の判定は、その人の共通層とプロジェクトの層の和で決まる
- 失ったもの: 配点の衝突した定性の項目は `lib:outward` のように接頭辞付きで `record-risk` する。移行のとき、作業中の子に
  `<層>:<id>` の定性の項目が新しく現れ、その判定が揃うまで `finish` が止まることがある（前は層ごと落ちていた項目が数えられるようになるため）
- 失ったもの: レビューの無い親は、閉じる前に人の端末での 1 手が要る
- 失ったもの: 印は範囲を宣言しないマーカーなので、承認済みの親のワークツリーの中で、写した分をコミットする前なら、シェルから間接的に
  印と中身を書けば外れる。ただし中身は共通層と同じでなければならない。2 回目の敵対的レビューで、チケットの無いワークツリー、
  シンボリックリンク、人が直したあとの書き戻しでも外れることが分かり、条件を足して塞いだ
- 失ったもの: 配点の同じ項目かの判定で、`script:` の指すスクリプトを読む（中身で比べる）

## 採らなかった案

| 案 | 落とした理由 |
|---|---|
| フェーズの種類と配点を各ツリーの層だけにし、共通層はルールだけにする | 配点の下限が外れ、外から届く 1 コミット（セッションの頭の自動 ff で効く）でレビュー要否を緩められる |
| 承認のときに合成した配点の定義を親に写し、その写しで数える | 定義は揃うが、承認した人の共通層が黙って決める。人が気づく場面が無い |
| `.risk.json` に数えた定義の指紋を残すだけ | ずれは後から追えるが、作業の前に人が気づく場面が無い |
| 判定でもプロジェクトの層だけを見て、共通層を読まない | 原則には沿うが、次の着手までの間、プロジェクトの設定を緩める 1 コミットがそのまま効く。今回は判定を変えずに置いた |
