# ADR-0084: 共通層は配る定義にし、親の着手でプロジェクトの層を上書きして最初のレビューで知らせる

状態: 採用

## 状況

2026-09-24、共通層を持つ意味をユーザと見直した。発端は配点の穴。

- 配点（`risks.yml`）の合成は、同じ `id` で中身の違う項目が共通層とプロジェクトの層にあると、error にして
  **その層を空として扱っていた**。項目も境目の点も落ち、点が下がる。プロジェクトが共通層と同じ名前（`big-diff` など）の
  項目を 1 本書くだけで起きる
- 原因はもっと深いところにあった。共通層はワークスペースの git にあり、プロジェクトだけを clone したユーザからは見えない。同じプロジェクトを
  別のワークスペースで扱うユーザは、どの共通層で判定され、どの配点で数えられたかを知る手段が無い

途中で 2 つの案を検討して落とした（下の表）。敵対的レビュー（2 本）で、フェーズの種類と配点を各ツリーの層だけにする案は
配点の下限が外れることが指摘された。ユーザの判断は「2 重管理になっても、プロジェクトの側だけを見ているユーザが気づけない状況が
いちばんよくない」。

## 決定

**共通層は、共通の設定を各プロジェクトへ配るための定義。正本は各プロジェクトの `.ccnavi/config/`。**

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| プロジェクト向けの親の `ticket start` で、共通層にあるファイルごとに、親のワークツリーのプロジェクトの層と比べ、違えば共通層の中身で上書きする | 作業の直前で、ワークツリーがある。上書きした中身は親のブランチに入って、プロジェクトの git で見られる | 承認のときにコピーする（承認はユーザがボードか端末で打つ場面で、ワークツリーに書く場面ではない）。子の着手でもコピーする（子は親のブランチに入る） |
| コピー先は `.ccnavi/config/{rules,phases,risks}.yml` そのもの | 置き場を分けると、見る場所が増えて分かりにくい（ユーザの判断） | `.ccnavi/config/common/` に別に置く |
| 共通層に無いファイルは消さない | このワークスペースの共通層に `phases.yml` は無い。消すとプロジェクトのフェーズの種類が消え、計画が承認で止まる | 共通層に無いファイルも消して揃える |
| 上書きで消える識別子を、着手の出力と上書きの記録に名指しする | 気づかないうちに消えるのを避ける | 言わずに上書きする |
| 上書きの記録 `phases/<親>/config-sync.json` を置き、最初のレビュー（依頼の本文か chat の確認）の頭に載せ、`notified` に残す | 上書きをユーザの目に通す。2 回目以降は繰り返さない | 着手を止めてユーザにコピーさせる（止まる理由が「共通層が新しい」だけのことが多い） |
| 判定の仕組みは変えない | 共通層の保護（`deny`、配点の項目、境目の点の min）が下限として残る | フェーズの種類と配点を各ツリーの層だけにする（下限が外れる） |
| 配点が指す共通層のスクリプトもコピーし、`script:` の指す先をプロジェクトの層のパスに直す | 層から共通層のスクリプトは指せない。直さずにコピーすると、プロジェクトの配点が層ごと使えなくなる（敵対的レビューの指摘。ユーザの判断で「一緒に写す」） | `script:` を持つ配点はコピーしない |
| コピーする前にプロジェクトの層として読めるかを確かめ、コピー先に未コミットの変更があれば止める。上書きの記録を先に置き、1 本でも書けなければ全部戻す | 壊れた設定を配らない。ユーザの書きかけを上書きしない。途中で止まっても知らせを失わない | 読めるかを見ずにコピーする |
| 知らせていない親は、ユーザが端末で `ccnavi --config-synced <親>` を打つまで閉じず、Draft も外さない（`close_problems` に置き、finish と ready の両方が通る）。早めに閉じるときは、閉じる前の確認に知らせを出す | 計画の無い親や `review: none` だけの親は、最初のレビューを通らず、知らせがユーザに届かない | 閉じるときに出力で知らせるだけにする（読むのはエージェントで、ユーザに届く保証が無い） |
| コピーで入った書き込みは、実行後チェックとバックアップと復元が、置き場（承認済みの親チケットのワークツリー）・リンクが無いこと・内容（共通層と同じ）・その親の上書きの記録（その指紋を名指し）・変更前のコミット済みの中身（上書きの記録が持つ上書き前と同じ）の 5 つで見分けて外す。コミットに入った分はコミットされた中身をバイト列で見る | 外さないと、着手がコピーした中身が同じ呼び出しで戻され、報告される。台帳は持たない（ADR-0075 と同じ理由）。上書きの記録をその親に限らないと、1 度どこかでコピーしたあとは、どのワークツリーでも共通層の中身へ戻す書き込みが外れる（敵対的レビューで再現） | 中身だけで見る（シェルでコピーした分も外れ、知らせが残らない）。どこかのツリーの上書きの記録で見る（上のとおり外れる）。ディスクの中身で見る（コミットしてからディスクだけ戻す形が外れる） |
| 配点の同じ `id` で中身が違う項目は、層を空にせず両方を数え、後ろの層の側を `<層>:<id>` と名乗らせる（warn） | 空にすると点が下がる。配点は足すだけの仕組みなので、両方を数えれば加点を増やす側にしか働かない。ルールの同じ `id` と同じ扱い | 空にしたまま lint の error で目に付かせる |

## 得たもの・失ったもの

- 得たもの: プロジェクトだけを clone したユーザが、どの共通層のもとで作業されたかをプロジェクトの git で見られる
- 得たもの: 共通層が変わると、次の親の最初のレビューでユーザの目を通る
- 得たもの: 配点の同じ `id` で点が下がる穴が無くなった
- 失ったもの: 2 重管理になる。共通層とプロジェクトの層は、次の親の着手まで食い違いうる
- 失ったもの: プロジェクトの層に、共通層にあるファイルと同じ名前でプロジェクトだけの設定を持てない。次の着手で上書きされる
- 失ったもの: 違う共通層を持つワークスペースどうしが同じプロジェクトを扱うと、着手のたびに上書きが入れ替わり、知らせが出る
- 失ったもの: 並行する 2 本の親が別々に上書きすると、統合先へ戻すときに衝突しうる
- 失ったもの: 共通層のルールの中身がプロジェクトの git に入る。public のリポジトリなら外に出る
- 失ったもの: 「見える」ようにはなるが「揃う」わけではない。プロジェクトだけを clone したユーザの判定は、そのユーザの共通層とプロジェクトの層の和で決まる
- 失ったもの: 配点の衝突した定性の項目は `lib:outward` のように接頭辞付きで `record-risk` する。移行のとき、作業中の子に
  `<層>:<id>` の定性の項目が新しく現れ、その判定が揃うまで `finish` が止まることがある（前は層ごと落ちていた項目が数えられるようになるため）
- 失ったもの: レビューの無い親は、閉じる前にユーザの端末での 1 手が要る
- 失ったもの: 上書きの記録は範囲を宣言しないファイルなので、承認済みの親のワークツリーの中で、コピーした分をコミットする前なら、シェルから間接的に
  上書きの記録と中身を書けば外れる。ただし中身は共通層と同じでなければならない。2 回目の敵対的レビューで、チケットの無いワークツリー、
  シンボリックリンク、ユーザが直したあとの書き戻しでも外れることが分かり、条件を足して防いだ
- 失ったもの: 配点の同じ項目かの判定で、`script:` の指すスクリプトを読む（中身で比べる）

## 採らなかった案

| 案 | 落とした理由 |
|---|---|
| フェーズの種類と配点を各ツリーの層だけにし、共通層はルールだけにする | 配点の下限が外れ、外から届く 1 コミット（セッションの頭の自動 ff で反映される）でレビュー要否を緩められる |
| 承認のときに合成した配点の定義を親にコピーし、そのコピーで数える | 定義は揃うが、承認したユーザの共通層で、気づかれないまま決まる。ユーザが気づく場面が無い |
| `.risk.json` に数えた定義の指紋を残すだけ | ずれは後から追えるが、作業の前にユーザが気づく場面が無い |
| 判定でもプロジェクトの層だけを見て、共通層を読まない | 原則には沿うが、次の着手までの間、プロジェクトの設定を緩める 1 コミットがそのまま判定に反映される。今回は判定を変えずに置いた |
