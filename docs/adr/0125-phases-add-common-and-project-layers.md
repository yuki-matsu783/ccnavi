# ADR-0125: フェーズ定義を共通レイヤーと project レイヤーの足し算にする

状態: 採用（実装済み。2026-10-12 にユーザが決めた。ADR-0107 の「`phases.yml` は config だけに置き、足し算はしない」を改める）

## 状況

ADR-0107 は、フェーズ定義（`phases.yml`）を config の 1 本だけにし、共通レイヤーに置けば `--lint` が error で、判定に使わず空として扱うと決めた。
足し算をやめた理由は、`id` の衝突、`title` の重なり、全レイヤーで `dag` が揃わないと効かない順序の規則が絡み、合成が難しかったこと。

その後、ADR-0109 で定義から順序の欄（`order` と定義の `after`）が無くなり、順序は親の計画の項の `after` が持つようになった。
足し算を難しくしていた順序の整合の規則は要らなくなった。残る `id` と `title` の衝突は、合成したあとの検査で見られる。

一方で、どのプロジェクトでも同じ形の定義（小さい作業・調査・設計・受入テスト作成・実装・フィードバック対応）を、レイヤーごとの `phases.yml` に
同じ中身で書き写す必要があった。`src/*` と `tests/*` の構成は全プロジェクトで守らせる前提なので、これらを `scope` に持つ定義は共通に置ける。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| `phases.yml` を共通レイヤー（`.ccnavi/config/common/phases.yml`）にも置ける。判定・承認の検査・`--fill-phases`・`ticket new`・`--lint` が読むのは、共通レイヤーと、親の `project:` が指すレイヤーの和 | どのプロジェクトでも同じ定義を 1 か所に置ける。置き場の構成に依存する定義だけをレイヤーに置く | config の 1 本だけ（ADR-0107） |
| 共通とレイヤーのどちらが無くても正常（無い = 空）。両方無いときだけ定義が無い | ルールと配点の「無い = 空」と揃える | 共通が無ければ組み込みの定義に戻す |
| 同 `id` で全欄が同じ定義はレイヤーの側を捨てて info。中身が違えば error、別の `id` で `title` が共通と重なっても error。error のときは、レイヤーの側の衝突した定義だけを捨てる（同じ `id` なら共通の定義を使う）。そのレイヤーのほかの定義は使う | 共通の定義は全プロジェクトで同じ中身に保つ。1 つの定義の衝突で、そのレイヤーの無関係な定義まで使えなくなると、無関係な計画の承認まで止まる。error は出すので、捨てた定義はユーザに見える | 後ろのレイヤーが上書きする、両方を採る、衝突したレイヤーを丸ごと空にする |
| 自身のレイヤーとプロジェクトのレイヤーどうしは足さない。足すのは共通とレイヤーの 2 本だけ | ルールと配点の「共通 + 1 レイヤー」と同じ形 | 全レイヤーの和 |
| 共通レイヤーの `phases.yml` が壊れていれば、共通を空としてレイヤーの定義だけを使い、`--lint` が error で言う | 壊れた共通がレイヤーの定義まで消すと、無関係なプロジェクトの承認が止まる。共通の定義を使う計画は承認で止まるので、緩む側にはならない | 共通が壊れたらレイヤーも足さない |
| 親の着手は、共通レイヤーの `phases.yml` もプロジェクトの `.ccnavi/config/common/` へミラーする。フェーズ定義として読めなければ配らず、着手しない | 単体 clone でも同じ和で判定される | 共通の `phases.yml` は配らない |
| 導入スクリプト（`ccnavi-setup.sh`）は、共通レイヤーの `phases.yml` だけを配り、自身のレイヤーの `phases.yml` は配らない。配布先に既にある自身のレイヤーの `phases.yml` には `--force` でも触らない。共通の `phases.yml` は、配布先に既にあれば `--force` が無いかぎり入れ替えない。点検の「まだ無いもの」には、共通にも自身のレイヤーにも `phases.yml` が無いときだけ出す | 共通へ移した定義が、導入したワークスペースに届かないと、`implement` などを使う計画が承認できない。自身のレイヤーの定義は配布元（ccnavi 自身）のレイアウトに合わせたもので、配った先では存在しないパスを範囲に持つ定義が並ぶ | 自身のレイヤーの `phases.yml` だけを配る（共通へ移した定義が届かない）、両方を配る（配布元専用の定義が配布先に並ぶ） |
| 承認のあとの判定は、今までどおり親に写した `phases:` を読む | 承認したときの定義を親に固定する決まり（ADR-0109）は変えない | 判定のたびに和を読み直す |

## 理由

足し算を難しくしていたのは順序の整合で、それは定義から無くなった。残る衝突は合成したあとの 2 つの検査（同 `id` で中身が違う、`title` の重なり）で
見られるので、足し算に戻す費用が小さくなった。共通に置けるようになると、各プロジェクトに同じ定義を書き写さずに済み、写し間違いで定義がずれることも無くなる。

## 得たもの・失ったもの

- 得たもの: 共通の定義を 1 か所で持てる。レイヤーの `phases.yml` には、そのレイアウトに依存する定義だけが残る
- 得たもの: 単体 clone でも、ミラーを通して同じ定義で判定される
- 失ったもの: 共通の定義と同じ `id` の定義をレイヤーで別の中身にできない。変えたいときは別の `id` を付ける（このリポジトリの `implement-ccnavi` がその例）
- 失ったもの: 共通の `phases.yml` を直すと、全プロジェクトの次の承認に効く。進行中の親は写しを読むので変わらない
- 失ったもの: ミラーは次の親の着手まで共通とずれる（ルールと配点と同じ）
- 失ったもの: 新しく導入したワークスペースには、自身のレイヤーの `phases.yml` のひな形が無い。レイアウトに依存する定義（文書の置き場や配布の sh を範囲に持つものなど）は、ユーザが書く
- 失ったもの: この変更より前に配られた `.ccnavi/config/project/phases.yml`（`quick` や `implement` などの汎用の定義を含む版）は、`ccnavi-setup.sh` を打ち直しても入れ替わらない（自身のレイヤーの `phases.yml` はもう配らず、既にあるものには `--force` でも触らない）。共通の `phases.yml` と同じ `id` で中身が違う定義（古い版の `implement` など）があると、`--lint` が error を出し、その定義を捨てて共通の定義を使う（そのレイヤーのほかの定義は使われる）。移行は、`phases.yml` から共通に移った定義（`quick` `research` `design` `acceptance` `implement` `design-feedback` `implement-feedback`）を消し、そのプロジェクトだけに要る定義を残す。ユーザが持つ設定なので、書き換えるのはユーザ

## 採らなかった案

| 案 | 落とした理由 |
|---|---|
| レイヤーが共通の定義を同じ `id` で上書きできる | どの定義が効いているかを、2 本のファイルを見比べないと読めない。上書きで `review: none` にする緩め方もできてしまう |
| 共通の定義に接頭辞（`common:`）を付けて衝突を避ける | `plan:` と記録とマーカーが裸の `id` で定義を指す形が崩れる。得るものが小さい |
