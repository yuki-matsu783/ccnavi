# ADR-0172: Chrome 拡張の decide は、issue・返信・解決の順にホストへ書いてから、親のブランチへ 1 コミットする

状態: 採用

## 状況

VS Code のボードと端末の `decide` は、sh が返信と解決を先にホストへ書き、置いたあとに issue とコメントを投稿する。途中で止まった分は、state の操作記録から `--resume` で続きを送る。Chrome 拡張には state も操作記録も無く、書けるのは親のブランチへのコミットだけだった。拡張からも `decide` を行えるようにするには、ホストへの書き込み（返信・解決・issue）を拡張が担い、途中で止まったときの扱いを決める必要がある。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| ホストへの書き込みは、issue の作成、スレッドへの返信（issue の URL を入れる）、スレッドの解決の順に行う。そのあとで親のブランチへ 1 コミット（続きの子・マーカー・`done/` への移動）する | 解決まで進んだスレッドは必ず issue が作成済みになり、「解決したのに issue が無い」が起きない。止まっても、MR の画面に返信と issue が残り、どこまで済んだかが人間に見える | 返信・解決を先に、issue をあとに書く（解決後に issue の作成が失敗すると、選択が誰にも見えず消える）。コミットを先にする（コミット済みでホストが未解決の窓ができ、次の確認が止まる） |
| ホストへの書き込みは `writeLoop` の外で 1 回だけ行う。ループの中は判定とコミットだけにする | ループは先頭が動くと最大 3 周読み直す。中に入れると、周ごとに返信や issue が重なる | ループの中に入れる |
| 操作の記録は持たない。止まったら、読み直した未解決のスレッドだけを決め直して押せば続きが進む。issue の本文には決定的な操作 ID の印（隠しコメント）を入れ、作成前に同じ印の issue を検索して、重複をなるべく避ける | 拡張にはブラウザをまたぐ記録の置き場が無く、VS Code と併用しても記録が食い違うため。止まったときの人間の復元が、ホストに残る印だけでできる | `chrome.storage` に操作記録を持つ（端末をまたいで復元できない）。検索を当てにして重複を完全に防ぐ（検索は遅れて見えるため、防げない分は人間が閉じる） |
| 書く前に、PAT の権限（返信・解決・issue の作成）と、スレッドが解決できる種類かを確かめ、足りなければ何も書かずに必要な権限名を出して止める。解決できないスレッド（GitLab の差分以外のコメント、保留中のレビュー）は、拡張では扱えないと言って VS Code へ誘導する | 権限不足は 403/404 としか見えず、途中まで書いて止まるのを避ける | 書いてから失敗を見分ける |
| 「このフェーズで直す」の指摘には、返信も解決もしない。続きの子の採番は、親のブランチ上の既存のチケットだけを見る。手元の退避は見ない | 直した結果をユーザがホストで確かめて解決する原則を守る。手元の退避は拡張から見えず、連番の再利用は人間が見分けられる範囲として許す | 退避を見られないことを理由に、拡張では直す選択を無効にする |
| PAT に Pull requests と Issues の書き込み権限（GitLab は `api` スコープのまま）を要求する。画面（ページ）には PAT を渡さず、service worker だけがホストを呼ぶ原則は変えない | 返信・解決・issue の作成に要る | 権限を増やさず、端末のコマンドを案内する |
| GitHub のスレッドは、登録したリポジトリのその MR のものかを確かめてから返信・解決する | スレッドの id はホストのグローバルな id なので、取り違えた id が渡ると別のリポジトリや別の MR のスレッドに書いてしまう | id の形だけを見て書く |
| 返信の本文の末尾に操作 ID の印を付け、同じ印が既にあるスレッドには返信しない | 止まったあとに決め直して押しても、同じ返信が二重に付かない | 返信を毎回投稿する（再実行のたびに重なる） |
| issue の続きのコメント（本文が収まらないときの分割）には part の印を付ける。使い回した issue では、足りない part だけを付ける | 再実行で続きのコメントが重ならず、途中まで付いた issue も補える | 続きのコメントを毎回付ける。使い回した issue では付けない |
| 送る本文のコードフェンスの外は、`@` のメンションと行頭の `/`（GitLab の quick action）を無害にする | 外から来た指摘の本文が、拡張の書き込みで第三者への通知やコマンドの実行になるのを防ぐ。フェンスの中は読み手がコードとして読む | 本文をそのまま送る。フェンスの中も直す |
| 親のブランチへコミットする前に、書き終えたキーが読み直した結果で解決済みであることをコアが確かめる。通らないときだけ、短く待って最大 3 回取り直す | ホストの読み取りの遅れで、書いた直後の解決が見えないことがある。それ以外の食い違いは待っても直らない | 毎回待つ。通らなければすぐ失敗にする |
| 指摘が 0 件の確定では、ホストへ何も書かず、コメントも投稿しない | 決めた内容が無く、「レビュー済みにする」と同じコミットで足りる | 空の内容のコメントを投稿する |
| issue は指摘 1 件につき 1 件作る。1 回の確定で issue に回せるのは 40 件まで | 1 件ずつ辿れる。1 回の書き込みの量と PAT の呼び出しの回数に上限を置く | 複数の指摘を 1 つの issue にまとめる。上限を置かない |
| GitLab で本文が目印で始まるだけの投稿を機構自身の投稿として未解決から外す判定に、書き手が PAT の持ち主であることを加える | 他の人が目印で始まる指摘を投稿して、確認と `decide` をすり抜けさせられるため | 書き手を問わず目印で外す |

## 得たもの・失ったもの

- 得たもの: 端末も VS Code も使わずに、ブラウザだけで残った指摘の行き先を決められる。途中で止まっても、MR に残る印から人間がやり直せる。
- 失ったもの: 操作の記録が無いので、`--resume` のような自動の続きは無い。issue が重複しうる。PAT に書き込み権限が要り、既存の PAT は作り直しになる。
