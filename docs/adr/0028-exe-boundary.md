# ADR-0028: 実行ファイルの境界は自分のディレクトリの中

状態: 採用

## 状況

2026-09-10、`review check` が GitLab を実行ファイルの中から直接読みに行っていることが分かった。
実測できていない部分（API のパス、トークンの権限、ページング、セルフホストの差）が配布物の中に
閉じ、壊れたときに実行ファイルを作り直すしかなかった。

以前の `--review-fixture`（環境変数で写しを指せた版）は、エージェントが Bash の環境に付けて
`check` を打てば偽のホストでゲートを開けられた。

## 決定

実行ファイルが自分で見て判断するのは、プロジェクトのディレクトリの中で把握できるものだけ。
作業ツリー、git のオブジェクトと参照、承認済みチケット、印、hook の payload。その外にあるもの
（マージリクエスト、レビューのスレッド、ホストの API、認証）は `.claude/scripts/` の sh が
取ってきて写し（JSON）を `--result` で渡し、実行ファイルはその写しを材料にチケットと印を
動かすところだけを持つ。

依頼は `prepare`（前提の検査と本文の書き出し）→ sh が投稿 → `requested`（印）の 2 段。
`check` / `requested` は、依頼の印にあるホストとマージリクエストの番号が写しと一致しなければ拒む。
sh は `gh` / `glab` を優先し、無ければ `curl` とトークン、それも無ければ MCP などを提案して止まる。
道具は起動時に絶対パスへ固定する。

この線は今後も動かさない。実行ファイルに「外を見に行く」コードを足したくなったら、それは sh の
仕事で、実行ファイルに足すのは「その結果をどう読むか」だけ。

## 理由

1. 外との接続は実測でしか確かめられず、プロジェクトごとに違う。配布物の中に閉じると、壊れたときに
   実行ファイルを作り直すしかなく、直せるのが作った人だけになる。sh なら使う側が直せる
2. 写しの形を契約にすると、テストは sh の代わりに写しを渡すだけで本番と同じ経路を通る。
   代役という別の経路が要らない
3. 信頼の境界が言葉で言える。sh はルールで守られた場所にあり（`guard-scripts`）、写しを
   実行ファイルへ直接渡せるのは人の手だけ（ADR-0029）。実行ファイルが約束するのは承認済みチケットに対する
   判定であって、写しが実物と一致していることではない。それは sh と道具の側の責任

段の名前を分けるのは、どちらで止まったかが終了コードを見なくても分かるように。
写しは sh が作るファイルなので、別のマージリクエストの写しでゲートを開けないように番号を照合する。
道具を絶対パスへ固定するのは、PATH の細工で `curl` をすり替える道を 1 行で塞ぐため。

## 得たもの・失ったもの

- 得たもの: 実行ファイルがネットワークに出ない。sh はプロジェクトごとに直せる
- 失ったもの: sh に `jq` が要る。sh 3 本は `.claude/scripts/` に人が置く
- 失ったもの: sh の中の綴り（伏せ字、origin の読み方）は人が直す。エージェントはスクリプトを触れない

## 採らなかった案

- 実行ファイルの中でホストの API を叩く。上のとおり
- 環境変数で写しを指す。エージェントがゲートを開けられる
