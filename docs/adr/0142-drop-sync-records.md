# ADR-0142: 取り込み状態（sync/）を廃止し、親ブランチの状態だけで判定する

状態: 採用（2026-10-18。ADR-0136 の「取り込み記録はキャッシュとしてだけ使う」を、記録そのものをやめる形に改める。ADR-0093 の取り込み結果による「閉じた」の照合、ADR-0118 の `push-gone-family` と `push-ambiguous-family` の材料、ADR-0122 の `--forget` も改める。互換の版を 13 に上げた）

## 状況

ccnavi は、チケットの置き場のほかに、手元の `logs/state/sync/` に 2 種類の状態を持っていた。

- `families/<P>`: 親子ごとの取り込み状態。`state`（present・closed・gone・blocked）に、`mr`・`branch`・`sha`・`fetched_at` を持つ
- `integration/`: 統合先の `done/`・レイヤー・設定のコピーと `head`

設計書（9.2）は取り込み状態を「キャッシュで、判定には使わない」と書いていた。実装は `gone`・`blocked`・`broken` で操作を止めており、書いてあることと食い違っていた。

- 取り込み状態は手元にだけあり、別の PC に引き継げない。同じ親でも PC によって止まり方が変わった
- write-and-push の `present` の確認と `ccnavi-git.sh push` の `gone` 拒否が、記録に頼って「消えた親ブランチの再作成」を止めていた。write-and-push と承認の push（`ccnavi-push-approved.sh`）は素の `git push` を打つので、記録を消すとこの 2 経路が無防備になる
- 閉じた識別子の再利用検知は統合先の `done/` のコピーに頼っていた。統合先には閉じたチケットを残さない運用なので、実際にはほとんど効いていなかった
- Chrome 拡張は、仮のツリーに `families/<P>` と `integration/` を組み立てて手元と同じ関数に渡していた。記録を組み立てる分だけ、拡張の実装が手元の記録の形に縛られていた

目指すのは、判定が「親ブランチの状態（承認済みチケット、`phases/<親>/` のマーカー、MR）」だけで決まり、チケットの切れ目で別の PC に移っても同じ結果になることである。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| `families/<P>` の記録と `integration/` のコピーを廃止する。`gone`・`blocked`・`closed`・`broken` の状態を持たない。`syncstate.py` を `standing.py`（立ち位置）、`donecopy.py`（`DoneCopy`）、`infra/tree.py`（`SELF`・`repo_key`）に分け、記録の読み書きは消す。`ccnavi-sync.sh` は記録を書かない | 判定が手元の状態に依らず、別の PC でも同じになる。設計書の「判定には使わない」と実装が一致する | `gone` だけ残して `blocked` と `closed` を消す。`integration/` を残して `families/` だけ消す |
| 親ブランチの消失は、共通の push 関門 `ccnavi_push_gate`（`ccnavi-common-state.sh`）で止める。通る経路は `ccnavi-git.sh push`（送り先が origin のとき）、write-and-push の `ccnavi_wap_prepare`、`ccnavi-push-approved.sh` の 3 つ。対象は親のワークツリー（`.claude/worktrees/<P>` で、ブランチ名から作る識別子がフォルダ名と合い、実行ファイルが親と答えるもの）のブランチだけで、通常のブランチと子の push には掛けない | 素の push を打つ経路が 3 つあり、記録の確認を外すと write-and-push と承認の push が消えた親ブランチを作り直す。関門を 1 つにして 3 経路で共有すれば、判定が食い違わない | 経路ごとに別の確認を持つ。`gone` の記録を残して関門に使う |
| 関門の「形跡」は `refs/remotes/origin/<B>` の存在、または実行ファイルが答える着手済み（承認済みの親チケットの `started_at` が空でない）・`.requested` のマーカー・手元の退避（`logs/archive/`）のどれか。承認済みというだけでは形跡にしない。`branch.<B>.remote` は使わない。形跡があれば `ls-remote`（`ccnavi_git_timed`。3 経路とも 60 秒、`CCNAVI_WRITE_AND_PUSH_TIMEOUT` で変えられる）でリモートにあるかを聞く。あれば通す、無ければ拒否、失敗・時間切れは確かめられないとして拒否側に倒す（fail-closed） | `branch.<B>.remote` は `origin/main` から切っただけの未 push の親にも設定され、初回の push を誤って止める。直接作業で提案を書き、同名のワークツリーを切って承認し、最初に `ccnavi-push-approved.sh` を打つ流れでは、承認済みでも一度も push していないので、承認済みを形跡にすると初回の push を止めてしまう。着手（`ticket start`）は write-and-push で push してから完了するので、`started_at` があれば一度は push している。`fetch.prune` で参照が消えても、`started_at`・マーカー・退避は残るので、形跡として使える | 承認済みの親チケットを形跡にする（初回の push を止める）。`branch.<B>.remote` を形跡にする。照会に失敗したら通す（fail-open） |
| 関門は `ccnavi-review.sh merged` を呼ばない。拒否は「親ブランチがリモートに無い」だけで決める | ホストへの照会と認証が push のたびに増える。マージ済みで消えたブランチも、作り直す形は同じく止めたいので、拒否の理由を分ける必要がない | `ls-remote` で無いときに `merged` で閉じたか聞き、閉じた親だけ別の文面で拒否する |
| 関門の迂回手段は、ユーザが端末で生の git を打つこと（`git push origin <B>` を一度）。拒否の文面は、改名・消し間違いならユーザに元の名前で戻してもらうこと、捨てた親ならワークツリーを片付けること、診断は `ccnavi-sync.sh <P>` であることを言う。親のワークツリーを片付ければ関門の対象から外れる | 照会に失敗したときに拒否側に倒すので、認証が対話式の環境などで止まり続けないよう、人が通す手段が要る。エージェントは生の git を打てない（ADR-0114） | エージェントにも通せる迂回の旗を付ける |
| 関門の判定のために、実行ファイルの `tree parent` が `approved yes/no/unreadable`（親ワークツリーの承認済み・doing か done に親チケットがあるか。提案は数えない）、`requested yes/no`、`archived yes/no`、`started yes/no`（承認済みの親チケットの `started_at` が空でないか）、`mr <番号>/-` の行を足して返す。古い実行ファイルはこの行を返さず、sh は `started` などが無いとき `unknown` と読み、形跡が無ければ通す。古い sh は未知の行を読み飛ばす | sh はチケットの YAML を読まない決まりを守りながら、`fetch.prune` で参照が消えた親も形跡として見分けるため | sh が承認済みチケットを自分で読む |
| P13（判定は hook と実行ファイルが持つ）の例外の範囲を、`ccnavi-git.sh` の中の判定から、親ブランチの共通の push 関門にも広げる。write-and-push と `ccnavi-push-approved.sh` は許可リストで読むラッパーを通らないので ADR-0118 の 3 条件を満たさないが、関門だけを例外に入れる。関門の材料のうちチケットの中身は実行ファイルに聞き、`ls-remote` は sh が打つ。この 2 経路にほかの判定は足さない。ADR-0077 の「止める・通すの判定は hook が持つ」の例外が増える | 2 経路が素の push を打つ以上、関門はそこに置くしかない。範囲を関門 1 つに限れば、sh に判定が増え広がるのを防げる | 関門を hook に置く（hook はネットワークを待てず、sh が打つ push の直前を見られない）。2 経路の素の push をやめて `ccnavi-git.sh` を通す |
| 親を閉じた後の片付けの列挙元を `ready` が書く `state/retire/<親>.json` にする。`retire.note()` が `mr` を足して書く。書けなかったとき（置き場が無い、前の記録が壊れている、読めない閉じたチケットがある）は `ready` を error（終了コード 1）で止め、退避へ進まない。`ccnavi sync retired` が一覧を返し、`ccnavi-sync.sh` はそれを列挙元にする。読めない記録や `mr` が無い記録は `incomplete` として知らせ、自動では消さない。`ccnavi worktree retire` の片付けが済めば、実行ファイルが記録を消す（sh は消さない） | 取り込み状態の `mr` と `branch` が担っていた「ワークツリーを片付けた後の列挙」を、`ready` を打った時点で確かな値を持つ記録に移す。列挙できない親を黙って落とさない | `ready` が書けなくても警告だけで進める。ブランチ名から MR を探して列挙する |
| 放棄した親（MR をマージせずに閉じた親）の記録は、ユーザだけが端末で打つ `ccnavi worktree retire --abandon <親>` で消す。親のワークツリーが残っている間は断る。`phase_forms` のユーザ専用のガードを、`ccnavi-sync.sh --forget` から `--abandon` に置き換える。`--forget` は廃止する。`ccnavi-sync.sh` の終了コードは、片付け待ち（`mr` が無い記録、`incomplete`、マージされていない）では案内を出すだけで 0 にする。終了コード 1 になるのは、親のワークツリーが在る間の、リモートに無くマージもされていない親（引数なしでも名指しでも） | 放棄した親は MR がマージされず、記録が残り続ける。消せるのは、親のワークツリーを片付けたと確かめたユーザだけにしたい。片付け待ちで 1 にしないのは、write-and-push が終了コード 0 だけを見るため、無関係な親の片付け待ちで別の親の操作を止めないようにするため。見落とさないよう、案内は毎回出す | `--forget` を sh に残す。放棄した親を自動で見分けて消す |
| ブランチ名から MR を探す推定（ADR-0103 の仕組み）は、閉じたかの判定にも片付けの列挙にも使わない。記録の `mr` が無い親は「閉じたか判断できない」と 1 行言って止める。ADR-0136 の「推定しない」は保つ | 返った MR が同名の別のブランチのものかもしれず、閉じていないものを閉じたと読むと、生きた親を片付けてしまう。同名ブランチの再利用でも `tidy` が生きた親を消さないよう、ブランチ確認の後にワークツリーを消す順にした（`retire.run_merged`） | 補助として使い、返った MR の先頭が手元の履歴に含まれ、マージ先が統合先で、複数あれば 1 件でも open なら「閉じていない」とする（下の「採らなかった案」） |
| `Standing.closed` を廃止する。閉じた別の親子の子を先行（`predecessors`）に持つチケットは `PRED_MISSING` になる。文面は「どの置き場にもありません。閉じて片付いた親子のチケットなら、取り込み済みなので predecessors から削除してください」とし、置き換えの手段は設けない | 閉じた親子の子が先行として満たされるかは、取り込み状態の `closed` と統合先の `done/` のコピーが答えていた。この 2 つを廃するので、置き場に無い先行は満たさない（ADR-0088 の厳しい側） | 退避から閉じたと読む（PC によって答えが割れる） |
| 閉じた識別子の再利用検知は、`ccnavi-start.sh` の開始時にホストへ聞く照会だけにする。承認の経路（手元・Chrome とも）では検知しない。`approval_checks.integration_problems`・`integration_closed`・`_closed_elsewhere` を削除する | 実行ファイルはネットワークに出ない決まりで、承認の経路からは照会を呼べない。統合先の `done/` のコピーは、閉じたチケットを残さない運用では効いていなかった | 承認時に統合先のコピーと比べる |
| レイヤー（ルール・フェーズ定義・リスク配点）のずれは、`integration/` のコピーを使わず、`git show refs/remotes/origin/<統合先>:<パス>` で元リポジトリのチェックアウトのレイヤーと比べ、違えば warn にする。`--lint` と `ccnavi sync check` の両方で出す（`lint_layers.layer_drift`）。`origin/<統合先>` が手元に無ければ、`--lint` は info を 1 行、`sync check` は黙る。停止にはしない。運用の決まりを「ルール・フェーズ定義・リスク配点の変更は、先に統合先へ入れてから、それを使う作業をする」とする | ずれを知らせるのは、統合先に入るまで他の機械と Chrome の判定に使われないと伝えるため。比べる側は取得済みの参照を読むだけで、ネットワークに出ない | 常時の検知を残す。ずれたら止める |
| `ccnavi sync check` は残すが、`blocked` を書く前提を消す。`error ...` と `warn ...` の行で返し、sh が表示して、error があれば終了コード 1 にする（状態は書かない）。頭の行 `check 1` は変えない。`ccnavi-sync.sh` の終了コード 3（`blocked` を書けなかった）と、`sync closed` の副命令は廃止する | 書く状態が無くなったので、止める理由は表示と終了コードだけで足りる | 状態に書いて次の操作を止める |
| 統合先の名前の解決から `integration/head` の枝を外す。順は環境変数、`.claude/settings.local.json` の `env`（`ccnavi sync paths` の `integration` 行。同一プロセス内でキャッシュ）、デフォルトブランチ（`origin/HEAD`・`origin/main`・`origin/master`） | コピーが無いので `head` を読めない。設定を sh に運ぶ道は既にある | `head` の代わりに別のキャッシュを持つ |
| ロックは残す（`ccnavi-common-lock.sh`、`ccnavi_repo_key`、`integrate` のマーカー用の `ccnavi_record_get` と `ccnavi_record_write`）。`mr` を引き継ぐ処理と、`ccnavi_record_put`・`ccnavi_family_record` は消す | 並行する子の `finish` が共有の親ワークツリーで merge するため、同じ PC の中の排他は要る。取り込み状態とは別の問題で、ここで外すと範囲が広がりすぎる | ロックも外す（子の `finish` が親ワークツリーを奪い合う） |
| Chrome 拡張は、`ccnavi_chrome.py` の `records()` と、記録の組み立て（`families`・`integration` の `state`）を削る。仮のツリー、`_placement`、手元と同じ関数で読むこと（REQ-EXT-32）は変えない。ホストに親ブランチが無いときの停止は、偽のワークツリーが作られず `Standing.stop`（親のワークツリーがありません）で止まる既存の動きに任せ、`gone` 専用の入力は足さない | 拡張が手元の記録の形を知らなくてよくなる。止まる向きは変わらない | `gone` の入力を拡張に足す |
| VS Code のボードは、`unprepared[]`・`remote.fetched_at`・`remote.mr` を消す。「このPCでは未準備」のカードと「準備する」ボタン、「最終取り込み」の表示は項目ごとなくす。MR の番号は親チケットの `mr:` から出す | 出す元の記録が無い。親のワークツリーが無い PC では、その親子のチケットがボードに出ず、`ccnavi-start.sh --mr <番号>` で用意する | 親チケットの有無から未準備を組み直す |
| 互換の版 `CCNAVI_COMPAT` を 12 から 13 に上げる（`COMPAT`・`CCNAVI_COMPAT`・`EXTENSION_COMPAT` の 3 か所を同時に）。`tests/sh/test_compat_skew.py` の版を追従する | 新しい sh が、実行ファイルの新しい副命令（`tree parent` の追加行、`sync retired`、`sync migrate`）を呼ぶ。Chrome と手元の判定の規則が変わる（記録の有無で止まらなくなる） | 上げずに副命令の有無を見る |
| 古い取り込み状態を `ccnavi sync migrate`（冪等）で移す。`ccnavi-sync.sh` は先頭で 1 回呼ぶ（頭の行が `migrate 1` でなければ何もしない）。親のワークツリー（`.claude/worktrees/<P>`）が無い古い記録だけを、`mr` と `branch` を持つ `retire/<P>.json` に書く（`moved`）。既にある `retire/<P>.json` は尊重する（`kept`）。親のワークツリーが在る記録、`mr` も `branch` も無い記録は古いファイルを消す（`dropped`）。シンボリックリンクは辿らず消さない（`skipped`）。`integration/` は消す。状態（`gone`・`blocked` など）は捨てる。古い記録の読み取りは使い捨てのモジュール `tickets/legacy_sync.py` に最小限で写す | ADR-0115 は移行のための読み取りを外す方針だが、ready 済みで `retire/<P>.json` が無い古い親の片付けを列挙し続けるために 1 回だけ要る。使い捨てにして本体に残さない | 移行せず、古い親を手で片付けてもらう |

### push の関門の判定

| 状況 | 結果 |
|---|---|
| 親のワークツリーでない | 通す（0） |
| 実行ファイルが無い、または `parent unreadable` | `origin/<B>` の参照の形跡だけで続ける |
| 形跡あり（参照、または `started`・`requested`・`archived` のどれかが yes） | `ls-remote` で聞く。リモートにあれば通す（0）、無ければ拒否（1）、失敗・時間切れは確かめられない（2。拒否側） |
| 形跡なしで、`started`・`requested`・`archived` がすべて no（承認済みでも未着手・未 push の親を含む） | 通す（初回の push） |
| 形跡なしで、`started` などが `unknown`（古い実行ファイル） | 通す |
| `approved` が `unreadable`（承認済みチケットを読めない。着手済みかを確かめられない） | 確かめられない（2。拒否側） |

`ccnavi-start.sh` の push（`ensure_push`）も `cgit` で `ccnavi-git.sh push` を通るので、関門が掛かる。作ったばかりのブランチは親のワークツリーではないので通る。承認済みでまだ push していない親を `ccnavi-start.sh` で開始し直しても、着手済み・依頼・退避が無ければ初回の push として通る。着手済みなのにリモートに無い親は、`push-parent-missing` で止まる（安全側。ユーザが端末で `git push origin <B>` を一度打つ）。

`ccnavi-git.sh push` の送り先は、引数のリモート名を origin と同じ URL なら origin とみなす（origin の URL が `:` を含まないローカルのパスのとき、`push <そのパス>` で関門を飛ばせないように）。write-and-push は、取り込み（`ccnavi-sync.sh`）がマージ済みの親のワークツリーを片付けて終了コード 0 を返した後、ツリーが無ければ何も書かずに止める。

## 理由

- 判定の材料を、親ブランチ（承認済みチケット、マーカー、MR）とワークツリーの有無だけにすれば、別の PC に移っても同じ答えになる
- 親ブランチの消失は状態に書かず、push の前に毎回聞く。古い記録が実際と食い違って止め続けることが無い
- 手元にだけある状態を減らすことと、sh に判定を足さない決まりは、関門という 1 つの例外に絞って両立させた

## 得たもの・失ったもの

- 得たもの: 手元にだけある取り込みの状態が無くなり、別の PC への引き継ぎで判定が食い違わない。設計書の「判定には使わない」と実装の食い違いが消えた。`syncstate.py`（776 行）の大半、`ccnavi-sync.sh` の書き込み、`integration` コピー、Chrome 拡張の記録の組み立てが消えた。古い `gone` の拒否が、3 経路で同じ関門になった（それまで write-and-push と承認の push は記録頼みだった）
- 失ったもの: `gone`・`blocked` の永続的な検知。オフラインの hook では親ブランチの消失が分からず、気づくのは `ccnavi-sync.sh`・push の関門・セッション開始の fetch の時点になる。`blocked` が埋めていた、取り込み直後に判定し直しの error が出るまでの間の止めも無くなり、error は `ccnavi sync check` の表示と終了コード 1 でだけ伝わる
- 失ったもの: 閉じた識別子の再利用検知のオフライン動作と、承認経路での検知（統合先のコピーに頼る形は元から効いていなかった）。検知は開始時の照会だけになる
- 失ったもの: 常時のレイヤーのずれ検知。warn と運用の決まりで守る。ccnavi 自身の開発では、レイヤーを変える作業と、それを使う作業を別のチケットに分ける。Chrome の承認は統合先のレイヤーを読むので、ずれは手元の warn でしか知らされない
- 失ったもの: push の前に `ls-remote` が走る。失敗したら拒否に倒すので、認証が対話式の環境ではユーザが端末で `git push origin <B>` を一度打つ必要がある
- 失ったもの: 片付けの列挙元（`retire/<親>.json`）は `ready` を打った PC にだけある。別の PC で `ready` 後の片付けを列挙することはできない。放棄した親は、ユーザが `--abandon` を打つまで、`ccnavi-sync.sh` が毎回案内を出し続ける（終了コードは 0。親のワークツリーが在る間だけ 1）
- 失ったもの: ユーザの手が増える。sh（`.ccnavi/scripts/`）は保護された場所にあり、互換の版を 13 に揃えるまで、ユーザがコピーする。Chrome 拡張は、統合先に新しい sh が入った後に公開する
- 失ったもの: 閉じた別の親子の子を先行に持つチケットは `PRED_MISSING` になり、`predecessors` からの削除が要る。承認済みチケットは保護されていてエージェントは直せないので、ユーザが `predecessors` を手で編集するか、改版（提案を出し直して承認）する。統合先のルートの `done/` にその先行のコピーが残っていると、`PRED_MISSING` ではなく「親のワークツリーがありません」で止まり、案内が「親のワークツリーを切り直して」になる（`approval_checks.align_imported`）。この場合も直し方は同じで、`predecessors` から外す
- 失ったもの: 読めない承認済みチケット（マージのコンフリクトマーカーが入った `doing/<子>.md` など）が親のツリーにあっても、hook は親子の全チケットを止めない。古い `blocked` は親子の全チケットを止めていた。再現して確かめた範囲では、その子のワークツリーに読める写しがあれば親のワークツリーの外にしか無いチケットとして deny、写しも読めなければチケットの無いツリーと同じ扱い（`UNDECLARED`）になり、親の範囲を借りて書けることはない。一方、読める兄弟の子と親の書き込みは止まらず、読めないことは `ccnavi sync check` の表示と終了コード 1 でだけ伝わる（`--lint` の `family_check` にも出る）
- 失ったもの: 承認では、閉じた識別子の再利用を検知しない。手元の退避（`logs/archive/`）に同じ識別子の閉じたチケットがあっても、同じ識別子の提案を承認できる。検知は `ccnavi-start.sh` の開始時の照会だけ
- 古い sh と新しい実行ファイル、新しい sh と古い実行ファイルが混ざる間は、新しい行を知らない側が読み飛ばすか `unknown` と読み、関門は参照の形跡だけで通す。互換の版が違う間は `--lint` が error を出す

## 採らなかった案

- **`gone` だけ残して `blocked` と `closed` を消す。** オフラインの hook でも消失が分かるが、手元だけの状態が残り、別の PC で食い違う
- **`integration/` のコピーを残して `families/` だけ消す。** 変更は小さいが、レイヤーのずれ検知と再利用検知の窓口が手元のコピーに残り、別の PC に引き継げない
- **Chrome 拡張を別の作業に分ける。** 手元側を先に直せるが、拡張が組み立てる記録の形と食い違う期間ができる
- **ロックも外す。** 同じ PC の並行する子の `finish` が親ワークツリーを奪い合う
- **関門で `ccnavi-review.sh merged` を呼び、マージ済みも拒否する。** 閉じた名前の再作成を別の文面で止められるが、push のたびにホストへの照会と認証が増え、失敗の経路も増える
- **ブランチ名から MR を探す推定を補助に使う。** 返った MR の先頭が手元の履歴に含まれ、マージ先が統合先で、同名の MR が複数あれば全件を見て 1 件でも open なら「閉じていない」とし、GitLab は `source_project_id` で絞る、という条件を付ければ使える。ただし条件を満たしても、同名ブランチの再利用や別のプロジェクトの MR を取り違える余地が残る。`ready` が MR の番号を記録に書く形にして、推定なしで足りるようにした
