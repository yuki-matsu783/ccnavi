# ADR-0038: チケットのプロジェクトは提案を置いた場所で決める

状態: 採用

## 状況

ADR-0033 は「プロジェクトを決めるのは人の承認で、判定はその値を見ない」とし、frontmatter の
`project:` を親が書いて子が承認で継ぐ形にしていた。承認まで値が決まらないので、承認待ちの子は
どの画面でも無所属になり、ボードのプロジェクトの絞り込みが親子を割った。

もう 1 つ、壊れ方があった。写しから提案を引く道は最初から置き場を前提にしていたので、
`wip/tickets/`（プロジェクト名の無い置き場）に提案を置いて `project:` だけ書いた形は、承認は
通るのに写しを閉じられない。

## 決定

プロジェクトは提案を置いた場所が決める。`wip/<名前>/tickets/` ならその名前、作業ツリーの中なら
その切り元、ワークスペースの `wip/tickets/` なら空。走査がそれを入れ、写しに残す。

frontmatter の `project:` は宣言ではなく照合のためで、書かなくてよく、置き場と違えば承認しない。
親と子は同じ置き場に並ぶので、承認が子に継がせる段は無い。`projects/` に無い名前の置き場は
走査されないので、そこに提案を置いても承認画面にもボードにも出ない（`--lint` が名指しする）。

## 理由

置き場は提案を書いた時点から在る。承認を待たずにプロジェクトが分かるので、画面が親子を割らない。
設計は元から提案の置き場を `wip/<名前>/tickets/` と決めていて、写しから提案を引く道もそれを
前提にしていたのだから、真を置き場の側に寄せるほうが実装の他の部分と噛み合う。

`project:` を残して照合に使うのは、人が読む提案に、どのリポジトリへ書くつもりかが書いてあるほうが
読めるため。真が 2 か所にあるのではなく、置き場が真で、欄はその写し。

## 得たもの・失ったもの

- 得たもの: 承認待ちの子にもプロジェクトが付く。承認は通るのに閉じられない形が消えた
- 得たもの: 承認が子に値を継がせる段が要らなくなった
- 失ったもの: プロジェクトを変えるには提案を別の置き場へ動かすことになる。欄を書き換えるだけでは
  変わらない（変えるつもりで欄だけ直せば、承認が食い違いとして止める）

## 採らなかった案

- `project:` を真のまま、走査の時点で欄を読む。置き場と欄の 2 つが真になり、食い違ったときに
  どちらを採るかを決める必要が出る
- 承認まで無所属のままにして、画面側で親から引く。解釈が画面と実行ファイルの 2 か所に増える（ADR-0035）
