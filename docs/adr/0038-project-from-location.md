# ADR-0038: チケットのプロジェクトは提案を置いた場所で決める

状態: 採用

## 状況

ADR-0033 は「プロジェクトを決めるのはユーザの承認で、判定はその値を見ない」とし、frontmatter の
`project:` を親が書いて子が承認で継ぐ形にしていた。承認まで値が決まらないので、承認待ちの子は
どの画面でも無所属になり、ボードをプロジェクトで絞り込むと親と子が別々に分かれた。

もう 1 つ問題があった。承認済みチケットから提案を引く処理は最初から置き場を前提にしていたので、
`wip/tickets/`（プロジェクト名の無い置き場）に提案を置いて `project:` だけ書いた形は、承認は
通るのに承認済みチケットを閉じられない。

## 決定

プロジェクトは提案を置いた場所で決まる。`wip/<名前>/tickets/` ならその名前、ワークツリーの中なら
その元リポジトリ、ワークスペースの `wip/tickets/` なら空。走査のときにその値を入れ、承認済みチケットに残す。

frontmatter の `project:` は宣言ではなく照合に使う。書かなくてもよく、書いた値が置き場と違えば承認しない。
親と子は同じ置き場に並ぶので、承認のときに値を子へ継がせる段階は無い。`projects/` に無い名前の置き場は
走査されないので、そこに提案を置いても承認画面にもボードにも出ない（`--lint` がその置き場の名前を挙げる）。

## 理由

提案の置き場は、提案を書いた時点で決まっている。承認を待たずにプロジェクトが分かるので、画面で親と子が分かれない。
設計は元から提案の置き場を `wip/<名前>/tickets/` と決めていて、承認済みチケットから提案を引く処理もそれを
前提にしていたのだから、正しい値を置き場の側に持たせるほうが実装の他の部分と合う。

`project:` を残して照合に使うのは、どのリポジトリへ書くつもりかが提案に書いてあるほうが、
ユーザが読みやすいため。正しい値を持つのは置き場だけで、`project:` の値は置き場を写したものにすぎない。

## 得たもの・失ったもの

- 得たもの: 承認待ちの子にもプロジェクトが付く。承認は通るのに閉じられない形が消えた
- 得たもの: 承認のときに子へ値を継がせる段階が要らなくなった
- 失ったもの: プロジェクトを変えるには提案を別の置き場へ動かすことになる。キーの値を書き換えるだけでは
  変わらない（変えるつもりで値だけ直すと、承認のときに食い違いとして止められる）

## 採らなかった案

- `project:` の値を正しい値として残し、走査の時点でその値を読む。正しい値が置き場と `project:` の 2 か所にでき、食い違ったときに
  どちらを採るかを決める必要が出る
- 承認まで無所属のままにして、画面側で親から引く。解釈が画面と実行ファイルの 2 か所に増える（ADR-0035）
