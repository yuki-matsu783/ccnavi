# ADR-0051: `regex` も大文字小文字を区別せずに当てる

状態: 採用

## 状況

綴りの大文字小文字を、当てるものごとに違う扱いにしていた。

| 当てるもの | 扱い |
|---|---|
| ルールの `glob`、チケットの範囲の `glob`、フェーズの種類とリスクの配点の `scope` | 区別しない（どの機械でも） |
| 組み込みの守り（`selfguard._folded` / `phase` の承認の経路） | 区別しない（どの機械でも） |
| ルールの `regex`、チケットの範囲の `regex` | **区別する** |
| `regex` に埋めた `{root}` | 区別しない機械でだけ `(?i:...)` で囲む |

`regex` だけ区別していた理由は「書いた人が `(?i:...)` を自分で書けるので、意図を持てる側に
任せる」だった。実際には、次の 3 つがそろっていた。

1. **同じ場所への書き込みが経路で割れていた。** ワークツリーの中の `.Claude/Settings.json` へ、
   シェルから書く形は組み込みの守り（`builtin-guard-setting-files`、綴りを問わない）が止めるのに、
   `Write` は `guard-settings`（`regex`、綴りを見る）が外れて `worktrees` の `allow` で通っていた。
   hook の登録はコアファイルで、守りの意図は 1 つなのに、答えがツールで違った
2. **共通層の `regex` は、そのほとんどがパスの守りだった。** `guard-ccnavi-config`・`main-tree`・
   `credentials`・`guard-settings` の 4 本。区別しない機械では `.Ccnavi/common/Rules.yml` は
   同じファイルなので、綴りを変えるだけで名指しの守りから外れる
3. **`{root}` の分岐が残っていた。** 「当たり方を機械で変えない」と決めた範囲の中で、ここだけ
   `os.path.normcase` を見ていた

## 決定

ルールの `regex` とチケットの範囲の `regex` も、`glob` と同じくどの機械でも大文字小文字を
区別せずに当てる（`rules._build` / `ticket._entries` の `re.IGNORECASE`）。
`root_pattern` の機械ごとの分岐は落とす。

書いたとおりに区別させたいときは `(?-i:...)` で囲む。囲むのは区別したい部分だけでよい。
弾いているのは先読み・後読み・後方参照（ADR-0010）だけなので、この書き方は通る。

## 理由

ルールと範囲は人が宣言する意図で、機械のファイルシステムの都合ではない。同じ宣言が
Windows では止めて Linux では通る、あるいは同じ場所が `Write` では通ってシェルでは止まる、
という割れ方をすると、「守っている」と言いながら回避できる形が残る（11.4）。

「書いた人が選べる」は残す。ただし既定を、選び忘れたときに**守りが消える側**から
**過剰に止まる側**を採る。区別が要ると分かっている人は `(?-i:...)` を書ける。

## 得たもの・失ったもの

- 得たもの: `Write` で `.Claude/Settings.json`、`Read` で `.ENV`、`Bash` で `GIT push` が止まる。
  どれも綴りを変えるだけで外れていた
- 得たもの: 止める側だけでなく案内の側も綴りを問わなくなる。`CURL` にも `prefer-webfetch` の文面が出る
- 得たもの: `{root}` の扱いから機械ごとの分岐が消えた
- 失ったもの: `allow` が綴り違いに広がる。`glob` で受け入れた代償（11.11）が `regex` にも及ぶ。
  共通層では `prefer-read-grep` と `prefer-glob` が `allow` なので、`CAT ...` `FIND ...` も allow になる。
  区別しない機械ではそれが `cat` `find` そのものなので正しい。区別する機械で `CAT` という別の実行
  ファイルが在るときだけ、名指ししていないプログラムに `allow` が掛かり、どのルールも言及しない
  呼び出しを権限モードへ渡す動き（`UNDECLARED`）が働かない。敵対的レビューで実測して見つけ、
  この 2 本を `(?-i:...)` で囲む案と比べたうえで、**同じ綴りには同じ判定を返す**ほうを採った
- 失ったもの: **綴りの文字を除外する否定の文字クラスは、除外の側が広がる。** `main-tree` の
  `\.[^c\\/]` のような「`.claude/` だけ除く」という書き方は、区別せずに当てると `.Claude/` も除外に
  入る。除外を狭く保ちたいルールは、そこを `(?-i:...)` で囲む。共通層でこれに当たるのは `main-tree`
  の 1 本だけで（`[^\x00]` や `[^\w.-]` のような否定は区別しなくても意味が変わらない）、ここは
  綴り違いのディレクトリを作らせない側の話として扱い、囲んでいない
- 失ったもの: シェルのコマンド文字列にも綴りを問わず当たる。`HEAD` と `head`、`-f` と `-F` のように
  綴りが意味を持つ場所で、`deny` は過剰に止まる側に、`allow` は広がる側になる
- 変えなかったもの: 組み込みの守り（`selfguard._folded`）は場所の綴りだけを `(?i:...)` で囲んで
  いたが、この守りも `rules._build` を通るので、コマンドの動詞（`rm` / `cp`）も区別されなくなった。
  `RM` が走る保証は無いので守りが増えるわけではなく、`deny` が広がる側なのでそのままにし、
  docstring の側を実装に合わせた
- 変わらないもの: `re.IGNORECASE` は Unicode の同一視（`ſ` と `s`）も伴うが、`glob` が既に
  そうなっていたので、当てるものの間の差は増えない

## 採らなかった案

- **区別しない機械でだけ区別をやめる。** 当たり方が機械で変わる。`glob` をどの機械でも区別しないと
  決めた理由（同じルールファイルが機械で意味を変えない）と正面からぶつかる
- **パスを持つツールだけ区別をやめる。** `match: Bash|Read|Write` のような 1 本のルールが、呼び出しの
  たびに違う当たり方をする。綴りの読み方がツールで変わるのは、判定を読む人に説明できない
- **`allow` のコマンドの名前だけ `(?-i:...)` で囲む。** `CAT` を「言及の無い呼び出し」として扱って
  確認へ回せるが、区別しない機械では `CAT` は `cat` そのもので、小文字なら黙って通る呼び出しに
  綴りだけで確認が出る。守れるのは、区別する機械に `CAT` という別の実行ファイルが在る場合だけ
- **既定は区別したまま、`--lint` で「パスの守りに見える `regex` に `(?i:...)` が無い」と言う。**
  書き手に意図を持たせる建前は保てるが、言われるのは自分でルールを書く人だけで、見本を
  そのまま持ち込んだ層では穴が残る。既定を安全側にするほうが効く
