# ADR-0009: ルールが言及しない呼び出しは判定を返さず、権限モードに委ねる

状態: 採用

## 状況

当初の設計は、ルールが言及しない呼び出しを「暗黙的 ask」と呼んで ask の一種として扱い、
ユーザが意図して置いた「明示的 ask」と UI とキャッシュで分ける計画だった。実装でも一時期、
言及の無い呼び出しを ask に格上げして返していた。

## 決定

ccnavi はその呼び出しについて判定を持たない。判定を返さず、扱いを Claude Code の権限モードに
委ね、委ねたことを記録に残す。「暗黙的 ask」という考え方はやめ、理由コードも
`IMPL_UNDECLARED` / `EXPL_ASK` から `UNDECLARED` / `RULE_ASK` に改めた。

| `permission_mode` | 結末 | 記録の `decision` |
|---|---|---|
| `auto` | classifier が判断する | `handover` |
| `default` / `acceptEdits` / `plan` | Claude Code 自身の権限の仕組みが決める | `handover` |
| 空 / 不明 | ユーザに確認が出る | `ask` |
| `dontAsk` / `bypassPermissions` | 通さない（REQ-PRE-08）。設定で委ねる側にできる | `deny` |

どのモードを委ねる側に置くか、確認できる者が居ないモードをどうするかは ADR-0049 で決めた。

ルールに `ask` と書いた場所では、権限モードによらずユーザに確認する。確認の文面には「危険だから聞いている」
とは書かない。危険だと言い切れないからユーザに聞いている。

## 理由

持っていない判定を ask として返すと、判断できるモードでも必ず止まってユーザに確認が出て、`auto` が実質
使えなくなる。逆に、ユーザが意図して置いた確認ポイントを classifier の判断で消してはいけないので、
ルールの `ask` は委ねない。確認できる者が居ないモードだけは通さない。そのモードで ask を返しても、
誰も答えないまま通ってしまうため。知らないモードの名前は確認として扱う。モードの名前が 1 つ増えたときに、
そのまま通さず確認に回すため。

記録で `handover` と `ask` / `deny` を分けるのは、ルールを足すべき場所は `handover` の数で分かり、ガードが実際に働いた回は
`ask` と `deny` で分かるから。この 2 つは同じ項目には置けない。

## 得たもの・失ったもの

- 得たもの: `auto` モードが使える。ルールが手薄な場所を記録で数えられる
- 失ったもの: 端末からの試験には `permission_mode` が来ないので、言及の無い呼び出しは
  `ask` として出る。`auto` で classifier に委ねる場合や `bypassPermissions` で止まる場合は、試験では確かめられない

## 採らなかった案

- 暗黙的 ask を ask の一種として返し、UI とキャッシュで分ける。上のとおり
