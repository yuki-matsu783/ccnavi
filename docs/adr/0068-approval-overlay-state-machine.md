# ADR-0068: 承認のオーバーレイの遷移を 1 か所に集め、単体で試せるようにする

状態: 採用

## 状況

ボード画面の承認のオーバーレイは、状態を `ApprovalOverlay`（`src/core/board-view.ts`）の union で
持っていた。`loading`（一覧を読んでいる）→ `preview`（一覧と本文を見せた）→ `approving`（承認を
打っている）→ `done`（承認した。渡す文がある）。ほかに `error`（読めなかった）と `prompt`（レビュー済みの
連絡の文）。無い状態（閉じている）も含めて 7 つ。

**状態は 1 つの型にまとまっていたが、遷移の規則は `src/board-panel.ts` に散っていた**（issue #92）。
「承認の途中は二重に開かない」「一覧が返ったとき、まだ `loading` のままか」「`preview` のときだけ
承認を打つ」「`approving` の最中は閉じない」「承認の文の上にレビュー済みの連絡を被せない」
「文を渡せるのは `done` と `prompt` のときだけ」の 6 つ。**issue はこの 6 つを数えたが、移してみると
7 つ目があった**: 絞り込みで送られた識別子がいまのボードでも承認待ちか（旧 `pendingOf`）。
画面の側にも対になる見張りがある（`src/webview/board/Approval.tsx`: `approving` の間は Esc を受けない）。

困るのは 2 つ。**操作を 1 つ足したときに「この状態では受けない」を書き落としやすい**（遷移表が
無いので、6 か所を思い出して追記する）。**単体テストが 1 本も無い**（`board-panel.ts` は VS Code の
API と絡んでいてテスト対象外で、守られていることを確かめる手立てが実機での手動確認しかない）。

危ないのはまさにこの画面。承認は取り返しがつかず（承認済みチケットが置かれ、コミットと push が
端末に送られる）、連打・承認中の再入・古いボードからの承認は現実に起きうる。指紋の照合（ADR-0043）と
ボードの承認待ちとの突き合わせはそれを踏まえて足したもので、**規則そのものは正しい。散らばって
いることと、試せないことが問題。**

## 決定

**`core/screen-host.ts` と同じ手を使う。VS Code の API に触れる部分を外に出し、「いまの状態 ＋ 入力 →
次の状態 ＋ やること」だけを `src/core/approval-machine.ts` に置く。**

| 決めたこと | なぜ |
|---|---|
| 入口は `approvalStep(state, input)` 1 本。返るのは `{ state, redraw, effects }` | 見張りが 1 ファイルに集まる。状態を作るのも遷移を通すだけになり、テストが実物と同じ道を通る |
| 外へ出る仕事は `ApprovalEffect` として**返すだけ**（一覧を読む・承認を打つ・端末に送る・クリップボードに入れる・新しいセッションで開く・人に言う・ボードを読み直す）。**行うのは `board-panel.ts`**。人に言う文面は機械の側が全部持つ | `screen-host.ts` の `Surface` と同じ形。VS Code も子プロセスも要らないので単体で試せる。文面を両側に散らすと、次に足す人がどちらに書くか決められない |
| 呼ぶ側の段取りは「状態を持ち直す → 描き直す → やることを行う」の 3 行で、**順を変えない** | 逆にすると、文を渡すときに画面が古いまま残る |
| 返事が要るもの（一覧と承認の結果）は、返ってきたら**また入力として入れる** | 「返ってきたときにまだその状態か」を見張るのも遷移の側になる。`board-panel.ts` に残るのは「パネルがまだ同じか」だけ |
| 状態は `ApprovalOverlay`（画面へ渡すぶん）＋ `only`（絞り）＋ `recheck`（食い違いで読み直している最中） | 画面との契約（`board-view.ts` の `ApprovalOverlay`）は 1 文字も変えない。拡張ホストの中だけの控えを、同じ 1 つの値にまとめる |
| 承認の結果（`approved`）にだけ「この状態でなければ受けない」を置かない | 承認済みチケットは既に置かれていることがある。受けずに捨てると、渡す文が人に届かない。**見張りを足す向きが、取り返しのつかない側になる** |
| テストは `test/shared/approval-machine.test.ts`（CB-T169〜181）。見張りの確かめは**守る状態を全部**回す（`loading` だけでなく `preview` と `approving` も） | 1 つの状態でしか押さないと、見張りを**消さずに 1 つ抜いた**とき（`approving` だけ外す）に素通しする。全部回せば、その弱めが確かめのほうで落ちる |
| そのうえで**変異テストで、見張りを 1 つ消したらテストが落ちることまで見る**（CB-T181） | 「確かめが空」を止める最後の砦。ソースを `typescript` の `transpileModule` でその場で組み立て直して読み込むので、道具は増えない。落ちるのが `assert.AssertionError` であることまで見る（無い持ち物を読んだ `TypeError` で偶然通らないよう、確かめる状態を選んである） |

## 理由

`screen-host.ts` で 1 度通した道をもう 1 度通しただけで、新しい発明はしていない。選んだのは
「どこで切るか」で、**切り口を「VS Code に触れるか」ではなく「外に出るか」に置いた**。
実行ファイルの呼び出し（`ccnavi.ts`。VS Code には触れないが子プロセスを起こす）も外に出すので、
遷移は同期の純関数になり、テストは `await` を 1 つも書かずに済む。

見張りを集めたこと自体は、遷移表を 1 枚の表にしてドキュメントに書いても得られる。そうしなかったのは、
**表は黙って古くなる**ため（`0066-webview-css-beside-components.md` が CSS の対応表を置かなかったのと
同じ理由）。見張りは
`GUARDS` の配列として**テストの中に**あり、変異テストが「表の 1 行がソースの 1 行に当たっている」ことを
毎回数え直す。ソースを直して `find` の行が消えれば、そこでテストが落ちて気づく。

## 得たもの・失ったもの

得たもの。

- 承認の見張り 7 つが 1 ファイルに集まり、表として読める（`approval-machine.ts` の頭のコメント）
- 単体テストが 0 本から 13 本になった。実機の手動確認でしか見られなかったものが、`pnpm test` で回る
- **変異テストが「確かめが緩い」ことまで見る。** 見張りを消したのにテストが通る、が起きない
- `board-panel.ts` が 665 行 → 582 行になり、承認まわりは「入力を入れて、返ったやることを行う」だけになった
- 操作を 1 つ足すときに触るのが 1 ファイルになる。`ApprovalEffect` に足して書き忘れれば、
  `board-panel.ts` の網羅検査（`never`）が止める
- 描き直しは「オーバーレイが差し替わったか」で決まるので、**変わっていないときは描き直さない**。
  移す前は、閉じているところへ「やめる」が届いても 1 度描き直していた（実害は無かったが、
  やらない仕事が 1 つ減る）

失ったもの。

- **移し替え自体がリスク。** 承認の経路は取り返しがつかないので、移す前後で挙動が同じことは
  実機の手動確認（拡張の README の 4 系）でも踏む必要がある
- **間接的になる。** 読む人は 2 つのファイルを行き来する（「何が起きるか」は `approval-machine.ts`、
  「どう起こすか」は `board-panel.ts`）
- **`carrier`（運ぶ sh が置いてあるか）を、呼ぶ側が見て入力に添える形になった。** 遷移が
  ファイルを見ないためだが、「見る時点」が呼ぶ側に移ったぶん、そこを取り違えると
  `done` の `carried` が実際と食い違う。移す前は 1 つの関数の中に収まっていた。
  **あわせて `carried` の意味が「送った」から「送ることにした」に変わった**（端末へ送るのは
  この後で呼ぶ側が行うので、送れたかまでは見ていない）。`board-view.ts` の説明をそう直した
- **変異テストは、ソースの 1 行を文字列で当てる。** 見張りの行を書き直すと、挙動が正しくても
  CB-T181 が「変異させる 1 行が見つからない」で落ちる。直すのは `find` の文字列 1 か所だが、
  **落ち方が主題と関係ない**ので、初めて見る人は戸惑う
- **見張りの確かめが「守る状態を全部」回っているかは、人が保つ。** 見張りを足した人が 1 状態しか
  押さなければ、そこは弱めても素通しする。いまの 7 つはそうなっていない（確かめてある）が、
  それを見張るものは無い

## 採らなかった案

| 案 | 落とした理由 |
|---|---|
| 遷移表をドキュメントに書くだけ（コードは動かさない） | 表は黙って古くなる。単体テストも書けないままで、issue #92 の 2 つ目が残る |
| `board-panel.ts` を丸ごとテストできるよう、VS Code の API を差し替え可能にする | 差し替える口が `vscode.window`・`vscode.env`・`vscode.workspace` と広い。承認の見張りを試したいだけなのに、パネルの生成・監視・破棄まで写しを作ることになる |
| 状態を画面（React）側に持たせ、遷移も画面で回す | 監視の更新でボードが入れ替わるとオーバーレイが消える（`board-view.ts` が拡張ホスト側に持つと決めた理由）。承認した文は取り返せないので、消える道を作らない |
| 承認の結果（`approved`）にも「`approving` のときだけ受ける」を置く | 承認済みチケットが置かれた後に受けずに捨てると、渡す文が人に届かない。**見張りは、取り返しのつく側にだけ足す** |
