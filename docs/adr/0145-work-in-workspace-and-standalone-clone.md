# ADR-0145: ワークスペース内 clone と単体 clone の両方で動かす

状態: 採用（考え方の決定。個別の機能の振る舞いは、足すたびに決める）

## 状況

ccnavi を導入したプロジェクト（git リポジトリ）は、2 通りの形で使われる。

- ワークスペース内 clone: ワークスペースの `projects/<名前>/` に clone する。Claude Code はワークスペースで起動し、プロジェクトへは `cd` で入る。hook・実行ファイル・共通レイヤー・工程スキルはワークスペースにある
- 単体 clone: そのリポジトリだけを clone し、そこで作業する。ワークスペースは無く、プロジェクトのルートがそのまま ccnavi のルートになる

呼び名は既存の文書に合わせる。単体 clone は、設計書・要件・実行ファイルのコメントがすでに「単体 clone」「プロジェクトを単体で clone したとき」と書いている形である。既存の「モード A / モード B」は、ワークスペース側の形の呼び分け（モード B は `projects/` の下に別リポジトリを置く形、モード A は `projects/` が無い形）で、どちらもワークスペースがある。単体 clone はそのどちらでもないので、この呼び名は流用せず、混ぜない。

ワークスペースにあるものを前提にした機能は、単体 clone でその前提が崩れる。これまでは機能ごとに個別に手当てしてきた。

- 共通レイヤーはワークスペースの git にあり、プロジェクトだけを clone した人からは見えない。そこで親チケットの着手のとき、プロジェクトの `.ccnavi/config/common/` に写し（ミラー）を置いた。単体 clone ではそのミラーを共通レイヤーとして読む（ADR-0107）
- プロジェクト向けのスキルは、ワークスペースではなくプロジェクトの git に置いた。プロジェクトだけを clone した人にも見えるため（ADR-0091）
- 共通の工程スキルはワークスペースの `.claude/skills/` にあり、単体 clone からは見えない。そこで親チケットの着手のとき、プロジェクトの `skills/<工程>/` に写している（`src/ccnavi/tickets/skillsync.py`）

手当ての理由が、機能ごとの ADR や設計書に散っている。新しい機能を足す人が、単体 clone のことを考える拠りどころが無い。

## 決定

ワークスペース内 clone と単体 clone の、どちらでも ccnavi が動くようにする。ワークスペースにあるものに頼る機能は、単体 clone でどうなるかを、足すときに決める。結果は次の 3 つのどれかにする。

| 結果 | 意味 |
|---|---|
| 動く | 単体 clone でも同じ結果になる |
| 縮退して動く | 頼るものが無いことを検出し、決めた小さい振る舞いに落とす。黙って誤った結果を出さない |
| 動かない | 単体 clone では使えない。使えないことが分かる形で止まる |

プロジェクトの git に入るものだけで、最低限の作業が成り立つことを土台にする。

## 設計上の指針

実コードと既存の設計書で確かめたものだけを挙げる。

| 指針 | 根拠 |
|---|---|
| 読み先をルートで決める。ワークスペースの中ではワークスペースルートのものだけを読み、単体 clone ではそのプロジェクトのものを読む。同じものを二重に読まない | 共通レイヤー。ワークスペースの中ではミラーを読まず、単体 clone ではミラーが共通レイヤー、`config/project/` が自身のレイヤーになる。どちらも「共通 + 1 レイヤー」の和になる（要件 REQ-MLT-41、設計 11.12） |
| ワークスペースにしか無いものは、プロジェクトの git にある写しで届ける。写しは着手のときに、ワークスペース側の変更に追随させる | 共通レイヤーのミラー、工程スキルの `skills/<工程>/`（`skillsync.py`） |
| プロジェクトに固有の知識は、プロジェクトの git に置く | プロジェクトのスキル（`skills/<名前>/SKILL.md`。設計 11.13） |
| ワークスペースの有無を、git のトップから推測しない | ワークスペースルートは `.ccnavi/scripts/ccnavi-common.sh` を目印に探す。git のトップは用途が別で、ワークスペース内 clone では cwd がプロジェクトの中だと git はプロジェクトを答える（`ccnavi-common.sh` の `ccnavi_workspace` のコメント） |

次のことは、この ADR では決めない。

- 縮退の中身。機能ごとに、足すとき、または不都合を直すときに決める
- 個別の不都合は別途洗い出す

## 帰結

得たもの: 単体 clone を、例外の手当てではなく、ワークスペース内 clone と並ぶ前提として扱える。機能を足す人が、確かめる項目を持てる。

失ったもの: 新しい機能は、ワークスペースだけで動いて済ませられなくなる。ワークスペースにあるものに頼るたびに、単体 clone での扱いを決める手間が増える。

新しい機能を足すときの確認項目:

1. ワークスペースにあるもの（共通レイヤー、工程スキル、実行ファイル、`logs/`・`scratchpad/`、ほかのプロジェクト）に頼るか
2. 頼るなら、単体 clone で動く・縮退して動く・動かないのどれか。縮退と動かないは、設計書か使い方の文書に書く
3. 縮退では、頼るものが無いことを検出しているか。黙って別の結果を出さず、利用者に分かる形にしているか
4. ワークスペースにあるものをプロジェクトの git へ写すなら、写しを更新するのはいつか。写しを誰も手で編集しない置き場にしているか
5. ワークスペース内 clone で、同じものを二重に読んだり数えたりしていないか

## 採らなかった案

- ワークスペースを前提にし、単体 clone は対象外にする。プロジェクトだけを clone して作業する人は実際にいて、共通のルールが見えない状態で作業することになる
- 単体 clone を主にし、ワークスペースの機能を足し算で扱う。道具をワークスペースに集め、プロジェクトごとに重ねない構成（ADR-0033）と合わない
