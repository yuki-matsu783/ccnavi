# ADR-0059: 承認できるかはエージェントが先に確かめ、その案内は判定に触れずに渡す

状態: 採用

## 状況

提案を書いたエージェントには、それが承認できる形かどうかを知る手立てが無かった。承認の対象を
組み立てるのは `approval.gather` / `approval.candidates` で、これを通る経路はユーザが打つ `--approve` と、
VS Code のボードが打つ `--approve --preview --json` の 2 本である。前者は端末を必要とする。後者は一覧を
見せるための枝で、承認の対象にしない提案（親が承認されていない、計画に無いフェーズ、順序、
範囲の書き損じ）があっても 0 で返る。これは、読む側のボードが 0 以外を失敗として扱い、
0 以外を返すと一覧を出せなくなるためである。

その結果、提案が承認で落ちたことを最初に知るのは、端末の前にいるユーザになっていた。往復が 1 回増えるだけでなく、
ユーザの承認という確認の段階の前に「エージェントの書き損じ」を並べることになる。この段階はユーザの判断のためにあり、
形の検査のためではない（2026-09-17）。

案内の届け方にも穴があった。確かめる手立てを文書に書いても、提案を書いている最中のエージェントに
届くとは限らない。ccnavi は「要る場所で言う」という方針を採ってきた（`reasons.py` の冒頭）のに、
提案を書いた回にそれを伝える仕組みが無かった。

`ccnavi --lint` は提案を走査していたが、当てていたのは `approval.validate` だけで、順序で
落ちる子・計画に無い番号・`project:` の食い違い・改版の検査については何も言わなかった。承認で落ちるものを
数える経路が 2 本あり、片方は誰にも気づかれないまま検査が弱くなっていた。

## 決定

- **確かめる枝は `--approve --preview --verify` として `--preview` に相乗りさせる。** 新しい免除の語を
  足さない。組み込みの deny（`builtin-guard-ticket-approval`）が免除するのは `--preview` の付いた
  `--approve` だけで、その表記は 1 語のまま変わらない
- **答えは終了コードで返す。0 が「はい」、`modes.EXIT_ANSWER_NO`（3）が「いいえ」。** 1 はほかと
  同じ「使い方か設定の誤り」で、答えとは分ける。読む相手はエージェントなので、文だけで返すと判断が
  その場の読み方次第になる。また答えと誤りが同じ値だと、エージェントは打ち方の誤りを提案の落ち度と読み違える
- **判定は `gather` / `candidates` の 1 か所に置く。** `--verify` はその結果を読み替えるだけ。**`--lint` も
  同じ `candidates` を通す。** 終わり方だけが違う（`--verify` は真偽、`--lint` は severity）。
  「まだ承認できない」は `--lint` では warn にする（下の「代償」を参照）
- **`--approve` が落とさないものでは落とさない。** 該当するのは範囲の超過（判定が切り詰めるだけ）と、
  読めない提案（走査は絞る前の全ツリーを見る）である。どちらも本文には出す
- **提案を書いた回に、この確認を 1 度だけ勧める。判定には触れない。** 案内は文であって判定ではないので、
  ルールの表ではなく承認の知らせ（`approval.news`）と同じ経路で渡す（`ticket.propose_notice`）

## 理由

**免除を広げないために相乗りさせた。** ここは ADR-0040 が「免除は許さない側から書く」と決めた場所である。
そこに新しい語を足すと、免除の条件が 1 つ増える。`--verify` は `--preview` を要求し、
単独で打てば使い方の誤りとして 1 で返る。免除の正規表現に新しい語は 1 つも増えていない
（この枝では逆に、`--preview` を単独の語に限る向きへ厳しくした。下の「ついでに直したもの」を参照）。

**`--preview` の終了コードは変えなかった。** ボードのオーバーレイは `--preview --json` の
0 以外を失敗として扱う。その終了コードで答えを返すと、承認の対象にしない提案が 1 件あるだけで
一覧が出せなくなる。見せる枝と確かめる枝は、読む相手が違う。

**読めない提案があっても落とさないのは、承認でも落とさないから。** 走査は全ツリー（絞る前）を見るので、
他のセッションの書きかけが 1 本あるだけで「確かめは『いいえ』なのに承認は通る」状態になる。確かめの答えが事実と食い違う形に
すると、確かめる習慣のほうが先に廃れる。ただし、読めない提案を出力から消すこともしない。自分が書いた 1 本かもしれないので、
件数とパスは本文に出す。

**案内を判定の表に足さなかった。** 最初は組み込みの allow ルール（`additionalContextOnce` 付き）
として入れた。案内の文はエージェントに届いたが、代償が 3 つあった。

- `todo/` が「ccnavi が言及する場所」になり、どのタイプも言及しないときの扱い
  （`judge.undeclared_verdict`）を通らなくなる。確認できる人がいないモード（`dontAsk` /
  `bypassPermissions`）の deny も、知らない名前のモードを ask として扱う既定も、そこだけ外れる。
  `CCNAVI_GUARD_UNWATCHED=enable`（既定）でも外れるので、プロジェクトが選べる範囲
  （ADR-0049、REQ-PRE-08）から 1 経路が抜ける
- 判定は強いタイプから見て最初に当たった段で決まるので、**提案の置き場に `deny` か `ask` を
  書いているワークスペースには文が届かない。** 承認の流れをいちばん気にしているところにだけ
  届かない、という結果になる
- 組み込みのルールで持つのは、ガード自身を守るものと取り返しの付かない操作だけ（設計 P4）。助言は
  そのどちらでもない

承認の知らせと同じ経路で渡せば、3 つの代償はどれも生じない。`approval.news` は判定と無関係に
`additionalContext` へ合流する既存の経路で、通した回・止めた回・権限モードへ渡した回の
どれでも文が付く。回数は `ctxfile` の記録をルールと同じ形で使って数え、その 1 本は表に入れない。

**`--lint` も同じ関数を通すようにした。** 同じ事実を数える経路が 2 本あると、片方が気づかれないまま弱くなる
（`post.py` の冒頭に書いてあるとおり）。実際に弱かったのは `--lint` のほうで、順序で落ちる子について
何も言わなかった。同じ関数を通した結果、**承認で落ちる提案がある間は `--lint` が非ゼロで終わる**。

## 得たもの

- **ユーザの確認の前に、形の検査が並ばなくなる。** 落ちる提案は書いた側が気づいて直す
- **確かめと承認の答えが食い違わない。** 両者は同じ関数を通り、食い違いうる分岐（読めない提案・範囲の超過）は
  落とさない側に揃えた
- **ボードの契約は 1 バイトも変わらない。** `--preview --json` の形も終了コードもそのまま
- **判定は変わっていない。** `todo/` への書き込みの扱いは、この枝の前後で同じ
- **「承認で落ちるもの」の言い方が 1 つになった。** `--approve` / `--preview` / `--verify` /
  `--lint` が同じ関数の答えを、それぞれの終わり方で返す

## 代償

- **これは保証ではなく手当てにすぎない。** 確かめずに承認を頼む手段は塞いでいない。hook の境界からは
  「エージェントがチャットで何を頼んだか」が見えないので、止める場所が無い。要求（`requirements.md` 1）に
  挙げてある「プロンプトに書いた禁止は確率を下げるだけ」の項目に、この決定自体も当てはまっている
- **案内が届かない書き方がある。** 案内が出るのは `Write` / `Edit` / `NotebookEdit` のときだけで、Bash の
  リダイレクトや MCP の書き込みツールで `todo/` に書いた回には届かない。案内は 1 つの文脈で 1 度きり
  なので、無関係な編集（他人の提案の誤字直し）でその 1 度を先に使い切ってしまうこともある
- **`--lint` が非ゼロで終わる場面が増えた。** 承認で落ちる提案があると error になる
  （計画に無い番号、`project:` の食い違い、範囲の書き損じ、改版の不整合）。`--lint` の終了コードは
  CI だけでなく、VS Code の設定画面が保存してよいかの判断にも使われる（`phases-panel.ts` /
  `risk-panel.ts` / `rules-panel.ts`）ので、**編集と関わりのない提案 1 本で設定の保存も止まる**。
  「まだ承認できない」もの（前のフェーズが閉じていない子。`rules.KIND_NOT_YET`）だけは error から外し、
  `--lint` では warn にした。書いた側に直すところが無く、前のフェーズが閉じれば同じ提案が通るため。
  承認そのものは落とす（`approval.candidates` の側は error のまま）ので、緩むのは報告の重さだけ
- **枝が 3 本になった。** `--approve` / `--preview` / `--preview --verify` は同じ関数を通るが、
  読む側から見ると「置く・見せる・答える」の 3 つを覚えることになる。しかも `--verify` の表記に
  混じる `--preview` は、やりたいこととは関係が無く、免除される形にするためだけに要る
- **終了コードの決まりが 1 つ増えた。** 3 は見慣れない値で、覚えることが増える
- **確かめは合意ではない。** 0 で返っても、承認そのものはユーザが通す。確かめが通ることを
  「承認されたも同然」と読む余地ができる（文面は「ユーザに承認を依頼してよい」までにとどめてある）
- **回数を数えるための鍵（`builtin-ticket-propose`）は予約された id ではない。** 共通レイヤーに同じ id のルールを書くと、
  回数の記録を共有してしまい、案内が出なくなる。ルールファイルはユーザしか書けないので実害は小さいが、`--lint` は何も言わない
  （`builtin-ticket-state` からある形で、この枝で作ったものではない）

## ついでに直したもの（この枝の別のコミット）

免除の表記として、**単独の語として現れた `--preview`** だけを数えるように厳しくした。以前は同じコマンドに
`--preview` という文字列が現れれば免除が成立していたので、`ccnavi --approve --reason=--preview` で
外せた。argparse は `--reason` の値として受け取るので `--preview` は単独の語にならず、実行ファイルは本物の
`--approve` を実行する。hook が見る文字列と、実行ファイルが実行する枝がそこでずれていた
（端末さえ取れれば、エージェントが自分で承認を置けることになる）。この枝が作った穴ではないが、
この決定が「その免除に相乗りする」ことを安全の根拠にしている以上、同じ枝で直す。

## 採らなかった案

- **`--approve --dry-run` を新設する。** 表記が短く、ユーザの言葉（dry-run）にも近い。採らなかった
  のは、組み込みの deny の免除に語を 1 つ足すことになるため（ADR-0040）。加えて ccnavi の
  `dry-run` は「判定するが止めない」の意味で使っており、同じ語が 2 つの意味を持つことになる
- **`--check` と書く。** 最初はこの表記で入れた。`check` は `ccnavi review check`（副作用を持つ
  ユーザの判断の経路）で既に使われ、組み込みの deny が止める動詞の一覧にも入っている。`--dry-run` を
  落とした理由がそのまま当てはまるので `--verify` に改めた。`--ch` が `--chat` と曖昧になる問題も消えた
- **`ccnavi-ticket.sh` に `verify` を足す。** エージェントの入口が 1 本に揃う。採らなかったのは、
  `.ccnavi/scripts/` が保護済みでユーザがコピーする手順が要り、判定結果の JSON を sh の側で読むことになるため
- **`--preview` 自身の終了コードを答えにする。** 枝が増えない。採らなかったのは、ボードが
  一覧を出せなくなるため（上の理由）
- **案内を組み込みの allow ルールで渡す。** ルールとして `--lint` や記録から見える。採らなかった
  理由は上の 3 つ（判定に触れる・deny/ask を書いた先に届かない・P4）
- **案内を `.ccnavi/common/rules.yml` に書く。** 実行ファイルを触らずに済み、配布先ごとに
  文面を変えられる。採らなかったのは、保護済みファイルなのでユーザがコピーするまで届かず、確かめる枝と
  同じ版で配れないため
- **案内を `PostToolUse` で渡す。** 書き終えたあとに伝えるので「書いた回」に正確に合わせられる。採らなかった
  のは、`decide_before` で渡せば同じ回に、しかも止めた回にも届くため。判定に触れない点は同じ
- **セッション開始の案内（`reasons.py`）に 1 行足す。** Bash や MCP で書いた場合も対象にできる。

  採らなかったのは、あの文が「線引きと入口だけ」と決めてあるため。ただし上の「届かない書き方」を
  埋める手当てとしては、ここがいちばん安い候補として残っている
