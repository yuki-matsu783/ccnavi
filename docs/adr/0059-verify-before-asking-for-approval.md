# ADR-0059: 承認できるかはエージェントが先に確かめ、その案内は判定に触れずに渡す

状態: 採用

## 状況

提案を書いたエージェントには、それが承認できる形かどうかを知る手立てが無かった。承認の対象を
組むのは `approval.gather` / `approval.candidates` で、それを通るのは人が打つ `--approve` と、
VS Code のボードが打つ `--approve --preview --json` の 2 本。前者は端末を求め、後者は一覧を
見せるための枝で、承認の対象にしない提案（親が承認されていない、計画に無いフェーズ、順序、
範囲の書き損じ）があっても 0 で返る。読む側のボードが 0 以外を失敗として扱うので、そこで
0 以外を返すと一覧が出せなくなるため。

その結果、落ちたことを最初に知るのは端末に座った人になっていた。往復が 1 回増えるだけでなく、
人の承認という門の前に「エージェントの書き損じ」を並べることになる。門は人の判断のためにあり、
形の検査のためではない。2026-09-17。

案内の届け方にも穴があった。確かめる手立てを文書に書いても、提案を書いている最中のエージェントに
届くとは限らない。ccnavi は「要る場所で言う」を採ってきた（`reasons.py` の冒頭）のに、
提案を書いた回に言うものが無かった。

`ccnavi --lint` は提案を走査していたが、当てていたのは `approval.validate` だけで、順序で
落ちる子・計画に無い番号・`project:` の食い違い・改版の検査には無言だった。承認で落ちるものを
数える経路が 2 本あり、片方が黙って弱い状態だった。

## 決定

- **確かめる枝は `--approve --preview --verify` として `--preview` に相乗りさせる。** 新しい免除の語を
  足さない。組み込みの deny（`builtin-guard-ticket-approval`）が免除するのは `--preview` の付いた
  `--approve` だけで、その綴りは 1 語のまま動かない
- **答えは終了コードで返す。0 が「はい」、`modes.EXIT_ANSWER_NO`（3）が「いいえ」。** 1 はほかと
  同じ「使い方か設定の誤り」で、答えとは分ける。読む相手がエージェントなので、文だけでは判断が
  その場の読みに委ねられ、答えと誤りが同じ値だと、打ち方の誤りを提案の落ち度と読み違える
- **判定は `gather` / `candidates` の 1 か所に置く。** `--verify` は読み替えるだけ。**`--lint` も
  同じ `candidates` を通す。** 終わり方だけが違う（`--verify` は真偽、`--lint` は severity）
- **`--approve` が落とさないものでは落とさない。** 範囲の超過（判定が切り詰めるだけ）と、
  読めない提案（走査は絞る前の全ツリーを見る）。どちらも本文には出す
- **提案を書いた回に、この確認を 1 度だけ勧める。判定には触れない。** 文であって判定ではないので、
  ルールの表ではなく承認の知らせ（`approval.news`）と同じ口から渡す（`ticket.propose_notice`）

## 理由

**免除を広げないために相乗りさせた。** ADR-0040 が「免除は許さない側から書く」と決めた場所で、
そこに新しい語を足すのは、免除の条件を 1 つ増やすこと。`--verify` は `--preview` を要求し、
単独で打てば使い方の誤りとして 1 で返る。免除の正規表現に新しい語は 1 つも増えていない
（この枝では逆に、`--preview` を単独の語に限る向きへ締めた。下の「ついでに直したもの」）。

**`--preview` の終了コードは変えなかった。** ボードのオーバーレイは `--preview --json` の
0 以外を失敗として扱う。そこに答えを載せると、承認の対象にしない提案が 1 件あるだけで
一覧が出せなくなる。見せる枝と確かめる枝は、読む相手が違う。

**読めない提案で落とさないのは、承認が落とさないから。** 走査は全ツリー（絞る前）を見るので、
他のセッションの書きかけ 1 本で「確かめは『いいえ』なのに承認は通る」になる。確かめが嘘をつく形に
すると、確かめる習慣のほうが先に壊れる。黙らせもしない。自分が書いた 1 本かもしれないので、
件数と綴りは本文に出す。

**案内を判定の表に足さなかった。** 最初は組み込みの allow ルール（`additionalContextOnce` 付き）
として入れた。文は届いたが、代償が 3 つ付いてきた。

- `todo/` が「ccnavi が言及する場所」になり、どのタイプも言及しないときの倒し方
  （`judge.undeclared_verdict`）を通らなくなる。確認できる者が居ないモード（`dontAsk` /
  `bypassPermissions`）の deny も、知らない綴りのモードを ask に倒す既定も、そこだけ外れる。
  `CCNAVI_GUARD_UNWATCHED=enable`（既定）でも外れるので、プロジェクトが選べる範囲
  （ADR-0049、REQ-PRE-08）から 1 経路が抜ける
- 判定は強いタイプから見て最初に当たった段で決まるので、**提案の置き場に `deny` か `ask` を
  書いているワークスペースには文が届かない。** 承認の流れをいちばん気にしているところにだけ
  届かない、という向きになる
- 組み込みで持つのは、ガード自身を守るものと取り返しの付かない操作だけ（設計 P4）。助言は
  そのどちらでもない

承認の知らせと同じ口から渡せば、3 つとも消える。`approval.news` は判定と無関係に
`additionalContext` へ合流する既存の経路で、通した回・止めた回・権限モードへ渡した回の
どれにも載る。数えは `ctxfile` の控えをルールと同じ形で使い、その 1 本は表に入れない。

**`--lint` を同じ関数に寄せた。** 同じ事実を数える経路が 2 本あると、片方が黙って弱くなる
（`post.py` の冒頭が書いているとおり）。実際に弱いほうが `--lint` で、順序で落ちる子に
無言だった。寄せた結果、**承認で落ちる提案がある間は `--lint` が非ゼロで終わる**。

## 得たもの

- **人の門の前に、形の検査が並ばなくなる。** 落ちる提案は書いた側が気づいて直す
- **確かめと承認の答えが割れない。** 同じ関数を通り、割れる分岐（読めない提案・範囲の超過）は
  落とさない側に揃えた
- **ボードの契約は 1 バイトも変わらない。** `--preview --json` の形も終了コードもそのまま
- **判定は 1 ミリも動いていない。** `todo/` への書き込みの扱いは、この枝の前後で同じ
- **「承認で落ちるもの」の言い方が 1 つになった。** `--approve` / `--preview` / `--verify` /
  `--lint` が同じ関数の答えを、それぞれの終わり方で言う

## 代償

- **これは担保ではなく手当て。** 確かめずに承認を頼む道は塞がっていない。hook の境界からは
  「エージェントがチャットで何を頼んだか」が見えないので、止める場所が無い。要求（`requirements.md` §1）が
  自分で挙げている「プロンプトに書いた禁止は確率を下げるだけ」の欄に、この決定は自分から入っている
- **届かない書き方がある。** 当たるのは `Write` / `Edit` / `NotebookEdit` だけで、Bash の
  リダイレクトや MCP の書き込みツールで `todo/` に書いた回には届かない。1 つの文脈で 1 度きり
  なので、無関係な編集（他人の提案の誤字直し）が先に食うこともある
- **`--lint` が非ゼロで終わる場面が増えた。** 承認で落ちる提案があると error になる。先回りして
  次のフェーズの子を書く形もここに入る（そのときの文面は「作業が終わるまで次の計画は立てない」）。
  CI が赤くなる条件が 1 つ増えた
- **枝が 3 本になった。** `--approve` / `--preview` / `--preview --verify` は同じ関数を通るが、
  読む側から見ると「置く・見せる・答える」の 3 つを覚えることになる。しかも `--verify` の綴りに
  混じる `--preview` は、やりたいこととは関係が無く、免除の綴りを満たすためだけに要る
- **終了コードの決まりが 1 つ増えた。** 3 は見慣れない値で、覚えることが増える
- **確かめは合意ではない。** 0 で返っても、承認そのものは人が通す。確かめが通ることを
  「承認されたも同然」と読む道ができる（文面は「利用者に承認を依頼してよい」で止めてある）
- **数えの鍵（`builtin-ticket-propose`）は予約 id ではない。** 共通層に同じ id のルールを書くと
  数えを共有して案内が黙る。ルールファイルは人しか書けないので実害は小さいが、`--lint` は無言
  （`builtin-ticket-state` からある形で、この枝で作ったものではない）

## ついでに直したもの（この枝の別のコミット）

免除の綴りが**単独の語として立った `--preview`** だけを数えるように締めた。以前は同じコマンドに
`--preview` という並びが現れれば免除が成立していたので、`ccnavi --approve --reason=--preview` で
外せた。argparse は `--reason` の値として食うので `--preview` は立たず、実行ファイルは本物の
`--approve` を走らせる。hook が見る文字列と、実行ファイルが走らせる枝がそこでズレていた
（端末さえ取れれば、エージェントが自分で承認を置けることになる）。この枝が作った穴ではないが、
この決定が「その免除に相乗りする」ことを安全の根拠にしている以上、同じ枝で塞ぐ。

## 採らなかった案

- **`--approve --dry-run` を新設する。** 綴りが短く、利用者の言葉（dry-run）にも近い。採らなかった
  のは、組み込みの deny の免除に語を 1 つ足すことになるため（ADR-0040）。加えて ccnavi の
  `dry-run` は「判定するが止めない」の意味で使っており、同じ語が 2 つの意味を持つ
- **`--check` と綴る。** 最初はこの綴りで入れた。`check` は `ccnavi review check`（副作用を持つ
  人の判断の経路）で既に使われ、組み込みの deny が止める動詞の一覧にも入っている。`--dry-run` を
  落とした理由がそのまま当たるので `--verify` に改めた。`--ch` が `--chat` と曖昧になる問題も消えた
- **`ccnavi-ticket.sh` に `verify` を足す。** エージェントの入口が 1 本に揃う。採らなかったのは、
  `.ccnavi/scripts/` が保護済みで人が写す手順が要り、判定の読み取り（JSON）が sh の側に乗るため
- **`--preview` 自身の終了コードを答えにする。** 枝が増えない。採らなかったのは、ボードが
  一覧を出せなくなるため（上の理由）
- **案内を組み込みの allow ルールで渡す。** ルールとして `--lint` や記録から見える。採らなかった
  理由は上の 3 つ（判定に触れる・deny/ask を書いた先に届かない・P4）
- **案内を `.ccnavi/common/rules.yml` に書く。** 実行ファイルを触らずに済み、配布先ごとに
  文面を変えられる。採らなかったのは、保護済みファイルなので人が写すまで届かず、確かめる枝と
  同じ版で配れないため
- **案内を `PostToolUse` で渡す。** 書けたあとに言うので「書いた回」に正確に当たる。採らなかった
  のは、`decide_before` で渡せば同じ回に、しかも止めた回にも届くため。判定に触れない点は同じ
- **セッション開始の案内（`reasons.py`）に 1 行足す。** Bash や MCP の書き方も覆える。
  採らなかったのは、あの文が「線引きと入口だけ」と決めてあるため。ただし上の「届かない書き方」を
  埋める手当てとしては、ここがいちばん安い候補として残っている
