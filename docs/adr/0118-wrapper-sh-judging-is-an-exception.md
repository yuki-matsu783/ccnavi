# ADR-0118: 入口を 1 本に寄せたラッパーの中の可否の判定は、止める・通すの原則の例外にする

状態: 採用（例外の範囲を、親ブランチの共通の push 関門（write-and-push と `ccnavi-push-approved.sh` の push の前を含む）に広げることは ADR-0142 が改める。表の `push-gone-family`・`push-ambiguous-family` の材料だった取り込み状態の `state`・`branch`、`ig_bound` が読んでいた取り込み状態、統合先の名前の「取り込み結果」の分は、取り込み状態をやめたことで改まった）

改訂（2026-10-20）: `integrate` / `integrate-done` の状態操作（`merge --squash`、取り込みの記録、stagedの確認）は、ADR-0154 が改める。一時ワークツリーとfast-forwardに変わった。`integrate-ticket` の判定をshに置く例外の条件は変わらない。

改訂（2026-10-19）: 統合先の名前の決め方（環境変数・取り込み結果・`origin/HEAD` の順）は ADR-0148 が改める。統合先は各リポジトリの `origin/HEAD` だけで決め、環境変数 `CCNAVI_INTEGRATION_BRANCH`・`settings.local.json` の env・`--integration-branch` は廃止した。本文は当時の記述として残す。

改訂（2026-10-14）: 「承認済みの `branch:` のブランチへ移る 1 操作の前提」は、ADR-0136 が `branch:` を廃止したため無くなった。

## 状況

設計原則 P13（ADR-0077）は「止める・通すの判定は hook と実行ファイルが持ち、sh が ccnavi の状態を読んで止めるのは
2 重目の確認」と決めた。2026-10-11 に `.ccnavi/scripts/ccnavi-git.sh` を見直すと、この形に当てはまらない判定が
残っていた。どれも sh がチケットと取り込み状態を読んで、hook より先に（hook には同じ判定が無いまま）止めている。

| 何 | sh の中の場所 | 何を読むか |
|---|---|---|
| `integrate` が取り込むブランチがチケットに結び付くなら断る（`integrate-ticket`） | `ig_bound` | 親のワークツリーか、どのツリーかの置き場に同じ名前のチケットか提案があるか、取り込み状態があるか |
| 統合先への push を断る（`push-integration-branch`） | push の検査 | 統合先の名前（環境変数・取り込み結果・`origin/HEAD`） |
| 親のブランチを 2 つの親子のチケットが宣言していれば断る（`push-ambiguous-family`） | push の検査 | 取り込み状態の `branch` |
| リモートから消えた親のブランチへの push を断る（`push-gone-family`） | push の検査 | 取り込み状態の `state` |
| 承認済みの `branch:` のブランチへ移る 1 操作の前提を確かめる（`carry-dirty`・`carry-busy`・`carry-record`・`carry-claimed`） | `co_carry` | 作業ツリー、途中の操作、取り込み状態 |

あわせて、`integrate` / `integrate-done` の状態操作（取り込みの記録の読み書き、`merge --squash`、取り込んだブランチの
`update-ref -d`）も sh が持っている。

別の変更（ADR-0114）で、チケット制御が有効なら生の `git` を組み込みの判定で止めるようになった。git の入口は
`ccnavi-git.sh` 1 本に寄り、その中で何を通すかは許可リストで読む。ここで、上の判定を hook か実行ファイルへ移すかを決める。

## 決定

**入口を sh 1 本に寄せたラッパーの中の可否の判定は、P13 の正式な例外にする。** 例外に入るのは、次の 3 つを
すべて満たすものだけ。

1. **生の操作が組み込みの判定で止まっている。** ラッパーを通らずに同じ操作をする道（生の `git`）を、hook の組み込みが
   止めている。ラッパーの中の判定を外す道は、ラッパーを書き換えること（`guard-scripts` のルールと自己防衛が守る）か、
   生の操作（組み込みが止める）しか無い
2. **ラッパーは許可リストで読む。** 知らないサブコマンド・知らないオプションは通さない。判定が見落とした形は止まる側に倒れる
3. **判定の材料のうち、チケットの中身は実行ファイルに聞く。** sh はチケットの YAML と JSON を自分で読まない。
   親のワークツリーかは `ccnavi tree parent`、親のブランチ名は `ccnavi write-and-push family`、閉じたかは `ccnavi sync closed` に聞き、
   1 行 1 項目の答えを見る。答えが得られないときは、止める側の検査は止める向きに、ツリーを動かす側は動かさない向きに倒す。
   sh が自分で読んでよいのは、sh が書いた取り込み状態（1 行 1 項目）、git の参照と作業ツリー、環境変数だけ

例外に入る判定は「状況」の表の 5 つ。`integrate` / `integrate-done` の状態操作も sh に残す。どれも hook へ移さない。

hook が先に止めるもの（子のワークツリーからの push の `DENY_CHILD_PUSH`、環境変数の差し替えの
`DENY_SCRIPT_ENV_OVERRIDE`）は、これまでどおり sh の側が 2 重目の確認になる。新しい判定を足したくなったら、まず hook に
置けないかを考える、という順も変えない。

子のワークツリーからの push を sh が確かめる 2 重目の検査（`push-child-worktree`）は、条件 3 に揃えず、チケットの `parent:` を
`sed` で読む形のまま残す。hook が先に同じものを止めており、sh 側は実行ファイルが無い・壊れたときにも効く
独立した 2 重目であることに意味があるため（ユーザの決定）。

## 理由

**判定の材料がネットワークと git の手順の途中にある。** 統合先の名前は取り込み結果と `origin/HEAD` から、消えた親の
ブランチは `ccnavi-sync.sh` が書いた取り込み状態から決まる。`co_carry` は作業ツリーと途中の操作を見てから、checkout と
merge を続けて打つ。判定と操作の間に別のプロセス（hook の判定）を挟むと、判定したときと操作するときで状態が変わる隙が
増える。

**入口が 1 本なら、迂回の道は組み込みが塞いでいる。** P13 が sh の判定を 2 重目に限ったのは、sh を通らない道（生の
`git`、環境変数の差し替え）で外れるからだった（ADR-0077）。生の `git` が組み込みで止まり、環境変数の差し替えも止まって
いれば、ラッパーの中の判定は、それだけで外せない。

**チケットを読むのは実行ファイル 1 か所。** 例外を認めても、チケットの読み方を sh に写すと、Python と sh の読み方がずれて
気づかない（ADR-0077 の「sh 側のコピーがずれる」）。材料は実行ファイルに聞き、sh は答えの 1 行で決める。

## 得たもの・失ったもの

- 得たもの: 判定と操作が 1 つの sh の中で続けて走り、間に隙ができない。状態操作（squash・`update-ref -d`）も
  hook の時間の枠に縛られない
- 得たもの: sh が持ってよい判定の範囲が言葉になる。3 つの条件を満たさない判定は例外に入らない
- 失ったもの: **止める・通すの判定が hook・実行ファイル・ラッパーの 3 か所に分かれる。** ラッパーの判定は hook の
  `--test` / `--explain` を通らない（P9 の外）。確かめるのは `tests/sh/` の受入テスト
- 失ったもの: 判定の材料を実行ファイルに聞くので、実行ファイルが無い・入れ替え中・古いときは止まる側に倒れる
  （`integrate` が「確かめられない」で断る、親のワークツリーかを決められないツリーでは checkout が狭まる）。
  ツリーを動かす側（セッションの頭の早送り、取り込み）はその回の動きを見送る
- 残したもの: 子のワークツリーからの push の 2 重目の確認（`push-child-worktree`）は、今も sh がチケットの `parent:` の行を
  自分で読む。ADR-0077 が、YAML として読めないチケットも子と見る広さと、実行ファイルを差し替えても外れないことを
  理由に、実行ファイルに聞く形を採らなかったため。条件 3 に揃えないことは「決定」に書いた
- 失ったもの: ラッパーの中の判定を直すには、`guard-scripts` が守る sh をユーザが差し替える手間が要る

## 採らなかった案

- **判定を実行ファイルへ移し、sh は答えに従うだけにする。** sh は「止めるか」を 1 行で聞き、実行ファイルが統合先の名前・
  取り込み状態・チケットを読んで答える形。判定の置き場は P13 に揃うが、統合先の名前（環境変数・取り込み結果・
  `origin/HEAD` の順）と取り込み状態の読み方を実行ファイルにも持つことになり、`ccnavi-fetch.sh`・`ccnavi-sync.sh`・
  `ccnavi-review.sh` が同じ順で読む `ccnavi_integration` と 2 つに分かれる。`co_carry` は判定の直後に checkout と merge を
  打つので、判定だけを移しても隙は残る。状態操作（squash・`update-ref -d`）を実行ファイルへ移すと、実行ファイルが
  git の参照を書くことになる。実行ファイルは判定と見分けだけを持ち、コミットもしない（write-and-push の分担）ので、その線が動く
- **判定を hook へ移す。** hook はコマンド行しか見ないので、統合先の名前や取り込み状態を読むために hook が git と
  取り込み状態を読むことになり、ツール呼び出しのたびの時間が延びる。`co_carry` の前提（作業ツリー・途中の操作）は
  打つ瞬間の状態で、hook の判定のときと違うことがある
