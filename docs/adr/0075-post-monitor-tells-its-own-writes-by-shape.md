# ADR-0075: 実行後チェックは、自分の副命令の書き込みを正規化した内容で見分ける

状態: 採用

## 状況

実行後チェックは、保護領域をルールファイルの `deny` と `ask` から導く（ADR-0017）。監視の対象から
外していたのは、記録と state の置き場（`CCNAVI_LOG`、`CCNAVI_STATE`）だけだった。

承認済みチケットの置き場（`.ccnavi/approved/`）は、このリポジトリの共通層が
`deny`（`guard-approved-tickets`）と宣言している。ワークスペースルートでは `main-tree` も
同じ場所に当たる。この置き場へ書き込むのは、ユーザの承認だけではない。**`ccnavi-ticket.sh` の
`start` / `done` / `cancel` と、`ccnavi-review.sh` の `request` / `check` / `ready` も書き込む。**
書くのは着手の時刻と基準点、レビュー待ちへの移動、フェーズのマーカーで、どれも手順を進めるための
書き込みだ。その書き込み先が `deny` の範囲の中にある。

その結果、実行後チェックはこれらの書き込みを毎回「エージェントによる書き換え」として報告していた。
報告の文面は `ccnavi did not touch this path` で、ccnavi が自分で書いたものを自分で否定していた。`CCNAVI_MODE` と
`CCNAVI_RESTORE_IF_DENY` の両方を `enable` にすると、**`start` が書いた着手の時刻は
コミット済みの内容へ戻り、`ready` が置いたマーカーは `state/aside/` へ退避される。**
手順はそこで止まる。2026-09-22 に再現して確かめた。

実行前チェックでは、この経路は通る（`tests/guard/test_repo_rules.py`）。スクリプトの実行そのものは
通るのに、書いた結果だけが報告されるという食い違いが起きていた。

`is_ticket_place` は既にあり、実行前チェックと、ターンの終わりに「コミットに入ったぶん」を見る処理
（ADR-0072）は、これを使ってチケットの置き場を対象から外している。ただし、外す根拠は経路ごとに違う。
ADR-0072 が外した理由は「ユーザが承認してコミットするたびに、その操作が違反として並ぶから」だった。
`is_ticket_place` の docstring が理由に挙げていたのは「外しても、承認済みチケットは自己防衛の
組み込みのルールが `deny` で止めるから」で、こちらは実行前チェックの話だ。**組み込みのルールを足すのは
`judge` だけで、実行後チェックが使うルールの集合には 1 本も入らない。** 呼び出しごとの実行後チェックでチケットの
置き場をそのまま外すと、そこへの書き込みを代わりに止めるものが何も無くなる。

## 決定

- 実行後チェックは、チケットの置き場（提案と承認済みチケット）の変更を **内容で見分けて外す**
  （`post._script_writes`）。外すのは次の 3 つ
  - どちらの版も範囲を宣言していないもの（マーカー、`.risk.json`、閉じの記録）
  - スクリプトだけが書くキー（`ticket_model.SCRIPT_FIELDS`）のうち **コミット済みの版がまだ
    持っていないキー** を除いて、1 文字も変わっていないチケット（`ticket_fields.script_shape` が同じ正規化した内容を
    返す）。既に入っている値を書き換えると、正規化した内容が変わる。副命令はどれも 1 度しか書かない
    （`ops.start` は着手済みを拒む）ので、既にある値が変わったのなら、それは副命令が書いたものではない
  - `done` と `cancel` の移動。正規化した内容が同じチケットが作業中（`.ccnavi/approved/doing/`）か
    レビュー待ち（`wip/proposals/review/`）から消えて、レビュー待ちか閉じた置き場
    （`.ccnavi/approved/done/`）に現れた組。**外すのは両側とも 1 件ずつのときだけ。** 片側だけのときや、
    正規化した内容が同じものが 2 つ以上あるときは外さない
- **範囲・親・フェーズ・本文が変わったチケット、既に値のあるキー（`base_sha` など）の値の書き換え、
  新しく現れた承認済みチケット、消えただけのチケットは今までどおり報告する。**
- 見分けるのは **未コミットの変更だけ**。ターンの終わりにコミット済みのぶんを数える処理
  （`_committed_findings`）は、今までどおり置き場ごと外す（ADR-0072）
- **読めなかったものは外さない。** git を起動できない、期限に達した、HEAD が無い、ファイルを
  読めない、のどれも「変わっていない」とはみなさない
- 誰が書いたかの台帳は持たない

## 理由

**台帳を持たない理由。** 承認とマーカーは親のブランチに入ってgit で別の機械と共有され、そこで clone すれば
作業の続きができる（設計 9.2、REQ-MLT-14）。台帳はワークスペース側にあって git に入らないので、
共有された先の機械には 1 件も無い。台帳で見分けると、同じ操作がその機械でだけ報告される。内容で
見分ければ、どの機械でも同じ結果になる。

**置き場をまるごと外さない理由。** 承認済みチケットの frontmatter は、そのワークツリーの
作業範囲そのものだ。まるごと外すと、引数に現れない書き込み（シェル、ビルドの出力、スクリプトが
内部で開くファイル）で自分の範囲を広げる手段が 1 つでき、しかもどのチェックもそれを報告しない。
実行後チェックは、まさにその経路を見るために置かれている。

**戻す働きだけを止める案（`_restorable` でチケットの置き場を外す）も採らなかった。** ccnavi が
書いたものを監視が戻すことは無くなるが、報告は残る。報告に付く `undo:` の手順が毎回モデルに渡り、
モデルが親切にそれを実行すれば、やはり書いたものが元に戻る。

**移動の元と行き先を絞った理由。** `doing/` から出したチケットを `todo/` に置き直す形は、
承認済みチケットを消すのと同じ結果になる。承認済みチケットが 1 本も無いワークツリーは
範囲を持たず、範囲を持たないツリーはチケットによる制限を何も受けない。移動の元の側を絞るのは、
承認を通っていない提案（`todo/`）をレビュー待ちに見せかける形を、外す組に含めないため。

**組を 1 対 1 に限った理由。** どちらかの側に正規化した内容が同じものが 2 つ以上あると、どれがどれの行き先かを
内容からは決められない。決めずに全部外すと、正規の移動 1 件と一緒に、正規化した内容が同じチケットを単に消したものや、
行き先へ直接置いた偽物まで外れてしまう。正規化した内容が同じなら識別子まで同じなので、そうしたチケットが揃うことは
普通の手順では起きない。曖昧なときは報告するほうを選ぶ。

**`base_sha` を落とすキーから外した理由。** `base_sha` はサブエージェント終了時チェック
（`phase.scope_findings` の `base_sha..HEAD`）と実績リスク（`risk.measure`）の基準点で、
書き換えるとコミット済みの範囲外の変更が検査に出なくなる。`base_sha` を「いつでも落とす」キーにすると、
その書き換え自体も実行後チェックに出なくなる。キーごとに例外を並べるのではなく、「コミット済みの版が
まだ持っていないキーだけ落とす」という 1 つの規則にしてある。キーが増えても同じ規則で守れる。

## 得たもの

- **ccnavi 自身の手順が、ccnavi 自身のチェックで止まらなくなった。** `CCNAVI_RESTORE_IF_DENY=enable` に
  したままで使える。ただし `review accept` が `doing/` に起こす続きの子は「新しく現れた承認済み
  チケット」なので、ユーザがコミットするまでは報告と退避の対象のまま（`--approve` で起こした子は直後に
  `ccnavi-push-approved.sh` がコミットするので、これに当たらない）
- 実行前チェックと実行後チェックが揃った。スクリプトの実行が通り、その結果も通る
- 承認済みチケットが宣言する範囲は、引数に現れない書き込みで変えられた場合も、今までどおりチェックされる
- 別の機械へ clone して続けた作業でも、同じ変更が同じように外れる

## 代償

- **範囲を宣言しないファイルは、置いても書き換えても消しても監視に出なくなった。** マーカー
  （`<N>.requested` / `<N>.reviewed` / `ready.json`）だけではない。`.risk.json`（実績の点）、
  `.judge.json`（定性の判定）、`accepted.json`（ユーザが受け入れた指摘）、チケットの置き場に
  置かれたその他のファイルも同じ。正規に置いたものと偽って置いたものを、内容からは見分けられない。
  実行前チェックでは、組み込みのルールが置き場を名指しするツールとシェルを止めるが、引数に現れない
  書き込みは通る。この抜けを埋めるには台帳が要る
- **移動が正規の手順を通ったかは問わない。** `ticket done` は納品物・リスクの記録・親の状態を
  確かめてからチケットを動かすが、正規化した内容が同じチケットを手で動かした形も、1 対 1 の組であれば外れる
- **1 回の呼び出しの中でコミットまで済ませた変更は、どちらのチェックにも出ない。** 呼び出しごとの実行後チェックは
  作業ツリーしか見ず、ターンの終わりの処理はコミット済みのぶんを置き場ごと外している（ADR-0072）。
  これはこの ADR より前からある抜けだ。埋めるには、`_committed_findings` でも基準の版と HEAD の版の
  正規化した内容を照らし合わせることになる。そうするとユーザの承認のコミットが毎回ターンの報告に並ぶ
  （ADR-0072 が避けた形）ので、別の判断が要る
- **git を 1 回多く起動する。** チケットの置き場に変更があった回だけ、ファイル 1 本につき
  `git show HEAD:<path>`（新しく現れたファイルなら `ls-tree` も）が増える
- **`ticket_model.SCRIPT_FIELDS` を増やすと、外れる範囲が広がる。** キーを 1 つ足すと、
  チェックの穴も 1 つ増える。キーを足すときは、このことを思い出す必要がある
- 正規化した内容の比較は行単位なので、スクリプトがキーの書き方を変えた（1 行の値を複数行にした、など）
  ときは正規化した内容が変わり、報告が出る。報告が出たら、直すのはチェックではなくスクリプトのほう
