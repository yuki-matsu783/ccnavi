# ADR-0075: 実行後チェックは、自分の副命令の書き込みを姿で見分ける

状態: 採用

## 状況

実行後チェックは、保護領域をルールファイルの `deny` と `ask` から導く（ADR-0017）。そこから
外れるのは記録と控えの置き場（`CCNAVI_LOG`、`CCNAVI_STATE`）だけだった。

承認済みチケットの置き場（`.ccnavi/approved/`）は、このリポジトリの共通層が
`deny`（`guard-approved-tickets`）と宣言している。ワークスペースルートなら `main-tree` も
同じ場所に当たる。そこへ書くのは、人の承認だけではない。**`ccnavi-ticket.sh` の
`start` / `done` / `cancel` と、`ccnavi-review.sh` の `request` / `check` / `ready` が書く。**
着手の時刻と基準点、レビュー待ちへの移動、フェーズのマーカー。どれも手順を進めるための
書き込みで、置き場は `deny` の中にある。

結果、実行後チェックはこれを毎回「エージェントによる書き換え」として報告していた。文面は
`ccnavi did not touch this path` で、自分が書いたことを自分で否定していた。`CCNAVI_MODE` と
`CCNAVI_RESTORE_IF_DENY` の両方を `enable` にすると、**`start` が書いた着手の時刻は
コミット済みの内容へ戻り、`ready` が置いたマーカーは `state/aside/` へ退避される。**
手順はそこで止まる。再現して確かめた。2026-09-22。

実行前チェックはこの経路を通している（`tests/guard/test_repo_rules.py`）。スクリプトを実行すること
自体は通り、書いた結果だけが咎められる、という食い違いになっていた。

`is_ticket_place` は既にあり、実行前チェックと、ターンの終わりの「コミットに入ったぶん」
（ADR-0072）はこれで置き場を外している。ただし根拠が経路ごとに違う。ADR-0072 が外したのは
「人が承認してコミットするたびに、その操作が違反として並ぶから」。`is_ticket_place` の
docstring が書いていたのは「外しても、承認済みチケットは自己防衛の組み込みが `deny` で
止めるから」で、こちらは実行前の話。**組み込みを足すのは `judge` だけで、実行後のルール集合には
1 本も入らない。** 呼び出しごとの監視で置き場をそのまま外すと、代わりに止めるものが何も残らない。

## 決定

- 実行後チェックは、チケットの置き場（提案と承認済みチケット）の変更を **内容で見分けて外す**
  （`post._script_writes`）。外れるのは 3 つ
  - どちらの版も範囲を宣言していないもの（マーカー、`.risk.json`、閉じの記録）
  - スクリプトだけが書く欄（`ticket.SCRIPT_FIELDS`）のうち、**コミット済みの版がまだ
    持っていない欄**以外が 1 文字も変わっていないチケット（`ticket.script_shape` が同じ姿を
    返す）。既に値のある欄の書き換えは姿に出る。副命令はどれも 1 度しか書かない
    （`ops.start` は着手済みを拒む）ので、既にある値が変わったのなら副命令が書いたものではない
  - `done` と `cancel` の移動。同じ姿のチケットが作業中（`.ccnavi/approved/doing/`）か
    レビュー待ち（`wip/proposals/review/`）から消えて、レビュー待ちか閉じた置き場
    （`.ccnavi/approved/done/`）に現れた組。**両側とも 1 件ずつのときだけ。** 片側だけ、
    あるいは同じ姿が 2 つ以上あるなら外さない
- **範囲・親・フェーズ・本文が変わったチケット、既に値のある欄（`base_sha` など）の書き換え、
  新しく現れた承認済みチケット、消えただけのチケットは今までどおり報告する。**
- 見分けるのは**未コミットの側だけ**。ターンの終わりがコミット済みのぶんを数えるところ
  （`_committed_findings`）は置き場ごと外す旧来のまま（ADR-0072）
- **読めなかったものは外さない。** git を起動できない、期限に達した、HEAD が無い、ファイルを
  読めない。どれも「変わっていない」ではない
- 誰が書いたかの台帳は持たない

## 理由

**台帳を持たない理由。** 承認とマーカーは親のブランチに入って別の機械へ届き、clone すれば
続きができる（設計 9.2、REQ-MLT-14）。台帳はワークスペース側にあって git に入らないので、
届いた先には 1 件も無い。台帳で見ると、同じ操作がその機械でだけ報告される。内容で見れば、
どの機械でも同じ答えになる。

**置き場をまるごと外さない理由。** 承認済みチケットの frontmatter は、そのワークツリーの
作業範囲そのもの。まるごと外すと、引数に現れない書き込み（シェル、ビルドの出力、スクリプトが
内部で開くファイル）で自分の範囲を広げる手段が、どの監視からも報告されないまま 1 つできる。
実行後チェックは、まさにその経路のために置かれている。

**戻す側だけを止める案（`_restorable` でチケットの置き場を外す）も採らなかった。** 手順が
戻ることは無くなるが、報告は残る。`undo:` の手順が毎回モデルに届き、親切に実行されればやはり手順が戻る。

**移動の元と行き先を絞った理由。** `doing/` から出したチケットを `todo/` に置き直す形は、
承認済みチケットを消すのと同じ結果になる。承認済みチケットが 1 本も無いワークツリーは
範囲を持たず、範囲を持たないツリーはチケットによる制限を何も受けない。元の側を絞るのは、
承認を通っていない提案（`todo/`）をレビュー待ちに見せる形を組にしないため。

**組を 1 対 1 に限った理由。** どちらかの側に同じ姿が 2 つ以上あると、どれがどれの行き先かを
内容からは決められない。決めずに全部外すと、正規の移動 1 件に、同じ姿のチケットのただの削除や、
行き先へ直接置いた偽物が紛れ込んで一緒に外れる。姿が同じということは識別子まで同じということなので、
揃うのは普通の手順では起きない。曖昧なら報告する側にする。

**`base_sha` を落とす欄から外した理由。** `base_sha` はサブエージェント終了時チェック
（`phase.scope_findings` の `base_sha..HEAD`）と実績リスク（`risk.measure`）の基準点で、
書き換えるとコミット済みの範囲外の変更が検査から消える。「いつでも落とす」にすると、その
書き換えが実行後チェックからも消える。欄ごとに例外を並べるのではなく、「コミット済みの版が
まだ持っていない欄だけ落とす」という 1 つの規則にしてある。欄が増えても同じ規則で守れる。

## 得たもの

- **ccnavi 自身の手順が、自分の監視で止まらない。** `CCNAVI_RESTORE_IF_DENY=enable` に
  して使える。ただし `review accept` が `doing/` に起こす続きの子は「新しく現れた承認済み
  チケット」なので、人がコミットするまでは報告と退避の対象のまま（`--approve` は直後に
  `ccnavi-push-approved.sh` がコミットするので当たらない）
- 実行前と実行後の判定が揃った。スクリプトの実行が通り、その結果も通る
- 承認済みチケットが宣言する範囲は、引数に現れない書き込みに対しても監視されたまま
- 別の機械へ clone した続きでも、同じ変更が同じように外れる

## 代償

- **範囲を宣言しないファイルは、置いても書き換えても消しても見えなくなった。** マーカー
  （`<N>.requested` / `<N>.reviewed` / `ready.json`）だけではない。`.risk.json`（実績の点）、
  `.judge.json`（定性の判定）、`accepted.json`（人が受け入れた指摘）、チケットの置き場に
  置かれたその他のファイルも同じ。正規の設置と偽の設置を内容からは見分けられない。実行前は
  組み込みが名指しのツールとシェルを止めるが、引数に現れない書き込みは通る。この抜けを埋めるには台帳が要る
- **移動が正規の手順を通ったかは問わない。** `ticket done` は納品物・リスクの記録・親の状態を
  確かめてから動かすが、同じ姿のチケットを手で動かした形も、1 対 1 の組であれば外れる
- **コミットまで同じ呼び出しで済ませた変更は、どちらの監視にも出ない。** 呼び出しごとの監視は
  作業ツリーしか見ず、ターンの終わりのコミット済みのぶんは置き場ごと外している（ADR-0072）。
  これはこの ADR より前からの抜けで、埋めるなら `_committed_findings` でも基準の版と HEAD の版を
  同じ姿で照らし合わせることになる。そうすると人の承認のコミットが毎回ターンの報告に並ぶ
  （ADR-0072 が避けた形）ので、別の判断が要る
- **git を 1 回多く起動する。** チケットの置き場に変更があった回だけ、その 1 本につき
  `git show HEAD:<path>`（新しく現れたファイルなら `ls-tree` も）が増える
- **`ticket.SCRIPT_FIELDS` を増やすと、外れる範囲が広がる。** 欄を 1 つ足すことが、
  監視の穴を 1 つ足すことになる。足すときはここを思い出す必要がある
- 突き合わせは行単位なので、スクリプトが欄の書き方を変えた（1 行の値を複数行にした、など）
  回は姿が変わり、報告が出る。出たときに直すのは監視ではなくスクリプトの側
