# ADR-0120: レビュー依頼までの道の途中で終えようとしたら、Stop で 1 回だけ止めて次の一手を返す

状態: 採用

## 状況

チケット作業の道は決まっている。子の `finish`、親ブランチへの合流、ELI5 の HTML、`ccnavi-review.sh request`
（`requested` のマーカーが置かれる）。ここから先はユーザのレビューで、エージェントは待つ。

MR #313 のフェーズ 1 で、エージェントが道の各所（`finish`・合流・ELI5・`request`）で「進めてよいですか」と
確認してターンを終え、そのたびにユーザが「進めて」と打つ往復が起きた。どの確認も、ユーザの許可が要る
分岐ではなく、決まった道の次の一手だった。作業を終えたのに `finish` されていない形は
既に Stop で促している（`finish` の促し）が、それは子のコミット済みの形だけで、合流以降は拾わない。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| 最後の発言に問いがあるかは見ない。transcript も最後の発言も読まず、hook の入力欄も増やさない。問いで終わった回も止める | 問いの有無は文面の解釈で、読み違える。状態（親・フェーズ・子・マーカー）だけなら ccnavi が確かめられる範囲で決まる。本当にユーザの判断が要る問いは、促しの文が「その問いを最後に書き直して終える」と言うので消えない（ターンの終わりの振り返りの前置きと同じ考え方） | 最後の発言の末尾が問いかどうかで止める。transcript を読む経路が要り、言い回しで外れる |
| 止める条件: 承認済みの親（着手済み・信頼できる・早めに閉じていない）に結び付いた cwd で、(a) 作業中（`doing/`、着手済み）の子が残っている、または (b) 子が全部閉じ、レビューを要するフェーズに `requested` のマーカーがまだ無い。子のツリーでは自分の子の (a) だけを見る | 道の途中は、`requested` が置かれる手前まで。並行して動く別の子は別のセッションの作業で、巻き込まない。(b) は親の仕事（合流・ELI5・依頼）なので親のツリーだけ | 全部の子を子のツリーでも数える。別のセッションの作業に促しが出る |
| 止めない: `requested` が在る（レビュー待ち以後）、サブエージェントの終わり、`stop_hook_active` が真、state の置き場が無いか書けない、チケット制御が `disable`、モードが `disable`、このセッションで見る計画（`review: chat`）の依頼前、レビューが要らない／延期したフェーズ、ユーザが早めに閉じた親 | `requested` は変更要求（changes requested）のレビューが残る間も残る（その間は `reviewed` を置かないだけ）。同じフェーズに子を足すと `requested` が外れて足した子が作業中になるので、そのときは止めてよい。`review: chat` は依頼を打たずユーザが端末で進める | `requested` ではなく `reviewed` の有無で見る。変更要求の間ずっと止まる |
| 文は理由コード `NUDGE_TICKET_REQUEST` で始め、「決まった道の途中でユーザの許可は要らない。次を実行する。本当にユーザの判断が要る問いなら、その問いを最後に書き直して終える」と、状態に応じた次の一手を言う。一手は、作業中の子の `finish`、合流していない子の `merge`、ELI5、`request`。合流は子のブランチが親の HEAD の祖先かで、ELI5 は `wip/eli5/phase-N.html` の有無で見分ける | 打つコマンドまで言わないと、確認を取り直して止まる | 「進めてください」だけを言う |
| 同じ状態につき 1 回だけ。鍵は「親＋フェーズ」、値は状態の要約（一手の種類・残っている子・親のツリーの HEAD）。`finish` の促しと同じ `nudged-<セッション>.json` に `request:` で始まる鍵で置く。進めば（子を閉じる、合流する、コミットを足す）次に終えるときまた止めてよい | ターンの終わりのたびに止めると、促しが読まれなくなる。ファイルを分けると、後始末（prune）の対象にも足すことになる。鍵の頭を分ければ、チケットの識別子と重ならない | `stop_hook_active` だけに頼る。連鎖の 2 回目しか言わない。別のファイルを足す |
| 1 回の Stop で止める理由は 1 つ。順序は `finish` の促し → この促し → `match: Stop` のルール。前の促しが止めた回は、後ろの促しを出しも数えもしない | 数えを進めて届かない回を作らない | 全部を 1 つの文にまとめる。何を先にすればよいか分からなくなる |
| `dry-run` でも止める。記録は `decision: nudge`、`code: NUDGE_TICKET_REQUEST`、`enforced: true` | Stop でモデルに文を届ける経路は止めることしか無い。`finish` の促しと同じ | `dry-run` では止めない。文が届かない |
| 判定は実行ファイルの `ops_stop_request.pending_at_stop` に置く。見るのは承認済みチケット、マーカー、git（`rev-parse`、`merge-base --is-ancestor`）、ELI5 の有無だけ | 実行ファイルの境界の中。ネットワークには出ない | sh で見る |

## 得たもの・失ったもの

- 得たもの: 決まった道の途中の確認で止まる往復が、状態を見るだけで減る。最後の発言を読まない
- 失ったもの: 問いで終わった回も止まる。ユーザの判断が要る問いのときも 1 回は止まり、問いを書き直す手間が増える
- 失ったもの: **バックグラウンドのサブエージェントに任せてターンを終える回も、作業中の子が残っていれば止まる。**
  SubagentStart / SubagentStop は「開始したが終わっていない」サブエージェントの記録を残さないので、
  確実に見分けられない。誤って止めるより見逃すほうが害が小さいが、この形は止まる側に倒れている。
  1 回だけなので、待つ理由をユーザに書けば通る
- 失ったもの: 進むたびに 1 回ずつ止まる。道の 4 手（`finish`・合流・ELI5・`request`）で最大 4 回
- 失ったもの: 合流の確認は子のブランチが親の HEAD の祖先かだけ。squash で取り込んだ子は祖先にならないので、
  合流の案内が残ることがある
- 失ったもの: `review: chat` のフェーズは依頼の前を促さない（作業中の子の `finish` は促す）
- 失ったもの: `finish` の促しで止めた次の回に、同じ状態でこの促しがもう 1 回出ることがある

## 採らなかった案

- 最後の発言を読んで、問いで終わったときだけ止める。上のとおり、文面の解釈に頼る
- `finish`・合流・ELI5・`request` を自動で打つ。閉じるかどうかの判断は作業した側にあり、依頼文はエージェントが書く
