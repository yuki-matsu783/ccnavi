## 1. 概要

### 1.1 何を解くか

Claude Code のエージェントは、作業に必要だと判断すると、禁止された操作を突破しようとする（hook を外す、deny を緩める）。
設定のパターン一致はコマンドの構造（連鎖・サブシェル・リダイレクト）を見ないので、複合コマンドの後段は判定されずに通る。
プロンプトでの禁止は確率を下げるだけである。静的な権限は、広く開けるか毎回確認するかの二択になる。拒否の根拠は、
エージェントが書き換えられるワークツリーの中にある。

ccnavi は Claude Code の hook から呼ばれ、危ないツール呼び出しを止め、「代わりに何をすればよいか」を名指しで返す。これは 4 つのコア機能の 1 つ目（1.1.1）の出発点である。
止めるだけだと、エージェントは別の表記で打ち直す。そのため、拒否は別の手段へ誘導する文と一緒に返す。

### 1.1.1 コア機能と設計原則

コア機能の定義は要件書（[10_requirements.md](10_requirements.md) の「コア機能」）にある。設計の置き場は、ルールによる作業のガードとガイドが 5〜8 章と 10 章、チケットによる作業・レビュー管理が 9 章と 11 章、ドキュメント・スキルの検索と必要時の参照が 4 章と 11 章、記録と振り返りによる改善が 4 章・9 章・10 章である。判定は hook の処理がモデルのコンテキストの外で行い、関係する場面で文面（`message` と `additionalContext`）を届ける（6.6）。

ガイドと検索の違いは、届くきっかけにある。ガイドは操作や作業の状況がきっかけで、判定の結果と一緒に届く。検索は、エージェントが情報を必要としたときに自分で引く。

製品の考え方は、5 つのテーマに分けて[ccnavi の思想](00_idea.md)に書く。P1〜P14 は、そのテーマを実装に落とした決まりで、対応は次のとおり。

- **テーマ 1 エージェントに、指示と制約を守らせる**（P1〜P9、P13）。判定と案内はモデルの外の hook が持ち、拒否は誘導と一緒に返し、逸脱は見せる。宣言された制約は緩めない
- **テーマ 2 計画で決めて、そのとおりに進める**（P2、P12）。承認された範囲の外を止め、親のコンテキストは計画・判断・報告に絞って、作業は子に切り出す
- **テーマ 3 レビューを厳密に管理する**（P10、P11）。承認・レビュー・採否は、人間が直接操作する場所で受ける。実行ファイルは自分のディレクトリの外を見ず、ホスト上のレビューは sh がつなぐ。親のブランチ上のチケットとマーカー、ホスト上のレビューで、複数の PC・セッションをつなぐ（同期は操作の時点で行う。9.17）
- **テーマ 4 設定ファイルを共通とプロジェクトで共存させる**。個別の P はなく、複数リポジトリの章（11 章）が受け持つ
- **テーマ 5 必要な情報を必要な時に届け、記録から育てる**（P14、P10）。開始時は作業の前提と入口だけを渡し、具体的な理由と手順は関係する場面で、詳しい資料は必要なときに引く。改善の採否は人間が決める

### 1.2 骨子

| 骨子 | 中身 |
|---|---|
| 判定はルールで、既定は委ねる | ルールファイルの `deny` / `ask` / `allow` にヒットすればその判定。ヒットしなければ ccnavi は判定を持たず、Claude Code の権限モードに従う（6.5） |
| 引数に現れない書き込みは実行後に拾う | 実行前チェックはツール呼び出しの引数を見る。ビルドの出力やスクリプトの中のファイル操作は、実行したあとのワークツリーを git で読んで拾う（7 章） |
| ガード自身の設定はルールの外で守る | ルールが空にされた場合も不正になった場合も、ルールから導いた保護領域は 0 件になる。そのため hook の登録・ルール・実行ファイルは、組み込みの仕組みでバックアップを取って戻す（8 章） |
| チケットは絞る向きにだけ働く | 承認された範囲の外を止め、中は聞かない。ルールの判定と比べて強い側を採るので、ルールの `allow` も範囲の外では止まる。判定のキーはファイルの行き先が属するワークツリー（9 章） |
| 実行ファイルは自分のディレクトリの外を見ない | マージリクエストやレビューのスレッドは `.ccnavi/scripts/` の sh が取得して JSON ファイルに書き、そのパスを `--result` で渡す。実行ファイルはネットワークに出ない（9.10） |

### 1.3 失敗の向き

誤検知なら、エージェントが一手止まるだけで済む。一方、止めるべき呼び出しを通すと気づけない。判断がつかないときは拒否にする。

ただし、設定 1 つの破損で回復手段まで奪う形は作らない。ルールが読めなければ、組み込みの既定を使って判定を続ける（5.6）。
未承認のチケットは判定に何も反映しない（9.4）。ルールファイルが読めない間は `Write` / `Edit` も止める。直す道は、下書きを `wip/handoff/` に置き、ユーザが `ccnavi-user-handoff.sh` で取り込む形（8.2）。

## 2. 脅威モデルと守るもの

### 2.1 想定する主体

| 主体 | 説明 | 対象か |
|---|---|---|
| 逸れていく LLM | 悪意はないが、文脈の薄れ・誤解・思い込みにより破壊的な操作を行う | 主対象 |
| 誘導された LLM | 取り込んだページ・issue の本文・依存パッケージの文書に混じった指示に沿って動く | 主対象 |
| 事故 | 正常なコマンドの副作用、ビルドの想定外の出力 | 主対象 |
| 実行環境を掌握した攻撃者 | 同一ユーザ権限で任意のシェルを実行できる | 対象外 |

同じ権限で動く hook は、任意のシェルを実行できる主体に対しては境界にならない。ccnavi は LLM の逸脱と事故に対する柵である。
最終防衛線は、OS・DB・実行環境の権限分離が担う（12 章）。

判定は呼び出しの内容だけから決め、その呼び出しを引き起こしたテキストの出どころでは変えない（REQ-PRE-09）。
出どころを理由に例外を設けると、注入された文も、出どころを自称すればその例外を受けられる。

### 2.2 守るもの

| 何 | 想定する被害 | 守る仕組み |
|---|---|---|
| hook の登録、ルール、実行ファイル、保護済みスクリプト、承認済みチケットとマーカー | 防御そのものの無効化 | 自己防衛（8 章）とルールの `deny`、状態の置き場の組み込み拒否（9.5） |
| 認証情報の置き場、取り返しの付かない操作（`rm -rf`、`git push`、`git reset --hard`） | 漏洩、消失 | 組み込みの既定（5.6）とプロジェクトのルール |
| プロジェクトが `deny` / `ask` と宣言した場所 | 意図しない書き換え | 実行前チェック（6 章）と実行後チェック（7 章） |
| チケットが宣言した範囲の外 | 作業の範囲の逸脱 | チケット制御（9.5）とサブエージェント終了時チェック（9.12） |
| レビューを通っていない成果 | ユーザが見ていないものの合流 | フェーズの HITL ポイント（9.8）とレビューの確認（9.10） |

## 3. 設計原則

| # | 原則 | 中身 |
|---|---|---|
| P1 | 拒否にするが、回復の手段は残す | 対象を確定できない呼び出しは許可にしない（6.3）。設定が読めないときは既定を使い、直す手段を残す（5.6） |
| P2 | 宣言された制約は緩められない | ルールの `deny` / `ask` は、チケット・環境変数のどれによっても緩まない。チケットはルールと比べて強い側を採り、ルールの `allow` も狭める（9.5） |
| P3 | 言及の無い呼び出しは委ねる | ルールが言及しない呼び出しは権限モードに委ねて記録に残す（6.5） |
| P4 | 組み込みは最小 | ルールの外で持つのは、ガード自身を守るものと、取り返しの付かない操作だけ（5.6、8 章）。チケット制御が有効な間に生の git を止める組み込みは前者で、ラッパーの中のチケット制御の可否を外させないためのもの（9.1） |
| P5 | 判定の根拠を構造化する | すべての判定は理由コード・対象・ヒットしたルールの識別子を持ち、記録と文面と試験の出力を同じ材料から作る（6.4、付録 A） |
| P6 | 逸脱は必ず見せる | 委ねた回、既定を使った回、実行後チェックが見られなかった回も 1 行ずつ記録し、実行後に汚れた保護領域はモデルとユーザの両方に示す（4.7、7 章） |
| P7 | 静的と動的の二段 | 実行前のコマンド構造の解析と、実行後の git の状態の検証を併用する（6 章、7 章） |
| P8 | 拒否は誘導と一緒に返す | `deny` の文面は「なぜ止めたか、代わりに何をするか」を必ず持つ。持たないルールは受け付けない（5.1） |
| P9 | 判定と試験は同じ関数 | `--test` と `--explain` と拡張の JSON は hook の判定と同じ関数を通る（10 章） |
| P10 | ユーザの判断はユーザが直接操作する場所で受ける | 承認、レビュー済み、未解決の指摘の行き先、親を早めに閉じる操作は、ユーザがターミナル・ボード・Chrome 拡張のどれかで操作する。エージェントがシェルから同じ操作を打つ形は組み込みの deny が止める。エージェントがユーザの合意を出せる形を作らない。受け方の細部は 9.4 と 9.10 |
| P11 | 実行ファイルの境界は自分のディレクトリ | 実行ファイルが見て判断するのはワークツリー、git のオブジェクトと参照、承認済みチケット、マーカー、hook の payload だけ。外にあるものは sh が JSON ファイルに書いて渡す（9.10）。例外は、リスクの配点の `script:`（ユーザが置いたスクリプト）を起動して点を受け取ること（9.9） |
| P12 | 親のコンテキストは清潔に保つ | 親（メインエージェント）は計画・提案・子の起動・合流・レビューの依頼だけをし、作業は子に切り出す。ccnavi が親へ返す文も短く、詳細は子へ渡す（9.7） |
| P13 | 止める・通すの判定は hook と実行ファイルが持つ | sh が持つのは、外との出入り・実行ファイルへの入口・打たれた形（コマンド行・パスの表記）の検査・運用の道具の 4 つ。sh が ccnavi の状態を読んで止めるのは 2 重目の確認で、同じことを hook が先に止める（8.2、9.10）。チケット制御が有効な間は生の git を組み込みで止め、git の入口を `ccnavi-git.sh` の 1 本に寄せる（9.1）。ラッパーの中の可否の判定と `integrate` / `integrate-done` の状態操作だけが例外（9.2） |
| P14 | 先に詰め込まず、危険と失敗を検知して正しい方法を促す | 起動時にエージェントへ渡すのは最小の案内だけにして、決まりを全部は入れない。危険な作業とよくある失敗は、hook と `--lint` が起きた時点で検知し、その場で「何が起きたか・代わりに何をするか」を返す。判定は変えず、案内を足す形を基本にする。新しい失敗が見つかったときも、まず検知して案内する道で直す（P8、P12） |
