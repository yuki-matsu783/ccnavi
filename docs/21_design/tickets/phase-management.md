### 9.14 フェーズ管理の全体像

フェーズ管理は、大きな作業を「親の計画に並べた番号付きのまとまり」に分け、まとまりごとに順序と
ユーザの確認を決める仕組み。この節は全体をつなぐ入口で、各部分の細部は 9.6〜9.11 にある。
用語は CONTEXT.md の「フェーズ」の項に従う。

**何を管理するか。** 次の 3 つで、それぞれ持ち主と置き場が違う。

| 対象 | 何か | 持ち主 | 置き場 |
|---|---|---|---|
| フェーズ定義 | 名前付きの型（種類、見る場所、範囲の上限、成果物） | ユーザ。エージェントは書き換えない | `phases.yml`（9.7） |
| 計画 | 親が `plan:` / `feedback:` に並べる、定義の並びとステップの `after` | 親が書き、ユーザが `user agree` で合意する | 親の提案・承認済みチケット |
| フェーズ | 計画の番号付きの実体。同じ親の同じ `phase` 番号の子をまとめたもの | 子のチケットの状態から導出する。専用のファイルは無い | 子の置き場（9.6） |

「終わった」「レビュー要」「止めている」は、子の置き場と
マーカーから都度導出する（9.6、9.8）。

**1 つのフェーズの一生。**

```
  計画にステップとして並ぶ（全体計画の合意）
        │  先行する番号が全部閉じてレビュー済みになるまで、その番号の子は承認されない（順序は承認で止める）
        ▼
  子を提案して承認（user agree）──→ 親が子ごとにワークツリーを切って着手（start）
        ▼
  子が作業し、閉じる（finish）。成果物（deliverables）が無ければ閉じられない
        ▼
  番号の子が全部閉じた = フェーズが終わった
        │
        ├─ review: none ─→ skipped（次へ進む）
        └─ review: mr ──→ pending ─→ request ─→ requested ─→ confirm / decide / Chrome のレビュー済み ─→ reviewed
```

- 順序を決めるのは計画のステップの `after` だけ。先行関係は承認済みチケットの計画から
  都度計算する（9.7）
- 見る場所（`none` / `mr`）は、定義の `review`、ステップの `mr`、引き受けた延期の分のうち厳しい側。
  `reviewed` が付くまで、その親からは次の子を起こせない（9.8）
- `defer`（延期）のステップは止めず、次にレビューがあるフェーズの依頼に含める。省略ではない。最後のステップは延期できない（9.7）
- レビューで指摘が残れば、同じ番号に続きの子を足してやり直すか、受け入れて閉じる（9.10）

**2 つの計画。** 全体計画（`plan`）は親の承認で合意する。全体計画の最後のレビューが済んだあと（`reviewed`。
依頼しただけでは足りない）、フィードバック計画（`feedback`。指摘が無くても `[]` で）を改版として 1 回だけ出して合意する。
この承認はレビューの状態を変えない。
番号は全体計画が 1 から、フィードバック計画がその続き（9.7）。

**親の局面。** 局面は、親が計画のどこにいるかを表す呼び名。表示と案内（拒否の文面、`--explain`、ボードのバッジ）が使う。

| 局面 | 親の状態 | 次に動く者 |
|---|---|---|
| 全体計画待ち | 計画が承認されていない | ユーザ（`user agree`） |
| 作業中 | 作業中の子がいる | エージェント |
| レビュー準備中 | フェーズが終わり、依頼を出していない | エージェント（合流済みの確認・push・`request`） |
| レビュー待ち | 依頼を出した。`reviewed` が無い | ユーザ（`confirm` / `decide` / Chrome 拡張のレビュー済み） |
| フィードバック計画待ち | 全体計画が終わり、`feedback` が承認されていない | エージェントが出し、ユーザが `user agree` |
| フィードバック対応中 | フィードバック計画の子が作業中 | エージェント |
| 閉じられる | 全フェーズが閉じ、`feedback` が承認済み | エージェント（`finish` → push → `ready`） |

**役割の分担。** 親は計画・依頼だけをし（合流は子の `finish`）、作業は必ず子に切り出す。親のコンテキストに作業の出力が積もると、
計画と依頼の判断が薄まるため。ユーザの手が入るのは、範囲の承認（`user agree`）、フェーズの終わりのレビュー、
未解決の受け入れの 3 か所（9.8）。

**親を閉じる。** 計画のフェーズが全部閉じ、`feedback` が承認済みで、止まっていないとき（9.11）。
未完でも早く閉じたいときは、ユーザが `ccnavi-user-close-early.sh --reason` を打つ。

**どこを読むか。**

| 知りたいこと | 読む節 |
|---|---|
| フェーズ定義の欄、計画の書き方、`after` と延期、承認での検査 | 9.7 |
| 子とマーカーの置き場の遷移、誰がいつ動かすか | 9.6 |
| フェーズの終わり、見る場所、止める仕組み、呼び名 | 9.8 |
| 子を閉じるときのリスク | 9.9 |
| レビューの依頼・確認・続きの子 | 9.10 |
| 親を閉じる、早めに閉じる、Draft を外す | 9.11 |
| なぜこの形か | ADR のうち、フェーズの種類と計画、`order: dag` の先行関係、計画の順序、親は計画を必ず持つこと |
