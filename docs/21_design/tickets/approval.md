### 9.4 承認

計画を立てている間、親はルールだけで動く。計画が終わったらユーザがターミナルで `ccnavi-user-agree.sh` を打つ。標準入力が
ターミナルでなければ拒む（`CCNAVI_GUARD_TICKET_APPROVAL=disable` で免除）。引数は無く、承認の対象は
「`todo/` に在って、同じ識別子がどの置き場（作業中・レビュー待ち・閉じた）にも無い提案の全部と、
親の改版」。承認は提案を `todo/` から `.ccnavi/approved/doing/` へ動かす。
改版するときは、同じ識別子の提案を `todo/` に書いて出す。承認すると `doing/` の側は計画・`phases:`・範囲だけが差し替わり、`todo/` の側は
消える。提案の置き場は、ワークスペースルートと `.claude/worktrees/*` の全部を走査する。

識別子を並べた `ccnavi-user-agree.sh <識別子>...` はその識別子だけを対象にする（VS Code 拡張とターミナルの
`ccnavi-user-agree.sh <識別子>...` が使う。sh は `-` で始まる語と空の語を受けない）。絞りは対象を狭めるだけで、
絞らないときに外れるものは通さない。承認待ちに無い識別子が混じれば何も承認せず、親の改版が承認待ちなのに
対象に無い子も何も承認しない。対象から外した親を持つ子は「親が承認されていない」で外れる。

同じ識別子が複数のツリーにあれば、承認済みチケットと同じ、正とする側の決め方（9.2）で 1 つを採る。
元ツリーの版の比べ方は置き場の順（`todo` < `doing` < `review` < `done`）。別のリポジトリの同じ識別子は
1 つにまとめない（別のチケットとして扱う）。決まらなければ全部残り、`--lint` と状態の操作が「複数の場所にある」と言う。同じツリーの
中で同じ識別子が 2 つの置き場に在るとき（移動の途中で止まった形跡）も同じ。

親の提案は、新規も改版も `issue:` と `mr:` の両方が要る（書いていなければ承認しない。子には求めない）。
承認は提案の中身を変えないので、提案に書いた `mr:` はそのまま承認済みチケットに入り、ダイジェストにも入る（提案の全文）。
承認のあとに `review request` が書き足す `mr:`（空のときだけ。`proposal-format.md`）はダイジェストの外で、改版の不変検査は
両方に値があって違うときだけ error にする。

順序は「承認 → コミット（と push）→ 子のワークツリーを作る → `start`」。コミットの前にワークツリーを
作ると、その子には範囲が適用されない。

承認画面に出るのは、件数、各提案の識別子とタイトル（親 / 親 X、フェーズ N: フェーズ定義名）、親なら
「このチケットで編集可能な範囲」、子なら「この子チケットで編集可能な範囲」とフェーズ定義の範囲の上限、新規の子なら親の
`issue:`、子の人間レビュー
要否と先行、親の全体計画とフィードバック計画、理由、ワークツリーと提案のパス、判定に効かない記述の
warn、チケットで編集対象としているが書き込めない場所（下）。計画を持つ親なら、親に固定するフェーズ定義を 3 つに分けて出す
（この親が使う定義＝タイトル・`review`・`scope`・`deliverables`・使う番号、使われていない定義、`phases.yml` にあってこの親では使わない
定義。9.7）。改版なら範囲の差分（追加・削除）と計画の差分と `phases:` の差分（足した・外した・変わった定義。改版が書く中身から組む）。リスクの点は出ない（9.9）。`y` / `yes` でまとめて承認する。1 件だけの
承認はできない。

承認時に確かめること。親の計画と、親に固定するフェーズ定義のコピー（`phases:`）が噛み合うか（計画を持つのにコピーが無い、
ステップの定義がコピーに無い、`kind`、延期できる定義か）と、コピーの各定義が承認したときの `phases.yml` の同じ名前の定義と読んだ形で
同じか（違う・名前が `phases.yml` に無いは error。`phases.yml` にあってコピーに無い定義は何も言わず、コピーにあってどのステップも使わない
定義は warn。改版では、子が承認された番号が使う定義は `phases.yml` ではなく承認済みチケットのコピーと比べる。9.7）と、
計画の順序が組めるか（ステップの `after` の形、終端は 1 つ、最後のステップは延期できない、延期の引き受け手とそのレビュー。
全体計画とフィードバック計画の両方。9.7）。先行関係は承認済みチケットの計画のステップの `after` から
都度計算する（9.7）。提案にスクリプトだけが書く欄（`started_at`・`completed_at`・`base_sha`・`merged_sha`・`cancelled_at`・`cancel_reason`）の空でない値や
`workflow:` の欄が無いか。子の親が承認の対象の中か承認済みチケットにあるか、深さ 2 段。
`project` が置き場に在るか、子は親と同じか。前のフェーズが閉じてレビュー済みか（9.7）。子の先行（`predecessors`）が
全部 `done/` に在って取り消しでないか（先行が閉じれば通るものはフェーズの順序と同じく「まだ承認できない」、
取り消し・どこにも無い・複数の場所はふつうの error）。error が
あればその提案は外して標準エラーに出し、読めない提案があって承認するものが無ければ 1 を返す。

**範囲の広さは承認で止めない。** 子の項が親の範囲を超える、フェーズ定義の `scope` を超える、regex で
どちらにも入るかを確かめられない、親の `allow` の項が計画のどの定義の `scope` とも重ならない（#424。
`scope: inherit` の定義が計画にあれば言わない）、の 4 つは warn（判定が切り詰める。9.5）。error は「チケットの形」の検査。
超過は承認画面の見出し「チケットで編集対象としているが、書き込めない場所」に出す。`--agree --preview --json`
では `batch[]` の `overflow[]` に載り、超過だけの子は `batch[]` に入る。`--lint` も warn。

**承認はチケットの中身を変えない。** 承認済みチケットは提案のファイルそのもので、承認は `todo/` から `doing/` へ
rename するか、バイト単位でコピーして元を消す。欄を書き足さず、改行も BOM も変えない。ターミナル・ボード・Chrome 拡張・手で
動かす、のどれで承認しても、承認済みチケットは提案とバイト単位で同じになる。欄の有無が承認の経路を表すと、読む側は欄の
無いもの（手で動かした承認）を不正な承認と読み違えるため。承認済みチケットのプロジェクトは置き場（ツリー）から決まる。
承認画面の「提案:」はツリーからの相対パスで出すので、画面の本文とダイジェストは機械に依らない。

表示（ボード・`--diagnose`・`ccnavi-ticket.sh status`）は、
`git log --no-renames --diff-filter=A` で `doing/<識別子>.md` を足したコミットの時刻を読む。
`--no-renames` を付けるのは、GitHub の画面での移動が rename のコミットになるため。どれも無ければ「未コミット（手で置いた）」と
出す。

承認が中身を変えないので、提案に書いた値はそのまま承認済みチケットの値になる。提案（`todo/`）にスクリプトだけが書く欄の空でない値が
あれば、`user agree` と `--lint` が error にする（判定では提案に適用しない）。改版の提案も同じで、承認済みチケットをコピーして書くときは
`started_at`・`completed_at`・`base_sha`・`merged_sha`・`cancelled_at`・`cancel_reason`・`finished_to`・`settled_by` を空にする（`ccnavi ticket revise` の雛形は、これらの欄を外して書く。改版は承認済みチケットの側の値を残し、計画・
`phases:`・範囲だけを差し替える）。続きの子の目印 `followup_of` も、ユーザの判断だけが残す欄なので、提案にあれば
`user agree` と `--lint` が error にする（改版の提案でコピーしたときも消す）。`wip/proposals/review/` で読むのは `completed_at` に値があるもの（`finish` が書く）だけ。判定が読むのは `doing/` だけで、
承認後に同じ識別子の提案を `todo/` に書いても、適用される範囲は変わらない（親の改版〔計画・`phases:`・範囲〕だけが承認の対象に入る）。
終わったフェーズに子を足して
承認すると、その番号のマーカーを全部消す。

**承認する場所は 4 つある。** ターミナルの `user agree`、VS Code 拡張のボードのオーバーレイ、Chrome 拡張のボード、そして
置き場を動かすこと。
オーバーレイは `--agree --preview --json [<識別子>...]` で一覧を読み、ユーザが押したら
`user agree --yes <識別子,…> --digest <値> --json` を子プロセスで打つ（形は docs/11_requirements/json-shapes.md「承認の JSON」）。
どちらも承認の対象を同じ関数で求めるので、見せたものと承認するものが食い違わない。

| 経路 | 誰が打つ | ユーザが押したことの証拠 |
|---|---|---|
| `ccnavi-user-agree.sh [<識別子>...]` | ユーザがターミナルで | 標準入力がターミナルであること。hook の中や `echo y \|` から来ていないことの、いちばん安い証拠。y の入力のあとに、見せた提案と今の提案を同じ照合にかける |
| `ccnavi user agree --yes <識別子,…>` | 拡張が、ユーザがオーバーレイで押したときに | 見せた提案（識別子の一覧と各提案ファイルのバイト列）が今も同じこと。加えて、組み込みの deny がシェルからの `--yes` を止める |
| Chrome 拡張のボードで承認を押す | ユーザが、ブラウザで | PAT の持ち主が書き込みの権限を持つこと。承認は 1 コミットとしてリモートのブランチに書かれる |
| 提案を `.ccnavi/approved/doing/` へ動かす | ユーザが、git を触れる場所で（GitLab や GitHub の画面など） | その置き場にエージェントが書けないこと。動かせたのは書ける権限を持つユーザだけ |

`--yes` にターミナルを求めないのは、拡張の子プロセスがターミナルを持たないから。残った指摘の対応方針（9.10）も
同じ形でボードから送る。

**置き場を動かす経路の検査は判定が持つ。** 親が引けない、親自身が子、番号が親の計画に無い、`project:` が
置き場と違う、予約名を指している、のどれかにヒットする承認済みチケットは、`scan` が `Ticket.blocked` を
立て、`scope_verdict` が範囲を適用する前に止める（実行前チェック・実行後チェック・サブエージェント終了時チェックで
同じ）。理由コードは `DENY_TICKET_BLOCKED`（ユーザがチケットを直すまでどこにも書けない）。フェーズの順序と
計画の形はここに入れず、`--lint` が warn で言う。

**承認の照合は、ターミナル・ボード・Chrome 拡張で同じ強さにする。** 照合するのは、承認の対象の提案の識別子の一覧と、
各提案ファイルの**元のバイト列全体**（本文・改行・BOM を含む）だけ。解析した後の値では比べない。
承認の可否は、承認の直前に最新の状態から計算し直す（外れた提案があれば承認しない）。

- ダイジェストは、識別子の順に「識別子と提案ファイルの SHA-256」を並べ、件数を頭に付けて、その全体の SHA-256 を取る
  （`agree_digest.proposals_digest`）。`--agree --preview --json` が `digest` として出す
- ボードは `--yes` に `--digest <値>` を付け、実行ファイルが承認の直前に取り直したものと比べる。違えば何も置かず
  `mismatch` と `digest: {expected, current}` を返して 1 で終わる。`--digest` が無いときも 1。値の大文字小文字の違いは無視する
- ターミナルの `user agree` は、y の入力のあとに最新の状態から取り直して比べる。Chrome 拡張は、親のブランチの先頭が動いたら
  読み直して同じ照合をする
- **違いが見つかったら、拒否で終わらない。** 「内容が更新されました」と伝えて最新の一覧を表示し直し、もう一度押して（y と答えて）もらう。
  何も承認しない。ボードは同じ絞りで読み直し、絞りが通らなければ絞りを外して全体を出す
- 指した識別子が承認待ちに残っていなければ、残りや増えた提案を代わりに承認しない
- レビュー指摘の対応方針（9.10）の照合と、計画編集の保存のハッシュは別で、この照合では変えない

**承認済みチケットは push するまで届かない。** 承認済みチケットは親のツリーの置き場
（`.ccnavi/approved/`）に置かれ、コミットして push するまで子のワークツリーにも他の機械にも
渡らない。どちらの経路でも、承認のあと `ccnavi-user-push-approved.sh` がコミットして push する。変更のあるツリーごとに
置き場と、承認で `todo/` から消えた提案（追跡されていたものの削除だけ）をコミットし（パスを限る。
`-a` も `add -A` も使わない）、保護されたブランチ
（`main` / `master` / `develop` / `release` / `release/*` と、`ccnavi-common-state.sh` の `ccnavi_integration` が決める
そのリポジトリの統合先。決まらなければ固定のリストだけ）でなければ push する。

| 経路 | 承認の push |
|---|---|
| ターミナルの `ccnavi-user-agree.sh` | 承認が通ったあとに sh から `--path <パス>...` つきで呼ぶ。渡すのは、この承認が書いた・消したパス（実行ファイルの `--record-writes` の一覧）だけで、同じ置き場の承認と無関係な変更は入れない。承認の push に失敗しても承認は 0 で終わる（コミットは残り、打ち直せば送れる。未送信のパスは文面で言う）。一部だけ書けたとき（実行ファイルの終了コード 4）も、書けた分をコミットして push し、書けた分と書けなかった提案を `--placed-out` の JSON で言う（終了コードは 1） |
| ボードの承認 | 1 件以上承認したら、`ccnavi-user-push-approved.sh --path <パス>...`（`--yes --json` の `written` のパス）を絶対パスでターミナルに送り、Enter まで送る。途中で止まったときも、書けた分（`partial.placed` が空でないとき）は `partial.written` で同じように送り、書けなかった提案と未送信かどうかを画面に出す。sh が無ければ送らず、導入スクリプトで配るよう警告で言う |
| ボードのフローの保存 | 保存したら `ccnavi-user-push-approved.sh <親>` をターミナルに送る |
| ユーザの判断の入口（`ccnavi-user-close-early.sh`） | 実行ファイルが書いた後、write-and-push の対象の親子のチケットなら `ccnavi-user-push-approved.sh <親>` を呼ぶ |

write-and-push の対象の親子のチケットでは、親のワークツリーで write-and-push と同じく親子のチケットのロックを取り、途中の操作が無いことを
確かめ、`ccnavi-sync.sh` で取り込んでから置き場（承認済みと、レビュー待ちの `review/` と、消えた `todo/` の提案）を
`commit --only` して送る。push が失敗したように見えたら `ls-remote` で届いたかを確かめる。失敗してもコミットは残す。

- エージェントからは組み込みの deny（`DENY_TICKET_APPROVAL_CLI`）で止める（9.5）。push の時機はユーザが決める
- sh の側で標準入力がターミナルかは確かめない
- 実行ファイルはネットワークに出ないので（P11）、`user agree` は置き場に書くところまで

`ccnavi-user-push-approved.sh` の細部は次のとおり。

- ワークスペース、`projects/*`、`.claude/worktrees/*` のツリーごとに、変更があれば置き場（`.ccnavi/approved/`）だけをコミットし、そのブランチへ push する。シンボリックリンクは辿らず、名指しして飛ばす。
- 保護されたブランチをチェックアウトしていないツリーは push せず、コミットまでで止める。
- 親のワークツリーのブランチは、push の前に共通の push の関門（`ccnavi_push_gate`。9.2）を通す。
- コミットするものが無ければ `コミットして push する承認済みチケットはありません。` と 1 行出す。
- `--path <パス> [--path <パス>...]` は、置き場の変更のうち並べたパス（ワークスペースルートからの相対）だけをコミットして push する。並べたパスの変更があるツリーだけを対象にし、`<親>` とは一緒に使えない。
- `ccnavi-user-agree.sh` は、承認が通れば、承認の push の段が 1 で終わっても 0 を返す（未送信のパスは文面で言う）。

| 終了コード | いつ |
|---|---|
| 0 | コミットするものが無い、または全部コミットした（push しなかったブランチ、飛ばしたツリーを含む） |
| 1 | `git add` / `commit` / push が失敗したツリーが 1 つ以上ある。巻き戻さないので、もう一度打てば送れる |
| 2 | 引数の誤り、ワークスペースルートが見つからない |

承認が一部だけ書けたとき（親は書けて子の書き込みだけ失敗した、など）、実行ファイルは終了コード 4 で終わる（何も書かない失敗の 1 と分ける）。
`ccnavi user agree --placed-out <ファイル>` は、書き込みに入ったとき、実際に書けた承認済みチケットのパスなどを次のキーの JSON で書き出す。

| キー | 何 |
|---|---|
| `placed[]` | 実際に書けた承認済みチケットのパス |
| `written[]` | この承認で書いた・消したパス（承認済みチケット・マーカー・`todo/` から消した提案）。ワークスペースルートからの相対 |
| `failed[]` | 書き込みで止まった提案。`{ticket, reason}` |
| `unwritten[]` | 止まったために書かなかった提案の識別子 |
| `rejected[]` | 検査で承認の対象にしなかった提案。`{ticket, problems[]}` |
| `dirty_parent[]` | 承認した親のワークツリーに残る、提案とチケットの置き場以外の未コミットの変更。`{ticket（親の識別子）, paths[]}`。承認は止めない。親のワークツリーが無い・読めないときは出さない。`user agree --yes --json` の本体にも同じ名前で載り、承認の通知（`prompt`）には戻し方を添えた `案内:` の行が付く |

`ccnavi-user-agree.sh` は 0 か 4 のとき `ccnavi-user-push-approved.sh --path <パス>...` を呼び、この承認が書いた・消したパス（実行ファイルの `--record-writes` の一覧）だけをコミットして push する。
そのあと上の JSON を標準エラーに出し、コミットか push が済んでいないツリーがあればそう言う（送れたツリーは push-approved が「pushしました」と言う）。
4 のとき、`ccnavi-user-agree.sh` は 1 で終わる（通らなかった分は直して承認し直す）。何も書かずに失敗したとき（4 以外の非 0）も、上の JSON があれば出してから 1 で終わる。

**絞りと「見せたもの」は別の引数で渡す。** `user agree --yes <識別子,…> [<絞り>...]` の `--yes` は
「オーバーレイに出ていた識別子」、後ろの語は「そのとき掛けていた絞り」（`--preview` に渡したものと同じ）。
その絞りで今できる一覧とユーザが見た識別子を比べる。絞り込みが無ければ承認待ち全部と比べる。

一覧を見るだけの `--agree --preview` はエージェントにも通す。免除は `--preview` の付いた `--agree`
だけで、`--yes` は免除しない。免除の範囲はコマンド 1 本まで（Bash は shellread の区切り、PowerShell は
`;` `&` `|` と改行を区切りと見る）。免除の理由になるのは単独の語として現れた `--preview` だけ（前は生の
空白、後ろは空白か区切りか行末。引用がつないだ空白や別のフラグの値 `--reason=--preview` は数えない）。
免除は許さない側から書く。

**コピーを作る補助は `user agree` の外に置く。** 親に固定するフェーズ定義のコピー（`phases:`）は、承認の前に提案へ書いておく
（承認はチケットの中身を変えないので、承認のときには書き足せない）。コピーするのは `ccnavi --plan-order <親> --fill-phases` で、
承認待ちの親の提案の `phases:` の値だけを、計画が使う定義の集まり（`phases.yml` から。改版では子が承認された番号の定義は
承認済みチケットから）に差し替える（9.7）。`user agree` の副フラグにすると組み込みの止めにヒットし、`--preview` と同じ厳しさの
免除が要るので、独立したフラグにしてある。実行ファイルは `user agree` のターミナルの確かめより手前でここへ分け、`user agree` と一緒には
受けない。書くのはエージェントも書ける提案だけで承認はしないので、エージェントが打ってよい。書き換えたあとの承認は
ダイジェストで縛られる。`user agree` がコピーの違いで落とすときは、文面にこのフラグを出す。

**計画の順序の振り直しと書き戻しも同じフラグに置く。** VS Code の計画編集タブは、図で引いた線を元の番号
（いま提案に書いてある番号）での直接の先行として `--order` に付け、`ccnavi --plan-order <親> --json --order <JSON>` で
振り直した答えを受け取る（読むだけ）。保存では `--order <JSON> --expect <ハッシュ> --write` で提案を書き換える。
振り直しの決まりは 9.7。番号の振り直しの正は実行ファイルで、画面は同じ決まりで仮の番号を出すだけ（見本の表
`tests/fixtures/plan-reorder.json` を両方のテストが読む）。答えの JSON は次のとおりで、承認の `--agree --preview --json` の
`plans` も同じ関数で作る（`--order` は渡さない。承認する提案そのものの順序）。`plans` は足しただけなので、承認の JSON の版は
上げていない。

| 欄 | 中身 |
|---|---|
| `plans` | 計画ごと（全体計画とフィードバック計画）に 1 件。`items`（`number` 振り直した番号・`from` 元の番号・`type`・`title`・`review`・`deferred`・`review_at`・`locked` 子が承認された番号）、`after`（振り直した番号での直接の先行）、`proposed`（提案に書いてある先行。「案に戻す」に使う）、`current`（改版のとき、承認済みの先行関係から戻した直接の先行。新規なら `null`）、`loose`（最後のステップの先行になっていないステップ）、`ready`（すぐ始まるステップ）、`problems`（その計画の順序の検査の error）、`source_sha` |
| `source_sha` | 親の提案と、その親の `todo/` の子の提案と、その子を `predecessors` で指す `todo/` の子の提案のバイト列をまとめたハッシュ（ツリーとツリーからの相対パスで区切る）。`--order` によらない。`--expect` に返す |
| `problems` / `loose` | 振り直した計画の順序の検査（`after` の形・終端・最後のステップの延期・延期の引き受け手とそのレビュー）の error と、最後のステップの先行になっていないステップ（両方の計画） |
| `refused` | 引けない線（`kind` が `cycle` 循環・`locked` 子が承認された番号へ入る線を変えた・`unpackable` 固定した番号を動かさずに番号が振れない、`number`、`text`）。断ったときは振り直さず、提案のままの答えを返す |
| `revision_problems` | 改版の錠（子が承認された番号の定義・`review`・推移的な先行・延期の引き受け手）にヒットするもの。延期したステップは元のステップの同一性（振り直す前の番号）で比べる |
| `children` | 付け替える `todo/` の子の提案（`ticket`→`new_ticket`・`path`→`new_path`・`phase`→`new_phase`・`predecessors`→`new_predecessors`）。保存の前にタブが一覧で見せる |
| `child_problems` | 子を付け替えられない理由（付け替え先の衝突、承認済みの側の参照） |
| `mismatched` | `phase:` が親の計画の番号に無い `todo/` の子の提案（`ticket`・`path`・`phase`・`text`）。知らせるだけで、書き戻しは止めない |
| `writable` | 書き戻せるか（`refused`・`problems`・`revision_problems`・`child_problems` が無い） |
| `written` | `--write` のときだけ。書いたか。書いたときの `source_sha` は書いたあとの値 |

書き戻しは親の提案の `plan:` / `feedback:` の値だけを差し替え、ほかの行（値の外のコメントも）と本文は変えない。
値の中に書いたコメントは消える。

**子の提案の追従。** 子の識別子はフェーズ番号を含む（`<親>-<2 桁のフェーズ番号>-<連番>`）ので、番号の変わるステップを
指す `todo/` の子の提案は、識別子の 2 桁・ファイル名・`ticket:`・`phase:` を新しい番号に付け替える（連番は変えない）。
その子を `predecessors` で指す `todo/` の子の提案（ほかの親の子も）は、参照を新しい識別子に直す。提案の置き場の
フローの下書き（`flows/<子>.yml`）も一緒に名前を変える。直すのは承認前の提案だけで、承認済みの子には触れない
（子が承認された番号は振り直しで動かない）。子の提案は `ticket:`・`phase:`・`predecessors:` の値だけを差し替え、組んだ
全文を読み直して、ほかの欄と本文が読んだ形で元と同じことを確かめる。書く順は子が先、親が最後で、付け替える子は
新しい名前に書いてから古い名前を消す。途中で落ちたら、触ったパスを全部書く前の中身へ戻す（戻しまで落ちる形は防げない）。

次のどれかにヒットすれば何も書かない。

- `--expect` が今の `source_sha` と違う（開いたあとに親か子の提案が変わった）。書く直前にもう一度読み、読んだときの
  バイト列と違えば書かない。確かめてから書くまでの間に提案を書かれる隙は、1 回の起動の中に狭めるだけで、錠は持たない
- 引けない線がある、振り直した計画の順序の検査に error がある、改版の錠にヒットする。範囲など順序と関係の無い理由で
  承認に落ちる提案でも、順序の書き戻しは止めない
- 組んだ全文を読み直すと、`plan` / `feedback` / `phases` のほかの欄か本文が読んだ形で元と変わる（値にアンカーがあり、
  ほかの欄が別名で指しているときなど）
- 付け替え先の識別子が、動かないファイルや提案・承認済みチケットと重なる
- 承認済みの側に、付け替える識別子への参照がある（承認済みチケットの識別子・`predecessors`、`review/` の提案、承認済みの
  置き場の `flows/`・`phases/<親>/` の記録、同じ名前のワークツリー）。承認済みの側はエージェントが直せないので、
  ユーザが手で直すか、取り消して出し直す

書き換えは承認ではない。書き換えると承認のダイジェストが変わるので、書き換える前に見せた一覧では承認できず、
承認は開き直した一覧で行う。書き戻しはコミットされないまま承認されるのが普通なので、承認したあとに戻す操作は無く、
子は取り消して出し直し、親は改版するか取り消す（state-transitions.md）。
承認を渡す文（`approved_text`）は、計画を持つ親とその子があれば、いつも「番号は承認済み
チケットで読み直す」と添える。書き換えられたかを見分ける材料が無い（エージェントのコミットしていない編集と同じ形になる）
ので、見分けずに添える。

**承認を頼む前の確認は `--preview` に相乗りする。** `--agree --preview --verify [<識別子>...]` は、
置かずに「いま `user agree` を打てば、その提案が承認の対象に入るか」を終了コードで返す（REQ-APV-13）。
0 が「はい」、`modes.EXIT_ANSWER_NO`（3）が「いいえ」、1 は使い方か設定の誤り。判定は承認と同じ
`gather`・`candidates` が持ち、`user agree` が外さないもの（範囲の超過と、読めない提案）では外さない。
走査は絞る前の全ツリーを見るので、他のセッションの書きかけ 1 本で「いいえ」になることがある。承認で外れる
ものは `--lint` も名指しする。新規の提案に雛形の空欄の目印が残っているのも、外れる条件の 1 つ
（改版は warn で外さない。親の必須の見出しの欠けも warn。提案の書式 9.3）。ただし「まだ承認できない」もの（前のフェーズが閉じていない子。
`rules.KIND_NOT_YET`）は `--lint` では warn。

提案を `todo/` に書いた回に、この確認を勧める文を 1 度だけ渡す（REQ-APV-14、`ticket_guard.propose_notice`）。
判定には足さず、ルールの文と同じ `PreToolUse` の `additionalContext` の経路で渡す。

`CCNAVI_MODE=dry-run` の間も、承認の経路は関門なので止まり、エージェントは `--yes` を打てない。承認の経路だけを
例外にはしない。

**承認したことは、拡張が渡す文と `status` で伝わる。** hook は承認を伝えない。

- ボードの承認は、`user agree --yes` の `prompt`（`agree_screen.approved_text`）を拡張が通知からユーザに渡し、ユーザが進行中の
  セッションに貼るか、新しいセッションを開く
- ターミナル・GitLab や GitHub の画面・Chrome 拡張の承認では、ユーザがそのあとセッションに一言送る。エージェントは、承認済みチケットの状態を
  確かめるとき（着手の前、引き継ぎを読んだあと、承認の有無に迷ったとき）に、ファイルを読んで推測せず
  `ccnavi-ticket.sh status [<親>]` を打つ

**次の通し番号は `next-id` で聞く。** `ccnavi-ticket.sh next-id [<先頭の語> <slug>]`（実行ファイルの `ccnavi ticket next-id`）は、直接作業のワークツリー名に付ける通し番号と識別子を答える。親チケットには使わない。チケット作業は issue と MR のセットで、親の識別子は issue の番号から決まる。

番号は、呼んだ時点で今ある名前の番号の最大値に 1 を足したものになる。子は数えない。`--lint` の warn が示す通し番号と同じになる。数える名前は、承認待ち・作業中・レビュー待ち・閉じた親、ワークスペースと各プロジェクトの手元のブランチ名（origin の追跡ブランチは数えない）、`.claude/worktrees/` の直下のディレクトリ名である。番号は予約しない。そのため、同時に呼べば同じ番号が出ることがあり、消えた作業と同じ番号が再び出ることもある。

チケット制御が `disable` でも使える。どこかのリポジトリのブランチを数えられなかったときは、番号を出さず終了コード 2 で止まる。標準出力は空で、標準エラーに理由と「番号を決められないので、ユーザに確かめてください」を出す。引数なしなら番号だけを出す。先頭の語と slug を渡せば、`<先頭の語>-<番号>-<slug>` を 1 行で出す。先頭の語と slug の字が合わない・末尾が `-<2 桁>` の形である・長さが合わない、のいずれかなら、理由を言って止まる。読むだけで何も書かず、ネットワークにも出ない。サブエージェントも打てる。

**状態は `status` で聞く。** `ccnavi-ticket.sh status [<親>]`（実行ファイルの `ccnavi ticket status`）は、親を渡せばその親子を、
渡さなければ作業中・レビュー待ち・承認待ちのチケットがある親子を全部、閉じたものも含めて出す。チケットごとに次を ccnavi が
判断して言う。読むだけで何も書かず、ネットワークにも出ない（P11）。

| 項目 | 中身 |
|---|---|
| 置き場とツリー | `todo/` / `doing/` / `review/` / `done/` と、見つけたツリー。複数の場所にあれば、どれが正か決まらないと言う |
| 承認の時刻 | `doing/` に足したコミットの時刻。無ければ「未コミット（手で置いた）」 |
| 着手 | 未着手か、着手済み（`started_at` と `base_sha`）か。閉じたものは完了か取り消しか |
| 置き場のファイル | 未コミット（ファイルがまだコミットに無い）、コミット済みのファイルに未コミットの変更がある、コミット済みで未 push、push 済み。push 済みかは手元のリモート追跡の ref で見るので、古いかもしれないと添え、最新にするには `ccnavi-sync.sh` を先に打つよう言う |
| 止まっている理由 | `blocked`、親子のチケットが決まらない、write-and-push が状態の操作を断る親子（`target` の理由）、満たしていない先行、親が未着手、write-and-push の対象の親子で承認済みチケットが未コミット |
| 注意 | `base_sha` がワークツリーの HEAD の祖先でない、再開（`done/` から手で戻す）で残った閉じるときの欄。どれも `start` と判定は止めない（`--lint` も warn） |
| 次の一手 | 下 |

- 未コミットの承認済みチケットには、ユーザに `ccnavi-user-push-approved.sh <親>` を打ってもらうことだけを言う。エージェントが運ぶ
  コマンドは出さない。承認が中身を変えないので「手で置いた」と「`user agree` が置いてまだ運んでいない」は見分けられず、
  エージェントが運ぶ道具にすると、保護をすり抜けて置いたものまで運べてしまう
- そのうえで、その親子が write-and-push の対象（`ccnavi write-and-push family <親>` と同じ `target`）なら「ユーザが運ぶまで `start` は止まる」、
  対象外なら「`start` へ進んでよい」と言う。write-and-push が状態の操作を断る親子（決まらない・親のワークツリーが無いなど）は、その理由を
  止まっている理由に出し、進んでよいとは言わない。判定は未コミットの承認済みチケットも読むので、write-and-push の対象でなければ運ばなくても
  着手できる。write-and-push の対象では、`start` の write-and-push が親のワークツリーの未コミットの `doing/` の追加をユーザが運ぶものとして止める
- サブエージェントも打てる（hook が止めるサブコマンドの一覧に入れていない）。実行ファイルは呼び手がサブエージェントかを知らない
  ので出力を分けず、状態を動かすコマンドの行には「親（メインエージェント）だけが実行する」と書く。サブエージェントが
  その行を打っても hook が止める
