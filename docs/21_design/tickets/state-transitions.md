### 9.6 状態遷移

状態を持つ場所は 2 層で、層ごとに動かす者と条件が違う。チケットの置き場（1 本のファイルが
提案の置き場と承認済みチケットの置き場を行き来する）と、マーカー。判定に使われるのは
`.ccnavi/approved/doing/` に在る承認済みチケットだけ。マーカーが使われるのは HITL ポイントだけ。

**チケットの遷移**

```
                approve                     finish（レビュー要）
  todo ─────────────────→ doing ───────────────────────────→ review
  (wip/proposals)      (.ccnavi/approved)                (wip/proposals)
                            │                                  │
                            │ finish（レビュー不要）／cancel    │ confirm / decide / user reviewed / close-early / Chrome のレビュー済み
                            ▼                                  ▼
                          done ←───────────────────────────────┘
                     (.ccnavi/approved)
                            │
                            └── ユーザが手で doing/ へ戻す（再開）
```

| 遷移 | 動かす者 | 条件 | 書く欄 |
|---|---|---|---|
| 無し → `todo` | 親が `Write` / `Edit` で作る | 無し | ― |
| `todo` → `doing` | `ccnavi-user-agree.sh`（ユーザ）、ボード、Chrome 拡張 | 9.4。同じ識別子がどの置き場にも無い | ―（中身は変えない。先行関係は承認済みチケットの計画から都度計算する） |
| `todo` → `doing`（手で） | ユーザが hook の外で動かす | 無し。動かせること自体が条件（その置き場にエージェントは書けない）。承認の検査は判定が適用する | ― |
| `todo`（改版）→ 消える | `ccnavi-user-agree.sh`（ユーザ） | 同じ識別子が `doing/` にあり、計画・`phases:`・範囲のどれかが違う。`doing/` の側の計画・コピー・範囲を差し替える | `plan` / `feedback`（ステップの `after` ごと）・`phases:`・`allow` / `ask` / `deny` |
| `doing` のまま | `ccnavi-ticket.sh start` | 着手の欄が空。`.claude/worktrees/<識別子>/` がワークツリーとして在り、元リポジトリが承認済みチケットの `project` と合い。子なら親が `doing/` に在って着手済みで、先行が全部 `done/` に在って取り消しでない | `started_at`、`base_sha`（そのワークツリーの HEAD） |
| `doing` → `review` | `ccnavi-ticket.sh finish` | 着手済み。子で、閉じた時点のフェーズがレビュー要（延期を含む。9.8）。フェーズ定義の成果物が在り、定性のリスク判定が揃っている（9.9） | `completed_at` |
| `doing` → `done` | `ccnavi-ticket.sh finish` | 着手済み。子ならフェーズがレビュー不要。親なら開いている子が無く、レビューで止まっておらず、計画があればフィードバック計画が承認済みで全フェーズが終わっている（早めに閉じていれば子だけ） | `completed_at` |
| `doing` → `done`（取り消し） | `ccnavi-ticket.sh cancel --reason`、`ccnavi-user-close-early.sh`（未着手の子） | 理由が空でない。親なら開いている子が無い | `cancelled_at`、`cancel_reason` |
| `review` → `done` | `ccnavi-review.sh confirm`、`ccnavi-user-decide.sh`、Chrome 拡張のレビュー済み、`ccnavi-user-close-early.sh` | そのフェーズ（延期を引き受けた分を含む）のレビューが済んだ（9.10） | ― |
| 無し → `doing`（続きの子） | ユーザが `decide` で選ぶ | レビューで指摘が残った（9.10）。同じフェーズの番号、範囲は見た子の和 | `followup_of`（トップレベルの欄。ccnavi が新しく作るチケットに書く） |
| `done` → `doing` | ユーザが hook の外で動かす | エージェントは `Write` でもシェルでも止まる。再開の意図がレビューのやり直しなら、そのフェーズのマーカーも手で消す | ― |

**子の `finish` の合流。** `start` は置き場を動かさず、着手の時刻と基準点（そのワークツリーの HEAD）を書く。`finish` は完了の時刻を書き、フェーズがレビュー要（延期を含む）なら `review/`、不要なら `done/` へ動かす。`cancel` は `doing/` から `done/` へ動かし、時刻と理由を書く。
子の `finish` は、write-and-push の対象の親では 1 操作（write-and-push）で次を行う。

1. 取り込み
2. 子のワークツリーと親のワークツリーの未コミットの確認
3. 子の変更（親との共通の祖先から先頭まで）の置き場・範囲の検査
4. `merge --no-ff --no-commit`
5. 完了の記録と子の `merged_sha`
6. 1 つのマージコミット
7. push

衝突・置き場や範囲の外の変更・未コミットは、何も変えずに止まる。push が通らない・中断されたときは、合流したコードも含めて元の先頭まで戻す。
完了（`done/`）した子のワークツリーは片付け、レビュー待ち（`review/`）の子のワークツリーは残す。`cancel` は子を親へ合流させずに閉じる。
レビューの依頼の前提は「すべての子が合流済み」で、子の `merged_sha` が親の先頭の祖先かで確かめる。子のワークツリーが残る PC では、手元の子のブランチの先頭が `merged_sha` と違い親の先頭にも無ければ、
finish の後に積んだ合流されていない修正があるとして止める。Stop の促しも同じ確認を使う。サブエージェントの範囲検査とリスクの計測も、親との共通の祖先から数える。
子が統合先（リモート追跡ブランチ）を取り込んだ merge が持ち込んだだけのパス（merge が 1 つめの親から変えたパスのうち、先頭の中身が取り込んだ側と同じもの。`gitstate.taken_from_remote`）は、3 の範囲の検査にも、サブエージェントの範囲検査・リスクの行数とファイル数にも数えない。衝突を解いて書き換えたパスと、取り込んだあとに子が直したパスは子の変更として数える。読めなければ何も外さない。子が自分のコミットを持たないうちの merge は git が早送りで済ませ、merge コミットの印が残らないので、`ccnavi-git.sh merge` がワークツリーの中で `--ff`・`--no-ff`・`--ff-only`・`--squash` の指定が無いときに `--no-ff` を補う。

承認を取り下げて `todo/` に戻す操作は無い（Chrome 拡張にも置かない）。承認した子は `cancel --reason` で取り消し、
新しい連番の子として出し直す。承認した親は、中身を直すなら改版し、やめるなら `cancel` する。

スクリプトは置き場を動かして欄の行だけを書き換える。本文とユーザの書いたコメントは保つ（承認は
中身を変えずに動かすだけ）。コミットは親がする。`start` と `finish` と `cancel` は
`doing/` に在るチケットを扱う。未承認の提案（`todo/`）は消せばよい。
同じ識別子が `doing/` と `todo/` の両方に在るときは `doing/` の側を相手にする（`todo/` は改版の
候補か書き損じで、`--lint` が言う）。それ以外の組み合わせで 2 つの置き場に在るときは動かさない。

閉じる向き（`doing` → `review` / `done`）は範囲が消える向きなので承認は要らない。再開は範囲が戻る
向きなのでユーザの手に置く。運用の基本は、閉じたチケットを戻さず新しいチケットを作り直すことで、
再開は想定しない。された場合は、`--lint` と `ticket status` が、作業中の子のフェーズに `reviewed` が残っていることを
warn で言う。マーカーを消すかは、レビューをやり直すかどうかで、人が決める
（機構は消さない）。親を閉じても子の承認済みチケットは閉じない。

**状態は置き場とマーカーだけで決まる。** いつ動いたかは `git log`、承認の時刻は `doing/` に足したコミットから引く。

**先行は着手でも見る。** 子の `start` は、`predecessors` の各チケットが `done/` に在って取り消しでないことを
求める。承認でも同じ検査を適用するが、承認のあとに先行が戻された子と、置き場を手で動かして承認した子が
あるので、着手の手前でもう一度見る。止めたときは、どの先行が何の状態か（承認待ち・作業中・レビュー待ち・取り消し済み・
どこにも無い・複数の場所）と、先行を閉じる（`finish`）か、先行が要らないならユーザに承認済みチケットの欄から外してもらうか
取り消して出し直す（`cancel`）ことを sh の書き方で言う。続きの子（9.10）は、見た子のうち取り消したものを先行に入れない。
止めるのは `start` まで。

**`finish` の打ち忘れは `Stop` で 1 回だけ促す。** メインエージェントの `Stop` で、cwd のワークツリーに
結び付いた承認済みチケットが着手済み（`doing/`、閉じても取り消してもいない）で、そのワークツリーに未コミットの変更が無く
（追跡していないファイルも数える）、基準点より先に自分で作ったコミットがあれば（取り込んだだけのコミットは数えない。
子なら親のブランチ、親なら `origin/HEAD` にあるものとマージのコミットを除く）、`decision: block` で止めて、`finish` の sh の書き方と
「続けるなら理由をユーザに書いてから終える」を渡す（`NUDGE_TICKET_FINISH`）。同じセッションで同じチケットを同じ HEAD のまま
促すのは 1 回だけ（記録は state の置き場の `nudged-<セッション>.json`。git では共有しない）。HEAD が進めばまた促す。payload の
`stop_hook_active` が真なら促さない。state の置き場が無いか書けないときも促さない。除くのは、チケット制御かモードが `disable`、ワークスペースルートかチケットの無いワークツリー、
未着手、`blocked`、基準点が無い、子で親のブランチを引けない、親で `close_problems`（開いている子・レビュー準備中／レビュー待ち・フィードバック計画待ち・
終わっていないフェーズ）が空でない、git を読めない、`SubagentStop`。`dry-run` でも止める。

**レビューの依頼までの道の途中で終えようとしたら、`Stop` で 1 回だけ止める。** 子の `finish`（親ブランチへの合流を含む）・ELI5・`ccnavi-review.sh review-request` は決まった道で、各所で「進めてよいですか」と確認して止まる必要が無い。メインエージェントの `Stop` で、cwd のツリーが承認済みの親（`doing/`、着手済み、`blocked` でない、`close-early` が無い）に結び付いていて、(a) 作業中（`doing/`、着手済み）の子が残っている（子のツリーでは自分の子だけ。並行する別の子は別のセッションの作業）、または (b) 子が全部閉じ、レビューを要する（`review: none` でも延期でもない）フェーズに依頼のマーカー（`requested`）が無ければ、`decision: block` で止める（`NUDGE_TICKET_REQUEST`）。文は「決まった道の途中でユーザの許可は要らない・次のコマンド（コマンドでなく作業を続けることやユーザへの相談なら、無理にコマンドの形にしない）」に、共通の 1 文を添える。共通の 1 文は「直前にユーザが『止めて』『待って』『相談したい』と言った場合は、このまま進めずにターンを終える。止めた理由と、再開するときの次の一手を 1 行で書く。ユーザの判断が本当に要る問いがある場合は、その問いを最後に書き直して終える」（`lifecycle.stop.USER_STOP_NOTE`。`finish` の促しにも同じ文）。次の一手は状態ごとの案内（各 `STEP_*`）のままで、共通の 1 文は状態の案内を変えない。状態ごとの次の一手は: 作業中の子の `finish`、子のブランチが親の HEAD の祖先でなければ `ccnavi-git.sh merge <子>`、`wip/eli5/phase-N.html` が無ければ ELI5、それ以外は `review-request`。ユーザが子を手で `done/` へ動かして共有（commit・push）済みのフェーズでは、次の一手を `confirm` にして 1 回だけ促す（`STEP_CONFIRM`。手動移動の確定は review.md）。問いで終わった回も止める。変更要求のレビューが残る間は `requested` が残るので止めない（`reviewed` を置かないだけ）。同じフェーズに子を足すと `requested` が外れ、足した子が作業中になるので止める。同じ状態（親・フェーズ・残っている子・HEAD）では 1 回だけで、記録は `finish` の促しと同じ `nudged-<セッション>.json` の`request:<親>:<フェーズ>` のキー。進めばまた止める。`stop_hook_active` が真、サブエージェント、state の置き場が無いか書けない、チケット制御かモードが `disable` では止めない。`dry-run` でも止める。1 回の `Stop` で止める理由は 1 つで、`finish` の促しが止める回は出さず覚えもしない。この促しが止める回は、あとの直接作業の `integrate` の促し（6.6）と `match: Stop` のルールも出さず数えもしない。実行中のサブエージェントが居る間は、委任して待つ回なので止めない。判定は `SubagentStart` / `SubagentStop` が残す印（9.12）で、1 体でも実行中の印があれば（入れ子の孫も数える。読めない・壊れた印も）促しを見送り、「1 回だけ」の記録は進めない。終わったあとの `Stop` でまた促せる。待ちに数えるのはサブエージェントだけ。制限: `agent_id` の無い `SubagentStart` は印を置けず、その体は実行中と数えられない。`SubagentStop` が `Stop` より少し遅れて来る終わりぎわの回は見送るだけで、害は無い。

**フィードバック計画待ちのまま終えようとしたら、`Stop` で 1 回だけ止める。** 全体計画のレビューが済み、親の局面（`phase.stage`）が「フィードバック計画待ち」の親子のツリーで（親が `blocked` でない、着手済み、早めに閉じていない）、改版（`feedback: []` か対応のフェーズ）を書いて `approval-request` で送り、ユーザに承認を頼むよう促す（`NUDGE_TICKET_FEEDBACK`）。提案済み（親の `wip/proposals/todo/` に親と同じ識別子で `feedback:` を持つ提案）かで文面を分ける。同じ状態（親・HEAD・提案済みか）では 1 回だけ止め、記録は `nudged-<セッション>.json` の `feedback:` で始まるキー。実行中のサブエージェントが居る間は見送り、記録も進めない。`finish` の促しも、実行中のサブエージェントが居る間は見送る。

**子の着手は親の着手のあと。** 親が `doing/` で着手済みでなければ、子の `start` は止まる（親のワークツリーが
要る）。案内は親の置き場で分かれ、`todo/` なら承認から、`doing/` で未着手なら親の `start` から。親が
どこにも無いときと、複数の置き場にあって定まらないときも、同じ場所で止めて見えたとおりを言う。

**マーカーの遷移**

フェーズは同じ親の同じ `phase` 番号の子のまとまり。「終わった」は導出で、そのまとまりの子が `doing/` に
1 枚も無く、`review/`（レビュー待ち）か `done/`（取り消しでない）に 1 枚以上あること。取り消しだけの
フェーズは終わらない。「レビュー要」も導出（9.8）。止めているのは **終わった ∧ レビュー要 ∧
`reviewed` が無い** のとき。`pending` と `requested` は止める条件に入らない（`requested` は
呼び名を「レビュー準備中」から「レビュー待ち」へ変えるだけ。9.8）。

```
    無し ──終わった ∧ mr で見る──→ pending ──review-request──→ requested ──confirm / user reviewed──→ reviewed
     │
     └────終わった ∧ レビュー不要──→ skipped

    どのマーカーからも: 同じ番号に子が承認される ──→ 無し
```

| 遷移 | 動かす者 | 条件 |
|---|---|---|
| 無し → `pending` | `PostToolUse` の告知（cwd が親のワークツリー） | 終わっていて、マーカーが 1 つも無く、レビュー要。文を 1 度だけ返す |
| 無し → `skipped` | 同上 | 終わっていて、マーカーが 1 つも無く、レビュー不要（または延期） |
| 任意 → `skipped` | `ccnavi-user-close-early.sh`（ユーザ） | 終わっていないフェーズのうち、レビュー待ちか閉じた子が居るもの(未着手の子を取り消すと終わるもの)に置く。手を付けていないフェーズには置かず、issue に書き出す（9.11） |
| 任意 → `requested` | `ccnavi-review.sh review-request`（親） | 9.10 の前提と ELI5 の HTML（`--eli5`。`wip/` の下にコミット済み）。`pending` は要らない |
| `requested` → `reviewed` | `ccnavi-review.sh confirm`（ユーザがターミナルで打つか、VS Code のボードの連絡を受けた親が打つ）、`ccnavi-user-decide.sh`（ユーザ）、Chrome 拡張のレビュー済み、`ccnavi-user-close-early.sh` | 変更要求のレビューが無い。`confirm` は未解決が 0、`decide` は未解決をユーザが受け入れる（続きの子を起こす選択ではマーカーは置かず、そのフェーズのマーカーを消す）。置いたときに `review/` の子は `done/` へ動く |
| 任意 → 無し | `ccnavi-user-agree.sh` で同じ番号の子が承認された | 4 種を全部消す |

マーカーはユーザが子を再開しても残る。再開は想定しない運用で、された場合は `--lint` と
`ticket status` が、作業中の子のフェーズに `reviewed` が残っていると warn で言う（閉じ直したときにレビューが要らないフェーズ、つまりフェーズ定義が `review: none` で、再開された子も
`human_review` を求めていないフェーズは言わない）。再開の意図がレビューのやり直しなら、そのフェーズのマーカーを人が手で消す
（マーカーがあるツリー、つまり `approval.home_dir` が決めるツリーで `ccnavi-git.sh rm .ccnavi/approved/phases/<親>/<N>.reviewed`
を打ち、削除をコミットする。write-and-push の対象（親のワークツリーがあり、origin があり、HEAD の確認に通る）で、マージリクエストで見るフェーズがある親子なら、
`ccnavi-user-push-approved.sh <親>` が取り込んでからコミットして送る。それ以外の親子では、名指しの
`ccnavi-user-push-approved.sh <親>` は「ここではコミットも push もしない」と出して終わるので、ユーザが自分でコミットする。
引数なしの `ccnavi-user-push-approved.sh` は、置き場に変更のあるツリーを全部コミットする）。
警告文は、そのツリーをワークスペースルートからの相対で言う。
マーカーが未コミットのときは `git rm` が拒む（一度もコミットしていなければ「どのファイルにもヒットしない」、
コミット後に書き換えていれば「手元の変更がある」）。`-f` は `ccnavi-git.sh` が通さないので、先に
`ccnavi-user-push-approved.sh <親>` でコミットしてから `rm` するか、ファイルを直接消す（消したことは次の
`ccnavi-user-push-approved.sh <親>` がコミットする。一度もコミットしていなければ消すだけで済む）。続きの作業だけなら、残してよい。
延期したフェーズ N の子を再開したときも、N が一度終わった印（`N.skipped`）が残っていれば警告する。消すべきマーカーは引き受けた側の番号のものだが、引き受け手は辿らない。警告は、マーカーの置き場（`.ccnavi/approved/phases/<親>/`）に `*.reviewed` が残っていれば再開後の作業はそのレビューに含まれないと言い、消し方を番号を `<番号>` にした形で示す。引き受けた側がまだレビュー前でも言う（続きの作業だけなら残してよい、と添える）。`N.skipped` は消さない（手順は上と同じ）。

**2 層の組み合わせで決まるもの**

| 見るもの | 使う層 | 決まり方 |
|---|---|---|
| `Write` / `Edit` の判定 | チケットの置き場、ワークツリー | 行き先のワークツリーと同じ識別子の `doing/` の承認済みチケット。無ければルールだけ |
| `SubagentStop` の範囲外の検査 | チケットの置き場 | cwd のワークツリーが子ならその子（差し戻す）、親ならその親の `doing/` の子の全部（検査するが差し戻さず、`unattributed` として親へ知らせる）。基準点は承認済みチケットの `base_sha` |
| HITL ポイント | チケットの置き場、マーカー | cwd のワークツリーと同じ識別子の `doing/` の親 → その子の置き場で「終わった」→ マーカー |
| レビューの依頼の前提 | チケットの置き場、マーカー | 終わっている、`requested` が無い、ほか git の条件 |
| `SubagentStart` の一覧 | チケットの置き場、ワークツリー | cwd のワークツリーが親ならその親の `doing/` の子、子ならその子 |
| `user agree` の承認待ち | チケットの置き場 | `todo/` に在って同じ識別子がどの置き場にも無い提案と、親の改版 |
