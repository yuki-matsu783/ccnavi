### 9.8 フェーズの終わりと HITL ポイント

フェーズの終わりは、ユーザの手が入るところ（HITL ポイント。Human In The Loop）の 1 つ。ユーザの手が入る場所は
範囲の承認・レビュー・未解決の受け入れの 3 か所にまとめてあり、フェーズの終わりはその 2 つめにあたる。
フィードバック計画の承認（9.7）は、このどれにも数えない。レビューの状態を変えず、全体計画の最後のレビューが
済んでいること（3 か所の 2 つめ・3 つめのどちらかで済ませたこと）を前提にする。

同じ親の同じ `phase` の子が `doing/` に無く、`review/` か `done/` に 1 枚以上あるとき、
そのフェーズは終わり。終わりの扱いは**ユーザがどこで見るか**で 2 つに分かれる。子を閉じる
`ticket finish` は、その子を閉じたものとして数えたこの答えで行き先を決める。レビュー要（延期を含む）なら
`wip/proposals/review/`、不要なら `.ccnavi/approved/done/`。レビューが済むと
`review/` の子は `done/` へ動く。

見る場所は `none` / `mr` の 2 値で、次のうち厳しい側を採る（`none` < `mr`）。

- フェーズ定義の `review`（9.7）
- 計画のステップの `mr`（フェーズ定義の `review` が `none` でも `mr` にする）
- 引き受けた延期の分（延期したステップの分は、引き受けた側が、引き受けた分の
  宣言と自分の宣言の厳しい側で見る。覆っている分のフェーズ定義が読めなくなっていたら `mr` として扱う）

閉じた子の `human_review.required` と、実績のリスクが HIGH 以上であること（9.9）は、
**要るとだけ言い、場所は言わない**。宣言が `none` のフェーズを `mr` へ上げる。
場所を決めるものが 1 つも無い番号（計画が無い親の番号。
計画を持つ親の定義は親に固定したコピーから読み、コピーに無ければ親が止まる）では、子が `required: true` と言うか実績が
高ければ `mr`。

| | `mr` | `none` |
|---|---|---|
| 最後の子を閉じた呼び出しの `PostToolUse` で返す文 | 「すべての子が合流済みと確かめ、`review-request` でレビューを頼み、ターンを終えてユーザを待て」 | 「人間レビューを省略して次のフェーズへ進む」 |
| マーカー | `pending` | `skipped` |
| HITL ポイント | 来る。`reviewed` のマーカーまで止まる | 来ない |
| 開ける者 | `ccnavi-review.sh confirm` / `decide`（9.10） | — |

告知は「マーカーが 1 つも無い」ときだけ出る。子を足してマーカーが消えた後、フェーズが再び終われば、告知はもう一度出る。
最後の子を閉じる前に、フェーズ定義の `deliverables` が親か子のワークツリーに在って追跡されているかを見る。
無ければ `finish` を拒む。閉じてレビューが通ったら、案内が次のフェーズの計画を促す。

**止めている間の呼び名は 2 つある**。依頼を出すまでが **レビュー準備中**（次に動くのは
エージェント。合流済みの確認・push・依頼）、出してからレビュー済みまでが **レビュー待ち**（次に動くのはユーザ。
判定の `review_waiting`）。拒否の文面・`--explain`・親の局面・ボードの状態のバッジとフェーズ行の一言はこの名前で言い、どちらの段かで
「やること」も変わる（未依頼なら review-request まで、依頼済みなら待って `confirm`）。
JSON の欄名は `gate_closed`。これは判定とボードの契約で、この呼び名とは対応しない（10 章）。

**並行する枝があっても止めるのは親ごと。** 並行している枝の片方がレビュー準備中・レビュー待ちに入ると、
その親の cwd からはサブエージェントを起こせなくなる（止めるのは新しい子を起こすところなので、先に起こしてあった子は動き続ける）。

依頼を出したあとに別の枝の子を親ブランチへ合流すると、依頼時の HEAD と食い違い、`confirm` が依頼の
やり直しを求める（9.10）。やり直した依頼には、その枝の作業も入る。

**受け入れは親全体に適用される。** `decide` で受け入れたスレッドは、スレッドに「受け入れて進む」旨の返信を残して
解決済みにする。`confirm` が数えるのはホスト上の未解決のスレッドだけなので、
どのフェーズの依頼でも同じに数える。
受け入れたスレッドを他の人が開き直せば、未解決として数える。返信か解決に失敗したら、受け入れは未完了として止める
（設計 9.10。置く前に結果を取り直して確かめる）。

止めるかどうかは cwd のワークツリーで親を引いて決める。止めている間、その親の cwd からの `Agent`（サブエージェントの
起動）と `Bash` / `PowerShell` を `DENY_PHASE_REVIEW` で止める。通すのは `Bash` で、連結の全部が
`sh|bash …ccnavi-(ticket|review|git).sh` の形で読み切れたときだけ。読み切れないコマンドに例外は
与えない。`PowerShell` に例外は無く、止めている間は必ず止まる。`Write` / `Edit` は通す。次のフェーズの計画はレビュー前に進めてよい。別の親は別に
止め、ワークスペースルート直下や無関係のツリーからの呼び出しは止めない。

「ターンを終えてユーザに聞け」を強制する手段は hook に無いので、先に文で言い、進んだら止める 2 段構えになる。
`cwd` は `cd` を 1 回打てば外れるが、外れた先で起動したサブエージェントの書き込みは行き先で止まる。

**手で動かした子。** ユーザが `review/` の子を `done/` へ手で動かすのは、そのレビューが済んだというユーザの意思として読む。
`finish` が置いた先を `finished_to` に、ccnavi が動かした経路を `settled_by` に書くので、`finished_to: review` で
`settled_by` が無い子が `done/` にあれば手で動かした子とする。`finished_to` が無い子（finish を通らず手で動かした子など）は
手動とみなさず、`confirm` か `decide` で確かめる。確定してよいのは、依頼のマーカーがあり、レビューを待つ子が残らず、
動かした `done/` のファイルが HEAD にコミット済みで `origin/<親のブランチ>` に入っているときだけ（`manual_settle.assess`。
判定に使うのは親の正本の置き場と git の履歴で、PC ごとの state は使わない。エージェントは代わりに push しない）。
移動が未コミット・未 push なら「移動が未共有」と言って確定せず、依頼が無ければ `review-request` を案内する。確定は `confirm` が行い、
移動の前に付いた未解決の指摘を、ホストで解決せずに版つき（キー・指摘の版・最後のコメントの id）で受け入れ台帳
`phases/<親>/accepted.json` に足す。移動の後に付いた指摘、変更要求があれば確定せず、`decide` を案内する。台帳に受け入れた
指摘は、版が同じで受け入れた後にコメントが付かない間は未解決に数えない。読めない台帳は空として扱い、未解決を隠さない。
ボードは、この確認待ちや未共有を、フェーズの `manual` の 1 行として出す（設計 10 章）。

**送信の途中で止まったとき。** `decide`・`close-early`・`review-request`・`comment`・`ready` のホストへの送信は、送る前に
操作記録（`logs/state/ops/<操作ID>.json`）へ段階ごとに載る。途中で止まった操作は、`status` と `--lint` が未完了として言い、
`--resume <操作ID>` で続きから送る（自動では送り直さない）。未完了の記録は prune が消さない。
`decide` の投稿は操作ID のロック（`locks/ops/<操作ID>`）で直列にし、同じ判断の二重の投稿を防ぐ。`--resume` は返信・解決の前からこのロックを持つ。
記録を保存できなければ、返信・解決・適用に進まず何も送らない。送る本文の末尾に目印 `<!-- ccnavi:op=<操作ID> stage=<段階ID> -->` を足し、送り直す前に、目印・送ったアカウントで一覧を最後まで読んで照合する。0 件と確定したときだけ送り、打ち切り・アカウントの食い違い・反映待ちは結果不明として自動では送らず、確かめ方を言う。`decide` に渡す
ダイジェストは版 2 で、指摘ごとの版を含む。見せた指摘が変わった・消えていれば止まり、増えた指摘は止めずに追加分として
未対応で残す（9.10）。
