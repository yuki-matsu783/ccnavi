### 9.12 サブエージェント

| イベント | すること |
|---|---|
| `SubagentStart` | cwd のワークツリーが承認済みチケットに結び付くときだけ、開いている子の一覧（識別子・ワークツリーの有無・範囲・未完了の先行・フェーズ定義・`agent` の案内）を `additionalContext` で渡す。親のツリーならその親の子、子のツリーならその子自身。止められないイベントなので案内だけを渡す。子がフロー（9.3.1）を持てば、下の「フローの案内」も足す。着手中の子のフローが着手のときのハッシュから変わっていれば、`systemMessage` にも載せて知らせる。チケット制御が有効で state の置き場があり、payload に `agent_id` があれば、実行中の印（下の「実行中の印」）も置く。チケット制御が有効で state の置き場があり、`agent_id` があるときは、同じワークツリーで実行中の別の編集するサブエージェントがいれば、その旨の案内も渡す（下の「同じワークツリーの案内」。ワークスペースルートからの起動にも渡す）。どの起動にも、cwd がプロジェクトの中ならそのスキルの目録（11.13）と、「気づいたスキル候補は最後の報告に節を足して返す」の 1 行（`subagent.CANDIDATE_NOTE`）を渡す。この 1 行を渡すのは、サブエージェントには `Stop` の振り返りが届かないため（6.6） |
| `SubagentStop` | 実行中の印を外す（差し戻して続けさせる回は外さない。判定の途中で例外が出ても外す）。対象の子の仕事の始まり（親の先頭との共通の祖先）から先頭までのコミット済みの差分と未コミットの変更の両方から範囲外を探し、残っていれば `enable` で 1 回だけ終了コード 2 で差し戻す。担当の子が決まるのは cwd が子のワークツリーのときだけで、親のツリーから起動された体は全部の子を検査するが差し戻さず、`unattributed` として親に知らせる。終わり方は 5 つに分けて `state/subagent-<セッション>-<id>.outcome`（JSON）に残す（下の「終了結果の記録」）。差し戻しの記録は `state/subagent-<セッション>-<id>.bounced`。`agent_id` が来ない payload では `<id>` がワークツリーの名前になり、同じワークツリーから `agent_id` 無しで来る 2 体目は通る。名前で書いた記録はセッションが終わるまで残る。2 回目は通して文だけ渡す。未コミットが残っていること自体は差し戻さない。対象の子のフローが着手のときのハッシュから変わっていれば、それも知らせる（9.3.1）。対象の子のワークツリーを読めず範囲を確かめられなかったら、差し戻さずに通す（読めない原因は子の作業とは限らず、差し戻しても子には直せないことがある）。範囲外が他に見つからなければ記録を `skip` / `worktree-unreadable` にして許可と分け、どちらの場合も `detail` に確かめなかった子を残す。この出力は親に届かないので、`state/subagent-<セッション>-<id>.unchecked` に 1 行目のセッションの識別子（そのまま）と子の識別子を書き、親に 1 行言う（下の 2 行）。処理が ccnavi の内部エラーで終わった回も、通して、`systemMessage` でユーザに知らせ、同じ印を置く。どの子を見るはずだったかは分からないので中身は空にし、親には内部エラーで確かめていないと言う |
| `PreToolUse`（`Agent`・`Task`） | 起動の担当を、プロンプトの言及から決める（下の「起動前の担当の決め方」）。決まらなければ止め、決まれば担当の案内をプロンプトの末尾に書き足す（`updatedInput.prompt`）。`isolation` は止める |
| `PostToolUse`（`Agent`・`Task`） | サブエージェントが差し戻しを無視して終わったこと、`SubagentStop` で子の範囲を確かめられなかったこと（`worktree-unreadable`。印は読んだら消す）を親に言う（`SubagentStop` の出力は親に届かない）。起動したのがサブエージェント（payload に `agent_id` がある入れ子）なら、同じ文を `systemMessage` にも載せる。同じ呼び出しで実行後チェックが `enable` の差し戻し（終了コード 2）をするときは載らない |
| `PostToolUse`（親のどのツールでも）・`UserPromptSubmit` | payload に `agent_id` の無い親の呼び出しなら、このセッションに残った `.unchecked` の印をぜんぶ読んで言い、消す。どのセッションの印かは、名前ではなく中身の 1 行目と完全一致で比べる（名前の前置きは別のセッションのものとも重なりうる）。バックグラウンドで動かしたサブエージェントは、親の `Agent` の `PostToolUse` が `SubagentStop` より先に来るので、そこだけで読むと知らせが落ちて印が残る。親が次のツールを使えばその `PostToolUse` で、ツールを使わずにターンを終えたなら次の依頼の `UserPromptSubmit`（`additionalContext`）で届く。`Stop` では読まない（`Stop` から親に言うには、終わろうとするのを止めて続けさせることになる）。サブエージェントの中の呼び出しでは読まない（その子の親でない印を消すと、親に届かなくなる）。`.outcome` が `unattributed` のものも、この 2 つの経路で 1 度だけ言う（出力に書き終えてから `notified` の印を付けるので、書く前に止まれば次の機会に出し直す） |

判定は行き先で決まるので、`SubagentStart` の一覧は案内でしかない。

**範囲外の変更の検査と、確かめられなかった印。** 子チケットには編集してよい範囲が決まっている。書き込み先が呼び出しに
現れるツール（`Write`・`Edit` など）は `PreToolUse` が事前に止める。一方、スクリプトやシェルが中で別のファイルを
書き換える場合、その行き先は呼び出しからは分からず、事前には止められない。`SubagentStop` の検査は、この取りこぼしを
「結果として何が変わったか」から見つけるための二段目の守りになる。

- 例（検査できた回）: 子の範囲が `src/foo/**` で、サブエージェントが `sh gen.sh` を実行した。`gen.sh` は
  `src/foo/a.py` のほかに `docs/b.md` も書き換えた。`PreToolUse` は `sh gen.sh` の中身までは追えず通す。
  サブエージェントの終了時に差分を読むと `docs/b.md` が範囲外なので、1 回だけ差し戻して「`docs/b.md` は範囲外」と伝える。
- 例（検査できなかった回）: 子のワークツリーが消えている、または git が失敗して差分を読めない。範囲外の変更が
  あったのかどうかも分からない。差し戻しても子には直せないので止めない。ただし何も言わないと、親には「問題なし」と
  区別がつかない。そこで確かめられなかった子を印（`.unchecked`）に残し、親に「子 X のワークツリーを読めず、範囲外の
  変更を確かめていない。合流の前に確かめて」と伝える。
- 例（親に届くまで）: 親が次にツールを使えば、その `PostToolUse` で伝わる。ツールを使わずにターンを終えたなら、
  ユーザの次の依頼の `UserPromptSubmit` で、上の文が `additionalContext` として渡る。伝えたら印は消す。

**親のワークツリーへの書き込み（`DENY_SUBAGENT_PARENT_TREE`）。** サブエージェントは子のワークツリーで手元にコミットするだけで、親のワークツリーへの merge・commit・書き込みは hook が止める。子のワークツリーでのコミットと、衝突を解くための親のブランチの merge は通る。動かすスクリプトと push は `DENY_SUBAGENT_TICKET_OP` が止め、子チケットのワークツリーからの push は git のラッパースクリプトが拒む。子の合流と push は、メインエージェントが打つ子の `finish` が行う。親を閉じる（レビューの依頼・`ready`）のもメインエージェントである。

- 親のワークツリーかは、そのワークツリー自身のチケットで決める。`parent:` の無い同名のチケットが 1 つでもあれば親とする。
- 居場所は `cd` と `env -C`・`sudo -D` の行き先で追う。`GIT_DIR`・`GIT_WORK_TREE` などの git の置き場の変数を置いてラッパーを呼ぶ形は止める（ラッパーも先頭で外す）。
- 書き込みは Write / Edit のほか、Bash のリダイレクト・`tee`・`sed -i`・`cp` / `mv` の行き先も見る。
- `python -c`・`node -e`・`perl -e` のコードは読み切れないので、親のワークツリーのパスと書き込みを疑う語が並べば止める。
- スクリプトのファイルを実行する形と、変数で組み立てた行き先は見ない（限界）。

**親の局面。** 子の一覧を渡すときは、その子の親ごとに「親 X の局面: <局面>」を 1 行足す（`subagent._stage_lines`）。
局面の文字列は `phase.stage` が返すまま（局面の名前は 9.7 の「局面の名前」）。開いた子が居ないときは一覧ごと渡さないので、
子が居ない親は何も出ない。計画の無い親（局面が空）や、局面を組めなかったとき（置き場を読めないなど）は、その行だけ出さず、
`SubagentStart` は失敗させない。局面は案内であって判定ではない。

**終了結果の記録。** `SubagentStop` は、終わり方を 5 つに分けて `state/subagent-<セッション>-<agent_id>.outcome`（JSON）に残す（`hook/subagent_outcome.py`）。差し戻しの記録（`.bounced`）が残すのは「差し戻したか」で、こちらは「終わったときにどうだったか」を残す。

| 結果 | 意味 | 親への知らせ | Stop の促し |
|---|---|---|---|
| `ok` | 範囲外の変更が無い | 言わない | しない |
| `fixed` | 差し戻した後に直った | 言わない（警告しない） | しない |
| `outside` | 範囲外の変更が残ったまま終わった | 差し戻しを無視した知らせを出す | する |
| `unchecked` | 読めない・内部エラーで検査できなかった | `.unchecked` の知らせを出す | する |
| `unattributed` | 担当の子が分からない（親のツリーから起動された） | `PostToolUse`・`UserPromptSubmit` で 1 度 | しない |

- 担当の子が決まるのは、cwd が子のワークツリーのときだけ。親のツリーから起動された体は、全部の子を検査するが差し戻さない（別の子の変更を、関係ない体に直させないため）。範囲外が見つかれば `unattributed` にして親へ知らせる。最終的には `finish` の範囲検査が止める
- 差し戻して続けさせる回は `final: false` で書き、結果を確定しない。次の `SubagentStop` で直っていれば `fixed`（親に警告しない）、差し戻しを残したまま終われば `outside` に確定する。`dry-run` は差し戻さないので、`outside` を差し戻し 0 回で残し、親への文は「差し戻していない」と言う
- 親への知らせは、確定した結果を 1 度だけ。出力に書き終えてから `notified` の印を付ける
- `Stop` が促すのは `outside` と `unchecked` だけ（理由コード `NUDGE_SUBAGENT_OUTCOME`）。同じ結果では 1 回で（`nudged` の印）、別の経路で同じ内容を親に言った結果は促し済みにする。`stop_hook_active` が真のとき、サブエージェントの中、実行中のサブエージェントが居る間、state の置き場が無いときは促さない。順序は `finish` → 依頼までの道 → サブエージェント結果 → `integrate` → ルール（6.6）
- `.outcome` は prune が 14 日で掃除する
- サブエージェントの hook の cwd は、起動したときのメインの cwd に固定される。体が `cd` しても、あとでメインが `cd` しても変わらない。このため `SubagentStop` の担当は、メインがワークスペースルートから起動した体では決まらず、`unattributed` になる。`isolation: worktree` で起動した体だけは、`cwd` が隔離したワークツリーのパスになる（起動の時点で止める。付録 C）。起動の PreToolUse の `updatedInput.cwd` は、`permissionDecision: allow` を付けても Agent の引数として使われず（体の `pwd` と相対パスの解決先は変わらない）、cwd の注入では解けない
- バックグラウンド（`Agent` の既定。`-p` でも同じ）で起動したサブエージェントでは、メインのターンの開始（`UserPromptSubmit`）と `Agent` の `PostToolUse` が `SubagentStop` より先に来る。`SubagentStop` はメインのターン開始より後になりうるので、終了結果の記録（`.outcome`）を読む側は、記録が無いときも扱えるようにする
- 非対話（`claude -p`）では、メインが終わったあとのバックグラウンドのサブエージェントは待ち上限まで待たれるが、環境の設定によってはターン終了で消える。そのため作業の決まりはフォアグラウンドで起動して完了を待つよう言う（[12.5](../limits.md)）

**実行中の印。** メインの `Stop` が、委任して待つ回を「レビュー依頼までの道」の促し（`NUDGE_TICKET_REQUEST`。6.6・9.6）で止めないための記録。

- `SubagentStart` が `state/subagent-<セッション>-<agent_id>.running` を置き、`SubagentStop` が外す。サブエージェントごとに 1 ファイルなので、並行して始まる・終わるサブエージェントが同じファイルを取り合わない。中身は 1 行目に `session <セッション>`（`.unchecked` と同じ。別のセッションの名前と前置きが重なりうるので、セッションは中身で決める）、2 行目に開始時刻（エポック秒）。編集するサブエージェントだけが、3 行目以降に `tree <種類> <名前>` と `type <agent_type>` を足す（「同じワークツリーの案内」）
- メインの `Stop` は、そのセッションの印が 1 つでも「実行中」なら促しを見送り、「1 回だけ」の記録（`nudged-<セッション>.json`）も進めない。入れ子の体（孫）も自分の `agent_id` の印を持ち、全部が外れるまで見送る。順序は `Agent` の `PostToolUse` が `SubagentStop` より先に来ても関係しない（始まりと終わりの印だけを見る）。`Stop` が `SubagentStop` より先に来れば印が残っていて見送る。逆に `SubagentStop` が `Stop` より少し遅れる終わりぎわの回も見送るだけで、害は無い
- 印を読めない（置き場を一覧できない、壊れて開始時刻を読めない）ときも見送る。壊れた印はファイルの更新時刻で期限を見る。促しは保護ではないので、迷ったら止めない側に倒す
- `SubagentStop` が来ないまま残った印（中断・クラッシュ・内部エラー）は、開始から `RUNNING_MAX_SECONDS`（既定 4 時間。`CCNAVI_SUBAGENT_RUNNING_MAX_SECONDS` で変える）を過ぎたら実行中と数えない。値は、バックグラウンドの体が実際に走る長さ（数分から 1 時間ほど）に余裕を足して決めた。長すぎても、取りこぼした印が促しを止める時間が延びるだけ。加えて、セッションの起動と再開（`SessionStart` の `source=startup` と `resume`）で、そのセッションの印を全部破棄する。どちらも新しいプロセスで、前のプロセスのサブエージェントは生きていないため。compact と clear では破棄しない（同じプロセスで、実行中の体が残りうる）。古いセッションの印は後始末（prune）が、ほかの `subagent-` の記録と同じに消す（`.outcome` も同じ 14 日）
- `agent_id` が payload に無い始まり・終わりは、キーが決まらないので印を置かず外しもしない。その体は実行中と数えられない（制限）
- 数えるのはサブエージェントだけ。チームメイトとバックグラウンドのシェルは待ちに数えない

**同じワークツリーの案内。** 同じワークツリーで編集するサブエージェントを並行させると、途中の変更でテストが落ちる、同じ文書を同時に編集する、未コミットの変更が常に残る、といった問題が出る。並行するときは別のワークツリーを割り当てる決まり（`.ccnavi/docs/decisions.md`）を、起動の時点で気づけるようにする。これは案内である。要件（外から観測できる約束）ではなく、実装の案内である。子チケットの一覧を渡す条件（REQ-TKT-22）とは別に、ワークスペースルートからの起動にも渡す。mode によらず、dry-run でも同じ文を渡す（`subagent._shared_note`）。

- 実行中の印（上）に、編集するサブエージェントだけが 3 行目以降を足す。`tree <種類> <名前>`（起動時の `cwd` のツリー。ワークスペースルートの名前は空）と `type <agent_type>`。読み取り専用のサブエージェントと、ワークスペースの外からの起動は書かない。3 行目の無い印（古い版が置いたものを含む）は、案内の相手に数えない。印は書きかけを見せない書き方（`fsio.write_text_atomic`）で置く。ファイルを作った時点で中身が空になる書き方だと、同時に起動した相手が中身の空の印を読み飛ばして、案内を逃す
- 起動したサブエージェントが編集するものなら、自分の印を先に置いてから、同じセッションの印を探す。自分のキーではなく、開始から `RUNNING_MAX_SECONDS` を過ぎておらず、ツリーが同じ（種類が同じで、名前は大文字小文字を区別せず比べる）ものが相手。同時に起動した 2 体のうち後から探すほうは、先に置かれた印を必ず見つけるので、相手を見つけ損ねる窓はない
- 「編集する」の見分け（`agentkind.kind_of`）は広めに倒す。読み取り専用と確かめられたものだけを読み取りとする。読み取りになるのは、ツールの一覧（定義の `tools`。`SubagentStart` の payload に `tools` は来ない）が空でなく、全部が読み取り系（`Read`・`Grep`・`Glob`・`LS`・`WebFetch`・`WebSearch`・`NotebookRead`・`TodoWrite`・`Agent`・`Task`。`agentkind.READ_ONLY_AGENT_TOOLS`）のときと、定義が無い組み込みの `Explore`・`Plan`・`claude-code-guide`。定義は `<ツリー>/.claude/agents` か `<ルート>/.claude/agents` から探し（`name` は大文字小文字を区別せず比べる）、組み込みと同名なら定義を優先する。これ以外は編集するものとして数える。`tools` に制限の無い定義、`*`、`Edit(src/**)` のような括弧付き、`Bash`、MCP のツール、空の一覧、定義が無い・読めない、`agent_type` が空、プラグインやユーザ階層の定義がこれにヒットする。`disallowedTools` は読み取りの根拠にしない（外していない `Bash` や MCP が残るため）。`Bash` だけで書き込むものも編集するものに数える（コードから書く経路は読み切れない）
- 同じ相手への案内は 1 回に抑えるため、案内した相手のキーを `state/once-<セッション>-peers-<agent_id>.json` に残す。同じセッションの中で `SubagentStart` がまた走っても（サブエージェントの再開）、同じ相手は重ねて案内しない。新しい相手には案内する。記録は `deliver` の数えと同じく `SessionStart` のたびに破棄するので（`ctxfile.forget`）、起動・再開・compact・clear のあとは、同じ相手にもう一度案内しうる。`deliver` が読み書きする `once-<セッション>-<agent_id>.json` とは別のファイルにする（書き戻すときに相手のキーを落とすため）。記録を読めない・置き場が無いときは、案内する側に倒す
- 案内は子チケットの一覧に至る前に組み、スキルの目録と同じ文にまとめる。チケットの無いツリーやワークスペースルートからの起動にも届く
- 案内の文は「起動時の作業ディレクトリが同じ」と言う。サブエージェントの `cwd` はメインの `cwd` になりうる（付録 C）ので、親が別のワークツリーを割り当てて隔離している場合も同じに見える。文には、別のワークツリーで作業している場合と、親から委任された子の場合は対応が要らないことを添える
- 既知の制限。(1) 入れ子の子は、待っている親と同じツリーで動く。hook の入力に親の `agent_id` は無いため、親子を見分けられない。そのため、委任のたびに案内が出る。(2) 案内が出るのは、起動した側だけである。先に動いていたサブエージェントは、後から来たサブエージェントについて知らされない。(3) 中断などで `SubagentStop` が来なかった印は、最大 4 時間残る。その間は誤って案内が出る。案内済みの相手の記録（上記）により、誤った相手への案内も、起動したサブエージェントごとに 1 回で止まる。(4) 印は、チケット制御の有無によらず置く。直接作業の促しが、チケット制御に依らないためである

**フローの案内。** 一覧の子がフローを持てば（ファイルが在れば）、その子の行の下に次を足す（`flow.briefing`）。

- 手順を並べるのは、起動の cwd が**その子のワークツリー**で子が 1 本に決まるときだけ。親のツリーからの起動
  （入れ子の孫も cwd は親のツリー）では、各子のフローのパスを 1 行ずつと「自分の担当の子チケットのフローだけを
  読んで従う。他の子のフローには従わない」だけを渡す。以下は子のワークツリーからの起動のとき
- フローのファイルの絶対パスと、それが合意済みの手順でエージェントは編集しないこと、作業の前に読んでその順に
  進めること、の 1 行（compact で案内が消えても辿り直せるようファイルを名指しする。付録 C）。ロックと、着手のあとの
  書き換えの知らせは、サブエージェントには言わない。ロックは書き込みを止めるときの理由で、書き換えの知らせは
  ユーザとメインに向く
- 手順を 1 ノード 1 行で並べ、合意済みのフローの本文（データ）として囲ったもの。`start` から繋がりを辿った順に
  `<番号>. [<種類>] <名前>: <中身> → <次の番号>（<分岐の名前>）`。40 ノードか文の上限（9.3.1）を超えたら
  そこで切り、続きはファイルを読ませる。リンクや読めないフローは 1 行で言う
- `askUserQuestion` のノードがあれば、その扱い。サブエージェントには AskUserQuestion が渡らないので、そのノードで
  手を止め、問いと選択肢を添えてメインに返す。メインがユーザに聞き、答えを持って同じサブエージェントを再開させる
- `loop` のノードがあれば、その扱い。条件が成り立つあいだ「繰り返す」側へ進み、成り立たなくなるか繰り返した回数が最大に
  達したら「抜ける」側へ進む。回数は自分で数え、最大に達しても条件が成り立つままなら最後の報告に書く
- `subAgent` / `subAgentFlow` のノードがあれば、その扱い。Agent ツールがあれば入れ子のサブエージェントとして起動し、
  そのプロンプトに担当の子の識別子を 1 つだけ書く（ccnavi がその子のワークツリーで案内する）。担当以外の子の識別子と
  ワークツリーのパスは書かず、`isolation` は使わない。
  **Agent ツールが無ければ**（入れ子の上限。`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`、クラウドの環境は 1）、
  そのノードで手を止め、起動してほしいエージェントの種類・プロンプト・担当の子の識別子を添えて
  メインに返す。メインがそのとおり起動し、結果を持って同じサブエージェントを再開させる（`askUserQuestion` と同じ流れ）

既知の制限: 孫の hook の `cwd` はメインの `cwd` になるので、孫の起動では `SubagentStart` が親の全部の子を
並べる（フローはパスだけ）。`SubagentStop` は全部の子を検査するが差し戻さず、`unattributed` として親へ知らせる。
孫は範囲の中なら兄弟のワークツリーにも書ける。入れ子の起動に担当の案内をプロンプトで渡すのはこのため（下の「起動前の担当の決め方」）。フローのファイルが無いときは何も足さない。

compact の前後の hook でフローを入れ直すことはしない。どちらの hook も `additionalContext` を受け付けるとは文書に書かれておらず、`systemMessage` は破棄されるため（付録 C）。

**起動前の担当の決め方（`hook.agentlaunch`）。** メインがワークスペースルートから任せると、`SubagentStart` の cwd がルートのままで、子の範囲とフローの案内が届かない。そこで起動の PreToolUse（`Agent`・`Task`。一覧は `toolnames.AGENT_TOOLS`）で、プロンプトの言及から担当を決める。作業場所（cwd）の注入は、実測で効かなかったので行わない（`INJECT_CWD`。更新の計画は cwd とプロンプトを別々に持つので、効く版で戻せる）。案内はプロンプトに書き足す。

- **言及。** 承認済みの子の識別子（作業中・レビュー待ち・閉じたの子。語として一致するものだけで、前後が `[A-Za-z0-9._-]` でない。大小は区別しない。親の識別子と未承認の提案は数えない）と、`.claude/worktrees/` を含むパス。「子 B には触れず」と書いた子 B も言及として数える（意味は読まない）。チケット制御が無効なときは識別子を拾わず、パスだけを拾う
- **検証。** 検証に通らないパスは担当の候補にならない（担当が決まっていれば無視し、決まらなければ止める）。パスは、このワークスペースの `.claude/worktrees/<名前>` で、`..` を含まず、途中にシンボリックリンクが無く、ccnavi のツリーに認識されている（`.git` と登録先の相互参照）こと。子は、`doing/` にあり、着手済みで、blocked でなく、親の `project:` とワークツリーの元リポジトリが一致し、ワークツリーがあること。子に結び付くものは、条件を満たさなくても直接作業として扱い直さない。直接作業のワークツリーは、結び付く承認済みチケットが無く、親のワークツリーでもない有効なパス
- **止める理由の優先順位。** 上から見て最初にヒットしたもの。(1) `isolation` のキーがある（値によらず `DENY_AGENT_ISOLATION`。チケット制御が無効でも、dry-run でも止まり、`CCNAVI_MODE=disable` だけ通す）。(2) 担当にできる言及が 1 つも無いのに無効なパスがある（パスが多すぎるときは、担当が決まっていても）`DENY_AGENT_TARGET_INVALID`。担当にできる言及があるときは、登録にない綴りのパスは担当にせず無視する。(3) 有効な指定が違うワークツリーを 2 つ以上指す `DENY_AGENT_MULTI_TARGET`（チケット制御が無効でも、パスが 2 つ以上なら止める）。(4) 1 つで親のワークツリー `DENY_AGENT_PARENT_TREE`。(5) 1 つの子が担当にできない `DENY_AGENT_CHILD_UNAVAILABLE`（理由を名指しし、未着手とワークツリーが無い場合だけ `start` の打ち方を示す）。(6) `tool_input` に決めた担当先と違う cwd が既にある `DENY_AGENT_CWD_CONFLICT`。(7) 言及が無く、呼び手の cwd が作業中の子を持つ親に属し、起こす種類が編集するもの `DENY_AGENT_NO_CHILD`（読み取り専用の種類は止めない）。種類は GATE（dry-run でも止める。MULTI_TARGET はチケット制御が無効なら AUX）と AUX に分かれる
- **入れ子。** 入力に `agent_id` があれば呼び手が体。呼び手の cwd が子のワークツリーなら、その子を 1 つの担当先として数える。言及が無い・同じ子だけなら担当は呼び手の子（子が担当にできなければ `CHILD_UNAVAILABLE`）、違う子やパスの言及があれば `MULTI_TARGET`。(7) だけは入れ子では適用しない（呼び手が子でなければ適用する）
- **入れ子の限界。** 呼び手の担当は、その呼び出しの `payload.cwd` が指す子のワークツリーで決める。メインがワークスペースルートから任せた体では `payload.cwd` がルートのままなので、呼び手の担当を引けず、入れ子の起動への検査（呼び手の子との食い違い）は効かない。`agent_id` と担当の対応表は持たない。このとき入れ子の起動には、プロンプトの言及だけで 1〜6 を行う
- **判定との合成。** 止める理由は `judge.decide_before` の中で、レビュー待ちの止め（`DENY_PHASE_REVIEW`）とサブエージェントの禁止の検査より後、ルールの照合より前に返す。更新の計画は持ったまま既存の判定を最後まで進め、応答を 1 つの JSON に合成する（`hookio.write_pre_tool_use`）。ルールには書き足す前の入力を適用する。ルールの allow と、どのルールにもヒットせず素通しする回は `updatedInput` を `permissionDecision` なしで載せる（allow を付けると権限の確認を飛ばすので付けない）。ルールの ask は `ask` に `updatedInput` を添える（公式文書では、`ask` との併用は変更後の入力をユーザに見せる。`-p` では確かめられない）。強制される deny には載せない。dry-run で報告だけになる deny・ask には載せる
- **担当の案内。** 担当の子、ワークツリーの絶対パス、範囲、先行、フローの手順、親の局面、「Bash の cd は続かない／担当外のワークツリーに触れない／push と状態の操作はしない」の 3 行を、`[ccnavi] 担当の案内（ここから）` と `（ここまで）` で囲んで末尾に足す。4,000 文字以内。先に必須の行（担当・パス・3 行・閉じ・フローのファイルの絶対パス）の分を確保し、残りに範囲・手順・局面を並べる。収まらない分は省いて「続きは <フローのファイル> を読む」を残す。元のプロンプトにある囲みは中身を信用せずに取り除いてから足す。同じ部品（`hook.childnote`）が `SubagentStart` の文も組む。直接作業のワークツリーには、担当とパスと 3 行だけを足す。チケット制御が無効なときは足さない
- **案内でできないこと。** 案内が届くかは、体がプロンプトの末尾を読むかどうかで決まる。体の cwd は変わらないので、相対パスの解決先は直らない。範囲の判定は、書き込み先のワークツリーのチケットで決まり、`agent_id` で担当外への書き込みを縛るものではない（子 A を担当に指して起こした体が、子 B のワークツリーへ絶対パスで書けば、子 B の範囲で判定される）。`SubagentStop` の差し戻しは cwd で決まるので、メインがルートから起こした体は `unattributed` のまま
- **finish の促しとの関係。** `Stop` の `finish` の促しは、実行中のサブエージェントが居る間は見送る（`_request_nudge` と同じ。「1 回だけ」の記録も進めない）。防ぐのは誤った促しだけで、メインが自分から早く `finish` を打つことは防がない
