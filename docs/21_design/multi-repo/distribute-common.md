### 11.12 共通レイヤーを配る

共通レイヤーはワークスペースの git にあり、プロジェクトだけを clone したユーザからは見えない。そこで、
ワークスペースルートの `.ccnavi/config/common/` の中身を、そのプロジェクトの `.ccnavi/config/common/` へミラーする。プロジェクトの `.ccnavi/config/project/` には触れない。
ミラーは誰も編集しないので、上書きで失うものは無い。このため、上書きで消える識別子の名指し、コピー先の未コミットの変更で止める処理、
上書きの記録、最初のレビューでの知らせ、知らせるまで親を閉じさせない処理は要らない。

ミラーを書く入口は 2 つ。

| 入口 | 書き先 | いつ |
|---|---|---|
| ユーザの発言（`UserPromptSubmit`。`tickets/promptsync.py`） | `project:` を持つ着手済みの親チケットのワークツリー | 発言のたび。差分が無ければ何も読まず書かない |
| ユーザが押す `ccnavi-user-mirror.sh`（`tickets/mirrorsync.py`。拡張のプロジェクト管理画面のボタンも同じ） | プロジェクトのユーザのチェックアウト（`projects/<名前>/`） | ユーザが調べたいとき、押したとき |

`ticket start` とツール呼び出しの中では書かない。書く場所と書く時が決まっているので、書いた分は実行後チェックとバックアップと復元から特別扱いしない。
発言のときに書いた分は、そのあとの受け入れ（`selfguard.accept`、`post.at_prompt`）が基準に取り込むので、次のツール呼び出しが戻さない。
ツール呼び出しの中でミラーが書き換わったら、共通レイヤーと同じ中身でも、エージェントの書き込みとして戻す・報告する。

発言のときの同期（`promptsync`）。

- 対象: `project:` が空でない、着手済み（`started_at`）の親チケット。子、未着手の親、ワークスペース自身の作業（`project:` が空）には書かない。ワークツリーが承認済みの `project` の元リポジトリから切られていることも確かめる
- 速い経路: コピーする元（共通レイヤー、ワークスペースの `.claude/skills/`）とコピー先（ミラー、`skills/`）の置き場の下のファイルの名前・大きさ・更新時刻から指紋を作る（`stat` だけ。中身は読まない）。前に揃えたときの指紋（`state/mirror-<親の識別子>.json`）と同じなら、そこで抜ける。違えば、検証つきの全体の比較（`configsync.plan`、`skillsync.plan`）を行い、差分があるぶんだけ書き、書いたあとの指紋を残す。一律に書き直す形は、読み込みの検証と全ファイルの書き込みが毎回要るので採らない
- コピーできなかったとき（読めない、リンク、書き込みの失敗）は、書かず、理由をモデルの文脈に言う。指紋は残さないので、直るまで毎回言い、直った発言でコピーする。発言と着手は止めない。書き込みが途中で失敗したら、書いた分は元に戻す
- コピーしたときは、コピーしたファイルの一覧と、コミットの案内（`ccnavi-git.sh add` と commit）を文脈に足す
- ユーザの発言のときだけ動く。バックグラウンド作業の完了通知では動かない（その間に動いたプロセスの変更と区別が付かないため、受け入れの対象にならない）
- 並行するセッションは、同じ内容を書くだけで、互いの結果を壊さない。指紋の置き場はセッションに依らない

何を: ワークスペースルートの `.ccnavi/config/common/` の中身（`rules.yml`・`phases.yml`・`risks.yml`・期待する判定・配点が指す `scripts/` の下・作業・レビュー計画のテンプレート `templates/*.yml`。テンプレートは読めるかを確かめる、設計は 9.15）を、
プロジェクトの `.ccnavi/config/common/` へ、中身の違うものだけ上書きして置く（改行の違いは同じとみなす）。共通レイヤーから無くなったファイルは、ミラーからも消す。ミラーは共通レイヤーのコピーで、
プロジェクトの `config/project/` とは別なので、消して失うものは無い。消すのも一時ファイルからの置き換えと同じく、途中で止まれば戻す。

- 配点の `script:` の値は書き換えない。ミラーの置き場も `.ccnavi/config/common/scripts/` で、共通レイヤーと同じ表記のまま指せる（11.4.2）
- コピーする前に、コピーするものを、ミラー（単体 clone では共通レイヤー）として読めるか確かめる。error が 1 つでもあれば何もコピーしない。
  共通レイヤーやスクリプトが読めないときも同じ。`phases.yml` はフェーズ定義として読めるかを確かめる（11.4.1）
- 共通レイヤーの `.ccnavi/config/common/` が無い、または空（配るファイルが 1 つも無い）なら、何も配らず、プロジェクトのミラーを消さない（共通が無いのは「設定が無い」正常。ミラーの全消去事故を防ぐ）。1 ファイルでも在れば上のとおり
- コピー先かその途中がシンボリックリンクなら止める
- 上書きは一時ファイルからの置き換えで行う。途中で書けなくなったら、書いた分を元の中身へ戻し、戻せなかったものを名指しする
- 書くのは実行ファイル。コミットはエージェントが `ccnavi-git.sh` で行い、同期の出力がそれを案内する
- プロジェクトの `.ccnavi/config/project/` は読みも書きもしない

読まれ方は 11.4 のとおり。ワークスペースの中で共通レイヤーとして読むのは、ワークスペースルートの `.ccnavi/config/common/` だけ。
ミラーが共通レイヤーとして読まれるのは、そのプロジェクトだけを clone したときだけで、そのとき `.ccnavi/config/project/` は自身のレイヤーになり、
ワークスペースの中と同じ「共通 + 1 レイヤー」の和で判定される。ミラーのおかげで、単体 clone のユーザにも共通のルールが「見える」。

ミラーの同期（`ccnavi-user-mirror.sh`）。プロジェクトのユーザのチェックアウトは、発言のときの同期の対象ではない。ユーザが見たいときに調べ、押したときに揃える入口を、
`handoff` と同じ作り（`user` の入口、見るだけと `--yes --expect`、ボードの経路 `--via board`）にする。中身は `tickets/mirrorsync.py`。

- 調べる: 何も書かない。プロジェクトのユーザのチェックアウト（`projects/<名前>/`）のミラーと共通レイヤーの差分を `configsync.plan` で、`skills/` と共通の工程スキルの差分を `skillsync.plan` で求め、1 つの変更の一覧に合わせる（`rel` の頭が `.ccnavi/…` と `skills/…` で分かれる）。共通レイヤーか工程スキルが読めなければ全体の誤り（どのプロジェクトでも同じ理由のため）。どちらにもコピーするものが無ければ `common_empty` で、全プロジェクトを同期済みとする。プロジェクトごとに調べられなければ（ミラーのディレクトリがリンクになっているなど）そのプロジェクトだけ `error` にし、まとめて揃える対象から外す
- 照合の値（`expect`）: 対象のプロジェクトを名前順に並べ、名前と、変更ごとのパス・種類・中身のハッシュを連結した SHA-256。ユーザに見せたあとに共通レイヤーかミラーが変わると値も変わり、揃える形は何も書かず「内容が更新されました」を返す
- 揃える: `expect` が今の差分と一致したときだけ、プロジェクトごとに、`skills/` の分を `skillsync.apply`、ミラーの分を `configsync.apply` で、この順に書く（途中で書けなければ、その分を元に戻す。`skills/` が失敗したらミラーは書かない。書けた分は残り、次に調べると残りの差分だけが出る）。1 つのプロジェクトが失敗しても、ほかは書く。書くのはワークツリーだけで、コミットしない。プロジェクトの `config/project/` に触れない
- ターミナル要求: 書くとき（`--yes`）はターミナルを求める。拡張の子プロセスは `--via board` でターミナルを求めない経路を使い、`--expect` と `--json` を付けて呼ぶ。hook は `user mirror` を `user handoff` と同じ扱いで止める
- 実行後チェックとの関係: エージェントのターンの最中に書くと、ツール呼び出しの実行後チェックが戻しうる。拡張は押す前に、自己防衛の設計書のターン中の印（8.4）を `turns` で確かめて知らせる。ユーザが書いた内容は、次の発言のときに基準に取り直される

代償。

- 二重管理になる。共通レイヤーとミラーは、発言のたびに揃うが、発言の間は食い違いうる
- ミラーを書いたあと、コミットするまでは未コミットの差分としてワークツリーに残る。セッションの最初の実行後チェックと、コミットしたターンの終わりの報告に、ミラーのファイルが 1 度ずつ載る（ユーザが直した保護領域と同じ扱いで、内容では見分けない）
- 別のセッションの発言が親のワークツリーを書く間に、そのワークツリーで動くセッションのツール呼び出しが重なると、その呼び出しの実行後チェックが、書かれたミラーを戻して報告しうる。戻すのは安全な側で、次の発言で指紋が食い違うので、コピーし直される
- レビュー待ちや統合の直前の親でも、共通レイヤーが変わるたびにミラーが差分になり、コミットの案内が出る
- 並行する 2 本の親が別々に配ると、統合先に取り込むときに衝突しうる
- 共通レイヤーの中身（ルール・配点・スクリプト）がプロジェクトの git に入る。public のリポジトリなら外に出る
- 違う共通レイヤーを持つワークスペースどうしが同じプロジェクトを扱うと、発言のたびにミラーが入れ替わる。止めるにはユーザが共通レイヤーを揃える
- 「揃う」のは、ミラーを共通レイヤーとして読む単体 clone だけで、ミラーが古ければ古い共通レイヤーで判定される
- プロジェクトだけのルールや配点は、プロジェクトの `.ccnavi/config/project/` に書ける。ミラーとは別のファイルなので、同期で上書きされることは無い
