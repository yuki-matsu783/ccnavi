### 11.4 ルール

パスを取るツール（Read / Grep / Glob / Write / Edit / MultiEdit / NotebookEdit）は共通設定に行き先の設定を足した統合結果。行き先は解いた先のパスで、
Grep と Glob が探す場所を省いたときは `cwd`。行き先がプロジェクトに属するならその git プロジェクトルートの `.ccnavi/config/project/rules.yml`、
ワークスペースのツリー（ワークスペースルートと、そこから切ったワークツリー）なら `<ワークスペースルート>/.ccnavi/config/project/rules.yml` を足す。
ルールは解いた先の絶対パスに適用するので、プロジェクトのルールに `*/schema/*` と書けば、元リポジトリでもそこから切ったワークツリーでもヒットする。
設定ファイルは元リポジトリのものを読む（ユーザが見たルールだけを適用する）。ワークツリーで設定を直しても、統合されるまで反映されない。
ワークツリーにしかない設定ファイルは `--lint` が warn で知らせる。承認済みの領域（`.ccnavi/approved/` の承認済みチケット・マーカー・子の記録・フロー）は数えず、そこは親のワークツリーの版を読む。

パスを取らないツール（Bash / PowerShell / WebFetch / Skill / Agent）は全部の設定を足した統合結果。共通設定、ワークスペースの設定、全プロジェクトの設定をタイプごとに
連結して適用する。`deny` `ask` `allow` の順は変わらない。Bash は `cd` で `cwd` の外に移れ、WebFetch・Skill・Agent は行き先のパスを持たないので、
どのプロジェクトの呼び出しかは決めず、どこに `cwd` があっても同じ判定になる（REQ-MLT-05）。

順は共通設定 → ワークスペースの設定 → プロジェクトの設定（名前順）。先にヒットしたルールが文面に載るだけで、判定は同じ。

**共通設定はワークスペースルートの 1 本だけ。** ワークスペースの中で共通設定として読むのは、ワークスペースルートの `.ccnavi/config/common/` だけ。
ミラーが共通設定として読まれるのは、そのプロジェクトだけを clone したとき（そのプロジェクトがルートになる）だけ。
このとき、プロジェクトの `.ccnavi/config/project/` はワークスペースの設定（`self`）として読まれ、ワークスペースの中と同じ共通設定に1 つの設定を足した統合結果になる。
プロジェクトの設定ファイルは、ワークスペースの中ではプロジェクトの設定（`<名前>:id`）、単体 clone ではワークスペースの設定（`self:id`）と、名前だけが違う。

識別子には設定の名前を添える。共通設定は裸の `id`、ワークスペースの設定は `self:id`、プロジェクトは `<名前>:id`（REQ-MLT-07）。記録の `rules` と
文面の `source` はこの形で出す。

裸の `id` にコロンは書けない。`id` を持つ 3 本（rules・phases・risks）とも、書いた `id`（`phases` のキー、配点の項目名を含む）にコロンがあれば error にして読み込みから外す。
接頭辞は足した設定だけが付ける。

設定の名前に `common` と `self` を予約する。この名前のプロジェクト（`casefold` で比べ、`projects/Self/` も同じ）は設定として数えず、
`--lint` が error で名指しし、`user agree` はその `project:` を承認しない。
予約名のプロジェクトへの書き込みは共通設定だけで判定する。ワークスペースの設定で判定すると、その設定の広い `allow` で通ってしまうため。
予約の判断は 1 か所に置き、設定を数える側と行き先の設定を引く側が同じ答えを引く。

重複は後ろを破棄する。裸の `id` が同じで、`{root}` を置き換えたあとの全欄（`match` / `glob` / `regex` / `message` /
`additionalContext*` / `additionalContext*File` / タイプ）が一致する定義は、後ろの設定のものを破棄する。`--lint` が
info で言い、`--explain` は残った 1 本だけ出す。全部の設定を足した統合結果でも同じ。

同 `id` で中身が違うとき、ルールは両方適用され、`--lint` が warn で言う。`allow` はパスを取るツールでは行き先の 1 つの設定にしか足さないので
そのツリーの中だけで済むが、パスを取らないツールでは他のプロジェクトの作業にも適用される。配点の項目も両方を数える（11.4.2）。
フェーズ定義は、同 `id` で中身が違えば error にする（11.4.1）。

`glob` も `regex` も、どの機械でも大文字小文字を区別しない（ルールの記法は設計の rules.md の「記法」）。チケットの範囲、フェーズ定義とリスクの配点の `scope`、
組み込みの保護（8.2）のパス、コマンドの名前も同じ規則で適用する。

Grep と Glob は、探し始める場所で設定を選び、ルールもその場所のパスに適用する。`*/secrets*` のようなルールは
探し始める場所のパスに `secrets` が無ければヒットしない。設定の選び方で差が出るのは、パスによらずヒットする広いルール（`match: Grep`・`glob: "*"` など）だけ。

ファイルが無いのは「設定が無い」正常で、不正なのとは違う。土台の deny と `builtin:guard-*` の扱いは 11.2 にある。

読めない設定は空として扱う。そのツリーを行き先にするパスを取るツールは共通設定だけで判定し、全部の設定を足した統合結果からもその設定を外す。
記録の `fallback` に設定の名前を残し、`--lint` が error で言う。組み込みの既定には戻さない（11.2）。
共通設定のルール自身が破損して読めないときだけは、組み込みの既定を使い、設定は足さない（REQ-PRE-06）。

できないこと（REQ-MLT-18）: プロジェクトの設定で共通設定の `ask` を `allow` に緩める、共通設定の `allow` をプロジェクトごとに外す、他のプロジェクトの設定をパスを取るツールの判定に足す。
「A のルールを B にも」は共通設定へ上げる。ccnavi ディレクトリの下（既定なら `.ccnavi/`。共通設定の `.ccnavi/config/common/` も入る）は、ルールに書かなくても書き込みが止まる。設定ファイルと配点のスクリプトは判定の中身そのものだから（8.2）。


#### 11.4.1 フェーズ定義

フェーズ定義（`phases.yml`）は、共通設定（`.ccnavi/config/common/phases.yml`）と、親の `project:` が指す設定（空ならワークスペースの設定）を足した統合結果で決める。共通設定には、どのプロジェクトでも同じ構成（`src/*`・`tests/*` など）を前提にできる定義を置き、
`scope` が置き場のレイアウトに依存する定義だけを、足した設定に置く。
この統合結果を読むのは提案の承認の検査と `--plan-order <親> --fill-phases`・`ticket new`・`--lint` だけで、承認のあとの判定は親にコピーした定義
（`phases:`）を読む（tickets/phases.md）。
足した設定は提案を置いた場所が決め（11.5）、子も親と同じ値を持つ。`project:` が空ならワークスペースの設定の `.ccnavi/config/project/phases.yml`、
プロジェクトの名前なら、そのプロジェクトの `.ccnavi/config/project/phases.yml`。ワークツリーの元リポジトリが `project:` と合うことは着手時に確かめてある（REQ-MLT-13）。

1 本の中の `id` の重複と表示名（`title`）の重なりは、その 1 本の読み込みで確かめる。足したあとは次の 2 つを見る。

- 共通設定と同じ `id` の定義: 全欄が同じなら足した設定を破棄して `--lint` が info で言う。中身が違えば error
- 共通設定のフェーズ定義と `title` が重なる、別の `id` の定義: error（ユーザは表示名で見るので、承認画面で見分けられない）

error のとき、破棄するのは足した設定の、その定義だけ。同じ `id` なら共通設定のフェーズ定義が使われ、`title` の重なりなら足した設定にその定義が
無いのと同じになる。その設定のほかの定義は足す。破棄する側はいつも足した設定で、共通設定のフェーズ定義はどのプロジェクトでも
同じ中身で読まれる。足した設定が共通設定のフェーズ定義を上書きする形は無い。破棄した定義は `--lint` が error で名指しする。
フェーズ定義は順序を持たない。順序は親の計画のステップの `after` が決める（tickets/phases.md）。足すときに揃える欄は `id` と `title` だけ。

ファイルが無いのは正常（11.2）。共通と足した設定のどちらかが無ければ、在る側の定義だけを使う。両方無ければフェーズ定義は空で、計画を持つ親の提案は、コピーを
確かめる相手が無いので承認で止まる。不正なら、そのファイルの定義は空として扱い、`--lint` が error で言う（共通設定が不正なら、
足した設定のフェーズ定義だけを使う）。承認済みの親はコピーで判定されるので、どのときも進行中の親は止まらない（`--lint` が warn で言う）。

`id` は裸のままキーにする。`plan:` と `feedback:` とマーカーは裸の `id` でフェーズ定義を指し、設定の名前は `--explain` と記録の「設定」の欄に出す。
接頭辞を付けない（足すのは共通設定と 1 つの設定だけで、同じ `id` は上の検査で 1 本に揃う）。

`scope` はワークツリーのルートからの相対。`inherit` も同じ。

#### 11.4.2 リスクの配点の合成

配点は統合結果をする。子をクローズするときに、親の承認済みチケットの `project:` が指す設定（空ならワークスペースの設定）を、共通設定に足す。
共通設定にも足した設定にも `risks.yml` が無ければ、組み込みの 4 項目を使う（11.2）。共通設定だけ無く足した設定が在るときは、共通設定を空として足した設定の項目だけを数える。

項目は連結し、閾値はキーごとに小さいほうを採る。共通設定の項目の後ろに足した設定の項目を並べる。全欄一致なら重複として後ろを破棄する（info）。
`levels` は `medium` / `high` / `critical` のそれぞれで、書かれたキーだけが参加し、そのうち小さいほうを採る。どの設定も書いていないキーは既定（20 / 40 / 70）。
合成後に `medium <= high <= critical` でなければ error。

同じ項目かは全欄で比べる。`script:` は書いたパスと置き場の対で比べる。ミラー（11.12）は共通設定と同じ `.ccnavi/config/common/scripts/` を指すので、
書き換えは要らない。

同 `id` で中身が違う項目は両方を数え、`--lint` は warn。後ろの設定の項目は `<設定の名前>:<id>`（例 `lib:big-diff`）と表記し、記録の `hits`、
`<子>.judge.json`、`record-risk` の項目名、問いの見出しはその名前で出す。足した設定を空にすると点が下がるので空にしない。

`levels` の順が崩れた設定は空として扱う。`fallback` に設定の名前を残し、クローズするときの出力が言い、`--lint` は error。共通設定だけで測るので、点は小さくなりうる。

`script:` の解決先は設定ごとに違い、たがいに指せない。

| 設定 | `script:` に書けるパス | 解決の基準 |
|---|---|---|
| 共通設定（単体 clone ではミラーも） | `.ccnavi/config/common/scripts/...` | そのとき共通設定を持つルート（ワークスペースルート、単体 clone ではそのプロジェクトの git プロジェクトルート） |
| ワークスペースの設定 | `.ccnavi/scripts/...` | ワークスペースルート |
| プロジェクトの設定 | `.ccnavi/scripts/...`（同上） | そのプロジェクトの git プロジェクトルート |

共通設定から `.ccnavi/scripts/` を、足した設定から `.ccnavi/config/common/scripts/` を指す定義は読み込みで error。指す先が git プロジェクトルートに無ければ
`--lint` が error（走らせるときは「測れなかった」でその項目の点を加える）。`cwd` は
子のワークツリーで、環境変数（`CCNAVI_BASE_SHA` 等）も同じ。プロジェクトの `.ccnavi/` はそのプロジェクトだけで閉じる。
