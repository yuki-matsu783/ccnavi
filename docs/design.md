## 1. 概要

### 1.1 何を解くか

Claude Code のエージェントは、作業に必要だと判断すると禁止された操作を突破しようとする（hook を外す、deny を緩める）。
設定のパターン一致はコマンドの構造（連鎖・サブシェル・リダイレクト）を見ないので複合コマンドの後段は判定されずに通り、
プロンプトの禁止は確率を下げるだけで、静的な権限は広く開けるか毎回確認するかの二択になり、拒否の根拠は
エージェントが書き換えられる作業ツリーの中にある。

ccnavi は Claude Code の hook から呼ばれ、危ないツール呼び出しを止め、「代わりに何をすればよいか」を名指しで返す。
止めるだけだとエージェントは別の表記で打ち直すので、拒否は別の手段へ誘導する文と一緒に返す。

### 1.2 骨子

| 骨子 | 中身 |
|---|---|
| 判定はルールで、既定は委ねる | ルールファイルの `deny` / `ask` / `allow` に当たればその判定。当たらなければ ccnavi は判定を持たず、Claude Code の権限モードに従う（6.5） |
| 引数に現れない書き込みは実行後に拾う | 実行前チェックはツール呼び出しの引数しか見ない。ビルドの出力やスクリプトの中のファイル操作は、走ったあとの作業ツリーを git で読んで拾う（7 章） |
| ガード自身の設定はルールの外で守る | ルールを空にされた形も壊れた形も、ルールから導いた保護領域は 0 件になる。hook の登録・ルール・実行ファイルは組み込みでバックアップして戻す（8 章） |
| チケットは絞る向きにだけ働く | 承認された範囲の外を止め、中は聞かない。ルールの判定と比べて強い側を採るので、ルールの `allow` も範囲の外では止まる。判定の鍵はファイルの行き先が属するワークツリー（9 章） |
| 実行ファイルは自分のディレクトリの外を見ない | マージリクエストやレビューのスレッドは `.ccnavi/scripts/` の sh が取得して JSON ファイルに書き、そのパスを `--result` で渡す。実行ファイルはネットワークに出ない（9.10） |

### 1.3 失敗の向き

誤検知ならエージェントが一手止まるだけで済むが、止めるべき呼び出しを通すと気づけない。判断がつかないときは拒否にする。

ただし設定 1 つの破損で回復手段まで奪う形は作らない。ルールが読めなければ組み込みの既定を使って判定を続け（5.6）、
未承認のチケットは判定に何も反映せず（9.4）、設定ファイルを `Write` / `Edit` で直す手段は既定では止めない。

## 2. 脅威モデルと守るもの

### 2.1 想定する主体

| 主体 | 説明 | 対象か |
|---|---|---|
| 逸れていく LLM | 悪意はないが、文脈の薄れ・誤解・思い込みにより破壊的な操作を行う | 主対象 |
| 誘導された LLM | 取り込んだページ・issue の本文・依存パッケージの文書に混じった指示に沿って動く | 主対象 |
| 事故 | 正常なコマンドの副作用、ビルドの想定外の出力 | 主対象 |
| 実行環境を掌握した攻撃者 | 同一ユーザー権限で任意のシェルを実行できる | 対象外 |

同じ権限で動く hook は、任意のシェルを実行できる主体に対しては境界にならない。ccnavi は LLM の逸脱と事故に対する柵で、
最終防衛線は OS・DB・実行環境の権限分離が担う（12 章）。

判定は呼び出しの内容だけから決め、その呼び出しを引き起こしたテキストの出どころでは変えない（REQ-PRE-09）。
出どころを理由にした例外は、注入された文でも出どころを自称すれば受けられる。

### 2.2 守るもの

| 何 | 想定する被害 | 守る仕組み |
|---|---|---|
| hook の登録、ルール、実行ファイル、保護済みスクリプト、承認済みチケットとマーカー | 防御そのものの無効化 | 自己防衛（8 章）とルールの `deny`、状態の置き場の組み込み拒否（9.5） |
| 認証情報の置き場、取り返しの付かない操作（`rm -rf`、`git push`、`git reset --hard`） | 漏洩、消失 | 組み込みの既定（5.6）とプロジェクトのルール |
| プロジェクトが `deny` / `ask` と宣言した場所 | 意図しない書き換え | 実行前チェック（6 章）と実行後チェック（7 章） |
| チケットが宣言した範囲の外 | 作業の範囲の逸脱 | チケット制御（9.5）とサブエージェント終了時チェック（9.12） |
| レビューを通っていない成果 | ユーザが見ていないものの合流 | フェーズの HITL ポイント（9.8）とレビューの確認（9.10） |

## 3. 設計原則

| # | 原則 | 中身 |
|---|---|---|
| P1 | 拒否にするが、回復の手段は残す | 対象を確定できない呼び出しは許可にしない（6.3）。設定が読めないときは既定を使い、直す手段を残す（5.6） |
| P2 | 宣言された制約は緩められない | ルールの `deny` / `ask` は、チケット・環境変数のどれによっても緩まない。チケットはルールと比べて強い側を採り、ルールの `allow` も狭める（9.5） |
| P3 | 言及の無い呼び出しは委ねる | ルールが言及しない呼び出しは権限モードに委ねて記録に残す（6.5） |
| P4 | 組み込みは最小 | ルールの外で持つのは、ガード自身を守るものと、取り返しの付かない操作だけ（5.6、8 章） |
| P5 | 判定の根拠を構造化する | すべての判定は理由コード・対象・当たったルールの識別子を持ち、記録と文面と試験の出力を同じ材料から作る（6.4、付録 A） |
| P6 | 逸脱は必ず見せる | 委ねた回、既定を使った回、実行後チェックが見られなかった回も 1 行ずつ記録し、実行後に汚れた保護領域はモデルとユーザの両方に示す（4.7、7 章） |
| P7 | 静的と動的の二段 | 実行前のコマンド構造の解析と、実行後の git の状態の検証を併用する（6 章、7 章） |
| P8 | 拒否は誘導と一緒に返す | `deny` の文面は「なぜ止めたか、代わりに何をするか」を必ず持つ。持たないルールは受け付けない（5.1） |
| P9 | 判定と試験は同じ関数 | `--test` と `--explain` と拡張の JSON は hook の判定と同じ関数を通る（10 章） |
| P10 | ユーザの判断は端末で受ける | 承認、未解決の受け入れ、親を早めに閉じる操作はユーザが端末で打つ。エージェントがユーザの合意を出せる形を作らない（9.4、9.10） |
| P11 | 実行ファイルの境界は自分のディレクトリ | 実行ファイルが見て判断するのは作業ツリー、git のオブジェクトと参照、承認済みチケット、マーカー、hook の payload だけ。外にあるものは sh が JSON ファイルに書いて渡す（9.10） |
| P12 | 親のコンテキストは清潔に保つ | 親（メインエージェント）は計画・提案・子の起動・合流・レビューの依頼だけをし、作業は子に切り出す。ccnavi が親へ返す文も短く、詳細は子へ渡す（9.7） |
| P13 | 止める・通すの判定は hook と実行ファイルが持つ | sh が持つのは、外との出入り・実行ファイルへの入口・打たれた形（コマンド行・パスの表記）の検査・運用の道具の 4 つ。sh が ccnavi の状態を読んで止めるのは 2 重目の確認で、同じことを hook が先に止める（8.2、9.10） |
