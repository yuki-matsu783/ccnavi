### 2.11 並行するチケット — REQ-TKT

複数のチケットが、それぞれ別のワークツリー（git worktree）で同時に進む。
メインエージェントが親チケットの下に子チケットを複数書き、サブエージェントが
子を 1 本ずつ実行する。子はフェーズというまとまりに分かれ、フェーズの終わりでユーザがレビューする。

| ID | 型 | 要求 |
|---|---|---|
| REQ-TKT-01 | 常時 | ccnavi は、書き込みの対象が行き着く先の属するワークツリーから、その呼び出しに適用するチケットを決めること。呼び出し元の作業ディレクトリや、呼び出したエージェントの素性によって変えないこと |
| REQ-TKT-02 | 常時 | ccnavi は、ワークツリーの名前とチケットの識別子が一致するものだけを結び付け、チケットの範囲をそのワークツリーのルートからの相対として解き、その範囲の `glob` と `regex` を機械によらず大文字小文字を区別せずに照合すること |
| REQ-TKT-03 | 状態 | チケットに結び付くワークツリーが存在しない間、ccnavi は、そのチケットの許可を有効にしないこと |
| REQ-TKT-04 | 常時 | ccnavi は、子チケットの範囲が親チケットの範囲を超えていれば承認の画面でそれを示し、判定では親チケットの範囲の外への書き込みを止めること |
| REQ-TKT-05 | 常時 | ccnavi は、親と子の判定が異なる対象について、厳しい側の判定を使うこと |
| REQ-TKT-06 | 常時 | ccnavi は、親子の深さを 2 段に限り、子を親に指定したチケットを承認の対象にしないこと。承認の画面を経ずに承認済みチケットの置き場に置かれたものにも同じ検査を判定のときに適用し、ヒットすれば範囲を適用せずにそのワークツリーへの書き込みを全部拒否すること |
| REQ-TKT-07 | 常時 | ccnavi は、子チケットの識別子を親の識別子とフェーズ番号とそのフェーズ内の連番の組に限り、別の親の子と衝突しない形にし、識別子の中のフェーズ番号が子のフェーズと食い違うものを読まないこと |
| REQ-TKT-08 | 事象 | チケットの承認を求められたとき、ccnavi は、主となるワークツリーとすべてのワークツリーの提案の置き場を走査し、未承認のチケットを、それぞれの人間レビューの要否と理由とともに一度に示すこと |
| REQ-TKT-09 | 常時 | ccnavi は、チケットの状態を置き場で表すこと。提案の置き場に承認待ちとレビュー待ち、承認済みチケットの置き場に作業中と閉じた（取り消しを含む）の 4 つとし、チケットは 1 本のファイルとしてその間を動くこと。承認済みチケットの置き場へ動かすのはユーザの操作（承認・レビュー済み・受け入れ・親を早めに閉じること、およびユーザがファイルを直接動かすこと）に限り、レビュー待ちの置き場への直接の作成と移動を、エージェントの素性によらず拒否すること |
| REQ-TKT-10 | 常時 | ccnavi は、チケットの状態を動かす操作と、レビューの依頼・確認・コメント・ready、リモートへの push、ワークツリーや統合の操作をサブエージェントに許さず、読み取りの副命令だけを許すこと。sh を介さず実行ファイルを直に呼ぶ形も、承認の経路を切る設定（`CCNAVI_GUARD_TICKET_APPROVAL`）の値によらず許さないこと |
| REQ-TKT-11 | 事象 | チケットが着手されたとき、ccnavi は、開始の時刻と差分の基準点を記録し、以後そのワークツリーの範囲外の検査を、基準点以降のコミット済みの差分と未コミットの変更の両方に対して行うこと |
| REQ-TKT-12 | 事象 | 承認済みのチケットが作業中の置き場から出たとき（レビュー待ち・閉じた・取り消し）、ccnavi は、ユーザの承認を経ずにそのチケットの許可を無効にすること。再び有効にするのはユーザの操作によること |
| REQ-TKT-13 | 事象 | 同じ親の同じフェーズに属する子チケットがすべて閉じられ、そのフェーズに人間レビューが要るとき、ccnavi は、エージェントに、すべての子が親ブランチへ合流済み（子の finish が合流して push する）と確かめ、ターンを終えてユーザを待つよう伝えること。見る場所がマージリクエストなら push とレビューの依頼を、このセッションならユーザに差分を見てもらうことと、先へ進めるのがユーザの直接起動であることを伝えること |
| REQ-TKT-14 | 事象 | 同じ親の同じフェーズに属する子チケットがすべて閉じられ、人間レビュー要のものが 1 枚も無いとき、ccnavi は、人間レビューを省略して進むことをエージェントに伝え、省略した事実を残すこと |
| REQ-TKT-15 | 状態 | 人間レビュー要のフェーズが終わり、そのフェーズにレビュー済みのマーカーが無い間、ccnavi は、サブエージェントの起動と、チケットの状態を動かす操作・レビューの依頼と確認・git のラッパースクリプト以外のシェル実行を拒否し、理由にユーザへの問い合わせを入れること |
| REQ-TKT-16 | 事象 | レビューの依頼を求められたとき、ccnavi は次の前提をすべて確かめること。フェーズが終わっている。そのフェーズの子がすべて親ブランチに合流済みである（子の finish が書いた合流した先頭が、親ブランチの先頭の祖先であること。さらに、子のワークツリーが手元にあるとき、子の手元のブランチに finish のあとに積まれ親に入っていないコミットがあれば、合流していない修正があるとして満たさない）。未コミットの変更が無く、push 済みである。この 2 つの検査では、提案と承認済みチケットの置き場を数えない。そのフェーズのレビューが延期されていない。そのフェーズがレビュー済みでない。まだ依頼していない。1 つでも欠ければ、欠けたものを全件示して依頼しないこと。すべて満たせば、対応するマージリクエストに依頼を投稿し、依頼の時点を記録すること。マージリクエストが無ければ下書きで作る。依頼の後に親ブランチの HEAD が動いていれば、依頼し直せる。提案と承認済みチケットの置き場だけを変えたコミットと、ELI5 の置き場（wip/eli5/ の下）だけを変えたコミットは、動いたと数えない。ELI5 とほかのファイルを一緒に変えたコミットは数える。依頼には、変更をやさしく説明した HTML（ELI5）が添えられていることも求めること。ELI5 が次の条件を欠けば、欠けたものを全件示し、何も書かずに止め、ELI5 を書いてコミットして渡すよう伝えること。ファイルが在り、空でない。拡張子が .html か .htm である。依頼を出すワークツリーの wip/eli5/ の下にある。名前が英数字と . _ / - だけでできている。HEAD に普通のファイル（モード 100644）として入っていて、手元の中身が HEAD と同じである。つまり、ELI5 がマージリクエストの差分に載っていること。ccnavi は、ELI5 をユーザが見る道具（crit）を起動しないこと。投稿が済んだら、ユーザが打つ形を示すこと。ユーザはソースの行に指摘を付け、crit push でマージリクエストの行のスレッドとして送る。送られたスレッドは REQ-TKT-17 の未解決のスレッドとして数え、REQ-TKT-18 で行き先を選ぶ対象にすること |
| REQ-TKT-17 | 事象 | レビューの確認を求められたとき、ccnavi は、そのフェーズがレビュー済みなら拒み、依頼の記録が無いか、記録にホストとマージリクエストの番号が無ければ拒み、あれば、いま解決されていないスレッド（ccnavi 自身の投稿を除く。受け入れたスレッドは解決済みにしてある）と、レビュアーごとの判断を示した最新のレビュー（承認・変更要求・取り下げ。コメントだけのものと書きかけは数えない）を数え、変更要求のレビューが無く未解決のスレッドも無ければレビュー済みのマーカーを置き、そのフェーズ（延期を引き受けた分を含む）のレビュー待ちのチケットを閉じた置き場へ動かし、あればマーカーを置かずにその一覧を示すこと。依頼の時点より後かどうかでスレッドを除かないこと |
| REQ-TKT-18 | 事象 | 未解決のスレッドの扱いを求められたとき、ccnavi は、ユーザが直接起動したとき（ターミナル）か、見せた一覧に対する選択とダイジェストを渡されたとき（`ccnavi-user-decide.sh` の `--choices --digest`。見せた指摘と今の指摘のダイジェストが一致するとき）に限りそれを受け付け、未解決の指摘を 1 件ずつ示して、それぞれの行き先を選ばせること。行き先は、対応しない（スレッドに返信を残して解決する）、このフェーズで直す（同じフェーズの番号で、見た子の範囲の和と直す指摘の一覧を持つ子を承認済みチケットの置き場に直に置き、そのフェーズのマーカーを消す）、課題に回す（対応しないと同じく返信を残して解決し、その指摘を載せた課題を作る。フィードバック計画の有無に関わらずいつでも選べる）の 3 つ。見せたあとに増えた指摘（追加分）は止めず、未対応のまま残すこと。直す指摘も追加分も無ければレビュー済みのマーカーを置くこと（直す指摘が無くても追加分があれば置かない）。マーカーを置いたときも、続きの子を起こしたときも、見た子のレビュー待ちのチケットを閉じること（追加分だけが残るときは動かさない）。途中で失敗した送信は、操作記録（`logs/state/ops/`）から続きを送れること。続きの子は、本文に指摘ごとの全文を転記し、操作記録の ID を持たせ、ユーザが選んだことで承認されたものとし、別の承認を求めないこと。ボードの経路の形をエージェントがシェルから打つことは止めること（拡張側は REQ-VSC-05） |
| REQ-TKT-19 | 状態 | 変更要求のレビューが立っている間、ccnavi は、ユーザの直接起動によってもレビュー済みのマーカーを置かないこと |
| REQ-TKT-20 | 事象 | チャットで受けた承認や判断の書きコピーを求められたとき、ccnavi は、それをマージリクエストの通常のコメントとして投稿し、レビューの状態を変えないこと |
| REQ-TKT-21 | 事象 | 終わったフェーズに子チケットが新たに承認されたとき、ccnavi は、そのフェーズの依頼・レビュー済み・省略のマーカーを消すこと |
| REQ-TKT-22 | 事象 | サブエージェントが親または子のワークツリーで開始されたとき、ccnavi は、そのワークツリーに関わる承認済みで閉じていない子チケットの識別子・ワークツリー・範囲・先行チケットの状態をサブエージェントに渡すこと。主となるワークツリーやチケットの無いワークツリーでの開始には渡さないこと。あわせて「Bash の cd は続かない・担当外のワークツリーに触れない・push とチケットの状態を動かす操作はしない」の 3 行を添えること |
| REQ-TKT-23 | 事象 | サブエージェントが終了しようとしたとき、そのワークツリーに範囲外の変更（基準点以降のコミット済みの差分または未コミットの変更）が残っていれば、ccnavi は、1 回に限りそれを示して終了を差し戻すこと |
| REQ-TKT-24 | 常時 | ccnavi は、提案の置き場と承認済みチケットの置き場を設定で差し替えられ、承認済みチケットの置き場が保護されていないときはそれを診断で示すこと |
| REQ-TKT-25 | 事象 | 設定の検証を求められたとき、ccnavi は、チケットの無いワークツリー・識別子と名前の一致しないワークツリー・識別子の形が規約に合わない子・同じ識別子が複数の置き場にあるもの・先行が閉じていないのに作業中の子・読まれない場所に置かれた承認済みチケット・無い認証情報・ワークツリーでも主でもないのに設定ディレクトリを持つディレクトリ・下書きの置き場に追跡されているファイルがあるリポジトリと、その置き場が git で無視されていないリポジトリ（ワークスペースと各プロジェクトのそれぞれ）を示すこと |
| REQ-TKT-26 | 常時 | ccnavi は、フェーズ定義（識別子・表示名・作業かフィードバック対応かの別・ユーザがどこで見るか（見ない・このセッション・マージリクエスト）・範囲の上限・成果物）を、保護された設定ファイル（共通レイヤーと、親の `project:` が指すレイヤーの 2 本）の和から読むこと。識別子か表示名が重なる定義、範囲の上限か成果物が 20 件を超える定義は誤りとして示すこと。フィードバック対応のフェーズ定義に「見ない」を許さないこと |
| REQ-TKT-27 | 常時 | 親チケットが全体計画（作業フェーズ定義のリスト）とフィードバック計画（フィードバック対応フェーズ定義のリスト）を持てること。全体計画に作業以外のフェーズ定義、フィードバック計画にフィードバック対応以外のフェーズ定義があれば承認を拒むこと |
| REQ-TKT-28 | 常時 | 計画のステップでレビューを延期できること。延期したフェーズの終わりでは進行を止めず、延期したフェーズが先行する後ろのフェーズのうち延期していない最初のもの（全体計画とフィードバック計画で同じ決まり）の依頼に、延期した分を含めること。計画の最後のステップとレビュー不要のフェーズ定義は延期できないこと |
| REQ-TKT-29 | 事象 | 子チケットの承認を求められたとき、その番号に先行するフェーズ（親の計画のステップの `after` を推移的に辿った番号。フィードバック計画のステップは全体計画の番号を全部と、フィードバック計画の中で辿った番号）が全部閉じ、レビュー（延期でなければ）が済んでいなければ、ccnavi は、承認を拒むこと。同じ承認で親の計画を改版していても、改版後の計画で先行させること |
| REQ-TKT-30 | 常時 | 子チケットの範囲が、そのフェーズ定義の範囲の上限を超えていれば、ccnavi は、承認の画面でそれを示し、判定ではその上限の外への書き込みを止めること |
| REQ-TKT-31 | 事象 | フェーズの最後の子を閉じようとしたとき、フェーズ定義の成果物が親または子のワークツリーに在って追跡されていなければ、ccnavi は、閉じるのを拒み、無いものを示すこと |
| REQ-TKT-32 | 常時 | 親チケットの改版で変えられるのは計画・計画が使うフェーズ定義のコピー・範囲（allow / ask / deny）だけで、範囲を変える改版は作業中の子が居ないときだけ通ること。題・課題番号・`mr:` は変えられないこと。子が承認された番号のステップ（定義・レビューの指定・番号・先行する番号）とその番号が使う定義は変えられないこと。フィードバック計画は全体計画の最後のレビューが済んでから 1 回だけ置け、それを立てる改版とそのあとの改版では全体計画を変えられないこと |
| REQ-TKT-33 | 常時 | フィードバック計画は、指摘が無くても空のリストとして承認を受けること。ccnavi は、親を閉じる前にフィードバック計画が承認されていることを求めること |
| REQ-TKT-34 | 事象 | フィードバック対応フェーズの最後のレビューで指摘が残ったとき、ccnavi は、同じフェーズに子を足してやり直す道と、残りを切り出す道の 2 つを示すこと。切り出す先は、マージリクエストで見た親ならユーザが REQ-TKT-18 で課題に回すことで作る別の課題、どのフェーズもマージリクエストに出していない親なら新しい親チケットの提案とすること。新しいフィードバック対応フェーズは足せないこと |
| REQ-TKT-35 | 常時 | 診断とサブエージェントへの案内が、フェーズを番号とフェーズ定義の表示名で示し、親の局面（作業中・レビュー準備中・レビュー待ち・フィードバック計画待ち・フィードバック対応中・クローズ可。ユーザが早めに閉じたときは「閉じられる（ユーザが早めに閉じた）」）を名指しすること。サブエージェントへの案内は、開いた子が居る親についてだけ名指しする |
