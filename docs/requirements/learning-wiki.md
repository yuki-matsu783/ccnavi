### 2.14 学びの蓄積 — REQ-LRN

状態: 実装済み。今ある wiki の移行と後方互換は対象外。実装の範囲は設計 9.16 の「実装の範囲」。

チケット作業で拾った気づきを、そのまま破棄せずに溜め、ルール・配点・フェーズ定義・テンプレート・スキル・文書のどれかへの提案として育てる。
育てる仕事のうち、集める・溜める・提案するまでがエージェントで、反映を受け入れるのは人間である。
実行環境が作業のたびに作り直され、git で追跡されないファイルが残らない場合も成り立つようにする。
その場合は、子チケット 1 本が 1 セッションで、1 ターンで終わることもある。

用語は次のとおり（CONTEXT.md）。

| 用語 | 意味 |
|---|---|
| 気づき | 子チケットのセッションが拾った、次の作業でも使える知識の 1 件。子ごとに 1 ファイルの記録に書く |
| パターン | learning-wiki の 1 ページ。気づきを統合した、失敗や有効だった進め方 1 つ |
| 反映先 | 提案が直すもの。ルール・配点・フェーズ定義・テンプレート・スキル・文書の 6 種 |
| 提案 | 反映先 1 つへの変更の案。差分と、動機のパターンを持つ |

| ID | 型 | 要求 |
|---|---|---|
| REQ-LRN-01 | 常時 | ccnavi は、気づき・パターン・提案の採否を、git で追跡されるファイルにだけ置くこと。判定の記録・state・セッションの履歴・スクラッチパッドにしか無い情報を、後の工程の入力にしないこと |
| REQ-LRN-02 | 任意 | ccnavi は、学びの蓄積を使うかを 2 段階で決めること。全体は、ルールの判定・チケット制御とは別の 1 つの設定（`CCNAVI_LEARNING`。`enable` / `disable`、既定 `enable`）で決め、`enable` と `disable` 以外の値は `enable` とし、そのことを診断で示すこと。フェーズ定義は欄 `learning`（`on` / `off`、既定 `on`）を持てること。子に適用されるのは、全体が `enable` で、その子のフェーズ定義が `off` でないときだけであること（統合の子だけは、印から決まる。REQ-LRN-25）。適用されない子については、着手の案内・子を閉じる検査に出ないこと。追記の依頼（REQ-LRN-20）は、全体が `enable` のときフェーズ定義によらず使えること |
| REQ-LRN-03 | 事象 | 学びの蓄積が有効で、子チケットが着手されたとき、ccnavi は、気づきの記録の書き方と置き場（その子の識別子のファイル 1 本）と、閉じる前に記録の操作（REQ-LRN-04）を打つことを、着手の出力に 1 行で示すこと |
| REQ-LRN-04 | 事象 | 気づきの記録の操作を求められたとき、ccnavi は、その子の気づきの記録の雛形（無ければ、または空なら）と、そのワークツリーの判定の記録の要約（REQ-LRN-05）を、追跡される置き場に書くこと。中身のある記録は上書きせず、要約だけを書き直すこと |
| REQ-LRN-05 | 常時 | 判定の記録の要約は、そのワークツリーでの判定ごとの件数（`deny` `ask` `nudge` `handover`）と、繰り返し同じ呼び出しを止めた形（ルールの識別子・ツール名・コマンド名の語）だけを持つこと。絶対パス・コマンドの全文・環境変数の値を含めないこと。コマンド名の形をしていない語は持たないこと。判定の記録が読めない環境では、要約は読めなかったことを示し（件数 0 と区別すること）、記録の操作は失敗しないこと |
| REQ-LRN-06 | 事象 | 学びの蓄積が有効な親の子チケットを閉じようとしたとき、その子の気づきの記録が、その子のブランチの HEAD にコミットされた通常のファイルで、空でなければ、閉じられること。そうでなければ、ccnavi は、閉じるのを拒み、置き場と記録の操作とコミットが要ることを示すこと。気づきの有無や質は問わないこと。気づきが無いときは、無いと書いた記録で閉じられること |
| REQ-LRN-07 | 常時 | 気づきの記録を書くのは、その子のセッションだけで、書くのは自分の識別子の記録だけであること。パターンを書く役は統合の子だけであること。採否の記録は、提案の MR の中で書き、マージで決着すること。承認する人間のレビューを最後の防御とすること（防御の方針）。複数の子が並行して進んでも、記録の置き場が衝突しないこと |
| REQ-LRN-08 | 事象 | 学びの蓄積が有効な親を閉じようとしたとき、ccnavi は、学び以外の検査をすべて通したあと、親の今の HEAD で、すべての気づきに処理の証跡（節ごとの `処理:` の行と、反映したパターンの `sources` の観測元の ID）がそろい、受信箱が空になるまで閉じさせないこと。止めるときは、該当のファイルと節を名指しし、統合の子を作る `ticket consolidate <親>` を案内すること。記録・パターン・受信箱の置き場に未コミットか未追跡の変更があるとき、読み取れない記録や整合の検査にヒットする記録があるときも止め、理由と直し方を示すこと。統合を済ませた後でも、毎回今の HEAD で検査し直すこと。全部の記録が `none` で受信箱も空なら、統合は要らず通ること |
| REQ-LRN-09 | 常時 | パターンは、反映先の種類（`target`）と、重複しない観測元の ID の一覧（`sources`）を持つこと。観測元の数は、その一覧の数で決めること。観測元の ID は、子の記録なら子の識別子、親の記録なら親の識別子、受信箱なら `inbox:<ファイル名から .md を除いたもの>` とすること |
| REQ-LRN-10 | 事象 | セッションが始まったとき、ccnavi は、リポジトリごとに、統合先（手元の `origin/HEAD`、無ければ `origin/main`・`origin/master`）の手元の参照が指すコミットの `docs/wiki/` を数え、「候補」が `CCNAVI_LEARNING_NOTICE_COUNT`（既定 5）件以上か、観測元の数が閾値（`CCNAVI_LEARNING_SOURCES`、既定 3）以上の候補が 1 件以上あり、かつ、通知済みの記録に無い候補が現れたとき、または新しく閾値に届いたときに、件数・`target` ごとの内訳・依頼の仕方を、ユーザにだけ（`systemMessage`）知らせること。参照を決められないか読めないリポジトリは見送り、通知済みの記録を変えないこと。モデル向けの文脈には学びの情報を足さないこと |
| REQ-LRN-11 | 常時 | ccnavi は、提案を反映先ごとに分け、1 つの提案が直す反映先を 1 つにすること。反映先がルール・配点・フェーズ定義のとき、エージェントが書くのは下書きだけで、ユーザが置くまで効かないこと。テンプレートは取り込み（REQ-TKT の作業・レビュー計画のテンプレート）に従い、スキルと文書はチケットの範囲とレビューに従うこと |
| REQ-LRN-12 | 常時 | ccnavi は、提案の差分を、ユーザの承認を経ずにどの反映先へも書かないこと。承認はユーザの直接の操作によること（REQ-APV、REQ-TKT-18 と同じ） |
| REQ-LRN-13 | 常時 | 提案の手順の文書（`.ccnavi/docs/learning-propose.md`）は、関係する採否の記録を先に読み、却下されたものを、理由を覆す根拠なしに出し直さないよう定めること。機械は止めないこと |
| REQ-LRN-14 | 常時 | 提案の採否は、提案の MR の中で採否の記録（`docs/wiki/impact/<提案>.md`）の `status`（`承認`・`却下`・`延期`）・`decided_at`・`patterns` の観測元の数を書き換えてマージすることで決着すること。専用のコマンドは持たないこと。承認は、反映先の実際の差分を確かめてから書くこと。決着するときは `patterns` の各値を、その時点でマージ先のパターンから数えた観測元の数に書き直すこと。パターンの状態は、採否の記録からパターンごとに 1 つ（提案中・候補・決着）に決まること |
| REQ-LRN-15 | 常時 | 採否の記録は、却下した提案も差分ごと残し、消さないこと。パターンも、提案が却下されたことを理由に消さないこと。整理（統合・要約・古いものの削除）は、エージェントが自動で行わず、提案として出すこと |
| REQ-LRN-16 | 常時 | ccnavi は、learning-wiki の中身を、セッション開始・サブエージェント開始・子チケットの着手の、モデル向けの案内と目録に載せないこと（REQ-LRN-10 のユーザ向けの通知は、モデルに渡さない）。作業のセッションは、気づきの記録を書くために learning-wiki を読まなくてよいこと |
| REQ-LRN-17 | 事象 | `ccnavi --learnings [--json]` を求められたとき、ccnavi は、指定したツリー（既定は cwd のツリー）の wiki について、パターンごとの状態と観測元の数、閾値以上かどうか、「候補」の件数と `target` ごとの内訳、`承認待ち` の提案の一覧を、判定せずに示すこと。frontmatter の壊れたファイルは名指しし、数えないこと |
| REQ-LRN-18 | 異常時 | パターン・採否の記録が、読めない・形が違うとき、ccnavi は、それを `--learnings` と `--lint` で名指しし、そのファイルだけを数えずに、ほかのものの読みを続けること。気づきの記録が読み取れない・整合の検査にヒットするときは、親の `finish` と `consolidate` を止め、記録を直すよう案内すること |
| REQ-LRN-19 | 常時 | ccnavi は、学びの統合と反映を親のフィードバック計画のフェーズ定義としては持たないこと。共通レイヤーの `phases.yml` と計画テンプレートから `learning-consolidate` と `learning-apply` を外すこと。統合は、親の `finish` が止めて案内する統合の子が行うこと |
| REQ-LRN-20 | 事象 | 対話セッションでユーザが気づきの記録への追記を依頼し、記録の操作に本文が渡されたとき（`ticket learn --note`）、ccnavi は、気づき 1 件を追記すること。作業ディレクトリがチケットに結び付いたワークツリー（親・子）なら、そのワークツリーの名前の記録（REQ-LRN-04 と同じ置き場）へ追記し、記録が無ければ雛形を作ってから追記すること。気づきの数は追記のたびに数え直すこと |
| REQ-LRN-21 | 事象 | 追記の依頼の作業ディレクトリが、チケットに結び付かない直接作業のワークツリーのとき、ccnavi は、気づきをそのワークツリーの受信箱（`docs/wiki/inbox/`）に、1 件 1 ファイルで書くこと。受信箱のファイルの名前は重ならず、既存のファイルを上書きしないこと。`docs/wiki/inbox/` のファイルは、統合先へ取り込まれても外れないこと。ワークスペースルートとプロジェクトのルートのときは、何も書かずに断り、ワークツリーを切るよう案内すること。統合の子は、受信箱を入力に含め、処理したファイルを消すこと |
| REQ-LRN-22 | 常時 | 追記の依頼では、種類と信号を省けること。省いた種類は未定、省いた信号は `訂正` とすること。種類が反映先の 6 種に無い、信号が 4 種に無い、本文が空のときは、何も書かずに拒むこと |
| REQ-LRN-23 | 常時 | 追記する本文は、判定の記録と同じ規則で秘密の形を伏せ、2000 字で切ること。切ったことは、本文の末尾に示すこと |
| REQ-LRN-24 | 常時 | 取り下げた提案（取り消した提案の子、承認前に取り下げた提案）は、延期として扱うこと。もっと観測されてから手順にすればよいため |
| REQ-LRN-25 | 常時 | 統合の子は、子・`phase: 0`・`maintenance: learning-consolidate` の 3 つがそろうものだけとし、組み合わせのおかしいもの（親に印、印つきで `phase` が 0 でない、知らない値）は構造エラーとして、承認の側でも判定の側でも止めること。印は通常の提案・承認の経路では使えず、印を持つ提案は承認で拒むこと。統合の子だけは、計画のステップと照合せず、フェーズの進行・レビュー待ちの集計・レビュー依頼の対象に含めず、気づきの記録を求めず、実績リスクを測らず、必ずレビュー不要で `done/` へ移すこと |
| REQ-LRN-26 | 常時 | 統合の子の範囲は、ccnavi の中に固定した定義（書ける場所は `docs/wiki/patterns/*` と `docs/wiki/inbox/*`）を上限とし、子の `allow` も適用し、親の範囲の上限だけを適用しないこと。ルールの deny と自己防衛はそのまま効くこと。実行前・実行後・サブエージェント終了時・合流前の検査が同じ判定を共有すること |

REQ-LRN-01 は、作業のたびに実行環境が作り直され、追跡されないファイルが残らない場合でも、集めた気づきが次の工程に届くようにするため。
判定の記録には絶対パスとコマンド全文が入るので、そのままは持ち出さない（REQ-LRN-05）。

REQ-LRN-06 が子を閉じる条件にするのは、1 ターンで終わるセッションではターン終了の振り返りが届かないため。
閉じる操作は必ず通るので、気づきを書く機会をそこに置く。中身の質を問わないのは、無理に作った気づきが混ざるのを避けるため。

REQ-LRN-07 が 1 子 1 ファイルにするのは、並行する子が共有のファイル（索引や経過）を直すと、親へ合流するときに衝突するため。
パターンを直すのは、統合の子だけ。

REQ-LRN-20 から 23 は、対話の中で人が「これは覚えておいて」と言った場面の入口。ターン終了の振り返りは 10 回に 1 回しか来ず、子を閉じる検査はセッションの最後にしか来ないので、
その場の訂正は人が頼まないと記録に届かない。追記は記録までである（REQ-LRN-07、REQ-LRN-12）。

REQ-LRN-21 が受信箱を分けるのは、直接作業には親が無く、`wip/handoff/` は統合先へ取り込むときに外れるため。ルートに書かないのは、追跡されず、誰がまとめるかも決まらない置き場になるため。
受信箱のファイルは 1 件 1 ファイルで名前が重ならないので、並行する作業が同じファイルを直して衝突することが無い。

REQ-LRN-02 が 2 段なのは、全体の設定が「使うか」と、ユーザだけが切れる止め弁の役を持ち、定義ごとの欄が「この作業は気づきを求める意味が薄い」を表すため（小さい作業の `quick-work` など）。定義はユーザが持つ設定なので、エージェントが自分で記録を免除することはできない。

REQ-LRN-24 が取り下げを延期とするのは、もっと観測されてから手順にすればよく、観測元が増えたパターンだけが候補に戻るため。

REQ-LRN-08 が親の今の HEAD で毎回検査し直すのは、統合の子が閉じたことは処理の証拠にならず、未コミットの変更は届かないため。追記や子の追加も同じ検査で扱える。

防御の方針。学びの蓄積の記録・wiki・採否の記録を、本来の役でないエージェントが書き換えて偽装することへの備えは、最低限にとどめる。
決めた備えは、書く役を定めること（REQ-LRN-07）、他の作業の識別子の記録へ書かない操作の検査（REQ-LRN-20）、記録を HEAD の通常のファイルとして見ること（REQ-LRN-06）、
反映先を人間の承認なしに書かないこと（REQ-LRN-12）の 4 つ。
作り込まない理由は、これらの記録は提案の材料であって、効くのは人間が承認した反映先だけであり、承認する人間のレビューが最後の防御になっているため。

REQ-LRN-12 と REQ-LRN-14 が人間の操作に限るのは、チャットでの「採ってよい」を hook が見られないため（REQ-TKT-18 と同じ理由）。

REQ-LRN-13 は、同じ提案の出し直しを機械で止めず、人間が気づく材料を出す。却下の理由を覆す根拠があれば、出し直してよいため。

REQ-LRN-16 は、作業のセッションが learning-wiki から答えを得ると、手順書（スキル）の効きが見えなくなるため。
