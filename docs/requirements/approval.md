### 2.9 チケットの承認 — REQ-APV

| ID | 型 | 要求 |
|---|---|---|
| REQ-APV-01 | 事象 | チケットの承認を求められたとき、ccnavi は、そのチケットによって新たに無確認で書き込めるようになる領域を、提示の最初に置くこと |
| REQ-APV-02 | 事象 | チケットの承認を求められたとき、ccnavi は、前回承認されたチケットからの権限の差分と、人間レビューの要否と、計画を示すこと |
| REQ-APV-03 | 常時 | ccnavi は、チケットが宣言した範囲の広さでリスクの点を付けないこと。リスクは子チケットを閉じるときに実績の差分で測ること（REQ-RSK） |
| REQ-APV-04 | 状態 | 現在のチケットの内容が承認された内容と一致しない間、ccnavi は、そのチケットが与える許可をすべて確認以上の厳しさにすること |
| REQ-APV-05 | 事象 | チケットが承認されたとき、ccnavi は、承認された内容を、エージェントが書き換えられない場所に残すこと。承認は提案の中身を変えずに動かし、どの経路（置き場を動かす経路を含む。REQ-APV-07）で承認しても、承認済みチケットが提案と同じ中身になるようにすること |
| REQ-APV-06 | 事象 | 承認の対象を識別子で絞るよう求められたとき、ccnavi は、対象を狭めるだけで、絞らないときに承認されないものを承認しないこと。承認待ちに無い識別子、親や親の改版が承認待ちなのに対象に無い子が含まれていれば、何も承認しないこと |
| REQ-APV-07 | 常時 | ccnavi は、承認をユーザが押したことの証拠を求めること。端末から求められた承認は標準入力が端末であることを、画面から求められた承認は見せた一覧と現在の一覧が一致し、見せた中身のハッシュも一致すること（REQ-APV-09・REQ-APV-15）を条件とし、一致しなければ何も承認しないこと。承認済みチケットの置き場に在ること自体を 3 つめの証拠として認めること。手元の置き場へのファイル操作はエージェントに書かせないこと。リモートの置き場（親のブランチ）はホストの権限でのみ守り、書き手の表示は行わないこと。エージェントがシェルから承認の経路を起動することは、どの形でも拒むこと（拡張側は REQ-VSC-01・REQ-CHR-01） |
| REQ-APV-08 | 事象 | チケットが承認されたとき、ccnavi は、承認したことが、承認の答えに載せる Claude Code に渡す文と、承認済みチケットの状態を聞く手立て（REQ-APV-20）で伝わるようにすること（文を渡すのは拡張。REQ-VSC-02） |
| REQ-APV-09 | 事象 | 見せた一覧に対する承認を端末を介さずに求められたとき（`--agree --yes`）、ccnavi は、見せた中身（承認画面の本文と、承認済みチケットとして書き出す中身）と承認のときに読み直した中身が一致するときだけ承認済みチケットを置くこと。一致しないとき、または見せた中身を照合する値が渡されないときは、何も承認しないこと（拡張側は REQ-VSC-01） |
| REQ-APV-10 | 事象 | 見せた一覧に対する承認を端末を介さずに求められたとき（`--agree --yes`）、ccnavi は、承認済みチケットをコミットして push する手順を、ユーザの端末で打つ sh（`ccnavi-push-approved.sh`。REQ-EXT-20）として用意すること（端末へ送るのは拡張。REQ-VSC-03） |
| REQ-APV-11 | 事象 | エージェントが承認済みチケットをコミットして push する sh を実行しようとしたとき、ccnavi は、それを止めること |
| REQ-APV-12 | 事象 | エージェントが承認の経路の sh を実行しようとしたとき、ccnavi は、大文字小文字の違いによらずそれを止めること |
| REQ-APV-13 | 事象 | 承認できる状態かを確かめるよう求められたとき、ccnavi は、承認済みチケットを置かずに、承認の対象に入るものと入らないもの、入らない理由（絞りそのものが通らないときはその理由）を示し、指定されたもの（指定が無ければ承認待ち全部）がそのまま承認の対象に入るかどうかを終了コードで返すこと。答えの終了コードは、使い方と設定の誤りを表すものと分けること。承認が落とさないものでは落とさず、確かめの答えと承認の結果を食い違わせないこと |
| REQ-APV-14 | 事象 | エージェントが承認待ちの置き場に提案を書こうとしたとき、ccnavi は、その呼び出しの判定を変えずに、承認を依頼する前に確かめる手立て（REQ-APV-13）を 1 つの文脈につき 1 度伝えること |
| REQ-APV-15 | 事象 | 読み直した中身で承認の判定を求められたとき（`core.judge_approval` と `core.plan`）、ccnavi は、その中身で判定し直し、見せた一覧とダイジェストが一致するときだけ、親のブランチへの承認の書き込みを返すこと。ダイジェストが違えば何も返さないこと（読み直して親のブランチへ 1 コミットで置くのは拡張。REQ-CHR-01） |
| REQ-APV-16 | 事象 | 承認の取り下げを求められたとき（`core.withdraw`）、ccnavi は、承認済みチケットの中身が承認コミットの親の提案とバイト単位で同じで、親なら固定した待ち方があるときはそれが承認したときの待ち方と同じで、続きの子でなく、子もマーカーも無く、戻す先に提案が無いときだけ、承認済みチケットと固定した待ち方を消し、その提案を元のバイト列のまま戻す書き込みを返すこと（承認コミットの親の提案を渡し、親のブランチへ 1 コミットで置くのは拡張。REQ-CHR-02） |
| REQ-APV-17 | 常時 | 同梱の ccnavi の互換の版が統合先の互換の版と違うとき、承認と取り下げは書かれないこと。書く先が保護されたブランチの名前か統合先の名前のときも書かれないこと（互換の版を読む行の形は REQ-EXT-06。書かないのは拡張。REQ-CHR-03・REQ-CHR-04） |
| REQ-APV-18 | 事象 | 読み直した親のブランチでフェーズのレビュー済みを求められたとき（`core.confirm`）、ccnavi は、その親のブランチと、マージリクエストのスレッドとレビューで、レビューの確認（REQ-TKT-17）と同じ判定を行い、通るときだけ、レビュー待ちのチケットの移動とレビュー済みのマーカーの書き込みを返すこと。依頼の後にユーザが見るものが動いていないと確かめられないとき（変更の一覧が打ち切られた、依頼時の先頭が祖先でない場合を含む）は返さないこと。マーカーには付けたアカウントと経路を残すこと（スレッドとレビューを取り、親のブランチへ 1 コミットで置くのは拡張。REQ-CHR-05） |
| REQ-APV-19 | 事象 | issue から始める親の識別子を求められたとき（`ticket.issue_identifier`）、ccnavi は、issue の番号とタイトルから識別子（`feature-<番号>-<slug>`。プロジェクトのリポジトリなら `feature-<番号>-<プロジェクト名>-<slug>`）を決めること（その識別子の親のブランチを作るか決めて作り、マージリクエストを作らないのは拡張。REQ-CHR-06） |
| REQ-APV-20 | 事象 | 承認済みチケットの状態を求められたとき、ccnavi は、チケットごとに、置き場、承認の時刻、着手しているか、置き場のファイルが未コミットか・コミット済みで未 push か、止まっている理由、次の一手を示すこと。何も書かず、リモートへ取りに行かず、push 済みかが手元の記録によることを示すこと。未コミットの承認済みチケットを運ぶ手順はユーザに頼むものとして示し、エージェントが運ぶ手順は示さないこと |

REQ-APV-02 の「前回承認されたチケット」は、子チケットでは親チケットを指す。子の承認画面が示す差分は、
親の範囲をどこまで絞ったかになる。

REQ-APV-05 が求めるのは、エージェントが書き換えられないことと、承認した時点の内容が残ることの 2 つ。
並行するチケット（REQ-TKT）ではチケット 1 本ごとの承認済みチケットで満たす。承認の経路によって中身を変えると、欄の有無が経路を
表し、欄の無い承認（置き場を動かした承認）が壊れた承認に見える。承認の時刻は欄に持たず、状態の履歴か、承認済みチケットを置いた
コミットから引く。親の待ち方は承認済みチケットの外（マーカーの置き場）に固定する。

REQ-APV-07 の「画面から求められた承認」は VS Code の拡張を指す。拡張の子プロセスは端末を持たないので、
ユーザに見せたものとこれから承認するものが同じことを証拠にする。3 つめの「置き場に在ること」は、端末もボードも
持たないユーザのための経路。この経路は承認の画面を通らないので、承認のときの検査
（REQ-TKT-06、REQ-MLT-11）は判定の側が当て、止まっているものは検証（REQ-DIA-06 の `blocked`）が示す。

REQ-APV-07 の改訂: Chrome 拡張が PAT で親のブランチへ承認を書くように
なったので、リモートの置き場はホストの権限でのみ守り、書き手の表示も行わない。前の文（置き場へエージェントが書けないことを
もって成り立たせる）と比べて**判定が緩む変更**である。エージェントがホストの API に直接書いたチケットは、ユーザが承認したものと区別できない
（ユーザの判断で、この危険は受け入れる）。手元の置き場の保護（実行前チェック・実行後チェック）は変えない。

REQ-APV-18 の判定は、手元のレビューの確認と同じコア（`core.confirm` と
`review.moved_since`）で出す。スレッドとレビューを取ってくる処理だけが sh（`ccnavi-review.sh`）と拡張（TS）の 2 か所にあり、
録っておいたホストの応答の見本を使い、両方が同じ結果を組み立てることを試験で確かめる。マーカーのアカウントは記録で、判定にも表示にも使わない。手元のレビューの確認（REQ-TKT-17）も、`ccnavi-review.sh` がトークンの持ち主を引けたときはマーカーに残す（引けなければ
前と同じ中身）。マーカーのアカウントは押したユーザではなくトークンの持ち主で、マージリクエストの作者本人でも通る
（自己レビューは防がない）。

REQ-TKT-17 の「ccnavi 自身の投稿」は、GitLab で、依頼を投稿したアカウントが書いた、目印で始まるスレッドに限る。
GitHub の依頼はスレッドにならないので、目印で始まるスレッドもユーザの指摘として数える。投稿者が分からない依頼の記録
（投稿者を記録するようになる前に置いたもの）では見分けずに数える（厳しくする側を選ぶ）。

REQ-APV-15 の「画面」は Chrome 拡張のボードで、判定は同梱の ccnavi を Pyodide で動かして出す。拡張は判定を自分で書かず、ccnavi の判定をそのまま使う。
先頭の一致は GitHub の `createCommitOnBranch` の `expectedHeadOid` で取る。
GitLab は Commits API に比較つきの書き込みが無いので、書く直前に先頭を読み、書き換える・消すファイルに
そのファイルを最後に変えたコミット（`last_commit_id`）を付けて、同じファイルを他人が変えていれば書かない。書いた後にコミットの親が
読んだ先頭かを確かめる。違えば直前の状態で判定し直し、書くものが変わるなら元に戻すコミット（revert）を積んで読み直す。元に戻すまでの間は、
判定の変わった書き込みが親のブランチに乗りうる（受け入れた危険）。元に戻せなければユーザの対応に切り替え、
手元は取り込みの後の判定し直しでその親子のチケットを止める。`seq` ファイルによる比較つきの書き込みは、本物の GitLab で
前提を確かめてから足す。

REQ-APV-18 のマーカーのアカウントと経路は、手元でレビューの指摘の行き先を決めた（decide）ときも残す。
`ccnavi-review.sh` がトークンの持ち主を引けたときだけで、経路は端末で選んだなら `terminal`、VS Code のボードで押したなら `board`。
引けなければ前と同じ中身。

REQ-APV-19 の識別子は `ticket.issue_identifier` の 1 つだけから決め、Chrome も同梱の ccnavi で
同じものを呼ぶ。始められない issue は、識別子をユーザが付けて（フォールバック）手元で始める。プロジェクト名は手元の
`projects/` の下の名前で、Chrome 拡張には設定画面でリポジトリごとに登録する。

REQ-APV-08 は、画面で承認すると承認とセッションが離れ、伝えないとユーザが「承認した」と打つまで作業が止まるため。以前は hook が
次にモデルへ渡す機会に 1 度だけ伝えていたが、セッションの最初に起点を取る形では、開始時の取り込みで届いた承認を取りこぼした。
ボードの承認は拡張が承認の文を渡し、ほかの経路の承認はユーザがそのあとセッションに一言送り、エージェントは REQ-APV-20 で聞く。

REQ-APV-16 の「中身が同じ」は、承認が中身を変えないことから、改版も着手もされていないことを表す。置き場を動かした承認も取り下げられる。
待ち方を固定したファイルが無い親（置き場を動かした承認）は、改版が必ずそのファイルを書くので、待ち方の改版は起きていないとみなす。
前の版の承認が承認済みチケットに承認の記録を書き足していた古い形は、承認コミットの親の提案と一致しないので、記録の欄で決める。

REQ-APV-20 はサブエージェントにも許す。状態を動かす手順を示す行には、親（メインエージェント）だけが実行することを書く。
エージェントがファイルを読んで推測すると、置き場を動かした承認（記録の欄が無く未コミット）を承認が途中で止まったものと読み違える。

REQ-APV-11 の補足: 取り込み済みの親子のチケットでは、状態の操作（`ccnavi-ticket.sh`・
`ccnavi-review.sh`）が C1 で親のブランチへ push する。C1 の push は親のブランチの未送信のコミットをすべて送る
（git push の性質）。コードのコミットはエージェントが `ccnavi-git.sh push` で送れる範囲と同じ。置き場について
送るのは、状態の操作がこの実行で書いたパスと、ccnavi が書いたと内容で分かるパス（hook の `pending`・`skipped`
のマーカーと状態の履歴の追記）だけで、それ以外の置き場の変更が未送信なら C1 は送らずに止める。ユーザの判断をコミットして push するのは、これまでどおりユーザである
（`ccnavi-push-approved.sh`。ユーザの判断の入口の sh が最後に呼ぶ）。

REQ-APV-13 が終了コードで返すのは、読む相手がエージェントだから。見せる枝（REQ-DIA-10）と分けるのは、
それを読む VS Code のボードが 0 以外を失敗として扱うため。承認が落とさないのは範囲の超過と読めない提案で、
どちらも本文で名指しする。承認待ちが 1 件も無いときだけは答えが違い、承認は「することが無い」で通り、
確かめは「いいえ」を返す。

REQ-APV-14 の文は判定ではないので、ルールの表に載せない。1 度に限るのはコンテキストを食わないため。

### 2.9.1 実績で測るリスク — REQ-RSK

| ID | 型 | 要求 |
|---|---|---|
| REQ-RSK-01 | 事象 | 子チケットを閉じようとしたとき、ccnavi は、その子のワークツリーの基準点から HEAD までの差分を数えて点とそのリスクレベルを出し、エージェントが書き換えられない場所に残すこと |
| REQ-RSK-02 | 常時 | ccnavi は、点の配点を保護された設定ファイルから読み、無ければ組み込みの配点で、壊れていれば組み込みの配点に戻ってそのことを示すこと。リスクレベルの名前は固定で、境目の点だけを設定で変えられること |
| REQ-RSK-03 | 常時 | 配点の項目は、差分の量（行数・ファイル数・消したファイル数・触ったパス）、保護された場所に置かれたスクリプトの出力、サブエージェントが判断して親が記録する定性の問い、の 3 系統を持てること。スクリプトが測れなかった項目は、その項目の点を加えて示すこと |
| REQ-RSK-04 | 状態 | 定性の項目の判定が子の現在の HEAD に対して揃っていない間、ccnavi は、その子を閉じさせず、問いと差分の要約を親に示すこと。判定を記録できるのは親だけで、サブエージェントには許さないこと |
| REQ-RSK-05 | 状態 | フェーズの点（子の最大値）が高いリスクレベル以上である間、ccnavi は、種類や子の宣言がレビュー不要でも、そのフェーズを人間レビューが要る扱いにすること。実績が小さいことを理由に宣言のレビュー要を下げないこと。レビューをどこで受けるかは指定せず、宣言が「見ない」だったフェーズだけをこのセッションで見る扱いに上げ、マージリクエストで見ることを勧める文を添えること |
| REQ-RSK-06 | 事象 | 子を閉じたとき・フェーズが終わったとき・診断を求められたとき・レビューを依頼するとき、ccnavi は、点・リスクレベル・加点した理由を示すこと |
