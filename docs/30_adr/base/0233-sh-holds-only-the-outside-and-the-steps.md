# ADR-0233: sh は外との出入りと段取りだけを持つ

状態: 提案（今の sh のうち分担に合っていない処理を 1 本ずつ直す。直した範囲は `.agents/docs/sh-go-gaps.md` の「済み」の表）

## 状況

実行ファイルを Go に移して起動は速くなったが、テストの時間は縮まらなかった。Python のテストの全件は、4 並列で 8 分半、
直列に足すと 34 分かかった。その 7 割は sh を起こすテストで、遅さの元は sh 自身だった。`ccnavi-start.sh` の典型の
テスト 1 本（0.44 秒）は外部プロセスを 87 個、重いもの 1 本は 709 個起こしていた（git・tr・dirname・jq・sed）。
ネットワークに出る処理はそのうちの一部で、残りは引数の検査、ホストの応答の読み取り、振り分けの判断、ローカルの git の操作、
案内の文の組み立てだった。テストを Go で書き直しても、sh の中のこの処理は残るので速くならない。

分担の線は、実行ファイルはネットワークに出ない（ADR-0028、設計原則 P11）と、止める・通すの判定は hook と実行ファイルが持つ
（ADR-0077、P13）で決まっていた。ただ、sh に置いてよいものは「外との出入り・実行ファイルへの入口・打たれた形の検査・運用の道具」
としか書かれておらず、全 30 本を読むと、この線の内側で実行ファイルに置ける処理が大半を占めていた。決まりからずれた所もあった。

| ずれ | 場所 |
|---|---|
| 保護するブランチの一覧を 4 か所に書いている。形も揃っていない（`release-*` と `release/*`） | `ccnavi-git.sh`（2 か所）・`ccnavi-user-push-approved.sh`・`ccnavi-common.sh` |
| 実行ファイルの答え（`ops show` の JSON）を sh が jq で読む | `ccnavi-user-lib-review.sh` |
| パスを自分で小文字にして比べる | `ccnavi-review.sh` |
| 実行ファイルの規則を sh に手で写している | `ccnavi-stage.sh` の `is_importable`、`ccnavi-branches.sh` の `names_number` |
| 同じ応答の読み方を jq と TS の 2 つで持つ | `ccnavi-common-review.sh` の `threads` と Chrome 拡張の `gitlab.ts` |

ラッパー（`ccnavi-git.sh`）の中の可否の判定と `integrate` / `integrate-done` の状態操作は、ADR-0118 が P13 の例外として sh に置いた。
理由は、判定の材料がネットワークと git の手順の途中にあり、判定と操作の間に別のプロセスを挟むと状態が変わる隙が増えることだった。
このラッパーは 2,571 行あり、テストも重い（`test_integrate_sh` 66 秒、`test_gitwrap` 29 秒）。

## 決定

**sh が持つのは、外との出入りと段取りだけにする。プロジェクトのディレクトリの中で決められることは、すべて実行ファイルが持つ。**
sh は実行ファイルに次の一手を聞き、言われたネットワーク操作をして、結果をファイルで返す。P11 の線（実行ファイルはネットワークに出ない）は動かさない。

処理は「sh で実装するもの」と「Go で実装するもの」の 2 つに分ける。sh で実装するのは次の表の 7 つだけで、どれにも当たらない処理は Go で実装する。

| sh で実装するもの | 例 |
|---|---|
| 外との出入り。ホストの API、origin への fetch・push・ls-remote、認証、その時間の上限 | `ccnavi_host_api`・`ccnavi_host_pages`・`ccnavi_git_timed`・`ccnavi_run_timed`。API のパスとページの送り方もここに入る |
| 段取り。ネットワークと実行ファイルの呼び出しを並べる順序 | start・sync・write-and-push の流れ。次に何を取るかを決める最小の読み（件数・cursor）もここに入る |
| sh のプロセスの寿命に結び付くもの | ロック（持ち主は sh の pid）、信号を受けたときの trap、idle の待機 |
| 起動役 | launcher、ワークスペースと実行ファイルの探し方、診断ログ |
| 実行ファイルを起こさずに動くもの | `ccnavi-fetch.sh`・`ccnavi-user-push-approved.sh`（実行ファイルの入れ替え中も動かすため。ADR-0077）、実行ファイルが壊れていても効く、独立した2 重目の検査（子のワークツリーからの push。ADR-0118） |
| ユーザだけが打つ入口 | `ccnavi-user-*` の名前、y/N の確認、引数の許可リスト |
| ラッパーの受け口 | ラッパーが受けた引数を、環境を整えてから実行ファイルへ渡すこと。何を通すかは実行ファイルが決める |

| Go で実装するもの | 例 |
|---|---|
| 応答の解釈 | GitHub と GitLab の形の吸収、本文の解析、失敗の種類の分け方。Chrome 拡張の WASM と同じ関数を使う |
| 判断 | 引数の検査、振り分け、止める条件。ラッパーが何を通すか |
| ローカルの git とファイルの操作 | ワークツリー、早送り、コミット、merge、integrate、記録の読み書き |
| 出力の文 | すべて文面ファイルに置く |

境界の約束は次のとおり。

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| sh から実行ファイルへは、取ってきた応答をそのままファイルで渡す（`--result`）。引数もそのまま渡す | 実行ファイルは外を見ずに、渡された材料だけで決められる（ADR-0028 の理由 2 と同じ） | sh が整えてから渡す。整え方が sh と実行ファイルに分かれる |
| 実行ファイルは 1 行 1 項目で答え、判断は次の一手の語で返す（`create <branch>`・`stop <終了コード>`・`fetch <何を>` など） | sh は行の先頭の語を見るだけで済み、JSON を読まない | JSON で返す。sh に jq の読みが残る |
| sh は JSON（実行ファイルの答えを含む）もチケットの YAML も読まない。例外は段取りの最小の読みと、実行ファイルを起こさずに動く検査だけ | 読み方が sh と実行ファイルの 2 つに分かれると、片方だけ直してずれる | 実行ファイルの答えなら jq で読んでよいとする |
| 規則の写しを sh に置かない。保護するブランチ・識別子・ホストの種類は実行ファイルに聞く。実行ファイルを起こさずに動く sh が写しを持つときは、一致をテストで確かめる | 同じ規則が複数あると形がずれる（`release-*` と `release/*`） | 写しを残し、直すときに両方を直す決まりにする |
| 取得と解釈が交互に来る所（ページ送り、GitLab の権限の 2 段、sync の merged）は、次に取るものを決める最小の読みだけを sh で実装し、中身の解釈は Go で実装する | 起動を応答のたびに挟むと、遅さの元が実行ファイルの起動に移るだけになる | 実行ファイルが毎回次に取るものを返す。sh の読みは無くなるが、起動が増える |
| 信号を受けたときの戻しは、その操作を始めた側が持つ。Go で実装する一続きのローカルの書き込みは 1 回の起動の中で完結させ、戻しもその中で持つ。sh の trap は子を止めて待つだけにする | 戻す側と書いた側が別のプロセスだと、どこまで書いたかを受け渡す必要が出る | 書き込みは実行ファイル、戻しは sh の trap。途中の状態を sh が知る必要がある |
| ラッパー（`ccnavi-git.sh`）の中の可否の判定と、`integrate` / `integrate-done` の状態操作は Go で実装する。ラッパーは環境を整えて実行ファイルに聞き、言われたネットワーク操作（fetch・pull・push と、push のゲートの ls-remote）だけを打つ。これで ADR-0118 を置き換える（ラッパーを Go で実装し直した時点で 0118 の状態を変える） | 0118 の理由（判定と操作の間に別のプロセスを挟むと隙が増える）は、判定と状態の操作を実行ファイルの 1 回の起動にまとめれば無くなる。0118 の 3 条件のうち、生の操作が組み込みで止まることと、許可リストで読むことは、置き場が実行ファイルに変わっても保てる。ADR-0077 が sh から実行ファイルに聞く形を退けた理由（`CCNAVI_ENTRY_PATH` で偽物を指せる）は、`DENY_SCRIPT_ENV_OVERRIDE` で塞がっている | 0118 のまま sh に置く。ラッパーの 2,571 行とその重いテストが残る |
| Go で実装するローカルの git の書き込みは、ラッパーが通すかを決めるのと同じ検査の関数を通す | 経路によって検査が外れる形を作らない | 実行ファイルは信頼できるので検査しない |
| 今の sh の処理を Go で実装し直すときは、書き換える前の出力（終了コード・標準出力・標準エラー）を見本に取り、文面を変えない | 実装の置き場の変更と振る舞いの変更を切り離し、置き場を変えたことで変わった所を見本が捕まえる | 書き換えながら文を直す |
| sh のテストは通しの確認だけにする。経路ごとに数本とし、1 回の実行で終了コード・出力・作られた物・ホストへの要求をまとめて見る。判断と解釈は Go の表駆動のテストで確かめる | sh のテストの時間は sh を 1 回走らせる時間でほぼ決まる。観点を分けると、同じ実行を観点の数だけ繰り返す | 観点ごとに 1 本の sh のテストを残す |

## 得たもの・失ったもの

- 得たもの: sh で実装してよいかを、表の 7 つのどれに当たるかで言える。当たらない処理は Go で実装する
- 得たもの: 判断と解釈が Go の表駆動のテストになり、プロセスを起こさずに確かめられる。sh のテストは本数も時間も減る
- 得たもの: ホストの応答の読み方を、実行ファイルと Chrome 拡張の WASM が共有できる
- 失ったもの: 実行ファイルのサブコマンドが増え、sh との約束（次の一手の語と、渡すファイルの形）を保つ手間が増える
- 失ったもの: ラッパーと integrate が実行ファイル無しでは動かなくなる。今も `tree bound` などに聞いているので、増えるのは integrate の状態操作の分だけ
- 失ったもの: 使う側が sh を書き換えて直せる範囲が、外との出入りと段取り（接続・API のパス・順序）に狭まる。ADR-0028 の理由 1 が守っていたのはこの範囲

## 採らなかった案

- **sh の処理を丸ごと Go で実装する。** 実行ファイルがネットワークに出ることになり、P11 と ADR-0028 の線を越える
- **テストだけを Go で書き直す。** 遅さの元は sh の中の外部プロセスで、テストを書く言語では変わらない
- **sh のテストを 1 本に観点を詰めて減らすだけにする。** 時間は縮むが、判断と解釈が sh に残り、ずれ（上の表）も残る
