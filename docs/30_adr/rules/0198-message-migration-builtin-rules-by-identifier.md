# ADR-0198: 文面の移行は、組み込みルールの文を識別子で判定の時点に引く案から進め、4 本の PR に束ねる

状態: 採用

ADR-0184 の補足。ADR-0184 の決定は変えない。ADR-0184 は「移行は段階的」とし、ルールの `message` はその段では移さないと決めた。この ADR は、その後の移行で、残りをどの順で、どの案で、何本の PR で進めるかを決めた記録。

## 状況

文面ファイルへ移していない文は、組み込みのルールの文、hook の通知と実行後の報告、Python の CLI の次の手、sh の `案内:` などに残っていた。中でも組み込みルールの文は、`policy/builtin.py`・`policy/selfguard_shell.py`・`tickets/model/ticket_guard.py`・`tickets/model/phase_forms.py` にあり、判定のたびに組み立てられる。

測った値は次のとおり。数と時間は当時の checkout のコードで数え、Linux（Python 3.13）で測った目安。

| 測ったもの | 値 |
|---|---|
| 文面ファイル | 10 本、約 87 KB、118 件 |
| 冷たい `texts.load`（プロセスで最初の 1 回） | 約 44〜52 ms。うち YAML の読みが約 33 ms、検査が約 6 ms |
| 署名の検査（`os.listdir` と 10 本の `os.stat`） | 約 27 µs |
| 温まった `texts.load` と `texts.say` | それぞれ約 30〜50 µs |
| `say` を 16 回続けた時間 | 約 0.6〜0.9 ms |
| 実行前の判定 1 回の中身（`--test`、import 後） | `Bash ls` で中央値約 90 ms、`Read` で約 66〜84 ms |
| 同じ判定の前に冷たい `texts.load` を 1 回足した場合 | `Bash ls` で約 136〜145 ms、`Read` で約 103〜109 ms（約 +20〜55 ms） |

- 時間がかかるのは冷たい読みだけ。キャッシュは `texts` のモジュールの中にあり、hook は 1 呼び出しで 1 プロセスなので、呼び出しをまたいで温まらない。組み立てで引くと、拒否に当たらない大半の呼び出しにも約 45 ms が乗る。拒否に当たった呼び出しだけがその時間を負担するのが、引く時点が判定のときの形
- 判定 1 回で組むルール 1 本ごとに `texts.say` を呼んでも、署名の検査にかかる時間は約 0.7 ms（27 µs × 24 本）にとどまる
- 上の表は、`say` が全件の `texts.load` を通っていたときの値。`say` が `texts.find` で識別子を含むファイルだけを読む形にしたあとは、冷たい 1 回でも数 ms で済む（`ls` の実行前の判定で、YAML の読みが 16 回・約 89 KB から 2 回・約 18 KB に減った）
- プロセス全体の壁時間は import が大半を占め（約 430 ms、ばらつき ±50 ms）、上の差は測定のばらつきに隠れる。差を見るには判定の中身だけを測る
- 実行前の判定 1 回（`--test Bash ls`）で作られる `Rule` は 39 本。`message` つきは 29 本で、うち `builtin:` は 24 本

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| 組み込みルールの文は、案 (a) で進める。組み込みの `Rule` に識別子（`message_id`）と値を持たせ、`spoken_message` の呼び手が判定の時点で `texts.say` で引く | 組み立てで `texts` を触らないので、通る呼び出しに読みが乗らない。当たったときだけ引く（拒否の文はいまもそうしている）。識別子で `test_texts_catalog` の対象にできる | 案 (b)・案 (c) |
| 識別子は `RULE_` で始め、種類は `deny` にする。名前は組み込みのルールの id から決める（`builtin:git-push` なら `RULE_GIT_PUSH`）。場合の分け（ラッパーの有無）は `what` の場合分けにする | `DENY_TICKET_SCOPE` の前例がある | 場合ごとに識別子を分ける |
| `message_id` と値は組み込みの `Rule`（`from_file` が偽のもの）にだけ持たせる。ルールファイルからは書けない。`rules.yml` に `message_id` を開かない | ルールの書式の版（`rules.VERSION`）、レイヤーの合成、`--lint`、`--explain` に手を入れることになる。配布先が `rules.yml` に書く 1 本ずつの文は、その場で読める自由文のほうが書きやすい | `rules.yml` に `message_id` を開く |
| `rule_lint.py` に、文の型（what／why／next／迂回しない）の検査を足さない。ADR 番号の検査も足さない。型は書き方の手引きで伝える | 自由文から型を見分けるには語を推測するしかなく、正しい 1 文（「ここは読み取り専用です」）を誤って違反にしてしまう。配布先は自分の ADR を持ってよく、番号を書くことが誤りではない | 型の検査を足す |
| 冷たい読みは、まず受け入れて出す。遅さが問題になったら、文面ファイルを必要な 1 本だけ読む形に直す。PR に測った数字を書く | `undeclared` は、ルールが言及せず ask か deny になった呼び出しのたびに文を組む。頻度は測っておらず、移すと、その呼び出しに冷たい読み約 45 ms が加わる。冷たい読みは YAML の読みが大半（約 33 ms）で、先に直すには重複した識別子の検査を全ファイルを読む前提から `--lint` へ回す必要がある | 先に必要な 1 本だけを読む形に直す |
| 既存の文を、`what` `why` `next` `no_bypass` の 4 欄に分け直す。言うことが無い欄は空にしてよい。空の欄を許すかの検査は最初の PR で `texts` に足す（`RULE_` の文に限るか、`deny` の欄全体を任意にするかもそこで決める） | いまの文は 1 段落の自由文。欄は 1 つ 600 字まで、1 件で 2000 字までなので、長い文（承認済みの置き場の約 530 字。置き場のパスで変わる）は欄に分けて収める。分け直しは文の見直しにもなる | 自由文のまま写す |
| `undeclared`・`fallen_back` は、新しい種類 `notice`（識別子の頭は `NOTICE_`）を足して移す。必須は `what`、任意は `why` `next` `note` | `nudge` に入れないのは、`nudge` の識別子は記録の `code` と同じという決まりがあり、`UNDECLARED` の見出しと `subject:` の行はコードに残るため | `nudge` に入れる |
| 実装の PR は 4 本程度にまとめる。順は、エージェントに届く頻度の高い順にする | 同じ仕組みを使う出力元を 1 本に束ねる。1 本が大きくなる分は、PR の中をコミットごとに分けて、レビューで追えるようにする。1 本目で仕組みの形が固まり、あとの PR はその形に合わせる。頻度はコードから読んだもので、記録の集計ではない | 出力元ごとに PR を分ける |

実装の PR は次の 4 本。

| 順 | PR | 中身 |
|---|---|---|
| 1 | 組み込みルールの文 | 仕組み（`Rule` の欄、`_build` の検査、`key()`、引く 3 か所、点検の拡張、空の欄を許す検査）と、`builtin.py`・`selfguard_shell.py`・`tickets/model/ticket_guard.py`・`tickets/model/phase_forms.py` の文。手引きの 1 行を含む |
| 2 | hook の通知と実行後の報告 | `notice` の種類と `undeclared`・`fallen_back`、`post.py`・`post_report.py`・`post_findings.py`、`hook/rootwrite.py`・`catalog/docsearch.py` の文。`policy/selfguard.py` の知らせは含めず、残りに置く |
| 3 | Python の CLI の次の手 | `tickets/lifecycle/commands.py`・`tickets/proposal/agree_screen.py`・`tickets/approval/checks.py` の一部・`tickets/review/request.py` の一部 |
| 4 | sh の `案内:` | `ccnavi-git.sh`・`ccnavi-worktree.sh`・`ccnavi-start.sh` など。状態を報告する `案内:` は移さない |

移さないものと、その理由は次のとおり。

| 移さないもの | なぜ |
|---|---|
| sh の `fail "…"`（約 210 件） | 失敗の理由の報告が大半で、次の一手は文ごとに違う。1 件ごとに実行ファイルを起こす（import を含めて約 0.4 秒）と失敗の経路が遅くなり、実行ファイルに不具合があるときに理由を言えなくなる。次の一手を含む `fail` が見つかったら、その `次:` の行だけを `ccnavi_text` に分けて移す |
| `internal_error_notice` | ツールの呼び出しを持たないイベントで、ccnavi 自身に不具合があるときに出る文なので、不具合があるかもしれない文面ファイルに頼らない。まれで、止めない通知でもある |
| 共有する定数の文（`PARALLEL_REQUEST_NOTE`・`EXEMPT_NOTE`・`USER_STOP_NOTE`・`TURN_DEFINED` など） | 複数の文と、下位の層が使う値だから |
| `stderr.write("ccnavi: …")` の診断 | 内部の不具合や状態の報告で、次の一手ではない |
| 配布側の sh の `次:`（`ccnavi-doctor.sh`・`ccnavi-package.sh`・`ccnavi-install.sh`） | 配布の道具で、ワークスペースの実行ファイルが無いときにも動くため、`ccnavi text` に頼らない |

## 理由

案 (a)・(b)・(c) は次のとおり比べた。

| 案 | 中身 | 利点 | 欠点 | コード量 | 性能 |
|---|---|---|---|---|---|
| (a) 識別子を持たせ、判定の時点で引く | 組み込みの `Rule` に `message_id` と値を持たせ、`spoken_message` の呼び手が `texts.say` で引く | 組み立てで `texts` を触らないので、通る呼び出しに読みが乗らない。当たったときだけ引く。識別子で `test_texts_catalog` の対象にできる | `Rule` に欄が 3 つ増える。`Rule.key()`（レイヤーをまたいだ同一判定）に入れる。`rules` が `texts` を import できない（`texts` が `rules` を import する）ので、引く関数を呼び手から渡す。呼び手 3 か所を直す | `Rule` と `_build` で約 +40 行、呼び手 3 か所で約 +20 行。組み立ての側は、文字列 24 本を `(識別子, 値)` に替えて約 −150 行。文面ファイルに 24 件ほど足す | 通る呼び出しは今と同じ。当たった呼び出しは冷たい読み約 45 ms（拒否に当たる他の文と同じで、増えない） |
| (b) 組み立ての時点で引く | `_deny`・`add_rules` などが `texts.say` を呼び、できた文字列を `message` に入れる | `Rule` を変えない。差分が最小 | 判定のたびに冷たい読みが加わる（+20〜55 ms、中身の約 1.3〜1.5 倍）。24 本の `say` で約 1 ms。文面ファイルが壊れていると、24 本すべてが既定の短い文になる | 組み立ての側の置き換えだけ（約 −150 行） | 全呼び出しに約 +20〜55 ms |
| (c) 遅れて評価する文字列 | `message` に、引くまで評価しない値を入れる | `Rule` の欄は 1 つ | `message` を文字列とみなす箇所（`rule_lint`、`entry/suggest.py`、`entry/diagnose_board.py`、`Rule.key()`）が型に合わなくなる。識別子が欄に見えず、点検が拾いにくい | 約 +60 行と、各所の分岐 | (a) と同じ |

(a) を採った決め手は性能。(b) は全呼び出しに冷たい読みを足す。(c) は (a) の欄を隠すだけで、型が合わなくなる箇所が増える。ユーザが (a) で進めると決めた。

(a) の実装に伴って決めたことは次のとおり。

- `message` が空だと `rules.parse` が「message がない」と断る（`_NEEDS_MESSAGE` の検査）。`message_id` があれば通す。`message` を直接読む `rule_lint`・`entry/suggest.py`・`entry/diagnose_board.py`・`Rule.key()` には、空のまま渡さない。`key()` は識別子と値を含め、表示と検査は識別子を引いた文を使う
- 既存の文の `{root}` は値として渡す。`{script:<名前>}` は文面ファイルの書式にそのまま使える
- 引く側は、`reasons.reason_for`・`post_report._messages`・`session_rejects` の 3 か所。`texts.say` が引けなかったときは既定の文が出て、判定は変わらない

## 得たもの・失ったもの

- 得たもの: 通る呼び出しに冷たい読みが乗らない。組み込みルールの文を、識別子で点検の対象にできる。文を 4 欄に分け直すので、型を機械で点検できる
- 失ったもの: `Rule` に欄が 3 つ増え、呼び手 3 か所を直す。分け直しは文の見直しにもなるので、レビューの負担はここがいちばん大きい
- 失ったもの: `undeclared` が出る呼び出しには、冷たい読み約 45 ms が加わる。遅さが問題になったときは、必要な 1 本だけ読む形に直す
- 残る課題: `rules.yml` の `message` は移さない。設計書の `message_id` を持たないという段と、それを決めた記録は、実装の PR で直す。決定の記録は既存のものを書き換えず、新しく 1 枚書く

## 採らなかった案

- 案 (b)（組み立ての時点で引く）: 全呼び出しに約 +20〜55 ms の冷たい読みが乗る。文面ファイルが壊れていると、24 本すべてが既定の短い文になる
- 案 (c)（遅れて評価する文字列）: `message` を文字列とみなす箇所が型に合わなくなり、識別子が欄に見えず、点検が拾いにくい
- `rules.yml` の `message` にも `message_id` を持たせる: ルールの書式の版、レイヤーの合成、`--lint`、`--explain` に手が入る
- `rule_lint.py` に文の型の検査を足す: 自由文から型を見分けるには語を推測するしかなく、正しい 1 文を誤って違反にする
- 冷たい読みを先に短くしてから移す: まず受け入れて出し、遅さが問題になってから直す
