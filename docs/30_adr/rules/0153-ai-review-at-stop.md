# ADR-0153: Stop の AI 判定（agent 型 Stop フック）を、既存の促しを変えずに足す

状態: 採用（接続部分まで実装。enable にする前の条件は「決定」の最後に書く）

## 状況

推論能力の弱いモデルでは、チケットの提案で次の取りこぼしが起きる。

- チケット作業と指示・合意されているのに、提案を書かず「作ってよいですか」と許可だけを取り直す（R1）
- 新しい親の提案（その子を含む）が、依頼に応える具体性を持たない（R2）
- 書いた提案を `propose` で送らないまま終える（R4）

Stop の既存の促し（`finish`・依頼までの道・`integrate`・ルール）は、状態だけで決まる決定的なもので、会話を読まない（transcript と最後の発言を読まないという決まりがある）。上の 3 つの取りこぼしは、会話を読まないと判定できない。LLM の API は ccnavi の実行ファイルから直接呼ばない。

## 決定

| 決めたこと | なぜ |
|---|---|
| Claude Code の agent 型 Stop フックを、command hook（ccnavi）の隣に足す。判定役は `ccnavi stop-review material` で材料を受け、`record` に結果を渡し、`record` が出力した返り値をそのまま返す | LLM を呼ぶ処理を実行ファイルに持たない。返り値を ccnavi が作るので、dry-run で止めないことと、検証に通った不備検出だけ差し戻すことを、プロンプトだけに頼らず支えられる。従わない判定役は「記録外の停止の疑い」として数える |
| command hook が既存の促しの連鎖を実行したあとで、共有キー（セッション ID と transcript 末尾のサイドチェーンでないアシスタント行の `uuid`）で判定計画と試行を 1 件書く | 促しの回数を進める副作用と、AI 判定の候補条件が食い違わないようにする。両方の hook が同じ入力から同じキーを導く |
| 既存の促しが止める Stop では、AI 判定は停止を足さない（対象外にする） | 1 回の Stop で止める理由は 1 つにする |
| 差し戻しの次の Stop（`stop_hook_active` が真）は「AI による継続」として消費し、既存の促しを `stop_hook_active` が偽のときと同じく 1 回だけ動かす。止めなければ 1 回だけ再判定し、再判定では差し戻さない | 差し戻しのせいで既存の促しが黙るのを防ぐ。差し戻しの効果（修正率）を測る。差し戻しの連鎖は最大 1 回 |
| 試行の最終分類（終了可・不備検出・未検査・対象外・検査省略）の書き手は ccnavi の 1 か所（`records/stopreview.py`） | 判定役が分類を書くと、集計が判定役の自己申告になる |
| 判定に限って、transcript の決めた範囲（今回のターンと直前 8 件のユーザ発言）を読む。決定的な促しは引き続き読まない | R1 は過去の指示と最後の発言を読まないと判定できない。材料は区切ったデータとして渡し、本文中の区切りは無害にする。プロンプトインジェクションを完全に防げるとは主張しない |
| 判定に渡した材料（提案の本文・判定定義・会話の材料）を、伏せ字にして試行ごとに保存する。保存期間は記録の保持日数とは別（既定 90 日） | 本文が後で削除・変更されても同じ材料で再評価できる。判定役には伏せ字の前の材料を渡し、保存するのは後。「prompt を記録に書かない」決まりは、この保存に限って置き換える |
| 効き方は機能ごとの `CCNAVI_STOP_REVIEW`（disable / dry-run / enable。既定 dry-run）と全体のモードを掛け合わせる。登録は `scripts/ccnavi-stop-review.sh` で行い、既定は登録なし | enable のワークスペースで、登録した瞬間に差し戻しが有効になるのを防ぐ |
| 判定役の呼び出しを他の hook から除く。見分けるのは payload の `agent_id` が `hook-agent-` で始まること（実機で確かめた）。判定役の Bash は 2 つの入口のどちらか 1 本だけを hook の許可で通す | 判定役の呼び出しが失敗の連続・範囲の読み取り・範囲の差し戻しを動かさないため。agent 型 hook の中は `dontAsk` で動き、未信頼のワークスペースでは `permissions.allow` も無視されるので、許可の規則に頼らず PreToolUse の許可で通す |
| 作業者の `stop-review` は止めて汚染の印を付ける（dry-run では印だけ）。作業者向けの文書には打ち方を載せない | 試行の横取り・偽の記録・評価の汚染・差し戻しの回避を、悪意の無い誤用から防ぐ。悪意のある作業者は完全には防げない（受け入れる脅威） |

enable にする条件: 採用基準を満たすこと、受け入れる脅威を判断し直すこと。成立性の検証は実機（Claude Code 2.1.303）で測った（`docs/21_design/stop-review.md` の「実測で確かめた前提」）。

## 理由

- 判定を決定的にできない部分（具体性・合意の有無）だけを AI に任せ、止める・止めないの決定と記録は ccnavi が持つ。
- 既存の促しの回数・記録・判定は変えない。変えるのは、差し戻しの次の Stop の 1 回だけ。

## 得たもの・失ったもの

- 得たもの: 提案の取りこぼしを、作業者と別のコンテキストで拾える。dry-run で、基準ごとの検出の精度と差し戻し後の修正率を、運用に影響を出さず測れる。
- 失ったもの:
  - すべての Stop で判定役が起動する費用と待ち時間（検証の中止条件の対象）。
  - 判定役が `record` の返り値に従わない可能性（記録外の停止の疑いとして数えるだけで、防げない）。
  - 作業者による `stop-review` の実行を完全には防げない（`material`・`record` に認証は無い。防ぐのは判定役を見分けたうえでの PreToolUse の制限だけ）。
  - 外側の層を飛ばす `CCNAVI_PROPOSE_INNER=1` や、外側だけが TERM を受けた場合は、propose の操作実績が残らない。
  - Bash 経由で書いた提案（`todo/` への書き込みが Write・Edit でないもの）は未送信として検出できない。
  - 着手済みの親への子の追加は対象外（`propose` のたびに依頼までの道の促しが止めるので、検査が届かない）。

## 採らなかった案

- ccnavi の Stop hook を包む command スクリプトが `claude -p` を順に起動する案: 見直しの筆頭候補として残す。agent 型フックの構造的なリスク（すべての Stop で起動する・判定役を見分けられない・Bash を使えない）が検証で該当したときに採る。
- agent 型フックを Stop の唯一のフックにする案: 既存の促しを別の方法で包む必要があり、挙動が変わる。
- AI 判定の最終分類を判定役が書く案: 集計が自己申告になる。
- 決定的な促しも transcript を読む案: 既存の促しの判定が会話の内容に左右される。
