# ADR-0124: 案内を使い方ごとの案内（ユースケース）に分け、見本と手順を YAML で定義する

状態: 採用（案内のある 6 画面すべてに入れた。ADR-0083 の「中身が空のときだけ見本を出す」を置き換える）

## 状況

ADR-0083 の案内は、画面ごとに 1 本の流れを TS に書き、今の設定を指して回る。ユーザは次を求めた。

- 案内の間は今の設定ではなく、案内用の見本を使う
- 初回の案内は今の量のまま、「?」でユースケースの一覧を出し、選んだユースケースごとに案内する（例: ルール管理の組み合わせ条件）
- ワークフローとフローの案内を充実させる

案内の中身（見本・手順・手順ごとの画面の様子）が画面のコードに埋まっていると、ユースケースを足すたびに TS を直すことになる。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| 「?」は案内の一覧（基本の案内 + ユースケース）を開き、選んだ 1 本だけが始まる。案内が 1 本の画面は一覧を挟まない。初回の自動の案内は基本の案内 | 初回の量を変えず、見たいときに用途から入れる | 初回を長くする |
| 案内の間は、画面が今の設定を使わず、見本を描く。画面の編集中の状態・タブ・開いた行には触れない（閉じたあとに戻すものが無い） | 設定が空でも、人の設定を見せなくても、同じ案内が回る。ADR-0083 の「全く無いときだけ見本」をやめる | 中身があるときは今の設定を指す |
| 案内と見本は `src/webview/tours/<画面>.yml` に書く（`screen` / `sample` / `courses`）。手順は `target`（`data-tour` の値）・タイトル・本文・`scene`（その手順の画面の様子）を持つ | ユースケースを YAML だけで足せる。文章を直すのに TS を読まなくてよい | TS に書く（今まで） |
| `scene` は手順ごとに全部を書き、前の手順を引き継がない。キーと値（文字列・数・真偽）は画面が決める。画面は `scene` を描くだけ | 「前へ」で戻っても同じ様子になる。手順の順序に依らない | 手順ごとに関数（`before`）で命令する |
| YAML はビルドのとき（esbuild のプラグイン）に JSON にしてバンドルへ入れる。実行時に YAML を解析しない。形は `parseTour` が確かめ、テストも同じ検査を通す | 案内のために解析器がバンドルへ入らない（フローの読み書きが元から持つボードとフローのバンドルを除く）。壊れた定義は配る前に落ちる | 実行時に解析する |
| 指す先は `data-tour="…"` の印。見た目用のクラス名や id には依らない | 見た目の直しで案内が壊れない | CSS 選択子 |
| ルールの見本は rules.yml と同じ書き方で書き、画面が持つ小さな読み取り（`core/tour-rules.ts`）で `RuleForm` にする。実際の読み取りと同じ結果になることをテストが見る。判定などは実行ファイルの JSON と同じ形で書き、既存の読み取りを通す | 見本が実際の形から外れたときに、テストで気づく | 型を直に組む |

## 得たもの・失ったもの

- 得たもの: ユースケースを YAML だけで足せる。案内の間は、人の設定を表示しない。
- 失ったもの: ビルドに YAML の変換が入る。画面ごとに `scene` を描く処理は要る（キーは画面ごと）。見本の読み取りが実際の読み取りと二重になる（ルール管理。一致はテストが見る）。
