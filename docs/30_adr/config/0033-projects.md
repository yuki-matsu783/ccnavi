# ADR-0033: 複数のリポジトリ：道具はワークスペース、設定はプロジェクト、Bash は和

状態: 採用

## 状況

道具（hook の登録、実行ファイル、保護済みスクリプト、スキル、CLAUDE.md）は public に出したくない
ワークスペースで、private のリポジトリに置く。直したいプロジェクトは別々のリポジトリで、
ワークスペースの下に clone して Claude Code に作業させる。ルールはプロジェクトごとに違い、
プロジェクトの git で育てる。

それまでの作りは、ルートが 1 つ（相対パスの解決、実行後チェック、ワークツリーの列挙がすべて
ワークスペースルート 1 か所を向く）、ルールファイルが 1 本、プロジェクトに `.claude/` を置けない
（Claude Code がそこのスキルを読み込む）、の 3 つを前提にしていて、この置き方が成り立たなかった。

## 決定

骨子は 3 つ。道具はワークスペース、設定はプロジェクト、git はツリーごと。パスを持つツールは行き先の
プロジェクトのルール、パスを持たないツールは全プロジェクトの和（ツールの分け方は ADR-0048）。プロジェクトを決めるのはユーザの承認で、判定は
その値を見ない。

- プロジェクトの置き場は `projects/` 直下の 1 段に固定する。名前がそのままツリーの名前になる
- プロジェクトのリポジトリに書くのはルール（`config/rules.yml`）だけ。提案はワークスペースルートの
  `wip/<プロジェクト>/tickets/` に置く。git のラッパースクリプトの記録も同じ向きで `logs/<プロジェクト>/` へ
  寄せる。決めた時点では未実施で `logs/` に平坦に出ていた（いまは実装済み。設計 11.2、11.8）
- ワークツリーの中に checkout されたルールファイルは読まない。読むのは元リポジトリの版
- 読めないプロジェクトのルールは組み込みの既定を使い、Bash の和からそのプロジェクトを外す
- チケットの `project:` は親が書き、子は承認で継ぐ。行き先のツリーが属するプロジェクトと、
  そのツリーに結び付く承認済みチケットの `project:` が違えば止める。**この行の前半は ADR-0038 が改めた。**
  プロジェクトは提案を置いた場所が決め、`project:` は照合に使う
- プロジェクトのルールファイルはコアファイル（ADR-0021）に加える
- フェーズの種類とリスクの配点はワークスペースに 1 本
- 拒否の文面が案内する sh のパスは `{root}/.claude/scripts/...` で書く。Bash ツールの環境に
  `CLAUDE_PROJECT_DIR` は来ない（実測済み）

## 理由

Bash を和にするのは、Bash の呼び出しがどのプロジェクトのものかを適用する仕掛け（`cwd`、`cd` の
追跡、引数の語の走査）が「どのルールファイルを引くか」の 1 点にしか役立たず、コマンドの副作用は
結局実行後チェックが拾うため。仕掛けの量と得るものが釣り合わない。適用せずに和を取れば、`deny` と
`ask` は増えるほうになり、緩むのは `allow` の共有だけになる。

置き場を 1 段に固定するのは、列挙が速いことと、何がプロジェクトかで迷わないため。
プロジェクトの中に提案と記録を書かないのは、プロジェクトが public のリポジトリで、提案と記録は
ワークスペースの運用の痕跡だから。ワークツリーのルールを読まないのは、ブランチで変えたルールが
そのブランチの判定に使われる形は、ユーザが見ていないルールで判定する形になるため。申告を見ないのは、
「プロジェクトは B」と言った値でルールを選ぶと、A に書きながら B を名乗る形が通るため。

## 得たもの・失ったもの

- 得たもの: 1 つのセッションが複数のプロジェクトを横断できる。`projects/` が無ければ前と同じに動く
- 失ったもの: allow の共有。プロジェクト A だけが許したい `npm test` はプロジェクト B に居ても通る。
  「プロジェクト A に居るときだけ止める」は書けない
- 失ったもの: ルールの読み込みがプロジェクトの数だけ増える。1 本 200 行の YAML で数 ms
- 残っているもの: git のラッパースクリプトの記録を `logs/<プロジェクト>/` へ寄せる（sh は人が直す）

## 採らなかった案

- `cwd` と `cd` の追跡、引数の語の走査でプロジェクトを適用する。上のとおり
- 2 段以上の深さやワークスペースの外にプロジェクトを置く。列挙と判定の材料が増える
- プロジェクトごとのフェーズの種類とリスクの配点。今回は入れない

## 追記（2026-10-18）

状況の「プロジェクトに `.claude/` を置けない」前提は、いまは成り立たない。プロジェクトが自前で ccnavi を導入した git リポジトリなら、プロジェクト自身の `.claude/` を持つのが通常の形である。`--lint` もプロジェクトの `.claude/` は指摘しない。決定の中身は変えない。変わるのは前提と、起動する場所ごとの挙動の読み方である。

Claude Code 2.1.303 で確かめた、起動する場所ごとの挙動は次のとおり。

- プロジェクトで起動すると、そのプロジェクトの `.claude/` のスキルと hook だけが使われ、ワークスペースの `.claude/` は使われない。`CLAUDE_PROJECT_DIR` はそのプロジェクトになる。ワークスペースの hook は動かず、ccnavi の見え方は単体 clone に近くなる
- プロジェクトのワークツリー（ワークスペースの `.claude/worktrees/<名前>`）で起動しても同じで、`CLAUDE_PROJECT_DIR` はそのワークツリー自身になる
- ワークスペースから起動した場合、プロジェクトの `.claude/skills` が読み込まれるかは、`projects/` がワークスペースの git で無視されているかで変わる。無視されている標準の構成では読み込まれない（`projects/<名前>/CLAUDE.md` は、無視されていても読まれる）。ccnavi は `projects/` を無視させるので、ワークスペースから起動してプロジェクトの `.claude/skills` に頼ることはできない。無視されていないときは読み込まれ、ワークスペースのスキルと共存する。同名のときに限り、素の名前はワークスペースのもので、プロジェクトのものは `projects/<名前>:<スキル名>` で呼ぶ。確かめたのはプロジェクトのファイルを Read した場合だけで、Write や Edit が起点の場合は確かめていない
- 「道具はワークスペース」は、ワークスペースから起動したときの話である

ワークスペース内 clone でも、プロジェクトのディレクトリで起動する形があることになる。この形の扱いは決めていない（ワークスペース内 clone と単体 clone の両方で動かす考え方は ADR-0145）。

決定の「拒否の文面が案内する sh のパスは `{root}/.claude/scripts/...`」の置き場は古い。いまの置き場は `.ccnavi/scripts/` である（ADR-0044）。

Bash ツールの環境に `CLAUDE_PROJECT_DIR` が来ないことは、今も変わらない。そのため、`CLAUDE_PROJECT_DIR` が無いターミナルや Bash ツールから、`.claude/` を持つプロジェクトの中で `ccnavi` を直接打つと、`--root` を渡さない限りそのプロジェクトが根と見なされる。`--root` を付けるか、sh のラッパーを通す。これは未解決で、洗い出しは `docs/21_design/multi-repo/standalone-clone-gaps.md` の A2 にある。
