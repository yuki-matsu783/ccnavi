# ADR-0145: ワークスペース内 clone と単体 clone の両方で動かす

状態: 採用（考え方の決定。個別の機能の振る舞いは、足すたびに決める）

## 状況

ccnavi を導入したプロジェクト（git リポジトリ）は、2 通りの形で使われる。

- ワークスペース内 clone: ワークスペースの `projects/<名前>/` に clone する。Claude Code はワークスペースで起動し、プロジェクトへは `cd` で入る。hook・実行ファイル・共通レイヤー・工程スキルはワークスペースにある
- 単体 clone: そのリポジトリだけを clone し、そこで作業する。ワークスペースは無く、プロジェクトのルートがそのまま ccnavi のルートになる

単体 clone は、設計書・要件・実行ファイルのコメントがすでに「単体 clone」「プロジェクトを単体で clone したとき」と書いている形である。

「モード A / モード B」は、README、sh のコメント、テストの docstring に出てくる呼び名で、設計書と要件には定義が無い。モード B は `projects/` の下に別リポジトリを置く形、モード A は `projects/` が無い形で、どちらもワークスペース全体の形を指す。ワークスペース内 clone は、モード B でそのプロジェクト 1 つを指す呼び方になる。単体 clone にはワークスペースが無いので、モード A でもモード B でもない。この ADR は、モード A / B を単体 clone に流用せず、混ぜない。

使い方は 2 通りに見えるが、ワークスペース内 clone でも、プロジェクトのディレクトリで Claude Code を起動することがある。その場合、ワークスペースの hook は動かず、ccnavi の見え方は単体 clone に近くなる（ADR-0033）。この ADR はその扱いを決めない。

ワークスペースにあるものを前提にした機能は、単体 clone でその前提が崩れる。これまでは機能ごとに個別に手当てしてきた。

- 共通レイヤーはワークスペースの git にあり、プロジェクトだけを clone した人の手元には無い。そこで親チケットの着手のとき、プロジェクトの `.ccnavi/config/common/` にコピー（ミラー）を置いた。単体 clone ではそのミラーを共通レイヤーとして読む（ADR-0107）
- プロジェクト向けのスキルは、ワークスペースではなくプロジェクトの git に置いた。git に入るので、プロジェクトだけを clone した人の手元にも入る（ADR-0091）。ただし、その目録を渡す hook はワークスペースにしか無い
- 共通の工程スキルはワークスペースの `.claude/skills/` にあり、単体 clone の手元には無い。そこで親チケットの着手のとき、プロジェクトの `skills/<工程>/` にコピーしている（`src/ccnavi/tickets/skillsync.py`）。コピーは git に入り、reference は `ccnavi --docs` で引ける。入口の SKILL.md を読ませる目録は、単体 clone では出ない

手当ての理由が、機能ごとの ADR や設計書に散っている。新しい機能を足す人が、単体 clone のことを考える拠りどころが無い。手当ての結果にも差があり、決めた時点の状況は下の「決めた時点の単体 clone」にまとめた。

## 決定

ワークスペース内 clone と単体 clone の、どちらでも ccnavi が動くようにする。ワークスペースにあるものに頼る機能は、単体 clone でどうなるかを、足すときに決める。結果は次の 3 つのどれかにする。

| 結果 | 意味 |
|---|---|
| 動く | 単体 clone でも同じ結果になる |
| 縮退して動く | 頼るものが無いことを検出し、決めた小さい振る舞いに落とす。黙って誤った結果を出さない |
| 動かない | 単体 clone では使えない。使えないことが分かる形で止まる |

プロジェクトの git に入るものだけで、最低限の作業が成り立つことを土台にする。

## 設計上の指針

実コードと既存の設計書で確かめたものだけを挙げる。実装が従っていない箇所は、根拠の欄に書いた。

| 指針 | 根拠 |
|---|---|
| 読み先をルートで決める。ワークスペースの中ではワークスペースルートのものだけを読み、単体 clone ではそのプロジェクトのものを読む。同じものを二重に読まない | 共通レイヤーで成り立つ。ワークスペースの中ではミラーを読まず、単体 clone ではミラーが共通レイヤー、`config/project/` が自身のレイヤーになる。どちらも「共通 + 1 レイヤー」の和になる（要件 REQ-MLT-41、設計書「複数のリポジトリ」の「共通レイヤーを配る」の節）。工程スキルは例外で、ワークスペース内 clone では目録にも `ccnavi --docs` にも二重に出る（`--docs` は 2 件に該当する）。この例外は直していない |
| ワークスペースにしか無いものは、プロジェクトの git にあるコピーで単体 clone に渡す。コピーは着手のときに、ワークスペース側の変更に追随させる | 共通レイヤーのミラーは、コピーを読む側も単体 clone で動く。工程スキルの `skills/<工程>/`（`skillsync.py`）は、コピーが git に入り reference が `ccnavi --docs` で引けるが、入口を読ませる目録が単体 clone では出ないので、入口は渡っていない |
| プロジェクトに固有の知識は、プロジェクトの git に置く | プロジェクトのスキル（`skills/<名前>/SKILL.md`。設計書「複数のリポジトリ」の「プロジェクトのスキル」の節）。git に入るが、目録は単体 clone では出ない |
| ワークスペースの有無を、git のトップから推測しない | ワークスペースルートは `.ccnavi/scripts/ccnavi-common.sh` を目印に探す。git のトップは用途が別で、ワークスペース内 clone では cwd がプロジェクトの中だと git はプロジェクトを答える（`ccnavi-common.sh` の `ccnavi_workspace` のコメント）。sh はこの指針に従う。Python の `default_root` は `CLAUDE_PROJECT_DIR` が無いとき、`.claude/` を持つ最も近い祖先を根に取るので、従っていない（未解決） |

次のことは、この ADR では決めない。

- 縮退の中身。機能ごとに、足すとき、または不都合を直すときに決める
- 個別の不都合の直し方。洗い出しは [単体 clone で不都合な処理の一覧](../../21_design/multi-repo/standalone-clone-gaps.md)

## 決めた時点の単体 clone

機能ごとに、決めた時点の実装が上の 3 つの結果のどれに該当するかを書く。縮退の中身はここでは決めない。

| 機能 | 結果 | 現状 |
|---|---|---|
| 共通レイヤーのミラー | 動く | 単体 clone ではミラーを共通レイヤーとして読み、`--lint` はルールの場所を `.ccnavi/config/common/rules.yml` にする（ADR-0107） |
| 工程スキルのコピー | 縮退。未解決 | コピーは git に入り、reference は `ccnavi --docs` で引ける。入口の SKILL.md を読ませる目録は出ない。目録の `project_of` は単体 clone を検出せず、黙って空を返す。検出していないので、上の「縮退して動く」の定義には該当しない |
| プロジェクトのスキル（`skills/`） | 縮退。未解決 | git に入るだけで、目録は出ない。理由は上と同じ |
| ルート探索（Python） | 未解決 | `CLAUDE_PROJECT_DIR` が無いと、`.claude/` を持つ最も近い祖先を根に取る。ワークスペース内のプロジェクトでは、そのプロジェクトを根と取り違える。`--root` を付けるか、sh のラッパーを通すと避けられる |

個別の不都合の一覧と重さは [単体 clone で不都合な処理の一覧](../../21_design/multi-repo/standalone-clone-gaps.md) にある。

## 得たもの・失ったもの

得たもの: 単体 clone を、例外の手当てではなく、ワークスペース内 clone と並ぶ前提として扱える。機能を足す人が、確かめる項目を持てる。

失ったもの: 新しい機能は、ワークスペースだけで動いて済ませられなくなる。ワークスペースにあるものに頼るたびに、単体 clone での扱いを決める手間が増える。

新しい機能を足すときの確認項目:

1. ワークスペースにあるもの（共通レイヤー、工程スキル、実行ファイル、`logs/`・`scratchpad/`、ほかのプロジェクト）に頼るか
2. 頼るなら、単体 clone で動く・縮退して動く・動かないのどれか。縮退と動かないは、設計書か使い方の文書に書く
3. 縮退では、頼るものが無いことを検出しているか。黙って別の結果を出さず、利用者に分かる形にしているか
4. ワークスペースにあるものをプロジェクトの git へコピーするなら、コピーを更新するのはいつか。コピーを誰も手で編集しない置き場にしているか。工程スキルの `skills/<工程>/SKILL.md` は、プロジェクト固有の `references/project/` や `skills/<名前>/` と同じディレクトリにあり、この点を満たしていない（ADR-0111 も同じディレクトリにコピーすると決めている）
5. ワークスペース内 clone で、同じものを二重に読んだり数えたりしていないか

## 採らなかった案

- ワークスペースを前提にし、単体 clone は対象外にする。プロジェクトだけを clone して作業する人は実際にいて、共通のルールが見えない状態で作業することになる
- 単体 clone を主にし、ワークスペースの機能を足し算で扱う。道具をワークスペースに集め、プロジェクトごとに重ねない構成（ADR-0033）と合わない
