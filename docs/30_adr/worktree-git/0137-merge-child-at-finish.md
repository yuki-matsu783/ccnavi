# ADR-0137: 子の成果の合流を finish で行い、状態と 1 つのマージコミットにして push する

状態: 採用（2026-10-14 に実装。ADR-0025 の「依頼の前提に子ブランチの合流を足した」点を改める。ADR-0136 の「子の finish が成功したとき、成果と状態はリモートの親ブランチにある」を満たすための決め方）

## 状況

別の PC が引き継げるのは push 済みのものだけ（ADR-0136）。それまでの `finish` は、子の完了の記録だけを親のブランチへ push し、子のコードは子のブランチに手元で残っていた。コードを親のブランチへ入れる合流は、親を閉じる前の統合のときにあとからまとめて行う前提だった。そのため、子の finish が成功しても、別の PC には子のコードが届かない。記録のない PC で次の子を始めても、前の子のコードがない。

もう 1 つ、リスクの計測と範囲の検査は、子の仕事の始まりの sha から先頭まで（`base_sha..HEAD`）を数えていた。衝突を解くために子へ親を取り込むと、ほかの子の変更まで数えてしまう。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| 合流は、メインが打つ子の `finish` が行う。サブエージェントは子のワークツリーで実装して手元でコミットするだけで、合流・状態の記録・push はしない | 成果と状態を 1 回の操作で親のブランチに載せ、成功なら push 済みにする。start・finish・cancel・push の禁止は変えない | 親を閉じる前の統合のときにまとめて合流する |
| `finish` は write-and-push の 1 操作の中で次の順に行う。(1) ロックを取り、親のワークツリーが merge / rebase の途中でないことを確かめる。(2) 取り込み。親のワークツリーに状態の置き場以外の未コミットの変更があれば止める。(3) 子のワークツリーに未コミットの変更があれば止める。(4) 差分を検査する。(5) 合流と状態の記録。(6) push。(7) 完了した子のワークツリーを片付ける | 検査から push までを 1 つにして、途中で止まったときに何も変えていない形にする | — |
| 合流は `merge --no-ff --no-commit <子のブランチ>` で入れ、完了の記録（`review/` か `done/` へ移す）と、子の承認済みチケットの `merged_sha:`（合流した子の先頭）を足して、**1 つのマージコミット**にする | 合流と状態が別のコミットになると、片方だけが push される形が残る。`--no-commit` なら状態を足してから 1 回でコミットできる | — |
| 差分の検査は、取り込み直後の親の先頭と子のブランチの共通の祖先から、子の先頭までの変更を対象にする。各パスを子・親・フェーズ定義の範囲にかける。範囲の外のパスが 1 つでもあれば合流しない | 子が自分で足した変更だけを数える。衝突を解くために子へ親を取り込んでも、ほかの子の変更が混ざらない | 子の仕事の始まりから先頭まで（`base_sha..HEAD`）を数える |
| 置き場（`.ccnavi/approved/`・`wip/proposals/`。フェーズのマーカーと記録を含む）の変更が 1 つでもあれば合流しない | 置き場はユーザの承認と ccnavi が書くもので、子のコミットで親へ持ち込ませない | — |
| サブエージェントの範囲の検査（SubagentStop）とリスクの計測も、同じ取り方（共通の祖先から）に変える | finish と検査の対象をそろえる | — |
| 衝突したら merge を取りやめ、何も変えずに止める。案内は「子のワークツリーで親のブランチを merge して衝突を解き、コミットしてから finish をやり直す」。並行していた子とぶつかったときは、先に合流した子の名前を出し、解くのは後から finish した子のワークツリーと名指しする（ADR-0190 で、名前は出さず名指しの 1 文だけにした） | 親のワークツリーで解くと、サブエージェントが書くことになり、親のワークツリーを汚す。解いた結果は子のコミットとして検査を通る | 衝突の解決を rebase にする |
| push が通らなければ、元の先頭 H0 から最終の先頭までを巻き戻す。戻すパスは `git diff --name-only H0 <コミット>` で求め、index とワークツリーの両方を戻す。シグナルでの中断も自動の再試行も同じ範囲。push の応答が失われても、リモートに届いていれば成功と扱う（確認は今の write-and-push のものを流用する） | 合流したコードも状態と一緒に戻さないと、親のワークツリーに合流だけが残る | — |
| `cancel` は合流しない。子のブランチは手元に残す | 取り消した子の成果を親へ入れない | — |
| レビューの依頼の前提は「すべての子が合流済みか」。子のブランチは見ず、`merged_sha` が親の先頭の祖先かで確かめる。Stop のときの促しも同じ確認に変える | 子のブランチは PC ごとのもので、別の PC には無い | ローカルの子のブランチが親に入っているかを見る |
| 完了（`done/`）した子のワークツリーは finish が片付ける。レビュー待ち（`review/`）の子のワークツリーは残す（そこで積んだコミットは合流しない。差し戻しは同じフェーズに子を足して直す。手元の子のブランチに合流されていないコミットがあれば、レビューの依頼の前提が止める）。片付けに失敗しても finish は成功 | 成果と状態の push が済んだあとの掃除で、失敗しても結果を変えない | — |
| サブエージェントは、親のワークツリーへの merge・commit・書き込みを禁止する。エージェントの識別と実行先のツリーで判定する検査を新設して、hook が止める。子のワークツリーでのコミットと、子のワークツリーで親を取り込むことは許す。実行先のツリーは `cd` と実行役（`env -C`・`sudo -D`）の行き先で追い、git の置き場を変える変数（`GIT_DIR`・`GIT_WORK_TREE` など）は止める（ラッパーも外す）。親か子かは、そのワークツリー自身のチケットだけで決め、曖昧なら親として扱う。書き込みは Write / Edit と、Bash のリダイレクト・`tee`・`sed -i`・`cp`/`mv` の行き先を見て、インタプリタのコードは親のパスと書き込みを疑う語が並べば止める | 親のワークツリーは正本で、書くのはメインの finish だけにする。判定は実行先のツリーで行い、子のワークツリーでの作業は止めない。居場所の追い方や役の決め方に穴があると、子の居場所に見せて親へ書ける | — |
| sh は git を動かす（`ccnavi-common-write-and-push.sh`）。実行ファイルは `ccnavi write-and-push merge <子>` で、合流してよいかの検査（`skip` / `stop` と案内 / 合流の材料）と、衝突したパスを先に合流した子から探す `merge-blame` を答える（ADR-0190 で `merge-blame` をやめた）。実行ファイルはネットワークに出ず、コミットもしない | 実行ファイルとネットワークの境界（sh が git とネットワーク、実行ファイルが判定）を保つ | — |
| origin のない親は write-and-push の対象外で、合流しない。`merged_sha` は、子の先頭がすでに親に入っているときだけ書く | push できないので、記録だけを書いても引き継げない | — |

## 得たもの・失ったもの

- 得たもの: finish が成功すれば、子のコードと状態がリモートの親ブランチにある。記録のない別の PC でも、次の子が前の子のコードを含んだ親から始まる。合流のたびに CI が走る。範囲検査とリスク計測が、衝突を解いても膨らまない
- 失ったもの: finish が重くなる（検査・merge・push・巻き戻しを 1 操作で持つ）。衝突を解くために、子のワークツリーで親を取り込んで、コミットしてから finish をやり直す手間が出る。置き場を書き換えたコミットを含む子は、合流できずコミットから取り除く必要がある。親のワークツリーに状態の置き場以外の未コミットの変更があると finish が止まる
