# ADR-0139: 受け入れた未解決スレッドは記録ファイルに持たず、ホストのスレッドに返信を残して解決する

状態: 採用（2026-10-17 に実装。ADR-0030 と ADR-0081 の、受け入れを `accepted.json` に記録して `confirm` が数えない、という点を置き換える。互換の版を 12 に上げた。手で動かした子の確定だけは、ADR-0152 が `accepted.json` を版つきの受け入れ台帳として復活させた。`decide`・`close-early` の受け入れは、この ADR のままホストのスレッドで持つ）

## 状況

ユーザが `decide` で「対応しない」「issue に回す」と選んだ未解決スレッドは、これまで親の `phases/<親>/accepted.json` にスレッドのキーを記録していた。`confirm` はそのキーのスレッドを未解決に数えなかった。これには 3 つの困りごとがあった。

- ホストの上ではスレッドが未解決のまま残る。MR を見る人（レビュアー、後から来た人）には、受け入れられたのか見落とされたのかが分からない
- 受け入れがフェーズごとに効く。受け入れたフェーズと、計画から計算した先行（`waits`）にそのフェーズを持つ番号でだけ数えず、並行した別の枝では数えた。同じスレッドを別の枝で受け入れ直すことになり、記録には番号の表（`phases`）を持たせていた
- 記録がもう 1 つの正本になる。ホストの解決状態と食い違い、記録だけが残る

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| 受け入れる指摘（`decide` の対応しない・issue に回す、`close-early` の未解決）には、スレッドに「受け入れて進む」旨の返信を残し、そのスレッドを解決済みにする。issue に回す場合は、issue の下書きを置く旨も返信に書く。返信の頭には目印 `<!-- ccnavi:accept -->` を付ける | 受け入れた事実が MR の上に残り、見た人に分かる。解決状態がホストの 1 か所になる | `accepted.json` に記録し続ける |
| `accepted.json` を廃止し、読み書きしない。親に以前の版が置いたものが残っていても読まない | 正本をホストの解決状態にそろえる。消す処理は足さない（読まれないので害が無い） | 残っているものを移行して消す |
| 受け入れは親全体に適用する。フェーズ番号と `waits` による範囲の判定（`accepted_threads` の `phase`・`owner`）をやめる | 解決済みのスレッドはホストの上でどのフェーズの `confirm` からも解決済みに見える。範囲を持つ理由が無くなる | 受け入れたフェーズとその子孫にだけ適用する（旧 9.8） |
| `confirm` などの未解決判定は、ホスト上の未解決スレッドだけを数える（機構自身の投稿を除く）。受け入れたスレッドを他の人が開き直せば、未解決として数える | 開き直しは「やはり気になる」という意思表示で、数えるのが意図に合う | 受け入れの記録でも除く |
| 返信か解決に 1 件でも失敗したら、受け入れは未完了として止める。マーカーも下書きも置かない。全部に返信してから全部を解決する順にし、解決に失敗しても返信が重なる範囲を小さくする。ホストに書き始めたあとで終わった場合は、計画を state に残してパスを言う | 受け入れを置いたのにホストが未解決のままだと、`confirm` が止まり続けるか、見えない受け入れが残る。受け入れの意味をホストの状態と一致させる | 失敗を警告にとどめて置く（コメントや issue の投稿と同じ扱い） |
| 返信と解決は sh がする。実行ファイルはネットワークに出ない（`.agents/docs/exe-boundary.md`）ので、計画（`--accept-plan <ファイル>`。受け入れるスレッドの id・キー・返信の本文）を書くだけにし、sh がホストに投稿する。置く呼び出しは、sh が済ませたあとに打つ | 境界を守る。投稿の失敗は sh が見分けて止められる | 実行ファイルがホストを呼ぶ |
| `decide` は 4 段で通る。(1) 選択とダイジェストが決まったあと、ホストに触る前にローカルで失敗しうること（write-and-push のロック・ツリーの確認）を済ませ、結果を取り直す。(2) `--yes` に `--accept-plan` を付けた呼び出しが、ダイジェストの照合・選択の検査・置く側の事前検査（続きの子を起こせるか、issue の下書きの置き場）を置くときと同じに適用し、通れば計画（受け入れるスレッドの id・キー・返信・見せたダイジェスト）だけを書く。(3) sh が計画の id を確かめて（API の経路に使える字、取り直した結果に在ること）全部に返信し、全部を解決し、結果を取り直す。(4) 置く呼び出し（`--accept-done`）が、取り直した結果で、受け入れるスレッドがホストで解決済みであることを実状態で確かめ、受け入れたスレッドを見せた指摘に数え直してダイジェストを照合してから置く。`close-early` は 1 回目（`--accept-plan`）で y/N を聞いて計画を書き、結果を取り直して 2 回目（`--accept-check`）で y/N の間に指摘が変わっていないことを確かめ、sh の返信と解決のあと、3 回目（`--accept-done`）で、計画のスレッドが解決済みでほかに未解決が無いことを確かめて置く | 置く前に済ませるため分ける。ホストに書く直前に鮮度を確かめ、書いたあとはホストの実状態で確かめるので、計画を書いてから置くまでの間に指摘が増減した場合や、解決が実際には効いていない場合に、確かめない検査で通らない | sh が置いたあとに返信し、失敗を警告にとどめる。計画のスレッドの数だけを比べる（取り直した結果とは別の古い結果を見るので、何も確かめない） |
| 返信と解決は、GitHub は GraphQL の `addPullRequestReviewThreadReply` と `resolveReviewThread`、GitLab は discussions の `POST …/discussions/<id>/notes` と `PUT …/discussions/<id>`（`resolved=true`）で行う。スレッドの id は、GitHub はレビューのスレッドの node id、GitLab は discussion の id（どちらも取得した結果が持つ） | 取得と同じ API の層に載せる | — |
| `reviewed` のマーカーの `accepted` 欄は残す。受け入れたスレッドのキーの一覧で、記録としてだけ使い、判定には使わない | 誰が何を受け入れたかをマーカーに残す。形を変えない（sh と拡張も読む） | 欄を消す |
| 互換の版（`COMPAT`・`CCNAVI_COMPAT`・`EXTENSION_COMPAT`）を上げる | sh が古い実行ファイルの知らないオプション（`--accept-plan`・`--accept-done`）を渡すようになった | 上げずにオプションの有無を見る |
| ボード（`ccnavi --explain --json`）の `accepted_threads` を廃止する | 記録が無いので出すものが無い | 空で出し続ける |

## 得たもの・失ったもの

- 受け入れた事実が MR の上に残り、解決状態の正本がホスト 1 つになった。フェーズごとの範囲判定と番号の表が無くなった
- 受け入れに返信と解決の通信が要る。ホストに届かないと受け入れられない（今は MR を読むのにも要るので新しい前提ではない）
- 受け入れたスレッドを他の人が開き直すと、また止まる。意図どおりだが、記録だけを根拠に通っていた親は通らなくなる
- 実行ファイルを直に打つターミナルの対話（`--reviewed N --accept-unresolved` に選択を渡す形）は、sh を通らないので、返信と解決をしない。sh の `decide` が通常の入口で、この形はテストと診断のために残る
- 返信と解決を書いたあとで置けずに終わると（write-and-push の push の失敗など）、解決済みのスレッドだけが残る。打ち直すと、そのスレッドは見せる指摘から外れ、`issue に回す` の下書きと `accepted` 欄の件数に入らない。置く側の失敗は、ホストに触る前に確かめられるもの（ロック・ツリー・続きの子・issue の下書きの置き場）を先に済ませ、ホストに書いたあとはダイジェストの照合と実状態の確認が済んだ結果だけを置くので、起こりにくくした。それでも残る穴は、sh が計画（id・キー・返信）を state に残してパスを言うところまでで止めた。計画を読み戻して、打ち直しの見せる指摘と選択に混ぜる案は入れていない（混ぜるには選択を保存して照合する仕組みが要り、受け入れた事実はスレッドの返信として MR に残っているため）
- 全部に返信してから全部を解決する順だが、返信まで済んで解決できなかったスレッドを打ち直すと、返信が重なる（重複を避ける処理は入れていない）
- 確かめていない: 自分の保留中（pending）のレビューに属するスレッドへの返信は、公開されるまで他の人に見えない（GitHub の仕様。保留中のレビューを持つトークンで受け入れた場合の挙動は確かめていない）
- 守らない: 同じ親・同じフェーズで `decide` を同時に打つ場合の排他。ボードとターミナルで同時に押すと、両方がホストに返信する（write-and-push のロックは置く側にしか掛からない）。置く側は片方がダイジェストの照合で止まる
