# ADR-0123: 親は計画を必ず持ち、計画の無い親は start が止まる

状態: 採用（ADR-0026 の「計画の無い親は今までどおり番号だけで動く。`phases.yml` も要らない」を置き換える）

## 状況

計画（`plan:`）を持たない親は、フェーズが番号だけの挙動で動いた（編集できる範囲や成果物、レビューの要否を決める定義を使わない）。
これには 2 つの困りごとがあった。

- 子の提案があっても、計画の無い親は `start` を通る。レビューを要る定義が使われないので、フェーズごとのレビューが働かない
- 計画も子も無い親は、設計上は正当でないとされ、`--lint` が警告するだけだった。警告が出ても `start` は通り、作業に入れる

計画のある親でも、子のないフェーズが残ったまま作業に入れる。親を閉じる `finish` は、終わっていないフェーズがあると止めるので、全部を親でやっても閉じられない。ただし、止まるのが `finish` と遅い。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| 計画の無い親は、子や子の提案があっても `start` が止まる。案内は「`phases.yml` に最小の定義（例: `work` を 1 つ）を書き、親に `plan:` を足す。書くのはユーザ」 | 計画の無い親では、フェーズの定義による範囲とレビューが効かない。定義はユーザが持つ設定なので、エージェントは書かない | 警告のまま通す。レビューを回避する抜け道が残る |
| 承認済みで着手前の計画の無い親には、停止の案内に、改版で計画を足してユーザが承認し直す手順を添える | 承認済みの親は動かさない原則の例外は改版だけ。直す道を示さないと止まったまま動けない | 案内を出さない。止まる理由だけで終わる |
| 計画のある親で、子のないフェーズが残るときは、`start` の成功時に案内を出す（止めない）。案内は、フェーズごとに子チケットを作ることと、子のないまま進めても `finish` で止まること。子は承認済み（`doing/`・`review/`・`done/`）と `todo/` の提案の両方で数える | 子の `start` は親が着手済みであることを条件にする（`parent_not_started`）。親の `start` を「子が無ければ止める」にすると、子を始められなくなる。止めるのは危険や失敗の検知時、という方針にも合う | 子が無ければ `start` を止める。deadlock になる。`--phase N` で子の作成から承認、着手までを自動にする。承認をスクリプトが代わりにやることになる |
| `--lint` の「計画も子も無い親」の warn は、「計画の無い親は `ticket start` が止まる」という文面に変えて、子のある親にも出す | `start` が止まる理由を、先に lint で知らせる | warn を外す。止まる理由を事前に知らせられない |

## 得たもの・失ったもの

- 得たもの: 親が必ず計画を持ち、フェーズごとの定義（範囲・成果物・レビュー）が効く。計画の無い親で作業に入る抜け道がなくなる
- 失ったもの: `phases.yml` を置かないプロジェクトでは、親チケットを `start` できない。最小の定義を 1 つ書く手間が要る。計画の無い親と子で動いていた承認済みで着手前の親は、改版で計画を足すまで着手できない（着手済みの親は変わらない）

## 採らなかった案

- 計画の無い親を、番号だけの親子として許し続ける: レビューが効かない親が残る
- 親に自由な形式の計画を書けるようにする: 計画のステップは定義の名前を指し、定義がレビューの要否や範囲を決める。自由なステップを許すと、エージェントがレビューを省く定義を作れてしまう
