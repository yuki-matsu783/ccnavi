# ADR-0236: decide のホストへの書き込みの順を Go の 1 つの関数が決め、ターミナルも Chrome も issue を先に書く

状態: 採用

## 状況

decide がホストへ書く順は 2 系統で違った。ターミナル（sh）は、返信と解決を置く前に済ませ、置いたあとに issue と決めた内容のコメントを書いた（ADR-0139・ADR-0151）。Chrome 拡張（TS）は、issue、返信、解決、親のブランチへのコミット、コメントの順だった（ADR-0172）。同じ判断を 2 つの言語で書いていたので、順の直しが片方に届かなかった。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| 順を Go の `host.WriteOrder` 1 つに置く。issue（と続きのコメント）、返信、解決、（親のブランチへのコミット）、決めた内容のコメント。sh は操作記録の段階（`decide.stageSpecs`）として、拡張は `host_plan.steps` として、その並びのとおりに送る | 順の決まりを 1 か所にする。実行ファイルはネットワークに出ないので、送るのは sh と拡張の service worker のまま | 順を両方に書いて、試験で一致を見る |
| 順は issue 先にする（Chrome の側に合わせる） | 解決したのに issue が無い状態を作らない。止まっても MR の画面に issue が残る。ターミナルは操作記録があるので、返信の前に issue の段階を送れる。Chrome は操作記録が無いので、issue を後にすると、解決後の失敗で選択が誰にも見えず消える | ターミナルの順に合わせる（Chrome では issue が消えうる） |
| 返信の本文に、作った issue の URL を書く（枠 `host.IssueURLSlot`。ターミナルは `accept threads` が置き換える） | issue を先に作るので、返信を書く時に URL が決まっている。「issue の下書きを置く」より、読み手が辿れる | 下書きを置く旨だけを書く |
| issue を作れなければ、返信も解決もせず、何も置かずに止まる | 解決したのに issue が無い状態を作らない。打ち直しか `--resume` で、送り済みの段階は繰り返さない | issue の失敗を警告にとどめて先へ進む |

`close-early` は残りを 1 つの issue にまとめて置いたあとに書くので、順は変えない（返信は「下書きを置く」旨のまま）。

## 得たもの・失ったもの

- 得たもの: 順の決まりが 1 か所になり、2 系統が同じ順になる。ターミナルでも、解決したのに issue が無い状態が起きない。
- 失ったもの: ターミナルは、置けずに終わったとき、issue だけが先にホストに残りうる（操作記録から `--resume` で続きを送れる）。
