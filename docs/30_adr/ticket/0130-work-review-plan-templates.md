# ADR-0130: 完了した作業・レビュー計画と子のフローをテンプレートとして溜め、下書きから取り込んで再利用する

状態: 採用（単位・蓄積の契機・置き場の層・入口の 4 点をユーザが推奨案で決めた。段階 1〜5 を実装した。保護済みの sh（`ccnavi-push-approved.sh`・`ccnavi-setup.sh`）の変更は、ユーザの許可を得て直接反映した。ボードのテンプレート管理画面も作った。画面が決めた取り込みの経路と入口は「実装で足した判断」の表。取り込み・編集の手順は ADR-0144 が置き換えた）

## 状況

今回使った計画と子のフローを、次回以降の作業で使い回したい。いまは完了した親の計画（`plan:` / `feedback:` のステップと `after`）も子のフローも、その親の中に閉じている。親が `ready` で閉じると、`wip/` は消え、`done/` と `flows/` は手元の `logs/archive/`（git 管理外）へ退避される。同じ形の作業をもう一度するときは、ユーザかエージェントが一から書き直す。

要求。

- 完了した作業から、再利用できる形を溜められる
- 次の作業を始めるとき、候補として見つけて、計画とフローの下書きを作れる
- 判定を緩めない。使った計画も通常の承認を通り、承認の検査（循環・終端が 1 つ・種類の `kind`）を受ける

制約。

- フローの文はサブエージェントへの案内文になり、プロンプトインジェクションの経路になる。効力のある側（取り込んだもの）にエージェントは書けない（ADR-0100）
- `.ccnavi/` 配下は組み込みの保護で書き込みが止まる。共通の設定は、ユーザが持つ設定として扱う
- フェーズの種類（`phases.yml`）は共通とプロジェクトの足し算で、定義は変わりうる（ADR-0125）

調べて分かったこと（コードを読んで確かめた）。

- 計画の検査は `ticket.parse` → `phasetypes.copy_problems` / `agree_candidates.plan_problems` / `workflow.problems`、フローの検査は `flow.load` と `lint.flow_problems` で、どちらもメモリ上のデータに対して使える
- `wip/proposals/` は丸ごと範囲外で、`wip/proposals/templates/` は判定のコードを変えずに書ける
- `--docs` の索引は md の frontmatter だけを対象にするので、yml のテンプレートは載らない
- テンプレートの保存・読み込み・適用に該当する既存のコードは無い。計画のステップの相対番号への正規化も新規

## 決定

「テンプレート」は、**1 つの親の作業・レビュー計画（全体計画 `plan:` とフィードバック計画 `feedback:` のステップと `after`）と、各子のフローの本文を 1 ファイルにまとめたもの**と呼ぶ。

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| 単位は計画とフローの一式を 1 ファイル（`<名前>.yml`）にする。欄は `name`・`description`・`when`（選ぶ手がかり）・`plan`・`feedback`・`flows` | 1 回の流れを丸ごと使い回せる。1 ファイルなら取り込み・差分・削除が 1 つで済む | 子のフロー単体（計画の形が使い回せない）。計画の形だけ（フローの文が使い回せない） |
| `plan` / `feedback` のステップは `type`・`review`・`after` を持つ。`after` は**その計画の中の添字（1 始まり）**で書く。フィードバック計画の `after` も、フィードバック計画の中の添字にする | 提案ではフィードバック計画の番号が全体計画の続きになり、使い回すと番号がずれる。相対にしておけば、適用時に付け直せる | 提案と同じ絶対番号で持つ |
| `flows` は、ステップの添字（全体計画の n 番目）をキーに、フローの本文を持つ | どの子のフローかを、識別子ではなく計画の位置で指す。識別子は使うたびに変わる | 識別子で指す |
| 置き場は 2 層。共通は `.ccnavi/config/common/templates/<名前>.yml`、プロジェクトは `.ccnavi/config/project/templates/<名前>.yml`。共通は設定の共通レイヤーと同じ仕組みでプロジェクトの common へミラーする | 設定の足し算と同じ置き方に揃える。共通は配布先にも届く | 1 層だけ（配布先で使えない／ワークスペース固有の雛形を置けない） |
| 同名が共通とプロジェクトに在り、中身が違えば、そのプロジェクト側を使わずに error にする（全欄同じなら info でプロジェクト側を破棄する） | 種類の定義の衝突の扱い（ADR-0125）に揃える。どちらが効くかを黙って決めない | プロジェクトを優先して上書き |
| エージェントは**下書きだけ**を `wip/proposals/templates/<名前>.yml` に書ける。下書きには効力が無い。使うのは取り込んだ側だけ | ADR-0100 と同じ。下書きの置き場は範囲外で、判定を変えずに書ける。害は余計な提案が 1 つ出る程度に収まる | `.ccnavi/` に直接書かせる（組み込みの保護に例外を作る） |
| 取り込みはユーザが `ccnavi --templates --import <下書き> --to common\|project` で行う。取り込み前に、下書きを検査して、いまのテンプレートとの差分を文の前後まで見せる。エージェントは打てない（`phase_forms._CLI_FORMS` に足す） | 歯止めは、ユーザが差分を読むこと。フローの文は案内文になるので、欄の名前だけの差分では足りない | エージェントも取り込める |
| 下書きの作成は `ccnavi --templates --draft <親>` で機械的に行う。完了した親の `done/` から `plan:` / `feedback:` を取り、`flows/` からフローをコピーして、`wip/proposals/templates/<名前>.yml` に書く。固有名の置き換えと不要な手順の削除は、そのあとエージェントが下書きを直して行う | 抽出は決まった変換で、毎回同じ結果になる。一般化は文の判断なので、エージェントに任せる。エージェントが打ってよい（効力が無い） | エージェントが全部書く（計画のコピーミスが起きる） |
| 蓄積の契機は、親の `finish`（親が閉じる出力）で、テンプレート化の案内を 1 行出すこと。`ready` の前に出す | `ready` で `wip/` が消え、承認済みの `done/` と `flows/` は手元の退避に移る。そこから先は拾いにくい | Stop の促しで毎ターン出す（完了の事実が見えない） |
| 見つけるのは `ccnavi --templates`（一覧）と `--templates --keyword <語>`（`name`・`description`・`when` の検索）、`--show <名前>`（中身）。`--docs` の索引には載せない | `--docs` は md の frontmatter だけが対象で、yml を載せるには索引の拡張が要る。テンプレートは別の入口で足りる | `--docs` の索引を yml に広げる |
| 使うときは `ccnavi ticket new <識別子> --title <タイトル> --template <名前>`（足場の作成。`ccnavi-ticket.sh` は `new` を通さず、実行ファイルを直接打つ）で、親の提案（`todo/`）に `plan:` / `feedback:` を書き、フローを `wip/proposals/flows/<子>.yml` に下書きとして置く。提案は通常の承認を通る | 判定を緩めない。フローは下書きなので、ユーザがフロー編集画面で取り込むまで効力が無い（ADR-0100） | 承認を飛ばして子を作る |
| `--lint` がテンプレートを検査する。計画（`type` が定義に在るか、`kind` が置き場と合うか、循環・終端・延期の引き受け手）とフロー（`lint.flow_problems`）。定義が変わって食い違うのは warn にとどめる | 承認後は親のコピーだけを読む原則（`phases.yml` を直しても進行中の親は止めない）に合わせる。使うときの承認で error にする | 定義が変わったら error |
| 判定・組み込みの保護・`rules.yml` は変えない | 下書きの置き場は範囲外、取り込み先は `.ccnavi/` 配下で既に保護される | 判定を足す |
| 最初の版にパラメータの差し込みは入れない。固有名は下書きの段で一般化し、使うときは下書きの文を直す | パラメータを増やすと、テンプレートが小さなプログラムになる | `params:` を持たせて差し込む |
| ボードの画面は最初の版に入れない。ただし最終的にはボードに**テンプレート管理画面**（ルール管理・リスク管理・フェーズ管理と同じ並び）を足す前提で、実行ファイル側の答えを作る | 実行ファイル側の検査・取り込みを先に確かめる。拡張は判定を自分で出さず実行ファイルの JSON を読んで描くので、`--templates --json` を画面がそのまま描ける形（層ごとの生の中身、効いているもの、内容のハッシュ、構造化した検査の結果、衝突で破棄した理由、書き込めるか）にしておけば、画面は読むだけの一覧から足せる。保存・取り込み・削除は、読み込んだモデルを書き戻せる形（読んで書くと中身が変わらない）で作る | 画面から始める。文字列だけの答えにして、画面のときに作り直す |

### 段階

1. **読む側**: テンプレートの読み込み（2 層の足し算と衝突）、検査、`--templates` の一覧・検索・`--show`、`--lint` への組み込み
2. **溜める側**: `--templates --draft`、`--templates --import`、下書きの置き場、取り込みで消した下書きのコミット（`ccnavi-push-approved.sh`）
3. **使う側**: `ccnavi ticket new --template`
4. **案内と配布**: 親の `finish` の案内、共通レイヤーのミラー（`configsync`）と導入 sh（`ccnavi-setup.sh`）への配布の追記
5. **文書と画面**: 設計書・README・`.ccnavi/docs/`。ボードの画面は別に決める

`ccnavi-push-approved.sh`・`ccnavi-setup.sh`・`.ccnavi/scripts/` の sh は保護済みで、エージェントは書けない。通常は完成品を `wip/design/scripts/` に全文で置き、ユーザがコピーする。今回（段階 2 と 4）はユーザが直接直す許可を出した。

## 得たもの・失ったもの

- 得たもの: 完了した作業の形を、承認を緩めずに溜めて使い回せる。溜める手間は下書きの一般化とユーザの取り込みだけで、使う側は通常の承認を通る
- 失ったもの: 取り込みと配布のために、実行ファイルのフラグと、保護済みの sh の追記が増える。テンプレートが古くなる（種類の定義が変わる）と、使うときの承認で初めて error になる。最初の版はパラメータを持たないので、使うたびに文の固有名を手で直す

## 実装で足した判断

実装の途中で決めたこと。決定の表の延長で、表の決定とは食い違わない。

| 決めたこと | なぜ |
|---|---|
| `--templates` に `--show <名前>`・`--layer <名>`（足し算の相手のレイヤー。既定は自身）・`--keyword` を足した | プロジェクトが複数あり、層ごとの足し算を選べないと一覧も画面も描けない |
| テンプレートの `name` はファイル名（拡張子を除く）と一致させる。`description` は必須 | 取り込みと検索で名前を 1 つに決める。一覧に出す |
| 下書きの名前は既定で親の識別子。`--name` で変えられる。名前に使えない識別子（日本語など）は `--name` を求めて断る | 下書きの名前の付け方を機械的に決める。同名の下書きは上書きしない |
| 取り込みは `--yes` に `--expect <下書きのハッシュ>` を必ず添える。見せた下書きと違う中身は書かない。`--yes` は `--templates --import` だけが値なしで読む | 差分を読んだ下書きだけを書く。承認の `--yes` の経路は変えない |
| 同名の改訂は `--replace`。共通とレイヤーに中身の違う同名を作る取り込みは断る | 足し算がレイヤー側を使わない error にするため、取り込みの時点で止める |
| 取り込みのプレビューは、制御文字・書式文字（右から左への上書きや幅ゼロの文字）を `\uXXXX` に直して見せる。さらに、そうした文字（改行とタブを除く Cc、Cf、Zl、Zp）を含む下書きは検査が error にして取り込めない | 歯止めはユーザが差分を読むこと。読み違えを誘う文字を隠さない。ターミナルに出る生の文字で文を隠せるので、見せ方だけに頼らず取り込み自体を止める |
| `--import` を `--yes` で書くときは、hook の止めに加えて、実行時に標準入力がターミナルかを確かめる（下見は求めない）。「ターミナルを求めない」の判断は取り下げる | hook の止めは文字列の照合で、すり抜ける書き方がある。ターミナルの確認を 2 段目に置く。ボードから呼ぶ入口は、次の行で決めた |
| ボードのテンプレート管理画面から呼ぶ入口は、承認（`--agree --yes <識別子> --digest <ダイジェスト>`）と同じ水準のガードにする: hook の止め（`_CLI_FORMS`）と、見せた内容との一致（`--expect`）。画面を作るときに、ターミナルの確認をこの経路だけ免除する（ユーザが決めた）。それまでは、ターミナルの確認が残る | 承認の経路は、ターミナルを持たない拡張の子プロセスから呼ぶために、ターミナルの確認を内容の一致と hook の止めに置き換えた。取り込みも同じ使い勝手（画面の中で差分を読んで押す）を得るために、同じ水準にそろえる。画面ができるまでは、使い勝手の需要が無いので、強い側の確認を残す |
| 下書きの `description` と `when` の両方に `TODO` の印を付け、残っていれば warn にする。下書きは未追跡のファイルで親の `ready` を止めるので、取り込むか `ready` の前に消す | 固有名の一般化が済んでいない下書きを取り込む前に気づかせる |
| 子のフローの下書きは、全体計画の n 番目のステップの最初の子 `<親>-<NN>-01` の名前で置く。フィードバック計画の子のフローはコピーしない | 承認前は子の識別子が決まらないので、最初の子と仮定する。`flows` は全体計画の添字で指す |
| `ticket new --template` は、フィードバック計画を既定では書かず、`--with-feedback` があるときだけ書く | フィードバック計画は全体計画の最後のレビューを見て改版で 1 回だけ足す決まり。最初の提案に入れると、承認後に全体計画を改版できなくなる |
| `ticket new --template` の入口は実行ファイル（`ccnavi ticket new`）で、`ccnavi-ticket.sh` は通さない | `ccnavi-ticket.sh` は `new` を元から通さない |
| 親の finish の案内は、計画を持ち、下書きが無く、同じ計画の形（`type`・`review`・`after`）のテンプレートが無いときだけ出す。マージリクエストで見るフェーズの無い親（`ready` が無い）には出さない | 同じ案内を繰り返さない。案内の文面が合うのは `ready` で閉じる親だけ |
| 共通テンプレートのミラーは、error のあるテンプレートを 1 本ずつ飛ばして着手は止めない。置き場そのものが読めない（リンクなど）ときも、テンプレートだけコピーせず着手は止めない | 使えないテンプレートのために作業を止めない。`--lint` が error で知らせる |
| 導入 sh と `ccnavi-push-approved.sh` の変更は、保護済みなので通常は `wip/design/scripts/` にステージし、ユーザがコピーする。今回はユーザが直接直す許可を出し、反映した | 保護済みの sh はエージェントが書けない |
| `--templates --import --yes` をテンプレート管理画面が呼ぶ経路は `--via board` を付ける。この経路だけターミナルの確認を免除し、止めるのは hook の止め（`_CLI_FORMS`）と見せた下書きとの一致（`--expect`）になる。`--via board` は `--import --yes --expect <ハッシュ> --json` と一緒に使うときだけ通る。下見の差分と本文は、実行ファイルが制御文字・書式文字を `\uXXXX` に直して返す。画面は、テンプレートの本文を見る欄で同じ置き換えをする（書く中身は変えない）。取り込みは作業中のチケットで止める（共通とワークスペースの設定はどのツリーの作業中でも、プロジェクトの設定はそのプロジェクトの作業中だけ）。チケット制御が disable なら画面は開かない。ボードのカードからの入口は作らない（親のカードから下書きを作る入口は、後に別の ADR（0133）が足した） | 承認と同じ水準のガードで、画面から押す取り込みを成り立たせるため。拡張はターミナルを持たない子プロセスから呼ぶので、ターミナルの確認は通らない。実行ファイルのボード JSON に「この親から下書きを作れる」欄が無いので、カードから入口を出せない |
| 取り込みの `--yes` は、hook の 2 段目 `human_path_form` の組（`--templates` と `--import` と `--yes`）でも止める。launcher の書き方に依らない | 承認と同じ水準にそろえる。launcher の正規表現だけでは、`python3 -u -m ccnavi` のような少し崩した書き方で、ターミナルの確認を免除した経路をエージェントが打てた |

## 設計の限界

エージェントに「人しかできない操作」を打たせない仕組みは、hook の文字列の照合を土台にしている。取り込み（`--import --yes`）も、承認（`--agree --yes`）と同じ水準のガードで足りるとユーザが決めた。

- 防げるもの: コマンドを素直に、またはよくある書き方で打つ形。見せたあとに下書きが差し替わる形（`--expect`）
- 防ぎきれないもの: 複雑な操作による迂回。例: launcher の正規表現が見ない書き方（`python` と `-m` の間や `uv run` と `python` の間にオプションを挟む、`env` を前置する）、Write で作った sh の中に書く形、`python -c` から呼ぶ形。`--agree`・`--reviewed`・`--close-early` にも効く前からの穴で、ここでは直さない
- 扱い: これらは設計の限界として受け入れる。ガードは、エージェントのうっかりと素直な試みを止めるもので、悪意をもって組んだ迂回を完全に止めるものではない。穴ごとに regex を足し続けない。足すなら、承認と取り込みの両方に効く形で、別に決める
- 残る歯止め: 効力のある側（`.ccnavi/` の下のテンプレート）へは、Write・Edit と Bash の書き込みが組み込みの保護で止まる。効力は取り込んだものだけに生じ、子への案内文に載るのは承認済みの `flows/` だけ

## まだ決めていないこと

- 使った結果の採否の記録（wiki 層に溜める情報と混ぜない）
- `feedback: []`（対応なしと確認済み）と `feedback` 無し（未計画）をテンプレートで区別するか。いまは区別せず、どちらも欄を書かない
