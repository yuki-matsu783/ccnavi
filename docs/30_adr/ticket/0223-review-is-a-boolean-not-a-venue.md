# ADR-0223: フェーズのレビューの要否は、場所を表す none / mr でなく真偽値 true / false で書く

状態: 採用

## 状況

フェーズ定義（`phases.yml`）の `review` は `none` か `mr` を取り、「フェーズの終わりにユーザがどこで見るか」を表していた。
計画のステップにも `review` があり、`mr`（定義が `none` でも要る）と `defer`（延期）を書けた。
ボードの JSON は、判定の結果を `review_kind`（`none` / `mr`）と `review_required`（真偽値）の 2 つで出していた。

全ての親がマージリクエストを持つことになった（ADR-0215）ので、`mr` 以外の見る場所は無い。
名前は「場所」を表すのに、実態は「レビューが要るか要らないか」の 1 ビットだけになった。
名前と中身が食い違うと、読み手は他にも場所があると考え、`none` < `mr` のような強さの順序や、厳しい側を採る関数（`stricter`）を探す。
`review_kind` は `review_required` から一意に決まるので、同じ事実を 2 つの欄で持っていた。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| フェーズ定義の `review` は真偽値（`true` / `false`）。既定は `true`。`true` はレビューが要る、`false` は要らない | 中身が 1 ビットなので、型もそのままにする。名前（`review`）はそのまま使える | `review: required\|skip` のような別の語。値の語が増えるだけで、真偽値より単純にならない |
| 計画のステップの `review` は `true` だけを書ける（定義が `false` でも要るにする）。`false` は書けない | 定義と同じ語・同じ型に揃える。弱める向きを書けない決まりは変えない | ステップの `mr` を残す案。定義と別の語が残る |
| 計画のステップの延期は、`review: defer` から `deferred: true` に分ける。`review: true` と同時には書けない | `review` を真偽値にすると、延期（後ろのフェーズと一緒に見る）を同じ欄の文字列で書けない。ボードの JSON と内部の名前（`deferred`）が既に `deferred` なので、書く側も合わせる | `review` に `true` と `"defer"` の両方を許す案。型が混ざり、読み込みも画面も分岐が増える |
| 複数の者が言う要否は「1 つでも要ると言えば要る」で決める。厳しい側を採る関数（`stricter`）と強さの順序は無くす | 真偽値の「厳しい側」は論理和そのもの | 順序の表を残す案。2 値の順序表は何も決めていない |
| ボードの JSON から `review_kind` をなくす。`review_required` が同じ事実を言う。フェーズ定義の `review`、計画のステップの `review` は真偽値で出す（定義が読めないステップは `null`） | 同じ事実を 2 つの欄で出さない | `review_kind` を真偽値にして残す案。`review_required` と同じ値の欄が残る |
| `review` に真偽値でない値（以前の `none`・`mr` を含む）が書かれていたら、読み込みで「`review` は true か false で書く」と言って止める。`--lint` も同じ関数が言う | 後方互換は考えない。別名や以前の形を読む処理は作らず、状態と直し方を言って止める | `none` / `mr` を読み替える案。移行用の分岐が残る |
| 親が固定したコピー（`phases:`）、マーカー（`pending` の `review`）、閉じた記録（`closed.json` の `reviews`）、テンプレートの JSON も同じ真偽値にする | 同じ意味の値を場所ごとに別の形で持たない | 画面に出る JSON だけ真偽値にして、保存する側は文字列のまま残す案 |
| 要件書・設計書・案内（ツアー）・VS Code 拡張の定義の編集画面（選択肢は `true` / `false`）と計画のテンプレートの編集画面（定義のまま / `review: true` / `deferred: true`）を同じ変更で置き換える | リポジトリ内の以前の書き方を残さない | 画面だけ後で直す案 |

## 理由

- 名前が表す範囲（場所）と実際に持つ情報（要否）を一致させる。値の語を見れば何を決めているか分かる
- 判定の関数が単純になる（順序の表と厳しい側を採る関数が、論理和になる）
- 同じ事実を表す欄（`review_kind` と `review_required`）を 1 つにする

## 得たもの・失ったもの

- 得たもの: 値の意味が名前と一致する。強さの順序と `stricter` が要らなくなる。ボードの JSON の欄が 1 つ減る
- 失ったもの: 共通設定を同期している各プロジェクトの `phases.yml`（共通レイヤーと `config/project/`）、承認済みの親が固定したコピー（`phases:`）、書きかけの計画のステップの `review: mr` / `review: defer` は、書き換えが要る。以前の値は読み込みで止まり、直し方を言う。`review: none` は `false`、`review: mr` は `true`、ステップの `review: defer` は `deferred: true` に直す
- 失ったもの: 将来、マージリクエスト以外の見る場所（このセッションで見る、など）を足すときは、真偽値では書けない。そのときは新しい決定で形を選び直す
- 失ったもの: 以前の形で書かれた拡張（VS Code・Chrome）の古い版は、新しい実行ファイルの JSON を読めない。拡張は同じ変更で置き換えてあるので、実行ファイルと拡張は組で更新する
