# ADR-0222: 以前の形式を読む処理を消す（can_issue 欄・拡張の欄の読み分け・decide.sh の直接投稿）

状態: 採用

## 状況

名前・形式を変えるときは別名や以前の形式を読む処理を作らず、リポジトリ内を置き換える決まりがある。それでも、次の 3 種類の処理が残っていた。

- `decide` の JSON・ダイジェスト・計画にある `can_issue` 欄。値は常に真で、「JSON の欄は互換のために残す」としていた。拡張もこの欄を読んでいた
- VS Code 拡張のボード JSON の読み取りにある、欄の無い実行ファイルの答えを読み分ける処理（`in_progress` の null、`lock_kind` の undefined、`archived`・`turns` の任意扱い、閉じた子の `flow` を拡張側で null にする念押しなど）。実行ファイルは、これらの欄を今は必ず出す
- `ccnavi-user-decide.sh` の `post_decision` にある、操作 ID の無い計画のときの直接投稿（issue の作成とコメントを直接送る）。現行の実行ファイルは計画に必ず操作 ID を書くので、本番では届かない。ただし試験の実行ファイルの代役が操作 ID の無い計画を書き、この経路を通っていた。ADR-0218 の「採らなかった案」に、残すものとして挙げていた

互換の版の約束（要件書の REQ-EXT-05）は、互換の版が合わない組み合わせを止める約束で、欄の無い実行ファイルの答えを読み分ける約束ではない。要件書を直す必要は無かった。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| `can_issue` を出力 JSON・ダイジェスト・計画・拡張の型と読み取りから全部消す。issue はいつでも選べるので、欄に意味が無い | 常に真の欄は読み手に判断を渡さない | 欄を残す |
| 拡張は、実行ファイルが今必ず出す欄（`in_progress`・`lock_kind`・`archived`・`turns`、閉じた子の `flow` の null）を「無いかもしれない」として読まない。型は必須にし、欄の有無で読み分ける分岐と試験を消す。読み取りの既定値（`in_progress` の欠けを偽、`archived`・`turns` の欠けを空とする）は、壊れた JSON への備えとして残す。`lock_kind` は null が正当な値なので `| null` のまま | 実行ファイルと拡張は同時に配る前提で組になる | 欄の有無で読み分ける |
| `post_decision` の直接投稿を消す。計画に操作 ID が無ければ `op_use_plan` が、状態（操作 ID が無く、何も送らなかった）と直し方（ccnavi を更新して打ち直す）を言って止める | まれな異常状態のために、投稿経路を 2 本持たない | 直接投稿を残す |
| 試験の実行ファイルの代役は、本物の `ccnavi ops` に渡し、操作 ID つきの計画を書く（`tests/sh/decide_support.py`）。`test_review_decide`・`test_decide_ops`・`test_decide_recovery` が共有する | 試験が本番に無い経路を通らないようにする | 代役に操作 ID を足すだけにする |

## 理由

どの処理も、現行の実行ファイルでは使われない。残すと、同じ意味の経路が 2 本になり、直すたびに両方を見ることになる。

## 得たもの・失ったもの

- 得たもの: 投稿の経路が 1 本になる。拡張の型が実行ファイルの出力と一致し、null・undefined の分岐が減る
- 失ったもの: 欄を出さない以前の実行ファイルとの組み合わせは、読み分けられず止まる。直し方は実行ファイルを更新すること

## 採らなかった案

上の表のとおり。拡張の読み取りには、実行ファイルが条件つきで出す欄（無いのが正常な欄）と、機能の有無を `features` で確かめる処理が残る。これらは以前の形式を読む処理ではないので、消していない。
