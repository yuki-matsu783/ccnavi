# ADR-0191: GitLab の API に届かないときは、段ごとの手順を出さず認証を頼んで打ち直す

状態: 採用（ADR-0161 の「`--mcp-checked` の GitLab の案内は、確かめる主体をユーザにする」行のうち、ホストに届かないときの案内を改める）

## 状況

`ccnavi-start.sh` がホストに届かず終了コード 4 で止まるとき、GitLab では段（既存の MR の探索・issue のタイトル・マージ済みの MR・閉じる issue・MR の作成）ごとに、ユーザにブラウザで確かめてもらう手順と、HTTP の番号ごとの原因の説明を出していた。
GitLab の利用者は glab か `GITLAB_TOKEN` を用意できる前提で、届かないのはその用意が無いか一時的な失敗のときに限られる。まれな場面のために、段ごとに 2 通りの手順と原因の推測を保ち、出力・sh・テストが長くなっていた。

## 決定

GitLab の API に届かないときは、段を問わず「GitLab の API に届かない（理由の 1 語）」と、完了済みの処理と、1 行の `次:`（ユーザに glab の認証か `GITLAB_TOKEN` の用意を頼み、返事を待って同じ引数で打ち直す。用意できなければ直接実装に切り替えず報告して止まる）だけを出す。理由の 1 語は `HTTP <番号>`・`認証なし`・`応答なし`。詳しい理由はログに残す。
GitHub の MCP での代行手順と `--mcp-checked` は残す。gh もトークンも無いクラウドでは、MCP が唯一の道のため。

## 得たもの・失ったもの

- 得たもの: GitLab の止まり方が 1 通りになり、sh の分岐とテストが減る。出来た段（ブランチ・ワークツリー・push）は打ち直しで飛ばすので、同じ引数のままで続きから進む
- 失ったもの: 認証を用意できない GitLab の利用者は、ブラウザで確かめて `--mcp-checked` で進む道を案内されなくなる。HTTP 404 など認証では直らない失敗にも認証を頼む文が出るので、原因はユーザがログと番号から見る

## 採らなかった案

- 段ごとの手順を残す: まれな場面のための説明を保ち続けることになる
- HTTP の番号ごとに次の一手を分ける: 原因の推測を作り込むことになる。番号は理由の 1 語に出すので、ユーザが見て判断できる
