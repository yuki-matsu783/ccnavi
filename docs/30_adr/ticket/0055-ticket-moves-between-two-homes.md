# ADR-0055: チケットは 2 つの置き場を行き来する 1 本のファイルにする

状態: 採用（本文の `--reviewed --chat` は当時の記述で、ADR-0132 が廃止した）

## 状況

チケットは 2 本のファイルで表していた。エージェントが書く提案（`wip/proposals/<状態>/`）と、
承認のときにコピーする承認済みチケット（`.ccnavi/tickets/`）の 2 本である。状態は提案の側の置き場
（`todo` / `doing` / `done` / `cancelled`）で表し、承認済みチケットの置き場は開（直下）と閉（`closed/`）の
2 段だけだった。判定は承認済みチケットを読み、フェーズの終わりは提案の置き場で決め、
レビューの進み具合はマーカーで見る。このように 3 か所を読み合わせていた（設計 9.6）。

2026-09-16 の時点で、困っていたことが 3 つあった。

- **同じチケットが 2 か所にあり、毎回どちらを見ればよいか迷う。** 承認したあとの提案は
  判定に使われないのに置き場に残る。書き足しても判定に反映されないことが、読み手には分からない。承認済み
  チケットとの食い違いは、diff を取らないと分からない（ADR-0023）
- **「レビュー待ち」を表す置き場が無い。** 子を `done/` に動かしたあとユーザが見るまでの間は、マーカー
  （`pending` / `requested`）と `--explain` を読まないと分からない。`ls` で見える形（ADR-0024）に
  なっていなかった
- **レビューで残った指摘を続きで直すには、承認の往復が要る。** ユーザが「これは続きの子で直す」と決めても、
  エージェントが提案を書いてユーザがもう一度承認するまで作業を始められない。決めたのはユーザなのに、
  合意をもう 1 回取り直す形になっていた

## 決定

チケットは **1 本のファイル**にする。このファイルは、**ユーザが動かすときは `.ccnavi/approved/` へ、エージェントが動かす
ときは `wip/proposals/` へ**、という規則で 2 つの置き場を行き来する。

置き場（`wip/proposals/{todo,review}/` と `.ccnavi/approved/{doing,done}/`）の意味、状態の遷移の図、誰が書くかは、設計書の [9.2 置き場](../../21_design/tickets/places.md) と [9.6 状態遷移](../../21_design/tickets/state-transitions.md) にある。決めたのは、次の 2 点。

- ユーザが動かすときは `.ccnavi/approved/` へ、エージェントが動かすときは `wip/proposals/` へ動かす。`approved/` にはエージェントが書けず、判定が範囲を読むのは `approved/doing/` だけ
- レビュー待ちは `wip/proposals/review/` に置く。取り消しは `cancelled_at` を持って `approved/done/` に入る（`cancelled/` を持たない）

承認の意味は変えない。ユーザが読んで合意したものが `.ccnavi/approved/` に入り、エージェントは
そこに書けない。変わるのは、承認のときにファイルを「コピーする」のではなく「動かす」ようになることである。

承認はコピーではなく移動になる（`todo/` から `approved/doing/` へ動かす）。`ticket start` は置き場を動かさず、`approved/doing/` のキーだけを書く。
未解決の指摘を残す判断では、受け入れて進むか、続きの子チケットを `approved/doing/` に起こすかをユーザがターミナルで選ぶ。

親子とフェーズの仕組み（9.7〜9.9）は変えない。「レビュー対象か」を決めるのは今までどおり
フェーズの見る場所（種類・計画のステップ・子の宣言・実績のリスク）で、子ごとに `review/` へ行くかどうかは
その子を閉じた時点のフェーズの答えで決める。

## 理由

- **置き場を見れば「誰の番か」が分かる。** `wip/proposals/` にあればエージェントが動かした直後で次はユーザ
  （承認かレビュー）、`.ccnavi/approved/` にあればユーザが動かした直後で次はエージェント（作業）か
  終わり。読み合わせが要らない
- **コピーをやめても、承認済みチケットを本物とする仕組みは弱まらない。** 判定が読むのは `.ccnavi/approved/doing/` だけで、
  そこはエージェントが書けない。承認のあとに提案を書き足す手段が無くなるので、ADR-0023 で守ろうと
  したもの（承認した内容が残る）は、コピーではなくファイルそのものが担う
- **続きの子をユーザが起こすのは、承認と同じ行為。** ユーザがターミナルで「この指摘は続きで直す」と選ぶことは、
  その範囲で作業してよいという合意そのものなので、承認の往復を挟まない。エージェントが起こす
  形にすると承認が要る（提案の側に書く）。ユーザが起こすから `approved/` に直に置ける

## 得たもの・失ったもの

- 得たもの: チケット 1 本につきファイル 1 本。`ls wip/proposals/review` で「ユーザが見るべきもの」が並ぶ
- 得たもの: レビューで残った指摘を続きの子に書き出すときの、承認の往復が 1 回減る
- 得たもの: `phase.sync`（提案のキーの値を承認済みチケットにコピーする・閉じたら `closed/` へ動かす）が要らなくなる
- 失ったもの: **承認済みチケットと提案の diff が取れない。** 承認したあとに何を書き足したかは、
  git の履歴で見ることになる（提案は承認で `todo/` から消え、その削除がコミットに入る）
- 失ったもの: 記録の `source_path` が指す提案は、承認のあとは無い。承認の出所は git の履歴で辿る
- 失ったもの: 続きの子チケットをユーザが起こす形は、エージェントが書く提案より本文が薄い
  （指摘の一覧と範囲だけ）。設計の相談が要る指摘には向かない。そのときは今までどおり
  エージェントが `todo/` に提案を書く

## 採らなかった案

- **提案の置き場の状態に `review` を足すだけ（コピーは残す）。** 「レビュー待ち」は見えるように
  なるが、2 本のファイルの読み合わせは残る
- **`review/` も `.ccnavi/approved/` の下に置く。** ユーザの番のものはエージェントが書けない場所に置く、
  と揃えたかった。しかし `done` はエージェントが打つ操作なので、その結果がエージェントの書けない場所に
  現れることになり、「`approved/` へ動かすのはユーザだけ」の規則が崩れる

- **続きの子を自動で起こす（`check` が未解決を見つけたら）。** ユーザの判断を挟まないので、
  「受け入れて閉じる」との選び分けができない。起こすかどうかはユーザが決める
- **`cancelled/` を残す。** 4 つの置き場に揃えるため、取り消しは `done/` に `cancelled_at` を
  持って入る。ボードは `cancelled_at` のキーで「取り消し」の列に分ける。ボードの列は今までどおり
  未着手・作業中・完了・取り消しの 4 つで、`doing/` と `review/` はどちらも作業中の列に入る
  （レビュー待ちはカードの属性で示す）
