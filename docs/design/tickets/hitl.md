### 9.8 フェーズの終わりと HITL ポイント

フェーズの終わりは、ユーザの手が入るところ（HITL ポイント。Human In The Loop）の 1 つ。ユーザの手が入る場所は
範囲の承認・レビュー・未解決の受け入れの 3 か所にまとめてあり、フェーズの終わりはその 2 つめにあたる。

同じ親の同じ `phase` の子が `doing/` に無く、`review/` か `done/` に 1 枚以上あるとき、
そのフェーズは終わり。終わりの扱いは**ユーザがどこで見るか**で 3 つに分かれる。子を閉じる
`ticket finish` は、その子を閉じたものとして数えたこの答えで行き先を決める。レビュー要（延期を含む）なら
`wip/proposals/review/`、不要なら `.ccnavi/approved/done/`。レビューが済むと
`review/` の子は `done/` へ動く。

見る場所は `none` / `chat` / `mr` の 3 値で、次のうち厳しい側を採る（`none` < `chat` < `mr`）。

- フェーズ定義の `review`（9.7）
- 計画の項の `mr`（フェーズ定義の `review` が `none` でも `mr` にする）
- 引き受けた延期の分（延期した項は自分では持たない。引き受けた側が、引き受けた分の
  宣言と自分の宣言の厳しい側で見る。覆っている分のフェーズ定義が読めなくなっていたら `mr` として扱う）

閉じた子の `human_review.required` と、実績のリスクが HIGH 以上であること（9.9）は、
**要るとだけ言い、場所は言わない**。宣言が `none` のフェーズを `chat` へ上げるだけで、
宣言された `mr` を `chat` に落とすことはない。場所を決めるものが 1 つも無い番号（計画が無い、
フェーズ定義のファイルが無い、その名前のフェーズ定義が読めない）では、子が `required: true` と言うか実績が
高ければ `mr`。

| | `mr` | `chat` | `none` |
|---|---|---|---|
| 最後の子を閉じた呼び出しの `PostToolUse` で返す文 | 「合流と push を済ませ、`request` でレビューを頼み、ターンを終えてユーザを待て」 | 「合流してユーザに差分を見てもらい、ターンを終えて待て。先へ進めるのはユーザが端末で」 | 「人間レビューを省略して次のフェーズへ進む」 |
| マーカー | `pending` | `pending` | `skipped` |
| HITL ポイント | 来る。`reviewed` のマーカーまで止まる | 来る。`reviewed` のマーカーまで止まる | 来ない |
| 開ける者 | `ccnavi-review.sh confirm` / `decide`（9.10） | ユーザが親のワークツリーの端末で `ccnavi-review.sh chat <N>`（中身は `ccnavi --reviewed <N> --chat`） | — |

`chat` で通したあと、ユーザが端末で指摘を 1 行ずつ打てば、`decide` の「このフェーズで直す」と同じ形で続きの子を
`.ccnavi/approved/doing/` に起こす（9.10）。何も打たなければ起こさない。

**`chat` はこのセッションでユーザが見る。** ホストへ出ないので、マージリクエストも認証も要らず、
`.ccnavi/scripts/` の sh は 1 本も動かない。ユーザの合意を確かめる材料は `mr` のときと同じ 2 つで、
標準入力が端末であること（`CCNAVI_GUARD_TICKET_APPROVAL`）と、`--reviewed` を含むコマンドを
エージェントが打てないこと（`DENY_TICKET_APPROVAL_CLI`、9.5）。`--chat` は見る場所が `chat` と
宣言され、依頼が出ていないフェーズにしか当たらない（依頼後は `confirm` / `decide`。9.10）。

実績のリスクが高い `chat` のフェーズでは、マージリクエストで見ることを勧める文を出すが、
止めはしない。選んだのがユーザであることは `reviewed` のマーカーに残す（`recommended: mr`）。

告知は「マーカーが 1 つも無い」ときだけ出る。子を足してマーカーが消えた後、フェーズが再び終われば、告知はもう一度出る。
最後の子を閉じる前に、フェーズ定義の `deliverables` が親か子のワークツリーに在って追跡されているかを見る。
無ければ `finish` を拒む。閉じてレビューが通ったら、案内が次のフェーズの計画を促す。

**止めている間の呼び名は 2 つある**。依頼を出すまでが **レビュー準備中**（次に動くのは
エージェント。合流・push・依頼）、出してからレビュー済みまでが **レビュー待ち**（次に動くのはユーザ。
判定の `review_waiting`）。拒否の文面・`--explain`・親の局面・ボードのバッジはこの名前で言い、どちらの段かで
「やること」も変わる（未依頼なら request まで、依頼済みなら待って `confirm`）。`chat` のフェーズは
ユーザが端末で先へ進めるまで「レビュー準備中」のまま。ただし `request` を通したときは「レビュー待ち」へ移る。
JSON の欄名は `gate_closed`。これは判定とボードの契約で、この呼び名とは対応しない（10 章）。

**`order: dag` でも止めるのは親ごと。** 並行している枝の片方がレビュー準備中・レビュー待ちに入ると、
その親の cwd からはサブエージェントを起こせなくなる（止めるのは新しい子を起こすところなので、先に起こしてあった子は動き続ける）。

依頼を出したあとに別の枝の子を親ブランチへ合流すると、依頼時の HEAD と食い違い、`confirm` が依頼の
やり直しを求める（9.10）。やり直した依頼には、その枝の作業も入る。

**受け入れは、受け入れたフェーズとその子孫にだけ適用される。** `decide` で受け入れたスレッドは
`accepted.json` に受け入れた番号と一緒に残り（別の枝で受け入れ直せば番号が足される）、`confirm` は
それらの番号か、コピーの `waits` にそれらの番号を持つ番号の依頼でだけ受け入れ済みと数える。並行した別の枝の
`confirm` では未解決のまま数える。`sequential` では受け入れは後ろの全部に適用される。

止めるかどうかは cwd のワークツリーで親を引いて決める。止めている間、その親の cwd からの `Agent`（サブエージェントの
起動）と `Bash` / `PowerShell` を `DENY_PHASE_REVIEW` で止める。通すのは `Bash` で、連結の全部が
`sh|bash …ccnavi-(ticket|review|git).sh` の形で読み切れたときだけ。読み切れないコマンドに例外は
与えない。`PowerShell` に例外は無く、止めている間は必ず止まる。`Write` / `Edit` は通す。次のフェーズの計画はレビュー前に進めてよい。別の親は別に
止め、ワークスペースルート直下や無関係のツリーからの呼び出しは止めない。

「ターンを終えてユーザに聞け」を強制する手段は hook に無いので、先に文で言い、進んだら止める 2 段構えになる。
`cwd` は `cd` を 1 回打てば外れるが、外れた先で起動したサブエージェントの書き込みは行き先で止まる。
