### 9.4 承認

計画を立てている間、親はルールだけで動く。計画が終わったらユーザが端末で `ccnavi --agree` を打つ。標準入力が
端末でなければ拒む（`CCNAVI_GUARD_TICKET_APPROVAL=disable` で免除）。引数は無く、承認の対象は
「`todo/` に在って、同じ識別子がどの置き場（作業中・レビュー待ち・閉じた）にも無い提案の全部と、
親の改版」。承認は提案を `todo/` から `.ccnavi/approved/doing/` へ動かす（`todo/` にコピーは残らない）。
改版するときは、同じ識別子の提案を `todo/` に書いて出す。承認すると `doing/` の側は計画と `phases:` だけが差し替わり、`todo/` の側は
消える。提案の置き場は、ワークスペースルートと `.claude/worktrees/*` の全部を走査する。

識別子を並べた `ccnavi --agree <識別子>...` はその識別子だけを対象にする（VS Code 拡張と端末の
`ccnavi-agree.sh <識別子>...` が使う。sh は `-` で始まる語と空の語を受けない）。絞りは対象を狭めるだけで、
絞らないときに落ちるものは通さない。承認待ちに無い識別子が混じれば何も承認せず、親の改版が承認待ちなのに
対象に無い子も何も承認しない。対象から外した親を持つ子は「親が承認されていない」で落ちる。

同じ識別子が複数のツリーにあれば、承認済みチケットと同じ、本物とする側の決め方（9.2）で 1 つを採る。
元ツリーの版の比べ方は置き場の順（`todo` < `doing` < `review` < `done`）。別のリポジトリの同じ識別子は
1 つにまとめない（別のチケットとして扱う）。決まらなければ全部残り、`--lint` と状態の操作が「複数の場所にある」と言う。同じツリーの
中で同じ識別子が 2 つの置き場に在るとき（移動の途中で止まった形跡）も同じ。

順序は「承認 → コミット（と push）→ 子のワークツリーを作る → `start`」。コミットの前にワークツリーを
作ると、その子には範囲が適用されない。

承認画面に出るのは、件数、各提案の識別子と題（親 / 親 X、フェーズ N: フェーズ定義名）、親なら
「このチケットで編集可能な範囲」、子なら「この子チケットで編集可能な範囲」とフェーズ定義の範囲の上限、新規の子なら親の
`issue:` と `branch:`（`branch:` は既にあるブランチなら「既存のブランチ <名前> を使う」、無ければ「新しく切るブランチ」。
改版では出さない）、子の人間レビュー
要否と先行、親の全体計画とフィードバック計画、理由、ワークツリーと提案のパス、判定に効かない記述の
warn、チケットで編集対象としているが書き込めない場所（下）。計画を持つ親なら、親に固定するフェーズ定義を 3 つに分けて出す
（この親が使う定義＝題・`review`・`scope`・`deliverables`・使う番号、使われていない定義、`phases.yml` にあってこの親では使わない
定義。9.7）。改版なら計画の差分と `phases:` の差分（足した・外した・変わった定義。改版が書く中身から組む）。リスクの点は出ない（9.9）。`y` / `yes` でまとめて承認する。1 件だけの
承認はできない。

承認時に確かめること。親の計画と、親に固定するフェーズ定義の写し（`phases:`）が噛み合うか（計画を持つのに写しが無い、
項の定義が写しに無い、`kind`、延期できる定義か）と、写しの各定義が承認したときの `phases.yml` の同じ名前の定義と読んだ形で
同じか（違う・名前が `phases.yml` に無いは error。`phases.yml` にあって写しに無い定義は何も言わず、写しにあってどの項も使わない
定義は warn。改版では、子が承認された番号が使う定義は `phases.yml` ではなく承認済みチケットの写しと比べる。9.7）と、
計画の順序が組めるか（項の `after` の形、終端は 1 つ、最後の項は延期できない、延期の引き受け手とそのレビュー。
全体計画とフィードバック計画の両方。9.7）。承認は待ち方を書かない。待ち方は承認済みチケットの計画の項の `after` から
都度計算する（9.7）。提案にスクリプトだけが書く欄（`started_at`・`completed_at`・`base_sha`・`cancelled_at`・`cancel_reason`）の空でない値や
`workflow:` の欄が無いか。子の親が承認の対象の中か承認済みチケットにあるか、深さ 2 段。
`project` が置き場に在るか、子は親と同じか。前のフェーズが閉じてレビュー済みか（9.7）。子の先行（`predecessors`）が
全部 `done/` に在って取り消しでないか（先行が閉じれば通るものはフェーズの順序と同じく「まだ承認できない」、
取り消し・どこにも無い・複数の場所はふつうの error）。error が
あればその提案は落として標準エラーに出し、読めない提案があって承認するものが無ければ 1 を返す。

**範囲の広さは承認で止めない。** 子の項が親の範囲を超える、フェーズ定義の `scope` を超える、regex で
どちらにも入るかを確かめられない、の 3 つは warn（判定が切り詰める。9.5）。error は「チケットの形」の検査。
超過は承認画面の見出し「チケットで編集対象としているが、書き込めない場所」に出す。`--agree --preview --json`
では `batch[]` の `overflow[]` に載り、超過だけの子は `batch[]` に入る。`--lint` も warn。

**承認はチケットの中身を変えない。** 承認済みチケットは提案のファイルそのもので、承認は `todo/` から `doing/` へ
rename するか、バイト単位でコピーして元を消す。欄を書き足さず、改行も BOM も変えない。端末・ボード・Chrome 拡張・手で
動かす、のどれで承認しても、承認済みチケットは提案とバイト単位で同じになる。欄の有無が承認の経路を表すと、読む側は欄の
無いもの（手で動かした承認）を壊れた承認と読み違えるため。承認済みチケットのプロジェクトは置き場（ツリー）から決まる。
前の版の承認が書き足していた `ccnavi_approved: {approved_at, source_tree, source_path}`（改版の `revised_at` /
`feedback_at`）・`project:`・`workflow:` を持つ承認済みチケットもそのまま読む（移行はしない。`workflow:` の欄はどれも読まない）。古い形とみなすのは、`ccnavi_approved` が前の版の必ず書いた欄（`approved_at`・`source_tree`・`source_path`）を
揃え、`approved_at` が空でないときだけ。`ccnavi_approved: {}` のような書きかけの記録は古い形とみなさない。ただし欄を
揃えた記録は手で書けるので、古い形そのものは偽装できる。古い形の `workflow:` の欄も読まない（待ち方は承認済みチケットの
計画の項の `after` から計算する。9.7）。古い形なのに
状態の履歴に承認（`approved`、続きの子は `raised`）の行が無ければ、`--lint` が warn にする。承認画面の「提案:」はツリーからの相対パスで出すので、画面の本文とダイジェストは機械に依らない。

承認の時刻は欄に持たない。表示（ボード・`--diagnose`・`ccnavi-ticket.sh status`）は、状態の履歴の `approved`（続きの子は
`raised`）の時刻、無ければ前の版の承認が書いた記録（古い形の `ccnavi_approved.approved_at`）、それも無ければ
`git log --no-renames --diff-filter=A` で `doing/<識別子>.md` を足したコミットの時刻を読む。
`--no-renames` を付けるのは、GitHub の画面での移動が rename のコミットになるため。どれも無ければ「未コミット（手で置いた）」と
出す。判定は履歴も git も読まないので、判定の拒否文には承認の時刻を出さない。

承認が中身を変えないので、提案に書いた値はそのまま承認済みチケットの値になる。提案（`todo/`）にスクリプトだけが書く欄の空でない値が
あれば、`--agree` と `--lint` が error にする（判定では提案に当てない）。改版の提案も同じで、承認済みチケットを写して書くときは
`started_at`・`completed_at`・`base_sha`・`cancelled_at`・`cancel_reason` を空にする（改版は承認済みチケットの側の値を残し、計画と
`phases:` だけを差し替える）。承認の記録 `ccnavi_approved` と続きの子の目印 `followup_of` も、ユーザの判断だけが残す欄なので、提案にあれば
`--agree` と `--lint` が error にする（改版の提案で写したときも消す）。`wip/proposals/review/` で読むのは `completed_at` に値があるもの（`finish` が書く）だけ。判定が読むのは `doing/` だけで、
承認後に同じ識別子の提案を `todo/` に書いても適用される範囲は変わらない（親の計画の改版だけが承認の対象に入る）。
承認済みチケットと提案のダイジェスト照合は持たない（承認で提案は承認済みチケットの置き場へ動き、コピーが残らないので、照らす相手が無い）。終わったフェーズに子を足して
承認すると、その番号のマーカーを全部消す。

**承認する場所は 3 つある。** 端末の `--agree`、VS Code 拡張のボードのオーバーレイ、そして
置き場を動かすこと。
オーバーレイは `--agree --preview --json [<識別子>...]` で一覧を読み、ユーザが押したら
`--agree --yes <識別子,…> --digest <値> --json` を子プロセスで打つ（形は README「承認の JSON」）。
どちらも承認の対象を同じ関数で求めるので、見せたものと承認するものが食い違わない。

| 経路 | 誰が打つ | ユーザが押したことの証拠 |
|---|---|---|
| `ccnavi --agree [<識別子>...]` | ユーザが端末で | 標準入力が端末であること。hook の中や `echo y \|` から来ていないことの、いちばん安い証拠 |
| `ccnavi --agree --yes <識別子,…>` | 拡張が、ユーザがオーバーレイで押したときに | 見せた一覧と今の一覧が一致すること、見せた中身のダイジェストが一致すること。加えて、組み込みの deny がシェルからの `--yes` を止める |
| 提案を `.ccnavi/approved/doing/` へ動かす | ユーザが、git を触れる場所で（GitHub の画面など） | その置き場にエージェントが書けないこと。動かせたのは書ける権限を持つユーザだけ |

`--yes` に端末を求めないのは、拡張の子プロセスが端末を持たないから。残った指摘の対応方針（9.10）も
同じ形でボードから送る。

**置き場を動かす経路の検査は判定が持つ。** 親が引けない、親自身が子、番号が親の計画に無い、`project:` が
置き場と違う、予約名を指している、のどれかに当たる承認済みチケットは、`scan` が `Ticket.blocked` を
立て、`scope_verdict` が範囲を当てる前に止める（実行前チェック・実行後チェック・サブエージェント終了時チェックで
同じ）。理由コードは `DENY_TICKET_BLOCKED`（ユーザがチケットを直すまでどこにも書けない）。フェーズの順序と
計画の形はここに入れず、`--lint` が warn で言う。

**ボードの承認は、見せた中身のダイジェストで照合する。** `--agree --preview --json` は `digest` を出し、
`--yes` は `--digest <値>` を受け取って、承認のときに読み直した中身のダイジェストと比べる。違えば何も置かず
`mismatch` と `digest: {expected, current}` を返し、1 で終わる。`--digest` が無いときも 1 で終わる。値の大文字小文字の違いは無視する。

- ダイジェストに含めるのは承認画面の本文と、判定が読んだ中身（`read_set`。`<ブランチ>:<ツリーからの相対パス>` ごとの中身の
  ダイジェスト。改行は LF に揃える。無かったファイルは「無い」として入る。state の置き場から入るのは取り込み状態 `sync/` だけ）と、
  一括のチケットごとに承認のとき書き出す中身（新規は提案のファイルのバイト列そのもの、改版は今の承認済みチケットの
  計画だけを差し替えたもの）。全ブランチの先頭は入れない
- 計算では、部分ごとの SHA-256 を件数と一緒に改行で並べ、その全体の SHA-256 を取る

**承認済みチケットは push するまで届かない。** 承認済みチケットは親のツリーの置き場
（`.ccnavi/approved/`）に置かれ、コミットして push するまで子のワークツリーにも他の機械にも
渡らない。どちらの経路でも、承認のあと `ccnavi-push-approved.sh` がコミットして push する。変更のあるツリーごとに
置き場と、承認で `todo/` から消えた提案（追跡されていたものの削除だけ）をコミットし（パスを限る。
`-a` も `add -A` も使わない）、保護されたブランチ
（`main` / `master` / `develop` / `release` / `release/*` と、`ccnavi-common-state.sh` の `ccnavi_integration` が決める
そのリポジトリの統合先。決まらなければ固定のリストだけ）でなければ push する。承認はしない。

| 経路 | 承認の push |
|---|---|
| 端末の `ccnavi-agree.sh` | 承認が通ったあとに sh から呼ぶ。承認の push に失敗しても承認は 0 で終わる（コミットは残り、打ち直せば送れる） |
| ボードの承認 | 1 件以上承認したら、`ccnavi-push-approved.sh` を絶対パスで端末に送り、Enter まで送る。sh が無ければ送らず、導入スクリプトで配るよう警告で言う |
| ボードのフローの保存 | 保存したら `ccnavi-push-approved.sh <親>` を端末に送る |
| ユーザの判断の入口（`ccnavi-review.sh chat` / `close-early`） | 実行ファイルが書いた後、取り込み済みの親子のチケットなら `ccnavi-push-approved.sh <親>` を呼ぶ。それ以外の親子のチケットでは承認の push をしない |

取り込み済みの親子のチケットでは、親のワークツリーで C1 と同じく親子のチケットのロックを取り、途中の操作が無いことを
確かめ、`ccnavi-sync.sh` で取り込んでから置き場（承認済みと、レビュー待ちの `review/` と、消えた `todo/` の提案）を
`commit --only` して送る。push が落ちたように見えたら `ls-remote` で届いたかを確かめる。落ちてもコミットは残す。

- エージェントからは組み込みの deny（`DENY_TICKET_APPROVAL_CLI`）で止める（9.5）。push の時機はユーザが決める
- sh の側で標準入力が端末かは確かめない
- 実行ファイルはネットワークに出ないので（P11）、`--agree` は置き場に書くところまで

**絞りと「見せたもの」は別の引数で渡す。** `--agree --yes <識別子,…> [<絞り>...]` の `--yes` は
「オーバーレイに出ていた識別子」、後ろの語は「そのとき掛けていた絞り」（`--preview` に渡したものと同じ）。
その絞りで今できる一覧とユーザが見た識別子を比べる。絞り込みが無ければ承認待ち全部と比べる。

一覧を見るだけの `--agree --preview` はエージェントにも通す。免除は `--preview` の付いた `--agree`
だけで、`--yes` は免除しない。免除の範囲はコマンド 1 本まで（Bash は shellread の区切り、PowerShell は
`;` `&` `|` と改行を区切りと見る）。免除の理由になるのは単独の語として現れた `--preview` だけ（前は生の
空白、後ろは空白か区切りか行末。引用がつないだ空白や別のフラグの値 `--reason=--preview` は数えない）。
免除は許さない側から書く。

**写しを作る補助は `--agree` の外に置く。** 親に固定するフェーズ定義の写し（`phases:`）は、承認の前に提案へ書いておく
（承認はチケットの中身を変えないので、承認のときには書き足せない）。写すのは `ccnavi --plan-order <親> --fill-phases` で、
承認待ちの親の提案の `phases:` の値だけを、計画が使う定義の集まり（`phases.yml` から。改版では子が承認された番号の定義は
承認済みチケットから）に差し替える（9.7）。`--agree` の副フラグにすると組み込みの止めに当たり、`--preview` と同じ厳しさの
免除が要るので、独立したフラグにしてある。実行ファイルは `--agree` の端末の確かめより手前でここへ分け、`--agree` と一緒には
受けない。書くのはエージェントも書ける提案だけで承認はしないので、エージェントが打ってよい。書き換えたあとの承認は
ダイジェストで縛られる。`--agree` が写しの違いで落とすときは、文面にこのフラグを出す。

**計画の順序の振り直しと書き戻しも同じフラグに置く。** VS Code のワークフロー編集タブは、図で引いた線を元の番号
（いま提案に書いてある番号）での直接の先行として `--order` に付け、`ccnavi --plan-order <親> --json --order <JSON>` で
振り直した答えを受け取る（読むだけ）。保存では `--order <JSON> --expect <ハッシュ> --write` で提案を書き換える。
振り直しの決まりは 9.7。番号の振り直しの正は実行ファイルで、画面は同じ決まりで仮の番号を出すだけ（見本の表
`tests/fixtures/plan-reorder.json` を両方のテストが読む）。答えの JSON は次のとおりで、承認の `--agree --preview --json` の
`plans` も同じ関数で作る（`--order` は渡さない。承認する提案そのものの順序）。`plans` は足しただけなので、承認の JSON の版は
上げていない。

| 欄 | 中身 |
|---|---|
| `plans` | 計画ごと（全体計画とフィードバック計画）に 1 件。`items`（`number` 振り直した番号・`from` 元の番号・`type`・`title`・`review`・`deferred`・`review_at`・`locked` 子が承認された番号）、`after`（振り直した番号での直接の先行）、`proposed`（提案に書いてある先行。「案に戻す」に使う）、`current`（改版のとき、承認済みの待ち方から戻した直接の先行。新規なら `null`）、`loose`（最後の項が待たない項）、`ready`（すぐ始まる項）、`problems`（その計画の順序の検査の error）、`source_sha` |
| `source_sha` | 親の提案と、その親の `todo/` の子の提案のバイト列をまとめたハッシュ（ツリーとツリーからの相対パスで区切る）。`--expect` に返す |
| `problems` / `loose` | 振り直した計画の順序の検査（`after` の形・終端・最後の項の延期・延期の引き受け手とそのレビュー）の error と、最後の項が待たない項（両方の計画） |
| `refused` | 引けない線（`kind` が `cycle` 循環・`locked` 子が承認された番号へ入る線を変えた・`unpackable` 固定した番号を動かさずに番号が振れない、`number`、`text`）。断ったときは振り直さず、提案のままの答えを返す |
| `revision_problems` | 改版の錠（子が承認された番号の定義・`review`・推移的な待ち・延期の引き受け手）に当たるもの。延期した項は元の項の同一性（振り直す前の番号）で比べる |
| `children` | 番号の変わる項を指す `todo/` の子の提案（`ticket`・`path`・`phase`・`new_phase`） |
| `writable` | 書き戻せるか（`refused`・`problems`・`revision_problems` が無い） |
| `written` | `--write` のときだけ。書いたか。書いたときの `source_sha` は書いたあとの値 |

書き戻しは親の提案の `plan:` / `feedback:` の値だけを差し替え、ほかの行（値の外のコメントも）と本文は変えない。
値の中に書いたコメントは消える。次のどれかに当たれば何も書かない。

- `--expect` が今の `source_sha` と違う（開いたあとに親か子の提案が変わった）。書く直前にもう一度読み、読んだときの
  バイト列と違えば書かない。確かめてから書くまでの間に提案を書かれる隙は、1 回の起動の中に狭めるだけで、錠は持たない
- 引けない線がある、振り直した計画の順序の検査に error がある、改版の錠に当たる。範囲など順序と関係の無い理由で
  承認に落ちる提案でも、順序の書き戻しは止めない
- 組んだ全文を読み直すと、`plan` / `feedback` / `phases` のほかの欄か本文が読んだ形で元と変わる（値にアンカーがあり、
  ほかの欄が別名で指しているときなど）
- 番号の変わる項を指す子の提案が `todo/` にある。子の識別子はフェーズ番号を含み（`<親>-<2 桁のフェーズ番号>-<連番>`）、
  `phase:` と食い違うと読めないので、`phase:` の値だけを書き換える追従はまだ入れていない

書き換えは承認ではない。書き換えると承認のダイジェストが変わるので、書き換える前に見せた一覧では承認できず、
承認は開き直した一覧で行う。書き戻しはコミットされないまま承認されるのが普通なので、承認したあとは取り下げられない
（承認コミットの親の提案と `doing/` のバイト列が違う。取り下げの文面が取り消して出し直すよう案内する。
state-transitions.md）。承認を渡す文（`approved_text`）は、計画を持つ親とその子があれば、いつも「番号は承認済み
チケットで読み直す」と添える。書き換えられたかを見分ける材料が無い（エージェントのコミットしていない編集と同じ形になる）
ので、見分けずに添える。

**承認を頼む前の確認は `--preview` に相乗りする。** `--agree --preview --verify [<識別子>...]` は、
置かずに「いま `--agree` を打てば、その提案が承認の対象に入るか」を終了コードで返す（REQ-APV-13）。
0 が「はい」、`modes.EXIT_ANSWER_NO`（3）が「いいえ」、1 は使い方か設定の誤り。判定は承認と同じ
`gather`・`candidates` が持ち、`--agree` が落とさないもの（範囲の超過と、読めない提案）では落とさない。
走査は絞る前の全ツリーを見るので、他のセッションの書きかけ 1 本で「いいえ」になることがある。承認で落ちる
ものは `--lint` も名指しする。ただし「まだ承認できない」もの（前のフェーズが閉じていない子。
`rules.KIND_NOT_YET`）は `--lint` では warn。

提案を `todo/` に書いた回に、この確認を勧める文を 1 度だけ渡す（REQ-APV-14、`ticket_guard.propose_notice`）。
判定には足さず、ルールの文と同じ `PreToolUse` の `additionalContext` の経路で渡す。

`CCNAVI_MODE=dry-run` の間は deny が止めないので、エージェントは `--yes` を打てる。承認の経路だけを
例外にはしない。

**承認したことは、拡張が渡す文と `status` で伝わる。** hook は承認を伝えない。

- ボードの承認は、`--agree --yes` の `prompt`（`agree_screen.approved_text`）を拡張が通知からユーザに渡し、ユーザが進行中の
  セッションに貼るか、新しいセッションを開く
- 端末・GitHub の画面・Chrome 拡張の承認では、ユーザがそのあとセッションに一言送る。エージェントは、承認済みチケットの状態を
  確かめるとき（着手の前、引き継ぎを読んだあと、承認の有無に迷ったとき）に、ファイルを読んで推測せず
  `ccnavi-ticket.sh status [<親>]` を打つ
- hook がセッションの最初で起点を取り、それより後に増えた承認を伝える形は採らない。セッションの開始時の取り込み
  （`ccnavi-fetch.sh`）で届いた承認は起点に含まれ、伝わらない。前の版が書いていた記録 `<state>/approved-<session>-<agent>.json`
  は今は書かず、残ったものを古い記録の後始末で消す

**状態は `status` で聞く。** `ccnavi-ticket.sh status [<親>]`（実行ファイルの `ccnavi ticket status`）は、親を渡せばその親子を、
渡さなければ作業中・レビュー待ち・承認待ちのチケットがある親子を全部、閉じたものも含めて出す。チケットごとに次を ccnavi が
判断して言う。読むだけで何も書かず、ネットワークにも出ない（P11）。

| 項目 | 中身 |
|---|---|
| 置き場とツリー | `todo/` / `doing/` / `review/` / `done/` と、見つけたツリー。複数の場所にあれば、どれが本物か決まらないと言う |
| 承認の時刻 | 上の順（状態の履歴 → 古い形の記録の `approved_at` → `doing/` に足したコミット → 「未コミット（手で置いた）」） |
| 着手 | 未着手か、着手済み（`started_at` と `base_sha`）か。閉じたものは完了か取り消しか |
| 置き場のファイル | 未コミット（ファイルがまだコミットに無い）、コミット済みのファイルに未コミットの変更がある、コミット済みで未 push、push 済み。push 済みかは手元のリモート追跡の ref で見るので、古いかもしれないと添え、最新にするには `ccnavi-sync.sh` を先に打つよう言う |
| 止まっている理由 | `blocked`、取り込み済みの親子が決まらない、C1 が状態の操作を断る親子（`c1.target` の理由）、満たしていない先行、親が未着手、取り込み済みの親子で承認済みチケットが未コミット |
| 注意 | `base_sha` がワークツリーの HEAD の祖先でない、再開（`done/` から手で戻す）で残った閉じるときの欄、状態の履歴に着手の行が無い着手。どれも `start` と判定は止めない（`--lint` も warn） |
| 次の一手 | 下 |

- 未コミットの承認済みチケットには、ユーザに `ccnavi-push-approved.sh <親>` を打ってもらうことだけを言う。エージェントが運ぶ
  コマンドは出さない。承認が中身を変えないので「手で置いた」と「`--agree` が置いてまだ運んでいない」は見分けられず、
  エージェントが運ぶ道具にすると、保護をすり抜けて置いたものまで運べてしまう
- そのうえで、その親子が C1 の対象（`ccnavi c1 family <親>` と同じ `c1.target`）なら「ユーザが運ぶまで `start` は止まる」、
  対象外なら「`start` へ進んでよい」と言う。C1 が状態の操作を断る親子（決まらない・親のワークツリーが無いなど）は、その理由を
  止まっている理由に出し、進んでよいとは言わない。判定は未コミットの承認済みチケットも読むので、C1 の対象でなければ運ばなくても
  着手できる。C1 の対象では、`start` の C1 が親のワークツリーの未コミットの `doing/` の追加をユーザが運ぶものとして止める
- サブエージェントも打てる（hook が止める副命令の一覧に入れていない）。実行ファイルは呼び手がサブエージェントかを知らない
  ので出力を分けず、状態を動かすコマンドの行には「親（メインエージェント）だけが実行する」と書く。サブエージェントが
  その行を打っても hook が止める
