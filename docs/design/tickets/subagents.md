### 9.12 サブエージェント

| イベント | すること |
|---|---|
| `SubagentStart` | cwd のワークツリーが承認済みチケットに結び付くときだけ、開いている子の一覧（識別子・ワークツリーの有無・範囲・未完了の先行・フェーズ定義・`agent` の案内）を `additionalContext` で渡す。親のツリーならその親の子、子のツリーならその子自身。ワークスペースルート直下とチケットの無いワークツリーからの起動には子の一覧を渡さない。止められないイベントなので判定はしない。子がフロー（9.3.1）を持てば、下の「フローの案内」も足す。着手中の子のフローが着手のときのハッシュから変わっていれば、`systemMessage` にも載せて知らせる（止めない）。チケット制御が有効で state の置き場があり、payload に `agent_id` があれば、実行中の印（下の「実行中の印」）も置く。どの起動にも、cwd がプロジェクトの中ならそのスキルの目録（11.13）と、「気づいたスキル候補は最後の報告に節を足して返す」の 1 行（`subagent.CANDIDATE_NOTE`）を渡す。この 1 行を渡すのは、サブエージェントには `Stop` の振り返りが届かないため（6.6） |
| `SubagentStop` | 実行中の印を外す（差し戻して続けさせる回は外さない。判定の途中で例外が出ても外す）。対象の子の `base_sha..HEAD` のコミット済みの差分と未コミットの変更の両方から範囲外を探し、残っていれば `enable` で 1 回だけ終了コード 2 で差し戻す。差し戻しの記録は `state/subagent-<セッション>-<id>.bounced`。`agent_id` が来ない payload では `<id>` がワークツリーの名前になり、同じワークツリーから `agent_id` 無しで来る 2 体目は通る。名前で書いた記録はセッションが終わるまで残る。2 回目は通して文だけ渡す。未コミットが残っていること自体は差し戻さない。対象の子のフローが着手のときのハッシュから変わっていれば、それも知らせる（9.3.1。止めない）。対象の子のワークツリーを読めず範囲を確かめられなかったら、止めない（読めない原因は子の作業とは限らず、差し戻しても子には直せないことがある）。範囲外が他に見つからなければ記録を `skip` / `worktree-unreadable` にして許可と分け、どちらの場合も `detail` に確かめなかった子を残す。この出力は親に届かないので、`state/subagent-<セッション>-<id>.unchecked` に 1 行目のセッションの識別子（そのまま）と子の識別子を書き、親に 1 行言う（下の 2 行）。処理が ccnavi の内部エラーで終わった回も、止めずに（`systemMessage` でユーザに知らせて）同じ印を置く。どの子を見るはずだったかは分からないので中身は空にし、親には内部エラーで確かめていないと言う |
| `PostToolUse`（`Agent`） | サブエージェントが差し戻しを無視して終わったこと、`SubagentStop` で子の範囲を確かめられなかったこと（`worktree-unreadable`。印は読んだら消す）を親に言う（`SubagentStop` の出力は親に届かない）。起動したのがサブエージェント（payload に `agent_id` がある入れ子）なら、同じ文を `systemMessage` にも載せる。同じ呼び出しで実行後チェックが `enable` の差し戻し（終了コード 2）をするときは載らない |
| `PostToolUse`（親のどのツールでも）・`UserPromptSubmit` | payload に `agent_id` の無い親の呼び出しなら、このセッションに残った `.unchecked` の印をぜんぶ読んで言い、消す。どのセッションの印かは、名前ではなく中身の 1 行目と完全一致で比べる（名前の前置きは別のセッションのものとも重なりうる）。バックグラウンドで動かしたサブエージェントは、親の `Agent` の `PostToolUse` が `SubagentStop` より先に来るので、そこだけで読むと知らせが落ちて印が残る。親が次のツールを使えばその `PostToolUse` で、ツールを使わずにターンを終えたなら次の依頼の `UserPromptSubmit`（`additionalContext`）で届く。`Stop` では読まない（`Stop` から親に言うには、終わろうとするのを止めて続けさせることになる）。サブエージェントの中の呼び出しでは読まない（その子の親でない印を消すと、親に届かなくなる） |

判定は行き先で決まるので、`SubagentStart` の一覧は案内でしかない。

**実行中の印。** メインの `Stop` が、委任して待つ回を「レビュー依頼までの道」の促し（`NUDGE_TICKET_REQUEST`。6.6・9.6）で止めないための記録。

- `SubagentStart` が `state/subagent-<セッション>-<agent_id>.running` を置き、`SubagentStop` が外す。1 体 1 ファイルなので、並行して始まる・終わる体が同じファイルを取り合わない。中身は 1 行目に `session <セッション>`（`.unchecked` と同じ。別のセッションの名前と前置きが重なりうるので、セッションは中身で決める）、2 行目に開始時刻（エポック秒）
- メインの `Stop` は、そのセッションの印が 1 つでも「実行中」なら促しを見送り、「1 回だけ」の記録（`nudged-<セッション>.json`）も進めない。入れ子の体（孫）も自分の `agent_id` の印を持ち、全部が外れるまで見送る。順序は `Agent` の `PostToolUse` が `SubagentStop` より先に来ても関係しない（始まりと終わりの印だけを見る）。`Stop` が `SubagentStop` より先に来れば印が残っていて見送る。逆に `SubagentStop` が `Stop` より少し遅れる終わりぎわの回も見送るだけで、害は無い
- 印を読めない（置き場を一覧できない、壊れて開始時刻を読めない）ときも見送る。壊れた印はファイルの更新時刻で期限を見る。促しは保護ではないので、迷ったら止めない側に倒す
- `SubagentStop` が来ないまま残った印（中断・クラッシュ・内部エラー）は、開始から `RUNNING_MAX_SECONDS`（4 時間）を過ぎたら実行中と数えない。値の根拠は、背景の体が現実に走る長さ（数分から 1 時間ほど）に余裕を足したこと。hook の timeout（10 秒）とは関係しない。長すぎる分の害は、取りこぼした印が促しを止める時間が伸びるだけ。加えて、セッションの起動と再開（`SessionStart` の `source=startup` と `resume`）で、そのセッションの印を全部捨てる。どちらも新しいプロセスで、前のプロセスのサブエージェントは生きていないため。compact と clear では捨てない（同じプロセスで、実行中の体が残りうる）。古いセッションの印は後始末（prune）が、ほかの `subagent-` の記録と同じに消す
- `agent_id` が payload に無い始まり・終わりは、鍵が決まらないので印を置かず外しもしない。その体は実行中と数えられない（制限）
- 数えるのはサブエージェントだけ。チームメイトと背景のシェルは待ちに数えない

**フローの案内。** 一覧の子がフローを持てば（ファイルが在れば）、その子の行の下に次を足す（`flow.briefing`）。

- 手順を並べるのは、起動の cwd が**その子のワークツリー**で子が 1 本に決まるときだけ。親のツリーからの起動
  （入れ子の孫も cwd は親のツリー）では、各子のフローのパスを 1 行ずつと「自分の担当の子チケットのフローだけを
  読んで従う。他の子のフローには従わない」だけを渡す。以下は子のワークツリーからの起動のとき
- フローのファイルの絶対パスと、それが合意済みの手順でエージェントは編集しないこと、作業の前に読んでその順に
  進めること、の 1 行（compact で案内が消えても辿り直せるようファイルを名指しする。付録 C）。ロックと、着手のあとの
  書き換えの知らせは、サブエージェントには言わない。ロックは書き込みを止めるときの理由で、書き換えの知らせは
  ユーザとメインに向く
- 手順を 1 ノード 1 行で並べ、合意済みのフローの本文（データ）として囲ったもの。`start` から繋がりを辿った順に
  `<番号>. [<種類>] <名前>: <中身> → <次の番号>（<分岐の名前>）`。40 ノードか文の上限（9.3.1）を超えたら
  そこで切り、続きはファイルを読ませる。リンクや読めないフローは 1 行で言う
- `askUserQuestion` のノードがあれば、その扱い。サブエージェントには AskUserQuestion が渡らないので、そのノードで
  手を止め、問いと選択肢を添えてメインに返す。メインがユーザに聞き、答えを持って同じサブエージェントを再開させる
- `loop` のノードがあれば、その扱い。条件が成り立つあいだ「繰り返す」側へ進み、成り立たなくなるか繰り返した回数が最大に
  達したら「抜ける」側へ進む。回数は自分で数え、最大に達しても条件が成り立つままなら最後の報告に書く
- `subAgent` / `subAgentFlow` のノードがあれば、その扱い。Agent ツールがあれば入れ子のサブエージェントとして起動し、
  そのプロンプトに担当の子チケット・ワークツリー・範囲を必ず書き、他の子のワークツリーに触れないことを書く。
  **Agent ツールが無ければ**（入れ子の上限。`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`、クラウドの環境は 1）、
  そのノードで手を止め、起動してほしいエージェントの種類・プロンプト・担当の子のワークツリーと範囲を添えて
  メインに返す。メインがそのとおり起動し、結果を持って同じサブエージェントを再開させる（`askUserQuestion` と同じ流れ）

既知の制限: 孫の hook の `cwd` はメインの `cwd` になるので、孫の起動では `SubagentStart` が親の全部の子を
並べ（フローはパスだけ）、`SubagentStop` は兄弟の子の変更でも差し戻し、孫は範囲の中なら兄弟のワークツリーにも
書ける。入れ子のプロンプトに担当を必ず書かせるのはこのため。フローのファイルが無いときは何も足さない。

compact の前後の hook でフローを入れ直すことはしない。どちらの hook も `additionalContext` を受け付けるとは文書に書かれておらず、`systemMessage` は捨てられるため（付録 C）。
