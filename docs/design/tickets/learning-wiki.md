### 9.16 学びの蓄積（learning-wiki）

状態: 実装済み（範囲は節末の「実装の範囲」）。`CCNAVI_LEARNING` の既定は `enable`。要求は [要件 REQ-LRN](../../requirements/learning-wiki.md)。用語は CONTEXT.md。

チケット作業で拾った気づきを、ルール・配点・フェーズ定義・テンプレート・スキル・文書への提案として育てる。
育てる仕事のうち、集める・溜める・提案するまでがエージェントで、反映を受け入れるのは人間。
いまスキルだけを対象にしているスキルの振り返りと wiki（`.ccnavi/docs/skill-review.md`、`skill-wiki.md`）を、反映先の 6 種に広げ、
子チケットの流れの中へ組み込む。

**3 層。** 経験の記録・溜めた知識・効くものを分け、提案はその間をだけ流れる。

| 層 | 中身 | 置き場 | 書くのは |
|---|---|---|---|
| 記録 | 子の気づきの記録と、判定の記録の要約 | 子のワークツリーの `wip/handoff/learnings/` | 子のセッション（自分の識別子の分だけ）と ccnavi（要約） |
| 知識（learning-wiki） | パターン・採否の記録 | `docs/wiki/`（プロジェクトは `projects/<名前>/docs/wiki/`） | 統合の子（パターン）と、提案の MR（採否の記録） |
| 反映先 | ルール・配点・フェーズ定義・テンプレート・スキル・文書 | それぞれの置き場（下の表） | ユーザが置く（ルール・配点・フェーズ定義・テンプレート）、または、ユーザが承認した子（スキル・文書。差分は子の MR で見る） |

**流れ。**

```
[集める] 子（と、あれば親）の気づきの記録 ／ 直接作業の受信箱 docs/wiki/inbox/
    ↓ 親の finish が、学び以外の検査を通したあと、親の HEAD で照合して止める
[溜める] ticket consolidate → 統合の子 <親>-00-NN (phase: 0、maintenance: learning-consolidate)
         気づきごとに「処理: 反映 <パターン>」か「処理: 対象外 <理由>」を書き、sources に観測元の ID を足す
    ↓ ccnavi --learnings が、提案の候補を決める
[提案] SessionStart の systemMessage でユーザに知らせる → 依頼を受けたエージェントが提案チケットを作る
       → MR のマージで採否が決まる（承認・却下・延期。パターンごとに 1 つに決まる）
```

#### 揮発する環境でも届くこと

作業のたびに実行環境が作り直され、追跡されないファイルが消える場合、残るのはブランチに入ったものだけ。

| 消えるもの | 残るもの（ブランチに入れば） |
|---|---|
| `logs/`（判定の記録）、`state/`、`scratchpad/`、セッションの履歴 | `wip/handoff/learnings/`、`docs/wiki/`、承認済みチケットとマーカー |

- 気づきの記録は子のブランチに入り、子の合流で親のブランチへ届く。親のセッションは別の環境でも、親のブランチを取れば全部の子の記録を読める
- `wip/handoff/` は統合先へ取り込むときに外れる（`.ccnavi/docs/scratchpad.md`）。記録は親を統合先へ取り込むまでの間だけ在る。その後も残る知識は learning-wiki のパターンで、出どころは子の識別子で指す（記録のパスでは指さない）
- 判定の記録はそのセッションの分しか無いので、子が 1 セッションなら、そのセッションの要約がそのまま子の要約になる

#### 気づきの記録

`wip/handoff/learnings/<子の識別子>.md`。1 子 1 ファイルで、frontmatter のあとに気づきを 1 件ずつ節にする。

```markdown
---
ticket: feat-12-01-01
parent: feat-12
learnings: 2
---

## git add は相対パスで打つと cwd 次第で外れる

- 種類: skill
- 信号: 落とし穴
- 内容: ワークツリーの中から相対パスで打つと別のツリーを指した
- 提案: commit スキルの references に「絶対パスで打つ」を足す
```

| 欄 | 値 |
|---|---|
| `learnings` | 気づきの数。無いときは `none` |
| `種類` | 反映先の種類。`rule` `risk` `phase` `template` `skill` `docs` |
| `信号` | `訂正`（ユーザの訂正・苛立ち）、`落とし穴`、`失敗と回避`、`誤り`（読んだ手順や文書の誤り）。拾うものと拾わないものは `.ccnavi/docs/skill-review.md` と同じ |
| `提案` | 任意。子の考える直し方 |

- 置くのは `wip/handoff/` の下（`.ccnavi/docs/scratchpad.md`）。frontmatter の検査（`NOTICE_DOC_FRONTMATTER`）の対象外
- 形は `--lint` が見る。`learnings` が数と合わない、`種類` が 6 種に無い、`ticket` が識別子と食い違う、は warn
- 子を閉じる検査は、追跡されていて空でないことだけを見る。中身の質は問わない（REQ-LRN-06）

#### 記録の操作と子を閉じる検査

`ccnavi ticket learn <子>`（ユーザかエージェントが打つ。書き込みは ccnavi が行う）。

| 状況 | すること |
|---|---|
| 記録が無い | 雛形（`learnings: none`、節なし）を書く。書く場所と形を出す |
| 記録が在る | 触らない。要約だけを書き直す |
| いつも | 判定の記録の要約を `wip/handoff/learnings/<子>.digest.json` に書く |

要約は、そのワークツリーの判定の記録（`decisions.jsonl` と同じ置き場の `decisions.*.jsonl` のうち、記録の `tree` 欄がそのワークツリーの名前のもの）から数える。記録にセッションの欄（`session`）はあるが、`ticket learn` を打つ実行ファイルはセッションの識別子を受け取らないので、ワークツリーの名前で絞る（再開したセッションや、同じ名前で作り直したワークツリーの記録は混ざりうる）。

| キー | 中身 |
|---|---|
| `counts` | `deny` `ask` `nudge` `handover` の件数（そのワークツリーの分） |
| `repeated` | 同じ呼び出しを繰り返し止めた形。ルールの識別子・ツール名・コマンド名の語・回数（回数 2 以上）。コマンド名の語は Bash と PowerShell の呼び出しだけで、環境変数の代入と `env` とそのオプションを読み飛ばし、シェルの引用を解いたうえで、先頭の語のうちパスは末尾の名前だけにする。コマンド名の形（英数字と `.` `_` `+` `-`）でない語は持たない。それ以外のツールの対象は持たない |
| `suggest` | `ccnavi --suggest` が出した候補の要点（ルールの識別子・タイプ・理由）。`message` と対象の文字列は持たない。この欄は未実装で、いまの要約には入らない（`ccnavi --suggest` 自体は実装済みで、判定の記録から候補を出す） |
| `recorded` | 判定の記録が読めたか。読めなければ `false` で、他は空。件数 0 の `true` とは別（「気づきが無い」と「拾えなかった」を区別するため。`--learnings` が分けて示す） |

- パス・コマンドの全文・環境変数の値は持たない。判定の記録には入るが、追跡して持ち出す物には入れない（記録に絶対パスとコマンド全文が入るため）
- 判定の記録が無い・読めない環境でも失敗しない。`recorded: false` で書く
- 要約は機械が書き機械が読む。ユーザとエージェントは直さない（直せば次の `learn` で書き直される）

子の `ticket finish` は、学びの蓄積が有効な親の子について、`wip/handoff/learnings/<子>.md` が子のブランチの HEAD にコミットされた通常のファイル（モードが `100644` か `100755` の blob。ディレクトリとシンボリックリンクは不可）で、空でないことを確かめる
（子の閉じる操作の検査のうち、成果物を見る `ops_close.deliverables_missing` の隣に置く。フェーズ定義の `deliverables` とは別に持つ）。満たさなければ閉じるのを拒み、置き場と `ticket learn` を示す。
`deliverables` に載せない理由は、置き場が固定で定義ごとに変える意味が無いことと、全定義に書き足すと書き漏れた定義の子だけ検査から抜けること。
`deliverables` と同じく、見るのは「在って追跡されている」ことと、空でないこと。

子の着手の出力に 1 行を足す（REQ-LRN-03）。「閉じる前に `ticket learn` を打ち、`wip/handoff/learnings/<子>.md` に気づきを書く（無ければ `learnings: none`）」。
子の起動の経路（`claude -p` のメインエージェントでも、サブエージェントでも）によらず、着手と閉じる操作は必ず通るので、この 2 か所に置く。

#### 統合の子（溜める）

親を閉じる前に、親の HEAD にあるすべての気づきを 1 件残らず判定する。判定するのは**統合の子**で、親の `finish` が止めて `ticket consolidate <親>` を案内し、メインが打つ（`finish` に止める以外の副作用を持たせないため）。親のフィードバック計画には置かない（親をまたいで育つ知識を、親 1 つのレビュー対応に載せないため。共通レイヤーの `phases.yml` と計画テンプレートから `learning-consolidate` と `learning-apply` は外した）。

| 項目 | 中身 |
|---|---|
| 識別子 | `<親>-00-<2 桁の連番>`。`phase: 0`、`maintenance: learning-consolidate`。`allow` は固定の範囲（`docs/wiki/patterns/*`、`docs/wiki/inbox/*`） |
| 作る操作 | `ccnavi-ticket.sh consolidate <親>`（`ticket consolidate`）。write-and-push に組み込み、親の操作ロックの中で、条件の確認・連番の決定（`next_child_id` のフェーズ 0）・作成・コミット・push を行う。出力で `start` を案内する |
| 打てる条件 | 学びの蓄積が `enable`。親の `finish` の学び以外の検査をすべて通る。処理すべきものの判定が 1 件以上。読み取れない記録・整合の検査に当たる記録が無い |
| 打ち直し | 開いている統合の子があれば新しく作らず、その識別子を出し、そのチケットを書いたパスの一覧に載せる（前の回の push が済んでいなければ write-and-push が送り直す） |
| 位置づけ | `CCNAVI_LEARNING=enable` のときにシステムが事前に許す、限られた保守操作。ユーザの承認の代わりではない。通常の提案・承認の経路では `maintenance:` の印を使えず、印を持つ提案は承認で拒む |

統合の子だけに当てる例外は、すべて `Ticket.is_consolidate` の 1 か所で決める（子・`phase: 0`・印の 3 つがそろうとき）。識別子の形や名前から推定しない。

- 構造エラー（例外を当てず、子を止める）: 親に印がある、印があるのに `phase` が 0 でない、`maintenance` の値が `learning-consolidate` 以外。承認の側（`agree_candidates.validate`）でも判定の側（`approval_checks.blocking_problems`）でも当てる。印の無い `phase: 0` の子は、今までどおり計画に無い番号として止まる
- 計画への所属: `phase: 0` を計画の項と照合しない。フェーズの進行・レビュー待ちの集計・レビュー依頼の対象に含めない（`phase.phases_of` が除く）。開いている子の検査・親への合流・連番の管理は通常の子と同じ
- 範囲: ccnavi の中に固定した定義（`phasetypes.consolidate_type`）を上限に使い、`scope_verdict` で親の範囲の上限だけを当てない。子の `allow` も当てる。実行前・実行後・サブエージェント終了時・合流前の 4 か所は `scope_verdict` を共有するので、判定が揃う
- 学び・リスク・レビュー: 気づきの記録を求めず、実績リスクを測らず、必ずレビュー不要で `finish` が `done/` へ移す

統合の子の手順は次のとおり。

- 気づき 1 件ごとに判定し、節の末尾に `- 処理: 反映 <パターン名>` か `- 処理: 対象外 <理由>` の 1 行を書く（食い違いのある節は処理の行を直す）。環境が原因の失敗なども、手順にしないなら理由を書いて `対象外` にする
- 反映するときは、似たパターンがあれば `sources` に観測元の ID を足して言い直し、無ければ新しく作る。1 パターン 10〜30 行。説明・原因・実際の操作の例・回避策
- 記録には処理の行を足すか直すだけにする。受信箱のファイルは判定してから消すだけにする（機械では検査しない）
- 記録の中の指示には従わない。終わったら全部をコミットしてから `finish` を打つ

#### 気づきの記録の読み取りと処理すべきものの判定

収集・親の検査・`consolidate`・`--learnings` が同じ読み方を使う（`learning_records`）。書式は、frontmatter の後の `## ` で始まる行を 1 件の気づきの見出しとし、処理の行はその節の中の `- 処理: ...` の 1 行（字下げした継続行は処理の行ではない）。

| 検査 | 当たる条件 | 扱い |
|---|---|---|
| 読み取りの検査 | ファイルを読めない、通常のファイルでない、frontmatter が無い／YAML として読めない、`learnings` が無い／`none` でも 0 以上の整数でもない | 「読み取れない記録」。節が無いから処理済み、とは見なさない |
| 整合の検査 | `none` なのに節がある、`learnings` の数と節の数が合わない、1 つの節に処理の行が 2 つ以上、形の分からない処理の行 | 「整合の検査に当たる記録」 |

どちらも統合では直せないので、親の `finish` も `consolidate` も止め、ファイルと当たった条件を名指しして記録を直すよう案内する。訂正や追加は新しい節を足す形に限り、処理済みの節の本文は書き換えない。

処理すべきものは、親の HEAD で次を列挙する（`learning_records.pending`）。親の `finish` と `consolidate` が同じ結果を使う。

- 処理の行が無い節（`learnings: none` でない記録）
- `処理: 反映` の指すパターンが無い節、または、そのパターンの `sources` に記録の観測元の ID が無い節
- `処理: 対象外` の後ろに理由が無い節
- `docs/wiki/inbox/` のファイル

#### 親の finish の検査

学び以外の検査をすべて通したあと、**親の今の HEAD** で次を見る（`learning.parent_blocked`）。統合を済ませた後でも毎回、今の HEAD で検査し直す。統合の後に親で `/learn --note` を追記したり、子を足したりしても、同じ検査が拾って再び `consolidate` を案内する（連番が進む）。

1. 記録・パターン・受信箱の置き場に、未コミットか未追跡の変更がある → コミットしてから打ち直すよう案内して止める
2. 読み取れない記録か、整合の検査に当たる記録がある → ファイルと条件を名指しして止める
3. 処理すべきものが 1 件以上 → 該当のファイルと節を名指しし、`consolidate` を案内して止める

全部の記録が `none` で受信箱も空なら、統合は要らずそのまま通る。親の記録は無くてよく、あるときだけ対象にする。`wip/handoff/` は `ready` で消え、squash でマージされるので、対象外の理由は親を閉じるまでの一時的な証跡になる。残るのは、反映したパターン（`docs/wiki/`）だけ。

#### パターンと観測元の数

`docs/wiki/patterns/<名前>.md`。失敗か、うまくいった進め方 1 つ（10〜30 行）。

| キー | 中身 |
|---|---|
| `type` | `learning-wiki` |
| `target` | 反映先の種類（`rule` `risk` `phase` `template` `skill` `docs`）。複数にまたがるときは、手順を実行する側の 1 つだけ |
| `sources` | 重複しない観測元の ID の一覧。この数を**観測元の数**と呼ぶ（「再発の回数」とは言わない）。子の記録は子の識別子、親の記録は親の識別子、受信箱は `inbox:<ファイル名から .md を除いたもの>` |
| `title` `description` `tags` `keywords` | `.ccnavi/docs/frontmatter.md` に従う |

`index.md` と `log.md` は置かない。一覧は `ccnavi --learnings`、経過は git の履歴で見る。プロジェクトの wiki は、親と同じリポジトリの `docs/wiki/` に溜め、その親の統合の子が処理する。

#### 採否の記録とパターンの状態

`docs/wiki/impact/<提案>.md`（`skill-impact.md` の後継）。提案 1 本の対象・差分・決着を残す。

| 欄 | 中身 |
|---|---|
| `proposal` `target` `files` | 提案の名前、反映先の種類、直すファイル |
| `patterns` | 動機のパターン名 → 観測元の数 |
| `status` | `承認待ち` `承認` `却下` `延期` |
| `reason` `decided_at` | 理由、タイムゾーン付きの日時（`承認待ち` では空） |

本文に差分を書く。決着するときは、`patterns` の各値を、その時点でマージ先のパターンから数えた観測元の数に書き直す（提案を作ったときの値のままにしない。提案中に観測元が増えた延期が、マージ直後に候補へ戻らないようにするため）。取り下げは延期として扱う（もっと観測されてから手順にすればよい）。

パターンの状態は 1 つに決まる（`records.wiki.pattern_status`）。

1. そのパターンを `patterns` に含む採否の記録に `承認待ち` が 1 つでもあれば「提案中」
2. それ以外は、`decided_at` が最も新しい採否の記録で決める。同じ日時なら `proposal` の名前順で後のもの。`承認`・`却下` なら「決着」。`延期` なら、今の観測元の数がその記録の `patterns` にある数より多ければ「候補」、多くなければ「決着」
3. 採否の記録が 1 つも無ければ「候補」

採否の残し方は、差分と採否の記録を同じ MR に入れ、マージを決着とする。承認は反映先の実際の差分を確かめてから書く（下書きが無いことは、取り込んだ証拠にならない）。却下・延期は差分を戻してマージする。MR を閉じただけの場合、採否の記録は統合先に入らず、パターンは候補のままで、次の通知の条件を満たしたときに、再び一覧に入る。専用のコマンド（`--learning-decide`）は持たない。frontmatter の壊れた記録は、`--learnings` と `--lint` が名指しし、無いものとして扱う。`承認待ち` のまま統合先にある記録は、`--learnings` の承認待ちの一覧に出し、ユーザが見て直す。

#### 提案の入口（`.ccnavi/docs/learning-propose.md`）

提案を始める専用のスキルやコマンドは持たない（スキルを増やすと説明文が常に文脈に入るため）。ユーザがエージェントに頼み、エージェントが `learning-propose.md` を引く。読む順は (1) `--learnings` の一覧、(2) 関係する採否の記録（却下されたものを、理由を覆す根拠なしに出し直さない）、(3) 動機のパターン、(4) 反映先の現物。提案は反映先 1 つに絞る。

| 反映先 | 直し方 |
|---|---|
| 保護対象でないもの（`.claude/skills/*` の多く、`docs/*`） | 提案チケットの中で直接直す |
| 保護対象のもの（ルール・配点・フェーズ定義・テンプレート・`.ccnavi/docs/*` など） | 下書きと取り込み（`user handoff`）の手順で直す。保護対象かどうかは、反映先のパスで決める |

#### `ccnavi --learnings` と SessionStart の通知

`ccnavi --learnings [--json]`: 指定したツリー（既定は cwd のツリー）の wiki について、パターンごとの状態と観測元の数を一覧にし、「候補」を数える。`target` ごとの内訳、閾値（`CCNAVI_LEARNING_SOURCES`、既定 3）以上かどうか、`承認待ち` の提案の一覧、壊れたファイルの名指しを出す。

SessionStart の通知（`learning_notice`）は、ユーザにだけ `systemMessage` で知らせる。`additionalContext` の今の起動案内はそのまま残し、学びの情報は足さない（wiki を作業のセッションに渡さないため）。

- 数える対象: リポジトリごと（ワークスペース自身と `projects/<名前>/`）に、`ccnavi_integration` の規則（手元の `origin/HEAD`、無ければ `origin/main`・`origin/master`）で統合先を決め、その手元の参照が指すコミットの `docs/wiki/` を git のオブジェクトから読む。チェックアウトは要らない。決められないか読めないリポジトリは、その回の通知を見送り、通知済みの記録も変えない。同じ回の `ccnavi-fetch.sh` による取り込みが終わっているかは保証しない（間に合わなければ次の回に知らせる）
- 条件と変化: 「候補」の集合を C、そのうち観測元の数が閾値以上のものを R とする。C が `CCNAVI_LEARNING_NOTICE_COUNT`（既定 5）件以上か、R が 1 件以上、かつ、通知済みの記録に無い ID が C にある、または通知済みの記録で閾値未満だった ID が R にある、のときに知らせる
- 出したら、通知済みの記録（`logs/state/learning-notice/<リポジトリ>.json`）を今の C（ID ごとに R に入っていたか）で置き換える。出さなかったときも、C に無くなった ID は外す。読めない・書けないときは空とみなす（通知が改めて出ることがある）
- まだマージされていない MR は追跡しない

#### 任意のタイミングの依頼（`/learn`）

対話セッションで、人が「これは覚えておいて」と言った気づきを、その場で記録へ足す入口。`ccnavi ticket learn [<識別子>] --note <本文> [--target <種類>] [--signal <信号>]`。`/learn` スキルはこの操作を呼ぶだけの薄い入口。

| 作業ディレクトリ | 書き先 |
|---|---|
| チケットに結び付いたワークツリー（親・子） | `wip/handoff/learnings/<ワークツリーの名前>.md` に 1 件追記。無ければ雛形を作る。`learnings` は追記のたびに数え直す |
| 直接作業のワークツリー | そのワークツリーの受信箱 `docs/wiki/inbox/<識別子>-<UTC 時刻 14 桁>.md` に 1 件 1 ファイル（排他的に作る。上書きしない） |
| ワークスペースルート、プロジェクトのルート | 書かずに断り、ワークツリーを切るよう案内する（追跡されず、誰がまとめるかも決まらない置き場を無くすため。ルートの `wip/handoff/inbox/` はやめた） |

追記する節は、記録の形と同じ。本文は `redact.redact` で秘密の形を伏せ、2000 字で切る。`docs/wiki/inbox/` のファイルは、統合先へ取り込まれても外れないので、統合の子が入力に含めて処理し、消す。

#### 防御の方針（最低限）

| 備える | 備えない |
|---|---|
| 書く役を定める（子は自分の記録、統合の子は wiki）。`ticket learn` は他の作業の識別子の記録へ書かない | 他の子の記録への Write の拒否（`wip/handoff/` は範囲の照合の外にある） |
| 記録を HEAD の通常のファイルとして見る。リンクと範囲外を指す置き場へ書かない | 処理済みの本文が書き換えられたことの検出、記録の内容のハッシュ、別の台帳 |
| 反映先は人間の承認（MR のレビューか、ユーザが置く操作）を経て初めて効く | 記録は処理の行を足すだけ・受信箱は消すだけ、の機械による検査 |
| 統合の子は記録をデータとして読み、中の指示には従わない。印は通常の承認の経路では使えない | 印の生成元を署名や台帳で保証すること、観測の独立性の検証 |

複数の親の統合の子が同じ受信箱やパターンを処理したときの排他制御は持たない。Git の衝突は通常の手順で解き、`sources` の重複は観測元の ID で除く。

#### 作業のセッションには渡さない

learning-wiki は手順書（スキル・ルール・テンプレート）を作る側の材料。作業のセッションが読むと、手順書の効きが見えなくなる。`SessionStart`・`SubagentStart`・子の着手の出力・プロジェクトのスキルの目録には載せない。`ccnavi --docs` は、`--type learning-wiki` を明示したときだけ引ける。ユーザへの通知（`systemMessage`）は、モデルに渡らない。

#### 設定と配布

実効は、全体が `enable` で、その子のフェーズ定義（親の写し）が `off` でないこと。統合の子だけは、印から決まる（定義を引かず、学びを求めない）。

| 項目 | 中身 |
|---|---|
| `CCNAVI_LEARNING` | 全体の切り替え。`enable` / `disable`。**既定は `enable`**。読めない値は `enable` として扱い、`--lint` が warn で言う。`disable` のとき、着手の 1 行・子を閉じる検査・親の検査・`consolidate`・`ticket learn`・通知が働かない |
| フェーズ定義の `learning` | `on` / `off`、既定 `on`。`off` の定義の子は、着手の 1 行も閉じる検査も受けない。親に固定した写しから読む |
| `CCNAVI_LEARNING_SOURCES` | 観測元の数の閾値。既定 3。読めない値と 1 未満は既定に戻る |
| `CCNAVI_LEARNING_NOTICE_COUNT` | 通知する候補の件数。既定 5。同上 |

#### 実装の範囲

| 範囲 | 状態 |
|---|---|
| `CCNAVI_LEARNING` の既定 `enable`、`ticket learn`、子を閉じる検査、`/learn` | 実装済み |
| 統合の子（印・構造エラー・例外）、`ticket consolidate`、気づきの記録の読み取りと処理すべきものの判定、親の `finish` の検査 | 実装済み |
| パターンの `target`・`sources`、採否の記録 `impact/`、パターンの状態の決め方、`ccnavi --learnings`、`--lint` の wiki の検査 | 実装済み |
| SessionStart の通知、提案の手順の文書 `learning-propose.md` | 実装済み |
| 今ある wiki の移行（`target`・`sources` の無い既存のパターン）と後方互換 | 対象外。`--learnings` と `--lint` が名指しする |

#### 決めていないこと

なし。次は、対象外として決めた。

- 対象外とした気づきの本文・理由を統合先に残すこと（squash マージと `ready` の削除で消える。一時的な証跡と割り切る）
- 受信箱のファイルを、消す前に判定したことの機械による検証
- 統合の最中や統合の後に、記録の追記や子の追加を禁じること（親の `finish` の検査し直しで扱う）
- 同じ親の先行の子の記録を、後の子へ渡すこと
