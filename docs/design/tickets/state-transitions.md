### 9.6 状態遷移

状態を持つ場所は 2 層で、層ごとに動かす者と条件が違う。チケットの置き場（1 本のファイルが
提案の置き場と承認済みチケットの置き場を行き来する）と、マーカー。判定に使われるのは
`.ccnavi/approved/doing/` に在る承認済みチケットだけ。マーカーが使われるのは HITL ポイントだけ。
ワークツリーの有無は状態として持たない。

**チケットの遷移**

```
                approve                     finish（レビュー要）
  todo ─────────────────→ doing ───────────────────────────→ review
  (wip/proposals)      (.ccnavi/approved)                (wip/proposals)
                            │                                  │
                            │ finish（レビュー不要）／cancel    │ confirm / decide / --reviewed / close-early
                            ▼                                  ▼
                          done ←───────────────────────────────┘
                     (.ccnavi/approved)
                            │
                            └── ユーザが手で doing/ へ戻す（再開）
```

| 遷移 | 動かす者 | 条件 | 書く欄 |
|---|---|---|---|
| 無し → `todo` | 親が `Write` / `Edit` で作る | 無し | ― |
| `todo` → `doing` | `ccnavi --agree`（ユーザ）、ボード、Chrome 拡張 | 9.4。同じ識別子がどの置き場にも無い | ―（中身は変えない。親なら `phases/<親>/workflow.yml` を置く） |
| `todo` → `doing`（手で） | ユーザが hook の外で動かす | 無し。動かせること自体が条件（その置き場にエージェントは書けない）。承認の検査は判定が当てる | ― |
| `todo`（改版）→ 消える | `ccnavi --agree`（ユーザ） | 同じ識別子が `doing/` にあり、計画だけが違う。`doing/` の側の計画を差し替える | `plan` / `feedback`（`workflow.yml` も書き直す） |
| `doing` のまま | `ccnavi-ticket.sh start` | 着手の欄が空。`.claude/worktrees/<識別子>/` がワークツリーとして在り、元リポジトリが承認済みチケットの `project` と合い、表記が大文字小文字まで同じ。子なら親が `doing/` に在って着手済みで、先行が全部 `done/` に在って取り消しでない | `started_at`、`base_sha`（そのワークツリーの HEAD） |
| `doing` → `review` | `ccnavi-ticket.sh finish` | 着手済み。子で、閉じた時点のフェーズがレビュー要（延期を含む。9.8）。種類の成果物が在り、定性のリスク判定が揃っている（9.9） | `completed_at` |
| `doing` → `done` | `ccnavi-ticket.sh finish` | 着手済み。子ならフェーズがレビュー不要。親なら開いている子が無く、レビューで止まっておらず、計画があればフィードバック計画が承認済みで全フェーズが終わっている（早めに閉じていれば子だけ） | `completed_at` |
| `doing` → `done`（取り消し） | `ccnavi-ticket.sh cancel --reason`、`close-early`（未着手の子） | 理由が空でない。親なら開いている子が無い | `cancelled_at`、`cancel_reason` |
| `review` → `done` | `ccnavi-review.sh confirm` / `decide`、`ccnavi --reviewed`、`close-early`、フィードバック計画の承認 | そのフェーズ（延期を引き受けた分を含む）のレビューが済んだ（9.10） | ― |
| 無し → `doing`（続きの子） | ユーザが `decide` / `--reviewed --chat` で選ぶ | レビューで指摘が残った（9.10）。同じフェーズの番号、範囲は見た子の和 | `followup_of`（トップレベルの欄。ccnavi が新しく作るチケットに書く） |
| `doing` → `todo`（取り下げ） | Chrome 拡張（ユーザ） | 着手前の新規の承認。`doing/` の中身が承認コミットの親の提案とバイト単位で同じ。親は、待ち方のファイルがあればその中身が承認したときの待ち方と同じ。子もマーカーも無く、続きの子でない。前の版の承認が欄（`ccnavi_approved`）を書いた古い形は、欄で決める | ―（承認コミットの親の提案のバイト列を戻す。親は `workflow.yml` も消す） |
| `done` → `doing` | ユーザが hook の外で動かす | エージェントは `Write` でもシェルでも止まる。再開の意図がレビューのやり直しなら、そのフェーズのマーカーも手で消す | ― |

スクリプトは置き場を動かして欄の行だけを書き換える。本文とユーザの書いたコメントは保つ（承認は
中身を変えずに動かすだけ）。コミットは親がする。`start` と `finish` と `cancel` は
`doing/` に在るチケットしか扱わない。未承認の提案（`todo/`）は消せばよく、取り消しの記録は要らない。
同じ識別子が `doing/` と `todo/` の両方に在るときは `doing/` の側を相手にする（`todo/` は改版の
候補か書き損じで、`--lint` が言う）。それ以外の組み合わせで 2 つの置き場に在るときは動かさない。

閉じる向き（`doing` → `review` / `done`）は範囲が消える向きなので承認は要らない。再開は範囲が戻る
向きなのでユーザの手に置く。運用の基本は、閉じたチケットを戻さず新しいチケットを作り直すことで、
再開は想定しない。された場合は、`--lint` と `ticket status` が、作業中の子のフェーズに `reviewed` が残っていることを
warn で言う（判定と `start` は止めない）。マーカーを消すかは、レビューをやり直すかどうかで、人が決める
（機構は消さない）。親を閉じても子の承認済みチケットは閉じない。

**状態の履歴。** 実行ファイルが上の表の遷移とマーカーの遷移を動かすたびに、承認済みの領域の
`events/<識別子>.ndjson` へ 1 行 1 JSON を追記する（`at` は UTC の ISO 8601、`kind`、元と先の置き場 `from` / `to`、
経路 `via` = `cli` / `terminal` / `board` / `hook`）。マーカーの履歴の行は親のファイルに `phase-mark` / `phase-reopened` /
`parent-mark` で残り、`from` / `to` は `null`。書くのは動かす操作の最下段（`approval.admit` など）で、書けなくても
状態の操作は止めず、`ccnavi: 警告: …` を標準エラーに出す（入口の `cli.run` が起動を抜けるときにまとめて出す）。
**状態は置き場で決まり、状態の履歴は補助。** 判定も状態の操作も状態の履歴を読まず、食い違ったら置き場を優先する。ユーザが hook の外で
置き場を動かした分（手での承認・再開）は状態の履歴が残らない。ボードは新しい側を `history` で受け取り、カードの
折りたためる一覧に並べるだけ（10 章）。

**先行は着手でも見る。** 子の `start` は、`predecessors` の各チケットが `done/` に在って取り消しでないことを
求める。承認でも同じ検査を当てるが、承認のあとに先行が戻された子と、置き場を手で動かして承認した子が
あるので、着手の手前でもう一度見る。止めたときは、どの先行が何の状態か（承認待ち・作業中・レビュー待ち・取り消し済み・
どこにも無い・複数の場所）と、先行を閉じる（`finish`）か、先行が要らないならユーザに承認済みチケットの欄から外してもらうか
取り消して出し直す（`cancel`）ことを sh の書き方で言う。続きの子（9.10）は、見た子のうち取り消したものを先行に入れない。
止めるのは `start` までで、書き込みは止めない（判定は `started_at` も先行も見ない）。

**`finish` の打ち忘れは `Stop` で 1 回だけ促す。** メインエージェントの `Stop` で、cwd のワークツリーに
結び付いた承認済みチケットが着手済み（`doing/`、閉じても取り消してもいない）で、そのワークツリーに未コミットの変更が無く
（追跡していないファイルも数える）、基準点より先に自分で作ったコミットがあれば（取り込んだだけのコミットは数えない。
子なら親のブランチ、親なら `origin/HEAD` にあるものとマージのコミットを除く）、`decision: block` で止めて、`finish` の sh の書き方と
「続けるなら理由をユーザに書いてから終える」を渡す（`NUDGE_TICKET_FINISH`）。同じセッションで同じチケットを同じ HEAD のまま
促すのは 1 回だけ（記録は state の置き場の `nudged-<セッション>.json`。git では共有しない）。HEAD が進めばまた促す。payload の
`stop_hook_active` が真なら促さない。state の置き場が無いか書けないときも促さない。除くのは、チケット制御かモードが `disable`、ワークスペースルートかチケットの無いワークツリー、
未着手、`blocked`、基準点が無い、子で親のブランチを引けない、親で `close_problems`（開いている子・レビュー準備中／レビュー待ち・フィードバック計画待ち・
終わっていないフェーズ）が空でない、git を読めない、`SubagentStop`。`dry-run` は止めずに文を `systemMessage` に載せる。

**子の着手は親の着手のあと。** 親が `doing/` で着手済みでなければ、子の `start` は止まる（親のワークツリーが
要る）。案内は親の置き場で分かれ、`todo/` なら承認から、`doing/` で未着手なら親の `start` から。親が
どこにも無いときと、複数の置き場にあって定まらないときも、同じ場所で止めて見えたとおりを言う。

**マーカーの遷移**

フェーズは同じ親の同じ `phase` 番号の子のまとまり。「終わった」は導出で、そのまとまりの子が `doing/` に
1 枚も無く、`review/`（レビュー待ち）か `done/`（取り消しでない）に 1 枚以上あること。取り消しだけの
フェーズは終わらない。「レビュー要」も導出（9.8）。止めているのは **終わった ∧ レビュー要 ∧
`reviewed` が無い** のとき。`pending` と `requested` は止める条件に入らない（`requested` は
呼び名を「レビュー準備中」から「レビュー待ち」へ変えるだけ。9.8）。

```
    無し ──終わった ∧ mr で見る──→ pending ──request──→ requested ──confirm / --reviewed──→ reviewed
     │
     ├────終わった ∧ chat で見る──→ pending ──────────--reviewed --chat─────────→ reviewed
     │
     └────終わった ∧ レビュー不要──→ skipped

    どのマーカーからも: 同じ番号に子が承認される ──→ 無し
```

| 遷移 | 動かす者 | 条件 |
|---|---|---|
| 無し → `pending` | `PostToolUse` の告知（cwd が親のワークツリー） | 終わっていて、マーカーが 1 つも無く、レビュー要。文を 1 度だけ返す |
| 無し → `skipped` | 同上 | 終わっていて、マーカーが 1 つも無く、レビュー不要（または延期） |
| 任意 → `skipped` | `ccnavi-review.sh close-early`（ユーザ） | 終わっていないフェーズの全部に置く（9.11） |
| 任意 → `requested` | `ccnavi-review.sh request`（親） | 9.10 の前提と ELI5 の HTML（`--eli5`。`wip/` の下にコミット済み）。`pending` は要らない |
| `requested` → `reviewed` | `ccnavi-review.sh confirm`（親）、`ccnavi-review.sh decide`（ユーザ）、フィードバック計画の承認、`close-early` | 変更要求のレビューが無い。`confirm` は未解決が 0、`decide` は未解決をユーザが受け入れる（続きの子を起こす選択ではマーカーは置かず、そのフェーズのマーカーを消す）。置いたときに `review/` の子は `done/` へ動く |
| `pending` → `reviewed` | `ccnavi-review.sh chat <N>`（ユーザが端末で。中身は `ccnavi --reviewed <N> --chat`） | 見る場所が `chat`。依頼の記録は要らない（9.8） |
| 任意 → 無し | `ccnavi --agree` で同じ番号の子が承認された | 4 種を全部消す |

マーカーはユーザが子を再開しても残る（機構は消さない）。再開は想定しない運用で、された場合は `--lint` と
`ticket status` が、作業中の子のフェーズに `reviewed` が残っていると warn で言う（閉じ直したときにレビューが要らないフェーズ、つまり種類が `review: none` で、再開された子も
`human_review` を求めていないフェーズは言わない。判定と `start` は止めない）。再開の意図がレビューのやり直しなら、そのフェーズのマーカーを人が手で消す
（マーカーがあるツリー、つまり `approval.home_dir` が決めるツリーで `ccnavi-git.sh rm .ccnavi/approved/phases/<親>/<N>.reviewed`
を打ち、削除をコミットする。取り込み済み（origin があり、取り込み状態が present）で、chat だけの親子でなければ、
`ccnavi-push-approved.sh <親>` が取り込んでからコミットして送る。それ以外の親子では、名指しの
`ccnavi-push-approved.sh <親>` は「ここではコミットも push もしない」と出して終わるので、ユーザが自分でコミットする。
引数なしの `ccnavi-push-approved.sh` は、置き場に変更のあるツリーを全部コミットする）。
警告文は、そのツリーをワークスペースルートからの相対で言う。
マーカーが未コミットのときは `git rm` が拒む（一度もコミットしていなければ「どのファイルにも当たらない」、
コミット後に書き換えていれば「手元の変更がある」）。`-f` は `ccnavi-git.sh` が通さないので、先に
`ccnavi-push-approved.sh <親>` でコミットしてから `rm` するか、ファイルを直接消す（消したことは次の
`ccnavi-push-approved.sh <親>` がコミットする。一度もコミットしていなければ消すだけで済む）。続きの作業だけなら、残してよい。
延期したフェーズ N の子を再開したときも警告する。ただし、引き受けた側 M（ゲートと同じく、承認済みの親の待ち方のコピーから引く。`N.skipped` の `deferred_to` ではない。
改版で引き受け手が動くと `deferred_to` は古くなる）に `reviewed` が
残っているときだけ。M のレビューが見たのは再開前の作業だけで、再開後の作業は誰のレビューも通らないため。M がまだ
レビュー前なら、これからのレビューが再開後の作業も覆うので言わない。M がレビュー不要なら、ゲートが `reviewed` を見ないので
言わない。消すのは M の `reviewed` で、`N.skipped` は消さない（手順は上と同じ）。

**2 層の組み合わせで決まるもの**

| 見るもの | 使う層 | 決まり方 |
|---|---|---|
| `Write` / `Edit` の判定 | チケットの置き場、ワークツリー | 行き先のワークツリーと同じ識別子の `doing/` の承認済みチケット。無ければルールだけ |
| `SubagentStop` の範囲外の検査 | チケットの置き場 | cwd のワークツリーが子ならその子、親ならその親の `doing/` の子の全部。基準点は承認済みチケットの `base_sha` |
| HITL ポイント | チケットの置き場、マーカー | cwd のワークツリーと同じ識別子の `doing/` の親 → その子の置き場で「終わった」→ マーカー |
| レビューの依頼の前提 | チケットの置き場、マーカー | 終わっている、`requested` が無い、ほか git の条件 |
| `SubagentStart` の一覧 | チケットの置き場、ワークツリー | cwd のワークツリーが親ならその親の `doing/` の子、子ならその子 |
| `--agree` の承認待ち | チケットの置き場 | `todo/` に在って同じ識別子がどの置き場にも無い提案と、親の改版 |
