### 9.17 複数人・別 PC・別セッションでの作業

ここは、チケット単位の分担という使い方の意図と、実装が実際に同期し状態を更新する単位との対応を書く。
要求は [要件 REQ-TKT](../../requirements/tickets.md)。利用者向けの説明は [docs/guide/multi-pc.md](../../guide/multi-pc.md)。

#### 利用の前提

- 1 台の PC・1 つのセッションで完結する個人作業に限らず、複数人での開発を想定する
- チケット（親と子）ごとの作業を、それぞれ別の PC・別の Claude Code セッション・別の人が進められる
- 作業者のセッションとレビュアー（承認者）のセッションが別でも動く。同じセッションの会話履歴や同じ PC のローカルな状態に頼らない
- サブエージェントによる分担（同じ PC・同じセッション。9.12）とは別のものとして扱う。前者だけを並行開発の説明にしない

#### 何を共有し、何を共有しないか

運び手は親のブランチ 1 本とホストである。

| 種類 | 置き場 | 備考 |
|---|---|---|
| 承認済みチケット、フェーズのマーカー、`ready.json` `close-early.json` `closed.json`、子の記録（`.risk.json` `.judge.json` `.flow.json`）、子のフロー、気づきの記録 | 親のブランチ（9.2 の表） | 各 PC では親のブランチをチェックアウトした親のワークツリー（`.claude/worktrees/<親の識別子>`）の中だけを正とする。ほかのツリーのコピーは診断にだけ使う |
| 子の成果物 | 子のブランチ → 親のブランチ | 子の `finish` が親へ合流して push する |
| 提案（`wip/proposals/`） | それを持つリポジトリのツリー | コミットして運ぶ |
| マージリクエストとレビューのスレッド、その解決状態 | ホスト | sh が取得した結果（JSON）を判定の材料にする（P11） |
| レビュー依頼の内容（コミット・マージリクエストの番号・URL） | 親のブランチ上の `.requested` マーカー | 依頼を出した人のセッションが無くても、確認の側が読める |
| 退避（`logs/archive/`）、親を閉じた後の片付けの記録（`logs/state/retire/<親>.json`） | その PC のローカル | 退避はバックアップで、閉じたかは退避ではなくホストへの問い合わせで決める。片付けの記録は `ready` を打った PC にだけあり、片付けの列挙元になる |

#### 取得・同期・引き継ぎの手順

| 場面 | 手順 | 担当 |
|---|---|---|
| セッション開始 | `ccnavi-fetch.sh` が親のブランチと統合先を取り、早送りだけで進める。届かなければ止めず、手元の版で判定して「リモート未確認」と示す。fetch 1 回の期限は `CCNAVI_FETCH_TIMEOUT`（既定 15 秒） | hook（SessionStart） |
| 別 PC で親を始める | `ccnavi-start.sh --mr <番号>` か `--issue <番号>`。origin から取って早送りし、最後に `ccnavi-sync.sh <識別子>` を打つ | ユーザ |
| 親が分かれた | `ccnavi-sync.sh [<親>]` が取り込む。衝突したら自分が始めた merge だけ取りやめる。取り込み後に判定し直し、error があれば表示して終了コード 1 にする | ユーザ |
| 親のブランチへの push | 親のワークツリーのブランチは、push の前に共通の push の関門（`ccnavi_push_gate`）を通す。リモートから消えた親のブランチを作り直す形を止める。`ccnavi-git.sh push`・write-and-push・`ccnavi-user-push-approved.sh` の 3 経路が同じ関門を使う（9.2） | `ticket` / `review` の sh |
| 状態を書く操作 | write-and-push（`ccnavi-common-write-and-push.sh`）が、ロック → 取り込み → 書く → コミット → push → 届いたかの確認の順で進める。push が通らなければ戻して取り込み直し、1 回だけやり直す。再び通らなければ戻して `ccnavi-sync.sh` を案内して終わる | `ticket` / `review` の sh |
| 提案を送る | `ccnavi-ticket.sh propose <識別子>` が、親のワークツリーの承認待ちの提案（`wip/proposals/todo/`）と子のフローの下書き（`wip/proposals/flows/`）を、write-and-push の手順（ロック → 取り込み → コミット → push）で親のブランチへ送る。書き終えた提案を、別 PC で承認できるようにする。サブエージェントは打てない | メインエージェント |
| 子の着手 | `ticket start` が、取り込み直後の親のブランチから子のワークツリーを作る | メインエージェント |

親のワークツリーが無い PC、HEAD のブランチ名を変換した識別子がフォルダ名と合わない PC では、承認・状態の操作・実行前チェックが止まる。
ボードにはその親子のチケットが出ない。`ccnavi-start.sh --mr <番号>` で用意してから続ける。

#### レビュアーのセッションが別でも動く理由

- 依頼は、本文とマーカー `phases/<親>/<N>.requested`（`head` `mr` `url` `host` `since`）として親のブランチに残る
- 確認（`review confirm`）は、sh がホストからスレッドとレビューを取得して JSON にし、実行ファイルがそれを材料に判定する。
  未解決のスレッドは付いた時刻で絞らず数え、変更要求はレビュアーごとの最新だけを見る
- 受け入れた指摘は、ホストのスレッドに返信を残して解決済みにする

#### 承認者・レビュアーの操作の入口

| 入口 | 動くところ | 書くもの | 作業者側への反映 |
|---|---|---|---|
| Chrome 拡張 | 承認者のブラウザ。トークンだけで、同梱の ccnavi（Pyodide）が同じ判定のコアを呼ぶ | 親のブランチへ 1 コミット（承認・レビュー済み・「始める」）。GitHub は `expectedHeadOid` で書く時点の先頭を確かめ、GitLab は Commits API でファイル単位の確認をする。保護されたブランチと統合先へは書かない | 次の `fetch` / `sync` |
| VS Code のボード | ユーザの VS Code。拡張が ccnavi の実行ファイルを子プロセスで呼ぶ | 承認は `user agree --yes`。端末の入力は要らない。エージェントが同じ形を打つことは組み込みの deny（`builtin:guard-ticket-approval`）が止める | 同じ PC の作業ツリー。承認後の push は統合ターミナルへ送る |

拡張は表示と書き込みの入口である（P10）。

#### 保証しないこと

実装に裏付けのある制約だけを挙げる。ここに無いことは約束しない。

- **リアルタイム同期ではない。** 取得は `fetch` / `sync` / push の操作の時点で行う
- **同じ親へ複数の PC から同時に書くことは保証しない。** ぶつかったら止まる。排他のロックは同じ PC の中の write-and-push だけが持つ。
  同じチケットを複数人が同時に編集しても安全であることは約束しない
- **競合を完全には自動で解決しない。** write-and-push の push が通らなければ 1 回だけやり直して止まる。Chrome 拡張（GitHub）は先頭が動いたら判定し直して最大 3 回やり直し、書けなければユーザの対応に切り替える。
  GitLab はファイル単位の確認と事後確認までで、別々のファイルを同時に書く競合は検出できない
- **オフラインで進められる状態更新は限られる。** `ccnavi-sync.sh` は `ls-remote` に失敗すると止まり、push は届かない。手元の版での判定は続く
- 未送信のコミットがあると、次の write-and-push の操作が止まる
- 親のブランチの書き手の識別や警報はしない。自分が出したレビューを自分で通すことは防がない（ホストのブランチ保護の仕事）
- 閉じたかどうかは、マージリクエストの状態を引けなければ推定せず止まる
- 親のブランチがリモートから消えたことは、`ccnavi-sync.sh`・push の関門・セッション開始の fetch の時点で分かる。オフラインの hook では消失が分からない
- 閉じた識別子の再利用は、`ccnavi-start.sh` の開始時の照会だけが検知する。オフラインと承認の経路では検知しない
- 同じ識別子のチケットが複数の置き場にあれば、状態の操作は止まる

分担の意図の単位はチケット（子）だが、同期と状態更新の単位は親のブランチ 1 本（コミットと push）である。
