### 9.2 置き場

| 何 | 場所 | 誰が書く | git |
|---|---|---|---|
| 提案（親も子も） | `wip/proposals/<状態>/<識別子>.md`（ツリーのルートからの相対）。状態は `todo`（承認待ち）と `review`（レビュー待ち）の 2 つの置き場。プロジェクト向けはそのプロジェクトの側に置く（11 章） | `todo/` は親が書く。`review/` へ動かすのは `ccnavi-ticket.sh finish` だけ | それを持つリポジトリにコミット |
| 承認済みチケット | 親チケットのツリーの `.ccnavi/approved/<状態>/<識別子>.md`（ツリーのルートからの相対）。状態は `doing`（作業中。判定が読むのはここだけ）と `done`（閉じた。取り消しは `cancelled_at` を持つ） | `doing/` へは `ccnavi --agree`（ユーザ）と、ユーザが `decide` で起こす続きの子。`done/` へはユーザのレビュー（`confirm` / `decide` / `--reviewed` / `close-early`）、レビュー不要の `finish`、`cancel`。コミットと push は `ccnavi-push-approved.sh`（9.4） | 親のブランチにコミット |
| フェーズのマーカー | 同 `phases/<親>/<N>.pending` / `.requested` / `.reviewed` / `.skipped` | hook、レビューのスクリプト、`ccnavi --reviewed` | 親のブランチにコミット |
| 親のマーカー | 同 `phases/<親>/ready.json` / `close-early.json` / `closed.json`、受け入れた指摘の `accepted.json` | レビューのスクリプト、`ticket finish <親>`、ユーザ | 親のブランチにコミット。`ready` は Draft を外す前に、閉じた親子のチケットと一緒にワークスペースの `logs/archive/<リポジトリ>/phases/<親>/` へ退避する（ブランチでは他の機械へ届かなくなる） |
| 閉じたチケットの退避 | ワークスペースの `logs/archive/<リポジトリ>/`（承認済みの領域と同じ構成）と、ready のマーカー `ready/<親>.json` | `ccnavi-review.sh ready`（実行ファイルの `review ready`）だけ。エージェントの書き込みは記録の保護が止める | 入れない（`logs/` は git が追跡しない） |
| 子の記録 | 同 `phases/<親>/<子>.risk.json` / `.judge.json` / `.flow.json`（着手のときのフローのハッシュ。9.3.1） | `ticket finish` / `ticket record-risk` / `ticket start` | 親のブランチにコミット |
| 気づきの記録 | 子（と親）のワークツリーの `wip/handoff/learnings/<識別子>.md` と `.digest.json`（9.16）。直接作業は `docs/wiki/inbox/`、ルートは `wip/handoff/inbox/` | `ticket learn`、子のセッション | 子の合流で親のブランチへ届く。`wip/handoff/` の分は統合で外れる |
| 状態の履歴 | 同 `events/<識別子>.jsonl`（9.6。1 行 1 JSON の追記だけ） | 状態を動かす実行ファイル（承認・`ticket` と `review` の副命令・`--reviewed`・`close-early`・hook の告知）。書き換え・消すコードは無い | 親のブランチにコミット（`ccnavi-push-approved.sh` が置き場ごとコミットして push する） |
| 子のフロー | 同 `flows/<子>.yml`（9.3.1） | ユーザ（ボードのフロー編集画面）。エージェントの Write / Edit は判定が止める。承認で提案のツリーから一緒に動く | 親のブランチにコミット（`ccnavi-push-approved.sh` が置き場ごとコミットして push する） |
| 子のフローの下書き | フローと同じツリーの `wip/proposals/flows/<子>.yml`（9.3.1。効力は無い） | 頼まれたエージェント。ユーザがフロー編集画面で取り込み、保存が成功したら同じ中身のときだけ消す | 書いたエージェントがコミットしてよい。取り込んで消えた削除は `ccnavi-push-approved.sh` がフローと一緒にコミットして push する |
| テンプレートの下書き | 提案の置き場の `wip/proposals/templates/<名前>.yml`（そのツリーの。プロジェクトのツリーならそのプロジェクトの下。9.15。効力は無い） | 頼まれたエージェント（`ccnavi --templates --draft <親>` か直接）。ユーザが `ccnavi --templates --import` で取り込み、書けたら同じ中身のときだけ消す | 書いたエージェントがコミットしてよい。取り込んで消えた削除は `ccnavi-push-approved.sh` が承認済みチケットの置き場の変更と一緒にコミットして push する |
| ワークツリー | `.claude/worktrees/<識別子>/` | 親が git のラッパースクリプトで切る | 管理外 |

状態は置き場で表す。チケットは 1 本のファイルで、2 つの置き場を行き来する。ユーザが動かす
向きは `.ccnavi/approved/` へ（承認・レビュー済み・受け入れ・早めに閉じる）、エージェントが動かす向きは
`wip/proposals/` へ（提案を書く・`finish` でレビュー待ちにする）。

```
  wip/proposals/todo ──ユーザが承認──→ .ccnavi/approved/doing
                                          │
                              エージェントが finish（レビュー要）
                                          ▼
  wip/proposals/review ──ユーザがレビュー──→ .ccnavi/approved/done
                                          ▲
                              エージェントが finish（レビュー不要）／cancel
```

`review/` への直接の作成・移動は、`Write` でもシェルでも、誰がやっても組み込みが止める
（`Write` 系は `builtin:ticket-state`、シェルは `builtin:ticket-state-shell`）。`.ccnavi/approved/` は
ccnavi ディレクトリの組み込みルール（`builtin:guard-project-home`）が止める。`todo/` への作成と編集は自由。
シェルの `cp` `ln` `install` は、組み込みの保護（11.6）と同じ部品で行き先を読む（`-t <dir>` の値か、選択肢でない
最後の引数）。`cp -t wip/proposals/review <提案>` も、行き先のあとに選択肢を回した形も止まり、置き場から外へ写すだけの形は止めない。
提案の置き場そのものを行き先にして、元の名前が状態の名前（`review`）か名前の決まらない形（`cp -r /tmp/review wip/proposals/`）も止める。
置き場の名前が状態名と大文字小文字まで一致しないディレクトリは読まない。

ワークスペースルート直下はチケットを持たない。

提案の置き場は `wip/proposals/`、承認済みチケットの置き場は `.ccnavi/approved/`（どちらもツリーのルートからの相対）。
置き場はこの 2 つに固定で、環境変数では動かない。sh と VS Code 拡張も同じパスを見る。

**承認済みチケットは git で共有する。** 承認した機械と作業する機械が違っても承認が届くよう、承認済み
チケットもマーカーも親チケットのブランチに乗せ、`ccnavi-push-approved.sh` がコミットして push する（9.4）。
受け取る側では、セッションの最初に `ccnavi-fetch.sh` が fast-forward で取り込む。同じ sh が、ワークツリーの
起点になる統合先（`CCNAVI_INTEGRATION_BRANCH`、無ければ `ccnavi-sync.sh` の取り込み結果、無ければデフォルトブランチ＝
`origin/HEAD` が指すもの）も、チェックアウトされていなければ `update-ref` で
進める。統合先の決め方は `ccnavi-common-state.sh` の `ccnavi_integration` にまとめてあり、`ccnavi-git.sh` は
その名前への直接の push を（`main` などの固定のリストと同じく）拒み、`ccnavi-review.sh` はそれをマージリクエストの宛先にする。
リモートに届かないときは手元の版で判定を続ける。fetch は 1 回ずつ時間を監視して打ち切り、hook の
上限に当たらないようにする。

親のワークツリー（`.claude/worktrees/<P>` で、HEAD のブランチ名を変換した識別子がフォルダ名と合うもの）は、SessionStart では
早送りだけにし、ロックが取れなければ飛ばす。取り込み状態の有無は問わない。分かれた親子のチケットの merge、リモートから消えた
親のブランチの確かめ（閉じたかは MR がマージ済みかで決める。ホストに聞けなければ推定せず止まる）、親子のチケットの取り込み状態と
統合先の取り込み結果（`logs/state/sync/`）の書き出しは、ユーザが打つ `ccnavi-sync.sh` が持つ。統合先は
`CCNAVI_INTEGRATION_BRANCH`（無ければホストのデフォルトブランチ）で、設定した名前がリモートに無ければ止める。
親子のチケットの取り込み状態（`sync/<リポジトリ>/families/<P>`）の鍵は親の識別子で、中の `branch`・取得した sha・同期結果・
MR の番号はキャッシュ。判定、C1 の対象、早送りの対象には使わない。sh は親のブランチ名を実行ファイルの
`ccnavi c1 family <P>` の `branch` の行で知る（親のワークツリーの HEAD から読んだ名前）。
`ccnavi-sync.sh` は取り込んだ後に `ccnavi sync check <P>` でその親子のチケットを判定し直し、error があればその取り込み状態を
`blocked` にして止める（理由を直して打ち直せば `present` に戻る）。MR がマージ済みと分かったら、手元の片付け
（`ccnavi sync tidy`。9.11）を行う。

**`ccnavi-git.sh` の中の判定は P13 の例外。** git の入口は `ccnavi-git.sh` 1 本に寄せてあり（生の
`git` は組み込みでいつも止まる）、その中で次の可否を sh が一次に判定する。チケットに結び付くブランチの `integrate` を断る
（`integrate-ticket`）、統合先への push を断る、取り込み状態が `gone` なら push を断る、親のワークツリーでの
`checkout`・`switch` の行き先を、今のブランチと、変換した名前がフォルダ名になるブランチに限る（`worktree add` も変換した名前の
形だけ）。`integrate` / `integrate-done` の状態操作（取り込みの記録・`merge --squash`・取り込んだブランチの
`update-ref -d`）も sh が持つ。例外に入るのは、生の操作が組み込みで止まり、ラッパーが許可リストで読み、判定の材料のうち
チケットの中身を実行ファイルに聞くものだけ。sh はチケットの YAML を読まず、親のワークツリーかは `ccnavi tree parent`、
親のブランチ名は `ccnavi c1 family`、閉じたかは `ccnavi sync closed` の 1 行の答えで決める。答えが得られないときは、
止める側の検査は止める向きに（`integrate` は断り、checkout は親のワークツリーとして狭める）、ツリーを動かす側
（`ccnavi-fetch.sh` の早送り、`ccnavi-sync.sh` の取り込み・閉じたかの見分け）は動かさない向きに倒す。

**正とする側。** 全部の親子のチケットで同じく、親のブランチに固定する。手元では `.claude/worktrees/<P>`（HEAD のブランチ名の
`/` を `-` に置き換えたものが `P` になるツリー）で、ほかのツリーのコピーでは代用しない。取り込み状態はキャッシュで、
有無では判定を変えない。記録が無くても、親のワークツリーがあれば決まる。
判定は git もネットワークも使わず、取り込み状態を読むだけ（取り込み状態の途中のシンボリックリンクは辿らず「破損している」とし、
統合先の取り込み結果の入れ替えの一瞬は少し待って読み直す）。

- 親のワークツリーが無い、HEAD のブランチ名を変換したものがフォルダ名と合わない、取り込み状態が `gone`・`blocked`・破損している:
  **決まらない**。その親子のチケットの承認・状態の操作（着手・終了・取り消し・記録・レビューのマーカー）・実行前チェックを止め、
  準備のしかた（`ccnavi-start.sh`）を出す。ボードでは「このPCでは未準備」のカードと「準備する」ボタンになる
- 閉じた親子のチケット: 統合先の取り込み結果の `done/` に、手元の親と同じ親のチケットがある（同じ親かは、スクリプトだけが書く欄を
  `base_sha` → `started_at` → `cancelled_at` の順に見て、最初に両方が値を持つ欄が同じかで決める。どの欄でも照合できないときと、
  親のワークツリーに親のチケットが無いときは「閉じていない」とし、止めて戻し方を出す）。閉じたかの第一の根拠は MR がマージ済みかで、
  `ccnavi-sync.sh` がホストに聞いて、親の片付けまで行う（9.11）。取り込み状態の `closed` や手元の退避（`logs/archive/`）からは
  推定しない。Python（`syncstate`）と `ccnavi-sync.sh` は同じ順で見る
- 親子のチケットの取り込み状態は、親のワークツリーを片付けても消えず、止めは外れない。MR がマージされて手元を片付けたときに消える。
  捨てた親子のチケットの取り込み状態は、片付けた後にユーザが `ccnavi-sync.sh --forget <P>` で消す（エージェントの Bash は組み込みの
  deny が止める）
- 親のワークツリー以外にあるチケット（ワークスペースルートや子のワークツリーに残った古いコピー、元ツリーに未コミットで残った
  チケットなど）は、`--lint` の診断にだけ使い、正としては扱わない。承認も、親のワークツリーの上の提案だけを対象にする
- 取り込んだことがあるリポジトリ（`sync/<リポジトリ>/`）では、新規の提案の識別子を統合先の取り込み結果の `done/` と比べる。閉じた識別子は
  承認しない。統合先の取り込み結果が無い・破損している・入れ替えが終わらないときも、確かめられないので「決まらない」として承認しない
  （理由を出す）。同じ識別子の再利用は、開始時にホストへ同名のブランチにマージ済みの MR が無いかを聞いて確かめる
- 先行は親のブランチ上のチケットで読み直し、決まらなければ満たさない（厳しくする向きだけ）
- 親のワークツリーに途中の操作（merge・rebase など）があって HEAD がブランチを指さないときも決まらない（文面で途中の操作を名指しする）
- 止めの解除（`gone`・`blocked`）はオンラインで打つ `ccnavi-sync.sh <P>` だけ
- レイヤー（フェーズ定義・ルール・配点）は、手元では作業ツリーから読む（統合先のレイヤーから
  計算するのは Chrome だけ）。統合先の取り込み結果のレイヤーとの違いと、親のブランチの上のプロジェクトのレイヤーの食い違いは
  `--lint` の warn で言う

既知の制限: 承認は push するまで他の機械には反映されない。承認の記録は履歴に残る。ccnavi が入っていない機械の
エージェントが偽の承認済みチケットを push できる（防ぐには承認への署名が要る。未実装）。

承認済みチケットの置き場は ccnavi ディレクトリ（`.ccnavi/`、11 章）の下で、組み込みの
`builtin:guard-project-home` が丸ごと守る。ccnavi ディレクトリの外に向けると `--lint` が error で言う。
提案の置き場は親が書くので、ccnavi ディレクトリの外に置く。

**正とするのは親のツリーの版 1 つ。** 子のワークツリーにも同じ承認済みチケットが checkout されるが、読むのは
親のツリー（親のワークツリー）の側だけ（子のワークツリー上の古いチケットから、閉じたチケットを復活させない）。親のワークツリーが
無い、そこにチケットが無い、複数のリポジトリにまたがるときは、ほかのツリーのコピーで代用せず、正とするツリーが決まらない
（`ticket_fold.authority` が `None` を返す）。状態の操作は止まる。
