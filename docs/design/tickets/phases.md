### 9.7 フェーズ定義と計画

番号だけのフェーズは「2 番目のまとまり」以上のことを言わない。`phases.yml`（親の `project:` が指す config の 1 本。足し算はしない。11.4.1）に
**フェーズ定義**を書き、親が `plan:` にその並びと順序（項の `after`）を書くと、フェーズに意味が付く。
フェーズ定義はユーザが持つ設定で、エージェントは書き換えない（コアファイル。8）。組み込みの既定は無く、
親の `project:` が指す `phases.yml` が無ければ、フェーズは番号だけの挙動になり、`plan:` は読めない。共通レイヤーには `phases.yml` を置けない（置けば `--lint` が error）。

| 欄 | 意味 | 使われる場所 |
|---|---|---|
| `kind` | `work` は全体計画に、`feedback` はフィードバック計画にしか置けない。既定 `work` | 承認 |
| `title` | ユーザ向けの名前。id と title はどちらも一意。重なれば `--lint` が error | 承認、案内 |
| `review` | `none` / `chat` / `mr`（既定）。そのフェーズの終わりにユーザがどこで見るか。`chat` はこのセッションで見る（ホストへ出ない。9.8）。既定であって上限ではない。`feedback` のフェーズ定義に `none` は書けない | HITL ポイント |
| `scope` | このフェーズ定義の子が宣言できる範囲の上限（glob のリスト）。省略か `inherit` なら親の範囲。子 ⊆ フェーズ定義 ⊆ 親。大文字小文字はどの機械でも区別しない（チケットの範囲と同じ規則。9.3）。超えても承認は止めず、承認画面に「チケットで編集対象としているが、書き込めない場所」として出す（9.4）。判定は子の範囲をこの上限でも切り詰める（9.5） | 承認（警告）、判定 |
| `deliverables` | フェーズを閉じる前に、親か子のワークツリーに在って追跡されているべきファイル（glob）。中身は見ない | `ticket finish` |
| `agent` / `when` | 案内。`agent` は `SubagentStart`、`when` は次のフェーズを促す文に出す。判定には使わない | 案内 |

**フェーズ定義は順序を持たない。** どのフェーズがどれを待つかは、親の計画の項の `after` が決める（下）。
前の版の `order`（ファイルの頭）・`after`・`overlap`・`requires`（フェーズ定義の欄）が残っていれば、読まずに通し、
`--lint` が warn で「読まない。順序は親の計画の項の `after` で決める」と言う。error にしないのは、更新した直後に
全部の計画の承認と `--lint` が止まらないようにするため。並行させたいかは計画ごとに違うので、形を定義で 1 つに
決めない。並行してよい組（前の `overlap`）は線を引かないことで書け、一緒に置くべき定義の組（前の `requires`）は
フェーズ定義の `when` の案内に書き、承認画面の待ちの一覧でユーザが見る。

**待ち方は計画の項の `after` から都度計算する。** 計算するのは判定・承認・`--explain` が承認済みチケット（と提案）を
読むたびで、ファイルにもチケットの欄にも持たない。承認済みチケットの計画は承認済みの置き場にあり、変えられるのは
改版（`--agree`）とユーザの手だけなので、計算の元も固定されている。`phases.yml` は計算の入力にならないので、
**承認したあとに `phases.yml` を直しても、進行中の親の待ち方は変わらない。** チケットの状態も入力にならず、提案も
承認済みも同じ関数で計算する。決まりは 2 つだけ。

- 項の待ちは、項の `after` を推移的に辿った全部の番号。`after` を書かない項は何も待たない（すぐ始まる）。
  同じフェーズ定義を 2 回置いても、`after` を書かなければ並行する
- 延期した項は、それを待つ延期していない項のうち、番号のいちばん小さいものが引き受ける

フィードバック計画は、いまは一直線（全体計画の番号を全部と、前のフィードバックの番号を全部待つ）で読む。
延期の引き受け手は同じ決まりで、一直線なら次の延期していない番号になる。
決まりを直すと進行中の親の待ちも変わるので、計画と待ち方の見本の表（`tests/fixtures/plan-waits.json`）を
テストで固定して見張る。

前の版の `--agree` が書いていた待ち方のファイル（`<承認済みの置き場>/phases/<親>/workflow.yml`）は読まない。
残っていれば `--lint` が「読まない」と warn で言い、ユーザが消す。提案と承認済みチケット（前の版の承認の記録を持つ
古いものを除く）に `workflow:` の欄があれば、`--agree`・`--lint`・判定が error にする（欄は読まないので、書いてあると
効くと読み手に思わせる）。

親の計画は `plan`（全体計画。作業フェーズ定義のリスト）と `feedback`（フィードバック計画。
フィードバック対応フェーズ定義のリスト）。項は名前だけか `{type, review, after}`。

```yaml
plan:
  - research                                  # 1。何も待たない
  - {type: design, after: [1]}                # 2
  - {type: acceptance, after: [2]}            # 3
  - {type: implement, after: [2]}             # 4。3 と並行
  - {type: implement, after: [3, 4], review: defer}   # 5。同じ定義の 2 回目も番号で指す
  - {type: docs, after: [5]}                  # 6。終端（ほかの全部を推移的に待つ）
feedback: [implement-feedback]                # 7。全体計画の続きの番号
```

`after` は、先に閉じてレビューが済んでいるべき項の番号のリスト。指せるのは**自分より小さい番号だけ**で、
番号の並びがそのまま実行できる順になり、循環は書けない。`feedback:` の項が指せるのはフィードバック計画の番号だけ
（全体計画はフィードバック計画の前提として全部済んでいる）。同じ番号を 2 度挙げたら 1 つにまとめ、`--agree` が warn を出す。
エージェントは `--explain` の「待つ: 1, 2」をそのまま `after` に写してよい（推移的に並べても意味は同じ）。
`after` の形の誤り（リストでない、整数でない、`true`、範囲の外、自分以上の番号、フィードバック計画から全体計画を
指す）はチケットを読む段では落とさず、誤った線は待ちに数えない。承認と `--lint` が error で言い、判定は親を止める（下）。

`review` に書けるのは `mr`（フェーズ定義の `review` が `none` でも要る）と `defer`（延期。後ろでこの項を待つ
フェーズのレビューに含める）だけ。引き受けるのは、延期した項より後ろで、その番号を待つ項のうち、**延期していない**
番号のいちばん小さいもの（延期した子孫は飛ばして辿る）。引き受け手のフェーズ定義が `review: none` なら承認が error を
出す。引き受け手が居なければ、承認が error を出す。延期の引き受け手を読む側（`review_at` を使う箇所）は、みな計画から
計算した待ち方を読む。最後の項は `defer` にできず、フェーズ定義の `review` が `none` の項も延期できない。番号は全体計画が
1 から、フィードバック計画がその続き。`feedback` が無いのは「まだ計画していない」、`[]` は「見たうえで対応なし」。

**延期は省略ではない。** 延期したフェーズでは止まらず、次にレビューがあるフェーズの依頼が
延期した分も含めて出る。マーカーは「レビューがあるフェーズの番号」に付く。

**合意は全部 `--agree` を通る。** 全体計画は親の承認。各フェーズの計画は、その番号の子を提案して
承認を受けること。別の文書は求めない。子の題・理由・範囲・本文が計画そのもので、承認画面が
それを見せる。フィードバック計画は `feedback:` を足した親の改版の承認で、全体計画の最後の
レビューが済んでから 1 回だけ。指摘が無くても `[]` で出す。承認画面はユーザが受け入れた未解決スレッドの数を見せ、状態の履歴の `revised` に `feedback: true` が残る。前提は、全体計画の
フェーズが全部終わり、最後のフェーズのレビューを依頼してあること（通っていなくてよい）。

**順序は承認で止める。** N 番目の子は、N 番目が待つ番号（計画から計算した待ち）が全部閉じてレビュー（延期でなければ）
が済むまで承認されない。フィードバック計画を同時に出した最後のフェーズは例外。待たない番号は開いていても待たない。

計画には、承認で次を確かめる（全体計画とフィードバック計画に同じ規則を当てる）。

- **`after` の形。** 上の誤りは error
- **終端は 1 つ。** 最後の項が、それより前の全部の項を推移的に待つこと。どこにも繋がらない項と途中で切れた枝はここで
  落ちる。`after` を 1 つも書かない 2 項以上の計画は必ず落ちる。独立した作業は最後に 1 項で受けるか、一直線に並べる。
  項が 1 つならその項が終端で、`feedback: []` は項が無いので当たらない
- **最後の項は延期できない。** 延期の引き受け手が居て、引き受け手にレビューがある

**辺の書き漏れは並行として通る。** 終端には繋がっているが途中の 1 本を書き忘れた形（3 と 4 を 5 が待つが、4 が 3 を
待つはずだった）は判定では止められない。承認画面は全部の番号の待ち（「3: implement — 待つ: 1, 2」）と、何も待たない
項が 2 つ以上あれば「すぐ始まる: 1, 3」を出す。ユーザはそこで確かめる。
フェーズには必ず子が 1 本以上ある。親は計画・合流・依頼だけをし、作業はしない（P12）。

**手で動かした承認も計画の `after` で読む。** `--agree` を通さずに承認済みの置き場へ動かした親も、ユーザが中身を見て
動かしたので `after` も承認したと読む。代わりに、`--agree` の検査を通っていない計画が壊れていても判定が進まないように、
**判定の側で、承認済みチケットだけを読んで済む検査を当てる**（`after` の形・終端・最後の項の延期・延期の引き受け手）。
誤りがあれば親を止め（範囲を当てない）、子も同じ理由で止める（子の承認・着手・書き込み。子の承認の順序の検査も、
壊れた待ちで順序を数えずに落とす）。止めるのは承認済みチケットそのものの形の誤りで、承認のあとに外の何かが動いて
起きるものではない（直せるのはユーザが承認済みチケットを直すときだけ）。判定の側の検査は `phases.yml` を読まない
ので、承認のあとに `phases.yml` を直しても進行中の親は止まらない。引き受け手にレビューがあるか（フェーズ定義の
`review` を読む検査）は承認でだけ見る。`--lint` と `ccnavi-ticket.sh status` も同じ文で言う。

**改版**は「承認済みチケットは動かない」の唯一の例外。提案の `plan` / `feedback` が承認済みチケットと違えば改版の候補に
なり、`--agree` が差分（計画と待ち方）を見せる。違うかは、項ごとの「フェーズ定義・`review`・推移的に辿った待ち」の並びで
比べる。`after` の書き方そのものは比べないので、`after: [2]` と「待つ: 1, 2」を写した `after: [1, 2]` は同じ計画で、
待ち方だけの改版は無い。変えられるのは `plan` と `feedback` だけで、範囲や題や `issue` が違えば拒む。
改版の書き込みは、承認済みチケットの計画を項の `after` ごと差し替える。

**錠は番号ごと。** 子が承認された（開いていても閉じていても）番号を「固定した番号」とし、その番号の項はフェーズ定義・
`review`・番号・推移的な待ちを変えられない（番号がずれると子の `phase` が指す先が変わる）。固定していない番号の項は、
前の番号でも変えてよい（並行に進むフェーズでは、後ろの番号に子があっても前の番号が始まっていないことがある）。
固定した番号が固定していない番号を待つ形（子を手で動かして承認した親）では、その先行の項も同じ項（フェーズ定義と
`review`）でなければ拒む。延期の引き受け手は、承認済みか提案の引き受け手が固定した番号のときだけ変えさせない
（済んだレビューが延期した作業を引き受けたことになる）。まだ始まっていない項の間で入れ替わるだけなら通す。
**フィードバック計画を立てたあとは全体計画を変えられない**（フィードバック計画の番号は全体計画の続きで、項を
足すと番号と `after` がずれる）。`feedback` の承認後は新しいフィードバック対応フェーズを足せない。承認済みの
フィードバック対応フェーズの中で差し戻しを受け、同じ番号に子を足してやり直すのは何度でもできる。

**局面の名前。** `--explain` と `SubagentStart` は親の局面を名指しする。全体計画待ち（承認済みチケットが無い）、
作業中（N 番目: フェーズ定義名）、レビュー準備中、レビュー待ち、フィードバック計画待ち、フィードバック対応中、
閉じられる、閉じられる（ユーザが早めに閉じた）、閉じられる（フィードバック対応済み）。計画が無い親と、
すでに閉じた親（`done/` に置かれた親）の局面は空。
局面は 1 つに絞らない。作業中・レビュー準備中・レビュー待ちのフェーズが 2 つ以上あれば、
番号を並べて言う（作業中（3: 受入テスト作成、4: 実装とテスト）、レビュー準備中（3））。子がまだ無く、
待つ番号が済んでいないフェーズは作業中に数えない。次のフェーズを促す文は、待つ番号が全部済んだ
フェーズだけを挙げる。`--explain` は計画の各項に、待っている番号（「待つ: 1, 2」）を添える。
