### 9.7 フェーズの種類と計画

番号だけのフェーズは「2 番目のまとまり」以上のことを言わない。`phases.yml`（共通層と親の `project:` の層の和。11.4.1）に
**フェーズの種類**を定義し、親が `plan:` にその順序を書くと、フェーズに意味が付く。
種類はユーザが持つ設定で、エージェントは書き換えない（コアファイル。8）。組み込みの既定は無く、
どの層にも無ければ、フェーズは番号だけの挙動になり、`plan:` は読めない。

| 欄 | 意味 | 使われる場所 |
|---|---|---|
| `kind` | `work` は全体計画に、`feedback` はフィードバック計画にしか置けない。既定 `work` | 承認 |
| `title` | ユーザ向けの名前。id と title はどちらも一意。重なれば `--lint` が error | 承認、案内 |
| `review` | `none` / `chat` / `mr`（既定）。そのフェーズの終わりにユーザがどこで見るか。`chat` はこのセッションで見る（ホストへ出ない。9.8）。既定であって上限ではない。`feedback` の種類に `none` は書けない | HITL ポイント |
| `scope` | この種類の子が宣言できる範囲の上限（glob のリスト）。省略か `inherit` なら親の範囲。子 ⊆ 種類 ⊆ 親。大文字小文字はどの機械でも区別しない（チケットの範囲と同じ規則。9.3）。超えても承認は止めず、承認画面に「チケットで編集対象としているが、書き込めない場所」として出す（9.4）。判定は子の範囲をこの上限でも切り詰める（9.5） | 承認（警告）、判定 |
| `deliverables` | フェーズを閉じる前に、親か子のワークツリーに在って追跡されているべきファイル（glob）。中身は見ない | `ticket finish` |
| `overlap` | 並行してよい種類。前のフェーズがこの種類なら、閉じる前に次を承認できる。対称 | 承認 |
| `requires` | 計画にこの種類を置くなら一緒に置くべき種類 | 承認 |
| `after` | 先に閉じてレビューが済んでいるべき種類（依存）。`order: dag` のときだけ使われる。`kind: work` の種類だけが持てて、指せるのも `kind: work` の種類だけ | 承認 |
| `agent` / `when` | 案内。`agent` は `SubagentStart`、`when` は次のフェーズを促す文に出す。判定には使わない | 案内 |

ファイルの頭の **`order`** は、全体計画のフェーズをどう待たせるかを決める。
**フィードバック計画はいつも一直線**で、`order` は適用されない（フィードバックの種類は `after` を持てない）。

| 値 | 意味 |
|---|---|
| `sequential`（既定） | 一直線。N 番目は 1〜N-1 番目の全部を待つ。`after` は読まない |
| `dag` | 種類の `after` を辺にした DAG（ワークフロー）。N 番目は、自分の種類の**祖先**に当たる前のフェーズだけを待つ。辺で繋がっていない種類は並行して進む |

**`dag` になるのは全部の層が書いたときだけ。** 合成に入る層（11.4.1）のうち `phases.yml` を持つものが**全部** `order: dag` と
書いたときに限り `dag` になる。1 本でも書かないか `sequential` と書けば `sequential`。
共通層に `phases.yml` が無ければ、プロジェクトの層 1 本で決まる。
層どうしが食い違えば `--lint` が warn を出す。`after` に循環があるか、同じ組を `after` と `overlap` の
両方に挙げていれば、`--lint` と承認が error を出す（両方あると `overlap` が採られ、書いた依存が消える）。

`dag` で `after` を書かない種類は根（何も待たない）になる。**辺の書き漏れは並行として通る。**
書き漏れを判定で止める手段は無く、ユーザが `phases.yml` を書くときと、承認画面に出る待ちの一覧（下）で確かめる。
層は、他の層の種類に `after` を足せない（同じ id で中身が違えば衝突。11.4.1）。

計画に置かなかった種類は飛ばす。祖先は `after` を推移的に辿るので、飛ばした種類が待っていたものは
その先へ引き継がれる（`research → design → implement` で `design` を置かなければ、`implement` は
`research` を待つ）。

**待ち方は承認のときに決めて、マーカーの置き場に固定する。** `--agree` は全体計画を承認するとき（改版を含む）に、
使う `order` と、全体計画の各番号が待つ番号と、延期の引き受け手の番号を計算し、`<承認済みの置き場>/phases/<親>/workflow.yml`
に書く（承認はチケットの中身を変えないので、チケットには書かない）。順序の判定・延期・フィードバック計画の前提は、このコピーだけを読み、`phases.yml` を
読み直さない。運び方・取り込み・ダイジェストの扱いはマーカーと同じで、C1 は `phases/<親>/workflow.yml` をユーザの判断（`--agree`）が書くものとして運ぶ。
コピーを持たない親（手で動かした承認）は一直線（前の番号を全部待つ）で読み、`ccnavi-ticket.sh status` がそう言う。並行にしたければ
改版で `--agree` を通す。前の版の承認が書いた `workflow:` の欄は、`ccnavi_approved` を持つ古い承認済みチケットでだけ読む。**承認したあとに `phases.yml` の `after` や `order` を直しても、進行中の親には反映されない。**
反映させたいときは親の改版を出す（コピーは改版の承認で書き直され、承認画面が待ちの差分を見せる）。
計画が同じでも、いまの種類で計算した待ち方がコピーと違えば改版になる。ただし子が承認された番号までの
延期の引き受け手は変えられない（済んだレビューが延期した作業を引き受けたことになる）。
コピーを書くのは `--agree` だけ。提案と新しい形の承認済みチケットに `workflow:` の欄があれば、`--agree`・`--lint`・判定が
error にする（手で書いた欄が承認済みの待ち方として効かないように）。
計画に読めない種類が
1 つでもあれば、コピーは `sequential` で書く（祖先が分からないものを並行にしない）。

```yaml
# <承認済みの置き場>/phases/<親>/workflow.yml。--agree が書く。ユーザもエージェントも書かない
order: dag
waits: {1: [], 2: [1], 3: [1, 2], 4: [1, 2], 5: [1, 2, 3, 4]}   # 祖先を推移的に並べる
review_at: {3: 5}    # 延期した番号 → 引き受ける番号
```

親の計画は `plan`（全体計画。作業フェーズの種類のリスト）と `feedback`（フィードバック計画。
フィードバック対応フェーズの種類のリスト）。項は名前だけか `{type, review}`。`review` に書けるのは
`mr`（種類が `none` でも要る）と `defer`（延期。次にレビューがあるフェーズの依頼に含める）だけ。
`order: dag` では「次」を番号でなく待ちで読む。引き受けるのは、延期した項より後ろで、コピーの `waits` に
その番号を持つ項のうち、**延期していない**番号のいちばん小さいもの（延期した子孫は飛ばして辿る）。引き受け手の
種類が `review: none` なら承認が error を出す。引き受け手が居なければ、承認が error を出す。計算はコピーを
作る 1 か所だけで行い、延期の引き受け手を読む側（`review_at` を使う箇所）はみなコピーを読む。
最後の項は `defer` にできず、種類が `none` の項も延期できない。番号は全体計画が 1 から、
フィードバック計画がその続き。`feedback` が無いのは「まだ計画していない」、`[]` は「見たうえで
対応なし」。

**延期は省略ではない。** 延期したフェーズでは止まらず、次にレビューがあるフェーズの依頼が
延期した分も含めて出る。マーカーは「レビューがあるフェーズの番号」に付く。

**合意は全部 `--agree` を通る。** 全体計画は親の承認。各フェーズの計画は、その番号の子を提案して
承認を受けること。別の文書は求めない。子の題・理由・範囲・本文が計画そのもので、承認画面が
それを見せる。フィードバック計画は `feedback:` を足した親の改版の承認で、全体計画の最後の
レビューが済んでから 1 回だけ。指摘が無くても `[]` で出す。承認画面はユーザが受け入れた未解決スレッドの数を見せ、状態の履歴の `revised` に `feedback: true` が残る。前提は、全体計画の
フェーズが全部終わり、最後のフェーズのレビューを依頼してあること（通っていなくてよい）。

**順序は承認で止める。** N 番目の子は、N-1 番目までが全部閉じてレビュー（延期でなければ）が済むまで
承認されない。`overlap` の組と、フィードバック計画を同時に出した最後のフェーズは例外。
`order: dag` では、待つのはコピーの `waits` に並ぶ番号だけ。`waits` は、N より前の項のうち、
種類が N の種類の祖先に当たるものと、N と同じ種類のもの。ただし `overlap` の組は、`sequential` と同じに
待ちに入れない。祖先でないフェーズは開いていても待たない。

`order: dag` の計画には、承認で 2 つを足して確かめる。

- **順序が DAG と噛み合うこと。** 後ろの項の種類が前の項の種類の祖先なら error
- **終端は 1 つ。** 全体計画の最後の項に対して、他のどの項も祖先か同じ種類であること（合流の種類を置けば満たせる）

承認画面は、`dag` の計画に各番号の待ち（「3 は 2 を待つ」「3 と 4 は並行」）を出す。
フェーズには必ず子が 1 本以上ある。親は計画・合流・依頼だけをし、作業はしない（P12）。

**改版**は「承認済みチケットは動かない」の唯一の例外。提案の `plan` / `feedback` が承認済みチケットと違えば改版の候補に
なり、`--agree` が差分を見せる。変えられるのは `plan` と `feedback` だけで、範囲や題や `issue` が
違えば拒む。`plan` は子がまだ承認されていない番号の項に限る（番号がずれると子の `phase` が指す先が
変わる）。`feedback` の承認後は新しいフィードバック対応フェーズを足せない。承認済みのフィードバック
対応フェーズの中で差し戻しを受け、同じ番号に子を足してやり直すのは何度でもできる。

**局面の名前。** `--explain` と `SubagentStart` は親の局面を名指しする。全体計画待ち（承認済みチケットが無い）、
作業中（N 番目: 種類名）、レビュー準備中、レビュー待ち、フィードバック計画待ち、フィードバック対応中、
閉じられる、閉じられる（ユーザが早めに閉じた）、閉じられる（フィードバック対応済み）。計画が無い親と、
すでに閉じた親（`done/` に置かれた親）の局面は空。
`order: dag` では、局面を 1 つに絞らない。作業中・レビュー準備中・レビュー待ちのフェーズが 2 つ以上あれば、
番号を並べて言う（作業中（3: 受入テスト作成、4: 実装とテスト）、レビュー準備中（3））。子がまだ無く、
待つ番号が済んでいないフェーズは作業中に数えない。次のフェーズを促す文は、待つ番号が全部済んだ
フェーズだけを挙げる。`--explain` は計画の各項に、待っている番号（「待つ: 1, 2」）を添える。
