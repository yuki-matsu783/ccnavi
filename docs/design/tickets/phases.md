### 9.7 フェーズ定義と計画

番号だけのフェーズは「2 番目のまとまり」以上のことを言わない。`phases.yml`（共通レイヤーと、親の `project:` が指すレイヤーの config の和。11.4.1）に
**フェーズ定義**を書き、親が `plan:` にその並びと順序（ステップの `after`）を書くと、フェーズに意味が付く。
フェーズ定義はユーザが持つ設定で、エージェントは書き換えない（コアファイル。8）。組み込みの既定は無く、
共通レイヤーにも親の `project:` が指すレイヤーにも `phases.yml` が無ければ、提案の `plan:` は承認の検査を通らない（コピーを確かめる相手が無い）。親は計画（`plan:`）を持つことが必須で、計画の無い親は `ticket start` が止まる（子や子の提案があっても同じ。`phases.yml` に最小の定義を書き、親に `plan:` を足す。書くのはユーザ）。承認の前に気づけるよう、`--lint` と `--agree --preview --verify` は未承認の親に計画が無いことを warn で言う（warn であって、承認は進められる）。番号だけのフェーズは、子の `phase:` が読める範囲の挙動として残るだけで、計画の無い親を新しく進める道ではない。計画のある親の `start` は、子（承認済みと `todo/` の提案）のないフェーズが残れば成功時に案内を出す（子の `start` は親が着手済みであることが条件なので、子が無いフェーズがあっても親の `start` は通る。子のないまま進めても `finish` が「終わっていないフェーズがある」と止める）。承認済みの親はコピーを読むので、承認のあとに `phases.yml` が無くなっても進行中の親は変わらない。共通レイヤーの定義とレイヤーの定義が同じ `id` で中身が違うか、`title` が重なれば、`--lint` が error で言い、レイヤーの側のその定義だけを使わない（同じ `id` なら共通の定義を使う）。
計画を持つ親は、計画が使う定義だけのコピーを `phases:` に持つ（下の「親に固定するフェーズ定義」）。`phases.yml` を読むのは
提案の承認の検査・`--fill-phases`・`--lint` の食い違いの warn だけで、**承認のあとの判定は親のコピーを読む。**

| 欄 | 意味 | 使われる場所 |
|---|---|---|
| `kind` | `work` は全体計画に、`feedback` はフィードバック計画にしか置けない。既定 `work` | 承認 |
| `title` | ユーザ向けの名前。id と title はどちらも一意。重なれば `--lint` が error | 承認、案内 |
| `review` | `none` / `mr`（既定）。そのフェーズの終わりにユーザがどこで見るか。既定であって上限ではない。`feedback` のフェーズ定義に `none` は書けない | HITL ポイント |
| `scope` | このフェーズ定義の子が宣言できる範囲の上限（glob のリスト。20 件まで）。省略か `inherit` なら親の範囲。子 ⊆ フェーズ定義 ⊆ 親。大文字小文字はどの機械でも区別しない（チケットの範囲と同じ規則。9.3）。超えても承認は止めず、承認画面に「チケットで編集対象としているが、書き込めない場所」として出す（9.4）。判定は子の範囲をこの上限でも切り詰める（9.5） | 承認（警告）、判定 |
| `deliverables` | フェーズを閉じる前に、親か子のワークツリーに在って追跡されているべきファイル（glob。20 件まで）。中身は見ない | `ticket finish` |
| `learning` | `on`（既定）/ `off`。`off` の定義の子は、学びの蓄積（9.16）の着手の案内と子を閉じる検査を受けない。YAML の引用符なしの `on` / `off` も読める | `ticket start`、`ticket finish` |
| `agent` / `when` | 案内。`agent` は `SubagentStart`、`when` は次のフェーズを促す文に出す | 案内 |

「使われる場所」で読むのは、承認のあとはどれも親に固定したコピー（`phases:`）の定義。`scope` と `deliverables` の
件数の上限（20 件。チケットの範囲と同じ）は、定義を親にコピーするので親の大きさを縛るためのもので、超えた `phases.yml` は
読み込みで error になる（`--lint` も同じ）。コピーにも同じ上限がヒットする。

**フェーズの順序は計画のステップの `after` が決める。** どのフェーズにどのフェーズが先行するかは親の計画に書く（下）。
定義に順序の欄は無い。並行させたいかは計画ごとに違うので、形を定義で 1 つに
決めない。並行してよい組（前の `overlap`）は線を引かないことで書け、一緒に置くべき定義の組（前の `requires`）は
フェーズ定義の `when` の案内に書き、承認画面の先行の一覧でユーザが見る。

**先行関係は計画のステップの `after` から都度計算する。** 計算するのは判定・承認・`--explain` が承認済みチケット（と提案）を
読むたび。承認済みチケットの計画は承認済みの置き場にあり、変えられるのは
改版（`user agree`）とユーザの手だけなので、計算の元も固定されている。`phases.yml` は計算の入力にならないので、
**承認したあとに `phases.yml` を直しても、進行中の親の先行関係は変わらない。** チケットの状態も入力にならず、提案も
承認済みも同じ関数で計算する。決まりは 2 つだけ。

- ステップの先行は、ステップの `after` を推移的に辿った全部の番号。`after` を書かないステップは先行なし（すぐ始まる）。
  同じフェーズ定義を 2 回置いても、`after` を書かなければ並行する
- 延期したステップは、それを先行に持つ延期していないステップのうち、番号のいちばん小さいものが引き受ける

フィードバック計画も同じ決まりで読む。フィードバック計画のステップは、全体計画の番号を全部（全体計画はフィードバック計画の
前提として全部済んでいる）と、フィードバック計画の中で `after` を推移的に辿った番号を先行に持つ。`after` を書かないステップは
フィードバック計画の中では先行なし（並行する）。延期の引き受け手も同じ決まりで、一直線に並べれば次の延期していない
番号になる。
決まりを直すと進行中の親の先行関係も変わるので、計画と先行関係の見本の表（`tests/fixtures/plan-waits.json`）を
テストで固定して見張る。

提案と承認済みチケットに `workflow:` の欄があれば、`user agree`・`--lint`・判定が error にする（欄は読まないので、書いてあると
効くと読み手に思わせる）。

親の計画は `plan`（全体計画。作業フェーズ定義のリスト）と `feedback`（フィードバック計画。
フィードバック対応フェーズ定義のリスト）。ステップは名前だけか `{type, review, after}`。

```yaml
plan:
  - research                                  # 1。先行なし
  - {type: design, after: [1]}                # 2
  - {type: acceptance, after: [2]}            # 3
  - {type: implement, after: [2]}             # 4。3 と並行
  - {type: implement, after: [3, 4], review: defer}   # 5。同じ定義の 2 回目も番号で指す
  - {type: docs, after: [5]}                  # 6。終端（ほかの全部が推移的に先行する）
feedback:
  - design-feedback                           # 7。先行なし（全体計画は済んでいる）
  - skill-improve                             # 8。7 と並行
  - {type: implement-feedback, after: [7, 8]} # 9。終端。7 と 8 を受ける
```

`after` は、先に閉じてレビューが済んでいるべきステップの番号のリスト。指せるのは**自分より小さい番号だけ**で、
番号の並びがそのまま実行できる順になり、循環は書けない。`feedback:` のステップが指せるのはフィードバック計画の番号だけ
（全体計画はフィードバック計画の前提として全部済んでいる）。同じ番号を 2 度挙げたら 1 つにまとめ、`user agree` が warn を出す。
エージェントは `--explain` の「先行: 1, 2」をそのまま `after` にコピーしてよい（推移的に並べても意味は同じ）。
`after` の形の誤り（リストでない、整数でない、`true`、範囲の外、自分以上の番号、フィードバック計画から全体計画を
指す）はチケットを読む段では落とさず、誤った線は待ちから外す。承認と `--lint` が error で言い、判定は親を止める（下）。

`review` に書けるのは `mr`（フェーズ定義の `review` が `none` でも要る）と `defer`（延期。後ろでこのステップを先行に持つ
フェーズのレビューに含める）だけ。引き受けるのは、延期したステップより後ろで、その番号を先行に持つステップのうち、**延期していない**
番号のいちばん小さいもの（延期した子孫は飛ばして辿る）。引き受け手のフェーズ定義が `review: none` なら承認が error を
出す。引き受け手が居なければ、承認が error を出す。延期の引き受け手を読む側（`review_at` を使う箇所）は、みな計画から
計算した先行関係を読む。最後のステップは `defer` にできず、フェーズ定義の `review` が `none` のステップも延期できない。番号は全体計画が
1 から、フィードバック計画がその続き。`feedback` が無いのは「まだ計画していない」、`[]` は「見たうえで対応なし」。

**延期は省略ではない。** 延期したフェーズでは止まらず、次にレビューがあるフェーズの依頼が
延期した分も含めて出る。マーカーは「レビューがあるフェーズの番号」に付く。

**合意は全部 `user agree` を通る。** 全体計画は親の承認。各フェーズの計画は、その番号の子を提案して
承認を受けること。子の題・理由・範囲・本文が計画そのもので、承認画面が
それを見せる。フィードバック計画は `feedback:` を足した親の改版の承認で、全体計画の最後の
レビューが済んでから 1 回だけ。指摘が無くても `[]` で出す。前提は、全体計画の
フェーズが全部終わり、最後のフェーズがレビュー済みであること（`reviewed` がある。レビュー不要・延期は
今までどおり。手で `done/` に動かした子の確定でもよい）。依頼しただけでは足りない。
**この承認はレビューの状態を変えない。** `reviewed` を置かず、`review/` の子も `done/` へ動かさず、
`settled_by` も書かない。差し戻しを受けたなら、先に `decide` か `confirm` で最後のレビューを済ませる
（残った指摘は `decide` で keep・fix・issue に分けられる）。まとめて承認するとき、フィードバック計画を
初めて足す改版と、同じ親の全体計画の番号の子が同じ承認に入っていたら、改版と該当する子を両方拒む
（子を足すとそのフェーズが開き直るため。全体計画に足す子を先に承認し、その作業と再レビューを済ませてから
改版を承認する）。フィードバック計画のフェーズの子との同時承認は許す。

**順序は承認で止める。** N 番目の子は、N 番目に先行する番号（計画から計算した先行）が全部閉じてレビュー（延期でなければ）
が済むまで承認されない。先行でない番号は開いていても止めない。

計画には、承認で次を確かめる（全体計画とフィードバック計画に同じ規則を適用する）。

- **`after` の形。** 上の誤りは error
- **終端は 1 つ。** 最後のステップに、それより前の全部のステップが推移的に先行すること。どこにも繋がらないステップと途中で切れた枝はここで
  落ちる。`after` を 1 つも書かない 2 ステップ以上の計画は必ず落ちる。独立した作業は最後に 1 ステップで受けるか、一直線に並べる。
  ステップが 1 つならそのステップが終端で、`feedback: []` はステップが無いのでヒットしない
- **最後のステップは延期できない。** 延期の引き受け手が居て、引き受け手にレビューがある

フィードバック計画で互いに独立した対応が 2 つ以上あるときは、最後に合流のステップを置いて受けるか（上の例の 9）、
片方をもう片方の後ろに置く（一直線。合流のステップが要らない代わりに並行しない）。全体計画が終わったときの案内
（次はフィードバック計画）と、承認で終端の検査に落ちたときの文は、この 2 つの直し方を言う。

**辺の書き漏れは並行として通る。** 終端には繋がっているが途中の 1 本を書き忘れた形（5 の先行に 3 と 4 を書いたが、3 が 4 の先行になるはずだった）は判定では止められない。承認画面は全部の番号の先行（「3: implement — 先行: 1, 2」）と、先行なしのステップが 2 つ以上あれば「すぐ始まる: 1, 3」を出す（フィードバック計画は分けて「すぐ始まる（フィードバック計画）: 3, 4」）。ユーザはそこで確かめる。
フェーズには必ず子が 1 本以上ある。親は計画・依頼だけを受け持つ（P12。合流は子の `finish`）。

**小さい作業。** 子を作らない親は無い。小さい作業も、親 1 本と子 1 本を同時に提案して、1 回の承認（`ccnavi user agree <親> <子>`）で通す。

- 親は `plan: [quick]` の 1 ステップだけを持つ。`quick` は小さい作業向けのフェーズ定義で、`review: mr`（マージリクエストでユーザが見る）、
  `scope: inherit`（範囲は親の範囲そのまま）。子は `phase: 1`。ステップが 1 つなので `after` は要らない（そのステップが終端）
- 親の提案には、計画が使う定義のコピー `phases:`（ここでは `quick` だけ）も書く。`ccnavi --plan-order <親> --fill-phases` で差し込む
- `quick` の見る場所は定義の `review: mr` で決まる。子の `human_review.required: false` ではレビューは外れない
  （子の宣言は「要る」を言うだけで、見る場所は定義が決める）。レビューを外したい作業は `review: none` の定義を使う
- 親は計画・依頼だけを受け持つ（合流は子の `finish`）。作業は子が行う（P12 のまま）
- 親の提案には `feedback: []` も書く（対応が無くても空で出す。無いと親を閉じられない）
- 流れ: 承認 → 親に着手 → 子に着手 → 子で作業して `finish`（子は `review/`。親のブランチへの合流と push も `finish` が行う） → 親が ELI5 の HTML を
  `wip/eli5/phase-1.html` に書いてコミットして push し、`ccnavi-review.sh request --phase 1 --body-file <依頼文>
  --eli5 wip/eli5/phase-1.html` で、開始のときに用意したマージリクエストへ依頼 → ユーザが `crit review` で指摘を付ける → 親が `confirm`
  （指摘が残れば `decide`。子が `done/`） → 親を `finish`（親は `done/`） → push して `ready`（Draft を外す）。各段の前提は 9.10

**手で動かした承認も計画の `after` で読む。** `user agree` を通さずに承認済みの置き場へ動かした親も、ユーザが中身を見て
動かしたので `after` も承認したと読む。代わりに、`user agree` の検査を通っていない計画が壊れていても判定が進まないように、
**判定の側で、承認済みチケットだけを読んで済む検査を適用する**（`after` の形・終端・最後のステップの延期・延期の引き受け手）。
定義は親に固定したコピーから読むので、コピーの検査（計画を持つのに `phases:` が無い、ステップが `phases:` に無い定義名を使う、
コピーの定義の形、`kind` が置いた計画と合う、引き受け手にレビューがある＝コピーの `review` とステップの `review: mr`）も判定の側で
適用する。子に書いた `phases:` も同じに止める。
誤りがあれば親を止め（範囲を適用しない）、子も同じ理由で止める（子の承認・着手・書き込み。子の承認の順序の検査も、
壊れた待ちで順序を数えずに落とす）。止めるのは承認済みチケットそのものの形の誤りで、承認のあとに外の何かが動いて
起きるものではない（直せるのはユーザが承認済みチケットを直すときだけ）。判定の側の検査は `phases.yml` を読まない
ので、承認のあとに `phases.yml` を直しても進行中の親は止まらない。コピーと今の `phases.yml` の食い違いは判定では
見ず、`--lint` が warn で言う。`--lint` と `ccnavi-ticket.sh status` も同じ文で言う。

**改版**は「承認済みチケットは動かない」の唯一の例外。提案の `plan` / `feedback` か `phases:` が承認済みチケットと違えば
改版の候補になり、`user agree` が差分（計画と先行関係と `phases:`）を見せる。計画が違うかは、ステップごとの「フェーズ定義・`review`・
推移的に辿った先行」の並びで比べる。`after: [2]` と「先行: 1, 2」をコピーした
`after: [1, 2]` は同じ計画で、先行関係だけの改版は無い。`phases:` が違うかは定義を読んだ形で比べ、計画が同じでコピーだけが
違う提案も改版の候補にする（`--fill-phases` で今の `phases.yml` に揃えた提案を出せるように）。範囲（`allow`・`ask`・
`deny`）が違う提案も改版の候補で、画面に範囲の差分（追加・削除）を出す。範囲を変える改版は、作業中（`doing/`）の子が
居ないときだけ通す（子の範囲は親の範囲の中に収まる前提で承認されているので、子は取り消して出し直す）。古い範囲は
上書きされ、git の履歴にだけ残る。変えられるのは `plan`・`feedback`・`phases:`・範囲で、題や `issue`・`mr:` が違えば
拒む。改版の書き込みは、承認済みチケットの計画をステップの
`after` ごと差し替え、`phases:` も提案の値に差し替える（差し替えないと、改版で足したステップ（フィードバック計画の立案）は
必ず改版が、コピーに無い定義名を使うことになり、承認したとたんに親と子が全部止まる）。承認のダイジェストと承認画面の
`phases:` の差分は、この書く中身から組む。

**錠は番号ごと。** 子が承認された（開いていても閉じていても）番号を「固定した番号」とし、その番号のステップはフェーズ定義・
`review`・番号・推移的な先行を変えられない（番号がずれると子の `phase` が指す先が変わる）。固定していない番号のステップは、
前の番号でも変えてよい（並行に進むフェーズでは、後ろの番号に子があっても前の番号が始まっていないことがある）。
固定していない番号が固定した番号の先行になる形（子を手で動かして承認した親）では、その先行のステップも同じステップ（フェーズ定義と
`review`）でなければ拒む。延期の引き受け手は、承認済みか提案の引き受け手が固定した番号のときだけ変えさせない
（済んだレビューが延期した作業を引き受けたことになる）。まだ始まっていないステップの間で入れ替わるだけなら通す。
**フィードバック計画を立てたあとは全体計画を変えられない**（フィードバック計画の番号は全体計画の続きで、ステップを
足すと番号と `after` がずれる）。フィードバック計画を立てる改版で一緒に全体計画を変えるのも拒む（足したステップは
レビュー済みの前提と合わなくなる）。`feedback` の承認後は、ステップも `after` も
変えられない（定義・`review`・推移的な先行の並びで比べ、`after` だけの違いも違いとして拒む）。新しいフィードバック対応
フェーズも足せない。承認済みの
フィードバック対応フェーズの中で差し戻しを受け、同じ番号に子を足してやり直すのは何度でもできる。

**番号の振り直し（`ccnavi --plan-order <親>`）。** 保存される計画は「`after` は自分より小さい番号だけ」を保つ。
VS Code の計画編集タブでは並びの逆向きの線も引けるので、線を変えるたびに番号を振り直し、保存で振り直した計画を
承認の前に提案へ書き戻す（承認は提案をそのまま動かすので、承認の段では書き換えない）。振り直しの正は実行ファイルで、
タブは図で引いた線（元の番号での直接の先行）を渡して答えを描くだけ（渡し方と書き戻しの検査は [9.4](approval.md)）。
決まりは次のとおりで、見本の表（`tests/fixtures/plan-reorder.json`）を実行ファイルと拡張のテストが共有する。

- 先行が全部前に並んだステップのうち、元の番号がいちばん小さいものから順に番号を振る（同じ段のステップは元の番号順を保つ）。
  線を変えても並びが崩れなければ番号は変わらない
- `after` の指す先は振り直した番号に付け替える。`review: defer` はステップに付いたまま動く。延期の引き受け手は保存せず、
  振り直した計画から計算し直す
- 全体計画とフィードバック計画は別に振り直す（フィードバック計画の番号は全体計画の続きのまま）
- 子が承認された番号（固定した番号）は動かさず、空いた番号に承認されていないステップを詰める。固定した番号へ入る線
  （固定したステップの先行）は変えられない。固定した番号を動かさずに番号が振れない線は「詰められない」と断る
  （例: 1〜4 で 1 が 2・3 の先行、2・3 が 4 の先行で、1・3 に子があるとき、3 を 2 の先行にする線は、2 番を埋めるステップが無いので断る）。
  回したいときは、ステップを足す改版で空いた番号を埋めてから線を引く
- 循環になる線は断る。断ったときは振り直さず、提案のままの答えを返す
- 振り直した計画には順序の検査と、改版なら番号ごとの錠を適用する。延期したステップの引き受け手は、元のステップの同一性（振り直す
  前の番号）で比べる。どれかにヒットすれば書き戻さない
- 番号の変わるステップを指す承認前の子の提案（`todo/`）は、識別子のフェーズ番号・ファイル名・`ticket:`・`phase:` を新しい
  番号に付け替え（連番は変えない）、それを指す子の `predecessors` も直す。承認済みの子は固定した番号にいるので動かない。
  付け替え先が重なるか、承認済みの側（承認済みチケット・記録・マーカー・フロー・ワークツリー）が付け替える識別子を
  指していれば書き戻さない（見本の表の `children` のある例）

**局面の名前。** `--explain` と `SubagentStart` は親の局面を名指しする（文字列は `phase.stage` が返すもの）。
作業中（N 番目: フェーズ定義名）、レビュー準備中、レビュー待ち、フィードバック計画待ち、フィードバック対応中、
クローズ可、クローズ可（フィードバック対応済み）、閉じられる（ユーザが早めに閉じた）。計画が無い親
（全体計画の承認済みチケットが無い親）と、すでに閉じた親（`done/` に置かれた親）の局面は空で、名指ししない。
局面は 1 つに絞らない。作業中・レビュー準備中・レビュー待ちのフェーズが 2 つ以上あれば、
番号を並べて言う（作業中（3: 受入テスト作成、4: 実装とテスト）、レビュー準備中（3））。子がまだ無く、
先行する番号が済んでいないフェーズは作業中から外す。次のフェーズを促す文は、先行する番号が全部済んだ
フェーズだけを挙げる。`--explain` は計画の各ステップに、先行している番号（「先行: 1, 2」）を添える。

#### 親に固定するフェーズ定義（`phases:`）

計画を持つ親は、frontmatter の `phases:` に、計画（`plan:` / `feedback:`）が使うフェーズ定義**だけ**のコピーを持つ。
`phases.yml` の全定義のコピーではない（調査を飛ばす親の `phases:` に `research` は入らない）。中身は定義の id を
キーにしたマップで、各定義の欄は `phases.yml` と同じ（`kind` `title` `review` `scope` `deliverables` `agent` `when` `learning`）。
読み方も `phases.yml` の定義と同じで、形の誤りも同じ文で言う。ステップの `type` は `phases:` のキーを指す。

```yaml
phases:                      # 親だけ。plan: / feedback: が使う定義のコピー
  research:
    kind: work
    title: 調査
    review: none
    scope: ["wip/research/*"]
    deliverables: ["wip/research/summary.md"]
  design: {kind: work, title: 設計, review: mr, scope: ["wip/design/*"]}
plan:
  - research
  - {type: design, after: [1]}
```

承認したときの定義が親に固定され、**承認のあとの判定・フェーズの題と見る場所・成果物の確かめ・子の範囲の上限はコピーを
読む。** 承認のあとに `phases.yml` を直しても、進行中の親とその子には届かない（範囲を狭めても
効かない）。子の承認の定義（範囲の上限の警告）と順序の検査も、親が承認済みならそのコピー、同じ承認で通る提案ならその
提案のコピーから引く。`allow:` は変えない（親の `allow` / `ask` / `deny`、子の範囲、`scope: inherit` は今のまま。子の範囲は
「子 ⊆ コピーの定義の `scope` ⊆ 親の `allow`」）。

**承認（`user agree`）はコピーを確かめる。** 定義を決めるのは今までどおり `phases.yml`（ユーザの設定）で、コピーはそのコピー。
エージェントがコピーの値を変えても通らない。

| 検査 | 重さ |
|---|---|
| 計画を持つのに `phases:` が無い、ステップが `phases:` に無い定義名を使う（使う定義はコピーに明記する） | error |
| コピーの各定義が、承認したときの親の `project:` が指す `phases.yml` の同じ名前の定義と同じ（読んだ形で比べる。YAML の書き方・キーの順・既定値を省いた書き方・`inherit` の書き方の違いは同じとみなす） | error |
| コピーの定義の名前が `phases.yml` に無い | error |
| 定義の形（`kind` と置いた計画、`review` の値、`scope` の glob、件数の上限） | error |
| `phases.yml` にあってコピーに無い定義 | 何も言わない（この親では使わないだけ） |
| コピーにあって、どのステップも使わない定義 | warn（判定はどのステップからも引かないので、範囲・見る場所・成果物は変わらない。error にすると、ステップを消した・並べ直したあとの消し忘れで承認が止まる） |

コピーが違うと落とすときの文面は `ccnavi --plan-order <親> --fill-phases` を出す。承認画面（ターミナルと VS Code）は定義を
3 つに分けて出す。**この親に固定する定義**（題・`review`・`scope`・`deliverables` と使う番号）、**使われていない定義**
（名前と題）、**この親では使わない定義**（`phases.yml` にあってコピーに無いもの。名前と題を 1 行に並べる）。
ユーザが読むのは「どの定義をこの親に固定し、どれを外したか」。コピーはチケットのバイト列なので、何もしなくても承認の
ダイジェストに入る。承認はチケットの中身を変えないので、コピーは承認の**前**に提案へ書いておく。

**コピーを作るのは補助のフラグ `ccnavi --plan-order <親> --fill-phases`。** 承認待ちの親の提案の計画が使う定義だけを
`phases.yml` から読み、`phases:` の値をその定義の集まりに差し替える（無ければ `plan:` の前に足す。ステップが使わない定義は
外す）。ほかのバイト（コメントも）と本文は変えず、書く前に組んだ全文を読み直し、`phases` のほかの欄が読んだ形で元と
同じでなければ何も書かない（`phases:` の値にアンカーがあり、ほかの欄が別名で指しているときなど）。`phases:` の値の中の
コメントは消える（定義のコメントは `phases.yml` 側に書く）。`user agree` の外の独立したフラグで、エージェントが打ってよい
（書くのはエージェントも書ける提案だけ）。計画のステップが使う定義が `phases.yml` に無ければ何も書かない。

**改版でのコピーの扱い。** 子が承認された番号（固定した番号）が使う定義は、承認済みチケットのコピーと同じでなければ error
（`phases.yml` と違っていてよい。外すこともできない）。それ以外の定義は改版を承認したときの `phases.yml` と同じでなければ
error で、足すのも外すのも自由。同じ定義を固定した番号と固定していない番号の両方が使うなら、固定した側の値に揃える。
`--fill-phases` も改版の提案ではこの規則で差し込む（固定した番号の定義は承認済みチケットから、ほかは `phases.yml` から）。
固定した番号の定義を直したいときは、ユーザが承認済みチケットの `phases:` を手で直す（エージェントは書けない）。
閉じたフェーズの `review` を後から変えて済んだレビューの扱いが揺れたり、進んでいるフェーズの範囲が改版の承認で
変わったりしないため。

**手で動かした承認では、コピーはそのまま効く。** `user agree` を通さずに承認済みの置き場へ動かした親では、コピーが
`phases.yml` と同じかの検査が働かず、エージェントが書いたコピーがそのまま効く。承認を本物とするのは置き場で（9.2）、
置き場へ動かしたユーザが中身を承認したと読む（計画の `after` を信じるのと同じ向き）。理由は弱い。手で動かすユーザが
コピーを `phases.yml` と見比べるとは限らず、`review: none` や広い `scope` を気づかずに通しうる。`--lint` が食い違いを warn で言う
（「進行中の親には効かない。反映するには、子の無い番号の定義なら `--fill-phases` を打った改版を出す。計画が同じでも
改版になる。子が承認された番号の定義ならユーザが承認済みチケットを直す」）。

**コピーを持たない親。** 計画を持つのに `phases:` の無い親（コピーを書かずに手で動かした承認など）は判定の側で
「計画が使う定義が親に固定されていない」として止まり、子も止まる。直し方は、ユーザが承認済みチケットに `phases:` を
足すか、取り消して出し直す。計画を持たない親は `start` が止まるので、その子も着手できない（着手済みの古い親は今のまま、番号だけで進む）。計画を持たない親に
`phases:` があれば、全部が「使われていない定義」として warn になる。子（`parent:` を持つ）に `phases:` があれば error
（子の `phase:` と名前が似ていて取り違えやすい）。どちらの誤りもチケットを読む段では落とさず、判定の `blocked` の
理由にする（読む段で落とすと承認済みチケットが索引に入らず、判定がその親を知らないまま範囲を適用しなくなる）。


### 見本（フェーズ定義と親の計画）

version: 1
phases:
  research:
    kind: work            # work は全体計画に、feedback はフィードバック計画にだけ置ける
    title: 調査           # id と title はどちらも一意
    review: none          # none | mr。既定であって上限ではない
    scope: ["wip/research/*"]          # 子の範囲の上限（20 件まで）。省略か inherit なら親の範囲
    deliverables: ["wip/research/summary.md"]   # 閉じる前に在って追跡されているべきもの（20 件まで）
    agent: explorer       # .claude/agents/<名前>.md。案内。判定には使わない
    when: 既存の振る舞いが分からないとき          # 案内。判定には使わない
  implement:
    kind: work
    title: 実装とテスト
    review: mr
    scope: ["src/*", "tests/*"]
    when: 振る舞いを変えるとき。受入テスト作成を先に置く
  acceptance:
    kind: work
    title: 受入テスト作成
    review: mr
    scope: ["tests/*"]
  implement-feedback:
    kind: feedback
    title: 実装フィードバック対応
    review: mr                         # feedback に none は書けない
    scope: inherit
    when: フィードバック計画の最後に置き、ほかの対応を受ける
```

フェーズ定義は順序を持たない。順序は親の計画のステップの `after` が決める。

```yaml
# 親チケット
ticket: i0001
issue: 1
phases:                                # 計画が使う定義のコピー。ccnavi --plan-order i0001 --fill-phases で差し込む
  research: {kind: work, title: 調査, review: none, scope: ["wip/research/*"], deliverables: ["wip/research/summary.md"]}
  acceptance: {kind: work, title: 受入テスト作成, review: mr, scope: ["tests/*"]}
  implement: {kind: work, title: 実装とテスト, review: mr, scope: ["src/*", "tests/*"]}
plan:                                  # 全体計画。user agree が通ることが合意
  - research                           # 1。先行なし
  - {type: acceptance, after: [1], review: defer}   # 2。レビューを後ろと一緒に見る（延期。省略ではない）
  - {type: implement, after: [1, 2]}   # 3。終端（ほかの全部が先行する）
feedback:                              # フィードバック計画。レビューのあと改版で足す。空でも出す
  - implement-feedback                 # 4。after はフィードバック計画の番号だけを指せる
```

子は `phase: N`。N 番目のフェーズ定義は親の計画で決まる。番号は全体計画が 1 から、フィードバック計画がその続き。
