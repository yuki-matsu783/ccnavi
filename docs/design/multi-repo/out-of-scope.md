### 11.11 見ないもの、入れないもの

- VS Code 拡張のリスク管理画面の層への追従。共通層の 1 本（`.ccnavi/common/risks.yml`）だけを開き、自身の層とプロジェクトの層の risk は画面から
  直せない（層の配点を差し替えて検証する手段も無い）。ルール管理画面とフェーズ管理画面は `--explain --json` の `layers[]` から置き場を取り、
  プロジェクト管理画面から自身の層とプロジェクトの層を開く。層の種類は `--project-phases-file` で共通層と合成して検証してから保存する
- `CCNAVI_TICKET_CONTROL` のプロジェクト単位化。あれはワークスペース単位のつまみで、README の語をその意味に直すだけ
- 統合先ブランチの git オブジェクトから設定を読む形。読むのは checkout されている版だけ
- プロジェクトの `.claude/` を認める形
- `.ccnavi/scripts/` をコアファイルにする形（11.6）。中身のハッシュを突き合わせる形も入れない
- 層が無いことを `--lint` が言う形。このため、層を消す・層が入る前のコミットへ `checkout` する、のどちらでも
  そのプロジェクトの deny が痕跡なく消える（「壊す」と error、「消す」と何も言わない、の非対称。未解決）
- プロジェクト A に居るときだけ適用される Bash のルール、`cwd` と `cd` の追跡、引数の語の走査
- 2 段以上の深さに置いたプロジェクト、ワークスペースの外に置いたプロジェクト
- ワークツリーの中に checkout された設定ファイルとスクリプト

受け入れる代償。

- プロジェクトは共通層の `ask` を `allow` に緩められない（`ask` は `allow` より先に当たる）
- 共通層の `allow` が全プロジェクトに適用される
- パスを持つツールに他プロジェクトのルールは足さないので「A のルールを B にも」は書けない。要るなら共通層へ上げる
- ワークツリーで足した `.ccnavi/` の変更は、元リポジトリに入るまで使われない
- `glob` も `regex` もどの機械でも大文字小文字を区別せずに当てるので、`allow` も表記違いに広がる
- 層の数だけ読み込みが増える。1 本 200 行の YAML で数 ms なので期限の中に収まるが、`ms` の欄で見る（11.10）
