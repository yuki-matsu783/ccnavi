### 11.4 ルール

パスを持つツール（Read / Grep / Glob / Write / Edit / NotebookEdit）は共通レイヤー + 行き先のレイヤーの和。行き先は解いた先のパスで、
Grep と Glob が探す場所を省いたときは `cwd`。行き先がプロジェクトに属するならその git プロジェクトルートの `.ccnavi/config/project/rules.yml`、
ワークスペースのツリー（ワークスペースルートと、そこから切ったワークツリー）なら `<ワークスペースルート>/.ccnavi/config/project/rules.yml` を足す。
ルールは解いた先の絶対パスに当てるので、プロジェクトのルールに `*/schema/*` と書けば、元リポジトリでもそこから切ったワークツリーでも当たる。
レイヤーのファイルは元リポジトリのものを読む（ユーザが見たルールだけを適用する）。ワークツリーでレイヤーを直しても、統合されるまで反映されない。
ワークツリーにしかないレイヤーのファイルは `--lint` が warn で知らせる。承認済みの領域（`.ccnavi/approved/` の承認済みチケット・マーカー・子の記録・フロー）は数えず、そこは親のワークツリーの版を読む。

パスを持たないツール（Bash / PowerShell / WebFetch / Skill / Agent）は全部の和。共通レイヤー、自身のレイヤー、全プロジェクトのレイヤーをタイプごとに
連結して当てる。`deny` `ask` `allow` の順は変わらない。Bash は `cd` で `cwd` の外に移れ、WebFetch・Skill・Agent は行き先のパスを持たないので、
どのプロジェクトの呼び出しかは決めず、どこに `cwd` があっても同じ判定になる（REQ-MLT-05）。

順は共通レイヤー → 自身のレイヤー → プロジェクトのレイヤー（名前順）。先に当たったルールが文面に載るだけで、判定は同じ。

**共通レイヤーはワークスペースルートの 1 本だけ。** ワークスペースの中で共通レイヤーとして読むのは、ワークスペースルートの `.ccnavi/config/common/` だけ。
ミラーが共通レイヤーとして読まれるのは、そのプロジェクトだけを clone したとき（そのプロジェクトがルートになる）だけ。
このとき、プロジェクトの `.ccnavi/config/project/` は自身のレイヤー（`self`）として読まれ、ワークスペースの中と同じ「共通 + 1 レイヤー」の和になる。
プロジェクトの 3 本は、ワークスペースの中ではプロジェクトのレイヤー（`<名前>:id`）、単体 clone では自身のレイヤー（`self:id`）と、名前だけが違う。

識別子にはレイヤーの名前を添える。共通レイヤーは裸の `id`、自身のレイヤーは `self:id`、プロジェクトは `<名前>:id`（REQ-MLT-07）。記録の `rules` と
文面の `source` はこの形で出す。

裸の `id` にコロンは書けない。3 本とも、書いた `id`（`phases` の鍵、配点の項目名を含む）にコロンがあれば error にして読み込みから外す。
接頭辞はレイヤーを足す側だけが付ける。

レイヤーの名前に `common` と `self` を予約する。この名前のプロジェクト（`casefold` で比べ、`projects/Self/` も同じ）はレイヤーとして数えず、
`--lint` が error で名指しし、`user agree` はその `project:` を承認しない。
予約名のプロジェクトへの書き込みは共通レイヤーだけで判定する。ワークスペース自身のレイヤーで判定すると、そのレイヤーの広い `allow` で通ってしまうため。
予約の判断は 1 か所に置き、レイヤーを数える側と行き先のレイヤーを引く側が同じ答えを引く。

重複は後ろを捨てる。裸の `id` が同じで、`{root}` を置き換えたあとの全欄（`match` / `glob` / `regex` / `message` /
`additionalContext*` / `additionalContext*File` / タイプ）が一致する定義は、後ろのレイヤーのものを捨てる。`--lint` が
info で言い、`--explain` は残った 1 本だけ出す。全部の和でも同じ。

同 `id` で中身が違うとき、ルールは両方適用され、`--lint` が warn で言う。`allow` はパスを持つツールでは行き先の 1 レイヤーにしか足さないので
そのツリーの中だけで済むが、パスを持たないツールでは他のプロジェクトの作業にも適用される。配点の項目も両方を数える（11.4.2）。
フェーズ定義は、同 `id` で中身が違えば error にする（11.4.1）。

`glob` も `regex` も、どの機械でも大文字小文字を区別しない。チケットの範囲、フェーズ定義とリスクの配点の `scope`、
組み込みの保護（8.2）のパス、コマンドの名前も同じ規則で当てる。区別が要る `regex` は、区別したい部分だけ `(?-i:...)` で囲む。
否定の文字クラス（`[^c]` など）を持つルールは、区別しないと除外の側が広がるのでそこを囲む。

Grep と Glob は、探し始める場所でレイヤーを選び、ルールもその場所のパスに当てる。`*/secrets*` のようなルールは
探し始める場所のパスに `secrets` が無ければ当たらない。レイヤーの選び方で差が出るのは、パスによらず当たる広いルール（`match: Grep`・`glob: "*"` など）だけ。

**無いのと不正なのは違う。** common も config も、ファイルが無いのは「設定が無い」正常で、空として扱う。ルール・リスクの配点・フェーズ定義の
すべてでこれに揃える。common だけ、config だけ、のどちらでも動く（11.2）。
土台の deny（5.6 の取り返しの付かない操作の止め）は、common と config の有無・状態によらず常に有効で、common と config のルールはその上に足す。
`builtin:guard-*`（設定の保護。8.2）は土台の deny とは別。シェルからの書き込みを止める `add_rules` の分は、共通レイヤーのルールが不正で組み込みの既定を使っている間は外す（既定が同じ形を持つ）。名前で書くツールの 4 本（`builtin:guard-hooks`・`-settings`・`-scripts`・`-ccnavi-config`）は、読めない間も外さない。
ルールは、common にも config にも 1 本も無いときは、組み込みの既定だけで判定する。

読めないレイヤーは空として扱う。そのツリーを行き先にするパスを持つツールは共通レイヤーだけで判定し、全部の和からもそのレイヤーを外す。
記録の `fallback` にレイヤーの名前を残し、`--lint` が error で言う。組み込みの既定には戻さない（11.2）。
共通レイヤーのルール自身が破損して読めないときだけは、組み込みの既定を使い、レイヤーは足さない（破損した共通レイヤーの上にレイヤーを足すと、何が判定に使われているのかをユーザが読めないため。REQ-PRE-06）。

できないこと（REQ-MLT-18）: プロジェクトのレイヤーで共通レイヤーの `ask` を `allow` に緩める、共通レイヤーの `allow` をプロジェクトごとに外す、他のプロジェクトのレイヤーをパスを持つツールの判定に足す。
「A のルールを B にも」は共通レイヤーへ上げる。ccnavi ディレクトリの下（既定なら `.ccnavi/`。共通レイヤーの `.ccnavi/config/common/` も入る）は、ルールに書かなくても書き込みが止まる。設定 3 本と配点のスクリプトは判定の中身そのものだから（8.2）。

代償は 11.11 の「受け入れる代償」。

#### 11.4.1 フェーズ定義

フェーズ定義（`phases.yml`）は、共通レイヤー（`.ccnavi/config/common/phases.yml`）と、親の `project:` が指すレイヤーの
config の和で決める。共通レイヤーには、どのプロジェクトでも同じ構成（`src/*`・`tests/*` など）を前提にできる定義を置き、
`scope` が置き場のレイアウトに依存する定義だけをレイヤーに置く。
この和を読むのは提案の承認の検査と `--plan-order <親> --fill-phases`・`ticket new`・`--lint` だけで、承認のあとの判定は親に写した定義
（`phases:`）を読む（tickets/phases.md）。
足すレイヤーは提案を置いた場所が決め（11.5）、子も親と同じ値を持つ。`project:` が空ならワークスペース自身のレイヤーの `.ccnavi/config/project/phases.yml`、
プロジェクトの名前なら、そのプロジェクトの `.ccnavi/config/project/phases.yml`。ワークツリーの元リポジトリが `project:` と合うことは着手時に確かめてある（REQ-MLT-13）。

1 本の中の `id` の重複と表示名（`title`）の重なりは、その 1 本の読み込みで確かめる。足したあとは次の 2 つを見る。

- 共通レイヤーと同じ `id` の定義: 全欄が同じならレイヤーの側を捨てて `--lint` が info で言う。中身が違えば error
- 共通レイヤーの定義と `title` が重なる、別の `id` の定義: error（ユーザは表示名で見るので、承認画面で見分けられない）

error のとき、捨てるのはレイヤーの側の、その定義だけ。同じ `id` なら共通レイヤーの定義が使われ、`title` の重なりならレイヤーにその定義が
無いのと同じになる。そのレイヤーのほかの定義は足す。捨てる側をいつもレイヤーにするのは、共通レイヤーの定義をどのプロジェクトでも
同じ中身で読ませるため。レイヤーが共通レイヤーの定義を上書きする形は無い。捨てた定義は `--lint` が error で名指しする。
フェーズ定義は順序を持たない。順序は親の計画の項の `after` が決める（tickets/phases.md）。足すときに揃える欄は `id` と `title` だけ。

ファイルが無いのは正常（11.2）。共通とレイヤーのどちらかが無ければ、在る側の定義だけを使う。両方無ければフェーズ定義は空で、計画を持つ親の提案は、写しを
確かめる相手が無いので承認で止まる。不正なら、そのファイルの定義は空として扱い、`--lint` が error で言う（共通レイヤーが不正なら、
レイヤーの定義だけを使う）。承認済みの親は写しで判定されるので、どのときも進行中の親は止まらない（`--lint` が warn で言う）。

`id` は裸のまま鍵にする。`plan:` と `feedback:` とマーカーは裸の `id` でフェーズ定義を指し、レイヤーの名前は `--explain` と記録のレイヤーの欄に出す。
接頭辞を付けない（足すのは共通レイヤーと 1 レイヤーだけで、同じ `id` は上の検査で 1 本に揃う）。

`scope` はワークツリーのルートからの相対。`inherit` も同じ。

#### 11.4.2 リスクの配点の合成

配点は統合結果をする。子を閉じるときに、親の承認済みチケットの `project:` が指す config のレイヤー（空ならワークスペース自身のレイヤー）を、共通レイヤーに足す。
共通レイヤーにも config にも `risks.yml` が無ければ、組み込みの 4 項目を使う（11.2）。共通レイヤーだけ無く config が在るときは、共通レイヤーを空として config の項目だけを数える。

項目は連結し、境目の点はキーごとに小さいほうを採る。共通レイヤーの項目の後ろにレイヤーの項目を並べる。全欄一致なら重複として後ろを捨てる（info）。
`levels` は `medium` / `high` / `critical` のそれぞれで、書かれた鍵だけが参加し、そのうち小さいほうを採る。どのレイヤーも書いていない鍵は既定（20 / 40 / 70）。
合成後に `medium <= high <= critical` でなければ error。

同じ項目かは全欄で比べる。`script:` は書いたパスと置き場の対で比べる。ミラー（11.12）は共通レイヤーと同じ `.ccnavi/config/common/scripts/` を指すので、
書き換えは要らない。

同 `id` で中身が違う項目は両方を数え、`--lint` は warn。後ろのレイヤーの項目は `<レイヤー>:<id>`（例 `lib:big-diff`）と表記し、記録の `hits`、
`<子>.judge.json`、`record-risk` の項目名、問いの見出しはその名前で出す。レイヤーを空にすると点が下がるので空にしない。

`levels` の順が崩れたレイヤーは空として扱う。`fallback` にレイヤーの名前を残し、閉じるときの出力が言い、`--lint` は error。共通レイヤーだけで測るので、点は小さくなりうる。

`script:` の解決先はレイヤーごとに違い、たがいに指せない。

| レイヤー | `script:` に書けるパス | 解決の基準 |
|---|---|---|
| 共通レイヤー（単体 clone ではミラーも） | `.ccnavi/config/common/scripts/...` | そのとき共通レイヤーを持つルート（ワークスペースルート、単体 clone ではそのプロジェクトの git プロジェクトルート） |
| 自身のレイヤー | `.ccnavi/scripts/...` | ワークスペースルート |
| プロジェクトのレイヤー | `.ccnavi/scripts/...`（同上） | そのプロジェクトの git プロジェクトルート |

共通レイヤーから `.ccnavi/scripts/` を、レイヤーから `.ccnavi/config/common/scripts/` を指す定義は読み込みで error。指す先が git プロジェクトルートに無ければ
`--lint` が error（走らせるときは「測れなかった」でその項目の点を加える）。`cwd` は
子のワークツリーで、環境変数（`CCNAVI_BASE_SHA` 等）も同じ。プロジェクトの `.ccnavi/` はそのプロジェクトだけで閉じる。
