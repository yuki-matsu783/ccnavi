### 11.12 共通レイヤーを配る

共通レイヤーは、共通の設定を各プロジェクトへ配るための定義で、優先するのは各プロジェクトの `.ccnavi/config/`。
共通レイヤーはワークスペースの git にあり、プロジェクトだけを clone したユーザからは見えないので、作業を始める前に共通レイヤーをプロジェクトへコピーし、
最初のレビューでユーザに見せる。

いつ: 親チケットの `ticket start`。親の `project:` が空（ワークスペース自身の作業）なら比べない。子の着手でも比べない（親のブランチに乗る）。

何を: 共通レイヤーの各ファイル（`rules.yml`・`phases.yml`・`risks.yml`）と、親のワークツリーにあるプロジェクトのレイヤーの同じ名前のファイルを
比べる（改行の違いは見ない）。違えば、共通レイヤーの中身で上書きする。

- 共通レイヤーにあるファイルだけをコピーする。共通レイヤーに無いファイル（このワークスペースでは `phases.yml`。11.2）は、プロジェクトの側を消さずに残す
- 配点が指すスクリプトもコピーする。共通レイヤーの `risks.yml` の `script:` の値の頭にある `.ccnavi/common/scripts/` を
  プロジェクトのレイヤーの `<ccnavi ディレクトリ>/scripts/` に直してコピーし（11.4.2）、指されているスクリプトもそこへコピーする（同じスクリプトは 1 回）。
  直すのは `script:` の値だけで、`glob` や `message` の同じ表記は触らない。統合先に入ったあと、共通レイヤーの項目とそのコピーは同じ項目として 1 本に数える（11.4.2）
- コピーする前に、ルール・フェーズの種類・配点（直した形）をプロジェクトのレイヤーの読み方で読む。
  error が 1 つでもあれば何もコピーせず、着手しない。共通レイヤーやスクリプトが読めないときも同じ
- コピー先に未コミットの変更があれば止める。コピー先かその途中がシンボリックリンクでも止める
- 上書きで消える識別子と、中身の変わる識別子（ルールの `id`、フェーズの種類の鍵、配点の項目の `id`）を名指しする。同じ `id` のまま
  `deny` から `allow` へ移ったものも「中身が変わった」に入る。上書き前を読めなければ、名指しできなかったと書く。着手の出力と上書きの記録に出す
- 上書きの記録を先に置き、1 本でも書けなければ全部戻す。上書きは一時ファイルからの置き換えで行う。途中で書けなくなったら、書いた分を元の中身へ、
  上書きの記録を前の中身へ戻し、戻せなかったものを名指しする。上書きのあとに着手が止まっても、上書きしたことは知らせに残る
- 書くのは実行ファイル（`configsync`）。コミットはエージェントが `ccnavi-git.sh` で行い、着手の出力がそれを案内する

上書きの記録: 親の `phases/<親>/config-sync.json` に、コピーしたファイル（相対パス・中身のハッシュ・上書き前の中身のハッシュ・上書きか新しく置いたか・
消えた識別子・中身の変わった識別子）、`prepared`（知らせを本文に載せた依頼の番号）、`notified`（知らせた先。空なら未だ）を置く。
親のブランチに乗って届く。

最初のレビューで知らせる。上書きの記録の `notified` が空なら、マージリクエストへの依頼（`review prepare`）の本文の頭に
「プロジェクトの設定が変わった」と、ファイルと識別子を載せ、`prepared` にその番号を書く。投稿が済んだら（`review requested`）、
`prepared` がその番号のときだけ `notified` に投稿の URL を書く。
このセッションで受けるレビュー（`--reviewed --chat`）では、確認の前に同じ文を出し、通したら `notified` に `chat` を書く。
2 回目以降のレビューでは載せない。

知らせるまで、親を閉じず Draft も外さない。`notified` が空のまま親の `ticket finish` か `review ready` を打つと止め
（どちらも `ops_close.close_problems` を通る）、ユーザに端末で `ccnavi --config-synced <親>` を打ってもらうよう案内する
（計画の無い親、全フェーズが `review: none` の親はこの経路になる）。`--config-synced` は知らせを出して `y` を受け、`notified` に `terminal` を書く。
`--agree` と同じく端末を求め、エージェントが Bash で打つ形は組み込みの deny（`builtin-guard-ticket-approval`）が止める。
早めに閉じる（`close-early`）ときは、閉じる前の確認に同じ知らせを出し、`y` で閉じたら `notified` に `terminal` を書く。

判定は変えない。コピーした中身はプロジェクトのレイヤーとしてそのまま読まれるが、読むのは元リポジトリに checkout されている版（11.2）なので、
適用されるのは親のブランチが統合先に入ってから。手元のワークスペースでは共通レイヤーと全欄一致の重複として後ろが捨てられる（11.4）。

保護の側（実行後チェック（7 章、11.7）とバックアップと復元（8.3））は、コピーした書き込みを戻さない。区別は内容で付け（`configsync.is_synced_write`）、
次のすべてが揃ったものだけを外す。

1. 置き場が、プロジェクトから切った承認済みの親チケットのワークツリー（名前が親の識別子で、その `project:` がワークツリーの
   プロジェクトと同じ）の中。元リポジトリ、子のワークツリー、チケットの無いワークツリー、他のプロジェクトのワークツリーは外さない
2. そのパス（解く前）の途中にシンボリックリンクが無い
3. その中身が、共通レイヤーの対応するもの（設定はプロジェクトのレイヤーの形に直したもの、スクリプトはそのまま）と同じ
4. その親の上書きの記録 `config-sync.json` が、その相対パスとその中身のハッシュを名指ししている（探すのはその親の 1 か所だけ）
5. 変更前のコミット済みの中身（呼び出しごとなら HEAD、ターンの終わりのコミット分ならターンの始まりの版）が、上書きの記録に残した上書き前の中身と同じ
   （外すのはコピーしてからコミットするまでに限る）

ターンの終わりにコミットに入った分は、ディスクではなくコミットされた中身で答える。中身はバイト列のまま読む。
バックアップと復元で外すのはワークツリー側の設定だけ。誰が書いたかの台帳は持たない。

残る穴: 上書きの記録は範囲を宣言しないファイルなので、実行後チェックから外れる。承認済みの親のワークツリーの中で、
コピーした分をまだコミットしていない間に、シェルから間接的に上書きの記録と中身を書けば、共通レイヤーの中身への書き換えは外れる（中身は共通レイヤーと
同じでなければならない）。`notified` を埋めて知らせを消すこともシェルからはできる。

コピーしたあと、コミットする前に共通レイヤーが変わる（`ccnavi-fetch.sh` の ff、ユーザの編集）と、コピーした中身は共通レイヤーと
合わなくなり、3 が外れて報告される（止まる側の誤報）。

代償。

- 2 重管理になる。共通レイヤーとプロジェクトのレイヤーは、次の親の着手まで食い違いうる
- プロジェクトのレイヤーに、共通レイヤーにあるファイルと同じ名前でプロジェクトだけの設定を持てない。書いても次の着手で上書きされる。
  プロジェクトだけのルールや配点は、共通レイヤーにパスで絞って書くか、共通レイヤーに無いファイルとして持つ
- 違う共通レイヤーを持つワークスペースどうしが同じプロジェクトを扱うと、着手のたびに上書きが入れ替わり、そのたびにレビューで知らせが出る。
  止めるにはユーザが共通レイヤーを揃える
- 並行する 2 本の親が別々に上書きすると、統合先に取り込むときに衝突しうる
- 共通レイヤーのルールの中身がプロジェクトの git に入る。public のリポジトリなら外に出る
- 判定の仕組みは変えていないので、プロジェクトだけを clone したユーザの判定は、そのユーザの共通レイヤーとプロジェクトのレイヤーの和で決まる。「見える」ようにはなるが、「揃う」わけではない
