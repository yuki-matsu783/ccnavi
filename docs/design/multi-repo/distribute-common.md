### 11.12 共通レイヤーを配る

共通レイヤーはワークスペースの git にあり、プロジェクトだけを clone したユーザからは見えない。そこで、作業を始める前に、
ワークスペースルートの `.ccnavi/config/common/` の中身を、そのプロジェクトの `.ccnavi/config/common/` へミラーする。プロジェクトの `.ccnavi/config/project/` には触れない。
ミラーは誰も編集しないので、上書きで失うものは無い。このため、上書きで消える識別子の名指し、コピー先の未コミットの変更で止める処理、
上書きの記録、最初のレビューでの知らせ、知らせるまで親を閉じさせない処理は要らない。

いつ: 親チケットの `ticket start`。親の `project:` が空（ワークスペース自身の作業）なら配らない。子の着手でも配らない（親のブランチに乗る）。

何を: ワークスペースルートの `.ccnavi/config/common/` の中身（`rules.yml`・`phases.yml`・`risks.yml`・期待する判定・配点が指す `scripts/` の下・作業・レビュー計画のテンプレート `templates/*.yml`。テンプレートは読めるかを確かめる、設計は 9.15）を、親のワークツリーにあるプロジェクトの
`.ccnavi/config/common/` へ、中身の違うものだけ上書きして置く（改行の違いは見ない）。共通レイヤーから無くなったファイルは、ミラーからも消す。ミラーは共通レイヤーの写しで、
プロジェクトの `config/project/` とは別なので、消して失うものは無い。消すのも一時ファイルからの置き換えと同じく、途中で止まれば戻す。

- 配点の `script:` の値は書き換えない。ミラーの置き場も `.ccnavi/config/common/scripts/` で、共通レイヤーと同じ表記のまま指せる（11.4.2）
- コピーする前に、コピーするものを、ミラー（単体 clone では共通レイヤー）として読めるか確かめる。error が 1 つでもあれば何もコピーせず、着手しない。
  共通レイヤーやスクリプトが読めないときも同じ。`phases.yml` はフェーズ定義として読めるかを確かめる（11.4.1）
- 共通レイヤーの `.ccnavi/config/common/` が無い、または空（配るファイルが 1 つも無い）なら、何も配らず、プロジェクトのミラーを消さない。着手は止めない（共通が無いのは「設定が無い」正常。ミラーの全消去事故を防ぐ）。1 ファイルでも在れば上のとおり
- コピー先かその途中がシンボリックリンクなら止める
- 上書きは一時ファイルからの置き換えで行う。途中で書けなくなったら、書いた分を元の中身へ戻し、戻せなかったものを名指しする
- 書くのは実行ファイル。コミットはエージェントが `ccnavi-git.sh` で行い、着手の出力がそれを案内する
- プロジェクトの `.ccnavi/config/project/` は読みも書きもしない

読まれ方は 11.4 のとおり。ワークスペースの中では、ミラーを共通レイヤーとして読まない（ワークスペースルートの `.ccnavi/config/common/` だけを読む）。
ミラーが共通レイヤーとして読まれるのは、そのプロジェクトだけを clone したときだけで、そのとき `.ccnavi/config/project/` は自身のレイヤーになり、
ワークスペースの中と同じ「共通 + 1 レイヤー」の和で判定される。ミラーのおかげで、単体 clone のユーザにも共通のルールが「見える」。

保護の側（実行後チェック（7 章、11.7）とバックアップと復元（8.3））は、ミラーの書き込みを戻さない。区別は内容で付け、
次のすべてが揃ったものだけを外す。

1. 置き場が、プロジェクトから切った承認済みの親チケットのワークツリー（名前が親の識別子で、その `project:` がワークツリーの
   プロジェクトと同じ）の中の `.ccnavi/config/common/`。元リポジトリ、子のワークツリー、チケットの無いワークツリー、他のプロジェクトのワークツリーは外さない
2. そのパス（解く前）の途中にシンボリックリンクが無い
3. その中身が、ワークスペースルートの共通レイヤーの対応するものと同じ（バイト列で比べる）

ターンの終わりにコミットに入った分は、ディスクではなくコミットされた中身で答える。
バックアップと復元で外すのはワークツリー側のミラーだけ。誰が書いたかの台帳は持たない。

内容が共通レイヤーと同じなら、書いたのが誰でも判定は変わらないので、上書きの記録などで書き手を絞らない。
プロジェクトの `.ccnavi/config/project/` と、共通レイヤーと中身の違うミラーは、いつもどおり戻す・報告する対象のまま。

コピーしたあと、コミットする前に共通レイヤーが変わる（`ccnavi-fetch.sh` の ff、ユーザの編集）と、ミラーは共通レイヤーと
合わなくなり、3 が外れて報告される（止まる側の誤報）。

代償。

- 2 重管理になる。共通レイヤーとミラーは、次の親の着手まで食い違いうる
- 並行する 2 本の親が別々に配ると、統合先に取り込むときに衝突しうる
- 共通レイヤーの中身（ルール・配点・スクリプト）がプロジェクトの git に入る。public のリポジトリなら外に出る
- 違う共通レイヤーを持つワークスペースどうしが同じプロジェクトを扱うと、着手のたびにミラーが入れ替わる。止めるにはユーザが共通レイヤーを揃える
- 「揃う」のは、ミラーを共通レイヤーとして読む単体 clone だけで、ミラーが古ければ古い共通レイヤーで判定される
- プロジェクトだけのルールや配点は、プロジェクトの `.ccnavi/config/project/` に書ける。ミラーとは別のファイルなので、着手のたびに上書きされることは無い
