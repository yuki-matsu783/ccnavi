# 複数人・別 PC・別セッションで進める

ccnavi は、1 台の PC・1 つのセッションで完結する個人作業だけを想定していない。チケット（親と子）ごとの作業を、別の PC、
別の Claude Code セッション、別の人が進めることを想定している。作業者のセッションとレビュアー（承認者）のセッションが別でも動く。
そのため、同じセッションの会話履歴や同じ PC のローカルな状態には頼らず、次のものを介して作業をつなぐ。

| つなぐもの | どこにあるか |
|---|---|
| 承認済みチケット、フェーズのマーカー（依頼済み・レビュー済み・省略）、親の閉じ方、子の記録（リスク・判定）、子のフロー、気づきの記録 | 親のブランチ（git）。各 PC では `.claude/worktrees/<親の識別子>` に親のブランチをチェックアウトしたものを正とする |
| 子の成果物 | 子の `finish` が親のブランチへ合流し、push する |
| レビュー依頼の内容（コミット・マージリクエストの番号と URL） | 親のブランチ上の `.requested` マーカー |
| マージリクエストとレビューのスレッド、その解決状態 | ホスト（GitHub・GitLab）。`ccnavi-review.sh` が取得して判定に渡す |

閉じた親子のチケットの退避（`logs/archive/`）は PC ごとのバックアップで、閉じたかの判定には使わない。ccnavi は取り込みの状態を持たない。
提案（`wip/proposals/`）は、それを持つリポジトリのツリーにコミットして運ぶ。

仕組みは [設計 9.17](../design/tickets/sharing.md)、承認と push は [設計 9.4](../design/tickets/approval.md) にある。

## 手順

1. セッションの開始で `ccnavi-fetch.sh` が、親のブランチと統合先を取ってきて早送りだけで進める。ignored のファイルと重なるときは上書きせず進めない。届かなければ、手元の版で判定して「リモート未確認」と示す
2. 親のワークツリーが無い PC では、承認や状態の操作は止まる。`ccnavi-start.sh --mr <番号>`（`--issue <番号>` だけだと、MR があるときは「このブランチで続けるか」を聞いて止まる。続けるなら `--issue <番号> --mr <番号>`）で、origin から取って親のワークツリーを用意する。親のワークツリーが無い PC のボードでは、その親子のチケットは出ない
3. 親のブランチが分かれたら、ユーザが `ccnavi-sync.sh [<親>]` を打って取り込む。衝突したら ccnavi が始めた merge だけ取りやめ、ユーザに判断を渡す
4. 状態を書く操作（`ticket start`・`finish`、`review` 系）は、ロック → 取り込み → 書く → コミット → push → 届いたかの確認の順で進む。push が通らなければ戻して取り込み直し、もう 1 回だけ試す。2 回目も通らなければ戻して `ccnavi-sync.sh` を案内して終わる

## 取ってくるときの挙動

- セッション開始時に取ってくるのは、チェックアウト中のブランチと、ワークツリーの起点になる統合先である。進めるのは fast-forward だけで、未コミットの変更があるツリーや分岐したツリーは触らず理由を 1 行で示す
- リモートに届かないときは、手元の版で判定する。認証は尋ねず、fetch 1 回を `CCNAVI_FETCH_TIMEOUT` 秒（既定 15）で打ち切る
- 認証で失敗したときはその旨を 1 行添える。ユーザが端末で一度 `git fetch origin` を打って資格情報を保存すれば、次のセッションから通る
- 親のワークツリーは、未コミットの変更があっても早送りを試し、書きかけや ignored のファイルと重なれば重なったパスを示して進めない。分かれていれば「取り込みが要る」と 1 行出す
- 取り込み（merge）と、親のブランチがリモートから消えたかの確かめは、ユーザが打つ `ccnavi-sync.sh [<P>...]` がする。取り込んだ後は親子のチケットを判定し直し、error があれば表示して終了コード 1 にする
- 判定は親のブランチとチケットの置き場だけで決まるので、別の PC でも同じ結果になる。親のワークツリーが無い・途中の操作（merge・rebase など）があるなどで決まらなければ、その親子のチケットの承認・状態の操作・実行前チェックを止める

親のブランチがリモートから消えている（改名・消し間違い・MR を閉じた後の片付け残り）のに、同じ名前で作り直して push する形は止まる。
迂回は、ユーザが端末で `git push origin <B>` を一度打つこと（元の名前で戻す）。診断は `sh .ccnavi/scripts/ccnavi-sync.sh <P>`。

## 承認者・レビュアーの操作

承認者・レビュアーの操作は、作業者の環境だけに限らない。

- **Chrome 拡張** は、承認者のブラウザとトークンだけで動き、親のブランチへ 1 コミットとして承認・レビュー済みを書く
- **VS Code のボード** は、ユーザの VS Code が ccnavi の実行ファイルを呼び、端末の入力を要しない

どちらも、ほかの人が作業しているセッションへ文を送る手段は持たず、結果は次の `fetch` / `sync` で作業側に届く。
拡張は表示と書き込みの入口で、判定のコアは hook と同じ ccnavi を使う。承認したことは、承認した人がそのあとセッションに一言送るか、
エージェントが `ccnavi-ticket.sh status` で確かめる（[チケットによる作業範囲の使い方](tickets.md)）。

## 子の作業を中断したとき

子の作業途中の状態は、リモートへ反映しない。子のブランチは手元に置き、`ccnavi-git.sh push` も子のワークツリーからは拒否される。
親のブランチに入るのは、子の `finish` が合流したものだけである。そのため、子の作業が途中で中断したときは、次の 3 つのどれかで進める。
別の PC へ途中の状態を引き継ぐ手順は用意していない。

| 続け方 | 向いているとき | 手順 |
|---|---|---|
| 同じ PC の別セッションで続ける | 中断した PC がそのまま使える | 子のワークツリー（`.claude/worktrees/<子>`）に入って作業を続け、`finish` まで進める |
| `cancel` して出し直す | やり方が違った。最初からやり直したい | 子を取り消し、新しい連番の子として出し直す |
| `finish` して続きの子を出す | 方向は合っていて、残りだけをやる。別の PC に移る前に区切りたい | 区切りのよいところまでコミットして `finish` し、残りを同じフェーズの続きの子として出す |

非対話セッション（`claude -p`、コンテナでの自動実行など）は、終わるとコンテナごと閉じ、手元の子の作業が失われる。
そこで子が詰まったりユーザの確認が要ったりしたときは、エージェントへの案内として、メインが `cancel` するか、`finish` して続きの子を `propose` で送るかを決め、リモートへ反映してからターンを終える。
手順は [.ccnavi/docs/ticket-work.md](../../.ccnavi/docs/ticket-work.md)。反映した続きの子は承認待ちの提案になり、ユーザが別の PC・別のセッションから承認できる。

### 同じ PC の別セッションで続ける

子のワークツリーとブランチは、その PC に残っている。新しいセッションから、子のワークツリーを作業ディレクトリにして続ける。
`start` は着手済みで拒否されるので、打ち直さない。状態は `ccnavi-ticket.sh status <子>` で確かめる。

セッションの起動・再開では、前のセッションのサブエージェントの「実行中の印」を捨てる。落ちた場合も、4 時間で実行中と数えなくなる。

### `cancel` して出し直す

```sh
sh .ccnavi/scripts/ccnavi-ticket.sh cancel <子> --reason <理由>
```

- 子が `doing/` から `done/` へ動き、`cancelled_at` と理由が付く。親のブランチへ push される。理由が空だと拒否される
- 承認を取り下げて `todo/` に戻す操作は無い。同じフェーズに、新しい連番の子（`<親>-<フェーズ>-<次の連番>`）として提案を書き、`propose` で送り、ユーザが承認する。識別子は再利用できない
- 取り消した子のワークツリーは片付く。未コミットの変更があるものは、消さずに名指しされる
- 取り消した子のブランチは手元に残り、途中のコミットはそこにある。親の `ready` のあとに、一覧をユーザに見せて確認を取ってから消す
- 取り消した子は先行として数えられない（先行は「`done/` にあり、取り消しでない」こと）。その子を待っていた子がいれば、提案の出し直しが要る
- `cancel` は親のワークツリーの状態を書く操作なので、中断した PC が使えなくても打てる

### `finish` して続きの子を出す

`finish` は、子のワークツリーに未コミットの変更が無く、変更が子の範囲に収まり、フェーズ定義の成果物とリスクの判定が揃っていれば通る。
チケット本文に書いた内容をすべて終えたかは見ない。区切りのよいところまでコミットして `finish` すれば、その成果が親へ合流し、push される。

残りは、同じフェーズに新しい連番の子として出す。

```sh
sh .ccnavi/scripts/ccnavi-ticket.sh finish <子>
sh .ccnavi/scripts/ccnavi-ticket.sh propose <続きの子>
```

- 続きの子の提案は、`propose` で送ってユーザの承認を受ける。エージェントが `doing/` に直接置くことはできない
- `finish` と `propose` は別々の操作で、それぞれが親のブランチへ push する。1 回で両方を送る操作は無い。`propose` は、親のブランチに未 push のコードがあると止まるので、先に `finish` を済ませる
- 続きの子は、`finish` 後の親の先頭から切られる。元の子の成果を含んだ状態で始まるので、元の子を先行に指定する必要は薄い（レビューを要るフェーズでは、元の子は `review/` に入り、先行の条件の `done/` を満たさない）
- 元の子は「完了」と数えられるが、本文の内容は終わっていない。続きの子の本文と、レビューの依頼文に、元の子の残りであることを書く
- レビューの依頼後に指摘が出たときは、ユーザが `decide` で「このフェーズで直す」を選ぶと、続きの子が `doing/` に直接できる。こちらは指摘を直すための経路で、`finish` のときに半端な状態を区切る使い方とは別である

## サブエージェントによる分担とは別のもの

サブエージェントは同じ PC・同じセッションの子のワークツリーで実装し、手元でコミットするだけで、親のワークツリーへは書かず、push もしない。
子の合流と push は、メインが打つ `finish` が行う。別の PC・別のセッション・別の人による分担は、上の表のとおり親のブランチとマージリクエストを介し、
サブエージェントの仕組みとは別の経路である。

## 前提と制約（保証しないこと）

- リアルタイム同期ではない。取ってくる・送るは `fetch` / `sync` / push の操作の時点で行う
- 同じ親に複数の PC から同時に書くことは保証しない。ぶつかったら止まる。排他のロックは同じ PC の中だけ。同じチケットを複数人が同時に編集しても安全であることは約束しない。分担の単位はチケットだが、同期と状態更新の単位は親のブランチ 1 本
- 競合を自動で解決しきるわけではない。GitHub では、書く時点の先頭が動いていれば Chrome 拡張が判定し直し、最大 3 回やり直したあと、ユーザの対応に切り替える。GitLab では、ファイル単位の確認と事後確認までで、別々のファイルを同時に書く競合は検出できない
- オフラインで進められるのは手元の版での判定までで、`ccnavi-sync.sh` は `ls-remote` に失敗すると止まり、push も届かない
- 未送信のコミットがあると、次の状態を書く操作が止まる
- 親のブランチに書いた人の識別や警報はしない。自分が出したレビューを自分で通すことは ccnavi では防がない（ホスト側のブランチ保護の仕事）
- 閉じたかどうかは、マージリクエストの状態を取得できなければ推定せず止まる
- 親のブランチがリモートから消えたことは、`ccnavi-sync.sh`・push の関門・セッション開始の fetch の時点で分かる。オフラインの hook では消失が分からない。閉じた識別子の再利用は、`ccnavi-start.sh` の開始時の照会だけが検知する
