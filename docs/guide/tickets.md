# チケットによる作業範囲の使い方

ルールが「どこに書かせないか」を長く決めるのに対し、チケットは作業 1 本のあいだ「今回どこに書くか」を決める。
チケットは範囲を決めるだけのものではなく、合意した作業をレビューまで進める仕組みである。目的・範囲・計画を提案に書き、人間が承認し、
フェーズを進め、先行との依存を守り、子へ分担し、子の差分からリスクを測り、必要なレビューを経て、指摘に対応して閉じる。
チケットは複数を同時に有効にできる。親（メインエージェント）が作業を子チケットに分け、子は別々のワークツリーでサブエージェントが実行する。

別の PC・セッション・人で進める場合は [複数人・別 PC・別セッションで進める](multi-pc.md)、レビューの受け方は [レビューの依頼と確認](review.md) を読む。
仕組みは [設計 9](../design/tickets.md)、外から観測できる約束は [要件 REQ-TKT](../requirements/tickets.md) にある。

## 使うかどうかはワークスペースが決める

`CCNAVI_TICKET_CONTROL` は `.claude/settings.json` の `env` に 1 つだけ書く設定で、ワークスペース（Claude Code を開いた場所）の
下のプロジェクト全部に同じ値が適用される。既定は `enable`。全体ルールだけで足りるワークスペースは `disable` を書く。
導入スクリプトは `--ticket-control` で聞き、常にこの 1 行を書く（[導入](install.md)）。

チケット制御が有効なワークスペースでも、作業の進め方は 2 つある。

- **直接作業**: 調査や小さな修正。チケットを起こさず、判定は全体ルールだけ。ワークスペースルート直下と、承認済みチケットの無いワークツリーがこれ。新しく切るワークツリーとブランチの名前は `<先頭の語>-<番号>-<slug>` の形にそろえる（形に合わないと `--lint` が warn で名指しする。拒否はしない）
- **チケット作業**: 設計に触れる・複数のフェーズに分かれる・ユーザのレビューが要る修正。提案を書き、`ccnavi-ticket.sh propose` で親のブランチへ送って（別のPCでも承認できる）承認を受け、フェーズとリスクの配点に従って進める

どちらで進めるかはモデルが決める。ccnavi はセッション開始時に、作業の進め方を `.ccnavi/CCNAVI.md` から渡す（サブエージェントには渡さない）。
渡す内容は [.ccnavi/docs/ticket-work.md](../../.ccnavi/docs/ticket-work.md) と [.ccnavi/docs/ccnavi-md.md](../../.ccnavi/docs/ccnavi-md.md) にある。
「作業の進め方」の末尾には、`CCNAVI_MODE` が `dry-run` のときだけ出る一文がある。内容は「一般の deny は止まらないが、チケットの関門と補助の保護で止まる。通ったことを許可と読まず、表示された案内に従う」である。
それ以外の手順（レビューの sh、`review: mr`、配点の書き方、後工程）は、必要になった場所で改めて届く。

## 置き場と状態

チケットは 1 本のファイルで、2 つの置き場を行き来する。提案は `wip/proposals/<状態>/<識別子>.md`、
承認済みチケットは `.ccnavi/approved/<状態>/<識別子>.md`。状態は置き場が表す。

```
  wip/proposals/todo ──ユーザが承認──→ .ccnavi/approved/doing
                                          │
                              エージェントが finish（レビュー要）
                                          ▼
  wip/proposals/review ──ユーザがレビュー──→ .ccnavi/approved/done
                                          ▲
                              エージェントが finish（レビュー不要）／cancel
```

| 置き場 | 意味 | 動かすもの |
|---|---|---|
| `wip/proposals/todo/` | 承認待ち | 親が書く。作成と編集は自由 |
| `.ccnavi/approved/doing/` | 承認済み。判定が範囲を読むのはここだけ | `ccnavi user agree`（ユーザ）、ボード、置き場のファイルの移動。続きの子をユーザが起こすときも、ここに直接置く |
| `wip/proposals/review/` | 作業が終わり、ユーザのレビューを待つ | `sh .ccnavi/scripts/ccnavi-ticket.sh finish <識別子>`（フェーズがレビュー要のとき） |
| `.ccnavi/approved/done/` | 閉じた。取り消しは `cancelled_at` を持ってここに入る | `ccnavi-review.sh confirm`、`ccnavi-user-decide.sh`、`ccnavi user reviewed`、Chrome 拡張のレビュー済み、`ccnavi-user-close-early.sh`（ユーザ）。レビュー不要の `finish` と `cancel --reason` |

- `.ccnavi/approved/` へ動かすのはユーザ、`wip/proposals/` へ動かすのはエージェント
- `review/` への直接の作成・移動は誰がやっても止まる。`.ccnavi/approved/` も止まる
- 動かすスクリプトと push はサブエージェントには打てない。サブエージェントは子のワークツリーで手元にコミットするだけで、親のワークツリーへの書き込みも止まる。子の合流と push は、メインエージェントが打つ子の `finish` が行う。親を閉じる（レビューの依頼・`ready`）のもメインエージェント
- 再開するときはユーザが `done/` から `doing/` へ戻す

フェーズのマーカーを含む遷移は [設計 9.6](../design/tickets/state-transitions.md)。サブエージェントが止まる条件の詳細は [設計 9.12](../design/tickets/subagents.md)。

## 識別子とブランチ名

- 親の識別子は `<先頭の語>-<番号>-<slug>`（`feature-63-integration-branch`、`hotfix-64-統合先の解決`）。先頭の語は既定で `feature` `hotfix` `fix` `bugfix` `chore` `refactor` `docs` のどれか。チャットで「hotfix で」と言えばエージェントがその語で書く
- リストを変えるときだけ `.claude/settings.json` の `env` に `CCNAVI_BRANCH_PREFIXES=feature,hotfix,fix` のように書く
- 番号は issue の番号（通し番号は直接作業のワークツリー名だけに使う）。slug には日本語も使える
- 子の識別子は `<親>-<2 桁のフェーズ番号>-<2 桁のフェーズ内の連番>`。ワークツリーの名前は識別子と同じ

提案の書式、親のワークツリーの扱い、深さと件数の上限は [設計 9.3](../design/tickets/proposal-format.md)。ワークツリーの名前の決まりは [.ccnavi/docs/worktree.md](../../.ccnavi/docs/worktree.md)。
提案はエージェントが書くので、ユーザが frontmatter を直接書くことはほとんどない。ユーザが見るのは承認の画面である。

## 効くのは承認したものだけ

判定が読むのは `.ccnavi/approved/doing/` の承認済みチケットで、`wip/proposals/todo/` の提案ではない。承認のあとに同じ識別子の
提案を書いても範囲は適用されない（親の改版〔計画・`phases:`・範囲〕だけが承認の対象に入る）。承認の詳細は [設計 9.4](../design/tickets/approval.md)。

```sh
ccnavi user agree
ccnavi user agree i0002 i0002-01-01   # 並べた識別子だけを承認の対象にする
```

全ツリー（ワークスペース、プロジェクト、ワークツリー）の `wip/proposals/` を走査し、未承認のものをまとめて見せる。
画面に出るのは、親が新たに書けるようにする領域、子が親の範囲をどこまで絞ったか、子ごとの人間レビュー要否、計画、親の `issue:`。
子の範囲が上限を超えていれば、また親の `allow` の項が計画のどの定義の `scope` とも重ならなければ、「チケットで編集対象としているが、書き込めない場所」の見出しで出る。

- 識別子を並べると対象を狭める。承認待ちに無い識別子や、承認待ちの親の改版を外した子が混じれば、何も承認しない
- 対象から外した親を持つ子は「親が承認されていない」で承認されない。前のフェーズが閉じていない子も承認されない
- 終わったフェーズに子を足して承認すると、そのフェーズは開き直り、マーカーは全部消える
- リスクの点は承認では数えない。子を閉じるときに実績で測る（「実績のリスク」）
- 計画の待ち方は、承認の画面の待ちの一覧（「すぐ始まる: 1, 3」）で確かめる。辺の書き漏れは並行として通る
- 合意は全部 `user agree` を通る。全体計画は親の承認、各フェーズの計画はその番号の子の承認、フィードバック計画は `feedback:` を足した親の改版の承認

承認する場所は 4 つある。どこで承認しても**承認はチケットの中身を変えない**。提案のファイルを
`todo/` から `doing/` へ動かすだけで、欄を書き足さず、改行も BOM も変えない。手で動かした承認と ccnavi の承認は、承認済みチケットが
提案とバイト単位で同じになり、見分けが付かない（欄が無いことや未コミットであることは、承認が途中で止まった印ではない）。

| 経路 | 形 |
|---|---|
| 端末 | `sh .ccnavi/scripts/ccnavi-user-agree.sh [<識別子>...]`。一覧を見せて y/N を取り、y のあとに提案が更新されていれば「内容が更新されました」と最新を表示し直して確認し直す。通れば `ccnavi-user-push-approved.sh` でコミットして push する。一部だけ書けたときも、書けた分をコミットして push し、書けなかった提案と未送信のパスを言う |
| ボード | VS Code のボードで承認の一覧から選んで承認する。見せたあとに提案が更新されていれば承認せず、「内容が更新されました」と最新に読み直す。1 件以上書けたら `ccnavi-user-push-approved.sh` を統合ターミナルへ送る |
| Chrome 拡張のボード | ブラウザと PAT だけで、リモートのブランチの承認待ちを見て承認する。承認は 1 コミットとしてリモートのブランチに書かれる（[拡張の README](../../extensions/chrome/ccnavi-approval/README.md)） |
| ファイルを動かす | 提案を `.ccnavi/approved/doing/` へ動かす。GitLab や GitHub の画面しか使えないユーザ向け。承認の画面を通らないぶん、構造の検査は判定のときに行い、引っかかれば `DENY_TICKET_BLOCKED` で止まる（`--lint` でも分かる） |

エージェントが承認を実行する形は止まる。エージェントは、承認できる状態かを確かめる `--agree --preview --verify` だけを打てる。

### 承認したら push する

**承認済みチケットは親チケットのブランチに乗って他の機械へ届く。** 承認しても push しなければ、他の機械では承認されなかったことになる。
承認の push は `sh .ccnavi/scripts/ccnavi-user-push-approved.sh` で行う。端末とボードの承認は、このスクリプトを自動で呼ぶ。

- ワークスペース、`projects/*`、`.claude/worktrees/*` のツリーごとに、変更があれば置き場（`.ccnavi/approved/`）だけをコミットし、そのブランチへ push する
- `main` / `master` / `develop` / `release` / `release/*` と、そのリポジトリの統合先は push せず、コミットまでで止める
- コミットするものが無ければ `コミットして push する承認済みチケットはありません。` と 1 行出す
- エージェントが打つ形は止まる

| 終了コード | いつ |
|---|---|
| 0 | コミットするものが無い、または全部コミットした（push しなかったブランチ、飛ばしたツリーを含む） |
| 1 | `git add` / `commit` / push が失敗したツリーが 1 つ以上ある。巻き戻さないので、もう一度打てば送れる |
| 2 | 引数の誤り、ワークスペースルートが見つからない |

`ccnavi-user-agree.sh` は承認が通れば、承認の push の段が 1 で終わっても 0 を返す（未送信のパスは文面で言う）。
内部の詳細（部分的に書けたときの扱い）は [設計 9.4](../design/tickets/approval.md)。

消えた親ブランチを作り直す push は拒否される。迂回は、ユーザが端末で `git push origin <B>` を一度打つこと。詳しくは [複数人・別 PC・別セッションで進める](multi-pc.md)。

### 承認したことを伝える

承認したことは、拡張が渡す文と `ccnavi-ticket.sh status` で伝わる。hook は承認を伝えない。
VS Code のボードは、承認の文をオーバーレイの 2 ボタン（コピー、新しいセッションで開く）から渡せる。端末・GitLab や GitHub の画面・Chrome 拡張で
承認したときは、ユーザがそのあとセッションに一言送る。

ユーザがレビューを終えたことは、VS Code のボードの［レビュー完了］で済ませる。ボードがエージェントに `confirm` を打たせることはしない。
端末の `confirm` や `decide`、Chrome 拡張のレビュー済みで済ませたときも、ユーザがそのあとセッションに一言送り、エージェントは `status` で確かめる。

### 状態を聞く

承認済みチケットの状態は `status` で聞く。ファイルや `git status` を読んで推測せず、ccnavi に聞く。

```sh
sh .ccnavi/scripts/ccnavi-ticket.sh status          # 作業中・レビュー待ち・承認待ちのチケットがある親子を全部
sh .ccnavi/scripts/ccnavi-ticket.sh status i0002    # その親子だけ（子の識別子を渡しても親子で出す）
```

チケットごとに、置き場とツリー、承認の時刻、着手しているか、置き場のファイルが未コミットか・コミット済みで未 push か、止まっている理由、
次の一手を出す。読むだけで何も書かない。push 済みかどうかは、最後に取得したリモートの状態に基づくため、最新の状態と異なる場合がある。最新にしたければ先に `ccnavi-sync.sh` を打つ。
未コミットの承認済みチケットがあるときは、ユーザが `ccnavi-user-push-approved.sh <親>` を打つ。親を渡して何も見つからなければ終了コード 1。
出力の読み方は [設計 9.4](../design/tickets/approval.md)。

## 止まったときの見方

Write / Edit の対象が `.claude/worktrees/<名前>/` の中なら、その名前と同じ識別子の承認済みチケットで判定する。
呼び出し元の cwd も、サブエージェントかどうかも見ない。ワークスペースルート直下と、チケットの無いワークツリーはルールだけで判定する。
ルールとチケットの判定を両方出し、**強い側を採る**（`deny` > `ask` > `allow` > 何も言わない）。同じ強さならルールの判定と文面を使う。

| ルール | チケット | 結果 |
|---|---|---|
| `deny` に当たる | どれでも | 止まる（ルールの文面） |
| `ask` / `allow` に当たる | 範囲の外、または `deny` の項 | 止まる（`DENY_TICKET_SCOPE`） |
| `ask` に当たる | 範囲の中（ask / allow）、またはチケットが無い | ユーザに確認が出る（`RULE_ASK`） |
| `allow` に当たる | 範囲の中（ask） | ユーザに確認が出る（`TICKET_ASK`） |
| `allow` に当たる | 範囲の中（allow）、またはチケットが無い | 通る |
| 何も言わない | 範囲の中（allow） | 通る |
| 何も言わない | 範囲の中（ask） | ユーザに確認が出る（`TICKET_ASK`） |
| 何も言わない | 範囲の外、または `deny` の項 | 止まる（`DENY_TICKET_SCOPE`） |
| 何も言わない | ワークツリーにチケットが無い | 権限モードに従う（`UNDECLARED`） |

チケットの判定がルールの判定より強かった回は、文面の頭に `rule: <id> (allow) lets this through, but the ticket for this worktree narrows it` が載る。
上限で止めたときは、文面の頭に `limit: phase type 設計 (design): wip/design/*, docs/*` や `limit: parent i0001: src/*, tests/*` の形で 1 行載る。
子の範囲は、子の宣言を親の範囲とフェーズ定義の `scope` の両方で切り詰めたものである。

範囲の外として扱わない場所は次のとおり。

- 提案の置き場（`wip/proposals/`）と承認済みチケットの置き場（`.ccnavi/approved/`）。`review/` と承認済みチケットは組み込みの deny が止める
- 下書きの置き場。ツリーのルート直下の `wip/handoff/` の下で、大文字小文字は区別しない
- ELI5 の HTML の置き場。ワークツリーのルートからの `wip/eli5/` の下で、大文字小文字は区別しない

シェルが書いたものは実行後チェックが `POST_TICKET_SCOPE` で報告する。子のワークツリーは、サブエージェントの終了時に基準点からのコミット済みの差分と未コミットの両方を見て、範囲外が残っていれば 1 回だけ差し戻す。

ワークツリーへの書き込みを `allow` で許しているルールがあっても、承認済みチケットに結び付いたワークツリーの書き込みはチケットの範囲に制限される。
止まったら、ルールを緩めるのではなく、その場所を範囲に持つチケットを提案する。判定の仕組みは [設計 9.5](../design/tickets/judging-by-path.md)。
記録からルールを狭めた回を拾う `jq` の例も設計 9.5 にある。

## フェーズとレビュー

フェーズの終わりは、ユーザの手が入るところ（HITL ポイント）の 1 つ。ユーザが関わるのは、範囲の承認・レビュー・未解決の受け入れの 3 か所にまとめてある。
同じ親の同じ `phase` の子が `doing/` に 1 枚も無く、`review/` か `done/` に 1 枚以上あれば、そのフェーズは終わり。取り消しだけのフェーズは終わらない。
設計は [9.8](../design/tickets/hitl.md)。

ユーザがどこで見るかは `none` / `mr` の 2 つで、次のうち厳しい側が採られる（`none` < `mr`）。

- フェーズ定義の `review`
- 親の計画の項の `mr`（フェーズ定義の `review` が `none` でも `mr` にする）
- 延期した番号の分を引き受けているなら、その分の宣言

閉じた子の `human_review.required` が `true` か、実績のリスクが HIGH 以上のときは、`none` を `mr` に上げる。

| | `mr` | `none` |
|---|---|---|
| 返す文 | すべての子が合流済みと確かめ、`request` でレビューを頼み、ターンを終えてユーザを待て | レビューを省略して次のフェーズへ進める |
| HITL ポイント | 来る。レビュー済みのマーカーまで止まる | 来ない。省略のマーカーを残す |
| 先へ進める者 | `ccnavi-review.sh confirm` / `ccnavi-user-decide.sh`、Chrome 拡張のレビュー済み | — |
| `review/` の子 | レビュー済みで `.ccnavi/approved/done/` へ動く | `finish` の時点で `done/` へ |

止めている間は、その親の cwd からのサブエージェントの起動と Bash が止まる（`DENY_PHASE_REVIEW`）。通すのは `ccnavi-ticket.sh` `ccnavi-review.sh`
`ccnavi-git.sh` の 3 本だけ。Write / Edit は通すので、次のフェーズの計画はレビュー前に進められる。
止めている間は、依頼を出すまでが「レビュー準備中」（次に動くのはエージェント）、出してからが「レビュー待ち」（次に動くのはユーザ）。
レビュー待ちで止めるのは親ごとなので、どれかの枝がレビューを待つ間は別の枝にも子を起こせない。

レビューの受け方は [レビューの依頼と確認](review.md)。

## フェーズ定義と計画

`phases.yml` に**フェーズ定義**を書き、親が `plan:` にその並びと順序（項の `after`）を書くと、フェーズに意味が付く。
フェーズ定義はユーザが持つ設定で、エージェントは書き換えない。親は `plan:` を持つことが必須で、計画の無い親は `ticket start` が止まる。
書き方と置き場は [設計 9.7](../design/tickets/phases.md) と [.ccnavi/docs/grow-phases.md](../../.ccnavi/docs/grow-phases.md)。設定の追加や確かめには `ccnavi-config` スキルを使う。

ユーザが気にするのは次の点である。

- 承認の画面の待ちの一覧（「すぐ始まる: 1, 3」）で、書き漏れを確かめる。**辺の書き漏れは並行として通る**
- 合意は全部 `user agree` を通る。全体計画は親の承認、フィードバック計画は全体計画の最後のレビューが済んでからの改版の承認である
- 順序は承認で止まる。N 番目の子は、N 番目が待つ番号が全部閉じてレビューが済むまで承認されない
- 改版で変えられるのは `plan`・`feedback`・`phases:`・範囲だけである。範囲を変える改版は、作業中（`doing/`）の子が居ないときだけ通る
- 改版は、承認済みチケットが在るツリー（親のワークツリーがあればそこ）の `todo/` に書く。ほかのツリーに書いた改版は承認待ちに入らず、`user agree` と `--lint` が置き場を名指しする

提案の雛形は、エージェントが `ccnavi ticket new` で作る（[設計 9.3](../design/tickets/proposal-format.md)）。

## 実績のリスク

リスクは宣言ではなく実績で測る。子を `ticket finish` で閉じるとき、子の差分を数えて点を付け、フェーズの点は子の最大値とする。
**HIGH 以上なら、宣言に関わらずそのフェーズは人間レビューが要る扱いになる。** 宣言が `none` なら `mr` に上がる。

点と加点した理由は、閉じたときの出力、フェーズの終わりの文面、`--explain`、レビューの依頼文の先頭
（「このレビューのリスク: 58 (HIGH) — 行数が多い（…）」）に出る。配点の書き方と測り方は [設計 9.9](../design/tickets/risk.md)、配点の育て方は [.ccnavi/docs/grow-risks.md](../../.ccnavi/docs/grow-risks.md)。
不正な `risks.yml` は組み込みの配点を使い、`--lint` と閉じたときの出力がそのことを示す。

## 親を閉じる

親を閉じられる状態（全フェーズが終わり、フィードバック計画が承認され、レビューが済んでいる）になったら、順は「親を `finish` で閉じる → push → `ready`」である。
`ready` は Draft を外す（「マージに進んでよい」の合図）。Draft を外すのは親で、**マージはユーザ**である。取り込みは squash（GitLab ではマージリクエストの `squash` を有効にする）。

- 最後のレビューが済んだあとは、ユーザがレビュー済みにした時点で、この順の操作まで合意に含まれる。エージェントは push と Draft を外す前にユーザへ確認を取り直さない
- `ready` は、親の承認済みチケットが `done/` にあること、`wip/` に未追跡のファイルが無いこと、未コミットが無いこと、push 済みであることを求める。`wip/` の追跡済みのファイルは `ready` が消す。未追跡のものは履歴から戻せないので、あれば消さずに名指しして止まる
- `ready` は親のワークツリーの中からも、外から `ready --parent <親>` でも打てる

設計は [9.11](../design/tickets/close.md)。

### まだ残っているが早めに閉じたいとき

ユーザが端末で `ccnavi-user-close-early.sh --reason <理由>` を打つ。作業中の子がいる間は打てない。残っているものを全部見せてから y/N を取る。
Draft は親が片付けて push したあとの `ready` で外す。

### ワークツリーは ccnavi が片付ける

マージを待たずに片付ける。

- 閉じた子のワークツリーは、完了でも取り消しでも消す。残るのは作業中（`doing/`）とレビュー待ち（`review/`。見返す場所）の子のワークツリー
- `ready` が Draft を外したあとの最後に、子と親を片付ける。Draft を外す前と、外せなかったときは消さない。未コミットの変更や git が無視しているファイルがあるワークツリーは、理由を出して残す
- 子の手元のブランチは、合流した子なら条件を確かめてから消す。取り消した子は、一覧を出すだけで、消すのはユーザである。消してよければユーザが先頭に `!` を付けて `ccnavi-user-clean-branch.sh <子の識別子> --confirmed` を打つ
- 親の手元のブランチは MR がマージされるまで残す
- cwd が消す対象の中にあるときは消さず、外に出てから打つ 1 本（`sh .ccnavi/scripts/ccnavi-clean.sh --worktree <名前>`）を出す
- この 1 本が Claude Code の自動モードの分類器に止められたら、ユーザに許可を頼むか、ユーザのホームの `~/.claude/settings.json` の `permissions.allow` に操作ごとに絞った許可（例 `Bash(sh <ワークスペース>/.ccnavi/scripts/ccnavi-clean.sh --worktree *)`）を足す。分類器はプロジェクトの `.claude/settings.json` を読まない。`ccnavi-git.sh *` のような広い許可は push まで通すので勧めない

片付けの条件の詳細は [.ccnavi/docs/worktree-cleanup.md](../../.ccnavi/docs/worktree-cleanup.md) にある。

### 閉じたチケットは既定のブランチに残らない

`ready` は、閉じた親子のチケットをワークスペースの `logs/archive/` へ移す。`logs/` は git が追跡しないので、git の上では削除になる。
その削除を push してから Draft を外すので、squash でマージすると既定のブランチにはチケットが残らない。退避は手元の機械にだけ残るバックアップで、閉じたかの判定には使わない。
仕組みは [設計 9.11](../design/tickets/close.md)。

### MR がマージされたあと

`ccnavi-sync.sh` が、MR がマージされたかをホストに聞き、マージ済みなら手元の親を片付ける。MR をマージせずに閉じた親（放棄した親）は、親のワークツリーを片付けても
`ccnavi-sync.sh` が列挙し続けて、毎回案内を出す。ユーザが端末で `ccnavi worktree retire --abandon <親>` を打って記録を消すと、列挙されなくなる（ブランチは消さない。エージェントからは打てない）。

## issue・MR を指定された依頼

「#152 を直して」「!5 の指摘に対応して」のように issue や MR を指定して頼むと、ccnavi が依頼文から指定（`#152`・`issue 152`・`.../issues/152`、`!5`・`MR 5`・`PR #12`・`.../pull/5`・`.../-/merge_requests/5`）を見つけ、
着手の前に `ccnavi-start.sh` を打つよう、エージェントに指示を足す。指示を足すだけである。チケット制御が disable なら足さない。

チケット作業は必ず issue と MR のセットで進める。最初に、ホストの API（認証・リポジトリの有無・書き込みの権限）と git のリモートが使える状態かを確かめる。

```sh
sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-start.sh --check   # 0 使える / 1 不備 / 4 確かめられない項目がある
```

そのうえで次の 1 本を打つ。既存の候補が無ければ、Draft MR・ワークツリー・ブランチを作る。

```sh
sh <ワークスペースルート>/.ccnavi/scripts/ccnavi-start.sh --issue 152   # MR なら --mr 5。両方も渡せる
```

終了コード 0 で終わったら、採用した MR と、その MR が閉じる issue と、元ブランチが確定している。出力の「必須」の行の `issue:` と `mr:` を提案に書く。どちらかが無い親の提案は、`ccnavi ticket new`・承認・`--lint` が止める。
MR の無い候補（作りかけの再開を除く）は成功させず、終了コード 3 で一覧を出す。
ホストに届かないときは、`--issue`・`--mr`・`--branch` の 3 つと `--mcp-checked` がそろうときだけ、ホストを見ずに成功する。
`ccnavi-ticket.sh` の `start`・`finish`・`propose`・`consolidate` も、ロックの前に同じ確認（API と git）を自動で行う。直接作業では確かめない。

依頼の URL のリポジトリが `projects/<名前>` のものなら、そこに `cd` して `--repo <owner/repo>` を付けて打つ。実行した場所の origin と違えば、ホストに問い合わせる前に止まって移動先を案内する。

候補が複数あるときは、エージェントが一覧を見せて「既存のブランチで続ける・新しく `<先頭の語>-<番号>-<slug>` を切る・やめる」を聞くので、答える。
ホストに届かないときは、出力の案内どおりに進む。ほかの終了コードや候補の探し方は [設計 9.13](../design/tickets/branch-lookup.md) と [.ccnavi/docs/worktree-start.md](../../.ccnavi/docs/worktree-start.md)。

## プロジェクトのスキル

プロジェクト向けのスキルの形の手順書は、プロジェクトの git で育てるため、`projects/<名前>/skills/<スキル>/SKILL.md` に置く（頭の frontmatter に `name` と `description`）。
Claude Code はそこをスキルとして読まないので、ccnavi が目録（名前・説明・場所）をエージェントに渡す。本文はエージェントが要るときに参考に開く。

- プロジェクトが自前の `.claude/skills/` を持つなら、Claude Code がそれを別に読む。ただし、ワークスペースから起動した場合に読み込まれるかは、`projects/` がワークスペースの git で無視されているかで変わる。ccnavi は `projects/` を無視させるので、ワークスペースから起動してプロジェクトの `.claude/skills` に頼ることはできない。プロジェクトで起動すれば、そのプロジェクトの `.claude/` のスキルと hook だけが使われる
- `skills/` はプロジェクトだけを clone した人の手元にも git で入るが、目録は渡らない

目録の渡し方、上限、名前の規則は [設計 11.13](../design/multi-repo/skills.md)。

## プロジェクトを clone したあと

プロジェクト管理画面の clone は、`git clone` をターミナルへ送るだけで、リポジトリを取得する操作である。ccnavi の導入（setup）は含まない。
共通レイヤーのミラーは、そのプロジェクトで親チケットに着手（`ticket start`）した時点で配られる。子の着手と、ワークスペース自身の作業では配らない。
ワークスペースの中では共通レイヤーをルートから読み、ミラーは使わない。ミラーが働くのは、プロジェクトだけを clone して使うとき（単体利用）である。
単体利用の手順と、まだ対応していない用途は [単体 clone の未解決事項](../design/multi-repo/standalone-clone-gaps.md)にある。ここに無い用途を「使える」と読まない。

## 作業・レビュー計画のテンプレート

完了した作業の計画とフローを、次の作業で使い回すためのひな形である。1 ファイル（`<名前>.yml`）に、親の作業・レビュー計画と、各子のフローの本文を入れる。
一覧・検索・表示は読むだけで、何も書かないので、エージェントが打ってよい。

```sh
ccnavi --templates                          # 一覧（名前・層・説明・いつ使うか）
ccnavi --templates --keyword 調査            # name・description・when の検索（語を重ねるとどれか）
ccnavi --templates --show feature           # 1 本の中身（計画・フロー・検査・ファイルの本文）
ccnavi --templates --layer lib --json       # 共通 + プロジェクト lib の統合結果。画面向けの完全な答え
ccnavi --templates --draft <親> [--name <名前>] [--to common|project] [--layer <名前>]
                                            # 完了した親から下書きを wip/handoff/ に作る（エージェントが打ってよい）
ccnavi user handoff [<相対パス>…]            # 下書きの一覧と差分（何も書かない。ユーザ専用）
ccnavi user handoff <相対パス>… --yes --expect <ハッシュ>
                                            # 取り込む（ユーザ専用）
```

置き場は 2 層で、使うのは共通と 1 つのレイヤーの和である。

| 層 | 置き場 |
|---|---|
| 共通 | `.ccnavi/config/common/templates/<名前>.yml` |
| プロジェクト（`self` かプロジェクト名） | `.ccnavi/config/project/templates/<名前>.yml` |

置き場が無いのは正常。同名のテンプレートが両方に在るときは、全欄が同じならレイヤーの側を捨てて info、中身が違えばレイヤーの側だけを使わず error になる（どちらが効くかを黙って決めない）。
形と検査の規則は [設計 9.15](../design/tickets/templates.md)。

### 下書きを作って取り込む

溜める流れは「完了した親 → 下書き（効力なし）→ ユーザが差分を読んで取り込む」である。

1. **下書きを作る**（エージェントが打ってよい）。`ccnavi --templates --draft <親>` は、完了した親（`done/` に在る）の計画と各子のフローを 1 ファイルに写し、`wip/handoff/` の下に書く。名前の既定は親の識別子、`--to` の既定は `project`（`common` は他のプロジェクトへ配られる）
2. **`ready` の前に作る。** 計画を持つ親を `ticket finish` で閉じると、出力の最後に下書きを作る合図が出る。`ready` で閉じると下書きの材料は退避されて拾えない。取り込んでいない下書きは `ready` を止めるので、取り込むか消してから `ready` を打つ
3. **下書きには効力が無い。** 固有名の一般化は機械ではやらない。`description` と `when` の `TODO` の印をエージェントが消す
4. **取り込む**（ユーザ専用）。`ccnavi user handoff` で対象の一覧と差分を見て、`--yes --expect <ハッシュ>` を付けて書く。書くときは端末の前のユーザが打つ。取り込めたら下書きは消える

取り込みの規則（conflict・検査・制御文字の見え方）は [設計 9.19](../design/tickets/handoff.md)。エージェント向けの手順は [.ccnavi/docs/templates.md](../../.ccnavi/docs/templates.md)。

### テンプレートから親の提案を作る

エージェントが、識別子と同名のワークツリーの中で打つ。

```sh
ccnavi ticket new <識別子> --title <題> --template <名前> [--layer <名前>] [--with-feedback] --issue <N|owner/repo#N> --mr <N>
```

`wip/proposals/todo/<識別子>.md` に、テンプレートの項から計画を書いた親の提案ができる。

- フィードバック計画は既定では書かない。全体計画の最後のレビューを見て、改版で 1 回だけ足す決まりだからである。最初から入れたいときだけ `--with-feedback` を付ける
- 子の提案の足場は作らない（子の提案は手で書く）。子のフローの下書きだけを `wip/proposals/flows/` に書く。下書きに効力は無く、ユーザがフロー編集画面で読んで取り込むまで効かない
- 同じ識別子の提案・承認済みチケットなどが在れば、何も書かずに断る

出力の例は次のとおり。

```text
feature-9-from-template の提案を .../wip/proposals/todo/feature-9-from-template.md に書いた（テンプレート feature、common の .ccnavi/config/common/templates/feature.yml）
plan（3 項）: 1 research / 2 design（待つ 1・defer） / 3 implement（待つ 2）
テンプレートにはフィードバック計画（2 項）がある。全体計画のレビューを見てから足すなら、`--with-feedback` を付けて作り直すか、提案を改版で足す
フローの下書き 1 件:
  計画の 3 番目 -> feature-9-from-template-03-01: .../wip/proposals/flows/feature-9-from-template-03-01.yml
下書きには効力が無い。フローの文は子への案内文になるので、ユーザがフロー編集画面で読んで取り込むまで効かない。...
```

書いたあとは、rationale と本文、テンプレートの固有名の残りを直し、`ccnavi --lint` で確かめてから承認をユーザに頼む。

### テンプレート管理画面

VS Code 拡張の「テンプレート管理画面」で、テンプレートの一覧・検索・表示ができる。対象は共通の設定、ワークスペースの設定、プロジェクトの設定の 3 種で、「設定」の欄で切り替える。
一覧は「統合結果」（共通と選んだ層で実際に使われる結果）と「層ごと」（層ごとの生の中身）を切り替えて見られる。
開いている対象の層のテンプレートは、行の「編集」で、計画の項と線を図で、子のフローをフロー編集と同じ図で直して保存できる（「作る」で新規も作れる）。下書きは読むだけで、取り込みは取り込み待ち画面で行う。

下書きの取り込みは「取り込み待ち」の画面で行う。`wip/handoff/` の下書きのうち、テンプレート・設定（`rules.yml` など）・文書の種類を一覧にし、差分を読んでから取り込む。
防御のファイル（`.ccnavi/scripts/`・hook・`settings.json`）は一覧に出るが、ボードからは取り込めず、端末で打つコマンドを案内する。
作業中のチケットがあると、テンプレートと設定の取り込みは止まる（共通とワークスペースの設定は、どのツリーの作業中でも止まる）。
`CCNAVI_TICKET_CONTROL` が `disable` なら入口ごと出ない。
