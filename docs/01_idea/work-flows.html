直接作業とチケット作業の流れ

ccnavi には、性格の違う 2 つの作業の流れがあります。どちらも、前の作業が終わった時点で、次の作業だけを案内します。線の横の「次:」が、その案内です。

直接作業

承認なし。調査や小さな修正をその場で進め、統合先へ取り込む

  1. ワークツリーを切るccnavi-worktree.sh
    次: ワークツリーの中で編集する
  2. 編集する
    次: 区切りがついたらコミットする
  3. コミットするccnavi-git.sh commit
    次: AI のレビューを頼む。まず敵対的レビュー、続けて別の AI によるフラットな評価
  4. 2 段のレビューを受ける
    次: 指摘を取り込んで修正し、integrate を打つ
  5. 取り込みを準備するintegrate
    次: 差分をユーザに報告する
  6. ユーザの了承で確定するintegrate-done
    次: push はユーザに頼む
  7. ユーザが git push する

チケット作業

issue とマージリクエストのセット。計画を承認してから、子ごとに進める

  1. 提案を書くticket new
    次: 空欄を埋めて、approval-request で送る
  2. 提案を送るapproval-request
    次: ユーザに承認を頼む
  3. ユーザが承認する
    次: 親を start する
  4. 親を始めるticket start
    次: 子を start する
  5. 子を始め、実装を任せるticket start <子>
    次: 実装が終わったら、子を finish する
  6. 子を閉じるticket finish
    次: レビューを依頼する。不要なら親の status を見る
  7. レビューを確定するconfirm / decide
    次: 親の status で、次の子か親の finish かを確かめる
  8. 親を閉じるfinish → ready
    次: マージリクエストのマージはユーザに頼む
  9. ユーザがマージする
    次: ccnavi-sync.sh で同期する
  10. 同期するccnavi-sync.sh

「次:」の文言は、流れを説明するための例です。実際の出力は、操作ごとの文面ファイルで決まります。
