CCNAVI / IDEA

ccnavi の思想

7 つのテーマごとに、なぜ・何を・どう

エージェントに任せる範囲を広げながら、人間の判断と目が届く道を失わせない。
OVERVIEW / 全体像

ccnavi が解決する 7 つのテーマ

1 指示を緻密に書いても、希望どおりに動かない外れを検知し、ガイドして、やり直させる
2 目的のために、制約を突破しようとする守る対象を決め、あとは合意に委ねる
3 レビュー管理が要るが、作業は複数の PC・セッションに散るissue・MR・ブランチを 1:1:1 で紐づける
4 共通ルールとプロジェクトのルールを分けて管理したいルールを git で管理し、共通を同期する
5 分け方・範囲・レビューの場所を、計画で決めたい分類は事前に定義し、承認どおりに進める
6 リスクの高い作業は、人間が必ず見る事前に定義し、一定以上はレビュー必須
7 同じ流れを毎回作り直し、状況も見えにくいテンプレートで再利用し、拡張で見せる
テーマ 1 / 指示が守られない

指示を緻密に書いても、希望どおりに動かない

WHY

  • hello と尋ねたら answer.md に「こんにちは」と書くスキルでも、必ず従うとは限らない
  • LLM の答えは確率的。絶対にはならない
  • スキル自体が使われないこともある

WHAT

  • 外れを検知し、ガイドを添えてやり直させる
  • 外れる確率が 1% の LLM でも、ほぼ希望どおりに動く
  • hook を作る手間を軽くする

HOW

  • 判定と案内は、モデルの外の hook が行う
  • 検知と案内はルールとして宣言する。hook を自作しない
  • 起きた時点で、その場に案内する
テーマ 2 / 制約の突破

エージェントは、目的のために制約を突破しようとする

WHY

  • 悪意なく「hook を外す」「deny を緩める」を選ぶ
  • パターン一致は構造を見ない。禁止の文は確率でしかない
  • 権限は広く開けるか毎回確認するかの二択。根拠は書き換えられる場所にある

WHAT

  • 守る対象はプロジェクトが決め、あとは作業ごとの合意に委ねる
  • 逸れたら人間の目に触れさせる
  • 二択を崩す

HOW

  • 拒否は理由と代わりの手段を一緒に返す
  • 迷ったら止める。ただし回復手段は奪わない
  • 宣言された制約は緩めない。ガード自身を守る。逸脱は記録する
テーマ 3 / レビュー管理

厳密なレビュー管理が要るが、作業は複数の PC・セッションに散る

WHY

  • チケット作業では、レビューを厳密に管理したい
  • 作業は複数台の PC・複数のセッションで進む
  • 終われば消える自動実行もある

WHAT

  • チケットをマージリクエストに載せて管理する
  • issue・MR・ブランチを 1:1:1 で紐づける
  • チケットの動きを制御する

HOW

  • チケットとマーカーを親のブランチに載せ、レビューはホスト上で受ける
  • 承認とレビュー済みは、人間が直接操作する場所で受ける
  • 作業は子のワークツリーで行う
テーマ 4 / ルールの共存

共通ルールとプロジェクトのルールを分けて管理したい

WHY

  • ワークスペースの下に clone して共通ルールを管理する使い方がある
  • 各プロジェクトで直接 Claude Code を起動する使い方もある
  • 同じチームで共存する

WHAT

  • どちらの使い方でも、誰もが同じルールで作業できる

HOW

  • ルールは共通とプロジェクトの 2 層。判定は両者の和
  • ルールを git で管理し、共通ルールをプロジェクト側へ同期する
  • 写しが無くても動く
テーマ 5 / 計画で決める

作業の分け方・範囲・レビューの場所を、計画で決めて進めたい

WHY

  • 分割・範囲・レビューの場所は、始める前に決めたい
  • 計画のたびに分類を考え直すと、ぶれる

WHAT

  • 計画時に、分割・範囲・レビューの場所を決める
  • 分類は事前に定義し、計画ではその中から選ぶ
  • 承認された計画のとおりに作業する

HOW

  • 親子のチケット（目的・範囲・フェーズ・レビューの位置）を人間が承認する
  • 承認範囲の外は止め、中は聞かない。変更は改版の提案
  • 分類はフェーズの定義として持つ
テーマ 6 / リスク

リスクの高い作業は、人間が必ず見る

WHY

  • すべてを同じ重さでレビューすると、人間が追いつかない
  • 重く見るものを勘で選ぶと、ぶれる

WHAT

  • リスクの高い作業を事前に定義する
  • 一定以上は、人間のレビューを必須にする

HOW

  • リスクは、実績の差分に配点して測る
  • 高いものは、レビューが済むまで先へ進めない
テーマ 7 / 再利用と可視化

同じ流れを毎回作り直し、いまの状況も見えにくい

WHY

  • 似た流れが何度も現れる。毎回ゼロから計画すると手間もぶれも増える
  • チケットの状態や承認待ちは、文字だけでは追いにくい

WHAT

  • 流れをテンプレートとして蓄積し、次のタスクでも再利用する
  • VS Code の拡張で、状態を見える形にする

HOW

  • 完了した計画を貯め、新しい計画の提案に使い回す
  • 記録と振り返りから改善候補を出す。採るかは人間
  • 拡張のボードで、状態・承認・レビューを見せる
COMMON / 共通の原則

テーマをまたぐ 3 つの原則と、作らないもの

1必要な情報を、必要なタイミングで先に詰め込まず、場面で案内し、必要なときに引く
2人間の判断を残し、守る承認・レビュー・採否を、エージェントが代行できる形にしない
3単一の場所に閉じ込めないブランチとホストで、複数の PC・セッションをつなぐ
作らないものOS 権限分離の代わり ／ 人間の判断の代行 ／ モデルの学習 ／ 守られる保証
