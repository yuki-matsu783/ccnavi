CCNAVI / IDEA

ccnavi の思想

5 つのテーマごとに、なぜ・何を・どう

エージェントに任せる範囲を広げながら、人間の判断と目が届く道を失わせない。
OVERVIEW / 全体像

ccnavi が解決する 5 つのテーマ

1 エージェントに、指示と制約を守らせる外れを検知してやり直させる。守る対象は決め、逸れたら人間の目に触れさせる
2 計画で決めて、そのとおりに進める分類は事前に定義し、承認どおりに進める。流れはテンプレートで再利用
3 レビューを厳密に管理するissue・MR・ブランチを 1:1:1 で紐づける。高リスクはレビュー必須。拡張で見せる
4 ルールを共通とプロジェクトで共存させるルールを git で管理し、共通を同期する
5 必要な情報を必要な時に届け、記録から育てる入口だけ渡して必要時に引かせる。記録から改善候補を出し、人間が採ったものを活かす
テーマ 1 / 守らせる

エージェントに、指示と制約を守らせる

WHY

  • 指示を書いても、LLM は確率的。絶対に従うとは限らない
  • 目的のために、hook を外す・deny を緩めることを選ぶ
  • パターン一致は構造を見ず、禁止の文は確率でしかなく、根拠は書き換えられる

WHAT

  • 外れる確率 1% の LLM でも、検知してやり直せば、3 回続けて外れる確率は 1% × 1% × 1% = 0.0001%
  • 守る対象はプロジェクトが決め、あとは合意に委ね、逸れたら人間の目に触れさせる
  • hook を作る手間を軽くする

HOW

  • 判定と案内は、モデルの外の hook が行い、ルールとして宣言する
  • 拒否は理由と代わりの手段を返す。迷ったら止める
  • 宣言された制約は緩めない。ガード自身を守り、逸脱は記録する
たとえばエージェントが生の git push --force を打つ → ccnavi が止め、理由と決められた入口（ccnavi-git.sh）を返す → 入口から打ち直す。設定の書き換えで hook を外そうとしても、それも止まる
テーマ 2 / 計画

計画で決めて、そのとおりに進める

WHY

  • 分割・範囲・レビューの場所は、始める前に決めたい
  • 計画のたびに分類を考え直すと、ぶれる
  • 似た流れを毎回ゼロから計画すると、手間もぶれも増える

WHAT

  • 計画時に、分割・範囲・レビューの場所を決める
  • 分類は事前に定義し、計画ではその中から選ぶ
  • 流れをテンプレートとして蓄積し、再利用する

HOW

  • 親子のチケットを人間が承認する。承認範囲の外は止め、中は聞かない
  • 計画の変更は改版の提案に限る
  • 分類はフェーズの定義。完了した計画をテンプレートに貯める
たとえば「ログイン画面のバグを直して」→ 調査（読むだけ）と実装（src/auth/ と tests/ だけ）の 2 つの子に分け、レビューの位置を決めて、人間が承認。子が migrations/ を触ろうとすると止まる。終わった計画は「バグ修正」のテンプレートに貯まる
テーマ 3 / レビュー

レビューを厳密に管理する

WHY

  • レビューを厳密に管理したい。作業は複数の PC・セッションに散り、自動実行は終われば消える
  • 全部を同じ重さで見ると追いつけない。重く見るものを勘で選ぶとぶれる
  • 状態や承認待ちは、文字だけでは追いにくい

WHAT

  • チケットを MR に載せ、issue・MR・ブランチを 1:1:1 で紐づける
  • リスクの高い作業を事前に定義し、一定以上は人間のレビューを必須にする
  • VS Code の拡張で、状態を見せる

HOW

  • チケットとマーカーを親のブランチに載せ、レビューはホスト上で受ける
  • 承認とレビュー済みは、人間が直接操作する場所で受ける
  • リスクは実績の差分に配点して測り、高いものはレビューが済むまで進めない
たとえばissue「ログインのバグ」に、ブランチ fix-login と MR が 1 つずつ付く。別の PC でも MR を開けば同じ状態が見える。マイグレーションを変える子は高リスクと測られ、レビューが済むまで進めない。承認待ちは VS Code のボードに並ぶ
テーマ 4 / ルールの共存

ルールを共通とプロジェクトで共存させる

WHY

  • ワークスペースの下に clone して共通ルールを管理する使い方がある
  • 各プロジェクトで直接 Claude Code を起動する使い方もある
  • 同じチームで共存する

WHAT

  • どちらの使い方でも、誰もが同じルールで作業できる

HOW

  • ルールは共通とプロジェクトの 2 層。判定は両者の和
  • ルールを git で管理し、共通ルールをプロジェクト側へ同期する
  • 写しが無くても動く
たとえば共通ルール「git push --force は禁止」を、ワークスペースで 1 回書く。projects/web でも、projects/api を単独で開いた人でも、同じ判定になる。「migrations/ は確認する」は、そのプロジェクトのルールに書く
テーマ 5 / 届ける・育てる

必要な情報を必要な時に届け、記録から育てる

WHY

  • 決まりや文書を最初から全部渡すと、肝心なものが読まれない
  • 決まりや手順は、作って終わりにならない。同じ失敗を繰り返したくない

WHAT

  • 開始時は入口だけ。理由は場面で、詳しい資料は必要なときに引かせる
  • 記録・気づき・振り返りから、ルール・手順・文書の改善候補を提案する
  • 人間が採ったものを、次に活かす

HOW

  • 本文は渡さず、frontmatter の索引と目録で、自分で引く
  • 提案まではエージェント。採るかは人間が決める
  • 改善するのはルール・手順・文書の側で、モデルの学習ではない
たとえば開始時は、入口と文書の目録だけを渡す。マイグレーションを触る場面になって初めて、その手順書を引かせる。記録に「同じ拒否が 5 回出ている」と出れば、ルールの文面を直す案が提案され、人間が採ると、次の作業から効く
NOT / 作らないもの

ccnavi がやらないこと

OS 権限分離の代わり逸れるエージェントと事故への柵。同じ権限で任意のシェルを動かせる相手には境界にならない
人間の判断の代行承認・レビュー済み・採否を、エージェントが出せる形は作らない
モデルの学習改善するのは、ルール・手順・文書・計画の側
守られる保証そうなるよう設計するが、保証はしない
