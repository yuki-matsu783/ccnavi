CCNAVI / IDEA

ccnavi の思想

AI に仕事を任せながら、人間の目を残すために

エージェントに任せる範囲を広げながら、人間の判断と目が届く道を失わせない。
GUIDE / この資料の読み方

この資料の読み方

Claude Code を知らなくても読めるように、まず前提を説明します。そのあと、テーマごとに「どんな問題があり、ccnavi がどう解決するか」を、具体例つきで見ます。

前提 1 / Claude Code とは

Claude Code は、自分で考えて作業を進める AI

人間が一手ずつ指示しなくても、AI が読む・書く・動かすを自分で選んで、作業を進めます。便利な反面、人間の見ていないところで多くの操作が起きます。

前提 2 / ツール呼び出し

AI は「ツール呼び出し」で、実際に作業する

ファイルを消す、コマンドを動かす、git を操作する。AI の作業は、すべてツール呼び出しという 1 回ずつの操作でできています。

前提 3 / hook

hook は、ツール呼び出しの前後に割り込める仕組み

Claude Code には、ツールを使う直前と直後に、外部のプログラムを呼べる hook があります。ccnavi は、この hook に登録された見張り役です。

前提 4 / 文章の指示と hook

文章の「お願い」と、プログラムの「検問」は別もの

文章の指示は、AI が読んで従うかどうかを決めます。hook は、AI の頭の外で、プログラムが機械的に判定します。

前提 5 / ccnavi とは

ccnavi は、hook に登録された見張り兼案内役

ccnavi は、AI の操作を判定して、通す・止める・人間に確認する、のどれかを返します。止めるときは、理由と代わりの手段を一緒に返します。

前提 6 / 想定する環境

ccnavi は、いろいろな環境で使われることを前提にする

手元の PC の対話セッションも、別の PC も、終われば消えるコンテナの自動実行も、同じ道で扱います。作業はブランチとホストでつなぎ、人間の判断は、あとから別の場所でも受けられるようにします。

OVERVIEW / 5 つのテーマ

ccnavi が解決する 5 つのテーマ

テーマごとに、「AI を任せるとどんな問題が起きるか」と「ccnavi がどう解決するか」を、具体例で見ていきます。

テーマ 1 / 問題 1

問題: 指示を書いても、毎回守られるとは限らない

同じ指示でも、毎回同じ結果になるとは限りません。LLM の答えは確率的で、100% に近づけても絶対にはならず、スキル自体が使われないこともあります。

テーマ 1 / 問題 2

問題: 目的のためなら、制約を突破しようとする

悪意はありません。目的を達成しようとして、「禁止を避ける」「禁止を外す」を普通に選びます。任せる範囲を広げるほど、人間が一手ずつ見ることはできなくなります。

テーマ 1 / 既存の防ぎ方

既存の防ぎ方には 4 つの穴がある

パターン一致は構造を見ず、文章の禁止は確率で、権限の固定は二択になり、禁止の根拠は AI が書き換えられる場所にあります。

テーマ 1 / 解決 1

解決: 外れを検知して、案内して、やり直させる

外れる確率が 1% の LLM でも、外れるたびに検知してやり直させれば、続けて外れる確率は 1% × 1% × 1% = 0.0001% まで下がります（やり直しが互いに独立なら）。

テーマ 1 / 解決 2

解決: AI の頭の外で、ccnavi が機械的に止める

判定は AI の外にあるので、AI が守る気になるかに頼りません。止めるときは、止めた理由と代わりの手段を一緒に返します。止めるだけだと、AI は別の書き方で打ち直すからです。

テーマ 1 / 具体例

具体例: rm -rf を止めて、ファイル名の指定へ案内する

禁止するだけでなく、「代わりに何をすればよいか」まで返すので、AI は案内どおりにやり直せます。hook を外そうとする操作も、ccnavi が止めます。

テーマ 2 / 問題

問題: 計画なしで任せると、範囲が勝手に広がる

範囲を決めずに任せると、人間が気づかないうちに、想定外のファイルが変わります。分け方・範囲・レビューの場所は、始める前に決めたいところです。

テーマ 2 / 解決 1

解決: AI が計画を提案し、人間が承認し、そのとおりに進める

親チケット（計画）は AI が提案し、人間が承認します。子は承認された範囲で作業し、計画でレビューが要ると決めた子だけを、人間がレビューします。範囲の外は、ccnavi が止めます。

テーマ 2 / 解決 2

解決: 分類は事前に定義し、流れはテンプレートで再利用

計画のたびに分類を考え直すとぶれます。作業の分類を先に決めておき、計画ではその中から選びます。似た流れはテンプレートに貯めて、次のタスクで使い回します。

テーマ 2 / 具体例

具体例: ログイン画面のバグを直す

範囲外の migrations/ を触ろうとした時点で、ccnavi が止めます。人間が事後に気づく必要はありません。終わった計画は「バグ修正」のテンプレートに貯まります。

テーマ 3 / 問題

問題: 作業が散らばり、確認が抜けやすい

作業は複数台の PC や複数のセッションで進みます。終われば消える自動実行もあります。厳密なレビュー管理が要りますが、状態は散らばりがちです。

テーマ 3 / 解決 1

解決: issue・マージリクエスト・ブランチを 1 対 1 対 1 で紐づける

チケットを MR に載せて管理し、チケットの動きを制御します。どの PC からでも、MR を開けば同じ状態が見えます。

テーマ 3 / 解決 2

解決: レビューのタイミングを、ccnavi が機械的に止める

レビュー待ちの間は、先へ進む操作も、エージェント自身による「レビュー済み」の合図も、ccnavi が止めます。人間が自分で操作する場所でだけ、レビュー済みにできます。

テーマ 3 / 解決 3

解決: 計画で見落としても、リスクが高ければレビュー要にする

計画の時点で、どの作業にレビューが要るかを完全に判断するのは難しいことです。そこで、リスクの高い作業を事前に定義し、実績の差分が一定以上のリスクになったら、計画でレビュー不要としていた子でも、レビュー要にします。

テーマ 3 / 解決 4

解決: 状態は VS Code のボードで見える形にする

チケットの状態や承認待ちは、文字だけでは追いにくいものです。VS Code の拡張のボードで、状態を見える形にし、人間が判断する場所にもします。

テーマ 3 / 具体例

具体例: マイグレーションを変える作業のレビュー

別の PC でも、MR を開けば同じ状態が見えます。高リスクの子は、人間のレビューが済むまで、ccnavi が先へ進ませません。

テーマ 4 / 問題

問題: 2 つの使い方が共存し、設定がばらつく

専用のワークスペースの下に clone して共通設定をまとめる使い方と、各プロジェクトで直接 Claude Code を起動する使い方は、同じチームに共存します。

テーマ 4 / 解決

解決: 設定ファイルを git で管理し、共通設定を同期する

ルール・フェーズ定義・リスクの配点などの設定ファイルは、共通とプロジェクトの 2 層に分け、どちらも git で管理します。ワークスペースの共通設定は、プロジェクト側にも常に同期します。

テーマ 4 / 具体例

具体例: 共通のルール「rm -rf は禁止」を 1 回書くだけで、全員に効く

共通のルールは全員に効き、プロジェクト固有のルールは、そのプロジェクトにだけ効きます。誰もが同じルールで作業できます。

テーマ 5 / 問題

問題: 全部渡すと読まれず、作って終わりでは育たない

決まりや文書を最初から全部渡すと、コンテキストが膨らみ、肝心なものが読まれません。また、決まりや手順は、作って終わりにすると同じ失敗を繰り返します。

テーマ 5 / 解決 1

解決: 必要な情報を、必要な時に届ける

最初は入口だけを渡し、理由と手順は関係する場面で届け、詳しい資料は、AI が必要になったときに自分で引きます。

テーマ 5 / 解決 2

解決: 記録から、改善候補を出して育てる

判定の記録、作業やレビューの気づき、振り返りから、ルールや手順の改善候補をエージェントが提案します。採るかどうかは人間が決めます。

テーマ 5 / 具体例

具体例: 「同じ拒否が 5 回」からルールを直す

ルールの文面が分かりにくくて同じ拒否が繰り返されるとき、記録から気づき、直し、次の作業に活かします。
