### 2.12 複数のリポジトリ — REQ-MLT

道具（hook の登録、実行ファイル、保護済みスクリプト、スキル）を持つ private のリポジトリをワークスペースと呼び、
その下に clone した別々のリポジトリをプロジェクトと呼ぶ。Claude Code はワークスペースを開く。プロジェクトのディレクトリで開く使い方もある（[想定する使い方](../10_requirements.md)）。設定 3 本（ルール・フェーズ定義・
リスクの配点）はレイヤーごとに置く。レイヤーは、どのツリーにも適用される共通レイヤー（`.ccnavi/config/common/`）、ワークスペース自身のレイヤー（ワークスペースルートの
`.ccnavi/config/project/`）、プロジェクトのレイヤー（`projects/<名前>/.ccnavi/config/project/`）の 3 種で、プロジェクトのレイヤーはプロジェクトの git で育てる。
ルール・リスクの配点・フェーズ定義は共通と config のどちらにも置け、効くのは和。フェーズ定義に足す config は親の `project:` が決める。
プロジェクトの `.ccnavi/config/common/` は共通レイヤーのミラーで、そのプロジェクトを単体で clone したときにだけ共通レイヤーとして読まれる。
`.ccnavi` は ccnavi ディレクトリの名前で、固定。設計は 11。

| ID | 型 | 要求 |
|---|---|---|
| REQ-MLT-01 | 常時 | ccnavi は、ワークスペースルートの直下のプロジェクト置き場（既定 `projects/`）にある git リポジトリだけをプロジェクトとして数え、それより深い場所と置き場の外のリポジトリをプロジェクトとしないこと |
| REQ-MLT-02 | 常時 | ccnavi は、書き込みの行き先が属するツリー（ワークスペースルート、プロジェクト、ワークツリー）を最長一致で決め、行き先がワークスペースルートの外にあるとき判定を持たないこと |
| REQ-MLT-03 | 常時 | ccnavi は、パスを持つツール（Read・Grep・Glob・Write・Edit・NotebookEdit）の判定に、共通レイヤーのルールと、行き先のツリーが属するレイヤー（プロジェクトに属するならそのプロジェクトのレイヤー、それ以外ならワークスペース自身のレイヤー）のルールを、タイプごとに合わせたものを用いること |
| REQ-MLT-04 | 常時 | ccnavi は、各レイヤーの設定ファイル（ルール・フェーズ定義・リスクの配点）と配点が呼ぶスクリプトとして、元リポジトリにあるものだけを読み、ワークツリーの中にあるものを読まないこと |
| REQ-MLT-05 | 常時 | ccnavi は、パスを持たないツール（Bash・PowerShell・WebFetch・Skill・Agent・Task）の判定に、共通レイヤーと自身のレイヤーと全プロジェクトのレイヤーのルールをタイプごとに合わせたものを用い、呼び出し元の作業ディレクトリによらず同じ判定を返すこと |
| REQ-MLT-06 | 状態 | 自身のレイヤーかプロジェクトのレイヤーの設定ファイルが読めない間、ccnavi は、そのレイヤーを空として扱い、組み込みの既定を使わず、空として扱ったことを記録と診断で示すこと。設定ファイルが無いだけのときは、空として扱い、記録にも診断にも不備として示さないこと |
| REQ-MLT-07 | 常時 | ccnavi は、記録と文面で、ヒットしたルールの識別子にレイヤーの名前（自身のレイヤーは `self`、プロジェクトのレイヤーはその名前。共通レイヤーは裸の識別子のまま）を添え、記録に判定を下したルールのレイヤーを残すこと |
| REQ-MLT-08 | 常時 | ccnavi は、自身のレイヤーとプロジェクトのレイヤーの設定ファイル 3 本を設定ファイルの自己防衛の対象（書き込みの拒否、シェル書き込みの拒否、バックアップと復元）に含め、共通レイヤーの 3 本をシェル書き込みの拒否とバックアップと復元の対象に含め、それらのうち追跡されているものについて、その元リポジトリから切ったワークツリーが持つ同じファイル（ワークツリー側の設定）も同じ対象とすること |
| REQ-MLT-09 | 常時 | ccnavi は、プロジェクトの列挙とルールの読み込みのために、実行前チェックの間に外部プロセスを起こさないこと |
| REQ-MLT-10 | 常時 | ccnavi は、実行後チェックを、ワークスペースルートと、そのターンで書き込みのあったプロジェクトとワークツリーのそれぞれの git で行い、差し戻しもそのツリーの git で行い、報告にツリーの名前を添えること |
| REQ-MLT-11 | 常時 | ccnavi は、チケットのプロジェクトを提案を置いた場所で決め、承認の画面にそれを示すこと。frontmatter の `project:` が置き場と違うチケット、親と違う置き場にある子チケット、置き場に無い名前を承認しないこと。承認の画面を経ずに置かれたものにも同じ検査を判定のときに適用し、ヒットすれば書き込みを全部拒否すること |
| REQ-MLT-12 | 常時 | ccnavi は、書き込みの行き先のツリーが属するプロジェクトと、そのツリーに結び付く承認済みチケットの `project:` が違うとき止めること。エージェントが申告したプロジェクトを判定に使わないこと |
| REQ-MLT-13 | 常時 | ccnavi は、ワークツリーの元リポジトリがどのプロジェクトかを相互参照で確かめ、承認済みチケットの `project:` と違うワークツリーを着手させないこと |
| REQ-MLT-14 | 常時 | ccnavi は、提案と承認済みチケットとフェーズのマーカーを、そのツリーのルートからの相対の置き場に書き、そのツリーの git が追跡できるようにすること。git のラッパースクリプトの記録はワークスペースルートの下に置き、プロジェクトのリポジトリの中に書かないこと |
| REQ-MLT-15 | 常時 | ccnavi は、プロジェクト置き場が無いか空のとき、共通レイヤーとワークスペース自身のレイヤーだけを判定に用い、提案・承認済みチケット・フェーズのマーカー・記録をワークスペースの置き場だけに書くこと |
| REQ-MLT-16 | 常時 | `--lint` は、プロジェクト置き場が無視されているか、プロジェクトの中にワークツリー（`.claude/worktrees/`）が無いか、ワークツリーの元リポジトリと `project:` が合うか、走査されないチケットの置き場が残っていないかに加えて、レイヤーのファイルが読めるか、レイヤーをまたぐ重複と同じ識別子の衝突、配点の `script:` の欠けとレイヤーの外への参照、予約名のプロジェクト、識別子のコロン、ワークツリーの ccnavi ディレクトリにある元リポジトリに無いファイルを言い、レイヤーのファイルが無いことは言わないこと |
| REQ-MLT-17 | 常時 | `--explain` は、レイヤーごとに、判定に入っているルールの全件と、フェーズ定義と配点の定義を、その出どころのレイヤーとともに示し、読めないレイヤーと置いていないレイヤーをそれと分かる形で示すこと |
| REQ-MLT-18 | 常時 | ccnavi は、レイヤーの和を足すだけで行い、後ろのレイヤーの宣言が前のレイヤーの宣言を上書きしたり取り消したりできないこと |
| REQ-MLT-19 | 事象 | 同じ識別子で中身の一致する定義が複数のレイヤーにあるとき、ccnavi は、前のレイヤーのものだけを用い、診断で info として示すこと |
| REQ-MLT-20 | 事象 | 同じ識別子で中身の違うルールか配点の項目が複数のレイヤーにあるとき、ccnavi は、両方を判定に用い、配点の項目は後ろのレイヤーの側を `<レイヤー>:<識別子>` として記録し、診断で warn として示すこと |
| REQ-MLT-21 | 異常時 | もし合成後の配点の境目の点が `medium <= high <= critical` を守らないならば、ccnavi は、そのレイヤーの配点を空として扱い、そのことを診断で error として示し、子の記録と閉じるときの出力でも示すこと |
| REQ-MLT-22 | 常時 | ccnavi は、フェーズ定義と配点を、共通レイヤーと、親の承認済みチケットの `project:` が示すレイヤー（`project:` が空ならワークスペース自身のレイヤー）の和から決めること。フェーズ定義で、共通レイヤーと同じ識別子で中身が違う定義か、表示名が重なる定義があれば、レイヤーの側のその定義だけを外し（同じ識別子なら共通レイヤーの定義を使い、そのレイヤーのほかの定義は使う）、`--lint` で error として示すこと |
| REQ-MLT-24 | 常時 | ccnavi は、配点の境目の点を、キーごとにレイヤーに書かれた値のうち小さいほうで決め、どのレイヤーにも書かれていないキーを既定とし、書かれていないキーを合成に参加させないこと |
| REQ-MLT-25 | 常時 | ccnavi は、配点の `script:` を、共通レイヤーでは `.ccnavi/config/common/scripts/` の下、自身のレイヤーとプロジェクトのレイヤーではそのレイヤーの ccnavi ディレクトリの `scripts/` の下に限り、たがいの側を指す定義を受け付けないこと |
| REQ-MLT-26 | 常時 | ccnavi は、各レイヤーの ccnavi ディレクトリの下への名指しのツールとシェルによる書き込みを、ルールにその宣言が無くても拒否し、シェルでは ccnavi ディレクトリの名前に区切りが続くパスと ccnavi ディレクトリの名前で終わるパス（ccnavi ディレクトリごと消す・移す形）の両方を拒否すること |
| REQ-MLT-27 | 常時 | ccnavi は、ルールの `glob` と `regex` を、照合する対象がパスであるかコマンドであるかによらず、また機械によらず、大文字小文字を区別せずに照合し、`(?-i:...)` で囲まれた部分だけを書かれた表記のとおりに照合すること |
| REQ-MLT-28 | 異常時 | もしルール・フェーズ定義・配点の項目の識別子にコロンが書かれていたならば、ccnavi は、その定義を受け付けず、名指しで示すこと |
| REQ-MLT-29 | 常時 | ccnavi は、`common` と `self` を大文字小文字を問わずレイヤーの名前に予約し、その名前のプロジェクトをレイヤーとして数えず、そのプロジェクトへの書き込みを共通レイヤーのルールだけで判定し、その名前を `project:` に持つチケットを承認せず、そのプロジェクトの設定ファイルは自己防衛の対象に含めること |
| REQ-MLT-30 | 常時 | ccnavi は、承認のとき承認済みチケットを親チケットのツリーに置き、同じ識別子が複数のツリーにあるときは親のツリーの版だけを読み、親のツリーがその識別子を持たないときは元ツリー（ワークスペースルート、プロジェクトのチケットならそのプロジェクト）の版を読み、元ツリーも持たないか元ツリーより先の置き場に在る版があるときにかぎり見つかった側を読むこと |
| REQ-MLT-31 | 事象 | ユーザがターミナルからまとめて承認したもののうち一部が承認の対象から外れたとき、ccnavi は、承認されたぶんの承認済みチケットを置いたうえで、外れたものを名指しし、非ゼロの終了コードで終わること |
| REQ-MLT-32 | 常時 | 導入スクリプトは、共通レイヤーにルールと配点とフェーズ定義のひな形を配り、無いものを点検で示すこと。自身のレイヤーのフェーズ定義は配らず、配布先に既にあれば触らないこと。フェーズ定義は、共通にも自身のレイヤーにも無いときだけ無いものとして示すこと |
| REQ-MLT-33 | 事象 | 既定でない位置を指す実行ファイルの位置の設定を見つけたとき、導入スクリプトは、それを書き換えずに名指しすること |
| REQ-MLT-34 | 事象 | ユーザが発言したとき、ccnavi は、`project:` を持つ着手済みの親チケットのワークツリーのプロジェクトの `.ccnavi/config/common/` へ、ワークスペースルートの `.ccnavi/config/common/` の中身を、中身の違うものだけ上書きしてミラーし、配点の `script:` の値は書き換えず、プロジェクトの `.ccnavi/config/project/` に触れないこと。元も先も変わっていなければ、何も書かないこと。コピーするものがミラー（単体 clone では共通レイヤー）として読めないか、コピー先かその途中がシンボリックリンクならば、何もコピーせず、理由を示し、発言と着手を止めないこと。途中で書けなくなったら、書いた分を元に戻し、戻せなかったものを示すこと。共通レイヤーの `.ccnavi/config/common/` が無いか空ならば、何も配らず、ミラーを消さないこと。`ticket start` はミラーを書かないこと |
| REQ-MLT-36 | 常時 | ccnavi は、ユーザの発言でコピーしたミラーを、ユーザの手による変更と同じに受け入れ、次のツール呼び出しの実行後チェックとバックアップと復元で戻さず、繰り返し報告しないこと。ツール呼び出しの中でミラーが書き換わったときは、共通レイヤーと同じ中身でも、今までどおり戻し、報告すること |
| REQ-MLT-38 | 事象 | セッションかサブエージェントが始まったとき、または作業ディレクトリがプロジェクトのツリーの中にある最初のツール呼び出しのとき、そのプロジェクトの `skills/<名前>/SKILL.md` があれば、ccnavi はそれぞれの名前・説明・場所の目録を、1 つの文脈でプロジェクトごとに 1 度だけモデルに渡すこと。本文は渡さないこと。読むのは元リポジトリの版で、名前が英数と `._-` だけのディレクトリの、シンボリックリンクでもハードリンクでもないファイルだけとすること。名前・説明・場所はデータとして囲んで 1 行にまとめ、ccnavi の接頭辞と区切りの行を真似た表記を崩し、数と長さに上限を置いて、超えた分は数だけ言うこと |
| REQ-MLT-39 | 異常時 | もし共通レイヤーの `phases.yml` が読めないならば、ccnavi は、共通レイヤーのフェーズ定義を空として扱い、`--lint` で error としてそのファイルを名指しすること。記録の `fallback` にはその名前を残さないこと |
| REQ-MLT-40 | 常時 | ccnavi は、共通レイヤーと config のどちらか片方だけがあっても、両方が無くても動き、ルール・リスクの配点・フェーズ定義のすべてで、ファイルが無いことを空として扱い、記録の `fallback` にも `--lint` と診断の不備にも出さないこと。不正（読めない・error）ときだけ、ルールと配点は記録の `fallback` に残し、フェーズ定義は `--lint` の error・承認の拒否・`--explain` の表示で示すこと（判定ごとの記録にフェーズ定義の経路は無い）。土台の deny（取り返しの付かない操作の止め）は、共通と config の有無・状態によらず常に有効とし、共通と config のルールはその上に足すこと。ルールは共通と config の両方が無いときは組み込みの既定だけで判定すること |
| REQ-MLT-41 | 常時 | ccnavi は、ワークスペースの中では、ワークスペースルートの `.ccnavi/config/common/` だけを共通レイヤーとして読み、プロジェクトの `.ccnavi/config/common/`（ミラー）を二重に読まないこと。プロジェクトを単体で clone したときは、そのプロジェクトの `.ccnavi/config/common/` を共通レイヤー、`.ccnavi/config/project/` を自身のレイヤーとして読み、ワークスペースの中と同じ「共通 + 1 レイヤー」の和で判定すること |
| REQ-MLT-42 | 常時 | ccnavi は、ワークスペースのルートで Claude Code を起動する使い方と、プロジェクトのディレクトリで Claude Code を起動する使い方（[想定する使い方](../10_requirements.md)）のどちらでも、チケット作業と直接作業を進められること。実行ファイルは、起動するツリーの `.ccnavi/bin/<os>-<arch>/` に置いたものと、環境の PATH に登録したもののどちらでも、どちらの使い方とも組み合わせて使えること。両方あるときは `bin/` に合うものを先に使うこと |
| REQ-MLT-43 | 事象 | ユーザが共通レイヤーのミラーの状態を求めたとき（`ccnavi user mirror`）、ccnavi は、何も書かずに、プロジェクトごとに、ワークスペースの共通レイヤーとプロジェクトのユーザのチェックアウトにあるミラーが同じか（同期済み）、違うか（ずれ。どのファイルの追加・更新・削除か）、調べられないか（理由つき）を返すこと。共通レイヤーにコピーするものが無いときは、ずれとせず、ミラーを消さないこと |
| REQ-MLT-44 | 事象 | ユーザが見せた変更の一覧（ファイルと種類）の照合の値を付けて揃えるよう求めたとき（`ccnavi user mirror --yes --expect`）、ccnavi は、今の差分から求めた値と一致するときだけ、差分のあるプロジェクトのミラーを共通レイヤーに揃えること。書くのはミラーだけで、プロジェクトの `.ccnavi/config/project/` に触れず、コミットしないこと。一致しないときは何も書かず、内容が更新されたと返すこと。ターミナルでの確認を省く経路は拡張の子プロセスの経路（`--via board`）だけで、エージェントがこの経路を実行しないよう止めること |

REQ-MLT-05 は、パスを持たない呼び出しがどのプロジェクトのものかを決められないため。和を取れば、
`deny` と `ask` は増えるほうになる。

REQ-MLT-06 は、共通レイヤーが読めているのに組み込みの既定を使うと共通レイヤーの `deny` が消えるため。
共通レイヤーのルール自身が読めないときは REQ-PRE-06 のまま組み込みの既定を使い、レイヤーは足さない。

REQ-MLT-18 は、プロジェクトのレイヤーを書けたエージェントが共通レイヤーの `deny` を消せないようにする。

REQ-MLT-21 は、配点の境目の点が崩れたレイヤーを何も示さずに採ることはせず、止まる側を採る。配点の項目の同じ識別子は、空にすると点が下がるので
REQ-MLT-20 で両方を数える。フェーズ定義は足さないので、レイヤーをまたぐ衝突は起きない（REQ-MLT-22）。

REQ-MLT-29 は、`self` を宣言するプロジェクトがワークスペース自身のレイヤーで判定され、そのプロジェクトの `deny` が
読まれない形を防ぐ。数えない側とレイヤーを引く側の両方に同じ予約を掛ける。

REQ-MLT-31 は、ターミナルを見ていない側（スクリプト、CI）が全部通ったと読まないようにする。

REQ-MLT-12 は REQ-TKT-01 と同じ理由で、申告ではなく行き先で決める。

REQ-MLT-14 は、承認を git で他の機械と共有するため。git のラッパースクリプトの記録はその機械で打ったものでしかないので、
ワークスペース側に置く。提案は ccnavi ディレクトリ（`.ccnavi/`）の外に置く（その下は組み込みが丸ごと止めている）。
承認済みチケットとフェーズのマーカーは ccnavi ディレクトリの下に置き、それがそのまま保護になる。

REQ-MLT-30 は、子のワークツリーに checkout された古い承認済みチケットで、閉じたチケットの範囲が復活するのを防ぐ。

REQ-MLT-34 がミラーを配るのは、共通レイヤーがワークスペースの git にあり、プロジェクトだけを clone したユーザからは見えないため。
ミラーは誰も編集しないので、上書きで失うものは無く、名指しも知らせも要らない。プロジェクトの config には触れない。
REQ-MLT-36 は、ミラーを書く時が発言のときだけで、ツール呼び出しの中の書き換えと区別できるため。
REQ-MLT-39 は、読めない共通の `phases.yml` が使われていないことを利用者に知らせる。
REQ-MLT-40 は、ファイルが無いのは設定が無いだけで、不備ではないため。土台の deny を常に有効にするのは、共通が無い・config だけのときも、取り返しの付かない操作の止めが消えないようにするため。不正なときだけ止まる側（空と error）に倒す。
REQ-MLT-41 は、ミラーを共通レイヤーとして読むと、ワークスペースの中で同じルールを 2 度数えるため。
REQ-MLT-42 は、ワークスペースを用意する使い方と、clone 済みのディレクトリで起動する使い方を、どちらも大前提にするため。後者では、ワークスペースの hook ではなくプロジェクトの hook が使われる。実行ファイルの置き方は使い方とは別の軸なので、同じ要求の中で別に書く。
REQ-MLT-43 と REQ-MLT-44 は、プロジェクトのユーザのチェックアウトのミラーが、発言のときの同期（REQ-MLT-34）の対象ではなく、間が空くと古いまま残るため。調べる形は何も書かないので、定期的に呼べる。揃える形は、見せた差分と書く内容が同じことを照合の値で確かめ、ユーザが見ていない内容を書かない。

REQ-MLT-33 は、ユーザが決めたパスの先で何が使われているかを導入スクリプトが決められないため。
