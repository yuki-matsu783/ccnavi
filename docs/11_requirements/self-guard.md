### 2.7 設定ファイルの自己防衛 — REQ-SLF

| ID | 型 | 要求 |
|---|---|---|
| REQ-SLF-01 | 事象 | ツールが実行される前、ccnavi は、自身の判定と起動が依存する設定ファイルの内容をバックアップすること |
| REQ-SLF-02 | 事象 | ツールの実行が完了したとき、ccnavi は、バックアップした内容と現在の内容を突き合わせ、異なる場合はバックアップした内容へ戻し、戻した対象を示すこと。ただし、ユーザの発言の時点で受け入れた変更（ターンの間にユーザが直した・消したもの）は戻さないこと |
| REQ-SLF-03 | 状態 | 対象が存在しない間、ccnavi は、バックアップまたはバージョン管理から復元を試み、いずれも持たない場合はその対象を保護の対象から外すこと |
| REQ-SLF-04 | 常時 | ccnavi は、自己防衛が守る対象を、プロジェクトが書いたルールから導かないこと |
| REQ-SLF-05 | 任意 | 自己防衛が無効である場合、ccnavi は、バックアップも復元も行わず、REQ-SLF-06 の拒否も行わないこと |
| REQ-SLF-06 | 状態 | 自己防衛が有効である間、ccnavi は、対象の設定ファイルへシェル経由で書き込む呼び出しを、プロジェクトのルールにその宣言が無くても拒否すること |
| REQ-SLF-07 | 状態 | 自身の実行ファイルの位置が設定されている間、ccnavi は、それを守る対象に含め、シェル経由の書き込みと名指しのツールによる書き込みの両方を拒否すること |
| REQ-SLF-08 | 事象 | セッションが開始されたとき、ccnavi は、ツール呼び出しごとにバックアップするには大きすぎる対象を、そこでバックアップすること。ツール呼び出しの外で変わったときだけ、取り直すこと |
| REQ-SLF-09 | 事象 | 保護済みのスクリプトを呼ぶシェルのコマンドが、スクリプトの検査の材料を変える環境変数（出力の量と待ち時間だけを変えるものを除く）を同じコマンド行で置く・外すとき、ccnavi は、それを拒否すること |
| REQ-SLF-10 | 状態 | 自己防衛が有効である間、ccnavi は、git のラッパースクリプトを通して REQ-SLF-06 の対象を消す・別のコミットの中身に戻す呼び出しを拒否すること。対象を読み切れない呼び出し（変数・置換で組み立てたパス、居場所を読めない後の相対パス）も拒否すること。エージェントが承認済みチケットの置き場とレビュー待ちの置き場（その親は、消す呼び出しなら置き場に何かがある間、別のコミットの中身に戻す呼び出しなら常に）を消す・戻す呼び出しも拒否し、ユーザがターミナルから打つレビュー済みのマーカーの削除は拒否しないこと。衝突の解決と、索引の中身に戻す操作と、何も消さない試し（`rm -n`）は拒否しないこと |

REQ-SLF-04 は、ルールを空にされた時点で守る対象が 0 件になるのを防ぐ。保護の根拠を守られる対象の外に置く。

REQ-SLF-07 が実行ファイルを含めるのは、差し替えるとルールを変えずに判定を入れ替えられるため。実行ファイルは
バージョン管理の外にあることが多く、バックアップだけが戻す手段になる。位置が設定されているときだけ守るのは、推測した
パスの先にある別のファイルを実体として扱わないため。位置が振り分けのスクリプトを指すときは、そのスクリプトが
起動する実行ファイルの置き場も守る。

REQ-SLF-08 は、実行ファイルがツール呼び出しごとにバックアップするには大きいため。作り直すのはユーザの作業なので、セッションに 1 度でよい。

REQ-SLF-10 は、ラッパースクリプトの `git rm` が、シェルの `rm` で止まる場所を消せたため。ラッパースクリプト自身を消すと、
ラッパースクリプトがあるときだけ働く生の git の止めも外れる。衝突の解決を残すのは、ルールファイルが衝突したときに直す道がそこしか無いため。
レビュー待ちの置き場を含めるのは、エージェントが提案を置き場から外すと、ユーザのレビューを経ずにレビュー待ちでなくなるため。
空の置き場の親を消す形を除くのは、親を閉じた後に `wip/` を消す案内を止めないため。戻す形を除かないのは、いまは空でも過去のコミットの `wip/` にはレビュー待ちの提案がありうるため。

REQ-SLF-06 が止めるのが本筋で、REQ-SLF-02 の戻しは止めきれなかったぶんの受け皿である。

REQ-SLF-03 は、設定ファイルを置いていないことが正常な状態だから。

実行前にも見るのは、hook の登録を消されると実行後のイベント自体が発火しなくなるため。
実行前の登録ごと消された場合は 4 章。
