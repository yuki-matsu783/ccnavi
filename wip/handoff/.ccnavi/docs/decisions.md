# 提案と判断・セッションの役割分担

## 提案と判断

- 提案にはメリットとデメリットを両方書く。デメリットが本当に無いなら「無い」と書く
- 次のどれかに当たる対応は自分で決めない。手を動かす前に「何をなぜ変えるか・得るもの・失うもの・
  やらない場合どうなるか・代案」を示し、返事を待つ
  - 判定が緩む、例外が増える、確認が減るなど、止まっていたものが通るようになる変更
  - コマンド、出力、設定の書き方といった、ユーザとのやり取りの形が変わる変更
  - 判定の結果を無視する、条件を狭める、報告を消す
  - 消す、履歴を書き換える、他セッションの作業に触るといった、元に戻せなくなる操作
  - 影響範囲を読み切れない変更。共有の設定、hook、スクリプト、配布物、他のプロジェクトへ配るものを変える場合
- 再現する、読む、隔離した場所で試すといった調べる作業は、相談せずに進める。相談が要るのは、結果をこのリポジトリに入れるとき
- ccnavi に止められたら迂回せず、案内された道を使う。承認や親を早めに閉じることなど、ユーザが下す判断を、エージェントが代わりに作らない

## 提案を書く前に読むもの

- 提案（チケット）を書く前に、`ccnavi-launcher.sh --docs`で`proposal-format`と`phases`を引く。書式と、フェーズ（計画の項）の決め方が載っている
- 親は計画（plan）を必ず持つ。計画の無い親は、子や子の提案があっても`ticket start`が止まり、`--lint`も警告する。止まったら、`phases.yml`に最小の定義（例: workを1つ）を書き、親に`plan:`を足す。`phases.yml`はユーザが持つ設定で、書くのはユーザ
- 計画のある親の`start`は、子のないフェーズが残るとき案内を出す。フェーズごとに子チケットを作る。子のないまま進めても`finish`で止まる
- 親の提案は、識別子と同名のワークツリーに書く（.ccnavi/docs/worktree.md「直接作業からチケット作業に移るとき」）
- `--lint` と提案を書くときの `--agree --preview --verify` が出した警告のうち、承認の後に取り返せなくなるもの（提案を識別子と違う名前のワークツリーに書いた、など）は、承認の依頼の前に直す。「通る」（終了コード 0）を、警告が無い意味に読まない。提案を書いたサブエージェントの報告の「警告」は、そのまま流さずに確かめる

## 承認の経路

承認とは、提案を`todo/`から`.ccnavi/approved/doing/`へ動かすこと。経路は 4 つあり、どれで承認しても承認済みチケットは提案と同じ中身になる。ユーザに承認を頼むときは、この 4 つから案内する。

- 端末: ユーザが`ccnavi user agree [<識別子>…]`を打つ
- VS Code 拡張のボード: ユーザがオーバーレイで承認を押す
- Chrome 拡張のボード: ユーザがブラウザで承認を押す。リモートのブランチに承認が書かれる
- ファイルを動かす: ユーザが GitLab や GitHub の画面などで、提案を`.ccnavi/approved/doing/`へ動かしてコミットする

エージェントは`ccnavi user agree --yes`を打てない。承認はユーザが行う。端末・Chrome 拡張・ファイルを動かす承認はセッションに届かないため、ユーザはあとでセッションに一言送る。エージェントは承認の有無を、ファイルを読んで推測せず`ccnavi-ticket.sh status [<親>]`で確かめてから着手する。

## レビュー済み（`review/`から`done/`）の経路

レビューを依頼したフェーズ（`ccnavi-review.sh request`）は、レビュー済みになると、そのフェーズの`review/`の子が`done/`へ動く。ユーザがレビューを終えたと伝える場所は 4 つある。

- 端末の`confirm`: ユーザが親のワークツリーで`sh .ccnavi/scripts/ccnavi-review.sh confirm --phase <N>`を打つ
- VS Code 拡張のボードの「レビュー済み連絡」: ユーザが出た文をセッションに貼り、エージェントがその文のとおりに`confirm`を打つ。この操作ではボードはマーカーを置かない
- Chrome 拡張のボードの「レビュー済み」: ユーザがブラウザで押す。マーカーと`done/`への移動が、リモートの親のブランチに書かれる
- `decide`: 未解決の指摘が残っているとき、ユーザが指摘ごとの方針を決める。端末の`ccnavi-user-decide.sh <N>`（一覧だけは`ccnavi-review.sh decide <N> --preview`）か VS Code のボードの「決める」で、Chrome 拡張には無い。方針は対応しない・このフェーズで直す・issue に回すの 3 つで、issue に回すはフィードバック計画の有無に関わらず（最後のレビューでも）いつでも選べる。指摘が 0 件のときと、どれも直さないときはレビュー済みになる。1 件でも直すときは、見た子が`done/`へ動き、マーカーは置かれない。選んでいる間に増えた指摘（追加分）は止めずに未対応のまま残り、直す指摘が無くても追加分があればレビュー済みにならない（次の`decide`で扱う）。送信が途中で失敗したら`ccnavi-user-decide.sh --resume <操作ID>`で続きを送る

未解決のスレッドが残っていると、`confirm`と Chrome の「レビュー済み」は通らない。変更要求が立っている間は、`decide`も含めてどれも通らない。Chrome の「レビュー済み」と`decide`で`done/`へ動いた子のワークツリーは、その場では消えず、次の親の`finish`の片付けが拾う。Chrome の経路で済ませたときは、ユーザがそのあとセッションに一言送り、エージェントは`ccnavi-ticket.sh status [<親>]`で確かめる。

## 計画の途中で見つかった修正

- 全体計画の途中で分かった設計の誤りは、`feedback:`（全体計画の最後のレビューが済んだあとの対応計画。出せるのは 1 回）では直さない。設計フェーズに追加の子を提案してユーザの承認を受け、その子で設計書を直す。足すとそのフェーズのレビュー済みマーカーが消えるので、元のチケットを手で再開する必要はない
- 設計フェーズを開き直しても、消えるのはそのフェーズのマーカーだけ。着手済みの実装の子や、済んだ受入テストのレビュー状態、後続フェーズの `after` は、ccnavi が見直さない。ccnavi は開き直したときに、後続の着手済み・レビュー済みのフェーズを挙げる。挙がったら、実装中の子を止めるか・受入テストを作り直すか・どの工程を再レビューするかを、継続・追加修正・取り消しの方針としてユーザに相談する。自動で取り消さない
- フィードバック計画を初めて足す改版の承認は、全体計画の最後のフェーズがレビュー済みになってからだけ通り、承認でレビューの状態は変わらない（`reviewed` を置かず、`review/` の子も動かさない）。差し戻しを受けたら、先に`decide`か`confirm`でレビューを済ませる。全体計画に足す子の承認と同じ承認には入れられない（両方拒まれる）ので、子を先に承認し、その作業と再レビューを済ませてから改版を承認する
- フィードバック計画は変更できない。対応中に設計の修正が分かったときは、既存の対応フェーズ（例: `implement-feedback` は `scope: inherit`）の上限と親の範囲に収まるかを見る。親の範囲に設計書が入っていれば、そのフェーズに設計書を直す子を足して対応できる。収まらないときは、ユーザによる定義の変更か、別作業への切り出しが要る
- 子の書き込みが親の範囲に止められたときは、子の範囲を広げても通らない（子の範囲は親の範囲の中に収まる）。別作業として切り出せるなら新しい親を提案する。今回の機能に欠かせないなら、メインセッションがユーザに親の範囲の改版を相談する。範囲を変える改版は、作業中（`doing/`）の子が居ないときだけ通るので、進める順は次のとおり
  1. 作業中の子を全部 `ccnavi-ticket.sh cancel <子> --reason <理由>` で取り消す（子の範囲や計画を直すときも、直さず取り消して出し直す）
  2. 承認済みチケットを写して、親と同じ識別子の提案を正とするツリーの `todo/` に置く（`started_at`・`completed_at`・`base_sha`・`merged_sha`・`cancelled_at`・`cancel_reason`・`finished_to`・`settled_by` は空にする）。`allow`・`ask`・`deny` を直して改版として承認を受ける。承認画面に範囲の差分（追加・削除）が出る。古い範囲は上書きされ、git の履歴にだけ残る。題・課題番号・`mr:` は変えられない
  3. 承認後、新しい範囲で子を新しい子として提案し直す。取り消した子の番号の項は固定されたままなので、同じフェーズに子を足す形になる。親の範囲を広げても、子が書けるのは親の範囲とフェーズ定義の範囲の両方に入る場所だけ。定義の範囲が足りないときは、定義の写し（`phases:`）の改版も要る
  保護対象のファイルなら、範囲の承認とは別に、下書きとユーザの差し替えで直す
- 変更要求（`CHANGES_REQUESTED`）が立っている間は、レビュー済みにも `decide` にもできない（判定はホストを問わず同じ）。直すときは、同じフェーズに新しい子を提案して承認を受ける。解除のしかたと案内の文面はホストで違う:

  | ホスト | 案内 |
  |---|---|
  | GitLab | 変更を依頼（Request changes）が出ています。解除はレビュアーの承認（Approve）で行います。作成者によるレビューの再依頼（Re-request review）で状態が戻るかは未検証です。再依頼した場合も、ccnavi で状態を取り直して確かめます |
  | GitHub | 変更要求（Changes requested）が出ています。解除はレビュアーの Approve か、レビューの dismiss で行います |
- 続きの子は、見た子の範囲の和を持つ。和が上限（20 件）を超えると起こせず、`decide` は何も置かずに止まる。対応を複数の子に分けるか、直す指摘を選び直して範囲を絞る

## セッションの役割分担

- メインは相談・判断・報告といったユーザとのやり取りを受け持つ。実装・調査・テストは、サブエージェントを
  バックグラウンドで起動して任せる
- 1ファイルで済む小さな確認や修正と、レビュー準備中以降の push・依頼は、サブエージェントに任せない
- 子の成果を親のブランチへ合流するのは、メインが打つ子の`finish`（合流・状態の記録・push が1操作）。サブエージェントは子のワークツリーで実装して
  コミットするだけで、push・チケットの状態を動かす操作（start・finish・cancel・propose）・親のワークツリーへの merge / commit / 書き込みは hook が止める。
  子のワークツリーでのコミットと、衝突を解くための親のブランチの merge は打てる。親のワークツリーかは、そのワークツリー自身のチケットで決める。
  居場所は `cd` と `env -C`・`sudo -D` の行き先で追い、`GIT_DIR`・`GIT_WORK_TREE` などの git の置き場の変数は置けない。
  書き込みは Write / Edit と、Bash のリダイレクト・`tee`・`sed -i`・`cp`/`mv` の行き先を見る。`python -c` などのコードは読み切れないので、
  親のワークツリーのパスと書き込みを疑う語が並べば止める（スクリプトのファイルを実行する形や、変数で組んだ行き先は見ない）。
  下書き・提案・ELI5 の置き場（`wip/proposals/`・`wip/handoff/`・`wip/eli5/`）は書ける
- 親を閉じたあとの片付け（子と親のワークツリー、子と親の手元のブランチ、片付けの記録）は ccnavi が行う。ブランチは、成果が失われないと
  条件で確かめられたものだけを消す。エージェントに`git branch -D`は開けない。片付けの入口（`ccnavi sync tidy`・`ccnavi worktree retire`・
  `ccnavi worktree branch`・`ccnavi-user-clean-branch.sh`）は、メインもサブエージェントも直には打てない（sh が中で呼ぶ）。取り消した子のブランチは、
  一覧をユーザに見せ、ユーザが先頭に`!`を付けて`ccnavi-user-clean-branch.sh <子> --confirmed`を打つ（.ccnavi/docs/worktree-cleanup.md）。
  親を閉じたかは MR のマージ済みで決める
- サブエージェントを並行して動かすときは、それぞれに別のワークツリーを割り当てる。
  同じ作業ツリーで編集するサブエージェントが既に動いているところへ、別の編集するサブエージェントを起動すると、
  新しく起動したサブエージェントに案内を出す（チケット制御の有無によらない）。同じ作業ツリーで続けるなら、触るファイルの持ち主を分け、
  他のサブエージェントの未コミットの変更には触れない
- サブエージェントはユーザに直接は聞けない。相談が要る条件に当たったら、作業を止め、聞きたいことを書いてメインに返す。
  メインがユーザに聞き、その答えを渡して同じサブエージェントを再開させる
- サブエージェントには、報告を結論・変えたファイル・テスト結果・相談したいことに絞らせる。ログや長い出力の全文はメインに持ち込まず、
  置き場のパスだけを書かせる。メインのコンテキストを清潔に保つため
- サブエージェントには、バックグラウンドのコマンドを残したまま報告しない、終わるのを待ってから報告する、と指示する。
  報告のあとに自分のバックグラウンド作業が残ると、同じ報告が何度も再送され、メインのコンテキストを消費する。
  止めるなら`TaskStop`で行う
- メインはサブエージェントの報告を差分とテスト結果で確かめてから、ユーザに伝える
- 修正が多いとメインが判断したときは、実装したのとは別のサブエージェントに差分を敵対的にレビューさせる。
  レビュー役には差分と担当の子チケットを渡し、実装の経緯や意図の説明は渡さない。実装役の思い込みを引き継がせないため
- レビュー役には読むことと確かめるための実行だけをさせ、直させない。直しやすさで指摘を選ばせないため
- レビュー役には、指摘ごとに再現の手順（打ったコマンドとその結果）を付けさせる。経緯を渡さない分、推測だけの指摘が混ざりやすいため
- 指摘を直したあとにもう一度レビューさせるときは、新しいレビュー役を起動し、前の指摘も直した内容も渡さない。
  前の回の見方を引き継がせないため
- 修正が複雑だとメインが判断したときは、メインと同じモデルのレビュー役と、メインと違うモデルのレビュー役を
  並列で起動する。モデルによって見落としやすいところが違うため。違うモデルは「サブエージェントのモデル選び」から選び、
  haikuは使わない
- メインはレビュー役の指摘を差分で確かめてから、直すか見送るかを決める。見送った指摘は理由を添えてユーザに伝える
- 入れ子で起動するときは、プロンプトに担当の子チケット・ワークツリー・範囲と、他の子のワークツリーに
  触れないことを必ず書く。孫のhookの`cwd`はメインの`cwd`になるので、ccnaviは孫の担当を見分けられない
- サブエージェントが終わったとき、ccnaviは結果を`ok`・`fixed`・`outside`・`unchecked`・`unattributed`に分けて残す。子のワークツリーから起動した体は、範囲外の変更が残れば1回だけ差し戻される。親のツリーから起動した体は担当の子が決まらないので差し戻されず、`unattributed`として親（メイン）に知らされる。メインは知らせを受けたら、どの子に残っているかを確かめる
- ターンの終わりに「サブエージェントが範囲外の変更を残したまま（`outside`）、または範囲を確かめられないまま（`unchecked`）終わった」と促されたら、`finish`の前にその子のワークツリーの範囲外の変更を確かめて直すか、ユーザに伝える。同じ結果の促しは1回だけ
- 入れ子の上限（`CLAUDE_CODE_MAX_SUBAGENT_SPAWN_DEPTH`）に達したサブエージェントには、Agentツールが無い。
  入れ子での起動が必要なのにAgentツールが無いときは、起動してほしいエージェントの種類・プロンプト・担当を書いて
  メインに返す。メインがそのとおりに起動し、結果を渡して同じサブエージェントを再開させる。上限の値と実測の結果は
  ccnavi の設計書の付録「入れ子のサブエージェント」にある

## サブエージェントのモデル選び

Agentツールの`model`に、任せる作業に合わせてモデルを指定する。省くとエージェント定義のモデルで動き、
定義にモデルが無ければメインと同じモデルで動く。

- 候補はメインと同じモデルまでで、それより強いモデルは使わない
- 候補を弱い順に並べ、弱いほうから「このモデルで足りるか」を下の目安で判断し、最初に足りると判断したものを使う。
  どれも足りないと判断したら、メインと同じモデルを使う
- 任せたモデルが力不足で失敗したら、一つ上のモデルで同じ作業をやり直し、メインと同じモデルまで繰り返す。
  メインと同じモデルでも失敗したら、それ以上は試さずにユーザに報告する
- 力不足とは、手順を読み違えた、拒否の理由を誤解して止まった・迂回した、報告が依頼に答えていない、のような失敗を指す。
  相談が要る条件に当たって止まったのは失敗ではないので、モデルを上げずにユーザに聞く
- やり直すときは、前の試みで何が失敗したかと、ワークツリーに残った変更を上のモデルに伝える

モデルごとの目安は次のとおり。ここに無いモデルは、強さの順で並べた位置に置き、一つ下のモデルでは足りない作業に使う。

- haiku: 用意したファイルへの置き換え、決まった語の検索、ログの抜き出しのように、手順が決まっていて判断の要らない作業。
  速くて安いが、手順書を読み違えたり、拒否の理由を誤解したりしやすい
- sonnet: 調査、ふつうの実装、テストの実行と修正。判断力と費用のバランスがよい。ただし、設計について深い判断が
  要る作業では、opusより見落としが出やすい
- opus: 設計に関わる変更、影響範囲の広い修正、文章の推敲のように細かい判断が要る作業。sonnetより質が安定するが、
  遅くて高い
- `ccnavi-git.sh`を通すgit操作のように、拒否の文面を読んで進める場面がある作業は、手順が決まっていてもsonnet以上を使う
