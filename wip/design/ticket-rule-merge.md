# 設計: ルールとチケットの判定を合わせ、厳しい側を採る

チケット `ticket-rule-merge`（親）の設計フェーズ `ticket-rule-merge-01` の成果物。受入テスト（フェーズ 2）と
実装（フェーズ 3）はこの文書に従う。ADR の下書きは `wip/design/adr-ticket-rule-merge.md`。

**レビューで見てほしいところ**は 2 つ。どちらも判定が緩む向きに触れる。

- §2 チケットの置き場を範囲の外から外す範囲を、「チケット自身の提案ファイル」から「提案と承認済みチケットの置き場まるごと」に広げる
- §3 理由コードを増やさず、文面と記録の欄で区別する

## 0. 前提（親で合意したこと）

- ルールの判定とチケットの判定を両方出し、厳しい側を採る。強さは `deny` > `ask` > `allow`
- チケットの範囲の外は `deny`
- ルールの `deny` は常に最も強い
- チケットが効く条件は変えない。`Write` / `Edit` / `NotebookEdit` で、行き先が承認済みチケットと同じ名前の
  作業ツリーの中にあり、承認済みで、親子は厳しい側

## 1. 実行前の判定の組み立て

### 今

`ccnavi/judge.py` の `decide` は、ルールを `deny` → `ask` → `allow` の順に当て、最初に当たったタイプで
`verdict` を決める（`judge.py:229-257`）。チケットを見るのは `verdict` が空のときだけ（`judge.py:259-266`）。

作業ツリーへの `Write` / `Edit` では、ルールより前にプロジェクトの食い違いの点検（`project_mismatch`、
`judge.py:223-227`）が `approval.scan` を 1 度呼ぶ。ルールが何も言わなければ、`ticket_verdict` がもう 1 度呼ぶ。

### 決めたこと

1. **ルールの当て方は変えない。** `verdict` と `group` はそのまま出す
2. **ルールが `deny` でなければ、チケットの判定も出す。** `deny` のときは出さない。結果が変わらず、
   走査の代金だけが掛かるため
3. **合成は強さの比較。** 強さは `deny` 3、`ask` 2、`allow` 1、何も言わない 0。チケットの範囲の外は `deny`。
   強い側を採る。**同じ強さならルールを採る**
4. **承認済みチケットの走査は 1 回の判定で 1 度だけ。** `project_mismatch` と `ticket_verdict` が同じ一覧を使う
   （§9）

同じ強さでルールを採る理由。どちらを採っても判定は同じで、違うのは見せる文面だけ。人が書いた
ルールの文面（`message`）のほうが、その場所で何に気をつけるべきかを具体的に言っている。チケットの
文面は「範囲の中で済ませよ」しか言えない。

### 記録の欄

| 判定を決めた側 | `code` | `rules` | `source` |
|---|---|---|---|
| ルール（チケットが同じか弱い、またはチケットが無い） | 今と同じ（`DENY_PATH` / `RULE_ASK` / なし） | 当たったルールの id | ルールの層（今と同じ） |
| チケット（ルールより強い） | `DENY_TICKET_SCOPE` / `TICKET_ASK` | `(ticket-scope)` を先頭に、当たったルールの id を続ける | 空 |
| チケット（ルールが何も言わない） | 今と同じ | `(ticket-scope)` | 空（今と同じ） |

「チケットがルールを狭めた」回は、`rules` に `(ticket-scope)` とルールの id が並ぶことで数えられる。
`source` を空にするのは、判定を下したのが層を持たないチケットだから（`judge.py:253-257` の約束どおり）。

ルールの `additionalContext` は、判定を決めた側に関わらず今と同じく載せる。当たったことに変わりはない。

## 2. チケットの置き場を範囲の外から外す

### 今

| 場所 | 外しているもの |
|---|---|
| 実行前の判定（`judge.py:512`） | そのチケット自身の提案ファイルと承認済みチケット（`Ticket.is_own_file`） |
| 実行後の監視（`post.py:306`） | 同上 |
| サブエージェント終了時の検査（`phase.py:686-689`） | 提案の置き場（`CCNAVI_TICKETS`、既定 `wip/tickets`）と承認済みチケットの置き場（`CCNAVI_APPROVED`、既定 `.ccnavi/tickets`）の下まるごと |

今までは、実行前の判定と実行後の監視の違いは表に出なかった。このワークスペースのルールの `allow`
（`worktrees`）が、作業ツリーへの書き込みを先に通していたため。変えたあとは表に出る。親が自分の
作業ツリーに子の提案を書くと、親の範囲の外として止まる。

### 決めたこと

**3 か所とも、サブエージェント終了時の検査と同じ外し方にそろえる。** ツリーのルートからの相対パスが、
提案の置き場か承認済みチケットの置き場の下なら、チケットの範囲を当てない。判定を 1 つの関数にまとめ
（`ticket.py` に置く。例 `is_ticket_place(rel, tickets_rel, approved_rel)`）、3 か所がそれを呼ぶ。
前置は `/` の境で切る。`wip/ticketsX/a.md` は外さない。

### これで緩むもの（レビューで判断してほしい）

チケットのある作業ツリーで、**他のチケットの提案**も範囲の外で書けるようになる。

| 置き場 | 書けるようになるか | 理由 |
|---|---|---|
| `wip/tickets/todo/` の他の提案 | 書ける | 提案は承認されるまで何にも効かない（ADR-0023）。次の子を提案する道でもある |
| `wip/tickets/doing/` `done/` `cancelled/` | 止まる | 組み込みの `builtin-ticket-state`（`deny`）が先に当たる |
| `.ccnavi/tickets/`（承認済みチケットと印） | 止まる | 組み込みの `builtin-guard-project-home`（`deny`、`.ccnavi/` の下まるごと）が先に当たる |

ルールの `deny` はチケットより強いので、外したことで開くのは「ルールが `deny` にしていない提案の置き場」
だけになる。

- **代案 A：実行前の判定と実行後の監視は「自分自身の提案ファイル」のまま残す。** 親が子の提案を書く手が止まる。
  子の提案を書くたびに親の範囲に `wip/tickets/*` を足すことになり、結局まるごと開けるのと変わらない
- **代案 B：サブエージェント終了時の検査のほうを「自分自身」に狭める。** 子が親の提案を書き換えても差し戻す。
  ただし子のツリーに写った親の提案を書き換えても判定には効かず、差し戻す実益が薄い。
  3 か所のうち唯一今効いている検査を厳しくすると、今通っている子の終了が止まる

勧めるのは本文の決めたことで、代案はどちらも採らない。

## 3. 理由コードと文面

### 決めたこと

**理由コードは増やさない。** `DENY_TICKET_SCOPE` と `TICKET_ASK` のまま。区別は文面と記録の `rules` で持つ。

| 場面 | コード | 文面の頭に足す行 |
|---|---|---|
| 範囲の外 | `DENY_TICKET_SCOPE` | 今と同じ |
| チケットの `deny` に当たった | `DENY_TICKET_SCOPE` | `ticket entry: deny <書かれた綴り>` |
| ルールが `allow` / `ask` だったが、チケットが止めた / 聞いた | `DENY_TICKET_SCOPE` / `TICKET_ASK` | `rule: <id> (<allow|ask>) lets this through, but the ticket for this worktree narrows it` |

理由。`reasons.py:50-54` がコードを分ける基準にしているのは「受け取った側の次の一手が違うか」。
範囲の外もチケットの `deny` も、ルールを狭められた場合も、次の一手は同じで、「範囲の中で済ませるか、
親に伝えて範囲を持つチケットを提案する」になる。

- **得るもの**：README の付録 A、VS Code 拡張、記録を数える側、既存のテストが変わらない。
  拡張は理由コードを読んでいない（`vscode-extension/ccnavi-board/src` に該当なし）
- **失うもの**：「ルールは通したのにチケットが止めた」回を `code` だけでは数えられない。記録の `rules` に
  `(ticket-scope)` とルールの id が並ぶことで数える（§1）

**代案：`DENY_TICKET_NARROWED` などのコードを足す。** 数えやすいが、付録 A と要求表に行が増える。
次の一手が同じものにコードを分けると、コードの意味（次の一手の違い）が崩れる。採らない。

## 5. 実行後の監視

### 今

`post._findings`（`post.py:392-426`）は変更ごとに次の順で見る。

1. ルールの `deny` と `ask` に当たる → ルールの側で報告（`POST_VIOLATION`）
2. `scope` が無いか、ルールの `allow` に当たる → 報告しない（`_allowed`）
3. チケットの範囲の外 → `POST_TICKET_SCOPE`

### 決めたこと

- **2 の `_allowed` の近道を外す。** `scope` が無いときだけ飛ばす。`_allowed` 関数は使い手が無くなるので消す
- **1 はそのまま。** ルールの `ask` に当たり、かつチケットの範囲の外という変更は、実行前なら `DENY_TICKET_SCOPE`、
  実行後は `POST_VIOLATION`（ルール）で報告される。コードは違うが、どちらでも報告はされる。
  ルールの側で言うのは、範囲を広げても済まない（ルールが見る場所だ）ことを先に伝えるため（`post.py:405-407` のとおり）
- **チケットの `ask` の中は報告しない。** 今と同じ（`ScopeGuard.finding` が `ask` を中と数える）
- **外し方は §2 の関数を通す**

## 9. 判定の代金

2026-09-13 にこのワークスペースで測った（作業ツリー 3、承認済みチケット 5、`scratchpad/measure_scan.py`）。

| 処理 | 1 回あたり |
|---|---|
| `approval.scan` | 約 400 ms（30 回の平均） |
| `tree.tree_of` | 約 5 ms |

作業ツリーへの `Write` / `Edit` 1 回で `approval.scan` が走る回数。

| | 今 | 決めたことのとおりに変えたあと |
|---|---|---|
| ルールが `allow` / `ask` に当たる | 1（`project_mismatch`） | 1（共有） |
| ルールが何も言わない | 2（`project_mismatch` と `ticket_verdict`） | 1（共有） |
| ルールが `deny` に当たる | 1 | 1 |
| 実行後の監視 | 1（`events.scope_guard`） | 1 |

**共有すれば、どの場合も今より増えない。** 共有しないと、ルールが当たる場合に約 400 ms 増える。
`approval.scan` は内部で `scan_all` を 2 度呼ぶ（開いたものと閉じたもの）。1 回の走査そのものを速くするのは
このチケットの外に置く。

共有の形。`decide` の中で、`tickets_enabled` かつ `SCOPE_TOOLS` かつ行き先が作業ツリーのときに一度だけ
`approval.scan` し、索引を `project_mismatch` と `ticket_verdict` に渡す。どちらも索引を受け取らない呼び方を残し、
受け取らなければ自分で読む（他の呼び手を変えないため）。

## 11. 配った先の移り方

- 作業ツリーを `allow` で開けているプロジェクト（このワークスペースの `worktrees` と同じ形）では、更新した時点で、
  **承認済みチケットに結び付いた作業ツリー**の書き込みがチケットの範囲に縛られる
- チケットの無い作業ツリー、ワークスペースルート直下、チケット制御が無効のプロジェクトは変わらない
- 止まったら、ルールを直すのではなく、範囲を持つチケットを提案する。README の移り方の節にこの 3 点を書く
- 前の振る舞いに戻すスイッチは足さない（採らなかった案。ADR の下書き）

- 親子の合成。子の `allow` と親の範囲の外は範囲の外、子の `allow` と親の `ask` は `ask`。ルールが `allow` のときも同じ
- 未承認の提案しか無い作業ツリー、作業ツリーの無い承認済みチケット、`CCNAVI_TICKET_CONTROL=disable`、
  ワークスペースルート直下（main）への書き込みは、ルールの判定だけで決まる
- ルールより先に見る点検（サブエージェント、ゲート、プロジェクトの食い違い）はルールとチケットより先に返す
- dry-run では同じ判定を「would have stopped / asked」の文で返し、止めない
- ルールが読めず組み込みの既定に落ちたとき、チケットの判定がそのまま出る

### 12.5 診断

- `--test Write <子のツリーの範囲外で、ルールが allow の場所>` の `verdict` が `deny (DENY_TICKET_SCOPE)` で、
  `rules` にルールの id と「ルールファイルの外から来た根拠」の `(ticket-scope)` が並ぶ
- 承認画面の親の見出しの下に §7 の 1 行が出る
- `--explain` のチケットの節の頭に §8 の 1 行が出る

### 12.6 書き換えが要る既存テスト

調べた範囲では無い。範囲のテスト（`tests/test_ticket.py`）のルールは `deny` 1 本だけで `allow` を持たない。
`tests/test_root_placeholder.py` はルールに `worktrees` の `allow` があるがチケットが無い。
`tests/test_projects.py:381-386` はルールの `allow: */src/*` とチケットの範囲が重なる。範囲の中の `src/a.py` は
通り、範囲の外の `docs/a.md` はルールが何も言わない場所なので、今も変えたあとも `DENY_TICKET_SCOPE`。
受入テストを足したあと、全部のテストを回して確かめる。
