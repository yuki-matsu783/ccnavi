# ADR-0109: フェーズの順序は親の計画の項に書き、ワークフロー編集タブの図でユーザが決める

状態: 提案（草案。採用前）。採用すると次を置き換える。

- ADR-0026 の「`overlap` は例外」と、定義を判定のたびに `phases.yml` から読む読み方（承認済みの親は自分の `phases:` から読む）。「定義はユーザが持つ設定で、エージェントは書き換えない」は保たれる（`phases:` は `phases.yml` の写しで、`--agree` が同じかを確かめる）
- ADR-0043 の「種類の `scope` を書き込みのたびに当てる」の読む先（`phases.yml` から、親の `phases:` へ）。判定が親と定義の `scope` の両方で切り詰めることは変えない
- ADR-0070 のフェーズ管理画面の図（図をなくす。`@xyflow/react` を入れた理由と払った代償の記録は、フロー定義画面で今も当てはまる）
- ADR-0078 の、定義の `after`・ファイルの頭の `order`・レイヤーの `order` の読み方・「フィードバック計画は常に一直線」・「祖先か同じ定義を待つ」・「順序が DAG と噛み合う」の検査・`overlap` を残す・`after` と `overlap` の両方の検査・`PhaseType.key()` に `after` を入れる・フェーズ管理画面の節。終端は 1 つ、をフィードバック計画にも広げる。「待ち方を承認時に計算して固定する」は、承認済みチケットの計画から都度計算する、に替える（固定する元は承認済みチケットの計画そのものになる）。残すのは、延期の引き受け手の計算を 1 か所に置くこと、止める単位は親ごと、受け入れの適用範囲、局面と案内の読み方、承認画面に待ちを出すこと
- ADR-0082 の、図の区分の枠・折れ線・図の下の凡例と注意・雛形を `dag` にすること（図がなくなる）。初回の吹き出しの案内の仕組みは残す
- ADR-0104 の、全体計画の待ち方を承認のときに計算して `<承認済みの置き場>/phases/<親>/workflow.yml` に固定する決定（ファイルを廃止し、承認済みチケットの計画から都度計算する）。それに伴う、承認でファイルを書く・落ちたら戻す、取り下げでファイルを今の計算と比べて一緒に消す、計算し直した待ち方の違いで改版にする、C1 がファイルをユーザの判断が書くものとして運ぶ、前の版の `workflow:` 欄を今の計算と見比べて採る、手で動かした承認（ファイルが無い）を一直線で読む、の各行。**「承認はチケットの中身を変えない」（提案をバイト単位でそのまま動かす）は保たれる。** 承認で書くものは提案の移動だけになる。親の `phases:` も承認の前に提案へ書いておくもので、承認は書き足さない

**`allow:` は変えない。** 親の `allow` / `ask` / `deny`、子の範囲、`scope: inherit`（親の `allow` そのもの）は今のまま
- ADR-0093 のうち、Chrome の承認と取り下げ（同梱の ccnavi が決め、親のブランチへ書く）が運ぶものに待ち方のファイルが入る部分（運ばなくなる）
- ADR-0107 の「フェーズ定義は親の `project:` が指す `config/` の 1 本で決まる」の効く範囲（承認の検査と提案の補助だけになり、承認のあとの判定は親の `phases:` を読む）。`config/` だけに置くことは変えない
- ADR-0105 のうち、承認で一緒に書く親の待ち方のファイルと、落ちたときにそれを戻す処理の記述（ファイルが無くなる）

## 状況

2026-10-06 の時点で、フェーズの順序は `phases.yml` が持っている。定義の `after`（先に済んでいるべき定義）とファイルの頭の `order`（`sequential` / `dag`）が待ち方を決め、`overlap`（並行してよい）と `requires`（一緒に置くべき）が承認の検査に効く。
このワークスペースの `phases.yml` には `order` も `after` も無く、全体計画は一直線で進む。

困りごとは 3 つあった。

- 並行させたいかは計画ごとに違うのに、形は定義で 1 つに決まる。計画ごとに変えるには `phases.yml` を直すしかなく、直すと他の計画の待ち方も変わる
- 順序に関わる欄が 4 つあり、組み合わせの検査（`after` と `overlap` の両方、レイヤーの食い違い、循環）が要る
- ユーザが順序を見るのはフェーズ管理画面の定義の図で、承認する計画そのものの図ではない。フィードバックの定義は `after` を持てないので、フィードバック計画は常に一直線だった

ADR-0078 は `plan:` の項ごとに先行を書く形を「依存を決めるのがエージェントの提案になる」として退けた。今回は、エージェントの先行は案に留め、承認の前にユーザが図で線を引き直して決める。退けた理由はこれで当たらなくなる。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| `phases.yml` から `order`・`after`・`overlap`・`requires` をなくし、フェーズ定義だけにする。残っていれば読まずに通し、`--lint` が warn を出す | 順序は計画ごとに決める。warn に留めるのは、更新した直後に全部の承認と `--lint` が止まらないように | 残っていれば error |
| 親の `plan:` / `feedback:` の項に `after: [番号]` を書く。保存される書式では、指せるのは自分より小さい番号だけ。`feedback:` の項はフィードバック計画の番号だけを指す | 番号は既にフェーズの名前（子の `phase:`、マーカー、`--explain` の待ち）。同じ定義を 2 回置いても 1 つに決まる。小さい番号だけにすると循環が書けず、「終端は最後の項」「延期の先は後ろ」の前提が保てる | 項に名前を付けて指す（呼び名が 2 つになる）。辺の一覧を親に別に持つ。保存する書式で任意の DAG を許す（前提を作り直すことになる） |
| `after` を書かない項は何も待たない。同じ定義を 2 回置いても暗黙には待たない | 線が全て。図に無い待ちを作らない | 何も書かなければ一直線（図と待ち方が食い違う） |
| 終端は 1 つ（最後の項が、それより前の全部の項を推移的に待つ）を、全体計画とフィードバック計画の両方に求める。最後の項は延期できない | どこにも繋がらない項と途中で切れた枝を承認で落とす。両方の計画で規則を揃える | フィードバック計画には求めない（独立した対応を並行のまま終えられるが、書き漏れが通る） |
| 判定が読む待ち方は、承認済みチケットの `plan:` / `feedback:` から都度計算する。`phases/<親>/workflow.yml` は廃止する。`Ticket.workflow` の型と読む側は残し、`approval.load_copy` が `workflow.compute` の結果を入れる。残ったファイルは読まず、`--lint` が warn で言う | 計算の入力は計画の `after` と `review: defer` だけで、`phases.yml` も状態も入らない。図で直した順序は承認の前に提案へ入る。ファイルは計画の完全な写しになり、写しを持つ理由（`phases.yml` を後で直しても進行中の親の待ちを変えない）が消えた。2 か所に持つための仕組み（片方だけ書けたときの戻し、取り下げでの比較と削除、C1、Chrome の運び方、孤児の warn、前の版の欄の見比べ）が全部要らなくなる | ファイルを残す（後の版で計算の決まりを直しても、承認したときの答えが残る） |
| エージェントは `after` に先行（案）を書く。VS Code のワークフロー編集タブ（承認待ちの親の提案ごとに 1 枚の専用パネル。子のフロー編集と同じ作り）が計画の図を出し、ユーザは並びの逆向きを含めて任意の線を引ける。循環になる線と、子が承認された番号へ入る線は、引いている最中に断る | 順序を決めるのはユーザ。断るのは線と点だけで決まる形で、計画の良し悪しの判定ではない | 小さい番号への線だけを引ける（並びを変えるには差し戻しが要る） |
| 線を変えるたびに番号をトポロジカル順に振り直す（先行が全部前にある項のうち、元の番号の小さいものから）。`after` の指す先は振り直した番号に付け替え、延期は項に付いたまま動く。子が承認された番号は動かさない | 保存される書式の不変条件（小さい番号だけ）を保ったまま、図で並びを変えられる。同じ段は元の番号順にして、変えていない項の番号をなるべく保つ | 番号を振り直さず、番号の対応表を別のファイルに持つ（番号で項を引く全部の箇所が対応表を通すことになる） |
| 振り直した順序は、タブの保存（「この順序に決める」）で実行ファイル（`--plan-order --write --expect <ハッシュ>`）が親の提案の `plan:` / `feedback:` の値と、`todo/` にある子の提案の `phase:` の値だけを書き換えて決める（承認済みの子には触れない）。開いたときから親か子の提案が変わっていれば何も書かず、順序の検査に error があれば書かない。ユーザはそのあと承認をふつうに行う | 承認は提案をそのまま動かす（ADR-0104）。順序を決めるのは承認の前のユーザの書き換えで、承認ではない。順序がすべて計画に入るので、待ち方はいつも計画から計算し直せる | 承認の段で書き換えて置く（承認がチケットの中身を変える） |
| 振り直しと保存の読み書きは、`--agree` の外の独立したフラグ `--plan-order <親>`（`--json`・`--order`・`--write`・`--expect`）にする。エージェントが打ってもよい | `--agree` の副フラグにすると組み込みの止め（`phase_forms._CLI_FORMS`）に当たり、`--preview` と同じ厳しさの免除と変異テストが要る。書くのは親と子の提案（エージェントも書ける置き場）だけで、承認はしない | `--agree --plan` / `--agree --reorder` と免除 |
| タブは線を変えるたびに、元の番号での直接の先行を `--order` に付けて `--plan-order <親> --json` を呼び直す（読むだけ）。振り直した番号・本文・落とす理由・最後の項が待たない項（`loose`）は実行ファイルが返す。画面は同じ決まりで仮の番号を先に出し、返った番号で置き換える | 答えを出すのは 1 か所（ADR-0035）。振り直しの正も実行ファイル。画面が仮の番号を出すのは、線を変えた手応えを遅らせないため | 振り直した計画を画面が作って送る（保存される番号を画面が決める） |
| 承認のオーバーレイには同じ図の部品を読むだけで出す。中身は preview の `plans`（承認する提案そのものの順序）。「ワークフローを編集」はオーバーレイを閉じてからタブを開く。親のタブに未保存の変更があれば、その親を含む一覧は承認を打たない | 編集はタブだけ、保存は承認の前に提案へ入るので、オーバーレイの図と承認の対象がずれない。承認の遷移に preview を呼び直す状態を足さずに済む。閉じるのは、タブで保存すると一覧のダイジェストが変わり、その一覧では承認できないから | オーバーレイで線を引き直す（承認の途中に preview の呼び直しと提案の書き換えの状態が要り、編集途中の順序と承認の対象がずれる隙ができる）。オーバーレイを開いたままタブへ移る（タブの保存を受けて一覧を読み直す段が要る） |
| タブはフロー編集の作り（親ごとに 1 枚、未保存の「●」と閉じた後の聞き方、外で変わったら保存しない）に合わせる。違いは、エージェントの提案そのものが下書きで取り込む段が無いこと、書くのが拡張ではなく実行ファイルであること、保存先がエージェントも書ける提案であること。外で提案が変わったら差分を見せて取り込むかを選ばせる | ユーザが覚える操作を 1 つにする。保存先の提案はエージェントも書けるので、`--plan-order --write` を保護しなくても緩まない | 承認済みの領域に順序を置く（承認がチケットの中身を変えない決まりと、待ち方が計画から計算できることが崩れる） |
| start / end の仮ノードを描き、先行の無い項へ start から、後続の無い項から end へ線を引く。`loose` の項と、その end への線を注意の色で描く。仮ノードは保存せず、実行ファイルは知らない | 並行と終端の崩れが絵で読める。どれを目立たせるかは実行ファイルが決める | 仮ノードを描かない |
| 端末の `--agree`・Chrome 拡張・手で動かした承認は順序を直さない。待ち方はどの経路でも承認済みチケットの計画から計算する | 端末は文字で結果を確かめる形でよい（ユーザの判断） | 端末にも順序を直す引数を出す |
| 親の frontmatter の `phases:` に、`plan:` / `feedback:` が使うフェーズ定義だけのコピー（`phases.yml` と同じ欄。定義の id をキーにした辞書）を持たせる。`--agree` は、項が `phases:` に無い定義名を使えば error、`phases:` に書いた各定義が承認したときの `phases.yml` の同じ名前の定義と（読んだ形で）同じでなければ error、名前が `phases.yml` に無ければ error。`phases.yml` にあって `phases:` に無い定義は何も言わない。`phases:` にあってどの項も使わない定義は warn。承認のあとの判定・`phases_of`・成果物の確かめ・子の範囲（`type_for`）は親の `phases:` を読み、`phases.yml` を読まない | 承認したときの定義を親に固定し、承認のあとに `phases.yml` を直しても進行中の親の範囲・見る場所・成果物を変えない。エージェントが書いても値は `phases.yml` と同じでなければ通らないので、定義を決めるのは今までどおりユーザ（ADR-0026）。承認の前に書くので、承認は書き足さない（ADR-0104）。使われていない定義を warn に留めるのは、判定に効かず、error にすると消し忘れで承認が止まるため | 全定義を写す（外した定義が読めない）。承認のときに書き足す（承認が中身を変える）。今までどおり毎回 `phases.yml` を読む（承認したものと効くものが変わる） |
| コピーは補助のフラグ `ccnavi --plan-order <親> --fill-phases` が、項が使う定義だけを `phases.yml` から差し込んで作る（使わない定義は外す）。エージェントが打ってよい | 写し間違いを無くす。`phases.yml` を直したあとに提案を追いつかせるのも同じ 1 本 | エージェントが手で書き、検査で落とすだけ |
| 改版では、子が承認された番号が使う定義は承認済みチケットの `phases:` と同じでなければ error（外せない）。それ以外の定義は改版を承認したときの `phases.yml` と同じでなければ error で、足す・外すは自由。両方が使う定義は固定した側に揃える。子が承認された番号の定義を直したいときは、ユーザが承認済みチケットの `phases:` を手で直す | 進んでいるフェーズの範囲・見る場所・成果物を改版で変えない。フィードバック計画の立案（必ず改版）が `phases.yml` の変更で詰まらない | 改版ではいつも今の `phases.yml` に揃える（閉じたフェーズの `review` が後から変わりうる）。改版でも既存の定義を変えない（固定していない番号も古いまま） |
| 承認画面に、この親が使う定義（題・`review`・`scope`・`deliverables`・使う番号）、使われていない定義、`phases.yml` にあってこの親では使わない定義を分けて出す。改版では `phases:` の差分を出す | ユーザが「どの定義を固定し、どれを外したか」を読んで承認できるように。`phases:` はチケットのバイト列なのでダイジェストに入る | 固定する定義を出さない |
| 子に `phases:` があれば error。計画を持つのに `phases:` の無い親は、判定の側で止め、子も止まる。`unread_type`（定義が読めないときは定義で切り詰めない）は消す。定義の `scope` と `deliverables` は 20 件まで | 子の `phase:` との取り違えを読む段で止める。定義が親に無いのは壊れた親。`phases:` の大きさを縛る | 計画付きで `phases:` の無い親は `phases.yml` を読む（2 つの答えが残る） |
| 手で動かした承認（`--agree` を通さずに承認済みの置き場へ動かした親）も、計画の `after` を信じて並行で読む。特例は置かない。代わりに判定の側（`approval_checks.blocking_problems`）で 承認済みチケットだけを読んで済む検査（`after` の形・終端・最後の項の延期・延期の引き受け手と、親の `phases:` から読む定義の有無・`kind`・引き受け手のレビュー）を当て、error があればその親を止める。`after` の形の誤りはチケットを読む段では落とさない。子は `child_problems` で親の計画の error を引き継ぎ、承認・着手・書き込みが止まる。`phases:` と今の `phases.yml` の食い違いは `--lint` の warn | `after` は承認済みの置き場にあるチケットの中身で、ユーザが見て動かしたもの。`--agree` の検査を通っていないぶんを判定で受ける。読む段で落とすと承認済みチケットが索引に入らず、判定がその親を知らないまま空の答えを出す。判定が `phases.yml` を読まないので、承認のあとに定義を直しても進行中の親は止まらず、`mark_blocked` の引数も変えずに済む | ファイルの無い手動の承認を一直線で読む（ファイルを廃止すると合図が無い）。`after` の無い 2 項以上の計画だけを一直線で読む特例（計画の読み方が経路で変わる）。判定で `phases.yml` の定義を読む（承認後の定義の変更で進行中の親が止まる）。判定を `after` の形・終端・延期だけに留める（親の `phases:` があれば留める理由が無い） |
| 待ち方の計算は項の `after` を推移的に辿る。`order` はいつも `dag` で、一直線の読み方の枝は消す。フィードバック計画の番号も `waits` と `review_at` に入る | 判定・延期・局面の読み方（`waits` / `review_at` を読む側）をそのまま使える | 直接の先行だけを渡す（読む側を全部直す） |

## 得たもの・失ったもの

- 得たもの: 順序を計画ごとに決められ、決めるのはワークフロー編集タブのユーザ。並びの逆向きを含めて図だけで直せる。順序に関わる欄と組み合わせの検査が減る
- 得たもの: フィードバック計画も並行と合流を書ける
- 得たもの: ユーザが見る図が、承認する計画そのものになる
- 失ったもの: **辺の書き漏れが並行として通る。** 今の既定（一直線）では止まる側に倒れていた。終端の検査で、どこにも繋がらない項と途中で切れた枝は落ちる。`after` を 1 つも書かない 2 項以上の計画は必ず落ちる。残るのは、終端には繋がっているが途中の 1 本を書き忘れた形で、タブと承認画面の図と本文の「すぐ始まる」で見るしかない
- 失ったもの: フィードバック計画で、独立した対応を並行のまま終える形。最後に 1 項で受けるか、一直線に並べる
- 失ったもの: `requires` の検査。計画に要る定義の組は、定義の `when` の案内とタブ・承認画面の図でユーザが見る
- 失ったもの: タブで順序を直すと、承認の前に提案が書き換わる。書き換えた提案はコミットされないまま承認されるのが普通で、承認コミットの親に直す前の提案が残るので、その親は取り下げられない。止まる側のまま受け入れ、取り下げの文面で「取り消して出し直す」と案内する
- 失ったもの: 番号の振り直しの決まりを、実行ファイル（正）と画面（仮）の 2 か所に持つ。見本の表をテストで共有して見張る
- 失ったもの: ワークフローの形を定義で一度決めて使い回す手段。計画ごとに書く
- 失ったもの: 前の版の承認済みの親（`after` の無い計画）は、計算すると全部の項が並行に見える。判定の側の検査で終端の error になり止まる側に倒れる。承認済みで動いている親は無い
- 失ったもの: **手で動かした承認が、計画の `after` で並行に進むようになる（判定が緩む側の変更）。** 今はファイルが無いことを合図に一直線で読んでいた。手当ては判定の側の `workflow.problems`（`phases.yml` を読まない検査）で、壊れた計画の親は止まり、子の承認・着手・書き込みも止まる。残るのは、形は正しいが意図と違う並行で、これは `--agree` を通しても同じく図と本文で見るしかない
- 失ったもの: **計算の決まりを後の版で直すと、進行中の親の待ちが変わる。** ファイルなら承認したときの答えが残った。決まりは「`after` を推移的に辿る」「延期は、延期した項を待つ延期していない最小の番号が引き受ける」の 2 つだけにして設計に書き、直すときは ADR を立て、計画と待ち方の見本の表（`tests/fixtures/plan-waits.json`）を固定するテストで見張る（`tests/sh/test_compat_skew.py` は互換の版を見るだけなので足りない）
- 失ったもの: **`phases.yml` を承認のあとに直しても、進行中の親に届かない**（範囲を狭めても効かない）。子の無い番号は改版で `--fill-phases` を打ち直して揃え、子が承認された番号はユーザが承認済みチケットの `phases:` を手で直す。`--lint` が食い違いを warn で言う
- 失ったもの: `phases.yml` を直すと、承認待ちの提案が全部 `--agree` に落ちる（`--fill-phases` を打ち直せば通る）
- 失ったもの: 親チケットが定義のコピーのぶん大きくなる。`phases.yml` の定義の `scope` と `deliverables` に 20 件の上限が新しく付く
- 失ったもの: 計画を持つのに `phases:` の無い親（前の版、`phases:` を書かずに手で動かした承認）は止まる
- 失ったもの: 計画付きの親の見本を持つテスト（約 25 本）に `phases:` を足す
- 得たもの: 待ち方の持ち場が承認済みチケットの計画の 1 か所になり、計画と待ち方が食い違う経路が無くなる。C1・Chrome・`--lint` のファイルの扱いが要らなくなる
- 失ったもの: ボードの画面に読むだけの図のために React Flow が入り、約 180KB 重くなる。新しいタブの画面（約 440KB）は開いたときだけ読む。フェーズ管理画面からは約 180KB 抜ける
- 失ったもの: 順序を直すには承認とは別のタブを開いて保存し、承認を開き直す。タブは線を変えるたびに実行ファイルを呼び直す
- 失ったもの: タブの編集中にエージェントが提案を書き直すと、その編集は保存できない（差分を見て取り込み直す）。ハッシュを確かめてから書くまでの間にエージェントが書くと、どちらかが失われる（TOCTOU。実行ファイルの 1 回の中に狭めるだけ）
- 失ったもの: `plan:` / `feedback:` の値を差し替えると、計画の中に書いたコメントが消える
- 失ったもの: 番号を振り直すと `todo/` の子の提案の `phase:` も書き換わる。全部を戻せる形で書くが、戻しまで落ちると親と子が食い違いうる（子を先、親を最後に書いて、食い違いを `--plan-order` が言う）
- 失ったもの: 改版の錠が前置ごとから番号ごとに変わり、子の無い前の番号を直せるようになる（判定が緩む側）。固定した番号の中身と待ちは変えさせない
- 失ったもの: 始まっていない小さい番号の項を、始まった大きい番号の項の後ろに回せないことがある（空いた番号を埋める項が無いとき。例: 1〜3 で 1・3 に子があるときの 3→2 の線）
- 失ったもの: フィードバック計画を立てたあとは全体計画を変えられない。前の版の形の親は取り下げられない
- 失ったもの: 2 項以上で `after` の無い計画を見本に持つテストが多く（14 本と拡張の見本）、先に見本を直す段が要る

## やらなかった場合

順序は定義で 1 つに決まったまま。計画ごとに並行を変えるには `phases.yml` を直すしかなく、直すと他の計画の待ち方も変わる。フィードバック計画は一直線のまま。
