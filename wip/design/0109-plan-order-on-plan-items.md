# ADR-0109: フェーズの順序は親の計画の項に書き、承認画面の図でユーザが決める

状態: 提案（草案。採用前）。採用すると次を置き換える。

- ADR-0026 の「`overlap` は例外」と「最後の項は延期できない」（後続の無い項は延期できない、に広げる）
- ADR-0070 のフェーズ管理画面の図（図をなくす。`@xyflow/react` を入れた理由と払った代償の記録は、フロー定義画面で今も当てはまる）
- ADR-0078 の、定義の `after`・ファイルの頭の `order`・レイヤーの `order` の読み方・「フィードバック計画は常に一直線」・「祖先か同じ定義を待つ」・「順序が DAG と噛み合う」の検査・`overlap` を残す・`after` と `overlap` の両方の検査・`PhaseType.key()` に `after` を入れる・フェーズ管理画面の節。残すのは、待ち方を承認時に固定すること、延期の引き受け手の計算を 1 か所に置くこと、終端は 1 つ、止める単位は親ごと、受け入れの適用範囲、局面と案内の読み方、承認画面に待ちを出すこと
- ADR-0082 の、図の区分の枠・折れ線・図の下の凡例と注意・雛形を `dag` にすること（図がなくなる）。初回の吹き出しの案内の仕組みは残す
- ADR-0104 の、取り下げで待ち方のファイルを今の `phases.yml` から計算し直して比べること（承認コミットのファイルと比べる、に替える）と、計算し直した待ち方の違いで改版にすること

## 状況

2026-10-06 の時点で、フェーズの順序は `phases.yml` が持っている。定義の `after`（先に済んでいるべき定義）とファイルの頭の `order`（`sequential` / `dag`）が待ち方を決め、`overlap`（並行してよい）と `requires`（一緒に置くべき）が承認の検査に効く。
このワークスペースの `phases.yml` には `order` も `after` も無く、全体計画は一直線で進む。

困りごとは 3 つあった。

- 並行させたいかは計画ごとに違うのに、形は定義で 1 つに決まる。計画ごとに変えるには `phases.yml` を直すしかなく、直すと他の計画の待ち方も変わる
- 順序に関わる欄が 4 つあり、組み合わせの検査（`after` と `overlap` の両方、レイヤーの食い違い、循環）が要る
- ユーザが順序を見るのはフェーズ管理画面の定義の図で、承認する計画そのものの図ではない。フィードバックの定義は `after` を持てないので、フィードバック計画は常に一直線だった

ADR-0078 は `plan:` の項ごとに先行を書く形を「依存を決めるのがエージェントの提案になる」として退けた。今回は、エージェントの先行は案に留め、承認の前にユーザが図で線を引き直して決める。退けた理由はこれで当たらなくなる。

## 決定

| 決めたこと | なぜ | 採らなかった側 |
|---|---|---|
| `phases.yml` から `order`・`after`・`overlap`・`requires` をなくし、フェーズ定義だけにする。残っていれば読まずに通し、`--lint` が warn を出す | 順序は計画ごとに決める。warn に留めるのは、更新した直後に全部の承認と `--lint` が止まらないように | 残っていれば error |
| 親の `plan:` / `feedback:` の項に `after: [番号]` を書く。指せるのは自分より小さい番号だけ。`feedback:` の項はフィードバック計画の番号だけを指す | 番号は既にフェーズの名前（子の `phase:`、マーカー、`workflow.yml`）。同じ定義を 2 回置いても 1 つに決まる。小さい番号だけにすると循環が書けず、「終端は最後の項」「延期の先は後ろ」の前提が保てる | 項に名前を付けて指す（呼び名が 2 つになる）。辺の一覧を親に別に持つ。任意の DAG（前提を作り直すことになる） |
| `after` を書かない項は何も待たない。同じ定義を 2 回置いても暗黙には待たない | 線が全て。図に無い待ちを作らない | 何も書かなければ一直線（図と待ち方が食い違う） |
| エージェントは `after` に先行（案）を書く。VS Code の承認画面は計画の図を出し、ユーザが線を引き直してから承認する。直した順序は `phases/<親>/workflow.yml` に入り、チケットは変えない | 順序を決めるのはユーザ。承認はチケットの中身を変えない（ADR-0104） | 直した順序をチケットに書き戻す |
| 図の部品はフロー定義画面の `Canvas.tsx` と `flow-doc.ts` の `canConnect` / `connect` を流用する。start / end の仮ノードを描き、先行の無い項へ start から、後続の無い項から end へ線を引く。仮ノードは保存せず、実行ファイルは知らない | 並行（start から何本も出る）と終端（end へ何本入る）が絵で読める | 仮ノードを描かない（並行が読み取りにくい） |
| 画面は判定しない。線を変えるたびに `--agree --preview --json --order <JSON>` を呼び直し、実行ファイルが返した本文・落とす理由・ダイジェストを出す。引ける線は実行ファイルが渡す `may_wait_on` で決める。承認は同じ `--order` とダイジェストで打つ | 答えを出すのは 1 か所（ADR-0035）。ダイジェストに書く待ち方が入るので、見せた順序と書く順序が食い違わない | 画面が終端や延期を見る |
| 端末の `--agree`・Chrome 拡張・手で動かした承認は順序を直さない。端末と Chrome は計画の `after` で計算する。手で動かした承認は今までどおり待ち方のファイルを書かず、一直線で読む | 端末は文字で結果を確かめる形でよい（ユーザの判断）。手で動かした承認を計画の `after` で読むと、ユーザが図を見ていない順序が並行として効く | 端末にも順序を直す引数を出す |
| 待ち方の計算は項の `after` を推移的に辿る。`workflow.yml` の形は変えず、新しい承認は `order: dag` を書く。フィードバック計画の番号も `waits` と `review_at` に持つ | 判定・延期・局面の読み方をそのまま使える | 直接の先行だけを保存する（読む側を全部直す） |
| 承認の検査は全体計画とフィードバック計画に同じ規則を当てる: 後続の無い項は延期できない、延期の引き受け手（延期した項を待つ、延期していない最小の番号）がいてレビューを持つ。終端は 1 つ、は全体計画にだけ求める | フィードバックの定義が `after` を持てない制約は、定義から順序が消えるので無くなる。フィードバック計画の終わりは親を閉じることで、1 つの番号を前提に使う処理が無い | フィードバック計画にも終端 1 つを求める |
| 改版になるのは、提案の計画（`after` を含む）が承認済みチケットと違うときだけ。子が承認された番号の先行は変えられない | ユーザが図で直すと計画と待ち方は違うのが普通なので、計算し直して比べると、計画が同じ提案が改版に見える。始まったフェーズの待ちを後から変えない | 今までどおり計算し直した待ち方の違いでも改版にする |
| 取り下げは、`workflow.yml` が承認コミットに入ったものとバイト単位で同じときに通す | 図で直した順序は計画からは計算し直せない。`phases.yml` は待ち方に効かなくなる | 今の `phases.yml` から計算し直して比べる |
| `workflow.yml` を読むとき、番号の範囲と「待つのは小さい番号だけ」を確かめ、外れていれば読めない待ち方として判定を止める | ファイルはユーザが図で決めた中身を持つようになる | 形を確かめない |
| フェーズ管理画面の図と、関係の欄・`order` の選択をなくす。一覧の編集は残す | 図に描く関係が定義から無くなる | 図を定義の一覧として残す |

## 得たもの・失ったもの

- 得たもの: 順序を計画ごとに決められ、決めるのは承認画面のユーザ。順序に関わる欄と組み合わせの検査が減る
- 得たもの: フィードバック計画も並行と合流を書ける
- 得たもの: ユーザが見る図が、承認する計画そのものになる
- 失ったもの: **辺の書き漏れが並行として通る。** 今の既定（一直線）では止まる側に倒れていた。終端の検査で、どこにも繋がらない項と途中で切れた枝は落ちる。`after` を 1 つも書かない 2 項以上の計画は必ず落ちる。残るのは、終端には繋がっているが途中の 1 本を書き忘れた形で、承認画面の図と本文の「すぐ始まる」で見るしかない
- 失ったもの: `requires` の検査。計画に要る定義の組は、定義の `when` の案内と承認画面でユーザが見る
- 失ったもの: ワークフローの形を定義で一度決めて使い回す手段。計画ごとに書く
- 失ったもの: 並びを変える手段が承認画面に無い（小さい番号しか指せない）。並びを変えたいときは差し戻して計画を直させる
- 失ったもの: 前の版の `workflow:` 欄で `dag` だったものは、計画に `after` が無いので今の計算と合わず、一直線で読む（止まる側）
- 失ったもの: ボードの画面に React Flow が入り、約 180KB 重くなる。フェーズ管理画面からは抜ける
- 失ったもの: 取り下げで承認コミットの `workflow.yml` を引く経路が 1 つ増える。線を変えるたびに preview を呼び直す

## やらなかった場合

順序は定義で 1 つに決まったまま。計画ごとに並行を変えるには `phases.yml` を直すしかなく、直すと他の計画の待ち方も変わる。フィードバック計画は一直線のまま。
