# フェーズの順序を親の計画で決める（設計草案）

採用前の草案。ADR の草案は同じ置き場の `0109-plan-order-on-plan-items.md`。

## 1. 目的

フェーズの順序（どのフェーズがどれを待つか）を、`phases.yml` のフェーズ定義から外し、親チケットの計画（`plan:` と `feedback:`）の項どうしの関係として決める。
エージェントが計画に先行（案）を書き、ユーザは承認の前に VS Code の承認画面で計画の図を見て、線を引き直して順序を決めてから承認する。

今の形の困りごと。

- 順序がフェーズ定義（`after`）とファイルの頭（`order`）にあるので、計画ごとに形を変えられない。並行させたいかどうかは計画ごとに違う
- 順序に関わる欄が 4 つ（`order` `after` `overlap` `requires`）あり、組み合わせの検査（`after` と `overlap` の両方、レイヤーの食い違い、循環）が要る
- ユーザが順序を見るのはフェーズ管理画面の図で、承認する計画そのものの図ではない

## 2. 変えるもの・変えないもの

### 変えるもの

| 何を | どう |
|---|---|
| `phases.yml` | `order`・`after`・`overlap`・`requires` をなくす。フェーズ定義だけにする（`kind` `title` `review` `scope` `deliverables` `agent` `when`） |
| 親の `plan:` / `feedback:` | 項に `after: [番号]`（先に閉じてレビューが済んでいるべき項）を書けるようにする |
| 待ち方の計算 | 定義の祖先ではなく、項の `after` から計算する。フィードバック計画も同じ計算にする |
| 承認時の検査 | 循環・終端・延期の引き受け手を、項の `after` で見る。終端は全体計画とフィードバック計画の両方に求める。`requires` の検査と、定義どうしの関係の検査をなくす |
| VS Code の承認画面 | 計画を持つ親（新規・改版）に図を出す。ユーザは任意の線を引け、線を変えるたびに番号が振り直される。「この順序に決める」で提案の計画を書き換えてから、ふつうに承認する |
| フェーズ管理画面 | 図と、関係の欄（`overlap` / `requires` / `after`）と `order` の選択をなくす。一覧の編集は残す |

### 変えないもの

- 待ち方の保存先は `<承認済みの置き場>/phases/<親>/workflow.yml`。承認はチケットの中身を変えない（承認は提案をバイト単位でそのまま動かす）
- `workflow.yml` の形（`order` / `waits` / `review_at`）。`waits` は今と同じく推移的に辿った全部の先行を並べる
- 判定・延期・フィードバック計画の前提は `workflow.yml` だけを読む。書くのは `--agree` だけ
- 承認済みの親で `workflow.yml` が無いもの（手で動かした承認）は一直線で読む
- レビュー準備中・レビュー待ちで止める単位は親ごと。受け入れは受け入れたフェーズとその子孫にだけ効く
- 子チケットの `predecessors`（子どうしの先行）。計画の項の先行とは別のもの
- 端末の `--agree` は文字で結果を見せる。図は出さない
- 番号の振り方（全体計画が 1 から、フィードバック計画はその続き）と、子の `phase:` が番号を指すこと

## 3. `plan:` の新しい書式

### 案（採るもの）: 項に `after: [番号]` を書く

```yaml
plan:
  - research                                  # 1。何も待たない
  - {type: design, after: [1]}                # 2
  - {type: acceptance, after: [2]}            # 3
  - {type: implement, after: [2]}             # 4。3 と並行
  - {type: implement, after: [3, 4], review: defer}   # 5。同じ定義の 2 回目も番号で指す
  - {type: docs, after: [5]}                  # 6。終端（ほかの全部を推移的に待つ）
feedback:
  - design-feedback                           # 7。何も待たない（全体計画は済んでいる）
  - skill-improve                             # 8。7 と並行
  - {type: implement-feedback, after: [7, 8]} # 9。終端。7 と 8 を受ける
```

保存される書式の不変条件。

- `after` は番号のリスト。指せるのは**自分より小さい番号だけ**。番号の並びがそのまま実行できる順（トポロジカル順）になり、循環は書けない
- `after` を書かない項は何も待たない（すぐ始まる）。線が全てで、隠れた待ちは作らない。同じ定義を 2 回置いても、`after` を書かなければ並行する
- `feedback:` の項が指せるのはフィードバック計画の番号だけ。全体計画はフィードバック計画の前提として全部済んでいるので、線にしない
- 項は今までどおり名前だけか辞書。辞書の欄は `type` `review` `after`
- 同じ番号を 2 度挙げたら 1 つにまとめ、`--agree` が warn を出す

承認画面では、並びの逆向きの線も引ける（6）。そのとき画面は番号を振り直し、「この順序に決める」で振り直した計画を提案に書き戻す。保存される `plan:` はいつも上の不変条件を満たす。

理由。

- 番号は既にフェーズの名前になっている（子の `phase:`、マーカー、`workflow.yml` の鍵、`--explain` の「待つ: 1, 2」）。同じ定義を 2 回置いても番号なら必ず 1 つに決まる。新しい名前の空間を作らない
- 「小さい番号だけ」にすると、今のコードの前提（待つのは前の番号、終端は最後の番号、延期の引き受け手は後ろの番号、順序の検査は前のフェーズを順に見る）がそのまま保てる。並びを変えたいときは番号の振り直しで吸収する
- 改版で項を足せるのは子が承認されていない番号だけなので、番号が詰め直されて先行がずれるのは、まだ始まっていない項の中だけになる
- エージェントは `--explain` の「待つ: …」をそのまま `after` に写せる（推移的に並べた先行を書いても、意味は同じ）

### 代案

| 代案 | 採らない理由 |
|---|---|
| 項に名前（`id: impl-a`）を付け、`after: [impl-a]` で指す | 読みやすく、並びを変えても指し先がずれない。だが番号と名前の 2 つの呼び名ができ、子の `phase:` は番号のまま。名前の一意の検査も要る |
| 親に辺の一覧を別に持つ（`edges: [[1, 2], [2, 3]]`） | 項を見ただけでは何を待つか分からない。項を消したときに辺が残る |
| 定義の名前で指し、2 回目は `implement#2` と書く | 番号と同じことを読みにくい形で書くだけになる |
| 保存する書式でも大きい番号を指せる（任意の DAG） | 循環の検査が要り、「終端は最後の項」「延期の先は後ろ」「前のフェーズを順に見る」の前提が崩れる。図の操作で任意の線を引けるようにし、保存の前に振り直せば同じことができる |
| 何も書かなければ一直線（今の `sequential` を既定に残す） | 書き漏れは安全側に倒れる。だが「線のない項はすぐ始まる」というユーザの決定と食い違い、図と待ち方が合わなくなる |

## 4. 待ち方の計算

`workflow.compute(parent)` の入力を、フェーズ定義から計画の項の `after` に替える。図で直した順序は、承認の前に提案の計画へ書き戻してある（6）ので、計算の入力は計画だけになる。

1. 項ごとの直接の先行は、項の `after`
2. 推移的に辿って `waits` に並べる（今の形と同じ。番号の小さい順）
3. フィードバック計画の項の `waits` は、全体計画の番号を全部と、フィードバック計画の中で辿った先行を並べる
4. 延期の引き受け手を計算する（5 の延期）
5. `order` はいつも `dag` で書く。`sequential` は前の版のファイルと、ファイルの無い承認済みの親を読むためだけに残す

フェーズ定義を読まなくなるので、「計画に読めない定義があれば一直線」の分岐は要らない（読めない定義は承認の検査が error で落とす）。
`phasetypes.PhaseTypes.order`・`ancestors`・`PhaseType.overlaps` は消える。

`workflow.yml` の鍵は、全体計画の番号に加えてフィードバック計画の番号も持つ。フィードバック計画を承認する改版で書き直す。
フィードバック計画の番号を持たない前の版のファイルは、フィードバック計画を一直線（前の番号を全部待つ）で読む。

`workflow.yml` は承認した計画からいつも計算し直せる中身になる（計画の外に順序の情報を持たない）。それでもファイルに固定するのは、手で動かした承認と前の版の扱いを今のまま保ち、判定がチケットの計画を読み直さずに済むようにするため。

## 5. 承認時の検査

`workflow.problems` に集め、全体計画とフィードバック計画に同じ規則を当てる（今はフィードバック計画の延期だけ `agree_candidates.plan_problems` が別に見ている）。

| 検査 | 全体計画 | フィードバック計画 | 重さ |
|---|---|---|---|
| `after` の形（番号の整数、範囲の中、自分より小さい、フィードバック計画の項は全体計画を指さない） | 見る | 見る | error（計画を読む段で落とす） |
| 循環 | 書けない（小さい番号だけ） | 同じ | — |
| 終端は 1 つ（最後の項が、それより前の全部の項を推移的に待つ） | 見る | 見る | error |
| 最後の項は延期できない（終端が 1 つなので、後続の無い項は最後の項だけ） | 見る | 見る | error |
| 延期の引き受け手がいる（延期した項を推移的に待つ、延期していない項のうち番号の最小） | 見る | 見る | error |
| 引き受け手にレビューがある（定義の `review` が `none` なら項の `review: mr` が要る） | 見る | 見る | error |
| 何も待たない項が 2 つ以上ある | 承認画面に「すぐ始まる: 1, 3」と出す | 同じ | 知らせるだけ |

`feedback: []`（見たうえで対応なし）は項が無いので、終端の検査に当たらない。項が 1 つなら、その項が終端。

延期の引き受け手は今の計算（後ろでこの番号を待つ、延期していない最小の番号）のまま、フィードバック計画にも当てる。
今のフィードバック計画の「次の延期していない番号」は、全部を一直線に書いたときの特別な場合になる。
フィードバックの定義が `after` を持てないという制約は、定義から順序の欄が無くなるので消える。

### フィードバック計画の合流の項

終端を求めるので、互いに独立した対応が 2 つ以上あるフィードバック計画にも、最後に 1 項で受ける形が要る。受け方は 2 つ。

- 最後に合流の項を置く（例: `design-feedback` と `skill-improve` を `implement-feedback` が受ける）
- 片方をもう片方の後ろに置く（一直線）。合流の項が要らない代わりに並行しない

出し方。

| 場所 | 出すこと |
|---|---|
| 図の初期値 | エージェントが書いた `after` をそのまま描く。最後の項に入っていない項があれば、その項と end への線を目立たせる（下の「図」） |
| 案内文 | 全体計画が終わったときの次の案内（`phase.py` の「次はフィードバック計画です」）に「最後の項がほかの全部を待つように `after` を書く。独立した対応は最後に 1 項で受けるか、一直線に並べる」を足す。承認で落ちたときの文も同じ 2 つの直し方を言う |
| 見本 | 設計の例（3 の `feedback:`）、提案の書式の文書、拡張の見本（`tour-sample.ts`）を、最後の項が受ける形にする |
| `when` | このワークスペースの `implement-feedback` の `when` に「フィードバック計画の最後に置き、ほかの対応を受ける」と書く（staging の版に入れる） |

### 改版

- 改版になるのは、提案の `plan` / `feedback`（`after` を含む）が承認済みチケットと違うときだけ。待ち方は計画から計算できるので、計算し直した待ち方とファイルの違い（今の `agree._workflow_differs`）は、前の版のファイルを持つ親のほかでは起きない。前の版のファイルを持つ親を、計画が同じでも改版の候補にするかは今のまま
- 子が承認された番号は、番号も直接の先行も変えられない。その番号の先行が今の `workflow.yml` から戻した直接の先行と違えば error。承認画面ではその点を動かせず、入る線も変えられない。振り直しもその番号を動かさない（6）
- 子が承認された番号までの延期の引き受け手を変えさせない、は今のまま
- 改版の図の初期値は提案の `after`。エージェントは改版を書くとき、今の待ち方（`--explain` の「待つ」）を写す

### 取り下げ

今は「`workflow.yml` が、承認コミットの親の提案と今の `phases.yml` から計算した待ち方と同じ」で通している。`phases.yml` は待ち方に効かなくなるので、
「承認コミットの親の提案から計算した待ち方と同じ」に縮める。図で直した順序は承認の前に提案へ書き戻してあるので、計算で再現できる。

ただし、図で直した提案は、書き戻しがコミットされないまま承認されるのが普通で、承認コミットの親には直す前の提案が残る。
すると「`doing/` の中身が承認コミットの親の提案とバイト単位で同じ」が通らず、取り下げられない。**止まる側に倒れたまま受け入れる（決定済み）。**
取り下げの文面は、`doing/` と承認コミットの親の提案の違いが `plan:` / `feedback:` の値だけのとき、「承認画面で順序を直した提案は取り下げられない。`ccnavi-ticket.sh cancel` で取り消して、提案を出し直す」と言う（ほかの違いは今の文面のまま）。

### 読むときの形の検査

`approval.read_workflow` で、`waits` の鍵と値が計画の番号の範囲にあり、値が鍵より小さいことを確かめ、外れていれば読めない待ち方として判定を止める（今の `workflow_unreadable` に乗せる）。

### `phases.yml` に残った古い欄

`order`・`after`・`overlap`・`requires` が残っていれば、読み込みは読まずに通し、`--lint` が warn で「読まない。順序は親の計画の `after` で決める」と言う。
error にしないのは、更新した直後に全部の計画の承認と `--lint` が止まらないようにするため。

## 6. 承認画面（VS Code）

置き場は今の承認のオーバーレイ（`webview/board/Approval.tsx`）。一覧に計画を持つ親（新規・改版）があれば、本文の上にその親の図を出す。全体計画とフィードバック計画は別の図にする。

### 図

- 部品はフロー定義画面の `webview/flow/Canvas.tsx` を流用する。図の中身は新しい `core/plan-graph.ts` が組む（フローの文書と同じ形の点と線）
- 点は計画の項。番号・定義の題・見る場所（`review`、延期なら「延期 → 5」）を出す
- start と end の仮ノードを描く。先行の無い項へ start から、後続の無い項から end へ線を引く。どちらも図だけのもので、保存しない。実行ファイルは知らない。この 2 種類の線は選べず、消せない（先行を全部消せば start からの線が出る）
- フィードバック計画の図では、start を「全体計画のレビュー後」、end を「親を閉じる」と名付ける
- **終端に当たらない項を目立たせる。** 実行ファイルが返す `loose`（最後の項が待たない項の番号）に入る項は、点の縁と、その項から end への線を注意の色で描き、図の下に「最後の項がこの項を待っていない。最後の項へ線を引くか、合流の項を置く」と出す。end へ 2 本以上入っていること自体も絵で読める。どの項を目立たせるかは実行ファイルが決め、画面は印を付けるだけ
- 子が承認された番号は、点を薄くし、動かせない（入る線を変えられない）
- 置き場所は start からの最長の段数で列に分け、列の中は番号順。線を変えて番号が振り直されたら、点の名札の番号だけが変わり、置き場所は動かさない。「並べ直す」で段数に合わせて並べ直す。位置は画面の状態にだけ持つ

### 線の引き直しと番号の振り直し

- 線を引く（m から n へ）＝ n が m を待つ。線を消す＝待たない。並びの逆向き（大きい番号から小さい番号へ）の線も引ける
- 引いている最中に断るのは、自分へ・start へ入る・end から出る（`flow-doc.ts` の `canConnect` の規則）と、**循環になる線**（n から m へ既に辿れる）と、子が承認された番号へ入る線。React Flow の `isValidConnection` で断るので、放しても線はできない。循環は線と点だけで決まる形の検査で、計画の良し悪しの判定ではない
- 線を変えるたびに、番号をトポロジカル順に振り直す。決まりは「先行が全部前に並んだ項のうち、元の番号がいちばん小さいものから順に番号を振る」（Kahn の方法で、同じ段の項は元の番号順を保つ）。線を変えても並びが崩れなければ、番号は変わらない
- 改版では、子が承認された番号を動かさない。空いている番号に、承認されていない項を上の決まりで詰める。詰められない線（承認された番号より前に置くことになる線）は、引いている最中に断る
- `after` の指す先は振り直した番号に付け替える。`review: defer` は項に付いたまま動く。延期の引き受け手は保存せず計算するので、振り直した番号で実行ファイルが計算し直す
- 「案に戻す」で、計画に書いてあった先行と番号に戻す

### 振り直した順序の行き先

振り直すと、計画の項の並びと `after` が変わる。承認は提案をバイト単位でそのまま動かす決まりなので、承認の段で計画を書き換えることはできない。選べる形は 3 つあった。

| 案 | 中身 | 良いところ | 困るところ |
|---|---|---|---|
| **R1（決定済み）: 承認の前に提案を書き換える** | 「この順序に決める」で、実行ファイルが `todo/` の提案の `plan:` / `feedback:` だけを振り直した形に書き換える。続けて一覧を読み直し、ユーザはふつうに承認する | 承認は今までどおりそのまま動かす。待ち方は計画から計算でき、`workflow.yml` に計画の外の情報が入らない。読む側（子の `phase:`・マーカー・`--explain`）は番号の対応表を知らなくてよい | ユーザの手で提案が書き換わる。取り下げで「承認コミットの親の提案」と合わなくなる（5 の取り下げ） |
| R2: 承認の段で書き換えて置く | `--agree --yes` が振り直した計画で `doing/` を書く | 手順が 1 回で済む | 承認がチケットの中身を変える。取り下げをバイト一致で決める仕組みと、経路によらず承認済みチケットが同じになる約束が崩れる |
| R3: 計画は変えず、番号の対応を `workflow.yml` に持つ | 計画の n 番目の項がフェーズの何番かを対応表で持つ | チケットに手が入らない | 番号で項を引く全部の箇所（`item_at`・`plan[n-1]`・子の `phase:`・マーカー・ボードの JSON・Chrome のコア）が対応表を通すことになる。計画を読んだエージェントは違う番号で子を書く |

R1 の段取り。

1. 線を変えるたびに、拡張は元の番号での直接の先行を付けて `ccnavi --agree --preview --json --order <JSON>` を呼び直す。何も書かない
2. 実行ファイルは振り直した計画で待ち方を計算・検査し、振り直した番号・本文・落とす理由・`loose` を返す。番号の振り直しの正は実行ファイル。画面は同じ決まりで先に仮の番号を出し、返ってきた番号で置き換える（同じ決まりを 2 か所に持つので、見本の表を Python と TS のテストで共有して食い違いを見張る）
3. 「この順序に決める」で `ccnavi --agree --reorder <親> --order <JSON>` を打つ。実行ファイルは提案の `plan:` / `feedback:` の値だけを差し替え、ほかのバイトは変えない。書き換えた提案は提案の検査をもう一度通す
4. 拡張は一覧を読み直し（ダイジェストは書き換えた提案で決まる）、ユーザがふつうに承認する。`--agree --yes` は `--order` を取らない
5. 承認したことをエージェントに渡す文（`approved_text`）に「計画の順序はユーザが直した。番号は承認済みチケットで読み直す」と添える

`--order` の形は、**元の番号（いま提案に書いてある番号）での直接の先行**。`{"<親>": {"plan": {"1": [], "2": [3], "3": [1]}, "feedback": {...}}}`。渡した部分は全部の番号の先行をそこから取る（書いていない番号は何も待たない）。
振り直し後の計画を渡さないのは、振り直しの正を実行ファイルの 1 か所に置くため。拡張は「どの項がどの項を待つか」だけを送る。

`--agree --reorder` は提案（エージェントも書ける置き場）を書き換えるだけで、承認はしない。エージェントが打っても、自分で書けるものを書くのと変わらないので、新しい保護は要らない。書き換えたあとの一覧はダイジェストで縛られるので、書き換えと承認の間に提案が変われば承認は止まる。

### `--agree --preview --json` に足す欄

足すだけなので版は上げない。欄が無ければ画面は図を出さない。

```json
"plans": [
  {
    "ticket": "i0001",
    "part": "plan",
    "items": [{"number": 1, "from": 1, "type": "research", "title": "調査", "review": "none", "deferred": false, "locked": false}],
    "after": {"2": [1], "3": [2]},
    "proposed": {"2": [1], "3": [2]},
    "current": {"2": [1]},
    "loose": [],
    "ready": [1]
  }
]
```

`number` は振り直した番号、`from` は元の番号、`after` は振り直した番号での直接の先行、`proposed` は提案に書いてある先行（「案に戻す」に使う）、`current` は改版のときの今の待ち方から戻した直接の先行（差分を描く）、`loose` は最後の項が待たない項、`ready` はすぐ始まる項。

### 判定の境界

画面がするのは、線と点だけで決まる形の扱い（引けない線を断る、循環を断る、仮の番号を出す、置き場所）まで。終端・延期の引き受け手・すぐ始まる項・振り直しの答えは実行ファイルが出し、画面はそれを描く。

### 承認のオーバーレイの遷移

状態を 2 つ足す。`ordering`（preview を呼び直している。承認のボタンは押せない）と `reordering`（提案を書き換えている。閉じない）。
承認を打てるのは、最後に受けた一覧が、書き換えたあとの提案で読み直したものであるとき。線を変えたまま「この順序に決める」を押していなければ、承認のボタンは「この順序に決める」に替わる。ガードとその変異テストを足す。

### 端末の `--agree` との関係

端末は今までどおり文字で見せる。待ちの一覧は、一直線かどうかに関わらず全部の番号に出し（今は `dag` のときだけ）、「すぐ始まる」と「最後の項が待たない」の行を足す。端末から順序を直す手段は作らない。直したいときは VS Code で承認するか、計画を直させる。
Chrome 拡張の承認と手で動かした承認も直す手段を持たない。Chrome は計画の `after` で計算した待ち方を書く。手で動かした承認は今と同じく `workflow.yml` を書かず、一直線で読む。

## 7. 失うものと手当て

| 失うもの | 手当て |
|---|---|
| `requires`（この定義を置くなら一緒に要る）の検査 | 判定では持たない。フェーズ定義の `when` に「受入テスト作成を先に置く」のように書く。ユーザは承認画面の図で見る。このワークスペースの `implement` と `staging` の `when` に書き足す（staging の版に入れる） |
| `overlap`（並行の許可）の意味 | 線を引かないことで同じことが書ける。失う機能は無い |
| **辺の書き漏れが並行として通る。** 今の既定（一直線）なら書き漏れは止まる側に倒れた | (1) 終端の検査で、どこにも繋がらない項と途中で切れた枝は error になる。`after` を 1 つも書かない 2 項以上の計画は必ず落ちる。(2) 承認画面の図で、start から何本出ているかと、終端に当たらない項が見える。(3) 本文に「すぐ始まる: …」を出す。(4) 計画の書き方の案内に「最初の項のほかは `after` を書く」と書く。残るのは、終端には繋がっているが途中の 1 本を書き忘れた形（例: 3 と 4 を 5 が待つが、4 が 3 を待つはずだった）。これは図で見るしかない |
| フィードバック計画で、独立した対応を並行のまま終える形 | 最後に 1 項で受けるか、一直線に並べる。合流の項は実際に子を持つフェーズなので、受ける作業（まとめの確認など）が無い計画では一直線に並べるほうが軽い |
| 承認画面で順序を直すと、提案が書き換わる | 書き換えるのは `plan:` / `feedback:` の値だけで、ほかのバイトは変えない。書き換えのあとは一覧を読み直し、ダイジェストで縛る。承認したことを渡す文で、エージェントに番号を読み直させる |
| 承認画面で順序を直した親は、取り下げられない（5 の取り下げ） | 止まる側のまま受け入れる。取り下げの文面で「取り消して出し直す」と案内する |
| 番号の振り直しの決まりを、実行ファイルと画面の 2 か所に持つ | 正は実行ファイル。画面の番号は仮で、返った番号で置き換える。見本の表をテストで共有する |
| ワークフローの形を定義で一度決めて使い回す手段 | 計画ごとに書く。エージェントは前の計画や `when` の案内を手本にする |
| 同じ定義を 2 回置いたら順に進む、の暗黙の待ち | 線で書く。図に出るので見落としにくい |
| フェーズ管理画面の図 | 一覧で見る。順序は計画の図で見る |
| 前の版の `workflow:` 欄で `dag` だったもの | 欄は今の計算と同じときだけ採る決まりなので、計画に `after` の無い古い欄は採られず一直線で読む（止まる側）。承認済みで動いている親は無いとユーザが確かめている |
| 承認画面の重さ | ボードの画面に React Flow が入り、`out/webview/board.js` が 180KB ほど増える見込み（フェーズ管理画面の図を入れたときの実測が +182KB）。フェーズ管理画面からは抜けるので、合計はほぼ変わらない |

段 1 と段 2 は独立に出せる。段 4 までは、ユーザは計画に書いた先行（案）のまま承認する（図はまだ無い）。

## 10. 迷ったところ

- 同じ定義を 2 回置いたときの暗黙の待ちを消した。「線のない項はすぐ始まる」に揃えるためで、残すと図に無い待ちが残る
- 手で動かした承認は一直線のまま。計画の `after` で読むと、ユーザが図を見ていない順序が並行として効く（緩む側）
- 振り直しの正を実行ファイルに置き、画面は仮の番号を出す形にした。画面だけで振り直すと、保存される番号を画面が決めることになる。実行ファイルだけにすると、線を変えるたびに番号が一拍遅れて変わる
- `--order` は元の番号での先行にした。振り直したあとの計画を送らせると、振り直しの決まりを画面が持つことになる
- 「この順序に決める」と「承認」の 2 段にした。書き換えと承認を 1 回にまとめると、承認がチケットの中身を変える形（R2）になる

## 11. 決まったこと

1. 承認画面の図では任意の線を引ける。循環になる線は引いている最中に断る。線を変えるたびに番号をトポロジカル順に振り直す（同じ段は元の番号順）。保存される `plan:` は「`after` は自分より小さい番号だけ」を保つ
2. 終端の検査（最後の項が、それより前の全項を待つ）は、全体計画とフィードバック計画の両方に求める
3. 承認の図の置き場は、今の承認のオーバーレイの中
4. 振り直した順序の行き先は R1（承認の前に、`--agree --reorder` が提案の `plan:` / `feedback:` の値を書き換える）
5. 図で順序を直した親の取り下げは、止まる側のまま受け入れる（W1）。取り下げの文面で「取り消して出し直す」と案内する

### 採らなかった案

- R2（承認の段で書き換えて置く）: 承認がチケットの中身を変え、取り下げのバイト一致と、経路によらず承認済みチケットが同じになる約束が崩れる
- R3（番号の対応を `workflow.yml` に持つ）: 番号で項を引く全部の箇所が対応表を通すことになり、計画を読んだエージェントが違う番号で子を書く
- W2（`--order` を `workflow.yml` に残し、取り下げで同じ振り直しを当てて比べる）: `workflow.yml` の形が変わり、C1・Chrome の見本まで直す。取り下げのために持つ情報としては重い
- W3（書き換えた提案を承認の前にコミットする）: 拡張か保護された `ccnavi-push-approved.sh` にコミットの段が増え、承認の段取りが複雑になる
