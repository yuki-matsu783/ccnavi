# フェーズの順序を親の計画で決める（設計草案）

採用前の草案。ADR の草案は同じ置き場の `0109-plan-order-on-plan-items.md`。

## 1. 目的

フェーズの順序（どのフェーズがどれを待つか）を、`phases.yml` のフェーズ定義から外し、親チケットの計画（`plan:` と `feedback:`）の項どうしの関係として決める。
エージェントが計画に先行（案）を書き、ユーザは承認の前に VS Code のワークフロー編集タブで計画の図の線を引き直して順序を決め、承認画面で同じ図を見て承認する。

今の形の困りごと。

- 順序がフェーズ定義（`after`）とファイルの頭（`order`）にあるので、計画ごとに形を変えられない。並行させたいかどうかは計画ごとに違う
- 順序に関わる欄が 4 つ（`order` `after` `overlap` `requires`）あり、組み合わせの検査（`after` と `overlap` の両方、レイヤーの食い違い、循環）が要る
- ユーザが順序を見るのはフェーズ管理画面の図で、承認する計画そのものの図ではない

## 2. 変えるもの・変えないもの

### 変えるもの

| 何を | どう |
|---|---|
| 親の `phases:`（新） | 親の frontmatter に、計画が使う定義だけのコピーを持たせる。`--agree` が `phases.yml` の同じ名前の定義と同じかを確かめる。承認のあとの判定は `phases:` を読み、`phases.yml` を読まない（5b） |
| `phases.yml` | `order`・`after`・`overlap`・`requires` をなくす。フェーズ定義だけにする（`kind` `title` `review` `scope` `deliverables` `agent` `when`） |
| 親の `plan:` / `feedback:` | 項に `after: [番号]`（先に閉じてレビューが済んでいるべき項）を書けるようにする |
| 待ち方の計算 | 定義の祖先ではなく、項の `after` から計算する。フィードバック計画も同じ計算にする |
| 待ち方の持ち方 | `phases/<親>/workflow.yml` を廃止する。判定は承認済みチケットの `plan:` / `feedback:` から都度計算する（4） |
| 手で動かした承認 | 一直線ではなく、計画の `after` で読む。代わりに判定の側で計画の検査を当て、壊れた計画を止める（5） |
| 改版の見つけ方・取り下げ | 改版は計画の違いだけで見つける。取り下げはチケットのバイト一致だけで決める（5） |
| 承認時の検査 | 循環・終端・延期の引き受け手を、項の `after` で見る。終端は全体計画とフィードバック計画の両方に求める。`requires` の検査と、定義どうしの関係の検査をなくす |
| VS Code のワークフロー編集タブ（新） | 計画を持つ親の提案（新規・改版）ごとに 1 枚。ユーザは任意の線を引け、線を変えるたびに番号が振り直される。保存（「この順序に決める」）で実行ファイルが提案の計画を書き換える |
| VS Code の承認画面 | 計画を持つ親に同じ図を読むだけで出し、タブへ移る入口を置く。承認はふつうに行う |
| フェーズ管理画面 | 図と、関係の欄（`overlap` / `requires` / `after`）と `order` の選択をなくす。一覧の編集は残す |

### 変えないもの

- 承認はチケットの中身を変えない。新規の承認は提案をバイト単位でそのまま動かすだけで、待ち方のファイルが無くなるので書き足すものも無い。改版は今までどおり承認済みチケットを書き直し、差し替えるのは計画（`plan:` / `feedback:`）と `phases:`
- 判定が読む待ち方の型（`ticket_model.Workflow` の `waits` / `review_at`）。読む側（`Ticket.review_at`・`covered_by`、`phase.py`、受け入れの適用範囲、`review.py`）は読み方を変えず、一直線の枝とフィードバック計画の別扱いだけを外す。`waits` は今と同じく推移的に辿った全部の先行を並べる
- `allow:`。親の `allow` / `ask` / `deny`、子の範囲、`scope: inherit`（親の `allow` そのもの）は今のまま。子の範囲は「子 ⊆ 定義の `scope` ⊆ 親の `allow`」で、定義の `scope` が親に固定したもの（5b）になるだけ
- レビュー準備中・レビュー待ちで止める単位は親ごと。受け入れは受け入れたフェーズとその子孫にだけ効く
- 子チケットの `predecessors`（子どうしの先行）。計画の項の先行とは別のもの
- 端末の `--agree` は文字で結果を見せる。図は出さない
- 番号の振り方（全体計画が 1 から、フィードバック計画はその続き）と、子の `phase:` が番号を指すこと

## 3. `plan:` の新しい書式

### 案（採るもの）: 項に `after: [番号]` を書く

```yaml
plan:
  - research                                  # 1。何も待たない
  - {type: design, after: [1]}                # 2
  - {type: acceptance, after: [2]}            # 3
  - {type: implement, after: [2]}             # 4。3 と並行
  - {type: implement, after: [3, 4], review: defer}   # 5。同じ定義の 2 回目も番号で指す
  - {type: docs, after: [5]}                  # 6。終端（ほかの全部を推移的に待つ）
feedback:
  - design-feedback                           # 7。何も待たない（全体計画は済んでいる）
  - skill-improve                             # 8。7 と並行
  - {type: implement-feedback, after: [7, 8]} # 9。終端。7 と 8 を受ける
```

保存される書式の不変条件。

- `after` は番号のリスト。指せるのは**自分より小さい番号だけ**。番号の並びがそのまま実行できる順（トポロジカル順）になり、循環は書けない
- `after` を書かない項は何も待たない（すぐ始まる）。線が全てで、隠れた待ちは作らない。同じ定義を 2 回置いても、`after` を書かなければ並行する
- `feedback:` の項が指せるのはフィードバック計画の番号だけ。全体計画はフィードバック計画の前提として全部済んでいるので、線にしない
- 項は今までどおり名前だけか辞書。辞書の欄は `type` `review` `after`
- 同じ番号を 2 度挙げたら 1 つにまとめ、`--agree` が warn を出す

ワークフロー編集タブでは、並びの逆向きの線も引ける（6）。そのときタブは番号を振り直し、保存で振り直した計画を提案に書き戻す。保存される `plan:` はいつも上の不変条件を満たす。

理由。

- 番号は既にフェーズの名前になっている（子の `phase:`、マーカー、`--explain` の「待つ: 1, 2」）。同じ定義を 2 回置いても番号なら必ず 1 つに決まる。新しい名前の空間を作らない
- 「小さい番号だけ」にすると、今のコードの前提（待つのは前の番号、終端は最後の番号、延期の引き受け手は後ろの番号、順序の検査は前のフェーズを順に見る）がそのまま保てる。並びを変えたいときは番号の振り直しで吸収する
- 改版で項を足せるのは子が承認されていない番号だけなので、番号が詰め直されて先行がずれるのは、まだ始まっていない項の中だけになる
- エージェントは `--explain` の「待つ: …」をそのまま `after` に写せる（推移的に並べた先行を書いても、意味は同じ。改版の比べ方も推移的な待ちで比べるので、写しても違いにならない）

### 代案

| 代案 | 採らない理由 |
|---|---|
| 項に名前（`id: impl-a`）を付け、`after: [impl-a]` で指す | 読みやすく、並びを変えても指し先がずれない。だが番号と名前の 2 つの呼び名ができ、子の `phase:` は番号のまま。名前の一意の検査も要る |
| 親に辺の一覧を別に持つ（`edges: [[1, 2], [2, 3]]`） | 項を見ただけでは何を待つか分からない。項を消したときに辺が残る |
| 定義の名前で指し、2 回目は `implement#2` と書く | 番号と同じことを読みにくい形で書くだけになる |
| 保存する書式でも大きい番号を指せる（任意の DAG） | 循環の検査が要り、「終端は最後の項」「延期の先は後ろ」「前のフェーズを順に見る」の前提が崩れる。図の操作で任意の線を引けるようにし、保存の前に振り直せば同じことができる |
| 何も書かなければ一直線（今の `sequential` を既定に残す） | 書き漏れは安全側に倒れる。だが「線のない項はすぐ始まる」というユーザの決定と食い違い、図と待ち方が合わなくなる |

## 4. 待ち方の計算

`workflow.compute(parent)` の入力を、フェーズ定義から計画の項の `after` に替える。タブで直した順序は、承認の前に提案の計画へ書き戻してある（6）ので、計算の入力は計画だけになる。

1. 項ごとの直接の先行は、項の `after`
2. 推移的に辿って `waits` に並べる（今の形と同じ。番号の小さい順）
3. フィードバック計画の項の `waits` は、全体計画の番号を全部と、フィードバック計画の中で辿った先行を並べる
4. 延期の引き受け手を計算する（5 の延期）
5. `order` はいつも `dag`。一直線（`sequential`）の読み方は使われなくなるので、`phase.py` の一直線の枝（次の案内など）と `workflow.effective` の分岐は消す

フェーズ定義を読まなくなるので、「計画に読めない定義があれば一直線」の分岐は要らない（読めない定義は承認の検査が error で落とす）。
`phasetypes.PhaseTypes.order`・`ancestors`・`PhaseType.overlaps` は消える。

### 計算の入力

| 出すもの | 入力 | 計画の外の入力 |
|---|---|---|
| `waits` | 各項の `after`（推移的に辿る）。フィードバック計画の項は全体計画の番号を全部足す | 無い |
| `review_at` | 各項の `review: defer` と `waits` | 無い（今の延期の引き受け手の計算も定義を読まない） |
| `order` | いつも `dag` | 無い |

- 定義の `review` と `kind` は、検査（引き受け手にレビューがあるか、どちらの計画に置けるか）でだけ読み、計算には入らない。承認のあとは親の `phases:` から読む（5b）
- 図で直した順序は、承認の前に提案へ書き戻すので、承認済みチケットの計画に含まれる
- チケットの状態は入力にならない。提案（`todo/`）も承認済みも同じ関数で計算する

### `workflow.yml` を廃止する

上の表のとおり、待ち方は承認済みチケットの計画だけから計算し直せる。ファイルを持つ理由だった「`phases.yml` を後で直しても、進行中の親の待ちを変えない」は、`phases.yml` が計算の入力でなくなったことで消えた。承認済みチケットの計画は承認済みの置き場にあり、変えられるのは改版（`--agree`）とユーザの手だけなので、計算の元も固定されている。

- **`Ticket.workflow` の型と読む側はそのまま残し、入れ方だけを変える。** `approval.load_copy` がファイルを読む代わりに `workflow.compute(ticket)` の結果を入れる。提案も同じ関数で入る
- 外すもの: `workflow.yml` の読み書き（`approval.read_workflow`・`write_workflow`・`workflow_path`・`workflow_bytes`、`approval_ops.admit` と `agree_digest.revise_copy` の書き込みと戻し）、ダイジェストに足していた待ち方のバイト列、`agree._workflow_differs`、前の版の `workflow:` 欄を見比べる `approval.settle_old_workflows`、取り下げでのファイルの比較と削除、C1 の名前の一覧の `workflow.yml`、`--lint` の残ったファイルの warn、`status` の「ファイルが無いので一直線」の warn
- 提案と承認済みチケットにある `workflow:` 欄は読まない。今までどおり `--agree`・`--lint`・判定が error にする（手で書いた欄が効くと読み手に思わせない）
- 残ったファイルは読まない。`--lint` が「読まないファイル」と warn で言い、ユーザが消す（承認済みの置き場はエージェントが書けない）。承認済みで進んでいる親は無いので、移行の手当ては要らない
- 性能: 1 親あたり項数 n に対して O(n²)（推移的に辿る）。n はふつう 10 未満。チケットを読むときに 1 回計算して `Ticket` に持たせて使い回す。ファイルを 1 本読む I/O と YAML の読みが減るので、遅くはならない見込み

### ファイルを残す形との比較

| 観点 | 残す | 廃止する（採る） |
|---|---|---|
| 情報の持ち場 | 計画と、その写しのファイルの 2 か所 | 計画の 1 か所 |
| 食い違いが起きる経路 | 改版で片方だけ書けたとき（戻す処理で防いでいた）、親が消えてファイルだけ残ったとき、前の版の欄 | 無い。代わりに、計算の決まりを後の版で直すと進行中の親の待ちが変わる（7） |
| 手で動かした承認 | ファイルが無いので一直線 | 計画の `after` で読む（緩む側。7） |
| 取り下げ | チケットのバイト一致と、ファイルと計算の一致。ファイルも消す | チケットのバイト一致だけ |
| 改版の見つけ方 | 計画の違いと、ファイルとの違い | 計画の違いだけ |
| C1・Chrome・`--lint` | ファイルを運ぶ・消す・孤児を言う扱いが要る | 要らない |
| 承認がチケットの中身を変えない | 保たれる | 保たれる。承認で書くものは提案の移動だけになる |

## 5. 承認時の検査

`workflow.problems` に集め、全体計画とフィードバック計画に同じ規則を当てる（今はフィードバック計画の延期だけ `agree_candidates.plan_problems` が別に見ている）。

| 検査 | 全体計画 | フィードバック計画 | 重さ |
|---|---|---|---|
| `after` の形（番号の整数、範囲の中、自分より小さい、フィードバック計画の項は全体計画を指さない） | 見る | 見る | error（読む段では落とさない。5 の「手で動かした承認」） |
| 循環 | 書けない（小さい番号だけ） | 同じ | — |
| 終端は 1 つ（最後の項が、それより前の全部の項を推移的に待つ） | 見る | 見る | error |
| 最後の項は延期できない（終端が 1 つなので、後続の無い項は最後の項だけ） | 見る | 見る | error |
| 延期の引き受け手がいる（延期した項を推移的に待つ、延期していない項のうち番号の最小） | 見る | 見る | error |
| 引き受け手にレビューがある（定義の `review` が `none` なら項の `review: mr` が要る） | 見る | 見る | error |
| 何も待たない項が 2 つ以上ある | 承認画面に「すぐ始まる: 1, 3」と出す | 同じ | 知らせるだけ |

`feedback: []`（見たうえで対応なし）は項が無いので、終端の検査に当たらない。項が 1 つなら、その項が終端。

延期の引き受け手は今の計算（後ろでこの番号を待つ、延期していない最小の番号）のまま、フィードバック計画にも当てる。
今のフィードバック計画の「次の延期していない番号」は、全部を一直線に書いたときの特別な場合になる。
フィードバックの定義が `after` を持てないという制約は、定義から順序の欄が無くなるので消える。

### フィードバック計画の合流の項

終端を求めるので、互いに独立した対応が 2 つ以上あるフィードバック計画にも、最後に 1 項で受ける形が要る。受け方は 2 つ。

- 最後に合流の項を置く（例: `design-feedback` と `skill-improve` を `implement-feedback` が受ける）
- 片方をもう片方の後ろに置く（一直線）。合流の項が要らない代わりに並行しない

出し方。

| 場所 | 出すこと |
|---|---|
| 図の初期値 | エージェントが書いた `after` をそのまま描く。最後の項に入っていない項があれば、その項と end への線を目立たせる（下の「図」） |
| 案内文 | 全体計画が終わったときの次の案内（`phase.py` の「次はフィードバック計画です」）に「最後の項がほかの全部を待つように `after` を書く。独立した対応は最後に 1 項で受けるか、一直線に並べる」を足す。承認で落ちたときの文も同じ 2 つの直し方を言う |
| 見本 | 設計の例（3 の `feedback:`）、提案の書式の文書、拡張の見本（`tour-sample.ts`）を、最後の項が受ける形にする |
| `when` | このワークスペースの `implement-feedback` の `when` に「フィードバック計画の最後に置き、ほかの対応を受ける」と書く（staging の版に入れる） |

### 改版

- 改版になるのは、提案の計画か `phases:` が承認済みチケットと違うとき。待ち方は計画から決まるので、待ち方だけの改版は無い
  - 計画が違うかは、項ごとの「定義・`review`・推移的に辿った待ち（`compute` の `waits`）」の並びで比べる（`approval.plan_differs` をこの形に替える）。`PlanItem.__eq__` は使わず、`after` も入れない。`after: [2]` と、`--explain` の「待つ: 1, 2」を写した `after: [1, 2]` は同じ待ちなので、違いにしない
  - `phases:` が違うかは、定義を読んだ形で比べる。計画が同じで `phases:` だけが違う提案も改版の候補にする（`--fill-phases` で今の `phases.yml` に揃えた提案を出せるように。固定した番号が使う定義は変えられない規則のまま）
- **錠は番号ごとにする（決定済み）。** 子が承認された（開いていても閉じていても）番号の集合を「固定した番号」とし、その番号の項は定義・`review`・番号を変えられない。今の「子が承認されたいちばん後ろの番号までの前置を丸ごと固定する」（`agree_candidates.revision_problems` の `plan[:frozen]` と、延期の検査の `n <= frozen`）を置き換える
- 固定した番号の待ちは、**推移的に辿った待ち**（`compute` の `waits`）で比べる。承認済みチケットの計画から計算した `waits[n]` と、提案から計算した `waits[n]` が同じでなければ error。直接の先行で比べないのは、エージェントが「待つ: …」（推移的に並べたもの）を写しても、直接の先行だけを書いても、同じ意味なら通すため。この比較も `__eq__` は使わない
- 延期の引き受け手を変えさせない検査は、**引き受け手が固定した番号かどうか**で見る。承認済みの引き受け手か、提案の引き受け手のどちらかが固定した番号なら、両方が同じ固定した番号でなければ error（固定した番号は振り直しで動かないので、番号で比べてよい）。両方が固定していない番号なら、番号が変わっても通す。まだ始まっていない項の間で引き受け手が入れ替わるだけで、済んだレビューが延期した作業を引き受けたことにはならないため
  - 例: 承認済みの a(1, 延期, 子あり)・x(2, 先行なし)・b(3, `after: [1, 2]`) の引き受け手は b(3)。タブで x→b を消して b→x を引くと b が 2 番、x が 3 番になり、引き受け手は 3 番から 2 番に変わるが、どちらも b で固定していない番号なので通る。番号だけで比べると、ここで落ちていた
- `--plan-order <親> --json --order` も改版の錠（固定した番号の定義・`review`・待ち・引き受け手）を当て、落ちる形は保存の前に「改版で通らない」と返す。タブは保存させない
- `--agree` を通った親では、固定した番号の先行は固定した番号だけになる（子が承認されたフェーズは、待つフェーズが済んでから承認されている）。なので振り直しは固定した番号を動かさずに、空いた番号へ承認されていない項を詰められる。詰められないとき（空いた番号を埋める項が無い）は、`--plan-order <親> --json --order` がその線を「詰められない」と返し、タブは線を引く前の形に戻す（判定は実行ファイル。6）
- **固定した番号の先行がすべて固定した番号であることを確かめる。** 子を手で動かして承認した親では、固定した番号が固定していない番号を待つことがある（固定した 3 の待ちが [1, 2] で、2 に子が無い）。このとき番号だけで待ちを比べると、2 番の項を別の定義に入れ替える改版が通ってしまう。固定していない先行を持つ固定した番号は、先行を番号ではなく項の同一性（その番号の定義と `review`）でも比べ、違えば error
- **フィードバック計画があれば（`feedback:` が None でなければ）、全体計画を変える改版は止める。**「全体計画を変えたか」も上の並び（定義・`review`・推移的な待ち）で比べる。`after` の書き方の違いだけでは止めない。 フィードバック計画の番号は全体計画の続きなので、全体計画に項を足すとフィードバック計画の番号と `after` がずれる。フィードバック計画は全体計画の最後のレビューが済んでから立てるので、そのあとに全体計画を変える場面は無い
- 改版の画面の差分は、承認済みチケットの計画から計算した待ち方と、提案から計算した待ち方を比べて出す
- 改版の図の初期値は提案の `after`。エージェントは改版を書くとき、今の待ち方（`--explain` の「待つ」）を写してよい（推移的に並べても違いにならない）
- **改版の書き込み（`agree_digest.revised_front`）は、計画に加えて `phases:` も提案の値に差し替える。** 今は承認済みチケットの frontmatter を写して `plan` と `feedback` だけを差し替えるので、そのままだと改版の `phases:` が捨てられる。フィードバック計画の立案は必ず改版なので、承認したとたん「項が `phases:` に無い定義名を使う」で親と子が全部止まる。`revision_problems` の「変えてよい欄」に `phases:` を足し、5b の規則で検査する。ダイジェストに入れる書く中身（`agree_digest.carried`）と、承認画面の「`phases:` の差分」は、`revised_front` が実際に書くものから組む

例。承認済みの計画が a(1)・b(2)・c(3)・d(4) で、b と c は a だけを待ち、d は b と c を待つ（d が終端）。1 と 3 に子があり、2 と 4 には無い（c は a だけを待つので、b が始まる前に承認できる）。改版で e(5) を足す（e は a を待つ）。

| 操作 | 今の錠（前置） | 番号ごとの錠 |
|---|---|---|
| e を足し、d が e も待つようにする | 通る（1〜3 は同じ） | 通る（固定した 1・3 の定義・`review`・待ちは同じ） |
| タブで e→b の線を引く（b が e を待つ） | — | b は e より後ろに要る。固定した 1・3 は動かさず、空いた 2・4・5 に、先行の済んだ順で e・b・d を詰める。e が 2 番、b が 4 番、d が 5 番になる。`plan:` は a・e・c・b・d になり、todo/ にある b の子の提案は `phase: 2` が `4` に、識別子が `<親>-02-<連番>` から `<親>-04-<連番>` に、d の子の提案は `phase: 4` が `5` に、識別子が `-04-` から `-05-` に付け替わる（6） |
| 振り直した提案を承認する | 2 番の項が b から e に変わるので止まる | 1・3 の定義・`review`・待ちが同じなので通る |
| タブで e→a の線を引く（a が e を待つ） | — | a は固定した番号なので、入る線は引いている最中に断る |

番号ごとの錠は、前置の錠より通るものが増える（上の例で、子の無い 2 番を変えられる）。並行に進むフェーズでは、後ろの番号に子があっても前の番号がまだ始まっていないことがあり、その項を直せるようにするため。

### 取り下げ

取り下げは「`doing/` の中身が承認コミットの親の提案とバイト単位で同じ」だけで決める。待ち方は `doing/` の計画から決まるので、待ち方を別に比べる段も、ファイルを一緒に消す段も要らない。

図で順序を直した提案は、書き戻し（`--plan-order --write`）がコミットされないまま承認されるのが普通で、承認コミットの親には直す前の提案が残る。すると `doing/`（直した後）と承認コミットの親の提案（直す前）のバイト列が違い、取り下げられない。原因はチケットのバイト列の違いで、待ち方のファイルとは関係が無いので、ファイルを廃止してもこの結果は変わらない。**止まる側に倒れたまま受け入れる（決定済み）。** 書き戻しで `phase:` を書き換えた子の提案も、承認したあとは同じ理由で取り下げられない。
取り下げの文面は、違いが `plan:` / `feedback:` / `phases:` の値（子なら `phase:` の値）だけのとき、「承認の前にワークフロー編集タブか `--fill-phases` で書き換えた提案は取り下げられない。`ccnavi-ticket.sh cancel` で取り消して、提案を出し直す」と言う。`--fill-phases` で差し込んだ `phases:` をコミットしないまま承認した場合も同じ理由で止まるので、条件に `phases:` を入れる（ほかの違いは今の文面のまま）。

**前の版の形（`ccnavi_approved` を持つ）の親は、取り下げを一律に止める。** 今は、前の版の形の改版を見分ける印が待ち方のファイルの有無だけ（`hook/core_withdraw.py` の 169〜177 行付近）で、改版は記録の欄を残したまま計画を書き換える（`agree_digest.revised_front`）。ファイルを廃止すると、改版した前の版の親を、改版の前の提案へ戻せてしまう。前の版の形の親で進んでいるものは無いので、一律に止めても困らない。前の版の形の子は今の条件（記録の欄）のまま。

### 手で動かした承認と、判定の側の検査

`--agree` を通さずに承認済みの置き場へ動かした親も、計画の `after` を信じて並行で読む。ユーザが中身を見て動かしたので、`after` も承認したと読む。「`after` の無い 2 項以上は一直線」のような特例は置かない。

**親の `phases:` も同じく信じる（決定済み）。** 手で動かした承認では `--agree` の検査（`phases:` が `phases.yml` と同じか）が働かないので、エージェントが書いた `phases:` がそのまま効く。判定の側で `phases:` と `phases.yml` を合わせる処理は入れない（判定は `phases.yml` を読まない）。`--lint` は食い違いを warn で言う。

- 信じてよい理由: 承認を本物とするのは置き場で、承認済みの置き場へ動かすのはユーザだけ（エージェントの書き込みは組み込みの止めとルールが止める）。ユーザが自分で動かした＝中身を承認した、と読む。`after` を信じるのと同じ向き
- 前の版では、手で書いた `workflow:` 欄を承認済みの待ち方として効かせなかった。欄を読むと、手で書いた値が判定と手で動かした承認に効いてしまう（ユーザが承認していない待ち方を効かせられる）からで、待ち方をファイルに固定したのはこの穴を塞ぐためでもあった。`phases:` では、この「手で書いた欄を効かせない」方針を採らない。手で動かした承認では、置き場へ動かしたユーザが中身を承認したと読み、`phases:` を効かせる
- 理由の弱いところ: ユーザは承認の前に `phases:` の中身を `phases.yml` と見比べるとは限らない。手で動かすときは承認画面の「この親が使う定義」「使わない定義」の区分も、`phases.yml` との一致の検査も見ない。エージェントが `review: none` や広い `scope` を書いた `phases:` を、ユーザが気づかずに動かせば、その定義が効く。`--agree` を通る承認ではこの穴は無い

その代わり、`--agree` の検査を通っていない計画が壊れていても判定が進まないように、**判定の側で、承認済みチケットだけを読んで済む検査を当てる。** 定義は親の `phases:`（5b）から読むので、`phases.yml` は読まない。

| 検査 | 判定の側 | `--lint` |
|---|---|---|
| `after` の形（番号の整数・範囲の中・自分より小さい・フィードバック計画の項は全体計画を指さない） | 当てる | error |
| 終端は 1 つ（全体計画・フィードバック計画） | 当てる | error |
| 最後の項は延期できない、延期の引き受け手がいる | 当てる | error |
| 計画を持つのに `phases:` が無い、項が `phases:` に無い定義名を使う | 当てる | error |
| `phases:` の定義の形、`kind` が置いた計画と合う、引き受け手にレビューがある（`phases:` の `review` と項の `review: mr`） | 当てる | error |
| `phases:` の定義が今の `phases.yml` と違う | 当てない（進行中の親には効かないのが決まり） | warn |
| `phases:` に使われていない定義がある | 当てない | warn |

前の決め方（定義の有無・`kind`・`review` は `--lint` の warn）は、判定が `phases.yml` を読むと承認のあとの定義の変更で進行中の親が止まるのを避けるためだった。親の `phases:` を読むならその心配は無いので、判定の範囲を広げる（5b の「判定の側で見る範囲」）。

- **計画と定義の誤りは、チケットを読む段では落とさない。** 読む段で落とすと、承認済みチケット全体が読めずに索引に入らず、判定（`hook/judge.py` の `ticket_verdict` は `ticket is None` で空の答えを返す）がそのチケットを知らないまま範囲を当てない。読む段で落とさないものは次のとおりで、どれも `blocking_problems` で `blocked` の理由にする
  - `after` の形の誤り
  - 最後の項の延期（今は `ticket._plan` が読む段で落としている。122〜126 行付近）
  - 子に書いた `phases:`
  - 親の `phases:` の定義の形の誤り
- **形の誤った `after` で例外を出さない。** リストでない、`"2"`、`1.5`、`[[1]]`、`0`、`-1`、自分を指す、桁の大きな整数、`[true]`（bool は整数と見なさない）のどれでも、読み・`compute`・`review_at`・`lines` が例外を出すと hook が 0 以外で終わり、判定が読まれない。`PlanItem.after` には正しい整数（1 以上、自分より小さい、計画の範囲の中）だけを残し、誤りは `PlanItem.after_errors` に元の値と理由で持たせる。`compute` は誤った線を無視し、`workflow.problems` が `after_errors` を error で言う。崩した入力を並べたテストを足す
- 親は `approval_checks.blocking_problems` で `blocked` の理由を持ち、範囲を当てずに止まる（`phase_scope.scope_verdict`）。今の判定が止めるのは「範囲が決まらない構造の誤り」だけで、`blocking_problems` の説明（705〜711 行付近）は「計画の形と順序は範囲に影響しないので入れない」と書いている。計画と定義が親の範囲（定義の `scope`）を決めるようになり、壊れた計画では子の範囲が決まらないので、止める対象に入る。説明を書き直す
- 先行の検査を判定に入れる案は「承認のあとに先行が戻されると、作業中の子が突然どこにも書けなくなる」として採らなかった。今回止めるのは承認済みチケットそのものの形の誤りで、承認のあとに外の何かが動いて起きるものではない（直すのはユーザが承認済みチケットを直すときか、手で動かしたときだけ）。作業中の子が外の変化で突然止まる形は起きない
- **子は、親の計画に error があれば止まる（決定済み）。** `approval_checks.child_problems` に「親の計画が壊れている」を足す。`child_problems` は承認（`agree_candidates.validate`）と判定（`blocking_problems`）の両方が引くので、子の `--agree`・着手・書き込みが同じ答えで止まる。子の承認の順序の検査（`phase.order_problems`）は親の待ちを読む前に同じ理由で落とす（壊れた待ちで順序を数えない）
- 子の承認（`agree_candidates.validate` と、定義を引く `types_for` / `phase.load_types`）と、子の順序の検査（`phase.order_problems` に渡す定義）も、親が承認済みならその `phase_types`、親が同じ承認で通る提案ならその提案の `phases:` から引く。今は `phases.yml` から引いているので、承認のあとに `phases.yml` から定義を消す・名前を変えると、進行中の親の子の承認が落ちる
- 判定の側の検査は `phases.yml` を読まない（定義は親の `phases:` から）ので、`approval_checks.mark_blocked(conf, kept)` に `root` や定義を渡す必要は無い（今の引数のままでよい）
- 承認のあとに `phases.yml` の定義を直しても、進行中の親は判定で止まらない。`--lint` が warn で言う
- `--lint` と `status` も同じ文で言う

### `phases.yml` に残った古い欄

`order`・`after`・`overlap`・`requires` が残っていれば、読み込みは読まずに通し、`--lint` が warn で「読まない。順序は親の計画の `after` で決める」と言う。
error にしないのは、更新した直後に全部の計画の承認と `--lint` が止まらないようにするため。

## 5b. 親に固定するフェーズ定義（`phases:`）

親チケットの frontmatter に、`plan:` / `feedback:` が使うフェーズ定義**だけ**のコピーを `phases:` として持たせる。`phases.yml` の全定義の写しではない（このワークスペースなら、`research` を飛ばす親の `phases:` に `research` は入らず、`staging` を使わない親に `staging` は入らない）。承認したときの定義が親に固定され、承認のあとの判定は `phases.yml` を読まない。
**`allow:` は変えない。** 親の `allow` / `ask` / `deny`、子の範囲、`scope: inherit`（親の `allow` そのもの）は今のまま。

### 衝突する決定と、その解き方

| 決定 | 何とぶつかるか | 解き方 |
|---|---|---|
| 定義はユーザが持つ設定で、エージェントは書き換えない（エージェントが定義を書けると、レビュー不要の定義を作ってから使える） | 提案を書くのはエージェントなので、`phases:` もエージェントが書く | `--agree` を通る承認では、`--agree` が `phases:` に書いた各定義が**承認したときの `phases.yml` の同じ名前の定義と同じ**ことを確かめ、違えば error。エージェントが値を変えても通らない。手で動かした承認ではこの検査は働かず、`phases:` がそのまま効く（5 の「手で動かした承認」。塞がない）。中身を決めるのは今までどおり `phases.yml`（ユーザの設定）で、`phases:` はその写し |
| 承認はチケットの中身を変えない。欄を書き足さない（取り下げを中身の一致で決め、経路によらず承認済みチケットを同じにするため） | 承認のときに定義を書き足すと中身が変わる | 定義は承認の**前**に提案へ書いておく（下の補助のフラグ）。承認はバイト列を動かすだけ |
| 判定は承認済みでも定義を毎回 `phases.yml` から読む（`phase.phases_of`、`judge.ticket_verdict`、`ops_close.deliverables_missing`、`subagent`、`events`） | 固定したコピーと `phases.yml` の 2 つの答えができる | 承認済みの親（と、その子の判定）は `phases:` だけを読み、`phases.yml` は読まない。`phases.yml` を読むのは、提案の検査と `--lint` の食い違いの warn だけ |

### 書式

```yaml
phases:                      # 親だけ。plan: / feedback: が使う定義のコピー
  research:
    kind: work
    title: 調査
    review: none
    scope: ["wip/research/*"]
    deliverables: ["wip/research/summary.md"]
    when: 既存の振る舞いや依存が分からないとき
  design: {kind: work, title: 設計, review: mr, scope: ["wip/design/*", "docs/*"]}
plan:
  - research
  - {type: design, after: [1]}
```

- 欄名は `phases:`。中身は、この親が使う定義の id をキーにした辞書で、各定義の欄は `phases.yml` と同じ（`kind` `title` `review` `scope` `deliverables` `agent` `when`）。読むのは `phasetypes` の定義の読み（今の `_one`）と同じ関数で、形の誤りも同じ文で言う
- `plan:` / `feedback:` の項の `type` は `phases:` のキーを指す。項の書き方は変えない
- `ticket_model.Ticket` には生の辞書 `phases_raw` を足し、`ticket.py` はそれだけを読む。定義にした `phase_types` は work 層（`approval.load_copy` / `scan_all`、`agree_candidates`、`--plan-order`）が入れる。`Ticket` の欄の型は前方参照の文字列で書き、state 層から compose 層を読み込まない（型注釈でも層の検査に捕まるため）
- 子（`parent:` を持つ）に `phases:` があれば error。子の `phase:`（番号）と名前が似ているので、取り違えを読む段で止める
- 計画を持たない親に `phases:` があれば、全部が「使われていない定義」として warn になる（下の表）

### 承認での検査（`--agree`）

| 検査 | 重さ |
|---|---|
| `plan:` / `feedback:` の項が、`phases:` に無い定義名を使う（使う定義は `phases:` に明記する） | error |
| `phases:` に書いた各定義が、承認したときの親の `project:` が指す `phases.yml` の同じ名前の定義と同じ（読んだ形で比べる。YAML の書き方・キーの順・`inherit` の書き方の違いは同じとみなす） | error |
| `phases:` に書いた定義の名前が `phases.yml` に無い | error |
| 定義の形（`phasetypes` の検査。`kind` と置いた計画、`review` の値、`scope` の glob） | error |
| `phases.yml` にあって `phases:` に無い定義 | 何も言わない（この親では使わないだけ） |
| `phases:` にあって、`plan:` / `feedback:` のどの項も使っていない定義 | warn。承認画面に「使われていない定義」と出す |

使われていない定義を warn にする理由: 判定はどの項からも引かないので、残っていても範囲・見る場所・成果物は変わらない。error にすると、計画の項を消した・振り直したあとの消し忘れで承認が止まり、補助のフラグを打ち直すだけの往復が増える。ユーザが承認画面で読めれば足りる。補助のフラグは使われていない定義を消すので、ふつうは残らない。

比べるのは読んだ形なので、エージェントは書式を整えても落ちない。`phases.yml` に残った古い欄（`order` `after` `overlap` `requires`）は比べない（読まない欄なので、コピーに書かない）。

### コピーを作る手段

| 案 | 中身 | 良いところ | 困るところ |
|---|---|---|---|
| **補助のフラグ（決定済み）** | `ccnavi --plan-order <親> --fill-phases`。提案の `plan:` / `feedback:` の項が使う定義だけを `phases.yml` から読み、`phases:` の値をその定義の集まりに差し替える（無ければ足す。項が使わない定義は外す）。ほかのバイトは変えない（書く前に全文を読み直し、`phases` のほかの欄が読んだ形で元と同じことを確かめる。6 の「子の提案の追従」と同じ）。`--plan-order` と同じく `--agree` の外の独立したフラグで、エージェントが打ってよい | 写し間違いが起きない。`phases.yml` を直したあとに提案を追いつかせるのも同じ 1 本 | フラグが 1 つ増える。`phases:` の値の中のコメントは消える |
| エージェントが手で書き、検査で落とすだけ | 足すものが無い | 写し間違いで何度も落ちる。`phases.yml` を直すたびに全部の提案を手で直す |

補助のフラグにする（決定済み）。`--agree` が「`phases:` が `phases.yml` と違う」で落とすとき、文面に `--plan-order <親> --fill-phases` を出す。ワークフロー編集タブの保存（`--write`）は `phases:` に触れない（順序だけを書く）。

### `phases.yml` を承認のあとに直したとき

進行中の親には効かない。判定は承認済みチケットの `phases:` を読む。

改版での扱いは次のとおり（決定済み）。

- 改版の提案の `phases:` のうち、**固定した番号（子が承認された番号）が使う定義**は、承認済みチケットの `phases:` と同じでなければ error。`phases.yml` と違っていてよい。外すこともできない（その番号の項が使うので、外せば「`phases:` に無い定義名」で落ちる）
- それ以外の定義（まだ子の無い番号だけが使う定義、改版で足す項の定義、フィードバック計画の定義）は、改版を承認したときの `phases.yml` の同じ名前の定義と同じでなければ error。足すのも、使わなくなった定義を外すのも自由（外し忘れは「使われていない定義」の warn）
- 同じ定義を固定した番号と固定していない番号の両方が使うなら、固定した側の値に揃える（1 つのキーに 2 つの値は持てない）
- `--plan-order <親> --fill-phases` は改版の提案でも、項が使う定義だけをこの規則で差し込む（固定した番号の定義は承認済みチケットから、ほかは `phases.yml` から。使わなくなった定義は外す）
- 固定した番号の定義を直したいときは、ユーザが承認済みチケットの `phases:` を手で直す（承認済みの置き場はユーザが書ける。エージェントは書けない）。直した値は判定の側の形の検査を通る

| 案 | 中身 | 良いところ | 困るところ |
|---|---|---|---|
| **固定した番号の定義は変えない（決定済み）** | 上のとおり | 進んでいるフェーズの範囲・見る場所・成果物が改版で変わらない。改版（フィードバック計画の立案は必ず改版）が `phases.yml` の変更で詰まらない | ユーザが `phases.yml` で範囲を狭めても、進んでいるフェーズには届かない（手で直す） |
| 改版ではいつも今の `phases.yml` に揃える | 全部の定義が `phases.yml` と同じでなければ error | 規則が 1 つ。改版を承認すれば最新の定義が効く | 閉じたフェーズの `review` を後から変えると、済んだレビューの扱いが変わりうる。進んでいるフェーズの範囲が改版の承認で変わる |
| 改版でも `phases:` の既存の定義は変えられない | 足す定義だけを今の `phases.yml` から取る | 一番動かない | 固定していない番号の定義も古いまま |

### 子の扱い

- 子の定義は、親の `phases:` から引く（`phase_scope.type_for` は `parent.phase_types` を見る。`phase.load_types` を読まない）。親がまだ提案（同じ承認で通る親）なら、その提案の `phases:` から引く
- 子の範囲は今までどおり「子 ⊆ 定義の `scope` ⊆ 親の `allow`」で切り詰める。定義の `scope` が親に固定されたものになるだけ
- `phase_scope.unread_type`（定義が読めないときは定義で切り詰めない、の例外）は、計画と `phases:` を持つ親では要らなくなる。`phases:` に定義が無い親は、判定の側の検査で壊れた親として止まる（5 の手で動かした承認と同じ扱い）。例外を残すのは、`phases:` を持たない計画付きの親を読むときだけで、それも下のとおり止めるので、`unread_type` は消せる
- 計画を持たない親と、その子: 今のまま（番号だけ。定義で切り詰めない）
- 計画を持つが `phases:` の無い親（前の版の承認、`phases:` を書かずに手で動かした承認）: 判定の側で「計画が使う定義が親に固定されていない」として親を止め、子も `child_problems` で止まる。進んでいる前の版の親は無い（ユーザの確認）。`--lint` は error で言い、直し方（ユーザが承認済みチケットに `phases:` を足すか、取り消して出し直す）を言う

### 判定の側で見る範囲（5 の見直し）

定義が親に固定されたので、判定は `phases.yml` を読まずに定義の有無・`kind`・`review` を見られる。

| 案 | 判定の側で見るもの | 良いところ | 困るところ |
|---|---|---|---|
| **広げる（決定済み）** | `after` の形・終端・最後の項の延期・延期の引き受け手に加えて、計画が使う定義が `phases:` にある・`kind` が置いた計画と合う・引き受け手にレビューがある（`phases:` の `review` と項の `review: mr`）・`phases:` の定義の形 | `--agree` の検査とほぼ同じ答えを、手で動かした承認にも当てられる。読むのは承認済みチケットだけなので、承認のあとに `phases.yml` を直しても進行中の親は止まらない | 判定の検査が増える（チケットを読むたびに 1 回。項の数に比例して小さい） |
| 今のまま | `after` の形・終端・延期の引き受け手だけ | 検査が少ない | 手で動かした承認で、引き受け手にレビューの無い計画が通る |

「定義の有無・`kind`・`review` は `--lint` の warn」という前の決め方は、判定が `phases.yml` を読むと承認のあとの定義の変更で進行中の親が止まるのを避けるためだった。`phases:` を読むならその心配は無いので、広げる。`phases.yml` と `phases:` の食い違いは、`--lint` の warn（「進行中の親には効かない。反映するには、固定していない番号の定義なら `--plan-order <親> --fill-phases` を打った改版を出す。計画が同じでも改版になる。固定した番号の定義ならユーザが承認済みチケットを直す」）で言う。

### 承認画面での見せ方

- 承認のダイジェストはチケットのバイト列で決まるので、`phases:` は何もしなくてもダイジェストに入る
- 端末と VS Code の承認画面の本文で、定義を 3 つに分けて出す
  - **この親が使う定義**（`phases:` にあり、項が使う）: 1 定義 1 段で、題・`review`・`scope` の glob・`deliverables` と、使う番号（「2, 4 番」）
  - **使われていない定義**（`phases:` にあるが、どの項も使わない）: 名前と題だけ。warn と同じ行
  - **この親では使わない定義**（`phases.yml` にあるが `phases:` に無い）: 名前と題だけを 1 行に並べる（「使わない: 調査、ユーザがコピーする版の作成」）。ユーザが「この定義を外した」ことを読んで承認できるように
- 中身は `phases.yml` と同じ（検査で確かめてある）なので、ユーザが読むのは「どの定義をこの親に固定し、どれを外したか」
- 改版では、`phases:` の差分（足した定義・外した定義・変わった定義の欄）を出す。固定した番号の定義は変わらないので出ない
- ワークフロー編集タブの図とオーバーレイの図は、点の題と見る場所を `phases:` から出す（`plans` の `items` の `title` / `review` を `phases:` から引く）。タブは `phases:` を書き換えないので、保存の前後で変わらない

### 大きさの上限

- 定義の `scope` と `deliverables` は、それぞれ `MAX_SCOPE_ENTRIES`（20 件。チケットの範囲と同じ上限）までにする（決定済み）。`phases.yml` の読みで error にし（`--lint` も同じ）、コピーにも同じ上限が当たる。今の `phases.yml` には件数の上限が無いので、ユーザの設定に新しい制約が 1 つ増える（このワークスペースの定義は最大 8 件）
- `phases:` の定義は、計画が使うものと、使われていない定義（warn）だけ。使われていない定義は補助のフラグが外すので、ふつうは定義の数が計画の項の数以下になる。`--agree` を通る承認では、`phases:` の定義の数は `phases.yml` の定義の数を超えられない（同じ名前の定義が要るため）。手で動かした承認にはこの縛りは効かず、判定の側も数を見ない（承認済みの置き場を信じる決まりに合わせる）。チケット全体の大きさには別の上限を足さない

## 6. ワークフロー編集タブと承認画面（VS Code）

計画の図は 2 か所に出す。**編集するのはワークフロー編集タブ**（子チケットのフロー編集と同じ形の専用パネル）、**承認のオーバーレイは同じ図を読むだけ**で出す。
全体計画とフィードバック計画は別の図にする。

### 入口とタブの開き方

- 対象は、承認待ちの提案（`todo/`）のうち計画を持つ親。新規の親と、改版の提案の両方
- 入口は 2 つ。ボードの親の提案のカードの「ワークフロー」と、承認のオーバーレイの「ワークフローを編集」
- **タブは親ごとに 1 枚。** 同じ親をもう 1 度開けば前面に出す（フロー編集の「子ごとに 1 枚」と同じ）
- オーバーレイの「ワークフローを編集」はオーバーレイを閉じてからタブを開く。タブで保存すると提案が書き換わり、オーバーレイが見せていた一覧はもう承認できない（ダイジェストが変わる）ので、承認はタブを保存したあとに開き直す（決定済み。11 節の決まったこと）
- 提案が承認されて `todo/` から無くなったら、タブは読むだけになり、「承認済み。順序を変えるには改版を出す」と出す。提案が消えた（取り下げ・削除）ときも読むだけにする

### 図

- 図の部品は 1 つ（`webview/shared/PlanGraph.tsx`）にして、タブとオーバーレイで共有する。`editable` が偽なら線を引けず、点も線も選べない（`Canvas.tsx` の読むだけの扱いと同じ）。パン・ズームは両方でできる
- 部品の中身はフロー定義画面の `webview/flow/Canvas.tsx` を流用する。図の中身は新しい `core/plan-graph.ts` が組む（フローの文書と同じ形の点と線）
- 点は計画の項。番号・定義の題・見る場所（`review`、延期なら「延期 → 5」）を出す
- start と end の仮ノードを描く。先行の無い項へ start から、後続の無い項から end へ線を引く。どちらも図だけのもので、保存しない。実行ファイルは知らない。この 2 種類の線は選べず、消せない（先行を全部消せば start からの線が出る）
- フィードバック計画の図では、start を「全体計画のレビュー後」、end を「親を閉じる」と名付ける
- **終端に当たらない項を目立たせる。** 実行ファイルが返す `loose`（最後の項が待たない項の番号）に入る項は、点の縁と、その項から end への線を注意の色で描き、図の下に「最後の項がこの項を待っていない。最後の項へ線を引くか、合流の項を置く」と出す。どの項を目立たせるかは実行ファイルが決め、図は印を付けるだけ
- 子が承認された番号は、点を薄くし、動かせない（入る線を変えられない）
- 置き場所は start からの最長の段数で列に分け、列の中は番号順。タブで線を変えて番号が振り直されたら、点の名札の番号だけが変わり、置き場所は動かさない。「並べ直す」で並べ直す。位置は画面の状態にだけ持つ

### タブでの線の引き直しと番号の振り直し

- 線を引く（m から n へ）＝ n が m を待つ。線を消す＝待たない。並びの逆向き（大きい番号から小さい番号へ）の線も引ける
- 引いている最中に断るのは、自分へ・start へ入る・end から出る（`flow-doc.ts` の `canConnect` の規則）と、**循環になる線**（n から m へ既に辿れる）と、子が承認された番号へ入る線。React Flow の `isValidConnection` で断るので、放しても線はできない。循環は線と点だけで決まる形の検査で、計画の良し悪しの判定ではない
- 線を変えるたびに、番号をトポロジカル順に振り直す。決まりは「先行が全部前に並んだ項のうち、元の番号がいちばん小さいものから順に番号を振る」（Kahn の方法で、同じ段の項は元の番号順を保つ）。線を変えても並びが崩れなければ、番号は変わらない
- 改版では、子が承認された番号を動かさない。空いている番号に、承認されていない項を上の決まりで詰める。詰められない線（承認された番号より前に置くことになる線）は、`--plan-order <親> --json --order` が「詰められない」と返し、タブは線を引く前の形に戻す。固定した番号を考えに入れた振り直しを画面で組むと画面の判定になるので、画面は答えを受けて戻すだけにする。改版の錠（5 の改版）に落ちる形も `--plan-order` が返し、タブは保存させない
- `after` の指す先は振り直した番号に付け替える。`review: defer` は項に付いたまま動く。延期の引き受け手は保存せず計算するので、振り直した番号で実行ファイルが計算し直す
- 「案に戻す」で、提案に書いてある先行と番号に戻す

### 振り直した順序の行き先

振り直すと、計画の項の並びと `after` が変わる。承認は提案をバイト単位でそのまま動かす決まりなので、承認の段で計画を書き換えることはできない。選べる形は 3 つあった。

| 案 | 中身 | 良いところ | 困るところ |
|---|---|---|---|
| **承認の前に提案を書き換える（決定済み）** | タブの保存で、実行ファイル（`--plan-order --write`）が `todo/` の提案の `plan:` / `feedback:` の値だけを振り直した形に書き換える。承認はそのあとにふつうに行う | 承認は今までどおりそのまま動かす。待ち方は計画だけから計算できる（`workflow.yml` を廃止できる）。読む側（子の `phase:`・マーカー・`--explain`）は番号の対応表を知らなくてよい | ユーザの手で提案が書き換わる。取り下げで「承認コミットの親の提案」と合わなくなる（5 の取り下げ） |
| 承認の段で書き換えて置く | `--agree --yes` が振り直した計画で `doing/` を書く | 手順が 1 回で済む | 承認がチケットの中身を変える。取り下げをバイト一致で決める仕組みと、経路によらず承認済みチケットが同じになる約束が崩れる |
| 計画は変えず、番号の対応を別のファイルに持つ | 計画の n 番目の項がフェーズの何番かを対応表で持つ | チケットに手が入らない | 番号で項を引く全部の箇所（`item_at`・`plan[n-1]`・子の `phase:`・マーカー・ボードの JSON・Chrome のコア）が対応表を通すことになる。計画を読んだエージェントは違う番号で子を書く |

### フロー編集との対応

フロー編集は「エージェントが下書きを置き、ユーザが取り込んで、承認済みの領域へ保存する」形。ワークフロー編集では、**エージェントの提案そのものが下書き**で、保存先もその提案になる。

| | フロー編集（子のフロー） | ワークフロー編集（親の計画の順序） |
|---|---|---|
| 編集の元 | 承認済みの領域のフロー。エージェントの下書きは「提案あり」から取り込む | `todo/` の提案の `plan:` / `feedback:`。開いたときの中身がそのまま初期値で、取り込む段は無い |
| 保存先 | 承認済みの領域（エージェントは書けない） | `todo/` の親の提案と、その親の子の提案（どちらもエージェントも書ける） |
| 書くのは | 拡張（`flow-write.ts`。リンクを辿らない入れ替え） | 実行ファイル（`--plan-order --write`）。拡張はファイルを書かない |
| 保存の前の確かめ | `--lint --json --flow` に書き出す本文を掛け、error なら保存しない | `--plan-order <親> --json --order <JSON>` に掛け、順序の検査（`after` の形・終端・延期）に error があれば保存しない。提案のほかの理由で落ちるもの（範囲など）は保存を止めない |
| 外で変わったとき | 読み込んでから外で変わっていれば保存しない | 開いたときのハッシュ（親の提案と、書き換える子の提案をまとめたもの）を持ち、`--plan-order --write --expect <ハッシュ>` で渡す。実行ファイルはどれかが変わっていれば何も書かない。拡張は監視で変化に気づいたら「提案が外で変わった」と出し、差分を見せて「取り込む」（編集を捨てて新しい提案から始める）か「編集を続ける」（保存はできない）を選ばせる |
| 錠 | 子が着手していれば読むだけ | 提案が `todo/` に無ければ読むだけ。改版では子が承認された番号の点だけ動かせない |
| 未保存のまま閉じた | 題の頭に「●」。閉じた後に「開き直して戻す」「YAML で開く」「破棄する」を聞く | 題の頭に「●」。閉じた後に「開き直して戻す」「破棄する」を聞く。開き直すのは、提案のハッシュが閉じた時点から変わっていないときだけ。変わっていれば戻せないと言う（YAML で開く先は無い。直すのは順序だけなので） |
| 保存のあと | 取り込んだ下書きを消し、ボードを読み直す | ボードを読み直す。エージェントに渡す文は承認のときに出す（下の 5） |

段取り。

1. タブを開くと、拡張は `ccnavi --plan-order <親> --json` を打ち、その親の図の中身（下の `plans` の 1 件と、提案のハッシュ）を受け取る。何も書かない
2. 線を変えるたびに、元の番号での直接の先行を付けて `ccnavi --plan-order <親> --json --order <JSON>` を呼び直す。実行ファイルは振り直した計画で待ち方を計算・検査し、振り直した番号・待ちの一覧・落とす理由・`loose` を返す。番号の振り直しの正は実行ファイル。画面は同じ決まりで先に仮の番号を出し、返ってきた番号で置き換える（同じ決まりを 2 か所に持つので、見本の表を Python と TS のテストで共有して食い違いを見張る）
3. 保存（「この順序に決める」）で `ccnavi --plan-order <親> --order <JSON> --expect <ハッシュ> --write` を打つ。実行ファイルは親の提案の `plan:` / `feedback:` の値と、子の提案の識別子・ファイル名・`ticket:`・`phase:`・`predecessors` の参照（下の「子の提案の追従」）だけを差し替え、ほかのバイトは変えない。書き換えた計画は順序の検査をもう一度通す
4. ユーザはボードから承認を開く。オーバーレイの図は書き換えた提案を読んだもので、承認する中身と同じ。`--agree --yes` は `--order` を取らない
5. 承認したことをエージェントに渡す文（`approved_text`）には、計画を持つ親と、計画を持つ親の子があれば、いつも「番号は承認済みチケットで読み直す」と添える。承認の前に書き換えられたかを見分ける材料が今は無い（`approved_text` は書き換えを知らない）。見分けるなら、提案のバイト列をそのツリーの `HEAD` の版（`git show HEAD:<パス>`）と比べ、違いが `plan:` / `feedback:` / `phase:` の値だけなら「計画の順序はユーザが直した」と言える。ただしエージェントのコミットしていない編集でも同じ形になるので、言い切れない。見分けずにいつも添える（決定済み）

`--order` の形は、**元の番号（いま提案に書いてある番号）での直接の先行**。`{"plan": {"1": [], "2": [3], "3": [1]}, "feedback": {...}}`。渡した部分は全部の番号の先行をそこから取る（書いていない番号は何も待たない）。
振り直し後の計画を渡さないのは、振り直しの正を実行ファイルの 1 か所に置くため。拡張は「どの項がどの項を待つか」だけを送る。

### 子の提案の追従

番号を振り直すと、その番号を指す子の提案（`todo/` にある `phase:`）が違う項を指すようになる。子の識別子はフェーズ番号を含み（`<親>-<2 桁のフェーズ番号>-<連番>`）、識別子の番号と `phase:` が食い違うと読めない。そのため `--plan-order --write` は親の計画と一緒に、子の提案の識別子・ファイル名・`ticket:`・`phase:` を付け替え、その子を指す `predecessors` も直す（決定済み）。

- 付け替える範囲: 親が同じで `todo/` にある子の提案（どのツリーにあっても、承認と同じ集め方で探す）のうち、`phase:` が振り直しで番号の変わった項を指すもの。識別子の 2 桁を新しい番号に、ファイル名と `ticket:` を新しい識別子に、`phase:` を新しい番号にする。連番は変えない。ほかのバイトは変えない
- 参照の付け替え: `todo/` の子の提案（ほかの親の子も）の `predecessors` が付け替える識別子を指していれば、新しい識別子に直す。提案の置き場のフローの下書き（`flows/<子>.yml`）も名前を変える
- 承認済みの子（`doing/`・`review/`・`done/`）には触れない。その番号は固定した番号で、振り直しで動かない（5 の改版）
- 付け替え先の衝突: 振り直しは元の番号と新しい番号が 1 対 1 なので、付け替える子どうしは重ならない（入れ替わる 2 本は、読んだ中身を持っているので上書きしてよい）。付け替え先が動かないファイル・提案・承認済みチケットと重なれば、何も書かずに理由を出す
- 承認済みの側の参照: 承認済みチケット（識別子、`predecessors`）・`review/` の提案・承認済みの置き場の記録（`flows/`・`events/`・`phases/<親>/`）・同じ名前のワークツリーが、付け替える識別子を指していれば何も書かない。承認済みの側はエージェントが直せないので、ユーザが手で直すか、取り消して出し直す
- ハッシュ: `--plan-order <親> --json` が返す `source_sha` は、親の提案、その親の `todo/` の子の全部、その子を `predecessors` で指す `todo/` の子の提案のバイト列をまとめたもの（`--order` によらない）。`--expect` が今のまとめと違えば何も書かない。子の提案が増えた・消えた、も違いになる
- 原子性: 書く前に全部の新しい中身を組み、検査が通ってから書く。書く順は子の提案が先、親の計画が最後。付け替える子は新しい名前に書いてから古い名前を消す。途中で落ちたら、触ったパスを全部、書く前の中身へ戻す（無かったものは消す）。戻しまで落ちた形（電源断など）は防げない。そのときは親の計画と子の `phase:` が食い違いうる。書く順を子が先にするのは、途中で止まれば親は前の番号のままで、付け替えた子だけがずれるようにするため。`--plan-order <親> --json` は `phase:` が親の計画の番号に無い子の提案を `mismatched` で言う（項の定義との食い違いは、子が定義を持たないので見ない。承認の検査が落とす）
- **書く前に、組んだ全文を読み直して確かめる。** `plan:` / `feedback:` / `phases:` の値に YAML のアンカーがあり、ほかの欄から別名で参照されていると、値を差し替えると別名の行き先が無くなる。`--plan-order --write` と `--fill-phases` は、組んだ全文を読み直し、親は `plan` / `feedback` / `phases`、子は `ticket` / `phase` / `predecessors` のほかの欄が、読んだ形で元と同じでなければ何も書かない
- 承認の前に書くので、子の提案の書き換えもコミットされない。承認した子は、親と同じ理由で取り下げられない（5 の取り下げ）
- タブは保存の前に、付け替える子の提案と、変わる識別子と番号（`<親>-02-01 → <親>-04-01`、`phase: 2 → 4`）を一覧で見せる

### エージェントが打ってよいか

`--plan-order` は `--agree` の外の独立したフラグにする。今の組み込みの止め（`tickets/phase_forms.py` の `_CLI_FORMS`）は `--agree` を含む呼び出しを、`--preview` を除いてエージェントに打たせない。`--agree --plan` のような副フラグにすると止めに当たるので、免除を足すことになる。免除は `--preview` と同じ厳しさの形で書き、変異テストを付ける必要があり、止めの穴になりうる。独立したフラグなら止めの形に当たらない。

`entry/cli.py` では `--agree` の端末の確かめ（`cli_args._from_terminal`）の手前で分け、`--plan-order` を端末の確かめなしで走らせる。`phase_forms.py` には「`--plan-order` を止めない」ことを確かめるテストだけを足す。

エージェントが打ってもよい。書くのは親と子の提案（エージェントも書ける置き場）だけで、承認はしない。自分で書けるものを書くのと変わらない。書き換えたあとの承認はダイジェストで縛られるので、書き換えと承認の間に提案が変われば承認は止まる。

### 承認のオーバーレイ

- 一覧に計画を持つ親があれば、本文の上にその親の図を読むだけで出す。中身は `--agree --preview --json` の `plans`（`--order` は渡さない）で、**承認する提案そのものの順序**。タブで直した順序は保存の時点で提案に書き換わっているので、図と承認の対象はずれない
- 図の横に「ワークフローを編集」を置く（上の入口）
- **タブで保存したあとに提案が書き換わっていれば、注意を出す。** タブは最後に保存したときの `source_sha`（親と子の提案のまとめたハッシュ）を拡張ホストに残す。オーバーレイは一覧を開くときに今の `source_sha` と比べ、違えば「ワークフロー編集タブで保存したあとに提案が変わった（エージェントが書き換えた可能性がある）。図を確かめてから承認する」と出す。図は今の提案をそのまま出すので、エージェントが `after` を書き戻して順序を黙って戻しても、ユーザが気づけるように。承認は止めない（今の提案の中身はダイジェストで縛られていて、図はそれを見せている）
- 親のワークフロー編集タブに未保存の変更があれば、その親の図の上に「ワークフロー編集タブに保存していない変更がある」と出し、承認のボタンを押せなくする（保存するか破棄するまで）。未保存の順序のまま承認して、直したつもりの順序と違うものが通らないように
- 遷移は今の状態のまま増やさない（`ordering` / `reordering` は要らない）。足すのは「未保存のタブがある親を含む一覧は承認を打たない」のガード 1 つと、その変異テスト

### 実行ファイルの JSON に足す欄

`--agree --preview --json` の `plans` と、`--plan-order <親> --json` の答えは同じ関数で作る。`--plan-order` の答えには、付け替える子の提案の一覧（`children: [{ticket, new_ticket, path, new_path, phase, new_phase, predecessors, new_predecessors}]`）、付け替えられない理由（`child_problems`）、計画と食い違う子の提案（`mismatched`）も入れる。足すだけなので承認の JSON の版は上げない。欄が無ければ画面は図を出さない。

```json
"plans": [
  {
    "ticket": "i0001",
    "part": "plan",
    "source_sha": "…",
    "items": [{"number": 1, "from": 1, "type": "research", "title": "調査", "review": "none", "deferred": false, "locked": false}],
    "after": {"2": [1], "3": [2]},
    "proposed": {"2": [1], "3": [2]},
    "current": {"2": [1]},
    "loose": [],
    "ready": [1],
    "problems": []
  }
]
```

`source_sha` は親の提案とその子の提案のバイト列をまとめたハッシュ（`--expect` に返す）、`number` は振り直した番号、`from` は元の番号、`after` は振り直した番号での直接の先行、`proposed` は提案に書いてある先行（「案に戻す」に使う）、`current` は改版のときの今の待ち方から戻した直接の先行（差分を描く）、`loose` は最後の項が待たない項、`ready` はすぐ始まる項、`problems` は順序の検査の error。

### 判定の境界

画面がするのは、線と点だけで決まる形の扱い（引けない線を断る、循環を断る、固定した番号の無い計画で仮の番号を出す、置き場所）まで。固定した番号を考えに入れた振り直しと「詰められない線」は実行ファイルが答え、画面は線を戻すだけ（改版では仮の番号を出さず、答えを待つ）。終端・延期の引き受け手・すぐ始まる項・振り直しの答え・保存してよいかは実行ファイルが出し、画面はそれを描く。

見積もりの元は、フェーズ管理画面に図を入れたときの実測（`phases.js` が 237.7KB から 420.4KB、+182KB）。React Flow と `Canvas.tsx` のぶんがおよそ +180KB と見る。

### 端末の `--agree` との関係

端末は今までどおり文字で見せる。待ちの一覧は、一直線かどうかに関わらず全部の番号に出し（今は `dag` のときだけ）、「すぐ始まる」と「最後の項が待たない」の行を足す。端末から順序を直す手段は作らない。直したいときは VS Code のワークフロー編集タブで直すか、計画を直させる。
Chrome 拡張の承認と手で動かした承認も直す手段を持たない。どの経路で承認しても、待ち方は承認済みチケットの計画から計算する（手で動かした承認も計画の `after` で読む。5）。

## 7. 失うものと手当て

| 失うもの | 手当て |
|---|---|
| `requires`（この定義を置くなら一緒に要る）の検査 | 判定では持たない。フェーズ定義の `when` に「受入テスト作成を先に置く」のように書く。ユーザはワークフロー編集タブと承認画面の図で見る。このワークスペースの `implement` と `staging` の `when` に書き足す（staging の版に入れる） |
| `overlap`（並行の許可）の意味 | 線を引かないことで同じことが書ける。失う機能は無い |
| **辺の書き漏れが並行として通る。** 今の既定（一直線）なら書き漏れは止まる側に倒れた | (1) 終端の検査で、どこにも繋がらない項と途中で切れた枝は error になる。`after` を 1 つも書かない 2 項以上の計画は必ず落ちる。(2) ワークフロー編集タブと承認画面の図で、start から何本出ているかと、終端に当たらない項が見える。(3) 本文に「すぐ始まる: …」を出す。(4) 計画の書き方の案内に「最初の項のほかは `after` を書く」と書く。残るのは、終端には繋がっているが途中の 1 本を書き忘れた形（例: 3 と 4 を 5 が待つが、4 が 3 を待つはずだった）。これは図で見るしかない |
| フィードバック計画で、独立した対応を並行のまま終える形 | 最後に 1 項で受けるか、一直線に並べる。合流の項は実際に子を持つフェーズなので、受ける作業（まとめの確認など）が無い計画では一直線に並べるほうが軽い |
| タブで順序を直すと、承認の前に親と子の提案が書き換わる | 書き換えるのは実行ファイルで、親の `plan:` / `feedback:` と、承認前の子の提案の識別子・ファイル名・`ticket:`・`phase:`・`predecessors` の参照だけ。ほかのバイトは変えず、開いたときのハッシュと違えば書かない。承認はダイジェストで縛る。承認したことを渡す文で、エージェントに番号を読み直させる |
| `plan:` / `feedback:` の値を差し替えると、計画の中に書いたコメント（`# 調査は飛ばしてよい` のような行の後ろのコメントや、項の間の行）が消える | 値の外（キーの前の行、ほかのキー）のコメントは残す。消えることを保存の前の確認に書く。エージェントには、計画の意図は本文に書くよう案内する |
| ハッシュを確かめてから書くまでの間にエージェントが提案を書くと、どちらかが失われる（TOCTOU） | 確かめてから書くまでは実行ファイルの 1 回の中で、間は短い。書いたあとに読み直してハッシュを返し、拡張は次の監視で食い違いに気づいたら「提案が外で変わった」を出す。防ぐには提案の置き場に錠が要るので、ここでは狭めるだけにする（フロー編集の保存と同じ扱い） |
| 始まっていない小さい番号の項を、始まった大きい番号の項の後ろに回せないことがある | 固定した番号は動かさないので、空いた番号を埋める始まっていない項が無ければ線を断る（例: 計画が 1〜4 で、2・3 は 1 を待ち、4 は 2・3 を待ち、1・3 に子があるとき、3→2 の線（2 が 3 を待つ）は、2 を 4 番へ回すと 4 番だった終端の置き場が無く、2 番を埋める項も無いので断られる）。回したいときは、項を足す改版で空いた番号を埋めてから線を引く |
| 改版の錠が、前置ごとから番号ごとに変わる（判定が緩む側。子の無い前の番号を直せるようになる） | 固定した番号の定義・`review`・推移的な待ち・延期の引き受け手は変えさせない（5 の改版）。始まっていない項だけが動く |
| フィードバック計画を立てたあとは、全体計画を変える改版ができない | フィードバック計画は全体計画のレビューが済んでから立てるので、困る場面は無い見込み |
| 前の版の形（`ccnavi_approved` を持つ）の親は取り下げられない | 進んでいる親は無い。取り消して出し直す |
| 順序を直すには、承認とは別のタブを開いて保存し、承認を開き直す。手順が 1 段増える | オーバーレイに「ワークフローを編集」の入口を置く。オーバーレイでは直せないので、図と承認の対象がずれない |
| タブの編集中に、エージェントが提案を書き直すと保存できない | 「提案が外で変わった」と出し、差分を見せて取り込むかを選ばせる（フロー編集の「提案あり」と同じ形） |
| タブで順序を直した親は、取り下げられない（5 の取り下げ） | 止まる側のまま受け入れる。取り下げの文面で「取り消して出し直す」と案内する |
| 番号の振り直しの決まりを、実行ファイルと画面の 2 か所に持つ | 正は実行ファイル。画面の番号は仮で、返った番号で置き換える。見本の表をテストで共有する |
| ワークフローの形を定義で一度決めて使い回す手段 | 計画ごとに書く。エージェントは前の計画や `when` の案内を手本にする |

## 10. 迷ったところ

- 作業メモ: この草案は検討のための文書なので、決定の記号や ADR の番号に触れているところがある。`docs/design/tickets/phases.md` などの文書へ写すときは、ADR の番号や決定の記号に触れず、決めた中身と理由をその場で書く

- 同じ定義を 2 回置いたときの暗黙の待ちを消した。「線のない項はすぐ始まる」に揃えるためで、残すと図に無い待ちが残る
- 書き換えの順は子の提案が先、親の計画が最後にした。途中で止まったときに、親の計画が新しい番号を指したまま子が古い番号に残る（別の項を指したまま承認が通りうる）形を避けるため
- 振り直しの正を実行ファイルに置き、画面は仮の番号を出す形にした。画面だけで振り直すと、保存される番号を画面が決めることになる。実行ファイルだけにすると、線を変えるたびに番号が一拍遅れて変わる
- `--order` は元の番号での先行にした。振り直したあとの計画を送らせると、振り直しの決まりを画面が持つことになる
- 「この順序に決める」と「承認」の 2 段にした。書き換えと承認を 1 回にまとめると、承認がチケットの中身を変える形になる
- タブの保存は、提案の順序の検査に error があれば止める（フロー編集の lint と同じ扱い）。範囲など順序と関係の無い理由で承認に落ちる提案でも、順序の保存は止めない
- タブを閉じた後の「YAML で開く」は持たない。直すのは順序だけで、名前の無いエディタに出しても戻す先が無い

## 11. 決まったこと

1. ワークフロー編集タブの図では任意の線を引ける。循環になる線は引いている最中に断る。線を変えるたびに番号をトポロジカル順に振り直す（同じ段は元の番号順）。保存される `plan:` は「`after` は自分より小さい番号だけ」を保つ
2. 終端の検査（最後の項が、それより前の全項を待つ）は、全体計画とフィードバック計画の両方に求める
3. 図の編集はワークフロー編集タブ（親の提案ごとに 1 枚の専用パネル）で行う。承認のオーバーレイには同じ部品の図を読むだけで出し、タブへの入口を置く
4. 振り直した順序は、承認の前に提案へ書き戻す（タブの保存で `--plan-order --write` が提案の `plan:` / `feedback:` の値を書き換える）
5. 図で順序を直した親の取り下げは、止まる側のまま受け入れる。取り下げの文面で「取り消して出し直す」と案内する。原因はチケットのバイト列の違いで、待ち方のファイルの廃止では変わらない
6. オーバーレイの「ワークフローを編集」を押したら、オーバーレイを閉じてからタブを開く
7. `phases/<親>/workflow.yml` を廃止し、待ち方は承認済みチケットの計画から都度計算する
8. 手で動かした承認も、計画の `after` を信じて並行で読む。特例は置かない。判定の側で、`phases.yml` を読まずに済む検査を当てて壊れた計画を止める（承認のあとに `phases.yml` を直しても進行中の親は止まらない）。11 節の項 11 で親に定義が固定されたので、定義の有無・`kind`・`review` も親の `phases:` から判定の側で見る（5b。範囲を広げた）
9. 壊れた計画の親（手で動かした承認を含む）の子は、承認・着手・書き込みとも止める。止めるのは `child_problems` の 1 か所（承認と判定が同じ答えを引く）
10. 図で番号を振り直すとき、`todo/` にある子の提案の識別子・ファイル名・`ticket:`・`phase:` と、それを指す子の `predecessors` も一緒に付け替える（承認前の提案だけ。子の識別子がフェーズ番号を含むため）
11. 親チケットの frontmatter の `phases:` に、この親が使うフェーズ定義だけのコピーを持たせ、承認のときの定義を親に固定する。`--agree` は `phases:` に書いた各定義が `phases.yml` の同じ名前の定義と同じかを確かめる。`phases.yml` にあって `phases:` に無い定義は error にしない。`allow:` は変えない
12. `phases:` のコピーは補助のフラグ `ccnavi --plan-order <親> --fill-phases` が、項が使う定義だけを `phases.yml` から差し込んで作る。エージェントが打ってよい
13. 改版で、子が承認された番号が使う定義は変えない。変えたいときはユーザが承認済みチケットの `phases:` を手で直す
14. 判定の範囲を広げる。定義の有無・`kind`・引き受け手の `review` も、親の `phases:` から判定で見る
15. `phases.yml` の定義の `scope` と `deliverables` に 20 件の上限を付ける
16. 改版の錠は番号ごと（前置ごとの錠を置き換える）
17. `phases:` にあってどの項も使わない定義は warn

### 採らなかった案

- 改版でいつも今の `phases.yml` に揃える: 閉じたフェーズの `review` が後から変わり、済んだレビューの扱いが揺れる。進んでいるフェーズの範囲が改版の承認で変わる
- 改版でも既存の定義を一切変えない: まだ子の無い番号の定義まで古いままになる
- 壊れた親の子は承認と着手だけを止める: `child_problems` は承認と判定が同じ答えを引く 1 か所で、書き込みだけ通すと承認と判定で答えが分かれる
- 定義の `scope` と `deliverables` に上限を付けない: 親の `phases:` に写すので、親の大きさが縛れない

- `phases:` に `phases.yml` の全定義を写す: 使わない定義も親に固定され、ユーザが「この親で外した定義」を読めない
- `phases:` の使われていない定義を error にする: 判定に効かないのに、消し忘れで承認が止まる
- `phases:` を承認のときに書き足す: 承認がチケットの中身を変える
- `phases:` をエージェントが手で書き、検査で落とすだけ: 写し間違いで何度も落ちる
- 判定の側の検査を `after` の形・終端・延期の引き受け手だけに留める: 親の `phases:` を読めば `phases.yml` を読まずに済むので、留める理由が無くなった

- `--agree --plan` / `--agree --reorder` のような `--agree` の副フラグ: 組み込みの止めに当たるので、`--preview` と同じ厳しさの免除と変異テストが要り、止めの穴になりうる。独立したフラグ `--plan-order` にした
- 改版の錠を前置ごとのまま残す: 並行に進むフェーズで、後ろの番号に子があると、始まっていない前の番号を直せない。番号を振り直す図と噛み合わない
- 改版の錠を直接の先行で比べる: エージェントが「待つ: …」を写しただけで食い違って落ちる。推移的な待ちで比べる
- 承認を渡す文で、提案が書き換えられたかを `HEAD` の版との比較で見分ける: エージェントのコミットしていない編集と見分けられない。いつも「番号は承認済みチケットで読み直す」と添える
- 前の版の形の親の取り下げに、改版を見分ける別の印を決める: 進んでいる親が無いので、印を足す手間に見合わない。一律に止める

- 承認の段で書き換えて置く: 承認がチケットの中身を変え、取り下げのバイト一致と、経路によらず承認済みチケットが同じになる約束が崩れる
- 番号の対応を別のファイルに持つ: 番号で項を引く全部の箇所が対応表を通すことになり、計画を読んだエージェントが違う番号で子を書く
- `--order` を別のファイルに残し、取り下げで同じ振り直しを当てて比べる: 廃止した待ち方のファイルのような置き場をもう一度作ることになり、C1・Chrome の扱いも要る。取り下げのために持つ情報としては重い
- 書き換えた提案を承認の前にコミットする: 拡張か保護された `ccnavi-push-approved.sh` にコミットの段が増え、承認の段取りが複雑になる
- オーバーレイで線を引き直す形（前の草案）: 承認の途中で preview を呼び直す状態（`ordering` / `reordering`）が要り、承認の遷移が重くなる。編集の途中の順序と承認の対象がずれる隙ができる
- オーバーレイを開いたままタブへ移る: タブで保存するとダイジェストが変わり、その一覧では承認できない。使えるようにするには、タブの保存を受けてオーバーレイが一覧を読み直す段（遷移の入力が 1 つ）が要る
- `workflow.yml` を残す: 承認済みの計画の完全な写しで、2 か所に持つための仕組み（片方だけ書けたときの戻し、取り下げでの比較と削除、C1、Chrome、孤児の warn）だけが残る。後の版で計算の決まりを直しても承認したときの答えが残る点は失うが、決まりを ADR と版ずれのテストで縛る
- 手で動かした承認のうち `after` の無い 2 項以上の計画を一直線で読む特例: 計画の読み方が経路で変わる。壊れた計画は判定の側の検査で止まる
