# `nudge-rule-check` — `.ccnavi/common/rules.yml` に足す 1 件

編集がたまったところで、溜めた決まり（`CLAUDE.md`・`rules.yml`・`docs/adr/`・`CONTEXT.md`）との
突き合わせを勧告するルール。親チケット i0055 のフェーズ 3（staging）の成果物。

`.ccnavi/common/rules.yml` は `deny:guard-ccnavi-config` で保護されていて、エージェントは書けない。
**写すのは人。** この 1 枚は「写せば済む全文」と「写し方」と「写したあとの確かめ方」を持つ。

---

## 1. 写す全文

`.ccnavi/common/rules.yml` の `allow:` の**いちばん最後**（`prefer-glob` の次）に、この
ブロックをそのまま貼る。インデントは合わせてある。

```yaml
  # 編集がたまったところで、溜めた決まりとの突き合わせを勧める。
  # every: 5 は「渡す回」の刻みで、5・10・15… 件目の編集で文が届く。
  # 文面をここに直書きしているのは、配布先にファイルが無いと黙って何も渡らない
  # additionalContextFile の事故を避けるため（判断の根拠は下の §2）。
  - id: nudge-rule-check
    match: Write|Edit|NotebookEdit
    glob: "*"
    every: 5
    additionalContext: |-
      このセッションで 5 件の編集がありました。次の編集へ進む前に、Agent ツールで
      レビューをバックグラウンドに出してください。

      見てほしい観点を、この順で:

      1. 蓄積された決まりに沿っているか。読む先は CLAUDE.md（作業の進め方）、
         .ccnavi/common/rules.yml（判定の決まり）、docs/adr/（過去の決定）、
         CONTEXT.md（用語）。触った場所に関係する ADR を grep で絞ってから読む。
         沿っていない箇所は、どの決まりのどの行に反するかを名指しする
      2. 過去の決定を、理由を知らずに覆していないか。ADR が「やらない」と書いたことを
         やり直していたら、その ADR 番号を挙げる
      3. 決まりのほうが古くなっている可能性。反していると見えた箇所が正しく、
         決まりを直すべきなら、そう書く

      指摘は「どのファイルのどの行が、どの決まりに、どう反するか」の形で返す。
      決まりを名指しできない指摘は返さない。
```

欄の読み方（親チケット i0055 で決めたもの）:

| 欄 | 何を言っているか |
|---|---|
| `match: Write\|Edit\|NotebookEdit` | ツール名。`Bash` は入れない。シェルやビルドが書いたぶんは数えない |
| `glob: "*"` | 対象を絞らない。`CLAUDE.md` や `docs/adr/` を直しているときにも出す（§4 の判断 A） |
| `every: 5` | 「渡す回」の刻み。当たった回数が 5 の倍数になった回だけが渡す回 |
| `additionalContext` | 渡す回のたび。つまり 5・10・15… 回目。`Once` にしないのは、編集が続いても二度と言わなくなるのを避けるため |

**数えるのは「このルールが当たった回数」で、変わったファイルの本数ではない。** 同じファイルを
5 回直しても 5 と数える。控えは `logs/state/once-<session>-<agent>.json`。文脈はセッションと、
サブエージェントならその 1 回の起動（`agent_id`）で分かれるので、サブエージェントは自分の数えを持つ。

## 2. 文面は `rules.yml` に直書きする（`additionalContextFile` にしない）

親チケット i0055 が「`staging` で決める」とした分かれ道。**直書きを採る。**

| | 直書き（採る） | `additionalContextFile`（採らない） |
|---|---|---|
| 届かない事故 | 起きない | 配布先にファイルが無ければ黙って何も渡らない |
| `rules.yml` の読みやすさ | 20 行ほど伸びる | 伸びない |
| 観点を足すとき | `rules.yml` を開く（保護されていて人が写す） | 別ファイルを直せる（保護の外に置けば、ここだけはエージェントが直せる） |

**届かない事故のほうが重い。** 勧告は「届かなくても誰も困らない」ので、届いていないことに
気づく人が居ない。観点が伸びて `rules.yml` が読みにくくなったら、そのときに外へ出す。

## 3. 写し方と、写したあとの確かめ方

1. **写す。** 人が `.ccnavi/common/rules.yml` を開き、`allow:` の末尾に §1 のブロックを貼る。
   エージェントには書けない（`deny:guard-ccnavi-config`）
2. **`--lint` を掛ける。** error が 0 件のままであること

   ```
   ccnavi --lint
   ```

   warn は §4 を参照。判断 A（`ccnavi/lint.py` を直す）が入るまでは 1 件増える

3. **当たることを見る。** ワークツリーの中のパスを 1 本渡して `nudge-rule-check` が
   ルールの一覧に出ること

   ```
   ccnavi --test Write <ワークツリーの中のパス> --json
   ```

4. **5 回目に届くことを見る。** 実際に 5 件編集して、5 件目のあとに文が届くこと。
   控えは `logs/state/once-<session>-<agent>.json`。鍵は `nudge-rule-check` で、
   値が当たった回数になる。1〜4 件目では何も届かない

**写す前に手元で試したいとき**は、`rules.yml` の写しを追跡しない場所（そのワークツリーの
`scratchpad/`）に作り、`--rules` で差し替えて掛ける。`--rules` は診断（`--lint` / `--test` /
`--explain`）でだけ効き、hook からの判定では無視される。

```
ccnavi --lint --rules scratchpad/rules-draft.yml
```

## 4. `--lint` の warn について（判断 = A）

このルールを写すと、`--lint` が warn を 1 件増やす。実際に掛けて確かめた。

```
warn: nudge-rule-check: 広い allow に additionalContext がある（何にでも当たる）。
      当たるたびに同じ文がコンテキストに積まれる。狭いルールに分けて書く
```

苦情の理屈（`ccnavi/lint.py` の `_broad`）は「`additionalContext` は当たった回ごとに渡るので、
広い allow に書くと毎回積まれる」。**`every: 5` を書いた今、この理屈は事実として成り立たない。**
渡るのは 5 回に 1 度で、それがこのルールの目的そのもの。苦情のほうが `every` を知らない。

**利用者の判断は A。** `_broad` の判定を `every > 1` のときは掛けない。

| | 何をする | 得るもの | 失うもの |
|---|---|---|---|
| **A（採る）** | `_broad` の判定を `every > 1` のときは掛けない。`ccnavi/lint.py` に 1 条件とテスト 1 件 | 苦情が事実と合う。`--lint` の出力に「見なくていい warn」が居座らない | **報告を 1 つ消す方向の変更**。`every: 1000` のような刻みでも広さを咎めなくなる |
| B（採らない） | warn を出たまま受け入れる | 何も足さない。判定の形を変えない | `--lint` に恒久的に「対処しない warn」が 1 件残る。次に warn を見る人が、それを飛ばす習慣を付ける |
| C（採らない） | ルールを狭める（`glob` をソースの下だけに絞る） | warn が消え、lint を触らずに済む | 勧告の対象が狭まる。`CLAUDE.md` や ADR を直しているときには出なくなり、いちばん突き合わせが要る編集を外す |

**A はこのチケット（フェーズ 3 = staging）の外の仕事。** 触るのが `ccnavi/lint.py` と `tests/` で、
このチケットの範囲は `wip/design/*` だけ。`ccnavi/*` と `tests/*` を範囲にした子を別に 1 件立てる。

その子でやること:

- `ccnavi/lint.py`: `_broad` を呼ぶ手前（`additionalContext` を持つ allow を見ている条件）に
  「刻みが 1 以下のときだけ」を足す。`_broad` 自身は触らない（`every` を知らないままにする）
- `tests/config/`: `every: 5` の広い allow が warn を出さないこと、`every` の無い
  同じルールは今までどおり warn を出すこと、の 2 件

**子が入るまでは warn が 1 件出る。** 写すのを待つ必要は無い（error は増えない）。

## 5. 写したあとに何が変わるか

**得るもの**

- 親 i0055 の目的が、初めて実際に動く。ここまでの 3 フェーズは器を作っただけで、勧告は 1 度も出ていない
- `every` が本番の設定で 1 件使われる。使われない欄は次の改修で壊れても気づけない

**失うもの**

- **5 件編集するごとに、全セッションのコンテキストが文面のぶん減る。** 20 行ほどが
  5・10・15 件目に入る。短い作業では出ないが、長い作業では何度も入る
- **要らない場面でも出る。** 文字を 1 つ直しただけの 5 件でも、突き合わせを勧める。
  当たるのは編集の回数であって、変更の大きさではない
- **勧告に従うかはモデル次第。** 止めないルールなので、無視されても記録に「無視した」は残らない
- **シェルやビルドが書いたぶんは数えない。** `match` がツール名なので、`Bash` を書かない限り当たらない

**戻し方**: `rules.yml` から §1 のブロックを消すだけ。控え（`logs/state/once-*.json`）に
残った `nudge-rule-check` の数えは、当たるルールが無くなれば読まれない。
