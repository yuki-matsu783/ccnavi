# `{!root}` — ワークスペース外を指す合言葉の設計

親チケット i0061 / フェーズ 1（design）の成果物。実装はこの文書の決定に従う。

**版**: 敵対的レビュー（3 本）の指摘を反映した第 2 版。何を直し、何を退けたかは §11。

## 1. 目的

ルールファイルで「ワークスペースの外」を書けるようにする。いま書けるのは
「外の置き場を名指しする」形までで（`outside-temp` が一時ディレクトリを 4 環境ぶん
列挙している）、列挙に無い場所は素通りする。

書けない理由は 2 つ重なっている。

1. `(?!...)` は契約で禁止されている（[rules.py](../../ccnavi/rules.py) の `_UNSUPPORTED`）
2. `{root}` は読み込み時にエスケープ済みの 1 塊として埋まるので、ルールを書く側が
   1 文字ずつに割って否定を組み立てられない

どちらもルールを書く側の都合では外せない。**展開する側（実行ファイル）が、
先読みを使わない等価な式を作って渡す**のが、契約を崩さずに済ませる唯一の道。

## 2. 決定 1 — 展開の契約

### 2.0 展開元のルートの正規化【レビューで追加】

展開の前に、ルートを次の順で正規化する。**この 2 手を飛ばすと判定が全面的に壊れる**
（§11 の指摘 B）。

```python
real = os.path.realpath(root).rstrip("\\/")
```

1. `os.path.realpath` で解く
2. **末尾の区切りを落とす（`rstrip("\\/")`）**

既存の `rules.root_pattern`（[rules.py:130-139](../../ccnavi/rules.py#L130-L139)）が
まったく同じ 2 手を踏んでいる。`{!root}` だけ違う扱いにしない。

末尾の区切りを落とさないと何が起きるか。ルートの最後の文字が区切りだと、
それを「同じ」の側で消費した直後に最内の `[^\\/]` へ落ち、**ルート直下の普通の
ファイル名が「外」と判定される**。実測で確認した。

```
root='C:\Users\…\ccnavi\'  path='C:\Users\…\ccnavi\README.md'  -> 外（誤り）
root='C:\'                 path='C:\README.md'                  -> 外（誤り）
```

これは机上の話ではない。**Windows では `os.path.realpath('/')` が `'C:\\'` を返す**ので、
ドライブ直下をワークスペースにした環境は必ず踏む。`rstrip` を入れると `C:` になり、
`C:\README.md` は「中」、`C:-fork\x.md` は「外」と正しく判定される（実測で確認）。

**ルートが `rstrip` の結果として空文字になる場合**（ルートが `\` や `/` だけ）は、
展開せずに §4 の失敗として扱う。ルートが無いのと同じで、「外」が定義できない。

### 2.1 形

正規化したルートを 1 文字ずつ「ここで終わる／ここが違う／ここは同じ」の入れ子に分解する。

```
root = C:\Users\…
 ↓
^(?:\Z|[^c]|c(?:\Z|[^:]|:(?:\Z|[^\\/]|[\\/](?:\Z|[^u]|u(?:…)))))
      └─┘ └──┘ └──────────────┘
   ルートより上  綴りが違う      同じなら次の文字へ
```

最内（ルートを全部なぞり切った先）は `(?:\Z|[^\\/])` を置く。

**`$` ではなく `\Z` を使う**【レビューで変更】。Python の `$` は文字列の末尾だけでなく
「末尾がちょうど 1 個の改行で終わるときの、その直前」にも当たる。ここで言いたいのは
「文字列がここで終わる」なので `\Z` が正確。

ただし**実測では `$` と `\Z` で判定が変わる入力を作れなかった**（末尾に改行が付いた
綴りは、どちらでも「違う」側の `[^\\/]` が改行を食って同じ答えになる）。
挙動を変えるためではなく、式が意図どおりの意味を持つようにするための変更である。

### 2.2 規則

| ルートの文字 | 「違う」の側 | 「同じ」の側 |
|---|---|---|
| 区切り（`\` または `/`） | `[^\\/]` | `[\\/]` |
| それ以外の 1 文字 `c` | `[^` + `re.escape(c)` + `]` | `re.escape(c)` |

### 2.3 何を「外」と数えるか

| 綴り | 判定 | 効かせ方 |
|---|---|---|
| `C:\Users\u\Desktop\git\other\x.md` | 外 | 途中で「違う」に落ちる |
| `C:\Users\u\Desktop` | 外（ルートより上） | 各段の `\Z` |
| `C:\Users\u\Desktop\git\ccnavi-fork\x.md` | 外（前置きが一致して続く） | 最内の `[^\\/]` |
| `C:\Users\u\Desktop\git\ccnavi\README.md` | 中 | 最内が区切りなので落ちない |
| `C:/Users/u/Desktop/git/ccnavi/README.md` | 中 | 区切りはどちらの綴りにも当てる |
| `c:\users\u\desktop\git\ccnavi\readme.md` | 中 | 下の 2.4 |
| **`C:\README.md`（ルートが `C:\` のとき）** | **中** | **§2.0 の `rstrip` が要る** |
| **`C:\Users\u\Desktop\git\ccnavi`（対象がルートそのもの）** | **中** | **最内に `\Z` を置かない**【実装で追加】 |

**最後の行は第 1 版に無かった**【実装で追加】。そのために最内を
`(?:\Z|[^\\/])` と書いてしまい、ルートを最後までなぞり切った位置で文字列が終わると
「外」に落ちる欠陥が生まれた。敵対的レビューで見つかった。

机上の話ではない。`Glob` を `path` 省略で呼ぶと対象が cwd になり、cwd が
ワークスペースルートのセッションでは**対象がちょうどルートと一致する**。
「ワークスペースの外を読ませない」という自然な使い方で、いちばん普通の呼び出しが
誤判定される。

各段の `\Z` は「ルートより上」を拾うためのもので、最内とは意味が違う。

### 2.4 `re.IGNORECASE` の下での否定

ルールは式ごと大文字小文字を区別せずに当てる（[ADR-0051](../../docs/adr/0051-regex-ignores-case.md)）。
`[^c]` は `C` にも当たらなくなるので、**「違う」の側が狭まり、「中」と数える範囲が広がる**。

これは意図した挙動として明記する。綴りだけが違うパスは Windows でも macOS でも
**同じ場所**なので、「中」と数えるのが正しい。ADR-0051 は `main-tree` の `[^c\\/]` に
ついて同じ論法で「囲んでいない」と前例を作っており、そこに揃える。`(?-i:...)` で囲まない。

**既知の例外**【レビューで追加】。`re.IGNORECASE` は Unicode の畳み込みを行うので、
**トルコ語の `İ`（U+0130）と `ı`（U+0131）を ASCII の `I` / `i` と同一視する**。
ファイルシステムは一般にこれらを同一視しないので、`taniyama` と `tanİyama` は
別の場所なのに「中」と判定される（実測で確認）。

これは受け入れる。理由は 2 つ。

- 外れる向きが「中と数える」＝ このルールが**当たらなくなる**向きで、
  `deny: ^{!root}` の文脈では「外なのに止めない」という素通りになる。ただし
  それを踏むには、ルートの綴りにトルコ語の I 系を混ぜた**別のディレクトリを
  作る**必要があり、攻撃としては `ccnavi-fork` を作るのと同じ難度でありながら、
  そちらは正しく「外」と判定される
- `(?-i:...)` で囲むと、ADR-0051 が避けた「機械によって判定が割れる」ほうへ戻る

対照として、ギリシャ文字の終端シグマ（`ς`/`σ`）、ドイツ語の `ß`/`ss`、全角の `ｃ`/`c` は
いずれも正しく「外」（別物）と判定される（実測で確認）。

### 2.5 展開結果が守るべきこと

- 繰り返し（`+` `*` `{n,}`）を含まない
- 先読み・後読み・後方参照を含まない
- 各段の選択肢は最初の 1 文字でほぼ排他。戻りは即座に失敗する

**「ほぼ」と書く理由**【レビューで修正】。末尾の改行がある位置では `\Z` の分岐と
「違う」の分岐が同時に成立しうるので、文字どおりの排他ではない。実測では
指数的な伸びは観測されず（ルート 266 字・当てる綴り 2,250 字で 1 回 23〜33 マイクロ秒）、
実務上の問題は無い。

**自己点検は `_unsupported` では足りない**【レビューで修正】。`_unsupported`
（[rules.py:460-466](../../ccnavi/rules.py#L460-L466)）が見るのは 4 つのリテラルと
`\1`〜`\9` だけで、**繰り返し演算子を一切見ていない**。上の 1 つ目を守るには、
「展開結果に `*` `+` `{n,}` が現れないこと」を見る別の検査を足す。`_unsupported` に
掛け直すだけでは名ばかりの安全網になる。

### 2.6 層との関係【レビューで追加】

`{!root}` の展開先は、既存の `{root}` と同じく**ワークスペースルートで固定**する。
共通層・自身の層・プロジェクトの層のどこに書かれたルールでも変わらない
（`ruleload` は全層に同じ `root` を渡す）。プロジェクトのルートを指したいという
要求は、この合言葉では扱わない。

### 2.7 なぜ入れ子か（平ら型を採らない理由）

前置きを 1 文字ずつ伸ばして並べる平ら型（`^(?:[^c]|c[^:]|c:[^\\/]|…)`）は式の長さが
ルートの長さの 2 乗で伸びる。実測で 436 字のルートに対し 141,365 字・組み立て 481 ms、
836 字で 505,245 字・1,853 ms（PreToolUse の期限 3 秒に手が届く）。

入れ子型は線形。実測は §5。

## 3. 決定 2 — 書ける場所

### 3.1 `regex` 専用【レビューで追加】

**`{!root}` は `regex` にしか書けない。`glob` に書かれていたら `--lint` の error。**
親の提案が「決まっていること」として確定済みの制約であり、設計で覆さない。

`glob` は fnmatch に翻訳されてから当てるので、入れ子の選択肢を持つ展開結果を
埋める場所が無い。

### 3.2 置ける位置

**`{!root}` は `^` の直後にのみ書ける。1 つの式に 1 回だけ。** 違反は `--lint` の **error**。

```yaml
regex: '^{!root}'                 # 可
regex: '^{!root}.*\.py$'          # 可
regex: '^{!root}[\\/]foo'         # 可だが warn（下記）
regex: 'x{!root}'                 # 不可。error
regex: '^{!root}a{!root}'         # 不可。error
regex: '^{!root}?'                # 不可。error（下記）
```

**直後に量化子は書けない**【実装で追加】。`?` `*` `+` `{` が続いたら error。

第 1 版にはこの規則が無かった。敵対的レビューで、`^{!root}?` と書くと
**展開結果ごと省略できる式になり、どの対象にも当たる deny になる**ことが分かった。
「外だけを止める」はずのルールが、ワークスペースの中への書き込みまで止める。

位置の規則（`^` の直後、1 回だけ）だけでは通ってしまい、§3.3 の warn も
量化子かどうかは見ない。error にしないと本番の `rules.yml` に入る。

### 3.3 後ろに続く式の扱い【レビューで修正】

第 1 版は `^{!root}.*\.py$` を「可」、`^{!root}[\\/]foo` を「不可」と書いていたが、
**その 2 つを区別する規則を書いていなかった**。lint が実装できない約束だったので直す。

区別は意味の問題で、機械には判定できない。展開結果が食い終わる位置は綴りによって
変わるので、そこがパスの区切りである保証は無い。だから:

- **error にするのは位置だけ**（`^` の直後、1 式に 1 回、`regex` のみ）
- **後ろに式が続くのは許す。** ただし、続く式の先頭が「どこへでも飛ぶ」構文
  （`.*` / `.+` / `[\s\S]*`）**でない**場合は `--lint` の **warn** にする。
  文面は「`{!root}` が食い終わる位置はパスの区切りとは限らない。
  区切りを当てにした綴りは意図どおりに動かない」

warn であって error ではないのは、`^{!root}[\\/]foo` が「意味は薄いが壊れてはいない」
書き方だから。止めるほどではないが、書いた人はまず勘違いしている。

## 4. 決定 3 — ルートが長すぎるとき

### 4.1 閾値

**正規化したルートの長さが 256 字以上なら生成しない。**

| 根拠 | 数字 |
|---|---|
| Python 3.12（再帰の上限 1000）で `re.compile` が落ちる長さ | **493 字**（`RecursionError`、実装後の再測定） |
| 採る閾値 | 256 字（壁の半分以下） |
| Windows の `MAX_PATH` | 260 字（256 字のルートはその時点で実用にならない） |

**494 という数字は、この文書の §2.1 の形で組み立てたときのもの**【レビューで補強】。
1 文字あたりの入れ子の段数が変われば壁も変わる（レビュアの 1 人は別の組み立て方で
248 字という数字を出した）。実装が §2.1 と違う形になったら、閾値を測り直す。

再測定で確かめたこと。

- 区切りを含まない `'c'*n` でも、現実的な綴り（`C:\a\bcdefghij…`）でも、落ちる長さは同じ
- **呼び出し時のスタックの深さを 0 / 100 / 300 / 500 段と変えても、落ちる長さは変わらない**。
  「hook は深いスタックから呼ばれるので、もっと短いところで落ちる」という見方は当たらない

**実装後に `\Z` を使う形へ変えたので、落ちる長さは 494 字から 493 字になった**
（`tests/core/bench_not_root.py`）。閾値 256 はどちらでも半分以下で、変える必要は無い。

### 4.2 `RecursionError` を必ず捕まえる【レビューで追加】

閾値で先回りしていても、**`RecursionError` を明示的に捕まえる**。

いまの `_build` は `except re.error` しか書いていない（[rules.py:452-455](../../ccnavi/rules.py#L452-L455)）。
`ruleload.load_rules` は `except (OSError, ValueError)` だけ（[ruleload.py:72-78](../../ccnavi/ruleload.py#L72-L78)）。
`cli.py` は `events.decide(...)` を裸で呼ぶ。つまり `RecursionError` はどこにも
捕まらず、**プロセスが未処理例外で落ちる**。

hook が異常終了したときに呼び出しが通るなら、これは素通りになる。同じコードベースに
前例がある（[shellread.py:936-940](../../ccnavi/shellread.py#L936-L940) が
`RecursionError` を「深さの上限」と同じ扱いに倒している）。それに揃える。

**実装フェーズで確かめること**: Claude Code の hook が終了コード 2 以外の異常終了を
どう扱うか（止めるのか通すのか）。これは ccnavi の外側の契約なので、
このリポジトリのコードでは確かめられない。

### 4.3 生成できないとき — 強い側に倒す

生成できなかったルールは、**そのルールの `match` に並ぶツールの呼び出し全部に当たる**
扱いにする。ただしタイプによって向きを変える。

| タイプ | 生成できないとき | なぜ |
|---|---|---|
| `deny` | `match` の全部に当たる（全部止まる） | 守りが消えるより止まるほうがよい |
| `ask` | `match` の全部に当たる（全部聞く） | 同上。確認は戻せる |
| `allow` | **どれにも当たらない**（＋ error 報告） | 当たる扱いにすると ccnavi が黙る範囲が広がる。緩む側に倒さない |

**これは `{!root}` の生成失敗に限った扱い**【レビューで明確化】。正規表現の書き損じや
`_UNSUPPORTED` 抵触など、既存のあらゆる壊れ方は今までどおり REQ-RUL-08 の
「報告して捨てる」のまま。ここだけ特別扱いするのは、守られなくなる範囲が
「ワークスペースの外の全部」に広がるからで、一般則を変えるものではない。

### 4.4 いまの構造では表現できない【レビューで追加】

**このままでは実装できない。** `_build` の戻り値の型は
`tuple[Rule, None] | tuple[None, Problem]`（[rules.py:372-374](../../ccnavi/rules.py#L372-L374)）で、
Rule と Problem を同時に返す道が無い。`parse` のループは Problem が付いた回を
`continue` で飛ばす（[rules.py:362-367](../../ccnavi/rules.py#L362-L367)）。
`Rule.matches()` は `compiled is None` なら常に `False`。

つまり既存の流儀をなぞって実装すると、**生成に失敗した deny が黙って消え、
設計の意図と真逆の素通りになる**。実装フェーズで次のどちらかを選ぶ。

- **案 1**: `_build` の戻り値を `tuple[Rule | None, Problem | None]` に広げ、
  `parse` が「Problem を出しつつ Rule も採る」経路を持つ
- **案 2**: 生成に失敗したときだけ、`match` の全部に当たる catch-all の `compiled` を
  持った Rule を作って返す（Problem は別に足す）

どちらも既存の呼び出し側に影響するので、実装フェーズの最初に決める。

### 4.5 文面

止められた側に、何が起きていて誰が何をすれば直るかを返す。ルール自身の `message` は
「外への書き込みです」としか言わないので、それでは直せない。展開に失敗したときは
別の文面を返す。

**書いた文面は残す**【実装で変更】。第 2 版は「`message` を差し替える」と書いていたが、
それでは人が書いた文面が消える。`Rule` のコメント自身が「書いた文面は置き換えずに持つ。
報告と `--explain` は書いた綴りを出す」と決めている。実装では `degraded_message` を
別に持ち、`spoken_message()` がそちらを優先する形にした。

**層ごとに名指しするのは、構造上できなかった**【実装で変更】。第 2 版は
「実際に壊れているルールファイルの綴りを名指しする」としていたが、`_build` は
ファイルパスを引数に持たず、`rule.source`（層名）は `ruleload.mark_source` が
`parse` の**後**に設定する。`_build` の時点では、どのファイルかを知る手立てが無い。

実装では決め打ちを避け、「このルールが書かれているルールファイルから外してもらってください」
という一般的な言い方にした。**設計の要求は満たせていない。** 満たすには `_build` に
ファイルの情報を渡す変更が要るので、必要なら別チケットにする。

```
ワークスペースルートの綴りが長すぎて（312 字）、ルール 'outside-workspace' の
「ワークスペースの外」を組み立てられませんでした。守りが消えるのを避けるため、
このルールが見るツール（Write / Edit / NotebookEdit）を止めています。
ワークスペースをもっと浅い場所へ移すか、利用者に
<実際に壊れているルールファイルの綴り> からこのルールを外してもらってください。
```

### 4.6 記録 — 新しい欄は足さない【実装で変更】

**当初は `logs/log.jsonl` に `root-too-long` を残すつもりだったが、足さないことにした。**

`audit` の `REASON_*` は「判定に至らなかった理由」を並べる欄で、`deadline-exceeded` も
`payload-unusable` もそこに属する。今回は**判定に至っている**（deny する）ので、
同じ欄に置くと意味の違うものが混ざる。`audit.py` のコメント自身が
「ルールが読めないことは、ここには無い」と断っている。

記録には `deny` と当たったルールの id が既に残り、なぜ止めたかは §4.5 の文面が言う。
足りないものは無い。

### 4.7 `dry-run`

既存のモードの扱いに揃える。`dry-run` では止めず、`additionalContext` に
「`enable` なら止めていた」と理由を並べて終了コード 0。

## 5. 実測

ルートは `C:\Users\taniyama\Desktop\git\ccnavi`（36 字）。

## 6. 決定 4 — fail-closed からの回復

**回復は利用者の手作業のみ。逃げ道の env は作らない。**（利用者の判断）

ルートが 256 字以上の機械では `Write` / `Edit` / `NotebookEdit` が全部止まる。
`.ccnavi/common/rules.yml` は `guard-ccnavi-config` と組み込みの
`builtin-guard-common-layer` に守られているので、**エージェントには外せない**。
外すのは利用者。

この 1 件だけを降ろす env（`CCNAVI_GUARD_NOT_ROOT=disable` のような形）は**作らない**。
作ると「止まったら env で外す」が手順になり、守りを外す道がルールを直す道より
安くなる。`CCNAVI_MODE=dry-run` で全部降ろす道は既に在るが、それは
「守りを全部降ろしている」と自分で分かる形をしている。

### 6.1 止まる前に言う — 何もしないことにした【実装で変更】

**結論から: SessionStart では何も言わない**（利用者の判断）。

256 字のルートは Windows の `MAX_PATH`（260）の外で、その時点で実用にならない。
踏む人はまずいない。踏んだときは §4.5 の文面が理由と直し方を言う。
めったに起きないことのために SessionStart を毎回重くする取引はしない。

以下は、そう決めるまでに分かったこと。

第 1 版は「SessionStart でルールを読んだ時点でルート長は分かる」と、既に起きて
いることのように書いていた。**これは誤り。** `events.decide_at_start` は
`selfguard.at_start` と `reasons.ways_of_working` しか呼んでおらず、ルールを
読んでいない。新しく足す必要がある。

足すもの、と代償。

- ルート長そのもの（`len(os.path.realpath(root).rstrip("\\/"))`）は SessionStart でも
  すぐ計算できる。これは安い
- しかし「どのルールが `{!root}` を使っていて、どの層のどのファイルにあるか」を
  知るには、**共通層に加えて自身の層と全プロジェクトの層をこの時点で読む**必要がある。
  `ruleload.load_rules` は共通層しか読まず、他の層は「行き先のツリー」が決まってから
  読む仕組みで、SessionStart にはその決定材料が無い
- 全層を読むのは SessionStart の実行時間に効く（hook の期限は 10 秒）

**実装フェーズで決めること**: ルート長だけで「危ない」と言うに留めるか、
全層を読んでファイルまで名指しするか。前者は安いが不親切、後者は親切だが
SessionStart が重くなる。§4.5 の文面（層を名指しする）は判定の側の話なので、
そちらとは分けて考える。

## 9. この設計で得るもの・失うもの

**得るもの**

- 「中でなければ外」が書け、名指しの列挙が漏れる問題が消える
- 展開結果が既存の契約（先読み無し・繰り返し無し）を崩さない
- 判定の費用が実測済みで、期限に対して 5 桁の余裕がある
- 失敗が緩む側に落ちない

**失うもの**

- 語彙が 1 つ増える。`--explain` に出す式は 475 字になるので、書いた綴りのほうを
  出す実装が要る
- 合言葉なのに `{root}` と性質が違う（`glob` に書けない、前に置けない、
  直後の綴りが意味を持たない）。error と warn で補うが、覚えることは増える
- 組み立てが毎回 +2 ms。`{!root}` を使うルールの本数だけ積まれる
- ルートが 256 字以上の機械では、利用者が手で直すまで書き込みが全部止まる
- `_build` / `parse` の構造に手を入れる必要があり、他のルールの読み込み経路にも影響する

**やらない場合**

`outside-temp` のように場所を列挙し続ける。漏れは残るが範囲は目で読める。

## 10. 使う人への手引き【レビューで追加】

第 1 版は「実際のルールを置くのは範囲外」で終えていたが、それでは
(a) 誰も怖くて使わず機構が死重量になるか、(b) 誰かが素朴に置いて運用を壊すか
のどちらかになる。道具と一緒に、最低限の注意を残す。

**`deny: ^{!root}` を素朴に置いてはいけない。** 次が全部塞がる。

| 塞がるもの | なぜ困るか |
|---|---|
| セッションのスクラッチパッド | CLAUDE.md が「ワークツリーがまだ無いときは」の逃げ道として明示的に指している |
| 他リポジトリの参照・clone | `projects/` の外に置いた参照用のツリー |
| 他ツールの出力先 | 一時ディレクトリに吐くものを指定する場面 |

**使うなら `match` を絞る。** 「外への書き込みを止める」なら
`match: Write|Edit|NotebookEdit` にして `Read` は残す。読む手を取り上げると、
外に吐かれたものを確かめられなくなる。

**セッションのスクラッチパッドを許したいなら、`{!root}` は向いていない。**
`{!root}` は 1 つの否定しか持てず、そこに例外を彫る手が無い。例外が要るなら
`outside-temp` のような名指しのルールのほうが適している。**この選択自体が、
この機能を使う前に決めるべきこと。**

### 10.1 このチケットで扱わないもの

- `{!root}` を使った実際のルールを `rules.yml` に置くこと
- シンボリックリンクを解いた後の綴り、UNC パス（`\\server\share\…`）、
  ドライブ相対の綴り（`C:foo`）の扱い。実測していない。実装フェーズで
  `os.path.realpath` が何を返すかを確かめ、必要なら別チケットにする
