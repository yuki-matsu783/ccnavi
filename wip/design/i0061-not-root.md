# `{!root}` — ワークスペース外を指す合言葉の設計

親チケット i0061 / フェーズ 1（design）の成果物。実装はこの文書の決定に従う。

## 1. 目的

ルールファイルで「ワークスペースの外」を書けるようにする。いま書けるのは
「外の置き場を名指しする」形までで（`outside-temp` が一時ディレクトリを 4 環境ぶん
列挙している）、列挙に無い場所は素通りする。

書けない理由は 2 つ重なっている。

1. `(?!...)` は契約で禁止されている（[rules.py](../../ccnavi/rules.py) の `_UNSUPPORTED`）
2. `{root}` は読み込み時にエスケープ済みの 1 塊として埋まるので、ルールを書く側が
   1 文字ずつに割って否定を組み立てられない

どちらもルールを書く側の都合では外せない。**展開する側（実行ファイル）が、
先読みを使わない等価な式を作って渡す**のが、契約を崩さずに済ませる唯一の道。

## 2. 決定 1 — 展開の契約

### 2.1 形

ルートの実パス（`os.path.realpath` で解いたもの）を 1 文字ずつ
「ここで終わる／ここが違う／ここは同じ」の入れ子に分解する。

```
root = C:\Users\…
 ↓
^(?:$|[^c]|c(?:$|[^:]|:(?:$|[^\\/]|[\\/](?:$|[^u]|u(?:…)))))
      └┘ └──┘ └──────────────┘
   ルートより上  綴りが違う      同じなら次の文字へ
```

最内（ルートを全部なぞり切った先）は `(?:$|[^\\/])` を置く。

### 2.2 規則

| ルートの文字 | 「違う」の側 | 「同じ」の側 |
|---|---|---|
| 区切り（`\` または `/`） | `[^\\/]` | `[\\/]` |
| それ以外の 1 文字 `c` | `[^` + `re.escape(c)` + `]` | `re.escape(c)` |

### 2.3 何を「外」と数えるか

| 綴り | 判定 | 効かせ方 |
|---|---|---|
| `C:\Users\u\Desktop\git\other\x.md` | 外 | 途中で「違う」に落ちる |
| `C:\Users\u\Desktop` | 外（ルートより上） | 各段の `$` |
| `C:\Users\u\Desktop\git\ccnavi-fork\x.md` | 外（前置きが一致して続く） | 最内の `[^\\/]` |
| `C:\Users\u\Desktop\git\ccnavi\README.md` | 中 | 最内が区切りなので落ちない |
| `C:/Users/u/Desktop/git/ccnavi/README.md` | 中 | 区切りはどちらの綴りにも当てる |
| `c:\users\u\desktop\git\ccnavi\readme.md` | 中 | 下の 2.4 |

### 2.4 `re.IGNORECASE` の下での否定

ルールは式ごと大文字小文字を区別せずに当てる（[ADR-0051](../../docs/adr/0051-regex-ignores-case.md)）。
`[^c]` は `C` にも当たらなくなるので、**「違う」の側が狭まり、「中」と数える範囲が広がる**。

これは意図した挙動として明記する。綴りだけが違うパスは Windows でも macOS でも
**同じ場所**なので、「中」と数えるのが正しい。ADR-0051 が警告している
「否定は区別せずに当てると除外の側が広がる」に当たるが、ここではその広がる先が
正しい答えと一致している。`(?-i:...)` で囲まない。

### 2.5 展開結果が守るべきこと

- 繰り返し（`+` `*` `{n,}`）を含まない
- 先読み・後読み・後方参照を含まない
- 各段の選択肢は最初の 1 文字で排他。戻る余地が無い

`_unsupported` は**書かれた綴り**に対して走るので、展開結果は検査を通らない。
**契約を守る責任は展開側にある。** 展開結果を `_unsupported` に掛け直す自己点検を
実装に入れる（費用は組み立て時の 1 回だけ）。

### 2.6 なぜ入れ子か（平ら型を採らない理由）

前置きを 1 文字ずつ伸ばして並べる平ら型（`^(?:[^c]|c[^:]|c:[^\\/]|…)`）は式の長さが
ルートの長さの 2 乗で伸びる。実測で 436 字のルートに対し 141,365 字・組み立て 481 ms、
836 字で 505,245 字・1,853 ms（PreToolUse の期限 3 秒に手が届く）。

入れ子型は線形。実測は §5。

## 3. 決定 2 — 置ける位置

**`{!root}` は `^` の直後にのみ書ける。1 つの式に 1 回だけ。** 違反は `--lint` の **error**。

理由。展開結果は「先頭から、外だと確定するところまで」を食う式で、食う長さは
綴りによって変わる。だから前に何かを置くことも、直後に特定の綴りを続けることも
意味を持たない。

```yaml
regex: '^{!root}'                 # 可
regex: '^{!root}.*\.py$'          # 可。外にある .py（下記）
regex: '^{!root}[\\/]foo'         # 不可。error
regex: 'x{!root}'                 # 不可。error
```

**後ろに式が続くのは許す。** 展開結果が食い終わった位置から続きを当てられるので、
`^{!root}.*\.py$`（外にある `.py`）のような絞り込みは意味を持つ。
`.*` が入っても、前半に viable な経路が 1 本しか無いため戻りは即座に失敗する。

案 C（式全体が `^{!root}` と完全一致することを要求）は採らない。上の絞り込みまで
禁じることになり、得るものが無い。

## 4. 決定 3 — ルートが長すぎるとき

### 4.1 閾値

**解いたルートの長さが 256 字以上なら生成しない。**

| 根拠 | 数字 |
|---|---|
| Python 3.12（再帰の上限 1000）で組み立てが落ちる長さ | **494 字**（`RecursionError`） |
| 採る閾値 | 256 字（壁の半分以下） |
| Windows の `MAX_PATH` | 260 字（256 字のルートは時点で実用にならない） |

壁の直前ではなく半分で止めるのは、Python の版が変わって再帰の上限が動いたときに
黙って壊れないため。閾値は定数として 1 か所に置き、由来をコメントに書く。

### 4.2 `--lint`

**error** でルールを名指しする。文面はルート長を実数で出す。

```
error: outside-workspace: ワークスペースルートが長すぎて `{!root}` を組み立てられない（312 字 / 上限 255 字）
```

### 4.3 実行時 — 強い側に倒す

生成できなかったルールは、**そのルールの `match` に並ぶツールの呼び出し全部に当たる**
扱いにする。ただしタイプによって向きを変える。

| タイプ | 生成できないとき | なぜ |
|---|---|---|
| `deny` | `match` の全部に当たる（全部止まる） | 守りが消えるより止まるほうがよい |
| `ask` | `match` の全部に当たる（全部聞く） | 同上。確認は戻せる |
| `allow` | **どれにも当たらない**（＋ error 報告） | 当たる扱いにすると ccnavi が黙る範囲が広がる。緩む側に倒さない |

一言でいうと「**強い側に倒す**」。既存の `deadline-exceeded`（遅延が許可に化けないための
先回り）と同じ考え方で、新しい思想を持ち込まない。

### 4.4 文面

止められた側に、何が起きていて誰が何をすれば直るかを返す。ルール自身の `message` は
「外への書き込みです」としか言わないので、それでは直せない。展開に失敗したときは
`message` を差し替える。

```
ワークスペースルートの綴りが長すぎて（312 字）、ルール 'outside-workspace' の
「ワークスペースの外」を組み立てられませんでした。守りが消えるのを避けるため、
このルールが見るツール（Write / Edit / NotebookEdit）を止めています。
ワークスペースをもっと浅い場所へ移すか、利用者に .ccnavi/common/rules.yml から
このルールを外してもらってください。
```

### 4.5 記録

`logs/log.jsonl` に `root-too-long` を残す。既存の `deadline-exceeded`・
`payload-unusable`・`worktree-unreadable` と同じ欄に置く。

### 4.6 `dry-run`

既存のモードの扱いに揃える。`dry-run` では止めず、`additionalContext` に
「`enable` なら止めていた」と理由を並べて終了コード 0。

## 5. 実測（親の提案から移送）

ルートは `C:\Users\taniyama\Desktop\git\ccnavi`（36 字）。

| | 式の長さ | 組み立て | 1 回の判定 |
|---|---|---|---|
| 既存の `main-tree` | 143 字 | — | 0.81 μs |
| 既存の `outside-temp` | 159 字 | — | 2.28 μs |
| **入れ子型（採用）** | 475 字 | **2.03 ms** | **3.47 μs** |
| 平ら型（不採用） | 1,485 字 | 3.19 ms | 8.21 μs |

- 判定 3.47 μs は PreToolUse の期限 3 秒の 0.0001%
- ルート 236 字でも 21.85 μs。**比例して伸びるだけ**で爆発しない
- 組み立ては毎プロセス走る。今の `rules.yml` 一式の読み込み 24.29 ms に対して **+8%**

## 6. 決定 4 — fail-closed からの回復

**回復は利用者の手作業のみ。逃げ道の env は作らない。**（利用者の判断）

ルートが 256 字以上の機械では `Write` / `Edit` / `NotebookEdit` が全部止まる。
`.ccnavi/common/rules.yml` は `guard-ccnavi-config` と組み込みの
`builtin-guard-common-layer` に守られているので、**エージェントには外せない**。
外すのは利用者。

この 1 件だけを降ろす env（`CCNAVI_GUARD_NOT_ROOT=disable` のような形）は**作らない**。
作ると「止まったら env で外す」が手順になり、守りを外す道がルールを直す道より
安くなる。`CCNAVI_MODE=dry-run` で全部降ろす道は既に在るが、それは
「守りを全部降ろしている」と自分で分かる形をしている。

### 6.1 止まる前に言う

止まってから気づくのは高い。**SessionStart の時点で報告する。**

- SessionStart でルールを読んだ時点でルート長は分かる
- 「ルート `<綴り>` は 312 字。ルール `outside-workspace` が組み立てられないため、
  Write / Edit / NotebookEdit を止めている。利用者が `.ccnavi/common/rules.yml` から
  外すか、ワークスペースを浅い場所へ移す必要がある」と出す
- これは案内であって、判定は 4.3 のまま

## 7. 決定 5 — 要件と ADR

### 7.1 `requirements.md` に 2 件足す（§2.3 REQ-RUL）

| ID | 型 | 要求 |
|---|---|---|
| REQ-RUL-09 | 常時 | ccnavi は、ワークスペースルートの外を指す条件を、ルートの綴りを書かずにルールファイルから宣言できること |
| REQ-RUL-10 | 異常時 | もしその条件を組み立てられないならば、ccnavi は、そのルールが対象とするツールの呼び出しを、緩むことのない側へ倒して扱い、組み立てられなかったことを示すこと |

REQ-RUL-10 は REQ-RUL-08（解釈できないルールを黙って飛ばさない）より強い。
REQ-RUL-08 は「報告すること」までで、飛ばした結果できた穴には触れていない。
`{!root}` は穴の大きさが「ワークスペースの外の全部」になるので、報告だけでは足りない。

### 7.2 ADR を 1 枚足す

`docs/adr/0055-not-root-placeholder.md`。ルールファイルの語彙が増えるのは
ADR-0032（`{root}` の導入）と同じ格なので、足す側に倒す。

書くこと: 先読みを禁じたまま否定を表現する手段として展開を選んだこと、
入れ子型を選び平ら型を捨てたこと、閾値 256 の由来、失敗を強い側に倒すこと。

**`docs/adr/` には既に 0051 が 2 枚ある**（`0051-regex-ignores-case.md` と
`0051-review-in-chat.md`）。0055 が空いていることは確認済みだが、実装フェーズで
もう一度見ること。

## 8. 実装への申し送り

| 置き場 | 足すもの |
|---|---|
| `ccnavi/rules.py` | `NOT_ROOT_PLACEHOLDER = "{!root}"`、展開関数、位置の検査、256 字の検査、展開結果の自己点検 |
| `ccnavi/rules.py` `_build` | タイプ別の倒し方（4.3）。`deny` / `ask` は全部に当たる式へ、`allow` は当たらない扱い |
| `ccnavi/lint.py` | 256 字の error、位置違反の error |
| `ccnavi/cli.py` ほか | SessionStart の報告（6.1）、記録の `root-too-long` |

### テストの観点（フェーズ 2 の acceptance へ）

1. 展開の正しさ — §2.3 の 6 通り全部
2. 区切りの綴り（`\` と `/`）、末尾に区切りが付いたルート
3. 前置きが一致して続く綴り（`ccnavi-fork`）
4. ルートより上、別ドライブ、ルートと無関係な絶対パス
5. 綴り違い（全部小文字）が「中」になること
6. 展開結果が `_unsupported` を通ること（繰り返しも先読みも含まない）
7. 256 字ちょうど（error）と 255 字（通る）の境界
8. 生成失敗時に `deny` / `ask` / `allow` がそれぞれ 4.3 のとおりに倒れること
9. `dry-run` で止まらず `additionalContext` に出ること
10. `^{!root}.*\.py$` が意味どおりに当たること、`^{!root}[\\/]foo` が error になること

## 9. この設計で得るもの・失うもの

**得るもの**

- 「中でなければ外」が書け、名指しの列挙が漏れる問題が消える
- 展開結果が既存の契約（先読み無し・繰り返し無し）を崩さない
- 判定の費用が実測済みで、期限に対して 5 桁の余裕がある
- 失敗が緩む側に落ちない

**失うもの**

- 語彙が 1 つ増える。`--explain` に出す式は 475 字になるので、書いた綴り
  （`^{!root}`）のほうを出す実装が要る
- 合言葉なのに `{root}` と性質が違う（前に置けない、直後に綴りを続けられない）。
  lint の error で補うが、覚えることは増える
- 組み立てが毎回 +2 ms。`{!root}` を使うルールの本数だけ積まれる
- ルートが 256 字以上の機械では、利用者が手で直すまで書き込みが全部止まる

**やらない場合**

`outside-temp` のように場所を列挙し続ける。漏れは残るが範囲は目で読める。

## 10. 範囲外（このチケットで扱わないもの）

- **`{!root}` を使った実際のルールを `rules.yml` に置くこと。** 道具を用意するのと、
  それを使って何を止めるかは別の判断。`deny: ^{!root}` を素朴に置くと、他リポジトリの
  参照も他ツールの出力先も、CLAUDE.md がワークツリー前の逃げ道として書いている
  セッションのスクラッチパッドも一度に塞がる
- シンボリックリンクを解いた後の綴り、UNC パス（`\\server\share\…`）、
  ドライブ相対の綴り（`C:foo`）の扱い。実測していない。実装フェーズで
  `os.path.realpath` が何を返すかを確かめ、必要なら別チケットにする
