## いま何がそうなっているか

ルール 1 件が持てる条件は 3 つ（§5.1）。

| 欄 | 何を見るか |
|---|---|
| `match` | ツール名 |
| `glob` / `regex` | 対象の綴り |

**「何回目に当たったか」を見る欄が無い。** 渡す頻度も 2 つしかない。

| いまの欄 | 頻度 |
|---|---|
| `additionalContext` | 当たるたび |
| `additionalContextOnce` | この文脈で最初の 1 回だけ |

一方で、数える器はもう在る。

- `ccnavi/ctxfile.py` の `additionalContextOnce` が「この文脈で初めて当たったときだけ」を実装している
- 控えは `logs/state/once-<session>-<agent>.json`。鍵は `rule.id`
- 文脈はセッションと、サブエージェントならその 1 回の起動（`agent_id`）で分ける
- 返す経路も在る。`ccnavi/hookio.py:134` が PostToolUse で `additionalContext` を返す
- ccnavi は `.claude/settings.json` の `PostToolUse` に**全 matcher で登録済み**。payload は毎回届く

つまり控えの数えを「当たったか」から「何回当たったか」へ広げるだけで、新しい仕組みは要らない。

決まりが溜まっている場所:

| 何の決まりか | 置き場 | 量 |
|---|---|---|
| 作業の進め方 | `CLAUDE.md` | 1 枚 |
| 判定に当てる決まり | `.ccnavi/common/rules.yml` | 1 枚 |
| 過去の決定と、その理由 | `docs/adr/` | 53 枚 |
| 用語 | `CONTEXT.md` | 1 枚 |

`requirements.md` に該当する要求は無い。足すので、要求も 1 行足す。

## 何をするか

### 1. `every: N` を足す（`implement`）

```yaml
- id: nudge-rule-check
  type: allow
  match: Write|Edit|NotebookEdit
  every: 5
  additionalContext: |
    ここまでに 5 件の編集がありました。次へ進む前に、Agent ツールで
    レビューをバックグラウンドに出してください。…
```

決める意味:

- **`every: N` が刻むのは「渡す回」。** 当たった回数が `N` の倍数になった回だけが渡す回になる。
  `every` が無ければ、当たるたびが渡す回
- **2 つの文は、どちらも「渡す回」を基準に読む。**

  | 欄 | いつ渡るか | `every: 5` のとき |
  |---|---|---|
  | `additionalContext` | 渡す回のたび | 5・10・15…回目 |
  | `additionalContextOnce` | 渡す回の最初の 1 回 | **5 回目だけ** |

  `every` を「どちらに掛かるか」ではなく「渡す回の刻み」と決めるので、掛かる先の例外を
  覚えなくてよい。文に続く本文も同じ扱いで、`additionalContextFile` は `additionalContext` に、
  `additionalContextOnceFile` は `Once` に従う
- **`Once` が 1 回目ではなく N 回目に来る。** これが `every` を添えたときの主な変化で、
  「たまったところで 1 度だけ言う」が書けるようになる
- `additionalContext` を倍数ごとに渡す（1 度きりにしない）のは、編集が続いても
  二度と言わなくなるため
- **数えるのは「そのルールが当たった回数」。** 変わったファイルの本数ではない（下の「失うもの」）
- 文脈の分け方は `once` と同じ（セッション + `agent_id`）。サブエージェントは自分の数えを持つ
- `every: 1` は `every` 無しと同じ意味になる。`--lint` が warning で言う

欄名は `ctxfile.py` の呼び名をそのまま設定へ出したもの。同ファイルは `additionalContext` の文を
入れる変数を既に `every` と名付けていて（117 行）、`additionalContextFile` もそこに合流する。
新しい語を持ち込まず、実装の中の呼び名と設定の欄名を一致させる。

触る場所:

| ファイル | 何を |
|---|---|
| `ccnavi/rules.py` | `Rule` に `every: int = 0`。`_rule()` で `raw.get("every")` を読む（373-390 行） |
| `ccnavi/ctxfile.py` | 控えを `set` から「鍵 → 回数」へ。`_load_once` / `_save_once` が古い形（配列）も読めるようにする |
| `ccnavi/lint.py` | `every` が 1 以上の整数か。`every: 1` は warning。文が 1 つも無い `every` も warning。**`additionalContextOnce` だけの `every` は warning にしない**（「N 回目に 1 度」として効く） |
| `vscode-extension/.../core/rules-doc.ts` | `every` を欄に足す（25-32 行の隣） |

### 2. 受入テスト（`acceptance`）

`tests/config/` と `tests/guard/` に置く。書いた時点では落ちる。

| 何を言うテストか |
|---|
| `every: 5` のルールは 5 回目に当たったときだけ文を渡す。1〜4 回目は渡さない |
| `additionalContext` は 10 回目にも渡す（倍数ごと） |
| **`additionalContextOnce` は 5 回目だけ。10 回目には渡さない** |
| `every` が無いルールはいままでどおり毎回渡し、`Once` は 1 回目に渡る |
| `additionalContextOnce` だけを持つ `every: 5` のルールは、5 回目に 1 度だけ渡す |
| `additionalContextFile` は `additionalContext` に、`additionalContextOnceFile` は `Once` に従う |
| 控えがセッションと `agent_id` で分かれる。サブエージェントは自分の数えを持つ |
| 古い形（配列）の控えを読んでも落ちない |
| `--state ""` のときは毎回渡す（覚えられないなら言うほうに倒す。`ctxfile.py:108` の既存の決まりに合わせる） |
| `--lint` が `every: 0` と `every: -1` と `every: "x"` を error にする |
| `--lint` が `additionalContext` の無い `every` と `every: 1` を warning にする |

### 3. このワークスペースで使うルール（`staging`）

`.ccnavi/common/rules.yml` は保護済みなので、足す 1 件の全文を `wip/design/` に置いて人が写す。
文面はこれ:

```
このセッションで 5 件の編集がありました。次の編集へ進む前に、Agent ツールで
レビューをバックグラウンドに出してください。

見てほしい観点を、この順で:

1. 蓄積された決まりに沿っているか。読む先は CLAUDE.md（作業の進め方）、
   .ccnavi/common/rules.yml（判定の決まり）、docs/adr/（過去の決定）、
   CONTEXT.md（用語）。触った場所に関係する ADR を grep で絞ってから読む。
   沿っていない箇所は、どの決まりのどの行に反するかを名指しする
2. 過去の決定を、理由を知らずに覆していないか。ADR が「やらない」と書いたことを
   やり直していたら、その ADR 番号を挙げる
3. 決まりのほうが古くなっている可能性。反していると見えた箇所が正しく、
   決まりを直すべきなら、そう書く

指摘は「どのファイルのどの行が、どの決まりに、どう反するか」の形で返す。
決まりを名指しできない指摘は返さない。
```

3 番目を入れるのは、突き合わせが「決まりは常に正しい」前提で走ると、古い決まりに
合わせて新しい判断を潰す方向にしか働かないため。

文面は `additionalContextFile` で外に出してもよい（観点が伸びたときに `rules.yml` が
読みにくくならない）。どちらにするかは `staging` で決める。

### 4. 文書（`docs`）

`ccnavi.md` §5.1 の欄の表と §6.6、`README.md` のルールの書き方、`requirements.md` に 1 行、
ADR を 1 枚（「勧告は設定が持ち、実行ファイルは数えるだけ」の決定）。

## フェーズの分け方

| 番号 | 種類 | 中身 |
|---|---|---|
| 1 | acceptance | 上のテストを書く（落ちる） |
| 2 | implement | `rules.py` `ctxfile.py` `lint.py` と拡張 |
| 3 | staging | `.ccnavi/common/rules.yml` に足す 1 件の全文を `wip/design/` へ |
| 4 | docs | `ccnavi.md` `README.md` `requirements.md` と ADR |

`acceptance` は `overlap: [implement]` なので 1 と 2 は並行してよい。

## やらないこと

- **`post.py` に焼き込むこと。** しきい値とレビュー観点が実行ファイルに固定され、
  配布先ごとに変えられなくなる。観点を足すたびにビルドが要る
- **専用の hook スクリプト（`.claude/hooks/review-nudge.sh`）。** `.claude/hooks/` は保護済みで
  人が写す必要があり、しかも数えるのが `Write`/`Edit` の呼び出しだけになる
- **`exit 2` での差し戻し。** 勧告に留める。`additionalContext` は hook エラーにならない
- **決まりを機械で照合すること。** 書き下せる決まりは既に `rules.yml` にある
- **`additionalContextOnce` の欄名を変えること。** 意味は「渡す回の最初の 1 回」に読み直すが、
  `every` の無い既存の設定では今までどおり 1 回目に渡る。振る舞いが変わるのは
  `every` を添えたルールだけなので、欄名はそのまま

## 得るもの

- **しきい値と観点が設定側に残る。** 観点は後から足したくなる種類のもので、そのたびに
  実行ファイルを作り直すのは割に合わない。`rules.yml` なら人が写すだけで変わる
- **配布先ごとに変えられる。** ADR の置き場も `CLAUDE.md` の有無もリポジトリで違う
- **新しい仕組みが要らない。** 控えも経路も hook の登録も既にある。`once` の数えを 1 から N へ広げるだけ
- **頻度が 1 本の軸に並ぶ。** `every` が「渡す回」を刻み、2 つの文はその上で「たびに」と
  「最初の 1 回」を選ぶ。欄名だけで表していた頻度に、数で刻める段が 1 つ増える
- **「たまったところで 1 度だけ言う」が書けるようになる。** `every: 5` + `additionalContextOnce` で
  5 回目に 1 度。いまは 1 回目か毎回しか選べない
- ADR 53 枚を、書いた本人ではない読み手が見る。編集しているセッションは目の前の変更で
  文脈が埋まっていて、53 枚を思い出す余地が無い
- 突き合わせが別コンテキストに出るので、本体の会話が診断の出力で埋まらない
- `every` は `additionalContext` を持つルールなら何にでも使える。今回の用途だけの欄にならない

## 失うもの

- **数えるのは「ルールが当たった回数」で、「変わったファイルの本数」ではない。**
  同じファイルを 5 回直しても 5 と数える。`post.py` が見ている git の実際の変更のほうが
  正確だが、そちらは実行ファイルに焼き込む形になる。**この不正確さは `every:` の定義そのもの**で、
  あとから直すには欄の意味を変えることになる
- **欄名だけでは「何が N 回ごとか」が分からない。** `every: 5` は「5 秒ごと」「5 ファイルごと」とも
  読める。「当たった回数」であることと「掛かる先は `additionalContext` だけ」は文書で覚える。
  `additionalContextEveryNth` のように欄名で言い切る道もあったが、家族の欄名がさらに伸びる
- **`every` を添えると `Once` が遅れて届く。** 1 回目に言いたいこと（そのルールの趣旨など）と、
  たまったところで言いたいことを、1 件のルールには同居させられない。両方要るならルールを 2 件書く
- **`Once` の読み方が 2 通りになる。** `every` の無いルールでは「当たった最初の 1 回」、
  `every` のあるルールでは「渡す回の最初の 1 回」。同じ欄が置かれ方で違う回に届くので、
  文書でどちらかに寄せて説明できない
- **シェルやビルドが書いたぶんを数えない。** `match` がツール名なので、`Bash` を書かない限り
  当たらない。`post.py` の冒頭が言う「引数に現れない書き込み」はここでも抜ける
- **強制力が無い。** `exit 2` と違い hook エラー通知が出ないので、モデルが無視しても画面に
  何も出ない。走ったかどうかを ccnavi は知れない（`matcher: Agent` の hook で拾う道はあるが、
  今回は持たない）
- **サブエージェントは決まりを全部は読めない。** ADR 53 枚を毎回読ませればレビュー 1 回が
  重くなり、grep で絞れば絞り方を間違えたぶんが落ちる。**通ったことを「決まりに沿っている」と
  読めない**
- **決まりの側が古いときに、古いほうへ引き戻す力が働く。** 観点の 3 番目で打ち消そうと
  しているが、打ち消しきれる保証は無い
- **ルールのスキーマが 1 つ増える。** 配布先すべてに届く。使わなければ無害だが、
  覚えることと `--lint` の検査が増える
- **綴りを間違えた `every` は黙って無視される。** ルールに未知の欄の検査が無いため
  （これは `every` に限らない既存の穴。この番号では直さない）
- **控えのファイル形式が変わる。** `once-*.json` が配列から辞書になる。古い形を読む道を
  残すが、読めなかったときは「覚えていない」＝毎回渡す側へ倒れる
- 届くのは次のモデル呼び出し。1 レスポンスに `Edit` を並べた場合、その束が終わるまで読まれない
- トークンの消費が増える。編集 5 件ごとに、ADR を読むぶんを含めたレビュー 1 回ぶん

## やらない場合どうなるか

いまのまま。決まりとの突き合わせは人が言い出したときだけ入る。ADR は増え続け、
読まれない割合が上がる。実害が出ているわけではない。

## 代案

- **`post.py` に焼き込む**（案 B）。git が返した実際の変更を数えるので「同じファイルへの 5 回」を
  正しく 1 本と数えられる。代わりにしきい値と観点が実行ファイルに固定される
- **専用 hook**（案 A）。ccnavi に触らない。代わりに `staging` で hook スクリプト全文を人が写し、
  数えるのは `Write`/`Edit` の呼び出しだけになる
- **折衷**: ccnavi が変わったファイルの本数を数え、文面は `rules.yml` が持つ。`every` の
  不正確さを埋めるが、`every:` の意味が「当たった回数」ではなくなるので欄の定義から決め直し
- **欄名で言い切る**（`additionalContextEvery` / `additionalContextEveryNth`）。掛かる先が欄名で
  決まるので決まりを覚えなくてよい。代わりに家族の欄名が伸び、`additionalContextOnceFile` と
  並べたときの読みにくさが増す
- **`Stop` で数える。** ターンの終わりに 1 回だけ。対象と現状がズレないが、
  ルールの条件ではなく hook の話になり、`rules.yml` から外れる
