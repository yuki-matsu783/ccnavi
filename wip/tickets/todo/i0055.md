## 何が起きたか（実測）

この環境で `ccnavi-review.sh check --phase 1` を打つと、こう出て終わります。

```
ccnavi-review: github.com への POST graphql が失敗した:
curl: (22) The requested URL returned error: 403
```

同じトークンで REST は 200 を返します。GitHub が GraphQL に対して返していた本文は
こうでした。

> GitHub GraphQL is not available from Claude Code sessions; use the REST API

この本文が画面に出ていません。`api()` の curl が `-fsS` を使っており、`-f` が 4xx の
本文を捨てるためです（`gh` / `glab` の経路では `2>&1` で本文が残ります）。結果として、
**認証の失敗と、GraphQL が塞がれていることの区別が文面から付きません。**

## 何をするか

保護済みファイルなので、直した全文を `wip/design/scripts/ccnavi-review.sh` に置き、
人が写す（staging）。直すのは 2 か所。

### 1. `api_failed` に GraphQL のときの案内を足す（本題）

```sh
api_failed() {
	printf 'ccnavi-review: %s への %s %s が失敗した:\n%s\n' "$host" "$1" "$2" "$3" >&2
	# GraphQL を塞いでいる実行環境がある（Claude Code のセッションは REST だけ通す）。
	# GitHub ではスレッドの解決状態（threads）と Draft 外し（undraft）が GraphQL でしか
	# 扱えないので、そこだけが 403 で止まる。塞がれていることと認証の失敗は見分けが
	# 付かないので、詰まったその場で逃げ道を名指しする。綴りは 191 行の案内と揃える。
	case "$2" in
	graphql)
		printf 'ccnavi-review: %s\n' \
			"GraphQL が塞がれている環境では check / fetch（スレッドの解決状態）と ready（Draft 外し）が通りません。MCP などリモートを読める道具でスレッドとレビューを JSON にして 'ccnavi review check --phase <N> --result <json>' を打ってください。写しの形は fetch_all と同じ {host, mr, threads, reviews, fetched_at} です。Draft 外しは道具の側で直接行ってください。" >&2
		;;
	esac
}
```

`case` は関数の直下に置き、`$( )` の中には入れない（bash 3.2 が `)` を読み違える）。
変数のすぐ後ろに全角が続く綴りは作らない。`tests/core/test_sh_portability.py` が見る。

### 2. curl が捨てているホストの本文を残す（付随）

`-f` を外すと本文は出ますが、4xx でも curl が成功で返るので、いまの `||` による
失敗の検出が効かなくなります。`-f` の代わりに `-w '%{http_code}'` で状態を取り、
本文と分けて読む形に変えます。**ここは触る範囲が広がるので、1 だけ入れて 2 は
別にする判断もあります。** レビューで決めてください。

## フェーズ

| 番号 | 種類 | 中身 |
|---|---|---|
| 1 | acceptance | 文面が出ることのテスト。`phases.yml` が `staging` に `acceptance` を要求する |
| 2 | staging | 直した全文を `wip/design/scripts/ccnavi-review.sh` に置く。人が写す |
| 3 | docs | `README.md` の「リモートを読み書きするのは sh」の節に、塞がれている環境での逃げ道を 1 段落 |

フェーズ 1 で確かめるのは 2 つ。`graphql` の失敗で案内が標準エラーに出ること、
それ以外の失敗（`repos/...` への GET など）では出ないこと。`tests/sh/` に、`transport` を
curl に固定して届かない `api_base` を渡す小さな土台を置き、標準エラーを読みます。
変えるのが文面だけでも、出る条件を固定しないと、次に触った人が case を消せます。

## 得るもの

- 詰まった人が、その場で次の一手を読める。いまは curl の番号だけが残る
- 認証の失敗（191 行が案内する）と、GraphQL が塞がれている場合が、文面で分かれる
- 逃げ道の綴りが 1 か所ではなく、実際に詰まる場所にも出る

## 失うもの

- 保護済みスクリプトが 1 本増えるぶん、写す手間が人に残る（staging の常）
- 文面が長くなる。GraphQL の失敗は珍しいので、大半の人には出ない行が増える
- 2 まで入れると `api()` の失敗の検出を書き換えることになり、全部の API 呼び出しに
  影響する。1 に比べて明確に重い

## やらない場合どうなるか

GraphQL を塞ぐ環境で `check` を打った人が、403 の番号だけを見て、トークンの問題だと
読む。実際にこのセッションで起きました。逃げ道はスクリプトの中に書いてあるのに、
読むきっかけが無い。

## 代案

- **`check` の側で 403 を捕まえて案内する。** 詰まる場所に近いが、`fetch` と `ready` には
  効かない。`api_failed` に置けば 3 つとも拾える
- **GitHub の REST 経路に寄せる。** `/repos/{owner}/{repo}/pulls/{n}/ccr/review_threads` の
  ような経路があるなら GraphQL を外せるが、これは環境が足したもので GitHub の公開
  API ではない。素の GitHub でも動く必要があるので、ここには寄せられない
