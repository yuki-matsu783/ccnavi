## いま何がそうなっているか

共通層の 3 本だけが env で置き場を変えられる。

| 層 | 置き場の決まり方 |
|---|---|
| 共通層 | `CCNAVI_RULES` / `CCNAVI_PHASES` / `CCNAVI_RISK`。既定は `.ccnavi/common/{rules,phases,risks}.yml` |
| 自身の層 | `<root>/<CCNAVI_PROJECT_HOME>/config/{rules,phases,risks}.yml` 固定 |
| プロジェクトの層 | `<CCNAVI_PROJECTS>/<名前>/<CCNAVI_PROJECT_HOME>/config/...` 固定 |

配る `settings.json`（`scripts/ccnavi-setup.sh:592`）が書いているのは既定値と同じ
`.ccnavi/common/rules.yml` で、`CCNAVI_PHASES` と `CCNAVI_RISK` は書いてすらいない。
つまり、いま動いているどのワークスペースでも、この 3 本は既定の場所を指している。

`requirements.md` に該当する要求は無い（外から観測できる要求ではない）。

## 何をするか

1. `ccnavi/settings.py` から `RULES_ENV` / `PHASES_ENV` / `RISK_ENV` と、overrides 表の
   3 行を消す。`rules` / `phases` / `risk` の各欄は既定値のまま残す（欄そのものは
   `--project-rules-file` などの診断用の差し替えが使う）
2. `ccnavi/selfguard.py` の `common_shell_clause` を消す。これは「共通層が既定の外に在る
   場合の綴り」をシェルの禁止に足すためだけの関数で、固定になれば `_PLACES` の
   `\.ccnavi` が丸ごと拾う。`common_layer_regex`（名指しのツール向け、専用の文面を返す
   `builtin-guard-common-layer`）は残す。当てる先は固定の既定値から組み立てる
3. `ccnavi/ruleload.py` と `ccnavi/diagnose.py` の env への言及を置き場の綴りに直す
4. `scripts/ccnavi-setup.sh` が書く `env` から `CCNAVI_RULES` を外す
5. VS Code 拡張（`rules-panel.ts` `phases-panel.ts` `risk-panel.ts` `projects-panel.ts`
   `core/model.ts`）の `envFromSettingsJson(..., "CCNAVI_*")` を消し、既定の綴りを直に使う
6. テストを消す・直す
   - `tests/sh/test_setup.py` の `REQUIRED_ENV` から `CCNAVI_RULES` を外し、269 行の
     値の検査を消す
   - `tests/config/test_config_union_guard.py` の
     `test_shell_writes_into_a_moved_common_layer_are_denied` を消す（「動かした共通層」が
     無くなるため）
   - `vscode-extension/ccnavi-board/test/rules/hooks.test.ts:64` の該当 assert を消す
7. 保護済みの 2 本は `staging` で渡す。エージェントは書けないので、直した全文を
   `wip/design/` に置き、人が写す
   - `.claude/settings.json` の `env` から `CCNAVI_RULES` の行を消す
   - `.ccnavi/scripts/ccnavi-ticket.sh` の `--help` の文面から `（CCNAVI_PHASES）` を外す
8. 文書（`ccnavi.md` 8 か所、`README.md` 10 か所、`HANDOVER.md`）を直し、
   ADR を 1 枚足す。ADR-0042 と ADR-0021 は経緯なので書き換えず、新しい ADR から参照する

## フェーズの分け方

| 番号 | 種類 | 中身 |
|---|---|---|
| 1 | acceptance | 固定になったことを確かめるテストを先に書く（この時点では落ちる） |
| 2 | implement | 実行ファイル・setup.sh・拡張から経路を消し、古いテストを消す |
| 3 | staging | 保護済み 2 本（`settings.json`・`ccnavi-ticket.sh`）の直した全文を `wip/design/` に置く |
| 4 | docs | `ccnavi.md`・`README.md`・`HANDOVER.md` と新しい ADR |

`acceptance` は `overlap: [implement]` なので 1 と 2 は並行してよい。

## やらないこと

- `CCNAVI_LOG` / `CCNAVI_STATE` は残す。記録と控えの置き場は層の話ではなく、
  `ccnavi-review.sh:83` が実行時に読んでいる
- `CCNAVI_PROJECT_HOME` / `CCNAVI_PROJECTS` は残す。層そのものの位置を決めるつまみで、
  今回消す 3 本とは役割が違う
- 保護済みファイルへの直接の書き込み。`staging` で人に渡す

## 得るもの

- 3 層が同じ決まり方になり、「どこを見ているか」がコードを読まずに言えるようになる
- 置き場を読む側（実行ファイル・setup.sh・拡張 4 画面）から env の分岐が消える
- `selfguard` から、共通層が動いている場合のためだけの経路が 1 本消える。
  守る対象が固定されるぶん、守りの穴の検査が楽になる

## 失うもの

- **共通層を既定の外へ置く手段が無くなる。** 複数のワークスペースで 1 本の
  `rules.yml` を共有する、読み取り専用の場所に置く、といった使い方は
  シンボリックリンクに頼ることになる
- 配布済みの `settings.json` に `CCNAVI_RULES` を書いて**既定の外を指している**利用者が
  居た場合、更新後は黙って `.ccnavi/common/rules.yml` を読む。値が無視されたことは
  どこにも出ない。`--lint` に「効かない env が書かれている」と言わせるかは実装で決める
- `tests/sh/test_setup.py` の `REQUIRED_ENV` が 1 本減り、配る `settings.json` に
  その行が在ることの検査が無くなる

## やらない場合どうなるか

いまのまま。実害は出ていない。非対称と、置き場を読む 6 か所の分岐が残る。

## 代案

- **env は残し、`--lint` に「既定と同じ値なので書く必要が無い」と言わせるだけにする。**
  失うものが無い代わりに、非対称も分岐も残る
- **3 本を 1 本にまとめる**（`CCNAVI_COMMON` で `.ccnavi/common/` 相当のディレクトリを
  指す）。動かす手段は残り、分岐は 1 つに減る。移行の手当てが要る
