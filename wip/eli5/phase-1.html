フェーズ 1: Chrome 拡張が「棚の場所を env から読まない」ことの合格線を引く

親チケット i0065（Chrome 拡張の置き場を既定に固定する）のフェーズ 1、子 i0065-01 です。 足したのはテストだけで、Chrome 拡張そのものは 1 行も変えていません。

1. なぜやるのか

チケットや控えをしまう棚の場所は「決まった 1 か所だけ。設定（env）では動かない」と決めました（i0064）。 ところが Chrome 拡張の Python 側は、いまも統合先の .claude/settings.json の env から棚の場所を読みます。 しかも、その env の名前を ccnavi 本体の定数から借りています。

直す前に「何ができたら直ったと言えるか」をテストで決めておくのが、このフェーズです。直すのは次のフェーズ（i0065-02）です。

2. 足したテスト（6 本）

#確かめることいま
B1settings.json の env で棚を別の場所（相対パス）に向けても、既定の棚を答える。答えに env の欄も残さない落ちる
B2env に絶対パス（/x・C:/x・~/x）を入れても止めず、既定の棚を答える落ちる
B3実際に一覧（board）を出す操作でも、env があっても無いときと同じ答えになる落ちる
B4-1Chrome 拡張のソースに、env の名前の定数を使う箇所が 1 つも無い（別名での import や文字列で引く形も拾う）落ちる
B4-2その定数を一時的に消しても、Chrome 拡張を読み込める（i0064 が入っても落ちない）落ちる
B5手元のパソコンの env に棚の場所を入れても、一覧の答えは変わらない（見張り）通る

B1〜B4 が落ちる理由は、どれも「Chrome 拡張がまだ env を読む・定数を使う」ことだけです。テストの組み立ての誤りで落ちているものはありません。

3. テストのテスト（敵対的レビュー）

別のエージェントに、わざと間違えた直し方を 9 通り作らせ、テストがそれを見逃さないかを試させました。見つかった穴は 5 つで、すべて直しました。

  • 正しい直し方まで落としていた（2 つ）: 定数を消したまま棚の場所を聞いていた。テストの道具が Chrome 拡張の内部の関数の形に依っていた。 どちらも、次のフェーズの直し方を不要に縛るので外しました。
  • 間違った直し方を見逃していた（3 つ）: 別名で定数を使う形、手元の env を素通しする形、答えに env の欄を残す形。どれも捕まるようにしました。

直したあと、正しい直し方の試作でテストが全部通ることも確かめました。

4. 変わらないもの

差分は tests/ticket/test_core.py の 1 ファイル（+182 −3）だけです。Chrome 拡張・実行ファイル・文書には触っていません。 既存のテストの意味も変えていません（テストの道具が棚の場所を取る道を、内部の関数から正式な問い合わせに変えただけです）。

5. 気にしてほしいこと（リスク）

  • 次のフェーズが済むまで、親のブランチには落ちるテストが 5 本残ります。main に入れるのは全フェーズが済んでからです。
  • この Windows 機では、既存の Chrome 拡張のテストが 7 本落ちます。変更の前から改行（CRLF）の違いで落ちていたもので、今回の変更とは関係ありません。 改行の問題が出ない Linux や CI で確かめる必要があります。
  • 同じ内部の関数を直に呼ぶテストが、ほかに 2 ファイル残っています（test_chrome_project.py・test_chrome_write.py）。 このフェーズの約束の外なので触っていません。次のフェーズで関数の形を変えるなら、そこで一緒に直します。
  • 合格線として足りているか。「env を入れても既定を使う」「絶対パスでも止めない」「定数を使わない」の 3 つの見方で足りるかを見てください。
