フェーズ 2: Chrome 拡張が棚の場所を env から読まなくなる

親チケット i0065 のフェーズ 2、子 i0065-02-01 です。フェーズ 1 で引いた合格線（受入テスト B1〜B5）を、実装で全部通しました。

1. 何が変わるのか

前統合先の .claude/settings.json の env を読み、棚（チケットの置き場）を動かせた。env に絶対パスがあると止めた。env の名前は ccnavi 本体の定数から借りていた
後棚はいつも決まった場所（wip/proposals・.ccnavi/approved・.ccnavi）。env に何が書いてあっても読まないし、止めない。本体の定数も使わない

2. 直したところ

Python 側（py/ccnavi_chrome.py）

  • env を拾う処理、絶対パスを断る分岐、env の名前の定数を消しました。棚の場所を答える関数は引数を取りません
  • 手元のパソコンの ccnavi の env を判定に混ぜない役目（_environ）は、前と同じ範囲で残しました

TS 側（拡張の画面と裏方）

  • 棚の場所は固定の値 DEFAULT_PLACES にしました。書く先の守り（棚の下にしか書かない）はこの値で前と同じように効きます
  • 棚の場所のためだけに統合先の settings.json を読んでいた処理と、それを Python に渡す欄を消しました。判定に要る settings.json は今までどおり読みます
  • 設定画面と README の説明を「棚は既定に固定、env では動かない」に直しました

3. テストのテスト（敵対的レビュー）

別のエージェントに、わざと間違えた実装でテストが見逃さないかを試させました。直すべき指摘は 0 件。できれば直す・参考の指摘 6 件は、このフェーズの中で直しました。

  • ホストから来たパスが木の外へ出ないかの検査に、試験が無かった → 足した（検査を外すと落ちることを確認）
  • 「パスの途中の ws を畳まない」ことの確かめが通しの試験から消えていた → プロジェクト名を ws にした場面で戻した
  • 承認済みの棚と層の棚も既定を読むことを、拡張の試験でも見るようにした

4. 決めたこと（あなたの判断）

プロジェクトのリポジトリに書くとき「ワークスペースも登録済みか」を見る確認は、戻さない。 この確認は、棚の場所を読むためにワークスペースを探す処理の副作用でした。棚を読まなくなったので一緒に消えました。 書ける範囲（登録済みのリポジトリ・保護されていないブランチ・棚の下）は前と変わりません。 ADR-0093 の「プロジェクトのワークスペースも登録したものに限る」は、フェーズ 3 で書き直します。

5. 気にしてほしいこと（リスク）

  • ccnavi が出したリスク 60（HIGH）は見かけより大きい。基準点が main を取り込む前なので、途中で取り込んだ main の変更（#190・#193 など）まで数えています。このフェーズで変えたのは 19 ファイル（+184 −200）です。
  • 途中で子の名前が変わった。main に入った新しい識別子の形（ADR-0101）に合わせ、i0065-01 → i0065-01-01、i0065-02 → i0065-02-01 に手で移しました。
  • main を取り込んだときに 6 ファイルがぶつかった。main 側の機能（ボードの自動読み直し、新しい識別子）を残したまま解きました。試験の番号が重なったので、このフェーズで足した試験を CX-T213 に付け替えました。
  • この Windows 機で落ちる試験がある。改行（CRLF）、権限、sh の起動、パスの区切り、拡張の CX-T155 で落ちる分は、変更の前から落ちていたものです。変更で新しく落ちた試験はありません。Linux か CI で確かめる必要があります。
  • 拡張を使っている人は、入れ直しが要る。置き場を env で動かしていたワークスペースは、入れ直したあと既定の棚を読みます。
