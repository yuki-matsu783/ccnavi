# フェーズの種類とリスクの配点はプロジェクトの層だけで決め、共通層はルールだけにする

## 決めたこと（2026-09-24、利用者と相談して）

**線を引く基準は、設定の結果がプロジェクトの git に入って他人へ届くかどうか。**

| 設定 | 結果が残る場所 | 置ける層 |
|---|---|---|
| フェーズの種類 `phases.yml` | 計画（`plan:`）とマーカー。プロジェクトの git | 各ツリーの層だけ（自身の層・プロジェクトの層） |
| リスクの配点 `risks.yml` | `.risk.json` とレビュー要否。プロジェクトの git | 各ツリーの層だけ（自身の層・プロジェクトの層） |
| ルール `rules.yml` | 残らない。その場で止めるか通すかだけ | 共通層 + 各ツリーの層（今のまま） |

2 つの願いをこう満たす。

- **プロジェクトだけを clone した人どうしで、作業の内容がずれない。** フェーズの種類とリスクの配点は、
  プロジェクトの git にある 1 本だけで決まる。ワークスペースの持ち物で結果が変わらない
- **ワークスペースで管理するプロジェクトは、同じ基準で作業する。** 実行時に層を重ねる形はやめる。
  代わりに、同じひな形から始め、ずれたら知らせる。そろえるかどうかは人が決め、プロジェクトの git で合意する

## 変えるもの

1. 共通層の `phases.yml` と `risks.yml` を読まない。置いてあれば `--lint` が error で名指しし、
   各ツリーの層へ移すよう案内する（読まないのに黙っていると、効いていると思い込む）
2. フェーズの種類とリスクの配点の合成（設計 §11.4.1・§11.4.2）をやめる。親の `project:` が指す層の 1 本だけで決める。
   その層に無ければ、今の「どの層にも無い」ときと同じ（種類は番号だけ、配点は組み込み）
3. ADR-0078 の `order` の関門（合成に入る層が全部 `dag` のときだけ `dag`）は、層が 1 本になるので、その 1 本で決まる
4. このワークスペースの `.ccnavi/common/risks.yml` を、自身の層の `.ccnavi/config/risks.yml` へ移す（保護済みなので staging。人が写す）
5. 導入スクリプト（`scripts/ccnavi-setup.sh`）が配るひな形を変える。配点を共通層ではなく自身の層へ置く（REQ-MLT-32）
6. 設計書 §11、requirements.md（REQ-MLT-21〜25・32 あたり）、README、`ccnavi-config` スキル、`ccnavi-ticket.sh --help` の置き場の説明を合わせる
7. ADR を 1 枚足す（決めたことと、下の得失）。ADR-0078 の該当行は置き換えを書き添える

## 設計フェーズで決めること

- **ひな形の置き場と、ずれの知らせ方。** 案は 2 つ。
  (a) ワークスペースにひな形の置き場（例 `.ccnavi/templates/`）を作り、`--lint` がプロジェクトの層との差を warn で言う
  (b) ひな形は導入スクリプトが写すだけで、ずれは見ない。
  自身の層をそのまま基準にする形は採らない（ワークスペースの `scope` はワークスペースの並びにしか合わない）
- **プロジェクトにひな形を写す手段。** 導入スクリプトの副命令にするか、`--lint` の案内だけにするか
- **共通層に `phases.yml`・`risks.yml` が残っているワークスペースの移り方。** error で止めるか、1 版だけ warn にするか

## 得るもの

- 原則が 1 行で言える。「共有される結果を生む設定はプロジェクトの git だけ。手元の実行を縛るルールだけが共通層を持てる」
- clone しただけの人と、ワークスペースで作業する人とで、計画・配点・レビュー要否が一致する
- 合成が消える。同じ id の衝突で層が空になる問題（配点では点が下がる側に倒れていた）が、起きようがなくなる
- 設計書 §11.4.1・§11.4.2 とそのテストが大きく減る

## 失うもの

- ワークスペースの持ち主が、全プロジェクトに配点の下限を強制できなくなる。プロジェクトの `risks.yml` を緩めれば、
  そのまま効く。守りは「緩めた変更がプロジェクトの git に合意として残る」ことに移る
- 基準を直したときは、各プロジェクトへ配り直してコミットが要る。自動では追いつかない
- フェーズの種類を複数のプロジェクトで使い回すなら、写して持つことになる
- ADR-0078 の関門（共通層が `sequential` ならプロジェクトは `dag` に切り替えられない）が無くなる。
  ただし、いまも共通層に `phases.yml` が無いので、実際の挙動は変わらない
- 設計書と ADR の書き直しが大きい（§11、ADR-0042・0052・0067・0078 の記述）

## やらない場合

共通層の配点が違う機械どうしで、同じ差分のレビュー要否がずれ続ける。共通層に同じ id の項目を書いたプロジェクトは、
その層の項目と閾値が落ちたまま、点が下がる。

## 採らなかった案

| 案 | 落とした理由 |
|---|---|
| 同じ id の配点を両方数える（層を空にしない）だけ直す | 衝突で点が下がる穴は塞がるが、機械ごとに配点が違う問題は残る。試作して捨てた |
| 共通層の中身をプロジェクトへ写し、共通層も残す | 写しと共通層が食い違えば、やはり機械ごとに結果が変わる |
| ルールもプロジェクトの層だけにする | ルールの結果は他人へ届かないので、ずれの問題が無い。共通層のルールは生の git・認証情報・ワークツリーの置き場など、手元の環境の守り。プロジェクトの git に預けると、外から届く 1 コミットで外せる |
