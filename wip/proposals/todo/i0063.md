# フェーズの種類とリスクの配点はプロジェクトの層だけで決め、共通層はルールだけにする

## 承認前に決めること（敵対的レビューで出た、方向を見直しうる論点）

**1. 配点の下限が外れる。** 今は `levels` をキーごとに小さいほうで合わせ、共通層の項目は消せない。
この提案の後は、プロジェクトの `risks.yml` の 1 本だけで点と閾値が決まる。`factors` を空にして
`levels: {high: 9999}` と書けば、HIGH 以上には二度と上がらない。しかも `ccnavi-fetch.sh` がセッションの頭で
プロジェクトのブランチを ff するので、外から届いた 1 コミットが、ワークスペースの持ち主が見ないまま効く。
ルールを共通層に残す理由（「外から届く 1 コミットで外せる」）が、配点の下限にもそのまま当たる。
フェーズの種類はいまも共通層に `phases.yml` が無いので、新しい穴ではない。新しいのは配点の側だけ。

**2. もっと小さい代案がある。** 目的の「作業者間で結果がずれない」は、次の形でも得られる。

| 案 | 得るもの | 失うもの |
|---|---|---|
| (A) この提案（配点も各ツリーの層だけ） | 原則が 1 行で言える。合成が消える | 下限が外れる（上の 1）。変更が大きい |
| (B) 承認のときに、合成した配点の定義を親の `.ccnavi/approved/phases/<親>/` に写し、閉じるときはその写しで数える（待ち方 `order` の写しと同じ作り） | 下限を保ったまま、その親の子は誰の機械で閉じても同じ定義で数える。定義はプロジェクトの git に乗って届く | 承認した人のワークスペースの共通層が、その親の配点を決める。途中で配点を直しても、進行中の親には効かない。写しを読み書きする仕組みが要る |
| (C) `.risk.json` に、数えた定義の出どころ（層ごとのパスとハッシュ）を残すだけ | 変更が最も小さい。ずれが起きたときに追える（ADR-0067 が挙げた「どの配点で数えたかを記録が持たない」穴を直接塞ぐ） | ずれそのものは防がない |

(B) ならフェーズの種類は今の合成のままでよく、配点の衝突で層が空になる問題（同じ id）は別に直す。
**利用者に、(A) のまま進めるか、(B) か (C) に切り替えるかを決めてもらう。** 以下は (A) で書いてある。

## 決めたこと（2026-09-24、利用者と相談して）

**線を引く基準は、他人が判定として読み返す記録を生むかどうか。** その場で止めるか通すかだけを決める、片側向きの関門とは分ける。
（最初は「結果が git に入るか」と書いたが、ルールで止まった変更や実行後の監視で戻された差分もコミットの中身を変えるので、
それではルールもプロジェクト側に倒れる。レビューの指摘で直した。）

| 設定 | 生むもの | 置ける層 |
|---|---|---|
| フェーズの種類 `phases.yml` | 計画（`plan:`）とマーカー。他人が読み返して続きを進める | 各ツリーの層だけ（自身の層・プロジェクトの層） |
| リスクの配点 `risks.yml` | `.risk.json` とレビュー要否。他人が読み返す | 各ツリーの層だけ（自身の層・プロジェクトの層） |
| ルール `rules.yml` | その場の関門。記録は手元の `logs/` だけ | 共通層 + 各ツリーの層（今のまま） |

配点は「足すだけ・閾値は小さいほう」で合わせてきたので、関門の性格も持っている。ここを記録の側に置く代償が、上の論点 1。

2 つの願いをこう満たす。

- **同じプロジェクトを別々のワークスペースで扱う人どうしで、フェーズとリスクの判定がずれない。**
  種類と配点は、プロジェクトの git にある 1 本で決まる。ただし完全な一致ではない。組み込みの配点は実行ファイルの版に付き、
  `judge:` の項目はサブエージェントの判断で、設定は元リポジトリにチェックアウトされているブランチの版を読む。
  ルールの違いで書ける範囲が変われば、コミットの中身も変わる。これらはこの提案の外に残る
- **ワークスペースで管理するプロジェクトは、同じ基準で作業する。** 実行時に層を重ねる形はやめる。
  代わりに、同じひな形から始め、ずれたら知らせる。そろえるかどうかは人が決め、プロジェクトの git で合意する

## 変えるもの

**判定と読み込み**

1. 共通層の `phases.yml` と `risks.yml` を読まない。置いてあれば `--lint` が error で名指しし、
   各ツリーの層へ移すよう案内する。lint を回さない人も気づけるように、閉じるときの出力と SessionStart でも言う
2. フェーズの種類とリスクの配点の合成（設計 §11.4.1・§11.4.2）をやめる。親の `project:` が指す層の 1 本だけで決める。
   その層にファイルが無ければ、今の「どの層にも無い」ときと同じ（種類は番号だけ、配点は組み込み）
3. **1 本しかない層が壊れた・読めないときの落ち先を決める。** 今の `load_layer` は壊れた層を空にする（REQ-MLT-06）。
   そのまま流用すると、YAML の誤り 1 つで項目が 0 件になり、点が 0 に倒れる。配点は組み込みへ落とし、`.risk.json` の
   `fallback` に必ず残す（今の共通層の `risk.load` の扱い）。フェーズの種類は今までどおり空（計画が承認で止まる）。
   REQ-MLT-06 を配点とフェーズで書き分ける
4. ADR-0078 の `order` の関門（合成に入る層が全部 `dag` のときだけ `dag`）は、層が 1 本になるので、その 1 本で決まる
5. `ccnavi/diagnose.py`（`--explain` と `layers[]`）、`ccnavi/ruleload.py`、`ccnavi/lint.py`、`ccnavi/phase.py`、
   `ccnavi/approval.py` の、共通層の種類と配点を前提にしている箇所を直す

**診断**

6. `--phases` と `--risk`（共通層の置き場を差し替える診断用のフラグ、ADR-0067）は意味を失う。
   代わりに、配点の層を差し替える `--project-risk-file <層>=<パス>` を足し、`--project-phases-file` と揃える。
   これが無いと、`ccnavi-config` スキルの「下書きを検証してから渡す」手順が配点で使えない。REQ-DIA-09 を直す

**守り**

7. 共通層の `phases.yml`・`risks.yml` の守り（`builtin-guard-common-layer`、コアファイル、見本）は**外さない**。
   読まなくなっても、外すと守りが緩む側に倒れる。REQ-MLT-08 と見本の記述は「読まないが守る」に直す

**このワークスペースと導入スクリプト**

8. このワークスペースの `.ccnavi/common/risks.yml` を、自身の層の `.ccnavi/config/risks.yml` へ移す（保護済みなので staging。人が写す）
9. 共通層の `script:` の置き場（`.ccnavi/common/scripts/`）は無くなる。自身の層の置き場 `.ccnavi/scripts/` は、
   導入スクリプトが `ccnavi-*.sh` を配る同じディレクトリで、名前がぶつかりうる。移し先を設計で決める
10. 導入スクリプト（`scripts/ccnavi-setup.sh`）が配るひな形を変える。今は配布元（このリポジトリ）の自身の層の
    `phases.yml` をそのまま配っており、「自身の層をそのまま基準にする形は採らない」とすでに食い違っている。
    `risks.yml` も自身の層へ移すと、このワークスペース自身の設定と配るひな形が同じ 1 本になる。
    だから、ひな形の置き場を分ける（下の設計の (a)）ことを、phases と risks の両方の前提にする（REQ-MLT-32）

**VS Code 拡張**

11. リスク管理画面は共通層の `risks.yml` 1 本だけを編集している（`src/risk-panel.ts`・`src/core/risk-doc.ts`・`src/core/risk-view.ts`）。
    提案の後は、ボードで配点を直しても何も効かない。フェーズ管理画面の既定（`src/phases-panel.ts`・`src/core/model.ts`）も同じ。
    どの層（どのプロジェクト）の配点と種類を編集するかを選べる形にし、README の手順と確認表を直す

**文書**

12. 設計書 §11（§11.2・§11.4・§11.4.1・§11.4.2・§11.6）と、§9 のフェーズとリスクの節
13. requirements.md: REQ-MLT-04・06・08・15・16・17・18・21〜25・32、REQ-DIA-09、試験計画の該当行
14. ADR を 1 枚足す（決めたことと得失、配点を記録の側に置いた理由）。置き換えや書き添えが要るもの: 0027・0033・0042・0052・0067・0070・0078

## 移行

- **このワークスペースで点がどう変わるか。** 自身の層へ移す中身は今の共通層と同じなので、このワークスペースの点は変わらない
- **他のワークスペースで点がどう変わるか。** 両方の向きがある。
  - 緩む: 自分の `risks.yml` を持ち、共通層の項目に頼っていたプロジェクトは、共通層の項目と閾値の下限を失う
  - 厳しくなる: `risks.yml` を持たないプロジェクトは、共通層の項目から組み込みの 4 項目に変わり、`ci`（35 点、`.github/**`）が増える

  プロジェクトごとに、移行の前と後の点を並べて出す dry-run を用意する
- **進行中の子。** 移行の前後で違う定義で数えられうる。(C) の出どころを記録する形を一緒に入れれば、後から追える
- **共通層に `phases.yml` を持つワークスペース。** 計画中の種類が消えると、承認は「種類が無い」で止まる。
  それだけでなく、種類で範囲を切り詰めなくなるので、子の範囲の上限が外れる（緩む）。待ち方の写しとも食い違う。
  このワークスペースには共通層の `phases.yml` が無いので影響しない。導入先の点検手順と移行の案内を出す

## 設計フェーズで決めること

- **ひな形の置き場と、ずれの知らせ方。** (a) ワークスペースにひな形の置き場（例 `.ccnavi/templates/`）を作り、`--lint` が
  プロジェクトの層との差を warn で言う。(b) ひな形は導入スクリプトが写すだけで、ずれは見ない。変えるもの 10 のとおり (a) が前提
- **プロジェクトにひな形を写す手段。** 導入スクリプトの副命令にするか、`--lint` の案内だけにするか
- **共通層に残った 2 本の扱い。** error で止めるか、1 版だけ warn にするか
- **配点の `script:` の移し先**（変えるもの 9）
- **拡張の層の選び方**（変えるもの 11）

## 得るもの

- 原則が 1 行で言える。「他人が読み返す記録を生む設定はプロジェクトの git だけ。その場の関門のルールだけが共通層を持てる」
- 同じプロジェクトを別々のワークスペースで扱っても、種類と配点の定義が一致する
- 合成が消える。同じ id の衝突で層が空になる問題（配点では点が下がる側に倒れていた）が、起きようがなくなる
- 設計書 §11.4.1・§11.4.2 とそのテストが大きく減る。読む層が 1 本減る

## 失うもの

- **配点の下限を、ワークスペースの持ち主が強制できなくなる**（承認前に決めること 1）。プロジェクトの `risks.yml` を緩める
  1 コミットは、セッションの頭の自動 ff でそのまま効く
- 基準を直したときは、各プロジェクトへ配り直してコミットが要る。自動では追いつかない
- 上流が ccnavi のファイルを受け入れない第三者のリポジトリでは、組み込み以外の配点を持てない。今は共通層で足せる
- フェーズの種類を複数のプロジェクトで使い回すなら、写して持つことになる
- ADR-0078 の関門（共通層が `sequential` ならプロジェクトは `dag` に切り替えられない）が無くなる。
  このワークスペースでは、共通層に `phases.yml` が無いので挙動は変わらない。他の導入先では変わりうる
- 予約名のプロジェクト（`common`・`self`）は、共通層で数える形から組み込みで数える形に変わる（承認されないので実害は小さい）
- 変更が大きい。コード・診断・拡張・導入スクリプト・設計書・要求・ADR 7 枚にまたがる

## やらない場合

同じプロジェクトを別々のワークスペースで扱うと、子を閉じた機械の共通層で点が決まり、レビュー要否がずれる。
どの定義で数えたかも残らない。共通層と同じ id の配点項目を書いたプロジェクトは、その層の項目と閾値が落ちたまま点が下がる。

## 採らなかった案

| 案 | 落とした理由 |
|---|---|
| 同じ id の配点を両方数える（層を空にしない）だけ直す | 衝突で点が下がる穴は塞がるが、機械ごとに配点が違う問題は残る。試作して捨てた。(B) を採るなら、これも一緒に入れる |
| 共通層の中身をプロジェクトへ写し、共通層も残す | 写しと共通層が食い違えば、やはり機械ごとに結果が変わる |
| ルールもプロジェクトの層だけにする | ルールはその場の関門で、他人が読み返す記録を生まない。共通層のルールは生の git・認証情報・ワークツリーの置き場など、手元の環境の守り。プロジェクトの git に預けると、外から届く 1 コミットで外せる |
| 承認時の写し (B)、出どころの記録 (C) | まだ落としていない。承認前に決めること 2 |
