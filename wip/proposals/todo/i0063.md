# 着手の前に共通層をプロジェクトへ写し、違っていたら最初のレビューで知らせる

## 決めたこと（2026-09-24、利用者と相談して）

- 共通層は今のまま持つ。判定も今のまま「共通層 + そのツリーの層」の和で行う
- **親チケットに着手するとき**、共通層の 3 本と、作業対象のプロジェクトの `.ccnavi/config/` にある同じ名前のファイルを比べる。
  違っていれば、共通層でプロジェクトの `.ccnavi/config/` を上書きしてから作業を始める
- **最初のレビューで**、プロジェクトの設定が変わったことを依頼の頭に載せ、人に見てもらう
- 2 重管理になるのは受け入れる。いちばん避けたいのは、プロジェクトの側だけを見ている人が気づけないこと

## 組み立て（既定。設計フェーズで確かめる）

**1. 写す先は、プロジェクトの `.ccnavi/config/{rules,phases,risks}.yml` そのもの。上書きする。**（利用者の判断。置き場を分けると分かりにくくなる）

- 比べるのは、共通層の 1 本とプロジェクトの同じ名前の 1 本の中身（改行を揃えたうえでの一致）
- **共通層にあるファイルだけを上書きする。** 共通層に無いファイルは、プロジェクトの側を消さずに残す。このワークスペースでは
  共通層に `phases.yml` が無い（フェーズの種類はツリーのレイアウトに縛られるので、各ツリーが持つ）。
  無いものまで写すと、プロジェクトのフェーズの種類が消え、計画が承認で止まる
- 上書きした結果、プロジェクトの層は、共通層にあるファイルについて共通層と同じ中身になる。プロジェクトだけのルールや配点は、
  共通層に書く（パスで絞る）か、共通層に無いファイルとして持つ

**2. 写すのは ccnavi の実行ファイルで、時点は親の `ticket start`。**

- `.ccnavi/` の下はエージェントの Write / Edit が組み込みの守りで止まるので、エージェントには書かせない。
  `start` が親のワークツリーの `.ccnavi/config/` を上書きし、同じ場所に印 `.ccnavi/approved/phases/<親>/config-sync.json`
  （共通層の指紋、変わったファイル、差分の要約）を置く。コミットはエージェントが `ccnavi-git.sh` で行う
  （Draft を外した印と同じ扱い）。実行後の監視は、この書き込みを自分の副命令の書き込みとして見分ける（ADR-0075）
- 子は親のブランチに乗るので、子の着手では比べない
- 承認のときにしない理由: 承認はボードや端末で人が打つもので、プロジェクトのワークツリーに書く場面ではない。
  着手はワークツリーがあり、最初の作業の直前にある

**3. 最初のレビューで知らせる。**

- 印があれば、最初のフェーズのレビュー依頼（マージリクエストの本文と、このセッションで受けるレビュー、ADR-0065）の頭に
  「プロジェクトの設定（共通層の写し）が変わった」と、差分の要約を載せる。ボードにも出す
- 知らせたことを印に残し、2 回目以降のレビューでは繰り返さない

**4. 判定の仕組みは変えない。写した中身は、プロジェクトの層としてそのまま読まれる。**

- 手元のワークスペースでは、共通層とプロジェクトの層が同じ中身になり、全欄一致の重複として後ろが捨てられる（info）。判定は共通層だけのときと同じ
- 別の共通層を持つワークスペースでは、その共通層と、プロジェクトの層に写された共通層の和で判定される。ルールと配点は厳しくなる側に働く。
  フェーズの種類は、同じ id で中身が違えばプロジェクトの層が空になる（今の規則。計画が承認で止まる側）

**5. 配点の同じ id の衝突で層が空になる穴も、ここで直す。**

- プロジェクトの `risks.yml` に共通層と同じ id の項目があると、今はその層の項目と閾値が全部落ち、点が下がる
- 同じ id で中身が違う項目は両方を数え、後ろの層の側を `<層>:<id>` と名乗らせる（ルールの同じ id と同じ扱い。先に試作して、テストが通ることを確かめた）

## 設計フェーズで決めること

- 上書きで消えるプロジェクトだけの設定を、着手の前に名指しするか（上書きの前に、共通層に無い項目がプロジェクトの側にあれば出力で言う）
- 比べて違ったときに、止めて人に聞くか、写して進めるか（決めたことは「写して進める」。止める形は採らない前提で確かめる）
- `{root}` の扱い。共通層のルールの `message` は `{root}` を持つ。置き換えずにそのまま写し、読むときにそれぞれのワークスペースで置き換わる想定
- ワークスペース自身（`projects/` の外）の作業では比べない想定。共通層と同じリポジトリにあり、写す意味が無い
- 印とレビュー依頼の文面、ボードでの見せ方

## 得るもの

- プロジェクトだけを clone した人が、どの共通層のもとで作業されたかをプロジェクトの git の上で見られる
- 共通層が変わると、次の親の最初のレビューで人の目を通る。黙って変わらない
- 判定の仕組みは変わらないので、下限（共通層の `deny`、配点の項目、閾値の min）は今のまま残る
- 配点の同じ id の衝突で点が下がる穴が塞がる

## 失うもの

- 2 重管理になる。共通層とプロジェクトの層は、次の着手まで食い違いうる
- **プロジェクトの層に、共通層にあるファイルと同じ名前でプロジェクトだけの設定を持てなくなる。** 書いても次の着手で上書きされる。
  プロジェクトだけのルールや配点は、共通層にパスで絞って書くことになる
- 上書きは親のブランチに乗るので、並行する 2 本の親が別々に上書きすると、統合先へ戻すときに衝突しうる
- **違う共通層を持つワークスペースどうしが同じプロジェクトを扱うと、着手のたびに写しが入れ替わる。**
  そのたびにレビューで知らせが出る。止めるには、人が共通層を揃えるしかない（知らせが出ること自体が狙いでもある）
- プロジェクトだけを clone した人の判定は、その人の共通層とプロジェクトの層（写された共通層）の和で決まる。
  「見える」ようにはなるが、「揃う」わけではない
- プロジェクトのリポジトリに、ワークスペースの運用の痕跡（共通層のルールの中身）が入る。public のリポジトリなら外に出る。
  提案と承認済みチケットが既に入っているので、新しい種類の露出ではないが、量は増える
- 着手のたびに比べる手間（3 本を読むだけで、数 ms）
- 配点の衝突の修正で、衝突した項目は `lib:outward` のように接頭辞付きで `record-risk` する。書いた名前と打つ名前が変わる

## やらない場合

プロジェクトの側だけを見ている人は、共通層のルールと配点が何で、いつ変わったかを知る手段が無い。
共通層と同じ id の配点項目を書いたプロジェクトは、その層の項目と閾値が落ちたまま点が下がる。

## 採らなかった案

| 案 | 落とした理由 |
|---|---|
| phases と risks を各ツリーの層だけにし、共通層はルールだけにする（前の版） | 配点の下限が外れ、外から届く 1 コミットでレビュー要否を緩められる（敵対的レビュー 2 本の最重要の指摘） |
| 承認のときに合成した配点の定義を親に写し、その写しで数える | 定義は揃うが、承認した人の共通層が黙って決める。人が気づく場面が無い |
| `.risk.json` に数えた定義の出どころ（指紋）を残すだけ | ずれは後から追えるが、作業の前に人が気づく場面が無い |
| 写しを別のファイル（`.ccnavi/config/common/*.yml`）に置き、判定には使わない | 設定が複数の場所に分かれて分かりにくい（利用者の判断）。プロジェクトだけの設定は残せるが、見る場所が増える |
| 違っていたら着手を止め、人に写させる | 着手のたびに人の手が要り、止まった理由が「共通層が新しい」だけのことが多い。最初のレビューで見てもらえば足りる |
