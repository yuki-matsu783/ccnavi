## 前提

**i0055（PR #60）が既定のブランチへ入っていること。** `every` はまだ `main` に無い。
入る前に着手すると、直す対象の条件式そのものが存在しない。

## いま何がそうなっているか

`ccnavi/lint.py:1175` が、`additionalContext` を持つ allow のルールを見て `_broad` に掛ける。

```python
# once の文は文脈ごとに 1 度しか積まれないので、広さは咎めない。
if (rule.additional_context or rule.additional_context_file) and rule.decision == rules.ALLOW:
    why = _broad(rule)
```

すぐ上のコメントが言うとおり、**`Once` は既に外してある**。「文脈ごとに 1 度しか積まれない」から
広さを咎めない、という理屈で外している。`every > 1` も同じ理屈に乗る（積まれる回数が
当たった回数より少ない）のに、こちらは外れていない。`every` があとから入った欄だからで、
判断の理由が違うわけではない。

`_broad` 自身（1227 行）は対象の綴りの広さだけを見ていて、頻度は扱わない。
そう書いてあるとおりで、ここは触らない。

## 何をするか

### 1. 受入テスト（`acceptance`）

`tests/config/` に置く。書いた時点では落ちる。

| 何を言うテストか |
|---|
| `glob: "*"` + `additionalContext` + `every: 5` の allow は warn を出さない |
| 同じルールから `every` を外すと、いままでどおり warn を出す |
| `every: 1` は warn を出す（既定を明示しただけで、毎回渡る） |
| `every` が読めない値（`0` / `-1` / `"x"`）のときも warn を出す。判定は毎回渡る側へ倒れるので、広さの苦情も残す |
| `additionalContextFile` に本文を置いた `every: 5` のルールも warn を出さない |

最後の 2 つが要る理由。読めない `every` は `rules.py:428` が既定の 1 に倒すので、
`rule.every` を見れば自動的に warn が残る。**その挙動を落とさないための杭**で、
`every_written` のほうを見る実装に書き換えたときに落ちる。

### 2. 条件を 1 つ足す（`implement`）

`ccnavi/lint.py` の上の条件に、刻みが 1 以下のときだけ、を足す。

```python
# once の文は文脈ごとに 1 度しか積まれないので、広さは咎めない。
# 刻み（every）のあるルールも同じで、渡るのは当たった回数の N 分の 1。
# 読めない every は rules.py が 1 に倒すので、ここでも毎回渡る側として咎める。
if (
    (rule.additional_context or rule.additional_context_file)
    and rule.decision == rules.ALLOW
    and rule.every <= 1
):
    why = _broad(rule)
```

- **`rule.every` を見る（`every_written` ではない）。** 読めない値は `rules.py:428` が
  既定の 1 に倒しているので、`every` を見れば「実際に毎回渡るか」と一致する。
  書かれたままの値を見ると、`every: "x"` のルールが毎回渡るのに咎められなくなる
- **`_broad` は触らない。** あれは綴りの広さだけを見る関数で、頻度を知らないままにする
- `_every_problems`（1189 行）は別に走り続ける。`every: 0` は error、`every: 1` は無言、
  文の無い `every` は warning のまま

## やらないこと

- **`_broad` に `every` を渡すこと。** 広さと頻度を 1 つの関数に混ぜない
- **刻みの大きさで線を引くこと。** `every: 1000` でも咎めない（下の「失うもの」）
- **`.ccnavi/common/rules.yml` に `nudge-rule-check` を写すこと。** 写すのは人で、
  全文と手順は i0055-04 が `wip/design/nudge-rule-check.md` に置いた
- **文書（`ccnavi.md` §5.1 / `README.md`）。** `every` の説明は i0055 のフェーズ 4 が持つ。
  ここで足すのは lint の挙動 1 行で、そちらに載せるかは i0055 側の判断

## 得るもの

- **苦情が事実と合う。** いま出ている warn は、`every` を書いたルールに対しては誤り
- **`--lint` に「対処しない warn」を残さない。** 1 件でも居座ると、次に warn を見る人が
  飛ばす習慣を付ける。検証の出力は、出たら何かする状態に保つほうが効く
- **`nudge-rule-check` を狭めずに済む。** 狭めると `CLAUDE.md` や `docs/adr/` を直している
  ときに勧告が出なくなり、いちばん突き合わせが要る編集を外す（i0055-04 §4 の案 C）
- **`Once` と同じ理屈に揃う。** すぐ上のコメントが既に書いている理屈を、`every` にも当てるだけ。
  新しい判断を持ち込まない

## 失うもの

- **報告を 1 つ消す向きの変更。** `--lint` が言わなくなることが増える。`ccnavi` の検証は
  「緩める変更は慎重に」の側なので、これは素直に代償
- **刻みが大きすぎるルールを咎めなくなる。** `every: 1000` は実質「ほぼ届かない」ルールだが、
  広さについては無言になる。刻みの妥当さを見る目は、この変更の後はどこにも無い
- **`additionalContext` を持つ広い allow を書きやすくなる。** `every` を添えれば苦情が消えるので、
  「とりあえず `every` を書いて黙らせる」道ができる。文がコンテキストを食うこと自体は変わらない
- **検査の条件が 1 つ長くなる。** 3 つの `and` が並び、次に読む人が全部を頭に入れる必要がある

## やらない場合どうなるか

`nudge-rule-check` を写した時点から、`--lint` が warn を 1 件出し続ける。error は増えないので
検証は通るが、出力に「見なくていい行」が固定で 1 行入る。`every` を使うルールが増えるほど
同じ warn が増える。

## 代案

- **i0055 のフィードバック対応フェーズでやる。** `every` を入れた本人が続けて直すので、
  文脈が近い。**ただし `feedback:` を足せるのは全体計画の最後のレビュー（フェーズ 4 docs）が
  済んでから 1 回だけ**（`ccnavi.md` §9.4）なので、i0055 が最後まで進むまで着手できない。
  この番号で独立に立てれば、i0055 が `main` に入った直後に始められる
- **`_broad` の中で `every` を見る。** 呼ぶ側の条件が伸びない。代わりに、綴りの広さだけを
  見ると書いてある関数が頻度も見ることになり、関数の説明を書き直すことになる
- **warn を info に落とす。** 報告を消さずに目立たなくする。代わりに `--lint` に
  「事実と合わない info」が残り、消す理由が将来もっと薄くなる
- **`nudge-rule-check` の `glob` を狭める**（i0055-04 §4 の案 C）。lint を触らずに済む。
  代わりに勧告の対象が狭まる。利用者は承認時にこれを採らないと決めた
- **何もしない**（同 案 B）。同じく利用者が採らないと決めた
