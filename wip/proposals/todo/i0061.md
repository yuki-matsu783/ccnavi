# ワークスペース外を指す `{!root}` をルールの語彙に足す

## 何を足すか

`regex` の中で使える合言葉 `{!root}` を 1 つ足す。読み込み時に「ワークスペースルートで
始まらない」を意味する式へ展開する。展開先は先読みを使わない。

```yaml
deny:
  - id: outside-workspace
    match: Write|Edit|NotebookEdit
    regex: '^{!root}'
    message: ワークスペースの外です。…
```

## なぜ要るか

いま書けるのは「外の置き場を名指しする」形までで、i0055 で足した `outside-temp` が
まさにそれ（一時ディレクトリを 4 環境ぶん並べる）。名指しは漏れる。列挙に無い場所へ
書かれれば素通りする。「中でなければ外」と書ければ漏れない。

## 決まっていること（利用者の判断）

| 論点 | 決定 |
|---|---|
| 書き形 | `{!root}` の合言葉を `regex` に足す。`glob` では使えない |
| ルートが 256 字以上 | `--lint` の **error** で名指しする |
| 生成できないときの実行時の倒れ方 | そのルールの `match` に並ぶツールを**まるごと止める**（fail-closed） |

## 生成する式の形

ルートを 1 文字ずつ「ここで終わる／ここが違う／ここは同じ」に分解した入れ子にする。

```
^(?:$|[^c]|c(?:$|[^:]|:(?:$|[^\\/]|[\\/](?:$|[^u]|u(?:…)))))
      └──┘ └─┘ └┘
    ルートより上  綴りが違う  同じなら次の文字へ
```

最後まで一致した先に `(?:$|[^\\/])` を置いて、`…/ccnavi-fork/x` のように前置きが
一致して続く綴りを「外」と数える。

**繰り返し（`+` `*`）を 1 つも含まない。** 各段の選択肢は最初の 1 文字で排他なので、
戻る余地が無い。破滅的バックトラッキングの条件に当たらない。

## 測ったこと

実測済み（`scratchpad/demo2.py`・`demo3.py`・`demo4.py`。ルートは 36 字）。

| | 式の長さ | 組み立て | 1 回の判定 |
|---|---|---|---|
| 今の `main-tree` | 143 字 | — | 0.81 μs |
| 今の `outside-temp` | 159 字 | — | 2.28 μs |
| **入れ子型（採用）** | 475 字 | **2.03 ms** | **3.47 μs** |
| 平ら型（不採用） | 1,485 字 | 3.19 ms | 8.21 μs |

- 判定は 3.47 μs。PreToolUse の期限 3 秒に対して 0.0001%
- ルートを 236 字まで伸ばしても 21.85 μs で、**比例して伸びるだけ**（爆発しない）
- 組み立ては毎プロセス走る。今の `rules.yml` 一式の読み込み 24.29 ms に対して **+8%**
- 平ら型は式が 2 乗で伸びる（436 字のルートで 141,365 字・481 ms）ので採らない
- 正しさは 10 通りのパスで確認済み。`ccnavi-fork`（前置き一致）、ルートより上、
  区切りが `/` の綴り、全部小文字の綴り、別ドライブ、すべて期待どおり

### 256 字の根拠

Python 3.12（再帰の上限 1000）では、**ルート 494 字で `RecursionError`** になる。
256 はその半分以下で、壁に当たる前に止まる。加えて Windows の `MAX_PATH` は 260 なので、
256 字のルートはその時点で実用にならない。余裕を数字で持っておくほうが、
Python の版が変わって再帰の上限が動いたときに黙って壊れない。

## 得るもの

- 「中でなければ外」が書けるようになり、名指しの列挙が漏れる問題が消える
- 展開結果は先読みも繰り返しも含まないので、既存の `_unsupported` の契約を崩さない
- 判定の費用が実測で分かっており、期限に対して 5 桁の余裕がある

## 失うもの・代償

- **ルールの語彙が 1 つ増える。** 覚えることが増え、`--explain` に出る式が人の読めない
  長さになる（475 字）。書いた綴り（`^{!root}`）のほうを出す実装が要る
- **合言葉なのに断片として合成できない。** `{!root}` は「先頭から丸ごと」の式に展開されるので、
  `^{!root}[\\/]foo` のような書き方は意味を持たない。`{root}` と対に見えて性質が違う。
  lint で「`{!root}` の後ろに何か続いている」を warn にして補う
- **組み立てが毎回 +2 ms。** 今は 24 ms なので +8%。ルールを何本も `{!root}` で書くと
  その本数ぶん積まれる。1 本に抑える運用が要る
- **fail-closed の代償。** ルートが 256 字以上の機械では、そのルールの `match` に並ぶ
  ツールが全部止まる。`Write|Edit|NotebookEdit` と書いてあれば、そのルールを消すまで
  一切書き込めない。回復の手は「ルールを消す」だけで、それ自体が Write を要る。
  **`.ccnavi/common/rules.yml` は deny で守られているので、利用者が手で消すことになる。**
  設計フェーズでこの回復経路を詰める（`CCNAVI_MODE=dry-run` で抜けられるが、
  それは守り全部を降ろすことでもある）
- **「外」が広すぎる危険。** `deny: ^{!root}` を素朴に書くと、他リポジトリの参照、
  他ツールの出力先、そして CLAUDE.md が正規の逃げ道として書いているセッションの
  スクラッチパッドまで一度に塞がる。**道具を用意することと、それを使ったルールを
  置くことは別**で、このチケットは道具までとする

## やらない場合

今のまま。外を指したいときは `outside-temp` のように場所を列挙する。漏れは残るが、
範囲が目で読める形には収まっている。実際 `outside-temp` は列挙で足りている。

## 代案

1. **ルールに `outside: root` の欄を足す。** `glob` とも組めて、`--explain` に「外」とだけ
   出せる。断片として合成できない問題も起きない。欄が 1 つ増える代わりに、
   `glob` / `regex` との組み合わせを lint が見る必要がある。**利用者は `{!root}` を選んだ**
2. **判定側に「ルートの中か」の関数を持ち、正規表現に展開しない。** いちばん速く、
   再帰の壁も無い。ただしルールファイルから条件を書けなくなり、組み込みルールに
   なってしまう（ルールは人が持つ、という構造から外れる）
3. **`(?!...)` の禁止を `{!root}` の展開時だけ免除する。** 実装は数行で済むが、
   「エンジンをまたいでも同じ意味」の契約が崩れる

## 承認のときに決めてほしいこと

**`.claude/skills/ccnavi-config/references/add.md` が範囲外。** ルールの書き方を説明して
いるのはこのファイルで、`{!root}` を足すなら当然ここも直す必要がある。しかし
`docs` フェーズの `scope` は `README.md` `ccnavi.md` `requirements.md` `HANDOVER.md`
`docs/*` `CONTEXT.md` `CLAUDE.md` で、`.claude/skills/*` を含まない。

どちらかを選んでほしい。

1. `phases.yml` の `docs` の `scope` に `.claude/skills/*` を足す（人の設定なので利用者が置く）
2. スキルの更新は別チケットにする

足さないまま進めると、実行ファイルは新しい語彙を持っているのにスキルは古い説明を
配り続けることになる。
