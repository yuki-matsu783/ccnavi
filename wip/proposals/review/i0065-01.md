# Chrome 拡張の Python 側が置き場の env を読まないことの受入テストを書く

親 i0065 のフェーズ 1（acceptance）。実装（`chrome-extension/`）と文書には触らない。

## 書くもの

`tests/ticket/test_core.py` に足す。置き場の確かめは `_placement` を直に呼ばず、入口の `handle`
（`op` が `placement` や `board` の要求）を通す。`_placement` の引数の形はフェーズ 2 で決めるので、
試験がそれに縛られないようにする。

| # | 確かめること | 実装前 |
|---|---|---|
| B1 | 要求の `settings`（統合先の `.claude/settings.json` の中身）の `env` に `CCNAVI_TICKETS_PROPOSAL`・`CCNAVI_TICKETS_APPROVED`・`CCNAVI_PROJECT_HOME` を既定と違う相対パスで入れても、`placement` の答えが既定の置き場（`settings.DEFAULT_TICKETS`・`DEFAULT_APPROVED`・`DEFAULT_PROJECT_HOME` から組んだ `tickets`・`approved`・`layer_dir`・`integration_paths`・`branch_paths` など）を返す | 落ちる |
| B2 | 同じ 3 つに絶対パス（`/x`・`C:/x`・`~/x`）を入れても `error` を返さず、B1 と同じ既定の置き場を返す | 落ちる |
| B3 | 判定まで通る操作でも同じ: `CoreHarness` の手元のツリーから組んだ `board` の要求に、置き場を既定から外す `env` を持つ `settings` を足しても、`settings` が無いときと同じ答えになる | 落ちる |
| B4 | `ccnavi_chrome.py` が `settings` の env 名の定数を参照しない。ソースを `ast` で読み、`settings.<名前>_ENV` の属性参照が 1 つも無いことを見る。併せて、`settings` から `TICKETS_ENV`・`APPROVED_ENV`・`PROJECT_HOME_ENV` を一時的に外した状態でも `ccnavi_chrome.py` を読み込める（i0064 で定数が消えても import で落ちない） | 落ちる |
| B5 | 手元のプロセスの環境変数に置き場の 3 つを入れても、`placement` の答えは既定のまま（`_environ` が他の ccnavi の変数を外す役目の見張り） | 通る（回帰の見張り） |

- 新しい試験は `CoreChromeTest` の見本（`test/fixtures/core-scenarios.json`）に載せない。見本は
  `chrome-extension/` 配下でこのフェーズの範囲外なので、`keep_scenario` を呼ばない別の組
  （`CoreHarness` を継ぐもの）に置く
- B4 で `settings` の属性を外すときは、試験の終わりに必ず戻す（`addCleanup`）。他の試験に漏らさない
- 統合先の `settings.json` が JSON として読めないときの扱い（今は断る）は、フェーズ 2 で `settings` を
  読むのをやめるかどうかで変わるので、ここでは試験を置かない

## 終わりの条件

- 既存の `CoreChromeTest` は今のコードで通る（`uv run python -m unittest tests.ticket.test_core`）
- B1〜B4 は今のコードで落ちる。落ちる理由が「`ccnavi_chrome.py` がまだ env を読む・定数を参照する」
  ことだけで、試験の組み立ての誤り（import の失敗・ツリーの組み損ね・型の誤り）ではないことを確かめ、
  落ちた試験ごとに理由を報告に書く
- B5 は今のコードで通る
- `uv run --with ruff ruff format --check .` と `uv run --with ruff ruff check .` が通る
- `chrome-extension/`・`ccnavi/`・`docs/` に差分が無い

## 得るもの

- 実装の子（フェーズ 2）が、落ちている試験を通す形で進められる
- i0064 で env 名の定数が消えたときに Chrome 拡張が import で落ちないことを、i0064 を入れる前から
  試験で見張れる（B4）

## 失うもの

- **フェーズ 2 が済むまで、親のブランチの `tests/` に落ちる試験が残る。** 統合先へ戻すのは全フェーズが
  済んでからなので親のブランチの中だけの話だが、その間 Stop hook の試験が失敗を報告し続ける
- B4 のソースを読む試験は、綴り（`settings.X_ENV` の形）に依る。別名で import して参照すると
  見落とすので、読み込みの試験（定数を外して import）と 2 段で見る

## やらない場合

実装と合格線が 1 つの子に混ざり、何を満たせば終わりかが差分から読めなくなる。env 名の定数を
参照しないことは、i0064 を main に入れて import で落ちるまで気づけない。
